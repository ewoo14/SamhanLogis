## 1. 점검 결과 (정찰)
- **auto-update 메커니즘 없음**: `clients/desktop/electron-builder.yml`(.exe 빌드)만, **electron-updater/autoUpdater 미사용**(소스 grep 0). 현 버전 `package.json` `0.1.0`.
- 즉 현재는 개발자가 새 .exe 빌드해도 사용자에게 **자동 알림/업데이트 경로 없음**. 수동 재설치만.
- (모바일 에픽 Option A 채택 시 웹 버전은 "항상 최신"이라 별도 — 새로고침 안내 패턴.)

## 2. 요구사항 (개발책임자)
- 개발자 신규버전 배포 → 사용 중/접속 시 **업데이트 팝업** → **강제 업데이트** 후 사용 가능.
- 개발자가 **개발내역 메모(릴리스노트)** 작성.
- 팝업 버튼 **'확인'·'다시 보지 않기'** 2개.

## 3. ⚠️ 정합 이슈 (개발책임자 확인 필요)
"**강제 업데이트**(해야 사용 가능)" vs "**다시 보지 않기**"는 상충. 해석 옵션:
- (a) **2단계 모델**: 강제(major/critical)=업데이트 안 하면 사용 차단('확인'만, 다시보지않기 없음) / 권고(minor)='확인'+'다시 보지 않기'(해당 버전 알림만 숨김).
- (b) **단일 강제**: 항상 강제, '다시 보지 않기'=이번 세션만 숨김(다음 접속 시 재노출).
- (c) **릴리스노트 알림형**: 업데이트는 자동, 팝업은 "무엇이 바뀌었는지"(릴리스노트) 안내. '확인'=닫기·'다시 보지 않기'=이 버전 노트 재노출 안 함.

## 4. 설계 옵션 (개발책임자 결정)
- **Option A — Electron auto-updater(electron-updater) + 릴리스 서버**: GitHub Releases/S3에 새 버전 게시 → 앱이 자동 감지·다운로드·강제 재시작. 릴리스노트는 게시 메타. Electron 표준. (모바일 웹은 별도.)
- **Option B — 자체 버전체크 API + 인앱 팝업**: 게이트웨이 `GET /app/version`(최신 버전+최소 강제버전+릴리스노트) → 앱이 기동/주기 폴링·현재버전 비교 → 팝업(강제 시 차단). 개발자가 **릴리스노트 관리 화면**(admin)에서 버전/메모 등록. 웹/Electron 공통 적용 용이.
- **Option C — 하이브리드**: 다운로드/설치는 electron-updater, 강제/릴리스노트 정책은 자체 API(B). 가장 유연·복잡.
