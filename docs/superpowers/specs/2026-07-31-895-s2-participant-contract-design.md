# 일정 대상자 집합 정본·단건 조회 설계

## 목표

Issue #895 후속 슬라이스 2에서 일정 접근 권한을 활성 `schedule_participants` 집합 하나로
일원화하고, 대상자만 단건 상세를 읽을 수 있는 백엔드 계약을 완성한다.

## 범위

- 기간 목록 조회에서 작성자 `ownerId` 조건절 우회를 제거한다.
- 정상 생성 경로의 작성자 활성 대상자 행 포함을 유지한다.
- 작성자 대상자 행이 없는 legacy 일정은 작성자에게도 목록에서 숨긴다.
- `GET /admin/groupware/schedules/{scheduleId}`를 추가한다.
- 단건 상세의 존재하지 않음과 권한 없음은 모두 `404 NOT_FOUND`로 응답한다.
- 등록자 본인만 수정·삭제할 수 있는 객체 권한은 유지한다.
- 데스크톱 화면, 종일 일정, 부서·전사 공유, 알림은 범위에서 제외한다.

## 데이터 흐름

호출자 UUID는 `X-User-Id` 헤더에서만 읽는다. 목록은 일정과 활성 대상자 행을 조회하고,
단건은 일정 ID와 호출자 대상자 행이 동시에 성립할 때만 반환한다. 상세 권한 조회는
`findVisibleById` 전용 저장소 메서드를 사용해 내부 권한 없는 `findById` helper를 공개
엔드포인트에 연결하지 않는다.

## 오류 정책

단건 상세에서 일정이 없거나 호출자가 활성 대상자가 아니면 같은 `NOT_FOUND`를 반환한다.
이렇게 하면 호출자가 임의의 일정 UUID로 일정 존재 여부를 탐색할 수 없다. PUT/DELETE의
작성자 전용 `FORBIDDEN` 정책은 변경하지 않는다.

## 테스트 전략

1. 기존 owner-less repository 회귀 단정을 먼저 반전해 현재 `ownerId OR` 조건에서 RED를
   확인한다.
2. 정상 POST 후 작성자 목록 조회가 1건이고, 대상자 POST 후 대상자 목록 조회가 1건인
   실제 MockMvc 경로를 검증한다.
3. 실제 POST로 만든 일정에 대해 대상자 상세 200, 비대상자 상세 404, 존재하지 않는
   상세 404를 검증한다.
4. 기존 수정·삭제 권한 테스트와 groupware-service 모듈 전체를 재실행한다.
5. 공유 PostgreSQL은 SELECT만 사용해 활성 일정 사용자별 기존 OR 조건과 새 EXISTS 조건의
   가시 건수를 변경 전후로 측정한다.

## 비범위

사용자 UUID는 API 내부 식별 payload로만 유지하며 화면 렌더링을 추가하지 않는다. 사용자
표시 표면을 만드는 다음 데스크톱 슬라이스에서 이름·부서·담당자코드만 렌더링한다.
