# #896 품목 수량 동기화 전수 정찰 및 규칙 모델 제안

> 대상: PR #948 / Issue #896  
> 성격: 기획 정찰 문서. 구현·코드 변경 없음.  
> 최우선 게이트: 수량이 금액으로 직결되므로 이관 전후 **품목별 수량·품목 선택·금액의 허용 오차는 모두 0**.

## 0. 결론

1. 현재 실행 포팅본 두 파일에서 최상위 품목 간 자동 수량 규칙을 **20개 코드 가족**으로 확인했다.
   - 홈멀티 8개(H-01~08)
   - 싱글중대형 3개(S-01~03)
   - 상업멀티/분기보드 9개(C-01~09)
2. 별도로 수량을 바꾸지만 #896의 최상위 품목 관계와 경계가 다른 동작이 4개 있다.
   - 운임/절삭 금액 입력→자기 수량 0/1(X-01)
   - 품목확장 OFF→확장행 0(X-02)
   - 세트 부모→구성품 수량 전파(B-01)
   - 구성품→세트 부모 수량 역산(B-02)
3. 단순 `{기준품목, 종속[{품목, 배수, 조건}]}`으로 H-01~06·H-08, S-01~03, C-01~08은 표현할 수 있다. 단, 런타임 품명 정규식을 저장하지 않고 **현재 카탈로그를 명시적 품목 관계로 펼쳐 시드**해야 한다.
4. 다음은 단순 모델에 넣지 않는 것이 안전하다.
   - H-07 홈 분기관: 여러 기준군의 합·차·하한·게이트가 결합된 집계식
   - C-09 분기보드: 배치 순서, 누적 용량 구간, 마지막 셀 강제, 수동 추가량을 쓰는 별도 알고리즘
   - B-01/B-02: 이미 `BundleComponent`/`BundleExpander`가 소유하는 세트 도메인
   - X-01/X-02: 행 입력 UX/표시 정책
5. 권장 경계는 **#896 = 동일 견적 카테고리의 독립 최상위 품목 간 수량 관계**이다. 세트 내부 구성, 옵션으로 선택할 구성품 종류, 가격/DC/VAT/단가 배분은 기존 도메인의 소유권을 유지한다.

## 1. 정찰 범위와 경로 실측

요청서의 다음 두 경로는 현재 워크트리에 존재하지 않는다.

- `tools/legacy-gas/estimate-app/views/index.ejs`
- `tools/legacy-gas/order-app/index.html`

함수명과 요청서의 기준 라인을 전역 검색한 결과, 요청한 실행 코드의 실제 위치는 다음과 같다.

| 역할 | 실제 실행 포팅본 | 실측 |
|---|---|---|
| 견적서 | `clients/web/estimate-app/views/index.ejs` | 19,626행, `recomputeHomeDerived` = `:8289` |
| 주문서 | `clients/web/order-app/index.html` | 9,698행, `recomputeHomePanels` = `:5033`, `recomputeHomeDerived` = `:5265` |

원본 감사 스냅샷도 별도로 존재하며 실행 포팅본과 파일 해시·행 수가 다르다.

| 감사 원본 | 실측 |
|---|---|
| `tools/legacy-gas/종합견적서/index.html` | 19,183행, `recomputeHomeDerived` = `:7900` |
| `tools/legacy-gas/거래처 발송 주문서/index.html` | 9,823행, `recomputeHomeDerived` = `:5103` |

`clients/web/estimate-app/README.md`는 `index.ejs`를 legacy Apps Script의 EJS 포팅본으로, `clients/web/order-app/README.md`는 `index.html`을 legacy 임베드 포팅본으로 명시한다. 따라서 아래 전수표는 **실행 포팅본 2개**를 기준으로 작성했다. `tools/legacy-gas` 한글 경로 원본은 회귀 대조용이며 #896 구현 대상에 포함할지는 개발책임자 결정이 필요하다.

### 정찰 방법

- 함수명: `recompute*`, `recalcCommAccessories`, `pushBranchPartsToCommFromBadges`
- 상태 쓰기: `homeQty.set`, `singleQty.set`, `commQty.set`
- DOM 직접 쓰기: 수량 input의 `.value = ...`, `dispatchEvent(new Event('input'))`
- 이벤트: 수량 입력, 옵션 변경, 화면 render, 초기 부팅, 스냅샷 복원
- 세트 경계: `defaultQty`, `part-qty-single`, `part-qty-comm`, `explodeSetParts`, `explodeCommSets_`

단순 상태 복사(`syncCommQtyFromDOM`)·합계 표시(`sync*Totals`)·초기화 버튼은 새 규칙으로 세지 않았다. 반면 다른 값에서 수량을 계산하는 모든 지점은 아래 표 또는 경계표에 포함했다.

- estimate-app과 order-app은 각 bootstrap에서 벌크 규칙을 읽어 동일한 평가기를 사용하면 된다.
- 거래처별 DC·옵션 기본값을 소유한 `dc-config-service`에는 관계를 중복 저장하지 않는다.

DB에서는 Product 내부 ID를 FK로 사용하되, API와 칩에는 `modelCode + 품목명`만 노출한다. UUID를 사용자에게 표시하지 않는다.

### 6.2 권장 저장 구조

#### `quantity_sync_rule`

| 필드 | 의미 |
|---|---|
| `rule_key` | 사람이 추적 가능한 안정 키. 예: `HOME_HOSE_1WAY_L` |
| `estimate_category` | `HOME_MULTI` / `SINGLE_SET` / `COMM_MULTI` |
| `name` | 관리 화면 표시명 |
| `enabled` | 활성 여부 |
| `aggregation` | 1차는 `SUM`만. 모든 기여를 원수량 스냅샷에서 합산 |
| `condition_json` | 제한된 타입 조건. 임의 JS/SQL 문자열 금지 |
| `inactive_behavior` | `ZERO` 또는 `KEEP`; 현 자동 파생은 대부분 `ZERO` |
| `conflict_policy` | `ADD` 또는 상호배타 그룹의 `REPLACE` |
| `priority` | 상호배타 조건 간 결정 순서. 같은 우선순위 충돌은 저장 거부 |
| `legacy_ref` | 이관 근거 코드 키/라인. 운영 계산에는 사용하지 않음 |

#### `quantity_sync_source`

| 필드 | 의미 |
|---|---|
| `rule_id` | 규칙 |
| `source_product_id` | 기준 Product 내부 FK |
| `factor` | 기준 기여 배수. 기본 1 |

#### `quantity_sync_target`

| 필드 | 의미 |
|---|---|
| `rule_id` | 규칙 |
| `target_product_id` | 종속 Product 내부 FK |
| `multiplier` | 합산 결과에 곱할 배수 |
| `rounding_mode` | `NONE` / `FLOOR` 등. 현 최상위 규칙 시드는 `NONE` |
| `display_order` | 칩·상세 표시 순서 |

조건 JSON은 다음 연산만 허용한다.

- `optionEquals`, `optionIn`
- `all`, `any`, `not`
- 허용된 option key: 기존 홈/싱글/상업 옵션 계약에 등록된 키만

품명 정규식, 함수명, 임의 expression 문자열은 저장하지 않는다. 현재 정규식 결과를 마이그레이션 시 **명시적인 source/target Product 행**으로 펼친다.

### 6.3 API 표현 예

```json
{
  "ruleKey": "HOME_1WAY_HOSE_L",
  "estimateCategory": "HOME_MULTI",
  "name": "홈 1Way → L형 유연호스",
  "sources": [
    { "productCode": "AJ020BN1PBC1", "factor": "1" },
    { "productCode": "AJ023BN1PBC1", "factor": "1" }
  ],
  "targets": [
    { "productCode": "HOSE-L-1WAY", "multiplier": "1" }
  ],
  "when": {
    "all": [
      { "optionEquals": ["homeNoHose", false] },
      { "optionEquals": ["homeHoseType", "L"] }
    ]
  },
  "aggregation": "SUM",
  "inactiveBehavior": "ZERO",
  "conflictPolicy": "ADD"
}
```

1:N은 `targets`를 여러 개 두면 된다. 홈 유선 리모컨은 같은 합계를 리모컨 본체와 키트 두 target에 각각 multiplier 1로 쓴다.

### 6.4 평가 순서

1. 사용자가 입력한 **최상위 원수량 Map을 불변 스냅샷**으로 만든다.
2. 활성 규칙의 source 기여량을 계산한다.
3. target별로 전 기여량을 합산한다.
4. 상호배타 조건과 `inactiveBehavior`를 적용한다.
5. 수동 잠금 overlay를 소비자 정책에 따라 마지막에 적용한다.
6. 완성된 target Map을 UI와 금액 계산에 한 번만 반영한다.

파생 target을 다시 source로 읽는 연쇄 계산은 1차에서 금지한다. 현재 코드도 실내기/실외기 원수량을 모으고 판넬·호스·리모컨 등 액세서리는 배제하는 구조다. 이 원칙은 순환과 호출 순서 의존을 없앤다.

### 6.5 저장 검증

- 같은 category 안에서만 연결. 명시적 승인 없는 교차 category 금지
- source=target 금지
- 동일 조건에서 같은 target에 `REPLACE` 규칙 2개 금지
- 순환 참조 금지
- 삭제/비노출 Product 연결 금지
- BUNDLE source→그 BUNDLE의 `BundleComponent` target 연결 금지
- 배수 범위와 소수 스케일 고정
- 규칙 저장 시 전체 그래프 검증 후 원자적 반영

### 6.6 표현 가능성과 잔존 하드코딩

| 규칙군 | 제안 모델 표현 | 판정 |
|---|---|---|
| H-01~06, H-08 | source를 현 카탈로그 품목으로 펼치고 옵션별 규칙 분리 | 완전 표현 가능 |
| S-01~03 | 대상 세트를 명시 source로 펼침 | 완전 표현 가능 |
| C-01~08 | 현재 정규식/HP/PUMP_MAP 결과를 명시 source→target 관계와 배수로 펼침 | 완전 표현 가능. C-08은 C-05에 흡수 |
| H-07 | 집계 그룹 3개, 빼기, 하한 0, 선행 게이트 필요 | **단순 모델 불가**. 1차 하드코딩 유지 또는 후속 `CLAMPED_DIFFERENCE` 타입 필요 |
| C-09 | 품목 수량뿐 아니라 보드 셀 순서·누적 용량·마지막 강제·수동 추가를 입력으로 사용 | **단순 모델 불가**. 분기보드 도메인 알고리즘으로 유지 |
| X-01/X-02 | 금액 입력/표시 옵션이 source | #896 관계 모델 비대상 |
| B-01/B-02 | 세트 구성과 양방향 편집 | 기존 Bundle 도메인 유지 |

권장하지 않는 안은 범용 문자열 수식(`eval`, JS expression, SQL fragment)을 저장하는 것이다. 수량→금액 경로에서 정적 검증, 사이클 검출, shadow 비교가 어려워지고 완료된 수식 빌더와 다시 겹친다.

## 9. 마이그레이션 제안

### 단계 0 — 정답 고정

구현 전에 현재 두 실행 파일의 legacy evaluator를 테스트 가능한 순수 입력/출력 경계로 감싼다. 코드를 고치는 단계가 아니라, 아래 golden을 만드는 단계다.

- 입력:
  - 원수량 Map
  - 홈/싱글/상업 옵션
  - 수동 잠금 Map
  - 카탈로그 snapshot
  - 단가/DC/반올림 config snapshot
- 출력:
  - 최종 품목별 수량 Map
  - 선택된 실제 target 모델
  - 품목별 단가·소계
  - 공급가액/VAT/총액

두 앱의 드리프트는 별도 golden으로 기록한다. 이 단계에서 임의로 통일하지 않는다.

### 단계 1 — 명시 규칙 시드 생성

1. 현 카탈로그 snapshot에 기존 정규식/모델 맵을 1회 실행한다.
2. H-01~06/H-08, S-01~03, C-01~08을 source Product→target Product 관계로 펼친다.
3. 각 행에 `legacy_ref`와 기존 옵션 조건을 기록한다.
4. C-08은 C-05와 같은 관계로 합치고 별도 중복 경로를 시드하지 않는다.
5. H-07과 C-09는 `legacy evaluator` 소유로 명시하고 설정 레코드를 만들지 않는다.
6. BUNDLE 내부 component target은 시드에서 제거하고 검증 실패 목록으로 남긴다.

신규 품목은 코드 정규식에 자동 편입되지 않는다. 견적품목 관리에서 개발책임자/권한 사용자가 chip으로 관계를 명시해야 활성화된다.

### 단계 2 — shadow 비교

두 evaluator를 같은 원수량 snapshot으로 병렬 실행한다.

```text
원수량 + 옵션 + 잠금
  ├─ legacy hardcoded evaluator → legacy target Map
  └─ config evaluator           → config target Map
                                 ↓
                      modelCode별 exact diff
```

diff는 다음을 모두 비교한다.

- 누락/추가 target 모델
- target별 정수 수량
- 수동 잠금 후 최종 수량
- 품목별 단가
- 품목별 소계
- 문서 공급가액·VAT·합계

한 항목이라도 다르면 cutover 금지다.

### 단계 3 — 기존 견적/주문 문서 before/after 금액 대조

기존 저장 문서를 replay corpus로 사용한다.

1. 견적 snapshot/주문 history에서 실제 문서를 추출한다.
2. 문서의 원 입력 수량과 옵션을 복원한다.
3. 당시 가격을 재현할 수 있도록 **bootstrap 카탈로그와 가격 config도 함께 snapshot**한다.
   - 현재 가격으로 과거 문서를 재계산하면 수량 이관과 가격 변동이 섞여 false diff가 난다.
4. 같은 입력을 legacy와 config evaluator에 각각 넣는다.
5. 업무 식별자(견적번호/주문번호)별로 다음을 exact 비교한다.

| 비교 항목 | 허용 차이 |
|---|---:|
| 최종 modelCode 집합 | 0 |
| 품목별 수량 | 0 |
| 품목별 단가 | 0원 |
| 품목별 소계 | 0원 |
| 공급가액 | 0원 |
| VAT | 0원 |
| 총액 | 0원 |

필수 corpus:

- 각 규칙 H/S/C 최소 1건
- 여러 source가 같은 target에 합산되는 건
- source 수량 0→양수→0
- 모든 제외 옵션
- 판넬/리모컨/호스 대체 옵션 전 조합
- 수동 파생수량 override 후 기준 품목 재변경
- 상업 SET HP 분해와 `+` 분기관
- 리뉴얼 필터 4개 source
- 분기보드 구간 경계값 직전/정확/직후
- 스냅샷 복원 직후
- 실제 저장 견적/주문 문서 전수 또는 최소 최근 운영기간 전체

### 단계 4 — 앱별 순차 cutover

기능 플래그:

- `LEGACY`: 기존만
- `SHADOW`: 기존 결과를 사용하고 config 결과는 diff만 기록
- `CONFIG`: config 결과 사용, 즉시 LEGACY rollback 가능

권장 순서:

1. 견적서 SHADOW
2. 견적서 CONFIG
3. 주문서 SHADOW
4. 주문서 CONFIG
5. 운영 diff 0 관찰 후 표현 가능한 18개 가족의 하드코딩 제거
6. H-07/C-09/X/B 경계 코드는 그대로 남기고 소유 주석·테스트로 잠금

### 단계 5 — 신규/변경 규칙 회귀

규칙 저장 시 대표 기준수량 0/1/2/최댓값으로 dry-run preview를 생성한다. 활성 규칙 변경은 audit history와 설정 버전을 남기고, 이미 저장된 문서를 소급 변경하지 않는다.

## 10. 테스트 게이트 제안

### 정적/단위

- 규칙 JSON typed validation
- source/target 존재·활성 검증
- 같은 target ADD 합산
- 상호배타 REPLACE 충돌 거부
- 순환 거부
- BUNDLE component 중복 거부
- inactive ZERO
- 수동 잠금 overlay
- rule version 고정

### golden matrix

- H-01~08, S-01~03, C-01~09 각각 독립 fixture
- 두 앱 드리프트 fixture 별도
- 옵션 Cartesian product는 pairwise로 줄이지 말고 target 모델이 바뀌는 모든 분기를 포함
- 금액은 정수 원 exact assertion

### mutation

다음 변형이 반드시 실패해야 한다.

- multiplier 1→2
- target 모델 하나 교체
- source 하나 누락
- ADD→REPLACE
- inactive ZERO→KEEP
- 공청/기본 조건 반전
- 수동 잠금 무시
- 견적/주문 중 한 앱의 드리프트 seed 삭제

### 운영 관찰

- `ruleVersion`, consumer(estimate/order), 업무번호, legacy/config diff 요약
- 사용자 UUID나 민감 원문은 로그에 노출하지 않음
- diff 발생 시 CONFIG 전환 자동 차단

## 11. 개발책임자 결정 필요 항목

1. **정본 파일 경계는 무엇인가?**

2. **앱 간 기존 드리프트를 어떻게 처리할까?**  
   (a) 이관 1차는 견적/주문 각자의 현행 결과를 그대로 시드 / (b) 도메인 정답 하나로 먼저 통일한 뒤 시드.

3. **규칙 source는 명시 품목인가 동적 attribute 조건인가?**  
   (a) chip으로 확인한 명시 Product 관계 / (b) `catM`, 품명 정규식, attribute가 신규 품목까지 자동 포괄.  
   **권장: (a)**. 분류 변경이 조용히 금액을 바꾸는 일을 막는다. attribute는 검색/초기 시드 보조로만 쓴다.

4. **H-07 홈 분기관을 1차 범위에 넣을까?**  
   (a) 후속 typed `CLAMPED_DIFFERENCE` 규칙으로 분리하고 1차에는 legacy 유지 / (b) 처음부터 범용 수식 모델에 포함.

   (a) 별도 분기보드 알고리즘으로 유지 / (b) #896 범용 규칙에 포함.  
   **권장: (a)**. 입력이 품목 수량만이 아니라 셀 배치·순서·누적 용량·수동 추가량이다.

6. **BUNDLE 경계 정책을 강제할까?**  
   “같은 BUNDLE의 구성품을 #896 target으로 선택”을 UI에서 숨기고 BE에서 400으로 거부할지 결정 필요.
