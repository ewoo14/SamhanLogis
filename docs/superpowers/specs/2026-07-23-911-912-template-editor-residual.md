## 결함별 실측 근거와 불변식

> PM 은 **불변식만** 말합니다. 구현 수단은 지시하지 않습니다.

### A. 좌표 기본값이 표시용이라 적용되지 않는다

```text
추가 직후          {coordLayerExists:false, elementPosition:"static",
                    inspectorShows:["x=0","y=0","w=100","h=10"]}
표시값 그대로 재입력  변화 없음
사람 키보드 경로     x 칸 클릭 → Ctrl+A → "0" 타이핑 → 여전히 static
h 만 11 로 변경     → coordLayerExists:true, position:"absolute"
```
`ElementInspector.tsx:225` 가 `geometry?.[key] ?? (w:100, h:10, 0)` 로 **geometry 가 없어도 값을 보여주고**, geometry 는 `:70 updateGeometry` 가 **`onChange` 에서만** 생성합니다. React value-tracking 상 **동일 값 입력은 `onChange` 를 내지 않아** 키보드로도 적용 불가입니다.

| # | 불변식 |
|---|---|
| **E1** | 패널이 보여주는 값은 **실제 저장 상태와 일치**한다 — 좌표가 없으면 없다는 것이 보인다 |
| **E2** | 사용자가 화면에 보이는 값을 그대로 받아들였을 때 **그 값이 실제로 적용**된다 |

### B. FIELD 본문 필드 참조가 구조적으로 불가능하다

**두 겹으로 막혀 있습니다.**
1. 문법이 한글을 못 받습니다 — `templateSchema.ts:365` `^body\.fieldRow\[[A-Za-z0-9_.-]{1,100}\]$` (**ASCII 전용**)
2. 매칭 대상이 key 가 아니라 **label** 입니다 — `DocumentRenderer.tsx:86-89` `fieldRows.find(f => f.label === fieldKey)`. 그런데 `approvalRenderModel.ts:124-127` 은 모델에 **`key` 를 싣지 않습니다**(`{label, value}` 뿐).

실서버 `GET /admin/groupware/approval-templates` 실측 — 실제 라벨 전량이 한글입니다:
```text
지출결의서   지출항목 · 금액 · 계정과목 · 지출일 · 적요
휴가신청서   휴가종류 · 시작일 · 종료일 · 사유
```
⟹ **실서버 라벨 집합과 binding 문법의 교집합이 공집합**입니다. 이 기능은 한 번도 동작한 적이 없습니다.

| # | 불변식 |
|---|---|
| **F1** | 편집기가 제공하는 참조 수단으로 **실제 존재하는 본문 필드를 가리킬 수 있다** |
| **F2** | 가리킬 수 없는 값을 넣으면 **사용자가 그 사실을 안다** — 빈칸으로 조용히 인쇄되지 않는다 |
| **F3** | 참조는 **선택**이 기본이다 — 사용자가 키를 외워서 타이핑하지 않는다 |

### C. 미리보기 인쇄가 넓은 창에서 겹친다

```text
1920×1080  ⓐ(화면 상태에서 바로 인쇄 = 실 사용자 경로)
             FWLROAWPMWAORRKD-10031 …  ← FLOWMARK-001 과 WRAPWORD103 이 겹쳐 인쇄(2줄 손상)
           ⓑ(인쇄 미디어 정착 후)  정상 10줄
2560×1300  ⓐ 겹침 5줄 · ⓑ 정상 10줄

편집기 미리보기 .paper 화면 폭   1440→562.8 · 1680→689.8 · 1920→816.8 · 2560→1155.4
인쇄 폭은 항상 793.7px(=210mm)   → 793.7 초과부터 조건 성립
```
`PositionedElementBand` 가 `getBoundingClientRect()` 로 초과분을 재 spacer 로 예약하는데, 그 값이 **React state 라 `window.print()` 의 동기 미디어 전환을 따라가지 못합니다.**

| # | 불변식 |
|---|---|
| **P1** | 예약 높이가 **인쇄가 실제로 일어나는 레이아웃 폭** 기준으로 결정된다 |
| **P2** | 미리보기에서 인쇄한 결과가 **실 결재문서 인쇄와 같은 배치**를 낸다 |
| **P3** | 검증은 **미리보기 용지 폭 > 인쇄 폭**이 되는 창 크기(1920 이상)를 포함해 잰다 |

⚠️ **실 결재문서 인쇄 경로는 정상입니다**(700/1024/1600/2560 네 뷰포트 대조군 전부 온전). 깨지 마십시오.

## 🚨 앞 슬라이스에서 비싸게 배운 것 — 이 트랙에 그대로 적용한다

#908 은 **fix 가 다음 결함을 낳은 것이 9연속**이었습니다. 원인은 두 가지였고 둘 다 검증 쪽이었습니다.

### 1. 실인쇄 폭에서 재라

`emulateMedia({media:'print'})` 는 **뷰포트를 그대로 둡니다.** 실제 인쇄는 **A4 용지 상자(794px)** 에서 레이아웃되므로, 좁은 뷰포트 + print 미디어 조합은 **사용자에게 존재하지 않습니다.**

`page.pdf` 마커 실험이 이를 확증했습니다:
```text
base        162,758B / 1page
+narrow639  162,758B / 1page   ← 완전 동일 = 죽은 규칙
+anyprint   163,434B / 2page   ← 양성 대조군(마커 기법 자체는 유효)
```
⟹ 그 조합을 대상으로 한 지적도, 그것을 고치려던 fix 도 **둘 다 헛것이었고**, 그 fix 가 **실재하는 HIGH 결함**을 만들었습니다.

🚫 **죽은 규칙을 새로 만들어 하네스만 GREEN 으로 만들지 말 것.**

### 2. 통과하는 폭만 골라 재지 마라

직전 하네스가 **375px 와 1280px 만** 스윕했는데 실측상 **정확히 그 두 폭만 통과**했습니다(1280 은 여유 0.81px).

| # | 불변식 |
|---|---|
| **V1** | 인쇄 관련 단언은 **실제 인쇄가 일어나는 레이아웃 폭**에서 측정한다 |
| **V2** | 반응형 단언은 최소 **12개 경계 폭**을 스윕한다 — `320·360·375·639·640·1100·1140·1152·1180·1280·1440·1600` (+ #911 때문에 **1920·2560 추가**) |
| **V3** | 검증은 **결함이 발생할 수 있는 입력**에서 측정한다 — 발생할 수 없는 입력의 `0` 은 증거가 아니다 |
