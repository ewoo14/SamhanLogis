## 2부 · 🚧 슬라이스 범위 (PM 결정)

이슈는 4앱인데 **두 형태가 섞여 있습니다**:

| 형태 | 앱 | "버전 업" 의 의미 | 필요 인프라 |
|---|---|---|---|
| **웹(Vite)** | 주문 웹 · 종합견적 웹 · 모바일 퍼블릭 웹 | 최신 index 재요청 = 새로고침 | 없음 |
| Electron 설치본 | 아로로지스 데스크톱 | 다운로드 → 설치 → 재시작 | **`electron-updater` 신설 + 코드서명 + 업데이트 피드** |

**이번 슬라이스 = 웹 3앱만.**

🔑 **아로로지스 데스크톱을 뺀 이유** — `electron-updater` 신설은 코드서명 인증서·업데이트 피드 URL·installer 빌드가 전제인데, `#910` 검증에서 **그 축이 현재 차단 상태**임이 확인됐습니다(`forceCodeSigning: true` 인데 인증서 부재, installer 단계 8회차 내내 미검증). 인프라가 없는 상태로 코드만 넣으면 **등록은 되는데 도달하지 않는** 지금과 같은 상태가 반복됩니다. 후속 슬라이스로 분리합니다.

**이번 슬라이스 밖**: 아로로지스 데스크톱 · 사용 중 알림(주기 폴링) · OTA

🚫 발견이 범위를 넘으면 **PR 코멘트로 목록만**. 새 이슈 등록 금지(개발책임자 사전 허락 사항).

## 3부 · 불변식 (구현 수단은 지시하지 않습니다)

| # | 불변식 |
|---|---|
| **M1** | 관리 메뉴에서 웹 3앱을 **각각 지정해 등록한 릴리스가 그 앱 사용자에게 도달**한다 — 등록만 되고 아무 일도 안 일어나면 안 된다 |
| **M2** | 🚨 **어떤 자동 동작도 저장되지 않은 사용자 입력을 소리 없이 잃게 하지 않는다.** 작성 중이던 주문서·견적서가 새로고침으로 사라지면 안 된다 — 알리고 **사용자가 선택**한다 |
| **M3** | **한 앱의 릴리스가 다른 앱에 영향을 주지 않는다** — 세 웹앱이 서로, 그리고 데스크톱·모바일과 오폭하지 않는다 (`#910` A1) |
| **M4** | **버전 확인 실패가 작업을 막지 않는다** — 조회 실패·404 는 fail-open (`#910` A4) |
| **M5** | 개발 빌드가 **차단되지 않는다** — `#910` 이 세운 sentinel 판정(`0.1.0-dev` 는 릴리스 순서·최소 지원 비교에서 제외)을 그대로 쓴다 |
| **M6** | **릴리스 산출물만 명시 버전을 요구**한다 — `#910` 의 개발/릴리스 경로 분리를 그대로 따른다. 세 앱의 평범한 `npm run build` 가 계속 동작해야 한다 |

### 📌 PM 결정 — 기존 자산을 재사용하고 새로 만들지 마십시오
`#910` 이 이미 만든 것: `scripts/app-build-version.cjs`(버전 해석) · `Semver`(판정) · `/app/version` API · 8식별자 · sentinel 처리 · `AppVersionGate` 패턴(데스크톱). **웹 3앱용으로 별도 체계를 새로 설계하지 마십시오** — 같은 축에 붙이십시오.

### 📌 PM 결정 — M2 의 해법은 구현자가 정합니다
*"알리고 사용자가 선택"* 이 불변식이고, 배너·모달·저장 후 새로고침 중 무엇을 쓸지는 구현자 판단입니다. 다만 **작성 중 데이터가 있는지 판단할 수 있어야** 하므로, 세 앱에 그런 상태가 있는지 먼저 읽으십시오.

## 4부 · 회귀 울타리

| 표면 | 잡아야 하는 것 |
|---|---|
| 도달 | 등록 → 그 앱에서 **실제로 안내가 뜬다**(존재 확인이 아니라 **실행**) |
| 오폭 | A 앱 등록이 **B·C 판정을 바꾸지 않는다**. "A 가 뜬다"만 재면 미검증 |
| **입력 보존** | 🚨 작성 중 데이터가 있을 때 **새로고침이 자동으로 일어나지 않는다.** 값을 넣고 확인 |
| fail-open | 404·네트워크 실패에서 앱이 정상 사용된다 |
| 개발 빌드 | 무주입 `npm run build` 3앱 전부 동작, sentinel 이 차단되지 않는다 |
| CI | 🚨 신규 테스트가 **실제로 실행되는 잡**에 들어간다. `order-app` 은 `tsc typecheck` 가 게이트이고 **vitest 만으로는 타입 오류를 못 잡는다**(기존 실측) |

🚨 **RED-first**: 각 불변식을 깨는 실패 테스트를 먼저 쓰고 **RED 원문 제출 후** 고치십시오.
🚨 **게이트가 진짜인지 증명**하십시오 — 오늘 하루에 `vi.mock`·`console.warn`·`toContainText`·타임존·`act()` 다섯 종류의 거짓 green 이 나왔습니다. 새 단정은 **고치기 전 코드에서 RED** 여야 합니다.
