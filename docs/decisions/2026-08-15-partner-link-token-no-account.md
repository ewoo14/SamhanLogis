# 거래처는 계정 없이 링크 토큰으로 — 귀속은 유지 (2026-08-15 개발책임자)

## 개발책임자 원문

> *"거래처는 계정으로 하지 않고 실제 데이터를 우리 앱에 전송할 때 매니저 계정의 권한으로 데이터를 넘기는 구조로 하면 어때?"*

## 🚩 제안 안에 질문이 둘 섞여 있었다

```
① 거래처가 로그인 계정을 갖는가          (인증)
② 들어온 데이터가 누구 것으로 기록되는가   (귀속·감사)
```

원안은 ①=아니오 · ②=매니저 였다. **그런데 둘은 분리할 수 있다.**

## 결정 — ①만 없애고 ②는 유지한다

```
✅ 채택   링크 토큰이 거래처를 식별한다
          계정·비밀번호 없음 · MAU 안 늘어남 · 감사 추적 유지
❌ 기각   매니저 권한으로 일괄 처리
❌ 기각   지금대로 거래처별 계정 유지
```

### 왜 ②를 매니저로 하면 안 되는가

`BaseEntity` 는 7개 감사 필드를 남긴다. 매니저 권한으로 넘기면 **모든 주문의 `created_by` 가 매니저**가 된다.

```text
주문이 수천 건 들어와도 전부 "매니저가 만들었다" 로 기록된다
⟹ 어느 거래처가 보냈는지 데이터로 알 수 없다
   분쟁 시("우리는 그런 주문 안 넣었다") 대조할 근거가 없다
   거래처별 주문 통계·이력도 못 낸다
```

🔑 **계정을 없애는 것과 귀속을 없애는 것은 다른 일이다.** 원안은 둘을 함께 없앴다.

### 왜 계정 유지도 아닌가

```text
활성 거래처 7,309곳 · 현재 발급된 로그인 계정 2개
⟹ 계정 발급·비밀번호 재설정·잠금 해제를 7,309곳 상대로 운영해야 한다
EAS 무료 티어 1,000 MAU 도 넘긴다 (초과 과금 없이 그냥 멈추는 구조)
```

## 🔑 이미 같은 패턴이 코드에 있다

```text
PublicSignatureResponse
  shareToken   base64url 64자 · signedAt + 30일 만료
  인수자가 /share/{shareToken} 으로 계정 없이 들어온다
```

**인수자(배송받는 사람)는 이미 계정 없이 서명한다.** 거래처 주문도 같은 형태를 쓴다.

## 🔒 이 설계가 지켜야 할 불변식

```text
1  🚨 토큰이 거래처를 식별한다 — 주문의 귀속이 매니저가 아니라 그 거래처여야 한다
2  🚨 권한 판정은 서버가 한다 — 토큰이 매니저 권한을 빌리는 구조가 아니다
   🔑 "계정이 없으니 매니저 권한으로" 가 되면 ②를 다시 잃는다
3  🚨 토큰 하나가 다른 거래처 데이터에 닿으면 안 된다
   자기가 보낸 것과 자기 것만 본다
4  토큰 만료·회수 경로가 있어야 한다
   🚩 인수자 토큰은 30일이다. 거래처 토큰의 수명은 별도로 정한다
      (거래처는 반복 사용이라 인수자와 성격이 다르다)
5  🚨 토큰이 URL 에 실린다 — 유출 시 영향 범위를 좁혀야 한다
   🚩 무엇까지 할 수 있는 토큰인지(제출만? 조회도?) 정해야 한다
6  🚫 사용자에게 UUID 를 보이지 마라 — 거래처 식별은 거래처코드다
```

## ⏳ 정찰이 답해야 할 것

```text
① 지금 partner_auth 계정 2개는 무엇에 쓰이고 있는가 (없애도 되는가)
② shareToken 구현을 재사용할 수 있는가 · 아니면 별도 축이 필요한가
   🚩 인수자 토큰은 1회성 서명, 거래처 토큰은 반복 제출이다
③ 거래처가 지금 어떤 경로로 주문을 넣는가 (order-app? mobile? 둘 다?)
④ 토큰 발급·전달을 누가 하는가 (매니저가 링크를 보내는가)
⑤ 기존 partner-order 의 공개 경로(gate-images·bootstrap·log)와 어떻게 맞물리는가
⑥ 거래처가 자기 주문 이력을 봐야 하는가 — 그러면 토큰이 조회 권한도 가져야 한다
```
