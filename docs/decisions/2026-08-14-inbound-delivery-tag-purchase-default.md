# 입고전표 배송태그 — `구매`를 명시 기본값으로 신설 (2026-08-14 개발책임자)

> 관련: [`2026-08-14-qr-lifecycle-correction.md`](2026-08-14-qr-lifecycle-correction.md) — QR 발행 대상 판정의 정본이 된다
> 트랙: `#1210`

---

## 개발책임자 원문

> *"맞아 **기본값을 '구매'로** 하고 나머지 **'차용', '반품', '회차' 이렇게 따로 설정**하게 하면 좋을 것 같아."*

---

## 🚩 왜 이 결정이 필요했나 — 실측이 먼저 있었다

QR 발행 대상을 *"구매·차용 입고"* 로 정했는데, **코드에 `구매` 태그가 없었다.**

```
DeliveryTag.java:17-27  전수 11종
  출고 8종  DAY 당일 · STACK 야적 · REGION 지방 · LOGEN 로젠택배
            GYEONGDONG_PARCEL 경동택배 · GYEONGDONG_FREIGHT 경동화물
            RENTAL 대여 · RETURN_RENTAL 반납
  입고 3종  RETURN_TRIP 회차 · RETURN 반품 · BORROW 차용
  ⟹ 구매 없음
```

실 DB 실측:

```sql
SELECT COALESCE(delivery_tag,'(태그없음)'), count(*)
  FROM slips WHERE slip_type='INBOUND' AND deleted_at IS NULL GROUP BY 1;

 (태그없음) |  61      ← 살아 있는 입고전표 전부
```

🔑 **`구매`가 "태그를 안 붙인 상태"로 암묵 표현되고 있었다.** 회차·반품·차용이 붙은 행은 0건이다.
컬럼도 `delivery_tag VARCHAR(30)` — nullable (`V1__init_slip_service.sql:27`). `CHECK` 제약은 없다.

### 🚨 암묵 기본값이 위험한 이유

```
"구매다"        를 표현하는 방법이 없고
"아직 안 골랐다" 와 구별되지 않는다
⟹ QR 발행 판정이 "null 이면 구매로 친다" 라는 추론 위에 서게 된다
```

이 상태로 QR 을 발급하면, 나중에 입력 누락으로 비어 있는 전표에도 QR 이 나간다. 그러면 **같은 물리 개체에 시리얼키가 둘** 생기고 되돌리기 어렵다.

## 결정

```
입고전표 배송태그 4종
  구매  ← 기본값 (명시적으로 존재한다)
  차용
  반품
  회차
```

🔑 **기본값이 "없음"이 아니라 "구매"다.** 사용자가 아무것도 고르지 않으면 `구매`가 선택된 상태로 시작하고, 나머지 셋은 골라서 바꾼다.

## 이 결정이 QR 판정에 주는 것

```
QR 생성   구매 · 차용
QR 미생성  반품 · 회차            ← 나갔던 개체가 원래 시리얼키로 돌아온다
🚨 그 밖    미생성 (fail-closed)   ← 새 태그가 생겨도 조용히 발급되지 않는다
```

🔑 이제 판정이 **enum 값 자체**를 근거로 선다. `null` 을 해석할 필요가 없어진다.
🚫 한국어 표시 라벨(`displayName`)로 판정하지 않는다 — 라벨은 FE 표시용이고 바뀔 수 있다.

## 🚩 기존 61건을 어떻게 하나

살아 있는 입고전표 61건이 전부 태그 없음이다. 결정에 따르면 이들은 `구매`다.

```
남겨 두면  null 과 구매가 계속 공존해 판정이 두 갈래로 남는다
채우면     의미가 하나로 모인다 — 이 결정의 목적이 그것이다
```

🚩 **다만 실제 업무 데이터를 쓰는 일이다.** 구현 트랙이 다음을 지켜야 한다.

```
① 채우기 전에 61건이 정말 전부 구매인지 다시 세고 원문을 남긴다
② 되돌릴 수 있게 한다 (무엇을 바꿨는지 식별 가능해야 한다)
③ 공유 DB 에 적용하기 전에 fresh Postgres 로 먼저 검증한다
```

## ⏳ 범위 밖 — 건드리지 않는다

```
출고전표도 태그 없음이 132건 있다 (태그 있는 것 38건)
🚫 이번 결정은 입고전표에 대한 것이다. 출고 기본값은 정해진 바 없으므로 손대지 않는다
```

## 부수 사실

`slips.delivery_tag` 에 `CHECK` 제약이 없다 — 값 추가에 제약 마이그레이션이 따라붙지 않는다.
