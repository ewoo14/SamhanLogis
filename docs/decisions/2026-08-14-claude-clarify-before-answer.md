# `#901` 클로드 대화 — 모호하면 되묻는다 (2026-08-14 개발책임자 결정)

> 트랙: `#1180`

## 개발책임자 원문

> *"사용자가 너무 모호한 질문을 했을 경우에는 **클로드가 질문을 했으면** 좋겠어. 예를 들어, **배차**라고만 하면 우리 배차 메뉴가 여러가지인데 **어떤건지 선택지를 제시하고 거기서 선택**하게 하면 좋지. 그렇게 해서 **확실한 내용을 사용자가 선택하게 한 다음 결과를 제시**해야 품질이 좋을거야."*

---

## 결정

```
모호한 요청  ❌ 추측해서 답한다
             ✅ 선택지를 제시하고 사용자가 고르게 한 뒤 결과를 낸다
```

**예 — 사용자가 `"배차"` 라고만 입력했을 때**

```
클로드: 배차 관련해서 어느 것을 말씀하시나요?
  ① 배차 등록
  ② 배차 현황
  ③ 배차 이력
  …
사용자가 고른다 → 그 다음에 결과를 낸다
```

---

## 🚨 이 결정이 지켜야 할 세 가지

### ① 선택지는 **실제로 존재하는 것**이어야 한다

🚫 클로드가 그럴듯한 메뉴 이름을 **지어내면 안 된다.** 이 프로젝트는 **가짜 데이터·목업 영구 배제**다.

```
선택지의 출처는 실제 메뉴·기능 목록이다
없는 메뉴를 제시하면 사용자가 그것을 고르고, 그 뒤는 전부 헛것이 된다
```

### ② 🔴 선택지는 **그 계정의 권한 안**이어야 한다

이것이 이 트랙의 게이트(**권한 우회 경로 0**)와 직접 맞물린다.

```
🚨 그 계정이 볼 수 없는 메뉴를 선택지에 넣으면
   "그런 메뉴가 있다" 는 사실 자체를 알려 주는 것이다
   ⟹ 축 1(그 계정의 업무 권한)을 클로드가 우회하는 셈이다

✅ 선택지는 축 0(클로드 사용 권한) 통과 + 축 1(그 계정 권한) 안에서만 만든다
```

🔑 **"고를 수 없는 것을 보여 주지 않는다"** 가 원칙이다. 권한 없는 메뉴는 선택지에서 **빠지는 것**이지, 보여 주고 거부하는 것이 아니다.

### ③ 되묻기도 **외부 전송 범위** 안이다

결정 2 — 모델로 나가는 것은 **사용자 질문 + 클로드가 호출한 API 응답만**.

```
선택지를 만들려고 메뉴 목록을 조회했다면 그것도 감사 로그에 남는다
🚫 선택지를 만들자고 DB 를 덤프하거나 전수 조회해 통째로 보내지 않는다
```

---

## 🚩 언제 되묻고 언제 바로 답하나

경계를 두지 않으면 **모든 질문에 되묻는 앱**이 된다. 그것도 나쁜 품질이다.

```
되묻는다      대상이 여럿이고 고르지 않으면 결과가 달라진다
              ("배차" — 등록인지 현황인지 이력인지)
바로 답한다    대상이 하나로 특정된다
              ("오늘 배차 현황 보여줘")
```

🚩 **경계 판단은 구현자가 정하고 근거를 남긴다.** 다만 **틀렸을 때의 비용**이 비대칭임을 고려한다 — 되물어서 한 번 더 클릭하게 하는 것보다, 잘못 추측해서 **엉뚱한 결과를 확신 있게 제시**하는 것이 훨씬 나쁘다.

## 🚩 가상 에이전트 상태에서도 이 흐름이 돌아야 한다

라이브QA 를 위해 가상 에이전트를 넣었다. **되묻기 흐름도 가상 상태에서 밟을 수 있어야** 검증이 된다.
🔒 단 가상 응답임이 화면·API·감사에 그대로 남아야 한다 — 되묻기 문구도 예외가 아니다.

## ⏳ 파생 미결

```
① 선택지 개수 상한 — 배차처럼 후보가 많으면 몇 개까지 보여 주고 나머지는 어떻게 하나
② 사용자가 선택지 밖의 답을 자유 입력하면 어떻게 하나
③ 되묻기가 몇 번까지 이어질 수 있나 (2단계 이상 좁히기를 허용할 것인가)
```
