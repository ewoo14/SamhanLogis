## Q1 — 외부 복수 생성: **N건 → N건 · 전부 성공 또는 전부 실패**

원 판매/구매전표 1건당 회계전표 1건이다. 하나라도 실패하면 **전부 되돌린다.**

🔑 이렇게 해야 **원천 1건별 삭제·재생성(Q3)과 재시도가 명확**해진다. 부분 성공을 허용하면 "어디까지 됐는지" 를 사용자가 추적해야 한다.
🚫 N건을 합산해 회계전표 1건으로 만드는 방식은 명세의 *"복수 생성"* 과 어긋나므로 채택하지 않는다.

## Q2 — 원장 인과: **문서원장 = 원 전표 즉시 · 총계정원장 = 회계전표 전기**

```
거래처 문서원장   원 판매/구매전표에서 즉시 반영      ← 명세 8번
총계정원장       회계전표 전기(POST) 시점의 분개
세금계산서        연결/발행만 담당                    ← 명세 10번
```

🔑 명세의 두 축(*"회계전표 없어도 원장 반영"* / *"연결 없으면 계산서 불가"*)을 둘 다 지키면서 **회계분개 시점**도 설명된다.

⚠️ **파생 과제** — Q2 를 이렇게 잡으면 **회계전표 삭제 시 총계정원장 분개를 어떻게 할지**를 Q3 과 함께 확정해야 한다. 명세 11번은 *"역처리가 아니라 삭제 후 재생성"* 이므로, 분개도 역분개가 아니라 **전기 취소 후 재전기**로 다뤄야 앞뒤가 맞는다.

## Q3 — 삭제 후 재생성: **DRAFT soft-delete · 전기된 것은 `VOIDED`**

```
DRAFT      soft-delete 후 재생성
POSTED     VOIDED 처리 후 재생성
연결된 세금계산서는 먼저 취소·연결해제
```

🔑 **hard delete 가 아니다.** 업무상 *"기존 회계전표를 폐기하고 새로 생성"* 으로 해석해야 `BaseEntity` 7 audit + Soft Delete 규칙과 양립한다. 감사 흔적이 보존된다.

## Q4 — 계산서 게이트: **전 메뉴 · 기존 19건은 legacy 읽기전용**

```
게이트 대상  목록 · 이력 · 신규 · 발행 · 묶음 · 수신 · 홈택스 · 출력  — 전부
기존 미연결  19건은 legacy 예외로 보존하되 읽기전용 (수정 불가)
```

🚩 정찰 실측 — 현행은 **묶음·수신 경로에만 게이트가 있고 일반 목록·발행은 우회 가능**하다. 그 구멍을 닫는 것이 이 결정의 실체다.

## Q5 — 일마감 미검증: **회계전표 생성·마감 차단**

할인율 또는 할인액을 **정정·확인해야** 진행된다.

🔑 명세 5번의 *"회계담당자가 적절한 금액인지 판단"* 을 **읽기 전용 경고가 아니라 실제 게이트**로 만든다.

## Q6 — 회계 권한: 🔄 **현행 유지 (회계담당자 + 관리자 + 마스터)**

생성·전기·삭제/재생성을 셋 다 할 수 있다. 권한 축소 없음.

## Q7 — 무결성 잔재: **착수 전 보정·격리**

집PC 실측:

| 항목 | 수 | 처리 |
|---|---|---|
| 삭제된 회계 매출전표 아래 활성 allocation | 1건 | **착수 전 공식 보정·격리** |
| CONFIRMED INBOUND · 거래처 코드 공백 UUID-only | 1건 | **착수 전 공식 보정·격리** |
| 활성 `slips` UUID-only | 9건 | 착수 전 보정·격리 |
| 활성 `tax_invoices` UUID-only | 13건 | **Q4 의 legacy 게이트 정책에 포함** |

🔑 **조인 키로 쓰는 코드 컬럼이 비어 있는데 UUID 만 채워져 있으면 그 조인은 조용히 0행을 낸다.** 그래서 착수 전에 정리한다 — 그 위에 기능을 얹으면 결함이 데이터 탓인지 코드 탓인지 가릴 수 없어진다.

⚠️ **회사PC 수치와 다를 수 있다.** 양 PC 시드가 크게 다르므로 보정 작업은 **각 PC 에서 다시 세고** 진행한다.
