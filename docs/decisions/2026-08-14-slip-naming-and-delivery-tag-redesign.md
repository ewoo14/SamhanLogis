## 1. 전표 명칭 통일

```
구매전표  →  입고전표
판매전표  →  출고전표
```

**메뉴 · 화면 제목 · 버튼 · 안내문 · 출력물 전부** 바꾼다.

### 🔒 권한 키(page-code)는 바꾸지 않는다

```
바뀐다 (사용자가 보는 것)   메뉴 · 제목 · 버튼 · 안내문 · 인쇄물
🚫 안 바뀐다 (내부 키)      purchases.slip.list · purchases.slip.edit
                            accounting.sales-slip.list · accounting.purchase-slip.list
```

🔑 이들은 `account_page_permissions` · `group_page_permissions` · `role_page_permissions` **세 테이블의 키**다. 바꾸면 전 계정 권한을 함께 옮겨야 하고, **하나라도 누락되면 그 화면이 안 열린다.** 표시와 키를 분리해 위험을 없앤다.

---

## 2. 배송태그 전면 재구성

### 입고전표 — 6종 (기본 `구매`)

| 태그 | QR |
|---|---|
| **구매** (기본) | ✅ 생성 |
| **차용** | ✅ 생성 |
| **대여반납** | ✅ 생성 |
| 반품 | ❌ |
| 착하반품 | ❌ |
| 회차 | ❌ |

### 출고전표 — 11종 (기본 `판매`)

```
판매 (기본) · 대여 · 차용반납 · 불량반납 · 직배 · 착하선조치
로젠택배 · 경동택배 · 경동화물 · 야적 · 지방
```

🔑 **입고·출고가 짝을 이룬다.** `차용`(입고) ↔ `차용반납`(출고) · `대여`(출고) ↔ `대여반납`(입고).

---

## 3. `당일`(DAY) → `판매` 로 **개명**

새 출고 목록에 `당일`이 없다. 실측하면 **살아 있는 전표 13건**이 쓰고 있고 마감시각 `00:01` 설정도 걸려 있다.

> 개발책임자 정정: *"**당일 → 판매로 변경한 거**라고 생각하면 될 것 같아."*

```
결정  폐기가 아니라 개명이다
      DAY 당일  →  판매 (출고 기본값)
      기존 13건은 의미가 유지된 채로 옮겨 간다
```

🔑 **처음에 PM 이 *"당일이라는 구분이 이력에서 사라진다"* 고 적었던 것은 틀렸다.** 사라지는 것이 아니라 그 자리를 `판매`가 이어받는다. 별도 보존 조치가 필요 없다.

### 마감시각도 승계한다 (개발책임자 확정)

```
DAY 00:01  →  판매 00:01
```

🚩 **이것이 145건에 영향을 준다.** 기존 당일 13건은 원래 걸려 있었지만, **태그없음 132건은 지금까지 마감이 없었고 이제 걸린다.**

```
전   태그없음 132건 — 마감 가드 없음 (언제든 수정 가능)
후   판매    145건 — 00:01 마감 가드 적용
```

🚨 **구현이 확인할 것** — 이미 마감시각이 지난 과거 전표들이 이 변경으로 **갑자기 수정 불가가 되지 않는지.** 소급 적용되면 업무가 막힌다. 적용 범위(앞으로 만드는 전표만인지, 기존 행까지인지)를 실측으로 확인하고 근거를 남긴다.

## 4. 🚩 `대여반납` QR 생성 — 앞선 원칙과의 관계를 기록해 둔다

PM 이 확인 요청했고 **개발책임자가 "지시대로 대여반납도 생성" 으로 확정**했다.

```
앞서 세운 원칙
  "이미 QR 이 생성되어 출고된 인스턴스가 다시 창고로 되돌아 오는 거니까"
  ⟹ 반품 · 회차 는 생성하지 않는다

대여반납은 다르게 다룬다
  ⟹ 대여 출고 시점에는 QR 을 붙이지 않고, 돌아올 때 발급하는 흐름으로 본다
```

🚨 **구현이 반드시 지킬 것** — 대여반납 스캔 시 **이미 시리얼키를 가진 개체면 새로 발급하지 않는다.**
같은 물리 개체에 시리얼키가 둘 생기면 그 순간부터 재고와 이력이 어긋나고 되돌리기 어렵다. *"대여반납은 생성 대상"* 과 *"이미 있으면 재사용"* 은 함께 성립해야 한다.

## 5. 진행 방식 — `#1210` 트랙에 함께

명칭 변경이 **131개 파일**에 걸치지만 배송태그와 같은 화면이라 한 트랙에서 끝낸다.
