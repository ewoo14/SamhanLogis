# 🔒 정찰 후 개발책임자 결정 2건 (2026-08-15)

## 결정 A — **Q1 대로 N건 → N건 으로 고친다**

```
Q1 결정   원천 전표 1건당 회계전표 1건 · 전부 성공 또는 전부 실패
현재 구현  외부 작성 1종뿐이고 N건을 회계전표 1건으로 합친다
          상세·일마감 생성 경로는 아예 없다
⟹ 현재 구현이 결정과 다르다. 구현을 고친다
```

🔑 **이렇게 해야 Q3(삭제 후 재생성)이 성립한다.** 합쳐 놓으면 *"어느 원천을 되돌릴 것인가"* 에 답이 없다.

🚨 **이미 합쳐서 만들어진 회계전표를 어떻게 다룰지 정해야 한다.**
```
그대로 두고 앞으로 만드는 것만 1:1 로 하는가
기존 것도 쪼개는가 — 쪼개면 전기된 것의 분개까지 건드려야 한다
🚩 구현 트랙이 실측(합쳐진 전표가 몇 건인가)하고 판단해 근거를 대라
   실 데이터가 0건이면 판단 자체가 필요 없다
```

## 결정 B — **Q5 를 서버 검증으로 옮긴다**

```
Q5 결정   일마감 미검증 시 회계전표 생성·마감 차단
현재      서버 검증 결과가 아니라 UI 의 amountVerified Boolean 을 본다
          그런데 UI 가 그것을 보내지 않는다
⟹ 금액 있는 마감은 409 가 되고, 회계전표 생성은 Q5 를 통째로 우회한다
```

🔑 **클라이언트 값을 믿는 게이트는 클라이언트를 고치면 뚫린다.** 서버가 일마감 검증 상태를 직접 확인한다.

🚩 UI 를 고쳐서 값을 보내게 하는 방식은 **채택하지 않는다** — 구조가 남는다.
