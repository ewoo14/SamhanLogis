# 🔒 정찰 후 개발책임자 결정 3건 (2026-08-15)

## 결정 A — 도구 호출은 **allowlist 만 열고 기본 deny**

```
정적 전수  매핑 핸들러 1,044개
  832  @RequirePermission(page, action) 로 축 1 확인됨
   89  @PreAuthorize 만
  123  두 선언 모두 없음
🚨 배차 취소 내부 API 는 계정 page/action 이 아니라 서비스 역할만 본다

결정  명시적으로 허용한 endpoint 만 도구로 노출하고 나머지는 전부 막는다
```

🔑 **범용 서버 API 호출기를 붙이면 그 순간 우회 통로가 생긴다.** allowlist 는 늘릴 때마다 *"이 endpoint 가 축 1 을 검사하는가"* 를 강제로 확인하게 만든다.

🚫 도구 표면에서 **제외**한다 — `/internal/**` · 서비스 토큰 경로 · 역할만 보는 endpoint · DB 직접 접근.
🔑 도구 실행기는 **사용자 계정 정체성을 보존**한 채 호출하고, 최종 endpoint 의 `@RequirePermission` 을 반드시 통과해야 한다.

## 결정 B — 되묻기 선택지 출처는 **서버 catalog 신설**

```
현재  계정의 page/action 목록은 조회 가능
      🚨 그러나 메뉴 이름·route·앱·노출여부의 정본 API 가 없다
      FE 하드코딩 메뉴와 권한 맵을 결합해야 한다

결정  서버가 메뉴 catalog 를 갖고 FE 와 클로드가 같은 정본을 쓴다
```

🔑 **정본이 없으면 선택지를 지어내게 된다.** 이 저장소는 가짜 데이터 영구 배제다.
🔑 FE 하드코딩과 어긋나는 일이 **구조적으로** 사라진다.
🚩 선택지는 `catalog ∩ 그 계정의 권한` 이다. 권한 없는 메뉴는 **빠지는 것**이지 보여 주고 거부하는 것이 아니다.

## 결정 C — 그룹방 owner 가 나가면 **자동 이전**

```
현재  나가기는 도메인 메서드만 있고 API/UI 가 없다 · owner 는 나갈 수 없다

결정  owner 가 나가면 다음 참여자에게 owner 를 넘기고 나간다
      마지막 참여자가 나가면 방은 보관하되 목록에서 감춘다
```

🚩 **대화 기록은 보관한다.** 감사·분쟁 때 필요하다. 방을 지우는 것과 목록에서 감추는 것은 다르다.
🚩 *"다음 참여자"* 를 무엇으로 정할지는 구현자가 정하고 근거를 댄다 (참여 순서·직급·입사일 등).
