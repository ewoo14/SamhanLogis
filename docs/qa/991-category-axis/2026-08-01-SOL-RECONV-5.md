### 사용자가 만들 수 있는 반례

1. 제품 A가 처음에는 `modelCode=OLD`, `modelName=OLD`이고, 전표 snapshot도 `OLD`를 저장한다.
2. 제품 관리 API로 A의 `modelName`을 `NEW`로 바꾼다. 이 API는 `modelCode=OLD`를 불변으로 보존한다.
3. 다른 제품 B의 `modelName`을 이제 비어 있는 `OLD`로 바꾼다. update 검사는 현재 active `modelName` 중복만 보므로 허용된다.
4. 과거 전표의 라벨 토큰 `OLD`를 구 방식으로 해소하면 immutable `modelCode=OLD`인 A를 찾는다. 반면 r5의 `lookupByModel("OLD")`는 현재 `modelName=OLD`인 B를 찾는다.
5. `effectiveProductMatch`는 exact 결과 B를 무조건 우선해 B의 가격·고정DC로 금액을 확정한다. 정당한 `AMBIGUOUS`/`UNKNOWN`도 아니고 **다른 제품으로 확정되는 역회귀**다.

사용자 권한이 있는 정식 `PATCH /products/{id}` 경로가 이 lifecycle을 만든다. 제품명 변경 후 `modelCode` 불변 계약은 전용 테스트로도 확인했다.

## (2) B-04·B-08 독립 RED 시도

### B-04 — **BLOCK**

r6 입력과 달리 “두 번째 allocation snapshot은 생성 당시 valid였지만 이후 제품 `modelName`이 변경됨”을 사용했다. 이 상태는 위 제품 PATCH API로 만들 수 있고, 전표 snapshot은 과거 모델을 그대로 가진다.

- 혼합 매출전표는 라인에 첫 원천의 `productName`을 공통 label로 저장하면서 allocation마다 모델·카테고리를 저장한다.
- 두 번째 snapshot 모델의 exact lookup이 rename 후 404이면 `effectiveProductMatch`는 두 번째 축도 공통 첫 label로 fallback한다.
- 따라서 두 번째 카테고리 축에 첫 상품의 productId/가격을 붙이는 원 B-04가 그대로 재발한다.
- 더 나쁘게 과거 모델 토큰이 다른 제품의 새 `modelName`으로 재사용되면, fallback도 없이 그 다른 제품을 exact로 확정한다.

이는 r6 테스트가 두 모델 lookup을 모두 성공하도록 mock한 조건 때문에 드러나지 않았다.

근거:

- r6 B-04 테스트가 두 exact lookup을 모두 성공시킴: `services/accounting-service/src/test/java/com/samhanair/logis/accounting/service/DailyClosingDetailServiceTest.java:561-590`
- 혼합 allocation도 공통 `line.getProductName()`을 label로 사용: `services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/MonthEndCloseService.java:360-375`
- exact 미매치 시 label fallback: `services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/MonthEndCloseService.java:513-523`
- 실제 생성 API가 source별 snapshot 축을 allocation에 저장: `services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/SalesAccountingSlipCreateAttemptService.java:88-110`

공유 DB 쓰기 금지 때문에 이 lifecycle의 POST/PATCH를 실제 shared service에 보내지는 않았다. 대신 정식 mutation 계약과 현재 판정 함수를 연결해 RED 데이터 흐름을 재구성했고, `update_modelNameChange_keepsModelCodeImmutable`를 현재 HEAD에서 직접 실행해 전제 계약을 확인했다.
