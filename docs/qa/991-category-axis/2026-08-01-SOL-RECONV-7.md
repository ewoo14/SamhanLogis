## 중간 기록

- 문서를 먼저 생성했다. 이후 코드 경로, 최소 반례, 실데이터 읽기 조회 결과를 순차 append한다.
- `git rev-parse HEAD`는 검증 대상 `2f3b0637a21daf745affe126587e9ca23fe09eb3`과 일치했다.
- r8의 “없음”은 두 층이다. 전표 `modelName`에서 축 토큰을 추출하지 못한 경우와, 축 토큰은 있지만 매칭된 제품의 불변 `modelCode`가 null인 경우다.
- 읽기 전용 DB 재집계(라인 자체 `is_deleted=false`, 직전 r6/r8과 같은 모집단): 제품 master `modelCode`가 없는 라인은 주문 2,048건 + slip 2,141건 = 4,189건이다. 이 가운데 축 토큰 있음 4,186건, 축 토큰 없음 3건이다.
- 4,189건 모두 snapshot `modelName`이 현재 권위 제품의 `modelName`과 정확히 일치했다. 현재 이미 다른 null-code 제품으로 향하는 재사용 충돌은 0건이다.
- 그러나 삭제되지 않은 null-code 제품이 100개(활성 96개) 존재하므로, 원제품 A의 `modelName` 변경 후 다른 null-code 제품 B가 과거 이름을 재사용할 수 있다. 이 lifecycle에서 4,186건은 r8의 `byModel.modelCode()==null` 허용으로 B를 확정할 수 있다. 축 토큰이 없는 나머지 3건은 모두 snapshot 품명이 현재 A의 제품명과 같아, A 제품명 변경 후 B의 제품명 재사용 시 라벨-only 분기로 B를 확정할 수 있다.
- 최초 DB 스크립트의 partner-order SQL은 모호한 `id` 때문에 실패했고, slip도 헤더 삭제 여부를 추가 제한해 직전 라운드 모집단과 달랐다. 그 실행 수치는 폐기하고 명시적 컬럼 및 라인 자체 `is_deleted=false`로 재조회했다.

## 최종 판정 — BLOCK

`modelCode` 없음 경로는 SOL-5 rename 역회귀의 우회로가 된다. 현재 DB에 이미 잘못 연결된 라인은 0건이지만, 정식 제품 PATCH로 사용자가 만들 수 있는 lifecycle에서 다른 제품의 가격·고정DC를 확정한다. r8 전제인 4,189라인 전부가 이 lifecycle의 후보이므로 실제 사용자 오작동 가능성이 있고 fix의 안전 가드로 볼 수 없다.

## 1. `modelCode` 없는 SOL-5 반례

### 축 토큰은 있고 master `modelCode`가 없는 4,186라인

1. 레거시 제품 A는 `modelCode=null`, `modelName=OLD`이고 과거 전표 snapshot은 `OLD`를 가진다.
2. 제품 PATCH로 A의 `modelName`을 `NEW`로 바꾼다. `modelCode`는 null로 남는다.
3. 다른 null-code 제품 B의 `modelName`을 이제 비어 있는 `OLD`로 바꾼다. 현재 활성 `modelName` 중복만 검사하므로 순서대로 실행하면 허용된다.
4. 과거 전표의 label 해소는 제품명 기준 A를 반환할 수 있지만, exact `lookupByModel("OLD")`는 이제 B를 반환한다.
5. r8은 exact B가 `MATCHED`이고 `byModel.modelCode()==null`이면 B를 즉시 반환한다. 따라서 A가 아니라 B의 가격·고정DC로 `VERIFIED`될 수 있다.

이 반례는 SOL-5와 동일한 이름 변경·재사용 lifecycle에서 A와 B의 불변 `modelCode`만 모두 null로 바꾼 것이다. 불일치를 비교할 식별자가 없는데 null을 정상으로 허용했으므로 재사용된 현재 이름 B가 확정된다.

근거:

- 축 토큰과 라벨을 각각 조회하고 effective match를 가격·고정DC에 사용: `services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/MonthEndCloseService.java:401-456`
- exact 제품의 `modelCode`가 null이면 즉시 허용하는 r8 분기: `services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/MonthEndCloseService.java:523-526`
- 제품 PATCH에서 `modelName` 변경 허용 및 현재 중복만 검사: `services/product-service/src/main/java/com/samhanair/logis/product/service/ProductService.java:516-527`
- exact 모델 조회는 현재 `model_name` 기준: `services/product-service/src/main/java/com/samhanair/logis/product/service/ProductService.java:151-180`

### snapshot 축 토큰 자체가 없는 3라인

1. 전표의 snapshot `modelName`에서 모델 패턴을 추출하지 못하면 `axis.modelToken()==null`이다.
2. r8은 이때 라벨 resolver 결과를 검증 없이 그대로 반환한다.
3. 실데이터의 해당 null-code 3라인은 snapshot 품명이 현재 권위 제품 A의 제품명과 모두 정확히 같다.
4. A의 제품명을 바꾸고 B가 과거 제품명을 재사용하면 라벨 resolver의 unique LIKE가 B를 반환할 수 있고, r8은 B를 그대로 확정한다. 제품 PATCH의 `name` 변경에는 중복 검사도 없다.

근거:

- 축 토큰 null이면 라벨 결과를 그대로 반환: `services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/MonthEndCloseService.java:516-521`

## 2. `modelCode`를 비우거나 누락시키는 경로

### 제품 PATCH의 `modelCode` 변경 — 없음

`PATCH /products/{id}`의 request에는 `modelCode` 필드가 없고, update는 `name`·`modelName` 등을 바꾸지만 `modelCode`를 건드리지 않는다. main 코드에서 `changeModelCode` 호출은 제품 create의 최초 설정뿐이다. 따라서 기존 non-null `modelCode`를 제품 PATCH로 바꾸거나 지우는 우회는 없다.

다만 이미 null인 100개 레거시 제품은 PATCH로 `modelName`을 바꿔도 null 상태가 유지된다. 위 반례는 바로 이 집합을 사용하므로 “PATCH로 지울 수 없음”이 r8을 안전하게 만들지는 않는다.

근거:

- update DTO에 `modelCode` 없음: `services/product-service/src/main/java/com/samhanair/logis/product/web/dto/UpdateProductRequest.java:16-33`
- 제품 PATCH endpoint와 update 호출: `services/product-service/src/main/java/com/samhanair/logis/product/web/ProductController.java:135-140`
- `modelCode` 불변 계약: `services/product-service/src/main/java/com/samhanair/logis/product/service/ProductService.java:509-527`
- 생성 시에만 `modelName.trim()`을 `modelCode`로 설정: `services/product-service/src/main/java/com/samhanair/logis/product/service/ProductService.java:469-490`

### snapshot 저장 시 누락 — 있음

- slip 생성 request의 `modelName`은 `@Size`만 있고 필수가 아니다. null이면 catalog `modelName`으로 fallback하지만 빈 문자열은 null이 아니므로 그대로 저장된다.
- slip 라인 추가도 같은 공용 저장 함수를 사용한다.
- slip 수정 request의 `modelName` 역시 optional이고, 수정 service가 값을 그대로 새 `SlipLine`에 저장한다. 따라서 editable 전표에서 null/blank snapshot을 저장할 수 있다.
- partner-order confirm은 master `modelCode`가 없으면 `modelName`으로 fallback하고, 주문 수정 request는 `modelCode`가 `@NotBlank`라서 이 두 경로는 snapshot 자체를 비우는 경로가 아니다.

## 3. 실데이터 읽기 전용 집계

모든 SQL은 기존 `samhan-postgres`에 `docker exec ... psql ... -c "SQL"`로 실행했고 `SET default_transaction_read_only=on`을 선행했다. Docker 재빌드·재기동과 DB 쓰기는 하지 않았다.

| 집합 | partner-order | slip | 합계 |
|---|---:|---:|---:|
| 비삭제 라인 | 2,052 | 2,791 | 4,843 |
| 현재 제품과 `product_id` 연결 가능 | 2,050 | 2,145 | 4,195 |
| 연결 제품의 `modelCode` 없음 | **2,048** | **2,141** | **4,189** |
| 그중 snapshot 축 토큰 있음 | 2,048 | 2,138 | **4,186** |
| 그중 snapshot 축 토큰 없음 | 0 | 3 | **3** |
| 현재 이미 다른 null-code 제품으로 확정될 재사용 충돌 | 0 | 0 | **0** |
| rename→재사용으로 반례 조건을 만들 수 있는 후보 | 2,048 | 2,141 | **4,189** |

제품 master는 비삭제 1,220개이며 `modelCode` 없음 100개(활성 96개), non-null `modelCode != modelName` 0개다. 4,189라인 모두 snapshot `modelName`이 현재 권위 제품의 `modelName`과 정확히 일치한다. 즉 현재 충돌은 아직 없지만, A를 rename한 뒤 다른 null-code B가 과거 이름을 재사용할 재료가 실재한다.

별도로 snapshot `modelName`의 SQL null/blank는 두 소스 모두 0건이었다. 다만 extractor 기준 축 토큰 없음은 전체 646건이고, 그중 r8 전제인 null-code 제품 연결 라인은 위 3건이다. SQL null/blank 0은 저장 API의 누락 가능성을 부정하지 않으며 현재 저장 상태만 뜻한다.
