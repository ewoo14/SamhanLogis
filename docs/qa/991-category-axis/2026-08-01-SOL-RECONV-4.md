## (1) `categoryKey` 보존이 복사·복원 자체를 깨뜨렸는가? — PASS

### 전표 복사

- `SlipLine.copyOf`는 원본과 별도의 `new SlipLine`을 만들면서 `source.categoryKey`를 마지막 nullable 인자로 전달한다. 기존처럼 `sourceOrderLineId`는 `null`로 끊는다: `services/slip-service/src/main/java/com/samhanair/logis/slip/domain/SlipLine.java:412-415`.
- 해당 생성자는 `categoryKey`에 null 검증이나 변환을 걸지 않고 그대로 대입하며, 금액 검증·계산 규칙은 종전과 동일하다: `services/slip-service/src/main/java/com/samhanair/logis/slip/domain/SlipLine.java:153-174`.
- DB 매핑도 nullable이며 수동/레거시 전표의 null 보존이 명시돼 있다: `services/slip-service/src/main/java/com/samhanair/logis/slip/domain/SlipLine.java:134-136`.
- 실제 복사 서비스는 활성 원본 라인마다 위 `copyOf`를 호출해 새 전표에 추가한다: `services/slip-service/src/main/java/com/samhanair/logis/slip/service/SlipDuplicateService.java:109-118`.

따라서 기존 데이터의 `categoryKey=null`은 새 객체의 nullable 필드에 그대로 들어갈 뿐 예외를 만들지 않는다. 복사 로직의 채번·라인 존재 검사·저장 계약도 이 변경으로 바뀌지 않았다.

### 협업 이력 캡처·JSON·복원

- 캡처는 각 활성 라인을 순서대로 매핑하면서 바로 그 라인의 `getCategoryKey()`를 같은 `SlipSnapshot.Line`에 넣는다: `services/slip-service/src/main/java/com/samhanair/logis/slip/domain/Slip.java:2029-2053`.
- `SlipSnapshot.Line`은 `categoryKey`가 nullable인 record이며 `@JsonInclude(NON_NULL)`이다. null이면 JSON에서 생략되고, 기존 14·13·11인자 생성자는 모두 새 인자에 null을 위임해 소스 호환을 유지한다: `services/slip-service/src/main/java/com/samhanair/logis/slip/revision/domain/SlipSnapshot.java:149-198`.
- 협업 캡처는 `slip.toSnapshot()`을 실제 ObjectMapper로 직렬화하고, 복원은 같은 포트의 ObjectMapper로 `SlipSnapshot`을 역직렬화한 뒤 도메인 복원·저장·RESTORE revision 캡처를 수행한다: `services/slip-service/src/main/java/com/samhanair/logis/slip/collab/SlipDocumentCollaborationPort.java:102-112`, `:226-247`.
- 일반 revision 복원도 DB의 `snapshot::text`를 ObjectMapper로 읽는다. 이 mapper는 unknown 속성 무시와 unknown enum→null을 허용하며 missing creator property를 필수화하지 않는다: `services/slip-service/src/main/java/com/samhanair/logis/slip/revision/service/SlipRevisionService.java:62-66`, `:322-333`.
- 필드가 없는 과거 라인 JSON은 Jackson record 역직렬화에서 새 참조형 component가 null이 된다. 해당 실제 legacy JSON 역직렬화 테스트가 통과했다: `services/slip-service/src/test/java/com/samhanair/logis/slip/domain/SlipSnapshotLineTest.java:35-49`.
- 복원은 snapshot의 라인마다 새 `SlipLine`을 만들고 `snapLine.categoryKey()`를 그대로 전달한다. 구 스냅샷은 이 값이 null이므로 nullable 생성 경로로 정상 복원된다: `services/slip-service/src/main/java/com/samhanair/logis/slip/domain/Slip.java:2159-2176`.

## (2) 보존이 잘못된 값을 나르는가? — PASS

### 원본과 같은 값인가 / 다른 라인의 축이 섞이는가

- 복사: `copyOf(target, source)` 한 번마다 오직 그 `source.categoryKey`를 새 라인 생성자에 전달한다. 컬렉션 인덱스나 외부 임시변수를 사용하지 않아 다른 전표·라인 값이 끼어들 경로가 없다: `services/slip-service/src/main/java/com/samhanair/logis/slip/domain/SlipLine.java:412-415`.
- 캡처: `this.lines.stream().map(line -> new SlipSnapshot.Line(... line.getCategoryKey()))` 구조라 각 snapshot line의 다른 필드와 같은 원본 line에서 축을 읽는다: `services/slip-service/src/main/java/com/samhanair/logis/slip/domain/Slip.java:2029-2052`.
- 복원: 현재 순회 중인 `snapLine.categoryKey()`를 바로 그 순회에서 생성하는 새 라인에 전달한다: `services/slip-service/src/main/java/com/samhanair/logis/slip/domain/Slip.java:2166-2176`.
- 값 보존 테스트는 `singleSets`가 복사본과 복원본에서 동일함을 확인했고 통과했다: `services/slip-service/src/test/java/com/samhanair/logis/slip/domain/SlipLineAmountOverflowTest.java:76-85`, `services/slip-service/src/test/java/com/samhanair/logis/slip/domain/SlipRestoreTest.java:43-57`.

### 복사본 수정이 원본 축에 영향을 주는가

- 복사본은 원본 `SlipLine` 참조를 재사용하지 않고 항상 별도 `new SlipLine`이다: `services/slip-service/src/main/java/com/samhanair/logis/slip/domain/SlipLine.java:412-415`.
- 복원도 기존 라인을 삭제 표시·컬렉션 제거한 뒤 snapshot마다 새 `SlipLine`을 생성한다: `services/slip-service/src/main/java/com/samhanair/logis/slip/domain/Slip.java:2159-2176`.
- `categoryKey`는 immutable `String` 값이고, 도메인에 이를 사후 변경하는 setter/mutator가 없다. 생성 후 라인 수정은 별도 엔티티의 상태를 바꾸므로 원본 축으로 전파될 공유 mutable reference가 없다: `services/slip-service/src/main/java/com/samhanair/logis/slip/domain/SlipLine.java:134-136`, `:153-167`.

따라서 복사본 수정이 원본의 `categoryKey`에 영향을 주는 사용자 오작동 경로는 확인되지 않았다.
