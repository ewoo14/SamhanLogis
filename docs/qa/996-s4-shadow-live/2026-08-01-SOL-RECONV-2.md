## (1) r2 canonical shadow 관측 복구 — PASS

canonical 판별 기준은 대소문자까지 정확한 `ruleKey=SINGLE_S03_CEILING_DRAIN_PUMP` 하나다. 거래처 요청이면 category로 먼저 조회한 비삭제 규칙에서 이 key만 남긴다(`QuantitySyncRuleController.java:41-46`, `QuantitySyncRuleService.java:116-124`).

직전 결함의 `legacyRef`와 둘 다 문자열 비교라는 외형은 같지만 의미는 다르다. `legacyRef`는 요청에서 임의로 넣는 설명 태그일 뿐 identity 결속이 없지만(`QuantitySyncRuleRequest.java:28-40`), `ruleKey`는 CRUD path와 활성 행 부분 unique index가 사용하는 natural identity다(`V24__quantity_sync_rule_schema.sql:80-82`, `QuantitySyncRuleService.java:290-317`). 따라서 일반 key에 `legacyRef=S-03`을 붙이거나 이름·legacyRef를 비슷하게 만드는 조합은 필터를 통과하지 않는다. 활성 exact key도 최대 1건이므로 일반 규칙이 canonical과 함께 섞이는 조합은 없다.

exact key 행의 source/target은 설정값이므로 고정 모델 문자열까지 canonical 판별에 포함하지 않는다. 대신 서버가 target 1개 및 source별 계수 parity를 강제하고(`QuantitySyncRuleValidator.java:465-503`), order-app이 category·집계·비활성 동작·조건·catalog·계수를 검증한 뒤에만 `ready`로 채택한다(`clients/web/order-app/src/quantitySync.ts:96-165`). 즉 exact key의 설정 오류는 범위 밖 identity 혼입이 아니라 해당 canonical 설정의 관측 `error`로 수렴하며 실제 주문 수량은 바꾸지 않는다.

실 API 증거는 두 겹이다.

1. 이번 fresh 격리 PostgreSQL API 실행에서 일반 key 1건과 canonical key 1건을 POST한 뒤 PARTNER GET은 canonical만 남겼다. 관련 SurfaceFixIT 전체 **4/4**가 통과했다(`QuantitySyncRuleSurfaceFixIT.java:140-170`).
2. 직전 r2 라이브 QA도 실제 API로 canonical 1건과 `QA996_R2_GENERAL_S03`(`legacyRef=S-03`) 1건을 만들었다. 거래처 응답은 canonical **1건**, 일반 규칙 혼입 **0건**, shadow `status=ready`였다(`live-2026-07-31/REPORT-2.md:45-87`).

현재 실 DB는 활성 규칙이 0건이므로 현재 partner 응답 영향은 canonical 0건·범위 밖 혼입 0건이다. r2가 범위 통제를 무너뜨렸다는 실제 사용자 오작동은 재현되지 않았다.

## (2) legacyRef 일반 규칙의 무결성 예외 제외 — PASS

정당한 shadow 규칙의 identity는 exact canonical key다. order-app은 `legacyRef=S-03`만인 규칙을 exact 규칙으로 선택하지 않는다(`clients/web/order-app/src/quantitySync.ts:105-116`). 따라서 r2가 guard에 다시 포함한 대상은 정상 shadow 규칙이 아니라 일반 규칙이다.

품목 상태·노출·카테고리 판정과 BUNDLE 구성품 판정은 모두 guard 후보를 만든 뒤 exact canonical key를 제외한다(`QuantitySyncRuleService.java:193-212`, `:227-254`, `:263-264`). 실제 품목 변경 호출부는 이 결과가 비었을 때 정상 진행한다(`ProductService.java:741-755`, `BundleComponentService.java:743-750`).

fresh 격리 API에서 다음 반대 방향을 직접 확인했다.

- exact canonical 규칙이 참조하는 품목의 노출·카테고리 PATCH: **HTTP 200, 1/1** — 정상 shadow 규칙이 변경을 막지 않았다(`QuantitySyncRuleSurfaceFixIT.java:118-137`).
- 일반 key + `legacyRef=S-03` 규칙이 참조하는 품목을 규칙 불만족 상태로 바꾸는 PATCH: **HTTP 409, 1/1** — 일반 규칙의 무결성 보호가 복구됐다(`QuantitySyncRuleSurfaceFixIT.java:173-192`).

읽기 전용 실 DB 전수 계수는 활성 canonical 규칙 0건, 활성 legacy-only 일반 규칙 0건, 활성 source/target 0/0건이다. 따라서 현재 r2 때문에 새로 막히는 일반 규칙 0건·distinct 품목 0건이며, 정당한 shadow 규칙 때문에 품목 상태·카테고리·구성품 변경이 막히는 실 데이터도 **0건**이다.

## 내가 보지 않은 것

- 공유 DB 쓰기 금지 때문에 이번 검토에서 live stack에 새 규칙을 생성하지 않았다. 실제 API 생성·partner 응답은 fresh 격리 PostgreSQL의 MockMvc API 4/4와 직전 r2 라이브 QA의 실제 HTTP 201/200 증거를 교차 사용했다.
- exact canonical key에 의도적으로 잘못된 category·조건·inactive behavior를 넣는 별도 API 변형은 만들지 않았다. 이 조합은 order-app의 명시적 shape 검증에서 `error`가 되며, 이번 질문의 범위 밖 identity 혼입과는 구분했다.
- 실 DB에 활성 규칙이 0건이므로 현재 실 데이터에서 canonical 규칙을 둔 채 단종·삭제·BUNDLE 구성품 PUT까지 각 mutation endpoint를 라이브로 반복하지 않았다. 동일 exact-key 예외를 공유하는 코드 경로와 격리 API의 노출·카테고리 PATCH를 확인했다.
- 주문 전송과 실제 수량 산출 전환은 관측 전용 범위 밖이므로 보지 않았다.
- 지시된 범위 밖 2건(soft-delete QA 데이터 잔존, QA 접속 유효기간)은 재검토하지 않았다.
