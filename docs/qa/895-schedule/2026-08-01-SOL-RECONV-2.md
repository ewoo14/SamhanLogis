## (1) 일정 삭제 대상자 연쇄 — PASS

### 다른 일정의 대상자 행

`delete()`는 먼저 ID 하나로 `Schedule`을 조회하고, 그 객체의 `participants` 컬렉션만 순회한다.

- 조회와 컬렉션 fetch: `services/groupware-service/src/main/java/com/samhanair/logis/groupware/repository/ScheduleRepository.java:18-21`
- 삭제 대상 순회: `services/groupware-service/src/main/java/com/samhanair/logis/groupware/service/ScheduleService.java:128-137`
- 컬렉션의 소유 관계: `Schedule.java:61-62`
- 자식의 단일 부모 FK와 변경 불가 매핑: `ScheduleParticipant.java:34-39`
- DB FK: `V1__init_groupware.sql:137-140`

따라서 한 `Schedule` 컬렉션에 다른 `schedule_id`의 행이 들어가는 경로가 없다. 실 DB도 orphan 0건,
활성 `(schedule_id, participant_id)` 중복 0건이다. **다른 일정 대상자 영향은 0건**이다.

### 실 데이터 영향 수

공유 DB에는 다음 SELECT 계수만 수행했다.

| 항목 | 실측 |
|---|---:|
| 활성 일정 | 42 |
| 활성 대상자 | 106 |
| 활성 일정 아래 활성 대상자 | 106 |
| 활성 일정 아래 이미 삭제된 대상자 | 0 |
| 활성 일정 중 활성 대상자 0명 | 0 |
| 대상자 1명인 활성 일정 | 10 |
| 대상자 3명인 활성 일정 | 32 |
| 삭제 일정 아래 남은 활성 대상자 | 0 |

현재 데이터에서 일정 하나를 삭제하면 정확히 1행 또는 3행을 새로 soft-delete한다. 42개 활성
일정을 각각 삭제한다고 가정한 영향 합은 기준값과 같은 **106행**이다. 이미 삭제된 일정 3건은
각각 대상자 1행도 삭제되어 있었고, 부모가 삭제됐는데 활성 자식이 남은 사례는 **0건**이다.

### 이미 삭제된 행, 재삭제, 복원

`ScheduleParticipant` 자체에는 `@SQLRestriction`이 없으므로 컬렉션에는 과거 삭제 행도 들어온다.
따라서 그런 행이 존재하면 현재 루프는 다시 `markDeleted()`하고 `deleted_at/deleted_by`를 덮는다
(`ScheduleService.java:136-137`, `shared/common/src/main/java/com/samhanair/logis/common/entity/BaseEntity.java:45-60`). 다만 현재 활성 일정 아래
그런 행은 **0건**이어서 실 데이터 영향도 0건이다. 이미 비가시인 행을 다시 비가시로 만들 뿐
현재 사용자 목록·상세 결과가 추가로 줄어드는 조합도 찾지 못했다.

일정 복원 API·서비스 경로는 저장소 전체에서 **0개**다. 현재 사용자가 삭제 일정을 복원하는
기능은 없다. 만약 DB/native 조회로 부모만 `markRestored()`하면 자식은 삭제 상태로 남고,
목록·상세의 활성 대상자 조건(`ScheduleRepository.java:23-29,39-46`)을 만족하지 못한다. 또한
부모와 자식이 각각 별도 `now()`를 사용하므로 기존 삭제 3쌍의 삭제시각·삭제자 exact marker
일치는 0쌍이었다. 이는 향후 복원 기능을 만들 때 부모·자식을 함께 복원해야 한다는 제약이지만,
현재 사용자가 실행할 수 있는 기능 회귀는 아니므로 BLOCK으로 세지 않았다.

### 같은 일정 재삭제·동시 삭제

- 첫 삭제가 commit된 뒤 재요청하면 `Schedule`의 `@SQLRestriction("is_deleted = false")`
  (`Schedule.java:29-34`) 때문에 `findById()`가 찾지 못해 404가 된다. 기존 부모 삭제 때도 같던
  동작이며 r2가 새로 만든 회귀가 아니다.
- 두 요청이 모두 commit 전에 같은 활성 일정을 읽으면 `@Transactional` 안에서 같은 부모·자식에
  `is_deleted=true`를 설정한다. `@Version`은 없어서 두 요청 모두 성공할 수 있으나 최종 상태는
  부모와 해당 자식 모두 삭제다. 삭제자는 일정 소유자 본인으로 제한되어 있다
  (`ScheduleService.java:128-137`). 다른 일정이나 활성 자식이 남는 경로는 없다.

## (2) Gateway route 우선순위·StripPrefix — PASS

### 기존 매칭 영향

r2 직전 설정은 72 routes / 117 Path patterns, 현재 설정은 신규 route 하나가 늘어난
73 routes / 118 Path patterns이다. 신규 predicate는 `/api/v1/admin/groupware/**` 하나다.

- 신규 route: `services/api-gateway/src/main/resources/application.yml:431-439`
- generic groupware route: 같은 파일 `:441-447`
- 기존 no-prefix route: 같은 파일 `:692-696`

세 predicate의 첫 구분 세그먼트는 각각 다음과 같아 서로 겹치지 않는다.

| route | 입력 prefix | 신규 요청과 중첩 |
|---|---|---:|
| `groupware-admin-v1` | `/api/v1/admin/groupware/` | 대상 |
| `groupware-service-v1` | `/api/v1/groupware/` | 0 |
| `groupware-service-noprefix` | `/admin/groupware/`, `/groupware/` | 0 |

직전 117개 Path pattern을 확인했으며 `/api/v1/admin/groupware/**`와 겹치는 기존 pattern은
**0개**였다. `/api/v1/admin/users/**` 등은 다음 세그먼트가 다르고 전체 `/api/v1/**` catch-all도
없다. 따라서 신규 route가 generic route보다 먼저 있어도, 원래 generic으로 갈 요청을 가로채는
경우는 없다. **기존 route 영향 건수는 구현자 주장과 같은 0건**이다.

### StripPrefix

`StripPrefix=2`는 `/api`, `/v1` 두 세그먼트만 제거한다.

```text
/api/v1/admin/groupware/schedules
        -- StripPrefix=2 --> /admin/groupware/schedules
```

downstream controller base mapping은 `/admin/groupware`이고 일정 목록은 `/schedules`다
(`GroupwareAdminController.java:62-65,300-310`). 따라서 변환 후 경로가 정확히 일치한다.
route IT도 Path, `StripPrefix=2`, JWT, 선언 순서를 확인한다
(`ApiGatewayContextLoadIT.java:240-252`).

`--rerun-tasks` 재실행 결과:

```text
ApiGatewayContextLoadIT.groupwareAdminV1Route_usesExistingAdminGroupwareContract
tests=1 failures=0 errors=0 skipped=0
BUILD SUCCESSFUL, 6 actionable tasks: 6 executed
```

배포된 gateway에 무인증 GET을 다시 호출한 결과 신규 일정 경로는 401이었다. 같은 시점 기존
`/api/v1/quantity-sync-rules`도 401이었다. 이는 두 경로가 각각 인증 필터까지 도달함을 확인하며,
유효 JWT 이후 downstream 200 자체는 이번 read-only 검토에서 재실행하지 않았다.
