## 4. `2026.7.31.1`·PE 경계·updater 비교

### 실제 builder 소비 경로

- `AppInfo`는 package metadata의 `shortVersion`과 `shortVersionWindows`를 실제로 읽는다: `clients/desktop/node_modules/app-builder-lib/out/appInfo.js:23-52`.
- app EXE rcedit는 `shortVersion → --set-file-version`, `shortVersionWindows → --set-product-version`으로 전달한다: `clients/desktop/node_modules/app-builder-lib/out/winPackager.js:121-140`.
- 직접 모킹 관측은 직전 `1.20260731.1`/`1.20260731.1.0`에서 현재 두 값 모두 `2026.7.31.1`로 바뀌었다.
- NSIS main installer는 `shortVersionWindows`가 아니라 `getVersionInWeirdWindowsForm()`을 commands에 넣고, short 값은 uninstaller 분기에만 적용한다: `NsisTarget.js:169-173,266-273`.

### 날짜와 일련번호 경계

`year 0000..9999 × month 01..12 × day 01..31` 총 3,720,000개를 실행했다.

| 관측 | 수 |
|---|---:|
| Gregorian valid | 3,652,425 |
| invalid | 67,575 |
| validator와 Gregorian 판정 불일치 | 0 |

정상 운영 연·월·일은 모두 PE 16-bit 범위 안이다. 순번 경계는 다음과 같다.

```text
2026/07/31-65534 -> 2026.7.31.65534
2026/07/31-65535 -> 2026.7.31.65535
2026/07/31-65536 -> 2026.7.31.65535
```

즉 65536 이상은 모두 65535로 포화돼 서로 다른 릴리스의 PE 표시값이 충돌한다(`scripts/app-build-version.cjs:129-137`). 이는 보고서에 제한으로 기재돼 있고 하루 65,536회 이상 릴리스라는 운영 경계이므로 이번 결함 수에는 별도 추가하지 않았지만, “완전한 순번 보존”은 아니다.

`resolveWindowsDisplayVersion()` 단독 호출은 정규식이 맞으면 달력 검증을 다시 하지 않아 `2026/02/30-1 → 2026.2.30.1`을 반환한다(`:131-134`). 실제 wrapper는 먼저 `resolveBuildAppVersion()`의 날짜 검증을 거치므로 이 잘못된 날짜는 제품 빌드 경로에서는 차단된다(`:23-35,146-160`).

### updater 비교값

PE 값은 updater 비교에 쓰이지 않는다.

- 현재 버전: `ElectronAppAdapter.js:13-15`의 `app.getVersion()`
- 현재 semver parse: `AppUpdater.js:212-217`
- feed semver 비교: `AppUpdater.js:339-362`

따라서 updater는 `extraMetadata.version=1.20260731.1`과 feed의 package semver를 비교하며 `2026.7.31.1`을 비교값으로 사용하지 않는다.

추가 경계로 순번 `9007199254740992` 이상과 연도 `0000..0999`는 helper 정규식/날짜 검증을 통과할 수 있지만 node-semver에서는 invalid가 될 수 있다. 현재 2026년의 통상 릴리스 경로와 거리가 큰 운영 입력 경계이므로 이번 사용자 도달 결함 수에는 넣지 않았으나 builder 인자 검증 상한은 존재하지 않는다.
