# PR #1003 (Issue #1001) 기능 회귀 검토 — Round 4

- 검토 역할: 기능 회귀 검토자(코드 수정 없음)
- 검증 대상 HEAD: `72577526113b55abca29a9fcb2f48aee7a66938d`
- 질문: 정규화가 발행 결과가 다른 요청까지 합치는가?
- 라이브 QA: **미실행** — 검증 대상 SHA의 배포 슬롯이 없음
- 최종 판정: **BLOCK**

## 결론

**그렇다.** R4의 병합 순서 정규화는 발행 결과가 다른 요청을 같은 지문으로 합친다.

병합 호출자는 사용자가 보낸 주문·라인 순서를 그대로 `sourceOrders`와 `lines`에 담는다(`PartnerOrderMergeConvertService.java:115-171, 204-222`). slip-service는 첫 주문을 대표 `source_id`와 audit `source_id`로 저장하고(`SlipPublishService.java:333-375`), 라인도 입력 순서대로 변환·추가한다(`SlipPublishService.java:756-783, 1043-1059`; `Slip.java:711-713`). 발행 응답은 대표 `sourceId`를 반환하고(`PublishSlipResponse.java:22-40`), 전표 상세도 `slip.getLines()` 순서를 그대로 응답한다(`SlipDetailResponse.java:238-244`).

그러나 R4 지문은 `sourceOrders`와 `lines`를 모두 정렬한다(`SlipPublishService.java:798-818, 906-910`). 따라서 아래 두 요청은 같은 멱등 키·같은 R4 지문이지만, 각각 신규 발행됐다면 대표 주문과 라인 배열이 다르다.

```text
요청 A: sourceOrders=[주문1, 주문2], lines=[라인1, 라인2]
요청 B: sourceOrders=[주문2, 주문1], lines=[라인2, 라인1]

신규 발행 A: sourceId=주문1, lines=[라인1, 라인2]
신규 발행 B: sourceId=주문2, lines=[라인2, 라인1]
R4 재시도 B: A의 전표를 200 replay
```

호출자의 멱등 키도 라인 ID를 정렬해 계산하므로 두 요청에 같은 키가 만들어진다(`PartnerOrderMergeConvertService.java:343-383`). R4 테스트는 바로 이 역순 조합의 지문이 같다고만 확인하고, 발행 결과 동등성은 확인하지 않는다(`SlipPublishFingerprintTest.java:34-52`). 실제 사용자는 요청 B의 순서로 발행하려 했는데 요청 A의 전표를 돌려받을 수 있으므로 기능 회귀다.

## 항목별 확인

### 1. 순서 정규화 — **BLOCK**

- `sourceOrders` 순서는 발행 결과를 바꾼다. 첫 항목이 전표 `source_id`, audit `source_id`, 발행 응답 `sourceId`가 된다(`SlipPublishService.java:333-375`; `PublishSlipResponse.java:22-40`).
- `lines` 순서도 발행 구성 순서를 바꾼다. 호출자가 요청 순서로 payload를 만들고(`PartnerOrderMergeConvertService.java:142-171`), slip-service가 같은 순서로 `ResolvedLines.entries`와 `Slip.lines`에 추가하며(`SlipPublishService.java:756-783, 1043-1059`; `Slip.java:711-713`), 상세·내부 출력은 그 컬렉션을 재정렬하지 않는다(`SlipDetailResponse.java:238-244`; `SlipInternalController.java:539-548`).
- 반대로 지문은 두 컬렉션을 정렬한다(`SlipPublishService.java:801-803, 817, 906-910`). 위 역순 조합이 재현 반례다.
- 실 데이터: 병합 전표 **3건**, 모두 다중 출처 **3/3건**, 다중 라인 **3/3건**이며 병합 라인은 총 **7개**다. DB 물리 삽입 첫 출처와 `slips.source_id`가 일치하는 전표도 **3/3건**으로, 첫 주문 선택이 실제 저장 결과에 반영되어 있다.

### 2. `null` ↔ 빈 문자열 — **PASS**

R4가 동일 취급하는 필드는 `ioDate`, `warehouseId`, `partnerCode`, `employeeCode`, `memo`, 단건 `orderApprovedAt`이다(`SlipPublishService.java:804-816, 840-852, 932-937`). 각 하류 결과는 다음과 같이 동일하다.

- `ioDate`: 둘 다 발행일 기본값으로 수렴(`SlipPublishService.java:649-658`).
- `warehouseId`: 둘 다 `warehouseCode` 해석으로 폴백(`SlipPublishService.java:445-455`).
- `partnerCode`: 단건은 둘 다 동일한 필수값 오류이고(`SlipPublishService.java:498-503`), 병합은 둘 다 partner snapshot을 설정하지 않는다(`SlipPublishService.java:343-345`).
- `employeeCode`: 둘 다 같은 헤더 사용자 또는 `system`으로 폴백(`SlipPublishService.java:661-668`).
- `memo`: 둘 다 저장 `null`로 수렴(`SlipPublishService.java:682-693`).
- `orderApprovedAt`: 둘 다 승인시각 prepend를 생략(`SlipPublishService.java:707-718`).

실 데이터의 PARTNER_ORDER 발행 전표 16건 중 memo는 `NULL` 13건, 빈 문자열 0건이고, `partner_code`와 `requester_id` 빈 문자열도 각각 0건이다. 원 요청의 null/빈 문자열 구분은 저장되지 않아 과거 입력별 건수는 복원할 수 없지만, 저장 결과에서 서로 다른 표현은 관측되지 않았다.

### 3. `lineNo` 제거 — **PASS**

`lineNo`는 DTO에만 있고(`PublishLineRequest.java:30-41`), 라인 해석·엔티티 생성·저장에 전달되지 않는다(`SlipPublishService.java:756-783, 1043-1059`). `slip_lines` 실 스키마에도 라인 번호/정렬 번호 컬럼이 없다. 따라서 `lineNo`만 다른 두 요청의 발행 결과는 같다. 테스트도 해당 지문 동일성을 확인한다(`SlipPublishFingerprintTest.java:66-77`).

실 데이터에는 PARTNER_ORDER 발행 라인 23개가 있으나 raw `lineNo`를 저장하지 않으므로 입력값별 영향 건수는 복원 불가하다. 저장 결과가 달라진 관측 건수는 0건이다.

### 4. 실제 유효 단가만 반영 — **PASS**

지문과 발행이 같은 선택 규칙을 쓴다. 둘 다 `unitPriceVat`이 있으면 그 절대값, 없으면 `unitPriceExVat` 절대값, 둘 다 없으면 0을 사용한다(`SlipPublishService.java:764-766, 896-898`). 따라서 무시되는 원본 단가만 다른 요청은 실제 저장 단가도 같고, 실제 선택되는 단가가 다르면 지문도 달라진다. `supplyAmount`와 `vatAmount`는 별도로 계속 지문에 포함된다(`SlipPublishService.java:899-900`).

두 단가 원본을 함께 저장하지 않으므로 과거 입력 조합별 건수는 복원 불가하다. PARTNER_ORDER 발행 라인은 총 23개이며, R4 기준 시각 이후 신규 audit이 0건이라 실제로 합쳐진 재시도는 실 데이터에서 관측되지 않았다.
