## 판정

### (1) 지문 확장이 정상 발행을 막는가? — **BLOCK**

- 새 지문 필드에 서버가 지문 계산 때마다 새로 만드는 timestamp나 request ID는 없다. `orderApprovedAt`은 요청 DTO 값이며 지문 계산 중 생성하지 않는다(`PublishFromPartnerOrderRequest.java:27-42`, `SlipPublishService.java:834-852`).
- 그러나 컬렉션 순서가 지문에 영향을 준다. 현행 병합 지문은 `sourceOrders`와 `lines`를 정렬하지 않고 입력 순서 그대로 JSON에 넣는다(`SlipPublishService.java:797-816`). 반면 호출 측 병합 멱등 키는 대상 라인을 UUID 순으로 정렬하여 요청 순서와 무관하게 같은 키를 만든다고 명시하고 실제로 그렇게 계산한다(`PartnerOrderMergeConvertService.java:343-383`). 같은 주문·라인의 정상 병합을 순서만 바꿔 재시도하면 호출 측 키는 같고 slip 지문은 달라져 `assertReplayOrConflict`가 409를 낸다(`SlipPublishService.java:595-615`).
- 이 순서 차이는 저장 결과와 완전히 무관하지도 않다. 병합 전표의 대표 출처는 첫 주문으로 정한다(`SlipPublishService.java:331-333`). 그럼에도 호출 측 멱등 키 계약은 순서 무관이므로, 동일 키의 재시도 허용 기준과 발행 본문의 순서 의미가 서로 충돌한다.
- `null`과 빈 문자열은 현행 지문에서 서로 다르다. 별도 정규화 없이 DTO 원시값을 map에 넣기 때문이다(`SlipPublishService.java:797-816, 834-852`). 실제 발행은 메모의 null·blank를 모두 null로 만들고(`681-692`), `employeeCode` null·blank를 모두 헤더 호출자 또는 `system`으로 대체하며(`660-668`), `warehouseId`는 trim한다(`444-453`). 따라서 예를 들어 같은 키의 `memo=null`과 `memo=""`는 저장 결과가 같아도 지문이 달라 409가 될 수 있다.
- 라인의 `lineNo`도 지문에는 들어가지만(`SlipPublishService.java:888-901`) 발행 라인 해석에는 사용하지 않는다(`755-782`). 같은 라인에 `lineNo`만 생략/null 또는 값으로 보낸 경우 저장 결과는 같지만 지문은 달라진다.
- 실데이터 직접 계수: 활성 `PARTNER_ORDER` audit는 **16건(단건 13, 병합 3)**이고 생성 시각은 `2026-05-30 13:37:02`~`2026-07-05 12:04:52`다. 대상 fix commit 시각 `2026-07-31 23:59:17+09:00` 이후 생성된 audit는 **0건**이다. 따라서 현행 새 지문으로 실제 발행된 모집단은 **0건**, 관측 가능한 “새로 막힌 건수”도 **0/0(측정 불가)**이지 구현 보고서가 암시한 0/16이 아니다.
- 같은 실데이터에서 병합 3건은 모두 출처 주문이 2개이고 라인도 2개 이상이다. 즉 순서 치환이 가능한 실제 업무 형태는 **3/3건**이며, 이 형태가 배포 후 현행 지문으로 신규 저장된 뒤 순서를 바꿔 재시도되면 위 409 경로에 들어간다. 실제 사용자에게 발생 가능한 정상 재시도 차단이므로 BLOCK이다.

### (2) legacy 경로가 서로 다른 발행을 합치는가? — **PASS**

- legacy 지문 자체에는 `shippingAddress`가 없지만(`SlipPublishService.java:855-885`), legacy replay 허용 전에 저장 전표의 `shippingAddress`와 요청값을 `Objects.equals`로 대조한다. 단건은 `927-936`, 병합은 `939-948`에서 주소가 다르면 `legacyPayloadMatches=false`가 된다.
- `assertReplayOrConflict`는 legacy hash 일치만으로 replay하지 않고 `legacyPayloadMatches`도 참이어야 한다(`SlipPublishService.java:595-608`). 따라서 같은 배포 전 키·같은 legacy 지문이어도 배송주소가 다르면 409이며, 직전 결함처럼 서로 다른 발행을 기존 전표로 합치지 않는다.
- 저장값도 발행 때 요청 `shippingAddress`를 전표에 직접 적용한다(`SlipPublishService.java:235-243, 335-341`; `Slip.java:1611-1653`). 즉 legacy 추가 대조가 비교하는 값은 해당 기존 발행의 저장 snapshot이다.
- 유효기간은 날짜나 키 발급시각으로 명시적으로 제한하지 않는다. `deliveryAddress == null`인 모든 단건·병합 재요청에서 legacy 지문을 계산한다(`SlipPublishService.java:198-207, 300-309`). 다만 실제 legacy 승인은 저장 audit 지문이 재현한 legacy hash와 같아야 하고(`602-608`), 신규 발행 audit에는 현행 확장 지문을 저장한다(`271-275, 372-376`). 따라서 새 키에도 legacy 계산은 시도되지만 정상적인 신규 키가 legacy 분기로 승인되지는 않으며, 효과상 배포 전 legacy hash가 저장된 키에만 적용된다.

## 내가 보지 않은 것

- 검증 대상 SHA가 배포된 서비스에서 실제 HTTP POST/replay. 배포 슬롯이 없어 실행하지 않았다.
- 현행 확장 지문으로 생성된 운영 audit의 실제 장애 통계. 공유 DB에는 fix commit 이후 행이 0건이라 사후 관측 모집단이 없다.
- 공유 DB write, Docker 재빌드·재기동, V14 적용/rollback, 동시 race 실험. 모두 수행하지 않았다.
- 모듈 전체 테스트의 최종 결과를 재판정하지 않았다. 이번 질문의 코드·실데이터 읽기 전용 검토에 한정했다.
- 슬라이스 1 원장 read 계약, 슬라이스 3·4·5, 과거 배송주소 공란 및 backfill, 마이그레이션 번호. 요청 범위에서 제외했다.
