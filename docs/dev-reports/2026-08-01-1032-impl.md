## 1. 착수 및 설계

- 정찰 보고서 `docs/dev-reports/2026-08-01-1032-recon.md` 확인.
- 개발책임자 결정에 따라 목록·상세·인쇄·모바일의 표시 금액은 VAT 포함 `공급가액 + 부가세`로 통일한다.
- 회계 장부·세금계산서·부가세 신고 등 공급가액이 정답인 projection/화면은 변경 대상에서 제외한다.
- legacy `unit_price_domain=NULL`을 포함해 저장된 공급가액과 부가세를 조합하는 표시용 계산 경계를 만들고, 목록·상세 합계가 같은 경계를 사용하도록 RED-first로 검증한다.
- 작업 제한 준수: git 명령, Docker 재빌드·재기동, 실 DB 쓰기를 수행하지 않는다.

## 8. D 범위 판정

### VAT 포함으로 통일한 6개 사용자 표시 화면

1. 판매관리 `SalesQueryPage` — `SlipResponse.totalAmount`
2. 구매관리 `PurchaseQueryPage` — `SlipResponse.totalAmount`
3. 결재 작성 `GroupwareApprovalCreatePage` — `SlipSearchResult.totalAmount`
4. 결재 상세 `GroupwareApprovalDetailPage` — `SlipSearchResult.totalAmount`
5. 공개 인수증 `MobileRecipientPage` — `SlipSignatureService` 집계
6. 전표 정리 `SlipCleanupPage` 및 CSV — `SlipCleanupService` 집계

### 공급가액이 정답이라 유지한 화면/계약

- 회계 장부 projection: `SlipSummary`의 공급가액·부가세 분리 원천값, `SlipSalesQueryResponse`, `PartnerLedgerSalesResponse`의 S/V 분리 필드.
- 세금계산서 및 부가세 신고 계열: TaxInvoice/TaxInvoiceBatch/TaxInvoiceInbound 응답의 `supplyAmount`, `vatAmount`, `totalAmount` 계약.
- 인쇄 3종과 모바일 영업 대시보드: 기존부터 S+V VAT 포함 기준이라 계산을 중복 변경하지 않았다.
- 전표 목록 XLSX: 정찰 결과 금액 컬럼이 없어 변경하지 않았다.

## 3. GREEN 구현

- `SlipDisplayAmount`를 추가해 사용자 표시 금액을 `공급가액 + 부가세`로 계산했다.
- 공급가액이 존재하는 legacy `unitPriceDomain=NULL` 행을 포함해 저장된 S/V를 우선 사용하고, S가 없을 때만 VAT 포함 단가×수량 또는 기존 lineTotal+VAT로 fallback한다.
- `SlipResponse`(판매·구매 목록), `SlipSearchResult`(결재 전표 검색), `SlipSummary`(전표 요약), `SlipCleanupService`(전표 정리 및 CSV), `SlipSignatureService`(공개 인수증)의 행·소계를 같은 계산기로 통일했다.
- 회계 장부·세금계산서·부가세 신고 projection(`SlipSalesQueryResponse`, `PartnerLedgerSalesResponse`, TaxInvoice 계열)은 공급가액/부가세 분리 계약을 유지해 변경하지 않았다.
- 인쇄 3종·모바일 대시보드는 기존 VAT 포함 계산을 유지하며, 전표 목록 XLSX는 금액 컬럼이 없어 변경하지 않았다.
- GREEN 원문:

```text

BUILD SUCCESSFUL in 17s
3 tests completed, 0 failed
```
