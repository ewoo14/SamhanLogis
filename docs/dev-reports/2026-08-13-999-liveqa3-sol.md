# #999 liveQA3 — CODEX SOL

## 결론

**실 사용자 경로에서 재현되는 결함: 0건. 머지 가능.**

격리 PostgreSQL과 현재 브랜치에서 새로 빌드한 product/inventory/slip 서비스, 데스크톱 web 산출물을 사용해 실제 Playwright Chromium GUI를 걸었다. 수불부의 `2026/08/02-17`은 클릭 가능한 링크로 복원됐고, 클릭 시 같은 전표 모달이 열렸다. 모달을 여는 동안 발생한 네트워크 요청은 검색·상세 2건 전부 200이며 400·404·500은 0건이다. 두 요청 URL과 두 응답 본문의 UUID도 0건이다.

`stock_movements`의 `TRANSFER` 계열은 0건이라 재고이동 행 미포함은 사양대로 결함으로 세지 않았다.

## 증거 무결성

- 작업트리에는 `scripts/qa/clone-db-utf8.sh`가 없어 읽기 전용 `git show main:scripts/qa/clone-db-utf8.sh`를 Git Bash에 파이프했다. `inventory_db`, `partner_db`, `product_db`, `slip_db` 모두 데이터·스키마 이중 비교가 PASS했고 하네스 컨테이너와 dump는 자동 제거됐다.
- 같은 원본을 별도 PostgreSQL `sol999-liveqa3-pg-202608130329`에 dump/restore했다. 이후 상태 변경, 실사 POST, fixture 입력은 이 격리 복제본에만 수행했다. 공유 DB에는 쓰지 않았다.
- 현재 원본에는 직전 QA 표적 `2026/08/02-17`과 `999bc001-*` 이동이 없음을 읽기 전용 트랜잭션으로 확인했다. 직전 증거의 동일 전표/라인 식별자와 저장소 fixture를 사용해 `fixture-slip.sql`, `fixture-inventory.sql`을 격리본에만 적용했다. 이로써 직전과 같은 7행 및 0→2→5→12→17→19→16→12 표본을 복원했다.
- 복제본 `server_encoding=UTF8`; 한글 원문 `(주)서울택배`, `(주)한국냉동물류`, `대한화물서비스(주)`, `지방/울산광역시 북구 사청6길 6`, `야적/경기도 광주시 파발로59번길 30`을 확인했다. 데이터 자리에 새 `?`는 없었다.
- 브라우저 런타임 원문은 `No browser is available`이었다. 실행 불가로 판정하지 않고 저장소 `@playwright/test` Chromium으로 실제 GUI·DOM 클릭·격리 서비스 왕복을 실행했다.
- `:services:inventory-service:bootJar`, `:services:slip-service:bootJar`, `:services:product-service:bootJar`, `npm run build:web`을 현재 브랜치에서 새로 실행한 뒤 전용 포트 42984/42985/42986/42973에 기동했다. 최종 `node docs/qa/2026-08-13-999-liveqa3/liveqa3.mjs`는 exit 0이었다.
