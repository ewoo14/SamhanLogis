# #1069 S2 SOL fix 지시서 — 판매전표 세트 전개

## 판정

**결함 있음 — 머지 차단.** 실 사용자 및 권한 보유 API 경로에서 재현 가능한 결함 3계열이다.

읽기 전용 실 DB 재계수는 `product_estimate_exposure` 기준 `BUNDLE 344`, `SINGLE 521`, `bundle_component 1,588행/345세트`, 노출 세트 중 구성품 미등록 `0`이었다. 따라서 아래 결함은 표본 부재가 아니라 경로 계약 위반이다.

## ① 좌표

### F1. 판매전표 수정 API가 세트품목을 그대로 영속한다

- 진입점: `services/slip-service/src/main/java/com/samhanair/logis/slip/web/SalesSlipUpdateController.java:49-57`
- 저장 경로: `services/slip-service/src/main/java/com/samhanair/logis/slip/service/SalesSlipUpdateService.java:72-116`
- 직접 생성 좌표: `SalesSlipUpdateService.java:92-98`, `:221-247`
- 재현:
  1. `sales.slip.edit UPDATE` 권한으로 기존 OUTBOUND DRAFT 상세을 조회한다.
  2. `PUT /slips/{id}/sales`에 유효한 `updatedAt`, `lineIdContract=true`와 함께 견적 노출 BUNDLE의 `productId`를 신규 익명 라인(`lineId=null`)으로 보낸다.
  3. `validateLines`는 수량·단가·UUID 존재만 확인하고, `toLine`은 BUNDLE 여부를 판별하지 않은 채 `SlipLine.create*`를 호출한다.
  4. `replaceSalesLines`가 그 BUNDLE `productId`를 전표 라인으로 저장한다.

동일 위험 표면:

- `services/slip-service/src/main/java/com/samhanair/logis/slip/mobile/service/MobilePartnerOrderService.java:153-173` — 권한 보유 `POST /mobile/sales/partner-orders` 라인이 `SlipLine.create`로 직행한다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/service/SlipUpdateService.java:67-113`, `:221-247` — INBOUND 전체수정도 같은 모양이나 판매전표 사양 밖이므로 이번 fix 범위에는 포함하지 않는다.

### F2. 화면 전개와 서버 저장 전개가 규격·세트 옵션에서 갈린다

- 서버 저장 기준: `services/slip-service/src/main/java/com/samhanair/logis/slip/service/SlipService.java:145-215`
  - `:180-186`은 세트 옵션·수량·단가를 전개 엔진에 전달한다.
  - `:198-205`는 구성품 규격이 없으면 원 세트 라인의 `specification`을 구성품에 승계한다.
- 화면 전개 요청: `services/slip-service/src/main/java/com/samhanair/logis/slip/web/dto/ExpandSlipLineRequest.java:11-15`, `SlipLookupController.java:59-73`
  - 요청 계약에 `specification`이 없어 동일 입력을 전달할 수 없다.
- 화면 반영: `clients/desktop/src/renderer/routes/SlipFormPage.tsx:732-795`
  - `:752`, `:762`가 응답 규격 `null`을 빈 문자열로 바꿔 원 행 규격을 소실한다.
  - `:784-791`은 품목 선택 순간의 옵션을 한 번 캡처한다.
- 옵션 입력 표면: `SlipFormPage.tsx:1254-1270`
  - `BundleOptionRow`는 BUNDLE 행에만 보이나, 품목 선택 직후 이미 전개 요청이 시작되고 완료 시 BUNDLE 행이 사라진다. 사용자가 바꾼 옵션으로 현재 세트를 다시 전개하는 경로가 없다.
- 재현 A(규격): 빈 행 규격에 `현장규격` 입력 → 자체 규격이 없는 구성품을 가진 세트 선택. 직접 저장 전개는 `현장규격`을 승계하지만 화면 선전개는 빈 규격 구성품을 만든다.
- 재현 B(옵션): 세트 선택 → 원격/패널/자재 옵션 변경. 최초 전개 요청은 변경 전 기본 옵션으로 이미 발행되며, 변경값으로 재전개되지 않는다.

### F3. 지연된 전개 응답이 같은 행의 최신 사용자 입력을 덮는다

- 요청·응답 적용: `clients/desktop/src/renderer/routes/SlipFormPage.tsx:732-797`
- 최신성 판정이 `source.id` 존재 여부뿐이다(`:738-739`). 현재 행의 품목·수량·단가·요청 세대는 비교하지 않는다.
- 재현 A: 세트 A 선택 → `/slips/expand-line` 응답 지연 → 같은 행을 일반 품목 B로 교체 → A 응답 도착. B가 A 구성품으로 교체되어 사용자 입력이 소실된다.
- 재현 B: 거래처 선택 상태에서 세트 선택 → 최근단가 조회 지연 중 수량 `1→3` 변경 → 조회 완료. `:910-912`가 선택 당시 `nextLine.quantity`로 전개하여 최신 수량 3이 반영되지 않는다.
- 재현 C: 세트 전개 실패가 늦게 도착하기 전에 같은 행에 일반 품목을 입력해도 `:793-795`가 빈 오류행으로 교체한다.

## ② 불변식 — 구현 수단 지정 금지

1. 견적 노출 BUNDLE은 판매전표의 생성·라인추가·전체수정·모바일 판매전표 생성 중 어느 쓰기 경로에서도 BUNDLE 자체로 영속되지 않아야 한다.
2. 동일한 세트 입력의 수량·VAT 포함 단가·세트 옵션·규격·구성품 순서가 화면 전개와 서버 저장 전개에서 모두 같아야 한다.
3. 구성품 자체 규격이 있으면 그것이 우선하고, 없으면 원 세트 행 규격을 승계하는 기존 저장 계약이 화면에서도 같아야 한다.
4. 비동기 전개 결과는 그 요청의 대상 세트와 입력 스냅샷이 여전히 최신인 경우에만 적용되어야 한다. 지연 중 사용자가 확정한 일반 품목·수량·단가·옵션·규격을 덮으면 안 된다.
5. 전개 실패는 해당 세트 요청에만 귀속되어야 하며, 이후 확정된 정상 품목이나 입력을 지우면 안 된다.
6. 구성품 단독 입력과 일반 품목 입력·수정·저장은 계속 허용되어야 한다.

## ③ 양방향 RED — 반대급부 필수

### RED-B — 재발 금지

- `PUT /slips/{id}/sales` 또는 모바일 판매전표 생성에 BUNDLE `productId`를 보내도 BUNDLE 전표 라인이 저장되면 RED.
- 동일 세트 입력에서 화면과 저장 전개의 품목, 수량, 단가, 공급가액/VAT/합계, 규격, 순서 중 하나라도 다르면 RED.
- 옵션 변경이 전개 결과에 반영되지 않거나 규격 없는 구성품이 원 행 규격을 잃으면 RED.
- 늦은 성공/실패 응답이 이후 사용자가 고른 일반 품목 또는 이후 수량·단가·옵션·규격을 덮으면 RED.
- 같은 세트를 연속 두 번 선택한 단일 사용자 동작이 구성품을 중복 삽입하면 RED.
- 전개 후 trailing 빈행이 0개 또는 2개 이상이면 RED.

### RED-A — 반대급부 보존

- BUNDLE 저장 차단 때문에 `SINGLE 521`개 일반 품목이나 구성품의 단독 입력·신규 저장·수정 저장이 차단되면 RED.
- stale 응답 차단 때문에 현재 요청의 정상 전개가 무시되거나 사용자가 최신으로 선택한 세트가 전개되지 않으면 RED.
- 화면/저장 정렬 때문에 기존 VAT 포함 단가 계산, 구성품 가격 배분, 구성품 자체 규격 우선, 원래 구성품 순서가 바뀌면 RED.
- 옵션 반영 때문에 기본 옵션 세트의 기존 결과가 달라지거나 옵션 변경마다 구성품이 누적 추가되면 RED.
- 실패 보존 때문에 실패한 세트 BUNDLE 행이 저장 가능 상태로 남거나 오류가 사용자에게 보이지 않으면 RED.
- `autoBlankRow`의 마지막 행 1회 증식, trailing 빈행 1개, 의미 없는 빈행 저장 제외가 깨지면 RED.

## ④ 범위 밖

- 견적 화면·견적 저장 엔진, 분개, 이동 화면
- 세트 마스터·`bundle_component` 데이터 변경 및 가격 정책 재설계
- INBOUND 전체수정의 동형 문제
- 다른 트랙 `#1045`, `#1057`, `#1066`
- Docker 재빌드·재배포·중지 및 DB 쓰기
- UUID 전면 API 계약 개편. `POST /slips/expand-line`은 `slip.lookup-product VIEW` 권한 게이트가 존재하며, 응답 `productId`는 클라이언트 내부 저장 키로만 사용되고 현재 화면 텍스트에는 노출되지 않는다.

안 본 범위 및 증거 한계:

- DB 쓰기 금지 때문에 F1의 실 DB 영속 재현은 실행하지 않았다. 서비스의 권한 보유 진입점부터 `saveAndFlush`/`save`까지 분기 없는 호출 사슬과 `SlipLine.create*` 좌표로 재현 조건을 확정했다.
- 공유 Docker 배포본은 이번 HEAD 산출물이라는 증거가 없으므로 라이브 화면/API 판정에 사용하지 않았다. Docker에는 조회만 수행했고 재빌드·재배포·중지하지 않았다.
- 견적·분개·이동·INBOUND 수정, partner-order-service 변환 경로는 판정하지 않았다.
- 전 범위 게이트, 브라우저 라이브QA, 모바일 실기기는 실행하지 않았다.
