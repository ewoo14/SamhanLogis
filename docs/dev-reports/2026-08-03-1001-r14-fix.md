## 조사 완료: ①의 원천 근거와 경로 전수

### 무엇을 세는 것이 옳은가

**결론: 이 화면의 수금 합계는 `POSTED` 분개의 계정코드 집합을 추측해 확장하는 대신, 같은 화면 상세의 확정 `cash_receipts.amount`를 거래처·기간별로 합산해야 한다.** 매출은 이미 R6/R7에서 확정한 출고 판매전표 품목 합계를 유지한다.

근거는 다음과 같다.

1. 정본 메모리 `.claude/memory/project_partner_ledger_and_cash_receipt.md` §4는 거래처별 원장 원천을 정확히 두 종류로 확정한다. 매출은 **출고 판매전표**, 수금은 **입금보고서**다. §1~2는 입금보고서가 입금내역을 거래처별 원장·회계반영을 위해 그룹화한 장부 입력임을 명시한다.
2. R7 보고서 `docs/dev-reports/2026-08-03-1001-r7-reconvergence.md`의 조사 로그는 Issue #1001과 정본 메모리를 근거로 같은 화면의 Step 1 매출을 출고 slip 기준으로 확정했고, 수금 원천은 입금보고서라고 기록한다. 과거 BE-A8의 401/110 설명은 선행 구현 문서일 뿐 현재 #1001 원장 사양보다 구체적이지 않다.
3. R5 보고서 `docs/dev-reports/2026-08-03-1001-r5-reconvergence.md` §46은 화면 수금 합계를 `CONFIRMED cash_receipts`로 산출하고, `CASH_RECEIPT` 분개의 110 대변 합계는 대조용으로 별도 산출했다. 즉 계정코드가 원장 수금의 정본이라는 근거가 아니다.
4. 현재 코드도 같은 결론을 교차 확인한다. `PartnerLedgerReadService`는 상세를 `PartnerLedgerSalesClient`의 판매전표와 `CashReceiptRepository`의 `CONFIRMED`·기간 조건 입금보고서로 만든다. 반면 `SalesAggregateService`는 `JournalLineRepository.aggregatePostedByPartnerAccount`의 401/110만 읽어 상세의 입금보고서를 누락한다.
5. `CashReceiptService`는 입금보고서마다 저장된 차변·대변 계정코드를 사용해 자동 분개를 게시한다. 따라서 110을 새 계정으로 늘리는 방식은 입금보고서 원천을 복원하지 못하며, 계정코드가 다른 기존 행을 임의로 포함하거나 이중 집계할 위험이 있다. 수금 금액의 정본은 `CashReceipt.amount`로 둔다.

**현재 확정된 값 변경 후보:** `8428102605 / 주식회사 제이시스템`은 R3 상세의 확정 입금보고서 6건 합계 `245,612,215원`이므로 목록 수금 합계가 `—`에서 `245,612,215원`으로 바뀌어야 한다. 매출 원천은 이번 fix에서 건드리지 않는다. 같은 기간 다른 거래처는 `CONFIRMED cash_receipts`가 있는 경우에만 수금·채권이 바뀌며, 해당 receipt 행이 없는 거래처의 값은 기존과 동일해야 한다.

**불변식 및 Linux 판정:** 이 결론은 OS가 아닌 Java repository 조건·도메인 원천·React API 계약에 대한 것이다. `ubuntu-latest`에서도 `CONFIRMED`/기간/partnerId 필터와 `BigDecimal` 합산은 동일하다. 실제 Windows Electron 캡처 자체는 Linux 화면 증거로 주장하지 않는다.

### Root cause hypothesis 확정

`SalesAggregateService`가 원장 화면의 수금 원천을 `JournalLine.accountCode == 110`으로 제한하고, `CashReceiptRepository`를 전혀 읽지 않는다. R3의 5월 기존 행은 `CASH_RECEIPT` 상세 6건이 있지만 해당 기간의 POSTED 계정코드 분포에 110이 없으므로, 목록의 수금과 채권은 0/공란으로 남고 상세만 245,612,215원이 된다. 이는 단순 포맷/렌더링 문제가 아니라 집계 원천 분기 누락이다.

**상태:** 원천 근거·경로 전수 조사 완료. 다음은 이 결함을 고정하는 실 API 경로 상태 fixture의 RED 테스트다.

### ① fix

수정은 다음 계약으로 제한했다.

- `JournalLineRepository.PartnerAccountTotal`에 `sourceType`을 포함하고 query `GROUP BY`에도 포함했다. 기존 계정별 합계가 `CASH_RECEIPT`인지 다른 원천인지 구분할 수 있게 했다.
- `SalesAggregateService`는 `CASH_RECEIPT` 분개 라인의 401/110 값을 매출·수금·채권 집계에 직접 더하지 않는다. 해당 원천은 상세와 동일하게 `CashReceiptRepository`에서 `status=CONFIRMED`, `transactionDate` 기간, 선택 시 `partnerId` 조건으로 읽는다.
- `CashReceipt.amount`를 거래처별로 한 번 합산한다. receipt-only 거래처도 집계 행을 만들며, 기존 비-CASH_RECEIPT 401/110 분개와 출고 slip 매출 보정은 그대로 둔다.
- `receivableBalance`는 기존 함수 `receivableDebit - paymentTotal`을 유지하면서 수금 합계만 상세 원천과 맞췄다. 따라서 수금만 있는 대상은 `0 - 245,612,215 = -245,612,215`가 된다.
- source type getter를 추가하면서 기존 projection fixture 두 곳에 `null`을 명시했다. 이는 테스트 컴파일 계약 보정이고 제품 동작·실 DB에는 영향이 없다.

보정 뒤에는 저장번호가 실제 DOM에 존재하고, 기존 `JR-2026-05-06-3`은 존재하지 않는다는 단정으로 제품 실패를 분리했다. 다중 페이지 헤더가 4개인 것은 기존 인쇄 레이아웃의 정상 구조이며, 이 단정이 Linux(ubuntu-latest)에서도 참인가: 예. 선택자 보정은 렌더 페이지 수를 명시적으로 허용하고 OS에 의존하지 않는다.

## ② fix 및 GREEN

BE는 `CashReceipt.journalId`로 연결된 `Journal`을 `JournalRepository.findAllById`로 조회하고, `Journal.journalNo`를 `PartnerLedgerResponse.Document.documentNo`로 반환한다. 따라서 대상 행은 저장값 `JR-2026-05-06-003`을 그대로 받는다. `journalId`가 없는 S1 legacy receipt만 기존 `receipt.slipNo`를 fallback으로 보존했다. 이 fallback은 저장된 journal 값이 존재하는 대상 행에 적용되지 않는다.

FE 상세는 API의 `documentNo → journalNo`를 그대로 렌더한다. 인쇄는 `stripSlipNoZeros` 변환을 제거하고 원 문자열을 출력하며, 상세와 같은 열 이름 `분개번호`를 사용한다. `UUID`를 새로 렌더링하는 경로는 만들지 않았다.

BE GREEN:

```text

```

`PartnerLedgerReadServiceTest` 3건(신규 저장번호 단정 포함) 통과. FE GREEN:


이 단정이 Linux(ubuntu-latest)에서도 참인가: 예. BE는 UUID batch 조회와 `Journal.journalNo` 문자열 전달, FE는 React DOM의 identity 렌더를 검증하며 OS·locale 의존이 없다. 다만 이 GREEN은 R13 배포 컨테이너의 화면 결과가 아니며, PM 재배포 전에는 라이브 화면에 반영되지 않는다.

### ② 상세·인쇄 대조

| 경로 | 수정 전 | 수정 후 | 근거 |
|---|---|---|---|
| 상세 `분개번호` | `2026-05-06-003` | `JR-2026-05-06-003` | `accounting_db.journals.journal_no` 그대로 |
| 인쇄 `분개번호` | `2026-05-06-3` | `JR-2026-05-06-003` | 동일 API `journalNo`, 문자열 변환 제거 |

상세와 인쇄는 같은 API 응답의 같은 저장 `journalNo`를 사용하므로 두 값이 같고, 열 이름도 실제 저장 분개번호와 일치한다. 판매전표 행의 기존 source number는 현재 API 계약을 보존하며, 이번 fix는 CASH_RECEIPT 연결 journal의 번호를 정확히 복원하는 데만 적용했다.

## 최종 변경 표면

이번 fix가 새로 만든 표면은 네 가지다.

1. `SalesAggregateService`가 상세와 동일한 `CONFIRMED cash_receipts.amount`를 수금 정본으로 읽고, `JournalLineRepository`가 `sourceType`을 함께 반환해 `CASH_RECEIPT` 자동분개 이중 집계를 막는다.
