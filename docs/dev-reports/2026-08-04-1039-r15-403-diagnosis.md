### 4. arologis-service의 role 소비 계약 확정

- `services/arologis-service/src/main/resources/application.yml:44-49`는 이 서비스만 `samhan.security.permission.enforcement-mode: role`로 고정한다.
- 가배차 endpoint는 `ArologisAdminController.java:340-347`이다. `@RequirePermission(page = arologis.dispatch.ops, action = VIEW)`가 붙고, `:346`에서 `X-User-Role`을 optional request header로 직접 받는다.
- shared `PermissionAspect.java:162-184`는 `X-User-Role`이 없으면 `UNKNOWN`으로 정규화하고, arologis의 role mode에서는 계정 UUID 권한 경로가 아니라 `checkRolePermission`으로 간다. `:291-302`는 이 role의 `canView/canEdit`가 없으면 정확히 `reason=role permission missing`으로 거부한다.
- 따라서 R14의 `role=UNKNOWN reason=role permission missing`은 이 코드 경로와 정확히 일치한다. arologis-service가 기대하는 헤더는 `X-User-Role`이며, 게이트웨이는 현재 그 헤더를 제거한다.
- `HeaderAuthenticationFilter.java:20-24,41-57`는 `X-User-Id`만으로 Spring Security 인증을 성립시키고 role은 무시한다. 즉 요청이 인증 자체는 통과한 뒤 `@RequirePermission`의 role 기반 인가에서 403이 되는 관측과도 일치한다.
- 소스 수준 원인 후보는 **게이트웨이의 C5-4 role 와이어 제거와 arologis-service의 role enforcement 잔존 간 계약 불일치**로 좁혀졌다.

### 7. 별건: dev_master 매출전표 발행 403

- `SlipController.java:296-304`의 `POST /slips`는 `checkCreatePermission(callerHeader, slipType)`을 호출한다. OUTBOUND는 `:788-795`에서 `sales.slip.create`의 `CREATE`를 검사한다.
- 실제 거부 메시지는 `SlipController.java:835-842`의 수동 `requireAccountPermission`에서 나온다. 이 코드는 `X-User-Id`를 UUID로 파싱해 `account_page_permissions`만 조회하며, 시스템 마스터 헤더/bypass는 확인하지 않는다.
- 읽기 전용 SQL(`psql -c`) 결과: `dev_manager`는 `sales.slip.create` account row와 `can_create=true`가 있고, `dev_master`는 시스템 마스터 그룹 소속이지만 의도적으로 account row가 없다. UUID는 조회 결과에 노출하지 않았다.
- 이는 `V39__account_page_permissions_overhaul.sql:186-213`이 MASTER/PARTNER를 account materialize 대상에서 제외하고, shared `PermissionAspect.java:162-165,324-330`가 `X-Is-System-Master=true`를 bypass하도록 설계한 것과 일치한다.
- 그러나 `SlipController`의 수동 가드는 shared master bypass를 거치지 않는다. 그래서 MASTER는 정상 설계대로 account row가 없는 바로 그 이유로 403이 되고, MANAGER는 201이 된다.
- 판정: 매출전표 403은 가배차의 `X-User-Role` 계약 충돌과 **직접 원인은 별개**다. 다만 둘 다 C5-4 이후 신원/권한 전환을 소비 서비스의 레거시 수동 가드가 완전히 따라가지 못한 같은 상위 계열의 제품 결함이다.
- 실행 중 `samhan-slip-service` 로그에도 R14 시각대 `sales.slip.create action=CREATE`의 `[M4] slip mutation permission denied`가 남아 있어, 위 수동 가드가 실제 403 발생 지점임을 확인했다. 계정 UUID는 보고서에 기록하지 않는다.

### 8. R14 가배차 403의 실제 로그인 계정 교정

- R14 본문은 매출전표 발행 실패 후 `dev_manager`로 전환해 3건을 생성했다고 기록하며, 이후 `dev_master`로 돌아갔다는 기록이 없다.
- 증거 캡처 `docs/qa/1039-provisional-dispatch-real-qa/r14-12-mode1-result.png`를 직접 열었다. 우상단 로그인 표시는 `[DEV-SEED] 개발매니저 · MANAGER`다.
- 따라서 R14가 실증한 `role=UNKNOWN` 가배차 403의 계정은 **dev_manager(MANAGER)**다. 이는 `X-Is-System-Master` bypass 대상이 아니므로 `X-User-Role` 제거와 arologis role enforcement 충돌이 그대로 발화한다.
- 사용자 브리프의 “dev_master로 가배차 조회 403”은 R14 캡처로는 뒷받침되지 않는다. fresh `dev_master`는 시스템 마스터 claim이 정상이라면 shared aspect에서 role 검사 전에 bypass되어야 한다. 이번 라운드는 비밀번호/세션을 새로 사용해 그 별도 재현을 하지 않았다.

### 9. MASTER bypass 실행 계약 교차 확인

- 배포 arologis JAR의 `PermissionAspect.class`를 bytecode로 확인했다. `checkPermission`은 `X-User-Role`을 읽은 직후 `X-Is-System-Master`를 읽고 `isMasterBypass`를 role enforcement보다 먼저 호출한다. 값이 `true`이면 즉시 원 메서드를 실행한다.
- 배포 게이트웨이 JAR bytecode는 inbound identity 헤더 제거 후 `X-User-Id`, `X-Is-System-Master`, `X-User-Groups` 순으로 claim 기반 값을 다시 추가한다.
- 읽기 전용 SQL상 `dev_master`는 활성 시스템 마스터 그룹 소속이다. 배포 auth-service JAR도 로그인 시 해당 멤버십을 조회해 JWT `isSystemMaster` claim을 생성하는 구현을 싣고 있다.
- 그러므로 **현재 증거로 확정된 가배차 결함은 MANAGER 등 비시스템마스터 직원의 role 소실**이다. truly fresh `dev_master`가 같은 `role permission missing`으로 거부된다면, 그때는 stale/non-master 세션 또는 claim 발급·쿠키 갱신을 별도로 확인해야 한다.

## 권고

- 가배차: 권한 시드나 환경값을 바꾸지 말고, Samhan 게이트웨이 경유 직원 요청은 `X-User-Id`/`X-Is-System-Master`/`X-User-Groups` 기반 중앙 account/group 인가를 사용하도록 arologis 경계를 고쳐야 한다. 아로로지스 자체 JWT의 `AROLOGIS_*` role 경로는 독립 로그인용으로 분리 보존하는 방향이 안전하다. 전역 `X-User-Role` 부활은 C5-4 신뢰 경계와 충돌하므로 권고하지 않는다.
- 매출전표: `SlipController` 수동 가드를 shared `@RequirePermission` 계약과 정렬하거나, 동일한 trusted `X-Is-System-Master` bypass를 적용해야 한다. MASTER용 account row를 억지로 seed하는 것은 V39 불변식과 충돌한다.
- 지금 재배포할 서비스는 없다. 코드 수정 뒤에는 선택한 구현 위치에 따라 가배차는 최소 `arologis-service`(게이트웨이까지 수정하면 `api-gateway`도), 매출전표는 `slip-service`를 재배포해야 한다.

## 이 라운드가 보지 않은 것

- fresh `dev_master` 세션으로 가배차 조회를 다시 실행하지 않았다. R14 캡처의 실제 계정은 `dev_manager`였고, 비밀번호/브라우저 세션을 새로 사용하지 않았다.
- 권한 결함 이후의 가배차 8개 모드 결과, 발행/저장, CSV는 보지 않았다.
- 수정 코드, 회귀 테스트, 테스트 스위트, 이미지 빌드, 재배포는 수행하지 않았다.
- DB 쓰기 및 권한 시드 변경은 수행하지 않았다. SQL은 `dev_master`/`dev_manager`의 시스템 마스터 여부와 `sales.slip.create` account/group 권한 상태를 읽는 조회만 실행했다.
- 사용자 제약에 따라 `git diff origin/main...HEAD -- services/api-gateway/`를 포함한 git 명령은 실행하지 않았다. 대신 배포 JAR 내부 설정과 브랜치 파일의 SHA-256 동일성, 배포 bytecode 동작을 대조했다.
- `/actuator/gateway/routes`는 배포본에서 404여서 actuator RouteDefinition 덤프는 보지 못했다.
- 요청별 debug 로그가 남지 않아 forwarded header를 로그 한 줄로 직접 캡처하지는 못했다. 실행 JAR bytecode, 소비 코드, 정확히 일치하는 403 reason으로 데이터 흐름을 확정했다.
