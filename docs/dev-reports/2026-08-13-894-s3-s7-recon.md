가장 큰 공통 공백은 별도로 있다. S1의 채팅 화면/API client는 **본체** `clients/desktop`에만 있고, S2의 `clients/internal-chat-desktop` 렌더러는 아직 정적 셸이다. S3~S7 중 어느 슬라이스가 S1 화면·client를 독립 앱으로 옮길지 정해져 있지 않다. 이 소유권을 정하지 않으면 S5~S7을 붙일 사용자 표면이 없다.

또한 PR #1193 제목은 “본체 연계 자동 로그인”을 포함하지만 PR 본문은 S3로 이월했고, 실제 README와 렌더러도 미구현이라고 명시한다. 제목을 구현 증거로 세면 안 된다.

## 2. S3 자동 로그인

### 이미 있는 것

본체 로그인·토큰 체계는 이미 있다.

- 로그인 API는 `POST /auth/login`이고 응답은 JWT `token`, userId, role, displayName을 준다. `clients/desktop/src/renderer/api/auth.ts:36-42,52-57`.
- Electron 본체는 `window.samhanAuth` IPC를 통해 세션을 저장/복원한다. `clients/desktop/src/renderer/auth/authProvider.ts:41-55`, `electronAuthProvider.ts:29-57`.
- 메인 프로세스 저장소는 Electron `safeStorage`로 토큰을 암호화하고, 복호화 실패 시 null을 반환하며 로그아웃/401 때 clear한다. `clients/desktop/src/main/store/auth-store.ts:58-81,100-119,156-165`.
- IPC 채널은 `auth:get-token`, `auth:set-token`, `auth:clear-token`이다. `clients/desktop/src/main/ipc/auth-token.ts:4-10,26-43`; main 등록은 `clients/desktop/src/main/index.ts:108`.
- API client와 SSE client는 provider에서 Bearer header를 얻는다. `electronAuthProvider.ts:35-48`, `createRealtimeClient.ts:125-145`.
- auth-service에는 login/logout/me가 있고 JWT TTL은 현재 3600초다. `services/auth-service/src/main/java/com/samhanair/logis/auth/web/AuthController.java:52-70,91-99`, `services/auth-service/src/main/resources/application.yml:47-54`.

### 없는 것

- `internal-chat-desktop`에는 auth store, auth IPC/preload, API client, session bootstrap, 로그인/실패 화면이 모두 없다. 현재 preload는 앱 이름만 노출한다(`src/preload/index.ts:1-5`), renderer는 정적 셸뿐이다(`src/renderer/main.ts:6-13`).
- 본체와 독립 앱 사이 custom protocol, deep-link, named pipe, local IPC, 일회성 교환 코드 등 인증 handoff가 없다. S2 정찰도 두 앱 간 전달 구현을 찾지 못했다고 기록했다. `docs/dev-reports/2026-08-12-894-s2-packaging-recon.md:36-38`.
- 본체 로그아웃/401/계정 전환이 독립 앱 세션에 전파되는 경로가 없다.
- refresh endpoint/token 모델은 없다. 1시간 JWT 만료 뒤의 독립 앱 재인증 UX가 비어 있다.
- “본체가 로그인돼 있지 않음”, “본체는 종료됐지만 저장 토큰은 있음”, “다른 Windows 계정/복호화 실패”의 상태별 계약이 없다.

### 인접 기능 재사용 가능성

- 본체의 `AuthSnapshot`, safeStorage, IPC/provider, Bearer 주입 방식은 코드 패턴으로 재사용 가능하다.
- 단, 본체 store 파일을 독립 앱이 직접 읽는 것은 현재 구현이 아니며 보안·수명주기 결정을 우회한다. 동일 구현 패턴 재사용과 동일 저장소 공유는 다른 선택지다.
- `/auth/me`는 전달받은 토큰의 유효성·사용자 메타데이터 재확인에 쓸 수 있는 기존 경로다.

### 개발책임자 판단 필요

1. 앱 간 인증 전달의 신뢰 경계를 선택해야 한다: (a) 본체가 일회성 교환 토큰/코드를 독립 앱에 전달, (b) OS 보호 저장소를 명시적으로 공유, (c) 독립 앱에서 별도 로그인 허용. 보안성과 “본체 로그인 연계” 의미가 달라진다.
2. 본체 로그아웃·계정 전환·JWT 1시간 만료 때 독립 앱을 즉시 로그아웃할지, 제한된 재인증 화면을 둘지 결정해야 한다.
3. S1의 방 목록/대화/API client를 독립 앱으로 옮기는 작업을 S3에 포함할지 별도 공통 슬라이스로 둘지 결정해야 한다.

## 3. S4 접속 상태 · 부재중

### 이미 있는 것

- 공용 `PresenceService`는 특정 entity를 보고 있는 세션을 in-memory로 보유하고 공용 `RealtimeBroker`에 join/leave를 발행한다. `shared/realtime-abstraction/.../PresenceService.java:19-30,36-45,54-84`.
- `PresenceEntry`는 sessionId/displayName/color와 내부 `lastSeenAt`을 가진다. `.../PresenceEntry.java:7-19`.
- 기본 TTL은 5분이며 30초마다 만료 정리를 수행한다. `PresenceService.java:30,134-173`.
- FE `usePresence`는 30초마다 join을 heartbeat로 재호출하고 unmount 시 leave한다. `clients/desktop/src/renderer/hooks/usePresence.ts:10,85-105,127-146`.
- 공용 SSE client는 30초 서버 heartbeat/60초 무응답 감지 및 5→60초 backoff 패턴을 이미 제공한다. `createRealtimeClient.ts:52-54,108-115,215-223`.

### 없는 것

- 위 presence는 **사용자 전역 상태가 아니라 entity 단위 문서 열람 상태**다. `PresenceService.java:20`, `PresenceEntry.java:7`.
- 사용자별/기기별 전역 presence entity/table/API가 없다.
- `ONLINE`, `AWAY`, `OFFLINE` 상태와 상태 변경 event가 없다.
- 키보드·마우스·창 focus 등 실제 사용자 활동을 감지해 10분을 계산하는 desktop 코드가 없다.
- 마지막 활동 시각의 영속/노출 정책이 없다. 현재 `lastSeenAt`은 JSON에서 숨겨진 TTL 정제용이다(`PresenceEntry.java:18-19`).
- 독립 앱에 참여자/사용자 목록과 상태 dot 화면이 없다.

### 인접 기능 재사용 가능성

- session heartbeat, TTL prune, SSE fan-out, opaque sessionId, avatar 색상과 `PresenceIndicator` 표현 패턴은 재사용 후보이다.
- 그대로 쓰면 안 되는 차이도 명확하다. 현재 registry는 node-local이고 다중 노드 list가 부분집합일 수 있다(`PresenceService.java:115-120`). 전역 직원 상태의 진실원으로 삼을지는 별도 판단이 필요하다.
- 현재 5분 TTL은 연결 단절 감지용이고, 요구의 10분은 사용자 활동 기반 부재중 전환이다. 같은 시간축으로 간주할 근거가 없다.

### 개발책임자 판단 필요

1. 접속 상태 공개 범위: 모든 재직자에게 전체 상태를 보일지, 같은 방 참여자만 보일지.
2. “활동”으로 인정할 입력 범위: 독립 메신저 창 활동만인지, 본체 앱 활동도 합산하는지. 이는 업무 의미이므로 코드가 대신 정할 수 없다.
3. 다중 기기/추후 모바일에서 한 기기만 활동 중일 때 사용자 집계 상태를 어떻게 표시할지.
4. 마지막 접속/마지막 활동 시각을 사용자에게 노출·영속할지, 현재 상태만 제공할지.

- 내부 발행은 `POST /internal/notifications`. `NotificationCenterInternalController.java:23-34`.

- FE wrapper는 같은 세 경로와 MESSENGER 일괄 확인 helper를 갖는다. `clients/desktop/src/renderer/api/notificationApi.ts:1-7,39-73`.
- 본체 알림 벨은 60초 polling, focus refetch, 채널 grouping, acknowledge, deeplink 이동을 이미 한다. `NotificationBellDropdown.tsx:1-8,30-40,73-83`.
- 기존 **레거시 쪽지** `MessageService`는 MESSENGER 채널, message sourceRef, `/messenger` deeplink로 notification-service에 after-commit 발행한다. `services/groupware-service/.../MessageService.java:56-67,136-147`.
- S1 room 채팅 자체의 방 SSE는 이미 있다. `ChatMessageService.java:39-43`.

### 없는 것

- S1 **room 채팅** `ChatMessageService`에는 `NotificationPublisher`가 없다. 즉 room 메시지는 SSE는 보내지만 기존 MESSENGER 알림 센터 행을 만들지 않는다.
- notification center publish/find/ack 흐름은 polling REST이고, 사용자 알림 신규 행을 실시간으로 밀어주는 SSE 경로는 확인되지 않았다. `NotificationRealtimeBroker`는 알림 감사 편집 event용이지 center 신규 알림 fan-out이 아니다.
- 독립 앱에는 notification API client, polling/SSE consumer, unread badge, tray flash, Windows native notification, 소리/미리보기, 클릭 deeplink가 없다.
- 이슈 결정인 “사람 발신 알림은 해당 1:1 방, 시스템 발신은 삼한이” projection과 읽음 동기화가 없다.
- 기존 deeplink `/messenger`는 숨겨진 본체 구표면을 가리킨다. 독립 앱 방으로 여는 경로가 없다.

### 인접 기능 재사용 가능성

- `notification_center`의 발행·대상자 필터·멱등 sourceRef·read_at과 본체 FE API는 재사용 가능하다.
- room SSE는 열린 대화 즉시 갱신에, notification-service는 백그라운드/미접속 알림과 이력 진실원에 각각 쓸 수 있는 기존 자산이다. 둘의 역할과 단일 read truth는 아직 결정되지 않았다.

### 개발책임자 판단 필요

1. Issue #894의 기존 결정대로 알림 벨을 채팅으로 완전히 대체할지, 병존시킬지. 병존 시 읽음의 단일 진실원을 어느 쪽으로 둘지.

## 5. S6 파일전송 · 참조번호

### 이미 있는 것

MinIO/파일 경로:

- 같은 `groupware-service`에 `ApprovalAttachmentStorage`의 put/get/delete 추상화와 MinIO 구현이 있다. `.../storage/ApprovalAttachmentStorage.java:5-24`, `MinioApprovalAttachmentStorage.java:17-25,36-44,64-100`.

- 결재 첨부는 `SLIP_REF`, `PARTNER_LEDGER_REF`, `FILE` 타입을 이미 구분한다. `ApprovalAttachmentType.java:3-10`.

- 카카오톡 모델의 사진·동영상·일반 파일 종류별 상한, 보존 기간, 허용 확장자/실행파일 차단은 Issue #894에서 미결정으로 남아 있다.

- 참조번호가 단순 텍스트인지 typed 업무 액션인지, 지원 문서 종류가 무엇인지 확정되지 않았다.

## 6. S7 이모티콘

### 이미 있는 것

- 메시지는 PostgreSQL `VARCHAR(2000)`/Java String/HTML 텍스트로 저장·전송되므로 일반 Unicode emoji 문자를 body에 넣는 기술적 통로는 이미 있다. `V1__init_groupware.sql:77-84`, `Message.java:56-57`, `ChatMessageRequest.java:5`, `ChatMessageResponse.java:6-12`.
- Issue #894에는 메시지 아래 공감 emoji reaction을 PC·모바일 공통 모델/API로 둔다는 개발책임자 결정이 있다. 현재 spec도 reaction을 별도 entity/index로 두도록 기록한다. `docs/superpowers/specs/2026-08-12-894-internal-chat.md:263,335-337`.

### 없는 것

- “이모티콘” 전용 entity/table/API/route/DI/config/화면이 없다.
- reaction entity/table/API도 없다. spec의 `chat:message-updated`는 미래 event 계약 문구일 뿐 현재 생산 코드의 reaction 구현이 아니다.
- composer emoji picker, 고정 세트, 최근 사용, 검색, custom image/sticker asset, 관리/배포 설정이 없다.
- 리액션을 누가 했는지, 1인 다중 허용, 취소/교체, 삭제 메시지와의 관계가 없다.
- `package-lock.json`의 간접 `emoji-regex` 의존성은 UI/도메인 기능 존재 증거가 아니다.

### 인접 기능 재사용 가능성

- 일반 Unicode emoji 입력은 현재 text body 경로를 그대로 쓸 수 있다.
- 메시지 reaction은 S1의 room participant/object authorization과 SSE 재조회 패턴을 재사용할 수 있다.
- 삼한이 tray PNG나 design-system mascot은 브랜드 자산이지 이모티콘 세트로 확정된 자산이 아니다.

### 개발책임자 판단 필요

1. S7의 “이모티콘”이 (a) 텍스트 emoji picker, (b) 메시지 공감 reaction, (c) 이미지 sticker/삼한이 세트 중 무엇을 포함하는지. Issue에는 reaction 결정은 있으나 세 표현이 동일하다는 결정은 없다.
2. reaction 고정 세트, 1인당 복수 허용 여부, 누른 사람 공개 여부.
3. custom 사내 이모티콘을 허용한다면 제작/승인/버전 배포 주체와 외부 이미지 업로드 허용 여부.

## 7. 의존 관계 기준 슬라이스 순서 제안

일정은 추정하지 않는다. 현재 코드 의존성만 놓고 다음 순서를 제안한다.

1. **공통 선행 결정: S1 채팅 UI/client의 독립 앱 이식 소유 확정**
   - 현재 독립 앱은 셸뿐이라 S5~S7의 부착 지점이 없다. S3에 포함하거나 별도 공통 슬라이스로 분리해야 한다.
2. **S3 자동 로그인**
   - 보호된 room/notification/upload API와 SSE 모두 인증이 선행돼야 한다.
3. **S5 알림**
   - 독립 앱이 트레이에 상주하는 이유와 백그라운드 메시지 수신 경로를 먼저 닫는다. 기존 notification center와 room SSE의 역할/읽음 진실원을 확정하면 이후 첨부·reaction 알림도 같은 경로를 쓴다.
4. **S4 접속 상태·부재중**
   - 인증된 사용자/기기 session이 전제다. S5와 구현 의존은 약하지만 전역 session/heartbeat 계약을 먼저 안정화하면 사용자 상태를 채팅 목록에 붙일 수 있다.
5. **S6 파일전송·참조번호**
   - 인증·방 참여자 인가·독립 앱 composer와 알림 문구 계약 위에 attachment/reference를 추가한다.
6. **S7 이모티콘/리액션**
   - 기본 대화 UI와 `chat:message-updated` 소비가 정리된 뒤 붙일 수 있다. S6와 데이터 의존은 없으므로 개발책임자 정의가 먼저 확정되면 순서를 바꿀 수 있다.

S4와 S5는 병렬 가능한 기술 영역이지만, 이 저장소의 현재 빈칸은 “상주 앱의 인증된 백그라운드 메시지 수신”이므로 S5를 먼저 제안했다. 이는 일정 추정이나 구현 방식 확정이 아니다.

## 9. 판정 불가로 남긴 것

1. **운영/공유 DB의 실제 row 수와 bucket 객체 수**: 다른 트랙 4건이 같은 스택에서 동작 중이므로 DB를 조회하지 않았다. 코드·마이그레이션 존재만 판정했다.
2. **PR #1181 auto-update 실제 설치 성공**: `main`에 병합된 코드와 계약 테스트는 확인했으나 서명 packaged installer와 release feed가 없어 E2E는 판정 불가다.

5. **이모티콘의 제품 의미**: Issue의 reaction 결정과 S7 명칭만으로 emoji picker/sticker 포함 여부를 확정할 수 없다.
6. **채팅 첨부 운영 정책**: 용량·보존·확장자·삭제 정책은 Issue #894에도 미결정으로 남아 있다.
7. **GROUP 방·정밀 읽음·멘션의 새 슬라이스 배치**: 과거 spec의 번호와 PR #1192/#1193 이후 번호가 달라 현재 S3~S7 표만으로 소유 슬라이스를 확정할 수 없다.
