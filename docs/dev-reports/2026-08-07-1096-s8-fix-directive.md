# PR #1097 / 이슈 #1096 — S8 결함 수정 지시서

## 1. 결함과 우선순위

### F1 — HIGH: 대량 soft-delete 뒤 기본 문서 목록이 활성 모집단을 표시하지 않음

- baseline 활성 견적 34건인데 `/sales/estimates`는 `전체 2,027건` 표시.
- 활성 주문 3건인데 `/sales/partner-orders`는 `전체 1,988건` 표시.
- 삭제행 감사/복원 계약과 활성 업무 목록을 한 기본 모집단에 합친 것이 직접 원인이다.

### F2 — HIGH: 잔존 활성 전표에 명백한 system 시드 103건 포함

- baseline 활성 전표 343건 중 `system` 100건, `system-internal` 3건.
- `2026/01/01-1`은 `[Stage 2 시드]`, `TEST-MODEL-0001`, `테스트제품-TEST-MODEL-0001`을 사용자 상세에 노출한다.
- “남은 문서는 정본”이라는 S8 전제를 충족하지 않는다.

3. 활성 34건 대신 `전체 2,027건`과 삭제행을 본다.
4. 주문서 관리에 진입한다.
5. 활성 3건 대신 `전체 1,988건`과 삭제행/복원 버튼을 본다.

```sql
SELECT count(*)
FROM slips

```

## 3. 근본원인과 금지되는 우회

F1 근본원인:

- 관리자 FE가 삭제 감사/복원 표면을 위해 기본 query에 `includeDeleted=true`를 고정한다.
- 대량 삭제 전에는 감당 가능한 UX였지만 cleanup 1,986/2,018건과 결합해 활성 업무 화면의 의미가 바뀌었다.

F2 근본원인:

- V117은 101개 product UUID 참조만 cleanup한다.
- 별도 Stage 2/system 시드 문서는 snapshot 모델명 또는 다른 product graph를 사용해 그 경계 밖에 남는다.
- `created_by='system'`만 보고 곧바로 전량 삭제해서는 안 된다. service 생성 정본 가능성을 먼저 배제해야 한다.

금지:

- hard delete 금지.
- 문서번호/품목명 prefix 하나만으로 삭제 금지.
- 기본 목록에서 삭제행을 완전히 없애 감사/복구 경로를 제거하는 우회 금지.
- 기존 cleanup actor를 재사용해 서로 다른 작업을 구분 불가능하게 만드는 방식 금지.

## 4. 요구 수정과 불변식

F1:

1. 견적/주문/판매전표 기본 목록은 활성행만 조회하고 카운터도 활성행만 센다.
2. 삭제행은 명시적 `삭제 문서 포함` 토글 또는 별도 감사 탭에서만 조회한다.
3. 삭제행 표면에서는 기존 삭제자/삭제시각/복원 가능 여부를 그대로 보존한다.
4. 필터 전환 시 페이지·카운터·empty state가 같은 모집단을 사용한다.

F2:

1. 103건을 문서번호, source_type, created_by, 메모 표식, 라인 product_id/model snapshot, 생성시각으로 전수 분류한다.
2. 정본 가능성이 0인 결정적 시드 집합만 새 migration actor로 soft-delete한다.
3. 혼합 문서는 기존 정책대로 정본 라인을 보존하고 시드 라인만 정리한다. 문서 전체 삭제가 필요한 새 범주는 개발책임자 결정 없이 확대하지 않는다.
4. 복구 SQL을 같은 migration 끝에 actor 한정으로 남긴다.
5. baseline 343의 판매/입고 축을 분리한다. S8 baseline은 `OUTBOUND 301 + INBOUND 42`; 판매 목록에 343을 기대하는 테스트를 만들지 않는다.

## 5. 완료 조건

- 정상 service 생성 문서 반대급부 fixture가 삭제되지 않는다.
- mixed 문서, 이미 삭제된 문서, 복원 가능/불가 문서 회귀 테스트가 있다.
