1. **`SALE_SUMMARY` 매출의 차·대변/잔액 방향이 반대다.**
   - 재현: journal 매출만 있는 기간·거래처를 조회 → 집계 행에서 `원장 보기` → `인쇄 미리보기`.
   - 결과: 집계에서는 매출인 금액이 상세·인쇄에서는 대변으로 표시되고 잔액이 음수가 된다.
   - 실증값: R8 `P-2026-0005`는 집계 매출 `26,000,000원`인데 상세·인쇄는 대변 `26,000,000원`, 기말 `-26,000,000원`이다. 현 DB 2026년 범위에서는 선택 가능한 27거래처·401 매출 `411,000,000원`이 이 분기를 탄다.

2. **집계 채권잔액과 상세·인쇄 기말잔액의 금액 원천이 달라 같은 거래처·기간에도 일치할 수 없다.**
   - 집계 채권은 110 차변/대변과 확정 입금을 쓰지만, 상세·인쇄 문서는 401 `SALE_SUMMARY`와 확정 입금만 쓴다.
   - R8 한 화면에서 집계 채권 `28,600,000원` 대 상세 기말 `-26,000,000원`으로 이미 갈라진다.
   - 현 DB의 위 27거래처는 401 `411,000,000원` 대 110 차변 `452,100,000원`이다. 따라서 표시 방향과 별개로 VAT `41,100,000원`이 상세·인쇄에서 빠진다. 현 코드 방향까지 포함한 집계↔상세 gap 합계는 `863,100,000원`이다.

3. **존재하지 않는 거래처 코드로 조회하면 0건이 아니라 전체 거래처 집계가 나온다.**
   - 재현: 거래처 코드에 `NOSUCH9999`처럼 master에 없는 값을 입력하고 `조회`.
   - 결과: BE에서 “해소되지 않은 필터”와 “필터 없음”이 모두 `selectedId=null`이 되어 기간 전체 journal·입금·판매전표를 반환한다.

4. **현재 DB의 QA 판매전표가 실 집계에 섞이고, 그 행의 상세·인쇄는 집계와 끊긴다.**
   - 기간에 `2026-06-24`를 포함해 무필터 조회하면 `2026/06/24-901`(`QA-GATE-A`, `2,400,000원`)과 `-902`(`QA-GATE-B`, `0원`)가 집계된다. 두 행 모두 활성 canonical OUTBOUND이지만 partner master에는 없는 QA 잔재다.
   - `QA-GATE-A` 행의 `원장 보기`를 누르면 선택 partner가 해소되지 않아 빈 상세가 나온다. 이 코드를 검색창에 직접 넣으면 결함 3 때문에 한 건이 아닌 전체 집계가 나온다.
   - `2026/08/04-*` 및 그 밖의 확인된 `QA-*` 전표는 현재 종류/상태 필터에서 제외되므로 이 결함의 현행 혼입 목록에는 넣지 않았다.

5. **복원 원장을 보고 있는 상태에서 저장·CSV·인쇄가 서로 다른 live 원장을 사용한다.**
   - 재현: 과거 이력 `복원` → 표에 복원본이 표시된 상태에서 각 버튼 실행.
   - `현재 원장 저장`: 화면 복원본이 아니라 서버 현재 read model을 다시 조회해 저장한다.
   - `CSV 다운로드`: 복원본이 아니라 캐시된 live `ledgerQuery.data`를 내보낸다.
   - `인쇄 미리보기`: 새 라우트가 서버 live 원장을 다시 조회한다.
   - 과거 snapshot과 현재 원장이 다르면 화면·저장·CSV·인쇄가 같은 사용자 세션 안에서 불일치한다. 반면 복원 상태가 아닌 정상 live 화면의 신규 payload 저장→복원 자체는 같은 `documents`를 왕복한다.

6. **21번째 이전 저장 이력은 GUI에서 복원할 수 없다.**
   - 이력 API 기본 page size는 20이고 FE는 page/size를 보내지 않으며 페이지 이동 UI도 없다.
   - 같은 거래처·기간에서 `현재 원장 저장`을 21회 이상 하면 오래된 snapshot은 DB에 남지만 목록과 복원 GUI에서 사라진다.

7. **서로 다른 두 GUI 세션의 같은 밀리초 저장은 전역 batch 번호가 충돌해 한 건이 실패한다.**
   - batch 번호가 `LED` + 밀리초 시각뿐이고 DB는 활성 `batch_no`를 unique로 제한한다. sequence/난수/충돌 재시도가 없다.
   - renderer별 중복 클릭 방지는 서로 다른 사용자 세션을 조정하지 못한다. 두 사용자의 정상 저장 요청이 같은 밀리초에 도달하면 한 요청이 unique violation으로 실패한다.

8. **명시적 저장 이력을 `자동 저장 이력`으로 오표기한다.**
   - 실제 저장은 `현재 원장 저장` 버튼 클릭으로만 발생하지만 이력 영역 제목은 항상 `자동 저장 이력`이다. 저장 시점을 사용자가 오해하게 하는 상시 GUI 문구 결함이다.

payload 분기 자체에서는 도달 결함을 확인하지 않았다. 제품 writer가 만든 legacy payload에는 `documents`가 없고, 신규 payload에는 빈 목록이어도 `documents`가 직렬화되므로 `root.has("documents")` 분기는 두 실제 형식을 구분한다. 수동 변조 payload는 이번 판정에서 제외했다.

## 이 라운드가 보지 않은 것

이번 라운드는 요청대로 이미지 재빌드·재배포·컨테이너 중지·DB 쓰기를 하지 않았다. 현재 실행 중 컨테이너가 대상 HEAD 산출물이라는 보장이 없어, 그 서버를 호출한 결과를 HEAD의 live 증거로 사용하지 않았다. 다음 live QA는 아래 순서로 수행해야 한다.

1. accounting/slip/desktop을 정확히 `b73d444697f54a8120cc9b91f6fe536e2e982d87`에서 배포하고, 화면의 `VITE_MOCK_MODE=0`, API base, 백엔드 build SHA를 먼저 증명한다.
2. 401/110 값이 알려진 거래처를 조회해 집계의 매출·수금·채권, 상세의 차변·대변·잔액, 단건/일괄 인쇄 합계·기말을 한 표로 대조한다. 특히 `SALE_SUMMARY`, VAT 포함 110, 확정 입금이 함께 있는 거래처를 포함한다.
3. `NOSUCH9999` 조회가 0건인지 전체 목록인지 확인하고, 기간 `2026-06-24`에서 `QA-GATE-A/B` 혼입 → 행 클릭 상세 → 단건/일괄 인쇄까지 기록한다.
4. 현재 DB에는 `PARTNER_LEDGER`가 0건이므로 신규 snapshot을 GUI에서 생성한 뒤 history 증가·행 수·복원을 확인한다. 그 후 원본 거래가 달라진 상태의 과거 snapshot을 복원해 화면, CSV, 인쇄, 다시 저장한 payload가 모두 복원본과 같은지 대조한다.
5. legacy 복원 분기는 실제 legacy `PARTNER_LEDGER` 행이 0건이라 live로 보지 못했다. 통제된 legacy `LedgerImageResponse` fixture가 있는 환경에서 목록→복원→화면 금액을 검증한다. 신규 빈 `documents: []` snapshot도 별도로 복원한다.
6. 두 독립 GUI 세션에서 저장 요청을 동기화해 batch 번호 충돌 여부와 사용자 오류 표시를 확인한다. 이어 같은 거래처·기간에 21건 이상 저장해 21번째 이전 이력에 접근 가능한지 확인한다.
7. 로컬 dev DB 밖의 운영 데이터, 운영 동시성, 실제 legacy row 분포는 보지 않았다. R12의 `12→13`과 `LED20260804074502997`은 현재 DB에 존재하지 않으므로 다음 QA의 baseline으로 재사용하면 안 된다.
