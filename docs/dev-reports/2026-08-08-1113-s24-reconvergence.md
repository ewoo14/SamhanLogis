## 신규 결함 1 — BLOCKER: 표준 기동 경로가 현재 지원 DB 상태에서 복구 불가능한 seed를 자동 활성화한다

S23은 `infrastructure/env-templates/.env.dev-seed:61`을 다음과 같이 바꿨다.

```text
SAMHAN_SEED_TEST_DATA=true
```

`infrastructure/scripts/start-local-full.ps1:274-299`는 이 파일의 모든 non-comment 값을 process environment에 강제로 적재하고, product-service 다음 inventory-service를 의존 순서로 기동한다. 사용자가 seed를 별도로 요청하거나 상태를 확인하는 분기 없이 표준 실행만으로 두 mutation seeder가 켜진다.

현재 DB를 SELECT만 한 결과, S23이 대상으로 삼는 `product_code ~ '^01[0-9]{4}$'` cohort는 다음과 같다.

```text
active=0
soft_deleted=100
```

도달 흐름은 코드상 결정적이다.

1. `HvacProductSeeder.java:144`는 활성 modelName만 존재 검사한다. 100건 모두 soft-deleted이므로 전부 신규 대상이 된다.
2. `:150-155`는 같은 deterministic PK로 native INSERT를 시도한다. 기존 soft-deleted PK와 충돌한다.
3. `:156-159`는 행별 `RuntimeException`을 로그로 남기고 계속하므로 product-service 자체는 활성 product 0건인 채 다음 단계로 진행할 수 있다.
4. inventory의 `ProductSeedIntegrityValidator.java:28-36`은 활성 deterministic product 100건을 조회하고, 누락 100건이면 `IllegalStateException`을 던진다.
5. 따라서 표준 순차 기동은 inventory-service health gate에서 중단된다. S23 A-2 메시지 역시 `:53-56`에서 재기동/toggle 재실행으로 자동 복구할 수 없다고 명시한다.

즉 공통 배선의 존재는 확인되지만, S23의 기본 `true`가 현재 표준 개발 상태를 정상 기동시키지 못한다. `start-local-full -SkipDocker -SkipServices -SkipPortCheck`가 exit 0인 것은 기존 컨테이너와 row count SELECT만 확인한 결과이며, 변경된 seed 기동 경로의 성공 증거가 아니다. 사용자 금지에 따라 실제 재시드/서비스 재기동으로 장애를 발생시키지는 않았다.

## S22 결함 5건 폐쇄 여부

### A-1 — 닫힘: 공통 toggle 배선은 세 지점 모두 존재한다

- template: `infrastructure/env-templates/.env.dev-seed:61`
- compose product: `infrastructure/docker-compose.local-all.yml:195`
- compose inventory: `infrastructure/docker-compose.local-all.yml:223`
- Spring property 소비: product `application.yml:58`, inventory `application.yml:51`

`docker compose ... config --format json`의 비파괴 확인 결과, process 환경 미설정 시 두 서비스 모두 `false`, `SAMHAN_SEED_TEST_DATA=true` 설정 시 두 서비스 모두 `true`였다. 배선 누락은 닫혔다. 위 신규 결함은 template에서 자동 선택한 값의 오차단이다.

### A-2 — 닫힘: 안내는 현재 가능한 행동을 말한다

`ProductSeedIntegrityValidator.java:52-56`은 현재 상태가 단순 재기동/toggle 재실행으로 자동 복구되지 않으며, soft-delete 처리 정책이 결정·적용될 때까지 재고 seed를 재시도하지 말라고 안내한다. 존재하지 않는 자동 복구 절차를 지시하지 않고, 사용자가 지금 취할 행동인 “재시도 중단 및 정책 결정 대기”를 명시한다.

다만 표준 template가 그 안내와 반대로 자동 재시도를 활성화하는 문제는 신규 결함 1로 분리했다.

### B-1 — 닫힘: `launch-local-stack.ps1`

`scripts/launch-local-stack.ps1:136-138`이 bootJar 직후 종료코드를 저장하고 nonzero에서 throw한다. 계약 테스트는 통과했고, PowerShell 5.1 동일 패턴 격리 probe는 build 23에서 부모 exit 1, build 0에서 exit 0이었다. 후속 compose 성공이 build 실패를 덮는 경로는 끊겼다.

### B-2 — 닫힘: `stop-local-stack.ps1`

`scripts/stop-local-stack.ps1:45-61`이 down의 두 분기 모두 종료코드를 저장하고 nonzero에서 완료 문구 전에 throw한다.

- PowerShell 5.1 격리 mock: down 0 → exit 0, down 37 → exit 1
- 고유 project `s24-empty-1113`의 이미 내려간 compose: 실제 Docker CLI exit 0

따라서 “이미 멈춰 있음”은 성공이고 실제 down 실패만 실패가 된다. 공유 stack을 대상으로 stop 스크립트를 실행하지 않았다.

### B-3 — 닫힘: `stop-local-full.ps1`

`infrastructure/scripts/stop-local-full.ps1:122-137`이 `down`/`down -v` 직후 종료코드를 저장하고 nonzero에서 `종료 완료` 전에 throw한다. Docker 관측을 차단하고 모든 서비스 포트를 미점유 격리 포트로 바꾼 뒤 `-KeepDocker`로 실행한 “이미 멈춰 있음” 경로는 PowerShell 5.1 exit 0이었다. 공유 service/process/container에는 접근하지 않았다.
