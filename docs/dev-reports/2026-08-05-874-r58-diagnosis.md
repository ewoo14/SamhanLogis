# R58 진단 및 수정 보고서 — PR #1057 · 이슈 #874

실행일: 2026-08-05 (KST)  
대상: 협업 수정 저장 `2026/08/01-7`  
배포 기준: slip-service V112, notification-service V10  
제한 준수: DB는 `SET default_transaction_read_only=on`을 적용한 SELECT만 수행했고, Docker 재빌드·재배포·중지 및 실제 vendor 발송은 수행하지 않았다.

## 결론

R57 결함은 수신자 해석 실패나 notification-service 미수신이 아니다. **끊긴 지점은 PUSH 발송 성공 경로가 `notification_center` 저장 경로를 호출하지 않는 계약 경계**다.

따라서 이번 수정은 협업 outbox의 비동기 worker가 다음 두 결과를 모두 확인한 뒤에만 `SENT`로 전이하도록 했다.

1. 기존 PUSH 발송 요청이 notification-service에서 `SENT`로 완료됨
2. 같은 사건·수신자의 `notification_center` 행이 생성되거나 이미 존재함

인앱 저장은 `sourceService=slip-service`, `sourceRefId=eventId`, `targetUserId` 조합으로 멱등 조회한다. PUSH 재시도 시 기존 idempotency key를 재사용하므로 중복 PUSH를 만들지 않는다. 저장 요청은 기존처럼 after-commit executor/scheduler에서 수행되므로 협업 저장 HTTP 응답은 외부 호출을 기다리지 않는다.

## R57 DB 읽기 증거 요약

- `slip_db.slip_collab_notification_outbox`: 협업 수정 제목 1행, `SENT`, 수신자 1명.
- `notification_db.notification_requests`: 해당 제목 1행, `USER/PUSH/SENT`, 멱등키 존재.
- `notification_db.notification_logs`: 해당 request에 대해 10행, 전부 `SUCCESS`.
- `notification_db.push_device_tokens`: 해당 수신자 active token 10개.
- `notification_db.notification_center`: 해당 제목·수신자 조합 0행.
- `auth_db.accounts`: 해당 수신자 UUID는 `dev_master` 활성 계정으로 해석됨.

UUID 값은 이 보고서와 사용자 화면에 기록하지 않았다.

## 적용한 수정

- `NotificationClient`에 내부 알림센터 publish 호출을 추가했다.
- 협업 outbox worker는 PUSH 성공 후 알림센터 publish까지 성공해야 `SENT`로 전이한다. center publish 실패 시 outbox는 기존 retry/terminal 정책을 따른다.
- `NotificationCenterService.publish`는 동일한 `targetUserId + sourceService + sourceRefId + channel`을 먼저 조회해 재시도 시 기존 center 행을 반환한다.
- 새 migration은 필요하지 않았다. 기존 `notification_center` 컬럼을 사건 멱등키로 사용했다.
