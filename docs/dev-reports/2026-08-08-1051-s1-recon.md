# #1051 S1 정찰 — 전표·견적·주문서 product 참조 재측정

- 조사 시점: 2026-08-08, 공유 Docker PostgreSQL, `SELECT`만 실행
- PR 본문 선독: PR #1129
- 비교 기준: `product_db.products.is_deleted = false`인 활성 카탈로그
- 대상 라인: `slip_lines`, `estimate_lines`, `partner_order_lines` 중 `is_deleted = false`
- UUID는 보고서에 기록하지 않았다. 실제 행의 UUID 필드는 `[UUID 비공개]`로 치환했다.

## A. 끊긴 참조 현황

DB가 서비스별 별도 PostgreSQL database라 단일 cross-database JOIN은 사용할 수 없었다. 아래 두 SELECT의 결과를 product `id`에 대해 읽기 전용으로 동등 비교했다.

```sql
-- slip_db
SELECT id, product_id, product_name, model_name, created_at, created_by,
       is_deleted, deleted_at, deleted_by
FROM slip_lines
WHERE is_deleted = false
  AND product_id IS NOT NULL;

-- slip_db
SELECT id, product_id, product_name, model_name, created_at, created_by,
       is_deleted, deleted_at, deleted_by
FROM estimate_lines
WHERE is_deleted = false
  AND product_id IS NOT NULL;

-- partner_order_db
SELECT id, product_id, product_name, model_name, created_at, created_by,
       is_deleted, deleted_at, deleted_by
FROM partner_order_lines
WHERE is_deleted = false
  AND product_id IS NOT NULL;

-- product_db
SELECT id, model_name, model_code, product_code, created_at, created_by,
       is_deleted, deleted_at, deleted_by, name
FROM products;
```


## B. 원인 세 갈래

### ① 삭제됐다

- 전표 343행/3 UUID: product 원본 `created_by=qa798`, `created_at=2026-07-12`, 모델명과 행 이름에 `QA797`, `deleted_by=system-sheet-sync`, `deleted_at=2026-07-28`가 공통이다. QA 잔재로 판정한다.
- 견적 53행/3 UUID: 같은 `QA797`/`qa798`/`system-sheet-sync` 계열이다. 전표와 동일한 QA 잔재다.
- 주문서 2행/2 UUID: product 원본은 `created_by=system`, `created_at=2026-05-31`, 삭제 actor가 `issue-1096-test-seed-cleanup`이다. QA/이슈 cleanup 잔재이며 삭제 시각은 2026-08-07 16:54:39다.

### ② 세대가 교체됐다

이번 표본에서 삭제 전용으로 분류된 product는 모두 **삭제 전 원본 행이 존재**한다. 다만 “활성 새 세대가 같은 모델명으로 교체됐다”는 판정은 할 수 없었다. 해당 삭제 행의 `model_code`가 NULL이고, 이 조회에서 같은 모델명의 활성 product가 있다는 증거를 확인하지 않았다. 따라서 현재 증거는 “세대 교체”가 아니라 “원본 soft-delete 후 참조 잔류”다.

### ③ 애초에 없는 UUID

전표 303행/101 UUID가 product DB에 전혀 없다. 전표 원본은 `created_at=2026-05-09`, `created_by=system`, 모델명이 `TEST-MODEL-0001` 등 결정적 테스트 시드 규칙이다. 이는 제품 삭제보다 **구형 dev 시더가 만든 orphan UUID**에 가깝다. `model_name`이 `TEST-MODEL-*`이고 product 행 자체가 0건이므로 QA797/issue-1096 삭제 계열과 섞지 않는다.

```sql
SELECT created_by, date_trunc('day', created_at), COUNT(*)
FROM slip_lines
WHERE is_deleted = false
  AND created_at >= TIMESTAMP '2026-05-09'
  AND created_at <  TIMESTAMP '2026-05-10'
GROUP BY created_by, date_trunc('day', created_at)
ORDER BY 2, 1;
```

```text
system  2026-05-09 00:00:00  300
```

## C. 조인 키 채움률

```sql
SELECT 'slip_lines', COUNT(*),
       COUNT(*) FILTER (WHERE product_id IS NOT NULL AND product_id::text <> ''),
       COUNT(*) FILTER (WHERE model_name IS NOT NULL AND btrim(model_name) <> ''),
       COUNT(*) FILTER (WHERE product_name IS NOT NULL AND btrim(product_name) <> '')
FROM slip_lines WHERE is_deleted = false;

SELECT 'estimate_lines', COUNT(*),
       COUNT(*) FILTER (WHERE product_id IS NOT NULL AND product_id::text <> ''),
       COUNT(*) FILTER (WHERE model_name IS NOT NULL AND btrim(model_name) <> ''),
       COUNT(*) FILTER (WHERE product_name IS NOT NULL AND btrim(product_name) <> '')
FROM estimate_lines WHERE is_deleted = false;

SELECT 'partner_order_lines', COUNT(*),
       COUNT(*) FILTER (WHERE product_id IS NOT NULL AND product_id::text <> ''),
       COUNT(*) FILTER (WHERE model_name IS NOT NULL AND btrim(model_name) <> ''),
       COUNT(*) FILTER (WHERE product_name IS NOT NULL AND btrim(product_name) <> '')
FROM partner_order_lines WHERE is_deleted = false;
```

```text
slip_lines             845  845  845  845
estimate_lines          89   89   89   89
partner_order_lines      8    8    8    8
```

라인 테이블에는 `model_code`·`product_code` 컬럼이 없다. 라인 측의 UUID 외 저장 조인 후보는 `model_name`뿐이며, 현행 활성 라인에서는 세 라인 테이블 모두 100% 채워져 있다. 이는 UUID가 끊겨도 화면 snapshot 문자열은 남는 구조다.

```sql
SELECT COUNT(*),
       COUNT(*) FILTER (WHERE is_deleted = false),
       COUNT(*) FILTER (WHERE is_deleted = false AND model_code IS NOT NULL AND btrim(model_code) <> ''),
       COUNT(*) FILTER (WHERE is_deleted = false AND product_code IS NOT NULL AND btrim(product_code) <> ''),
       COUNT(*) FILTER (WHERE is_deleted = false AND model_name IS NOT NULL AND btrim(model_name) <> ''),
       COUNT(*) FILTER (WHERE is_deleted = false AND name IS NOT NULL AND btrim(name) <> '')
FROM products;
```

```text
3221  3083  3083  2696  3083  3083
```

활성 카탈로그의 채움률은 `model_code 3083/3083`, `product_code 2696/3083`, `model_name 3083/3083`, `name 3083/3083`이다. 즉 현재 끊김의 직접 원인은 라인 `product_id`/snapshot 미채움이 아니라 product master의 soft-delete와 orphan UUID다.

## D. 사용자 영향

코드 확인 결과:

- `services/slip-service/.../client/ProductClient.java`: `/products/internal/lookup` 응답에서 요청 수보다 적은 product summary가 오면 `NOT_FOUND`를 던진다. product master를 다시 조회하는 경로는 오류가 된다.
- `services/slip-service/.../domain/SlipLine.java`와 `services/slip-service/.../web/SlipInternalController.java`: 전표 라인에는 `productName`·`modelName` snapshot이 있고 상세 응답에 그 값을 직접 매핑한다.
- `clients/desktop/src/renderer/print/InvoiceView.tsx`: `modelName`이 있으면 `modelName (productName)`으로 렌더링하고 둘 다 없을 때만 `-`를 렌더링한다.

따라서 영향은 경로별로 갈린다.

1. 전표·견적·주문서 상세/인쇄처럼 저장된 snapshot을 읽는 화면: 이번 실측 행들은 `model_name`·`product_name`이 모두 채워져 있어 **빈 값보다 기존 이름이 보일 가능성이 높다**.
2. product-service 재조회가 필요한 품목 보강/검증 경로: orphan UUID는 summary 누락으로 **NOT_FOUND/업무 오류**가 될 수 있다. 이 경우 200 OK 빈 값으로 안전하게 처리된다는 근거는 확인하지 못했다.
3. 모델코드 화면: line schema에 `model_code`/`product_code`가 없으므로 UUID만으로 product master를 재조회하는 화면에서는 코드가 조용히 채워지지 않는다. snapshot `model_name`은 모델코드와 동치라고 보장할 수 없다.

## 선택지

- 선택지 A — QA797·issue-1096 행은 복원하지 않고 잔재 정리 트랙으로 분리: 이걸 고르면 QA/cleanup 데이터를 업무 품목으로 되살리지 않게 되고, 전표·견적·주문서의 삭제 전용 참조는 그대로 남는다.
- 선택지 B — 전표 303행의 구형 dev 시드 orphan을 운영 복구와 분리: 이걸 고르면 `TEST-MODEL-*` 계열을 별도 환경 데이터 문제로 격리하고, 현행 업무 데이터의 relink은 하지 않게 되며, 화면의 해당 snapshot은 계속 남는다.
- 선택지 C — 저장 snapshot 표시를 유지하고 product 재조회 실패만 명시적 오류로 다루는 별도 설계: 이걸 고르면 상세/인쇄의 이름은 보존하면서 master-dependent 경로의 조용한 누락을 막을 수 있지만, 이번 정찰 범위에서는 API/UI 변경을 하지 않는다.
- 선택지 D — product_id를 모델명/코드로 일괄 재연결: 이걸 고르면 참조가 일부 활성 catalog로 이어질 수 있지만, 동명·세대 교체·QA 잔재 오연결 위험 때문에 현재 증거만으로는 안전성을 입증할 수 없다.

판정과 선택은 하지 않았다. 이번 작업에서 DB 쓰기, 코드 수정, Docker 재기동, 커밋·push는 수행하지 않았다.
