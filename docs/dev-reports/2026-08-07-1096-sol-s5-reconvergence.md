# PR #1097 / 이슈 #1096 — CODEX SOL 5.6 S5 재수렴

- 검증 HEAD: `c2c5988d2b53277da866085151b461e954102070`
- 판정 범위: 실 사용자 도달성만. 예외적으로 S5 근거의 증거 무결성을 확인했다.
- 판정: **BLOCK — 환경 이식성 도달 결함 1건**

## 0. 결론

V117은 견적번호 5개와 `is_deleted=FALSE AND status='QUOTE_DRAFT' AND converted_slip_id IS NULL`만으로 정리 대상을 고른다. 라인이 QA797인지, 101개 시더 품목인지, 또는 기대한 혼합 구조인지 확인하지 않는다. 따라서 다른 DB에서 같은 번호를 쓰는 정상 업무 DRAFT 견적도 모든 활성 라인과 헤더가 soft-delete된다. 더 나쁘게는 일반적인 정본 문서라면 헤더가 cleanup actor를 가지므로 화면의 `복원` 버튼도 409로 막힌다. 배포 시 Flyway가 자동 실행하고, 이후 견적서 관리 화면에서 바로 관측되므로 실 사용자 경로다.

현재 회사PC DB에서 하드코딩 선택 조건을 만족하는 행은 **4건**이다. PM이 말한 혼합 4건이며 총 **12라인**이다. `2026/07/27-1`은 이미 삭제 상태라 `is_deleted=FALSE` 가드에서 제외된다.

정책 비대칭은 기술적으로 명확하다. 혼합 4건은 배포 직후 `삭제됨`으로 보이지만 사용자가 `복원`을 누르면 QA 2라인과 정본 1라인이 전부 활성화된다. 순수 QA797 `2026/07/27-1`은 같은 버튼에서 `비정본 QA 잔재 견적은 일반 복원할 수 없습니다: 2026/07/27-1`로 막힌다. 이것이 결정 1을 무력화하는지, 정본 라인이 있으므로 맞는지는 이 보고서가 판단하지 않는다.

## 2. 도달 결함 — 견적번호 하드코딩이 다른 환경의 정상 문서를 삭제한다

### 원인 원문

V117의 대상 선택에는 문서 provenance가 없다.

```sql
SELECT id
FROM estimates
WHERE estimate_no IN (
    '2026/07/17-1', '2026/07/17-2', '2026/07/17-5',
    '2026/07/17-20', '2026/07/27-1'
)
  AND is_deleted=FALSE
  AND status='QUOTE_DRAFT'
  AND converted_slip_id IS NULL;
```

선택된 ID는 라인 내용과 무관하게 다음 OR 절로 모든 활성 라인이 삭제된다.

```sql
WHERE l.is_deleted=FALSE
  AND (l.product_id IN (SELECT id FROM _issue_1096_test_product_ids)
       OR l.estimate_id IN (SELECT id FROM _issue_1096_cleanup_estimate_ids));
```

활성 라인이 0이 되면 헤더도 cleanup actor로 삭제된다. `QUOTE_DRAFT`와 미전환 조건은 정상 업무 견적도 통과하므로 안전 provenance가 아니다.

### 실 사용자 도달 경로

```text

→ Flyway V117 자동 적용
```


현재 DB의 실제 선택 건수는 **4건/12라인**이다. 다른 환경의 업무 문서 건수는 그 DB를 읽지 않고는 셀 수 없지만, 같은 번호의 정상 DRAFT 한 건만 존재해도 위 SQL과 화면 경로로 결정적으로 재현된다.

### 자기 검증 조건이 필요한가

**필요하다.** 불변식은 “번호가 맞다”가 아니라 “이 환경에서도 삭제하려는 바로 그 비정본 artifact임이 데이터 자체로 증명된다”여야 한다. 상태와 미전환 여부는 보조 가드일 뿐 provenance 증명이 될 수 없다.

## 3. 두 정책의 비대칭 — 사용자에게 보이는 원문만

### 혼합 4건

V117 적용 후 혼합 4건은 헤더와 각 3라인이 모두 cleanup actor로 삭제된다. 목록 native query는 삭제행도 반환하고 화면은 다음을 렌더링한다.

```text
상태: 삭제됨
버튼: 복원
aria-label: “2026/07/17-1 견적서 복원” (각 번호별 동일 형식)
```

버튼 클릭 후 서비스 관측값은 다음과 같다.

```text
hasQa797Line=true
hasCanonicalLine=true
mixedQaAndCanonical=true
deletedLineCount=3
restorableLines=3
```

따라서 200으로 헤더와 3라인을 모두 복원하고 합계를 재계산한다. 사용자는 다시 활성화된 QA 2라인+정본 1라인과 전체 금액 **565,400 / 1,001,000 / 1,001,000 / 1,001,000원**을 보게 된다.

### 순수 QA797 `2026/07/27-1`

현재 문서는 삭제 헤더+활성 QA797 2라인이다. 목록에는 동일하게 `삭제됨`과 `복원`이 보인다. 클릭하면 다음 원문이 빨간 오류 배너에 표시된다.

```text
비정본 QA 잔재 견적은 일반 복원할 수 없습니다: 2026/07/27-1
```

행은 그대로 보존되고 헤더와 라인은 활성화되지 않는다.

### 정책 판정 보류

- 결정 1이 “이번 정리는 사용자가 되돌릴 수 없는 지속 격리”라는 뜻이면 혼합 4건의 화면 복원은 그 취지를 되돌린다.
- 결정 1이 “문서 전체를 soft-delete하되 정본 라인이 있는 문서는 기존 복원 권한을 유지”라는 뜻이면 현재 혼합 복원은 그 의미와 맞는다.

두 경우의 사용자 관측은 위와 같으며, 어느 의미인지는 이 라운드가 대신 결정하지 않는다.

## 4. 차단·삭제 건수와 S3 계약

### 차단되면 안 되는 정본 견적

V117 적용 후에도 활성로 남고 실제 정본 라인을 가진 견적은 **3건**이다.

```text
2026/08/05-1 (2라인), 2026/08/06-1 (1라인), 2026/08/06-2 (1라인)
```

모두 과거 삭제 라인 0건이다. 정상 DELETE는 헤더만 삭제하고, 이어지는 화면 복원에서 `deletedLineCount=0`, `restorableLines=0`이므로 **3/3 성공 경로**다. 현재 데이터에서 S5가 정본 라인 보유 견적의 정상 삭제→복원을 새로 막는 건수는 **0건**이다.

별도로 활성 라인이 0인 비-QA 빈 견적 헤더 4건(`2026/07/17-3`, `-4`, `-18`, `-19`)도 같은 0/0 조건으로 **4/4 복원 성공 경로**다. 실제 정본 라인이 없으므로 위 정본 3건 분자에는 넣지 않았다.

### 다섯 번호 밖의 영향

S5의 하드코딩 OR가 새로 추가한 영향은 혼합 4건의 QA 라인 **8개**와 헤더 **4개**뿐이다. 번호 목록 밖의 문서를 그 OR가 선택하는 건수는 **0건**이다.

다만 V117 전체는 기존 101개 product ID 경로로 다섯 번호 밖의 견적 **1,985건/활성 라인 1,989개**에도 영향을 준다. 그중 **1,981건**은 모든 활성 라인이 정리되어 헤더도 삭제되고, **4건**은 혼합 4건이라 S5 이전에는 QA 라인이 남아 헤더가 활성으로 남을 상태였다. 이는 S5에서 새로 넓어진 번호 조건이 아니라 기존 V117 범위이므로, 이 보고서는 1,985건을 신규 S5 오삭제로 판정하지 않는다.

S5 적용 후 전체 V117 견적 영향은 **1,989문서/2,001라인**, 헤더 삭제 **1,985건**이다. `2026/07/27-1`은 이 수치에 포함되지 않는다.

### S3 계약과의 정합성

S3의 주문 복원 계약은 “헤더와 `deletedBy`·`deletedAt`이 모두 같은 삭제 배치만 분모와 복원 대상”이다. S5의 견적 복원은 그 계약과 일반적으로 같지 않다.

```java
long deletedLineCount = 모든 삭제 라인;
long restorableLines = 삭제 라인 중 header.deletedBy와 같은 라인;
if (deletedLineCount != restorableLines) 409;
```

`deletedAt`을 비교하지 않고, 분모에 모든 과거 삭제 라인을 둔다. 현재 혼합 4건은 과거 삭제 라인 **0건**이고 Flyway의 `CURRENT_TIMESTAMP`와 actor가 헤더·라인에 같아서 우연히 3/3으로 통과한다. 그러나 다른 환경의 동번호 업무 견적에 과거 삭제 라인이 있으면 다른 actor는 409를 만들고, 같은 cleanup actor의 다른 시각 라인은 오복원될 수 있다. 따라서 현재 4건에서는 충돌이 관측되지 않지만 S3 불변식과 구현 계약은 불일치한다.

## 5. cleanup actor 묶음 되돌리기와 기본 재기동

### actor 묶음

`deleted_by='issue-1096-test-seed-cleanup'`으로 V117이 쓴 행을 식별해 일괄 플래그 복구하는 능력은 남아 있다. 현재는 마이그레이션 미적용이라 slip DB의 해당 actor 행이 견적/견적라인/전표/전표라인/첨부 모두 **0건**이다.

그러나 “S5의 다섯 문서를 정확히 한 묶음 원복”은 아니다.

1. `2026/07/27-1`은 cleanup actor를 받지 않으므로 묶음에 포함되지 않는다.
2. V117은 대상 견적 합계를 0으로 갱신하지만 주석의 actor 복구 SQL은 `total_supply/total_vat/total_amount`를 되돌리거나 재계산하지 않는다. 주석대로 DB 복구하면 라인과 헤더는 활성화되어도 합계 0이 남는다.

화면의 혼합 문서 복원은 `recalculateTotals()`를 호출하므로 네 문서의 합계를 되살리지만, 그것은 actor 기반 DB 일괄 복구와 다른 경로다.

### 기본 재기동

소스와 현재 compose의 기본값은 `SAMHAN_FULL_SEED_TEST_DATA=false`다. slip/partner-order 시더는 full flag 또는 기존 seed flag 중 하나가 true일 때만 실행된다. 현재 컨테이너에서 full flag는 미설정이라 application 기본 false다.

현재 partner-order 컨테이너에는 구 실행 환경의 `SAMHAN_PARTNER_ORDER_SEED_TEST_DATA=true`가 남아 있지만, 주문·전표·견적 시더 모두 삭제행 포함 조회로 기존 번호를 발견하면 skip한다.

```java
findByOrderNoIncludingDeleted(...)
findBySlipTypeAndSlipNoIncludingDeleted(...)
findByEstimateNoIncludingDeleted(...)
```

따라서 소스 계약상 기본 재기동으로 정리분이 재생성·활성화되는 경로는 없다. 재기동은 금지 조건에 따라 실제 수행하지 않았다.

## 7. fix 지시서 — 불변식만

1. **환경 독립 provenance 불변식**: 마이그레이션 대상 여부는 견적번호·상태·미전환 여부만으로 참이 되어서는 안 되며, 삭제하려는 비정본 artifact임을 해당 DB의 문서·라인 데이터가 스스로 증명해야 한다.
2. **fail-closed 불변식**: 기대 provenance 또는 기대 문서 그래프가 하나라도 성립하지 않으면 그 문서의 헤더·라인·합계는 모두 변경되지 않아야 한다.
3. **문서 원자성 불변식**: 선택된 문서는 헤더·정리 대상 전체 라인·금액이 하나의 삭제 배치로 귀속되거나, 어느 것도 변경되지 않아야 한다.
4. **복원 배치 불변식**: 일반 복원의 분모와 복원 대상은 헤더와 `deletedBy`·`deletedAt`이 모두 같은 현재 삭제 배치여야 하며, 과거 다른 배치 라인은 차단 사유나 복원 대상이 되어서는 안 된다.
5. **순수 QA 보존 불변식**: 순수 QA797 잔재는 라인의 현재 삭제 상태나 헤더 actor와 무관하게 일반 사용자 복원으로 활성화되지 않고, 행은 물리 삭제되지 않아야 한다.
6. **정본 비차단 불변식**: 정상 정본 견적의 삭제→복원은 정확한 삭제 직전 그래프로 성공해야 한다. cleanup 오인으로 409가 나서는 안 된다.
7. **혼합 정책 단일성 불변식**: 혼합 문서가 사용자 복원 가능한지 여부는 개발책임자 정책으로 하나만 확정되어야 하며, 화면 노출·서비스 허용·actor 복구가 같은 의미를 가져야 한다.
8. **정확 원복 불변식**: cleanup actor 기반 복구가 지원된다면 헤더·라인뿐 아니라 합계까지 복구 전 값과 같아야 하며, “한 묶음”으로 선언한 모든 대상이 실제 그 actor에 귀속되어야 한다.
9. **기본 재기동 비부활 불변식**: full seed는 명시적 opt-in 없이는 실행되지 않고, 어떤 seed flag가 켜져도 삭제행 포함 멱등 조회가 정리 문서를 재생성하거나 활성화하지 않아야 한다.

## 8. 이번 라운드가 보지 않은 것

- 검증 품질, 테스트 커버리지, 테스트 설계는 찾거나 판정하지 않았다.
