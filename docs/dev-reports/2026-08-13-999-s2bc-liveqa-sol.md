# #999 S2b·S2c 라이브QA — CODEX SOL

## 결론

**실 사용자 경로에서 재현되는 결함: 1건.**

- `C14 UUID 비공개` 위반: 전표번호 링크로 전표 모달을 여는 동안 화면과 페이지 URL에는 UUID가 없었지만, 전표 검색 API 응답에 UUID 1개가 포함됐고 이어지는 상세 API 요청 URL에 UUID 1개, 상세 API 응답에 UUID 3개가 포함됐다.

그 밖의 14개 항목은 재현 결함이 없었다. `stock_movements`의 `TRANSFER` 계열은 0건이므로 재고이동 미포함은 결함으로 세지 않았다.

## 증거 무결성

- 공유 DB에는 쓰지 않았다. 공유 PostgreSQL 컨테이너 안에서 `pg_dump -Fc -f`로 파일을 만든 뒤 `docker cp`로 파일 경유해 격리 PostgreSQL `sol999-s2bc-pg-20260813013557`에 `pg_restore`했다. PowerShell 파이프로 dump/restore 바이트를 흘리지 않았다.
- 격리 복제 DB: `inventory_db`, `partner_db`, `product_db`, `slip_db`.
- 현재 브랜치의 `inventory-service.jar`, `product-service.jar`, `slip-service.jar`를 각각 격리 복제 DB에 연결했다.
- 인증·권한·재고현황 첫 목록만 화면 진입용 고정 응답을 사용했다. 검증 대상인 품목 인스턴스 GET/PATCH, 수불부 GET, 전표 검색/상세 GET, 재고실사 GET/POST는 격리 서비스에 실제 왕복했다.
- Browser 런타임 원문은 `[]`였다. 실행 불가로 판정하지 않고 저장소 `@playwright/test` Chromium을 사용했다.

## 15가지 실행 원문

### 1. A1 — 사각형 QR

`재고 현황 → 010001 품목리스트`에서 세 시리얼 모두 QR canvas가 렌더됐다.

```json

  "canvas": 3,
  "bitmap": ["64x64", "64x64", "64x64"],
  "allSquare": true
}
```

1차원 바코드는 아니었다. 캡처: `A1-square-qr-serialkey.png`.

### 2. A2 — QR payload 실제 디코드

canvas PNG를 `jsQR`로 실제 디코드해 화면 시리얼키와 순서대로 대조했다.

```json
{
  "screen":  ["SI-KP5SD4", "SI-CH5HSS", "SI-SH29E5"],
  "decoded": ["SI-KP5SD4", "SI-CH5HSS", "SI-SH29E5"],
  "exactMatch": true

```

### 3. A3 — 기존 재고실사 바코드 입력

`/warehouse/audit/{내부키}`의 실제 `IN_PROGRESS` 실사에서 기존 `audit-line-barcode-input`을 사용했다.

```json
{
  "inputPresent": true,
  "POST /inventory/audits/{id}/lines": 200,
  "inputClearedAfterSuccess": true,
  "barcodeScanned": true
}
```

최종 실행 표본 품목명은 `냉난방기-TEST-MODEL-0002`였다. 쓰기는 격리 `inventory_db`에만 발생했다.

### 6. B6 — 누적 잔량 실제 숫자 검산

### 10. B10 — 품목 단위

요청 키는 `productCode=AJ030RXH4BC1` 하나였고 응답 모든 행의 품목코드가 동일했다. 응답에 `serialKey`가 없었으며 같은 품목의 입출고 전체를 합산했다.


## 못 한 것

- 현재 복제 DB에 `2026/08/02-17` 전표가 없어 그 번호 자체의 라이브 대조는 못 했다. 대신 실제 존재하는 `2026/08/08-9`로 행·검색 결과·상세 모달의 동일 건을 exact 대조했다.
