# #1209 서비스별 요청 신원 처리 방식 정찰

- 조사일: 2026-08-14
- 역할: SOL(정찰자)
- 구현/재배포/컨테이너 변경/DB 쓰기: 없음
- 기준 이슈: `#1209`
- 참조 PR: `#1206` (`a11930784`, 2026-08-14 머지)

## 0. 결론

1. 14개 서비스 모두 일반 사용자 경로에 `HeaderAuthenticationFilter`가 있고, 일반적으로 `X-User-Id`가 비어 있지 않으면 Spring Security 인증을 만든다. **그 헤더가 게이트웨이에서 왔다는 출처 확인은 하지 않는다.**
2. 별도로 존재하는 `InternalTokenFilter`는 대부분 `/internal/**` 같은 service-to-service 경로만 담당한다. 일반 사용자 경로의 `X-User-*` 출처를 보증하지 않으므로 이번 문제를 이미 막았다고 볼 수 없다.
3. `origin/main` 정적 매핑은 14개 합계 1,031개이고, 공개/내부전용 경로를 제외한 **헤더 인증 보호 표면은 878개**다. 이것은 런타임 호출 성공 수가 아니라 아래 정의에 따른 정적 매핑 수다.
4. `#1206`의 **원칙**을 표준형으로 적용할 수 있는 서비스는 11개다. `auth`, `partner-auth`, `arologis` 3개는 각각 공개 인증 경로 또는 독립 JWT 경로가 있어 분기 설계가 필요하다.
5. `#1206`의 **구현을 코드 그대로 복사**할 수 있는 서비스는 0개다. logging은 보호 경로가 `/logs/**`로 모여 단일 `path-prefix`를 쓸 수 있었지만, 14개 서비스는 공개/내부/일반 경로가 여러 prefix로 섞여 있다.
6. 현재 실행 중인 공유 스택에서 서비스 host publish는 대부분 `127.0.0.1`이다. 따라서 다른 사내 PC에서 직접 닿지는 않지만, 같은 호스트의 프로세스와 같은 Docker network의 컨테이너에서는 닿는다. `partner-order-service`는 현재 host publish가 없고, `slip-service`는 `127.0.0.1:18086`이다.
7. 예외는 아로로지스다. `infrastructure/nginx/arologis.conf`가 `api.arologis.samhan-air.com`을 `arologis-service:8097`로 **게이트웨이 없이 직접** 연결한다. 운영에 배치된 경우 외부 도달 표면이므로 첫 순서가 맞다.

## 1. 조사 기준과 한계

### 1.1 기준 소스

- 전수 파일 목록은 현재 index의 `git ls-files`로 만들었다.
- 이 워크트리 HEAD `fe9a2e3f1`은 조사 시점 `origin/main` `7e3581e29`보다 4커밋 뒤였다. 변경하지 않고 `git show origin/main:<path>`로 차이를 겹쳐 읽었다.
- `#1206`과 `#1208`이 바꾼 `logging-service`, gateway, accounting/slip 파일은 `origin/main` 버전을 정본으로 사용했다.
- 포트는 compose 파일뿐 아니라 읽기 전용 `docker ps`, `Get-NetTCPConnection`으로 현재 실행 형상을 한 번 더 확인했다.

### 1.2 “신원 결과를 쓰는 엔드포인트 수” 정의

정적 Java 컨트롤러의 method-level `@GetMapping`/`@PostMapping`/`@PutMapping`/`@PatchMapping`/`@DeleteMapping`을 센 뒤, 다음을 제외했다.

- `SecurityConfig`의 `permitAll` 경로
- `/internal/**`, `/auth/internal/**`, `/products/internal/**`처럼 별도 내부 토큰 principal만 허용하는 경로
- 아로로지스 공개 로그인/refresh 경로

남은 값은 `HeaderAuthenticationFilter`가 만든 인증을 `anyRequest().authenticated()` 및 메서드 권한 검사에서 사용하는 **정적 보호 표면**이다. 런타임 actuator mappings나 실제 요청 성공 건수는 아니다.

교차검산은 두 축으로 했다.

1. 컨트롤러 method mapping 총수: 1,031개
2. 서비스별 `SecurityConfig`의 공개/내부 matcher를 뺀 헤더 인증 표면: 878개

모든 서비스가 0보다 크다. 따라서 “검색식에 안 걸려 0”인 서비스는 없다.

### 1.3 코드 형태와 실제 동작 구분

- **실제 재현 완료:** `#1206`의 logging-service는 직접 포트 + 위조 사용자 헤더로 inspect/retry/discard가 200이었고 실제 DLQ 폐기까지 재현됐다. 이후 `#1206`에서 차단됐다.
- **이번 14개:** 코드와 배포 표면 조사만 했다. 파괴적 요청을 보내지 않았고, 현재 컨테이너의 JAR이 `origin/main`과 같은지도 단정하지 않는다. 따라서 아래는 “동일 결함 실재 확정 14건”이 아니라 **같은 신뢰 경계 구조와 도달 조건을 가진 후보 14개**다.
- `@RequirePermission`은 별도 권한 검사라는 점에서 의미가 있다. 다만 공통 `PermissionAspect`가 요청의 `X-Is-System-Master=true`를 MASTER bypass 근거로 읽으므로, 직접 포트에서는 그 헤더의 출처도 검증해야 한다. 코드상 필터가 있다는 사실만으로 실제 우회 성공을 확정하지는 않는다.

### 2.1 이미 다른 방식으로 정비된 부분

- 14개 모두 service-to-service 내부 경로용 `InternalTokenFilter` 또는 이에 준하는 내부 필터가 있다. 하지만 일반 사용자 경로의 헤더 attestation은 아니다.
- accounting/user는 “userId 없이 groups/system-master만 온 부분 헤더”를 401로 막는다. **userId와 위조 헤더를 함께 보내는 출처 문제는 남는다.**
- accounting의 일부 CODEF 경로는 userId UUID 형식을 확인한다. 형식 확인은 발급자 확인이 아니다.
- auth-service는 `/auth/internal/**`에서 missing token을 fail-closed로 처리한다. 일반 admin/password 경로는 여전히 헤더 방식이다.
- product-service는 `/products/internal/**`를 별도 내부 토큰으로 fail-closed 처리한다. 일반 product/admin 경로는 헤더 방식이다.
- arologis의 자체 JWT는 서명/만료를 검증한다. 이것은 실제로 다른 안전한 신원 경로다. 문제는 JWT가 없을 때 활성화되는 Samhan gateway 헤더 fallback이다.

## 3. `#1206` 형태 적용 가능 / 불가

### 3.1 원칙을 표준형으로 적용 가능: 11개

`accounting`, `dashboard`, `dc-config`, `groupware`, `inventory`, `notification`, `partner-order`, `partner`, `product`, `slip`, `user`

적용 경계는 다음과 같아야 한다.

1. gateway의 JWT 보호 route만 검증 가능한 gateway attestation token을 주입한다.
2. 서비스는 그 token이 검증된 principal일 때만 `X-User-*`를 인증/권한 입력으로 해석한다.
3. `/public/**`, 로그인/부트스트랩 등 공개 route는 사용자 헤더를 제거하되 내부 token을 요구하지 않는다.
4. 기존 `/internal/**` service-to-service token 계약과 gateway attestation 계약을 섞지 않는다.
5. `@RequirePermission`/`@PreAuthorize`는 그대로 두어 사용자 권한 축을 별도로 검사한다.

### 3.2 그대로 묶으면 안 되는 특수형: 3개

#### auth-service

- `/auth/login`, logout, password policy/reset 같은 공개 인증 경로와 보호 admin/permission 경로가 한 서비스에 섞여 있다.
- token 발급 경로에 gateway attestation을 요구하면 인증을 얻기 전 요청이 막힌다.
- **보호 관리 경로만** attestation 대상이어야 한다. `/auth/internal/**`의 기존 `ROLE_INTERNAL` 계약도 보존해야 한다.

#### partner-auth-service

- 파트너 등록/로그인/비밀번호/상태조회 공개 경로와 직원용 partner approval 경로가 섞여 있다.
- 보호 대상은 우선 `/api/v1/partner-approvals/**`다. 공개 파트너 인증 경로는 별도 위협모델과 rate-limit/credential 검증으로 다뤄야 한다.

#### arologis-service

- 자체 `ArologisJwtFilter`는 독립 JWT를 검증하고, nginx 운영 설정은 api.arologis 도메인을 서비스에 직접 연결한다.
- 모든 요청에 Samhan gateway token을 강제하면 독립 모바일/관리자 JWT 경로를 끊는다.
- **자체 JWT가 유효하면 현재 경로 유지**, 자체 JWT가 없고 Samhan `X-User-*` fallback을 쓸 때만 gateway attestation을 요구하는 OR 경계가 필요하다.
- 아로로지스를 동일 배포 wave에 넣을 수는 있어도 동일 필터 조건으로 묶는 것은 맞지 않는다.

### 3.3 왜 `#1206` 코드를 그대로 복사할 수 없는가

logging-service는 일반 보호 경로가 `/logs/**`로 모여 `app.security.internal.path-prefix: /logs/`, `allow-missing-token: false`, `role: INTERNAL` 조합을 사용할 수 있었다. 이번 14개는 다음처럼 다르다.

- 한 서비스에 보호 prefix가 여러 개다. 예: accounting은 `/accounting/**`와 `/admin/**`, slip은 `/slips/**`, `/admin/**`, `/mobile/**`가 공존한다.
- 기존 단일 `InternalTokenFilter`는 이미 `/internal/**` RPC 보호에 사용된다. 단일 `path-prefix`를 일반 경로로 바꾸면 내부 RPC 계약을 잃을 수 있다.
- 공개 경로가 같은 prefix 아래 섞인 서비스가 있다.
- 아로로지스는 gateway 외의 검증된 독립 JWT 경로가 있다.

따라서 구현 단계에서는 “단일 prefix 재활용”이 아니라 **gateway attestation 전용 필터/다중 matcher**가 더 안전하다.

### 4.2 현재 공유 스택 읽기 전용 실측

조사 시 `docker ps` 결과:

- `accounting`, `arologis`, `auth`, `dashboard`, `dc-config`, `groupware`, `inventory`, `notification`, `partner-auth`, `partner`, `product`, `user`: compose와 같이 `127.0.0.1` publish
- `slip-service`: `127.0.0.1:18086 -> 8086`
- `partner-order-service`: `8080/tcp`만 표시되어 host publish 없음
- `api-gateway`: `127.0.0.1:8080`
- 대상 서비스는 모두 healthy였지만, **실행 JAR의 소스 SHA까지 확인한 것은 아니다.**
- 8086/8088 listener는 `influxd` 소유였다. 서비스 포트로 오인하지 않았다.
- 실행 중 nginx 컨테이너는 대상 목록에서 관측되지 않았다.

### 4.3 도달 범위 판정

| 진입 주체 | 일반 13개 서비스 | partner-order 현재 | arologis |
|---|---|---|---|
| 다른 사내 PC → 서비스 포트 직접 | 127 bind라 직접 불가 | host publish 없음 | compose port는 불가. 운영 nginx 배치 시 도메인으로 가능 |
| 같은 host 프로세스 | 가능 | 직접 host port 없음 | 가능 |
| 같은 Docker network 컨테이너 | service DNS로 가능 | 가능 | 가능 |
| api-gateway 경유 | 가능 | 가능 | 가능 |
| 외부/인터넷 | prod gateway/nginx·방화벽 정책에 따름 | gateway를 통해서만 | 운영 nginx 설정상 직접 서비스 경로 존재 |

따라서 “포트가 전부 외부에 열려 있다”는 결론은 틀리다. 그러나 loopback은 신원 검증 대체물이 아니다. 같은 host의 도구·프록시·SSRF와 Docker network 내부 호출에는 신뢰 경계가 남는다.

## 5. 우선순위 제안

### P0 — arologis 단독 선행

이유:

- 저장소 운영 nginx 설정상 유일하게 gateway를 우회해 외부 도메인에서 서비스로 직접 들어간다.
- 배차 삭제/배정, 기사 서명, 사본 전송, 직원 종료 등 고위험 동작이 있다.
- 자체 JWT 정상 경로가 이미 있으므로, “유효한 자체 JWT OR 검증된 Samhan gateway attestation”으로 분리하면 목표가 명확하다.

### P1 — 권한의 뿌리와 외부 효과

1. `auth` — 계정/비밀번호/권한/그룹을 바꾸므로 다른 모든 서비스 권한에 파급된다.
2. `user` — 역할 변경, disable, 직원 terminate, 서명 handoff가 있다.
3. `partner-auth` — 파트너 승인·비밀번호 재설정. 공개 인증 경로와 분리 설계가 필요하다.
4. `notification` — SMS/알림 send·retry는 외부 전송 및 비용 효과가 있다.

### P2 — 업무 데이터 소멸·확정

1. `accounting` — 전표 post/reverse, 마감, 세금계산서 issue/emit의 법적·업무 무게가 크다.
2. `slip` — send/ship/deliver/confirm/delete와 배차·외부전송 표면이 가장 넓다(195개).
3. `inventory` — deduct/adjust/ship/receive/confirm이 실재고에 영향을 준다.
4. `groupware` — 결재 approve/reject와 메시지 전송이 있다.

### P3 — 나머지 mutation 표면

`dashboard` → `partner` → `partner-order` → `product` 순을 권장한다. 현재 `partner-order`는 host publish가 없어 도달 우선순위는 낮지만, 주문 confirm/convert/delete가 있어 장기 후순위로 미루면 안 된다.

### P4 — dc-config

헤더 보호 표면이 8개로 가장 작고, 정적 코드에서 삭제·발행·승인·전송 범주의 엔드포인트는 찾지 못했다. import/update는 있으므로 최종 wave에는 포함한다.

## 6. 재배포와 유지보수 창

### 6.1 전 서비스 재배포 여부

**최종적으로는 필요하다.** 완전 차단 기준은 다음 15개 런타임의 변경 배포다.

- api-gateway 1개: 보호 route에 attestation 주입, 공개 route에는 미주입/identity strip
- 서비스 14개: attestation 검증 후에만 사용자 헤더 해석

단, 한 번에 15개를 동시에 내릴 필요는 없다.

### 6.2 권장 무중단에 가까운 순서

1. 동일 token/config를 먼저 배포 가능 상태로 준비한다.
2. gateway를 먼저 배포해 보호 route에 token을 **추가 주입**한다. 기존 서비스는 일반 경로의 추가 `X-Internal-Token`을 무시하므로 호환 가능하다.
3. P0부터 서비스별로 새 검증을 켜고, 매 서비스마다 gateway 정상/권한없음/direct forged 3경로를 확인한다.
4. auth/partner-auth 공개 경로와 arologis 자체 JWT 경로를 별도 회귀한다.

역순으로 서비스가 먼저 token을 강제하면 gateway 정상 요청이 401이 되므로 피해야 한다.

### 6.3 유지보수 창 판정

- **동시 전면 유지보수 창은 구조상 필수 아님.** gateway-first 후 서비스별 rolling이 가능하다.
- 다만 현재 compose는 서비스별 단일 인스턴스이므로 컨테이너 교체 때 해당 서비스의 짧은 중단은 생길 수 있다. 무중단 replica/로드밸런싱이 없다면 **서비스별 짧은 공지 창** 또는 업무 저부하 시간 배포가 필요하다.
- auth/user를 같은 순간에 내리지 않고, gateway와 서비스의 호환 단계가 관측된 뒤 다음 wave로 넘어가는 편이 안전하다.
- token rotation까지 같은 작업에 묶으면 `#1162`와 운영 창이 결합된다. 이번 #1209의 attestation 도입과 기존 자격 전체 rotation을 한 번에 할지는 별도 결정이 필요하다.

## 7. 개발책임자 결정 필요

### 결정 1 — 아로로지스를 같은 형태로 묶을 것인가

- **(a) 별도 특수형으로 같은 트랙에 포함 — 권장.** 자체 JWT는 유지하고, Samhan gateway 헤더 fallback에만 attestation을 요구한다. 공통 목표는 한 트랙에서 닫되 필터 조건과 QA matrix를 분리한다.
- (b) 13개 Samhan Public만 #1209에서 처리하고 아로로지스는 별도 이슈로 분리한다. 외부 직결 표면이 가장 오래 남는 단점이 있다.
- (c) 아로로지스도 gateway-only로 전환한다. 독립 운영 단위/모바일 직접 JWT 계약을 바꾸므로 이번 결함 수정 범위를 넘는다.

### 결정 2 — 한 번에 갈 것인가, 단계로 갈 것인가

- **(a) 한 트랙·단계 배포 — 권장.** gateway 선행 → P0/P1/P2/P3/P4 wave → 최종 한 번 머지/종료. 저장소의 “한 이슈 = 한 트랙, 여러 슬라이스” 결정과 맞고 blast radius를 줄인다.
- (b) 15개를 한 번에 배포한다. 단순하지만 공개 경로/독립 JWT 회귀 시 전체 정상 경로를 동시에 막을 위험이 크다.
- (c) 서비스군별 별도 PR로 나눈다. 병렬성은 생기지만 이 저장소의 통합 PR 원칙과 충돌한다.

### 결정 3 — gateway attestation과 기존 internal RPC token을 같은 자격으로 쓸 것인가

- **(a) 자격/필터 목적 분리 — 권장.** gateway attestation principal과 service-to-service internal principal을 분리한다. 한 token 유출이 두 신뢰 경계를 동시에 무너뜨리지 않는다.
- (b) 현재 `SAMHAN_INTERNAL_TOKEN`을 재사용하되 matcher/principal만 분리한다. 배포는 단순하지만 자격 blast radius가 크다.
- (c) `#1162` rotation과 동시에 새 자격으로 일괄 전환한다. 운영 창과 회귀 범위가 가장 커진다.

## 8. 구현 트랙에 넘길 검증 불변식

이번 문서는 구현하지 않지만 다음 조건은 구현/QA의 수락 기준이 되어야 한다.

1. gateway 정상 + 권한 있음: 기존 성공 유지
2. gateway 정상 + 권한 없음: 403 유지
3. 서비스 직접 + `X-User-Id`/groups/system-master 위조: 401
4. 유효 attestation + 권한 없음: 403 — 내부 token만으로 업무 권한을 얻지 못함
5. token 미설정/불일치: 조용히 열리지 않고 fail-closed
6. auth/partner-auth 공개 인증 경로: 정상 유지, inbound identity 헤더는 제거
7. arologis 자체 유효 JWT: 정상 유지; JWT 없음 + 위조 헤더: 401
8. 삭제·발행·승인·전송 endpoint를 각 서비스에서 최소 1개씩 실 HTTP로 검증하되, QA 데이터와 복구 절차를 먼저 준비
