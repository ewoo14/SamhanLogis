## 0. 먼저 — 제가 만든 선택지가 잘못돼 있었습니다

개발책임자께 *"93.3% 거부를 어떻게 할 것인가"* 를 물으며 세 선택지를 드렸고, **재배정 규칙 신설**을 고르셨습니다.

그런데 56건의 내역을 열어 보니 **재배정은 5전표뿐**입니다.

| 엄격 거부 근거 | 전표 수 | 비율 |
|---|---:|---:|
| 원 재고 작업 없음 (활성 품목 정본도 없음) | **40** | 71% |
| 시리얼 입고 생성 집합 증명 불가 | 7 | 13% |
| 시리얼 출고 물리 미출고/회수 증명 없음 | 9 | 16% |
| **합계** | **56** | 100% |

> 집합 간 중복 없음. 재배정(5전표·12 instance·다른 OUTBOUND 9전표)은 위 **7건 안에** 있습니다.

⟹ **재배정 규칙은 56건 중 5건을 다룹니다.** 나머지 51건은 규칙 문제가 아니라 **판단 근거가 없어서** 거부됩니다.

🔑 이 저장소에 이미 기록된 교훈을 제가 어겼습니다 — *"어느 쪽이 맞나 를 올리기 전에 고를 게 있긴 한가 를 세라."* 표제 숫자(93.3%)만 보고 선택지를 만들었습니다.

### 그리고 40건은 실 업무 전표가 아닐 가능성이 높습니다

40건의 판정 근거는 *"현재 활성 품목 정본도 없음"* 입니다. 이것은 `#1051` 정찰이 **"전건 QA/시드 잔재 · 실 데이터 0행"** 으로 확정한 술어와 같습니다.

⟹ **"되돌림 대상 60건" 이라는 숫자 자체가 과대계상**입니다. 실 업무 전표는 20건 안팎입니다.

## 1. 설계 — 3단, 순서가 핵심입니다

### 1단 · source journal 을 먼저 만든다 (선행 필수)

정방향 재고 API 4개(`deduct` · `ship-batch` · `lots/inbound` · `instances/batch`)가 실행할 때마다 남깁니다.

```
sourceOperationId          이 호출의 유일 식별자
slipId · slipRevision      어느 전표의 어느 판이 일으켰나
productSnapshot            goods · productType · serialManaged · productCode
outcome                    APPLIED | NO_OP_EXISTING | NO_OP_EXCLUDED
createdLotIds              이 호출이 **새로 만든** lot 집합
createdInstanceIds         이 호출이 **새로 만든** instance 집합
```

**이것이 없으면 역연산은 영원히 "판단 불가 → 거부" 입니다.** 7건(생성 집합 증명 불가)·9건(custody)이 여기서 풀립니다.

🔑 **앞으로 생기는 전표에만 효력이 있습니다.** 그건 한계가 아니라 올바른 경계입니다 — 과거를 소급 추론하는 것이 바로 지금 거부되는 이유입니다.

**불변식**
- 🚨 journal 쓰기는 **정방향 작업과 같은 트랜잭션** 안에 있어야 합니다. 따로 쓰면 롤백 시 어긋나고, 그게 `#978 D-1` 에서 본 바로 그 병입니다.
- 🚨 `NO_OP` 를 오류로 다루지 않습니다. *"정상적으로 실행됐고 결과가 없음"* 과 *"호출이 없었음"* 은 다릅니다. outcome 으로 구분합니다.
- 🚨 정방향 API 와 역연산이 **같은 잠금을 공유**해야 합니다. 지금은 미공유라 동시성 계약이 성립하지 않습니다.

### 2단 · 되돌림 대상을 실 업무 전표로 재정의한다

60이 아니라 **QA/시드 잔재를 뺀 집합**이 대상입니다. `#1051` 의 판별 축(`created_by` · 이름 · provenance)을 그대로 씁니다.

- 40건은 자동 역연산 대상이 아니라 **판정 큐**로 뺍니다 — read-only 증거 + 수동 판정
- 🚫 **자동 통과시키지 않습니다.** 증명할 수 없는 것을 통과시키면 fail-loud 가 무너집니다
- 🚫 잔재를 지워서 숫자를 줄이지 않습니다

### 3단 · 재배정된 5전표 — 자동 연쇄 금지, 차단 + 안내

그 인스턴스를 소비한 OUTBOUND 전표 번호를 사용자에게 보여주고 **먼저 그것을 되돌리라**고 안내합니다.

```
🚫 자동 연쇄 되돌림     범위가 폭발하고 되돌릴 수 없는 사고를 만든다
🚫 대체 인스턴스 상계   시리얼 이력이 거짓이 된다 (수량은 맞고 이력은 틀림)
```

한국 ERP 의 통상 동작이기도 합니다 — 후속 처리가 있으면 수정 불가, **후속을 먼저 취소**하라고 안내합니다.

## 2. 함께 확정해야 하는 것 (적대검토가 지적)

```
정방향 API 와 역연산이 같은 잠금을 공유한다        지금 미공유 → 동시성 계약 미성립
saga 에 회계 취소·재생성 단계를 넣는다              지금 없음
추가 거부 조건
  OPEN_INVENTORY_AUDIT_EXISTS                     진행 중 실사
  OPEN_TRANSFER_EXISTS                            진행 중 이동 (예약 단계까지)
  SOURCE_SLIP_REVISED_AFTER_OPERATION             원 작업 뒤 전표 개정
  source 별 reversal 유일성                        (sourceOperationId, operationType) unique
  PHYSICAL_CUSTODY_UNPROVEN_OR_STALE              custody 증명 부재/낡음
  회계 마감 3층 (slip lock_flag · CLOSED period · 역마감)
```

## 3. PM 권고

**1단부터 하십시오.**

| | 이유 |
|---|---|
| 앞으로 만드는 전표는 되돌릴 수 있다 | source journal 이 판단 근거를 남긴다 |
| 과거 60건은 실익이 작다 | 40이 QA/시드 잔재다 |
| 3단은 1단이 있어야 의미가 있다 | 재배정 판정도 생성 집합 증명이 전제다 |

🚨 **되돌림 기능을 "과거 데이터 복구 수단" 으로 기대하지 않는 것**이 이 설계의 전제입니다. 과거 복구는 기능이 아니라 **작업**이고, 판정 큐로 분리합니다.

## 4. 개발책임자 확인이 필요한 것 (남은 하나)

**과거 실 업무 전표(약 20건)를 어떻게 할 것인가.**

| 선택지 | 대가 |
|---|---|
| 포기 — 앞으로만 | 가장 단순·안전. 과거 전표는 수정 불가로 남는다 |
| 판정 큐 + 수동 조정 | 증거를 모아 사람이 판단. 손이 많이 간다 |
| custody/생성집합 사후 재구성 | 되돌릴 수 있게 되지만 **추론으로 재구성**하는 것이라 틀리면 재고가 조용히 어긋난다 |

제 권고는 **판정 큐 + 수동 조정**입니다. 사후 재구성은 추론이라 이 도메인에 맞지 않습니다.
