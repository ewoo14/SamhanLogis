## 2. 충돌 해소

### `ProductCatalogResponse.java`

사용자 전제를 코드 구조로 확인한 결과, 두 값은 같은 record 자리를 다투지 않는다.

```text
record 선언 순서
goodsType
quantitySyncTargetEligible : boolean
fixedDiscountRate          : BigDecimal
...
fixedDiscountSource        : String
```

최종 생성자 인자와 JSON 의미는 다음과 같다.

```java
p.getGoodsType(),
QuantitySyncRuleValidator.isValidTargetRole(
        p.getCatL() == null ? null : p.getCatL().getName(),
        p.getGoodsType() == null ? null : p.getGoodsType().name()),
p.resolveFixedDiscount().rate(),
...
p.resolveFixedDiscount().source().name()
```

즉 `isValidTargetRole` 판정은 유지하고, `fixedDiscountRate`는 raw `getFixedDiscountRate()`가 아닌 분류축 S→M→L 및 품목 override를 해석한 `resolveFixedDiscount().rate()`를 사용한다. `withComponentCount`도 `quantitySyncTargetEligible → fixedDiscountRate → ... → fixedDiscountSource` 순서를 그대로 전달한다. record 선언과 생성자 인자 타입·순서를 대조했으며, 값 뒤바뀜은 없다.

### `EstimateItemsCatalogPage.test.ts`

양쪽 suite를 모두 보존했다.

- #1132: `FixedDiscountCell 적용 출처` — `S` 출처 표시
- origin/main #1126: quantity-sync 409 rule key 추출 및 활성 source 모델코드 편집 대상 해석

최종 파일은 충돌 marker 없이 두 describe 블록을 포함하며 해당 파일은 8 tests로 통과했다.

## 5. RED-B 보존 판정

- #1126 `isValidTargetRole` 필드와 validator 호출을 응답 record에 유지했다.
- #1132 정액DC율은 raw 품목값으로 되돌리지 않고 `resolveFixedDiscount().rate()`를 유지했다. 기존 #1132 검증 문서의 S 분류축 금액 `495,000 → 420,750` 경로를 덮는 변경은 없으며 product 전체 및 정액DC 단위 테스트가 통과했다.

- 판매전표 2건 3라인 VAT 포함 `15,242,370원`을 재작성하거나 DB에 쓰는 작업은 하지 않았다. 관련 저장 경로의 slip 통합 테스트는 통과했다.
