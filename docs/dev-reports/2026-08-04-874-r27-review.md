- 코드가 정의한 출처는 `ESTIMATE`, `PARTNER_ORDER`, `MANUAL`, `MIGRATED_ECOUNT` 네 가지다. SENT에서 오직 `PARTNER_ORDER`만 `cancel`을 제외하고, 나머지 세 값은 일반 전표와 같이 `accept/reject/cancel`을 유지한다(`SlipDetailPage.tsx:295-298`). 이는 백엔드도 `Slip.cancel()`에서 오직 `PARTNER_ORDER`만 409로 막고 나머지 출처의 DRAFT/SAVED/SENT 취소를 허용하는 계약(`Slip.java:1173-1198`)과 일치한다. 정의상 다른 출처의 정상 취소 경로가 R26 때문에 차단되지는 않았다.
- FE API 경계에는 `sourceType`을 버리거나 재매핑하는 단계가 없다. `getSlip(id)`는 `GET /slips/{id}`의 `res.data.data`를 그대로 `SlipDetail`로 반환한다(`api/slip.ts:503-505`). 따라서 백엔드 JSON의 `sourceType: "PARTNER_ORDER"`는 그대로 상세 화면의 `slip.sourceType`이 된다.
- 응답에서 `sourceType`이 없거나 JSON `null`이면 FE의 nullish fallback 때문에 `MANUAL`로 계산된다. 그 행이 SENT라면 데스크톱 `삭제`와 모바일 `전표 취소`가 나타난다. 다만 현재 스키마는 `source_type NOT NULL DEFAULT 'MANUAL'`이고 엔티티도 `nullable=false`·기본 `MANUAL`이며, 현 DTO가 실제 값을 항상 직렬화한다. 현재 배포/DB 조합에서는 누락·null인 실 행이 없으므로 이 가정 경로는 GUI 도달 결함으로 판정하지 않는다. 과거 백엔드와 새 FE를 혼용하면 주문전환 SENT에서만 다시 409 노출이 생긴다.
- generic `삭제` 조건부 렌더가 정상 작업을 없앴는지 상태·유형·권한 축으로 재확인했다. DRAFT/SAVED는 모든 출처에서 `cancel`을 보유해 계속 렌더되고, 일반 SENT(`MANUAL/ESTIMATE/MIGRATED_ECOUNT`)도 계속 렌더된다. 이 상태들에서 취소 권한이 없으면 버튼은 여전히 렌더되되 disabled와 권한 안내 title을 가진다(`4355-4369`). `PARTNER_ORDER` SENT만 숨는다. ACCEPTED/PROCESSING/CONFIRMED는 별도 `삭제 요청`, 이후 상태는 백엔드상 cancel 불가다. 별도로 DRAFT/SAVED의 진짜 soft-delete 버튼도 데스크톱·모바일 모두 그대로 존재한다(`1919-1941`, `3214-3239`, `3371-3397`). 사라진 것은 비허용 상태의 비활성 generic 취소 affordance뿐이며, 실 사용자가 하던 정상 GUI 작업이 막힌 조합은 찾지 못했다.
- 미발화 칸을 코드 끝단까지 연결했다. 주문전환 발행은 도메인에 `PARTNER_ORDER`를 저장하고 즉시 SENT로 전이한다(`SlipPublishService.java:262-270`). 상세 DTO가 같은 값을 반환하고 FE가 그대로 수신해 fallback 전의 값이 `PARTNER_ORDER`가 된다. `actionsForStatus`는 `cancel` 없는 `accept/reject`를 만들며, 데스크톱은 `possibleActions.includes('cancel')`이 false라 `삭제`를 렌더하지 않고(`4355-4371`), 모바일도 같은 조건으로 `전표 취소`를 렌더하지 않는다(`3412-3424`). 요청된 네 칸은 정적으로 모두 연결돼 있으며 이 경로의 도달 결함은 없다.
- `COMPLETED` 전이를 먼저 끝낸 뒤 새로 `수정`에 진입하는 경로는 상태별로 정합한다. OUTBOUND는 `SHIPPING`이 되어 `canCollabEdit=false`이고 진입 버튼이 사라지며 백엔드도 수정 금지다. INBOUND는 `CONFIRMED`가 물리 종결이 아니어서 상단의 일반 협업 `수정` 버튼(`3204-3212`)이 계속 남고, 백엔드도 `CONFIRMED` 협업 수정을 허용한다. 문제는 전이 전에 이미 열린 편집 모드를 전이 성공이 닫지 않는 결함 1이다.
- `setCollabEditMode` 소비처를 전수 확인했다. 여는 호출 3개와 패널 콜백 전달만 있고, status 변화나 transition 성공 시 false로 닫는 effect/callback은 없다. 따라서 결함 1의 열린 폼 잔존은 추측이 아니라 현재 React 상태 전이의 결정적 결과다.
- 독립 적대검증도 같은 결함 1을 confidence 10/10으로 재확인했다. `SlipCollaborationPanel`은 status가 아니라 권한만 검사해 열린 폼을 계속 렌더하고, 저장 오류 뒤에도 edit mode를 유지한다. 독립 검증은 추가 GUI 도달 결함을 찾지 못했다.

## 도달 결함

### 결함 1 — OUTBOUND COMPLETED에서 수정 중 배송 시작 시 편집 폼이 살아 있으나 저장은 409

재현 경로:

1. 데스크톱 판매관리 → 거래처가 연결된 OUTBOUND `COMPLETED` 전표 상세(`/sales/:id`)를 `slip.audit-overlay:update`와 배송 시작 권한이 있는 사용자(예: MASTER)로 연다.
2. 하단 `수정`을 눌러 협업 수정 폼을 열고 메모 등 값을 바꾼다.
3. 같은 화면 하단에 계속 노출된 `완료 (배송 시작)`을 누른다.
4. `/ship` 성공 후 상세 query가 갱신되어 상태는 `SHIPPING`이 되지만 `collabEditMode`는 닫히지 않아 이미 열린 수정 폼과 입력값이 그대로 남는다.
5. `수정완료`를 누르면 `POST /api/v1/slips/{id}/collab/edits`가 백엔드 `guardCollabModifiable`에서 `SHIPPING`을 물리 종결로 거부해 409를 반환한다. 사용자는 방금 입력한 수정 내용을 정상 저장할 수 없다.

근거:

- 협업 패널 다음에 footer가 무조건 이어져 편집 모드에도 전이 버튼이 남는다(`SlipDetailPage.tsx:4315-4347`).
- 전이 성공은 query만 invalidate하고 `setCollabEditMode(false)`를 호출하지 않는다(`1448-1457`).
- `SlipCollaborationPanel`은 이미 열린 `editMode`를 상태 변경 시 닫지 않고, 자체 `canEdit`도 권한만 본다. 부모의 새 `canCollabEdit=false`를 받지 않는다.
- 백엔드는 `SHIPPING/DELIVERED/CANCELED/REJECTED`를 협업 수정 불가로 두고 409를 반환한다(`SlipService.java:659-675`).

INBOUND `COMPLETED → CONFIRMED`는 `CONFIRMED`가 협업 수정 허용 상태라 같은 순서로 저장해도 이 409가 발생하지 않는다. 결함은 OUTBOUND의 `COMPLETED → SHIPPING` 조합에서 재현된다.

## 증거 무결성

- R26 라이브 QA의 원문 `"slip_db 미삭제 127건, 전부 OUTBOUND. OUTBOUND DRAFT 116건, OUTBOUND COMPLETED 2건(...), INBOUND 0건, SENT 0건, PARTNER_ORDER 0건"`은 `미삭제 127건`이 잘못 표기됐다. 현재 총행은 129, 미삭제는 120이고, R26이 생성했다고 밝힌 INBOUND 1건+OUTBOUND 1건을 빼면 측정 시작 시점 값은 총행 127, 미삭제 118로 정확히 역산된다. 현재 soft-delete 9건은 모두 2026-07-27 삭제라 R26 측정 전에 이미 삭제돼 있었다. 원문의 상태별 `DRAFT 116 + COMPLETED 2 = 118`도 이 미삭제 수와 맞는다. 따라서 정정은 **`전체 127건, 미삭제 118건, 미삭제는 전부 OUTBOUND`**다. 현재 미삭제 분포는 `INBOUND CONFIRMED MANUAL=1`, `OUTBOUND COMPLETED MANUAL=2`, `OUTBOUND DRAFT MANUAL=116`, `OUTBOUND SENT MANUAL=1`이다.

- R26 라이브 QA의 `"단계별 실화면 캡처 55개"` 주장은 `docs/qa/874-riusage-global-dc-real-qa/r26-*.png` 실제 파일 수 55개로 재현됐다.

**있다. GUI 도달 결함 1건.**

## 이 라운드가 보지 않은 것

- DB 쓰기 금지 때문에 거래처가 연결된 새 OUTBOUND 전표를 만들어 COMPLETED까지 진행하지 않았다. 현재 존재하는 OUTBOUND COMPLETED 2건은 모두 `partner_id`가 없어 `/ship`이 400인 행이다. 결함 1은 GUI 컴포넌트 상태와 배포 백엔드 409 가드의 끝단 추적으로 판정했다.
- 실 DB에 `PARTNER_ORDER` 행이 0건이고 주문서 앱 계정도 미등록/미승인이므로 주문전환 SENT 취소 미노출을 라이브 화면으로 다시 발화하지 않았다. 대신 실행 JAR·DB 스키마·DTO·FE 소비·양쪽 렌더 조건을 끝단까지 확인했다.
- 데이터 보존을 위해 일반 SENT의 `삭제`/`전표 취소`를 실제 클릭하지 않았다.
- 사용자 제한에 따라 관련 테스트는 `SlipDetailPage.lifecycle-contract.test.ts` 한 파일만 실행했다. R26 문서의 `partner-required 4/4`는 이번 라운드에서 재실행하지 않았다.
- 도달 불가능한 상태 조합, 테스트 품질, 문서 과장, 가드 구멍, 범위 밖 리팩터링은 조사·판정하지 않았다.
