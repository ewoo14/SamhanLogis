## 1. 결론

1차에서 `GET /inventory/balances` 자체는 행·실제 수량·페이지를 보존했지만, 같은 재고의 Excel
외부 내보내기가 부분 누락과 product-service 장애를 모두 HTTP 200 공란 파일로 바꾸는 차단결함을
발견했다. 지시서 전달 후 구현자는 Excel의 누락 참조만 `참조 끊김` / `제품 마스터 없음`으로
표시하고 4xx/5xx/연결 실패는 기존 업무 오류로 전파하도록 보완했다.

재검토에서 production 25호출 좌표, 실제 xlsx 셀, 전부 누락, 100건 혼합/101건 거부,
X-Internal-Token, strict 입고·출고, UUID 비노출을 다시 확인했다. 전체 inventory는 기존
616건에 이번 RED 13건을 더한 **629건, failures 0 / errors 0**이고 Chromium live QA도
1 passed다. 최종 판정은 **결함 0건**이다.

## 2. 호출부 전수 대조

`services/inventory-service/src/main/java`에서 `productClient.<method>(...)`를 직접 다시 센 결과는
production **25좌표**다.

보완 전 PR HEAD의 표는 다음과 같았다.

| 구분 | 좌표 수 | 좌표 |
|---|---:|---|
| 관용 조회 | 3 | `ProductSeedIntegrityValidator:30 lookupForSeedIntegrity`, `SafetyStockService:180 lookupAllowMissing`, `StockService:126 lookupAllowMissing` |
| strict 직접 lookup | 4 | `InventoryAuditService:124`, `SafetyStockService:321`, `StockExcelExportService:130`, `StockTransferService:65` |
| strict 단건 helper | 18 | `InboundInspectionService:261`, `InventoryAuditService:366`, `SafetyStockService:82`, `StockInstanceService:75,119,169,219,254,285,384,415,504,522`, `StockService:204,258,310,362,425` |

PR patch 대조 결과 관용으로 바뀐 production 호출은 `StockService.findBalancePage()`의
`lookup` → `lookupAllowMissing` **1좌표뿐**이다. seed 정합성 및 안전재고 표시 경로의 관용 조회는
기존 코드이며, 입고·예약·해제·차감·조정·이동의 존재 검증 호출은 strict 그대로다.

재검토 보완은 표시/내보내기 표면인 `StockExcelExportService:128` 한 좌표를 의도적으로
`lookupAllowMissing`으로 바꿨다. 따라서 최종 표는 관용 4좌표, strict 직접 lookup 3좌표,
strict 단건 helper 18좌표로 총수는 여전히 25다. 보완이 mutation 경로로 새지 않았고
입고·예약·해제·차감·조정·이동은 모두 strict다.

## 3. 은폐 여부

### 3.1 balances 화면

- 행: `StockBalance` 행을 먼저 전부 읽고, lookup 결과가 없어도 `BalanceRow.toResponse()`를 호출하므로 삭제·숨김하지 않는다.
- 수량: 실제 행은 `availableQty`, `reservedQty`, `totalQty`를 DB 값 그대로 반환한다. 누락을 0으로 채우지 않는다.
- 합계: 화면에는 수량 합산값이 없고 `totalElements`는 끊긴 행을 포함한 전체 행 수다.
- 정렬: UI DataGrid에는 정렬 기능이 없다. 서버는 품목 UUID ASC → 창고코드 ASC로 정렬한 뒤 페이지를 자르므로 누락 행도 같은 규칙으로 들어간다.
- 페이지네이션: 전체 응답 행을 만든 뒤 `pageOf()`가 `offset/pageSize`로 자른다. 끊긴 행은 페이지 경계에서도 한 행으로 계산된다.
- 조작: 이 화면은 `onRowClick`, paste, 수정·이동·조정·출고 버튼이 없는 조회/선택/복사 전용이다. 복사는 표시 문구와 실제 수량을 사용한다.
- UUID: `StockBalanceResponse`에 productId/warehouseId가 없고, Playwright 스펙도 UUID 정규식을 부정한다.

### 3.2 차단결함 SOL-1051-R1-01 — Excel이 끊김과 장애를 공란으로 은폐

**좌표 전수**

- `services/inventory-service/src/main/java/com/samhanair/logis/inventory/service/StockExcelExportService.java:128-136`
  - strict `productClient.lookup(chunk)`의 모든 `RuntimeException`을 잡고 청크 전체를 빈 결과로 둔다.
- 같은 파일 `:140-148`
  - 해석 실패 행의 `productCode`, `productName`을 빈 문자열로 출력한다.
- `services/inventory-service/src/test/java/com/samhanair/logis/inventory/it/InventoryControllerIT.java:362-449`
  - 정상 lookup과 UUID 비노출만 검사하며 부분 누락/전부 누락/서비스 장애 계약이 없다.

**재현 데이터**

1. 같은 창고에 정상 품목 P1 수량 7, product-service에 없는 P2 수량 4를 둔다.
2. `GET /inventory/stocks/export.xlsx`를 호출한다.
3. strict lookup은 `[P1,P2]` 요청에 `[P1]`만 받아 `NOT_FOUND`를 던진다.
4. catch가 청크 전체 결과를 버려 P1과 P2 모두 품목코드/명이 공란이 된다. 수량 행은 남지만 어느 품목인지 식별할 수 없다.
5. product-service가 5xx/연결 실패여도 같은 catch로 들어가 전 행 공란 HTTP 200 파일이 된다.

**불변식**

- 끊긴 참조만 `참조 끊김` / `제품 마스터 없음`으로 명시하고 행·실제 수량을 보존한다.
- 정상 품목 메타데이터는 같은 배치의 끊김 때문에 잃지 않는다.
- product-service 4xx/5xx/연결 실패는 끊긴 참조로 바꾸지 말고 기존 `INVALID_INPUT` / `INTERNAL_ERROR`로 실패시킨다.
- 입고·예약·해제·차감·조정·이동의 strict 검증은 완화하지 않는다.
- Excel/화면 어디에도 UUID를 노출하지 않는다.

**RED-A 구체 표적**

- Excel `[정상 P1=7, 누락 P2=4]`: P1의 코드/명 유지, P2는 두 표시 문구, 두 수량 유지.
- Excel 전부 누락: 모든 행에 표시 문구와 실제 수량 유지.
- Excel product-service 5xx/연결 실패: 공란 200 금지, `INTERNAL_ERROR` 유지.
- `lookupAllowMissing` 전부 누락, 100건 경계, 101건 `INVALID_INPUT`, X-Internal-Token, 4xx/5xx 구분.

**RED-B 구체 표적**

- 없는 품목의 입고와 출고(deduct)가 계속 `NOT_FOUND`이며 lot/balance/movement를 만들거나 바꾸지 않는다.
- 이동·예약·해제·조정 strict 호출 유지.
- inventory 전체 테스트 616건 실패 0.
- Chromium Playwright에서 행·수량·페이지·복사·UUID 비노출 확인.

**이 fix가 새로 가능하게 만드는 상태**

잔고 화면은 열린 뒤 사용자가 같은 데이터의 Excel을 받으면 끊긴 행이 익명 수량 행으로 바뀐다.
더 나쁘게는 product-service 장애 중에도 전 품목이 익명 행인 정상 HTTP 200 파일을 받아 장애를
데이터 결함처럼 오인할 수 있다.

> **제 전제가 틀렸다면 고치지 말고 중단·보고하십시오.** 특히 Excel을 의도적으로 공란 계약으로
> 유지해야 한다는 별도 PM 결정이 있거나, 외부 소비자가 표시 문구를 허용하지 않는 계약이 있으면
> 구현하지 말고 그 근거 좌표와 소비자를 보고하십시오.

## 5. 이 라운드가 아직 보지 않은 표면

최종 결함 0 판정이 보지 않은 표면은 다음과 같다.

- 재고 잔고 전용 인쇄 UI/endpoint는 코드 검색에서 발견되지 않아 인쇄 렌더링은 검증하지 않았다.
- Excel `MAX_ROWS=10,000` 초과 절단 계약과 101개 이상 distinct product를 두 lookup 청크로
  내보내는 성능/순서 표면은 이번 결함 범위 밖이라 실데이터로 만들지 않았다.
- product-service 실 컨테이너를 의도적으로 중단하지 않았다. 장애 구분은 MockRestServiceServer의
  5xx·연결 reset과 controller IT의 `INTERNAL_ERROR` 전파로 검증했다.
- DataGrid에는 사용자 정렬 기능 자체가 없어 정렬 클릭 QA는 없다. 서버의 UUID ASC → 창고코드 ASC
  안정 순서와 페이지 절단만 코드 및 50/5 페이지 이동으로 확인했다.
- 모바일/태블릿 레이아웃, 다른 재고 화면(안전재고·이동·조정)의 시각 회귀는 보지 않았다.
