# 2026-08-01 #1017 데이터 정정 마이그레이션 기능 회귀 검토

## 1. 정적 조건 대조 — 품목명은 실제 매칭 조건이 아님

마이그레이션 설명과 구현 보고서는 전표번호·품목·모델·수량·기존 금액을 모두 일치시킨다고 적었지만, 실제 세 매칭 구문(guard, 감사 INSERT, UPDATE)은 `product_name`을 비교하지 않는다. `product_name`은 임시 대상 테이블에 적재될 뿐이다.

실행:

```powershell
rg -n "product_name|t\.model_name|target_count NOT IN|CREATE TABLE slip_line_correction_audits|UPDATE slip_lines|CREATE EXTENSION" services/slip-service/src/main/resources/db/migration/V61__correct_partner_order_vat_overcharge.sql
```

출력 원문:

```text
11:CREATE EXTENSION IF NOT EXISTS "pgcrypto";
13:CREATE TABLE slip_line_correction_audits (
49:    product_name    VARCHAR(200) NOT NULL,
65:    target_no, slip_no, product_name, model_name, quantity,
99:       AND t.model_name = sl.model_name
110:    IF target_count NOT IN (0, 19) THEN
142: AND t.model_name = sl.model_name
153:UPDATE slip_lines sl
168:  AND t.model_name = sl.model_name
```

따라서 같은 전표 안에 모델·수량·기존 5개 금액은 같지만 품목명이 다른 라인이 있으면 그 라인도 정정 대상에 포함된다. 이 경우 20행 이상으로 계산되어 배포가 차단되거나, 원래 대상 하나가 빠진 동시에 이 비대상 라인이 대신 잡혀 총 19행이 되면 guard를 통과해 정정하면 안 되는 행을 정정할 수 있다. 아래 일회성 PostgreSQL에서 두 경우를 직접 재현한다.

## 2. 실 DB 읽기 전용 매칭 실측

공유 `samhan-postgres`는 재빌드·재기동하지 않았고 상태는 다음과 같았다.

```text
NAMES                          IMAGE                                                  STATUS
samhan-postgres                postgres:16-alpine                                     Up 26 hours (healthy)
```

마이그레이션의 19개 `VALUES`와 실제 guard의 조인 조건을 그대로 CTE로 옮겨 실행했다. 같은 쿼리에서 정찰 보고서의 정상 전표 7행과 확인불가 전표 3행도 직접 셌다. 연결은 읽기 전용이다.

출력 원문:

```text
 transaction_read_only 
-----------------------
 on
(1 row)

               metric               | value 
------------------------------------+-------
 migration_match_count              | 0
 matched_distinct_targets           | 0
 product_name_mismatches            | 0
 targets_with_duplicate_matches     | 0
 normal_candidate_rows              | 7
 normal_rows_matching_migration     | 0
 unresolved_candidate_rows          | 3
 unresolved_rows_matching_migration | 0
(8 rows)
```

현재 실 DB에서 V61의 **변경 전 금액 조건이 잡는 행은 19가 아니라 0행**이다. 정상 7행과 확인불가 3행은 각각 모집단 수가 재현됐고 V61 조건에는 모두 0행으로, 현재 상태에서는 실제로 제외된다. 다만 0행의 원인이 이미 정정된 상태인지, 원 데이터가 달라진 것인지 아래에서 Flyway 이력·감사 테이블·대상 금액을 읽기 전용으로 추가 확인한다.

### 2.1 실 DB에는 V61 적용 이력과 감사 테이블이 없음

V61이 이미 적용돼서 0행이 된 것인지 확인했다. 한 번에 감사 테이블까지 조회한 명령은 해당 테이블 부재로 종료 코드 1이었으며, 그 전에 출력된 이력은 다음과 같다.

```text
 transaction_read_only 
-----------------------
 on
(1 row)

      table_name       
-----------------------
 flyway_schema_history
(1 row)

 installed_rank | version | description | type | success 
----------------+---------+-------------+------+---------
(0 rows)

ERROR:  relation "slip_line_correction_audits" does not exist
LINE 4: ... FROM slip_line_correction_audits ...
```

즉 이 실 DB에는 V61 적용 이력이 없고 신규 감사 테이블도 없다. 따라서 매칭 0행은 V61이 이미 정정한 결과가 아니다.

### 2.2 0행의 직접 원인 — 실 DB의 `line_total`이 V61의 기존값과 다름

전표번호·모델·수량으로 19개 비즈니스 키를 찾은 뒤 현재 5개 금액을 V61의 변경 전·후 값과 비교했다.

```text
 transaction_read_only 
-----------------------
 on
(1 row)

         metric          |    value    
-------------------------+-------------
 business_key_rows       | 19
 old_amount_rows         | 0
 new_amount_rows         | 0
 other_amount_rows       | 19
 product_name_mismatches | 3
 current_supply_plus_vat | 56859000.00
 current_line_total      | 51690000.00
(7 rows)
```

19개 비즈니스 키 자체는 모두 존재한다. 그러나 실 DB의 19행은 V61이 가정한 변경 전 5개 금액 조합과 한 행도 일치하지 않는다. 현재 `supply_amount + vat_amount` 합계는 56,859,000원이지만 `line_total` 합계는 51,690,000원이다. V61은 각 대상의 `old_line_total`을 전자(과다 계상된 공급가액+부가세)와 같게 적었고 실제 DB는 후자(원래 사용자 총액)를 보존하고 있어 guard가 0행을 얻는다. 따라서 이 DB에 배포하면 서비스는 뜨지만 no-op으로 지나가며 감사 행도 생기지 않는다.

또한 품목명은 실제 데이터와 대상 목록이 3행 다르다. 이는 품목명 비교가 구현에 없다는 정적 확인과 일치하며, “품목까지 모두 일치”한다는 구현 보고서 문구는 실측 재현되지 않는다.

`partialdb`는 10행을 이미 새 금액으로 바꿨고, `deleteddb`는 대상 전표 하나를 soft delete, `changeddb`는 대상 한 행의 기존 단가를 1원 변경, `duplicatedb`는 품목명만 다른 동일 조건 비대상 행을 추가, `substitutiondb`는 원 대상 한 행을 이미 새 금액으로 바꾼 뒤 품목명만 다른 비대상 구값 행을 추가했다.

정정 후 19행 모두 `공급가액 + 부가세 = 원래 사용자 총액`이고 합계는 51,690,000원이다. **5,169,000원**은 정정 전 `공급가액 + 부가세` 56,859,000원과 사용자 총액 51,690,000원의 차이다. 즉 51,690,000원은 총액, 5,169,000원은 제거해야 할 과다 계상액이다.

## 4. `slip_lines` 외 영향 실측

실 DB에서 마이그레이션 실행 계정과 `pgcrypto` 상태를 읽기 전용으로 확인했다.

```text
 transaction_read_only 
-----------------------
 on
(1 row)

 current_user | rolsuper | can_create_in_database 
--------------+----------+------------------------
 samhan       | t        | t
(1 row)

 extname  | extversion 
----------+------------
 pgcrypto | 1.3
(1 row)
```

현재 실 DB에는 `pgcrypto 1.3`이 이미 있고 실행 계정은 superuser/DB CREATE 가능이므로, 이 환경에서 `CREATE EXTENSION IF NOT EXISTS`가 배포를 막지는 않는다.

일회성 정확 19행 적용 DB의 테이블 변경 통계는 다음과 같다.

```text
 schemaname |           relname           | n_tup_ins | n_tup_upd | n_tup_del 
------------+-----------------------------+-----------+-----------+-----------
 public     | slip_line_correction_audits |        19 |         0 |         0
 public     | slip_lines                  |         0 |        19 |         0
 public     | slips                       |         0 |         0 |         0
(3 rows)
```

기존 데이터 DML은 `slip_lines` 19행 UPDATE뿐이고, `slips`를 포함한 다른 기존 테이블 데이터는 건드리지 않는다. 다만 `slip_lines`의 금액 5개 외에도 기존 감사 컬럼 `modified_at`, `modified_by`를 갱신한다. 영구 스키마에는 신규 감사 테이블과 부분 인덱스가 생긴다. 임시 대상 테이블은 커밋 시 삭제된다.

fresh PostgreSQL에서는 `pgcrypto`가 없어서 extension과 그 소유 객체 36개도 생성됐다.

```text
 extname  | extversion 
----------+------------
 pgcrypto | 1.3
(1 row)

 pgcrypto_owned_objects 
------------------------
                     36
(1 row)
```

따라서 “새 테이블 생성 외 영향”에는 신규 인덱스, `pgcrypto`가 없는 DB에서의 extension 객체 생성, 그리고 `slip_lines.modified_at/modified_by` 변경이 포함된다. 현재 실 DB에서는 extension이 이미 있어 그 부분은 no-op이다.

## 5. 실 DB 현재 금액 모양 재현 — 배포 성공하지만 감사 0행·정정 0행

## 6. 최종 판정

**BLOCK — V61을 현재 상태로 배포 승인할 수 없다.**

1. 현재 실 DB의 V61 매칭은 구현 보고서의 19행이 아니라 **0행**이다. V61 적용 이력도 없으므로 이미 이 마이그레이션이 정정한 결과가 아니다. 실 DB와 같은 데이터를 일회성 PostgreSQL에서 재현해 적용하면 성공 종료하지만 감사 0행·UPDATE 0행이며 5,169,000원 과다 계상이 남았다.
2. **0도 19도 아닌 실제 가능한 수**를 재현했다. 10행 기정정/9행 구값은 9, 전표 하나 삭제는 18, 금액 한 행 1원 변경은 18, 동일 비품목 조건 중복 한 행은 20이었다. 모두 PostgreSQL 예외와 종료 코드 3으로 단일 트랜잭션이 롤백되어 Flyway 배포 및 서비스 기동을 막는다.
3. 정상 7행과 확인불가 3행은 현재 실 DB에서 각각 정확히 7·3행이 재현됐고 V61 조건 매칭은 양쪽 모두 0행이다. 현재 데이터에서는 이 10행이 제외된다.
4. 그러나 V61은 문서와 달리 `product_name`을 비교하지 않는다. 원 대상 하나가 빠지고 품목명만 다른 비대상 하나가 들어와 총수가 19로 상쇄되는 fixture에서 V61이 성공하며 비대상 1행을 실제 정정했다. 따라서 count guard만으로는 오정정을 막지 못한다.
5. 정확 19행 fixture에서는 감사 19행과 금액 전후 JSON이 채워지고, 정정 후 19/19행에서 `공급가액 + 부가세 = 원래 사용자 총액`이 성립한다. 합계 **51,690,000원**은 원래 사용자 총액이고 **5,169,000원**은 정정 전 56,859,000원에서 이를 뺀 과다 계상액이다.
6. 기존 데이터 변경은 `slip_lines` 19행의 금액 5개와 `modified_at/modified_by`뿐이다. `slips` 등 다른 기존 테이블 DML은 없었다. 영구 스키마 영향은 신규 감사 테이블·인덱스이며, `pgcrypto`가 없는 DB에서는 extension 객체도 생성된다(현재 실 DB에는 이미 존재).
