# 2026-08-01 1015 기능 회귀 검토

## 검토 경계와 선행 보고서 기준

- 검토 각도는 두 변경으로 기존 동작이 막히는지 여부로 한정한다. 코드 수정, git 명령, Docker 재빌드·재기동, 실 DB 쓰기, 비밀번호 재설정은 수행하지 않는다.
- 선행 구현 보고서가 주장한 변경은 안내문 교체와 `LONG_UNUSED -> NEED_PW_INPUT` 영속 전환이며, 판정 함수 `expirationAt()`과 30일 상수는 불변이라고 되어 있다.
- 선행 보고서의 프론트 실행 주장은 의존성 부재로 미검증이고, backend는 변경 서비스 단위 테스트 및 모듈 전체 테스트 성공을 주장한다. 아래에서 해당 원문을 fresh 실행으로 재현하고, 상태 전이 소비 경로까지 별도로 추적한다.

## 결함 1 — 승인 복구 직후 다시 `LONG_UNUSED`로 판정되어 주문 접근이 계속 차단됨 (차단)

`LONG_UNUSED -> APPROVED` 요청의 외부/내부 매핑 자체는 `APPROVED -> NEED_PW_INPUT`이 맞다. `PartnerApprovalStatus.fromInternal()`도 `NEED_PW_INPUT`을 화면의 `APPROVED`로 돌려주므로 dropdown 표시와 저장 상태는 이 지점에서는 일치한다.

그러나 복구 동작은 만료 기준시각을 갱신하지 않는다. `PartnerAuth.restoreFromLongUnused()`는 상태만 `NEED_PW_INPUT`으로 바꾸고, `expirationAt()`은 이전 `lastLoginAt`, 없으면 이전 `passwordChangedAt`에 30일을 더한다. `PartnerAuthService.evaluateEffectiveStatus()`는 `NEED_PW_INPUT`을 만료 평가 제외 상태로 취급하지 않으므로, 다음 `checkStatus()`에서 다시 `LONG_UNUSED`를 응답한다. 사용자가 상태조회를 건너뛰고 로그인해도 `tryLogin()`이 비밀번호 검증 전에 같은 평가를 수행하고 다시 `markLongUnused()`한 뒤 토큰 없이 차단한다.

기존 두 테스트를 fresh로 함께 실행해 각 연결 고리를 재현했다. 첫 테스트는 복구 후 저장 상태가 `NEED_PW_INPUT`이면서 `expirationAt()`이 복구 전과 같음을 검증하고, 두 번째는 30일이 지난 `NEED_PW_INPUT`이 로그인에서 `LONG_UNUSED`로 저장·응답되고 토큰이 없음을 검증한다.


따라서 선행 구현 보고서의 “복구된 거래처가 실제로 다시 주문 앱에 접근한다”는 효과는 재현되지 않는다. 화면에서 승인을 선택하면 응답 row는 `APPROVED`로 보일 수 있지만, 주문 앱의 다음 상태조회는 다시 장기미사용 안내를 표시한다. `NEED_PW_INPUT`에서는 기존 비밀번호로 로그인하는 것이 정상 경로이고 별도 비밀번호 재설정은 필요하지 않지만, 현재는 그 로그인 검증 지점까지 도달하지 못한다.

## 안내문과 실제 판정 기준 — 일치

- 실제 계산은 `lastLoginAt != null ? lastLoginAt : passwordChangedAt`, 그 기준시각에 `LONG_UNUSED_DAYS(30)`를 더한 값이다. 상태조회와 로그인 모두 이 `expirationAt()`을 사용한다.
- 주문서 앱의 새 문구는 “마지막 로그인일(로그인 기록이 없으면 비밀번호 변경일)로부터 30일간”으로 같은 우선순위와 기간을 설명한다. 최종 주문·출고 데이터는 현행 판정 경로에서 읽지 않는다.
- 경계 비교는 `expiresAt.isBefore(LocalDateTime.now())`이므로 정확히 만료시각과 같은 순간이 아니라 그 이후부터 차단된다. 문구의 30일 설명과 모순되는 거래처 집합 차이는 확인되지 않았다.

## 판정 기준 불변 — 확인

- `LONG_UNUSED` 모집단을 정하는 유일한 현재 계산은 `PartnerAuth.expirationAt()`과 `PartnerAuthService.evaluateEffectiveStatus()`이다. 새 복구 메서드는 이 계산에 참여하지 않고 이미 `LONG_UNUSED`인 엔티티에 관리자가 `APPROVED`를 요청한 뒤에만 호출된다.
- 복구 전후 `expirationAt()` 동일성을 검증하는 테스트와, 30일이 지난 `NEED_PW_INPUT`의 판정을 검증하는 테스트를 fresh 실행했다. 이 때문에 “어떤 거래처가 LONG_UNUSED가 되는가”는 바뀌지 않았다. 동시에 이 불변성이 결함 1의 즉시 재차단 원인이기도 하다.
- 안내문 변경은 정적 HTML 문자열뿐이며 backend 판정 입력에 전달되는 값이 없다.

## `APPROVED`와 `NEED_PW_INPUT` 매핑 — 저장 상태 선택 자체는 맞음

- 화면의 외부 상태 `APPROVED` 대표 내부값은 `PartnerApprovalStatus.toInternal()`에서 `NEED_PW_INPUT`이다.
- 응답 역매핑도 `NEED_PW_INPUT`, `OK`를 `APPROVED`로 묶는다. `OK`는 로그인 응답 전용이고 엔티티에는 저장하지 않으므로, 로그인 전 승인된 엔티티가 `NEED_PW_INPUT`인 것은 기존 상태 모델과 일치한다.
- 신규 가입 승인도 `PENDING -> NEED_PW_SET -> 비밀번호 최초 설정 -> NEED_PW_INPUT`으로 끝나고, 잠금 해제도 `LOCKED -> NEED_PW_INPUT`이다. 따라서 `LONG_UNUSED -> NEED_PW_INPUT`은 “기존 비밀번호 입력 가능 상태로 복구”라는 의도에 맞으며 `APPROVED`를 내부 엔티티에 직접 저장하는 설계는 아니다.
- 문제는 이 매핑이 아니라, 결함 1처럼 그 상태가 과거 만료시각 때문에 실제 인증에서 유효하지 않다는 점이다.

## 기존 승인·거절·조회 경로 — 별도 막힘은 재현되지 않음

코드 경로:

- 신규 승인: `PENDING`에서 `APPROVED` 요청 시 `approvePending()`으로 `NEED_PW_SET`.
- 잠금 승인: `LOCKED`에서 `APPROVED` 요청 시 `unlock()`으로 `NEED_PW_INPUT`.
- 접근 거절: `ACCESS_DENIED` 요청 시 기존 `denyAccess()` 호출.
- 조회: 전체/상태별 repository 조회 후 `PartnerApprovalResponse.from()`으로 외부 6종 상태에 매핑.
- frontend는 PATCH 성공 후 `partner-approvals` query를 invalidate하여 다시 조회한다. `LONG_UNUSED` 복구 row도 저장값 `NEED_PW_INPUT`이 외부 `APPROVED`로 보인다.

## 최종 판정

- **차단 결함 1건:** `LONG_UNUSED -> APPROVED`가 `NEED_PW_INPUT`을 저장해도 과거 만료 기준시각이 유지되어, 상태조회/로그인에서 즉시 `LONG_UNUSED`로 되돌아가고 주문 접근이 계속 차단된다.
- 안내문은 현행 판정 기준과 일치하고, 판정 대상 규칙 자체는 바뀌지 않았다.
- `NEED_PW_INPUT` 저장은 외부 `APPROVED`의 올바른 내부 표현이다. 다만 현재 복구 효과는 위 결함 때문에 성립하지 않는다.
- 기존 승인·접근제한·조회 및 주문 앱의 나머지 표면에서 추가 회귀는 재현되지 않았다.
- 선행 구현 보고서의 프론트 의존성 부재/실행 실패 원문은 현재 재현되지 않았고, fresh 전체 주문 앱 테스트 244건과 typecheck는 성공했다.

따라서 이번 fix는 **회귀 검토 불합격**이다. 코드 수정은 수행하지 않았다.
