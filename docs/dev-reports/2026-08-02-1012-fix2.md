
동일 46개를 `product_db.products.model_code`에 exact 대조한 원문:

```text
requested | model_code_exact | model_name_exact | model_code_ci | active_exact
```

판정: 요청 값의 대소문자·공백·인코딩 문제가 아니다. 현재 product 정본에 동일 모델코드가 0건이며, 기존 endpoint가 정상적으로 200 빈 배열을 반환할 수 있는 데이터 불일치가 실행으로 확인됐다. 다만 `model_name` 대체 가능성 및 서비스 경계는 다음 실행에서 확인한다.

## 실행 확인 2 — 실제 요청 원문·endpoint·서비스 경계

slip DB에서 직접 읽은 46개 값을 JSON으로 만들어 product-service 직접 포트 `8084`에 전송했다.

```text
REQUEST_COUNT=46
REQUEST_BODY={"modelCodes":["TEST-MODEL-0001", ... ,"TEST-MODEL-0100"]}
HTTP/1.1 200
{"success":true,"code":"OK","message":"성공","data":[],"timestamp":"2026-08-01T17:56:41.169707824Z"}
```

대소문자·공백 변환 없이 전표의 `product_id` 46개를 같은 product-service의 legacy UUID endpoint에도 읽기 요청했다.

```text
UUID_REQUESTED=46
UUID_HTTP=200
UUID_RETURNED=0
```

컨테이너 환경 원문:

```text
product-service SERVER_PORT=8084
slip-service SERVER_PORT=8086
slip-service SAMHAN_PRODUCT_SERVICE_URL=http://product-service:8084
SAMHAN_INTERNAL_TOKEN=dev-internal-token-change-me (양쪽 동일)
```

판정: 경로 `/products/internal/lookup-by-model-codes`, 본문 키 `modelCodes`, 내부 토큰, product-service 포트 `8084`는 실제 서비스 계약과 일치하고 HTTP 200도 확인됐다. gateway 비노출/호출 포트 `18086` 문제가 원인이 아니다. UUID 조회도 0건이므로 단순 UUID→모델코드 변환 실패가 아니라 현재 slip DB의 46개 라인이 product DB의 활성 정본과 연결되지 않은 환경/데이터 경계 결함이다.

gateway 경유도 별도로 확인했다.

```text
POST http://127.0.0.1:8080/products/internal/lookup-by-model-codes
HTTP/1.1 404 Not Found
```

판정: `/products/internal/**`는 gateway 비노출이 맞지만, slip-service는 Eureka의 `http://product-service:8084` 직결 경로를 사용하므로 이 404는 slip-service 호출 실패의 원인이 아니다.

## 실행 확인 3 — categoryKey와 이익률 원문

코드 출처:

```text
ProductSummaryResponse.from(Product)
categoryKey = categoryKey(p.getProductCategory())
Product 엔티티 product_category -> ProductCategory enum -> categoryKey
estimate_category는 응답 변환에 사용하지 않음
```

실 product DB 읽기 원문:

```text
active_products=1220
product_category filled=1119
product_category NULL=101
estimate_category filled=2
```

따라서 categoryKey 기준은 폐기된 `estimate_category`가 아니라 살아 있는 `products.product_category`다. 그러나 현재 실 판매 46개는 model_code exact 0건, model_name exact 0건, product name exact 0건이고 전표 `category_key`도 0건이므로 칩은 `0/46`이다.

이익률 0.00% 품목 `TEST-MODEL-0073`의 실 전표 원문:

```text
INBOUND  quantity=7  unit_price=828000.00  supply_amount=5796000.00  line_total=5796000.00
OUTBOUND quantity=1  unit_price=828000.00  supply_amount=828000.00   line_total=828000.00
OUTBOUND quantity=9  unit_price=828000.00  supply_amount=7452000.00  line_total=7452000.00
```

코드의 매입 출처는 `slip_lines.supply_amount` 우선, NULL이면 `slip_lines.unit_price * quantity` fallback이다. 이 품목은 실제 입고 `supply_amount / quantity = 828000.00`, 판매 `supply_amount / quantity = 828000.00`이므로 API의 `0.00%`는 판매가를 매입가로 잘못 읽은 결과가 아니라, 실 데이터가 같은 단가로 저장된 결과다. 다만 `unit_price_domain`은 legacy NULL이다.

## 실행 확인 5 — fallback GREEN

최소 수정:

- bulk lookup이 `model_code` exact 미해결 값에 대해 `model_name` bulk fallback을 수행한다.
- `ProductSummaryResponse.modelCode`는 `model_code`가 blank이면 `model_name`을 공개 business key로 반환한다.

```text
ProductServiceTest > lookupByModelCodes_fallsBackToModelNameWhenModelCodeIsBlank() PASSED
BUILD SUCCESSFUL in 21s
```

단, 현재 실 DB의 46개 값은 `model_code`·`model_name`·`products.name` 모두 0건이고 product UUID도 0/46이다. 따라서 현재 공유 데이터에 대한 실 API A는 여전히 `requested=46 returned=0`이며, 이 수정은 실제 정본에 model_name만 있고 model_code가 비어 있는 정상 경계의 코드 결함을 고쳤을 뿐 현재 불일치 데이터를 합성하거나 쓰지 않았다.

## 실행 확인 6 — slip-service 테스트

