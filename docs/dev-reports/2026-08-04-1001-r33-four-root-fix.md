## 1. 설계·범위 확인

R32 설계를 재작성하지 않고 다음 계약을 그대로 구현 대상으로 확정했다.

- A: `PartnerLedgerContract`가 VAT 포함 정상 판매전표·확정 수금·기초 포함 잔액·차변/대변 방향과 세 표면의 공통 fold를 강제한다. journal-only는 정상 `SALE`로 승격하지 않고 분개 기반 진단 행으로 노출한다.
- B: 미입력/등록/미등록을 tri-state로 분리하고, 미등록 입력은 전체 조회로 완화하지 않는다. 무필터·집계·상세의 공개 거래처 cohort를 active master와 canonical 문서로 닫는다.
- C: `LIVE`/`SNAPSHOT`을 하나의 active ledger 출처로 승격해 화면·저장·CSV·인쇄가 같은 원천을 사용하고, Page 이력의 21번째 이후를 UI에서 접근 가능하게 한다.
- D: 원장 snapshot 전용 advisory-lock 채번과 수동 저장 명칭을 적용한다.

개발책임자 잠금 결정도 설계에 반영했다.

- 채권 잔액은 `기초잔액 + 기간 매출 − 기간 수금 = 기말잔액`인 기초 포함 잔액이다.
- 정상 판매전표 금액은 VAT 포함 문서금액이다.
- journal-only 거래처는 집계에 포함하고, 상세에는 분개 기반 행과 `판매전표 없음 / 전표 미이관`을 명시한다.

## 8. 새 조합 열거 및 실제 밟은 경로

1. 정상 VAT 포함 SALE + legacy 401 순액 fixture: `1,000` legacy와 `1,100` 문서금액을 한 거래처에 넣고 read model의 문서·매출·기말을 모두 `1,100`으로 확인했다. 공통 계약은 VAT 포함 SALE `1,100` + 확정 수금 `400` + 기초 `500`의 기말 `1,200`을 확인한다.
2. journal-only 401/110 거래처: 정상 SALE로 승격하지 않고 분개별 `JOURNAL_ONLY` 행과 `판매전표 없음 / 전표 미이관`을 확인했다.
3. journal-only 110만 있는 거래처: 새 `journalSeen` 조건으로 상세 행 1건과 migration notice를 확인했다.
4. 미등록 입력 `NOSUCH9999`: empty result와 repository/client 무호출을 확인했다.
5. code-only + master 해소: unfiltered 집계에 포함되는지 확인했다. SUSPENDED지만 삭제되지 않은 master도 포함되어 정상 cohort 축소가 없는지 확인했다.
6. code-only + master 미해소: 집계와 상세 모두 공개하지 않고, 무필터 전체 결과로 완화하지 않는지 확인했다.
7. LIVE 원장: 명시 저장은 기존 capture를 사용하고 조회 반복은 snapshot을 만들지 않는지 확인했다.
8. SNAPSHOT 원장: 복원 후 저장은 copy endpoint, CSV는 snapshot data, 인쇄는 `batchNo` route를 사용하며 capture/live 재조회를 호출하지 않는지 확인했다.
9. 이력 2페이지: 다음 페이지에서 `LED-20260804-000001`을 복원할 수 있는지 확인했다.
10. soft-delete 이력 포함 채번: max suffix `41`과 advisory lock key를 사용해 `LED-20260804-000042`를 만드는지 확인했다.
