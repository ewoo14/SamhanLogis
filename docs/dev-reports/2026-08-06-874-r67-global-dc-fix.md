## 1. R65에서 고정DC만 살아남은 코드 원인

R65는 `SlipService.create()`에서 `ProductSummary.fixedDiscountRate`를 `POST /internal/price-calculations` 요청에 전달했다. `dc-config-service`의 `PriceCalculationService.pickCategoryRate()`는 고정율이 있으면 category와 무관하게 먼저 반환하므로 `MCU-S6NDB1N`의 40%는 적용됐다.

반면 고정DC가 없는 라인은 `categoryKey`와 `hasVariableDiscount`의 결합으로 전역DC 적용 여부가 결정된다. 기존 `DiscountPriceClient.toRequestLine()`은 `hasVariableDiscount`를 보내지 않았고, 전역DC 적용 의도를 slip 저장 경로에서 명시하지 않았다. `PriceCalculationService`는 실제 `false`를 받으면 전역율을 0%로 처리한다. 또한 화면 `SlipFormPage`는 `getPriceMemory()`만 호출하고 `dc-config-service`의 거래처 DC를 조회하지 않았다. 결과적으로 고정DC 라인은 우선 분기로 통과했지만 AR처럼 고정DC가 없는 라인은 전역DC 경로가 끊겼고, 화면과 `discountInfo`는 처음부터 별도 연결이 없었다.

`dc-config-service` 원천은 기존 읽기 검증 결과와 동일하다.

```text
partnerCode=4348703365
home_discount_rate=0.4800
commercial_discount_rate=0.4900
is_deleted=false
```

가격계산 POST는 감사 로그 insert를 수행하므로 DB 쓰기 금지에 따라 이번 라운드에서 직접 호출하지 않았다. 기존 R66 읽기 원문(`docs/qa/874-riusage-r66-real-qa/dc-read-4348703365.txt`)과 현재 `InternalDcConfigController`/`PriceCalculationService` 코드를 대조했다.

## 3. 변경 내용

### 저장 BE

- `DiscountPriceClient`가 요청에 `hasVariableDiscount=true`를 고정DC 미설정 slip 라인에 명시해 거래처 전역DC 적용을 보장한다.
- 계산 응답의 `appliedRate`를 함께 수집하고, 계산 실패/응답 결측은 기존처럼 입력 단가 fallback을 유지한다.
- `SlipDiscountCalculator`가 `고정DC 40%` 또는 `전역DC 48%` 같은 설명을 만들며 UUID를 포함하지 않는다.
- `SlipService.create()`가 요청의 `discountInfo`가 비어 있으면 자동 계산 설명을 저장한다. 조회 실패 시 `DC 미적용: 가격계산 조회 실패, 입력 단가로 저장`을 저장해 조용한 오염을 피한다.

### 화면 FE

- 품목 검색 결과에서 `categoryKey`와 `fixedDiscountRate`를 보존한다.
- 거래처 DC 단건 조회 wrapper를 추가했다.
- 품목 확정 시 고정DC 우선, 없으면 거래처 전역DC를 적용해 화면 단가를 갱신한다.
- DC가 적용된 라인은 이후 거래처 최근단가 조회가 덮어쓰지 않도록 조기 종료한다.
- 저장 payload의 `discountInfo`에 화면과 동일한 설명을 포함한다.
