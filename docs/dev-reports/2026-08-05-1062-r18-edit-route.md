## R18 구현 결과 append

### ② 편집 라우트 설계와 신규/편집 분기

- `routes/index.tsx`에 `/sales/:id/edit`를 `/sales/:id`보다 앞에 등록했다.
- 라우트 가드는 `sales.slip.edit` / `update`다. `/sales/new`의 `sales.slip.create`를 재사용하지 않았다.
- `SlipFormPage`는 `useParams<{ id: string }>()`에서 `id`가 있으면 편집 모드다.
- 편집 모드는 `GET /slips/{id}`로 기존 헤더·라인을 hydrate하고 `updateSalesSlip(id, ...)`로 기존 `PUT /slips/{id}/sales` 계약을 호출한다.
- `buildSalesSlipUpdateRequest`는 `willLineBeSaved`를 사용해 품목/수량이 확정된 라인만 전송하고, 기존 서버 라인은 `lineId`, 신규 확정 라인은 `lineId: null`로 보낸다.
- 저장 성공 시 `/sales/:id`로 복귀한다.
- `DRAFT`/`SAVED`가 아니면 저장 폼을 렌더하지 않고 현재 상태 및 “DRAFT 또는 SAVED만 수정 가능” 이유를 표시한다.
- `SlipDetailPage`의 `행 추가`는 `navigate(`/sales/${id}/edit`)`로 이동한다.

### ③ 고른 권한과 근거

`sales.slip.edit / update`를 선택했다. 근거는 `SalesQueryPage`의 기존 수정 버튼이 `canAccess('sales.slip.edit', 'update')`를 사용하고, `SlipDetailPage`의 기존 `canDirectEditSales`도 같은 권한과 `DRAFT/SAVED` 상태를 함께 검사하기 때문이다. 따라서 생성 권한 `sales.slip.create`와 분리된 기존 수정 권한 축을 그대로 사용했다.
