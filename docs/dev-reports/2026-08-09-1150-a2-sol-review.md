## 결함 1 — IME 조합 중에도 자동확정하여 조합 문자열이 확정 라벨 뒤에 붙는다

### 실 사용자 경로

1. 판매 → 주문서 관리 → `판매전표로 병합 전환`을 연다.
2. 출고 창고 입력에 한글 IME 조합으로 `본사`를 입력한다.
3. `compositionend` 전 단일 후보 자동확정이 발생한다.
4. 조합을 backspace 상당 갱신으로 `본`으로 줄이거나 조합 완료한다.

### 실측 원문

Chromium CDP `Input.imeSetComposition`으로 브라우저 네이티브 이벤트를 발생시켰다. 페이지 안에서 `CompositionEvent`를 합성하지 않았다.

```text
[WAREHOUSE_IME_DURING]
query="본사"
events: compositionstart → compositionupdate("본사")
        → beforeinput(inputType="insertCompositionText", isComposing=true)
        → input(inputType="insertCompositionText", isComposing=true, value="본사")
duringComposition.value="HQ-001 · 본사창고"
selection=13..13

[WAREHOUSE_IME_UPDATE_BACKSPACE_EQUIVALENT]
shortened="본"
value="HQ-001 · 본사창고본"
selection=14..14

[WAREHOUSE_IME_COMMIT]
compositionend.data="본"
value="HQ-001 · 본사창고본"
```

ESC도 실제 `keydown(isComposing=true, key="Escape")`가 발생했다. 이때 컴포넌트가 조합을 IME에 맡기지 않고 draft를 확정 라벨로 되돌렸다.

```text
[WAREHOUSE_IME_ESCAPE]
inputCountAfterEscape=1
state.value="HQ-001 · 본사창고"
selection=13..13
```

### 코드 원인

- `WarehouseAutocomplete.tsx:263`은 조합 중에도 `pick(nextCandidates[0]!, false)`를 호출한다. `isComposingRef`는 `pick` 자체가 아니라 suffix selection 인자만 막는다.
- `AsyncAutocomplete.tsx:383`도 동일하게 조합 중 `pick(results[0]!, false)`를 호출한다.
- 두 컴포넌트의 `onCompositionEnd`는 ref를 `false`로만 바꾸며, 조합 중 덮어쓴 draft/controlled value를 복원하지 않는다.
- 따라서 “IME 대응”은 selection만 억제했을 뿐 자동확정을 억제하지 못했다.

### 영향 범위

- 실증된 창고 병합 화면뿐 아니라 같은 `AsyncAutocomplete`를 쓰는 품목·거래처·다중선택에도 같은 원인이 있다.
- 특히 `BankTransactionPage.tsx:414-424`는 거래처 단일 후보 자동확정의 `onChange`가 곧바로 `matchPartnerMutation.mutate(...)`로 이어진다. 실 DB 쓰기 금지 때문에 라이브 선택은 하지 않았지만, 코드상 조합 완료 전 mutation 도달이 가능하다.
- `ApprovalLineConfigPage.tsx:784-804`의 다중선택과 `ProductMultiSelectAutocomplete`도 단일 후보를 즉시 add한다.

## 결함 2 — 비동기 자동확정 응답이 사용자의 현재 선택영역을 강제로 suffix로 바꾼다

### 실 사용자 경로

1. 판매 → 견적서 관리 → 새 견적서에서 `라인 1 모델명`을 연다.
2. 실 품목 API에서 단일 후보가 되는 `00003S`를 입력한다.
3. 250ms debounce/서버 응답 전 사용자가 입력값 첫 글자 영역 `0..1`을 선택한다.
4. 실 응답이 도착해 `00003SZO-00012`가 자동확정된다.

### 실측 원문

```text
[PRODUCT_EXISTING_SELECTION]
query="00003S"
modelName="00003SZO-00012"
userSelectionBeforeResult: value="00003S", start=0, end=1
selectionAfterResult:      value="00003SZO-00012", start=6, end=14
```

사용자가 만든 selection `0..1`은 보존되지 않고 자동생성 suffix `6..14`로 교체됐다.

### 코드 원인

- `AsyncAutocomplete.tsx:249-255`가 응답 시점의 사용자 selection을 검사하지 않고 `pendingSelectionRef`를 기록한다.
- `AsyncAutocomplete.tsx:192-195`의 layout effect가 현재 DOM selection의 출처/변경 여부를 확인하지 않고 `setSelectionRange(pending.start, pending.end)`를 실행한다.
- 서버 debounce 사이에 사용자가 selection을 바꿀 수 있으므로 타이밍 비의존 구현이 새 사용자 동작을 덮는다.

### ⑤ 라벨과 사용자 입력이 같을 때

실 품목 `000099` 및 `00003SZO-00012` 경로에서 suffix가 빈 문자열이면 selection은 라벨 끝에서 collapse됐다.

```text
value="00003SZO-00012", start=14, end=14
```

이 상태의 다음 문자는 일반 입력처럼 뒤에 붙는다. 빈 suffix 자체의 예외/크래시는 없었다.

### ⑥ 양방향·다른 자동완성 필드

- 창고 일반 입력 양방향: PASS (`H → HQ-...`, 다음 `Q → HQ-...`, suffix 1→2 이동).
- 품목 일반 입력 양방향: PASS (`00003S` 자동확정 뒤 `Z`, suffix 6→7 이동).
- 공유 범위 전수 결과:
  - `WarehouseAutocomplete` 명시 자동확정: 병합 전환 1곳.
  - `AsyncAutocomplete` 명시 자동확정: 품목 견적 1곳, 은행 거래처 1곳, 결재자 다중선택 1곳.
  - `ProductAutocomplete`는 wrapper 기본값이 `autoSelectSingleResult=true`여서 데스크톱의 품목 호출 4곳 전부 영향권이다.
  - `ProductMultiSelectAutocomplete`도 항상 자동확정하며 견적품목 관리 1곳에서 사용한다.
- 거래처 은행매칭 라이브 선택은 즉시 DB mutation이므로 금지 조건에 따라 실행하지 않았다. 공통 기반의 결함 1·2 도달 코드는 동일하다.

### ⑦ 기존 테스트 변경 대조

`git diff origin/main...HEAD -- '*.test.*'` 결과 기존 테스트가 수정됐다.

1. `알려진 동작: 자동확정 직후 이어진 키가 라벨 뒤에 붙는다 (#1141)`는 A2 기대 테스트로 교체됐다. 원 결함의 새 기대를 고정하는 변경이라 그 자체는 합리적이다.
2. 더 위험한 변경은 기존 `allows IME composition input immediately after auto-confirmation`에 `compositionStart`를 새로 넣고 “selection을 건드리지 않음”만 검사하게 한 부분이다. 이 테스트는 자동확정 자체가 조합 중 실행되는지, 조합 갱신/완료가 라벨 뒤에 붙는지 검사하지 않는다. 실 Chromium 결함 1을 green으로 통과시키는 회귀 신호 소거다.
3. 단위 테스트의 `fireEvent.change`는 브라우저 selection replacement와 네이티브 IME 수명주기를 재현하지 못한다. 219건 green과 라이브 결함 2건이 양립한 이유다.
