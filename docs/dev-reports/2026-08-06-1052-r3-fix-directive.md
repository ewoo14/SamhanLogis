# #1052 R3 fix directive — ApplicationReady readiness 경합

## 1. 좌표 — grep 전수

결함은 창고 alias 검증 결과와 Spring Boot 기본 readiness 전이가 같은 전역 상태를 마지막 쓰기 우선으로 갱신하는 데 있다.

- `services/slip-service/src/main/java/com/samhanair/logis/slip/publish/WarehouseMappingValidationService.java:43-45`
  - `ApplicationReadyEvent` listener가 `scheduleValidation()`을 호출한다.
- 같은 파일 `:55-66`
  - 먼저 `REFUSING_TRAFFIC`을 발행한 뒤 실제 검증은 `applicationTaskExecutor` worker에 넘긴다.
- 같은 파일 `:113-121`, `:130-143`
  - 조회 실패는 `UNAVAILABLE`과 `REFUSING_TRAFFIC`을 발행한다.
- Spring Boot 3.3.5 원문 `org.springframework.boot.context.event.EventPublishingRunListener#ready`
  - `ApplicationReadyEvent`를 동기 publish한 **다음 줄**에서 `ReadinessState.ACCEPTING_TRAFFIC`을 발행한다.
  - 따라서 Ready listener 또는 그 worker가 먼저 기록한 실패가 Boot 기본 상태로 덮일 수 있다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/publish/WarehouseCodeMapper.java:128-149`
  - readiness와 별개로 STRICT 미검증/실패 상태의 `resolve()`는 `INTERNAL_ERROR`를 던진다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/web/SlipPublishController.java:89-98` →
  `services/slip-service/src/main/java/com/samhanair/logis/slip/publish/SlipPublishService.java:121-135`
  - 실 사용자 견적→전표 발행 endpoint가 이 `resolve()`에 도달한다.
- `services/slip-service/src/main/resources/application.yml:200-211`
  - readiness probe를 활성화하고 `readinessState`를 readiness group에 포함한다.
- `infrastructure/docker-compose.prod.yml:426-431`, `infrastructure/terraform/CUTOVER.md:268-277`
  - prod 컨테이너 healthcheck와 배포 완료 판정이 `/actuator/health` 성공을 소비한다.

전수 확인 명령:

```powershell
rg -n "ApplicationReadyEvent|AvailabilityChangeEvent|ReadinessState|readinessState|actuator/health" `
  services/slip-service/src/main services/slip-service/src/test `
  infrastructure .github
rg -n "warehouseCodeMapper\.resolve|resolveWarehouseId" `
  services/slip-service/src/main clients
```

현재 repo의 창고 readiness writer는 `WarehouseMappingValidationService` 하나지만, 의존 중인 Spring Boot가 Ready 완료 시 같은 상태를 한 번 더 쓴다. Spring Boot 3.3.5 실제 클래스 조합으로 관찰한 원문은 다음과 같다.

```text
VALIDATOR_LISTENER=REFUSING_TRAFFIC
AFTER_EVENT_PUBLISHING_RUN_LISTENER_READY=ACCEPTING_TRAFFIC, HEALTH=UP
```

## 2. 불변식 — 금지할 수단

반드시 지킬 불변식:

1. STRICT에서 네 코드가 모두 `VERIFIED`가 아니면, Ready lifecycle 종료 뒤에도 readiness와 전역 health가 성공을 보고해서는 안 된다.
2. STRICT 발행 `resolve()` 허용 여부와 actuator readiness가 같은 사실을 말해야 한다.
3. alias 검증 성공 뒤에는 readiness가 `ACCEPTING_TRAFFIC`으로 전이하고 정상 발행이 즉시 가능해야 한다.
4. inventory-service 장애·지연이 Spring context 생성, web server 기동, `ApplicationReadyEvent` 반환을 막아서는 안 된다.
5. DEV_SUBSTITUTE는 외부 조회 없이 기존 로컬 발행을 유지해야 한다.

금지할 수단:

- 외부 조회를 생성자, `@PostConstruct`, context refresh thread 또는 Ready listener의 동기 경로로 옮기지 않는다.
- `WarehouseCodeMapper.resolve()`의 STRICT fail-closed 가드를 완화하거나 우회하지 않는다.
- 운영 mode를 DEV_SUBSTITUTE로 바꾸거나 UUID를 추측·하드코딩하지 않는다.
- sleep, 임의 지연, listener 우선순위만으로 경합을 숨기지 않는다. Boot의 기본 ACCEPTING 발행이 더 늦게 일어나는 원문 순서를 견뎌야 한다.
- prod healthcheck에서 readiness를 제거해 불일치를 감추지 않는다.

## 3. 양방향 RED — 반대급부 포함

### RED A: 실패가 성공 상태로 덮이지 않아야 한다

실제 Spring lifecycle을 사용하는 테스트에서 다음 순서를 결정적으로 만든다.

1. STRICT와 네 코드로 context를 시작한다.
2. alias client가 Ready 시점에 즉시 연결 실패를 반환하도록 한다.
3. 검증 worker의 실패 처리가 끝난 뒤 Ready lifecycle도 끝날 때까지 기다린다.
4. mapper 네 상태가 `UNAVAILABLE`인지 확인한다.
5. `/actuator/health/readiness`와 `/actuator/health`가 비성공인지 확인한다.
6. 같은 시점의 견적→전표 발행이 미검증 매핑으로 거부되는지 확인한다.

현재 RED의 핵심 실제값은 `mapper=UNAVAILABLE`인데 readiness health가 `UP`이 될 수 있다는 것이다. 단위 서비스의 `validateNow()` 직접 호출만으로 대체하지 말고, 반드시 Boot의 `ApplicationReadyEvent → 기본 ACCEPTING` 순서를 포함한다.

### RED B: 성공·기동 비차단을 함께 보존해야 한다

반대급부를 다음 세 갈래로 고정한다.

- alias 네 쌍이 일치하면 Ready lifecycle 뒤 readiness와 전역 health가 성공하고 네 코드의 `resolve()`가 모두 허용된다.
- alias client를 latch로 지연해도 web server/context와 Ready 호출은 즉시 완료되고, worker 완료 전에는 health만 비성공이어야 한다. 외부 조회 종료를 기다리도록 기동을 직렬화하면 실패다.
- DEV_SUBSTITUTE에서는 alias client 호출이 0회이며 로컬 전표 발행과 health 성공이 유지된다.

## 4. 범위 밖

- eCount alias 조회 계약, 26행 데이터 내용, 창고 UUID 값 자체는 변경하지 않는다.
- `WarehouseInternalClient`의 정렬·timeout, inventory endpoint/repository, 변수명 개명은 이 fix의 대상이 아니다.
- 옛 변수명이 남은 역사 문서 정리나 CI 설명 보강을 이 커밋에 섞지 않는다.
- Docker 재빌드·재배포·중지, AWS/Terraform apply, DB write는 하지 않는다.
