# #901 클로드 대화 기능 정찰 — 계정 권한 범위 내 내부 작업

> 작성일: 2026-08-13  
> 범위: 코드·GitHub 이슈/PR·기존 결정 문서 읽기 전용 정찰  
> 금지 준수: Docker/Testcontainers/격리 스택 미기동, 공유 DB 조회·쓰기 미실행, 구현 코드 미변경, git 변경 명령 미사용

## 0. 결론

`#901`은 단순 대화 UI가 아니라 **로그인 계정의 기존 서버 권한을 대리 실행에도 그대로 적용하는 보안 경계 기능**이다.

이미 결정된 경계는 다음과 같다.

1. 클로드 도구 호출은 **기존 BE 엔드포인트를 그대로 통과**한다.
2. 권한은 각 BE의 `@RequirePermission` 등 **서버 권위**가 강제한다.
3. 클로드에게 **DB 직접 접근이나 권한 우회 내부 경로를 주지 않는다**.
4. 대화 응답에도 UUID 비노출 규약을 적용한다.

아직 결정되지 않은 핵심은 다음과 같다.

- 내부 작업이 조회 전용인지, 생성·수정까지인지
- 승인·발행·삭제·전송·외부 API 호출 같은 되돌릴 수 없는 작업을 아예 제외할지, 확인 후 허용할지
- 클로드 수행을 사람 수행과 구조적으로 구분하는 감사 주체 모델
- 대화 이력 보존/삭제, 모델로 전송할 사내 데이터 범위, 비용 상한
- `#894` 사내 채팅 앱과 대화 UI/저장소를 공유할지

이 보고서는 위 미결정을 대신 결정하지 않는다.

## 4. “계정 권한 범위 내”를 이 레포가 판정하는 방법

### 4.1 권한 모델 요약

| 층 | 판정 |
|---|---|
| 인증 | API gateway가 Bearer JWT 또는 access token cookie를 검증한다. 실패 시 401 |
| 신원 전파 | 서명 검증된 JWT에서 `X-User-Id`, `X-Is-System-Master`, `X-User-Groups`, `X-Is-Partner`, `X-Partner-Code`를 다시 만든다. 클라이언트가 보낸 동일 헤더는 제거 후 덮어쓴다 |
| 실효 권한 생성 | 계정이 속한 활성 권한그룹들의 page/action 권한을 합집합하고, 계정 override가 같은 page를 대체하여 `account_page_permissions`를 materialize한다 |
| endpoint 강제 | Controller의 `@RequirePermission(page=..., action=...)`를 AOP가 가로채 계정 UUID+page+action을 auth-service에 확인한다 |
| 실패 정책 | 계정 ID 누락/파싱 실패, permission client 누락, auth-service 조회 실패, grant 없음은 모두 deny(fail-secure) |
| MASTER | `is_system_master=true` 그룹 소속 계정은 bypass. Samhan 일반 경로에서 `role==MASTER` 문자열 폴백은 제거됨 |
| PARTNER | 기본 deny. `partnerSelfService=true` endpoint만 통과하며, 실제 자기 거래처 범위는 service 계층이 별도 대조 |
| 아로로지스 예외 | 독립 JWT/role enforcement 모드에서는 `AROLOGIS_*` role 기반 `canView/canEdit`를 유지. Samhan Public 직원 경로는 계정 권한을 사용 |

### 4.3 #901에 적용되는 불변식

Claude 도구 실행기는 권한표를 한 번 읽고 스스로 허용/거부하는 권위가 되어서는 안 된다. 최종 업무 호출 자체가 기존 gateway→BE→`@RequirePermission` 경로를 통과해야 한다. 권한 사전 조회는 UX 안내용일 수 있지만, 그것만으로 내부 endpoint를 우회 호출하면 D-901-1을 위반한다.

## 5. 내부 작업 범위와 되돌릴 수 없는 작업

### 5.1 조회만인가, 쓰기도인가

**미정이다.** #901은 다음을 “착수 시 확정”으로 남겼다.

> “행위 범위 — 조회 전용부터 시작할지, 변경(생성/수정)까지 허용할지.”

따라서 “내부 작업”이라는 단어만으로 쓰기를 포함한다고 추론하면 안 된다.

### 5.2 삭제·확정·전송·외부 API 호출이 포함되는가

**미정이다.** #901이 명시한 예시는 “승인·발행·삭제”이며, 변경을 허용할 경우 별도 확인 절차를 검토하라고만 했다. 전송과 외부 API 호출은 #901에서 구체적으로 허용되지 않았다.

이 항목은 가장 무거운 업무·보안 결정이다. 권한 bit가 있다고 해서 자연어 대화 한 번으로 불가역 작업을 자동 실행해도 된다는 뜻은 아니다. `DELETE` 권한과 “AI에게 무확인 삭제를 위임한다”는 정책은 별개다.

## 6. 기존 감사 방식과 #901의 공백

### 6.1 BaseEntity 7 audit

`BaseEntity`는 다음 7필드를 제공한다.

- `created_at`, `created_by`
- `modified_at`, `modified_by`
- `deleted_at`, `deleted_by`, `is_deleted`

근거: `shared/common/src/main/java/com/samhanair/logis/common/entity/BaseEntity.java:14-43`, soft delete/복원 `:53-79`.

이 층은 행의 생성·수정·soft-delete 주체를 남기지만, **어떤 대화/도구 호출/확인을 통해 변경됐는지**는 남기지 않는다.

### 6.2 도메인 audit overlay (`inventory_audit_logs` 예)

공통 `AuditLogEntry`는 BaseEntity 7필드에 대상, revision, actor ID/표시명, 필드, 이전/새 값, 변경시각을 더한다.

- 공통 필드와 UUID 비노출: `shared/realtime-abstraction/src/main/java/com/samhanair/logis/shared/realtime/audit/AuditLogEntry.java:12-27`, `:48-84`
- inventory 구현: `services/inventory-service/src/main/java/com/samhanair/logis/inventory/realtime/domain/InventoryAuditLog.java:15-31`, `:42-61`
- INSERT+SSE 기록: `services/inventory-service/src/main/java/com/samhanair/logis/inventory/realtime/service/InventoryAuditLogRecorder.java:20-34`, `:49-87`
- 실제 테이블: `services/inventory-service/src/main/resources/db/migration/V4__add_inventory_audit_logs_and_edit_requests.sql:22-76`

이 층은 before/after와 사람 actor를 남길 수 있지만 역시 Claude 위임 메타데이터 전용 필드는 없다.

### 6.3 중앙 감사 파이프

PR #1177 머지 커밋 `d3623ada9`의 `AuditEventV2`에는 `userId`, `actorDisplayName`, `userRole`, request/trace, resource, before/after, 결과/오류, IP/UA가 있다. `EventKind`는 READ/MUTATION/AUTH/BATCH/INTERNAL을 구분한다.

원격 main 근거: `shared/audit-contract/src/main/java/com/samhanair/logis/shared/audit/contract/AuditEventV2.java@d3623ada9:12-21`, `AuditEnums.java@d3623ada9:6-9`. 현재 작업 브랜치에는 이 머지 파일이 아직 없다는 시간차에 유의한다.

그러나 다음 필드는 없다.

- `actorType` (`HUMAN`/`CLAUDE` 등)
- `delegatedByAccountId`
- `conversationId`
- `toolCallId`
- `confirmationId` 또는 승인 증거
- 사용 모델/정책 버전

따라서 현재 중앙 감사 스키마만으로는 **“사람이 직접 한 것”과 “그 사람 계정 권한으로 Claude가 수행한 것”을 구조적으로 구분할 수 없다.** `actorDisplayName` 문자열에 표시를 붙이는 것은 검색·위변조·정합성 측면에서 구조적 구분이 아니다.

추가로 중앙 감사는 after-commit·non-blocking·fail-soft라 업무를 막지 않는다. 이는 기존 결정이지만, 보안상 반드시 남아야 하는 AI 고위험 실행 증거의 유실 허용도까지 결정한 것은 아니다.

## 7. #894 사내 메신저와의 관계

확인된 관계:

1. #894의 사람 간 쪽지/채팅은 `messages` 확장+room 모델로 통합됐다.

## 8. 개발책임자 결정이 필요한 항목 — 선택지와 결과

아래는 선택지 제시만 하며 본 보고서가 선택하지 않는다.

### Q1. 첫 행위 범위

| 선택지 | 결과 |
|---|---|
| A. 조회 전용 | 가장 작은 보안 경계. VIEW endpoint만 도구화. 데이터 유출·UUID·객체 scope 검증에 집중할 수 있으나 “작업 수행” 가치는 제한됨 |
| B. 조회 + 되돌릴 수 있는 생성/수정 | CREATE/UPDATE 중 명시 allowlist만 허용. undo/restore 또는 원상복구 경로가 있는 업무부터 가능. 감사와 충돌/멱등성 설계가 필요 |
| C. 7-action 전부 후보 | DELETE/RESTORE/DOWNLOAD/PRINT까지 포함 가능. 가장 넓은 가치와 가장 큰 업무·보안 위험. Q2 확정 없이는 착수 불가 |

### Q2. 승인·발행·삭제·전송·외부 API 호출

| 선택지 | 결과 |
|---|---|
| A. AI 범위에서 제외 | 사용자가 해당 화면에서 직접 수행. 오작동 피해를 가장 강하게 제한하지만 자동화 완결성은 낮음 |
| B. 매 실행 2단계 확인 | Claude가 대상·변경 전후·부작용을 제시하고 사용자가 명시 확인한 단일 실행만 허용. 확인 토큰의 1회성·만료·대상 바인딩과 감사 증거 필요 |
| C. 업무별 사전 위임 정책 + 고위험만 재확인 | 예: 특정 발송은 한도 내 자동, 삭제/확정은 항상 확인. 운영 효율은 높지만 정책 엔진·금액/상태/대상 조건과 예외 관리가 필요 |

### Q3. Claude 감사 주체 표현

| 선택지 | 결과 |
|---|---|
| A. 기존 사용자 actor + 문자열 표식 | 스키마 변경이 작지만 사람 직접 수행과 구조적 구분이 약하고 검색/정책 집행이 취약 |
| B. Claude 전용 synthetic 계정 | actor 구분은 쉽지만 실제 위임자 계정과 권한 근거가 분리되어 “누가 시켰는가”를 추가 필드 없이 잃음 |
| C. 복합 주체 | `actorType=CLAUDE` + `delegatedByAccountId` + `conversationId/toolCallId/confirmationId`. 가장 명확하지만 중앙 감사 계약과 도메인 감사 연결을 확장해야 함 |

### Q4. 감사 유실 정책

| 선택지 | 결과 |
|---|---|
| A. 기존 fail-soft 그대로 | 감사 장애가 업무를 막지 않음. 대신 Claude 실행 감사도 유실될 수 있음 |
| B. 조회는 fail-soft, 쓰기는 durable outbox | 업무 DB commit과 감사 outbox를 같은 트랜잭션에 남겨 쓰기 증거를 보강. 서비스별 배선 비용 증가 |
| C. 고위험 작업은 감사 저장 실패 시 실행 차단 | 증거 없는 불가역 작업을 막음. 중앙/로컬 감사 장애가 업무 가용성에 직접 영향 |

### Q5. 대화 이력 보존·삭제

| 선택지 | 결과 |
|---|---|
| A. 단기 보존 후 자동 삭제 | 정보 노출 면적과 비용 감소. 장기 업무 맥락·분쟁 재현이 약함 |
| B. 업무 감사와 대화 원문 분리 보존 | 실행 증거는 길게, 일반 대화는 짧게 보존 가능. 두 저장소의 연결키·삭제 정합 필요 |
| C. 장기/무기한 보존 | 재현성과 검색은 좋으나 개인정보·기밀·저장비·삭제권 부담이 큼 |

### Q6. 사내 데이터의 모델 전송 범위

| 선택지 | 결과 |
|---|---|
| A. allowlist 필드만 전송 | 가장 엄격. 각 도구 응답에 모델용 안전 DTO 필요 |
| B. 권한 있는 응답을 기본 전송하되 민감 필드 redaction | 기능 범위는 넓지만 redaction 누락이 외부 유출로 이어질 수 있음 |
| C. 민감도 등급별 모델/처리 경로 분리 | 보안·기능 균형 가능. 데이터 분류·모델 계약·운영 복잡도 증가 |

어느 선택지든 UUID 비노출과 계정 권한은 별도 불변식이다. “사용자가 볼 수 있음”과 “외부 모델로 보내도 됨”은 같은 판단이 아니다.

## 9. 독립 머지 가능 슬라이스 제안

정책 결정 전 구현으로 들어가지 않는다. 각 슬라이스는 앞 슬라이스의 확정 계약을 소비하지만 자체 검증·롤백 가능한 머지 단위다.

### S0. 정책·위협모델 계약

범위: Q1~Q8 결정, 금지 작업, 데이터 분류, 확인 정책, 감사 actor/유실 정책, #894 관계를 spec/decision으로 고정.

끝 조건:

- 모든 도구 action이 `허용/확인 필요/금지` 중 하나로 분류됨
- 모델로 나갈 필드와 금지 필드가 명시됨
- 사람 직접 수행과 Claude 위임 수행의 감사 식별 계약이 명시됨
- 모르는 항목이 구현자 추론으로 남지 않음

### S1. 조회 전용 보안 수직 슬라이스

범위: 단일 저위험 VIEW 업무를 기존 gateway→BE endpoint로 호출하는 대화/도구 왕복. DB 직접 접근·internal bypass 없음.

끝 조건:

- 권한 있는 계정 200, 같은 도구의 권한 없는 계정 403
- 계정/그룹/MASTER/PARTNER 경계가 기존 직접 호출과 정확히 같음
- permission client/auth-service 장애 시 deny
- 응답·오류·대화에 UUID/민감 필드 0
- Claude/모델 SDK 자격이 소스·로그에 남지 않음

### S2. Claude 복합 감사 주체 수직 슬라이스

범위: S0에서 선택한 actor 모델로 대화→tool-call→기존 BE 실행→도메인/중앙 감사 연결.

끝 조건:

- 위임자 계정, Claude 수행 여부, 대화/도구 호출, 대상, 시각, 결과, 확인 증거를 한 경로로 추적 가능
- 사람 직접 수행과 쿼리로 명확히 구분 가능
- 감사 표시값에 UUID 미노출
- 선택한 감사 유실 정책의 장애 시나리오가 검증됨

### S3. 대화 이력·UI·외부 전송 경계

범위: S0의 #894 관계 선택에 따른 UI 셸, 대화 이력 보존/삭제, 모델 전송 DTO/redaction, quota 표시.

끝 조건:

- #894와 공유/분리 경계가 코드·저장소·라우트에서 명확함
- 보존 만료와 사용자 삭제가 감사 증거를 잘못 지우지 않음
- 외부 전송 payload를 테스트에서 관측 가능하고 금지 필드 0
- 호출량 상한과 초과 UX가 동작

### S4. 되돌릴 수 있는 쓰기 파일럿 — Q1이 허용한 경우만

범위: allowlist의 CREATE/UPDATE 한 종류. 변경 전후 diff와 원상복구 경로 포함.

끝 조건:

- 기존 `@RequirePermission` action과 정확히 일치
- 동시성/멱등성/중복 실행 방지 검증
- 잘못된 실행을 정해진 절차로 되돌릴 수 있음
- 사람 직접 수행과 Claude 수행 감사가 모두 남음

### S5. 불가역 작업 — Q2에서 허용한 경우만, 업무별 분리

범위: 승인, 발행, 삭제, 전송, 외부 API 호출을 한 PR에 섞지 않고 업무 종류별로 별도 슬라이스.

끝 조건:

- 확인 또는 사전 위임 정책이 대상·금액·상태·만료에 바인딩됨
- 재사용/재전송/replay 불가
- 실제 부작용 전에 최종 권한을 다시 검사
- 성공·실패·거부·취소와 외부 응답 식별자가 감사에 남음
- 각 업무의 개발책임자 승인 조건을 충족
