# PR #1078 · 이슈 #1075 — S19 SOL 재수렴 fix 지시서

## 1. 좌표 · 판정 · 재현 난이도

**판정: 실 사용자 경로 재현 결함 1건 · BLOCK · 머지 권고하지 않는다.**

### F1 — 버전 이력 복원에서 자동 규격 provenance가 소실된다

- `services/slip-service/src/main/java/com/samhanair/logis/slip/estimate/revision/domain/EstimateSnapshot.java:78`의 `EstimateSnapshot.Line`에는 `specification`은 있지만 `specificationSource`가 없다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/estimate/domain/Estimate.java:445-464`의 `toSnapshot()`은 `line.getSpecification()`만 캡처한다.
- 같은 파일 `Estimate.java:510-568`의 `restoreFromSnapshot()`은 라인을 전량 재생성하지만 `changeSpecificationSource()`를 호출할 스냅샷 값이 없다.
- 복원 응답의 평문 규격과 NULL source는 `clients/desktop/src/renderer/routes/EstimateFormPage.tsx:276`에서 `decodeEstimateSpecification(...).source`로 fallback되어 `USER`가 된다. 품목 해제는 같은 파일 `:1537`에서 `CATALOG`만 자동 규격으로 회수하므로 복원한 자동 규격은 남는다.

실패 재현은 제품 도메인과 같은 경계를 통과시킨 임시 RED로 확인했다.

```text
1. CATALOG / AUTO-SPEC 라인을 가진 DRAFT 견적 생성
2. Estimate.toSnapshot()
3. Estimate.restoreFromSnapshot(snapshot)
4. 복원 라인의 specificationSource == CATALOG 단정

결과: 1 test completed, 1 failed
S19SpecificationSourceRestoreTempTest > catalogSpecificationSourceSurvivesVersionRestore() FAILED
기대 CATALOG / 실제 null
```

사용자 경로는 `견적 상세 → 버전 이력 → 이 시점으로 복원 → 편집 → 해당 품목 삭제`다. 복원 직후 규격은 화면에 보이지만, 품목을 삭제해도 자동 규격만 남는다. 임시 RED 파일은 실행 직후 삭제했다.

**재현 난이도: 보통, 조건 충족 시 매회 재현.** 신규 코드로 자동 규격 품목을 저장해 revision을 만든 뒤 그 revision을 복원해야 한다. 복원 후 품목 해제 결과는 결정적이다.

## 2. 불변식

- `specification`과 `specificationSource`는 생성·수정·상세 조회뿐 아니라 버전 캡처·JSONB 직렬화·역직렬화·복원에서도 한 쌍으로 왕복해야 한다.
- 복원된 `CATALOG` 규격은 품목 해제 시 화면·로컬 상태·coedit 문서에서 제거되어야 한다.
- 복원된 `USER` 규격, 사용자 단가, 다른 라인의 규격·단가·수량은 품목 해제나 복원으로 소실되어서는 안 된다.
- provenance 필드가 없는 구 revision JSONB는 계속 역직렬화되어야 한다. 평문 규격의 출처를 사후 추측해 일괄 `CATALOG`로 바꾸지 않는다.
- 구 U+2060 규격은 기존 decode 호환으로 `CATALOG`, marker 없는 구 평문 규격은 출처 불명 상태의 무손실 기본값 `USER`로 취급한다.
- 견적→전표 변환은 규격 문자열을 그대로 복사하고 견적 전용 provenance는 전표에 이식하지 않는 현재 도메인 경계를 유지한다.

## 3. LUNA 수정 지시 · 양방향 RED

1. `EstimateSnapshot.Line`의 마지막 nullable 필드로 `String specificationSource`를 추가한다. 기존 JSONB에 필드가 없으면 null로 역직렬화되게 하고, 모든 호환 생성자는 null을 전달한다.
2. `Estimate.toSnapshot()`에서 `line.getSpecificationSource()`를 캡처한다.
3. `Estimate.restoreFromSnapshot()`이 각 라인을 재생성한 직후 `restored.changeSpecificationSource(snapLine.specificationSource())`를 호출한다. 금액 권위 3분기와 세트 계보 복원보다 provenance가 누락되지 않게 공통 지점에 둔다.
4. `EstimateRevisionService#lineDiffers`에도 `specificationSource` 비교를 포함해 값은 같고 출처만 바뀐 revision을 무변경으로 요약하지 않는다.

필수 RED/GREEN:

- `CATALOG` 라인 `toSnapshot → Jackson JSON → readValue → restoreFromSnapshot` 뒤 source가 `CATALOG`이고 응답에도 그대로 나온다.
- `USER` 라인도 같은 경계 뒤 `USER`다.
- `specificationSource`가 없는 구 JSON 문자열은 역직렬화·복원이 성공하고 null을 유지한다.
- 실제 revision restore service/API 경로에서 복원 응답이 `CATALOG`를 반환하고, `EstimateFormPage`가 그 응답을 받아 품목을 해제하면 자동 규격만 제거한다.
- 같은 시나리오에서 사용자 규격·사용자 단가·다른 라인 값은 보존한다.

## 4. DB · API · 소비자 · 마이그레이션 판정

### 기존 행

S19 시작 시 실 `slip_db` 활성 견적 라인은 2,043건, 규격 보유 행은 **4건**이었다. 이 중 2건은 S17이 만든 U+2060 QA 표본이고, 나머지 2건은 marker 없는 기존 평문 규격이다. 표본 0이 아니므로 판정 가능하다.

V113 적용 직후 기존 4건의 `specification_source`는 모두 NULL이다. 화면 hydrate 결과는 다음 셋째 상태로 갈린다.

- U+2060 2건: legacy decode로 `CATALOG` → 품목 해제 시 규격 제거.
- 평문 2건: 출처를 구별할 증거가 없으므로 `USER` fallback → 품목 해제 시 규격 보존.
- 평문 기존 행을 일괄 제거하는 것은 사용자 직접 규격까지 소실할 수 있으므로, 불명 provenance를 보존하는 현재 정책이 사용자에게 옳다.

S19 허용 범위의 API 생성으로 50자 표본 2건을 추가해 최종 규격 보유 행은 6건이다. 테스트 데이터는 `2026/08/06-3` 메모 `QA-S19-1075-50CHAR-SEPARATE-PROVENANCE`, `2026/08/06-4` 메모 `QA-S19-1075-50CHAR-ASCII-ROUNDTRIP`이다.

### 50자 API 계약

현재 실 게이트웨이에 marker 없는 50자 규격과 `specificationSource=CATALOG`를 보냈다. `POST 201`, `GET 200`, DB `VARCHAR(50)` 문자 길이 50, ASCII 표본 GET 원문 동일이었다. S17의 marker+표시 50자 `POST 400`과 달리 표시 50자는 저장된다. 다만 Docker slip-service는 S18 이전 배포라 응답에 신규 source 필드가 없었다. Docker 재빌드·재배포 금지 때문에 신규 필드의 실 배포 왕복은 실행하지 않았고, 브랜치 컴파일·140개 회귀로만 확인했다.

### 다른 소비자

- 데스크톱 상세/편집: `estimateApi.EstimateLine`이 신규 필드를 소비한다.
- 견적 상세 화면: 같은 `EstimateDetail`을 쓰며 JSON additive 필드로 깨지지 않는다.
- 인쇄: `api/sales.ts`의 부분 `LiveEstimateLineResponse`가 필요한 필드만 구조 매핑하므로 additive 필드를 무시한다.
- 견적→출고전표: `EstimateToSlipConverter`가 `specification` 문자열은 `SlipLine`에 복사하지만 `specificationSource`는 복사하지 않는다. 견적 provenance가 전표 계약을 바꾸지 않으며 표시 규격은 보존된다.
- 모바일: `MobileQuotationService`는 독립 생성 경로이고 모바일 입력 규격은 source null이다. 응답 필드 증가는 JSON additive 변경이다. 현재 `mobile-staff`의 별도 quotation API 타입은 이 DTO를 직접 역직렬화하지 않는다.
- 거래처 주문 변환: 현재 `FixtureEstimateClient` 기반 별도 snapshot 계약이며 `EstimateLineResponse` 직접 소비자가 아니다.

전수 추적에서 직접 응답 소비자 파손은 재현되지 않았다. 결함은 응답 이후의 **버전이력 저장·복원 소비자**에서 발생했다.
