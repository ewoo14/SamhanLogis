## 진단 결론

실서버 QA 원문(`docs/qa/1075-s27-real-qa/network.json`)과 코드를 대조한 결과 서버의 EstimateLine 저장 로직이 원인이 아니었다. 자동 규격이 떨어지는 최초 좌표는 `lookup-product` 응답을 프론트가 받는 경계다.

- `GET /api/products`는 같은 품목의 `specification`을 반환한다.
- `GET /slips/lookup-product`는 `ProductSummary`에 규격 필드가 없어 반환하지 않았다.
- `services/slip-service/.../ProductClient.java:297`은 응답 `data`를 `ProductSummary`로 변환한다. `ProductSummary`에 필드가 없으므로 product-service의 원문 규격이 여기서 탈락한다.
- `clients/desktop/src/renderer/api/slip.ts:781-797`은 `lookup-product` 응답을 견적용 결과로 매핑하지만 기존 wire 타입과 매퍼가 규격을 선언·전달하지 않았다.
- `clients/desktop/src/renderer/routes/EstimateFormPage.tsx:1359-1369`가 blur lookup 결과를 정규화하고, 기존 코드의 `: ''` 분기(`specification`/`specificationSource` 처리)는 규격 없는 lookup을 자동 규격 회수로 취급했다.
- 저장 payload 자체는 `EstimateFormPage.tsx`의 라인 payload 생성부에서 `specification`과 `specificationSource`를 전달할 수 있는 구조였다. 따라서 `POST /slips/estimates` 누락은 저장 API가 버린 것이 아니라 그 전에 화면 라인 값이 빈 문자열이 된 결과다.

## lookup-product 계약 전수 확인

차이는 의도된 경량 응답이 아니다. product-service의 `ProductSummaryResponse`는 이미 `specification`을 포함한다(`services/product-service/src/main/java/com/samhanair/logis/product/web/dto/ProductSummaryResponse.java:28-51`, 매핑 `:135-160`). slip-service의 facade DTO만 해당 필드를 누락한 공통 계약 결함이다.

`lookupProductByModelName`의 production 소비자는 다음 전부를 확인했다.

- `clients/desktop/src/renderer/routes/EstimateFormPage.tsx:1045` — 검색 fallback
- `clients/desktop/src/renderer/routes/EstimateFormPage.tsx:1360` — 모델명 blur lookup 및 규격/가격 반영
- `clients/desktop/src/renderer/routes/TransferFormPage.tsx:142` — 품목명·단가만 사용하며 규격을 별도 소비하지 않음
- API 선언·매퍼 `clients/desktop/src/renderer/api/slip.ts:778-797`

따라서 화면 하나에서만 보정하지 않고 공용 slip `ProductSummary` DTO, API wire 타입/매퍼를 함께 보강했다. TransferFormPage는 규격을 필요로 하는 소비자가 아니지만 동일 계약의 누락을 함께 제거한다.

## 적용한 수정

1. slip-service `ProductSummary`에 `String specification`을 추가하고 기존 호환 생성자에는 `null`을 연결했다.
2. `lookup-product` controller 문서와 IT에 규격 필드를 추가했다. 실제 product-service 응답의 규격이 facade 응답까지 유지되는 계약을 단언한다.
3. desktop API `ProductLookupResult`/wire 타입 및 매퍼에 규격을 추가했다.
4. `EstimateFormPage`에서 규격이 없는 구버전 lookup을 받아도 단순 blur는 기존 동일 품목의 규격/source를 보존하게 했다. 모델명을 해제하는 기존 clear 경로의 `CATALOG` 회수는 유지했다. 새 품목 확정 시에는 새 품목 응답 기준으로 교체·회수된다. provider에도 계산된 `nextLine.specification`과 source를 함께 쓴다.
5. RED-A를 보강해 저장 payload의 두 필드, mock 201 응답의 두 필드, 응답을 이용한 재조회 화면까지 단언했다. 50자 자동 규격 경로도 기존 테스트에서 유지한다.

## 기존 25라운드가 놓친 이유

기존 Playwright 17/17, Vitest desktop 140/backend 35/design-system 40, CI 49/49는 모두 green이었지만 다음 실제 경계를 통과하지 않았다.

- 기존 프론트 테스트는 후보 확정 응답에 규격이 있는 `ProductOption` 경로 또는 이미 화면에 hydrate된 값을 주로 단언했다.
- `lookup-product`의 실제 wire 응답에서 `specification`이 빠진 뒤, 같은 모델명 blur가 다시 lookup하고 저장하는 순서를 한 테스트가 연결하지 않았다.
- 저장 payload와 화면 상태를 함께 단언한 경우에도 201 응답과 재조회 응답까지 공통 계약의 규격/source 쌍으로 확인하지 않았다.
- 기존 slip 테스트의 `ProductSummary` 생성자는 규격을 표현하지 않았고, facade JSON의 `specification` assertion도 없었다.
- 지정 Playwright 1062 suite는 후보/blur/해제 UI 구조를 mock으로 검증하지만 실제 `/slips/lookup-product` 응답 필드와 Estimate 저장·재조회 경계를 호출하지 않는다.

즉 모든 기존 green은 이 결함 경로를 선택하지 않은 green이었다. 이번 RED는 `규격 있는 hydrate → 규격 없는 blur lookup → 저장 payload → 201 응답 → GET 재조회`를 하나의 흐름으로 만들었다.
