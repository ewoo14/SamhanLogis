## 1. fix 정적 표면 확인

먼저 지정된 직전 검토와 fix 보고서를 읽고 실제 V61을 대조했다. fix는 대상 품목명을 두 번째 `UPDATE ... CASE`의 UTF-8 hex 값으로 채운 뒤 품목명까지 조인하며, `line_total`은 OLD/NEW 양쪽 모두 원래 사용자 총액으로 비교한다. 감사와 UPDATE는 `OLD`만 수행하고, 동일 target이 둘 이상이면 예외를 낸다.

실행:


## 5. NEW 상태 과매칭 표면

### 5.1 실 DB

§2의 실측에서 현재 실 DB의 `NEW` 매치는 0행이고 중복 target도 0개다. 따라서 현재 실 DB에서는 정정 후 값과 우연히 같은 비대상 행을 NEW로 인식하는 사례가 없다.

### 5.2 합성 — 원 대상이 빠지고 동일 전체 키의 NEW 비대상이 대신 있는 경우

원래 target 1행을 soft delete하고, 같은 전표·품목명·모델·수량과 정확한 NEW 5개 금액을 가진 비대상 행을 넣었다. V61은 이를 target의 `NEW`로 실제 인식해 총 `SELECT 19`로 통과했다. NEW 비대상은 skip되므로 직접 UPDATE하거나 감사하지는 않았지만, 빠진 원 대상 대신 비대상을 “이미 정정됨”으로 인정했다.

출력 원문:

```text
DATABASE newovermatchdb
SELECT 19
DO
INSERT 0 18
UPDATE 18
migration_exit=0

 audit_rows | intended_rows | intended_equal_all | active_intended_equal | intended_v61_touched | non_target_rows | non_target_v61_touched | non_target_audited | intended_supply_plus_vat | intended_line_total 
------------+---------------+--------------------+-----------------------+----------------------+-----------------+------------------------+--------------------+--------------------------+---------------------
         18 |            19 |                 18 |                    18 |                   18 |               1 |                      0 |                  0 |              52290000.00 |         51690000.00
(1 row)
```

즉 우려한 **NEW 과매칭은 합성 케이스에서 재현된다.** 영향은 비대상 금액 오수정이 아니라 target 동일성의 오인과 누락 은폐다. 현재 구현은 불변 식별자가 아니라 전표번호+품목명+모델+수량+금액으로 NEW를 인정하므로, 원 대상이 사라진 자리를 동일 전체 키의 다른 행이 채우면 구분할 수 없다.

### 5.3 합성 — 원 OLD와 동일 키 NEW 비대상이 함께 있는 경우

원 target OLD를 유지한 채 동일 전체 키의 NEW 비대상을 추가하면 target 하나에 2행이 매칭되어 모호성 가드가 트랜잭션을 롤백했다.

출력 원문:

```text
DATABASE newambiguousdb
SELECT 20
ERROR:  VAT correction target is ambiguous
CONTEXT:  PL/pgSQL function inline_code_block line 1 at RAISE
migration_exit=3

 audit_table_after_failure | intended_equal | non_target_new_rows | v61_touched 
---------------------------+----------------+---------------------+-------------
                           |              0 |                   1 |           0
(1 row)
```

이 형태는 과매칭을 성공으로 삼지 않고 안전하게 실패한다. 취약 표면은 원 대상이 더 이상 OLD/NEW로 매칭되지 않으면서 동일 전체 키 NEW 비대상이 정확히 하나 존재하는 경우다.

## 7. 새 결함 — V61 정정 후 `line_total` 의미가 현행 도메인과 반대로 바뀜

**BLOCKING 결함이 재현됐다.** fix는 실 DB 매칭을 위해 `old_line_total`을 현재 값으로 고친 것까지는 맞지만, UPDATE의 `new_line_total`도 원래 사용자 VAT 포함 총액으로 유지했다. 그 결과 정정된 19행만 `line_total = supply_amount + vat_amount`가 되고, 현행 도메인 계약인 `line_total = supply_amount`를 19/19 위반한다.

정확 19행 fixture에서 V61 적용 후 측정 원문:

```text

----------------+-----------------------------------------------+-------------------------------------+-------------------------------+-------------+------------+-----------------------
             19 |                                            19 |                                   0 |                            19 | 46990908.00 | 4699092.00 |           51690000.00
(1 row)
```

요청한 등식 자체, 즉 **정정 후 `공급가액 + 부가세 = 원래 사용자 총액`은 19/19 성립**한다. 그러나 그 원래 사용자 총액을 새 `line_total`에도 저장하는 것이 결함이다. 총액은 이미 `supply_amount + vat_amount`로 보존된다. `line_total`은 정정 후 공급가액 46,990,908원 합계여야 현행 전표 도메인과 같지만, V61은 VAT 포함 51,690,000원을 넣는다.

실 DB의 정정 전 target 19행도 현재 `line_total=supply_amount` 19/19이며 모두 V59 이전 legacy 도메인이다.

현재는 과다 계상 때문에 `supply_amount`와 그 별칭인 `line_total`이 함께 51,690,000원이다. 올바른 정정은 공급가액과 별칭을 함께 46,990,908원으로 내리고 VAT 4,699,092원을 더한 표시 총액 51,690,000원을 보존하는 형태여야 한다. V61은 공급가액만 내리고 별칭을 내리지 않아 한 라인 안에서 두 공급가액 컬럼이 서로 달라진다.

## 8. 최종 판정

**BLOCK — fix가 실 DB 0행 결함과 품목명 오정정은 해소했지만 새 금액 의미 회귀를 만들었다.**

1. 실 DB 새 조건은 정확히 OLD 19행, 고유 target 19개를 잡는다. 품목명 불일치는 0행으로, 직전의 3행은 실제 DB 명칭에 맞춰 포함됐다.
2. 직전 6개 fixture는 fix 보고서의 결과대로 모두 재현됐다. 품목명 다른 중복·치환 비대상은 감사/UPDATE 0행이다.
3. NEW 과매칭은 실 DB에는 0행이지만 합성에서 재현됐다. 원 대상이 빠진 자리를 동일 전체 키 NEW 비대상 하나가 채우면 성공하며 누락을 은폐한다. OLD 원 대상과 같이 있으면 모호성 가드가 롤백한다.
4. 요청한 `공급가액+부가세=원래 사용자 총액`은 정확 fixture에서 19/19 성립한다.
5. 그러나 `line_total`은 현행 slip 도메인에서 공급가액 별칭이다. V61 결과는 `line_total=supply_amount`가 0/19, `line_total=supply_amount+vat_amount`가 19/19로 반대다. 이 재현 결함 때문에 배포 승인할 수 없다.
6. PM의 30행은 target 19 + 중복가산 아님 7 + 원천 소실 확인불가 3 + source link 없는 legacy 공급단가 형태 1이다. 정상 7이 서명에 잡히는 이유는 서명 자체가 정상 저장 계약과 충돌하기 때문이다.
