## 각도 1 — XLSX 차단의 정상 경로 오차단 여부

### 판정

- 정상 데이터 오차단은 현재 배포 API에서 재현되지 않았다. 저장소의 실 관계 원본 XLSX 158행을 `relationFile`로 보낸 요청은 **HTTP 200**이었다.
- 다만 PR/R13 주장인 **`relationFile XLSX = 422`는 재현되지 않았고 실제 응답과 다르다. 증거 무결성 결함 1건**이다.
- 동일 응답은 `totalRows=2854`, `updated=2696`, `aliasImported=2853`, `rejectedNullName=1`, `skippedGroupCount=0`을 반환했다.

### 실 사용자 재현 절차

1. `docs/migration/ecount-data/raw/품목-Excel다운로드.csv`를 `itemFile`로 선택한다.
2. 이카운트 관계 원본 `품목관계리스트-Excel다운로드.xlsx`를 변환하지 않고 `relationFile`로 선택한다.
3. 실제 product-service 관리 API에 MASTER 헤더로 multipart POST한다.

```powershell
$item=(Resolve-Path -LiteralPath 'docs\migration\ecount-data\raw\품목-Excel다운로드.csv').Path
$rel=(Resolve-Path -LiteralPath 'docs\migration\ecount-data\raw\품목관계리스트-Excel다운로드.xlsx').Path
curl.exe -i -sS --max-time 120 -X POST 'http://127.0.0.1:8084/admin/products/imports/ecount' `
  -H 'X-Is-System-Master: true' `
  -H 'X-User-Id: 00000000-0000-0000-0000-000000000001' `
  -F "itemFile=@$item;type=text/csv" `
  -F "relationFile=@$rel;type=application/vnd.openxmlformats-officedocument.spreadsheetml.sheet" `
  -w "`nHTTP_STATUS=%{http_code}`n"
```

## 각도 3 — 비어 있지 않은 필드 승자와 양쪽 값 충돌

### 판정

**실 사용자 도달 결함 없음.** 현재 관계 158행과 현재 품목 2,854행을 실제 DB 결과에 조인한 결과, 한쪽만 업무값(non-zero)을 가진 숫자 필드는 **31개**였고 최종 Product에서 비어 있지 않은 값이 사라진 필드는 **0개**였다.

양쪽이 모두 non-zero이면서 서로 다른 숫자 필드와, 양쪽이 모두 비공란이면서 다른 품목구분 필드는 현재 실 데이터에 각각 **0개**다. 따라서 “양쪽 모두 값이 있고 다를 때 어느 쪽이 남는가”를 실 데이터 충돌 표본으로 관찰할 수 없었다. 현재 데이터에서 존재하지 않는 충돌을 생성하지 않았으며 DB 직접 쓰기도 하지 않았다.

### 관측 원문

```text
both_nonzero_conflicts=0
one_sided_nonzero_fields=31
one_sided_value_losses=0
item_type_both_nonblank_conflicts=0
```

참고로 raw 문자열만 비교하면 `0`과 non-zero를 모두 “문자열 비공란”으로 세어 13그룹 18필드가 달랐으나, 이 PR의 병합 계약과 구현은 숫자 `0`을 빈 값으로 취급한다. 실제 업무값 기준 재계수는 위의 31개 one-sided 필드이며 모두 non-zero 쪽이 최종값이다.

### 영향 건수

- 한쪽 non-zero 값 소실: **0/31필드**.
- 양쪽 non-zero 상충: **현재 입력 0필드**(실측 불가 모집단).
- 품목구분 양쪽 비공란 상충: **현재 입력 0필드**.

## 최종 판정

### 결함 1 — 증거 무결성

① **한 줄 요약**: R13의 `relationFile XLSX → 422` 주장은 현재 지정된 실 API에서 재현되지 않고 HTTP 200이며, 배포 artifact 시각도 R13 commit보다 앞선다.

② **실 사용자 재현 절차**: 각도 1의 multipart 명령으로 현재 raw의 item CSV와 관계 XLSX를 product-service `:8084`에 직접 업로드한다.

③ **관측 원문**:

```text
HTTP_STATUS=200
totalRows=2854 updated=2696 aliasImported=2853 rejectedNullName=1 skippedGroupCount=0

CONTAINER_CREATED=2026-08-03T10:58:34.025855244Z
IMAGE_CREATED=2026-08-03T10:58:31.274449565Z
/app/app.jar timestamp=Aug 3 19:57
R13 commit e169e3305 commitDate=2026-08-03 20:16:07 +0900
```

실행 image와 jar는 R13 commit보다 먼저 만들어졌다. 그러므로 “이 브랜치 build”인 것은 맞을 수 있어도 **R13 HEAD `e169e3305`가 배포됐다는 증거는 성립하지 않으며**, 현재 API로 R13의 422를 인용할 수 없다.

④ **영향 건수**: 상태코드 불일치 **1요청**. 해당 요청의 관계 **158행은 무시되지 않고 staging에 전부 적재**됐으므로 현재 배포에서 XLSX 오차단/관계 소실은 0행이다.

### 실 사용자 도달 결함 판정

- 관계 미명시 동명 병합: **0건**.
- 한쪽 non-zero 값 소실: **0건**.
- `updated=2,696`, `aliasImported=2,853`: **DB 독립 재계수와 일치**.
- `409 MIG2_ALIAS_DUPLICATE`: 실 관계 XLSX 포함 요청에서 **미재현(HTTP 200)**.
- 실 사용자 기능 결함은 이번에 재현하지 못했다. 단, 위 증거 무결성 결함 1건은 필수 보고한다.

## 이 라운드가 보지 않은 것

1. **R13 HEAD의 실제 배포 동작**: 배포 artifact가 R13 commit보다 앞서므로 `e169e3305`를 실행한 실 HTTP 422 경로는 보지 못했다. 재배포 금지 지시에 따라 교체하지 않았다.
2. **양쪽 모두 non-zero인 상충 필드의 실 데이터 승자**: 현재 품목 2,854행·관계 158행에는 해당 표본이 0필드라 관찰하지 못했다. 한쪽만 non-zero인 31필드는 전부 비어 있지 않은 쪽이 남았다.
3. **이 endpoint 밖 영역**: 주문 transform, 회계/재고/전표, 데스크톱 화면, 동시 임포트, 다른 raw 파일과 다른 DB 환경은 조사하지 않았다.
4. **미래·비현재 입력**: 현재 SHA-256 두 파일에 존재하지 않는 코드·관계·값 충돌은 조사하지 않았다.
