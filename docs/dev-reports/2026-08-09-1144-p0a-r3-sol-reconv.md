# PR #1148 R3 SOL 재수렴 — 표시 관례 통일 표면

## 머지 가부 판정

**머지 가능. 이번 범위에서 도달 가능한 신규 결함은 발견하지 못했다.**

R3의 production diff는 매출·매입 작성 폼의 import와 공급가/부가세/합계 JSX 표시를 `formatVatAmount(number)`에서 `fmtKrw(String(number))`로 바꾼 것뿐이다. 계산 함수 호출, submit request 구성, API 계약 및 서버 코드는 바뀌지 않았다. 표시를 수정 전으로 되돌린 뮤테이션은 두 회귀 테스트를 정확히 RED로 만들었고, 원복 뒤 다시 16/16 GREEN이었다.

### 사용자 요약과 다른 사실 — 먼저 보고

`34,783.04`는 저장 요청에 `totalAmount` 같은 직접 필드로 실리지 않는다. 실제 create 계약은 `qty: "0.08"`와 `unitPrice: "434788"`를 보내며, 서버 `VatCalculator.split(BigDecimal qty, BigDecimal unitPrice, taxType)`가 `lineTotal=34783.04`를 계산한다.

따라서 “`34,783.04`가 payload에 그대로 간다”를 문자 그대로 해석하면 **아니다**. 그러나 그 값을 결정하는 두 입력 문자열은 오염 없이 전송되며, mock/server 계산 결과는 정확히 `supply=31620`, `vat=3163.04`, `total=34783.04`다. 표시용 `String(totalSupply)` 등은 submit payload 생성에 사용되지 않는다.

## (a) 저장 payload 관측 원문

일시 probe에서 실제 React 폼을 렌더링하고 100% 배분 후 `mutationFn` 경계에서 전체 인수를 관측했다. 실 DB 쓰기는 하지 않았다.

### 매출 TAXABLE

```text
R3_PAYLOAD sales TAXABLE {"slipDate":"2026-08-09","partnerId":"11111111-1111-4111-8111-111111111111","partnerCode":"P-R3","partnerName":"R3 거래처","taxType":"TAXABLE","lines":[{"productCode":"SKU-R3","productName":"R3 품목","qty":"0.08","unitPrice":"434788","allocations":[{"sourceSlipId":"slip-OUTBOUND","sourceSlipNo":"2026/08/09-OUTBOUND","sourceLineId":"line-OUTBOUND","sourceLineNo":1,"allocatedQty":"0.08","allocatedAmount":"34783"}]}]}
```

### 매입 TAXABLE

```text
R3_PAYLOAD purchase TAXABLE {"slipDate":"2026-08-09","partnerId":"11111111-1111-4111-8111-111111111111","partnerCode":"P-R3","partnerName":"R3 거래처","taxType":"TAXABLE","lines":[{"productCode":"SKU-R3","productName":"R3 품목","qty":"0.08","unitPrice":"434788","allocations":[{"sourceSlipId":"slip-INBOUND","sourceSlipNo":"2026/08/09-INBOUND","sourceLineId":"line-INBOUND","sourceLineNo":1,"allocatedQty":"0.08","allocatedAmount":"34783"}]}]}
```

ZERO_RATED와 EXEMPT에서도 같은 probe가 매출·매입 각각 `qty:"0.08"`, `unitPrice:"434788"`, `allocatedQty:"0.08"`, `allocatedAmount:"34783"`를 관측했다. 달라진 것은 `taxType` 값뿐이었다.

서버 DTO도 `qty`와 `unitPrice`를 `BigDecimal`로 받는다. 서버 계산은 `qty.multiply(unitPrice)` 후 TAXABLE이면 VAT 포함 분리, ZERO_RATED/EXEMPT이면 전액 공급가·VAT 0이다. 새로 실행한 서버 `VatCalculatorTest` XML은 `tests="5" skipped="0" failures="0" errors="0"`이며 TAXABLE, ZERO_RATED, EXEMPT 및 round-trip을 포함한다.

### `String(totalSupply)` 정밀도

표시 변환에 쓰인 각 number에 대해 `Number(String(value)) === value`를 실제 검증했다.

```text
R3_STRING 34,783.04.supply number=31620 string=31620 roundTrip=31620
R3_STRING 34,783.04.vat number=3163.04 string=3163.04 roundTrip=3163.04
R3_STRING 34,783.04.total number=34783.04 string=34783.04 roundTrip=34783.04
R3_STRING 큰 금액.supply number=9090909090908 string=9090909090908 roundTrip=9090909090908
R3_STRING 큰 금액.vat number=909090909091 string=909090909091 roundTrip=909090909091
R3_STRING 큰 금액.total number=9999999999999 string=9999999999999 roundTrip=9999999999999
```

큰 값 `9,999,999,999,999`는 매출·매입 라인의 DB 계약 `precision=15, scale=2`, 즉 정수부 최대 13자리의 상한 사례다. 이 범위에서 `String()` 자체의 정밀도 손실은 없었다. 더 중요한 점은 이 문자열들이 표시 전용이고 request에는 `submittedQty`/`submittedUnitPrice`의 문자열이 별도로 들어간다는 것이다.

## (b) 폼 ↔ 목록 금액대별 대조

매출·매입 각각 실제 FormPage와 ListPage를 별도로 렌더링해 같은 계산 결과를 공급했다. 양쪽 모두 공용 `fmtKrw()`의 같은 출력이었다. 표는 두 계열 공통 결과다.

| 입력 VAT 포함 총액 | 폼 공급가 | 목록 공급가 | 폼 합계 | 목록 합계 | 판정 |
|---:|---:|---:|---:|---:|---|
| 330,000 | 300,000 | 300,000 | 330,000 | 330,000 | 동일 |
| 904,332 | 822,120 | 822,120 | 904,332 | 904,332 | 동일 |
| 34,783.04 | 31,620 | 31,620 | 34,783 | 34,783 | 동일 |
| 0 | — | — | — | — | 동일 |
| 1 | — | — | 1 | 1 | 동일 |
| 9,999,999,999,999 | 9,090,909,090,908 | 9,090,909,090,908 | 9,999,999,999,999 | 9,999,999,999,999 | 동일 |

`1`원 TAXABLE의 공급가가 `—`인 것은 공급가 0을 공용 formatter가 placeholder로 표시한 결과이며, VAT 1 + 공급가 0 = 합계 1이라는 서버 분리 규칙과 일치한다.

일시 probe 원문 요약:

```text
R3_FORM_LIST sales 34,783.04 supply=31,620 vat=3,163 total=34,783
R3_FORM_LIST purchase 34,783.04 supply=31,620 vat=3,163 total=34,783
R3_FORM_LIST sales 큰 금액 supply=9,090,909,090,908 vat=909,090,909,091 total=9,999,999,999,999
R3_FORM_LIST purchase 큰 금액 supply=9,090,909,090,908 vat=909,090,909,091 total=9,999,999,999,999
```

## (c) R1·R2 회귀

### VAT 이중 가산 없음

`vatRounding.test.ts`의 부분 배분 계약은 `total=608685`, `supply=553350`, `vat=55335`, `supply+vat=total`을 유지했다. `330000`도 합계가 `330000`이지 `363000`이 아니다. R3 production diff에는 계산식 변경이 없다.

### 서버 계산과 일치

- `qty=2.08`, `unitPrice=434775` → `supply=822120`, `vat=82212`, `total=904332`.
- `qty=0.08`, `unitPrice=434788` → `supply=31620`, `vat=3163.04`, `total=34783.04`.
- desktop `vatRounding` 11/11, mock response 계약 137/137, 서버 `VatCalculatorTest` 5/5가 모두 통과했다.

### 면세·영세율

일시 폼 probe에서 매출·매입 모두 선택한 `taxType`이 TAXABLE/ZERO_RATED/EXEMPT 그대로 payload에 들어갔고 qty/unitPrice는 바뀌지 않았다. 서버 test XML에서 `zero_rated_VAT_0_supply_전체`와 `exempt_면세_VAT_0_supply_전체`가 각각 통과했다. R3는 `taxType === 'TAXABLE'` 계산 분기와 저장 경로를 수정하지 않았다.

## (e) 계열 조사

직접 계열인 다음 네 화면은 같은 공용 formatter를 사용하므로 추가 불일치가 없다.

- `SalesAccountingSlipFormPage.tsx`
- `PurchaseAccountingSlipFormPage.tsx`
- `SalesAccountingSlipPage.tsx`
- `PurchaseAccountingSlipPage.tsx`

다만 저장소 전체 회계 금액 표시는 하나의 관례로 완전히 수렴해 있지 않다. 같은 양의 소수 금액 `34783.04`를 그리면 다음 별도 계열은 다른 표면을 만든다.

- `TaxInvoiceListPage.tsx`, `HometaxExportPage.tsx`: `Math.trunc` + `₩` prefix → `₩34,783`.
- `EstimateListPage.tsx`: `Math.trunc` + `₩` prefix → `₩34,783`.
- `VatReportPage.tsx`와 재무제표 계열: `Number.parseInt` + 음수 괄호 관례. 양수는 `34,783`, 음수는 `(34,783)`.
- `PartnerLedgerPage.tsx`: 정수 반올림이지만 음수는 `-34,783`.
- 공용 `currencyUtils.fmtKrw`: 정수 반올림, 0은 `—`, 음수는 `△ 34,783`.
- `PrintLayout.krw`: 정수 반올림이나 0은 `0`으로 표시한다.

이들은 직접 매출·매입 작성/목록 네 화면의 동일 레코드 경로가 아니고 R3가 수정한 함수도 호출하지 않으므로 이번 PR의 도달 결함으로 판정하지 않았다. 단, 구현 보고서의 “다른 목록·보고서가 이미 `fmtKrw()` 또는 별도 목록 표시 규약을 사용한다”는 문장은 사실이나, 저장소 전체가 단일 관례라는 뜻으로 읽으면 충분하지 않다.

## 도달 결함·비도달·이번 라운드가 보지 않은 것

### 도달 가능한 결함

없음.

### 비도달로 분류

- 정수부 14자리 이상 금액: 매출·매입 라인의 영속 계약은 `precision=15, scale=2`라 정수부 최대 13자리다. 이번 검증은 그 상한 `9,999,999,999,999`까지 포함했다.
- 음수/NaN 배분: allocation 폼의 slider는 0 이상이고 저장 대상은 양수 배분이며, 서버 allocation DTO도 `@Positive`다. 다른 회계 화면의 음수 formatter 차이는 존재하지만 이 작성 폼에서 생성되는 같은 레코드의 도달 경로가 아니다.
- 다른 문서 계열의 `₩` prefix·괄호·하이픈·삼각형 차이: 위 (e)에 목록화했으나 직접 네 화면의 경로가 아니며 R3 변경 표면 밖이다.

### 이 라운드가 보지 않은 것

- 금지 조건에 따라 실 DB 쓰기, 실제 서버 재배포, 실제 네트워크를 통한 영속 round-trip은 수행하지 않았다.
- 실제 브라우저/Electron 픽셀 캡처는 수행하지 않았다. React/jsdom에서 폼과 목록의 실제 render 문자열 및 mutation payload를 관측했다.
- 여러 라인을 한 전표에 합산하는 큰 누적 합계는 별도 조합으로 확장하지 않았다. 단일 라인 DB 상한, 지정 금액대, 기존 16/11/137 및 서버 5개 계산 계약을 검증했다.
