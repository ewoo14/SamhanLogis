## 최종 판정

**실 사용자 도달 결함 1건. 증거 무결성 불일치 1건.**

1. 두 Electron 앱의 renderer 날짜 버전과 Electron package/update-feed 버전이 분리돼 있다.
   날짜 버전만 바꾼 두 번째 릴리스부터 updater는 영구적으로 `not-available`을 반환한다.
   정책 서버가 `CRITICAL`을 반환하면 사용자는 앱에 들어갈 수도, updater로 새 버전을
   설치할 수도 없다.
2. 라이브QA의 수정 브랜치 배너 소멸과 `main`의 최초 timeout 재현은 PNG와 코드에
   부합한다. 그러나 `main`에서 `다시 확인`을 실제 클릭한 뒤에도 실패 배너가 유지됐다는
   실측은 같은 비교군의 renderer 코드 전이와 양립하지 않는다. 제품 결함이 아니라
   **증거 무결성 불일치**로 분리한다.

## 결함 1 — 날짜 버전만 바꾼 후속 릴리스는 자동 업데이트가 영구적으로 감지되지 않는다

### 실 사용자 경로

1. `DESKTOP` 또는 `AROLOGIS_DESKTOP` 날짜 버전 A를 설치한 사용자가 있다.
2. 운영자가 저장소의 정상 release wrapper로 날짜 버전 B를 빌드하고 generic HTTPS
   update feed에 게시한다.
3. 운영자가 정책 서버에 B를 `CRITICAL`로 등록한다.
4. 사용자가 A를 기동한다.
5. renderer의 `/app/version` 요청은 날짜 버전 A를 보내므로 정책 게이트가 사용을 차단한다.
6. Electron updater는 설치본과 feed의 고정 semver가 같다고 판단해
   `update-not-available`로 끝난다.
7. 사용자가 `업데이트 다시 확인`을 눌러도 같은 비교를 반복한다.

## 각도별 판정

### 1. 패키징된 실 사용자 앱의 동작

**개발 모드 timeout fix 자체는 패키징 앱의 updater 분기를 바꾸지 않았다.**

- `clients/desktop/src/main/auto-update.ts:81-103`
- `clients/arologis-desktop/src/main/auto-update.ts:69-90`

변경문은 네 곳 모두 `if (!app.isPackaged)` 내부다. `app.isPackaged === true`이면
기존과 동일하게 `checkForUpdates()`와 `quitAndInstall(true, true)`를 실행한다.
updater event wiring도 base와 동일하다.

다음 renderer/policy 파일은 merge-base와 HEAD의 blob이 동일하다.

```text

```

따라서 `c6c62045c`가 패키징 앱의 checking, download, error, timeout 전이를
직접 바꾼 결함은 없다. 다만 패키징 전체 버전 계약에는 위 **결함 1**이 있다.

### 2. 개발 모드 `INSTALL_CHANNEL`의 `not-available`

**실 사용자 도달 결함 없음.**

`DESKTOP` renderer가 `install()`을 부르는 production 경로는 `downloaded` 상태를
받은 경우뿐이다.

```text
clients/desktop/src/renderer/components/common/AppVersionGate.tsx:231-250
```

개발 모드 check는 `electron-updater`를 호출하지 않고 즉시 `not-available`로 끝나므로,
정상 사용자 조작으로 `downloaded → nonpackaged install`에 도달할 수 없다.

인위적으로 `downloaded` IPC를 주입하면 `setInstalling(true)` 뒤 `not-available`에서
`installing`이 해제되지 않는 상태를 만들 수 있다. 그러나 DevTools/IPC 인위 주입 외
사용자 경로가 없어 결함으로 집계하지 않았다.

### 3. 버전 게이트의 사용자 차단

**timeout fix로 새로 생기거나 넓어진 차단은 없다. 그러나 결함 1과 결합하면 실 사용자
영구 차단이 발생한다.**

지목된 `resolveDesktopUpdatePresentation()`은 production 호출처가 없고 테스트에서만
사용된다. 실제 차단은 다음 경로다.

```text
clients/desktop/src/renderer/version/versionCheck.ts:66-93
  CRITICAL → { kind: 'blocking' }

clients/desktop/src/renderer/components/common/AppVersionGate.tsx:390-465
  blocking modal, 계속 사용 불가
```

이 renderer 코드는 PR에서 바뀌지 않았다. 그러나 결함 1 때문에 정책 게이트는 날짜 버전으로
정상 차단하면서 Electron updater는 고정 semver 때문에 새 설치본을 감지하지 못한다.

### 4. 아로로지스 데스크톱 동일 fix

**동일 fix가 아로로지스 고유 renderer 동작을 바꾼 결함은 없다.**

두 앱의 main updater event/IPC 구조와 의존성은 같다. renderer 구조는 다르다.

- Samhan Desktop: 기동 gate, 30초 check timeout, 180초 download timeout,
  기동 중 완료된 다운로드만 자동 설치.
- 아로로지스: 본문을 updater 상태로 지연하지 않고 `downloaded`를 받으면 즉시 install.

아로로지스 개발 모드는
`clients/arologis-desktop/src/renderer/components/common/AppVersionGate.tsx:67-86`에서
상태 구독 후 check하고, main의
`clients/arologis-desktop/src/main/auto-update.ts:69-78`에서 `not-available`로 끝난다.
정상 사용자 경로에 새 차단이나 오류가 없다.

다만 아로로지스도 고정 package version `1.0.0` 때문에 **결함 1**의 영향을 똑같이 받는다.

### 5. 슬2 installer 판정

**“installer가 renderer `CURRENT_VERSION`을 다시 쓰지 않는다”는 좁은 판정은 맞다.
“installer가 버전 문자열 관점에서 추가로 증명할 것이 없다”는 전체 판정은 틀리다.**

보존 `app.asar`에는 날짜 버전과 `/app/version` query 참조가 정확히 들어 있다.
NSIS는 이 renderer 문자열을 다시 쓰지 않는다.

그러나 installer/update-feed 단계에는 서로 다른 버전 표면이 추가된다.

- packaged `app.getVersion()`
- `latest.yml.version`
- NSIS/Windows 표시 버전
- updater `UpdateInfo.version`

이 값들의 정본은 renderer 날짜 버전이 아니라 고정 `package.json.version`이다.
따라서 최종 installer/feed는 결함 1을 추가로 드러내는 필수 증거다.

### 증거 무결성 불일치 E-1 — `main`의 수동 재확인 클릭 결과

## 이 라운드가 보지 않은 것

- 최종 서명된 NSIS/portable installer를 새로 만들거나 설치하지 않았다.
