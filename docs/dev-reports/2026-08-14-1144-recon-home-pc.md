### 0.1 즉시 결론

“새로 만들기”가 출발점이 아니다. 다음 기반은 현재도 존재한다.

```text
slip_db.slips / slip_lines
  ↕ source_slip_id + source_slip_no + source_line_id + source_line_no
accounting_db.{sales|purchase}_accounting_slip_allocations
  → {sales|purchase}_accounting_slip_lines
  → {sales|purchase}_accounting_slips
  → tax_invoice_id
```

- 매출·매입 회계전표 엔티티·테이블·DRAFT 생성·POST 전이·목록/작성 화면·VAT 분리·N:M allocation·세금계산서 연결 구조가 이미 있다.

## 2. 축 A~E 현행 상태

### 축 A — 원장 반영

**채권은 판매전표 자체로 반영되지만 채무는 그렇지 않다.**

- 공통 원장 상태는 `CONFIRMED`, `DELIVERED`, `COMPLETED`, `INSPECTING`, `SHIPPING`이다.
- slip-service의 `/internal/slips/partner-ledger-sales`가 활성 OUTBOUND를 읽고 accounting-service가 이를 `SALE`로 fold한다. 회계전표/세금계산서가 없어도 반영된다.
- 최종 재측정 시각의 정본 OUTBOUND는 15건/9,033,420원이다. 알려진 8월 13일 QA 잔재를 제외하면 12건/5,424,320원이다. 이 금액은 `PartnerLedgerSalesResponse`와 같은 `supply+vat → unit_price_with_vat×qty → line_total+vat` 우선순위로 계산했다.
- INBOUND용 문서원장 endpoint와 PAYABLE 문서 타입은 없다. 같은 상태 기준의 INBOUND는 15건/8,781,199원이고, 그중 CONFIRMED는 4건/3,210,709원이다. 알려진 QA를 제외한 CONFIRMED INBOUND는 1건/909원이지만 거래처 코드 공백 때문에 현 생성 경로에서는 거절된다.
- 활성 회계 매출·매입전표와 일치하는 journal은 각각 0건이다. tax invoice와 일치하는 journal은 5건이다. 즉 현행 회계전표 POST는 원장 분개 원인이 아니고, 일반 세금계산서 발행이 분개 원인이다.

판정: **축 A 부분 충족 — 채권 즉시 반영 O, 채무 즉시 반영 X, 총계정원장 시점은 별도 결정 필요.**

### 축 B — 계산서 게이트

- 매출 묶음: `SalesAccountingSlipRepository.findPostedUnlinkedForBatchCandidates()`가 POSTED+미연결만 노출하고 연결 후 발행한다.
- 매입 수신: 화면이 POSTED 매입전표만 선택하고 서비스가 동일 거래처·동일월·미연결을 검증한다.
- 일반 세금계산서: 목록/이력 쿼리에 회계전표 연결 조건이 없고, 수동 생성 요청 DTO에 회계전표 식별자도 없다. `/issue`도 연결을 검사하지 않는다.
- 집PC 활성 `tax_invoices` 19건 중 활성 회계전표 연결 0건, 그중 ISSUED 12건이다.

판정: **축 B 불충족 — 두 특수 경로만 게이트이고 세금계산서 메뉴/일반 발행은 우회한다.**

### 축 C — 생성 경로 3종

| 경로 | 현행 |
|---|---|
| 전표 상세 1건 | **없음** |
| 외부 일괄 | **부분 존재** — 외부 화면·다중 allocation 선택은 있으나 결과는 회계전표 1건 |
| 일마감에서 바로 | **없음** — 기존 회계전표 집계만 수행 |

판정: **3종 중 명세대로 완성된 경로 0개.** 다만 공통 DRAFT 생성/검증 서비스는 이미 있어 세 표면 모두 그 위에 얹어야 한다.

### 축 D — 삭제 후 재생성

- 전용 API/FE 액션 없음.
- 엔티티 `voidSlip()`은 dead code이고 unlink가 없다.
- 삭제된 회계 매출전표 `2026/07/26-1027`의 헤더와 라인은 삭제 상태인데 allocation 1행은 활성이다. 그 allocation 원천 OUTBOUND `2026/07/27-64`도 `REJECTED`, 삭제 상태다.

판정: **축 D 없음.** 현재는 역처리도 삭제 후 재생성도 아닌 “정정 수단 없음”이다.

### 축 E — 권한

현행 “회계담당자”는 역할 코드 `ACCOUNTANT`, 사용자 라벨 `회계원`이다.

| 역할 | 매출/매입 회계전표 | 일마감 조회/실행 | 일마감 해제 |
|---|---|---|---|
| `ACCOUNTANT`(회계원) | VIEW/CREATE/UPDATE/DELETE | 가능 | 불가 |
| `MANAGER`(매니저) | VIEW/CREATE/UPDATE/DELETE | 조회·실행 가능 | 불가 |
| `MASTER` | VIEW/CREATE/UPDATE/DELETE | 가능 | 가능 |
| `SALES`(영업원) | VIEW만 | 불가 | 불가 |

Controller/route는 `accounting.sales-slip.accounting`, `accounting.purchase-slip.accounting`으로 정렬돼 있다. 다만 “회계담당자만”을 엄격히 뜻한다면 `MANAGER`/`MASTER`의 현행 쓰기 권한과 충돌한다. 일반적으로 MASTER 예외는 유지하되 MANAGER 허용 여부를 확정해야 한다.

### 3.2 QA 잔재 분리

알려진 QA로 분리한 식별자는 요청에 제시된 다음 범위다.

- 회계전표 `2026/08/13-5591`, `2026/08/13-6831`
- OUTBOUND `2026/08/13-1`~`-5`
- INBOUND `2026/08/13-1`~`-3`
- 거래처 `P-2026-0017`

현재 상태는 다음과 같다.

- OUTBOUND `-1/-2` DRAFT, `-3/-5` CONFIRMED, `-4` INSPECTING.
- INBOUND `-1/-2/-3` 모두 CONFIRMED.
- 회계 매출 `-5591`은 OUTBOUND `-3`에, 회계 매입 `-6831`은 INBOUND `-1`에 각각 allocation 1행으로 연결된 DRAFT다.
- 따라서 현재 집PC의 “매입 생성 가능 3건”과 활성 매입 회계전표/allocation은 실 업무 표본이 아니라 QA 잔재다.

### 3.3 고아 allocation 상세

```text
회계 매출전표 2026/07/26-1027  POSTED, is_deleted=true
  회계 라인                           is_deleted=true
  allocation                       is_deleted=false
  원천 OUTBOUND 2026/07/27-64       REJECTED, is_deleted=true
```

활성 allocation은 총 3행(매출 2, 매입 1)이고, 관측된 카디널리티는 양방향 모두 최대 1이다. 스키마는 N:M이지만 현재 집PC 표본에는 실제 N>1 사용이 없다.

### 3.4 조인 키 공백 위험

`partner_id`가 있는데 `partner_code`가 빈 활성행은 다음과 같다.

| 테이블/범위 | 건수 | 영향 |
|---|---:|---|
| `slip_db.slips` 전체 활성 | **9** | code 기반 검색/조인이 조용히 0행 가능 |
| 그중 INBOUND CONFIRMED | **1** | `PurchaseAccountingSlipCreateAttemptService`가 명시적으로 거절 |
| `accounting_db.tax_invoices` 전체 활성 | **13** | code 기반 세금계산서 검색/거래처 연결 누락 가능 |
| 활성 sales/purchase accounting slip 헤더 | **0** | 현재 활성 QA 회계전표 2건은 코드 채움 |

### 3.5 계정과목/분개 라이브 DB 불일치

- `chart_of_accounts`: 353행(3자리 77, 4자리 275, 기타 1).
- `journal_lines`: 309행, 전부 3자리.
- 관련 활성 라인: `110` 99, `201` 3, `210` 1, `255` 7, `401` 42. 4자리 `1089/2519/2539/2559/4019` 활성 라인은 0.
- 코드의 관련 읽기/쓰기 상수는 이미 4자리다.
- `flyway_schema_history` 최신은 V98이며 V101 적용 기록은 없다. 파일 `V101__unify_legacy_account_codes.sql`은 워크트리에 존재한다.

이 상태는 공유 스택을 건드리지 말라는 제약 때문에 정찰에서 수정하지 않았다. 향후 라이브 QA 결과는 “현재 배포 jar/DB”와 “워크트리 코드” 중 무엇을 검증한 것인지 exact 기준을 기록해야 한다.

## 4. 착수 순서 제안

### 1순위 — 정책·데이터 게이트 고정

먼저 개발책임자 결정 §5를 확정하고, 현재 고아 allocation 1건·UUID-only 9/13건·legacy 미연결 세금계산서 19건을 각각 `복구/예외/차단`으로 분류한다. 동시에 V101 미적용 집PC를 구현 기준선으로 쓸지 결정한다. 이 단계 없이 경로를 열면 조인 0행, 중복 발행, 재생성 불가를 그대로 확대한다.

### 2순위 — 공통 연결 read model과 eligibility

원 판매/구매전표 한 건에 대해 다음을 한 번에 답하는 읽기 계약을 먼저 둔다.

```text
생성 가능 여부 / 잔여 수량·금액 / 연결 회계전표번호·상태 / 세금계산서 연결상태
```

기존 allocation과 create-attempt 검증을 정본으로 사용한다. 이것이 생기면 전표 상세, 외부 일괄, 일마감, 삭제 후 재생성, 세금계산서 게이트가 같은 판정을 공유해 이후 작업이 쉬워진다.

### 3순위 — 생성 orchestration 1개로 3경로 수렴

기존 단건 create-attempt 위에 “원천 전표 1건→회계전표 1건” 명령을 만들고, 상세은 1회 호출, 외부 일괄은 N회 원자 호출, 일마감은 판단 결과와 함께 같은 명령을 호출하게 한다. 화면별로 VAT/거래처/과배분 로직을 복제하지 않는다.

### 4순위 — 삭제/재생성 수명주기

새 생성 경로를 넓히기 전에 DRAFT/POSTED/세금계산서 연결 상태별 삭제·연결해제·allocation 연쇄·재생성 멱등성을 완성한다. 현재 고아 allocation이 회귀 테스트 기준이다.

### 5순위 — 원장 인과와 채무 축

OUTBOUND 전용 문서원장을 타입 안전한 SALES/PURCHASE 두 축으로 나누고 INBOUND 채무 fold를 추가한다. 이후 회계전표 POST 분개와 세금계산서 분개 책임을 확정해 이중계상 0을 검증한다. 단순히 기존 OUTBOUND 쿼리를 INBOUND까지 넓히면 안 된다.

### 6순위 — 중앙 세금계산서 게이트와 표시 완성

기존 batch/inbound의 POSTED+미연결 검증을 일반 목록/이력/신규/발행/홈택스/출력에 공통 적용하고 legacy 19건 정책을 함께 반영한다. 마지막으로 회계전표 상세/목록 VAT/역방향 출처 표시와 권한을 닫는다.

## 5. 개발책임자 결정이 필요한 미결 항목

### Q1. 외부 “복수 생성”의 결과 단위와 실패 원자성

- **(a) 원 판매/구매전표 N건 → 회계전표 N건, 전부 성공/전부 실패** — 권장. 원천 1건별 삭제·재생성과 멱등성이 명확하다.
- (b) N건 → N건, 건별 성공/실패 결과표.
- (c) N건 → 회계전표 1건 합산. 현재 화면과 가깝지만 명세의 “복수 생성”과 어긋날 가능성이 높다.

### Q2. 문서원장과 총계정원장의 인과

- **(a) 거래처 문서원장은 원 판매/구매전표 즉시, 총계정원장은 회계전표 POST 분개; 세금계산서는 연결/발행만** — 권장. 축 A/B 분리를 지키면서 회계분개 시점도 설명 가능하다.
- (b) 문서원장과 총계정원장 모두 원 판매/구매전표 즉시, 회계전표는 세금계산서 게이트 전용.
- (c) 현행처럼 세금계산서 발행이 매출채권 분개를 만들고 회계전표 POST는 상태만 전이. 명세 인과와 가장 멀다.

Q2에서 (a)를 택하면 회계전표 삭제 시 총계정원장 분개 처리와 “역처리 아님” 문구의 관계를 별도 확정해야 한다.

### Q3. “삭제 후 재생성”의 물리 수명주기

- **(a) DRAFT는 soft-delete, POSTED는 `VOIDED` 처리 후 재생성; 연결 세금계산서는 먼저 취소·연결해제** — 권장. hard delete를 피하고 감사 흔적을 보존한다.
- (b) DRAFT/POSTED 모두 soft-delete 후 재생성, 분개는 별도 생성하지 않는 Q2-(b)와 결합.
- (c) 세금계산서 연결 전 DRAFT만 삭제 허용하고, POSTED/연결 후에는 별도 정정 승인 필요.

정본은 hard delete가 아니라 업무상 “기존 회계전표를 폐기하고 새로 생성”으로 해석해야 BaseEntity/soft-delete 규칙과 양립한다.

### Q4. 세금계산서 게이트의 메뉴 범위와 legacy 19건

- **(a) 목록·이력·신규·발행·묶음·수신·홈택스·출력 모두 중앙 게이트; 기존 19건은 legacy 읽기전용 예외** — 권장.
- (b) 발행/전송만 차단하고 목록에는 미연결 자료도 경고 표시.
- (c) 기존 미연결 19건을 소급 연결하거나 취소·재생성한 뒤 예외 없이 즉시 게이트.

### Q5. 일마감 `verified=false`에서 회계담당자 행동

- **(a) 회계전표 생성/마감 차단 후 할인율 또는 할인액을 정정·확인** — 권장. “적절한 금액인지 판단”을 실제 게이트로 만든다.
- (b) 경고 후 사유를 남기고 강제 진행.
- (c) 읽기 전용 경고만 유지. 현행과 같아 명세의 회계담당자 판단이 업무 상태로 남지 않는다.

### Q6. “회계담당자” 권한 범위

- **(a) `ACCOUNTANT`+`MASTER`만 생성·전기·삭제/재생성, `MANAGER`는 조회/승인 보조** — 권장.
- (b) 현행대로 `ACCOUNTANT`+`MANAGER`+`MASTER` 모두 생성·전기.
- (c) `ACCOUNTANT`만 쓰기, `MASTER`도 일반 경로에서는 제외.

### Q7. 무결성 잔재 처리 범위

- **(a) #1144 착수 전 고아 allocation 1건과 UUID-only CONFIRMED INBOUND 1건은 공식 보정/격리하고, tax_invoices 13건은 legacy 게이트 정책(Q4)에 포함** — 권장.
- (b) 전부 legacy 예외로 남기고 신규 데이터만 제약.
- (c) 별도 데이터 정합성 이슈로 분리하고 #1144는 읽기 차단만 추가.

## 6. 최종 판정

11개 규칙 분류는 **이미 되어 있음 1개(규칙 1), 다름 7개(3·5·6·7·8·9·10), 없음 3개(2·4·11)**다.

가장 중요한 차집합은 다음 두 문장이다.

```text
원장: OUTBOUND 채권은 이미 원 전표 즉시 반영되지만 INBOUND 채무 축이 없다.
계산서: batch/inbound에만 연결 게이트가 있고 일반 메뉴·발행은 우회한다.
```

따라서 첫 구현 단위는 새 엔티티/테이블이 아니라 **기존 allocation 위의 공통 연결 read model·eligibility와 수명주기 정책**이어야 한다.
