## 0. 결론

### 정본 재정의의 대상

재정의 대상은 **삼한 퍼블릭 데스크톱의 `/sales/estimates` 한 메뉴**다.

- 현재 업무 메뉴/라우트는 `견적서 관리` **1개**다. 사이드바와 판매 상단 sub-nav에 각각 링크가 있어 화면상 진입점은 2곳이지만 둘 다 `/sales/estimates`를 가리키므로 메뉴 두 개가 아니다 (`AppLayout.tsx:731-738`, `SalesSubNav.tsx:20-25`).
- 외부 웹은 `웹 종합견적서`, `웹 주문서` **2개**이며 데스크톱 메뉴가 아니라 별도 웹앱 링크다 (`SalesSubNav.tsx:28-45`).
- 현재 견적 성격의 저장소는 `estimates`, `quote_snapshots`, `partner_order_drafts` **3개**다.
- 이미 확정된 정본은 저장소 **1개(`estimates`)**이며, 구분해야 할 웹 유래 계열은 **2개(종합견적서 웹/주문서 웹)**다. 기존 데스크톱 작성분/과거 미분류까지 포함한 source enum의 총 개수와 실제 이름은 아직 정해지지 않았다.
- 별도 `주문서 관리` 메뉴(`/sales/partner-orders`)는 확정 주문을 처리하는 기존 메뉴다. #1092 때문에 없애거나 견적서 메뉴와 하나로 합친다는 결정은 찾지 못했다.

현재 `통합 목록 보기`는 이름과 달리 웹 저장분을 통합하지 않는다. 코드가 합치는 것은 `estimates`와 확정 주문 `partner_orders`다 (`EstimateListPage.tsx:133-160`, `estimateUnifiedListModel.ts:63-98`). 따라서 PR #1121의 통합 목록은 보존해야 할 선행 기능이지만, #1092의 **웹 저장분 통합 완료**로 세면 안 된다.

### 한 문장 정본

> 데스크톱 `견적서 관리` 한 메뉴가 종합견적서 웹과 주문서 웹에서 영구 저장한 견적을 `estimates` 한 정본에서 출처별로 모두 보여 주고, 담당·미리보기·원래 웹으로의 재개·판매전표/주문 생성 계보를 제공한다.

이 문장 중 `estimates` 단일화, 담당의 기본 의미, 계정 축, 금액 동결은 이미 결정됐다. 기존 데이터 이관 범위, draft 존치, 미리보기 표현, 웹 hand-off 규약, 전환 중복/계보는 아직 결정되지 않았다.

## 1. 3축 대조

### 1-A. 코드

#### 찾은 것

1. **데스크톱 메뉴는 이미 완전한 견적 CRUD 표면이다.**
   - 목록 `/sales/estimates`, 신규, 상세, 편집, 인쇄 라우트가 있다 (`clients/desktop/src/renderer/routes/index.tsx:490-552`).
   - 목록은 기본적으로 `GET /slips/estimates`를 페이지당 50건 조회하고 필터·삭제문서 복원·SSE 무효화를 유지한다 (`EstimateListPage.tsx:98-184`, `:478-610`).
   - #1175는 최신 상세 셸/디자인으로 바꿨으며 라우트나 저장 정본을 바꾸지 않았다. 머지 커밋 `ed3bf9784`, PR #1175.

2. **PR #1121 통합 목록은 `estimates + partner_orders`다.**
   - `Promise.allSettled`로 `listEstimates`와 `listPartnerOrders`를 전량 수집한다 (`EstimateListPage.tsx:133-162`).
   - 모델의 출처는 `'estimate' | 'order'`, 주문 행 이동은 `/sales/partner-orders/{orderNumber}`다 (`estimateUnifiedListModel.ts:4-21`, `:83-98`).
   - 이것은 `quote_snapshots`나 `partner_order_drafts`를 읽지 않는다.

3. **담당 축은 이미 구현돼 있다.**
   - `estimates.requester_id`가 담당이다 (`Estimate.java:145-146`, `:206-212`).
   - 데스크톱 전체 조회는 `EstimateService.list`, 웹 자기 담당 조회는 `listAssigned(requesterId, ...)`로 분리돼 있다 (`EstimateService.java:530-565`).
   - 담당 변경 API는 `PATCH /slips/estimates/{id}/owner`이며 `requester_id`만 바꾸고 BaseEntity `created_by`는 보존한다 (`EstimateController.java:235-242`, `EstimateService.java:556-565`).
   - 클라이언트 계약도 `listAssignedEstimates`와 `changeEstimateOwner`까지 있다 (`estimateApi.ts:259-278`, `:358-367`).
   - 주문서 계열을 이 endpoint로 바꾸려 하면 서비스 층에서 거부한다 (`EstimateService.java:557-562`).

4. **종합견적서 웹 저장분은 아직 `quote_snapshots`다.**
   - 웹 저장은 `/internal/estimates/snapshots`로 POST/PUT한다 (`clients/web/estimate-app/lib/code.js:2457-2490`).
   - 조회는 같은 snapshot endpoint이며 현재 `userEmail`을 전달하지 않는다 (`code.js:2493-2523`). 서버는 이메일이 없으면 전체 활성 목록을 반환한다 (`QuoteSnapshotService.java:56-70`).
   - JSON 상태와 공급가/부가세/합계를 저장하지만 미리보기 이미지는 V100에서 제거했다 (`V100__normalize_quote_snapshot_json_owner_totals.sql:4-28`).
   - 웹 내부 `applySnapshot` 복원은 있다 (`clients/web/estimate-app/views/index.ejs:17171`, `:18222`).

5. **주문서 웹 저장분은 아직 `partner_order_drafts`다.**
   - 웹 RPC가 저장/목록을 `/partner-orders/drafts`에 연결한다 (`clients/web/order-app/src/samhanApi.ts:360-368`).
   - draft는 거래처 코드별 본인 범위로 저장·조회되고 상세에 payload가 들어 있다 (`PartnerOrderDraftController.java:31-90`).
   - 30일 TTL 뒤 soft-delete하는 별도 저장 모델이다 (`PartnerOrderDraft.java:18-24`, `:51-57`; `PartnerOrderDraftService.java:134-154`).
   - 웹 내부 `applySnapshot` 복원은 있다 (`clients/web/order-app/index.html:9461`, `:9650-9653`).

6. **전환 기반은 일부 이미 있다.**
   - 정규 `estimates`는 `POST /slips/estimates/{id}/convert`로 판매전표를 만들고 `converted_slip_id`를 남긴다 (`EstimateController.java:197-202`; `Estimate.java:54-55`, `:326-347`).
   - 주문서는 별도 주문서 메뉴에서 `convert-to-slip`을 수행한다 (`PartnerOrderConvertController.java:29-33`, `:59-67`).
   - 종합견적서 웹은 현재 폼을 복원한 뒤 자체 slip bridge로 판매전표를 발행할 수 있다. 다만 snapshot/estimate와 생성 전표의 통합 계보는 없다.

#### 찾지 못한 것

- `estimates`에 종합견적서 웹/주문서 웹/데스크톱을 구분하는 `source`/`origin` 컬럼이 없다. 현재 스키마는 `estimate_no`부터 `requester_id`, BaseEntity 필드까지만 있다 (`V13__add_estimate.sql:26-56`).
- 두 웹앱이 신규 저장부터 `estimates`에 쓰는 코드가 없다. D5는 **결정됐지만 미구현**이다.
- `clients/web`에서 `/slips/estimates/assigned`를 호출하는 소비처가 없다. 검색 결과는 데스크톱 API와 테스트뿐이다.
- 종합견적서 웹은 auth-service 계정이 아니라 자체 HMAC 이메일 쿠키를 쓴다 (`clients/web/estimate-app/lib/auth-context.js:5-39`). D4의 직원 계정 통일은 **결정됐지만 미구현**이다.
- 데스크톱 특정 견적을 원래 웹앱의 특정 저장 상태로 여는 식별자·URL·1회용 hand-off token 규약이 없다. 현재 외부 링크는 웹앱 origin만 연다 (`SalesSubNav.tsx:37-45`).
- 출처별 담당 identity pool(직원 계정/거래처 계정)을 검증하는 `estimates` 도메인 가드가 없다. 출처 컬럼 자체가 없기 때문이다.
- 웹 저장분의 데스크톱 미리보기, 저장 당시 고정 레이아웃, 전송 후 이력 포함 여부를 구현한 코드가 없다.
- `quote_snapshots`/`partner_order_drafts`와 `estimates`를 잇는 FK 또는 migration marker가 없다.

## 2. 실제 데이터 확인 — 웹 저장분이 어떻게 갈라졌는가

2026-08-12 공유 개발 컨테이너 `samhan-postgres`에서 각 쿼리를 `BEGIN TRANSACTION READ ONLY`로 실행했다. INSERT/UPDATE/DELETE, API mutation, 로그인은 수행하지 않았다.

### 2-1. `slip_db.estimates` — 데스크톱 정규 견적

```text
전체 2,063
활성 45 / soft-delete 2,018
활성 partner_id 28/45
활성 partner_business_no 32/45
활성 requester_id 45/45 · distinct 3
활성 converted_slip_id 5/45
활성 생성시각 2026-07-17 01:12:44.271153 ~ 2026-08-10 02:30:12.86601
```

출처 컬럼은 없다. 이 45건을 웹 종합견적/웹 주문서/데스크톱 작성으로 소급 분류할 근거는 DB에 없다.

### 2-2. `slip_db.quote_snapshots` — 종합견적서 웹 저장분

```text
전체 4
활성 4 / soft-delete 0
활성 작성 이메일 distinct 1
활성 total_amount 채움 4/4
저장시각 2026-08-01 15:34:30.967 ~ 2026-08-08 01:38:19.071
```

`author_email`, `participant_emails`, `snapshot_state`, 합계 3종은 있으나 `estimate_no`, `requester_id`, source FK는 없다. 현재 웹은 이 저장소에서 직접 읽고 복원한다.

### 2-3. `partner_order_db.partner_order_drafts` — 주문서 웹 저장분

```text
전체 2,005
활성 11 / soft-delete 1,994
활성인데 이미 만료 0
활성 partner_code distinct 3
활성 생성시각 2026-07-30 00:01:47.272903 ~ 2026-08-07 19:35:01.817407
활성 만료시각 2026-08-29 00:01:47.262155 ~ 2026-09-06 19:35:01.817174
```

`partner_code`, 거래처별 `draft_seq`, `payload_json`, `expires_at`만 있으며 직원 담당/정규 견적번호/source FK는 없다. 30일 TTL이므로 D5의 영구 `estimates` 저장과 현재 동작이 다르다.

### 2-4. `partner_order_db.partner_orders` — 현재 통합 토글이 보여 주는 것

```text
전체 2,025
활성 4
활성 source_estimate_id 0/4
활성 partner_code distinct 3
활성 생성시각 2026-06-08 02:09:05.396744 ~ 2026-08-07 19:35:02.280728
```

이 4건은 주문서 웹의 “저장한 견적” 11건이 아니라 confirm된 주문 레코드다. 현재 통합 토글이 45+4를 보여도, 웹 저장 견적 4+11을 통합한 것은 아니다.

### 2-5. 사용한 집계 SQL의 핵심

```sql
BEGIN TRANSACTION READ ONLY;

SELECT COUNT(*),
       COUNT(*) FILTER (WHERE NOT is_deleted),
       COUNT(*) FILTER (WHERE is_deleted)
FROM estimates;

SELECT COUNT(*),
       COUNT(*) FILTER (WHERE NOT is_deleted),
       COUNT(DISTINCT author_email) FILTER (WHERE NOT is_deleted)
FROM quote_snapshots;

SELECT COUNT(*),
       COUNT(*) FILTER (WHERE NOT is_deleted),
       COUNT(*) FILTER (WHERE NOT is_deleted AND expires_at < CURRENT_TIMESTAMP)
FROM partner_order_drafts;

COMMIT;
```

## 3. 담당 축 — 이미 된 것과 아직 없는 것

### 이미 된 것

- 담당 값: `estimates.requester_id`.
- 원작성 감사: `BaseEntity.created_by`; 담당 변경으로 바꾸지 않는다.
- 데스크톱: 역할 등급과 무관하게 권한 있는 견적서 메뉴는 전체 견적을 본다.
- 웹 계약: `/slips/estimates/assigned`는 `X-User-Id == requester_id`인 행만 본다.
- 담당 변경: 데스크톱 상세의 직원 선택 UI와 PATCH API가 있다. UUID는 화면에 표시하지 않는다.
- 현재 별도 `partner_orders`는 견적 owner API로 바꿀 수 없다.

### 아직 없는 것

- 웹 종합견적 저장분과 웹 주문서 저장분이 `estimates`가 아니므로 위 담당 계약의 대상이 아니다.
- 종합견적서 웹은 assigned endpoint 대신 무필터 snapshot 조회를 쓴다.
- 주문서 draft의 소유자는 `partner_code`이고 `requester_id`가 없다.
- D5 완료 뒤 한 `estimates.requester_id`에 직원 auth account와 partner-auth account를 함께 담을 때 identity type/source로 검증하는 계약이 없다.
- 같은 출처 안의 담당 변경 허용 범위와, 직원 pool↔거래처 pool 교차 금지를 source 기반으로 강제하는 코드가 없다.

따라서 “담당 축 신설”은 새 컬럼을 다시 만드는 슬라이스가 아니다. **이미 있는 `requester_id` 담당 계약을 두 웹 저장분과 source-aware identity 경계까지 확장하는 작업**이다.

## 4. 웹 왕복 — 무엇이 왕복해야 하는가

정본 원문과 현재 코드에서 확정되는 왕복 단위는 다음이다.

```text
웹 종합견적서 저장
  → estimates에 금액·라인·웹 재개 상태·출처·담당 저장
  → 데스크톱 견적서 메뉴 전체 조회/상세/담당 변경/미리보기
  → 원래 웹 종합견적서로 같은 견적 재개
  → 저장 또는 판매전표 생성

웹 주문서 저장
  → estimates에 금액·라인·웹 재개 상태·출처·담당 저장
  → 데스크톱 견적서 메뉴 전체 조회/상세/담당 변경/미리보기
  → 원래 웹 주문서로 같은 견적 재개
  → 저장 또는 주문 생성
  → 주문서 메뉴에서 판매전표 전환
```

“왕복”은 soft-delete 복원이 아니다. 현재 목록의 `복원`은 삭제 취소이고, #1092의 “다시 불러오기”는 저장 상태를 원래 웹 폼에 적용해 작업을 이어가는 것이다.

현재 가능한 절반은 **웹 내부 저장→웹 내부 복원**이다. 없는 절반은 **웹 저장→데스크톱 정본→특정 웹/특정 문서 재개**다. hand-off URL/토큰과 source별 payload 계약은 미정이므로 구체 방식은 단정하지 않는다.

## 6. 아직 결정되지 않은 사항 — 개발책임자 질문 후보

아래는 코드로 업무 의미를 확정할 수 없다. 각 항목은 한 번에 전부 묻기보다 구현 직전 필요한 순서대로 최대 1~2개씩 올리는 것이 안전하다.

### Q1. 기존 저장분 이관 범위

- **A. 활성 웹 저장분만 이관**: 현재 `quote_snapshots` 4건 + `partner_order_drafts` 11건을 후보로 검증 후 `estimates`에 이관. 정본 전환은 빠르지만 soft-delete 4,012건의 보존 의미를 별도로 정해야 한다.
- **B. 웹 저장소의 활성+soft-delete 전부 이관**: 활성 15건과 draft soft-delete 1,994건을 후보로 삼아 복원 가능 이력까지 한 정본에 모은다. 대신 QA/만료/사용자 삭제를 구분하는 판별·검증 비용이 매우 크다.
- **C. 과거는 기존 저장소에 두고 신규만 단일화**: migration 위험은 가장 작다. 그러나 데스크톱 정본에서 기존 웹 저장분을 보려면 장기 dual-read가 남는다.

### Q2. 주문서의 작성 중 draft를 별도로 유지할 것인가

- **A. draft 폐기, 모든 저장을 `estimates`로**: 저장 버튼 하나와 영구 복원은 단순해진다. 작성 중 자동/임시 상태까지 정본 목록에 나타나는 정책이 필요하다.
- **B. draft 유지, 사용자가 “견적 저장”할 때만 `estimates` 승격**: 메뉴에는 의도적으로 저장한 견적만 보인다. draft와 정본 저장의 버튼/상태 차이를 사용자가 알아야 한다.
- **C. draft와 `estimates` 동시 저장**: 웹 복원 호환은 쉽지만 이중쓰기 실패·동기화·중복 제거 계약이 추가된다.

### Q3. 기존 `estimates` 45건의 출처 표시

- **A. 전부 `DESKTOP_LEGACY` 같은 단일 과거 출처**: 표시가 명확하지만 실제 유래를 증명하지 못한 값을 단정하게 된다.
- **B. `UNKNOWN`으로 보존**: 증거에 가장 정직하다. 화면과 필터에서 미분류 출처를 수용해야 한다.
- **C. 휴리스틱으로 소급 분류**: 더 많은 행을 분류할 수 있으나 현재 공통 FK/source가 없어 오분류를 검증할 정답이 없다.

### Q4. 미리보기의 정본

- **A. 저장 JSON/라인을 현재 렌더러로 재렌더**: 저장 용량이 작고 접근성이 좋다. 미래 디자인 변경 뒤 모양은 달라질 수 있다.
- **B. 저장 당시 PDF/이미지 고정본**: 당시 보이는 문서는 그대로다. 편집 가능한 데이터와 별도 blob 수명·보관이 필요하다.
- **C. 둘 다 저장**: D1 금액과 당시 외형을 모두 증명할 수 있다. 저장·생성 실패 처리와 비용이 가장 크다.

### Q5. 원래 웹으로의 재개 범위

- **A. 같은 출처 웹만**: 종합견적은 종합견적서 웹, 주문서 견적은 주문서 웹으로만 간다. 출처/담당 경계가 가장 명확하다.
- **B. 양쪽 웹 모두 선택 가능**: 활용도는 높지만 source 변환, 담당 identity 변환, 필드 손실 규칙이 새로 필요하다.
- **C. 같은 출처가 기본이고 명시적 복제만 타 웹 허용**: 원본 source는 보존되지만 복제 문서번호·계보·금액 parity 계약이 필요하다.

### Q6. 전송 후 이력도 견적서 메뉴 대상인가

- **A. 작성 중/저장 견적만**: “다시 불러오기” 의미가 일관되고 전송 이력은 기존 주문/전표 메뉴에 남는다.
- **B. 저장 견적+전송 후 이력 모두**: 한 메뉴에서 전체 계보를 보지만 행 타입과 가능한 액션이 달라진다.
- **C. 같은 화면의 별도 탭**: 혼동을 줄이지만 메뉴/조회 모델 범위가 커진다.

### Q7. 판매전표 재전환과 계보

- **A. 견적 1건당 판매전표 1건**: 현재 `converted_slip_id` 모델과 맞고 중복을 막는다. 재발행은 취소/복제 절차가 필요하다.
- **B. 견적 1건에서 여러 판매전표 허용**: 분할/재발행이 가능하지만 1개 FK를 lineage 테이블로 바꿔야 한다.
- **C. 재전환 시 견적 복제 후 새 전표**: 원본 단일전환은 유지된다. 복제번호·원본 링크·담당/금액 승계가 필요하다.

### Q8. 만료·삭제 이력의 사용자 의미

- **A. 만료 draft는 정본 대상 아님**: 현재 TTL 의미를 유지한다. “언제든 다시 불러오기”는 명시 저장 견적에만 적용된다.
- **B. 만료 draft도 정본 이력으로 보존**: 모든 작업 상태를 찾을 수 있으나 현재 soft-delete 1,994건의 노출/정리 정책이 필요하다.
- **C. 일정 유예기간 뒤 보관 탭으로 이동**: 복구 여지는 남지만 보관 수명과 검색 범위를 새로 정해야 한다.

| S7 미리보기·웹 hand-off | Q4·Q5에 따라 source별 미리보기와 원래 웹 특정 문서 재개용 단기 hand-off 계약/URL 구현 | Q4·Q5, S3·S4·S6 | 데스크톱에서 UUID 노출 없이 미리보기 후 올바른 웹/문서로 열리고 미권한·재사용 token이 거부되면 끝 |
| S8 전환 계보 | 견적→판매전표, 웹 재개 후 판매전표/주문 생성, 주문→판매전표의 source lineage와 Q7 중복 정책 구현 | Q6·Q7, S1 | 생성 결과가 원 견적에서 역조회되고 중복/복제 정책과 금액 parity가 자동 테스트로 고정되면 끝 |
| S9 전송 후 이력 표면 | Q6이 B/C일 때만 별도 타입/탭으로 추가. 작성 중 견적의 “다시 불러오기” 액션과 섞지 않음 | Q6, S8 | 각 행 타입의 조회·인쇄·재개 가능 액션이 구분되고 잘못된 복원 버튼이 나오지 않으면 끝 |

### 권장 실행 순서

`S1 → S2 → (S3, S4) → S5 → S6 → S7 → S8 → 조건부 S9`

S3와 S4는 S1·S2 뒤 서로 독립적으로 머지할 수 있다. S5는 앱 cutover와 분리해야 신규 저장 결함과 과거 이관 결함을 한 PR에서 섞지 않는다.
