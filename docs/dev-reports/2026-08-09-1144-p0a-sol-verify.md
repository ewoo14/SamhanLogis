## 1. 판정

### 도달 가능한 결함 1 — 실 4라인 부분 배분에서 화면 3값과 저장 3값이 1원 어긋난다

PR의 `splitVatInclusive` 자체는 전달받은 정수 총액에 대해 항상 `공급가 + VAT = 총액`을 지킨다. 그러나 폼은 **배분액 합계**를 표시 계산에 넣고, 제출 시에는 `unitPrice = round(배분액 합계 / 배분수량)`로 다시 압축한다. 서버 저장값은 `qty × unitPrice`에서 계산하므로 부분 배분에서 두 총액이 달라질 수 있다.

현재 실 DB에서 저장 조건을 충족하는 양수 OUTBOUND `2026/08/03-6`의 VAT 포함 라인 합계는 다음 4개다.

```text
641,480 · 963,040 · 118,580 · 16,000 = 1,739,100원
```

폼의 슬라이더를 네 라인 모두 52%로 두는 재현:

```text
라인별 배분액 = 333,570 + 500,781 + 61,662 + 8,320 = 904,333
배분수량 합계 = 2.08
제출 unitPrice = round(904,333 / 2.08) = 434,775
서버 lineTotal = 2.08 × 434,775 = 904,332
```

실행 원문:

```text
{"pct":52,"amount":904333,"qty":"2.08","unit":434775,
 "display":{"supply":822120,"vat":82213,"total":904333},
 "server":{"supply":822120,"vat":"82212.00","total":"904332.00"}}
```

따라서 화면은 `822,120 + 82,213 = 904,333`, 저장 응답은 `822,120 + 82,212 = 904,332`가 된다. 총액뿐 아니라 VAT 표시도 1원 다르다. 53%에서는 화면 `837,929 + 83,793 = 921,722`, 서버 `837,930 + 83,793 = 921,723`으로 공급가와 총액이 각각 1원 다르다.

이 제출 압축식은 PR 전에도 존재했으므로 “PR이 새로 만든 저장 회귀”라고 단정할 수는 없다. 그러나 PR 본문이 주장하는 표시·BE 분리 정합성과 부분 배분 계약은 현재 코드에서 완결되지 않았다. 실 데이터와 현재 UI 조작으로 도달 가능하다.

### 도달 가능한 결함 2 — 변경된 mock은 소수 원 단위 서버 값을 절사한다

매출·매입 mock은 이번 PR에서 `splitVatInclusive(Number(qty) * Number(unitPrice), ...)`를 호출한다. 이 helper는 첫 줄에서 `Math.trunc(totalAmount)`를 수행하지만 서버 `VatCalculator.split(BigDecimal qty, BigDecimal unitPrice, ...)`는 `qty × unitPrice`의 소수 2자리를 보존한다.

같은 실 4라인을 2% 배분하면 폼이 만드는 요청은 `qty=0.08`, `unitPrice=434788`이다.

```text
mock/helper total = trunc(0.08 × 434,788) = 34,783
mock            = 공급 31,620 · VAT 3,163 · 총액 34,783
실 BE BigDecimal = 공급 31,620 · VAT 3,163.04 · 총액 34,783.04
```

실행 원문:

```text
{"pct":2,"amount":34783,"qty":"0.08","unit":434788,
 "display":{"supply":31620,"vat":3163,"total":34783},
 "server":{"supply":31620,"vat":"3163.04","total":"34783.04"}}
```

따라서 “양쪽 mock이 BE split과 동일”이라는 계약은 fractional quantity에서 성립하지 않는다. 현재 slider가 `allocatedQty`를 소수 둘째 자리까지 만들므로 도달 가능하다.
