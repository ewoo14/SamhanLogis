# #896 구글 의존성 제거 — 이관 실행 계획

- 작성일: 2026-08-08
- 성격: 읽기 전용 계획 수립 라운드
- 목표: Google Sheets를 1회성 이전 다리로만 사용하고, 이관 뒤 DB 모드가 저장된 sheet 모드 기준선과 동일한 출력을 내게 한다.
- 이 문서는 코드 수정, DB 쓰기, Git 작업, Docker 재기동, Google Sheets 접근을 수행하지 않았다.

## 0. 실행 원칙과 완료 정의

1. 품목 정본은 `product_db`다. 운영 중 Google Sheets fallback과 동기화는 남기지 않는다.
2. 접미사 없는 탭과 `_단가인상` 탭은 구조 정본/가격 벌로 구분해 1회성 원시 스냅샷에 함께 보존한다. 런타임은 스냅샷이나 Sheets를 읽지 않는다.
3. 납품가는 한 의미로 통일한다. 중복 `납품가` 열 중 레거시 견적 계산에 실제 쓰이는 마지막 열을 이관 입력으로 삼고, 첫 열은 원시 증거에는 남기되 운영 가격 필드로 만들지 않는다. 이 원칙은 일마감의 첫 열 소비 계약에 대한 개발책임자 확인 전에는 확정 실행하지 않는다.
4. 세트 대표 납품가는 `products.delivery_price`/`price_history.delivery_price`에 둔다. 세트 내부 실내기·실외기의 문맥 절대값은 별도 납품가로 복제하지 않고 배분 가중치로 보존한 뒤 대표 납품가에서 재생성한다.
5. 세트 합계 보존, 고정부품 선차감, 실내·실외 배분비, 1,000원 반올림, 잔차 흡수는 #1143의 데이터 계약이 정본이다. #1143이 끝나기 전에는 금액 묶음을 적재하지 않는다.
6. 합격의 최종 정의는 같은 커밋의 저장된 sheet 골든과 DB 출력 `01`~`06`이 바이트 단위로 같고, DB 서버가 Google 자격증명 없이 기동·동작하는 것이다.
7. 기존 활성 행은 hard delete하지 않는다. 이관 배치 식별자와 감사 필드를 남기고, 되돌리기는 배치 soft delete/이전 값 복원으로 한다.

현재 불합격 기준은 카탈로그 값 2,326레코드, 세트 전개 681레코드, 카탈로그 가격 979레코드, 다중 문맥 가격 sheet 134그룹 대 DB 2그룹, 단가변동 sheet 215셀 대 DB 2셀이다. 이 수치를 묶음별 감소 게이지로 사용한다.

## 1. 작업 묶음과 의존 관계

### 1.1 의존 그래프

```text
P0 골든·적재계약 고정
 ├─> P1 #1143 배분비·반올림 스키마/계약
 └─> P2 1회성 Sheets 추출·불변 적재본 생성

P2 ─> P3 기초품목·스펙·견적노출 이관
P2 + P3 ─> P4 세트·구성품·특징·기본값·수량 이관
P1 + P2 + P3 + P4 ─> P5 납품가·가격벌·가중치·할인 이관

P3 + P4 + P5
 ├─> P6A 종합견적서 DB 전환
 ├─> P6B 주문서 DB 전환
 ├─> P6C 일마감·주문서 인식기 DB API 전환
 └─> P6D product-service Sheets 동기화 종료

P6A + P6B + P6C + P6D ─> P7 통합 parity·무자격증명 canary
P7 + 롤백 관찰기간 종료 ─> P8 Google 코드·설정·권한 제거
```

P6A~P6D의 구현은 독립적으로 진행할 수 있지만, 배포 게이트는 P7 하나로 묶는다. 한 소비자라도 Sheets를 읽으면 Google 의존성 제거가 끝난 것이 아니다.

### 1.2 P0 — 골든, 열 계약, 적재 manifest 고정

**옮기는 것과 착지점**

- 데이터 자체를 DB에 옮기지 않는다.
- 저장된 원시 입력의 파일명, 탭, 행 번호, 모델, 세트, 특징, 가격 벌, 원시 셀, SHA-256을 갖는 1회성 적재 manifest를 만든다.
- 검증기에는 `source + setModel + model + feature`와 `sector + setModel + partModel + feature` 문맥 키를 그대로 고정한다.
- 숫자 기준: GAS 수식 3,391건/실질 2,648그룹, 주 시트 27탭/코드 read 17탭, 카탈로그 참조 1,118모델, 가격 셀 8,094개를 입력 총계로 고정한다.
- 스펙은 시트 적재 대상 행 수가 기존 보고서에 없으므로 P0에서 `장비스펙/부속품스펙`을 새로 읽는 조사를 하지 않는다. 이미 확보된 17탭과 기준선 JSON에서 실제 소비되는 스펙 키·값 수를 먼저 세고 manifest 총계로 고정해야 한다.

**선행 조건**: 없음.

**검증**

- `items.json` 3,392건, `groups.json` 2,649그룹(종료 마커 각 1건 포함)이 파싱되고, DATA_OK 524/DATA_PARTIAL 551/CODE_ONLY 1,560/UNKNOWN 14 그룹 합이 유지돼야 한다.
- 저장된 골든의 `01`~`06` SHA-256을 승인 기준으로 복사하지 말고 직접 계산해 manifest에 기록한다.
- 이 단계는 금액에 직접 닿지 않지만 이후 모든 금액 검증의 기준을 고정하므로 manifest 한 건이라도 출처 좌표가 없으면 다음 단계로 가지 않는다.

### 1.3 P1 — #1143 세트 구성품 비중·반올림 데이터 계약

**옮기는 것과 착지점**

- `bundle_component`에 세트 문맥 배분 가중치 `allocation_weight`와 배분 참여 모드 `allocation_mode`를 둔다. 모드는 최소 `WEIGHTED_BODY`와 `FIXED_COMPONENT`를 구분해야 한다.
- 세트별 정책 테이블 `bundle_allocation_policy`를 신설해 `bundle_product_id`, `indoor_weight`, `outdoor_weight`, `round_unit`, `rounding_mode`, `remainder_policy`, `effective_from`을 둔다.
- 실내·실외 그룹 내부 가중치는 시트의 문맥값에서 도출하되 납품가로 저장하지 않는다. 판넬·리모컨·자재·가정용 벽걸이 등 고정부품은 `FIXED_COMPONENT`로 분리한다.
- 대상 규모: 비인상 복수값 141그룹/인상 132그룹 중 계산 가능한 싱글 본체 납품가 105그룹, 그중 현재 식 불일치 83그룹. 판정불가 36/27그룹 중 납품가 24그룹은 고정부품 또는 전역값 여부를 분류해야 한다.

**선행 조건**: P0. #1143의 소관과 데이터 계약 승인.

**실행 전 추가 측정**

- 이미 저장된 CSV와 DB 스냅샷 결과를 조인해 83그룹을 `1+1 덮어쓰기`, `복수 실내/실외 가중치`, `고정부품`, `한쪽 그룹 누락`으로 분류한다. 새 Google 접근은 하지 않는다.
- 각 세트에 대해 레거시 선택 옵션을 적용한 구성품 합계와 대표 세트 납품가를 계산해 필요한 비중과 잔차 수신 행을 도출한다.
- 22 일치그룹뿐 아니라 83 불일치그룹도 새 정책으로 정확히 재현되지 않으면 P5로 가지 않는다.

**검증**

- 단위 테스트: `고정부품 합계 + 실내 배분 + 실외 배분 = 세트 대표 납품가`가 모든 대상 세트에서 성립해야 한다.
- 경계 테스트: 0원 가중치, 복수 실내기/실외기, 한쪽 그룹 누락, 가정용 벽걸이, 1,000원 반올림, 마지막 행 잔차를 각각 고정한다.
- 저장된 141/132 그룹 재현기를 다시 돌려 `불일치 83 → 0`으로 만든다. 판정불가 그룹은 억지로 0 처리하지 않고 `FIXED_COMPONENT` 또는 비대상 근거가 전건 있어야 한다.
- 금액 접촉: **매우 높음**. schema test, 계산 단위 test, 골든 상세행 test의 3중 게이트를 적용한다.

### 1.4 P2 — 1회성 Sheets 다리와 불변 적재본

**옮기는 것과 착지점**

- 실행 시점에만 Google Sheets 17개 code-read 탭을 읽어 UTF-8 CSV/JSON과 SHA-256으로 고정한다. 27개 탭 중 코드가 읽지 않는 10개 탭은 범위를 넓혀 적재하지 않는다.
- 구조는 접미사 없는 `홈멀티`, `싱글 세트`, `싱글 구성품`, `상업멀티`, `상업멀티 구성`, `구형`에서, 가격 벌은 접미사 없는 5종과 `_단가인상` 5종 및 공통 `구형`에서 분리 추출한다.
- 각 정규화 레코드에 `import_batch_id`, `source_tab`, `source_row`, `source_variant`, `source_sha256`을 붙인다. DB staging 테이블은 운영 조회에 노출하지 않고 검증 후 도메인 테이블로 승격한다.
- 대상 규모: 정본 6탭 데이터행 3,060, 고유 참조 모델 1,118, 두 가격 벌 각각 2,226 `(모델, 가격필드)` 그룹.

**선행 조건**: P0. P1과 병렬로 추출기는 만들 수 있으나 도메인 적재는 P1 뒤에 한다.

**검증**

- 탭별 행 수, 헤더 위치, 중복 납품가 위치, 모델 채움률 3,060/3,060을 manifest와 대조한다.
- 추출 직후 원시 파일 SHA-256을 기록하고 이후 단계는 Sheets가 아니라 이 불변 파일만 읽는다.
- 같은 `import_batch_id` 재실행은 insert/update 0건이어야 한다.
- 금액 접촉: 원시 금액을 운반하므로 높다. 파싱 전 문자열과 파싱 후 정수를 함께 남기고, 빈칸과 0을 합치지 않는다.

### 1.5 P3 — 기초품목·스펙·견적품목 참조

**옮기는 것과 착지점**

- `products`: 시트 참조 고유 모델 1,118개의 모델, 품명, 단위, 출고가 외 비가격 기본 속성. 기존 공통 1,116개는 보완하고 시트 전용 2개는 식별 결정 뒤 insert 또는 alias 처리한다.
- `product_spec`: 모델별 규격·용량 등 실제 출력 스펙을 key/value로 적재한다. 정확한 신규/갱신 건수는 보고서에 없으므로 P0 manifest에서 측정한 수가 이 묶음의 승인 총계다.
- `product_estimate_exposure`: 견적 카테고리, 표시 순서, 노출 여부를 적재하고 `product_id` FK만 참조하게 한다. 시트 행을 별도 견적품목 마스터로 복제하지 않는다.
- 문맥별 출력 차이를 보존하기 위해 `product_estimate_exposure`에 `display_name_override`, `unit_label_override`, `capacity_text_override`, `spec_text_override`, `fixed_discount_rate_override`, `note_override`를 둔다. 세트 구성품 문맥 override는 P4의 `bundle_component`에 둔다.
- 현재 차집합: 마스터형 780행, 공통 779, 이름/단위 충돌 42, 카탈로그 sheet 전용 398문맥/DB 전용 103문맥, 값 차이 2,326레코드.

**선행 조건**: P2. 시트 전용 2모델 식별 결정.

**검증**

- DB 모드로 하네스를 캡처하고 `01-catalog-and-categories.json`을 비교한다.
- 이 묶음 종료 축은 카탈로그의 `시트에만 398 → 0`, `DB에만 103 → 0`, `값이 다름 2,326 → 0`이다. 가격 필드는 P5 전까지 별도 허용목록으로 분리하되 최종 파일 전체 일치는 요구한다.
- `products`/`product_spec`/`product_estimate_exposure` FK 누락, 활성 중복 모델, 사용자 화면 UUID 노출은 모두 0이어야 한다.
- 금액 접촉: 출고가 필드는 P5로 미루므로 낮음. 고정DC override는 계산에 영향을 주므로 P5 전까지 조회 경로에 연결하지 않는다.

### 1.6 P4 — 세트·구성품·특징·기본값·수량

**옮기는 것과 착지점**

- `products.product_type='BUNDLE'`, `bundle_mode`: 시트 세트 키 361개. 공통 308, 시트 전용 18, 이름 충돌 35를 처리한다.
- `bundle_component`: 원시 관계행 1,639/고유쌍 1,616을 `bundle_product_id`, `component_product_code`, `default_qty`, `qty_mode`, `component_kind`, `component_variant`, `is_default`, `spec_text`, `display_order`로 적재한다.
- 구성 문맥 출력 보존용으로 `display_name_override`, `unit_label_override`를 둔다. `component_variant`는 특징, `is_default`는 기본 전개를 뜻한다.
- 현재 관계 차이: 일치 1,563, 시트 전용 33, DB 전용 2, 수량 충돌 20. 특징은 일치 1,446, 시트 전용 5, DB 전용 2, 값 충돌 0.
- 시트의 싱글 구성품 `수량` 열은 빈칸/0뿐이므로 적재 근거로 쓰지 않는다. 반복행, 괄호 HP, 기존 DB 수량의 우선순위는 승인된 도출 규칙으로만 결정한다.

**선행 조건**: P2, P3. 18개 시트 전용 세트와 20개 수량 충돌 결정.

**검증**

- `02-set-expansion.json`: 시트 전용 171행, DB 전용 174행, 값 차이 681레코드가 모두 0이어야 한다.
- `03-options-features-defaults.json`: 시트 전용 5행, DB 전용 2행, 구성품 특징/표시 값 차이 1,447레코드가 모두 0이어야 한다.
- `04-quantity-derived.json`: 모델·수량은 유지하고 남은 명칭 차이 2셀도 0이어야 한다.
- 모든 BUNDLE에 기본 전개가 있고, 전개 오류가 싱글 0/226·상업 0/86이라는 sheet 골든 수준을 유지해야 한다.
- 금액 접촉: **중간 이상**. 관계·수량·기본 옵션은 소계를 바꾸므로 P5 가격 검증과 함께 재검증한다.

### 1.7 P5 — 납품가 하나, 가격 이력, 세트 내부 가중치, 할인

**옮기는 것과 착지점**

- `products.delivery_price`: 현재 대표 납품가 한 값.
- `price_history.delivery_price`: 비인상/인상 가격 벌의 대표 납품가를 유효일별 한 값으로 보존한다. 중복 납품가 두 열을 별도 컬럼으로 만들지 않는다.
- `bundle_component.allocation_weight`와 `bundle_allocation_policy`: 싱글 세트 내부 본체 가격 재생성. 문맥 절대값 141/132그룹을 구성품 납품가로 복제하지 않는다.
- 고정부품은 P1에서 확정한 `FIXED_COMPONENT` 계약에 따라 제품 대표가 또는 별도 정책값 하나를 사용한다. 같은 구성품이 문맥별로 다른 고정부품 값을 가져 대표가 하나로 재현되지 않는 24그룹은 확인 없이 덮어쓰지 않는다.
- `price_change_schedule`: 견적 기본 토글과 주문 납기일 전환을 보존한다. `_단가인상`이라는 이름이 실제 증가를 뜻하지 않으므로 30개 차이(증가 8/감소 22)를 그대로 이력으로 취급한다.

### 3.2 단계별 되돌리기

1. **적재 전**: 관련 테이블의 논리 백업 또는 DB snapshot과 활성 행 SHA를 만든다. 원시 적재본과 manifest는 불변으로 보존한다.
2. **P2~P5 적재 실패**: `import_batch_id`로 이번 배치 행만 soft delete하고, 갱신 전 값 journal로 `products`, `price_history`, 관계/정책 테이블을 복원한다. Flyway 자체를 역실행하지 않는다.
3. **P6 소비자 실패**: 해당 소비자만 이전 배포 이미지로 되돌리고, P8 전까지 제한된 롤백 기간에는 sheet 경로를 임시 재활성화할 수 있다. 이때 신규 DB 쓰기를 중지하거나 dual-write하지 않아 두 정본이 생기지 않게 한다.
4. **P7 canary 금액 이상**: 신규 견적/주문 저장을 즉시 차단하고 이전 앱 이미지+이전 DB snapshot으로 함께 복귀한다. 앱만 또는 DB만 단독 복귀하지 않는다.
5. **P8 이후**: Google을 롤백 수단으로 쓰지 않는다. 이전 DB snapshot과 이전 애플리케이션 이미지가 유일한 복구 수단이다. 따라서 P8은 관찰 기간과 개발책임자 승인 전 실행하지 않는다.

## 4. 확정하지 못한 것 — 개발책임자 확인 필요

아래는 기존 방향으로 답이 나온 사항을 되묻는 것이 아니라, 실행 시 데이터를 다르게 만드는 남은 업무 의미다.

1. **통합 납품가의 원천 열**: 견적/주문 계산처럼 마지막 `납품가`만 운영 정본으로 삼고, 일마감이 소비하던 첫 `납품가`는 폐기해도 됩니까? 권고는 **예**다. 첫 열의 업무 명칭은 확인되지 않았고 견적 기본 가격 계산에는 쓰이지 않는다. 다만 일마감 행별 판정 결과가 바뀔 수 있어 승인 없이는 폐기하지 않는다.
2. **#1143 배분 정책 범위**: 기존 공통 6:4/4:6을 기본값으로 두되, 83개 불일치 그룹을 재현하기 위해 세트별 `indoor_weight/outdoor_weight`와 구성품별 `allocation_weight`를 허용해도 됩니까? 권고는 **허용**이다. 공통비만으로는 절대차 10만원 초과 83그룹을 재현할 수 없다.
3. **고정부품 문맥값 24그룹**: 판넬·리모컨·자재·가정용 벽걸이의 문맥별 값이 제품 대표 납품가 하나와 다르면, (a) 세트별 고정 정책값으로 보존 / (b) 제품 대표 납품가로 통일 중 무엇입니까? 권고는 **(a)**다. (b)는 “레거시처럼 그대로 출력”과 충돌할 가능성이 높다.
4. **시트 전용 식별자**: `AP110RNPPHH1↔AP110RNPPBH1`, `PC6NUNK1N↔PC6NUNK1NW`는 오타 alias입니까, 별도 품목입니까? 이 결정 없이는 2모델/1관계의 insert와 alias가 갈린다.
5. **시트 전용 세트**: JHJ 14세트와 그룹명 4개를 모두 운영 BUNDLE로 적재합니까? 화면 출력 parity만 보면 필요하지만 실제 판매 세트인지 계산용 중간키인지 확인되지 않았다.
6. **구성 수량 충돌**: 시트 반복횟수와 DB `default_qty`가 다른 20쌍은 어느 쪽이 정본입니까? 시트 `수량` 열은 근거가 될 수 없다. 권고는 괄호 HP/반복행/실제 출력 기준선으로 20건을 개별 확정하는 것이다.
7. **싱글 할인 247건**: 원문과 정규화 값을 보존만 합니까, 아니면 새 견적 가격 계산에도 적용합니까? 기존 공개 견적 경로에서는 projection에서 빠져 기준선 가격에 영향을 주지 않았다. 권고는 이번 #896에서는 **보존만 하고 계산 연결은 별도 이슈**로 분리하는 것이다.
8. **가격 효력일 역할**: `2000-01-01`, `2026-04-01`, `2026-07-01`을 각각 baseline 저장일, 가격 이력 효력일, 앱 전환일로 유지하면 됩니까? 세 날짜를 하나로 합치면 견적 토글과 주문 납기일 결과가 달라진다.

이 질문의 답이 없는 항목은 해당 묶음의 차단 조건으로 유지한다. 그럴듯한 기본값으로 적재하지 않는다.

### 5.1 CODE_ONLY 1,560그룹

이번 이관은 데이터 원천을 옮기는 작업이지 레거시 계산·표시 엔진을 재작성하는 작업이 아니다. 따라서 다음 CODE_ONLY 그룹은 데이터화하거나 동작을 개선하지 않는다.

| 종류 | CODE_ONLY 그룹 | 이번에 하지 않는 범위 |
|---|---:|---|
| 수량 | 96 | 기존 파생 알고리즘 재설계, DOM 수량 엔진 통일 |
| 금액 | 124 | 카드/절삭 적용순서 등 기존 계산식 개선 |
| 할인 | 65 | 기존 할인 우선순위·UI 입력 방식 재설계 |
| 조건게이트 | 457 | 정규식 분류와 화면 상태 게이트 전면 데이터화 |
| 클램프 | 56 | `Math.max/min` 경계 정책 일반화 |
| 코드합성 | 208 | 모델코드 문자열 합성 297계열의 전면 룩업화 |
| 표시 | 373 | rowspan, 색, px, 인쇄 레이아웃, 라벨 재설계 |
| 기타 | 181 | 인증/외부 API/UI 잠금/날짜·환경설정의 광범위 리팩터링 |
| **합계** | **1,560** | |

예외는 두 가지뿐이다. DB 데이터 소비를 위해 필요한 adapter 교체와, 저장된 sheet 골든을 맞추기 위한 1:1 출력 라벨 매핑은 한다. 이때 계산 동작을 바꾸지 않는다.

### 5.2 명시적 범위 제외

- 코드가 읽지 않는 시트 10개 탭의 본문 이관
- 런타임 인자로 열리는 미배차/전표정리/알리고/임시 업로드 외부 스프레드시트의 내용 조사·이관
- DB에만 있는 1,967개 모델 전체의 정리 또는 ECOUNT 품목 세계 재설계
- unrelated UI/인쇄 디자인 개선, CODE_ONLY 정규식/클램프/문자열 합성의 전면 치환
- `할인`/`1WAY할인` 유효값 0건을 근거로 한 신규 할인 기능
- Google 제거와 무관한 일마감 업무 절차, 주문 인식 정확도, 기존 레거시 버그의 동시 수정
- P8 전 운영 sheet를 먼저 폐기하거나, parity가 0이 아닌 상태에서 DB 기본값이라는 이유만으로 전환 완료 처리
