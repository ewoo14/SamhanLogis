# PR #1066 / Issue #1065 R9 fix

일자: 2026-08-07  
대상: OUTBOUND 검수 결재선 접근 차단 및 검수 완료 후 후속 전이

## 1. 새로 가능해진 상태·역할 조합과 결과

정책은 `결재선 개인 OR 기존 정적 권한자`의 OR 판정으로 정리했다. 결재선 개인은
검수 후 `COMPLETED`, `SHIPPING`, `DELIVERED`에서도 상세를 재조회할 수 있고
`ship → deliver → confirm`을 이어서 수행한다. 결재선 밖 계정은 기존 정적 권한만
사용한다.

| 역할 | 결재선 | INSPECTING | COMPLETED 이후 |
|---|---|---|---|
| SALES | 안 | 상세 도달 가능, 검수 결재선이면 검수 가능 | 정적 권한으로 후속 전이 가능; 결재선 개인이면 동일하게 가능 |
| SALES | 밖 | 정적 매출 조회 가능, 검수는 기존 판정 유지 | 기존 정적 권한으로 후속 전이 가능 |
| ACCOUNTANT | 안 | 상세 200, 검수 버튼 활성, 검수 200 | `ship` 200 → `deliver` 200 → `confirm` 200, `CONFIRMED` 도달 |
| ACCOUNTANT | 밖 | 상세 API 403, 화면은 명확한 접근 차단 안내 | 권한 없는 강제 호출 403 |
| MANAGER | 안 | 정적 매출 조회 가능, 검수는 기존 판정 유지 | 기존 정적 권한으로 후속 전이 가능 |
| MANAGER | 밖 | 정적 매출 조회 가능, 검수는 기존 판정 유지 | 기존 정적 권한으로 후속 전이 가능 |
| DEVELOPER | 안 | 결재선 개인이면 상세 200 및 검수 가능 | 결재선 개인이면 후속 전이 가능 |
| DEVELOPER | 밖 | 상세 API 403, 화면은 명확한 접근 차단 안내 | 권한 없는 강제 호출 403 |

검증한 핵심 시나리오는 `ACCOUNTANT/결재선 안`의 `INSPECTING → COMPLETED →
SHIPPING → DELIVERED → CONFIRMED` 전 경로와 `DEVELOPER/결재선 밖`의 강제
`ship` 403이다. `SENT` 등 검수 후속 전이 범위 밖 상태는 결재선 상세 우회를
허용하지 않는다.

R8의 `/sales/:id` 후보 진입 구조는 유지하되, 상세 GET 403을 일반 로드 실패와
구분해 “이 전표를 조회할 권한이 없습니다. 담당 관리자에게 접근 권한을
요청하세요.”와 목록 복귀 버튼을 표시한다. 서버의 403 자체는 유지된다.

## 2. 제거·이동·개명한 식별자 grep 전수

- 개명한 식별자는 없다.
- `ship`/`deliver`의 `@RequirePermission(page="slip.transfer.process", UPDATE)`를
  제거하고, 컨트롤러의 `checkOutboundPostInspectionPermission`으로 이동했다.
- `confirm`의 OUTBOUND 판정도 동일 helper로 이동했다. INBOUND는 기존
  `purchases.slip.edit` 판정을 유지했다.
- 새 식별자 grep 확인:
  - `slipDetailErrorMessage`
  - `isOutboundInspectionApprovalStage`
  - `checkOutboundPostInspectionPermission`
- `SlipReadGuard mode="OUTBOUND" allowApprovalLineCandidate`와 기존
  `PermissionGuard` 정책 매핑은 제거·개명하지 않았다. 결재선 후보를 서버로
  전달하는 R8 축을 보존하기 위해 유지했다.
