# #1090 · #1140 정찰 보고서 — 분류 정본과 단가변동 명칭

> 조사일: 2026-08-12 KST  
> 조사 범위: 코드·마이그레이션·`clients/desktop`·웹 견적/주문, GitHub 이슈/PR 본문과 코멘트, 저장소 결정 문서, 로컬 공유 개발 PostgreSQL의 읽기 전용 `SELECT`  
> 변경 범위: 본 보고서만 생성. 구현 코드와 공유 DB는 변경하지 않았다.

## 0. 결론

1. **#1090의 최신 정본 결정은 “품목 분류 단독 정본”이다.** 이슈의 2026-08-07 마지막 코멘트에는 “레거시 모델코드 파싱 정본”이 적혀 있지만, 그보다 늦은 PR #1132의 2026-08-08 개발책임자 결정이 “08-06 분류 단독 정본을 유지하고 08-07 모델코드 방향은 채택하지 않는다”고 명시했다. 현재 트랙 문서도 분류 단독 정본을 재논의 금지로 기록한다.
2. **그 결정은 아직 6종 정액 할인 판별에 구현되지 않았다.** 현재 실제 계산에는 레거시 모델코드 파싱과 `products.discount_flags`가 함께 살아 있다. `classification`에는 6종 매핑 컬럼/테이블이 없고, PR #1132가 추가한 `classification.fixed_discount_rate`는 0~100 퍼센트인 **고정DC율** 축이다. #1090의 거래처별 옵션 정액 6종과 다른 축이다.
3. 활성 품목 2,982건 실측에서 레거시 파싱 발화는 **331건**, `discount_flags <> '000000'`은 **8건**, 교집합은 **0건**이다. 분류가 L/M/S 모두 없는 품목은 **1,963건**, 그중 레거시 파싱 발화 품목은 **113건**이다.
4. **#1140의 표기 정본 “단가변동”과 의미 보존(`새 기본값 = NOT default_pre_change`)은 이미 결정됐다.** 저장 위치도 미결정이 아니다. `product_db.price_change_schedule`의 카테고리별 전역 4행이다. 사용자별·거래처별 저장소가 아니다.
5. #1140에서 실제 미결정은 두 가지다. 첫째, 코드/DB 계약까지 어떤 물리 이름으로 바꿀지다. 둘째, `oldProducts`는 2026-07-11에 “구형 인상 미적용”으로 확정됐으나 2026-08-08 #1140에서 “토글 신설” 지시가 내려와 충돌한다. 현재 구형 활성 37품목의 2000-01-01 인상 전 baseline은 **0건**이므로 업무 의미를 추론해 연결할 수 없다.
6. **두 이슈를 하나의 원자적 구현 슬라이스로 묶을 근거는 성립하지 않는다.** 같은 거대 파일 `clients/web/estimate-app/views/index.ejs`와 `clients/web/order-app/index.html`, 같은 product-service 모듈을 건드릴 가능성만 있다. 논리 함수·Desktop 화면·엔티티·DB 테이블은 다르다. 충돌 조정용 상위 트랙은 가능하지만, 독립 머지 슬라이스로 분리해야 한다.

## 6. 아직 결정되지 않은 사항 — 선택지와 결과

## 6.1 #1090 — 분류 정본의 물리 표현

“분류가 정본”은 결정됐지만 한 분류 노드가 6종 중 무엇을 뜻하는지는 저장되지 않는다.

### 선택지 A — 분류 노드에 6종 bitset/enum 집합

- 결과: 조회가 단순하고 기존 6자리 계산 입력과 직접 대응한다.
- 대가: bit 순서 계약과 다중 선택 허용 여부를 스키마/DTO에 고정해야 한다.
- `products.discount_flags`는 정본이 아니라 파생 캐시 또는 폐기 대상으로 명시해야 한다.

### 선택지 B — 분류 노드와 6종 타입의 별도 매핑 테이블

- 결과: 타입 추가/설명/감사 이력이 명확하고 DB 정규화가 된다.
- 대가: 조회 join과 관리 UI가 늘고, 한 분류에 여러 타입을 허용할지 unique 계약이 필요하다.

### 선택지 C — 분류 노드에 6개 명시 컬럼

- 결과: 각 타입의 의미가 SQL에서 가장 명확하고 bit 순서 오독이 없다.
- 대가: 타입 추가 시 migration이 필요하고 컬럼 수가 늘어난다.

세 선택지 모두 **분류 단독 정본 결정은 지킨다.** 품목별 fallback/override를 다시 제안하지 않는다. 그 갈래는 앞서 단일 진실원 선호로 물린 기록이 있다.

### 별도 결정: 113개 미분류 발화 품목

1. 분류를 사람이 확정한 뒤 cutover
   - 결과: 정본 원칙을 지키며 금액 불변 대조 가능
   - 대가: 113건 업무 분류 입력이 선행
2. cutover에서 제외하고 차단 상태로 유지
   - 결과: 오분류는 막지만 이중 계산축이 과도기 동안 남음
   - 대가: 완료 정의가 늦어지고 화면/서버 불일치 위험이 지속

모델코드로 분류값을 자동 확정하는 선택지는 개발책임자의 “모델명 체계 변경 시 서버 수정” 문제를 되살리므로 후보에서 제외한다.

## 6.2 #1140 — 내부 boolean/DB 계약 이름

상위 화면 용어 `단가변동`과 의미 보존은 결정됐지만 물리 계약은 미정이다.

### 선택지 A — DB/API는 `default_pre_change` 유지, 화면에서만 반전

- 결과: migration 위험이 가장 작다.
- 대가: 화면 `단가변동=true`와 API/DB `defaultPreChange=false`가 영구 반대라 유지보수 오독 위험이 남는다.

### 선택지 B — `default_price_change_enabled` 계열로 rename하고 값을 원자적으로 반전

- 결과: 화면·API·DB boolean이 같은 의미가 된다.
- 대가: product-service, Desktop, estimate-app, accounting-service 소비처를 한 번에 바꾸고 mixed-version 배포를 막아야 한다.

### 선택지 C — boolean 대신 명시적 variant enum

- 후보 값은 기존 원문만 사용해 `PRE_CHANGE` / `POST_CHANGE` 또는 한국어 표기 `변동 전` / `변동 후`로 올린다.
- 결과: NOT 반전과 true/false 오독이 사라진다.
- 대가: schema/API/UI 변경량이 가장 크다.

## 6.3 #1140 — 화면 exact 명칭 후보

상위 기능명은 **단가변동**으로 고정한다. 토글/상태 문구는 다음 중 판단이 필요하다.

1. `단가변동` OFF/ON
   - #1140 지시와 정확히 일치
   - OFF/ON이 어느 가격인지 보조 설명 없이는 모호할 수 있음
2. `변동 전 단가` / `변동 후 단가`
   - PR #688의 개발책임자 요구 대조 원문에 존재
   - “인상”에 한정되지 않아 상위 용어와 정렬
3. `인상 전 단가` / `인상 후 단가`
   - 현재 코드·화면과 가장 가깝고 migration 위험이 작음
   - #1140의 “단가변동으로 통일” 지시를 부분적으로만 이행

`인상단가`는 live GAS 관찰값일 뿐 확정 용어 기록을 찾지 못했으므로 후보로 추천하지 않는다.

## 6.4 #1140 — oldProducts 충돌 해소

### 선택지 A — #1140이 #777을 폐기: 구형 baseline을 먼저 만든 뒤 기능 토글 신설

- 결과: 실제 전/후 가격을 선택하는 토글이 된다.
- 대가: baseline 원천을 별도로 결정해야 한다. 현재 37품목에 2000-01-01 행은 0건이다.

### 선택지 B — #777 유지: 구형은 `대상 아님` 유지

- 결과: 현재 코드와 데이터가 일치하고 금액 변화가 없다.
- 대가: #1140의 “oldProducts도 토글” 지시를 취소/정정해야 한다.

### 선택지 C — 토글 UI를 먼저 보이되 비활성화하고 데이터 준비 상태를 표시

- 결과: #1140의 화면 방향은 보이면서 오동작을 막는다.
- 대가: 작동하지 않는 토글은 사용자 오해를 만들 수 있고, 완료가 아닌 과도기 상태다.

업무 의미는 코드로 확정할 수 없으므로 개발책임자 판단이 필요하다.

### 1140-S3. oldProducts 데이터/동작

- 범위: §6.4 결정 후 별도 진행. baseline을 만들 경우 37품목 데이터 출처·migration·토글·회귀 포함.
- **끝 조건:** 구형 토글이 실제 두 가격을 선택하거나, 구형 비대상 결정이 UI/API/DB에서 모순 없이 한 가지로 표현된다.

### 1140-S4. 내부 잔재 정리

- 범위: `*_INC`, `priceIncData`, `PRICE_DEFAULT_VARIANT`, `_단가인상` 호환 이름의 유지/폐기 경계를 문서화하고 가능한 내부 rename 수행.
- **끝 조건:** 같은 identifier가 “인상 전”과 “인상 후”를 반대로 뜻하는 경로가 0개이고 mixed-version 계약 테스트가 통과한다.

### 권장 실행 순서

`1090-S1`과 `1140-S1`은 서로 독립이다. 거대 웹 파일 충돌을 줄이려면 **1090-S4와 1140-S2를 동시에 진행하지 않고 순차 머지**한다. 하나의 통합 PR로 묶을 필요는 없다.

## 8. 재현용 읽기 전용 SQL

핵심 집계는 다음 조건으로 수행했다.

```sql
-- 모집단
FROM products
WHERE is_deleted = false AND status = 'ACTIVE';

-- 저장 축
SELECT discount_flags, count(*)
FROM products
WHERE is_deleted = false AND status = 'ACTIVE'
GROUP BY discount_flags;

-- 스케줄 4행
SELECT category, effective_date, default_pre_change
FROM price_change_schedule
WHERE is_deleted = false
ORDER BY category;

-- 구형 baseline
SELECT count(*)
FROM products p
WHERE p.is_deleted = false
  AND p.status = 'ACTIVE'
  AND p.product_category = 'OLD'
  AND EXISTS (
    SELECT 1 FROM price_history h
    WHERE h.product_id = p.id
      AND h.is_deleted = false
      AND h.effective_date = DATE '2000-01-01'
  );
-- 결과: 0
```

레거시 6종 집계는 `slipDiscount.ts:112-130`의 zero-based 문자 위치를 PostgreSQL `substr`의 one-based 위치로 정확히 옮겼다. 6종 합계가 331이고 복수 플래그는 관측되지 않았다.

## 9. 라운드 종료 점검

- `git ls-files --deleted`: 빈 출력 — 삭제된 추적 파일 없음.
- `git diff --name-status origin/main...HEAD`: 기존 트랙 문서 추가만 관측했으며, 본 라운드에서는 이 보고서 외 구현 파일을 수정하지 않았다.
- `git ls-files --error-unmatch tools/.s24-build-only/build/deep/tracked-writer.mjs`: 경로가 정상 반환됨 — **추적 파일 존재, 삭제되지 않음**.
