# PR #1057 / 이슈 #874 R10 — 전표 행 순서 보존과 레거시 `_zone` 대조

## 순서 필드 존재 확인

`[실데이터/로컬 read-only]` accounting 원천 3개 라인 테이블 모두 실제 순번 컬럼을 가진다.

| 원천 | Java 파일:줄 | DB 컬럼 | 제약/의미 |
|---|---|---|---|
| 세금계산서 | `TaxInvoiceLine.java:52-53` | `tax_invoice_lines.line_no` | `nullable=false`, 1-based 표시 순번 |
| 매출전표 | `SalesAccountingSlipLine.java:37-38,64-80` | `sales_accounting_slip_lines.line_no` | `nullable=false`, `(slip_id,line_no)` unique |
| 매입전표 | `PurchaseAccountingSlipLine.java:37-38,61-75` | `purchase_accounting_slip_lines.line_no` | `nullable=false`, `(slip_id,line_no)` unique |

read-only SQL 결과:

```text
tax_invoice_lines              active_rows=22 line_no_filled=22 parent_docs=14 docs_with_null_line_no=0
sales_accounting_slip_lines    active_rows=0  line_no_filled=0  parent_docs=0  docs_with_null_line_no=0
purchase_accounting_slip_lines active_rows=0  line_no_filled=0  parent_docs=0  docs_with_null_line_no=0
```

세금계산서 실데이터의 `line_no` 채움률은 22/22=100%이며, 나머지 두 원천은 active 행이 0이라 채움률을 규칙 증거로 산정할 모집단이 없다.

## 전달 경로 확인 — 순번은 저장되지만 정렬 계약은 없음

`[실데이터/로컬 read-only]` 현재 DB에서 세금계산서 14개 문서의 `array_agg(line_no ORDER BY id)`와 `array_agg(line_no ORDER BY created_at,id)`는 `array_agg(line_no ORDER BY line_no)`와 모두 일치했다. 관측값은 `id_order_diff=0`, `created_order_diff=0`이다. 매출·매입은 active 문서가 0개라 비교 모집단이 없다. 이 결과는 현재 데이터의 우연한 일치이며, JPA가 그 순서를 보장한다는 증거는 아니다.

`[DEV-SEED/단위 fixture]` 전달 코드의 보존 여부는 다음과 같다.

- `TaxInvoice.java:190-192`, `SalesAccountingSlip.java:73-74`, `PurchaseAccountingSlip.java:72-73`: 모두 `List<...> lines = new ArrayList<>()`이지만 `@OrderBy("lineNo ASC")`가 없다.
- `TaxInvoiceRepository.java:105-113`: `findIssuedInRange`는 `supplyDate,taxInvoiceNo`만 정렬하고 child line 정렬을 선언하지 않는다.
- `SalesAccountingSlipRepository.java:22-34`, `PurchaseAccountingSlipRepository.java:22-34`: `@EntityGraph(lines)`와 부모 `slipNo ASC`만 선언하며 line 정렬이 없다.
- `MonthEndCloseService.java:231-242,282-287,319-325`: `for (.. : ti/slip.getLines())` 순서로 `setPool`에 append한다. 중간에 set/map으로 line 순서를 재정렬하지는 않지만, 입력 List 자체의 순서 계약이 없으므로 레거시 전표 순서 보존을 확정할 수 없다.
- `MonthEndCloseService.java:632-641`: 이후 rows도 `setPool`을 filter/map할 뿐이고 현재 `RiUsageDecision`은 순서를 입력으로 받지 않는다.

결론: 원본 모델에는 순번 필드가 있고 값도 저장되지만, `line_no` 기준 정렬이 repository/entity/서비스 경계에 명시돼 있지 않다. 따라서 현행이 레거시 전표 행 순서를 **보존한다고 판정할 수 없다**. `id` 또는 `created_at` 순서를 순번의 대체값으로 추측해 구현하지 않는다.

## 개발책임자 판단 항목

이번 라운드는 순서 보존 여부 판정에서 멈춘다. 다음 중 제품 결정을 받아야 R10 구현을 시작할 수 있다.

1. 각 원천 `lines` collection과 조회 경로에 `line_no ASC` 정렬 계약을 추가해 레거시 `_zone` 순서를 보존한다.
2. 저장된 `line_no`를 사용하지 않고 현재 순서 무관 판정을 의도된 이탈로 승인한다.

현재 변경은 이 판단 전에는 없다. 따라서 R6/R8의 scope 격리·교차 행 의존·Q 자기 판정·두 main 집합 분리를 추측한 순서로 훼손하지 않았다.
