# #1035 slip-service 기동 시 창고 UUID 실재성 검증 구현 보고서

## 1. 시작 및 설계

- 정찰 보고서(`docs/dev-reports/2026-08-01-1035-recon.md`)를 먼저 확인했다.
- 기존 `WarehouseCodeMapper` 경계에서 기동 시 읽기 전용으로 `warehouses`의 실재성·창고코드 일치성을 검증한다.
- 기존 메인 `JdbcTemplate`만 사용하며 DataSource, JdbcTemplate, 트랜잭션 매니저 구성을 추가하거나 변경하지 않는다.
- 검증 실패 메시지는 창고코드만 포함하고 UUID 원문은 포함하지 않는다.
- 테스트가 창고 데이터를 생성하지 않도록 단위 테스트에서는 조회 결과를 주입하고, 기존 slip-service 전체 테스트로 회귀를 확인한다.

## 2. RED — 기동 시 오주입 조용한 통과 재현

추가한 테스트: `WarehouseCodeMapperStartupValidationTest.실재하지_않는_창고_UUID는_창고코드를_알리는_기동_실패가_되어야_한다`

실행:

```text
.\gradlew.bat :services:slip-service:test --tests com.samhanair.logis.slip.publish.WarehouseCodeMapperStartupValidationTest
```

RED 원문:

```text
1 test completed, 1 failed
java.lang.AssertionError:
Expecting code to raise a throwable.
at WarehouseCodeMapperStartupValidationTest.java:17
```

현재 구현은 잘못된 UUID 매핑을 넣어도 `warehouse-code-map 로드: 1 entries`만 기록하고 예외 없이 반환했다.

## 3. 구현 및 선택 검증

- 기존 `WarehouseInternalClient`에 내부 창고코드 조회(`GET /internal/inventory/warehouses/by-code`)를 추가했다.
- `WarehouseCodeMapper` 기동 검증은 각 매핑에 대해 UUID 문법, 활성 창고 실재성, 반환 창고코드·UUID 일치를 모두 확인한다.
- 검증은 기존 서비스 간 HTTP 계약을 사용하며 DataSource·JdbcTemplate·트랜잭션 매니저·커넥션 풀을 추가하지 않는다.
- 테스트 전체 경로는 `src/test/resources/application.yml`에서 검증을 비활성화해 inventory 창고 데이터/외부 서비스 없이 유지한다. 검증 자체는 단위 테스트에서 조회 결과를 주입한다.
- UUID가 로그·기동 예외·기존 mapper의 UUID 형식 예외에 원문으로 남지 않도록 정리했다.

선택 테스트 실행 결과:

```text
.\gradlew.bat :services:slip-service:test --tests com.samhanair.logis.slip.publish.WarehouseCodeMapperStartupValidationTest --tests com.samhanair.logis.slip.client.WarehouseInternalClientTest
BUILD SUCCESSFUL
```

검증한 경우:

- 실재하지 않는 UUID 조회 결과(empty) → 창고코드 포함 기동 실패
- 미치환 placeholder → 창고코드 포함 기동 실패, placeholder/UUID 원문 미포함
- 정상 UUID·창고코드 조회 결과 → 기동 성공
- UUID 또는 창고코드가 다른 조회 결과 → 기동 실패

## 4. 전체 모듈·풀 검증

실행:

```text
.\gradlew.bat :services:slip-service:test
```

원문:

```text
BUILD SUCCESSFUL in 8m 50s
```

테스트 결과 XML 집계:

```text
valid_files=207 invalid_files=0 tests=1538 failures=0 errors=0 skipped=0
```

커넥션 풀 확인:

```text
pool_exhaustion_hits=0
hikari_start_lines=72 hikari_shutdown_lines=71
```

`too many clients`, `connection is not available`, `SQLTransientConnectionException`, `Pool exhausted` 계열 원문은 없었고, 종료 로그에서 각 Hikari pool shutdown이 확인됐다. 전용 DataSource·JdbcTemplate·트랜잭션 매니저 구성은 변경하지 않았다.

## 5. 요구 불변식 판정

- A/B: 단위 기동 callback에서 미실재 UUID와 미치환 placeholder를 창고코드 원인의 `IllegalStateException`으로 차단한다.
- C/H: 기동 예외·로그에 UUID 원문을 남기지 않고 창고코드만 표시한다.
- D: 활성 창고 UUID·창고코드가 모두 일치하는 경우 예외 없이 반환한다.
- E: `slip-service` 전체 1,538건이 통과했다. 테스트 기본 설정은 `application.properties`에서 외부 창고 검증만 끄며 main Hikari 설정을 가리지 않는다.
- F/G: DataSource 구성과 `dedicatedDataSourceTrio`를 건드리지 않았고, 전체 테스트에서 풀 고갈 원문이 없었다.
