# R23 — slip publish warehouseId 회귀 CI fix

## 판정 — 테스트 fixture가 낡았고 `@NotBlank bizCode` 제약은 과하지 않음

`SlipPublishWarehouseIdIT.java:101-115`의 공통 `publish()` fixture는 `partnerOrderId`, `partnerCode`, `ioDate`, `warehouseCode`, 선택적 `warehouseId`, 라인만 만들고 `bizCode`를 넣지 않는다. 반면 R21 계약인 `PublishFromPartnerOrderRequest.java:27-35`는 `bizCode`를 `@NotBlank`로 요구한다.

이 API는 `partner-order-service`가 주문의 사업자번호를 알고 호출하는 `PARTNER_ORDER` 출고 경로다. 따라서 사업자번호를 모르는 호출을 성공시켜 NULL 출고를 만들 수 있게 하는 것은 R21 불변식과 맞지 않는다. `warehouseId`는 별개의 선택 필드이고, 이 fixture에 `bizCode`를 추가해도 창고 해석 로직 또는 기존 단언은 약화되지 않는다. 결론은 테스트가 낡았으며 fixture만 갱신한다.

실패 상태를 지정된 테스트만 재실행해 확인했다.

```text
./gradlew :services:slip-service:test --tests com.samhanair.logis.slip.publish.SlipPublishWarehouseIdIT

SlipPublishWarehouseIdIT > warehouseId 없음 → yml 폴백으로 warehouseCode 해석 (회귀) FAILED
    java.lang.AssertionError at SlipPublishWarehouseIdIT.java:124
SlipPublishWarehouseIdIT > warehouseId payload 존재 → yml 미경유, sourceWarehouseId = 전달 UUID FAILED
    java.lang.AssertionError at SlipPublishWarehouseIdIT.java:124

91 tests completed, 2 failed
```

## 수정 1 — warehouseId 회귀 fixture 계약 갱신

`SlipPublishWarehouseIdIT.java:104`의 공통 payload에 `bizCode=123-45-67890`을 추가했다. `warehouseId` 존재 여부와 `warehouseCode=WH-001`은 그대로 유지했으므로 두 테스트가 검증하던 직접 UUID 경로와 yml fallback 경로의 창고 ID 단언은 변경하지 않는다.
