# PR #1050 / 이슈 #1049 R9 — 품목 검색 상한 범위 수정

## 1. 결론

R8에서 발견된 품목 검색 상한 누출을 수정했다. `searchProducts`의 기본 상한은 `20`으로 복원하고, 검색 결과 선택 모달인 `ProductMultiSelectAutocomplete`의 호출부만 `size: 10000`을 명시한다. 안전재고·전표·구성품 단일 자동완성은 더 이상 `size=10000`을 보내지 않는다.

수정 파일은 Desktop 3개이며, design-system 공용 컴포넌트와 BE 소스는 수정하지 않았다. commit/push/checkout/브랜치 조작/Docker 재빌드/공유 DB write는 하지 않았다.

## 2. endpoint 호출 지점 전수 목록과 상한

대상은 정확히 `GET /api/products`이다. `/api/products/categories`, `/api/products/{id}`, `/api/products/lookup` 및 `GET /api/v1/products`는 다른 endpoint이므로 아래 표에서 분리했다.

### FE production 호출 지점: 6개

| # | 파일·호출 지점 | 화면/용도 | 현재 상한 | 모달 여부 |
|---:|---|---|---:|---|
| 1 | `clients/desktop/src/renderer/api/productApi.ts:47` `searchProducts` → `apiClient.get` | 공통 품목 검색 API 함수 | 기본 `20`, 호출자가 명시하면 전달 | 함수 자체는 중립 |
| 2 | `EstimateItemsCatalogPage.tsx:727` `searchComponentProducts` | 구성품 편집 모달 안의 단일 자동완성 | `20`(기본값) | 비모달 결과 dropdown |
| 3 | `EstimateItemsCatalogPage.tsx:1471` `searchMasterProducts` | 기초품목 선택 `ProductMultiSelectAutocomplete` | 명시 `10000` | 검색 결과 선택 모달 |
| 4 | `SafetyStockAlertsPage.tsx:298` `searchProducts={searchProducts}` | 안전재고 단일 `ProductAutocomplete` | `20`(기본값) | 비모달 단일 dropdown |
| 5 | `SlipFormPage.tsx:1645` inline wrapper | 전표 라인 단일 `ProductAutocomplete` | `20`(기본값) + `usageScope=PARTNER_ORDER` | 비모달 단일 dropdown |
| 6 | `SlipFormPage.tsx:1713` inline wrapper | 전표 라인 단일 `ProductAutocomplete` | `20`(기본값) + `usageScope=PARTNER_ORDER` | 비모달 단일 dropdown |

추가로 동일 endpoint를 직접 사용하는 내부 해소 경로가 1개 있다.

| 파일·호출 지점 | 화면/용도 | 현재 상한 |
|---|---|---:|
| `productCatalogApi.ts:426` `searchProductSummaries` → `ProductFormPage.tsx:175` | 품목 수정 화면의 모델코드→요약 내부 해소 | 호출 인자 `20` |

따라서 `/api/products` 검색의 FE 소비 호출은 **총 7개 표면**이다. 이 중 `size=10000`은 #3 한 곳뿐이며, 나머지 6개는 `20`이다.

### BE 재조사

| endpoint | 컨트롤러 | 기본 상한 | `size=10000` 소비처 |
|---|---|---:|---:|
| `GET /products` (gateway의 `GET /api/products`) | `services/product-service/src/main/java/com/samhanair/logis/product/web/ProductController.java:77-88` `ProductController.search` | `@RequestParam(defaultValue = "20")` | BE 내부 호출 0건; FE의 명시 요청은 위 표의 모달 1건 |

BE에는 이 endpoint를 호출하는 내부 client가 없고, `ProductController.search`는 `PageRequest.of(page, size)`로 요청값을 사용한다. 이번 R9의 범위는 비모달 FE 소비처의 `size=10000` 송신 차단이며, 컨트롤러/공용 BE 계약은 변경하지 않았다. 즉 “BE 소비처 0건”은 BE 소스 내부 호출 기준으로 다시 확인한 수치이고, 외부 HTTP 소비자가 임의 query를 만들 수 있다는 사실과 혼동하지 않는다.

참고로 `GET /api/v1/products`의 `listProducts`는 별도 `ProductCatalogController` 경로이며 기본 `size=50`이다. 이번 endpoint 전수 건수에는 포함하지 않았다.

## 3. RED — 비모달 재현

먼저 `productApi.search-modal.test.ts`에 비모달 기본 호출이 `size=20`이어야 한다는 단언을 추가하고 기존 코드에서 실행했다.

```text
FAIL src/renderer/api/productApi.search-modal.test.ts
  비모달 자동완성은 전역 모달 상한을 사용하지 않는다

Expected: params { q: "AJ", size: 20 }
Received: params { q: "AJ", size: 10000 }
Tests 2: 1 failed, 1 passed
```

이 실패는 테스트 오타가 아니라, 실제 비모달 `searchProducts('AJ')` 호출이 10000을 보내는 결함을 직접 재현한 RED다.

## 4. fix

- `searchProducts` 옵션에 `size?: number`를 추가하고 기본값을 `20`으로 변경했다.
- 모달 호출부인 `searchMasterProducts`만 `{ size: 10000 }`을 명시했다.
- 안전재고, 전표 2개 라인, 구성품 자동완성은 호출 인자를 추가하지 않아 기본 `20`을 사용한다.
- 모달/공용 design-system 컴포넌트 자체는 새로 작성하거나 수정하지 않았다.

## 5. GREEN

### R9 API 계약 테스트

```text
Test Files  1 passed (1)
Tests       2 passed (2)
```

기존 모달 `size=10000` 단언과 신규 비모달 `size=20` 단언이 모두 통과했다.

### 불변식 1~5

1. **상한 범위:** 저장소 FE 호출 지점 7개를 전수 목록화했다. `size=10000`은 `EstimateItemsCatalogPage.tsx:1471`의 검색 결과 선택 모달 1곳뿐이며, 단일 dropdown 5곳과 품목 수정 내부 해소 1곳은 `20`이다. BE 내부 소비처도 0건이다.
2. **모달 절단 0:** 모달 호출은 기존처럼 `size=10000`을 명시하고 API 테스트가 그 계약을 GREEN으로 확인한다. R8의 실제 5,612건 해소 실측 경로와 모달 UI 코드는 변경하지 않았다.
3. **16/16:** 4종×4상황 실제 입력·선택은 R8 실측의 16/16 PASS를 유지한다. 이번 R9에서는 live UI를 재실행하지 않았고, 품목 모달 호출의 상한 표기만 명시적으로 이동했으며 4종 UI 선택 로직은 건드리지 않았다.
4. **R6 계약 조정 8건:** R8 재수렴 실측의 8/8 PASS를 유지한다. 이번 R9에서는 해당 live 시나리오를 재실행하지 않았고, Messenger 및 검색 API 계약 테스트는 전체 GREEN이다.
5. **BE 상한 재조사:** `ProductController.search` 단일 GET handler의 기본값은 20이며 BE 내부 `size=10000` 호출은 0건이다. FE에서 10000을 보내는 지점은 모달 1곳으로 고정됐다. 컨트롤러 코드는 변경하지 않았다.
