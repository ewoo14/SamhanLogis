# #976 레거시 GAS 라이브 가격 변경 제품 반영 — 기획

> 2026-07-29 · 브랜치 `feat/976-gas-live-price-reflection`
> 개발책임자 지시: *"구글스크립트의 경우 예전과 달리 가격이 변동되었음. 그거 감안해줘야해."*

---

## 1. 성격 — **결함 수정이 아니라 실 가격 변경 반영**

PR #974 로 레거시 GAS 정본을 라이브로 갱신하면서 제품이 낡은 값을 쓰고 있음이 드러났습니다. 개발책임자 확인 결과 **가격이 실제로 변동된 것**이므로, 이번 트랙은 *"버그를 고친다"* 가 아니라 **"바뀐 가격을 반영한다"** 입니다.

⚠️ 다만 **금액이 실제로 다르게 나가고 있다**는 사실은 같으므로 **정밀 트랙**으로 운영합니다([[feedback_pm_adjusts_workflow_weight_per_track]]).

---

## 2. 🔑 기획 단계에서 확인한 것 — 항목마다 성격이 다르다

PM 이 실 코드·실 DB 를 확인한 결과, 6개 항목이 **세 가지 다른 성격**으로 갈립니다.

### 2-A. 운영 데이터 (코드 변경 불요 가능성)

**단가인상 기준일은 하드코딩이 아닙니다.** `V22__add_price_change_schedule.sql` 이 만든 테이블이고 **관리 API 로 수정 가능**합니다:

```text
PUT /api/v1/products/admin/price-change-schedule/{category}
    @RequirePermission(page = "products.price-schedule", action = UPDATE)
```

현재 운영 데이터 실측:
```text
 category        | effective_date | created_by
-----------------+----------------+---------------
 commercialMulti | 2026-04-01     | V22_MIGRATION
 homemulti       | 2026-08-01     | V22_MIGRATION   ← 혼자 다름
 oldProducts     | 2026-04-01     | V22_MIGRATION
 singleSets      | 2026-04-01     | V22_MIGRATION
```

라이브 GAS 는 `2026-07-01`(주문서) / `20260701`(일마감) 입니다.

🚨 **결정 필요 1** — `homemulti` 가 `2026-08-01` 인 것이 **의도된 별도 일정**인지, 아니면 잘못된 값인지. 라이브 GAS 는 카테고리 구분 없이 `07-01` 로 보입니다. **개발책임자 확인 대상**입니다.

🚨 **결정 필요 2** — 기준일을 **어떻게 갱신할 것인가**:
| 방식 | 장점 | 단점 |
|---|---|---|
| **관리 화면에서 수동 갱신** | 코드 변경 0. 앞으로도 같은 방식 | 환경마다 사람이 해야 함. dev/prod 가 어긋날 수 있음 |
| **신규 마이그레이션(`V26`)으로 갱신** | 전 환경 일관 | 운영 중 사용자가 바꾼 값을 덮을 위험 |
| **둘 다** — 마이그레이션은 `V22_MIGRATION` 이 만든 값만 갱신 | 사용자 수정본 보존 + 일관성 | 조건부 UPDATE 필요 |

**PM 권장 = 3안.** `created_by='V22_MIGRATION'` 인 행만 갱신하면 사용자가 손댄 값은 건드리지 않습니다.

### 2-B. 제품 하드코딩 (코드 변경 필요)

| # | 항목 | 라이브 | 제품 | 위치 |
|---|---|---|---|---|
| **4** | 360 실내기 리모컨 | `AR-EH05` (13,915) | `AR-KH05` (33,000, `useK2`) | `order-app/index.html` |
| **5** | 냉방전용 상부토출 30HP 방진가대 | S2중 (160,000) | S2대 (220,000) | `order-app/index.html` |
| **6** | I형 유연호스 고정단가 | 8,000 | 7,000 | `order-app/index.html` |

🚨 **결정 필요 3** — #4 는 **모델 코드 자체가 다릅니다**(`AR-EH05` vs `AR-KH05`). 단순 단가 변경이 아니라 **다른 품목**입니다. 카탈로그에 두 모델이 다 있는지, 어느 것이 맞는지 확인이 필요합니다. **`ACL-KORGHP06→07` 과 같은 계열**일 수 있습니다(PR #967 — 카탈로그에 없는 코드를 참조해 `find()` 가 undefined → 조용히 스킵 → 6,710,000원 누락).

### 2-C. 두 앱 규칙 불일치 (설계 결정 필요)

| 항목 | estimate-app | order-app | 라이브 GAS |
|---|---|---|---|
| 상업 구성품 **기준가** | **납품가**<br>`lib/db-catalog.js:144 price: num(r.deliveryPrice)` | **출고가**<br>`BootstrapService.java:455-457 firstDecimal(releasePrice, deliveryPrice)`<br>`:524 주석 "출고가 우선, 납품가 fallback"` | **납품가 우선**<br>`거래처 주문서/Code.js:1155 const basePrice = priceVal \|\| listVal` |

**우리 두 앱이 서로 다른 규칙을 씁니다.**

현재 미도달인 이유 — 소비처 `order-app/index.html:2659` 가 `(commUnitPrice(model)||0) || basePrice || 0` 이고, **137개 구성품 모델이 전부 COMMULTI 에 존재하며 가격 0 인 행이 0개**라 `basePrice` 에 닿지 않습니다.

🚨 **가려져 있는 것이지 무해한 게 아닙니다.** COMMULTI 에 없는 구성품이 **하나만 생겨도** `AM120AXVHHH1` 기준 **4,840,605원**이 벌어집니다.

🚨 **결정 필요 4** — 이 항목의 범위:
- (a) order-app 을 라이브(납품가 우선)에 맞춘다 → 두 앱 통일, 범위 작음
- (b) 두 앱의 가격 결정 경로를 한 곳으로 모은다 → 근본 해결, 범위 큼
- (c) 이번 트랙에서 분리한다 → 미도달이므로 후순위

**PM 권장 = (a).** 라이브와 estimate-app 이 이미 납품가 우선이므로 order-app 만 맞추면 셋이 일치합니다. (b) 는 별건 규모입니다.

## 3. 불변식 (구현자에게 하달할 것 — 수단 미지시)

> **P-1** 제품이 산출하는 금액이 **현재 라이브 레거시 GAS 와 같다** — 대상 항목 전부에 대해.
> **P-2** 기준일은 **환경마다 사람이 기억해야 하는 값이 아니다.** dev·prod 가 조용히 어긋나지 않는다.
> **P-3** 품목 코드는 **카탈로그에 실재하는 것을 참조한다.** 참조가 빗나갔을 때 **조용히 사라지지 않는다.**
> **P-4** 같은 계산에 대해 **estimate-app 과 order-app 이 같은 답을 낸다.**
> **P-5** 사용자가 관리 화면에서 손댄 값을 **자동 갱신이 덮지 않는다.**

🔑 **P-3 가 중요합니다** — GHP 건(`ACL-KORGHP06`)이 정확히 이 형태였습니다. 카탈로그에 없는 코드를 `find()` 하면 `undefined` 가 돌아오고 `if(!row) return;` 으로 **에러 없이 스킵**돼 6,710,000원 품목이 누락됐습니다. #4 도 같은 위험이 있습니다.
