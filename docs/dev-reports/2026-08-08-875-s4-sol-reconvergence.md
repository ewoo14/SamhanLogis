## 결함 1 — 저장분 복원·재렌더 뒤 세 탭의 사용자 `절삭`이 음수로 표시된다

레거시 원문은 `절삭`의 저장·계산값만 음수이고 화면 입력값은 절댓값이어야 한다.
현재 HEAD는 입력 직후에는 `handleFreightInput()`이 `Math.abs(val)`을 표시하지만, 이후
다시 렌더할 때 홈만 `Math.abs(currentPrice)`를 사용한다. 싱글·상업·구형은 저장된
음수값을 그대로 `fmt(currentPrice)`에 넘긴다.

### 실 사용자 경로

1. 싱글·상업·구형 중 한 탭에서 카탈로그 `절삭`에 `500`을 입력한다.
2. 내부 단가 `-500`, 수량 `1`로 저장되고 입력 직후 화면에는 `500`이 보인다.
3. 견적을 저장했다가 복원하거나, 해당 탭을 다시 렌더하는 경로를 밟는다.
4. 복원된 custom price map의 `-500`으로 `renderSingle()`·`renderComm()`·`renderOld()`이
   실행된다.
5. 입력칸에 `-500`이 표시된다. 홈 탭은 동일 경로에서 `500`을 표시한다.

금액 계산과 payload의 `-500`은 맞다. 잘못된 것은 사용자 화면 표시 부호다. 사용자가
그 상태에서 다시 변경해도 입력 핸들러가 숫자만 읽고 음수로 정규화하므로 금액이 한 번
더 차감되지는 않는다.

## 금액 도달성

### 사용자 `절삭`과 자동 합계 절삭 동시 발동

레거시 명세상 두 행은 별도 정산 artifact다. 사용자 카탈로그 `절삭`은 먼저 실제 합계에
포함되고, 자동 절삭은 그 결과의 나머지만 한 번 조정해야 한다.

실제 `buildSendRows()`와 `getStructuredQuoteData()`를 현재 EJS에서 추출해 다음 상태를
실행했다.

```text
일반 품목 10,500 + 운임 300 + 사용자 절삭 -200
합계 절삭 단위 1,000

절삭 전 합계                         10,600
자동 절삭                             -600
최종 합계                           10,000
```

두 payload 경로 모두 일반 품목을 `9,900`으로 조정하고, 카탈로그 운임 `+300`과
카탈로그 절삭 `-200`을 각각 한 번 유지해 최종 `10,000`을 만들었다. 사용자 절삭이
자동 절삭의 흡수 대상에서는 제외되지만 합계에서는 제외되지 않으므로 금액 소실·이중
차감은 없다.

일반행 없이 `운임 +300`, 사용자 `절삭 -200`만 넣은 조합에서는 두 함수 모두 별도
`AUTO_CUTOFF -100` 행을 생성해 최종 0을 만들었다. 카탈로그 절삭과 자동 절삭의
`source`·`identity`는 분리됐다.

### `운임`과 `절삭` 동시 입력

네 탭의 `buildSendRows()` 반환값에서 두 행은 각각 보존됐다.

| 탭 | 운임/절삭 q=1 payload 행 | 예시 순기여 |
|---|---:|---:|
| 홈 | 2 | `+300 -200 = +100` |
| 싱글 | 2 | `+500 -300 = +200` |
| 상업 | 2 | `+400 -100 = +300` |
| 구형 | 2 | `+600 -400 = +200` |

각 행은 `source=CATALOG_SPECIAL`을 유지했다.

### 금액을 다시 0으로 지운 경로

`handleFreightInput()`은 입력값 0/공백에서 custom price를 0, 수량을 0으로 만들고
입력칸을 비우며 `qty-static`을 0으로 바꾼다. 행 자체는 카탈로그 배열과 편집 화면에
남는다. 네 탭을 모두 q=0으로 만든 뒤 `buildSendRows()` 반환 행 수는 0이었다.
`getStructuredQuoteData()`도 각 탭에서 `if (!q) return`으로 제외한다.

따라서 화면=행 유지·금액 공백·수량 0, 합계=0 기여, 저장/출력 payload=제외라는
레거시 계약과 일치한다.

## 일반 상품 오차단 도달성

공유 `product_db`를 SELECT한 결과 active 상품 3,083건 중 이름에 `운임` 또는 `절삭`이
들어간 상품은 정확히 `운임`, `절삭` 2건뿐이었다. `운임설치비`처럼 부분 문자열만
포함하는 일반 상품은 0건이다.

실 앱이 받은 네 카탈로그에는 각 탭마다 정확히 이 두 행만 있었다.

| 탭 | 전체 행 | `운임`·`절삭` 행 | 실제 위치 |
|---|---:|---:|---|
| 홈 | 119 | 2 | 마지막 2행 |
| 싱글 | 288 | 2 | 마지막 2행 |
| 상업 | 408 | 2 | 마지막 2행 |
| 구형 | 40 | 2 | 마지막 2행 |

현재 `catalogSpecialMetadata()`가 정확 일치가 아니라 `/운임|절삭/i` 부분 일치이므로
그런 일반 상품이 향후 카탈로그에 생기면 특수행으로 오분류한다. 그러나 현재 실 데이터의
발화 건수는 0이므로 이번 라운드의 사용자 도달 결함으로 세지 않는다. 사용자 정의 행은
이 metadata 경계를 통과하지 않아 이름이 같아도 일반 payload에서 빠지지 않는다.

## 정렬·기존 저장분

- 홈은 source가 붙은 두 행을 기타/마지막으로 보낸다. 싱글·상업·구형은 DB 노출 순서가
  이미 마지막 두 행이며 현재 렌더가 그 순서를 유지한다. 특수행이 일반 품목 사이로 이동하는
  도달 경로는 없다.
- 변경 이전 snapshot에는 `source`가 없지만 수량·가격 map key는 그대로이고, 복원 시
  현재 카탈로그 경계에서 source를 다시 부여한 배열을 렌더한다. q=0/1, 합계, payload
  identity는 유지된다.
- 자동 절삭행은 snapshot의 독립 상품행이 아니라 복원된 `selCutUnit`과 현재 합계에서
  다시 계산된다. 중복 누적되지 않는다.
- 단, 기존 저장분 복원 화면의 절삭 부호는 위 결함 1에 해당한다.

## 증거 무결성

- 로컬 앱은 `http://127.0.0.1:5183/`에서 HTTP 200으로 렌더됐고, 서버가 실제 주입한
  네 카탈로그 배열을 읽었다.
- 연결 가능한 브라우저가 0개여서 실제 클릭·화면 캡처는 **판정 불가**다. 대신 서버가
  렌더한 실제 EJS의 `buildSendRows()`·`getStructuredQuoteData()`·`applyCutoffLogic()`·
  `handleFreightInput()`을 추출해 위 상태값으로 실행했다.
- DB/GAS/스프레드시트 쓰기, 공유 Docker 재기동, 코드 수정, commit, push는 하지 않았다.
- 화면에 새로 노출되는 UUID 또는 금지 용어 `슬립`은 이번 diff에 없다. 자동 절삭의
  `identity`는 내부 payload 필드이며 화면 라벨은 계속 `절삭`이다.
