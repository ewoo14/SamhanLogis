## 1. 결론

fix5를 적용했다. scroll→click 재열기에서 실제 anchor rect를 다시 읽고 fixed 좌표를 먼저 commit한 뒤 같은 event task 안에서 visibility를 되돌린다. rAF/setTimeout으로 노출을 늦추지 않는다.

Chromium-1217 headless에서 사용자가 지정한 재현(`scrollY 0→3`, 첫 rAF 측정)을 5회 반복해 모두 다음 상태를 확인했다.

```text
FIX5_FIRST_RAF={"visible":true,"aligned":true,"belowGap":4,"scrollY":3}
```

5/5 GREEN이다. 기존 portal, scroll-close, onClick gate와 기존 문서 참조 계약도 유지했다.

## 3. 원인과 순서 변경 근거

현행 fix4 경로는 다음 순서였다.

```text
scroll close → 다음 rAF에서 open=true → updateDropdownPosition()
```

따라서 첫 rAF에는 dropdown이 낡은 fixed 좌표로 존재하거나, visibility를 숨긴 기존 portal DOM이 재사용될 수 있었다. 특히 `setOpen(true)`와 `setDropdownPosition(...)`이 rAF callback 안에서 별도로 처리되어 첫 paint와 좌표 commit의 경계가 분리됐다.

fix5는 다음 순서로 바꿨다.

```text
현재 anchor rect 읽기 → DropdownPosition 계산 → flushSync로 position/open commit
→ 같은 event task에서 visibility 제거 → 다음 paint
```

재열기에서는 기존 portal을 먼저 숨기고, 계산된 좌표를 같은 commit에 적용한다. `flushSync` 뒤 DOM이 재사용되는 경우에도 그 시점은 아직 paint 전이므로 visibility를 제거하면 첫 paint에 이미 올바른 좌표다. 일반 scroll은 기존처럼 `position=null/open=false`로 닫힌다.

click 경로도 후보가 있으면 현재 anchor를 즉시 계산해 `position`과 `open`을 함께 설정한다. `!open` layout effect는 scroll-click 표식이 살아 있는 경합 commit에서 계산 좌표를 지우지 않는다.

## 4. RED 원문 — 구현 전

TDD RED로 first-rAF gate를 먼저 추가하고 생산 코드 변경 전에 Chromium-1217 headless에서 `--repeat-each=5` 실행했다. 계측은 실제 `page.mouse.click` 경로이며 `pointerdown`에서 실제 `window.scrollBy(0, 3)`을 발생시킨다.
