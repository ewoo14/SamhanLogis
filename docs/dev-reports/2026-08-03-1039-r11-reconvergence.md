두 발행 경로 모두 pending 표시와 전표 저장 뒤 `scheduleAfterCommit`을 호출한다. `WarehouseCodeSnapshotService.java:45-54`는 활성 synchronization에서 오직 `afterCommit()`에 executor 제출을 등록하므로 rollback이면 callback이 실행되지 않는다. 이후 `REQUIRES_NEW`는 executor/scheduler worker의 code 저장만 독립 commit한다. 현재 호출 그래프에서는 rollback된 전표에 code만 commit되는 도달 경로를 찾지 못했다.

## 확인 4 — executor 종료·재시작 유실 여부

`applicationTaskExecutor`는 `PartnerProductPriceMemoryAsyncConfig.java:61-65`에서 Boot builder로 생성되는 메모리 내 executor이고, executor 큐 자체는 영속하지 않는다. 그러나 발행 transaction이 commit되기 전에 신규 OUTBOUND 행에 pending=true가 함께 저장되고, executor 제출은 commit 뒤에만 일어난다.

따라서 다음 순서가 성립한다.

```text
전표 + pending=true DB commit
→ afterCommit executor 제출
→ 프로세스 종료로 queued/running 작업 유실 가능
→ 재기동 후 @Scheduled가 DB pending=true를 다시 조회
```

판정: executor 큐와 DB pending은 별도이지만, DB pending이 선행 영속되는 복구 권위다. 종료 시 executor 작업이 사라져도 pending 행이 남으므로 재시작 복구 경로가 있다. 단, 결함 1의 영구 실패 Top 100이 앞을 막으면 재시작 후에도 후속 행은 기아될 수 있다.

## 최종 판정

이 각도에서 도달 가능한 결함은 **2건**이다.

1. 영구 실패에 재시도 상한·백오프·포기 조건이 없고, 고정 oldest Top 100 때문에 후속 pending 큐가 기아될 수 있다.
2. executor 처리 중인 pending 행을 scheduler가 claim하지 않아 동일 전표 중복 inventory 호출과 optimistic-lock 경합이 가능하다.

전표 rollback 뒤 code만 독립 commit되는 현재 production 경로는 찾지 못했다. executor 메모리 큐 유실은 DB pending이 복구한다. V102 적용 직후 기존 행의 scheduler 대상은 0건이며, 공유 DB 현재 기존 모수는 2,455행이다.
