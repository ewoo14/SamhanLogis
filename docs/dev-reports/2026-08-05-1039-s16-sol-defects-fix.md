## 1. 결함별 진단 → 불변식 → 조치

### 결함 1 — 수신 배차 그룹 권한 누수

- 진단: `GET /admin/arologis/dispatch-groups`가 `ReceivedDispatchGroupController`에 있었지만 `@RequirePermission`이 없었다. 따라서 `arologis.dispatch.ops VIEW=false`인 회계 계정도 수신 그룹 목록과 snapshot을 읽을 수 있었다.
- 불변식: `AROLOGIS_ACCOUNTANT`는 수신 그룹을 읽지 못하고, `AROLOGIS_MASTER`는 기존처럼 읽는다.
- 조치:
  - 서버 목록 endpoint에 `ArologisPageCodes.DISPATCH_OPS + VIEW`를 부착했다. 내부 수신 `POST /internal/arologis/dispatch-groups`는 내부 token 경로이므로 가드 대상에서 제외했다.
  - 아로로지스 desktop의 `/dispatches/pre-classify`, `/dispatches/received-groups`에도 같은 `PermissionGuard`를 적용했다.
  - Arologis MASTER mock에 `arologis.dispatch.ops: VIEW`를 추가해 S13의 MASTER 읽기 경로를 보존했다.
- 검증: `ArologisPageCodesTest`의 endpoint annotation 단언, 기존 `ArologisPermissionControllerIT`, 아로로지스 desktop 전체 typecheck/test 통과.

### 결함 2 — 원격 수신 성공 후 응답 유실 시 한쪽만 남음

- 진단: 원격 upsert가 이미 커밋됐을 수 있는데 삼한 transaction이 `FAILED`로 롤백되어 사용자가 미전송으로 인식할 수 있었다.
- 불변식: 원격과 삼한이 최종적으로 같은 결과로 수렴하고, 재전송이 중복을 만들지 않는다.
- 조치:
  - `TransferStatus.PENDING`을 추가했다. 첫 호출과 즉시 1회 재확인 모두 결과를 받지 못하면 `FAILED`가 아니라 `PENDING`을 커밋한다.
  - PENDING 그룹은 scheduler가 동일한 `groupNo` 멱등 요청으로 재확인하고 성공 시 `SENT`로 수렴한다.
  - PENDING/SENT 그룹은 그룹·전표·운송사 변경을 잠근다. desktop은 30초 polling으로 최종 상태를 반영하고, PENDING을 `전송 확인 중`으로 표시한다.
  - 기존 S11 멱등 수신 계약과 동일한 요청을 재사용했다. `markTransferFailed()`의 기존 API는 다른 호출자의 호환을 위해 제거하지 않았다.
- 검증: `DispatchGroupLifecycleIT.lost_transfer_responses_stay_pending_then_converge_without_duplicate_group`에서 원격 실패 2회 → PENDING → 성공 재확인 → SENT를 검증했고 client 호출 횟수는 3회(중복 그룹 없음)였다.

### 결함 3 — SENT 후 운송사 마스터 변경으로 표시 불일치

- 진단: 삼한 목록은 carrier master를 다시 읽고 아로로지스 수신본은 전송 당시 snapshot을 보존하므로, SENT 뒤 carrier name/code를 수정하면 양쪽 표시가 영구히 달라진다.
- 불변식: 전송된 그룹 표시가 양쪽에서 같고, 아로로지스 수신본은 읽기 전용이다.
- 조치:
  - `CarrierService.update()`에서 해당 carrier를 참조하는 활성 `SENT` 또는 `PENDING` 그룹이 있으면 `CONFLICT`로 거부한다.
  - 아로로지스 수신본에 UPDATE 경로를 추가하지 않았다. 표시 일치를 위해 수신본 편집을 허용하지 않는 개발책임자 결정을 유지했다.
  - `DispatchGroupLifecycleIT.sent_carrier_cannot_be_changed_through_hr_master`로 HR master 경로를 검증했다.

### 결함 4 — 가배차 UNKNOWN 119건 판별 및 안내/회복

#### 판별 근거(데이터)

판별은 추측하지 않고 `inventory_db.warehouses`와 `slip_db.slips`를 읽기 전용으로 대조했다. 당시 inventory DB에는 창고 30개가 있었고, 대상 창고는 다음 두 개였다.

| inventory warehouse id | code | name |
|---|---:|---|
| `89e0eb1d-383d-475f-9ff8-bf5ac577fef7` | `2` | 상일물류 |
| `57314efb-92be-43ce-8b2f-4d53dd45fcd1` | `00003` | 삼성창고 (초월 무갑) |

실측 결과:

```text
active OUTBOUND = 121
source_warehouse_code IS NULL = 119
source_warehouse_code_snapshot_status = NOT_REQUESTED = 119
```

`NOT_REQUESTED` 119건을 실제 `source_warehouse_id`로 묶으면 다음과 같다.

| 실제 inventory code | 창고 | NOT_REQUESTED 건수 | 업무 판정 |
|---:|---|---:|---|
| `1` | 서초창고 | 108 | 비대상, 제외 |
| `HQ-001` | 본사창고 | 7 | 비대상, 제외 |
| `VH-001` | 1호차 차량재고 | 1 | 비대상, 제외 |
| `2` | 상일물류 | 2 | 대상, 회복 |
| `00003` | 삼성창고 (초월 무갑) | 1 | 대상, 회복 |
| **합계** |  | **119** | **116 제외 + 3 회복** |

따라서 119건 전체를 제외하는 것은 업무상 맞지 않다. `source_warehouse_id`가 상일·초월을 가리키는 3건은 V102의 “기존 행은 pending으로 승계하지 않음” 때문에 회복되지 않은 대상 행이다. 나머지 116건은 상일·초월이 아니므로 제외가 맞다. S15의 `UNKNOWN 120 = NOT_REQUESTED 119 + COMPLETED 1` 중 `COMPLETED 1`은 V107 대상에서 건드리지 않는다.

#### 4-a 안내와 건수

- `PreClassifyService`가 전체 원본 UNKNOWN을 먼저 세던 문제를 고쳤다. 실행 모드 결과에 실제 포함된 UNKNOWN STACK은 차감하므로 경고 건수는 화면 결과에서 제외된 UNKNOWN만 센다.
- 화면 문구를 “창고 정보를 확인한 뒤 다시 조회”에서 “창고 코드 보강 결과를 확인해 주세요. 상일·초월 외 창고는 가배차 대상이 아닙니다.”로 바꿨다. 사용자가 재조회로 복구되지 않는 행동을 하도록 안내하지 않는다.
- `PreClassifyServiceTest`는 UNKNOWN STACK 포함 1건 + 모드 제외 1건에서 경고를 1건으로 단언한다.

#### 4-b 회복 경로

- `V107__queue_legacy_source_warehouse_code_recovery.sql`을 추가했다. 기존 활성 `OUTBOUND` 중 `source_warehouse_id IS NOT NULL`, `source_warehouse_code IS NULL`, `NOT_REQUESTED`인 행만 기존 snapshot worker의 `PENDING` 큐로 승계한다.
- worker가 inventory code를 채우면 상일·초월 3건은 모드 판정에 복귀하고, 나머지 116건은 코드가 확정된 UNKNOWN으로 남는다.
- V107은 데이터 변경이므로 적용 전 rollback 계획은 다음과 같다.
  1. migration 실행 전 대상의 `id`, `source_warehouse_code_snapshot_status`, `source_warehouse_code_pending`, `source_warehouse_code_next_attempt_at`, `source_warehouse_code_attempt_count`를 별도 export한다.
  2. worker 실행 전 중단해야 하면 export 기준으로 `NOT_REQUESTED / FALSE / NULL` 및 기존 시도 metadata를 복원한다.
  3. worker가 이미 code를 채운 뒤 되돌려야 하면 export에서 code가 NULL이었던 id만 대상으로 code와 snapshot metadata를 원복한다. 다른 시점에 새로 생성된 전표는 포함하지 않는다.
- 열린 PR의 slip migration 파일을 조회한 결과 최고 번호는 V105였다. 이번 변경은 V106(전송 PENDING 상태), V107(기존 창고 code 회복 큐) 순서로 추가했다.
