# R45 fix 보고 — PR #1057 · 이슈 #874

## RED-first 증거

지시서의 RED-A/RED-B 테스트를 `SlipCollabNotificationDispatchTest`에 먼저 추가하고 다음 좁은 게이트를 실행했다.

```text
.\gradlew.bat :services:slip-service:test --tests '*SlipCollab*' --tests '*GlobalExceptionHandlerTest*' --console=plain
```

수정 전 실패 원문:

```text
SlipCollabNotificationDispatchTest > concurrentDrains_claimTheSameReadyRowOnlyOnce() FAILED
    org.mockito.exceptions.verification.TooManyActualInvocations at SlipCollabNotificationDispatchTest.java:93

SlipCollabNotificationDispatchTest > samePayloadFromDifferentSuccessfulEdits_keepsTwoIndependentOutboxRows() FAILED
    org.mockito.exceptions.verification.TooFewActualInvocations at SlipCollabNotificationDispatchTest.java:114

48 tests completed, 2 failed
BUILD FAILED
```

RED-A의 실제 관찰값은 동일 ready row에 대한 외부 push 2회, RED-B의 실제 관찰값은 동일 payload 두 저장 사건에 대한 outbox 저장 1회였다.

## 구현

- 협업 ACCEPTED 이력 ID를 `event_id`로 outbox에 저장하고 `(event_id, raw_recipient)`만 유일하게 했다. payload fingerprint는 사건 식별자로 사용하지 않는다.
- 후보 조회 후 조건부 UPDATE로 `PENDING/SENDING → SENDING`을 원자적으로 claim한다. claim 성공 뒤에만 외부 push를 실행한다.
- outbox ID를 notification-service의 idempotency key로 전달하고, notification-service는 이미 등록된 키를 gateway 재호출 없이 반환한다. 따라서 발송 수락 후 HTTP 응답 유실 재시도는 같은 요청을 재발송하지 않는다.
- 기존 행은 V109에서 `event_id=id`로 backfill한다. 실제 DB/Flyway 적용은 하지 않았다.

새 파일:

- `services/slip-service/src/main/resources/db/migration/V109__make_collab_notification_event_scoped.sql`
- `services/notification-service/src/main/resources/db/migration/V109__add_notification_idempotency_key.sql`
- `docs/dev-reports/2026-08-05-874-r45-fix.md`

## ① 새 상태·타이밍 조합과 결과

| 조합 | 결과 |
|---|---|
| scheduler ↔ afterCommit worker가 같은 ready row를 동시에 조회 | 조건부 claim 승자는 1개뿐이며 외부 push 1회로 GREEN |
| worker가 claim 후 외부 호출 전에 종료 | row는 SENDING lease 상태로 남아 lease 회수 대상이며, 외부 호출 전에는 SENT가 되지 않음 |
| 외부 발송 수락 후 slip-service 응답 유실 → lease 재시도 | 동일 outbox ID가 동일 idempotency key를 사용하므로 notification-service가 기존 요청을 반환하고 gateway를 재호출하지 않음 |
| `A→B`, `B→A`, `A→B` 정상 저장 | 각 ACCEPTED 이력 ID가 달라 `(event_id, recipient)` outbox 행 3개가 독립적으로 보존됨 |
| 동일 저장 사건에서 같은 수신자가 recipient 목록에 반복 | `distinct()`로 1행·1전달 유지 |
| 롤백된 저장 | enqueue와 이력 저장이 원 transaction에 참여하고 afterCommit drain만 외부 호출하므로 알림 0회 |
| executor 제출 거부·느린 auth/notification·backlog | 요청 thread 동기 fallback 없이 durable outbox와 scheduler에 남음 |

최종 좁은 검증에서 RED-A/RED-B 포함 `SlipCollab*` 47개와 `GlobalExceptionHandlerTest` 1개가 모두 통과했다.

## ② 식별자 grep 전수 조사

이번 fix에서 이동·개명한 식별자는 `enqueue` 계약(첫 인자 `eventId`)과 outbox `eventId` 필드다. 다음 grep 결과로 호출부·생성부를 전수 확인했다.

```text
SlipCollabEditService.java        enqueue(saved.getId(), ...)
SlipCollabNotificationOutboxService.java  enqueue(UUID eventId, ...)
SlipCollabNotificationOutbox.java         eventId / getEventId()
```

기존 `fingerprint` 식별자는 안정성 테스트와 기존 데이터 호환을 위해 제거하지 않고 비유일 payload 보조값으로 유지했다. `findByFingerprint`는 repository 호환 계약으로 남아 있으나 enqueue 차단 조건에서는 더 이상 사용하지 않는다.

`sendUserPushWithResult` 호출부는 4-인자 멱등 키 계약으로 모두 대조했고, 3-인자 호환 overload는 기존 소비자 보호용으로 유지했다. UUID를 사용자 응답에 추가하지 않았다.

## R46 — notification 마이그레이션 번호 정정

R45에서 notification-service 마이그레이션을 slip-service 기준 번호인 V109로 명명했으나, notification-service의 실제 최고 순번은 V7이고 Flyway `out-of-order: false`가 설정되어 있다. 따라서 파일명을 다음 순번으로 정정했다.

- `services/notification-service/src/main/resources/db/migration/V109__add_notification_idempotency_key.sql` → `services/notification-service/src/main/resources/db/migration/V8__add_notification_idempotency_key.sql`
- SQL 내용과 R45의 멱등 키·event 범위 claim·중복 방지 동작은 변경하지 않았다.
- slip-service의 V108·V109 마이그레이션은 변경하지 않았다.

파일명 참조 전수 조사 결과, 기존 V109 파일명은 이 보고서 안에서만 2줄(기존 R45 기록 1줄과 이 R46 개명 기록 1줄) 검색되며, services 디렉터리의 소스·설정 참조는 0건이다. 기존 R45 기록은 이력 보존을 위해 삭제하지 않았다.
