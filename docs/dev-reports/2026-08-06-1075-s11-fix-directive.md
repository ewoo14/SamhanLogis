# PR #1078 · 이슈 #1075 — S11 SOL 머지 전 최종 재수렴 지시서

## 1. 판정

**실 사용자 경로 재현 결함 2건, 증거 무결성 BLOCK 1건. 머지 비권고.**

- BLOCK-1 — 견적 후보 모달이 열리며 발생한 blur가 사용자가 고르지 않은 부분 문자열을 먼저 확정한다. 재현 난이도: **쉬움**.
- BLOCK-2 — 견적에서 확정 품목을 지운 뒤 blur하면 지운 모델명이 되살아난다. 재현 난이도: **쉬움**.
- EVIDENCE-BLOCK — S9가 복원한 `origin/main` 단정 2개를 S10이 다시 제거했다. `origin/main` 18개 중 현재 누락 2개다.

같은 공용 `ProductAutocomplete`를 쓰는 판매전표에서는 동일한 삭제 절차 후 빈 값이 유지됐다. 따라서 BLOCK-2는 공용 컴포넌트 자체가 아니라 견적 소비자 배선의 회귀다.

## 2. 사용자 재현과 관찰 결과

### BLOCK-1 — 모달 취소 전에 blur lookup이 부분 문자열을 확정

실 Chromium mock renderer에서 다음 순서로 매번 재현됐다.

1. `/sales/estimates/new?mockRole=MASTER` 진입.
2. `라인 1 모델명`에 `AJ` 입력.
3. `품목 검색 결과` 모달이 열린 뒤 300ms 대기.
4. 후보를 고르지 않고 `취소`.

기대값은 품목명·단가 공란이다. 실제로는 품목명이 **`(샘플) AJ`**, 단가가 **`1000000`**으로 채워졌다. 사용자가 모달에서 아무 후보도 확정하지 않았는데 blur exact lookup 결과가 라인에 선반영됐다.

호출 흐름은 다음과 같다.

```text
AJ 부분 검색 완료
→ 결과 모달을 열기 위해 input blur
→ AsyncAutocomplete.handleBlur가 onInputBlur('AJ')를 즉시 호출
→ EstimateFormPage가 modelName='AJ'를 쓰고 handleModelLookup 예약
→ lookupProductByModelName('AJ') 결과를 productId·품목명·단가로 반영
→ 이후 모달 취소는 이미 반영된 라인을 되돌리지 않음
```

`handleBlur`의 모달 전환 보호(`preserveDraftOnNextFocusRef`)는 120ms 타이머 안쪽에 있지만, S10의 `onInputBlur` 호출은 그 보호보다 앞에서 동기 실행된다. 따라서 blur와 모달 선택이 겹치면 blur lookup과 모달 선택 lookup이 둘 다 시작된다. 최신 요청 가드는 나중 선택이 끝까지 진행된 경우 최종 덮어쓰기 충돌은 막지만, 취소 경로의 선확정과 불필요한 lookup은 막지 못한다.

### BLOCK-2 — 견적 삭제값 부활, 판매전표는 정상

견적 재현:

1. `/sales/estimates/new?mockRole=MASTER`에서 `라인 1 모델명`에 `AJ040` 입력.
2. 단일 후보 자동 확정으로 입력값이 `AJ040RXH4BC1`이 된 것을 확인.
3. 입력을 다시 클릭하고 `Delete`를 누른 뒤 blur.

기대값은 공란 유지다. 실제값은 **`AJ040RXH4BC1`**로 복원됐다.

원인은 두 소비자 계약의 조합이다. 빈 draft에서는 견적의 S10 `onInputBlur`가 즉시 return하고, 이후 공용 컴포넌트가 `onChange(null)`을 보내지만 `handleProductSelection`은 `!product` 조건으로 null을 무시한다. controlled `value`가 남으므로 blur 뒤 기존 선택 레이블이 다시 표시된다.

대조로 `/sales/new?mockRole=MANAGER` 판매전표에서 같은 `AJ040` 확정 → 클릭 → `Delete` → blur 절차를 수행하면 입력값은 공란으로 유지됐다. 판매전표의 `applyProductSelection`은 null을 실제 품목 해제로 처리한다.

### 첫 각도 — 저장·발송 차단

- 정상 후보를 모달에서 선택한 coedit 견적은 임시저장·발송 버튼까지 활성 상태로 도달했다.
- 판매전표의 동일 공용 컴포넌트 경로는 위 삭제 대조와 기존 저장 계약에서 회귀를 재현하지 못했다.
- 다만 BLOCK-1의 nonempty blur마다 `lookupLoading`이 다시 켜져 견적 저장·발송 busy gate가 lookup 동안 반복 차단된다. 특히 모달 진입 blur는 사용자 확정 전 불필요한 차단이다.

## 3. `origin/main` 단정 대조와 본래 계약

다음 두 파일을 `git show origin/main:...`의 `expect(...)` 원문 문자열 부분집합으로 다시 대조했다.

```text
1062-line-input-ux.spec.ts       origin 18 · current 46 · missing 2
bundle-set-options.spec.ts       origin 48 · current 48 · missing 0
```

누락 2개는 S8이 지적하고 S9가 원문 복원했던 바로 그 단정이다.

```ts
await expect(page.getByTestId('estimate-form-line-3')).toBeVisible({ timeout: 10_000 })
await expect(page.locator('[data-testid^="estimate-form-line-"][data-price-source]')).toHaveCount(4)
```

S10은 provider 실패 폴백 시나리오를 coedit 구조 잠금 시나리오로 다시 바꾸면서 위 두 단정을 제거했다. 따라서 S10 보고서의 “origin/main 기준 18개 단정을 삭제하지 않았다”는 재현되지 않는다. bundle 스펙에서는 기준 단정 누락이 없다.

본래 목적 중 부분 문자열 후보 모달, 후보 1건 자동 확정, 후보 표의 규격·단가, 선택 후 단가 반영, UUID 비노출은 Chromium 경로에서 도달했다. coedit은 기존행 값 변경 허용, trailing 행과 라인 추가·삭제 잠금, 신규 작성 자동 빈행이 도달했다. 그러나 BLOCK-1·2 때문에 후보 취소와 clear 계약은 성립하지 않는다.

## 4. 수정 지시

1. `AsyncAutocomplete`의 blur draft callback을 모달 전환·후보 클릭·확정 선택과 구분한다. 모달을 열기 위한 blur에서는 소비자 exact lookup을 호출하지 않는다.
2. 견적의 lookup 권위는 한 경로로 수렴시킨다. 공용 검색 후보 선택은 `selectedProductRef` 경로로 한 번만 확정하고, 단순 focus 왕복이나 선택 직후 blur가 두 번째 exact lookup을 만들지 않게 한다.
3. 견적 `handleProductSelection(null)`이 판매전표와 대칭으로 productId/modelName/productName/productType/catalogUnitPrice 및 관련 확정 상태를 실제 해제하도록 한다. 빈 draft blur가 이전 controlled value를 복원하지 않게 한다.
4. 회귀 테스트를 실제 `ProductAutocomplete`로 추가한다: 모달 취소 시 미확정, 모달 선택과 blur 경쟁 시 선택값 단일 확정, 확정값 clear 후 공란 유지, 단일 후보 확정 후 외부 클릭 시 lookup 1회, 견적 저장·발송 및 판매전표 저장 비차단.
5. `1062-line-input-ux.spec.ts`에는 provider 실패 폴백 자동 빈행 시나리오를 coedit 구조 잠금 시나리오와 별도로 복원하고, 위 `origin/main` 단정 2개를 원문 그대로 되살린다. 수정 후 두 파일 모두 문자열 부분집합 누락 0을 다시 산출한다.
