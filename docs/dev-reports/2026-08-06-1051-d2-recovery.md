## 축 A와 축 B

아래에서 축 A는 `product_id ∉ products 전체 ID`, 축 B는 `product_id ∈ products WHERE is_deleted=false AND model_code IS NULL`이다. 따라서 한 line이 동시에 A와 B일 수 없다.

```sql
-- :all_product_ids와 :axis_b_product_ids는 product_db에서 별도 추출한 집합이다.
SELECT 'slip_lines' AS table_name,
       count(*) FILTER (WHERE product_id <> ALL(:all_product_ids)) AS axis_a_lines,
       count(*) FILTER (WHERE product_id = ANY(:axis_b_product_ids)) AS axis_b_lines,
       count(*) FILTER (WHERE product_id <> ALL(:all_product_ids)
                         AND product_id = ANY(:axis_b_product_ids)) AS axis_a_and_b_lines,
       count(*) FILTER (WHERE product_id = ANY(:axis_b_product_ids)
                         AND product_id = ANY(:all_product_ids)) AS axis_b_only_lines
FROM slip_lines WHERE is_deleted=false;
```

동일 SQL을 세 테이블에 실행한 출력:

```text

slip_lines                   303         2177                  0              2177
estimate_lines                 0         1993                  0              1993
partner_order_lines            2         2048                  0              2048
```

`#1019의 이름으로 품목을 찾는다`는 축 B 관계 자체의 결과는 아니다. 저장 관계는 이미 UUID로 활성 product를 정확히 가리키고 상세 화면도 snapshot을 쓴다. 이름 경로는 회계 `MonthEndCloseService`가 과거 line의 `productName/modelName`으로 현재 product를 재해소할 때 발생한다. 현재 코드의 `effectiveProductMatch()`는 exact modelName 후보가 있어도 그 product의 불변 `modelCode`가 null이면 그 후보를 채택하지 않고 label(`productName`) 결과로 되돌아간다. 즉 #1019 4,225건은 회계 재검증에서 실질적으로 label 경로에 의존한다.

product-service의 현재 3단 label resolver(`catalog exposed model → alias → unique LIKE`)를 같은 규칙으로 두 DB 출력에 적용한 원문 출력:

따라서 4,225건 중 현재 같은 UUID로 label 재해소되는 것은 192건, `AMBIGUOUS` 4,024건, `NOT_FOUND` 9건이며 다른 UUID로 잘못 확정된 건은 0건이다. 0건은 이 4,225 전수 결과이지 표본 0이 아니다. 다만 이름 변경·재사용 후 잘못 연결될 lifecycle 위험은 남고, 현재 4,033건은 이름 경로에서 유일하게 해소되지 않는다.

### 축 B의 다섯 항목

1. **무엇이 끊겼나:** UUID 연결은 끊기지 않았다. 활성 product 33개 중 `model_code`가 null이라 회계의 불변 식별 검증이 끊겼다. #1019 모집단은 4,225 line이고, estimate까지 포함하면 최종 시점 6,218 line이다.
2. **사용자에게 보이는 것:** 상세 화면에는 snapshot 이름/모델명이 정상 표시된다. 일반 조회 오류는 아니다. 회계 일마감 재검증은 4,033/4,225가 현재 label로 유일 해소되지 않아 가격·고정DC 검증이 미확정될 수 있다.
3. **복구 방안/대상:** line 4,225개를 relink하지 않는다. 먼저 33개 product master의 영속·불변 코드를 원본 이카운트/승인 매핑으로 보강하면 UUID를 유지한 채 4,225 line의 향후 식별 기반을 복구할 수 있다. 단, 현재 snapshot에 과거 modelCode 컬럼이 없으므로 과거 회계 재검증 코드가 새 master code를 곧바로 증명하는지는 별도 설계가 필요하다.
4. **오연결 위험:** 임의로 `model_code=model_name`을 채우거나 line을 이름으로 재연결하면 다른 SKU의 적용가격·고정DC로 회계 검증되고 품목별 매출/원가가 이동한다. UUID는 정상인 부류이므로 **지금 되살린다는 명목의 line 변경이 미변경보다 더 위험하다.**
5. **화면/배치:** 제품 PATCH DTO에는 `modelCode`가 없고 기존 modelCode는 불변 계약이다. 일반 사용자가 화면에서 고칠 수 없다. 승인된 원본에 따른 import/migration 배치 또는 별도 관리 기능이 필요하다.

## 권고 우선순위와 이슈 분리

1. **③의 5건 검증:** slip 3건은 화면 재선택 후보, partner-order 2건은 원문 확인 후 최소 배치 후보다. 완료 상태/재고 movement가 없어 가장 안전하다.
2. **②는 복원 금지:** QA797 product undelete가 아니라 QA 문서·최근단가 잔재를 하나의 공유-DB QA 정리 작업으로 다룬다.
3. **①은 dev 환경 작업:** 운영 복구와 분리해 동일 seed 세대 reset/보존 정책으로 처리한다.
4. **축 B는 데이터 relink 금지:** 33 master의 불변 코드 출처와 회계 snapshot 계약을 먼저 정한다.

이 이슈는 **다섯 갈래로 나누기를 권고**한다. (1) legacy seed 세대 불일치 300건, (2) QA797 공유 데이터 잔재 612건+최근단가 8건, (3) 사라진 partner-order source에서 발행된 slip UUID 오류 3건, (4) partner-order 자체의 부재 UUID 2건, (5) 정상 UUID이나 불변 modelCode가 없어 이름 fallback에 의존하는 #1019 4,225건이다. 특히 (3)과 (4)는 후보 모델명만 같을 뿐 UUID 버전·생성자·source 생존 여부가 달라 생성 원인을 하나로 단정할 수 없다. 분리 결정은 개발책임자 몫이며, 본 권고의 근거는 복구 수단과 오연결 시 영향 범위가 서로 다르다는 점이다.
