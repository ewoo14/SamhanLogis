## 1. 결론

R13의 행 순서 기반 오귀속은 고쳐졌다. 교차 배치 `head-A, head-B, child-A, child-B`는 행 순서와 무관하게 `[[head-A, child-A], [head-B, child-B]]`로 복원됐다. Slip·Estimate는 동일한 `BundleSetInstanceKeyPolicy`를 호출하고, signature가 유일할 때 같은 signature끼리 같은 새 key를 받는다.

그러나 duplicate signature를 keyless로 허용하기 위해 R14가 추가한 조기 `continue`가 **기존 head 삭제 무결성 검사를 통째로 우회한다.** 복원과 일반 수량 편집은 HTTP 200이지만, 사용자가 편집 화면에 실제로 노출된 `×`를 눌러 첫 인스턴스의 head 한 행만 제거해도 서비스가 예외 없이 저장한다. 결과는 구성품이 남은 0-head 계보다. “복원을 차단하지 않는다”는 PM 결정은 지켜졌지만, 현재 상태는 “안전하게 쓸 수 있다”까지 충족하지 않는다.

따라서 이 라운드는 **복원 거부를 재도입하라고 요구하지 않는다.** duplicate 복원과 비파괴 편집을 계속 허용하면서, 경계를 증명할 수 없는 parent에서 head 일부 삭제만 안전하게 막고 사용자가 취할 수 있는 복구 경로를 화면에 제공해야 한다.

## 2. HIGH — duplicate-signature keyless 편집에서 head 한 행 삭제가 저장된다

### 2.1 불변식

기존 라인의 `parentSetModel`이 남아 있고 원본에 head가 있었다면, 편집 결과도 해당 보존 인스턴스에 head가 정확히 하나여야 한다. 경계를 증명할 수 없는 duplicate-signature keyless parent라면 최소한 다음을 만족해야 한다.

1. 복원 자체는 HTTP 200이어야 한다.
2. 수량·단가·메모 같은 비파괴 편집은 HTTP 200이어야 한다.
3. 일부 원본 head가 사라졌는데 같은 불확정 parent의 다른 라인이 남는 저장은 HTTP 400 `INVALID_INPUT`이어야 한다.
4. 거부 시 저장, revision 생성, soft delete, 수정시각 변경이 없어야 한다.
5. 사용자는 화면에서 왜 일부 삭제가 불가능한지와 가능한 정리 경로를 알아야 한다.

### 3.2 signature 구성 요소

공통 정책 `BundleSetInstanceKeyPolicy.java:134-154`의 signature는 정확히 다음 5개다.

1. `remoteOption`
2. `remoteExcluded`
3. `panelOption`
4. `panelShape360`
5. `materialIncluded`

문자열은 `null`, blank를 모두 `null`로 정규화하고 그 밖의 값은 `trim()`한다. Boolean은 값을 그대로 비교한다. `parentSetModel`은 먼저 후보를 묶는 축이며 signature 필드 자체는 아니다. 기존 `instanceKey`, parent product ID, 생성 순번, 원본 인스턴스 식별자는 signature에 없다.

### 3.3 충분성 판단

이 signature는 **같은 parent의 두 인스턴스가 서로 다른 옵션 조합을 골랐을 때만** 소속을 구분하기에 충분하다. 같은 모델의 같은 옵션 세트를 두 번 넣는 정상 데이터에서는 두 head와 모든 child가 같은 signature를 갖는다. snapshot line에는 인스턴스 경계를 증명할 별도 식별자가 없으므로 이는 구현 실수가 아니라 정보 부족이다.

R14의 정책은 다음과 같다.

- signature별 head가 하나이고 모든 child signature가 head에 대응하면 UUID를 생성해 materialize한다.
- head signature 중복 또는 head 없는 signature가 하나라도 있으면 그 parent 전체를 keyless로 두고 WARN한다(`BundleSetInstanceKeyPolicy.java:89-123`).

따라서 unique 사례의 행 순서 오귀속은 해결했지만, 동일 옵션 반복 세트에서는 duplicate가 필연적이다. 공유 DB의 현재 후보 5건도 모두 이 duplicate 경로였다. 다만 5건 전부 QA 산물이므로 실제 운영 발생률은 이 DB로 판정할 수 없다.

## 4. duplicate keyless 복원 뒤 실제 동작

백엔드 IT 로그:

```text
R12-RESTORE-MATERIALIZE|restore=HTTP200|beforeGroups=0|rows=8|heads=2|instanceKeys=0
R12-RESTORE-EDIT|HTTP=200
```

즉 duplicate signature는 복원 HTTP 200, 8행/2head 유지, key 0개이고 이어지는 수량 편집도 HTTP 200이다. keyless라는 이유만으로 다음 편집 전체가 막히지는 않는다.

문제는 삭제 분기다. 현재 사용자가 할 수 있는 안전한 경로가 화면에 안내되지 않고, 행별 삭제는 전부 가능해 보인다. HIGH 수정에서는 다음 사용자 경로를 명시적으로 제공해야 한다.

- 수량·단가 등 비파괴 편집: 계속 허용
- 불확정 parent의 head 일부 삭제: 구체적 안내와 함께 거부
- 정리: 그 불확정 parent의 모든 행을 함께 삭제한 뒤 정상 세트를 다시 추가
- unique/keyed 인스턴스: 기존처럼 인스턴스 전체 삭제 허용

webServer의 상대 config 경로 기준이 Playwright config 디렉터리였던 문제다.

```text
VITE_APP_VERSION는 YYYY/MM/DD-{번호} 형식이어야 합니다: 2026/08/11-R15
```

앱 버전 형식을 `2026/08/11-15`로 고쳤다.

```text
page.waitForResponse: Timeout 20000ms exceeded
locator.click: Timeout 20000ms exceeded
```

브라우저 기본 `confirm()` 상태에서 full-page screenshot을 먼저 기다려 POST가 발생하지 않은 harness 순서 문제였다.

```text
locator('[data-testid="sales-slip-edit-button"]'): Timeout 20000ms exceeded
```

permission mock이 빈 권한을 반환해 수정 버튼이 숨겨진 문제였다.

```text
getByRole('button', { name: '닫기' }): strict mode violation: resolved to 3 elements
```

앱 업데이트/알림/모달의 동명 버튼 중 modal backdrop의 정확한 버튼으로 좁혔다.

임시 Playwright spec/config는 최종 성공과 스크린샷 채취 뒤 제거했다. 제품 소스에는 QA harness를 남기지 않았다.

주의: 이 Playwright 축은 HEAD Desktop의 실제 제어와 사용자 표면을 검증하지만 backend 응답은 mock이다. 배포 백엔드에 V119가 없으므로 live backend restore/edit를 성공했다고 확대 해석하면 안 된다.

## 9. 구현자 수정 지시서

### 9.1 수정 목표

복원 거부를 재도입하지 말고, duplicate-signature keyless 상태에서 비파괴 편집을 허용하되 head 일부 삭제로 0-head lineage가 생기지 않게 한다. 서버 로그 WARN만으로 끝내지 말고 사용자가 가능한 다음 행동을 화면에서 알 수 있게 한다.

### 9.2 좌표 전수

1. 공통 판정
   - `BundleSetInstanceKeyPolicy.java:81-123, 134-154`
   - unique materialize / duplicate keyless 정책을 유지한다.
2. Slip 편집 무결성
   - `BundleLineageResolver.java:170-218, 271-317`
   - ambiguous 조기 `continue`를 단순 제거하면 정상 round-trip이 다시 400이 될 수 있으므로 금지한다.
   - 원본 head line ID와 retained line ID를 별도로 비교해 “head 일부 제거 + 같은 ambiguous parent 잔존”만 거부한다.
3. 저장 순서
   - `SalesSlipUpdateService.java:97-127`
   - 검증은 `slip.update...`/revision 생성 전에 끝나야 한다.
4. API 사용자 신호
   - Slip/Estimate 상세 또는 복원 응답에 UUID를 노출하지 않는 업무 상태(예: ambiguous legacy lineage)를 제공한다.
   - 명칭은 API 계약과 화면 문구가 일치해야 한다.
5. Desktop
   - `SlipDetailPage.tsx:632-636, 1238-1259, 3436-3449, 3599-3612`
   - 복원 완료 및 후속 편집에 명시 경고/조치 문구를 표시한다.
   - 문구 예: “구 전표의 동일 세트 경계를 확정할 수 없습니다. 수량·단가 수정은 가능하지만 일부 세트의 head 삭제는 할 수 없습니다. 해당 모델 세트 전체를 삭제한 뒤 다시 추가하십시오.”
   - API가 거부하면 일반 실패 토스트가 아니라 같은 조치 문구를 보여 준다.
6. Estimate
   - 공통 복원 정책과 동일한 ambiguous 상태 신호를 사용한다. 정상 견적 화면이 keyless 다중 인스턴스를 새로 만들지 않는 R10 계약을 유지한다.

### 9.3 RED-A — 반드시 새로 고정할 표적

1. duplicate signature `[head-A, child-A, head-B, child-B]` revision 복원:
   - restore 200, 8행/2head 보존, key 0 허용.
2. 같은 전표의 수량 수정:
   - update 200, keyless round-trip 유지.
3. 첫 head line ID만 요청에서 제거하고 child-A/head-B/child-B 유지:
   - HTTP 400 `INVALID_INPUT`, 저장 0회, revision 0건, soft delete 0건, 수정시각 불변.
4. 두 번째 head만 제거하는 대칭 조합:
   - 동일하게 400.
5. ambiguous parent의 모든 행을 제거:
   - 200으로 정리 경로 제공. 다른 parent/일반 라인은 보존.
6. Desktop:
   - 복원 성공, 경고 노출, 수량 수정 200.
   - head 일부 삭제 시 구체적 조치 문구가 보이고 성공으로 오인하지 않음.
7. Slip·Estimate:
   - 같은 공통 ambiguous 판정/표시 계약을 소비함을 테스트한다.

### 9.4 RED-B — 절대 잃지 않을 기존 표적

1. 연속 행 복원 → 후속 편집 HTTP 200.
2. 교차 행 unique signature 복원 → `[[head-A, child-A], [head-B, child-B]]`.
3. duplicate signature 복원 자체 HTTP 200; 복원 단계 `INVALID_INPUT` 금지.
4. 공통 정책 한 곳, Slip·Estimate 함께 호출.
5. `PartnerProductPriceMemoryIT` 수정 금지, 30/30.
6. R10 정상 견적 화면이 keyless 다중 인스턴스를 재생성하지 않음.
7. V119 대상 8행/head 2/서로 다른 품목 4, 전표 전체 공급가 4,729,797원/VAT 472,980원.
8. 수량 0 → 422.
9. 비-head 삭제 → 200.

11. 복원 QA 스크린샷과 실제 버튼 경로 유지.

### 9.5 새 조합 전수

- 배열: 연속 `[H,C,H,C]`, 교차 `[H,H,C,C]`, child-first/head-last, 세 인스턴스, 다른 parent 교차.
- signature: 모두 동일, 모두 다름, 둘만 중복, child에만 unmatched, null/blank/공백 trim, Boolean null/false 차이.
- key: 전부 keyed, 전부 keyless, keyed+keyless 혼합.
- 편집: 첫 head 삭제, 두 번째 head 삭제, head의 product 교체, non-head 삭제, 수량/단가만 변경, ambiguous parent 전부 삭제, keyed 인스턴스 하나 전체 삭제.
- lifecycle: 복원 직후, 새로고침 뒤, 재복원 뒤, 동료 수정 뒤, 시스템 복원 뒤.
- 도메인: Slip restore/update, Estimate restore 및 이후 견적 편집/전환.

### 9.6 중단 조건

**제 전제가 틀렸다면 고치지 말고 중단·보고하십시오.** 특히 다음 중 하나를 코드·HTTP 증거로 보이면 임의 수정하지 않는다.

- 현재 API가 이미 ambiguous keyless head 일부 삭제를 4xx로 막는다.
- 삭제된 head가 남은 child의 계보 무결성과 무관하다는 별도 도메인 규칙이 있다.
- snapshot/line에 이번 검토가 놓친 신뢰 가능한 인스턴스 경계 정보가 있어 duplicate도 안전하게 materialize할 수 있다.
- ambiguous parent 전부 삭제가 기존 계약상 허용될 수 없다.

그 경우 실제 불변식, 요청/응답 원문, 저장 전후 DB 상태를 첨부해 PM 판단을 다시 받아야 한다.
