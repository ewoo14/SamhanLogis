## 1. 각도 1 — 새 상태 분류의 실제 도달성

### 1.1 HTTP 오류 형태는 분류기까지 보존된다

`createAuditApi.listAuditLogs()`는 공통 Axios 인스턴스 `apiClient`를 직접 사용한다. 응답 인터셉터는 401을 제외한 오류를 `Promise.reject(err)`로 원형 보존하고, 401도 세션 처리 뒤 같은 오류를 reject한다.

- `clients/desktop/src/renderer/api/client.ts:106-129`
- `clients/desktop/src/renderer/api/apiError.ts:18-24`
- `clients/desktop/src/renderer/api/createAuditApi.ts:80-86`

따라서 실제 HTTP 404·403·5xx는 `AxiosError.response.status`로 `getApiErrorInfo()`에 도달한다. 네트워크 실패는 AxiosError이지만 `response`가 없어 status가 `undefined`이고 `temporary`로 내려간다. 별도 fetch 변환이나 status를 지우는 wrapper는 이 일곱 경로에 없다.

| 입력 | 분류 | 정적 판정 |
|---|---|---|
| Axios 404 + `treat404AsNotSupported=true` | `not-supported` | 도달 |
| Axios 404 + flag 없음 | `not-found` | 분류 함수에는 도달 가능하나 재고감사 정상 BE 계약에서는 사실상 미도달 |
| Axios 403 | `forbidden` | 분류 가능. 이번 환경에 실제 권한 거부 표본이 없어 화면 종단 실측은 **판정 불가** |
| Axios 5xx | `temporary` | 도달 |
| Axios 네트워크 실패 | `temporary` | 도달 |
| 비-Axios 오류 | `temporary` | 도달. mock 재고감사 응답 shape 오류가 이 경로를 실제 사용 |

### 1.2 404 정책은 6 대 1로 배선됐지만 재고감사의 `not-found`는 BE에서 나오지 않는다

`treat404AsNotSupported`는 세금계산서 2화면, 마감 3화면, DC 설정 1화면에만 있고 재고감사에는 없다. 이 6 대 1 배치는 현재 라우트 보유 현황과 일치한다.

- accounting-service: `audit-logs` 라우트 0건
- dc-config-service: `audit-logs` 라우트 0건
- inventory-service: `/inventory/audits/{id}/audit-logs` 존재

재고감사 컨트롤러는 부모 `InventoryAudit` 존재 여부를 조회하지 않고 `auditLogRecorder.listByEntity(id)` 결과를 바로 감싸 반환한다.

- `services/inventory-service/src/main/java/com/samhanair/logis/inventory/web/InventoryAuditController.java:211-215`

따라서 이력이 없는 유효 대상뿐 아니라 syntactically valid UUID에 row가 없어도 컨트롤러 결과는 `200 + []`다. 정상 화면에서 `아직 버전 이력이 없습니다`가 맞다. 반대로 R3가 정의한 재고감사 404 → `해당 대상의 버전 이력을 찾을 수 없습니다`는 현재 BE 정상 계약으로는 발화하지 않는다. 라우트/배포 불일치 404가 생기면 오히려 대상 부재로 오분류할 수 있다.

### 1.3 mock 모드는 한 상태가 아니며 R3 상태표를 재현하지 않는다

| 화면 | mock 실제 경로 | 사용자 상태 |
|---|---|---|
| 세금계산서 상세·편집 2개 | `mock.ts:12937-12941`의 `tax-invoices` audit fixture가 가로챔 | `200 + 샘플 이력`; 실제 endpoint 부재가 가려짐 |
| 재고감사 1개 | `mock.ts:9886-9902`의 넓은 `/inventory/audits` 목록 handler가 audit URL까지 선점해 page 객체 반환 | `res.data.data.map is not a function` → 비-Axios `temporary` |
| 마감 3개 | audit mock handler 없음 | `mock.ts:14100`에서 `null` → 실 HTTP fallthrough. 서버가 있으면 404 `not-supported`, 없으면 네트워크 `temporary` |
| DC 설정 1개 | mock은 `/api/v1/partner-dc-configs`만 처리하고 FE audit URL은 `/api/v1/dc-configs/.../audit-logs` | 실 HTTP fallthrough. 환경에 따라 `not-supported` 또는 `temporary` |

즉 mock 모드만으로 7화면 상태를 동일하게 증명할 수 없다. 위 판정은 fixture를 새로 만들지 않고 현재 라우팅 순서만 추적한 결과다.

## 2. 각도 2 — 반대급부와 기존 화면 도달성

### 2.1 화면 예외 전파는 없지만 오류가 모달 안에만 있지는 않다

React Query에 `throwOnError`가 없으므로 조회 실패는 page render를 throw하지 않는다. `AuditVersionHistory`도 unknown 오류를 안전하게 `temporary`로 처리한다. 저장·발행·마감·역마감·DC 수정·재고감사 전이 handler는 R3 diff에서 변경되지 않았다.

그러나 `AuditRevisionBadge`는 오류여도 빈 `logs`로 revision 수를 계산하여 화면 본문에 계속 **`수정 0회`**를 표시한다.

- `clients/desktop/src/renderer/components/audit/AuditOverlaySection.tsx:49-67`
- 일곱 화면 모두 `logs=[]`와 `isError=true`를 Badge에 전달

title만 `수정 이력을 불러오지 못했습니다`로 바뀌고 보이는 숫자는 0이다. 따라서 R3의 핵심 불변식인 “조회 실패를 이력 없음으로 오표시하지 않음”은 모달에서는 성립하지만 화면 헤더에서는 여전히 깨진다. 또한 오류가 “모달 안에서만 처리된다”는 커밋 설명도 사실이 아니다. 오류 상태가 Badge tooltip까지 전파된다.

이것이 **도달 결함 1**이다. endpoint가 없는 6화면은 정상 진입/행 선택만으로 상시 발화하고, 재고감사는 실제 조회 실패 때 발화한다.

### 2.2 기존 표면은 수량상 유지됐다

정적 전수 결과:

| 화면 | `AuditRevisionBadge` | `AuditOverlay` |
|---|---:|---:|
| InventoryAuditDetailPage | 1 | 1 |
| MonthEndClosingPage | 1 | 1 |
| PeriodCloseListPage | 1 | 1 |
| SalesClosingPage | 1 | 1 |
| SalesPartnerDcConfigPage | 1 | 1 |
| TaxInvoiceDetailPage | 1 | 1 |
| TaxInvoiceFormPage | 1 | 0 (원래 없음) |
| 합계 | **7/7** | **6/6** |

R3의 일곱 route diff는 `.catch(() => [])` 제거와 `error`/`treat404AsNotSupported` prop 추가뿐이다. mutation source 직접 변경은 없다. 따라서 저장·발행·마감·DC 설정의 직접 소스 회귀는 확인되지 않았다. 실제 사용자 mutation 종단은 브라우저와 실데이터 사용이 금지되어 **판정 불가**다.

### 2.3 404는 모달 클릭이 아니라 화면 진입/행 선택 때 발생하고 R3가 2회로 늘렸다

일곱 `useQuery`의 `enabled` 조건은 modal open 상태를 사용하지 않는다.

- 재고감사: route `id`가 있으면 즉시
- 세금계산서 상세: route `id`가 있으면 즉시
- 세금계산서 편집: edit mode + `editId`가 있으면 즉시
- 마감 3개·DC: 행을 선택해 `selected...`가 생기면 즉시

공통 QueryClient는 `retry: 1`이다(`clients/desktop/src/renderer/App.tsx:19-27`). R3 이전에는 `.catch(() => [])`가 실패를 성공으로 바꿔 재시도가 없었다. R3 이후에는 404가 React Query에 도달하므로 endpoint가 없는 각 entity마다 **최초 1회 + 재시도 1회 = 총 2회** 요청된다.

모달 열기는 `auditHistoryOpen`만 바꾸므로 그 자체로 새 요청을 만들지 않는다. audit query 자체에 무한 재시도 loop는 없다. 다만 새 entity 선택, 화면 remount/reconnect, realtime invalidate가 있으면 다시 bounded 2회 묶음이 발생할 수 있다.

따라서 “모달을 열면 매번 404”는 틀리고 “사용자가 기능을 열지 않아도 진입/선택만으로 404 두 번”이 실제 동작이다. 최신 정찰 문서 `docs/dev-reports/2026-08-10-1091-slice2-recon.md` 5.1의 클릭 시점 서술도 코드와 충돌한다.

이것이 **도달 결함 2**이자 증거 무결성 결함이다. 네트워크 요청은 무한 loop가 아니지만 R3가 상시 실패 요청을 1회에서 2회로 늘렸다.

## 3. 각도 3 — 사용자 관점의 정직성

`버전 이력 조회 기능이 아직 제공되지 않습니다`는 “현재 GET endpoint가 없다”는 좁은 사실에는 맞다. 그러나 6화면을 같은 문구로 묶으면 다음 두 상태를 구분하지 못한다.

- 세금계산서: 감사 row가 일부 존재하되 조회 endpoint가 없음
- 마감·DC: 조회 endpoint뿐 아니라 변경 기록 writer 배선도 없음

따라서 문구는 거짓이라고 단정할 수 없지만, 후자에서 “기록은 되고 있고 조회만 준비 중”이라는 기대를 만들 수 있어 불완전하다. 현재 mock 세금계산서는 샘플 이력을 보여 이 기대를 더 강화한다.

개발책임자 선택지는 다음과 같다. 이번 리뷰는 선택하지 않는다.

| 선택지 | 얻는 것 | 대가 |
|---|---|---|
| A. 활성 버튼 + 현재 공통 문구 유지 | 향후 endpoint 연결 시 같은 진입점을 즉시 사용; `200 + []`와 404는 구분 | 미사용 사용자에게도 entity당 404 두 번; 기록 부재와 조회 부재를 혼동; 미완성 인상 |
| B. endpoint 없는 6화면에서 버튼 숨김 | 404 제거; 존재하지 않는 기능에 대한 기대 제거 | 예정 기능의 위치와 발견 가능성 상실; endpoint 연결 때 재노출 작업 필요 |
| C. 버튼을 비활성/준비 중으로 두고 도메인별 문구 사용 | 요청 없이 위치 보존; 세금계산서와 마감/DC의 기록 상태를 정직하게 구분 가능 | capability 설정과 문구 유지 비용; 기록 상태가 바뀔 때 UI 계약도 동기화 필요 |

## 4. 결함 3 — mock 증거 무결성

R3 단위 테스트는 synthetic AxiosError로 분류 함수 자체를 확인한다. 실제 `apiClient` 오류 shape와는 맞지만, 현재 mock runtime은 7화면에서 그 상태표를 동일하게 만들지 않는다.

- 세금계산서는 없는 실 endpoint 대신 샘플 성공 이력을 보여 준다.
- 재고감사는 잘못된 response shape 때문에 `temporary`가 된다.
- 마감·DC는 mock 밖 실 네트워크에 의존한다.

따라서 mock 캡처나 mock 화면을 “6화면 404 분류가 실제 도달했다”는 증거로 쓰면 안 된다. 이는 테스트 개수/품질 지적이 아니라 현재 산출 증거가 실제 사용자 경로를 대표하지 못하는 **증거 무결성 결함**이다.

독립 Codex Challenge도 읽기 전용으로 실행했으나 PowerShell stdin/JSON 스트림 문제로 최종 agent message를 회수하지 못했다. 해당 실행 결과는 판정 근거로 사용하지 않았다.

## 5. 지금 고칠 것 / 분리할 것

### 지금 고칠 것

1. **조회 오류인데 `수정 0회`로 보이는 Badge 계약**
   - 오류 시 숫자 0을 사실로 표시하지 않아야 한다.
   - 모달의 `data-error-kind`와 헤더 Badge가 같은 성공/실패 의미를 가져야 한다.
2. **endpoint 부재를 알면서 선조회하고 404를 재시도하는 계약**
   - 버튼 노출/숨김 선택과 별개로, 실제 요청 trigger와 retry 정책을 의도와 맞춰야 한다.
   - 적어도 404를 일시 장애처럼 재시도하여 R3 이후 요청을 두 배로 만드는 상태는 닫아야 한다.
3. **mock runtime의 세 상태 불일치와 정찰 문서의 호출 시점 오기**
   - mock을 근거로 쓸 경우 세금계산서 성공 가림, 재고 shape 오류, 마감/DC 실 HTTP fallthrough를 먼저 해소해야 한다.
   - `버튼을 눌렀을 때 404`를 `화면 진입/행 선택 즉시 최초+재시도`로 바로잡아야 한다.

### 분리할 것

1. accounting·dc-config audit endpoint 신설
2. 마감·DC 및 product-service 등 audit writer 배선
3. 과거 감사 row backfill
4. 재고감사 audit endpoint의 부모 존재 확인 및 404 계약 추가 여부
5. 협업 changeSet·SlipDetailPage·mobile-staff 등 이번 슬라이스 밖 표면

위 항목은 개발책임자 판단 대기 범위다. 특히 실제 감사 표본이 없는 도메인에 가상 revision을 만들어 검증해서는 안 된다.

## 최종 판정

**도달 결함 3건 · 현재 상태 머지 비권고.**

R3의 Axios 상태 분류는 실제 오류 형태와 맞고 화면 예외도 만들지 않는다. 그러나 7/7 Badge가 실패를 계속 `수정 0회`로 표시하고, 부재 endpoint 요청은 모달과 무관하게 선발화하며 R3 이후 두 번씩 나가고, mock 증거는 실제 7화면 상태를 대표하지 못한다.
