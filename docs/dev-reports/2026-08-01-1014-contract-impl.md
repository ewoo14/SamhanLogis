## 확인 1 — 재사용 계약과 첫 적용

- 재사용할 기존 계약: `services/accounting-service/src/main/java/com/samhanair/logis/accounting/domain/TaxInvoiceBatch.java:21-35, 88-107`의 RDB 배치 스냅샷(`dataSnapshotJson`, gzip+base64, `BaseEntity` 7 audit + Soft Delete), `services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/HometaxExportService.java:246-317`의 생성 시 스냅샷 저장, `:324-367`의 스냅샷 재생성, `services/accounting-service/src/main/java/com/samhanair/logis/accounting/web/AccountingReportController.java:323-369`의 날짜 범위 이력 목록·상세 조회를 재사용한다.
- 첫 적용: 거래처별 원장. 세 대상 중 인쇄 양식 revision 고정이 필요한 거래명세서와 입력 보조 상태까지 복원해야 하는 내일자 전표보다 저장 payload가 단순한 조회 결과 스냅샷이며, 기존 조회·인쇄 API를 유지한 채 저장/이력 계약을 검증할 수 있다.
- Flyway 확인: 저장소 전체 migration 최대 버전은 `V90__seed_accounting...sql` 계열이므로 신규 migration은 동시 트랙 충돌 여유를 둔 `V95`로 계획한다. 적용된 migration은 수정하지 않는다.

## 구현 내용

- 기존 `tax_invoice_batches` 테이블과 `TaxInvoiceBatch`의 gzip+base64 스냅샷 저장 방식을 재사용했다. `document_type`/`document_key`만 신규 컬럼으로 추가해 홈택스(`HOMETAX`)와 원장(`PARTNER_LEDGER`) 이력을 분리했다.
- `SnapshotCompression`으로 홈택스 계약과 동일한 gzip+base64 JSON 코덱을 공통 사용했다.
- 거래처별 원장 조회가 기존 응답을 반환한 직후 자동 저장한다. 기존 조회·인쇄 응답 형식과 쿼리 경로는 변경하지 않았다.
- `/accounting/journals/ledger-history` 날짜별 목록과 `/accounting/journals/ledger-history/{batchNo}/restore` 복원 조회를 추가했다. 사용자 응답에는 UUID를 넣지 않고 batchNo/partnerCode만 사용한다.
- 신규 migration은 `services/accounting-service/src/main/resources/db/migration/V95__add_document_snapshot_type.sql`이며 기존 migration은 수정하지 않았다.
- 이번 슬라이스에서는 거래명세서·내일자 전표 화면/서비스를 변경하지 않았다. 거래명세서 양식 revision pin은 다음 적용 슬라이스의 계약 입력으로 남겼다.

## 2026-08-01 추가 확인 — `getLedger` 계약 드리프트 복구

### 1. 원인 판정

이번 변경에서 바뀐 것은 `LedgerImageService.getLedger`의 조회 인자가 아니라, 자동 저장 배치의 `processedBy`에 `X-User-Id`를 넣기 위해 추가한 4번째 `UUID actorUserId` 인자였다. 저장 기능은 조회 결과를 저장할 뿐이므로 기존 조회 API에 actor 인자를 추가할 근거가 없다.

근거:

- 자동 저장 전 기존 호출자와 회귀 테스트는 `getLedger(partnerCode, from, to)` 3인자 형태였다.
- `LedgerSnapshotService.capture(..., UUID actor)`도 actor를 사용하지 않고 기존 3인자 호출을 했다.
- Playwright 문서 단언은 `AccountingReportController`의 `getLedger(partnerCode, from, to)` 계약을 명시하고 있었다.

따라서 시그니처 변경은 필요 변경이 아니라 저장 기능에 딸려온 변경으로 판정했다. 문서 단언은 삭제·완화하지 않고 실제 코드에 맞췄다.

### 2. 수정

- `LedgerImageService`의 4인자 overload를 제거하고 `getLedger(String partnerCode, LocalDate from, LocalDate to)`만 유지했다.
- `AccountingReportController`도 `ledgerImageService.getLedger(partnerCode, from, to)`를 호출하도록 되돌렸다.
- 자동 저장(`TaxInvoiceBatch` gzip+base64 snapshot), 이력 조회, 복원 endpoint는 그대로 유지했다.
- 기존 3인자 저장 테스트와 권한 가드는 수정하지 않았다.

### 3. `getLedger` 호출자 전수 목록

수정 후 `rg -n 'getLedger\\(' services/accounting-service clients/desktop` 결과 중 원장 계약 대상은 다음과 같다.

별도 `LedgerService`의 `getLedger(from, to, partnerCode, actorRole)`와 `LedgerController` 호출은 다중 거래처 원장 endpoint의 별도 계약이다. 이번 문서 단언의 `LedgerImageService`/`/accounting/journals/ledger-data` 계약과 혼동하지 않으며, 해당 4인자는 권한 role 검증에 사용된다. `LegacyBatchConsumerFailClosedTest`의 4인자 호출도 이 별도 `LedgerService` 대상이다.
