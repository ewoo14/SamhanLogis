# #1116 S4 — 발견 전 모집단 목록 제거 적대검증

## 결론

PR #1118의 exact head `01545ba09eb82bf35f1a83d1f3672ad8eb2ce2e8`에서 자격 소비자 발견 로직은 미등록 파일의 확장자·키 이름·접근 문법·루트 변주를 모두 잡았다. 지정된 정상 파일도 현재 오탐하지 않았다.

그러나 **S4 결함은 3건**이다. 따라서 이 검증 기준으로는 머지 게이트를 채우지 못했다.

1. `harness-false-green-guard.test.ts`에 옛 대상 목록 walker가 한 곳이 아니라 세 곳 남아 있고, 빈 목록을 순회하는 G8a는 vacuous green이다.
2. S1의 핵심 발견 가드 `scripts/lib/qa-credentials.test.cjs`를 실행하는 CI runner가 없다. 현재 43/43 green의 `Credential Plaintext Guard`는 다른 파일인 `scripts/check-credential-plaintext.sh`만 실행한다.
3. S3 보고와 달리 G8은 `discoveredEvidenceWritersCache`를 공유하지 않는다. `derivedEvidenceWriters()`가 CI에서 전수 discovery를 두 번 더 실행한다.

## 2. 죽은 코드 판정

**제거해야 한다. 남길 이유는 없다.** 전환 중 보관이라는 주석은 회귀 방지 근거가 아니며, 다음 수정자가 옛 registry walker를 되살릴 수 있다. 실제 잔존은 PM이 지목한 한 곳보다 많다.

| 위치 | 잔존 내용 | 판정 |
|---|---|---|
| `harness-false-green-guard.test.ts:66-83` | `walkG3Sources()`의 즉시 return 뒤 `G3_ROOTS` walker | 도달 불가 옛 대상 목록, 삭제 필요 |
| `harness-false-green-guard.test.ts:1419-1435` | `derivedEvidenceWriters()`의 즉시 return 뒤 `.ps1/.sh/.py` 확장자별 walker | 도달 불가 옛 확장자 모집단 분기, 삭제 필요 |
| `harness-false-green-guard.test.ts:1767-1786` | `guardScannedFiles()`의 즉시 return 뒤 `GUARD_ROOTS` walker | 도달 불가 옛 대상 목록, 삭제 필요 |

`G3_ROOTS`는 빈 배열이고 `GUARD_ROOTS`는 그 빈 배열을 펼친다. 그런데 reachable G8a는 `GUARD_ROOTS`만 순회하고 “목록 자체가 0건”을 단언하지 않으므로 아무 것도 검사하지 않고 green이다. 이것은 단순 미관 문제가 아니라 옛 목록과 무의미한 회귀 테스트를 함께 남긴 구조 결함이다. 관련 과거 설명 주석과 `GUARD_ROOTS` 추가를 요구하는 실패 메시지도 발견 기반 의미로 동기화해야 한다.

## 3. 오탐 전수

### k6 예외

`perf/k6/mixed-load.js`는 `__ENV.LOADTEST_PASSWORD`를 읽지만 정확한 파일 단위 제외가 유지된다.

- `mixed-load.js:50-52`: 값이 없으면 즉시 `throw`한다.
- `scripts/run-load-test.ps1:157`: `QA_DEV_DEFAULT_PASSWORD`가 없으면 실행 전에 `throw`한다.
- `scripts/run-load-test.ps1:183,200,224`: k6에 `-e LOADTEST_PASSWORD=...`로 주입한다.
- k6는 Node `fs`/공용 로더를 사용할 수 없으므로 이 단일 파일 제외는 정당하다.

예외가 `perf/**` 전체로 번지지 않았는지 확인하려고 `perf/.s4-k6-exception-control.js`에 같은 `__ENV.LOADTEST_PASSWORD` 읽기를 두었다. 표적 테스트는 exit 1로 그 파일을 지목했다. 대조 probe는 즉시 삭제했다.

### 지정 정상 파일

`node --test scripts/lib/qa-credentials.test.cjs`의 최종 정상 실행에서 다음 파일들은 소비자 위반으로 분류되지 않았다.

| 정상 표면 | 전수 수 | 결과/근거 |
|---|---:|---|
| `gradlew`, `gradlew.bat` | 루트와 Android 각 1쌍, 총 4파일 | basename 제외, 오탐 없음 |
| `Dockerfile` | 9 | basename 제외, 오탐 없음 |
| `_headers` | 1 | basename 제외, 오탐 없음 |
| `scripts/lib/qa-credentials.d.cts` | 1 | 선언 파일을 읽지만 자격 접근으로 분류하지 않음, 오탐 없음 |

자격 불필요 임시 파일도 discovery에서 제외되는 내장 대조 테스트가 함께 통과했다.

### `.env.local` 부재 환경과 CI

로컬 `infrastructure/.env.local`은 존재하지만 tracked 파일이 아니고 `.gitignore:62`의 `.env.local` 규칙으로 제외된다. exact SHA CI는 `actions/checkout@v4`로 merge ref를 강제 checkout하므로 이 로컬 파일은 전달되지 않는다.

CI의 `Credential Plaintext Guard (SP-08-8)`는 checkout-only 환경에서 `scripts/check-credential-plaintext.sh`를 실행해 PASS했다. 그러나 이 잡은 `scripts/lib/qa-credentials.test.cjs`를 실행하지 않는다. 따라서 “`.env.local` 없는 CI에서 S1 discovery 테스트까지 green”이라는 주장은 성립하지 않는다. loader의 로컬 단위 테스트는 명시적으로 빈 `env`와 존재하지 않는 임시 env 경로에서 fail-fast를 검증해 통과했지만, CI runner 부재는 별도 결함이다.

## 4. CI 실측 스캔 시간

측정 좌표:

```text
PR: #1118
head: 01545ba09eb82bf35f1a83d1f3672ad8eb2ce2e8
workflow run: 31181991493
job: 92877248479
checks: 43/43 success
```

독립 `Harness Guard` 로그의 Vitest 실측은 다음과 같다.

| 항목 | exact SHA CI 로그 |
|---|---:|
| G3a | 46,460 ms |
| G3b | 개별 시간 미출력 |
| G8b | 45,044 ms |
| G8c | 46,726 ms |
| 스펙 전체 tests | 138,996 ms |
| Vitest 명령 전체 | 139.56 s |

G3b는 G3a가 채운 `discoveredEvidenceWritersCache`를 재사용해 slow-test 행이 출력되지 않았다. 기존 로그에는 개별 시작·종료 timestamp나 machine-readable test artifact가 없으므로 **G3b의 정확한 ms 값은 사후 복원할 수 없다**. 로컬 값으로 대체하거나 0ms로 꾸미지 않는다.

같은 SHA의 전체 `Frontend Desktop` 잡에서도 G3a는 41,731 ms, 해당 스펙은 116,801 ms였다. 이 값은 독립 잡과 러너 부하가 달라 참고값으로만 둔다.

S3의 캐시는 G3a→G3b와 G9에는 적용됐지만 G8에는 적용되지 않았다. G8b와 G8c는 별도 함수 `derivedEvidenceWriters()`를 각각 호출하며, 이 함수에는 캐시가 없다. CI의 45,044 ms + 46,726 ms가 그 중복 전수 순회를 직접 보여 준다. 따라서 “G3·G8·G9가 전수 discovery 캐시를 나눠 쓴다”는 S3 설명은 현재 코드와 일치하지 않는다.
