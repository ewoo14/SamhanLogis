## ① 사용자 동선으로 옮긴 변경 표면

### QA가 밟을 동선

1. 데스크톱 로그인 후 출고 전표 목록에서 출고 전표를 선택한다.
2. `/sales/:id` 출고 전표 상세를 연다. 영업 정적 권한이 없어도, 현재 계정이 `OUTBOUND_INSPECT` 결재선 개인이면 상세 조회를 시도할 수 있다. 서버가 응답의 `canInspect`를 계산하고, 실패 시 일반 로드 실패가 아닌 403 안내를 표시한다.
3. `INSPECTING` 전표에서 `처리 완료`를 누른다. 실제 API 경로는 `POST /slips/{id}/inspect`이고 `INSPECTING → COMPLETED`다.
4. 완료 후 재조회하여 `배송 시작`(`POST /slips/{id}/ship`), `배송 완료`(`POST /slips/{id}/deliver`), `확정`(`POST /slips/{id}/confirm`)을 순서대로 밟는다.
5. 결재선 개인은 검수부터 후속 전이까지 계속 진행할 수 있어야 하고, `CONFIRMED`가 된 뒤에도 상세 조회가 가능해야 한다.
6. 같은 표면에서 정적 권한자(`slip.transfer.process` UPDATE 또는 system master)는 기존처럼 실행할 수 있어야 하며, 권한이 없는 계정은 목록/상세/전이에서 계속 막혀야 한다.

### 관측된 중요한 계약

현재 auth 모델에는 `approval_line_config`/`approval_line_approver`에 `slip_id`가 없다. 즉 “전표별 결재선 설정/미설정”이 아니라 `document_type × action_key` 전역 설정이다. 이는 사용자가 제시한 두 갈래 외의 셋째 관측이다. 따라서 김기철·김은지의 `OUTBOUND_INSPECT` 개인 자격은 현재 계약상 모든 OUTBOUND의 검수 후속 상태에 적용되며, 특정 전표에만 귀속된다고 가정하여 QA하면 안 된다.

추가 상태 분포 원문은 다음과 같다. `INBOUND/INSPECTING` 2건, `INBOUND/COMPLETED` 9건도 존재하지만 이번 fix의 결재선 개인 허용은 OUTBOUND 전용이다. 입고는 `inbound.inspection` 정적 권한 회귀용 RED-B 표본으로만 사용한다.

```sql
SELECT slip_type, status, COUNT(*) AS count
FROM slips
WHERE is_deleted = FALSE

```

정적 권한 실측은 다음 원문에서 `slip.transfer.process`의 `can_update=TRUE`로 계산했다. `dev_manager`는 정적 권한자이고 `kimgicheol`/`kimeunji`는 개인 결재선이지만 정적 UPDATE가 없다.

```sql
SELECT a.login_id, a.display_name,
       CASE WHEN p.account_id IS NOT NULL THEN 'personal' ELSE '' END AS personal,
       CASE WHEN s.account_id IS NOT NULL THEN 'static_update' ELSE '' END AS static_authority
FROM accounts a
LEFT JOIN (
  SELECT DISTINCT approver_ref_id AS account_id
  FROM approval_line_config c
  JOIN approval_line_approver al ON al.config_role_id=c.id AND al.is_deleted=FALSE
  WHERE c.is_deleted=FALSE AND c.document_type='SLIP_OUTBOUND'
    AND c.action_key='OUTBOUND_INSPECT' AND al.approver_type='USER'
) p ON p.account_id=a.id
LEFT JOIN (
  SELECT DISTINCT ag.account_id
  FROM account_groups ag
  JOIN group_page_permissions g ON g.group_id=ag.group_id
    AND g.is_deleted=FALSE AND g.page_code='slip.transfer.process'
    AND g.can_update=TRUE
  WHERE ag.is_deleted=FALSE
) s ON s.account_id=a.id
WHERE a.is_deleted=FALSE AND (p.account_id IS NOT NULL OR s.account_id IS NOT NULL)
ORDER BY a.login_id;
```

## ③ QA 시나리오 초안

실행 시 전표 상태를 바꾸므로 공유 서버 점유 트랙이 끝난 뒤 수행한다. 아래 RED-A는 기대되는 허용 경로, RED-B는 fix가 정상 경로를 막거나 권한을 새는지 확인하는 반대급부다.

### S1 — 결재선 개인의 검수 시작/상세 조회

- 표본: `2026/08/03-6` (`OUTBOUND`, 현재 `INSPECTING`), 계정 `kimgicheol` (비밀번호는 핸드오프 환경 절 참조 — 문서에 평문으로 적지 않는다).
- RED-A: 로그인 → 목록에서 전표번호 `2026/08/03-6`을 선택해 상세 진입 → `처리 완료` 실행. 상세가 열리고 `POST /slips/{id}/inspect`가 200, 상태가 `COMPLETED`가 되어야 한다. 화면에는 UUID를 표시하지 않고 전표번호를 확인한다.
- RED-B: 같은 표본에서 `dev_accountant`로 상세/검수 실행. 개인 결재선도 아니고 정적 `slip.transfer.process` UPDATE도 아니므로 403/권한 차단이어야 한다. `kimeunji`도 별도 반복하여 두 개인 USER가 모두 같은 경로를 갖는지 확인한다.

### S2 — 정적 권한자의 기존 경로 보존

- 표본: `2026/01/27-1` (`OUTBOUND`, `INSPECTING`), 계정 `dev_manager` (비밀번호는 핸드오프 환경 절 참조 — 문서에 평문으로 적지 않는다).
- RED-A: 로그인 → 출고 전표 상세 → `처리 완료` 실행. 결재선 개인이 아니어도 매니저 정적 권한으로 200/`COMPLETED`가 되어야 한다.
- RED-B: 같은 표본에서 `dev_dispatch` 또는 `dev_accountant`로 상세/검수 실행. 둘 다 현재 정적 UPDATE가 없고 결재선 USER도 아니므로 허용되면 안 된다. 단, 목록 접근과 상세 403의 실제 응답을 구분해 기록한다.

### S3 — 결재선 개인의 후속 전이와 정적 권한자의 후속 전이

- 표본: S1에서 `2026/08/03-6`을 `COMPLETED`로 만든 뒤 같은 전표를 계속 사용한다. 사전 상태 표본으로 `2026/08/07-3`(`COMPLETED`)도 준비되어 있고, 기존 후속 상태 확인용으로 `2026/02/03-1`(`SHIPPING`), `2026/02/08-1`(`DELIVERED`)이 있다.
- RED-A: `kimgicheol`로 재조회 → `배송 시작` → `배송 완료` → `확정`을 순서대로 실행한다. 각 단계에서 상세 재조회와 `canInspect=true`가 유지되고, 최종 `CONFIRMED`가 되어야 한다.
- RED-B: 각 단계에서 `dev_accountant`로 같은 전표를 열거나 전이를 실행한다. 개인 결재선·정적 UPDATE가 없는 계정은 403이어야 한다. 반대로 별도 반복에서 `dev_manager`가 같은 후속 전이를 수행하여 정적 권한 경로가 막히지 않았는지도 확인한다.

### S4 — `CONFIRMED` 이후 결재선 개인 조회 허용

- 표본: `2026/02/15-1` (`OUTBOUND`, `CONFIRMED`), `kimeunji`.
- RED-A: `kimeunji`로 로그인해 출고 상세를 연다. 확정 후에도 상세가 200으로 열려야 한다. 실행 버튼이 추가로 나타나는 것이 아니라 조회만 허용되는 것이 기대 동작이다.
- RED-B: 같은 표본에서 `dev_accountant`로 접근해 403을 확인한다. `dev_manager`로는 기존 정적 권한 경로가 유지되어 상세가 열리는지 별도 확인한다. `CONFIRMED`를 결재선 개인에게서 다시 막거나, 무권한 계정에게 열어 주면 결함이다.

### S5 — 입고 회귀(결재선 우회 금지)

- 표본: `2026/03/31-1` (`INBOUND`, `INSPECTING`) 또는 `2026/04/01-1`.
- RED-A: `dev_manager` 또는 입고 검수 권한이 있는 정적 계정으로 입고 검수 화면/전이를 수행하고 기존 `inbound.inspection` 경로가 유지되는지 확인한다.
