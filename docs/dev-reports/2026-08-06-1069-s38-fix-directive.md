## 1. 결함 좌표와 계약 게이트 공격 결과

### F1 — `Slip.java` 예외가 실제 사용자 버전복원 옵션 소실을 숨긴다

1. 사용자는 전표 상세의 `이 시점으로 복원` 버튼을 누를 수 있다(`SlipVersionHistoryPanel.tsx:211,419`). 클라이언트는 `POST /api/v1/slips/{id}/revisions/{revisionNo}/restore`를 호출한다(`slipRevision.ts:103-108`).
2. S37 일반 저장은 `SlipLine.bundleSetOptions`에 옵션을 저장하고(`SlipLine.java:151-152,402-405`) 상세 응답도 반환한다(`SlipLineResponse.java:57,82`).
3. 그러나 revision 캡처 `Slip.toSnapshot()`은 `SlipSnapshot.Line`을 만들 때 이 필드를 담지 않는다(`Slip.java:2138-2160`). `SlipSnapshot.Line`에도 옵션 필드가 없다(`SlipSnapshot.java:145-164`).
4. 복원은 `Slip.java:2278-2302`에서 `SlipLine.create(...)`로 라인을 다시 만들고 `parentSetModel`/`setHead`만 복원한다. 옵션을 전달할 데이터가 없으므로 복원 결과의 `bundleSetOptions`는 `null`이다.
5. 저장소 밖 `%TEMP%`에 일회성 테스트를 주입해 `EXPAND 옵션 부여 → toSnapshot → restoreFromSnapshot → 옵션 동일성`을 단언했다. 현재 HEAD 결과는 `S38BundleOptionRestoreReproTest: 1 test completed, 1 failed`였다. 임시 파일은 즉시 삭제했고 저장소는 다시 clean이다.

### F2 — 계약 범위 밖 `estimate_lines`는 옵션을 전개에만 쓰고 버린다

1. 견적 화면은 BUNDLE 옵션을 `setOptions`로 전송한다(`EstimateFormPage.tsx:120,1230-1234,1509`).
2. 서버는 이를 product-service 전개 옵션으로 변환한다(`EstimateService.java:125-130`).
3. 생성된 `EstimateLine`에는 `setHead`/`parentSetModel`만 부여한다(`EstimateService.java:145-151`, `EstimateLine.java:131-137,243-246`). 옵션 영속 필드가 없다.
4. `EstimateLineResponse`도 `parentSetModel`에서 끝난다(`EstimateLineResponse.java:24-26`). 편집 hydrate는 서버 값을 받을 수 없어 무조건 `emptyBundleSetOptions()`를 넣는다(`EstimateFormPage.tsx:239-285`).
5. 따라서 저장 성공 뒤 같은 견적을 다시 여는 정상 사용자 경로에서 선택 원문이 소실된다. 기존 견적 설계도 `estimate_line setOptions JSONB` 저장을 명시한다(`docs/superpowers/specs/2026-06-15-comprehensive-quotation-epic.md:32`).

### ① 새 계약 게이트 공격 결과

게이트는 뚫렸고 그 구멍 두 곳에서 위 실제 결함이 살아 있다.

- 정규식은 `SlipLine.create*`와 `slip.addLine`만 찾는다(`BundleStoragePolicyContractTest.java:14-15`). 실행 실측상 `SlipLine.copyOf`, 메서드 참조/별칭, `SlipLine . create`, 리플렉션, 직접 생성자, `EstimateLine.create`는 전부 매치되지 않았다.
- 파일에 `BundleModePolicy.shouldExpand` 문자열만 있으면 사용 여부를 보지 않는다. 주석만 둔 표본과 반환값을 버린 호출 표본 모두 정규식/문자열 조건을 통과했다(`:31-32`).
- `Slip.java`와 `SlipLine.java`는 파일명 예외다(`:33`). `Slip.java`의 실제 라인 생산 경로는 revision 복원 1개(`Slip.java:2278`)이며 정책 호출 없이 F1을 만든다. `SlipLine.java`에는 실 인스턴스를 만드는 공개 팩토리 3계열과 `copyOf`가 있고, 예외 때문에 향후 내부 생산 경로가 늘어도 게이트는 보지 않는다.
- 범위는 `services/slip-service/src/main/java` 전체이지만 패턴이 `EstimateLine`을 보지 않아 견적 생성·복원 경로는 사실상 범위 밖이다. F2가 그 실제 결과다.
- 기존 `SlipDuplicateService → SlipLine.copyOf`는 정규식 밖이지만 현재 구현은 옵션·계보를 그대로 복사하므로 추가 도달 결함은 재현되지 않았다(`SlipLine.java:427-445`). JPA cascade는 이미 만들어진 객체를 영속할 뿐 별도 생성 입구가 아니어서 이번 HEAD의 추가 결함은 아니었다.

## 2. 수렴 불변식

1. EXPAND 옵션 5개(`remoteOption`, `remoteExcluded`, `panelOption`, `panelShape360`, `materialIncluded`)는 전표의 일반 저장·상세 재조회뿐 아니라 복사·revision 캡처·revision 복원까지 정확히 동일해야 한다. `setHead`와 `parentSetModel`도 함께 보존한다.
2. 견적의 BUNDLE 선택 옵션도 화면 선택 → 생성/수정 → DB 저장 → 상세 재조회 → 편집 hydrate → revision 캡처/복원에서 동일해야 한다. 전개 결과만 남고 선택 문맥이 사라지는 상태를 허용하지 않는다.
3. KEEP 부모와 SINGLE에는 구성품 계보 또는 허위 옵션 문맥을 새로 부여하지 않는다. 기존 null 행은 추측 backfill 없이 null로 정상 조회·수정·인쇄되어야 한다.
4. 저장 입구 계약은 주석, 사용하지 않은 정책 호출, 파일명 예외, 팩토리 명명 변경만으로 우회할 수 없어야 한다. 정책 판정뿐 아니라 옵션 문맥을 생산·복원하는 사용자 경로도 자동 검출 대상이어야 한다.
5. 기존 SINGLE 기준선과 EXPAND/NULL 부모 차단 의미는 그대로 유지한다.

## 3. 양방향 RED

### RED-A — 결함을 반드시 잡는 단언

- 전표 EXPAND 라인에 서로 구분되는 옵션 5개와 `setHead`/`parentSetModel`을 부여한다. `toSnapshot → restoreFromSnapshot` 뒤 모든 값이 입력과 정확히 같아야 한다. 현재 HEAD는 옵션 동일성에서 RED다.
- 동일 전표를 실제 revision 서비스/REST endpoint로 복원한 뒤 상세 GET 응답의 각 구성품이 저장 당시 옵션과 같아야 한다.
- 견적 BUNDLE 생성과 수정 각각에서 옵션을 선택해 저장한 뒤 상세 GET 및 편집 hydrate 값이 입력과 같아야 한다. 이어서 견적 revision 복원 뒤에도 같아야 한다.
- 계약 게이트 공격 fixture로 ① 주석에만 정책 문자열이 있는 생산 경로 ② 정책 반환값을 버리는 생산 경로 ③ `Slip.java` 내부 복원 생산 경로 ④ `SlipLine.copyOf`/새 팩토리명 경로 ⑤ `EstimateLine` 생성·복원 경로를 둔다. 실제 정책/문맥 보존이 없으면 각각 RED여야 한다.

### RED-B — 반대급부

- 옵션 키가 없던 구 전표/견적 snapshot과 기존 DB null 행은 예외 없이 복원·조회·수정·인쇄되고 옵션은 null/기본값으로 남아야 한다.
- KEEP 저장 후 재조회에서 `parentSetModel`은 비어 있고 `setHead=false`여야 한다. 자기 자신을 구성품으로 만들거나 빈 옵션 객체를 영속 문맥으로 오인하면 안 된다.
- SINGLE 2,107행은 매출·매입 전체수정 정책 공통화 뒤에도 차단되지 않아야 한다.
- EXPAND/NULL 부모는 평면 저장에서 계속 차단되고, 이미 전개된 SINGLE 구성품은 계보·옵션과 함께 정상 통과해야 한다.
- 전표 복사는 현재처럼 옵션·계보·금액 권위값을 그대로 승계해야 하며, source order 역참조는 종전 계약을 유지한다.

## 4. 확인된 반대급부와 범위 밖

- 실 DB SELECT 재계수: 활성 OUTBOUND DRAFT + `created_at < 2026-08-06 00:00:00` + 현재 활성 SINGLE은 **2,107행 / 2,100전표 / 2,837,681,781.00원**이며 새 정책의 가드 적중은 **0행**이다.
- 활성 제품은 SINGLE 2,835, BUNDLE EXPAND 343, BUNDLE `bundle_mode NULL` 1, KEEP 0이다.
- KEEP 화면 payload 회귀는 `SlipFormPage.test.tsx`에서 통과했고, 서버는 `parentSetModel` 비공백일 때만 계보를 부여하므로 일반 저장 후 자기 계보 오부여는 닫혔다.
- 전표 EXPAND 일반 저장 경로는 옵션을 JSONB 필드에 넣고 상세 DTO로 반환한다. 전표 복사도 옵션을 승계한다. F1은 이 정상 경로 뒤의 revision 왕복에서만 재현됐다.
- `V114__preserve_bundle_set_options.sql`은 nullable JSONB 컬럼 1개를 default/backfill 없이 추가한다. 기존 `slip_lines`는 null이며 FE 상세 hydrate가 null을 빈 옵션으로 처리하고 인쇄 경로는 이 필드를 소비하지 않아 기존 행 조회·수정·인쇄 차단은 찾지 못했다.
- 마이그레이션 번호 판단은 맞다. `origin/main` slip-service 최고는 **V112**, 실 `slip_db` 적용 최고도 **112**, 열린 PR #1078이 **V113**을 예약한다. 따라서 이 PR의 다음 번호는 **V114**다.
- 안 본 범위: DB write가 필요한 실제 HEAD 서버 배포/라이브 전표·견적 생성, 실제 모바일 기기 GUI, vendor 발송, Docker 재빌드·재배포·중지, 다른 트랙 #1066/#1075 구현, 전체 저장소 CI. DB는 SELECT만 했다. 라이브QA는 아직 미실시 상태다.
