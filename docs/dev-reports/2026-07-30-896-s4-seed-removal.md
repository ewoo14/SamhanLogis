## 1. PM 결정과 변경 경계

재수렴 보고서 `2026-07-30-896-s4-scope-reduction-sol-reconv.md`의 R-01~R-03은
모두 `V29__seed_s03_quantity_sync_rule.sql` 하나에서 시작한다. 관측 전용 shadow에는
seed가 필요하지 않으므로, `enabled=FALSE` 전환이 아닌 migration 파일 자체를 제거했다.

이번 작업에서 한 일은 다음과 같다.

- `V29__seed_s03_quantity_sync_rule.sql` 삭제
- 기존 축소 보고서에 EI-01·EI-02 정정문과 V29 후속 정정문 삽입
- GitHub PR 본문은 수정하지 않음. EI-03은 PM이 직접 수정할 대상임
- 서버측 정수 계약 validator, shadow evaluator, 실 catalog fixture와 기존 하드코딩
  계산은 유지

공유 실데이터에 PUT/PATCH/POST/DELETE를 보내지 않았고, V29를 적용하지 않았다. 이미
실행 중인 Docker Compose stack을 재배포하지 않았으며, 테스트가 사용하는 임시
PostgreSQL Testcontainers만 Gradle 테스트 수명 안에서 사용했다.

## 2. R-01~R-03 재현 절차와 결과

### R-01. 저장 가능한 설정이 주문에 반영되지 않는 경로

원래 절차는 다음과 같다.

1. 관리자 권한으로 `PUT /api/v1/quantity-sync-rules/SINGLE_S03_CEILING_DRAIN_PUMP`를 호출한다.
2. AC072 factor `0.28`, ADP multiplier `25`, `rounding=NONE`, `enabled=true`를 저장한다.
3. 주문 앱에 로그인하고 AC072 1개를 선택한다.
4. 설정 조회 후 화면 수량·소계와 전송 payload를 확인한다.

이번에는 공유 DB write 금지 조건 때문에 1번 PUT을 보내지 않았다. 대신 seed가 만들어야
하는 선행 상태를 읽기 전용으로 확인하고, 그 상태에서 주문 경계를 실행했다.

읽기 전용 확인 명령:

```powershell
PS> docker exec samhan-postgres psql -U samhan -d product_db -v ON_ERROR_STOP=1 -Atc "SELECT 'active_s03=' || count(*) FROM quantity_sync_rule WHERE rule_key='SINGLE_S03_CEILING_DRAIN_PUMP' AND is_deleted=false;"
active_s03=0
```

legacy 주문 경계 실행 원문:

```powershell
PS> node -e "const h=require('./src/__tests__/quantitySyncS03Harness.cjs'); console.log(JSON.stringify(h.runLegacyS03({sourceQuantity:1})))"
{"sourceQuantity":1,"targetQuantity":1,"manualLock":false}
```

`V29`가 없어 활성 S-03 설정을 읽고 주문에 반영하지 않는 seed 기반 도달 조건이
성립하지 않는다. 주문 앱은 설정이 비어 있거나 shadow 조회가 실패해도 legacy 수식을
계속 사용한다. 따라서 이 슬라이스의 R-01 실 사용자 경로는 도달하지 않는다. 관리자
PUT을 통한 다음 슬라이스의 명시적 설정 전환은 이번 보고서의 공유 DB 범위 밖이다.

### R-02. 관측용 enabled 규칙이 품목 관리 쓰기를 409로 차단하는 경로

원래 절차는 다음과 같다.

1. V29가 만든 enabled S-03 규칙과 실 catalog 5개 품목 상태에서 시작한다.
2. `/products/estimate-items`에서 AC072 또는 ADP의 견적·주문 노출을 끈다.
3. 화면이 `PATCH /api/v1/products/{modelCode}/usage`를 호출한다.
4. product-service의 enabled 참조 규칙 guard가 409를 반환하는지 확인한다.

1번의 V29 선행 상태를 적용하지 않고 다음을 읽기 전용으로 확인했다.

```powershell
PS> Test-Path services/product-service/src/main/resources/db/migration/V29__seed_s03_quantity_sync_rule.sql

PS> docker exec samhan-postgres psql -U samhan -d product_db -v ON_ERROR_STOP=1 -Atc "SELECT 'active_s03=' || count(*) FROM quantity_sync_rule WHERE rule_key='SINGLE_S03_CEILING_DRAIN_PUMP' AND is_deleted=false;"

```

활성 S-03 참조 규칙이 0건이므로 AC072·ADP usage PATCH가 S-03 때문에 409가 되는
도달 사슬은 닫혀 있다. 이번에는 공유 품목 usage PATCH를 보내지 않았다. 수동으로
새 enabled 규칙을 만드는 경우의 일반 참조 guard 자체와 validator는 다음 규칙을
저장·운영할 때 필요한 서버 계약으로 유지한다. 그것은 제거한 V29 seed의 실 사용자
경로가 아니다.

### R-03. #996 선배포 후 #984 배포 시 Flyway 기동 실패

원래 절차는 다음과 같다.

1. #996을 먼저 배포해 V29를 Flyway history에 기록한다.
2. 그 뒤 #984의 V27·V28이 포함된 product-service를 기동한다.
3. 기본 `outOfOrder=false`, `validateOnMigrate=true`에서 낮은 미적용 버전이 V29
   뒤에 오므로 기동 실패 여부를 확인한다.

V29를 적용하지 말라는 조건에 따라 1번을 수행하지 않고, migration tree와 공유
Flyway history를 읽기 전용으로 확인했다.

```powershell
PS> [pscustomobject]@{V29Exists=Test-Path services/product-service/src/main/resources/db/migration/V29__seed_s03_quantity_sync_rule.sql; HeadMigrationDiff=(git diff --name-only origin/main -- services/product-service/src/main/resources/db/migration | Out-String).Trim()} | ConvertTo-Json -Compress
{"V29Exists":false,"HeadMigrationDiff":""}

PS> docker exec samhan-postgres psql -U samhan -d product_db -v ON_ERROR_STOP=1 -Atc "SELECT 'flyway=' || COALESCE(string_agg(version || ':' || description, ',' ORDER BY installed_rank) FILTER (WHERE version IN ('27','28','29')), 'none') FROM flyway_schema_history;"
flyway=27:allow skipped main candidate status,28:add product lineage
```

현재 #996 tree는 `origin/main`과 product-service migration 차이가 없고 V29도 없다.
공유 history에는 V27·V28만 있으며 #996이 선행 V29를 만들 수 없으므로, #984 뒤늦은
migration이 V29 때문에 거부되는 경로는 사라졌다. Flyway out-of-order 설정을 바꾸거나
V29를 시험 DB에 적용하지 않았다.

## 8. 다음 슬라이스가 seed를 넣을 때 갖춰야 할 것

다음 슬라이스는 아래 조건을 모두 갖춘 뒤에만 seed를 추가한다.

1. #984의 V27·V28이 기준 브랜치에 먼저 머지·배포된 뒤, 그 다음 순번의 migration으로
   추가한다. 현재 슬라이스에서 제거한 V29를 되살려 선배포하지 않으며,
   `outOfOrder=false`, `validateOnMigrate=true`에서 V1부터 최신까지와 V28 운영 상태
   upgrade를 모두 fresh PostgreSQL로 검증한다.
2. seed 목적을 관측용인지 실제 주문 계산용인지 먼저 결정한다. 관측 전용이면 seed를
   넣지 않는다. 실제 계산용으로 넣는다면 저장·조회된 설정이 주문 화면 수량·원 단위
   소계·최종 payload에 반영된다는 API부터 브라우저까지의 계약을 함께 구현한다.
3. S-03 규칙의 source는 실 catalog canonical code 네 개
   `AC072BSCPBH2SY`, `AC090BSCPBH2SY`, `AC130BSCPHH2SY`, `AC145BSCPHH2SY`, target은
   `ADP-F075SP`로 고정하고, seed 시점에 4 source와 target이 모두 존재·활성인지
   migration 테스트에서 확인한다. 부분 catalog일 때 조용히 enabled 규칙을 만들지
   않는다.
4. enabled 규칙이 품목 관리 usage PATCH·단종·삭제를 409로 막는 현재 guard와의
   운영 계약을 명시한다. 관측용으로 enabled를 넣어 관리 쓰기를 막는 상태를 다시
   만들지 않는다. 실제 계산을 켜는 경우에만 이 guard의 사용자 안내와 변경 절차를
   함께 검증한다.
5. `0.28 × 25 = 7.00`, `0.1 × 10 = 1.0`, 복수 source 합산을 포함해 서버
   `BigDecimal` 정수 validator와 브라우저 표현을 같은 계약으로 검증한다. `FLOOR`가
   아닌 경우 소수 결과를 저장·주문 payload로 통과시키지 않는다.
6. 실 catalog 4 source의 단독·모든 동시 조합과 실제 사용 수량 분포를 replay해
   main legacy 대비 수량·원 단위 소계·payload 0 불일치를 증명한다. 로그인·조회 실패,
   target 누락, 빈 설정에서도 사용자 화면·주문 버튼·payload가 legacy와 같아야 한다.
7. migration seed 자체, 관리자 PUT/GET, 품목 usage PATCH, order-app 계산·전송을
   fresh PostgreSQL과 실제 HTTP 계약 테스트로 묶고, 테스트가 만든 모든 행은 자기
   테스트가 정리한다. UUID는 응답·화면·payload에 노출하지 않는다.
