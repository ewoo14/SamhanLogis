## 3. 기본 런처 실제 실행

실행 명령:

```powershell

```

`-SkipBuild/-SkipClients`는 Compose 기동과 health gate를 그대로 두고, profile 판정과 무관한
Gradle 및 client dev server만 생략한다.

실행 전후 이름 비교:

```text

LAUNCHER_AFTER_COUNT=24
LAUNCHER_MISSING_NAMES=
```

전후 컨테이너 이름은 §2의 24개와 동일했다. 따라서 logging-service는 실제 기본 런처로
생성되지 않았고, 다른 service가 profile 때문에 빠진 흔적도 없다.

### 환경성 런처 실패 — 성공으로 기록하지 않음

런처 exit는 1이었다. 원문:

```text

Only one usage of each socket address (protocol/network address/port) is normally permitted.
```

읽기 전용 listener probe에서 PID 10612 `influxd`가 host 8088과 8086을 점유했다.
이 워크트리에는 `infrastructure/docker-compose.local-portfix.yml`이 없었다. 그 결과
`samhan-partner-order-service`와 `samhan-slip-service`는 `Created`에 남았다.

또한 Compose는 포트 충돌 전에 기존 24개 중 20개 컨테이너 ID를 바꿔 재생성했다.
Prometheus의 과거 t1113 mount 오류는 이번 실행에서 재현되지 않았고 prometheus/nginx는
현재 워크트리 mount로 재생성되어 healthy가 됐다. 최종 공유 상태는 24개 이름 중 22개
healthy, 위 두 service `Created`다. 이 두 service 및 나머지 공유 컨테이너에는 별도 cleanup,
stop, remove를 실행하지 않았다.

PR diff는 service port, 기본 런처, portfix를 변경하지 않는다. 따라서 위 실패는 profile
회귀 결함으로 판정하지 않지만, **이 PC에서 기본 런처 전체 성공은 확인하지 못했다**.

## 6. RabbitMQ 이름/인자 충돌 검증

logging-service 기동 전 기존 runtime topology:

```text
samhan.audit.exchange  topic  durable=true  auto_delete=false  internal=false  args=[]
samhan.audit.dlx       topic  durable=true  auto_delete=false  internal=false  args=[]
samhan.audit.queue     durable=true  auto_delete=false
  x-dead-letter-exchange=samhan.audit.dlx
  x-dead-letter-routing-key=audit.dlq
samhan.audit.dlq       durable=true  auto_delete=false  args=[]
samhan.audit.exchange -> samhan.audit.queue  audit.#
samhan.audit.dlx      -> samhan.audit.dlq    audit.dlq
```

`RabbitConfig.java` 선언은 위 기존 runtime 인자와 같다. production source 전체 exact-name
검색에서도 선언자는 logging-service `RabbitConfig` 하나뿐이다. opt-in 기동은 exit 0이었고
로그의 `PRECONDITION_FAILED`, `inequivalent arg`, `ShutdownSignalException`, `ERROR`,
`Exception` 적중은 0건이었다. 기동 후 exchange/queue/binding과 모든 인자는 기동 전과
동일했다.

따라서 기존 이름과의 중복은 존재하지만 **동일 타입·durable·auto-delete·DLX 인자**로
멱등 재선언되며 충돌하지 않는다.
