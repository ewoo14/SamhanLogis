## 1. 조사 방법과 작업 위치 검증

읽기 전용으로 현재 worktree의 브랜치와 HEAD를 확인했다. 사용자 지정 작업 위치·브랜치·HEAD가 실제 상태와 일치했으며, 조사 대상은 이 worktree 하나로 한정했다. 보고서 파일은 조사 시작 시 존재하지 않았고, 새 라운드 식별자로 신규 생성한다.

검색 시 `rg`를 사용해 다음처럼 문자열/컴포넌트/API/라우트 축을 분리했다.

```text
rg -n "버전이력|버전 이력|VersionHistory|versionHistory" clients
rg -n "listRevisions|revisions\.map|AuditOverlay|AuditRevisionBadge|AuditTimeline" clients
rg -n "edits\.map|HistoryTab|HistoryTable|Snapshot|history" clients
rg -n "path:|<.*Page|<.*Modal" clients/*/src/renderer/routes clients/*/src/renderer/components
```

raw grep 결과에는 테스트·스토리·주석·API 설정만 있고 실제 소비자가 없는 항목도 포함되므로, 최종 표에서는 다음을 분리했다.

1. 실제 production source에서 사용자에게 행/카드/테이블/배지를 렌더링하는 지점.
2. 같은 화면의 같은 데이터 지점에 대한 중복 호출(AuditOverlay 2개 등).
3. API 설정만 존재하고 production render consumer가 없는 항목.
4. 이미 별도 모달/상세 모달 안에 있는 항목.
5. 저장 이력처럼 이름은 유사하지만 full revision과 데이터 의미가 다른 항목.

### 2.2 버튼·모달·정렬 계약

- 버튼 라벨은 네 패널 모두 `버전이력`이다. Slip은 `SlipVersionHistoryPanel.tsx:281`, Estimate는 `EstimateVersionHistoryPanel.tsx:159`, PartnerOrder는 `PartnerOrderVersionHistoryPanel.tsx:249`, Partner는 `PartnerVersionHistoryPanel.tsx:155`에 있다.
- 버튼은 각 패널의 `Card` 안 첫 번째 직접 자식으로 놓인다. Slip `:268-282`, Estimate `:146-160`, PartnerOrder `:236-250`, Partner `:143-156`에서 확인된다. 네 위치 모두 `variant="secondary"`이며 `padding=4`, `shadow="sm"`, `marginTop: 24` 카드 안이다.
- 버튼에 `display`, `justifyContent`, `alignItems`, `marginLeft: auto` 등 별도 정렬 지시는 없다. 따라서 계약상 위치는 카드 안 정상 흐름의 첫 버튼이고, 화면 오른쪽 정렬을 전제로 하면 안 된다. 모달 내부 revision 목록만 `display: flex`, `flexDirection: column`, `gap: 8`의 세로 흐름이다. Slip `:363-367`, Estimate `:255-259`, PartnerOrder `:348-359`, Partner `:251-255`.
- 모달은 모두 디자인 시스템의 `Modal`을 직접 사용하며 제목은 화면 표시상 `버전 이력`(띄어쓰기 포함), `size="xl"`, `open={historyOpen}`, 닫기는 `onClose={() => setHistoryOpen(false)}`이다. Slip `:331-336`, Estimate `:223-228`, PartnerOrder `:316-321`, Partner `:219-224`.
- 이력 조회는 모달이 열릴 때만 활성화된다. 예를 들어 Slip은 `historyOpen` 상태와 query의 `enabled: !!slipId && historyOpen`을 `SlipVersionHistoryPanel.tsx:199-209`에서 사용한다. Estimate `:105-117`, PartnerOrder `:178-195`, Partner `:103-117`도 같은 패턴이다.
- `revisions.map` 앞에 FE 정렬 코드는 없다. 내림차순은 API/service 계약으로 보존된다. Slip 서비스는 내부 비교용으로만 오름차순을 만든 뒤 최종 결과를 newest-first로 뒤집고 `SlipRevisionService.java:246-290`에서 반환한다. 같은 패턴은 PartnerOrder `PartnerOrderRevisionService.java:370-401`, Partner `PartnerRevisionService.java:278-313`에 있다.

따라서 “시간 순 내림차순”은 UI가 임의로 `sort`해서 만드는 계약이 아니라, 백엔드가 반환한 최신 우선 순서를 모달이 그대로 렌더링하는 계약이다. 다음 구현에서 각 화면이 독자적으로 재정렬하면 API와 UI가 서로 다른 순서를 만들 위험이 있다.

### 2.3 카드 안 “변경항목 접기” 계약

`#1104`에서 실제 필드 단위 변경항목 접기를 구현한 좌표는 전표 패널 하나다.

- `clients/desktop/src/renderer/components/audit/SlipVersionHistoryPanel.tsx:424-456`
- 각 revision 카드의 변경영역은 native `<details>`이며 `data-testid`가 revision별로 부여된다.
- `open={expandedRevisionNos.has(rev.revisionNo)}`와 `expandedRevisionNos` 초기값 `new Set()`은 `:200`, `:442`에 있다. 따라서 기본 상태는 **접힘**이다.
- summary 라벨은 `변경 항목 {fieldChanges.length}개`이고, 펼쳤을 때 `fieldChanges.map`으로 필드별 before/after를 렌더링한다(`:442-445`). 복원 대상 revision을 자동으로 보여줘야 하는 경우에만 `:251-266`에서 해당 revision을 Set에 넣는다.

Estimate, PartnerOrder, Partner의 응답에는 `fieldChanges`가 없어서 네 패널에는 같은 필드 목록 접기를 적용할 데이터가 없다. 이 세 패널은 변경 요약/변경된 행 또는 자식 정보만 표시한다. 이를 Slip과 동일하다고 가정해 빈 변경목록 UI를 복제하면 데이터 계약을 위반한다.

### 2.4 재사용 대상

재사용할 수 있고 재사용해야 하는 공통 요소는 다음이다.

- `clients/web/design-system/src/components/Modal/Modal.tsx:14-16,78`: 공통 `Modal` 및 `size="xl"` 계약.
- 각 패널이 이미 사용하는 디자인 시스템 `Button`, `Card`, `Badge`, `Spinner` (`SlipVersionHistoryPanel.tsx:15` 등).
- 변경항목 데이터가 실제로 있는 표면에 한해 native `<details>`의 “기본 접힘” 동작을 계약으로 재사용한다.

현재 저장소에는 `VersionHistoryModal`이라는 공통 애플리케이션 컴포넌트가 없다. 네 패널은 각각 모달과 카드 마크업을 중복 구현하고 있다. 디자인 시스템 `Modal`은 컨테이너 재사용 대상이지만, `AuditOverlay`는 한 필드의 flat audit log를 펼치는 컴포넌트라 full revision 카드의 대체재가 아니다. 따라서 다음 라운드에서 자체 모달을 표면별로 새로 만들면 안 되며, 공통 모달 추출 여부를 먼저 결정하되 기존 DS `Modal`과 도메인별 adapter를 기준으로 검토해야 한다.

### 4.2 잔여 audit·협업·저장 history도 별도 계약이다

### 4.3 하나의 모달로 받을 수 있는가

현재 상태의 하나의 기존 모달로 모두 받을 수는 없다. 재사용 가능한 공통 컨테이너는 DS `Modal`뿐이고, 화면마다 API 응답·정렬 키·변경 표현이 다르다.

- full-snapshot 4종은 공통 `Modal` 외에 domain adapter가 필요하다. Slip만 fieldChanges 접기까지 지원한다.
- flat audit 9개 후보는 revision별 grouping, field alias 정규화, actor/time 키 정규화가 필요하다. 기존 `AuditOverlay`를 full revision 모달로 오용하면 안 된다.
- 협업 edit, save snapshot, 전송/비교 작업 history, 역할 변경 history는 의미 자체가 달라 하나의 “문서 버전이력” 모달에 합칠 수 없다.
- 이미 모달 안에 있는 Dispatch 상세, 창고 편집, 입금자 매핑, 직원 역할 history는 새 modal nesting을 만들지 말고 기존 컨테이너 계약을 먼저 유지해야 한다.

### 6.1 기존 테스트가 오름차순을 단정하는가

확인된 revision API 테스트는 오름차순을 단정하지 않고 최신 우선을 단정한다.

서비스 내부의 ascending sort는 인접 revision 비교를 위한 계산용이다. Slip `SlipRevisionService.java:246-290`, PartnerOrder `PartnerOrderRevisionService.java:370-401`, Partner `PartnerRevisionService.java:278-313` 모두 계산 후 최종 반환은 newest-first다. 이를 UI 요구사항 충돌로 오인해 내부 계산 정렬을 바꾸면 안 된다.

### 6.2 오름차순과 혼동할 수 있는 코드

- `clients/desktop/playwright/937-fix6-price-domain-real-qa/937-fix6-price-domain-real-qa.spec.ts:273`에는 `revisionNo` 오름차순 sort가 있다. 이것은 UI 이력 목록의 기대값을 단정하는 테스트가 아니라 가격 변경을 시간순으로 분석해 출력하는 QA helper다.
- `clients/mobile-staff/src/api/slipAudit.ts:5,117-120`은 응답을 `createdAt asc`라고 문서화하지만, desktop/BE 계약은 revisionNo 최신 우선이다. 실제 mobile overlay는 `clients/mobile-staff/src/components/AuditOverlay.tsx:53-56`에서 배열을 reverse한다. 더구나 현재 mobile-staff 전표 화면은 AppRootNavigator에서 도달하지 않는다. 오름차순 단정 테스트는 아니지만, 향후 mobile 표면을 되살릴 때 먼저 정리해야 하는 stale contract다.
- 기존 `AuditOverlaySection.tsx:50-52`와 DS `AuditOverlay.tsx:87-91`은 revisionNo 내림차순을 명시한다. 이 두 구현을 새 full revision modal의 공통 계약으로 확장할 수는 없지만, 현재 audit UI의 순서 기대값은 내림차순 쪽이다.

## 7. 슬라이스 제안

25개를 한 슬라이스로 처리하지 않는 것이 좋다. 데이터 계약과 회귀 범위가 다른 성격별로 **5개 슬라이스**를 제안한다.

1. **full-snapshot 공통 계약 슬라이스**: 현재 `#1104`의 4개 패널을 기준으로 DS `Modal`, 버튼 위치, backend newest-first, Slip만 fieldChanges 접힘이라는 원문 계약을 문서화하고 공통 adapter 경계를 확정한다. 새 표면 구현 전에 계약을 잠그는 선행 슬라이스다.
2. **전표·감사 이력 슬라이스**: SlipDetailPage의 2개 AuditOverlay, TaxInvoice detail/form, DC config, SalesClosing, PeriodClose, MonthEnd, InventoryAudit, 그리고 mobile source 후보를 묶는다. flat audit normalization과 기존 full revision/restore 경로 충돌을 한 번에 검증해야 한다.
3. **협업 수정이력 슬라이스**: Journal, Groupware Approval, DispatchTaskDetailModal의 `changeSet`/edit 상태를 묶는다. 이들은 document snapshot이 아니라 collaboration decision history이므로 “버전이력”으로 승격할지 PM의 의미 결정이 선행되어야 한다.
4. **저장 snapshot·작업 history 슬라이스**: 웹 견적·주문, PartnerLedger, Hometax, DPS 두 화면, SlipCleanup, DispatchSms, Arologis Unassigned/Reconcile을 묶는다. 복원 payload·작업 실행 history·페이지별 pagination이 중심이어서 full revision 모달과 별도의 UX 계약이 필요하다. 이 슬라이스는 PR #1126과 충돌 조정 후 진행해야 한다.
5. **이미 모달인 표면 정합성 슬라이스**: EditWarehouseModal, DepositorMappingPage, Arologis Employees, DispatchTaskDetailModal 내부 이력의 접근성·정렬·접힘이 #1104 기준과 충돌하지 않는지 확인한다. 새 모달을 추가하는 작업이 아니라 중복 모달/UUID 노출/정렬 회귀를 막는 정합성 슬라이스다.

PM이 작업량을 더 작게 쪼개야 하면 2번을 `SlipDetailPage` 단독과 회계/마감/재고 audit으로 나눌 수 있다. 반대로 3번과 4번은 한 PR로 합치면 데이터 의미가 섞이고 회귀 원인을 추적하기 어려워진다.

## 8. 회귀 위험이 큰 표면

가장 위험한 표면은 **`SlipDetailPage`**다.

- 같은 화면에 이미 `SlipVersionHistoryPanel`이 있고, 별도로 `AuditRevisionBadge`와 `AuditOverlay` 2개가 있다.
- full revision API(`slipRevision.ts`)와 flat field audit API(`slipAudit.ts`)가 병존한다.
- 복원 경로도 full revision restore로 일원화되었다는 계약이 코드 주석에 있다. 기존 audit UI에 복원 버튼을 되살리거나 API를 혼합하면 중복 복원 경로가 된다.
- PR #1131이 바로 `SlipDetailPage.tsx`를 수정 중이므로 병렬 충돌이 직접적이다.
- desktop은 `actorName`, `changedAt`, `beforeValue/afterValue`를 쓰고 mobile-staff는 다른 응답 필드와 오래된 asc 문서를 쓰므로 cross-client 회귀 위험도 있다.

그 다음은 **웹 견적 저장내역**이다. PR #1126이 같은 `index.ejs`와 snapshot API 코드를 수정하고, desktop `EstimateRevision`과 웹 snapshot의 의미가 다르기 때문에 단순히 `버전이력`이라는 문자열만 보고 통합하면 저장 복원 기능을 깨뜨릴 수 있다. 마지막으로 **closing/audit 계열 5개 화면**은 공통 API 설정을 공유하지만 화면별 Overlay와 Badge 조합이 달라서 공통화 시 한 화면의 회귀가 다른 마감 화면에 전파될 수 있다.

## 9. 조사 한계와 다음 라운드 입력

- 실제 DB의 revision row 수나 production runtime 도달 여부는 확인하지 않았다. 이번 라운드는 정적 source/API/type/route/PR 조사이며, Docker·서비스 재시작·라이브 QA를 하지 않았다.
- `createAuditApi.ts`의 모든 API config가 실제 화면 소비자를 의미하지 않으므로, API 이름만으로 최종 분모를 다시 세면 안 된다.
- mobile-staff 전표 화면은 source에는 있으나 현재 navigator에서 도달하지 않는다. PM은 “코드 표면까지 포함”이면 25에 포함하고, “현재 도달 가능한 화면만”이면 24로 관리할 수 있다. 다만 누락 방지를 위해 후보 원장에는 계속 남겨야 한다.
- “문서의 버전이력”을 full-snapshot revision으로 엄격하게 정의하면 `#1104` 4개 외 잔여는 0이다. 감사 이력·협업 edit·저장 history까지 이슈 #1091의 사용자 경험 통합 범위로 정의할 때만 11 또는 25가 작업 분모가 된다. 이 범위 결정은 구현자가 임의로 하지 말고 PM이 해야 한다.

정찰 결과의 기준값은 **25개 후보 표면 / 그중 11개 change-history 구현 후보 / full-snapshot 잔여 0개**이다. 숫자 18은 다음 구현 라운드의 입력값으로 사용하지 않는다.
