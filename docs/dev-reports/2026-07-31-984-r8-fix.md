## 결론

R7에서 BLOCK 된 네 불변식을 모두 코드와 회귀 테스트에 반영했다.

- 품목명 규격 라벨은 전체 라벨과 선두 alias 후보를 순서대로 해소하고, 미해소 라인도 product_id=NULL로 보존한다. 해당 주문 그룹은 영구 REJECTED가 아니라 PENDING으로 남긴다.
- resolver 5xx/timeout은 빈 map으로 변환하지 않고 예외를 전파한다. 따라서 일시 장애 때 staging 행을 REJECTED로 확정하지 않는다.
- reimport 응답은 거부 행의 source row, business key, raw value, error code, 사유를 전달하며, 거부 실행은 PROCESSED_WITH_REJECTIONS와 FAIL metric으로 남긴다.
- resolver가 예약한 Product를 시트 sync가 soft-delete하지 못하도록 동일 Product 행 잠금과 2분 reservation을 적용했다. 삭제가 먼저 끝난 경우 resolver도 해당 UUID를 반환하지 않는다.

### 변경 요지

Mig8OrderTransformService가 품목명 후보를 다음 순서로 조회하도록 바꿨다.

1. 기존 full label 전체 문자열
2. 공백, [ 또는 ( 앞의 선두 alias token

어느 한 라인이 해소되지 않아도 주문과 모든 라인을 upsert한다. 해소된 라인은 Product UUID를 저장하고, 미해소 라인은 product_id=NULL로 보존한다. 미해소 라인이 포함된 주문 그룹의 모든 staging 행은 PENDING으로 남겨 다음 실행에서 같은 주문·라인 구조를 재시도할 수 있게 했다. 미해소 행에는 MIG8_LOOKUP_MISS, source row, item name, alias token을 기록한다.

이는 Issue #1000의 순번코드→모델명 코드 전환이나 원본 병합 규칙을 변경하지 않고, 이 PR의 슬라이스 1 라벨 계약만 보완한 것이다.

## 2. 불변식 ② — 일시 장애는 재시도 가능 상태 유지

### RED 원문

위 RED 실행에서 다음 두 테스트가 실패했다.

    ProductAliasClientTest > resolveAliases_5xx는_일시적_장애를_전파한다 FAILED
    Mig8OrderTransformServiceTest > resolver_일시실패는_행을_거부확정하지_않고_예외를_전파한다 FAILED

R7의 실측 장애 경로는 resolver 전체 장애 시 imported/updated=0, REJECTED=26,055, 재시도 대상 0행이었다.

### 변경 요지

ProductAliasClient의 5xx, timeout, 네트워크 오류를 Map.of()로 바꾸지 않고 MIG20_REIMPORT_FAILED 예외로 전파한다. Mig8OrderTransformService는 resolver 예외를 잡아 거부 행으로 확정하지 않고 호출자에게 다시 던진다. 따라서 staging 상태 update가 발생하지 않아 기존 PENDING이 유지된다.

resolver가 정상 응답한 경우에는 후속 동시성 보호를 위해 reservation token을 발급하고, 변환이 끝난 뒤 finally에서 Product reservation을 해제한다. 일시 장애로 끝난 token은 Product 서비스의 TTL 2분 만료가 보조 정리한다.

### 실행 결과 숫자

    5xx response: BusinessException(MIG20_REIMPORT_FAILED) 1건
    resolver 일시 장애 fixture: staging update 0건, 영구 REJECTED 0건

공유 DB에서는 현재 PENDING=0, REJECTED=0, 전체 raw=0이므로 운영 데이터에 대한 추가 write/retry 실행은 하지 않았다.

### 변경 요지

EcountReimportService.summarize(EcountMig8TransformResult)가 기존처럼 count만 복사하지 않고 모든 ERROR sample을 EcountReimportResult.errors로 변환한다. 각 오류 메시지에 sourceRowNo, businessKey, rawValue, code, 원래 사유를 포함한다.

기존 공통 결과 builder의 20건 sample 상한도 제거했다. 그래서 20건을 넘는 거부가 UNSPECIFIED로 뭉개지지 않고 실제 행·사유가 모두 관리자 응답에 남는다. 거부가 있으면 상세 status는 PROCESSED_WITH_REJECTIONS, message는 거부 건수와 errors 확인 안내로 바뀌고, errors가 존재하므로 reimport metric은 FAIL이다.

## 4. 불변식 ④ — 동시 시트 sync에서도 삭제 UUID 결합 금지

### RED 원문

R7의 실제 경합 결과는 다음과 같다.

    resolver 응답 후 Product sheet soft-delete commit
    resolver가 반환한 삭제 UUID: 1/1
    삭제된 UUID를 신규 order line에 저장: 1/1
    AR-EC05 fixture: 삭제 UUID 결합 160/160 lines

### 변경 요지

Product 서비스에 다음을 추가했다.

- V29__add_ecount_alias_reservations.sql: reservation token, product UUID, 만료시각 테이블
- resolver 요청의 optional reservationToken
- resolver와 sheet sync가 같은 products 행에 FOR UPDATE를 사용하는 잠금 순서
- resolver가 잠금을 기다린 뒤 실제 예약에 성공한 Product만 UUID map에 남기는 재확인
- accounting 변환 종료 후 reservation release 내부 endpoint 호출
- 시트 sync가 active reservation을 발견하면 soft-delete 대신 deferredByEcountReservation으로 보류

이 순서에서는 resolver가 먼저 잠그면 sheet sync가 예약을 보고 삭제를 보류한다. sheet sync가 먼저 잠그고 삭제하면 resolver의 reservation 결과에서 해당 Product가 빠져 accounting이 삭제 UUID를 신규 line에 사용할 수 없다.

### 실행 결과 숫자

Testcontainers throwaway DB의 실제 결과:

    EcountAliasResolveServiceIT: reservation 생성 1건, active reservation 확인 1건, release 후 0건
    ProductSheetSyncServiceIT: softDeleted=0, deferredByEcountReservation=1, 삭제된 Product=0

공유 운영 DB는 write하지 않았으며, R7의 삭제 UUID 경합을 공유 데이터로 재현하지 않았다.
