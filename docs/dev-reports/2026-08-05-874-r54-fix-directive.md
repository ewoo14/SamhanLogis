# R54 2차 SOL 적대검증 → fix 지시서 — PR #1057 · 이슈 #874

최종 판정: **실 사용자 경로로 재현 가능한 결함 1건이 있다. 머지 비권고.**

R51의 세 결함을 각각 대조한 결과, 동시 gateway 진입과 blank PUSH 차단은 닫혔고 무한 재시도도
유한 `TERMINAL` 수렴으로 바뀌었다. 그러나 새 유한 정책은 약 30초짜리 일시 장애만으로 정상 협업 PUSH를
영구 포기하며, 그 `GATEWAY_RETRY_LIMIT` 종결을 소비하는 운영 주체도 없다. 사용자의 협업 수정 저장은
계속 성공하지만 수신자가 받아야 할 알림은 조용히 누락된다.

단언했다. 실제 상태는 TERMINAL이라 실패했다. 임시 테스트는 판정 후 제거했다.

실 사용자 경로는 협업 수정완료 커밋 → outbox enqueue → notification-service의 약 30초 재시작·네트워크
단절·짧은 장애다. t=0, 2, 6, 14, 30초의 다섯 호출이 실패하면 행은 영구 TERMINAL이 된다. t=31초에
notification-service가 정상화되어도 scheduler는 이 행을 선택하지 않으며, 수신자와 운영자 모두 포기를
알 수 있는 제품 경로가 없다.

### R51 세 항목 폐쇄 대조

| R51 항목 | R54 판정 | 근거 |
|---|---|---|
| 동일 PENDING gateway 동시 진입 | 닫힘 | notification V10 lease와 `claimDispatch()`가 `PENDING/FAILED/RETRYING`의 미점유·만료 행 하나만 원자 claim한다. 30초 만료이므로 claim 뒤 프로세스가 죽어도 PENDING recovery가 다시 획득한다. 좁힌 동시성 테스트 GREEN. |
| 멱등 키 없는 정상 PUSH의 V9 CHECK 위반 | 닫힘 | slip client는 null 키 필드를 생략하고, notification persistence는 null/blank를 NULL로 정규화한다. V8이 기존 165건에 nullable 컬럼을 추가하고 V9가 blank를 NULL로 backfill하므로 기존 165건과 신규 PUSH 모두 성립한다. |
| 영구 실패·해석 불가 무한 재시도 | 무한 루프는 닫힘, 반대급부 결함 발생 | 해석 불가와 editor 자신은 즉시 명시적 TERMINAL, gateway 실패도 5회 뒤 TERMINAL이다. 다만 위 결함처럼 일시 장애까지 약 30초 만에 영구 포기하고 최종 포기를 소비하는 주체가 없다. |

### lease·저장 차단 대조

- claim 뒤 gateway 전 프로세스가 죽으면 DB의 PENDING과 30초 lease가 남고, lease 만료 뒤
  `recoverPending()`이 다시 claim할 수 있다. 영구 미회수 경로는 재현되지 않았다.
- lease 획득 실패는 다른 발송자가 가진 30초 이내 권리일 때만 gateway 진입을 생략한다. 최초 승자가
  완료하면 SENT가 되고, 죽으면 위 만료 복구로 돌아온다.
- 협업 수정 저장 transaction은 outbox enqueue까지만 수행하고 auth/notification/FCM을 기다리지 않는다.
  저장 차단·rollback 회귀는 재현되지 않았다.
- FCM 호출 성공 뒤 complete 전 죽는 잔여 중복 표면은 개발책임자가 이미 인지한 vendor 비멱등 한계로 새
  결함에 세지 않았다.

### 마이그레이션 번호 대조

- notification: 기존 DB 최고 V7에서 이 브랜치 V8→V9→V10은 모두 더 높은 버전이며
  `out-of-order=false`에서 순차 적용 대상이다. 열린 PR 5건의 notification migration과 같은 번호는 0건이다.
- slip: 기존 DB 최고 V105에서 이 브랜치 V108→V109→V110→V111은 모두 더 높은 버전이라 현재 PR만
  적용하면 실제 pending 대상이다. 같은 번호를 가진 열린 PR은 0건이다.
- 단, 열린 PR #1045에는 아직 열린 V106·V107이 있다. **#1057을 먼저 DB 적용하면** slip-service 기본
  `out-of-order=false`에서 나중에 들어온 V106·V107은 현재 V111보다 낮아 정상 순차 적용되지 않는다.
  따라서 번호 중복 결함은 아니지만 **#1045의 V106·V107 적용이 #1057보다 반드시 선행해야 한다.**
- accounting migration 추가는 0건이며 accounting-service는 읽기·compile 범위 밖으로 유지했다.

## ② 불변식 — 구현 수단 지시 금지

1. 정상 수신자의 협업 알림은 수십 초 수준의 일시적인 notification 장애가 끝난 뒤 자동으로 다시 전달될
   기회를 가져야 한다. 단순 시도 횟수 소진만으로 정상 사건이 약 30초 안에 영구 포기되면 안 된다.
2. 해석 불가 수신자, editor 자신, 명백한 영구 실패는 유한 시간 안에 명시적으로 종결되어야 하며 무한
   vendor 후보가 되면 안 된다.
3. 실제 발송 실패로 TERMINAL이 된 사건은 업무 식별자와 종결 사유로 담당 운영 주체가 발견하고 조치할 수
   있어야 한다. DB row/index만 존재하고 아무 제품·운영 경로도 소비하지 않으면 안 된다.
4. 포기 관측에는 내부 UUID를 사용자에게 노출하면 안 되며, 같은 사건을 반복 경보하거나 SENT로 가장하면
   안 된다.
5. 동일 사건·최종 수신자는 retry 동안 같은 notification 멱등 키를 유지하고, 이미 SENT이거나 lease가
   살아 있는 행은 gateway에 다시 진입하면 안 된다.
6. 협업 수정 저장·감사·리비전·ACCEPTED 이력과 HTTP 응답은 retry 시간창, terminal 관측, auth,
   notification 또는 vendor를 기다리거나 그 실패로 rollback되면 안 된다.
7. 기존 165건 PUSH와 신규 null/blank PUSH는 V8~V10 적용 뒤에도 정상 저장·발송되어야 하며 nonblank 키는
   제거되거나 다른 사건과 합쳐지면 안 된다.

## ③ 양방향 RED — 반대급부 필수

### RED-A — 되돌리면 안 되는 것

- `system`, zero UUID, 존재하지 않는 loginId와 editor 자신은 외부 발송 없이 유한 terminal 수렴한다.
- 명백한 영구 gateway 실패는 무한 재시도되지 않고, 최종 포기가 담당 주체에게 한 번 관측된다.
- 느린 auth/notification, executor 거부, backlog, retry 중에도 협업 수정완료 응답은 외부 호출을 기다리지
  않고 성공 저장을 보존한다.
- 동일 PENDING send/send, send/recovery, recovery/recovery 경합의 gateway 승자는 최대 1이다.
- claim 직후 프로세스 종료 사건은 lease 만료 뒤 다시 발송 후보가 된다.
- null/blank 기존 PUSH는 NULL 의미를 유지하고 정상 발송되며, nonblank 멱등 키는 그대로 보존된다.
- **반대급부:** 일시 장애 회복을 위해 retry를 다시 무한화하거나 해석 불가 수신자를 영원히 PENDING으로
  두면 RED다.
- **반대급부:** 관측을 위해 협업 저장 transaction/HTTP 응답에서 notification 상태를 기다리거나 실패를
  사용자 저장 실패로 바꾸면 RED다.
- **반대급부:** 운영 경보에 수신자·전표·event UUID를 그대로 노출하거나 동일 terminal 사건을 scheduler
  주기마다 중복 경보하면 RED다.

### RED-B — 재발하면 안 되는 것

- notification 장애가 현 5회 eligibility 구간(t=0, 2, 6, 14, 30초) 동안 지속된 뒤 다음 시도 전에
  회복하는 시나리오에서 행이 이미 TERMINAL이면 RED다. 회복 뒤 같은 키로 SENT까지 수렴해야 한다.
- `GATEWAY_RETRY_LIMIT` terminal을 만든 뒤 운영자가 사용하는 조회·지표·경보 중 어느 곳에서도 사건 수와
  업무 식별자·사유를 발견할 수 없으면 RED다.
- terminal 관측을 확인한 뒤에도 같은 사건이 다음 주기마다 새 경보로 누적되거나 vendor에 다시 진입하면
  RED다.
- 동일 PENDING의 첫 gateway를 latch로 멈춘 상태에서 두 번째 요청/recovery가 gateway에 들어가면 RED다.
- claim 직후 종료하고 30초 lease를 만료시킨 PENDING이 다시 claim되지 않으면 RED다.
- V9 스키마에서 key 없는 PUSH가 blank CHECK 위반/HTTP 500/알림 누락을 만들거나 기존 165건을 비정상 키로
  바꾸면 RED다.
- #1057 migration을 #1045 V106·V107보다 먼저 적용하는 배포 순서가 허용되면 RED다.
