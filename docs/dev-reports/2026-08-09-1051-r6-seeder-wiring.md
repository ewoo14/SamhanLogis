## ② R5-SOL-2 진단

호출 흐름:

| 항목 | 확인 결과 |
|---|---|
| 호출 지점 | `services/slip-service/src/main/java/com/samhanair/logis/slip/seed/SlipSeeder.java:306` — `productClient.lookup(expectedIds)` |
| 요청 생성 | `SlipSeeder.java:299-303`에서 `HvacSeedProductCatalog` 100개 modelName으로 결정적 UUID 100개 생성 |
| HTTP 호출 | `services/slip-service/src/main/java/com/samhanair/logis/slip/client/ProductClient.java:96-100` — `POST /products/internal/lookup`, body `{ "ids": [...] }` |
| product-service 진입 | `services/product-service/src/main/java/com/samhanair/logis/product/web/ProductInternalController.java:92-95` |
| DB 조회 | `services/product-service/src/main/java/com/samhanair/logis/product/service/ProductService.java:400-410` → `ProductRepository.findAllByIdIn(ids)` (`ProductRepository.java:69`) |
| 조회 키 | `products.id` UUID. `model_code`나 `model_name`으로 조회하지 않는다. |

공유 `product_db` 실데이터 채움률(읽기 전용 SQL):

| 모집단 | 전체 | UUID 행 존재 | `model_code` 비어 있지 않음 | 활성(`is_deleted=false`) |
|---|---:|---:|---:|---:|
| 시더가 요청하는 결정적 UUID 100개 | 100 | 100 (100%) | 0 (0%) | 0 (0%) |
| 전체 `products` | 3,221 | — | 3,121 (96.9%) | 3,083 |

결정적 시드 100행은 모두 `created_by='system'`이며 현재 공유 DB에서는 soft-deleted다. 따라서 “조인 키로 쓰는 코드 컬럼이 비어 있고 UUID만 채워져 있다”는 현상은 해당 100행에 대해서는 **맞지만**, 이번 호출의 키는 코드 컬럼이 아니라 UUID다. 이 호출의 0건을 `model_code` 공백만으로 설명할 수 없다. 현재 소스 계약상 `findAllByIdIn`에는 `is_deleted=false` 조건도 없으므로, 현재 소스와 현재 DB를 함께 기준으로 하면 UUID 100개는 반환되어야 한다.

응답 0의 성격:

* `ProductInternalController`는 조회 결과가 비어도 `ApiResponse.ok(emptyList)`로 **HTTP 200 + 빈 배열**을 반환한다.
* `ProductClient.java:134-137`가 응답 항목 수가 요청 수보다 작으면 그 정상 200 응답을 `NOT_FOUND` 예외(“일부 제품을 찾을 수 없습니다 (요청 100, 응답 0)”)로 변환한다.
* 따라서 R5의 “응답 0”은 HTTP 오류가 아니라 **product-service가 빈 배열을 반환했고, slip-service가 후속 오류로 승격한 것**이다. 현재 소스·현재 실 DB 조합과 불일치하므로, 당시 실행 시점의 product-service 배포본/DB 상태 차이가 셋째 가능성이다. 이 라운드에서는 SOL-2 로직을 수정하지 않았다.

## ③ 격리 환경 실제 실행 원문

공유 스택과 별도로 `r6-1051-net` 네트워크와 `r6-1051-postgres` 컨테이너를 만들고, 빈 `product_db`·`slip_db`에 Flyway를 적용했다. `r6-1051-product`와 `r6-1051-slip`은 이번 수정 후 빌드한 JAR 이미지였고, 두 서비스 모두 공유 DB 주소를 사용하지 않았다.

첫 기동 로그 원문:

```text
HvacProductSeeder created 100 products (skipped 0, total 100)
[SlipSeeder] Stage 2 시드 시작 — 100 slip + ~300 line + 11 status 분포
[SlipSeeder] 완료 — 신규 100건, skip 0건 (총 100건)
[DeliveryBatchSeeder] 완료 — 신규 30건, skip 0건
[EstimateSeeder] 완료 — 신규 40건, skip 0건
[SlipLockSeeder] P2 마감 lock 시드 시작 — ... 대상 상태 CONFIRMED
[SlipLockSeeder] 완료 — 5건 lock 처리 (시더 대상 집합)
```

격리 DB SQL 집계:

```text
product_db products is_deleted=false: 100
slip_db slips: 100
slip_db lock_flag=true and is_deleted=false: 5
slip_db created_by='system', status='CONFIRMED', lock_flag=true: 5
```

같은 격리 환경에서 `r6-1051-slip`만 재기동한 원문:

```text
[SlipSeeder] 완료 — 신규 0건, skip 100건 (총 100건)
[DeliveryBatchSeeder] 완료 — 신규 0건, skip 30건
[EstimateSeeder] 완료 — 신규 0건, skip 40건
[SlipLockSeeder] 완료 — 0건 lock 처리 (시더 대상 집합)
SQL lock count: 5
SQL confirmed system locked count: 5
```

판정: fresh 실행은 **5건 신규 잠금**, 재기동은 **5 → 5**로 멱등했다.

## ④ 공유 DB 보호와 회수

공유 DB에는 INSERT/UPDATE/DELETE를 실행하지 않았다. 시작 전과 종료 후 읽기 전용 SQL 결과는 모두 다음과 같다.

```text
slip_db: lock_flag=true AND is_deleted=false = 5
```

격리 환경 종료 후 다음을 회수했다.

```text
docker rm -f r6-1051-slip r6-1051-product r6-1051-eureka r6-1051-postgres
docker network rm r6-1051-net
docker rmi r6-1051-slip r6-1051-product r6-1051-eureka
```

컨테이너, 네트워크, 임시 이미지 및 PostgreSQL 임시 writable layer가 남아 있지 않음을 `docker ps -a --filter name=r6-1051`와 네트워크 목록으로 확인했다. 별도 named volume은 만들지 않았다.
