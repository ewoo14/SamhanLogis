# #1142 검수완료 전표 되돌림 경로 — 결정 상신 정찰

- 조사일: 2026-08-13 (KST)
- 조사 브랜치: `feat/1142-completed-slip-revert` (`bd0189f76`)
- 관련 PR: #1189
- 조사 원칙: 구현 코드 변경 없음, Git 변경 명령 없음, 공유 DB는 `default_transaction_read_only=on`으로 `SELECT`만 실행
- 건수 기준: 별도 표기가 없으면 `is_deleted=false` 활성 행

## 0. 결론

1. 현행 전표 상태 머신은 전진·반려·취소만 있고 과거 정상 상태로 돌아가는 경로는 없다.
2. 활성 `COMPLETED`는 **13건**(INBOUND 9, OUTBOUND 4)이다. soft-delete 포함 `COMPLETED`는 27건(활성 13, 삭제 14)이다.
3. 활성 13건은 모두 재고 결과물과 연결된다. 9건은 serial instance 15행, 4건은 batch lot 4행이다.
4. 그러나 활성 13건과 연결된 `source_operation_journals`는 **0건**이다. S1 journal 전체 1행은 별도 `CONFIRMED` 전표에 속한다. 따라서 현재 활성 13건은 자동 역연산 근거가 없고, 기존 결정 기록대로 legacy 판정 큐/수동 조정 대상이다.
5. `INSPECTING → COMPLETED` 자체는 재고를 움직이거나 회계 문서를 만들지 않는다. 재고는 직전 `PROCESSING → INSPECTING`에서 예약 출고·차감 또는 입고 생성/회수가 일어난다. 회계전표는 원천 전표가 `CONFIRMED`여야 별도 생성할 수 있다.
6. 활성 `COMPLETED` 13건 중 완료 후 별도 구조물이 연결된 전표는 **1건**이다. `2026/08/03-4`가 완료 뒤 활성 배차그룹 `QA-1039-GROUP-S9`에 편입됐다. 활성 완료 전표의 회계전표 연결, 첨부, 서명 이력, 외부/차량 배차 연결은 각각 0건이다.
7. 개발책임자는 이미 **되돌림 구현**, **범위 B**, **수정 가능한 DRAFT/SAVED까지 복귀**, **재고도 함께 정합화**를 결정했다. 이를 다시 결정 항목으로 올리면 안 된다.
8. 아직 개발책임자 선택이 필요한 것은 권한 소유자, DRAFT/SAVED 목표 상태의 정확한 UX, legacy 전표 처리, 되돌림 이력 모델이다. 후속 연결 자동 연쇄는 기존 PM 결정 및 머지 PR 기록에서 금지되고 `차단 + 후속 전표 안내`로 정리돼 있다.

## 2. 이미 결정된 사항

### 2.1 되돌릴 수단을 구현한다

### 2.2 범위 B이며, 되돌린 뒤 품목·금액을 수정할 수 있어야 한다

> “**B로 진행해야겠어.** 아무래도 **품목이 바뀌거나, 금액이 바뀌거나** 했을 때는 **재고도 바뀌어야** 하고, **계산서를 추후에 바꾸기 위해 회계도 손대야** 하니까.”

> “실질 범위는 **DRAFT/SAVED 까지 되돌리기**”

### 2.3 회계전표는 원천 전표와 별도이며, 금액 변경 시 삭제·재생성한다

## 3. A — 현재 상태

### 3.1 상태 전이도

```text
DRAFT ─save─> SAVED ─send─> SENT ─accept─> ACCEPTED ─process─> PROCESSING
  │              │            │                │
  └─cancel───────┴─cancel─────┴─cancel─────────┘
                              ├─reject──────────────> REJECTED
                              └──────────────────────┐

PROCESSING ─complete + 재고 반영─> INSPECTING ─inspect(검수완료)─> COMPLETED
                                      │
                                      └─reject────────────────────> REJECTED

OUTBOUND: COMPLETED ─ship─> SHIPPING ─deliver─> DELIVERED ─confirm─> CONFIRMED
INBOUND : COMPLETED ─confirm───────────────────────────────────────> CONFIRMED
```

코드 근거:

| 전이 | 파일:줄 |
|---|---|
| 전체 상태 머신 주석 | `services/slip-service/src/main/java/com/samhanair/logis/slip/domain/Slip.java:40-46` |
| `DRAFT → SAVED` | `Slip.java:1098-1101` |
| `SAVED → SENT` | `Slip.java:1108-1117` |
| `SENT → ACCEPTED` | `Slip.java:1143-1152` |
| `ACCEPTED → PROCESSING` | `Slip.java:1159-1163` |
| `PROCESSING → INSPECTING` | `Slip.java:1172-1177` |
| `INSPECTING → COMPLETED` | `Slip.java:1188-1198` |
| `COMPLETED → SHIPPING` | `Slip.java:1205-1213` |
| `SHIPPING → DELIVERED` | `Slip.java:1220-1228` |
| 타입별 `→ CONFIRMED` | `Slip.java:1235-1244` |
| 반려 | `Slip.java:1256-1271` |
| 취소 | `Slip.java:1274-1300`; 허용 집합은 `Slip.java:90-91` |

역방향 메서드가 없다는 추가 근거: `Slip`의 `status = SlipStatus.*` 대입은 생성 및 위 전진/종결 전이뿐이다. `revert|rollback|undo|reopen|backTo` 상태 전이 메서드는 0건이다.

### 3.2 실데이터 건수

2026-08-13 공유 `slip_db` 읽기 전용 실측:

| 조건 | 건수 |
|---|---:|
| 활성 `COMPLETED` | **13** |
| 활성 `COMPLETED / INBOUND` | 9 |
| 활성 `COMPLETED / OUTBOUND` | 4 |
| soft-delete `COMPLETED` | 14 |
| 전체 `COMPLETED`(활성+삭제) | 27 |

이슈 발단 전표 `2026/03/31-1`은 현재 `INBOUND / COMPLETED / is_deleted=true`다. `completed_at=2026-08-08 20:04:11`, `modified_at=2026-08-09 11:55:54`이며 활성 건수에는 포함하지 않았다.

### 3.3 현행 되돌림 경로

**없다.**

- `cancel()`은 DRAFT/SAVED/SENT만 허용하고 COMPLETED에서는 409다(`Slip.java:90-91`, `Slip.java:1294-1299`).
- `reject()`는 SENT/ACCEPTED/INSPECTING만 허용하며 과거 상태가 아니라 REJECTED로 종결한다(`Slip.java:1256-1265`).
- revision restore는 콘텐츠 스냅샷만 복원하고 lifecycle status를 복원하지 않는다.
- soft-delete restore도 삭제 표시를 복구할 뿐 원래 status를 과거 상태로 바꾸지 않는다.
- 상태 되돌림 Controller/API/UI는 찾지 못했다.

### 3.4 검수완료가 실제로 확정하는 것

#### `INSPECTING → COMPLETED` 자체

`Slip.inspect()`는 다음만 변경한다(`Slip.java:1188-1198`).

- 상태를 `COMPLETED`로 변경
- OUTBOUND revision baseline 최초 고정
- `inspectorUserId`, `inspectorSignedAt`, `completedAt` 기록

서비스는 OUTBOUND redline anchor도 최초 고정한다(`SlipService.java:983-993`). 재고·회계·다른 전표 생성 호출은 없다.

#### 재고는 직전 `PROCESSING → INSPECTING`에서 이미 움직인다

`SlipService.complete()`(`SlipService.java:1132-1188`)의 실제 효과:

| 전표/품목 | 효과 |
|---|---|
| OUTBOUND batch | 예약분을 `deduct`하여 재고 차감 (`SlipService.java:1148-1149`) |
| OUTBOUND serial | 예약 instance를 `shipInstances`로 SHIPPED 처리 (`SlipService.java:1141-1145`) |
| INBOUND batch | lot 생성/재고 가산 (`SlipService.java:1173-1176`, `1200-1207`) |
| INBOUND serial | instance 생성 (`SlipService.java:1178-1184`) |
| INBOUND 회수/회차 | serial recall 후 batch inbound (`SlipService.java:1221-1253`) |

예약은 더 앞선 `SENT → ACCEPTED`에서 OUTBOUND에만 생긴다(`SlipService.java:917-950`). batch/serial 예약 해제 API는 있으나, 완료 단계의 deduct/ship/inbound 역연산은 현재 없다.

#### 회계·세금계산서·다른 전표

- lifecycle `complete/inspect/confirm`은 accounting-service를 호출하지 않는다.
- 매출·매입 회계전표는 원천 전표가 `CONFIRMED`일 때 별도 명령으로만 생성할 수 있다.
- 세금계산서는 accounting-service의 별도 흐름이다.
- 따라서 현재 `COMPLETED` 전표는 상태 전이만으로 회계 분개나 회계전표가 자동 생성되지 않는다.
- 실DB에서도 활성 완료 13건과 연결된 매출/매입 회계전표 allocation은 0건이다.

#### 되돌릴 때 필요한 처리

| 목표 | 필요한 처리 | 처리하지 않으면 |
|---|---|---|
| `COMPLETED → INSPECTING` | 상태 및 검수 메타/anchor 정책만 결정 | 재고는 이미 반영된 INSPECTING 의미와 같으므로 재고 수량 불변. 단, 이 목표는 B 결정의 수정 목적을 충족하지 못함 |
| `COMPLETED → PROCESSING` 이전 | complete의 재고 효과 역연산 | 상태는 처리 전인데 재고는 이미 출고/입고된 모순 발생 |
| `COMPLETED → SENT/SAVED/DRAFT` | complete 역연산 + ACCEPTED 예약 해제 + 수락/검수 메타 정책 | 예약 또는 출고/입고 결과가 고아로 남음 |
| 연결 회계전표가 있는 CONFIRMED 계열 | #1144에 따른 회계전표 삭제·재생성 | 금액 수정 뒤 원천과 회계·세금계산서 후보 금액 불일치. 현재 삭제 API 미구현 |

### 3.5 활성 COMPLETED의 연결 실측

#### 재고 결과물 — 완료 직전 생성된 것

| 연결 | 전표 수 | 행 수 | source journal 연결 |
|---|---:|---:|---:|
| serial `stock_instances`의 inbound/outbound/recall slip 번호 | 9 | 15 | 0 |
| batch `stock_lots.inbound_line_id` | 4 | 4 | 0 |
| 합집합 | **13** | 19 | **0** |

즉 활성 13건 전부 재고 흔적이 있지만, 어느 호출이 어떤 생성 집합을 만들었는지 증명하는 S1 journal이 없다. 현재 자동 되돌림 가능 건수는 **0건**으로 봐야 한다.

참고: `inventory_db.source_operation_journals` 전체는 APPLIED 1행뿐이며, 해당 전표는 `2026/08/09-6 / INBOUND / CONFIRMED`다.

#### 검수완료 이후 새로 연결된 것

| 연결 종류 | 완료 전표 수 | 행 수 | 완료시각 뒤 생성 |
|---|---:|---:|---:|
| `dispatch_group_slips` | **1** | 1 | **1** |
| `dispatch_vehicle_group_slip` | 0 | 0 | 0 |
| `external_dispatch_slip` | 0 | 0 | 0 |
| 회계전표 allocation | 0 | 0 | 0 |
| 전표 첨부 | 0 | 0 | 0 |
| 서명 audit / 현재 서명 | 0 | 0 | 0 |

유일한 후속 연결:

```text
전표       2026/08/03-4 (INBOUND, COMPLETED)
완료       2026-08-03 21:44:07
배차그룹   QA-1039-GROUP-S9 / NOT_SENT
그룹 생성  2026-08-05 07:39:17
편입 생성  2026-08-05 07:42:36  ← 완료 뒤
```

구조적 FK는 `dispatch_group_slips.slip_id → slips.id ON DELETE RESTRICT`다(`V104__create_dispatch_group_domain.sql:52-72`). 이 1건은 되돌림 전에 차단 또는 별도 해제가 필요한 실제 표본이다.

## 4. B — 개발책임자 결정이 필요한 것

이미 결정된 B 범위와 재고 정합화 자체는 선택지에서 제외한다. 아래는 남은 세부 결정이다.

### 4.1 누가 되돌릴 수 있는가

| 선택지 | 결과 | 되돌릴 수 없게 되는 데이터/위험 |
|---|---|---|
| A. 신규 전용 권한 `slip.revert / RESTORE` | 콘텐츠 revision 복원과 재고를 움직이는 lifecycle 되돌림을 분리한다. 역할별 최소 권한 부여 가능 | 권한 seed·관리 UI·14서비스 권한 projection 반영 필요. 데이터 비가역성은 늘지 않음 |
| B. 기존 `slip.audit-revert / RESTORE` 재사용 | 신규 page-code가 없어 구현이 작다 | 콘텐츠 복원 권한자가 재고 역연산까지 수행하게 되어 기존 권한 의미가 확대됨 |
| C. 기존 검수 완료 권한 재사용 | 현장 검수자가 실수를 즉시 복구할 수 있음 | 가장 넓은 쓰기 표면. 후속 연결/재고 custody 판단을 현장 역할이 수행하게 되어 잘못된 역연산 위험이 큼 |

별도 마감일은 어느 선택지든 기존 `slip.closed-date-exception / CREATE` 규칙을 추가로 통과해야 한다. 이것은 이미 결정된 규칙이다.

### 4.2 어디까지 되돌리는가

상위 결정은 이미 “DRAFT/SAVED까지”다. 남은 것은 목표 선택 방식이다.

| 선택지 | 결과 | 되돌릴 수 없게 되는 데이터/위험 |
|---|---|---|
| A. 항상 `SAVED` | 내용은 편집 가능하며 전송 전 단계부터 재진행. 채번·생성 사실 유지 | DRAFT로 돌아가야 하는 별도 업무가 있으면 추가 전이 필요. 재고 역연산 범위는 DRAFT와 동일 |
| B. 항상 `DRAFT` | 최초 작성 단계에서 전 과정을 다시 밟음 | SAVED 의미를 잃지만 기존 이력에 남길 수 있음. 재고 역연산 범위는 SAVED와 동일 |
| C. DRAFT/SAVED 중 선택 | 개발책임자 결정 문구를 가장 그대로 구현. 사용 목적에 맞춰 선택 | 잘못된 목표 선택 가능성이 있어 확인 UI와 사유가 필요. 두 목표 모두 재고·예약 역연산은 동일하게 필요 |

상태만 바꾸고 재고를 유지하는 선택지는 기존 B 결정과 충돌하므로 유효 후보가 아니다.

회계는 별도 연결 문서 삭제·재생성 명세가 이미 있다. 남은 구현 선택은 “되돌림 saga가 #1144 삭제를 자동 호출하는가”와 “회계 담당자가 먼저 삭제한 뒤 되돌리는가”지만, 현재 COMPLETED 13건에는 회계 연결이 0건이고 회계 삭제 API도 없다.

### 4.3 연결된 것이 있으면 어떻게 하는가

기존 기록의 정본은 **자동 연쇄 금지, 차단 + 후속 전표번호 안내**다. 아래 A는 기존 결정을 구체화하는 선택이고 B/C는 명시적 결정 변경이 필요하다.

| 선택지 | 결과 | 되돌릴 수 없게 되는 데이터/위험 |
|---|---|---|
| A. 모든 후속 연결 strict block + 안내 | 연결 배차/후속 출고/회계 문서를 별도 정상 경로로 먼저 해제해야 되돌림 가능. PR #1151 기록과 일치 | 해제 경로가 없는 연결은 영구 대기할 수 있으므로 각 도메인에 정상 해제 경로가 반드시 필요 |
| B. 소비 없는 가역 연결만 함께 해제, 소비된 연결은 차단 | `NOT_SENT` 배차그룹처럼 아직 외부 전송되지 않은 연결을 트랜잭션/보상으로 자동 해제 가능 | 서비스 간 부분 실패 시 고아 링크 위험. 기존 “자동 연쇄 금지”를 일부 변경 |
| C. 경고 후 권한자 force | 운영 복구는 빠르지만 연결을 남긴 채 상태를 되돌릴 수 있음 | 고아 배차, 잘못된 시리얼 custody, 원천/회계 불일치가 생길 수 있고 자동 복구 불가. 가장 큰 비가역 위험 |

실데이터 1건(`QA-1039-GROUP-S9`, NOT_SENT)은 A/B의 실제 acceptance 표본으로 사용할 수 있지만 공유 DB에서 실행해서는 안 된다.

### 4.4 이력을 어떻게 남기는가

어느 선택지든 최소 필드는 `operationId`, 전표번호/내부 ID, from/to 상태, 사유, 요청자/승인자, 시작·종료시각, 원 source operation IDs, 역연산 결과 IDs, 차단 연결 목록, 단계별 성공/실패, 재시도 횟수여야 한다.

| 선택지 | 결과 | 되돌릴 수 없게 되는 데이터/위험 |
|---|---|---|
| A. 기존 slip revision/audit에 상태 diff만 추가 | 사용자 타임라인 재사용, 구현 작음 | inventory 역연산과 saga 재시도 상태를 1:1 연결하기 어려움. 부분 실패 원인 복구 정보가 부족해질 수 있음 |
| B. 전용 `slip_revert_operations` + 단계 journal | 멱등성·부분 실패·재시도·후속 blocker를 구조적으로 기록 | 사용자 타임라인에 별도 projection 필요. 테이블/운영 UI 증가 |
| C. B의 전용 operation을 정본으로 하고 기존 audit에 요약 projection | 운영 복구와 사용자 감사 모두 충족 | 이중 기록 정합성 필요. 같은 트랜잭션/outbox 경계가 없으면 둘 중 하나만 남을 수 있음 |

S1 `source_operation_journals`는 정방향 근거이지 되돌림 사용자 감사 전체를 대체하지 않는다.

### 4.5 아직 모르는 것

- 검수자/수락자 ID와 시각, `completedAt`, revision baseline/redline anchor를 현재값에서 null/reset할지, 과거 사실로 유지할지 결정이 없다.
- 과거 실업무 전표 처리에 대해 “앞으로만”, “판정 큐+수동 조정”, “사후 재구성” 중 최종 개발책임자 결정이 없다. PM 권고는 판정 큐+수동 조정이다.
- 진행 중 재고 실사·이동, 후속 소비 lot/instance를 어떤 조회 계약으로 한 번에 판정할지 구현이 없다.
- 서비스 간 saga가 일부 성공 후 실패했을 때 원상 재적용할지 `REVERT_PENDING`으로 남길지 결정이 없다.
- `2026/03/31-1`이 왜 soft-delete됐는지 모른다.

## 5. C — 독립 머지 가능한 슬라이스

S1은 이미 PR #1151로 머지됐다. 아래 순서는 각 단계가 독립적으로 리뷰·배포 가능하도록 읽기 계약 → 재고 원자 기능 → orchestration → UX 순으로 자른 것이다.

### S2. 되돌림 preflight/판정 조회

범위:

- 전표 상태, 마감/lock, source journal 유무, 생성 lot/instance, 후속 소비·실사·이동, 배차/회계/첨부/서명 연결을 읽기 전용으로 집계
- 결과를 `ELIGIBLE` 또는 구체적 blocker code와 사용자 노출 전표번호로 반환
- mutation 없음

끝 조건:

- 4개 정방향 재고 경로마다 journal 있음/없음/NO_OP를 구분
- 현재 활성 COMPLETED 13건은 추정 통과하지 않고 전부 명시적 legacy blocker로 분류
- 배차그룹 실표본은 `DOWNSTREAM_DISPATCH_GROUP` blocker로 식별
- 같은 요청을 반복해도 DB 변화 0

### S3. inventory 역연산 4종

범위:

- `deduct`, `ship-batch`, `lots/inbound`, `instances/batch`의 source-operation 기반 inverse
- 정방향과 같은 잠금, reversal 유일키, 멱등 결과, 성공/실패 journal
- 후속 소비·open audit/transfer·revision drift는 fail-loud

끝 조건:

- 네 API 각각 APPLIED/NO_OP/차단 양방향 테스트 통과
- 두 번 호출해 추가 재고 변화 없음
- 부분 실패 시 원상복구 또는 결정된 중간상태가 일관되게 남음
- 과거 journal 없는 행을 식별자 추론으로 역연산하지 않음

### S4. slip-service 되돌림 orchestration

범위:

- 선택된 DRAFT/SAVED 목표, 선택된 권한, 마감일/lock 가드
- inventory inverse를 역순 실행하고 ACCEPTED 예약 해제
- 선택된 감사 모델과 idempotency
- 검수/수락 메타 및 anchor 처리 정책 반영

끝 조건:

- `COMPLETED → 목표 상태 → 수정 → save/send/accept/process/complete/inspect` 재진행 E2E 성공
- 재고 전후 delta가 정확하고 고아 예약/lot/instance 0
- 권한 없음, 마감일, lock, journal 없음, 후속 소비를 각각 차단
- 같은 operation ID 재호출로 중복 역연산 0

### S5. 후속 연결 blocker와 Desktop UX

범위:

- 상세 화면의 되돌림 진입, 사유/목표 확인, preflight blocker 표시
- UUID 대신 전표번호·배차그룹번호·회계전표번호 표시
- 기존 결정대로 후속을 먼저 해제하도록 안내

끝 조건:

- eligible/legacy/배차연결/회계연결/후속소비 화면 상태가 모두 구분됨
- 경고만 보고 force 실행되는 우회 경로 없음(선택 C가 별도 승인되지 않는 한)
- 성공 후 상태·이력·재고가 새로고침/SSE에서 일치

### S6. #1144 회계전표 삭제·재생성·재연결

범위:

- 매출·매입 회계전표의 상태별 삭제/취소 규칙
- 세금계산서 발행/POSTED/마감 연결 가드
- 금액 수정 후 재생성·재연결

끝 조건:

- DRAFT/POSTED/세금계산서 연결 상태별 허용·차단이 명세화되고 테스트됨
- 원천 전표 수정 금액과 새 회계전표 총액/공급가액/부가세가 일치
- 기존 회계전표 삭제 흔적과 새 연결 계보가 남음

이 슬라이스는 #1142 B의 상태 되돌림과 독립 머지 가능하며 #1144 에픽 소유로 두는 편이 경계가 명확하다. 단, 자동 saga 연동 여부는 개발책임자 결정 후 S4 또는 S6 후속으로 연결한다.

### S-Legacy. 과거 전표 판정 큐/수동 조정 (선택 슬라이스)

착수 조건: 과거 실업무 전표를 “앞으로만”으로 포기하지 않고 판정 큐로 처리하기로 결정한 경우.

끝 조건:

- QA/시드와 실업무 후보를 삭제 없이 분리
- 각 후보의 증거, 모르는 항목, 수동 조정 결과를 감사 가능하게 남김
- 사후 추정만으로 자동 inverse를 실행하지 않음

## 6. 실행용 게이트 요약

```text
S2 preflight가 ELIGIBLE
  AND source journal이 네 정방향 효과를 모두 증명
  AND 후속 소비/실사/이동 없음
  AND 배차·회계 등 blocker 해제
  AND 마감/lock/권한 통과
    → S3 inverse
    → 예약 해제
    → slip 상태·메타 전이
    → 감사 commit
    → 수정 후 정방향 lifecycle 재진행

하나라도 불명/불일치
    → 상태 변경 0
    → 명시적 blocker + 사용자 노출 식별자
    → legacy 판정 큐 또는 후속 문서 선해제
```

## 7. 실데이터 조회 재현 정보

- 컨테이너: `samhan-postgres`
- DB: `slip_db`, `inventory_db`, `accounting_db`
- 모든 psql 호출에 `PGOPTIONS='-c default_transaction_read_only=on'` 적용
- 로그인/API 호출 없음. 따라서 `last_login_at` 등 공유 DB write 없음
- INSERT/UPDATE/DELETE/DDL/상태 전이 실행 없음

주요 판정식:

```sql
-- 활성 검수완료
SELECT slip_type, count(*)
FROM slips
WHERE is_deleted=false AND status='COMPLETED'
GROUP BY slip_type;

-- S1 journal 연결
SELECT count(*), count(DISTINCT slip_id)
FROM source_operation_journals
WHERE is_deleted=false AND slip_id IN (<활성 COMPLETED slip UUID>);

-- 회계 연결
SELECT count(DISTINCT source_slip_id)
FROM sales_accounting_slip_allocations
WHERE is_deleted=false AND source_slip_id IN (<활성 COMPLETED slip UUID>);
-- purchase도 동일
```

DB 간 FK가 없으므로 `slip_db`에서 UUID/전표번호/line UUID를 읽은 뒤 각 DB의 `IN (...)` read-only 질의로 대조했다.
