## 1. 결론

외부 1px scroll 뒤 focus가 남은 검색 input을 실제 마우스로 다시 클릭하면 dropdown이 재열린다.
열린 상태의 클릭은 토글하지 않고 계속 열린 상태를 유지한다. 검색 결과가 0건이면 기존 6종 문서 참조 picker 관례대로 listbox와 빈 결과 문구를 만들지 않는다.

스크롤 중 닫기 정책은 유지했다. scroll event가 click보다 늦게 전달되는 Chromium 경합에서는, click 시점에 fixed dropdown과 anchor 좌표가 이미 어긋난 것을 ref로 기록하고 scroll close의 먼저 닫힌 commit 뒤 다음 rAF에서 후보와 새 위치를 다시 연다.

## 2. 원인 확정 근거

현행 원인은 SOL의 전제와 일치했다.

- `DocumentReferencePicker.tsx`의 기존 열기 경로는 `handleFocus()`와 검색 응답의 `setOpen(nextOptions.length > 0)`뿐이었다.
- input에는 `onFocus`, `onBlur`, `onKeyDown`만 있었고 focus-retained mouse click 경로가 없었다.
- 외부 scroll close는 query/options를 지우지 않고 `open`과 portal position만 닫는다.
- Chromium-1217 원문:

```text
INPUT_EVENT=focus
RED_A_BEFORE={"scrollY":0,"listboxCount":1,"active":"doc-ref-search-input","query":"2026/","options":7}
RED_A_ONE_PX_CLOSED={"scrollY":1,"listboxCount":0,"active":"doc-ref-search-input","query":"2026/","options":0}
INPUT_EVENT=pointerdown
INPUT_EVENT=mousedown
INPUT_EVENT=mouseup
INPUT_EVENT=click
RED_A_RECLICK={"scrollY":1,"listboxCount":0,"active":"doc-ref-search-input","query":"2026/","options":0}
```

재클릭에는 `focus`가 없었다. 닫힌 DOM의 option count는 0이지만 query는 보존되고, 같은 상태에서 ArrowDown을 누르면 후보 7건이 다시 나타나 state 보존도 확인됐다.

추가로 scroll 직후 mouse click 경합을 계측했다.

```text
pointerdown → mousedown → mouseup → click
약 10ms 뒤 window scroll event
click 직후: aria-expanded=true, listbox=1
scroll event 반영 후: aria-expanded=false, listbox=0
```

따라서 단순히 `onClick`에서 `setOpen(true)`만 호출하면 click 시점의 `open=true`와 뒤늦은 scroll close에 막힌다.

## 3. 기존 6종 picker 대조

기존 6종은 모두 같은 `DocumentReferencePicker`를 사용한다. 유형별로 다른 click/0건 정책은 없었다.

|---|---|---|---|---|
| 출고전표 `OUTBOUND_SLIP` | focus 또는 검색 응답 | 토글 없음 | listbox 없음, 빈 결과 문구 없음 | 공통 component |
| 입고전표 `INBOUND_SLIP` | focus 또는 검색 응답 | 토글 없음 | listbox 없음, 빈 결과 문구 없음 | 공통 component |
| 분개장 `JOURNAL` | focus 또는 검색 응답 | 토글 없음 | listbox 없음, 빈 결과 문구 없음 | 공통 component |
| 세금계산서 `TAX_INVOICE` | focus 또는 검색 응답 | 토글 없음 | listbox 없음, 빈 결과 문구 없음 | 공통 component |
| 거래명세서 `STATEMENT` | focus 또는 검색 응답 | 토글 없음 | listbox 없음, 빈 결과 문구 없음 | 공통 component |

검색 응답 0건의 실제 코드 계약은 `setSearchState({ options: [] })`와 `setOpen(false)`다. live spec도 `NO_MATCHING_DOCUMENT_000`에서 `listbox count = 0`을 단언한다.

design-system `AsyncAutocomplete`의 `검색 결과 없음`은 별도 컴포넌트 계약이다. 문서 참조 picker는 그 surface를 사용하지 않으므로 새 문구를 도입하지 않았다.

## 4. 선택한 수단과 새 surface 처리

- input에 `onClick={handleClick}`을 추가했다.
- 후보가 없거나 disabled면 아무 surface도 만들지 않는다.
- 후보가 있으면 `setOpen(true)`만 수행한다. 이미 열린 상태에서도 같은 값을 설정하므로 토글하지 않는다.
- 열린 상태에서 click 시 fixed dropdown과 anchor 좌표가 어긋나 있으면 `reopenAfterScrollRef`를 세운다.
- scroll close는 먼저 `visibility hidden`·`position null`·`open false`를 commit한다. 재열기 표식이 있을 때만 다음 rAF에서 `open true`와 `updateDropdownPosition()`을 실행한다.
- 일반 scroll에는 표식이 없으므로 기존 first-paint 닫기가 그대로 동작한다.
- Esc는 기존대로 options를 비우므로 Esc 후 click은 빈 surface를 만들지 않는다. 0건 검색도 동일하다.
