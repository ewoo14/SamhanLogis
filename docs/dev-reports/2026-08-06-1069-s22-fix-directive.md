# #1069 S22 SOL fix 지시서 — BUNDLE 전환 오류 안내 유실

## 판정과 재현 난이도

**실 사용자 경로에서 재현 가능한 결함 1건. 현 HEAD `f40e51205d7bca1614e3ad1fd87c353e130e0a8c`은 머지 비권고다.**

- **F1 — BUNDLE 거래처 주문을 판매전표로 전환하면 서버의 조치 안내가 서비스 경계와 화면에서 유실된다.**
- 재현 난이도: **낮음**. 경합·지연 조작이 필요 없다. BUNDLE 품목으로 거래처 주문을 만든 뒤 주문 상세의 `판매전표 전환` 또는 주문 목록의 병합 전환을 정상 조작하면 된다.
- 실제 결과:
  1. `SlipPublishService.resolveLines()`는 400 `INVALID_INPUT`과 `세트 품목은 판매전표 라인으로 저장할 수 없습니다. 구성품으로 전개해 주세요.`를 만든다.
  2. `partner-order-service`의 `SlipServiceClient`는 400 응답 본문을 읽지 않고 `slip-service 4xx: 400 BAD_REQUEST`로 바꾼다.
  3. 단건 화면은 400을 별도 처리하지 않아 다시 `전환에 실패했습니다. 잠시 후 다시 시도해 주세요.`로 덮는다. 사용자는 재시도로 해결되지 않는 이유와 필요한 조치를 알 수 없다.
  4. 병합 화면은 응답의 `message`를 표시하지만 이미 서비스 경계에서 원문이 사라져 `slip-service 4xx: 400 BAD_REQUEST`만 보인다.
- 저장 안전성은 유지된다. `PartnerOrderConvertService`는 slip 발행 실패 시 앞서 예약한 재고를 보상하고, `convertedQuantity` 누적은 발행 성공 뒤에만 수행한다. 결함은 조용한 원인·조치 유실이다.

## 1. 좌표

### 오류 원문 생성

- `services/slip-service/src/main/java/com/samhanair/logis/slip/publish/SlipPublishService.java:762-770`
  - BUNDLE을 명시적으로 거부하며 사용자가 해야 할 조치를 포함한 한국어 문구를 만든다.

### 첫 번째 유실 — 서비스 경계

- `services/partner-order-service/src/main/java/com/samhanair/logis/partnerorder/client/SlipServiceClient.java:136-144`
  - 단건 발행의 기타 4xx 처리에서 응답 본문을 읽지 않고 상태 코드만으로 새 `BusinessException`을 만든다.
- `services/partner-order-service/src/main/java/com/samhanair/logis/partnerorder/client/SlipServiceClient.java:218-226`
  - 병합 발행도 같은 방식으로 원문을 버린다.

  - 현 테스트는 400이 `INVALID_INPUT`인지에만 머물러 upstream 한국어 문구 보존을 계약하지 않는다.

### 두 번째 유실 — 단건 사용자 화면

- `clients/desktop/src/renderer/routes/SalesPartnerOrderDetailPage.tsx:317-368`
  - 409와 403만 업무 오류로 처리하고 400은 모두 일반 재시도 문구로 덮는다.
- `clients/desktop/src/renderer/routes/SalesPartnerOrderDetailPage.tsx:1705-1714`
  - 오류 배너 자체는 `role="alert"`로 접근 가능하지만 표시할 원인·조치 문구가 이미 유실됐다.
- `clients/desktop/src/renderer/routes/components/MergeConvertDialog.tsx:493-528`
  - 400의 `message`를 표시하나 서비스 경계에서 상태 코드 문구로 바뀌어 조치 가능하지 않다.

### 전수표 증거 무결성

S21 보고서의 생성 경로 표는 핵심 영속 지점을 대부분 포함하지만 이름 그대로의 전수표는 아니다.

- `services/partner-order-service/src/main/java/com/samhanair/logis/partnerorder/scheduler/SlipPublishOutboxProcessor.java:31-40`
  - scheduler/batch 재시도가 `publishFromPartnerOrder()`를 호출하는 진입점이 표에 없다. 최종적으로 S21의 공유 resolver를 지나므로 별도 부모 영속 우회는 아니다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/estimate/revision/service/EstimateRevisionService.java:131-161` → `Estimate.restoreFromSnapshot()` → `EstimateToSlipConverter.convert()`
  - 견적 revision 복원 뒤 판매전표 변환하는 사용자 진입점이 표에 없다. 현재 읽기 전용 DB에서 BUNDLE을 담은 활성 견적·전표 revision은 모두 0행이어서 이번 라운드의 별도 도달 결함으로 세지는 않았다.
- `SlipSeeder`는 `dev` 프로필과 `app.slip.seed-test-data=true` 이중 가드의 비사용자 시드 경로라 사용자 경로 전수에서 제외한다.

전수표는 위 진입점을 추가하고, `공유 resolver 통과`, `기존 스냅샷만 복원`, `비사용자 시드`처럼 영속 지점과 진입점을 구분해야 한다.

## 2. 불변식

1. BUNDLE 부모는 단건·병합·비동기 outbox 재시도·견적 발행 어디에서도 `slip_lines.product_id`로 저장되면 안 된다.
2. BUNDLE 전환이 거부되면 최종 사용자 화면에 원인과 실제 조치가 한국어로 보여야 한다. 내부 서비스명, HTTP 상태 문자열, 무의미한 재시도 안내만 노출하면 안 된다.
3. 단건과 병합은 같은 업무 오류에 같은 수준의 조치 안내를 제공해야 한다.
4. 정상 SINGLE 단건·병합 전환의 재고 예약, 전표 발행, VAT 포함 단가·수량·`sourceOrderLineId`·`categoryKey`, converted 누적 계약은 바뀌면 안 된다.
5. BUNDLE 거부 또는 다른 발행 실패에서 선행 재고 예약은 보상되고 converted 누적은 없어야 한다.
6. S19 a11y 상태 계약과 `#1063` 초기 5행·마지막 행 증식·trailing 빈행 저장 제외 규약은 유지해야 한다.
7. fix가 임의의 모든 400 원문을 그대로 노출해 내부 구현 정보나 민감값을 사용자에게 새로 노출하면 안 된다.

## 3. 양방향 RED

### RED-B — 결함 재현

- slip-service가 BUNDLE 전환에 대해 400과 `세트 품목은 ... 구성품으로 전개해 주세요.`를 반환했는데 partner-order-service 응답에서 원인·조치 문구가 사라지면 RED.
- 단건 전환 화면이 위 실패를 `전환에 실패했습니다. 잠시 후 다시 시도해 주세요.`로만 표시하면 RED.
- 병합 전환 화면이 위 실패를 `slip-service 4xx: 400 BAD_REQUEST`처럼 내부 서비스·HTTP 문구로 표시하면 RED.
- 오류 배너가 없거나 접근성 트리에서 안내를 읽을 수 없으면 RED.
- BUNDLE 실패 뒤 재고 예약이 남거나 `convertedQuantity`가 증가하면 RED.

### RED-A — 반대급부 보존

- 정상 SINGLE 단건·병합 전환이 새 오류 전달 처리에 걸리거나 발행 결과가 바뀌면 RED.
- 재고 부족 409, 권한 403, 잔여수량 경합 409의 기존 업무 안내가 BUNDLE 문구로 오분류되면 RED.
- 외부 서비스의 임의 400 본문에 든 내부 상세나 민감값을 무검증으로 화면에 투과하면 RED.
- 비동기 outbox의 transient/permanent 분류가 달라지거나 재시도 수렴이 깨지면 RED.
- 판매전표 화면의 pending/종료 a11y 상태 또는 `#1063` 빈행 규약이 깨지면 RED.

## 4. 범위 밖 / 안 본 범위

- 범위 밖: `#1057`, `#1066`, `#1075`, `#1080` 파일, BUNDLE 자동 전개 정책 재설계, product master 변경, Docker 재빌드·재배포·중지, DB write, 전체 게이트.
- 안 본 범위: DB write가 필요한 실제 주문 생성·전환 클릭, 실제 모바일 기기, 회계·재고의 전체 기능, 타 트랙 화면, 배포본과 HEAD의 바이너리 동일성.
- 읽기 전용으로 확인: 현재 활성 product의 권위 BUNDLE 344개, 활성 판매전표의 BUNDLE 교차 0행, slip/estimate revision의 BUNDLE 교차 0행, 현재 잔여 BUNDLE 주문 라인 0행.
- 기준 수치: `created_at < 2026-08-06 00:00:00`, 활성 `OUTBOUND DRAFT`의 전체 라인은 S20 기준과 정확히 같은 **2,387행 / 2,171전표 / 2,902,645,781원**이다. 다만 현재 활성 product master의 `SINGLE`과 직접 교차하는 부분집합은 **2,107행 / 2,100전표 / 2,837,681,781원**이며, 나머지 280행은 현재 활성 product ID와 교차하지 않는다. S21 보고서 자체는 DB 조회를 수행하지 않았다고 명시했으므로 수치를 S21 실측으로 표현하면 안 된다.
- 현재 DB 총계는 이후 데이터가 추가되어 위 고정 기준선과 다르다. 고정 cutoff 없이 현재 총계를 기준선과 비교하지 않았다.
