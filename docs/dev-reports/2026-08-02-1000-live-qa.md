## 4. 시나리오 결과

### 1) 목록·상세의 모델명 노출

대상은 실 DB에서 `product_code=010001`, `model_code IS NULL`, `model_name=AR05TXEAAWKNEU-01`인 이카운트 계보 품목이다.

- 목록 `GET /api/v1/products?q=AR05TXEAAWKNEU-01&size=5`: HTTP 200, `modelCode: "AR05TXEAAWKNEU-01"`
- 상세 `GET /products/by-model/AR05TXEAAWKNEU-01`: HTTP 200, `modelName: "AR05TXEAAWKNEU-01"`, `modelCode: null`
- 관찰: 옛 순번코드 `010001`은 사용자 노출 목록/상세 식별자로 나오지 않고 모델명이 반환됨.
- 캡처: `01-live-product-list-model-name.png`, `02-live-product-detail-model-name.png`

**판정: PASS (standalone 실 HTTP 응답 기준).**

### 3) 출고 수락 `SENT → ACCEPTED`

- standalone product lookup 관문까지 확인: 모델명 lookup 200, 옛 코드 lookup 200.
- 전표 상태 전이는 실행하지 않음. 공유 실전표를 ACCEPTED로 변경하는 write가 발생하므로 데이터 규율상 수행하지 않았다.
- 따라서 실 전표 19건 전수의 수락 경로 통과 여부는 **미실시**다.

### 4) 재고 현황 행 키·중복

- inventory-service 화면 렌더 및 `productCode-warehouseCode` 행 키 검증은 **미실시**다.
- 공유 inventory DB read-only 행 수는 측정했으나 화면 행 키 판정의 대체 근거로 사용하지 않는다.
