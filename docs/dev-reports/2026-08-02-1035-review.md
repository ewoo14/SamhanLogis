# #1035 창고 UUID 기동 검증 1차 적대검증 (PR #1048)

## 확인 0 — 범위·금지사항 고정

- 검증 범위는 오직 도달성이다. 코드 수정, Git 쓰기, Docker 재빌드·재기동, 실 DB 쓰기를 하지 않는다.
- 결함마다 실 사용자 경로 재현 여부, 재현 명령·출력 원문, 영향 범위를 기록한다.
- 보고서에는 창고 식별자 원문을 기록하지 않고 창고코드만 사용한다.

## 확인 1 — 선행 보고서의 주장과 검증 우선순위

- 구현 보고서는 기동 검증이 서비스 간 HTTP 계약을 사용하며, 전체 테스트에서는 외부 창고 검증을 끄고 전용 단위 테스트에서 조회 결과를 주입했다고 주장한다.
- 정찰 보고서는 운영 매핑이 환경변수 4개·창고코드 4개이고, 당시 읽기 전용 실 DB 대조에서 `[00003]`, `[2]`, `[14]`, `[1]` 모두 실재했다고 기록한다.
- 따라서 1순위는 정상 운영 값에서도 HTTP 의존성 때문에 기동이 막히는지, 일시 장애와 미실재가 구분되는지, 기본값 `true`가 로컬·CI의 실제 Spring 기동 문맥에 미치는 범위다.

## 확인 3 — 기동 차단 데이터 흐름

- `WarehouseCodeMapper.logEffectiveMap()`은 맵이 비어 있지 않고 기본값 `true`이면 `validateConfiguredWarehouses()`를 동기 호출한다.
- 각 항목마다 `WarehouseInternalClient.findWarehouseByCode(warehouseCode)`가 `GET /internal/inventory/warehouses/by-code?code=<매핑 key>`를 호출한다.
- client는 internal token 미설정, 모든 HTTP 오류, 연결·타임아웃·DNS 오류, 빈/비정상 응답, 응답 파싱 오류를 모두 `Optional.empty()` 하나로 축약한다.
- mapper는 그 모든 `empty`를 실제 미실재와 동일한 `IllegalStateException("활성 창고가 존재하지 않거나 조회할 수 없습니다")`으로 바꾼다.
- 첫 가설: inventory-service 일시 장애나 늦은 기동은 실제 미실재와 구분되지 않고 slip-service의 Spring context 생성을 차단한다. 실행 재현으로 확인한다.
- 추가 대조 필요: mapper의 key는 `[00003]`, `[2]`, `[14]`, `[1]`인데 정찰 보고서가 기록한 실 창고코드는 `HQ-001`, `VH-001`, `CS-001`, `VR-001`이다. `/by-code`가 어느 코드 체계를 받는지 endpoint 구현을 확인한다.

## 확인 6 — 전용 테스트 3건의 실제 경로

- 세 테스트 모두 Spring context를 기동하지 않고 `new WarehouseCodeMapper()`로 객체를 직접 만든 뒤 setter로 client·map·enabled를 주입하고 `logEffectiveMap()`을 직접 호출한다.
- `setWarehouseValidationEnabled(true)`는 private boolean field의 Lombok setter를 실제로 바꾸므로 이 직접 호출에서는 실효가 있다.
- 미실재 테스트는 mock 기본값 `Optional.empty()`로 validation 예외를 지난다. placeholder 테스트는 UUID 파싱 예외를 지난다.
- 정상 테스트는 `/by-code("00003")`가 code `00003`을 반환한다고 mock한다. 실제 inventory endpoint/DB에는 없는 상태를 만들어 green이므로 정상 운영 기동을 증명하지 않는다.
- 세 테스트 모두 실제 HTTP client 오류 분기, Spring `@PostConstruct`, application property 우선순위, 서비스 발견/기동 순서를 지나지 않는다.

## 결함 B-01 — 정상 운영 4개가 전부 404여서 slip-service 기동 차단

① 실 사용자 경로 재현 여부: **재현됨.** 현재 공유 inventory-service의 실 endpoint를 읽기 전용으로 호출했다. Docker 재빌드·재기동 및 DB 쓰기는 하지 않았다.

② 재현 명령: 실행 중 inventory-service의 internal token을 프로세스 메모리에서만 읽고, 응답 body에서는 `data.code`만 출력하도록 `System.Net.Http.HttpClient`로 `/internal/inventory/warehouses/by-code`를 호출했다.

출력 원문:

```text
requested=00003 status=404 returnedCode=-
requested=2 status=404 returnedCode=-
requested=14 status=404 returnedCode=-
requested=1 status=404 returnedCode=-
requested=HQ-001 status=200 returnedCode=HQ-001
requested=VH-001 status=200 returnedCode=VH-001
requested=CS-001 status=200 returnedCode=CS-001
requested=VR-001 status=200 returnedCode=VR-001
```

③ 영향 범위:

- PR 코드가 배포되면 정상 UUID 환경변수 4개와 실 DB 활성 창고 4개가 모두 있어도 첫 legacy code 조회가 404다.
- client가 404를 `empty`로 바꾸고 mapper가 이를 `IllegalStateException`으로 바꾸므로 slip-service Spring context가 기동하지 않는다.
- 영향은 특정 발행 요청이 아니라 slip-service 전체 비가용이다. 창고 매핑 iteration 순서에 따라 실패 메시지의 첫 창고코드만 달라질 수 있으나 4개 모두 실패 조건이다.

## 결함 B-02 — 일시 장애·늦은 기동을 미실재와 구분하지 않고 영구 기동 실패
