# R42 fix 보고서 — #1057 협업 알림 내구성·timeout 오매핑

## 1. RED-first 기록

지시서에 따라 구현 전에 RED를 작성하고 지정 Gradle 명령을 실행했다.

```text
SlipCollabNotificationDispatchTest > rejectedExecutor_neverRunsExternalNotificationOnRequestThread()
    java.lang.NoSuchMethodException at SlipCollabNotificationDispatchTest.java:30

... cannot find symbol
  symbol:   variable SlipCollabNotificationOutbox
```

첫 RED는 기존 `RejectedExecutionException` 동기 fallback을 겨냥했고, 아직 존재하지 않는 durable outbox 계약 때문에 컴파일 실패했다. `GlobalExceptionHandlerTest`에는 잠금 원인 없는 `QueryTimeoutException`이 409가 아니어야 한다는 RED를 추가했다.

구현 후 RED-A/RED-B 관련 좁은 회귀와 기존 협업 병렬 저장·알림·잠금 계약이 함께 GREEN이 되도록 수정했다.

## 2. 적용 내용

- 커밋 트랜잭션 안에 `slip_collab_notification_outbox` row를 저장한다.
- `(slip, editor, raw recipient, subject, body)` SHA-256 fingerprint와 DB unique 제약으로 동일 저장·수신자 중복을 차단한다.
- afterCommit에서는 outbox drain 제출만 수행한다. executor 거부 시 요청 스레드 동기 fallback을 하지 않고 scheduler가 row를 회수한다.
- worker는 `PENDING/SENDING`을 claim하고, 전달 성공은 `SENT`, 실패는 지수 backoff `PENDING`으로 남긴다.
- claim은 30초 `SENDING` lease를 사용해 scheduler/worker의 재claim을 막고, worker 비정상 종료 후에는 lease 만료 뒤 재회수한다. 외부 호출은 transaction 밖에서 실행한다.
- Spring task executor의 정상 종료 대기(`await-termination=true`, 기본 10초)를 켰다. 종료 중 미처리 row는 DB 상태로 남아 재기동 시 회수된다.
- `QueryTimeoutException`은 일반 500과 중립 문구로 분리하고, genuine JPA/Spring pessimistic lock 예외의 409 계약은 유지했다.
- 푸시 결과 판정용 `sendUserPushWithResult`를 추가했다. 기존 void API는 호환용으로 유지했다.

### ① 이번 fix로 새로 가능해진 상태·조합과 결과

| 상태·조합 | 결과 |
|---|---|

| 정상 컨텍스트 종료 + 미처리 row | executor 종료 대기 설정과 DB row 보존으로 재기동 후 재처리 가능 |
| 외부 auth/notification 실패 | 저장/응답은 rollback되지 않고 row가 backoff `PENDING`으로 남음 |

## R43 — 마이그레이션 번호 정정

### 결함 확인

PM 실측과 저장소를 대조한 결과, slip-service는 `out-of-order`를 켜지 않았고
(Flyway 기본값 `false`), R42의 outbox DDL이 `V62`로 존재했다. 기존 `slip_db`가
V105까지 적용된 상태에서는 V62가 미적용 resolved migration으로 남아 부팅을 막을 수
있다. R42의 outbox 저장·재시도·fingerprint 중복 방지·`수정완료` 응답 비차단 동작은
마이그레이션 파일명과 독립적이므로 변경하지 않았다.

### 조치 및 이유

- `V62__create_slip_collab_notification_outbox.sql`을
  `V108__create_slip_collab_notification_outbox.sql`로 이동했다.
- V108은 기존 DB 실측 최고 버전 V105보다 높고, 열린 #1045가 예약한 V101~V107보다도
  높아 신규 배포에서 순서대로 적용된다. `out-of-order`를 켜거나 기존 migration 내용을
  수정하지 않았다.
- 같은 결함의 재발 방지를 위해 `SlipCollabMigrationVersionTest`를 추가했다. 이 테스트는
  기존 DB 최고 버전(105)과 열린 PR 번호 상한(107)을 명시하고, outbox migration이
  V108 리소스로 존재하며 두 기준보다 높은지 검사한다. 따라서 상위 버전이 이미 적용된
  DB에서 낮은 번호 migration을 추가하는 실수를 CI의 좁은 게이트에서 바로 드러낸다.

### R43 검증

RED 단계에서 V108 리소스가 없음을 확인했다.

```text

```

