# R21 — 출고 사업자번호 보존·접근권한 경계 fix

## 조사 1 — R20 확정 범위와 기준

`docs/dev-reports/2026-08-03-1015-r20-reconvergence.md`의 운영 경로 표와 현재 HEAD(`1e54481e9`)를 확인했다. R18은 주문 전환 두 경로만 `bizCode`를 저장했고, R20은 운영 생성 구현 7개(일반 작성, 복사, 모바일 주문, 견적 직접 변환, 견적 publish, 주문 단일 전환, 주문 병합 전환)와 개발 seed를 구분했다. 이번 라운드는 사용자가 확정한 4개 결함과 CI 경계 테스트만 대상으로 한다.

## 조사 2 — CI red 3건의 원인 판정

먼저 구현을 바꾸지 않고 현재 실패를 재실행했다.

```text
./gradlew :services:partner-auth-service:test --tests com.samhanair.logis.partnerauth.service.PartnerAuthServiceTest

25 tests completed, 3 failed
PartnerAuthServiceTest > 복구하지 않은 30일 초과 거래처는 여전히 LONG_UNUSED로 선별 FAILED
    org.opentest4j.AssertionFailedError at PartnerAuthServiceTest.java:243
PartnerAuthServiceTest > 30일 미사용 ... Code.js:2957 보존 (sliding expiration) FAILED
    java.lang.NullPointerException at PartnerAuthServiceTest.java:306
PartnerAuthServiceTest > getExpiration ... 생성시각 + 30일 = expiresAt FAILED
    java.lang.AssertionError at PartnerAuthServiceTest.java:529
```

판정은 **테스트 fixture가 낡았고 구현은 유지해야 한다**이다. R18 이후 실제 코드는 세 경로 모두 `readSafely(activityReader, auth.getBizNo(), auth.getPartnerCode())`를 호출한다. 그러나 `PartnerAuthServiceTest.java:86`의 공통 mock은 구 계약인 `activityReader.read(anyString())`만 stub하고 두 키 overload를 stub하지 않는다. Mockito에서는 두 인자 mock 호출이 `null`이므로 활동 조회가 미완료가 되고, `checkStatus`/`tryLogin`은 보류, 만료 API는 `expiresAt=null`이 된다. 기대값인 strict `<` 경계 자체가 실패한 것이 아니다.

레거시 원문 근거:

- `tools/legacy-gas/거래처 발송 주문서/Code.js:2941-2948`은 주문 성공 로그와 출고를 거래처 번호로 조회한다.
- `Code.js:2977-2983`은 `logTime`, `shipTime`, `createdTime`의 최댓값에 정확히 30일을 더한다.
- `Code.js:2994-3003`은 최종 만료시각을 화면 계약으로 반환한다.
- strict 경계는 이미 R10에서 고정한 현행 `PartnerAccessPolicy.isLongUnused`/`isAuthenticationLongUnused`의 `expiresAt.isBefore(now)`와 R18 만료 API 공유 계산이다. 따라서 정확히 30일은 활성, 30일+1초부터 만료라는 기준을 바꾸지 않는다. `Code.js:2957`은 조회 fetch의 시작점이지 경계 기대값을 `<=`로 바꾸라는 근거가 아니다.

구 계약 mock에 두 키 overload를 추가한 뒤 GREEN이 되었다. production의 세 경로 키 통일이나 strict 경계 기대값은 변경하지 않았다.


## 구현 결과 — 운영 생성 7개 전수 표

| # | 운영 경로/API | 처리 결과 | 모르는 경우 |
|---:|---|---|---|
| 1 | 일반 작성 `POST /slips` | 기존 partnerId→정본 조회 후 성공 시 snapshot | 조회 실패/null은 기존대로 NULL. 임의 번호 보충 없음 |
| 2 | 전표 복사 `POST /slips/{id}/duplicate` | 기존 복사 경로의 partnerId 정본 재조회 유지 | 실패/null은 NULL. 원본의 다른 거래처 값 추정 없음 |
| 3 | 모바일 주문 `POST /mobile/sales/partner-orders` | 검증된 partnerId로 `resolveBusinessNumber` 후 성공 시 저장 | 정본 조회 실패면 NULL 유지 |
| 4 | 견적 직접 변환 `POST /slips/estimates/{id}/convert` | `Estimate.partnerBusinessNo` snapshot을 `Slip.businessNumber`로 복사 | 견적 snapshot 자체가 없으면 NULL |
| 5 | 견적 publish `POST /api/v1/slips/from-estimate`, `/internal/slips/from-estimate` | partner strict 검증 결과의 UUID로 정본 사업자번호를 조회해 저장 | 검증 skip/실패 또는 사업자번호 조회 실패면 NULL |
| 6 | 파트너 주문 전환 `POST /api/v1/slips/from-partner-order` | `bizCode`를 `@NotBlank`로 요구해 알려진 원천 없이 생성하지 않음 | 누락은 400; 임의 값으로 생성하지 않음 |
| 7 | 주문 병합 전환 `POST /api/v1/slips/from-orders-merge` | `bizCode`를 `@NotBlank`로 요구해 알려진 원천 없이 생성하지 않음 | 누락은 400; 임의 값으로 생성하지 않음 |

개발 seed는 운영 7개와 별개이며 기존처럼 개발 fixture로만 분류한다. 이번 변경은 seed·복사·일반 작성의 범위를 임의로 넓히지 않았다.

## 실데이터 재측정 — fix 후

공유 DB에는 계속 SELECT만 실행했다. `partner_id IS NOT NULL`을 거래처 정체성이 있는 행의 기준으로 사용했다. UUID 자체는 보고서에 노출하지 않는다.

```text
[실데이터/로컬 read-only]
source_type  | unfilled_with_partner_id
MANUAL       | 72
PARTNER_ORDER| 17

[실데이터/로컬 read-only]
manual_unfilled_with_partner_id: 72
partner_order_unfilled_with_partner_id: 17
```

현재 저장 행은 과거 데이터이므로 코드 fix만으로 숫자가 즉시 감소하지 않는다. 새 모바일·견적·주문 publish 생성은 각각 정본/snapshot을 전달하고, 주문 publish 누락은 400으로 차단한다. 따라서 unknown을 다른 거래처 번호로 채우는 회귀는 만들지 않는다.
