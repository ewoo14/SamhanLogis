## 1. 판정 요약

R8에서 차단한 `invisible-only actor → null → audit 필수 계약 충돌 → rollback-only → UnexpectedRollbackException` 경로는 사라졌다. R9는 인증 actor의 U+200B-only 이름을 원문 그대로 실제 감사 행에 저장하고, update/delete/restore/revert 네 창고 변경을 모두 commit한다. 같은 Spring 트랜잭션 프록시와 실제 `InventoryAuditLogRecorder`를 사용한 `WarehouseActorStorageIT`가 7개 조합을 통과했다.

저장층 되돌리기가 표시층을 굶기지 않았다. 공용 `safeActorName` 호출 7좌표를 실제 production component로 Chromium에 mount하고, 각 좌표에 `U+200B + canonical UUID` raw actor와 RED-B 정상 actor를 함께 공급했다. 7/7에서 UUID는 노출되지 않았고 정상 이름은 남았다. `AuditOverlay`와 창고 timeline은 은폐 대상을 `변경자 미상`으로 표시하며, 나머지 version/redline 좌표는 기존 계약대로 actor span만 생략한다.

저장된 actor 원문을 다시 편집할 때 화면 라벨이 저장되는 역류 경로도 없다. 창고 편집 payload에는 `name`, `type`, `address`, `displayOrder`, `description`만 있고 audit `actorName`은 read-only timeline 데이터다. 저장 요청의 actor는 overlay 텍스트가 아니라 현재 인증 JWT에서 gateway가 새로 주입한 `X-User-Name`으로 결정된다. 따라서 화면이 `변경자 미상`을 보여도 그 라벨이 다음 감사 행에 복사되지 않는다.

PM 기준의 실데이터 발화 조건 0건을 감안해도 이번 방어가 추가로 막는 정상 사용자 경로는 확인되지 않았다. R9 저장 변환은 `null` 또는 Java `String.isBlank()`인 이름 부재에만 한정된다. U+200B-only, U+200B-wrapped UUID, canonical UUID, 내부 invisible, `%`, `+`, `%20`, 하이픈 식별자와 정상 한글은 raw 저장된다.

## 3. 위험 2 — 저장 원문 재편집 비대칭

### 데이터 흐름

```text
감사 조회 actorName(raw)
  → safeActorName 표시 전용 정규화
  → 변경자 미상 또는 actor span 생략
  ↛ 창고 편집 form state/payload에는 연결되지 않음

사용자가 창고 저장
  → UpdateAdminWarehousePayload(업무 필드 5개만)
  → gateway가 현재 JWT display name을 X-User-Name으로 권위 주입
  → WarehouseController
  → WarehouseService가 그 요청 actor 원문을 새 감사 행에 저장
```

근거 좌표:

- `EditWarehouseModal.tsx:100-113`: payload는 `name/type/address/displayOrder/description`만 생성한다.
- `adminApi.ts`: `updateAdminWarehouse`는 위 payload만 PATCH body로 보낸다.
- `WarehouseAuditLog.actorName`은 timeline 응답 필드이며 input state나 PATCH DTO에 없다.
- desktop auth provider는 Bearer/cookie 세션만 전달하고 사용자 표시 라벨을 audit row에서 읽어 헤더로 만들지 않는다.
- gateway의 JWT display name → `X-User-Name` 경로와 inventory controller 전달 계약은 기존 전체 회귀에서 통과했다.

따라서 과거 raw actor가 표시층에서 `변경자 미상`이 되어도, 사용자가 창고 업무 필드를 저장할 때 그 라벨이 actorName으로 저장되지 않는다. 과거 감사 row는 불변이고 새 row는 현재 인증 actor로 별도 생성된다.

## 4. 위험 3 — `null/공백 → 변경자 미상`의 실제 역사

`git log -S`와 해당 커밋의 `WarehouseService` diff를 교차 확인했다.

| 시점 | 저장 동작 |
|---|---|
| R1 이전 (`0aac907c8^`) | system 호출자는 `system`, 인증 호출자는 `callerId` UUID를 actorName으로 저장 |
| R1 `0aac907c8` | 인증 호출자의 actorName을 무조건 `null`로 변경해 UUID 노출 제거 |
| R2 `ed63bf419` | `X-User-Name` 도입. null/blank/canonical UUID는 `null`, 정상 이름은 trim 저장 |
| R7 `f47ebcbfe` | invisible 제거 후 empty/UUID를 `null`, 그 외 정규화값 저장 |
| R9 미커밋 | system은 `system`; null/`isBlank()`만 `변경자 미상`; 그 외 입력 원문 저장 |

결론: `null/공백 → 변경자 미상` 저장은 기존 동작도 R7 동작도 아니며 **R9가 새로 도입한 최소 fallback**이다. 다만 감사 도메인의 `actorName` nonblank 필수 계약은 PR #1164보다 오래됐다. `AuditLogEntry` 생성자는 null/blank를 `actorName 은 필수입니다`로 거절한다. 그러므로 R9 fallback은 R8 rollback을 없애면서 감사 행을 잃지 않기 위한 계약 정합화다.

이 변환이 막는 실 사용자 이름은 확인되지 않았다. 전체 whitespace 이름은 사용자 생성의 `@NotBlank` 의미상 이름 부재이고, R7의 실제 위험이었던 U+200B-only는 Java `isBlank()`가 아니므로 raw 저장된다. leading/trailing whitespace가 있는 nonblank 이름도 R9 저장층은 trim하지 않는다.

## 5. 위험 4 — R8 차단 재현 재실행

다음 영구 IT를 캐시 없이 실행했다.

```text

  --tests "com.samhanair.logis.inventory.it.WarehouseActorStorageIT" \
  --no-build-cache --rerun-tasks
```

검증 조합은 총 7개다.

- U+200B-only `update`
- U+200B-only `delete`
- U+200B-only `restore`
- U+200B-only `revert`
- `null` update
- empty string update
- spaces-only update

네 U+200B 경로는 창고 도메인 변화와 실제 audit row를 함께 commit하고, `actorId`와 raw U+200B actorName을 보존한다. 이름 부재 3경로는 `변경자 미상` nonblank audit row를 commit한다. R8의 `UnexpectedRollbackException`은 재현되지 않았다.

R8의 정상 문자열 실제 저장 probe도 검토용 임시 Testcontainers IT로 다시 실행하고 파일은 제거했다.

```text
김감사 | 김%20감사 | 1-1-1-1-1 | 김%감사 | 김+감사 | % | +

BUILD SUCCESSFUL in 39s
18 actionable tasks: 18 executed
```

7값 모두 창고 변경과 감사 행을 commit했고 DB actorName은 입력과 정확히 같았다. `%20`을 공백으로 바꾸는 추가 decode는 없었다.

## 7. Playwright 중간 실패 원문

최종 7/7 전 세 번의 harness 실패가 있었다. 제품 실패로 과장하지 않고 원문과 원인을 남긴다.

### 1차 — warehouse exact locator 불일치

```text
Locator: getByText('1-1-1-1-1', { exact: true }).first()
Expected: visible
Error: element(s) not found
1 failed, 6 passed
```

실패 스크린샷에는 실제로 `#1 · 1-1-1-1-1`이 렌더링돼 있었다. actor가 별도 text node가 아니라 revision prefix와 같은 요소에 있어 exact locator만 실패했다.

### 2차 — query 완료 대기 누락

```text
Expected substring: "1-1-1-1-1" / "김%감사" / "김+감사" / "김%20감사"
Received: "버전 이력을 불러오는 중..." 또는 "이력 조회 중…"
4 failed, 3 passed
```

각 production component의 list/revision testid를 readiness 조건으로 추가했다.

### 3차 — warehouse fallback exact locator 불일치

```text
Locator: getByText('변경자 미상', { exact: true }).first()
Expected: visible
Error: element(s) not found
1 failed, 6 passed
```

화면에는 `#2 · 변경자 미상`으로 렌더링돼 있었다. body text의 포함 관계와 UUID 부재를 검사하도록 고친 뒤 최종 7/7을 얻었다. 임시 Vite QA entry와 Playwright spec은 캡처 후 제거했다.

별도로 첫 Gradle 시도는 `services/inventory-service` 안에서 `gradlew.bat`을 찾지 못해 즉시 실패했다. repo root wrapper와 `:services:inventory-service:test` project path로 바로잡았으며 코드/테스트 실패가 아니다.

## 8. 이 라운드가 보지 않은 표면

- 공유 DB write와 배포 환경의 실제 warehouse update/delete/restore/revert는 수행하지 않았다. 격리 PostgreSQL에서만 저장했다.
- 실제 로그인 → gateway → 배포 inventory → DB → desktop까지의 단일 live E2E는 수행하지 않았다. gateway/header는 코드·기존 계약 테스트, 저장은 Spring IT, 표시는 Chromium component QA로 경계를 나눠 검증했다.
- PM이 실측한 accounts 32 / employees 24의 invisible 0건은 재조회하지 않았다. 이번 라운드는 공유 DB를 아예 사용하지 않았다.
- 7개 actor 표시 좌표 밖의 전체 저장소 모든 사용자명/UUID 표면은 재감사하지 않았다.
- `arologis-desktop`, `mobile-public`, `mobile-staff` 전체 test/build는 다시 실행하지 않았다. 검색상 이번 7개 `safeActorName` production 호출 좌표에 포함되지 않는다.
- warehouse realtime SSE로 다른 관리자의 새 감사 행이 열린 모달에 들어오는 동시성 경로는 클릭하지 않았다. 정적 query invalidation 배선과 desktop 전체 회귀만 확인했다.
- 감사 recorder의 actorName 외 DB 장애/제약 실패에 대한 기존 best-effort 트랜잭션 의미는 재결정하지 않았다. R10은 R8의 actorName 필수 계약 충돌만 재현했다.
- helper가 열거하지 않은 다른 Unicode format 문자 전체를 확장 탐색하지 않았다. PM 기준에 따라 방어 범위를 늘리지 않았고, 지정 6종 및 U+200B-wrapped UUID만 검증했다.

## 9. PM 보고

**차단 결함 0건.** R9의 저장층 되돌리기는 7개 표시 좌표를 굶기지 않았고, 저장 원문이 편집 라벨로 역류하지 않으며, `null/공백 → 변경자 미상`은 역사적으로 새 동작이지만 기존 nonblank 감사 계약을 만족시키는 최소 fallback이다. R8의 rollback과 RED-B를 격리 PostgreSQL·전체 회귀·Chromium 7좌표로 다시 확인했으므로 PM에 재검토 통과로 보고할 수 있다.
