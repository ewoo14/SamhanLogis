### 실패 ① 원인 판정 — (가) 스펙이 잘못된 마이그레이션 파일을 읽음

근거:

- Playwright 스펙 `clients/desktop/playwright/sp-08-3-4-dispatch-sms-history/sp-08-3-4-dispatch-sms-history.spec.ts`가 `V7__retire_dispatch_sms_send_audit_history.sql`을 `migration`으로 읽고 테이블 생성·초기 `SEND_AUDIT` 제약·unique index를 단언한다.
- 실제 `V4__add_dispatch_sms_save_history.sql`에 `CREATE TABLE dispatch_sms_save_history`, `AUTO_LATEST`/`MANUAL_NAMED`/`SEND_AUDIT` 체크, `ux_dispatch_sms_save_history_auto_latest_per_user_program`가 존재한다.
- 실제 `V7__retire_dispatch_sms_send_audit_history.sql`은 주석대로 checksum 보존을 위해 V4를 수정하지 않고, 기존 `SEND_AUDIT` row를 soft-delete한 뒤 후속 CHECK에서 `AUTO_LATEST`/`MANUAL_NAMED`만 허용한다.
- 따라서 테이블과 초기 `SEND_AUDIT` 계약이 폐기된 것이 아니라, 생성 마이그레이션과 폐기 마이그레이션을 스펙이 혼동한 것이다. 제품 동작/DB 파일은 변경하지 않는다.

### 실패 ② 원인 판정 — 스펙 선택자 결함, 제품 중복 렌더 아님

근거:

- `DispatchSmsPage`의 실행 화면 CTA는 `내역으로 저장`, `DispatchSmsSaveDialog`의 명시 저장 CTA만 `저장`이다.
- 같은 화면에는 `저장내역` 탭도 button role을 가지며, Playwright `getByRole('button', { name: '저장' })`의 기본 부분 이름 매칭이 이를 `저장`으로 함께 매칭한다.
- 따라서 2개 요소는 의도된 서로 다른 UI이고 중복 렌더 결함이 아니다. 스펙의 저장 CTA 선택자를 `exact: true`로 좁힌다.
