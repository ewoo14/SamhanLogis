# PR #1127 R4 SOL 재수렴 적대 검증

검증 기준: `feat/978-fast-path-carryover` / `3feb154d67049d9561e4f4ac33a43ed59107c7f7`

## 머지 가부 판정

**머지 불가. PM이 개발책임자에게 상신해야 한다.**

카운터 분리, flaky 원인 제거, R1~R3 데이터 계약 및 전체 694건 회귀는 통과했다. 그러나 요청된 인증 감시 뮤테이션에서 `ROLE_INTERNAL`을 `ROLE_BROKEN`으로 바꿔도 두 테스트 18건이 모두 통과했다. 따라서 “두 테스트가 `ROLE_INTERNAL`로 내부 API에 접근한다는 단정이 그대로 유효하다”는 요약과 기존 fix 보고서의 취지는 사실과 다르다.

- 심각도: **MEDIUM — 인증 권한 회귀 감시 공백**
- 현재 도달성: **직접 운영 인증 우회는 확인되지 않았다.** 제품의 실제 `SecurityConfig`는 `/products/internal/**`에서 authority가 아니라 principal `system-internal`을 검사하며, 두 standalone 테스트에는 그 access decision 자체도 없다. 유효 토큰 거부 뮤테이션은 18건 중 11건을 실패시켜 토큰 검증 감시는 살아 있다.
- 미래 도달성: shared filter의 role 구성, product 설정의 `role=INTERNAL`, 또는 향후 `ROLE_INTERNAL` 의존 인가가 회귀해도 이 두 테스트는 green일 수 있다. 명시된 acceptance가 바로 이 감시를 요구하므로 라운드 상한 상태에서 임의로 비차단 처리하지 않는다.

셋째 가능성은 “제품 내부 API의 실제 계약이 `ROLE_INTERNAL`이 아니라 `system-internal` principal뿐”인 경우다. 그렇다면 제품 동작 결함은 아니지만, 요청 요약과 기존 보고서의 `ROLE_INTERNAL` 단정 표현을 수정하고 그 계약을 개발책임자가 확인해야 한다. 어느 경우든 현 증거로는 그대로 머지 승인할 수 없다.

## 요약과 다른 사실

1. 두 테스트는 `props.setRole("INTERNAL")`과 `InternalTokenFilter`를 사용하지만 authority를 직접 단정하지 않는다. `ROLE_BROKEN` 뮤테이션이 18/18 통과했다.
2. 기존 보고서의 강제 재현 전 원문은 `TARGET_CAUSE=java.lang.AssertionError`였으나, 이번 fresh 직접 호출에서 구체 예외형은 `TARGET_CAUSE=org.opentest4j.AssertionFailedError`였다. 이는 `AssertionError` 하위형이라 원인 의미는 동일하지만 원문은 동일하지 않다.
3. 나머지 사용자 요약(HEAD, R4 카운터 수치, 토큰 거부 시 테스트 실패, 49/694 테스트 수)은 fresh 증거와 일치한다.

## (a) 카운터가 판정을 오염시키지 않았는가

### 코드 판정

`ProductSheetSyncService`는 기존 Product에 모든 writer를 적용한 뒤 `ProductMutationSnapshot.changed()`로 `updated` 또는 `unchanged`를 먼저 결정한다. 새 관측 카운터는 이후 다음 조건에서만 증가한다.

```java
if (existing.isPresent() && !productChanged && externalWrites.changed()) {
    result.priceHistoryExposureSpecWrites++;
}
```

따라서 카운터 값이 `updated`/`unchanged` 분기에 입력되지 않는다. 신규 Product와 실제 변경 Product도 카운터 대상에서 제외된다.

### fresh 복수 시나리오

기존 IT에 임시 단정을 추가해 다음을 함께 확인하고 원복했다.

## (b) flaky 수정과 인증 감시

### cleanup 및 flaky 인과

두 오염원 테스트 모두 `@AfterEach`에서 `SecurityContextHolder.clearContext()`를 호출한다. 같은 JVM/스레드에서 실제 `InternalTokenFilter`와 실제 `HeaderAuthenticationFilterTest` 메서드를 호출하는 임시 하네스로 fresh 재현한 원문은 다음과 같다.

```text

    AFTER_INTERNAL_FILTER=[ROLE_INTERNAL]
    TARGET_CAUSE=org.opentest4j.AssertionFailedError
    TARGET_RESULT=PASS

BUILD SUCCESSFUL in 27s
```

cleanup 전에는 잔류 `ROLE_INTERNAL` 때문에 대상 단정이 실패하고, clear 후에는 같은 대상 메서드가 통과했다. 임시 하네스는 삭제했다.

## (c) product-service SecurityContextHolder 전수 조사

다음 축을 모두 검색했다.

```text
SecurityContextHolder
TestSecurityContextHolder

createEmptyContext(
new InternalTokenFilter
new HeaderAuthenticationFilter

```

직접 `SecurityContextHolder`를 사용하는 테스트는 세 파일뿐이다.

| 파일 | context 생성/관측 | cleanup |
|---|---|---|
| `ProductInternalControllerTest` | standalone `InternalTokenFilter`가 설정 | `@AfterEach clearContext()` 있음 |
| `ProductInternalLookupByModelTest` | standalone `InternalTokenFilter`가 설정 | `@AfterEach clearContext()` 있음 |
| `HeaderAuthenticationFilterTest` | `HeaderAuthenticationFilter`가 설정하고 테스트가 관측 | `@AfterEach clearContext()` 있음 |

`new InternalTokenFilter` 검색 결과도 앞의 두 오염원 파일뿐이다. `ProductPermissionControllerIT`의 `HeaderAuthenticationFilter`는 실제 Spring Security filter chain 안에서 사용된다. **직접 context를 세우고 정리하지 않는 추가 테스트는 0건**이다.

## (d) R1~R3 유지

- R1 롤백 재시도: `syncTab_후속저장실패로_롤백된_단가는_같은행_재시도에서_반영되어야한다()`가 전체 fresh XML에서 통과했다. 서비스에는 `lastKnownRowHash` 같은 인메모리 baseline이 없고 매 실행 현재 managed entity의 loaded state를 캡처한다.
- R2 name 분리: `sync_시트명과_DB명이_달라도_update를_반복하지_않는다()`가 통과했다. 2·3회 모두 `updated=0`, `unchanged=1`, `nameDrift=1`을 단정하며 DB 이름을 보존한다.
- R3 구조적 dirty 판정: `ProductMutationSnapshot`은 Hibernate `EntityEntry.getLoadedState()`와 persister의 `getPropertyValues()`/`findDirty()`를 사용한다. 서비스 자체의 비교 필드 목록이 없어 writer 필드와 판정 필드의 양방향 차집합이 구조적으로 없다. `sync_동일한_값이어도_ECOUNT_승격은_updated로_판정하고_시트_정본을_적용한다()`도 fresh 통과했다.
- R4는 이 구조를 바꾸지 않고 외부 상태 변화 추적과 summary/log 필드만 추가했다.

판정: **R1~R3 회귀 0.**

## 복구 후 최종 상태

보고서 작성 직전 제품/테스트 뮤테이션 대상의 `git diff --exit-code`는 0이었다. 전체 694건 fresh green도 모든 뮤테이션과 임시 하네스를 원복한 뒤 실행했다. 최종 작업트리에는 이 보고서만 신규 파일로 남긴다.

금지된 git commit/push, 다른 worktree/main checkout, 실 DB 쓰기, 실 Google Sheets 접근, Docker 재배포는 수행하지 않았다. IT는 mock Google client와 격리된 테스트 PostgreSQL만 사용했다. E-1(SA 키 컨테이너 마운트)은 범위 밖으로 보지 않았다.

## 이 라운드가 보지 않은 것

결함 0 라운드는 아니지만 범위 경계를 명시한다.

- 실 Google Sheets 및 실 서비스/실 DB 연동
- E-1 SA 키 컨테이너 마운트와 자격 상태
- Docker 이미지 재빌드·재배포 후 동작
- product-service 밖 다른 서비스의 `SecurityContextHolder` 오염원 전수 조사
- 실제 전체 Spring Security chain에서 `ROLE_INTERNAL` authority 자체를 요구하는 별도 통합 계약
