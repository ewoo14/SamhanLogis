# R47 2차 SOL 적대검증 → fix 지시서 — PR #1057 · 이슈 #874

최종 판정: **실 사용자 경로로 재현 가능한 결함이 있다. 머지 비권고.**

R47 첫 고정 각도인 “차단되면 안 되는 것이 차단되는가”부터 확인했다. R45의 조건부 claim은
worker 경로에만 있고, 협업 `수정완료` 요청은 커밋 뒤 executor에 작업을 제출할 뿐 외부 auth/notification이나
lease 만료를 기다리지 않는다. executor 거부 시 동기 fallback도 없다. 협업 저장 자체가 새 배선 때문에
실패하거나 외부 호출 시간만큼 지연되는 경로는 재현되지 않았다.

마이그레이션 번호도 별도로 대조했다. slip-service에는 V108·V109가 각 1개이고 기존 `slip_db` 최고
V105보다 모두 높다. notification-service에는 V8이 1개이고 기존 `notification_db` 최고 V7보다 높다.
slip-service는 별도 설정이 없어 Flyway 기본 `out-of-order=false`, notification-service는 이를 명시적으로
`false`로 둔다. 두 서비스 모두 동일 version 파일은 0개이므로 이 세 파일은 번호 때문에 건너뛰거나
차단되지 않고 V108→V109, V8 순서로 적용된다. 실제 DB 적용은 하지 않았다.

증거 무결성 정정: R45의 최종 총계 `48 tests`는 재현됐지만, 이를 “`SlipCollab*` 47개와
`GlobalExceptionHandlerTest` 1개”로 나눈 수치는 재현되지 않았다. 새 XML의 실제 분해는
`SlipCollabConfigTest` 2 + `SlipCollabMigrationVersionTest` 1 +
`SlipCollabNotificationDispatchTest` 4 + `SlipCollabIT` 34 = `*SlipCollab*` 41개,
`GlobalExceptionHandlerTest` 7개로 총 48개다. 총 failures/errors/skipped는 모두 0이다.

### 결함 2 — 외부 발송 뒤 notification transaction 커밋 전 종료·lease 경합에서는 중복 발송이 남는다

- `services/notification-service/src/main/java/com/samhanair/logis/notification/service/NotificationService.java:122-150`
  — 멱등 키 조회·요청 저장·외부 gateway 호출 전체가 한 transaction이며, gateway 호출은 transaction
  commit 전에 실행된다.
- `services/notification-service/src/main/java/com/samhanair/logis/notification/service/NotificationService.java:148-150`
  — idempotency row의 commit보다 외부 부수효과가 먼저 일어난다.
- `services/notification-service/src/main/resources/db/migration/V8__add_notification_idempotency_key.sql:4-6`
  — unique index는 DB row만 보호하며 이미 일어난 외부 발송을 되돌리지 못한다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/collab/SlipCollabNotificationOutbox.java:72-74`
  — slip claim lease는 30초 뒤 재개된다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/client/NotificationClient.java:54-56`
  — slip 호출자는 3초 read timeout 뒤 실패로 보고 재시도 상태를 남긴다.

notification-service가 외부 push를 실제 수락시킨 직후 DB commit 전에 종료되면 idempotency row는 남지
않는다. 30초 뒤 slip lease가 같은 키를 재전송하면 gateway가 다시 호출되어 같은 사용자에게 두 번 간다.
프로세스가 종료되지 않아도 첫 notification transaction이 30초 넘게 미커밋인 동안 두 번째 lease가
들어오면 READ COMMITTED에서 두 요청이 모두 기존 키를 보지 못하고 외부 호출을 실행할 수 있다. unique
충돌은 외부 호출 뒤 commit 시점에 한 transaction을 실패시킬 뿐 이미 발생한 두 번째 발송을 취소하지 못한다.

## ② 불변식 — 구현 수단 지시 금지

1. 같은 저장 사건·수신자의 재시도는 최초 시도가 성공했을 때 외부 전달을 반복하면 안 된다.
2. 같은 저장 사건·수신자의 최초 시도가 실패했을 때는 성공 또는 명시적 종결 상태에 이를 수 있어야 하며,
   멱등 키 자체가 실패 상태를 영구 고정하면 안 된다.
3. 외부 발송 부수효과와 그 멱등 판정 상태 사이의 프로세스 종료·transaction rollback 경계에서도 중복과
   영구 누락 어느 쪽도 허용하지 않는다.
4. scheduler, afterCommit worker, lease 회수, 응답 유실 재전송이 어떤 순서로 겹쳐도 한 저장 사건·수신자에
   대한 성공 외부 전달은 최대 한 번이어야 한다.
5. 이 불변식을 위해 협업 `수정완료` 응답이 외부 notification 완료나 lease 만료를 기다리거나, 유효한
   전표·감사·리비전·ACCEPTED 저장이 알림 장애 때문에 실패하면 안 된다.
6. 롤백된 협업 저장의 알림 0, genuine lock timeout 409, non-lock query timeout 중립 오류, UUID 비공개를
   유지해야 한다.

## ③ 양방향 RED — 반대급부 필수

### RED-A — 되돌리면 안 되는 것

- 느린 auth/notification, executor 제출 거부, 큰 backlog 중에도 `수정완료` 응답은 외부 호출이나 drain을
  기다리지 않는다.
- 협업 저장 rollback에는 outbox와 외부 알림이 없고, 성공 저장에는 전표·감사·리비전·ACCEPTED가 남는다.
- scheduler와 afterCommit worker가 같은 ready row를 동시에 읽어도 외부 전달 진입은 하나뿐이다.
- `A→B`, `B→A`, `A→B` 세 정상 저장은 payload가 같아도 각 사건의 알림 상태를 독립 보존한다.
- **반대급부:** 멱등성 보장을 위해 외부 gateway 호출 동안 slip 저장 transaction/row lock을 유지하거나
  notification 완료까지 사용자 HTTP 응답을 지연하면 RED다.
- **반대급부:** 실패 재시도를 복원하면서 동일 성공 요청·응답 유실·동시 lease가 gateway를 다시 호출하면
  RED다.
- **반대급부:** 중복을 막는 변경이 외부 gateway 실패를 성공으로 기록하거나 영구 누락시키면 RED다.
- **반대급부:** 같은 저장의 매 retry마다 새 event/outbox/사용자 알림을 만들거나 rollback 저장의 알림을
  남기면 RED다.

### RED-B — 재발하면 안 되는 것

- 같은 멱등 키의 최초 gateway 실패 후 재시도에서 gateway 호출 수가 그대로 1이면 RED다. 두 번째 성공
  응답 뒤 상태는 `SENT`여야 한다.
- 외부 gateway 성공 직후 notification transaction rollback/프로세스 종료를 주입하고 같은 키를
  재전송했을 때 외부 성공 전달 총수가 2이면 RED다.
- 첫 요청을 gateway 안에서 30초 lease보다 오래 정지시키고 같은 키의 두 번째 lease를 진입시켰을 때
  두 요청 모두 외부 gateway에 도달하면 RED다.
- 이미 커밋된 `SENT` 요청에서 HTTP 응답만 유실시킨 뒤 재시도했을 때 gateway가 다시 호출되면 RED다.
- claim 후 외부 호출 전 worker를 종료했을 때 lease 뒤에도 전달되지 않으면 RED다.
- 롤백 저장 알림, executor 거부 동기 fallback, non-lock timeout 잠금 409, 내부 UUID 화면 노출이 나타나면
  RED다.

## ⑤ 커밋 전 돌릴 명령 — 좁혀서

notification-service에는 최소 다음 결정적 RED를 추가한다.

```text

2. SENT idempotency row ↔ 응답 유실 재시도: gateway 총 1회
3. gateway 성공 ↔ notification transaction rollback/종료 ↔ 같은 키 재시도: 성공 외부 전달 총 1회
```
