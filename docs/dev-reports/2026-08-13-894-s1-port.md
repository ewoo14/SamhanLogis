## 2. RED 원문 (양방향)

### ① 독립 앱에서 S1이 아직 안 되는 상태

초기 실행:

```text

```

즉 독립 앱에는 S1 화면/API client가 없었다.

### ② 본체 무변화 경계

RED 테스트에는 다음 경계 계약을 포함했다.

```text
it('독립 앱은 본체 채팅 구현을 import하지 않는다', ...)
```

구현 전에는 위 테스트 파일 자체가 `./ChatApp` 부재로 수집 단계에서 중단되어 독립 앱 RED와 함께 실패했다. 구현 후에는 이 경계 테스트가 통과했고, 이번 라운드의 `apply_patch` 대상은 `clients/internal-chat-desktop/**`와 이 보고서뿐이었다. 본체 무변화는 독립 앱이 `clients/desktop`를 import하지 않는 구조 테스트와 본체 파일 미수정으로 보증했다.

## 3. 고른 수단과 이유

- 본체와 버전을 맞춰 React `18.3.1`, React Router `6.27.0`, TanStack Query `5.59.20`을 사용했다.
- 본체 화면의 데이터 흐름을 유지하되 독립 앱은 자체 `chatApi.ts`를 두어 본체 파일을 runtime import하지 않게 했다.
- 상태·재조회는 본체와 같은 TanStack Query 패턴을 사용했다.
- 방 식별자는 본체와 같은 `roomCode`만 URL에 사용했다.
- 화면 컴포넌트는 design-system의 `Button`, `Card`, `Input`을 우선 사용했다.
- 독립 Electron 셸의 `MemoryRouter` 초기 경로는 `/chat`로 설정했다.
- 로컬 file package에서 React가 중복 로드되는 문제를 피하기 위해 테스트·Electron renderer 모두 독립 앱 React를 alias했다.

## 5. 불변식별 보증

1. **독립 앱에서 채팅방 신설·대화** — `ChatApp.tsx`와 `chatApi.ts`, `chat-app.test.tsx`의 방 목록/새 대화/메시지 조회·전송 테스트.
2. **본체 무변화** — 본체 채팅 코드를 이동·삭제하지 않았고 독립 앱은 본체 모듈을 import하지 않는다. 경계 테스트 통과.
3. **design-system 우선** — `ChatApp.tsx`에서 `Button`, `Card`, `Input`을 `@samhan/design-system`에서 import.
4. **백엔드 계약 불변** — room/message controller, DTO, migration을 변경하지 않고 기존 endpoint와 envelope을 그대로 호출.
5. **UUID 사용자 노출 방지** — 화면과 URL에는 roomCode·이름·부서·사번만 표시. 단, 아래 선재 위반인 `participantId` UUID 요청은 개발책임자 결정에 따라 본체와 동일하게 유지.

## 6. 판단이 필요해 남긴 것 / 못 한 것

- **선재 UUID 위반**: `participantId`는 `ChatDirectRoomRequest.java:6`의 UUID 계약이며 새 대화 요청에 실린다. 이번 라운드에서는 제거하지 않았다. UUID 제거 별도 트랙으로 등록한다.
- **이슈 제목의 “편집” 계약 부재**: 확인된 백엔드 계약에는 방 생성, 목록, 메시지 조회·전송, 읽음, SSE만 있고 채팅방 편집 endpoint/권한은 없다(`ChatRoomController.java:27-78`). 편집 API·권한은 만들지 않았다. PM 판단 질문으로 상신한다.
- S3 자동 로그인, S4 부재중, S5 알림, S6 파일전송, S7 이모티콘은 구현하지 않았다.
- 실 백엔드 인증 연결과 실시간 서버 QA는 S3 인증 전제 및 후속 QA 범위로 남겼다.
- `npm install` 결과 audit 취약점 22건은 이번 S1 코드와 무관해 수정하지 않았다.

## fix 라운드 1

### RED 원문 (양방향)

독립 앱 production renderer와 같은 `MemoryRouter basename="/chat" initialEntries={['/chat']}`를 테스트에 재현하고, 실제 API 계약과 같은 `201 + roomCode` 성공 mock 뒤 방 화면 진입을 단정했다.

```text
npm test -- --run src/renderer/chat-app.test.tsx
Test Files 1 failed
Tests 3 passed | 1 failed
× production basename 환경에서 방 생성 직후 생성된 대화방에 진입한다
→ Unable to find an element by: [data-testid="chat-room-page"]
No routes matched location "/chat/CHAT-20260813-000001"
DOM: <body><div /></body>
```

본체 채팅 양방향 기준은 본체의 기존 계약 테스트로 재현했다.

```text
clients/desktop/src/renderer/routes/ChatRoomPage.fix1.test.tsx
6 tests passed
방 목록·방 열기·메시지 표시·생성 실패 안내·전송 실패 안내·상대 표시 계약 통과
```

### 원인

방 생성 API 응답 파싱은 `createDirectChatRoom()`에서 `res.data.data`를 반환하고, 응답의 `roomCode`도 정상적으로 mutation `onSuccess`까지 전달된다. 쿼리 무효화도 성공 콜백에서 시작된다. 실패 지점은 그 이후 라우팅이다.

독립 앱의 `ChatApp` route는 basename 내부에서 `index`와 `:roomCode`를 사용한다. 그런데 생성 성공 콜백과 방 목록 링크가 `/chat/{roomCode}` 절대 경로를 사용했다. basename `/chat`가 이미 적용된 router에서 이 값은 내부 `/{roomCode}`로 해석되어 `:roomCode` route와 일치하지 않는다. React Router가 `No routes matched location`을 기록하고 `ChatApp`이 렌더링할 요소가 없어져 QA의 빈 `#root`가 발생했다.

### 고른 수단과 왜 그것인가

독립 앱의 router 경계를 유지하면서 생성 성공 이동과 방 목록 링크를 basename 내부의 상대 경로로 바꿨다. 생성 후 이동은 `navigate(encodeURIComponent(room.roomCode))`, 방 목록은 `Link to={encodeURIComponent(room.roomCode)}`, 방 화면의 목록 복귀는 `Link to=".."`로 고정했다.

이 수단은 이미 `MemoryRouter basename="/chat"`와 `ChatApp`의 중첩 route가 제공하는 경계를 그대로 사용하므로 백엔드 계약·응답 파싱·쿼리 상태·본체 채팅을 건드리지 않는다. `roomCode`만 URL에 남기고 UUID 표시도 새로 만들지 않는다. 실패를 숨기거나 root fallback을 추가하는 방식보다, 실제로 매칭되어야 할 route 입력을 바로잡는 최소 변경이다.
