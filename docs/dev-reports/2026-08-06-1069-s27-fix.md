# #1069 S27 fix 보고서 — 매입전표 전체수정 BUNDLE 부모 차단

## 결론

`PUT /slips/{id}` 매입전표 전체수정에서 요청 `productId`가 활성 BUNDLE 부모여도 `SlipLine.create*()`로 바로 전달되던 결함을 수정했다. 저장 전에 product-service 정본을 조회하는 공통 `BundleProductGuard`를 두고, 매입·매출 전체수정이 같은 guard를 통과하도록 했다.

정상 SINGLE 라인은 계속 저장되며, BUNDLE 부모는 저장·가격기억·revision 전에 한국어 업무 오류로 거부된다. 내부 HTTP 문구와 UUID는 오류 메시지에 넣지 않았다.

## RED-first 증거

추가한 테스트:

- `services/slip-service/src/test/java/com/samhanair/logis/slip/service/SlipUpdateServiceTest.java:45-70`
  - INBOUND DRAFT 전표의 정상 PUT 요청에서 productId만 BUNDLE 부모로 바꾼 재현이다.
  - 원래 guard 호출을 제거한 상태에서 실행한 결과:

    ```text
    SlipUpdateServiceTest > 매입 전체수정은 BUNDLE 부모를 저장하지 않고 사용자 안내 오류로 거부한다 FAILED
        java.lang.AssertionError at SlipUpdateServiceTest.java:64
    1 test completed, 1 failed
    ```

- 같은 테스트에 정상 SINGLE 반대급부도 추가했다(`:73-101`). BUNDLE 차단이 정상 제품까지 오차단하지 않는지 `saveAndFlush` 호출로 확인한다.

## 선택한 지점과 지배 증명

### 선택한 지점

순수 `SlipLine.create*()`는 product type을 모르는 팩토리이므로 그 자체에서 BUNDLE 여부를 판정할 수 없다. 실제 product 정본을 조회할 수 있는 저장 직전 서비스 경계인 `BundleProductGuard.rejectParents()`를 선택했다.

- `services/slip-service/src/main/java/com/samhanair/logis/slip/service/BundleProductGuard.java:12-29`
  - 요청 productId를 `ProductClient.lookup()`으로 정본 조회한다.
  - `productType == BUNDLE`이면 `INVALID_INPUT`과 “세트 품목은 전표 라인으로 저장할 수 없습니다. 구성품으로 전개해 주세요.”를 던진다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/service/SlipUpdateService.java:76-83`
  - 매입 PUT의 `toLine()`/`replaceLines()`/`saveAndFlush()`보다 먼저 guard를 호출한다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/service/SalesSlipUpdateService.java:81-88`
  - 매출 PUT도 동일한 guard 인스턴스/문구/판정을 사용한다.

### 사용자 쓰기 입구 전수 대조

다음은 현재 생산 코드에서 `SlipLine.create*()` 또는 `EstimateLine.create*()`가 호출되는 사용자/전환 경계와 그 처리다.

| 입구 | 코드 근거 | BUNDLE 처리 |
|---|---|---|
| 일반 전표 신규·부분 추가 | `SlipService.java:145-208, 241-273, 789` | `productClient.lookup()` 후 `addSlipLinesExpanded()`가 BUNDLE을 구성품으로 전개 |
| 매출 전체수정 PUT | `SalesSlipUpdateService.java:81-88, 231-245` | 공통 guard가 부모 평면 저장을 사전 거부 |
| 매입 전체수정 PUT | `SlipUpdateService.java:76-83, 230-244` | 이번 fix로 공통 guard가 추가되어 부모 평면 저장을 사전 거부 |
| 모바일 주문 | `MobilePartnerOrderService.java:99-112, 167` | lookup 직후 BUNDLE을 한국어 오류로 거부한 뒤에만 라인 생성 |
| 모바일 견적 | `MobileQuotationService.java:104-106, 194-203` | BUNDLE은 `ProductClient.expand()` 결과 구성품만 `EstimateLine`으로 저장 |
| 일반 견적 | `EstimateService.java:178-211, 517` | product summary 기반 전개 후 `EstimateLine` 생성 |
| 견적→전표 | `EstimateToSlipConverter.java:78-111, 129-151` | 변환 시작 시 기존 estimate line의 부모를 재조회해 거부; 이후 구성품만 `SlipLine` 생성 |
| 주문 전환/outbox 발행 | `SlipPublishService.java:1091-1094` | 발행 입력은 기존 전개 결과이며 부모 평면 신규 생성 경계가 아님 |
| 복사 | `SlipDuplicateService.java:113` | `SlipLine.copyOf()`로 기존 라인 스냅샷/계보만 복사; 요청 productId를 받는 신규 입구가 아님 |
| revision/협업 복원 | `Slip.java:2113-2169`, `SlipDocumentCollaborationPort.java:238` | 저장된 스냅샷을 복원하며 신규 productId 입력을 받지 않음 |

따라서 이번 결함의 다섯 번째 입구인 매입 PUT도 매출 PUT과 동일한 정본 조회 경계를 통과한다. 신규 productId를 평면 라인으로 받는 두 direct PUT은 모두 guard를 지나고, 나머지 사용자 생성 입구는 BUNDLE을 전개하거나 명시 거부한다. 복사·복원은 새 부모를 선택할 수 있는 입력 입구가 아니므로 direct PUT guard의 누락 범위와 혼동하지 않는다.

## 불변식 및 회귀 확인

- BUNDLE 부모: 매입·매출 direct PUT에서 `saveAndFlush()` 이전 거부.
- 정상 SINGLE: `SlipUpdateServiceTest.purchaseUpdate_acceptsSingleLine` 통과.
- 사용자 안내: 오류는 한국어 사유와 구성품 전개 조치를 포함하며 UUID/내부 HTTP 문구 없음.
- 기존 모바일·견적·전환·Bundle·SlipUpdate 테스트 묶음 통과.
- DB 쓰기, Docker, migration은 사용하지 않았다. 스키마 변경이 없어 V113 이상 migration도 불필요하다.
