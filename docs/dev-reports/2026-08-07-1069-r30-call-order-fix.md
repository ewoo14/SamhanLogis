# R30 — 거래처 전환 bundle 전개 호출 순서와 가격 수렴

## 결론

R29의 `[R29-INSTRUMENT]` 로그 6개소를 `BundleExpander`에서 제거했다. `INVALID_INPUT` 가드와 기존 `BundleExpanderIT` RED/GREEN 테스트는 유지했다.

남은 결함은 단순한 응답 순서 역전만이 아니었다. 첫 bundle 전개가 응답 대기 중인 상태에서 거래처를 전환하면 `expandedBundleOptionsRef`에 bundle context가 아직 등록되지 않아, 전환 경로가 해당 bundle을 `bundleContexts`에서 누락했다. 그 결과 새 거래처 기준 `/expand-line` 재호출이 생략되고, 최초 전개의 늦은 응답이 화면에 남을 수 있었다.

## 계측 원문

테스트: `clients/desktop/src/renderer/routes/SlipFormPage.test.tsx`의 `R30 계측` 케이스.

```text
[R30-TRACE]
request#1:unitPrice=1590000
request#2:unitPrice=1590000
response#2:componentSum=1590000
setLines:unitPrice=954000;sum=1590000
response#1:componentSum=1660000
final:unitPrice=954000;sum=1590000
save:sum=1590000
```

호출부는 모두 `clients/desktop/src/renderer/routes/SlipFormPage.tsx`의 `expandSelectedBundle`이며, 거래처 전환 재전개는 `refreshAutoPricesForPartner`에서 실행된다. 두 번째 응답이 먼저 화면에 반영된 뒤 첫 번째 응답이 도착했지만, 최종 `setLines` 상태와 저장 payload는 두 번째 응답의 1,590,000을 유지했다.

## 수정

- `expandSelectedBundle` 요청 시작 시 bundle context를 즉시 `expandedBundleOptionsRef`/state에 등록한다.
- pending context를 거래처 전환 수집 대상에 포함해 새 거래처 재전개 요청을 보장한다.
- pending 부모 단가 갱신 시 VAT 파생값도 함께 재계산한다.
- 기존 구성행 삭제·사용자 override·delivery price 기반 계산 경로는 변경하지 않았다.
