## 3. S21-F1 양방향 RED와 요구 불변식

발생 사슬은 다음과 같다.

1. V113은 기존 행을 backfill하지 않으므로 DB source는 null이다.
2. 데스크톱 detail hydrate는 평문 규격의 null을 USER로, 구 마커 규격의 null을 CATALOG로 표시한다.
3. submit은 사용자가 규격을 건드리지 않아도 해석된 source를 모든 라인에 보낸다.
4. 새 revision snapshot에는 USER/CATALOG가 기록된다.
5. `EstimateRevisionService#lineDiffers`는 값이 같은 `null → USER/CATALOG`도 modified로 센다.
6. `EstimateVersionHistoryPanel`은 이를 `헤더 N · 라인 +0/-0/~1`로 사용자에게 표시한다.

반드시 먼저 추가할 양방향 RED는 다음과 같다.

- **RED-A, legacy 무변경:** 이전 snapshot의 평문 규격은 `"규격A"`, source는 null이고, 다음 snapshot의 규격은 동일하며 source만 USER다. 사용자는 메모만 바꿨다. 기대값은 `headerChanged=1`, `lineModified=0`이고 화면에는 라인 `~1`이 없어야 한다. 구 마커 null→CATALOG도 사용자가 보는 규격이 같고 라인을 건드리지 않았다면 같은 불변식을 만족해야 한다.
- **RED-B, 명시적 의미 변경:** 같은 보이는 규격 값이라도 사용자가 품목 규격을 직접 규격으로 명시적으로 전환하여 CATALOG→USER가 된 경우에는 `lineModified=1`이어야 한다. RED-A를 고치면서 이 의미 있는 변경을 숨기면 안 된다.

수정 후 지켜야 할 불변식은 “legacy null의 최초 정규화는 보이지 않는 라인 변경으로 세지 않되, 사용자 조작으로 확정된 CATALOG↔USER 전환은 센다”이다. 이를 위해 구 DB나 구 JSONB의 출처를 사후 추측하거나 일괄 backfill해서는 안 된다. 규격, 단가, 수량, 세액, 비고, 다른 라인 값도 수정 전후 동일해야 한다.

구 revision 복원의 값 보존 자체에는 새 결함이 없다. 평문 4건은 USER로 보존되어 품목 해제에도 남고, 마커 2건은 CATALOG로 해석되어 품목 해제 시 회수된다. 복원은 단가 포함/별도 VAT 및 legacy 공급가 분기를 유지한다. 문제는 복원값 소실이 아니라 그 다음 저장에서 생기는 거짓 변경 이력이다.

## 4. coedit·호환성 파급과 수정 금지선

S20이 추가한 협업 snapshot 필드는 Yjs wire update가 아니라 `EstimateDocumentCollaborationPort`가 `shared/collab-core` revision/suggestion에 제공하는 additive snapshot 필드다. 직전 클라이언트와의 혼용은 깨지지 않는다. source가 없는 구 문서는 현재 projection이 원격 규격 변경이면 USER, 그렇지 않으면 detail의 기존 source로 fallback한다. 마커 세대 구 문서는 마커 decoder가 CATALOG를 유지한다. 확인한 범위에서는 구 클라이언트 혼용으로 사용자 규격·단가·다른 라인 값이 조용히 사라지는 경로가 없다.

수정 범위는 다음 금지선을 지켜야 한다.

- 구 JSONB/DB null을 USER 또는 CATALOG로 일괄 추측·backfill하지 않는다.
- S21-F1을 숨기려고 source 비교 전체를 제거하지 않는다. 명시적 source 전환은 이력이어야 한다.
- 규격 회수 규칙(CATALOG만 회수)과 모바일 수동 규격 보존을 바꾸지 않는다.
- schema 변경이 없다면 V114를 만들지 않는다. schema 변경이 필요하면 기존 V113을 고치지 말고 V114와 세 카운트를 제시한다.
- 저장소 안에 QA driver 또는 raw `.log`를 만들지 않는다. 임시 실행물은 `os.tmpdir()`만 사용한다.
- #1057, #1066, #1069 트랙 파일과 무관한 견적/전표 동작을 건드리지 않는다.
