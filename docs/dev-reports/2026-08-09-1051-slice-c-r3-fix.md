# PR #1129 R3 — 선행 시딩 실패 후속 시더 차단

검증 시각: 2026-08-09 KST  
브랜치: `fix/1051-product-link-track`  
범위: 코드·회귀 테스트·R2 보고서 정정만 수행. commit/push, 실 DB 쓰기, 기존 행 수정·삭제, Docker 재배포 없음.

## 판정

BLOCKING과 HIGH를 모두 수정했다. 정상 경로에서 차단된 건수는 **0건**이다.

### BLOCKING — 선행 실패 후 반쪽 데이터

원인: `SlipSeeder.run()`이 예외를 내부에서 기록하고 정상 반환했지만, 후속 `CommandLineRunner`에는 실패 상태가 전달되지 않았다. `@Order(30)` `DeliveryBatchSeeder`는 매핑 가능한 Slip이 0건이어도 30개 batch를 만들었고, `@Order(40)` `EstimateSeeder`는 Slip/Product 검증 없이 40개 Estimate와 79개 line을 만들었다.

수정: `SeedDependencyState`를 dev 시더 공용 singleton으로 추가했다. `SlipSeeder`는 transaction 성공 후 `SUCCEEDED`, 예외 또는 flush/commit 실패 후 `FAILED`를 기록한다. `DeliveryBatchSeeder`, `EstimateSeeder`, 실제로 `CONFIRMED` Slip을 조회하는 `SlipLockSeeder`는 `SUCCEEDED`가 아니면 `ERROR` 로그와 함께 즉시 반환한다.

근거 로그 형식:

```text
[DeliveryBatchSeeder] 시딩을 건너뜁니다 — 선행 SlipSeeder가 성공하지 않았습니다. 상태=FAILED
[EstimateSeeder] 시딩을 건너뜁니다 — 선행 SlipSeeder가 성공하지 않았습니다. 상태=FAILED
[SlipLockSeeder] 시딩을 건너뜁니다 — 선행 SlipSeeder가 성공하지 않았습니다. 상태=FAILED
```

조용한 skip이 아니며, 실패 상태일 때 후속 repository와 상호작용하지 않는 회귀 테스트가 있다.

### HIGH — flush/commit 예외가 내부 catch 밖으로 탈출

원인: 기존 `@Transactional run()`은 메서드 반환 뒤 Spring transaction interceptor가 flush/commit을 수행하므로, 그 시점 최초 예외는 `run()` 내부 catch에 들어오지 않았다.

수정: `SlipSeeder` 운영 생성자는 `TransactionTemplate`으로 `seed()` callback과 transaction commit을 함께 감싼다. 따라서 callback의 flush 및 transaction commit 예외 모두 `run()`의 catch 범위에서 처리된다. 또한 `seed()` 마지막에 `slipRepository.flush()`를 명시해 지연된 JPA SQL 오류를 commit 이전에 catch로 끌어온다. 실패 시 `SeedDependencyState=FAILED`와 기존 ERROR stack trace 로깅을 유지한다.

근거: `flushFailureIsHandledAsSeedFailureWithoutEscapingRun`은 `flush()` 예외를 주입하고 `run()`이 예외를 전파하지 않으며 상태가 `FAILED`인지 확인한다.

## (a) 시더 의존 표

| 시더 | `@Order` | 코드상 선행 데이터 | R3 처리 |
|---|---:|---|---|
| `SlipSeeder` | 20 | product-service bulk lookup 후 Slip/SlipLine 생성 | root. 성공/실패 상태를 기록 |
| `DeliveryBatchSeeder` | 30 | `SlipRepository.findAllByStatusAndIsDeletedFalse`로 SHIPPING/DELIVERED/CONFIRMED OUTBOUND Slip 조회 후 batch 연결 | Slip 성공 아니면 ERROR skip; 성공 시 정상 30건 |
| `EstimateSeeder` | 40 | SlipSeeder 완료 뒤 실행하는 P2 seed. 라인은 `HvacSeedProductCatalog`의 product UUID를 사용 | Slip 성공 아니면 ERROR skip; 성공 시 정상 40건 |
| `SlipLockSeeder` | 50 | `CONFIRMED` Slip을 조회해 `lock()` | Slip 성공 아니면 ERROR skip |

Product/Partner 등 Slip 시더의 직접 실행 대상이 아닌 독립 시더에는 이 상태 게이트를 추가하지 않았다. DeliveryBatch와 Estimate를 정상 상태에서 막는 전역 “이전 runner 완료” 플래그가 아니라, 실제 Slip 선행 성공 여부만 검사한다.

## (b) 부분 저장 없음 근거

- `SlipSeeder`는 한 transaction 안에서 `save()`를 수행하고 마지막 `flush()`를 실행한다. 예외는 `TransactionTemplate`의 transaction 경계 안에서 rollback되며, 내부 catch에서 `FAILED`를 기록한다.
- 기존 `TransactionSynchronizationManager`/`setRollbackOnly()` 보강도 유지되어, 프록시 transaction 경로에서 callback 예외가 발생해도 부분 Slip/SlipLine commit을 허용하지 않는다.
- 후속 시더는 선행 실패 상태에서 첫 repository 호출 전에 반환하므로 DeliveryBatch, Estimate, EstimateLine 저장 자체가 없다.
- 정상 경로 테스트는 DeliveryBatch 저장 호출 30회, Estimate 저장 호출 40회를 확인해 RED-B 정상 건수 차단이 0임을 입증한다.
