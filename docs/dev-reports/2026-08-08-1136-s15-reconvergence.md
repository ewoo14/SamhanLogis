# PR #1137 / 이슈 #1136 — S15 재수렴 적대검증

## 결론

**결함 0이 아니다. 도달 결함 1건과 증거 무결성 결함 1건을 재현했다.**

1. **S15-BLOCK-1 — S11-BLOCK-1 미해소:** 실제 Flyway 10.10.0의 정상 출력 `Successfully validated ...`를 여전히 비-checksum 오류로 분류한다. `accounting-service`와 `auth-service`의 실제 `-WhatIf`가 모두 exit 1이었다. 기본 14-service 실행에서는 앞선 정상 서비스 하나가 뒤의 실제 checksum mismatch 대상 도달까지 막는다.
2. **S15-EVIDENCE-1 — S14 fixture 사용 주장과 실행 경로 불일치:** 고정 fixture는 정규식으로 세 문구만 확인할 뿐 fake Docker 입력으로 사용되지 않는다. fixture를 출력하는 `checksum-mismatch-real` mode는 한 번도 선택되지 않는다. S14 보고서의 “실제 Flyway validate 출력 fixture를 사용했다”는 판정 근거가 실행 사실과 다르다.

반면 S14의 핵심 git baseline 판정은 이번 표본에서 정상 동작했다. **머지된 편집이 현재 HEAD와 같고 DB checksum만 낡은 시나리오는 `-WhatIf` repair 지점까지 도달했고**, 같은 파일을 미커밋 상태로 파괴하면 HEAD/working-tree blob 차이를 출력하며 거부했다.

코드 수정, checkout, 실제 `repair`, `flyway_schema_history` 수정, Docker 재기동·재배포, QA 잔재 DB 접근·삭제는 하지 않았다.

## 1. S15-BLOCK-1 — 정상 Flyway 성공 출력이 여전히 복구 스크립트를 막는다

### 재현 절차

실행 중인 공유 PostgreSQL을 읽기 전용 `validate`만 하는 `-WhatIf`로 두 정상 서비스에 실행했다.

```powershell

powershell.exe -NoProfile -File scripts/repair-flyway-checksums.ps1 -Service auth-service -WhatIf
```

### 원인과 왜 실 경로인지

이것은 검증 품질 문제가 아니라 **복구 명령의 도달성 결함**이다. 문서가 안내하는 기본 전체 preview는 14개 서비스를 순서대로 처리하므로, checksum mismatch가 없는 첫 정상 서비스에서 exit 1이 나면 뒤 서비스의 실제 mismatch와 git baseline 판정에 도달하지 못한다.

## 2. 1차 각도 — S14 git baseline과 정상 복구 도달성

### 2.1 머지된 편집(working tree = HEAD) + 낡은 DB checksum

현재 HEAD의 auth V10 migration을 별도 migration root에 그대로 복사하고, checksum mismatch를 내는 Flyway 형식으로 `-WhatIf`를 실행한 현재 테스트를 직접 재실행했다.

```text
Environment file: C:\Users\user\AppData\Local\Temp\flyway-repair-test-...\infrastructure\.env
auth-service: checksum mismatch versions = 10
What if: Performing the operation "Flyway repair (checksum metadata only)" on target "auth-service".
REPAIR_TEST_EXIT=0
```

대상 파일의 실제 비교값도 같았다.

```text
HEAD=648dfeb08f11fd41215b6b97d44a60f7bc75d6b2
WORKING=648dfeb08f11fd41215b6b97d44a60f7bc75d6b2
```

**판정: 허용된다.** `Get-MigrationBaselineIssues`는 `ShouldProcess` 밖에서 실행되므로 `-WhatIf`에서도 baseline을 확인한 뒤 repair preview까지 간다. 실제 repair는 실행하지 않았다.

### 2.2 줄바꿈 — 이 PC의 `core.autocrlf=true`

```text
git config --show-origin --get core.autocrlf
file:C:/Program Files/Git/etc/gitconfig true

git check-attr -a -- <auth V10 migration>
text: auto
eol: lf

COUNT=407
DEFAULT_MISMATCH=0
RAW_MISMATCH=0
EOL_COUNTS: lf 407
```

`HEAD blob`, 기본 `git hash-object`, `git hash-object --no-filters`를 현재 407개 migration 전수로 한 번씩 대조했다. 모두 동일했다. 저장소 `.gitattributes`의 `* text=auto eol=lf` 때문에 이 PC에서도 migration working tree는 LF다.

**판정: 제시된 CRLF 전면 차단 가설은 이 PC/현재 checkout에서 반증됐다. 정상 파일 407/407가 baseline을 통과한다.**

### 2.3 detached HEAD, rebase/merge, dirty working tree

실제 detached worktree `t1103`에서 branch 이름이 비어 있는 상태로 같은 명령을 실행했다.

```text
DETACHED_BRANCH=
DETACHED_HEAD=1c6aa6ea1c32589284abb04ce5a48de53c5de31c
DETACHED_PATH=services/accounting-service/src/main/resources/db/migration/V10__seed_slice_c_validation_journals.sql
DETACHED_HEAD_BLOB=c9f6ef278e677a26760dc76f19cc7077069cb45e
DETACHED_WORKING_BLOB=c9f6ef278e677a26760dc76f19cc7077069cb45e
```

**detached 판정: 허용.** branch ref를 읽지 않고 `HEAD:<path>`만 사용한다.

현재 worktree는 `origin/main...HEAD = 8 behind / 10 ahead`인 분기 상태이고 migration diff는 0건이다. guard는 exit 0, 407개 baseline hash도 전부 일치했다. unrelated dirty 파일 유무는 baseline 함수 입력에 없고 대상 migration blob만 비교한다.

rebase/merge도 코드가 rebase/merge marker나 branch명을 읽지 않는다. 적용된 임시 commit 뒤 working tree가 그 HEAD와 같으면 허용되고, 충돌 중 대상 migration이 HEAD와 다르면 거부된다. 이번 S15 실행 시 현재 worktree에는 `rebase-merge`, `rebase-apply`, `MERGE_HEAD`가 모두 없어서 **실제 충돌 중 상태 자체는 만들지 않았다**. S11이 실제 임시 commit graph에서 측정한 rebase/main 반영 2종 exit 0 이후 guard 본체는 변경되지 않았다(`612ae6f0c`가 마지막 변경).

### 2.4 git 부재·레포 밖

레포 밖에서 같은 기준 조회를 실행했다.

```text
git -C C:\Windows\Temp rev-parse HEAD:<migration-path>
fatal: not a git repository (or any of the parent directories): .git
OUTSIDE_REPO_EXIT=128
```

`Get-GitOutput`은 nonzero면 `$null`을 반환하고, baseline 함수는 `-not $committedBlob`을 issue로 추가한 뒤 repair를 거부한다. `git` 실행 파일 자체가 PATH에 없을 때는 PowerShell `CommandNotFoundException`이 함수 밖으로 전파되어 스크립트가 중단됐다. **둘 다 허용이 아니라 fail-closed다.**

### 2.5 worktree·submodule·경로 계산·다른 cwd

```text
CURRENT_GIT_DIR=C:/dev/Samhan-Public/.git/worktrees/t1136
CURRENT_COMMON_DIR=C:/dev/Samhan-Public/.git
ALT_CWD=C:\Windows\Temp
ALT_CWD_HEAD_BLOB=648dfeb08f11fd41215b6b97d44a60f7bc75d6b2
ALT_CWD_WORKING_BLOB=648dfeb08f11fd41215b6b97d44a60f7bc75d6b2
SUBMODULE_CONFIG_COUNT=0
```

`$repoRoot` 기본값은 호출 cwd가 아니라 `$PSScriptRoot`의 부모이고, Git도 `git -C $repoRoot`로 실행한다. `$relative`는 기본 실행에서는 `$migrationRoot = $repoRoot`이므로 repo root 기준이다. 테스트용 `-MigrationRoot`를 주면 그 mirror root 기준 상대경로를 계산한 뒤 같은 repo HEAD 경로와 비교한다. `C:\Windows\Temp`에서 절대 script/repo 경로로 조회해도 blob은 같았다.

현재 저장소에는 submodule이 0개여서 submodule 내부 migration 실경로는 없다. linked worktree에서는 위 `git-dir != common-dir` 상태로 의도대로 동작했다.

## 4. 3차 각도 — 적용 migration guard 본체와 workflow

### 4.1 적용 migration 편집 차단

현재 `scripts/check-applied-migrations.test.ps1`은 임시 Git fixture에서 이미 main에 있는 V1을 수정·삭제·rename하고 각각 실제 guard exit 1을 단언한다. main 직접 push 단일 commit과 다중 commit 범위도 exit 1을 단언한다. 직접 재실행 결과:

```text
Flyway applied-migration guard scenarios: PASS
GUARD_TEST_EXIT=0
```

현재 HEAD `bd0f14a12`의 실제 GitHub Actions run `31251673131`(Ubuntu/pwsh)도 같은 테스트와 실제 branch 검사를 실행했다.

```text
가드 시나리오 테스트 (RED-A/RED-B)
Flyway applied-migration guard scenarios: PASS

적용된 마이그레이션 변경 검사
PASS: origin/main 대비 적용된 마이그레이션 변경 없음 (신규 migration 추가는 허용).
```

workflow는 PR과 main push 모두 `**/db/migration/V*.sql` 변경에 발화하고 `fetch-depth: 0`으로 checkout한 뒤 테스트와 guard를 순서대로 실행한다. **적용 migration 수정 commit은 fixture에서 exit 1로 실제 차단된다.** 현재 PR은 migration을 바꾸지 않아 실제 branch 검사 exit 0이 맞다.

### 4.2 실제 407개 전수 BLOCK 수

`origin/main` tree에서 guard의 실제 `Is-AppliedMigration` 정규식에 맞는 경로를 전수 집계했다.

```text
ORIGIN_MAIN_MIGRATIONS=407
AS_MODIFIED_BLOCK=407
AS_DELETED_BLOCK=407
AS_RENAMED_OLDPATH_BLOCK=407
```

서비스별 합계는 accounting 70, arologis 25, auth 94, dashboard 7, dc-config 5, groupware 18, inventory 23, notification 10, partner-auth 3, partner-order 17, partner 13, product 32, slip 78, user 12로 총 407이다.

새 migration은 diff status `A`라 violation switch(`M`, `D`, `R`)에 들어가지 않는다. main에 아직 없는 migration을 feature commit 안에서 다시 수정해도 최종 main merge-base 대비 status는 `A`다. S11의 실제 임시 graph에서 새 migration, 미적용 migration 재수정, rebase, main 반영 뒤 push가 각각 exit 0이었고, guard/workflow는 그 뒤 변경되지 않았다. 현재 분기된 실제 branch도 migration diff 0건, guard exit 0이다.

**정상 개발 경로 판정: 새 migration 추가·PR 안의 미적용 migration 수정·rebase·main 병합 자체를 막는 회귀는 확인되지 않았다.**

- RED-B의 미커밋 손상: `648d...` 대 `b847...` blob 불일치로 거부.

### S15-EVIDENCE-1 — 실제 fixture가 판정 입력으로 사용되지 않는다

S14 보고서는 “실제 Flyway validate 출력 fixture를 사용했다”고 적었다. 현재 테스트의 실제 참조는 다음뿐이다.

```text
7:  $flywayOutputFixture = ...flyway-validate-checksum-mismatch.txt
8:  $flywayOutput = Get-Content ...
9:  if ($flywayOutput -notmatch 'Flyway OSS Edition 10.10.0' ... ) { throw ... }
```

그 뒤 `$flywayOutput`은 다시 사용되지 않는다. fake Docker의 `checksum-mismatch-real` branch가 fixture와 같은 문구를 손으로 출력하지만, mode 설정 전수는 다음뿐이었다.

```text
mixed-validate-errors
checksum-mismatch
inspect-missing
inspect-env
checksum-mismatch-multiline
```

`checksum-mismatch-real`을 mode file에 쓰는 호출은 **0건**이다. 정상 복구 RED-A도 실제 fixture의 version 1/PostgreSQL 16.13 출력이 아니라 손으로 쓴 `checksum-mismatch-multiline`의 version 10/PostgreSQL 16.14 출력을 사용한다.

또한 재실행 원문에서 `What if:` 네 줄은 `RED-A raw output:`보다 앞에 직접 출력됐고, `$normalCommittedText` 안의 RED-A 원문에는 다음 두 줄만 있었다.

```text
Environment file: ...
auth-service: checksum mismatch versions = 10
```

S14 보고서는 `What if:`를 RED-A raw output 안에 포함한 것처럼 인용했다. 결론(정상 HEAD blob이 preview에 도달)은 별도 출력과 exit 0으로 재현되지만, **fixture 사용 및 raw-output 인용의 provenance는 보고서 서술과 일치하지 않는다.** 이는 허용된 증거 무결성 예외로 보고한다.

## 이 라운드가 보지 않은 것

- 실제 `repair` 실행과 `flyway_schema_history` 변경은 금지 조건 때문에 보지 않았다.
- 현재 S15 시점에 실제 rebase/merge conflict 상태를 만들지 않았다. 현재 marker 3종은 없었고, detached 실제 worktree와 분기된 현재 worktree를 실행 표본으로 사용했다.
- submodule은 현재 저장소에 0개라 submodule 내부 migration은 실행 표본이 없다.
- QA 잔재 DB(`slip_db_qa_e2estimate`, `sol951_*`)는 조회·삭제·서비스 취급하지 않았다.
- 전체 Gradle suite, Docker 재기동·재배포는 하지 않았다.
