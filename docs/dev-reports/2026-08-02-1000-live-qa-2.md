## 3. 시나리오 ③ — 출고 수락 lookup 관문

### 실제 실행

standalone product-service jar를 포트 18420에 기동하고, Playwright headless에서 실제 HTTP를 호출했다. 데스크톱 카탈로그 화면의 상품 목록 요청도 standalone으로 라우팅하여 대상 모델명이 화면에 표시되는 것을 확인했다.

실제 internal lookup:

~~~text
POST http://127.0.0.1:18420/products/internal/lookup-by-model
body {"modelName":"AR05TXEAAWKNEU-01"}
HTTP 200
id = 01949ab7-e922-35c6-b289-5337d867a0ee
modelName = AR05TXEAAWKNEU-01

POST http://127.0.0.1:18420/products/internal/lookup-by-code
body {"productCode":"010001"}
HTTP 200
id = 01949ab7-e922-35c6-b289-5337d867a0ee
modelName = AR05TXEAAWKNEU-01
~~~

이 경로는 inventory-service의 실제 ProductClient.lookupByCode()가 호출하는 /products/internal/lookup-by-code와 동일한 경로다. 모델명과 이카운트 옛 순번코드 양쪽 모두 같은 제품 UUID로 해소됐다.

캡처:

- 03-scenario-3-lookup-gate-catalog.png
  - 실제 데스크톱 카탈로그 화면
  - standalone 응답의 AR05TXEAAWKNEU-01 노출 확인

**관문 판정: PASS.**

### 검증 경계

- 확인한 범위: product-service standalone HTTP lookup 관문과 실제 카탈로그 화면 표시.
- 확인하지 않은 범위: 실 전표 19건 각각에 대해 inventory-service 출고 예약/출고 수락 전체 트랜잭션을 실행한 결과.
- 전표를 SENT → ACCEPTED로 변경하는 것은 공유 실데이터 write이므로 수행하지 않았다.
