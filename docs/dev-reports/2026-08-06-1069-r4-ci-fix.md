## 1. 결함 1 — `bundle-set-options` 시나리오 4

### 원인

R3에서 `bundle-options-0-panel-option`이 자유 입력 `<input>`에서 서버 도메인 값만 제공하는 `<select>`로 바뀌었는데, Playwright 스펙은 기존 방식인 `fill()`을 계속 호출하고 있었다. CI 원문은 다음과 같다.

```text
Error: locator.fill: Error: Element is not an <input>, <textarea> or [contenteditable] element
locator resolved to <select aria-label="판넬 옵션 (미입력=기본)" data-testid="bundle-options-0-panel-option">
```

### 조치

`clients/desktop/playwright/bundle-set-options/bundle-set-options.spec.ts:148-150`을 다음 계약으로 정합화했다.

```ts
const panelOption = page.getByTestId('bundle-options-0-panel-option')
await panelOption.selectOption('블랙판넬')
await expect(panelOption).toHaveValue('블랙판넬')
```

`toHaveValue('블랙판넬')` 단언은 유지했다. 따라서 이 스펙이 원래 지키던 **controlled value가 컴포넌트 상태에 붙고 다시 읽히는 round-trip**을 약화하거나 삭제하지 않았다.

같은 시나리오의 판넬 360 문자열 select, 자재 포함 checkbox 단언은 그대로 유지했다. 시나리오 6의 저장 payload 단언도 그대로 유지되어, 빈 판넬 옵션은 `null`, `panelShape360`은 문자열, `materialIncluded`는 `true`로 전송되는 계약을 계속 검증한다.

전수 sweep 중 `SlipFormPage.test.tsx`의 가짜 `BundleOptionRow`가 생산 UI에는 존재하지 않는 `PANEL-3`을 emit하던 것도 발견했다. 해당 mock과 3개 기대값을 서버 도메인 값 `블랙판넬`로 바꿔 테스트 표면도 R3 계약과 맞췄다.

## 2. 결함 2 — `SlipFormPage.test.tsx:2215`

### CI 관측

CI run `31064443719`, job `92499372898`의 실패는 다음과 같다.

```text
FAIL src/renderer/routes/SlipFormPage.test.tsx
  둘 다: 단가 input IDREF 는 "priceStatusId priceChangedStatusId" 복수를 순서대로 가리킨다
AssertionError: expected '1000' to be '200000'
Expected: "200000"
Received: "1000"
src/renderer/routes/SlipFormPage.test.tsx:2215:57
Test Files 1 failed | 208 passed (209)
Tests 1 failed | 1872 passed (1873)
```

`1000`은 `productA.sellingPrice`인 catalog fallback이다. 즉 이 테스트가 `mockResolvedValueOnce()`로 준비한 `getPriceMemories()`의 `200000` hit가 재가격 결과로 적용되지 않은 상태다.

### R3 관련성 판정

R3 diff를 부모 `d9d9c10e3`과 직접 비교했다. `SlipFormPage.tsx`의 R3 추가분은 `restorePreviousExpansion()`과 빈/실패 세트 전개 응답의 이전 구성 복원뿐이다. 가격 memory API, `useEffect`, 거래처 전환 handler, `usePartnerPriceRefresh` 호출은 R3에서 바뀌지 않았다.

코드 경로도 분리된다.

- `getPriceMemories`는 `usePartnerPriceRefresh.run()`에서만 호출된다.
- `run()`은 `refreshAutoPricesForPartner()`에서만 호출된다.
- `refreshAutoPricesForPartner()`는 거래처 autocomplete handler에서만 호출된다.
- R3의 `restorePreviousExpansion()`은 세트 전개 경로에만 있다.
- 실패한 테스트는 `productA`를 선택하는 단품 가격 memory 시나리오이며 BUNDLE 선택/옵션 변경/세트 전개를 실행하지 않는다.

따라서 R3의 재전개 실패·빈 응답 처리 때문에 이 테스트의 `mockResolvedValueOnce()`가 앞당겨 소진됐다는 가설은 코드상 성립하지 않는다. R3 경로는 이 테스트에서 실행되지 않는다.

### 결론 — 선재 flake로 분류, 수정하지 않음

직접 확인한 결과는 다음과 같다.

- 지정 테스트 파일 전체: `96 tests` 통과
- 해당 테스트 `-t` 격리 실행: 통과
- 해당 테스트 `-t` 10회 반복: `10/10` 통과
- 지정 4개 파일 묶음: `238 tests` 통과
- 직전 SHA `d9d9c10e3` CI green이라는 사용자 제공 표본과도 일치

현재 테스트는 거래처 전환 bulk 결과를 `mockResolvedValueOnce()`의 호출 순서에 의존한다. CI 전체 스위트처럼 실행 부하와 비동기 스케줄링이 달라지는 조건에서 hit가 호출되지 않거나 다른 in-flight mock 호출에 의해 소비되면, 코드가 정상적인 catalog fallback `1000`을 남기고 위와 같은 실패가 난다. 이것이 이 라운드에서 확인 가능한 셋째 원인( R3가 아닌 **suite-load/one-shot mock 순서 의존 flake** )이다.

이 현상은 R3 생산 코드의 회귀로 확정할 근거가 없고, 무관한 생산 코드나 가격 경로를 표면적으로 고치지 않았다. 정확히 어떤 전체 스위트 비동기 호출이 one-shot 응답을 앞당겨 소비했는지는 현재 단일 CI 표본과 로컬 green만으로 재현되지 않으므로, 별도 flake 트랙으로 남긴다.
