### 3.1 S36 `localSpecificationWrites`

- 생성 좌표: `EstimateFormPage.tsx:1170-1218`. 사용자가 규격을 바꾸면 현재 Y.Doc 규격과 새 규격을 라인 `uid`에 기록한다.
- 소비 좌표: `EstimateFormPage.tsx:362-453`. Y.Doc 값이 `previousSpecification`이면 같은 사용자 입력에서 먼저 발생한 `specificationSource` 쓰기의 stale 셀 snapshot으로 보고 현재 draft 값을 유지한다. 기대한 새 규격 또는 전혀 다른 규격이 오면 marker를 삭제한다.
- 이 marker는 비동기 원격 변경을 장기간 차단하는 큐가 아니다. 실제 입력 순서는 `CollaborativeSlipInput.tsx:292-303`의 한 JavaScript 호출 스택 안에서 `onValueChange` → `specificationSource` 쓰기 → `specification` 쓰기다. 원격 네트워크 이벤트는 그 두 동기 쓰기 사이에 끼어들 수 없다. 두 번째 쓰기에서 marker가 소비된다.
- 따라서 원격 사용자가 나중에 내 직전 값으로 되돌리는 경우에는 marker가 이미 없어 원격 값이 반영된다. marker가 남아 있더라도 `previousSpecification`과 다른 첫 원격 규격은 marker를 삭제하고 반영한다.
- 협업 활성 중에는 기존 양쪽 클라이언트의 라인 추가·삭제 UI가 잠긴다(`lineStructureLocked`, 삭제 버튼 `disabled={... || coeditActive}`). 실사용자 조작으로 index가 밀리는 경로는 없다. 저장 성공 후 상세로 이동하거나 버전 복원 뒤 편집 재진입하면 컴포넌트가 다시 생성되어 ref도 새로 만들어진다.
- 카탈로그 규격 lookup은 적용 직전에 해당 `uid` marker를 명시 삭제한다(`EstimateFormPage.tsx:1548-1551`).

결론: 제시된 세 marker 잔류 후보 중 실사용자 경로로 도달하는 잔류는 확인하지 못했다.

### 3.2 S33 병렬 보존과 금액 payload

- `ProductSummary` 정규 record에는 `bundleMode`, `fixedDiscountRate`, `specification`이 동시에 존재한다. 추가 전 호출자를 위한 오버로드는 빠진 필드만 `null`로 위임한다.
- 견적 신규 BUNDLE은 `BundleModePolicy.shouldExpand(summary)`로 전개되고, 요청 단가를 product-service 전개 호출에 전달한다. 구성품 규격 provenance와 `bundleSetOptions`를 함께 영속한다.
- 기존 전개 견적의 편집 저장은 각 상세 라인의 `lineId`를 왕복한다. FE에서 이미 전개된 구성품의 `productType`을 `null`로 두어 재전개하지 않고, BE `BundleLineageResolver`가 같은 `lineId + productId`에만 기존 `(parentSetModel, setHead, bundleSetOptions)`를 승계한다. UI가 없어진 뒤에도 기존 옵션은 이 서버 계보 경로로 보존된다.
- 권위 금액 라인은 S/V/T와 `unitPriceWithVat`를 그대로 견적→전표로 복사하고, 구 라인은 공급단가 경로를 유지한다. 전환 시 세트 구성품의 계보와 옵션도 1:1 복사한다.
- `EstimateSnapshot.Line`은 현재 `specificationSource`와 `bundleSetOptions`를 모두 가진다. 10/12/13/14-arg 구 생성자는 누락 필드를 `null`로 canonical 생성자에 위임하고, 구 JSON의 누락 키도 `null`로 역직렬화된다.

결론: #1077 금액/옵션과 #1078 규격 provenance가 같은 라인 payload에서 한쪽을 덮거나 구 snapshot 금액 의미를 바꾸는 조합은 확인하지 못했다.

- 부분 문자열 검색은 공용 `searchProducts(q)` 결과를 우선 사용하고, 결과 0건일 때만 정확 모델 legacy lookup으로 폴백한다.
- 후보 확정은 공용 `ProductOption`의 id·모델명·품목명·규격·단가를 draft와 payload에 보존한다. 품목 해제는 CATALOG 규격만 회수하고 USER 규격은 보존한다. 새 카탈로그 확정은 marker를 폐기하고 CATALOG 값을 적용한다.

### 3.5 R14 상태 위생 관측 재판정

품목 해제 뒤 빈 규격에 `specificationSource=USER`가 남는 관측은 이 게이트에서 도달 결함으로 뒤집지 않는다.

- 해제한 라인은 `productId`가 없어 저장 payload의 유효 라인에서 제외된다. 기존 라인 전체 해제 저장도 빈 `lines` 삭제 계약으로 들어가므로 잔류 source가 DB 라인으로 저장되지 않는다.
- 다른 카탈로그 품목을 확정하면 lookup 경로가 source를 `CATALOG`로 덮는다.
- 규격 없는 다른 품목을 확정해 `USER`가 남더라도 화면 규격·금액·저장 가능 여부는 달라지지 않고, 이후 카탈로그 규격이 생기면 CATALOG lookup이 우선한다.

따라서 현재 관측 가능한 영향은 내부 provenance의 빈 값 위생에 한정된다. PM의 기존 판정을 반박할 실사용자 도달 근거는 확인하지 못했다.
