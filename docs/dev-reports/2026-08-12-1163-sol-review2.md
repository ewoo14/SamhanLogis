## 1. 결론

fix1이 막은 canonical·32hex·brace·URN·일부 zero-width 변형은 확인했다. 그러나 변형 집합과 사람 표시 출구의 분모가 모두 닫히지 않았다.

1. 격리 서비스 라이브 QA에서 창고 이력과 협업 이력에 U+2063 wrapper 및 유니코드 유사문자 UUID가 그대로 표시됐다.
2. 권한 변경 로그는 UUID를 숨겼지만 원 actorId를 어떤 감사 저장소에도 남기지 않아 역추적 경로를 잃었다. 실제 권한설정 화면이 호출하는 계정별 권한 변경 경로는 actorId 인자를 아예 사용하지 않는다.
3. mobile-staff 감사, 아로로지스 저장 이력, 데스크톱 삭제 배지·툴팁, slip 감사 API 등 공통 resolver 우회 출구가 남았다. 따라서 fix1의 “출구 전수” 표는 전수가 아니다.
4. 별도 저장 이력 helper는 여전히 `system`을 화면 문자열로 반환하므로 `시스템` 통일도 완료되지 않았다.

홈택스 이력·제외 목록은 격리 라이브 화면에서 UUID 대신 `변경자 미상`을 표시했다. 정상 이름 `김감사`도 창고·협업 화면에서 그대로 표시되어 해당 경로의 과잉 차단은 없었다. `dashboard-service` N/A 판정은 되돌리지 않는다.

## 2. 차단 결함

### P1-1. 공통 resolver가 U+2063 및 유니코드 유사문자 UUID를 통과시켜 실 화면에 노출한다

**좌표**

- `shared/common/src/main/java/com/samhanair/logis/common/security/ActorDisplayName.java:15-20,49-67`
- `clients/web/design-system/src/utils/actorName.ts:2-16`

**원인**

- invisible 제거 집합은 `U+00AD`, `U+200B~U+200D`, `U+2060`, `U+FEFF`만 포함한다. Unicode category `Cf`인 `U+2063 INVISIBLE SEPARATOR`는 빠져 있다.
- NFKC 정규화와 UUID 구문용 유사문자 folding이 없다. fullwidth colon/Latin과 `U+2010 HYPHEN` 조합은 UUID regex에 걸리지 않는다.
- BE/FE 양쪽이 같은 좁은 패턴을 중복 구현해 동일하게 실패했다.

**격리 라이브 실패 원문**

```text
창고 이력 UUID 노출:
#2 · ⁣cafebabe-cafe-babe-cafe-babecafebabe⁣
#5 · urn：uuid：ＣＡＦＥＢＡＢＥ‐ＣＡＦＥ‐ＢＡＢＥ‐ＣＡＦＥ‐ＢＡＢＥＣＡＦＥＢＡＢＥ

협업 이력 UUID 노출:
⁣cafebabe-cafe-babe-cafe-babecafebabe⁣
urn：uuid：ＣＡＦＥＢＡＢＥ‐ＣＡＦＥ‐ＢＡＢＥ‐ＣＡＦＥ‐ＢＡＢＥＣＡＦＥＢＡＢＥ
```

- 첫 문자열의 양끝은 `U+2063`, UTF-8 hex `e281a3`이다.
- 둘째 문자열은 fullwidth `：`, fullwidth Latin/hex, `U+2010` 하이픈을 사용한다.
- Playwright의 비교 검출기는 NFKC → 모든 `\p{Cf}` 제거 → dash-like 문자 `-` folding 후 UUID를 판정했다.

**영향**

창고 audit row와 journal collaboration row에 원 actorId가 들어온 과거/오염 데이터가 있으면 desktop 화면 문자열로 노출된다. 같은 공통 resolver를 쓰는 저장·이벤트·로그 경로도 동일 변형을 안전한 이름으로 오판한다.

**수정 지시**

1. BE/FE 정규화를 동일 계약으로 정의한다: trim, Unicode NFKC, 모든 format character(`Cf`) 제거, UUID 구문의 colon/dash 유사문자 canonical folding.
2. canonical, mixed case, raw32, brace, URN, 앞뒤 공백뿐 아니라 U+2063과 유사문자 조합을 양쪽 공통 계약 테스트에 넣는다.
3. actorId가 별도 존재하는 경로는 정규화한 표시 후보를 정규화한 actorId와 비교하는 방어도 유지하되, UUID-shaped 타 값도 사람 이름으로 표시하지 않는다.

### P1-2. auth 권한 변경은 표시 UUID를 감추면서 원 actor 역추적도 잃는다

**좌표**

- 실제 화면 진입: `PermissionAdminController.updateAccountMatrix` → `AccountPermissionService.updateAccountMatrix`

**격리 실측**

`X-User-Id=cafebabe-cafe-babe-cafe-babecafebabe`로 격리 auth-service의 internal role-grant를 실행했다.

```text
HTTP: 200
controller WARN actorName=변경자 미상, UUID 없음
service INFO actorName=변경자 미상, UUID 없음
DB role_page_permissions.modified_by=system-internal
```

controller는 원 actorId를 service 인자로 넘기지만 service는 `ActorDisplayName.resolve(actorId, null)`로 만든 표시 문자열을 로그에만 기록한다. 신규/갱신 entity에는 actorId를 저장하지 않고 JPA audit principal인 `system-internal`만 남는다. 즉 로그와 DB 어느 쪽에서도 원 요청자를 복원할 수 없다.

또한 라이브로 밟은 `/admin/permission-matrix`의 실제 저장 경로인 `AccountPermissionService.updateAccountMatrix`는 `actorId`를 파라미터로 받지만 메서드 본문 `:207-229`에서 사용하지 않는다. 별도 변경 로그나 actor audit row도 없다. fix1의 권한 로그 테스트는 화면이 사용하는 이 경로를 검증하지 않는다.

**수정 지시**

- 사람에게 보이는 로그에는 이름/`변경자 미상`만 남기되, 접근 통제된 structured audit 필드나 별도 감사 entity에는 원 actorId를 보존한다.
- role-grant 신규/갱신과 계정 matrix/template/copy/bulk 경로 모두 같은 역추적 계약을 통과시킨다.
- “service mock이 원 actorId 인자를 받음”이 아니라 transaction 종료 뒤 audit 저장값으로 역추적 가능함을 검증한다.

| ASCII 앞뒤 공백 | trim 후 차단 | O |
| U+200B~U+200D, U+2060, U+FEFF wrapper | 제거 후 차단 | O |
| U+2063 등 나머지 `Cf` | 통과 | **X, 라이브 재현** |
| fullwidth colon/Latin + Unicode dash | 통과 | **X, 라이브 재현** |
| 임의의 Unicode 유사문자 | skeleton 계약 없음 | **X, 목록 미폐쇄** |

혼용 case·raw32·공백은 이번 결함이 아니다. 문제는 “zero-width”를 특정 6개 code point 목록으로 닫았다고 간주한 것과 Unicode 유사문자 정규화 계약이 없는 것이다.

## 8. 이 라운드가 실 화면으로 보지 않은 표면

결함이 있으므로 merge 판단용 0결함 보고가 아니다. 라이브로 보지 않은 표면은 명시한다.

- mobile-staff 감사 오버레이
- arologis-desktop 저장 이력/복원 banner
- desktop 삭제 배지의 visible text, title, aria-label
- slip version/redline/photo 감사 화면과 해당 raw API response
- QuoteView 인쇄 및 실제 PDF 파일 생성물
- Excel/XLSX·CSV 실제 다운로드 파일 바이트
- 이메일·SMS 실 송신 본문, webhook payload
- 나머지 audit 서비스의 실 DB→API→UI 왕복
- dashboard/version 서비스 연동 banner

이 표면들은 정적 sweep만 수행했다. 특히 앞의 네 그룹은 공통 resolver 우회가 코드로 확정되어 후속 수정·실 QA가 필요하다.
