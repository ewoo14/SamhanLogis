## 1. 레거시 GAS 실행 모드

확인 원본:

- `tools/legacy-gas/가배차분류리스트/Index.html`: `modeSelect`가 값 `1`~`8`의 선택지 8개를 표시한다.
- `tools/legacy-gas/가배차분류리스트/Code.js`: `runClassification(ecountData, methodCode, day)`의 `switch`가 `case '1'`~`case '8'`을 각각 아래 함수에 1:1 대응한다. 다른 정상 분기는 없다.
- `tools/legacy-gas/지방가배차분류리스트/Index.html` 및 `Code.js`: 별도 모드 선택기나 `methodCode` 분기 없이 `runClassification(ecountData, day)` 한 흐름만 실행한다.

따라서 레거시가 명시적으로 제공한 **가배차 실행 모드는 정확히 8개**다. 지방가배차 프로그램 자체는 별도 단일 실행 흐름이며, 이를 아홉 번째 선택 모드로 세지 않는다.

## 2. 현행 가배차 화면·기능 존재 여부

결론: **현행 아로로지스 데스크톱에 실제 가배차 화면과 조회 기능이 있다.** 단순 문자열 검색이 아니라 아래 라우트·화면 파일·API·백엔드 endpoint 연결을 확인했다.

- 실 라우트: `clients/arologis-desktop/src/renderer/routes/index.tsx`가 `/dispatches/pre-classify`를 `ArologisPreClassifyPage`에 연결한다.
- 실 메뉴: `clients/arologis-desktop/src/renderer/routes/dispatches/DispatchesLayout.tsx`가 위 경로를 `가배차 분류` 메뉴로 노출한다.
- 실 화면: `clients/arologis-desktop/src/renderer/routes/dispatches/PreClassifyPage.tsx`가 `가배차 (권역)`과 `지방가배차 (시도)` 두 탭을 렌더링한다.
- FE 호출: 같은 화면이 `getPreClassify(from, to)`와 `getRegional(date)`를 실행한다.
- API client: `clients/arologis-desktop/src/renderer/api/arologisDispatch.ts`가 각각 `GET /admin/arologis/dispatches/pre-classify`와 `GET /admin/arologis/dispatches/regional`에 연결한다.
- BE endpoint: `services/arologis-service/.../controller/ArologisAdminController.java`에 위 두 `@GetMapping`이 실제 등록돼 각각 `PreClassifyService`, `RegionalService`를 호출한다.

8모드 관점의 현재 경계도 확인했다.

- 현재 브랜치에는 `DispatchExecutionMode` 8개 enum, FE 동명 union type, `pre-classify` endpoint의 선택적 `mode` 파라미터와 서비스 필터가 존재한다.
- 그러나 `PreClassifyPage.tsx`에는 실행 모드 선택 UI가 없고 query도 `getPreClassify(from, to)`로 호출하여 `mode`를 전달하지 않는다.
- 따라서 **가배차·지방가배차 기본 화면/기능은 존재하지만, 화면에서 8개 실행 모드를 선택해 실행하는 완전한 기능은 아직 없다.**

## 3. `RegionalService` 17개 시도 분류 사용처 전수

### 현재 브랜치의 실제 동작 경계

`RegionalService.classifyBySido()`는 전체 출고전표를 바로 17개 문자열로 지방 판정하지 않는다. 먼저 `slip.deliveryTag()`가 `REGION`인 전표만 통과시키고, 그 선별된 전표의 주소에 `extractSido()`를 적용한다. 따라서 현재 17개 문자열은 **지방 포함 여부 판정이 아니라 화면 표시용 시도 그룹/미매칭 분리**에만 쓰인다.

### 개수

- 생산 코드의 `classifyBySido()` 직접 호출: **1곳** — `ArologisAdminController.regional()`.
- `RegionalService` 결과 계약의 런타임 소비: **6개 파일**.
- 해당 행동 계약을 고정하는 검증 소비: **4개 파일**.
- 합계: **소비 파일 10개**. 알고리즘 정의 파일 `RegionalService.java`까지 변경 영향에 포함하면 **총 11개 파일**이다.
- 라우트/메뉴/수동배차 이동 링크는 화면 진입점일 뿐 결과 DTO를 소비하지 않으므로 위 10개에 중복 산입하지 않았다.

### 런타임 소비 6개 파일

## 4. `REGION` 12건·`STACK` 11건 읽기 전용 대조

공유 PostgreSQL을 재기동·재빌드하지 않고 `BEGIN READ ONLY ... COMMIT` 트랜잭션의 집계 `SELECT`만 실행했다. 내부 식별자는 조회하지 않았다.

### DB 재현 결과

활성 전표(`deleted_at IS NULL`)의 태그 분포:

| 배송 태그 | 건수 |
|---|---:|
| 없음 | 2,261 |
| DAY | 52 |
| REGION | 12 |
| RETURN_RENTAL | 10 |
| STACK | 11 |

즉 요청에 제시된 **REGION 12건·STACK 11건은 현재 DB 집계와 정확히 일치**한다.

추가 대조:

- 활성 출고전표는 2,304건이며 REGION 또는 STACK은 23건, **1.00%**다.
- REGION 12건은 모두 `OUTBOUND / MANUAL / DRAFT`, 생성일은 2026-06-24~25다.
- STACK 11건은 모두 `OUTBOUND / MANUAL`; 10건은 2026-05-09, 1건은 2026-06-25 생성이다.
- REGION 12건과 STACK 11건 모두 `delivery_address` 보유 건수가 **0건**이다.
- `source_type=PARTNER_ORDER` 활성 출고전표 20건은 REGION 0, STACK 0, 태그 없음 20건이다.
- `SlipSeeder`가 STACK을 정확히 10건 생성하도록 고정돼 있고, DB의 STACK 10건이 같은 날짜에 집중돼 있어 STACK 11건 중 대부분은 운영 실건이 아니라 시드 표본일 가능성이 높다.
- 코드상 견적 발행, 주문 발행, 주문 병합 발행, 모바일 현장 발행은 `deliveryTag`를 `null`로 생성한다. 주소에서 태그를 자동 선택하는 생산 경로는 확인되지 않았다.

### 판정

- **DB에 저장된 태그 건수의 산술 정확성:** 확인 완료.
- **실제 업무상 지방·야적 전체 건수와의 일치:** 독립된 정답 표본이 없어 확인불가.
- **태그가 잘 붙고 있는가:** 완전하다고 볼 수 없다. 두 태그가 수동 생성에만 존재하고 자동/주문 발행 집합은 전부 미태그이며, STACK 다수가 시드 분포와 일치한다. 따라서 현행 태그 집합은 실제 지방·야적 모집단을 과소계상할 구조적 가능성이 높다.

이 판정은 배송주소 접두어나 17개 시도 문자열을 대체 정답으로 사용한 것이 아니다. 지방·야적 판정의 정식 수단은 각각 `delivery_tag='REGION'`, `delivery_tag='STACK'`이고, 여기서는 그 태그의 입력 완전성만 평가했다.

## 5. 창고 판정 기준 — 레거시와 현행

### 레거시 GAS

`tools/legacy-gas/가배차분류리스트/Code.js`는 업로드한 이카운트 행의 **`출고창고` 표시 문자열**을 읽는다. 창고 코드나 내부 식별자를 쓰지 않는다.

- 상일+초월 모드(1·6): `출고창고`에 `상일` 또는 `초월`이 포함되면 통과하고, 포함된 문자열에 따라 상일/초월 묶음에 넣는다.
- 초월 모드(2·7): `출고창고`에 `초월`이 포함되는지 판정한다.
- 상일 모드(3·8): `출고창고`에 `상일`이 포함되는지 판정한다.
- 야적 only(4), 지방 only(5): `출고창고`에 `상일` 또는 `초월`이 포함되는지 판정한다.
- 예외: 1~3·6~8 모드에서는 야적 표식 행을 일반 창고 검사보다 먼저 `recs_y`로 빼므로 그 야적 행은 `출고창고` 검사 없이 결과의 `<기존 야적>` 묶음에 들어간다.

별도 `tools/legacy-gas/지방가배차분류리스트/Code.js`는 창고로 행을 포함/제외하지 않는다. `출고창고` 값을 출력용 `창고`로 복사하면서 정확히 `삼성창고 (초월 무갑)`인 경우에만 `초월창고`로 이름을 정규화한다.

### 현행

현재 브랜치의 `PreClassifyService.warehouseAllowed()`가 의도한 기준도 창고 코드가 아닌 **`OutboundSlipSummary.warehouse` 표시 문자열**이다.

- 초월 전용은 `warehouse.contains("초월")`.
- 상일 전용은 `warehouse.contains("상일")`.
- 상일+초월·야적 only·지방 only는 둘 중 하나가 포함되는지 판정한다.
- 그러나 `warehouse`가 null/blank이면 보수적 fallback으로 **무조건 통과**시킨다.

실제 데이터 계약을 끝까지 추적하면 현행 창고 판정은 동작하지 않는다.

1. `SlipServiceClient`는 `/internal/slips/outbound` JSON의 `warehouse` 필드를 읽어 `OutboundSlipSummary.warehouse`에 넣도록 작성돼 있다.
2. 실제 slip-service의 `OutboundSlipResponse`에는 전표번호, 거래처코드/명, 일자, 배송 태그, 배송주소, 품목, 전화번호만 있고 `warehouse` 또는 창고명이 없다.
3. `SlipInternalController.findOutboundSlipsForDispatch()`는 이 DTO를 그대로 반환한다.
4. 따라서 실제 응답을 받은 `OutboundSlipSummary.warehouse`는 null이고 `warehouseAllowed()`의 blank fallback으로 모든 창고가 통과한다.

결론: **레거시는 이카운트 `출고창고` 이름 문자열을 기준으로 실제 분기했다. 현행도 이름 문자열 분기를 의도했지만 upstream 응답에 창고 필드가 없어 실질적으로는 창고 판정이 없다.** 특히 2·3·7·8번은 현재 실계약에서 초월/상일을 구분할 수 없다.
