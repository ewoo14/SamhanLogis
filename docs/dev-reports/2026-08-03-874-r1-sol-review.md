## 0. 최종 판정

**도달 가능한 결함 1건.**

레거시가 `SUB_INDOOR`로 분류하는 실제 Q형 싱글 구성품 8개 모델이 현재 `product_db`와 product-service 응답에서는 모두 `ACCESSORY`로 전달된다. 현행 `RiUsageDecision`은 `ACCESSORY`를 자기 `riUsage` 판정 대상으로 인정하지 않아 기존 단가 판정으로 빠진다. 그 결과 미소비 Q형 보조 실내기 `(used=0,total=1)`도 단가가 납품가와 같으면 레거시 `false`가 현행 `true`로 뒤집혀 일마감 화면에 `확인`으로 표시된다.

보고서가 표시한 별도 이탈, 즉 “실제 `SUB_INDOOR` kind가 들어왔을 때 미소비 SUB가 부속의 failed-main으로 전파되는가”도 값 역전을 재현했다. 다만 현재 활성 카탈로그에는 `SUB_INDOOR` kind가 0건이고 product-service의 구성품 enum/응답은 Q형을 `ACCESSORY`로 내보내므로, 그 합성 조합 자체는 현재 실사용 도달 결함으로 세지 않고 **미판정**으로 분리했다.

## 1. 관점 1 — 레거시 분기와 `SUB_INDOOR`

### 1.1 레거시 원문

직접 확인한 `tools/legacy-gas/일마감 프로그램/Code.js`의 의미는 다음처럼 두 집합이 다르다.

- `Code.js:494-496`: `INDOOR/OUTDOOR/SUB_INDOOR`가 있으면 `hasSingleMain=true`.
- `Code.js:697-700`: 부속의 실패 주 품목은 `INDOOR/OUTDOOR`만 포함하고 `SUB_INDOOR`는 제외.
- `Code.js:709-710`: `SUB_INDOOR` 자신의 `확인`은 자기 `riUsage.used === total`.

현행 `RiUsageDecision.java:59-60`은 세 의미를 하나의 `isMain()` 집합으로 합친다. 따라서 실제 `SUB_INDOOR` kind를 합성하면 미소비 SUB + 미소비 PANEL + `PANEL 단가==납품가` 조합에서 레거시는 PANEL을 가격 fallback으로 `true`, 현행은 SUB를 failed-main으로 세어 `false`로 만든다.

## 2. 도달 가능한 결함 #1 — 실제 Q형 `SUB_INDOOR`가 `ACCESSORY`라 자기 `riUsage`를 잃는다

### 파일:줄

- `tools/legacy-gas/일마감 프로그램/Code.js:198-203,709-710` — 12번째 문자가 `Q`인 AR 모델은 `SUB_INDOOR`; 자기 `riUsage` 완전소비 여부가 `확인`.

### 실 사용자가 하는 조작

1. 출고전표/견적에서 아래 활성 `SINGLE_SET` 부모 중 하나를 선택한다. slip-service의 `SlipService.java:142-143,155-188`은 BUNDLE을 product-service `/products/internal/expand`로 구성품 전개한다. Q형 구성품은 직접 노출 `usageScope=NONE`이어도 부모 세트 전개 자식으로 실제 전표에 들어간다.
2. DRAFT 전표에서 구성품 조합 또는 단가를 편집해 exact 세트 가격 매칭이 되지 않는 상태로 확정하고 매출회계전표/세금계산서로 반영한다. 이때 Q형 원본 행의 usage는 `(total=1, used=0)`이다.
3. 데스크톱 `/accounting/daily-closings`에서 해당 날짜와 판매 원천을 열어 `모델별 재검증`의 `확인` 열을 본다.

## 6. 관점 5 — `riUsage` 계승 완결성

세 사용 지점은 코드 구조상 모두 배선됐지만 의미 완결성은 실패했다.

| 레거시 사용 지점 | 현행 대응 | 판정 |
|---|---|---|
| `Code.js:694` 부속 자기 usage 완전소비 | `RiUsageDecision.java:48-51` | `PANEL/REMOTE/MATERIAL`에 대해 반영됨 |
| `Code.js:699` 실패 주 품목 usage | `RiUsageDecision.java:35-41,59-60` | 배선됐으나 SUB까지 포함해 레거시보다 넓음; 현재 실제 SUB kind 0이라 해당 역전은 미판정 |
| `Code.js:710` INDOOR/OUTDOOR/SUB_INDOOR 자기 usage | `RiUsageDecision.java:25-27,59-60` | INDOOR/OUTDOOR는 반영. 실제 Q형 SUB가 wire에서 ACCESSORY라 SUB 경로는 실데이터에서 도달하지 못해 결함 #1 발생 |

따라서 “세 줄에 해당하는 코드가 존재한다”는 의미에서는 3/3이지만, 실제 product-service 계약을 포함한 end-to-end 계승은 2/3이며 `Code.js:710`의 SUB 의미가 완결되지 않았다.

## 7. 이번 라운드에서 보지 못했거나 미판정으로 남긴 표면

- 공유 DB write 금지 때문에 Q형 구성품을 포함한 throwaway 출고전표→매출회계전표/세금계산서→실 HTTP→실 GUI 체인을 새로 만들지 않았다. 현재 `slip_db`의 해당 활성 라인은 0건이다. 결함 #1은 활성 실카탈로그와 컴파일된 production 판정 메서드로 재현했다.
- 현재 카탈로그에 없는 진짜 `kind=SUB_INDOOR` payload가 향후 들어오는 경우의 PANEL/REMOTE/MATERIAL 화면 결과는 CASE_A로 논리 역전까지 확인했지만, 현재 실 사용자 입력으로 만들 수 없어 미판정이다.
- 0·음수·소수 수량, 동일 모델/동일 단가가 여러 전표 scope에 걸쳐 일 단위 `AxisKey` 하나로 합쳐지는 조합은 이번 라운드에서 end-to-end 판정하지 않았다.
- PURCHASE 원천은 `MonthEndCloseService.java:328`에서 의도적으로 빈 set pool을 넘겨 이번 `riUsage` 기능이 적용되지 않는다. 그 매입 참고 판정의 기존 동작은 이번 질문의 판매 `riUsage` 사용자 경로로 재판정하지 않았다.
- accounting-service 전체 suite, Docker 이미지 재빌드, DB write/DDL은 지시대로 수행하지 않았다.
