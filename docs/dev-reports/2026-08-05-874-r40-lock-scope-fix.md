## ① 지시서 좌표별 조치

R38의 `SlipRepository.findByIdForCollabUpdate` 행 잠금 자체는 유지했다. 잠금은 필드별 baseline 비교와 mutation·감사·revision·ACCEPTED 이력을 한 transaction으로 직렬화하는 데 필요하다. 대신 `SlipCollabEditService.commitEdit`에서 잠금이 유지되는 transaction 안에는 외부 auth 조회와 notification POST가 들어가지 않도록 경계를 바꿨다.

- `services/slip-service/src/main/java/com/samhanair/logis/slip/collab/SlipCollabEditService.java:70-104`
  - mutation, ACCEPTED 이력 저장, 수신자 식별자 스냅샷은 기존 transaction 안에서 수행한다.
  - 실제 auth loginId resolve와 push는 `afterCommit`에서 application executor로 제출한다.
  - 커밋 전 executor 제출을 하지 않아 rollback된 변경의 알림이 생기지 않는다.
  - executor 제출 거부 시 커밋 후 현재 스레드에서 마지막 best-effort를 수행해 조용한 알림 누락을 피한다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/web/GlobalExceptionHandler.java:131-140`
  - JPA `LockTimeoutException`/`PessimisticLockException`과 Spring `PessimisticLockingFailureException`/`QueryTimeoutException`을 일반 500이 아닌 409로 매핑한다.
  - 예외 내부의 JDBC/Hibernate 메시지와 UUID는 응답에 싣지 않는다.
- `services/slip-service/src/test/java/com/samhanair/logis/slip/it/collab/SlipCollabIT.java:454-475`
  - transaction rollback 전에 알림이 발화하지 않는 회귀를 추가했다.
- `services/slip-service/src/test/java/com/samhanair/logis/slip/it/collab/SlipCollabIT.java:550-615`
  - 같은 전표의 실제 병렬 MockMvc 요청 2개를 별도 요청 스레드에서 실행한다.
  - 첫 요청의 auth login 조회와 notification push를 latch로 지연시킨 상태에서 둘째 요청이 다른 필드를 2초 안에 저장하는지 검증한다.
- `services/slip-service/src/test/java/com/samhanair/logis/slip/web/GlobalExceptionHandlerTest.java:69-90`
  - 잠금 timeout 예외군의 409 응답·중립 메시지·UUID 비노출을 고정했다.

잠금 query, JPA timeout 설정, 협업 baseline 비교, `expectedBefore`, revision/audit 생성 자체는 변경하지 않았다.

## ② 불변식 점검

1. **느린 부수효과 뒤 different-field 저장**: 첫 transaction은 commit 시점에 행 잠금을 해제하고, auth/notification은 별도 executor에서 실행한다. 둘째 요청은 첫 push가 끝날 때까지 기다리지 않고 최신 row를 기준으로 다른 필드를 병합한다.
2. **same-field stale 저장**: `PESSIMISTIC_WRITE`와 `expectedBefore` 비교를 유지했다. 최신 필드를 덮어쓰지 않고 기존 `SLIP_OPTIMISTIC_LOCK_CONFLICT` 409를 반환한다.
3. **different-field same-baseline 저장**: 두 요청 모두 동일한 저장 원자 구간에서 필드별 baseline을 비교하므로 순서와 무관하게 각 변경을 보존한다.
4. **잠금 실패/timeout 의미**: JPA/Spring 잠금 예외를 409와 재확인 안내로 매핑했다. 내부 예외 원문은 사용자에게 노출하지 않는다.
5. **성공 이력 정합성**: 전표 mutation, audit batch, EDIT revision, ACCEPTED suggestion은 기존 transaction 안에 그대로 남겼다. 알림 executor 작업은 이 저장 transaction의 결과를 변경하지 않는다.
6. **알림 실패·UUID 비공개**: 수신자 식별자와 본문은 commit 전 snapshot으로 한 번만 고정하고, 기존 `LinkedHashSet` dedup·self-skip·개별 push 예외 격리를 유지했다. 본문은 전표번호·수정자명·필드 요약만 사용한다.

### 반대급부 확인

- 알림 누락: afterCommit 이후에만 작업을 제출하고, executor 거부 시 커밋 후 fallback을 둔다.
- 중복/phantom 알림: 수신자 snapshot은 한 번만 만들고, `LinkedHashSet` dedup은 유지한다. rollback이면 afterCommit callback이 발화하지 않는다.
- 성공 이력 누락: 알림 작업은 transaction 밖이며 예외를 transaction으로 전파하지 않는다.
- 커밋되지 않은 변경의 알림: `TransactionSynchronization.afterCommit` 안에서만 executor를 호출한다.
- same-field lost update/different-field false 409: 저장 행 잠금과 필드별 `expectedBefore` 비교를 제거하지 않았다.
- 내부 UUID 노출: 기존 알림 본문과 409 응답의 UUID 비노출 계약을 유지했다.
