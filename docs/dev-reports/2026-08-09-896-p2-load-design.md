## 요약 — 새로 만드는 것 / 기존을 쓰는 것 / 버리는 것

### 먼저 확인한 상위 결론

개발책임자 발언 및 `2026-08-09-896-p1-mismatch-classification.md`와 이 보고서의 결론은 충돌하지 않는다.

- 세트, 세트 구성품, 스펙은 모두 기초품목 도메인 DB에 적재한다.
- 견적품목은 시트 행을 별도 품목 마스터로 복제하지 않고 기초품목을 참조한다.
- 비인상 탭과 `_단가인상` 탭을 모두 적재한다.
- 64개 `…RS` 세트에서 나온 83그룹은 업무 충돌 83개가 아니라 계산 순서 차이 하나다.
- 128개 본체 문맥의 세트 총액 차이는 0원이지만, 합격 관문은 총액이 아니다. `explodeSetParts()`가 실제 반환·인쇄하는 상세행이 골든과 같아야 한다.
- 따라서 64개 `…RS` 본체의 원시 셀값을 최종 구성품 단가로 적재하지 않는다. 고정부품을 먼저 차감한 뒤 6:4로 재계산한 반환값이 정본이다.

기존 P1 설계안 §5.2의 “83건 때문에 sheet 골든과 현행 계산이 충돌할 수 있다”와 §6.1의 A/B/C 선택 질문은 다음 날 확정된 P1 분류로 해소됐다. **현재 레거시 출력 재계산측이 정본이며 선택 질문은 0개**다. 이전 계획의 `83 → 0`도 원시 셀 일치가 아니라 `explodeSetParts()` 상세행 차이 0으로 읽어야 한다.

### 운영 값으로 버리는 것과 버리지 않는 것

- 중복 헤더의 **첫 번째 `납품가`**는 운영 가격 필드로 만들지 않는다. 현재 견적 출력은 마지막 `납품가`를 소비하며 첫 값의 업무 의미는 확정되지 않았다. 다만 원시 문자열·존재 여부·좌표는 `catalog_import_record`/불변 manifest에 보존하므로 증거를 삭제하지 않는다.
- `products.delivery_price`를 납품가 정본으로 읽는 경로는 버린다. 전환 기간에는 최신 가격 투영/cache로만 맞춰 두고, 모든 소비자가 `price_history.delivery_price`를 쓰면 물리 컬럼 정리는 별도 후속 판단으로 둔다.
- `products.purchase_price`와 HVAC 특화 단가 8종은 납품가와 같다고 추론해 합치지 않는다. 실측상 `purchase_price`와 `delivery_price`가 다른 활성 품목이 623건이며, 특화 단가에는 별도 주석과 소비 계약이 있다.
- `products.spec_text`, `products.specification`, `bundle_component.spec_text`를 무조건 한 열로 합치지 않는다. 모델 스펙 정본은 `product_spec`, 이카운트 규격은 `products.specification`, 관계 문맥 규격은 `bundle_component.spec_text`다. `products.spec_text`는 현행 주석대로 read-only fallback만 유지한다.

### 가격 컬럼 실측 — “납품가 하나”의 경계

`products`에는 금액 컬럼이 총 13갈래다.

1. `selling_price`
2. `purchase_price`
3. `release_price`
4. `delivery_price`
5. `unit_price_with_vat`
6. `inbound_price`
7. `outbound_price`
8. `single_price`
9. `outdoor_price`
10. `multi_50_price`
11. `multi_48_price`
12. `multi_45_price`
13. `item_35_price`

이 13개를 모두 “납품가”로 합치는 것은 금지한다. 스키마와 코드가 직접 납품가로 취급하는 물리 위치만 세면 현재 세 갈래다.

| 납품가 계열 | 현재 역할 | 통일 후 역할 |
|---|---|---|
| `products.purchase_price` | 공통 Product 생성 API에서 “납품가”라고 검증하지만 이카운트/매입 의미와 섞임 | #896 시트 납품가 원천으로 쓰지 않음. 별도 의미 유지 |
| `products.delivery_price` | 시트 기반 현재 대표 납품가, BundleExpander가 직접 읽음 | 최신값 투영만 유지하고 런타임 정본 읽기 금지 |
| `price_history.delivery_price` | 품목·효력일별 납품가 | **유일한 운영 정본** |

원천 시트에는 동일 헤더 `납품가`가 두 개 더 있다. 마지막 열만 현재 출력 가격이며 첫 열은 싱글 세트에서 읽고 버리고, 싱글 구성품에서는 값도 읽지 않는다. 따라서 운영 DB에는 한 값만 적재하고 첫 열은 원시 증거에만 둔다.

통일로 잃는 것과 보존하는 것은 다음과 같다.

- 잃는 것: `products.delivery_price`만 조회하면 최신가를 즉시 얻는 편의, 첫 번째 중복 납품가의 미확정 업무 의미.
- 보존하는 것: 첫 열 원문과 좌표, 비인상/인상 두 가격 벌, 과거일 조회, 세트 문맥 가중치·고정금액, 출고가, 이카운트·HVAC 특화 가격.
- 잃어서는 안 되는 것: `purchase_price`와 `delivery_price` 차이 623건, `selling_price`와 `release_price` 차이 1,563건. 이 차이는 의미 확인 없이 0으로 만들 대상이 아니다.

## (1) 적재 대상 — 무엇을 어디에 넣는가

### 1.1 세트 → 기초품목

세트 자체는 신규 세트 테이블을 만들지 않고 기존 `products`에 적재한다.

| 시트/정규화 값 | 착지점 | 신규 여부 | 규칙 |
|---|---|---|---|
| 세트 모델 | `products.model_code` | 기존 | 사용자용 업무키. UUID는 외부에 노출하지 않음 |
| 세트 품명 | `products.name`, `model_name` | 기존 | 동일 모델 충돌은 import record에 전후값 기록 |
| 세트 여부 | `products.product_type='BUNDLE'` | 기존 | 문자열/품명 추론을 런타임에 남기지 않음 |
| 전개 여부 | `products.bundle_mode='EXPAND'` | 기존 | 레거시처럼 구성행으로 출력하는 세트 |
| 단위 | `products.unit` | 기존 | 문맥별 표기가 다르면 exposure override 사용 |
| 대표 출고가·납품가 | `price_history.release_price/delivery_price` | 기존 | 비인상/인상을 유효일별 행으로 적재 |
| 규격·용량 | `product_spec` | 기존 | 구조화 가능한 값을 key/value/unit로 분리 |
| 비고 | `products.remark` 또는 exposure override | 기존/확장 | 모델 공통과 견적 문맥을 구분 |
| 견적 노출 | `product_estimate_exposure` | 기존 | 기초품목 FK 참조만 저장 |

`products.estimate_category`와 `products.display_order`는 V18 이후 deprecated이므로 신규 적재하지 않는다.

### 1.2 세트 구성품 → 기초품목

구성품은 두 층으로 적재한다.

1. 구성품 모델 자체는 `products`에 한 번만 존재한다.
2. 세트 안에서의 관계와 문맥은 `bundle_component`에 둔다.

| 데이터 | 착지점 | 상태 |
|---|---|---|
| 부모 세트 | `bundle_component.bundle_product_id` | 기존 |
| 구성품 모델 | `bundle_component.component_product_code` → `products.model_code` | 기존 |
| 수량/수량 모드 | `default_qty`, `qty_mode` | 기존 |
| 실내기/실외기/판넬/리모컨/자재/부속 | `component_kind` | 기존 |
| 특징/옵션 | `component_variant` | 기존 |
| 기본 선택 | `is_default` | 기존 |
| 표시 순서 | `display_order` | 기존 |
| 관계 문맥 규격 | `spec_text` | 기존 |
| 관계 문맥 품명·단위 | `display_name_override`, `unit_label_override` | 확장 필요 |
| 자동배분/고정금액 구분 | `allocation_mode` | 확장 필요 |
| 가격 벌별 가중치/고정금액 | `bundle_component_allocation_history` | 신규 필요 |

싱글 구성품의 마지막 `납품가`는 모델 전역 `products.delivery_price`로 평탄화하지 않는다. 같은 구성품이 세트별로 다른 값이면 다음처럼 저장한다.

- `WEIGHTED_BODY`: 원문 절대값을 최종 단가가 아니라 해당 가격 벌의 `allocation_weight`로 보존한다.
- `FIXED_COMPONENT`: 판넬·리모컨·자재·가정용 벽걸이처럼 반환값으로 유지되는 문맥 금액을 `fixed_allocation_amount`로 보존한다.
- 실내기와 실외기가 모두 있는 1+1 본체: 원문 절대값을 최종값으로 쓰지 않고 정책 계산 결과로 덮는다.

### 1.3 스펙 정보 → 기초품목

모델 공통 스펙의 정본은 기존 `product_spec`이다.

| 입력 종류 | 착지점 | 규칙 |
|---|---|---|
| 용량 | `product_spec(spec_key='용량', spec_value, unit='kW')` | 개발책임자 확정 단위 사용. 원문 키가 더 구체적이면 임의로 뭉개지 않음 |
| 규격 | 의미가 분리 가능한 경우 각각의 `product_spec` 행 | 쉼표 문자열 하나로 합쳐 정보 구조를 잃지 않음 |
| 출력용 단일 규격 문자열 | `product_estimate_exposure.spec_text_override` | 레거시 표시를 그대로 재현할 때만 사용 |
| 세트 관계별 규격 | `bundle_component.spec_text` | 모델 공통 스펙으로 승격하지 않음 |
| 이카운트 규격 | `products.specification` | 시트 규격과 같은 뜻이라고 추론하지 않음 |

P0 manifest의 스펙 실측은 카탈로그 2,735행 중 `capacity` 비어 있지 않음 2,735행/고유값 78, `spec` 1,995행/고유값 227, `note` 103행/고유값 35다. 적재 후 이 세 축의 원천 좌표 누락이 0이어야 한다.

### 1.4 시트 참조 → 견적품목

견적품목은 별도 복제 마스터가 아니라 `product_estimate_exposure`가 기초품목 `products.id`를 참조하는 구조를 유지한다.

| 견적 문맥 값 | 착지점 |
|---|---|
| 참조 품목 | `product_estimate_exposure.product_id` |
| HOME_MULTI/SINGLE_SET/COMMERCIAL_MULTI/LEGACY | `estimate_category` |
| 표시 순서 | `display_order` |
| 시트 문맥 품명 | `display_name_override` |
| 시트 문맥 단위 | `unit_label_override` |
| 용량 표시문 | `capacity_text_override` |
| 규격 표시문 | `spec_text_override` |
| 문맥 고정DC | `fixed_discount_rate_override` |
| 비고 | `note_override` |

견적품목 조회는 “exposure → product → product_spec/price_history” 순서로 조립한다. 시트 탭명·행 번호·원시 셀은 운영 응답에 넣지 않고 `catalog_import_record`에만 둔다.

## (2) 납품가 통일

### 권고안

**납품가의 단일 정본은 `price_history.delivery_price`다.** “하나”는 가격 벌을 버린다는 뜻이 아니라, 모든 가격 벌과 문맥이 동일한 금액 필드명을 사용하고 행 차원으로 구분된다는 뜻이다.

- 품목 대표가: `(product_id, effective_date) → delivery_price`
- 세트 내부 본체: 대표가에서 `bundle_allocation_policy`와 구성행 가중치로 계산
- 고정부품: `(bundle_component_id, effective_date) → fixed_allocation_amount`
- 현재가 편의: 필요하면 `products.delivery_price`에 최신 정본을 투영하되 소비자는 이를 정본으로 판단하지 않음

`fixed_allocation_amount`는 두 번째 납품가가 아니다. 세트 대표 납품가를 분해할 때 먼저 차감하고 그 구성품 상세행에 그대로 반환하는 **세트 문맥 배분 입력**이다.

### 대안과 대가

| 안 | 장점 | 대가 | 판정 |
|---|---|---|---|
| A. `price_history.delivery_price` 한 정본 + 행 버전 | 기존 이력 구조 재사용, 비인상/인상/과거일 공존, 중복 열 없음 | 모든 소비자가 기준일/가격 벌을 명시해야 함 | **권고** |
| B. `products.delivery_price`와 `price_history.delivery_price`를 둘 다 정본 | 변경량이 적음 | 0건이던 최신값 차이가 다시 생길 수 있고 “하나”를 위반 | 기각 |
| C. `base_delivery_price`, `increased_delivery_price` 두 컬럼 | 조회가 단순 | 세 번째 가격 벌부터 스키마 변경, 유효일·감사·토글 의미 중복 | 기각 |

## (3) 비율 계약

### 결정: 데이터 계약으로 둔다

6:4/4:6, 반올림, 잔차 처리는 코드 상수가 아니라 `bundle_allocation_policy` 행으로 저장한다. 코드는 저장된 정책을 해석하는 계산기만 제공한다.

| 컬럼 | 의미 |
|---|---|
| `bundle_product_id` | 정책 대상 세트 |
| `indoor_weight`, `outdoor_weight` | 가정용 6:4, 비가정 4:6 등 명시 비중 |
| `round_unit` | 레거시 1,000원 |
| `rounding_mode` | `HALF_UP` |
| `remainder_policy` | `LEGACY_OUTDOOR_ALIGN_LAST` |
| `effective_from` | 정책 효력 시작일 |

구성행에는 구조적 `allocation_mode`만 두고, 가격 벌에 따라 달라질 수 있는 값은 `bundle_component_allocation_history`에 둔다.

| 컬럼 | 의미 |
|---|---|
| `bundle_component_id` | 대상 관계행 |
| `effective_from` | 대응 가격 벌 시작점 |
| `allocation_weight` | `WEIGHTED_BODY` 그룹 내부 상대 가중치 |
| `fixed_allocation_amount` | `FIXED_COMPONENT` 문맥 고정금액 |

CHECK 계약은 mode별로 둘 중 하나만 허용한다. 정책 대상 세트는 모든 활성 구성행의 mode와 해당 가격 벌 입력이 완결돼야 활성화된다.

### 데이터로 두는 근거

1. Google 의존성을 없앤 뒤에도 품명 변경으로 6:4/4:6이 조용히 바뀌면 안 된다.
2. 64개 `…RS`의 정답은 “고정부품 선차감 후 6:4”라는 계산 순서까지 포함한다.
3. 복수 실내기/실외기는 가격 벌별 문맥값을 그룹 내부 가중치로 사용한다.
4. 정책·입력·효력일을 감사하고 되돌릴 수 있다.
5. 새로운 비율이나 반올림 정책이 생겨도 시트나 품명 정규식을 다시 넣지 않는다.

코드 규칙안은 컬럼 수가 적다는 장점이 있지만 세트별 예외와 이력, 설명 가능성, rollback을 잃으므로 기각한다.

## (4) `_단가인상`과 접미사 없는 탭을 모두 적재

### 결정: 별도 컬럼이 아니라 유효일별 별도 행

두 가격 집합은 `price_history`와 `bundle_component_allocation_history`에서 각각 별도 행으로 공존시킨다.

| 가격 집합 | 품목 가격 | 구성 문맥 입력 | 선택 계약 |
|---|---|---|---|
| 접미사 없음/인상 전 | `price_history`의 이전 효력 행 | allocation history의 이전 효력 행 | 견적 “인상 전 단가” 또는 주문 전환일 전 |
| `_단가인상`/인상 후 | `price_history`의 다음 효력 행 | allocation history의 다음 효력 행 | 견적 기본/토글 또는 주문 전환일 이후 |

명칭과 달리 `_단가인상`의 차이 30개에는 증가 8, 감소 22가 있으므로 `기존가 × 인상률`로 재계산하지 않는다. 시트의 실제 숫자를 그대로 별도 이력 행에 넣는다.

현행 날짜 역할은 합치지 않는다.

- `2000-01-01`: 인상 전 baseline 가격 행
- `2026-04-01`: 인상 후 가격 행
- `2026-07-01`: `price_change_schedule`의 앱 선택 전환일

앞의 두 날짜는 가격 레코드의 버전이고, 마지막 날짜는 주문 납기일/견적 기본 선택 규칙이다. 하나로 합치면 과거일 조회와 레거시 토글 출력이 달라진다.

### 대안과 대가

| 안 | 장점 | 대가 | 판정 |
|---|---|---|---|
| 유효일별 별도 행 | 기존 history/schedule 재사용, N개 가격 벌 확장 가능 | 선택 기준일을 모든 소비자가 전달해야 함 | **권고** |
| 같은 행의 별도 컬럼 | 읽기 단순 | 열 의미가 탭명에 결박되고 세 번째 벌에 취약 | 기각 |
| 가격 벌별 별도 테이블 | 격리 명확 | 조회·검증·관리 API 중복, “납품가 하나” 약화 | 기각 |

## (5) 합격 판정 — `explodeSetParts()` 상세행이 관문

### 5.1 비교 기준

기준선은 `docs/qa/896-p0-golden-manifest/`에 고정된 파일과 SHA다. 이관 과정에서 Google을 다시 읽어 새 정답을 만들지 않는다.

핵심 골든 규모:

- 카탈로그 2,735행
- 싱글 세트 226행
- 상업 세트 86행
- 구성품 특징 1,451행
- 가격 시나리오 5개
- 골든 JSON 6개

최우선 관문은 `golden/02-set-expansion.json`이다. DB 모드가 반환한 `explodeSetParts()` 결과를 세트/옵션별 결정적 순서로 정규화해 다음 필드를 전건 비교한다.

```text
setModel + 선택 옵션
  → model, name, kind, feature, isDefault,
    unit, quantity, unitPrice, subtotal, spec, 행 순서
```

합격값은 다음과 같다.

- 누락 상세행 0
- 추가 상세행 0
- 모델/특징/기본 여부/수량/순서 차이 0
- 구성품 단가 차이 0원
- 구성품 소계 차이 0원
- 세트 합계 차이 0원
- 전개 오류: 싱글 0/226, 상업 0/86

### 5.2 64개 `…RS` 전용 관문

64세트 × 실내·실외 본체 2행 = 128문맥을 별도 집계한다.

1. 골든의 `explodeSetParts()` 반환 상세행을 expected로 삼는다.
2. DB의 세트 대표 납품가에서 고정부품을 먼저 차감한다.
3. 잔액을 정책 6:4, 1,000원 `HALF_UP`, 레거시 잔차 규칙으로 배분한다.
4. 반환 본체 128행을 모델·단가·소계까지 exact compare한다.
5. 시트 원시 본체 셀과 다르다는 이유로 실패시키지 않는다.

128/128 세트 문맥의 총액 차이 0원만 확인하는 검사는 불충분하다. 실내기 `-x`, 실외기 `+x`가 상계돼도 인쇄 상세행은 틀릴 수 있기 때문이다.

### 5.3 단계별 자동 게이트

| 게이트 | 자동 검사 | 합격값 |
|---|---|---|
| G0 불변 입력 | manifest 레코드 4,186건과 저장 SHA 검증 | 누락/변조 0 |
| G1 적재 완전성 | 원천 좌표 → import record → 도메인 업무키 추적 | 고아/중복/미분류 0 |
| G2 스키마 정합 | FK, 활성 unique, BaseEntity, soft delete, mode CHECK | 위반 0 |
| G3 상세 전개 | `02-set-expansion` 전 필드 비교 | diff 0 |
| G4 옵션·수량 | `03`, `04` 전 필드 비교 | diff 0 |
| G5 가격 | `05-price-scenarios` 상세행·공급가·VAT·총액 비교 | diff 0 |
| G6 가격 벌 | `06-toggle-off-on` 변화 셀 집합과 전후 값 비교 | diff 0, 단순 건수 일치 불인정 |
| G7 전체 | 동일 serializer로 생성한 `01`~`06` SHA | 6/6 일치 |
| G8 무 Google | Google 자격증명/네트워크 없이 DB 모드 캡처 | Sheets 호출 0, 기능 실패 0 |

비교 출력이 잘릴 수 있으므로 diff 전건은 파일로 저장하고, exit code와 전체 레코드 수를 각각 확인한다. 파이프 뒤의 종료코드를 원 명령의 종료코드로 오인하지 않는다.

### 5.4 전환 금지 조건

다음 중 하나라도 있으면 소비자를 DB 이관 완료 상태로 전환하지 않는다.

- 상세행은 다르지만 세트 총액만 같음
- 64개 `…RS`에서 원시 셀을 최종 단가로 사용
- 비인상/인상 중 한 가격 벌만 적재
- 필수 가격 결측을 0원으로 대체
- `products.delivery_price`와 `price_history.delivery_price` 중 소비자마다 다른 값을 읽음
- Google 키가 없을 때 fallback으로 Sheets를 요구

## (6) 적재 순서와 되돌리기

### 6.1 적재 순서

1. **불변 입력 확인**
   P0 manifest와 골든 SHA를 검증한다. Google 재조회 결과를 합격 기준으로 만들지 않는다.
2. **배치 생성**
   `catalog_import_batch`를 `PREPARED`로 만들고 manifest SHA, 원천 파일 SHA, 코드 버전, 예상 건수를 고정한다.
3. **staging/journal 적재**
   `catalog_import_record`에 원시 문자열, 파싱값, 존재 여부, 탭·행·가격 벌, 업무키, 정규화 payload를 적재한다. 같은 배치 재실행은 변경 0이어야 한다.
4. **격리된 DB clone dry-run**
   운영 DB snapshot의 복제본에 아래 5~9단계를 적용하고 G0~G7을 먼저 통과시킨다. 실제 DB에는 아직 쓰지 않는다.
5. **품목 식별자와 마스터**
   기존 `products`를 업무키로 보완하고, 확정된 신규 모델만 생성한다. alias 판단 전 모델을 임의 병합하지 않는다.
6. **스펙과 견적 참조**
   `product_spec` 후 `product_estimate_exposure`와 문맥 override를 적재한다.
7. **세트 관계**
   부모/구성품 품목이 모두 존재한 뒤 `bundle_component`와 관계 override, `allocation_mode`를 적재한다.
8. **배분 정책과 가격 벌별 입력**
   `bundle_allocation_policy` 후 `bundle_component_allocation_history`를 적재한다. 64개 `…RS`는 원시 본체 셀이 아니라 재계산 계약으로 검증한다.
9. **가격**
   `price_history`에 비인상/인상 행을 적재하고 `price_change_schedule`은 기존 세 날짜 역할을 보존한다. 마지막 중복 납품가만 운영 값으로 승격한다.
10. **한 트랜잭션 승격**
    각 update 전에 `catalog_import_record.before_payload`를 기록하고, 도메인 변경을 한 트랜잭션으로 적용한다. SQL 불변식 실패 시 commit하지 않는다.
11. **commit 후 즉시 상세 parity**
    G3~G8을 실행한다. 모든 소비자 전환 및 Sheets 제거는 이 결과 뒤의 P6~P8 작업이다.
12. **배치 확정**
    6/6 SHA와 무 Google 게이트가 통과한 배치만 `VERIFIED`로 바꾼다.

가격을 마지막에 두는 이유는 품목·스펙·관계가 완결되기 전에 0원 fallback으로 “성공”하는 것을 막기 위해서다.

### 6.2 되돌리기

되돌리기는 Flyway 역실행이나 hard delete가 아니다.

1. 적재 전 product DB snapshot, 대상 테이블 활성행 SHA, 앱 이미지/설정 버전을 보존한다.
2. 신규 INSERT 행은 해당 batch actor/업무키로 찾아 reverse dependency 순서로 soft delete한다.
3. UPDATE 행은 `catalog_import_record.before_payload`의 정확한 이전값과 감사 필드를 복원한다.
4. 복원 순서는 가격/배분 이력 → 배분 정책 → 세트 관계 → 견적 노출 → 스펙 → 품목이다.
5. 신규 nullable 컬럼과 빈 신규 테이블은 남긴다. 적용된 Flyway를 삭제·수정·역실행하지 않는다.
6. rollback 후 적재 전 활성행 SHA와 G3~G7의 이전 기준을 다시 비교한다.
7. 성공 시 batch를 `ROLLED_BACK`, 실패 시 `ROLLBACK_FAILED`로 기록하고 신규 견적/주문 저장을 계속 차단한다.

P7 canary에서 금액 이상이 발견되면 앱만 또는 DB만 단독 복귀하지 않는다. 이전 앱 이미지와 이전 DB snapshot을 함께 사용한다. P8 이후에는 Google을 rollback 수단으로 사용하지 않는다.

### 6.3 멱등성

- 동일 `import_batch_id + source_tab + source_row + source_variant` 중복은 허용하지 않는다.
- 동일 manifest SHA의 `VERIFIED` 배치를 다시 실행하면 domain INSERT/UPDATE/DELETE가 모두 0이어야 한다.
- 업무키가 같은데 normalized payload가 다르면 자동 덮어쓰기하지 않고 conflict로 중단한다.
- 빈칸, 숫자 0, 열 부재는 서로 다른 상태로 보존한다.

## 개발책임자 판단이 필요한 질문

P1의 83그룹 정본에 대한 질문은 없다. 아래 두 항목만 실제 품목 식별/노출 상태를 바꾸므로 추론하지 않고 남긴다.

### 질문 1 — 시트 전용 모델 2쌍의 식별

대상: `AP110RNPPHH1 ↔ AP110RNPPBH1`, `PC6NUNK1N ↔ PC6NUNK1NW`.

| 선택지 | 대가 |
|---|---|
| A. 오타 alias로 기존 품목에 연결 | 중복 품목을 피하고 레거시 조회키를 보존. 단, 실제 별도 모델이면 재고·견적 식별이 합쳐짐 |
| B. 별도 기초품목으로 생성 | 원문 식별을 그대로 보존. 단, 실제 오타면 중복 품목과 관계가 생김 |

권고는 업무 확인 전 자동 선택하지 않는 것이다. 어느 쪽도 `explodeSetParts()` 출력키는 재현할 수 있으나 재고 식별 의미가 달라진다.

### 질문 2 — JHJ 14세트와 그룹명 4세트의 운영 노출

| 선택지 | 대가 |
|---|---|
| A. 일반 판매 BUNDLE로 적재·노출 | 시트 목록을 가장 직접적으로 재현. 계산용 중간키라면 사용자가 잘못 선택할 수 있음 |
| B. 기초품목/구성관계는 적재하되 견적 노출은 하지 않음 | 데이터는 모두 보존하면서 오선택을 막음. 현재 레거시 목록 노출과 차이가 날 수 있음 |
| C. 18건을 개별 분류 | 업무 의미가 가장 정확. P3/P4 착수 전에 결정표가 필요하고 시간이 듦 |

레거시 출력 parity만 보면 A, 업무 의미를 추론하지 않는 안전성은 C다. 개발책임자 판단 전에는 적재본에서 conflict 상태로 두고 활성 승격하지 않는다.

#### 🔑 개발책임자 정정 — 키 축

> 어짜피 UUID가 서버키이고, 거래처코드는 프론트용 키잖아.

⟹ `-` 나 비숫자 코드가 조인을 깨지 않는다. **중복이 0이라 코드는 매칭 키로 유효**하다.
적재는 **코드로 매칭해 UUID 로 저장**하고, **다시 돌려도 같은 결과**가 나와야 한다(멱등).

🚨 DC 고아 210건의 원인도 다시 읽어야 한다 — *"UUID 로 조인해서"* 가 아니라
**거래처가 재생성되며 UUID 가 바뀌었는데 재적재를 안 한 것**이다. 재적재가 멱등이면
같은 사고가 재발하지 않는다.
