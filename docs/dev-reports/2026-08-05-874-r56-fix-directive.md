# R56 2차 SOL 적대검증 → fix 지시서 — PR #1057 · 이슈 #874

최종 판정: **실 사용자 경로로 재현 가능한 결함 1건이 있다. 머지 비권고.**

R54의 30초 일시 장애 영구 누락은 닫혔다. 정상 수신자의 행은 24시간 안에서 재시도되고, 현재 백오프는
2·4·8·16·32초 뒤 60초 상한이므로 장애가 회복되면 같은 멱등 키로 다시 진입해 SENT로 수렴한다. 한 행은
24시간 경계 다음 실패까지 최대 약 1,445회 gateway를 시도하지만 행 자체를 추가 생성하지 않으며, 이번
읽기·좁은 테스트 범위에서 정상 알림의 재현 가능한 영구 차단으로 이어지는 경로는 확인되지 않았다.

반면 slip migration은 현재 DB V105와 열린 PR #1045의 V106·V107 사이를 건너뛰어 V108~V112를 먼저
적용할 수 있다. 이 순서가 한 번 실행되면 기본 `out-of-order=false`에서 뒤늦게 들어오는 V106·V107이
적용되지 않는다. 가배차 그룹 전송 대기와 레거시 원천창고 복구라는 다른 트랙의 실 사용자 경로가 코드와
DB 불일치로 차단된다. R54가 명시한 “#1045 V106·V107 선행” 조건을 R55가 배포 불변식으로 닫지 못했다.

재현 순서는 결정적이다.

```text

5. #1045 코드는 V106·V107 스키마/복구 상태를 전제로 실행하지만 DB에는 두 변경이 없다.
```

### 나머지 범위 대조

- 30초·수 분 장애: 5회 뒤에도 TERMINAL이 아니며 6번째 성공으로 SENT가 되는 좁은 회귀가 통과했다.
  24시간을 지난 다음 실패는 `GATEWAY_RETRY_LIMIT` TERMINAL로 유한 종결된다.
- 큐·워커: 실패 재시도는 같은 outbox 행을 갱신하므로 시도마다 행이 늘지 않는다. 백오프는 60초 상한이고
  한 행의 최대 호출 수는 약 1,445회다. 높은 호출량은 확인했으나 이번 범위에서 정상 사용자 알림의
  재현 가능한 영구 굶김으로 확정할 증거는 없어서 별도 결함으로 세지 않았다.
- 관리자 API: gateway의 `/admin/slip-collab-notifications/**` no-strip route에 `JwtAuthentication`이 있고,
  controller에는 `@RequirePermission(page="slip.collab-notifications", action=VIEW)`가 있다. MASTER는 서명된
  `X-Is-System-Master`로 bypass하고 그 외 계정은 동적 권한이 없으면 403이다.
- UUID 비공개: 응답 record는 `slipNo`, `reason`, `attempts` 세 필드뿐이다. entity/event/recipient UUID는
  response mapping에 들어가지 않는다.
- gateway 충돌: 신규 exact prefix는 `/admin/slips/**`, `/admin/dispatch-*`, `/admin/notifications/**`,
  `/admin/arologis/**`와 겹치지 않고 StripPrefix도 적용하지 않아 controller의 풀패스와 일치한다.
- R52·R53: null/blank 멱등 키는 NULL로 정규화되고, 동일 PENDING은 notification V10 lease claim 승자만
  gateway에 진입한다. 해석 불가/editor 자신과 24시간 초과 실패는 TERMINAL이며 scheduler 후보에서 빠진다.
- 첫 각도: 협업 저장 transaction은 outbox 저장까지만 포함하고 외부 호출은 afterCommit executor/scheduler가
  수행한다. notification 지연·실패와 executor 거부가 수정완료 저장을 rollback하거나 동기 대기시키지 않는다.
  기존 key 없는 PUSH 호출도 필드를 생략하므로 V9 CHECK에 막히지 않는다.

## ② 불변식 — 구현 수단 지시 금지

1. 현재 공유 DB 최고 V105에서 적용되는 이 PR은 아직 열린 다른 트랙의 V106·V107을 건너뛰어 Flyway 최고
   버전을 올리면 안 된다.
2. 어떤 PR의 배포 순서가 먼저이든 각 서비스의 모든 미적용 migration은 기본 `out-of-order=false`에서
   정확히 한 번 순차 적용되어야 한다.
3. 번호 충돌 회피를 위해 이미 적용된 migration을 수정하거나 checksum을 바꾸면 안 된다.
4. 마이그레이션 정합 복구가 협업 저장, 기존 PUSH, 24시간 재시도, terminal 관측, notification V8~V10을
   되돌리거나 지연시키면 안 된다.
5. terminal 조회는 인증과 동적 권한을 모두 거쳐야 하고 내부 UUID를 반환하면 안 된다.

## ③ 양방향 RED — 반대급부 필수

### RED-A — 되돌리면 안 되는 것

- 30초와 수 분의 일시 장애 뒤 같은 사건·수신자는 같은 멱등 키로 다시 시도되어 SENT에 도달한다.
- 해석 불가 수신자와 editor 자신은 vendor 0회로 TERMINAL, 24시간 초과 gateway 실패는 유한 TERMINAL이다.
- 동일 PENDING의 동시 요청·recovery에서 notification gateway 승자는 최대 1이다.
- key 없는 기존 PUSH는 NULL 의미로 정상 저장되고, nonblank 키는 보존된다.
- 협업 수정완료 저장은 auth/notification/vendor와 terminal 조회를 기다리지 않는다.
- terminal 응답은 전표번호·사유·시도 횟수만 노출하고 JWT 및 VIEW 권한 없이는 차단한다.
- **반대급부:** V106·V107 문제를 피하려고 Flyway `out-of-order=true`를 전역 허용하거나 이미 적용된 SQL을
  편집하여 다른 서비스/트랙의 migration 안전성을 낮추면 RED다.

### RED-B — 재발하면 안 되는 것

- 빈 DB가 아니라 **현재 운영 순서 V105**를 기준으로 #1057 migration 집합을 먼저 계산했을 때 V106·V107을
  건너뛴 채 V108 이상이 적용 가능한 상태면 RED다.
- #1057 선적용 뒤 #1045 파일을 추가했을 때 V106·V107이 `Ignored`/미적용으로 남으면 RED다.
- 반대 순서인 #1045 V106·V107 선적용 뒤 #1057 V108~V112가 순차 적용되지 않아도 RED다.
- migration 정리 뒤 30초 일시 장애가 다시 TERMINAL을 선점하거나 terminal 행이 vendor에 재진입하면 RED다.
- 관리자 API가 무인증으로 열리거나 UUID를 반환하거나, 권한 있는 MASTER조차 403/404가 되면 RED다.
- `/admin/slip-collab-notifications/terminal`이 다른 공유 gateway route로 전달되면 RED다.

## ④ 범위 밖

- FCM vendor 자체 dedupe/exactly-once와 실제 기기 도달률.
- 60초 상한/약 1,445회 정책의 운영 튜닝. 재현 가능한 정상 경로 차단은 확인하지 못했으므로 이번 결함 수에
  포함하지 않았다.
- 협업 알림 외 notification 재시도 정책 전면 재설계.
- 열린 PR #1045의 가배차 기능 내용 변경. 이 라운드는 migration 적용 가능성만 범위 안이다.
- Docker 재빌드·재배포·중지, 공유 DB 쓰기/Flyway 실제 적용, 실제 vendor 발송.
- 전체 Gradle/Playwright 게이트, accounting-service 실행·수정,
  `clients/desktop/playwright/874-riusage-real-qa.spec.ts` 변경.

안 본 범위: 실제 PostgreSQL에 V106~V112 적용, 운영 다중 replica 강제 종료, 실제 FCM, 전체 desktop/service
회귀, accounting-service 런타임·테스트, 관리자 terminal 화면의 별도 FE 존재 여부.
