## B·C 공통 경로 전수 확인

`source_warehouse_code_pending=true`를 실제 production 코드에서 만드는 경로는 다음 2개다.

| 생성 경로 | pending 표시 | 최초 처리 진입 | 현재 R12 전 처리 여부 |
|---|---|---|---|
| `SlipService.create`의 OUTBOUND 분기 | `Slip.markSourceWarehouseCodePending()` | `scheduleAfterCommit` → applicationTaskExecutor → `snapshot` | executor·scheduler 모두 처리하지만 claim 없음 |
| `MobilePartnerOrderService.createOrder` | `Slip.markSourceWarehouseCodePending()` | `scheduleAfterCommit` → applicationTaskExecutor → `snapshot` | executor·scheduler 모두 처리하지만 claim 없음 |

전수 sweep 결과 `markSourceWarehouseCodePending` 호출은 위 2곳뿐이다. `SlipPublishService`의 단일/병합 발행 2경로는 `setSourceWarehouseCode(req.warehouseCode())`로 code를 직접 저장하고, `EstimateToSlipConverter`·`SlipDuplicateService`는 pending을 세우지 않는다. 따라서 이 라운드에서 B·C의 저장 규약을 적용할 실제 pending 생성 경로는 2개이며, 두 경로 모두 공통 `WarehouseCodeSnapshotService`를 거친다. 테스트/seed의 `createOutbound` 직접 저장은 production 생성 경로로 세지 않았다.

### B·C fix

변경한 저장·처리 규약은 다음과 같다.

- V103에서 `source_warehouse_code_snapshot_status`(`NOT_REQUESTED/PENDING/PROCESSING/COMPLETED/ABANDONED`), 시도 횟수, 다음 시도 시각, claim 시각/token, 마지막 오류, 격리 시각을 추가했다. 기존 V102 pending row는 `PENDING`으로 승계하고, 기존 code 보유 row는 `COMPLETED`로 표시한다.
- 두 생성 경로(`SlipService.create` OUTBOUND, `MobilePartnerOrderService.createOrder`)는 기존 `markSourceWarehouseCodePending()`을 그대로 사용하고, domain method가 상태/초기 retry 시각을 함께 세운다. direct code 발행 경로는 `setSourceWarehouseCode()`가 `COMPLETED`로 정렬한다.
- scheduler 조회는 `PENDING && nextAttemptAt <= now` 또는 lease 만료 `PROCESSING`만 대상으로 하고 `nextAttemptAt, createdAt` 순으로 100건을 가져온다. backoff 중인 영구/일시 실패 row가 due 정상 row를 가리지 않는다.
- executor와 scheduler 모두 같은 atomic `claimWarehouseCodeSnapshot`을 통과해야 하며, claim token을 결과 저장/재큐잉/격리 시 재검증한다. HTTP 작업은 claim transaction 밖에 있고 결과만 `REQUIRES_NEW`로 저장한다.
- inventory 404(실 client의 `WarehouseNotFoundException`, 레거시 adapter의 `HTTP 404` 메시지)와 정상 응답의 code 없음은 `ABANDONED`로 격리하고 `last_error`/`abandoned_at`/ERROR log로 관측한다. timeout·5xx·network·재기동 예외는 `PENDING`으로 되돌리고 시도 횟수에 따른 지수 backoff(기본 30초, 최대 1시간)를 적용한다. 따라서 일시 장애를 `ABANDONED`로 오분류하지 않는다.
- PROCESSING claim은 30초 lease로 회수한다. inventory client read timeout은 3초이므로 정상 처리 시간이 lease를 넘지 않는다는 전제이며, stale worker는 결과 token 검증에서 무시된다.

## 이번 fix가 새로 만든 표면

제가 이번 수정으로 새로 만든 표면은 전표의 창고코드 snapshot 수명주기 상태(`PENDING → PROCESSING → COMPLETED/ABANDONED`), retry/lease 메타데이터와 V103 migration, 그리고 executor·scheduler가 공유하는 atomic claim API다. 이 표면 자체가 다음 결함을 만들지 않도록 Spring 생성자 선택, `Slip.@Version` 경합, 기존 두 pending 생성 경로, stale worker의 token 오염까지 통합 검증했다. 특히 snapshot 메타데이터는 전표 본문과 별도 bulk update로 저장해 비동기 처리가 기존 전표 저장을 깨지 않도록 했다.
