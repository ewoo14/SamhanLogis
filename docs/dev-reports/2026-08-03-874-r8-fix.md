## scope 축을 포함한 조합 전수 대조

`[DEV-SEED/단위 fixture]` 레거시 원문 `Code.js:494-496,688-712`를 다시 훑어 확인한 판정 축은 다음 6개다.

1. 판정 scope: 같은 invoice group/document scope인지, 서로 다른 scope인지.
2. scope 안 main 구성: `INDOOR/OUTDOOR` 존재, `SUB_INDOOR`만 존재, main 없음.
3. 주 품목 소비: 완전, 부분, 미소비.
4. 대상 kind: 주 품목, `PANEL/REMOTE/MATERIAL`, 그 밖.
5. 부속 대상 자신의 소비: 완전, 미완전.
6. 부속 fallback 단가: 단가 일치, 단가 불일치.

원문에는 이 밖에 별도 판정 축이 없다. `hasSingleMain` 존재 집합과 `hasFailedMain` 실패 집합은 main 구성 축 안의 서로 다른 집합이고, `currentZone`은 scope 내 main 존재에 따라 SINGLE 분기에 도달하는 조건이다.

| scope 조합 | scope 안 main | 대상 kind/소비 | 레거시 근거·결과 | 현행 결과 |
|---|---|---|---|---|
| 단일 scope | I/O 존재 | I/O 완전/미완전 | `Code.js:709-710` 자기 usage → `true/false` | `true/false` |
| 단일 scope | I/O 존재 | SUB 완전/미완전 | `Code.js:709-710` 자기 usage → `true/false` | `true/false` |
| 단일 scope | I/O 존재 | 부속 완전 | `Code.js:702-703` 자기 소비 우선 → `true` | `true` |
| 단일 scope | I/O 존재, I/O 완전 | 부속 미완전 | `Code.js:697-707` failed 없음 → 단가 fallback | `null` → 기존 단가 |
| 단일 scope | I/O 존재, I/O 부분/미소비 | 부속 미완전 | `Code.js:697-705` failed 있음 → `false` | `false` |

`[DEV-SEED/단위 fixture]` 각 행은 `RiUsageDecisionTest`의 main 3종, 단일 scope 3갈래, Q-only, main 없음, 그 밖 kind, 서로 다른 scope true+true fixture로 assertion했다. 서로 다른 scope의 rows를 한 `sawMain/failedMain` 집합으로 합치지 않고 scope별로 계산한다. 같은 scope 내부의 부속→main 교차 의존은 유지된다.

단가 축은 `null` 결과에서만 적용된다. `unitPrice == _deliveryPrice`면 기존 재검증의 `true`, 다르면 `false`가 유지되며 scope 결과 자체가 단가 비교를 대신하지 않는다.

## catalog 부재 fallback 전수 대조

`[DEV-SEED/단위 fixture]` catalog가 없을 때는 `LegacyModelKindClassifier.fallbackKind()`가 `Code.js:187-211`의 결과를 직접 반환한다. `PC* -> PANEL`, `AR-* -> REMOTE`, non-main `AC/AP/AF -> MATERIAL`, main 패턴 `AC/AP/AR/AF -> INDOOR/OUTDOOR/SUB_INDOOR`를 테스트했다. catalog가 구체 kind를 주는 경우에는 기존 `riUsageKind()` 경계로 재분류하지 않는다.

`[실데이터/로컬 read-only]` R7 fresh sweep의 활성 구체 catalog 모집단은 AP `INDOOR` 40모델/42 links, AP `OUTDOOR` 11모델/14 links, PC `PANEL` 16모델/250 links였다. 이 구체 kind의 effective 변경은 0모델/0links다. catalog 부재 fallback 자체는 현재 DB 전표 모델 보유 행 0건에서 실제 화면 행 변경을 관측하지 못했다.
