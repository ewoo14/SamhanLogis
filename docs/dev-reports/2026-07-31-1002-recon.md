# Issue #1002 정찰 보고서 — 입금보고서 거래처 재지정·입금액 분할

> 조사일: 2026-07-31  
> 범위: 현행 소스·마이그레이션·화면·API·기존 결정의 읽기 전용 조사  
> 결론: 구현하지 않았으며, 이 문서 외 파일은 생성·수정하지 않았다.

## 0. 조사 기준과 제한

- `gh issue view 1002`로 이슈 원문을 확인했다. 이슈의 정본 요구는 “입금보고서는 결재문서가 아니라 한 입금을 거래처·계정에 배분하는 그룹”이며, 거래처 재지정·금액 분할·합계 보존·원자 처리·변경 이력을 요구한다.
- 요청된 메모리 `.claude/memory/project_partner_ledger_and_cash_receipt.md`는 존재하며 정독했다. 결재 흐름을 붙이지 않는다는 결정은 해당 파일 `:10-16`, 거래처 재지정·분할은 `:18-27`, 용어는 `:49-53`에 명시되어 있다.
- 현행 구조 판단은 단순 문자열 검색 0건에 기대지 않았다. 실제 엔티티, DDL, 요청/응답 DTO, 서비스, 컨트롤러, 데스크톱 폼·라우트를 서로 대조했다.
- Docker, 서비스, 공유 DB에는 접근하지 않았다. 따라서 운영 데이터 건수나 실제 배포 DB의 마이그레이션 적용 상태는 **확인하지 못함**이다. 아래 “현재”는 이 워크트리 소스의 현재 계약을 뜻한다.
- 회사 PC 로컬 전용 시드 CSV는 이 워크트리에 없다. 메모리에는 `docs/migration/ecount-data/raw/입금보고서-Excel다운로드(20260501~20260519_1).csv`가 git 비추적 파일이라고 기록되어 있으나(`.claude/memory/project_partner_ledger_and_cash_receipt.md:77-85`), 워크트리 전체 파일명 재귀 조회에서도 찾지 못했다. 따라서 CSV 헤더와 현행 DTO의 열 단위 비교는 **확인하지 못함**이다.

## 1. 요약 결론

1. 현행 `CashReceipt`는 **보고서 1건 = 거래처 1곳 + 금액 1개 + 차변 계정 1개 + 대변 계정 1개**인 단일 헤더 모델이다. 분할 행 모델은 없다.
2. 거래처 재지정은 완전히 없는 기능이 아니다.
   - `MANUAL_RECEIPT`/`DEPOSIT_REPORT`의 `DRAFT`는 단순 수정할 수 있다.
   - 같은 종류의 `CONFIRMED`는 기존 분개 역분개 후 신규 분개 재게시로 수정할 수 있다.
   - `BANK_LINKED`는 상태와 무관하게 PATCH가 409로 막혀 있어 취소 후 재생성만 가능하다.
3. 입금액 분할은 엔티티·DDL·DTO·API·화면 모두에서 지원하지 않는다. 은행 화면은 오히려 “동일 거래처의 통장거래 N건을 입금보고서 1건으로 합산”하는 반대 방향의 기능이다.
4. 회계 잔액은 `POSTED + REVERSED`를 함께 집계하므로 역분개·재게시 뒤 순잔액은 맞도록 설계돼 있다. 다만 과거 거래처의 원분개와 역분개 행, 총수금 같은 총유량은 이력으로 남는다. “재지정 후 과거 거래처 원장에 정정 이력을 보일지, 현재 배분만 보일지”는 기존 결정만으로 확정할 수 없다.
5. 최신 “결재문서 아님” 결정과 달리 `AccountingLockPolicies.CASH_RECEIPT`에는 `CONFIRMED = LOCKED_REQUIRES_APPROVAL` 잔재가 있다. 현행 입금보고서 수정 경로에서 이 정책은 소비되지 않지만, 결정과 코드 표현은 충돌한다.
6. 가장 안전한 구현 단위는 **한 보고서 헤더 + 복수 배분 행**이다. 은행 원천 총액을 헤더 불변값으로 보존하고 배분 합계를 원자적으로 맞춰야 한다. 단, 회계 라인 구성과 통장거래의 단일 `matchedPartnerId` 의미는 구현 전에 개발책임자 결정이 필요하다.

### 2.2 API와 상태별 동작

입금보고서 기본 경로는 `/accounting/cash-receipts`다(`CashReceiptController.java:43-51`). 현재 엔드포인트는 다음과 같다.

| 동작 | API | 현재 동작과 경계 | 파일:행 근거 |
|---|---|---|---|
| 수기 생성 | `POST /accounting/cash-receipts` | 단일 거래처·금액의 `DRAFT` 생성, 분개 없음 | `CashReceiptController.java:53-61` |
| 통장거래로 생성 | `POST /accounting/cash-receipts/from-bank-transactions` | 동일 거래처로 매칭된 통장거래 N건을 합산해 `BANK_LINKED` 1건 생성 후 즉시 확정 | `CashReceiptController.java:63-87`, `BankDepositReceiptService.java:37-98` |
| 조회 | `GET /accounting/cash-receipts`, `GET /{id}` | 거래처·기간·상태·종류 필터 및 상세 | `CashReceiptController.java:89-114` |
| 수정 | `PATCH /accounting/cash-receipts/{id}` | `DRAFT` 단순 수정, 일반 `CONFIRMED` 역분개·재게시, `BANK_LINKED`/`CANCELLED` 409 | `CashReceiptController.java:116-139`, `CashReceiptService.java:123-167`, `:231-260` |
| 확정 | `POST /{id}/confirm` | 열린 기간에서 `POSTED` 분개 게시 | `CashReceiptController.java:141-157`, `CashReceiptService.java:170-185` |
| 취소 | `POST /{id}/cancel` | 원분개 역분개 후 `CANCELLED`; 은행 연결이면 통장거래를 `UNREFLECTED`로 원복 | `CashReceiptController.java:159-179`, `CashReceiptService.java:188-212` |

요청 DTO도 `partnerCode`/`bizNo`/`partnerName` 중 하나, `amount` 하나, 일자·메모·차·대변 계정 하나만 받는다(`services/accounting-service/src/main/java/com/samhanair/logis/accounting/web/dto/CashReceiptRequest.java:10-36`). 배열이나 배분 행은 없다.

권한은 페이지 코드 `accounting.cash-receipts`의 동적 CREATE/UPDATE/VIEW/DELETE로 검사한다. 기본 시드는 MASTER, MANAGER, ACCOUNTANT에 VIEW와 편집 권한을 준다(`services/auth-service/src/main/resources/db/migration/V80__seed_accounting_cash_receipts_page_permission.sql:1-31`, `:33-67`). 결재 권한이나 결재선 API는 입금보고서 컨트롤러에 없다.

### 2.3 통장거래 모델과 생성 흐름

- 통장거래 API는 CSV import, 목록, 미반영 건의 거래처 지정·해제를 제공한다: `services/accounting-service/src/main/java/com/samhanair/logis/accounting/web/BankTransactionController.java:39-94`, `:124-147`.
- `BankTransaction`은 `matchedPartnerId`, `matchedJournalId`, `cashReceiptId`를 각각 한 개씩 가진다. 거래처 재지정은 `UNREFLECTED`에서만 가능하고 `REFLECTED`/`FORCED`는 409다: `services/accounting-service/src/main/java/com/samhanair/logis/accounting/domain/BankTransaction.java:177-230`, `:249-310`.
- 은행 기반 생성 서비스는 선택 건의 첫 `matchedPartnerId`를 보고서 거래처로 삼고 금액을 합산한다. 모두 `UNREFLECTED`, 입금, 양수, 동일 거래처여야 한다: `BankDepositReceiptService.java:53-79`, `:121-156`.
- 분개 게시 후 `UNREFLECTED + 동일 matchedPartnerId` 조건부 UPDATE로 모든 통장거래를 같은 보고서·분개에 연결한다. 한 건이라도 경쟁 변경되면 예외로 전체 트랜잭션을 롤백한다: `BankDepositReceiptService.java:87-98`, `:159-185`.
- 취소 때는 연결된 통장거래의 상태와 `matchedJournalId`·`cashReceiptId`만 원복하고, 거래처 매칭 자체는 보존한다: `BankTransaction.java:275-284`.

즉, 현재 원천 관계는 “통장거래 N건 → 동일 거래처 입금보고서 1건”이다. Issue #1002가 요구하는 “입금 원천 1건 또는 한 그룹 → 거래처·계정 N개 배분”을 표현할 수 없다.

## 3. 요구와의 격차

### 3.1 거래처 재지정

| 상태/종류 | 현재 가능 여부 | 이미 있는 것 | 없는 것·막힌 것 |
|---|---|---|---|
| 일반 `DRAFT` | 가능 | 단일 거래처를 다른 거래처로 교체, 아직 분개가 없어 원장 영향 없음 | 복수 거래처 배분, 변경 전·후 행 단위 이력 |
| 일반 `CONFIRMED` | 부분 가능 | 기존 분개를 역분개하고 새 거래처로 재게시. 새 일자와 원분개 일자가 모두 열린 기간이어야 함 | 배분 단위 재지정, 전용 변경 이력 API, 재지정 결과를 “현재 배분”으로 보여주는 원장 투영 |
| `BANK_LINKED` | 불가 | 취소하면 통장거래를 미반영으로 되돌려 재생성 가능 | 직접 PATCH가 선행 409. 원천 입금 총액·통장 링크를 유지한 채 거래처만 고치는 명령이 없음 |
| 통장거래 자체 `UNREFLECTED` | 가능 | 회계 반영 전 `matchedPartnerId` 덮어쓰기 | 반영 후 재지정 불가. 복수 배분을 표현할 수 없는 단일 `matchedPartnerId` |
| `CANCELLED` | 불가 | 종결 상태 | 재활성화·수정 경로 없음. 이 상태는 유지하는 것이 기존 결정과 일치 |

핵심 격차는 “재지정 기능 자체의 부재”가 아니라 **은행 연결 보고서의 직접 정정 부재와 단일 거래처 모델**이다. 일반 확정 건의 재지정은 이미 작동하는 경로가 있으므로 새 구현이 이를 중복하거나 우회해서는 안 된다.

### 3.2 입금액 분할 등록

| 계층 | 현재 | 요구 대비 격차 |
|---|---|---|
| 엔티티·DDL | 헤더 `partnerId`·`amount` 단일 값 | 배분 행, 행 순번, 행별 거래처·금액·대변 계정·메모, 원천 총액 불변값이 없음 |
| 요청·응답 DTO | 단일 거래처·금액 | `allocations[]` 또는 동등한 복수 행 계약과 합계 차이 응답이 없음 |
| 서비스 | 한 금액으로 차변 1줄·대변 1줄 생성 | 행 합계 = 원천 입금액, 행별 양수, 중복·동시수정, 전부 성공/전부 실패 규칙이 없음 |
| 통장 연계 | N건 금액을 합산해 거래처 1곳의 보고서 1건 생성 | 원천 통장거래 합계와 배분 합계를 묶는 불변식, 단일 `matchedPartnerId`의 새 의미가 없음 |
| 화면 | 거래처·금액 입력 각 1개 | 행 추가·삭제·복사, 거래처별 배분, 실시간 합계·차액, 오류 행 표시가 없음 |
| 감사 | 최신 수정자·수정시각과 분개 체인만 존재 | 누가 어느 배분 행을 무엇에서 무엇으로 바꿨는지 조회하는 이력이 없음 |

분할을 `CashReceipt` 여러 건으로 단순 복제하는 방식은 현재 `bank_transaction.cash_receipt_id`가 하나뿐인 관계와 충돌한다. 또한 “원천 한 건의 합계”라는 업무 정체성이 사라진다. 따라서 보고서 헤더를 그룹으로 유지하고 자식 배분 행을 두는 방향이 현재 요구에 가장 자연스럽다. 이는 정찰 제안이며 확정 설계는 아니다.

## 4. 회계 무결성 경계

### 4.1 현행 반영 경로

```text
통장거래(선택·거래처 매칭)
  → CashReceipt(단일 거래처·금액, DRAFT)
  → CONFIRMED
  → Journal(CASH_RECEIPT, POSTED)
  → JournalLine 2개
       차변: 입금 계정(기본 102)  +금액, 같은 partnerId
       대변: 외상매출금(기본 110) +금액, 같은 partnerId
  → 거래처 원장·일반 원장·매출/수금 집계·채권 잔액·aging snapshot
```

실제 분개 조립은 `CashReceiptService.java:290-310`이다. 차변·대변 두 라인 모두 같은 `partnerId`를 가진다. 자동 분개는 `CASH_RECEIPT` 출처와 보고서 전용 링크를 기록한다(`JournalService.java:195-217`). 입금보고서 분개를 분개장에서 직접 역분개하는 것은 막고 원천 입금보고서의 취소·수정을 거치게 한다(`JournalService.java:148-155`).

### 4.2 확정 건 편집 시 연쇄 변경

일반 `CONFIRMED` 편집은 다음을 한 트랜잭션 안에서 수행한다.

1. 새 거래일이 열린 기간인지 확인한다.
2. 기존 분개 일자가 열린 기간인지 확인한다.
3. `CashReceipt`의 거래처·금액·일자·계정을 새 값으로 교체한다.
4. 기존 `POSTED` 분개를 `REVERSED`로 표시하고 차·대변을 바꾼 신규 `POSTED` 역분개를 만든다.
5. 새 값으로 `POSTED` 분개를 만들고 `CashReceipt.journalId`를 최신 분개로 교체한다.
6. 커밋 후 aging materialized view 갱신을 시도한다.

근거는 `CashReceiptService.java:231-260`, `JournalService.java:220-254`다. 연쇄 편집의 전체 분개 계보는 `journals.cash_receipt_id`로 유지되지만, 입금보고서 응답은 현재 분개 번호와 취소 역분개 번호 중심이라 편집 전·후 배분 이력을 완전하게 보여주지 못한다.

### 4.3 값별 영향

| 편집 항목 | 직접 바뀌는 값 | 연쇄 영향 |
|---|---|---|
| 거래처 A → B, 금액·계정·일자 동일 | 새 분개 라인의 `partnerId` | A의 기존 효과는 역분개로 순상쇄되고 B에 현금성 계정 차변·외상매출금 대변이 생긴다. 회사 전체 현금·외상매출금 순액은 동일하지만 거래처별 채권 잔액과 원장 귀속이 이동한다. |
| 금액 X → Y | `CashReceipt.amount`, 새 분개 차·대변 | 현금성 계정 순액은 `Y`, 외상매출금 순감은 `Y`가 된다. 은행 원천과 연결된 건에서 이를 자유롭게 허용하면 실제 입금액과 회계 금액이 달라지므로 원천 합계 불변식이 필수다. |
| 한 금액을 B/C로 분할 | 현행 표현 불가 | 구현 시 B/C별 현금성 계정·외상매출금 라인이 생기고 각 거래처의 수금·채권 잔액이 배분액만큼 이동해야 한다. 회사 전체 합계는 배분 총액이 원천 총액과 같을 때만 보존된다. |
| 거래일 변경 | 새 분개 일자 | 기간별 원장·aging 기준일·마감 집계 귀속이 달라진다. 원분개 기간과 새 기간 모두 열려야 한다. |
| 차·대변 계정 변경 | 새 라인의 `accountCode` | 현금/예금 계정별 잔액, 외상매출금이 아닌 다른 상대계정의 잔액, 자금·재무 보고서가 바뀐다. 비말단 계정은 현재 검증으로 거부된다. |
| 메모 변경 | 새 라인 메모·분개 적요 | 금액은 변하지 않지만 원장 표시와 감사 식별 문구가 바뀐다. |

### 4.4 원장·채권 잔액이 정확해지는 방식과 남는 위험

- 거래처 원장 상세는 `partnerId`의 `POSTED + REVERSED` 분개 라인을 시간순으로 직접 읽는다: `JournalLineRepository.java:93-108`, `LedgerImageService.java:53-99`.
- 거래처별 매출·수금 집계는 계정 110의 차변을 채권 발생, 대변을 수금으로 집계하고 잔액은 차변-대변으로 계산한다: `SalesAggregateService.java:24-29`, `:78-103`, `:130-135`.
- 거래처별 채권 잔액도 계정 110의 `POSTED + REVERSED`를 직접 집계한다: `PartnerAgingService.java:95-105`, `JournalLineRepository.java:133-156`.
- materialized view 역시 원분개 `REVERSED`와 역분개 `POSTED`를 함께 포함해 `net_receivable`, `net_cash`가 상쇄되게 한다: `V52__aging_snapshot_include_reversed.sql:1-9`, `:19-58`.

따라서 순잔액은 정정 후 값으로 맞는다. 그러나 두 가지 위험이 남는다.

1. **총유량과 이력 표시**: 기존 결정은 취소·수정 왕복을 총유량에서 제거하지 않는다(`V52__aging_snapshot_include_reversed.sql:8-9`). 거래처 A에서 B로 재지정하면 A의 순채권은 원복되지만 A의 과거 수금 원분개와 역분개는 원장에 남고, 총수금 같은 총유량에도 원래 신용액이 남을 수 있다. Issue 문구의 “거래처 원장 수금 행 갱신”이 과거 행 보존인지 현재 배분만 표시인지 **확인하지 못함**이다.
2. **스냅샷 지연**: materialized view 갱신은 커밋 후 실행되며 실패를 경고만 남기고 업무 처리는 성공으로 유지한다(`CashReceiptService.java:633-652`). 직접 조회형 원장·채권 보고서는 새 분개를 보지만, 이 view 소비처는 갱신 실패 시 일시적으로 오래된 수치를 볼 수 있다.

### 4.5 마감 기간 잠금

- 새 거래일이 마감 기간이면 확정·재게시를 409로 막는다: `CashReceiptService.java:281-287`.
- 기존 분개 일자가 마감 기간이면 역분개 자체를 409로 막는다. 새 일자가 열려 있어도 기존 기간이 닫혀 있으면 편집할 수 없다: `JournalService.java:270-297`.
- 마감은 DAILY 동일 일자 또는 MONTHLY 동일 월을 검사한다: `MonthEndCloseService.java:521-551`.
- 정정하려면 먼저 역마감해야 하며, 기존 서비스 문서상 역마감은 MASTER 경계다: `MonthEndCloseService.java:61-66`, `:127-134`.

이 경계는 분할 구현에서도 그대로 재사용해야 한다. 일부 배분 행만 성공하거나 역분개 후 새 게시가 실패하는 중간 상태는 허용할 수 없다.

### 4.6 동시성·감사 경계

- `CashReceipt` 헤더에는 `@Version` 낙관 잠금이 있다(`CashReceipt.java:82-84`). 자식 배분 행이 생기면 헤더 버전과 행 변경을 하나의 버전 계약으로 묶어야 한다.
- 통장거래 기반 생성은 조건부 UPDATE 실패 시 전체 롤백하는 선례가 있다(`BankDepositReceiptService.java:159-185`). 분할 편집도 입금보고서·배분 행·분개·통장 연결·감사 이력이 한 트랜잭션에서 원자적으로 바뀌어야 한다.
- `BaseEntity`는 생성/최종수정/soft delete의 사용자·시각만 보존한다(`shared/common/src/main/java/com/samhanair/logis/common/entity/BaseEntity.java:14-59`). 이것만으로는 “A의 100만원을 B 60만원/C 40만원으로 바꾼 사람과 전후 값”을 재구성할 수 없다.
- 확인한 `CashReceipt` 엔티티·컨트롤러·응답·화면에는 입금보고서 전용 변경 이력 테이블, 조회 API, 이력 UI가 없다. 분개 체인은 회계 수치 정정은 증명하지만 업무 배분 전후를 완전하게 증명하지 못한다.

## 6. 구현 전 결정이 필요한 사항

다음은 정찰로 확정할 수 없어 임의로 정하지 않는다.

1. **통장거래 `matchedPartnerId`의 의미**: 현재는 입금보고서의 단일 거래처와 동일하다. 분할 후에도 “입금자 식별 거래처”로 하나를 유지할지, 배분 거래처를 나타내는 필드로 폐기할지 결정이 필요하다.
2. **분할 분개 구성**: 배분 행마다 차변·대변 한 쌍을 만들지, 입금 계정 차변은 원천별로 묶고 대변만 거래처별로 나눌지 결정이 필요하다. 현재 거래처 원장은 두 라인 모두의 `partnerId`를 읽으므로 선택에 따라 표시가 달라진다.
3. **원장 정정 표시**: 과거 거래처의 원분개·역분개를 감사 이력으로 계속 노출할지, “현재 배분” 별도 투영을 제공할지 결정이 필요하다. 회계 원장은 삭제하면 안 되므로 현재 배분만 보여주려면 별도 읽기 모델이 필요하다.
4. **배분 가능한 필드**: 최소한 거래처·금액·대변 계정은 행별이어야 한다. 입금 계정, 수수료, 부서, 프로젝트, 추가정보도 행별인지 헤더 공통인지 시드 CSV 확인 후 확정해야 한다. CSV가 없어 이번 정찰에서는 확인하지 못했다.
5. **스냅샷 일관성 수준**: 커밋 성공 후 materialized view 갱신 실패를 허용하는 현행 eventual consistency를 유지할지, 재시도·모니터링 또는 동기 보장을 추가할지 결정이 필요하다.

## 7. 슬라이스 제안

## 8. 권장 검증 행렬

구현 라운드에서 최소한 다음 케이스를 자동화해야 한다. 이번 정찰에서는 테스트를 실행하지 않았다.

- 일반 `DRAFT`: A 100 → B 60/C 40, 합계 부족·초과·0원·음수 거부, 낙관 잠금 충돌
- 일반 `CONFIRMED`: A 100 → B 60/C 40 후 A 순채권 원복, B/C 수금·채권 반영, 회사 전체 차변=대변
- 같은 거래처 내 계정 분할, 여러 거래처 분할, 거래일·계정 변경 조합
- 원분개 기간 마감, 새 거래일 기간 마감, 역마감 후 재시도
- `BANK_LINKED`: 통장 원천 100 = 배분 100, 99/101 거부, 중간 경쟁 변경 시 보고서·분개·통장 링크·이력 모두 롤백

- materialized view 갱신 성공·실패 시 직접 조회와 스냅샷 소비처의 기대 일관성
