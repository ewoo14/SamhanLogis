### 2.1 화면은 있으나 현재 직접 원천이 0인 표면

현재 DB에서 “사용자 화면은 있으나 직접 원천 행이 0”인 것은 다음이다.

- 협업 edit: `#1, #2, #3` — 각 comments/suggestions가 모두 0행이다.
- common audit: `#7, #8, #9, #10, #11, #13` — 각각 직접 대상 audit 매칭 또는 table이 0행이다. 단 `#11`, `#13`은 정적 recorder 호출자가 있어 writer 단절로 확정하지 않는다.
- snapshot/save history: `#18, #20, #22, #23` — 각각 `quote_snapshots 0`, `PARTNER_LEDGER 0`, `dps_save_history 0`이다.

이 목록은 “화면을 없애자”는 결론이 아니다. 특히 `#7~#10`은 writer/endpoint를 함께 판단해야 하고, `#11/#13/#18/#20/#22/#23`은 실제 사용자 동작이 현재 DB에 없었는지, 기록 조건이 다른지, 화면이 다른 원천을 써야 하는지부터 확인해야 한다.

## 3. 이 트랙의 책임 경계

### 3.1 모달 UI만으로 닫히는 표면: `#4, #14, #17` (3개)

이 세 표면은 데이터와 조회 경로가 이미 있고, 사용자에게 이력 모달이 이미 있다.

- `#4`는 전표 상세의 field audit Overlay와 #1104 full revision 패널이 함께 있다. PR #1131이 같은 파일을 수정하므로 새 outer modal을 추가하지 않는다.
- `#14`는 accounting audit 28행/4 entity를 backend service가 HistoryTable 형태로 derive하며, 이미 DS Modal을 사용한다.
- `#17`은 역할 변경의 의미가 명확한 별도 모달이고 실제 3행이 있다. 문서 revision 모달로 합치지 않는다.

이 분류는 “아무 작업도 필요 없다”는 뜻이 아니라, #1091의 새 `버전이력` outer modal을 추가할 이유가 없다는 뜻이다. 정렬·접근성·빈 상태 정합성만 별도 검토 대상이다.

### 3.2 endpoint 신설: `#5, #6` (2개)

`createAuditApi.ts:99-102`가 이미 `GET /accounting/tax-invoices/{id}/audit-logs`와 기존 envelope/flat row adapter를 정의한다. accounting DB에는 실제 세금계산서 매칭 2행/1 entity가 있다. 따라서 이 계열은 writer나 migration이 아니라 backend 조회 경로만 닫으면 두 FE 표면이 동시에 실제 데이터를 받을 수 있다.

반대로 `#8~#10`은 closing 대상 매칭 0행이므로 endpoint만 만들면 빈 결과만 보여주게 된다. 이 둘을 같은 계열로 묶으면 “조회 endpoint가 있으나 영원히 빈 모달”이라는 결함을 재생산한다.

### 3.3 writer 배선: `#7, #8, #9, #10` (4개)

이 네 표면은 다음 근거로 writer 배선 후보로 분류했다.

- DC: `DcConfigAuditLogService`가 `AuditLogRecorder`를 구현하고 `dc_config_audit_logs` migration/table이 있으나, 현재 `dcConfigAuditLogService`를 mutation service에서 호출하는 production source가 `rg`에서 확인되지 않았고 table은 0행이다.
- 매출/기간/월말 마감: `AccountingAuditLogService`와 `accounting_audit_logs`는 존재하고 다른 accounting 기능은 실제 50행을 만들지만, `DailyClosingService`, `MonthEndCloseService`, accounting period mutation 경로에서 `recordOverlayPatch`/`recordBatch` 호출이 확인되지 않았다. 대상별 join도 0행이다.

이 분류의 의미는 writer를 이번 라운드에서 구현하라는 것이 아니다. 개발책임자가 “모든 서비스 동작을 기록” 범위를 확정한 뒤, 어떤 mutation을 기록할지와 actor/field 계약을 결정해야 한다.

### 3.4 설계 판단: `#1, #2, #3, #11, #12, #13, #15, #16, #18, #19, #20, #21, #22, #23, #24, #25` (16개)

- `#1~#3`: 협업 제안·댓글·결정 상태의 `changeSet`이다. full snapshot revision·restore와 동일시할 수 없다.
- `#11`, `#13`: 현재 common audit 행은 0이지만 `InventoryAuditService:428`, `WarehouseService:353`에 recorder 호출자가 있다. “writer 호출자 없음” 조건에는 맞지 않으므로, 실제 도달·기록 조건·현재 DB 시점 차이를 판단해야 한다.
- `#12`: mobile-staff source는 공통 slip audit을 읽지만 현재 navigator에 도달 route가 없다. route를 살릴지부터 결정해야 한다.
- `#15`, `#16`, `#18`~`#25`: 저장 snapshot, draft, restore payload, 전송/비교/정리/SMS 작업 history다. 실제 행이 있더라도 문서 revision 카드의 `변경 전/후` 계약이 아니다. #18은 현재 직접 snapshot이 0행이고 PR #1126과도 충돌한다.

이 16개를 강제로 #1104 모달로 바꾸면 데이터 의미를 바꾸거나, 이미 있는 복원·작업 history UI를 깨뜨릴 가능성이 있다.

## 4. 슬라이스 2 후보

### 4.1 권장: 세금계산서 endpoint 계열 `#5 + #6`

가장 값싸고 즉시 닫히는 후보는 `TaxInvoiceDetailPage`와 `TaxInvoiceFormPage`다.

1. 두 화면이 같은 `taxInvoiceAuditApi`와 같은 FE `AuditLogEntry` adapter를 이미 사용한다.

3. 기존 `accounting_audit_logs` envelope·row schema를 그대로 반환하면 FE adapter 수정 없이 동작할 수 있다.

## 6. 남은 위험과 다음 라운드 입력

- 가장 즉시 닫히는 데이터 계열은 `#5/#6`이지만, endpoint를 만들 때도 `accounting_audit_logs` 50행 전체를 tax invoice로 노출하면 안 된다. `entity_id` 대상 필터를 유지해야 한다.

- `#11/#13`은 recorder 호출자가 있으므로 “0행 = 코드 호출자 없음”이라는 이전 실패 패턴을 반복하면 안 된다. 현재 DB의 도달 데이터와 서비스 로그/배포 버전은 별도 확인 대상이다.
- `#18`은 snapshot 원천 0행이고 PR #1126과 같은 web 파일을 건드린다. #1091의 revision 모달로 편입하지 않는다.

이번 라운드에서 소스 수정, 테스트 수정, endpoint 신설, writer 배선, migration, Docker 기동/재시작, git add/commit/push는 하지 않았다. 새로 생성할 산출물은 이 보고서 파일 하나다.
