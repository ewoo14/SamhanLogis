## 1. B-1 재설계 — R1-1/R1-2 fix

### 1-1. 문제였던 것

R0 은 `clients/desktop/playwright.real-qa.config.ts` 의 `use` 에 다음 한 줄만 추가했었다.

```ts
baseURL: process.env['AUDIT_BASE_URL'] ?? 'http://127.0.0.1:5175',
```

상대경로 `page.goto('/…')` 를 쓰는 real-QA 스펙은 897 · 928 · 929-r4 **3개**다(직접 grep 재확인 —
`page.goto\(` 호출부를 897·928·929-r4·929-r5 네 파일 전부에서 직접 열어 대조했다. 929-r5 에서
매치된 유일한 상대경로 문자열은 Javadoc 주석 안의 예시(`{@code page.goto('/#…')}`)였고 실제
코드의 `page.goto` 는 전부 `${APP_BASE}/...` 형태의 절대 URL 이었다). 929-r5 는 자체 `QA_BASE_URL`
로 절대 URL 을 조립해 이 문제와 원래 무관하다 —
구판·기획서가 "4개"로 표기한 것은 과대 계수이며 이 문서와 기획서에서 정정한다(§5).

이 3개 중 897 · 929-r4 는 데스크톱 렌더러(HashRouter `/#/...`, `vite.renderer.dev.config.ts` 정본
포트 5175)를 목표로 하지만, **928 은 완전히 다른 Vite 앱인 주문 웹 order-app**(BrowserRouter `/`,
`clients/web/order-app`, 정본 포트 5181)을 목표로 한다. R0 처럼 전역 baseURL 을 5175 하나로
고정하면:

- 렌더러만 띄운 상태에서 928 을 돌리면 **데스크톱 앱의 DOM 을 로드**해 `web-version-notice` 를
  못 찾는 것으로 실패한다 — 하네스 설정 문제가 제품 결함처럼 읽힌다(R1-1 이 지적한 신호 악화).
- `AUDIT_BASE_URL` 은 이미 148개 스펙이 "자기 오리진" 기본값으로 스펙 코드 안에서 직접 읽고
  있다(그중 106개는 기본 오리진이 5175 가 아니다 — R1 적대검증 실측). 928 을 맞추려고 이 이름에
  값을 주입하면 그 148개가 동반 오작동한다(R1-2).

**독자 재확인**(R1 수치를 그대로 믿지 않고 직접 grep):

```
grep -rl "AUDIT_BASE_URL" clients/desktop/playwright --glob "*.spec.ts"   → 237개 파일
grep -rl "AUDIT_BASE_URL" clients/desktop/playwright --glob "playwright.config.ts" → 42개 파일
grep -rl "QA_BASE_URL"    clients/desktop/playwright                      → 24개 파일(다수가 .spec.ts 자체에서 직접 읽음: 937-*, 929-r6, 924, 920-*, 902-*, 809-* 등)
```

두 이름 모두 "이 공유 config 전용 override" 로 재사용하기엔 이미 과점유 상태임을 직접 확인했다.
`QA_BASE_URL` 도 928 자신의 정본 config 가 쓰는 이름이라 **928 전용 override 이름으로도 못 쓴다**
(다른 20여개 스펙이 동시에 끌려간다).

### 1-2. 설계 — Playwright `projects` 로 분리, 신규 이름으로 override

`clients/desktop/playwright.real-qa.config.ts` 를 다음처럼 재작성했다(전체는 파일 참고).

- 최상위 `use` 에서 `baseURL` 을 제거하고 `headless`/`viewport`/`actionTimeout`/`navigationTimeout`/
  `devices['Desktop Chrome']` 만 남긴다(두 프로젝트가 공통 상속).
- `projects: [{ name: 'order-app', testMatch: ['928-web-version-check-real-qa/**/*-real-qa.spec.ts'], use: { baseURL: ORDER_APP_BASE_URL } }, { name: 'renderer', testIgnore: 같은 글롭, use: { baseURL: RENDERER_BASE_URL } }]`.
  `renderer` 프로젝트는 `testMatch` 를 명시하지 않아 최상위 `testMatch: ['**/*-real-qa.spec.ts']` 를
  그대로 상속하고, `testIgnore` 로 928 글롭만 제외한다 — 두 프로젝트가 정확히 상호배타적으로
  전체 파일을 분할한다(중복도 누락도 없음, §1-3 실측).
- override 환경변수 이름을 이 config 전용 신규 이름으로 바꿨다 — `REAL_QA_RENDERER_BASE_URL`
  (기본 `http://127.0.0.1:5175`), `REAL_QA_ORDER_APP_BASE_URL`(기본 `http://127.0.0.1:5181`,
  928 정본 `playwright/928-web-version-check-real-qa/playwright.config.ts` 의 `QA_BASE_URL`
  기본값과 동일 포트). 두 이름 모두 저장소 전체에서 기존에 쓰인 적이 없음을 직접 확인했다(grep 0건).

## 2. 929-r5 설계 결정 — 유지(뒤집지 않음)

`929-r5-route-collision-real-qa.spec.ts:30-39` 의 주석은 "공유 config 에 baseURL 이 없다"는
전제였으나, 이 전제는 R0 시점에 이미 stale 이었고(R0 가 baseURL 을 추가했으므로) 본 라운드
에서 다시 stale 해졌다(projects 분리). 주석을 **현재 상태에 맞게 정정**했다 — 공유 config 가
이제 프로젝트별 baseURL 을 갖는다는 사실은 반영하되, **929-r5 의 설계 결정(절대 URL 자체
조립)은 뒤집지 않았다**. 이유: 929-r5 는 슬라이스 단위로 렌더러를 임의 포트에 띄워 공유
config 의 프로젝트 구성과 무관하게 독립 실행하려는 목적이며, 이 목적은 이번 fix 로도 사라지지
않는다(공유 config 의 project 구성이 앞으로 늘거나 이름이 바뀌어도 929-r5 는 영향받지 않아야
한다). 이 스펙의 `page.goto` 호출 자체(절대 URL 문자열)는 변경하지 않았다 — 코드 변경은
주석뿐이다.
