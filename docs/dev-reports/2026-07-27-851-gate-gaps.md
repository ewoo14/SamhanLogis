## 1. B-1 재설계 — R1-1/R1-2 fix

### 1-1. 문제였던 것

R0 은 `clients/desktop/playwright.real-qa.config.ts` 의 `use` 에 다음 한 줄만 추가했었다.

```ts
baseURL: process.env['AUDIT_BASE_URL'] ?? 'http://127.0.0.1:5175',
```

상대경로 `page.goto('/…')` 를 쓰는 real-QA 스펙은 897 · 928 · 929-r4 **3개**다(직접 grep 재확인 —
`page.goto\(` 호출부를 897·928·929-r4·929-r5 네 파일 전부에서 직접 열어 대조했다. 929-r5 에서
매치된 유일한 상대경로 문자열은 Javadoc 주석 안의 예시(`{@code page.goto('/#…')}`)였고 실제
코드의 `page.goto` 는 전부 `${APP_BASE}/...` 형태의 절대 URL 이었다). 929-r5 는 자체 `QA_BASE_URL`
로 절대 URL 을 조립해 이 문제와 원래 무관하다 —
구판·기획서가 "4개"로 표기한 것은 과대 계수이며 이 문서와 기획서에서 정정한다(§5).

이 3개 중 897 · 929-r4 는 데스크톱 렌더러(HashRouter `/#/...`, `vite.renderer.dev.config.ts` 정본
포트 5175)를 목표로 하지만, **928 은 완전히 다른 Vite 앱인 주문 웹 order-app**(BrowserRouter `/`,
`clients/web/order-app`, 정본 포트 5181)을 목표로 한다. R0 처럼 전역 baseURL 을 5175 하나로
고정하면:

- 렌더러만 띄운 상태에서 928 을 돌리면 **데스크톱 앱의 DOM 을 로드**해 `web-version-notice` 를
  못 찾는 것으로 실패한다 — 하네스 설정 문제가 제품 결함처럼 읽힌다(R1-1 이 지적한 신호 악화).
- `AUDIT_BASE_URL`은 148개, `QA_BASE_URL`은 17개 스펙이 "자기 오리진" 기본값으로
  스펙 코드 안에서 직접 읽는다(real-QA 트리 전체 실측 — 아래 §1-1 실측 블록의 146은 두 파일을
  뺀 부분집합 수치이며 그 제외 사유가 "Git 무시"라는 이전 서술은 사실이 아니다. R3-2에서
  정정, 근거는 §9-2). 합집합은 165개이고, 기본 오리진이 5175가 아닌 파일은 121개다(제외
  대상이던 두 파일도 기본 오리진이 5175라 이 수치 자체는 불변). 928을 맞추려고 이 이름에
  값을 주입하면 해당 스펙들이 동반 오작동한다(R1-2).

**독자 재확인**(R2에서 GNU grep으로 직접 재현):

```bash
cd clients/desktop
GREP_SCOPE=(--include='*-real-qa.spec.ts' --exclude='slip-form-3d-real-qa.spec.ts' --exclude='dispatch-collab-real-qa.spec.ts')
AUDIT_FILES=$(grep -rl "${GREP_SCOPE[@]}" -F "process.env['AUDIT_BASE_URL']" playwright)
QA_FILES=$(grep -rl "${GREP_SCOPE[@]}" -F "process.env['QA_BASE_URL']" playwright)
printf 'DIRECT_PROCESS_ENV_REAL_FILES=%s\n' "$(printf '%s\n' "$AUDIT_FILES" "$QA_FILES" | sort -u | sed '/^$/d' | wc -l)"
printf 'UNIQUE_DEFAULT_NOT_5175=%s\n' "$(printf '%s\n' "$AUDIT_FILES" "$QA_FILES" | sort -u | sed '/^$/d' | xargs grep -L -E 'process\.env.*5175' | wc -l)"
printf 'AUDIT_BASE_URL_ENTRIES=%s\n' "$(printf '%s\n' "$AUDIT_FILES" | sed '/^$/d' | wc -l)"
printf 'QA_BASE_URL_ENTRIES=%s\n' "$(printf '%s\n' "$QA_FILES" | sed '/^$/d' | wc -l)"
```
```
DIRECT_PROCESS_ENV_REAL_FILES=163
UNIQUE_DEFAULT_NOT_5175=121
AUDIT_BASE_URL_ENTRIES=146
QA_BASE_URL_ENTRIES=17
```

GNU grep에는 ripgrep의 `--glob` 옵션이 없으므로 위 명령은 `--include`/`--exclude`를 사용한다.
🚨 [R3-2 정정] 두 `--exclude`(`manual/slip-form-3d-real-qa.spec.ts`,
`dispatch-collab-real-qa/dispatch-collab-real-qa.spec.ts`)의 제외 사유를 이전 판은 "Git 무시
상태"라고 적었는데 **이는 사실이 아니다** — 두 파일 모두 `git ls-files`로 정상 추적(tracked)
되고 `git status`는 clean(무수정)이며 `git check-ignore`에도 매치되지 않음을 R3-2에서 직접
재확인했다(원문 §9-2). 실제로 검증되는 사실은, 둘 다 이 공유 배치 config 밖에서 단독
실행하도록 만들어진 스펙이라는 것이다 — `dispatch-collab-real-qa`는 자체
`playwright/dispatch-collab-real-qa/playwright.config.ts`(`testDir: '.'`)를 갖고 스펙 헤더 주석이
그 전용 config로 단독 실행하라고 명시하며, `manual/slip-form-3d-real-qa.spec.ts`는 안전한
기본값이 없는 `SAMHAN_QA_JWT`를 요구해(미주입 시 `''`) 무인 배치 실행 전제에 맞지 않는다.
R1 당시의 `rg` 기준과 같은 대상 집합(163)을 재현하려 그대로 뺀 것일 뿐, 이 두 파일이
존재하지 않거나 추적되지 않는다는 뜻은 아니다 — 제외 전 165든 제외 후 163이든 두 이름 모두
"이 공유 config 전용 override"로 재사용하기엔 이미 과점유 상태라는 결론 자체는 그대로다
(오히려 165가 더 강한 근거). `QA_BASE_URL`도 928 자신의 정본 config가 쓰는 이름이라
**928 전용 override 이름으로도 못 쓴다**(다른 스펙이 동시에 끌려간다).

### 1-2. 설계 — Playwright `projects` 로 분리, 신규 이름으로 override

`clients/desktop/playwright.real-qa.config.ts` 를 다음처럼 재작성했다(전체는 파일 참고).

- 최상위 `use` 에서 `baseURL` 을 제거하고 `headless`/`viewport`/`actionTimeout`/`navigationTimeout`/
  `devices['Desktop Chrome']` 만 남긴다(두 프로젝트가 공통 상속).
- `projects: [{ name: 'order-app', testMatch: ['928-web-version-check-real-qa/**/*-real-qa.spec.ts'], use: { baseURL: ORDER_APP_BASE_URL } }, { name: 'renderer', testIgnore: 같은 글롭, use: { baseURL: RENDERER_BASE_URL } }]`.
  `renderer` 프로젝트는 `testMatch` 를 명시하지 않아 최상위 `testMatch: ['**/*-real-qa.spec.ts']` 를
  그대로 상속하고, `testIgnore` 로 928 글롭만 제외한다 — 두 프로젝트가 정확히 상호배타적으로
  전체 파일을 분할한다(중복도 누락도 없음, §1-3 실측).
- override 환경변수 이름을 이 config 전용 신규 이름으로 바꿨다 — `REAL_QA_RENDERER_BASE_URL`
  (기본 `http://127.0.0.1:5175`), `REAL_QA_ORDER_APP_BASE_URL`(기본 `http://127.0.0.1:5181`,
  928 정본 `playwright/928-web-version-check-real-qa/playwright.config.ts` 의 `QA_BASE_URL`
  기본값과 동일 포트). 두 이름 모두 저장소 전체에서 기존에 쓰인 적이 없음을 직접 확인했다(grep 0건).

### 9-1. R3-1 — 928 하네스가 셸의 `VITE_APP_VERSION`에 지배되는 결함

#### 근본 원인

`clients/desktop/playwright/928-web-version-check-real-qa/playwright.config.ts`(R2 산출물)의
`webServer.command`는 `npm run preview -- ...`(= `npm run build && vite preview`)로 order-app을
**직접 빌드**한다. 빌드 버전 주입 줄이 다음과 같았다:

```ts
const orderAppVersion = process.env['VITE_APP_VERSION'] ?? '2026/07/26-92700'
```

`??`는 변수가 "없을 때만" 오른쪽 값을 적용한다. 호출한 셸에 `VITE_APP_VERSION`이 이미
설정돼 있으면(이 저장소 자신의 다른 real-QA 문서가 그렇게 지시한다 — `937-fix3-real-qa.spec.ts:13`
등 937 계열 5개 파일이 오늘 날짜로 `VITE_APP_VERSION=2026/07/27-1`을 셸에 export하라고
명시한다) 그 값이 928의 빌드에 그대로 흘러 들어간다. order-app은 이 값을 빌드타임에
번들에 굽고(`clients/web/order-app/vite.config.ts:28` `resolveBuildAppVersion`) 런타임에 자신의
"현재 버전"으로 백엔드 `/app/version`에 조회한다(`src/main.ts:27`). 928 스펙
(`928-web-version-check-real-qa-real-qa.spec.ts:9`)의 `CURRENT_VERSION = '2026/07/26-92700'`은
스펙이 직접 호출하는 API 프로브(`readVersion()`)에만 쓰이고, **실제 브라우저에 뜨는 번들이
어떤 버전으로 빌드됐는지와는 무관**하다 — 그래서 앰비언트 값이 섞이면 스펙의 API 프로브는
여전히 정상(고정 리터럴 기준이므로)인데 브라우저의 실제 버전 판정만 어긋나 버전 안내 UI가
뜨지 않는, "하네스 설정 문제가 제품 결함처럼 읽히는" 실패가 난다(이 PR 자신의 dev-report
§1-1이 미리 지적한 바로 그 패턴).
