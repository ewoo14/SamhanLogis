## 1. 좌표(파일:줄)

### D1 — 비공유 서버 snapshot이 공유 Y.Doc을 영구 분기시킨다

- `clients/desktop/src/renderer/realtime/createCoeditProvider.ts:580-584` — `SERVER_AUTHORITY_ORIGIN` update를 전송 queue에서 제외한다.
- 같은 파일 `:606-643` — 같은 문서는 이후에도 공유 snapshot을 5초마다 병합한다.
- 같은 파일 `:756-782` — 서버 snapshot이 기존 `items`를 삭제하고 새 Y.Map들을 같은 공유 Y.Doc에 비공유 transaction으로 삽입한다.
- 같은 파일 `:693-712` — 이후 사용자 편집은 그 로컬 전용 Y.Text/Y.Map에 일반 update를 만든다.

실사용 재현: A와 B가 같은 주문을 편집한다 → A가 revision을 복원한다 → A에는 복원 line/memo, B에는 복원 전 line/memo가 남는다 → A가 복원 line을 다시 편집한다. A가 POST한 증분 update는 B에게 없는 새 Y.Map 생성 구조에 의존하므로 B 화면에 통합되지 않는다. 반대로 B의 기존 line 편집도 A에서는 삭제된 구조에 적용되어 보이지 않는다.

인메모리 Yjs 재현에서 A의 후속 update 2개(26/49 byte)를 B에 실제 적용했지만, A는 `restored memo + A edit`/`L2`, B는 `old memo`/`L1`로 남았다. 이후 B 편집까지 A에 적용하면 memo 일부만 섞이고 line은 계속 갈렸다. 즉 “즉시 전파하지 않음”이 “다음 편집도 수렴하지 않음”으로 바뀌었다.

### D2 — 협업 수정완료 1회가 여전히 revision 무효화 2회를 만든다

- `clients/desktop/src/renderer/components/collab/PartnerOrderCollaborationPanel.tsx:110-114` — `partner-order:edit`와 `suggestion.accepted`를 모두 revision event로 분류한다.
- 같은 파일 `:142`, `:184-190`, `:263-264` — boolean은 local invalidate 뒤 첫 SSE 하나만 건너뛴다.
- `services/partner-order-service/src/main/java/com/samhanair/logis/partnerorder/audit/service/PartnerOrderAuditLogService.java:146-149` — 협업 commit이 `partner-order:edit`를 발행한다.
- `services/partner-order-service/src/main/java/com/samhanair/logis/partnerorder/collab/PartnerOrderCollabEditService.java:83-89` — 같은 commit이 `suggestion.accepted`도 발행한다.

실사용 재현: 로컬 협업 수정완료는 mutation success에서 1회 무효화하고, 두 SSE 중 하나만 boolean으로 건너뛰며 나머지 하나가 다시 무효화한다. SSE가 HTTP 응답보다 먼저 오면 둘 다 무효화한 뒤 local success까지 더해질 수 있다. 원격 사용자는 boolean이 없으므로 같은 사용자 사건에 두 SSE를 모두 무효화한다.

### D3 — 원격 revision 복원은 revision/detail 화면에 전달되지 않는다

- `services/partner-order-service/src/main/java/com/samhanair/logis/partnerorder/revision/service/PartnerOrderRevisionService.java:287-292` — RESTORE revision을 만들고 collection board의 `RESTORED`만 발행한다.
- `clients/desktop/src/renderer/routes/SalesPartnerOrderDetailPage.tsx` — detail 화면은 board collection realtime을 구독하지 않는다.
- `clients/desktop/src/renderer/components/collab/PartnerOrderCollaborationPanel.tsx:177-193` — detail 화면이 구독하는 order collab stream은 세 revision event만 처리한다.

실사용 재현: B가 주문 상세/버전 이력을 보고 있는 동안 A가 같은 주문 revision을 복원한다. A는 local mutation callback으로 갱신되지만, B가 구독한 per-order collab stream에는 RESTORE 사건이 없으므로 B의 상세와 revision 목록은 자동 갱신되지 않는다. R10이 무효화 조건을 좁히며 복원 생산자와 소비자 계약을 잇지 않았다.

## 2. 불변식(수단 금지)

1. 서버 권위 복원은 다른 사용자의 미저장 초안을 조용히 삭제하지 않으면서도, 모든 활성 세션이 복원 사건을 인지하고 충돌/재수렴할 수 있어야 한다.
2. 한 세션만 보는 서버 snapshot을 공유 Y.Doc의 CRDT 구조 변경으로 넣어 이후 정상 update의 의존 구조를 끊어서는 안 된다.
3. 복원 뒤 어느 세션에서 편집하든 정상 협업 update는 다른 활성 세션에 도달하고 최종 문서가 수렴해야 한다.
4. revision을 만드는 사용자 사건 1회는 로컬·원격 모두 revision 목록을 정확히 한 번 최신화해야 한다.
5. direct 수정·협업 수정완료·삭제·revision 복원 등 모든 revision 생산자는 활성 원격 상세 화면이 소비할 수 있는 사건을 내야 한다.
6. 복원 GET 실패 시 stale cache 금지와 사용자 오류 표시는 유지한다.
7. 해결 수단은 특정 flag, event 이름, Yjs API 또는 query API로 지정하지 않는다.

## 3. 양방향 RED

### D1

- RED-A: 공통 base update를 가진 A/B에서 A만 서버 snapshot을 비공유 적용한 뒤 A가 memo와 복원 line을 편집하고 그 일반 update를 B에 적용한다. B가 A의 후속 편집을 못 보거나 A/B visible state가 갈리면 실패.
- RED-B: 같은 상태에서 B도 복원 전 memo/line을 편집해 A에 전달한다. 양 세션이 충돌을 명시적으로 처리하지 않은 채 서로 다른 line 집합이나 혼합 memo로 남으면 실패. 일반 복원 무관 coedit update는 계속 양방향 수렴해야 한다.

### D2

- RED-A: local mutation success, `partner-order:edit`, `suggestion.accepted`를 HTTP→SSE와 SSE→HTTP 순서로 각각 전달한다. 유효 `/revisions` 재조회가 사용자 사건당 1회를 넘으면 실패.
- RED-B: 같은 협업 commit의 두 SSE를 원격 세션에 전달한다. 최종 최신 revision이 보이지 않거나 유효 재조회가 1회를 넘으면 실패. comment/비 revision suggestion은 계속 0회여야 한다.

### D3

- RED-A: A의 revision 복원으로 RESTORE revision을 생성하고 B의 활성 detail/revision query를 관찰한다. B가 별도 새로고침 없이 복원 상세와 새 revision을 인지하지 못하면 실패.
- RED-B: direct 수정·협업 수정완료·삭제·복원을 각각 원격에서 실행한다. revision 생성 경로가 누락되거나 한 사건이 중복 갱신되면 실패. revision을 만들지 않는 사건은 0회여야 한다.
