## ① 첫 50건 밖 품목의 실제 선택 도달성

실 API에서 `q=A&page=0&size=50` 첫 페이지에 없는 다음 세 품목을 각각 같은 사용자 경로로 밟았다.

1. 견적 작성 `/#/sales/estimates/new` 도달.
2. 화면 고유 요소 `estimate-form-save-button` 가시성을 먼저 단정.
3. 라인 1 모델명에 `A` 입력.
4. `품목 검색 결과` 모달의 정확한 절단 안내를 단정.
5. `검색 결과 필터`에 대상 모델코드를 입력하고 Enter.
6. 대상 radio 가시성 → check → `선택 확정` 클릭.
7. 원래 모델명 입력값이 대상 코드가 됐는지 단정.


## ④ Product 직접 응답 DTO 전수와 직렬화 mutation RED

다음 두 grep 축을 product-service 전체 production Java에 다시 적용했다.

```powershell
rg -n "(?:record|class)\s+[A-Za-z0-9_]*Product[A-Za-z0-9_]*Response" `
  services/product-service/src/main/java/com/samhanair/logis/product --glob '*.java'

rg -n "(?:from|of)\s*\(\s*Product\s+[A-Za-z0-9_]+" `
  services/product-service/src/main/java/com/samhanair/logis/product --glob '*.java'
```

- `*Product*Response` 선언: 7종.
- 그중 `Product` 엔티티를 직접 받는 `from/of(Product ...)`: 정확히 4종.
- 직접 DTO: `ProductSummaryResponse`, `ProductCatalogResponse`, `ProductResponse`, `ProductByCodeResponse`.
- 제외 3종: `ProductAuditLogResponse`, `ProductEditRequestResponse`, `ProductSpecResponse`. 각각 감사로그·수정요청·사양 하위 리소스이며 `from/of(Product ...)`가 없다.
- 따라서 5종째 Product 직접 응답 DTO는 없다.

각 production DTO의 `goodsType` wire field를 하나씩 제거하거나 `@JsonIgnore` 처리한 뒤 해당 단일 테스트를 `--rerun-tasks`로 실행했다.

| mutation | 단일 결과 |
|---|---:|
| `ProductSummaryResponse`의 `@JsonProperty("goodsType")` 제거 | 1/1 RED, exit 1 |
| `ProductCatalogResponse.goodsType`에 `@JsonIgnore` | 1/1 RED, exit 1 |
| `ProductResponse.goodsType`에 `@JsonIgnore` | 1/1 RED, exit 1 |
| `ProductByCodeResponse.goodsType`에 `@JsonIgnore` | 1/1 RED, exit 1 |

네 경우 모두 `ProductResponseGoodsTypeSerializationTest:47`의 `JsonNode.get("goodsType") == null`로 실패했다. mutation을 전부 원복한 뒤 해당 클래스는 4/4 GREEN, exit 0이다.
