# PR #1164 — SOL 5.6 R8 재검토

- 검토일: 2026-08-11
- 대상: PR #1164, LUNA 미커밋 변경
- 판정: **차단 결함 1건 — 머지 불가**
- DB 안전: 공유 DB는 조회를 포함해 쓰지 않았다. 저장 재현은 Testcontainers의 격리 PostgreSQL에서만 수행했다.

## 1. 판정 요약

7개 actor 표시 좌표는 Chromium에서 모두 열어 캡처했다. 정상 한글 이름과 RED-B 표적 `김%20감사`, `1-1-1-1-1`은 그대로 보였고, `%`·`+` 포함 이름도 실제 PostgreSQL 저장 경로에서 손실 없이 통과했다. 공용 유틸 자체도 이중 decode나 느슨한 UUID 오탐을 만들지 않았다.

그러나 warehouse 저장 경계에서 정규화 결과가 `null`이 되는 actor 이름을 허용하면 전체 warehouse 변경 트랜잭션이 롤백된다. `WarehouseService`가 예외를 잡아 감사 기록을 best-effort로 처리하려 해도, 같은 Spring 트랜잭션에 참여한 `InventoryAuditLogRecorder`가 이미 rollback-only를 표시하므로 메서드 종료 시 `UnexpectedRollbackException`이 발생한다. PM 실데이터 발화 조건이 현재 0건이어도, 이번 선제 방어가 정상 쓰기 요청을 거부할 수 있으므로 손익이 역전되는 차단 결함이다.

## 2. 차단 결함

### [HIGH] invisible-only actor가 warehouse 저장 전체를 롤백시킨다

#### 코드 경로

1. `WarehouseService`는 클래스 전체가 `@Transactional`이다 (`WarehouseService.java:35`).
2. `update`, `delete`, `restore`, `revertToRevision`은 각각 `recordAuditSafe`를 호출한다 (`:186`, `:215`, `:249`, `:314`).
3. `resolveActorName`은 U+200B/U+200C/U+200D/U+FEFF/U+00AD/U+2060 제거 후 빈 값 또는 canonical UUID를 `null`로 만든다 (`:391-410`).
4. `recordAuditSafe`가 그 `null`을 `InventoryAuditLogRecorder.recordBatch`에 전달한다 (`:375-385`).
5. recorder가 생성하는 `AuditLogEntry`는 `actorName == null || actorName.isBlank()`이면 `IllegalArgumentException("actorName 은 필수입니다")`을 던진다 (`AuditLogEntry.java:100-113`).
6. recorder의 트랜잭션 프록시를 통과한 예외가 동일 트랜잭션을 rollback-only로 표시한다. 바깥 `catch (RuntimeException)`은 표시를 되돌릴 수 없어 최종 commit에서 `UnexpectedRollbackException`이 발생한다.

#### 실제 재현

격리 PostgreSQL에 warehouse를 만들고 유효한 `callerId`와 `callerName = "\u200B"`로 실제 `WarehouseService.update`를 호출했다. 도메인 변경과 실 `InventoryAuditLogRecorder`를 함께 사용한 임시 IT 결과는 다음과 같다.

```text
2 tests completed, 1 failed

Expecting code not to raise a throwable but caught
"org.springframework.transaction.UnexpectedRollbackException:
 Transaction silently rolled back because it has been marked as rollback-only"

[warehouse-audit] audit 기록 실패 — ... cause=actorName 은 필수입니다
BUILD FAILED
```

같은 IT의 RED-B 사례 `김감사`, `김%20감사`, `1-1-1-1-1`, `김%감사`, `김+감사`는 모두 warehouse 변경과 감사 로그를 commit했고 저장된 actor 이름도 입력과 같았다. 즉 정상 문자열 자체의 변형 문제는 없지만, 정규화 결과가 빈 값인 조합은 저장을 거부한다.

LUNA의 `WarehouseServiceTest`는 recorder를 mock으로 대체하고 `null` 전달만 확인한다. Spring 트랜잭션 프록시와 실제 `AuditLogEntry` 검증이 없으므로 이 rollback을 재현하지 못한다. controller/filter 계약 테스트도 서비스 호출 인자까지만 확인하므로 동일하다.

## 6. LUNA 수정 지시서

### 6.1 불변식

1. `update`, `delete`, `restore`, `revertToRevision`은 actor 이름이 null·공백·invisible-only·canonical UUID라는 이유만으로 실패하거나 rollback되어서는 안 된다.
2. 실제 field 변화가 있으면 기존 정책대로 감사 행을 남겨야 한다. 단순히 recorder 호출을 생략하거나 예외 전파만 숨겨 감사 기록을 잃는 수정은 허용하지 않는다.
3. 감사 행의 `actorId`는 유효한 호출자 UUID를 보존한다. 인증 사용자를 `system` actor로 바꾸지 않는다.
4. 저장되는 `actorName`은 `AuditLogEntry`의 필수 계약을 만족하는 nonblank 값이어야 하며 canonical UUID를 사용자 표시 이름으로 저장해서는 안 된다. 이름을 표시할 수 없으면 비식별 fallback(예: `변경자 미상`)을 일관되게 사용한다.
5. 정상 한글 이름, `김%20감사`, `1-1-1-1-1`, `%`, `+`는 문자 단위로 보존한다. gateway 이후 추가 decode를 하지 않는다.
6. `김\u200B감사`는 actor 표시/감사 이름에서 `김감사`가 되어야 한다. warehouse의 업무 데이터 이름 등 actor가 아닌 사용자 입력은 이 helper로 바꾸지 않는다.
7. 지시대로 `@NotBlank`, gateway decode, UUID 정규식 범위는 변경하지 않는다.

- 서비스 쓰기 경계: `WarehouseService.java:35`, `:158-186`, `:212-215`, `:240-249`, `:291-314`
- 정규화/기록 경계: `WarehouseService.java:375-410`
- 실제 recorder: `InventoryAuditLogRecorder.java:54`, `:69` 이후 batch 생성·저장
- 도메인 필수 계약: `AuditLogEntry.java:100-115`
- 프런트 표시 전수: `AuditOverlay.tsx:119,156`, `EditWarehouseModal.tsx:335`, `EstimateVersionHistoryPanel.tsx:304-306`, `PartnerOrderVersionHistoryPanel.tsx:121`, `PartnerVersionHistoryPanel.tsx:60`, `RedlineCell.tsx:29,57`, `SlipVersionHistoryPanel.tsx:118,415-417`

### 6.3 필수 RED-A

mock recorder만 쓰지 말고 Testcontainers PostgreSQL + 실제 `InventoryAuditLogRecorder` + Spring 트랜잭션 프록시를 사용하는 통합 테스트를 추가한다.

1. 네 쓰기 경로 `update × delete × restore × revert` 각각에 유효한 actorId와 U+200B-only actor를 넣는다.
2. 각 요청이 `UnexpectedRollbackException` 없이 완료되고 도메인 변경이 commit됐음을 DB에서 확인한다.
3. 각 실제 변화에 대응하는 감사 행이 존재하고 actorId가 보존되며 actorName은 nonblank·비 UUID fallback인지 확인한다.
4. U+200C, U+200D, U+FEFF, U+00AD, U+2060, 일반 공백-only도 같은 표를 통과시킨다.
5. canonical UUID 단독 및 각 invisible 문자로 감싼 canonical UUID도 같은 표를 통과시킨다.
6. actorName `null` 경로와 system 호출자 경로를 별도로 검증한다. 인증 사용자와 system의 의미를 섞지 않는다.
7. recorder가 actor 이름 외 이유로 실패하는 기존 best-effort 정책도 실제 트랜잭션에서 검증한다. 정책상 도메인 쓰기를 살릴 것인지 감사 실패를 함께 실패시킬 것인지 기존 계약을 확인하고 명시한다.
8. 프런트 7개 좌표에는 invalid actor가 UUID를 노출하지 않고 기존 fallback/은폐 규칙을 지키는 테스트를 유지한다.

### 6.4 필수 RED-B

1. `김감사`, `김%20감사`, `1-1-1-1-1`, `김%감사`, `김+감사`를 네 warehouse 쓰기 경계에서 저장하고 감사 actorName이 정확히 동일한지 확인한다.
2. `김\u200B감사`는 정확히 `김감사`로 한 번만 정규화한다.
3. `%20`은 `%20` 그대로여야 하며 공백으로 이중 decode되면 실패한다.
4. warehouse 업무 필드의 사용자 입력값은 actor 정규화와 무관하게 기존 저장 의미를 유지한다.
5. 기존 desktop 전체 회귀, design-system test/typecheck/build, inventory 전체 관련 계약을 다시 실행한다.
6. 위 7개 actor 표시 좌표를 Chromium으로 다시 캡처한다.

### 6.5 새 조합 표

다음 조합을 누락 없이 열거해 테스트 이름 또는 parameterized case로 남긴다.

- 작업: `update | delete | restore | revert`
- 호출자: `authenticated UUID | system | null/invalid header`
- 이름: `정상 한글 | %20 | % | + | 1-1-1-1-1 | 내부 invisible | invisible-only 6종 | whitespace-only | canonical UUID | invisible-wrapped canonical UUID | null`
- 결과: `도메인 commit 여부 | 감사 행 수 | actorId | actorName | UUID 노출 여부 | UnexpectedRollback 유무`
- 변화: `실제 field 변화 | no-op 요청 | 여러 field batch`
- recorder: `정상 | actorName 계약 실패 가능 입력 | 기타 저장 예외`

최소 수정 방향은 warehouse 감사 저장 직전 `null`/은폐 대상 actor 이름을 nonblank·비식별 fallback으로 매핑하고 actorId는 그대로 보존하는 것이다. `system`으로 가장하거나 감사 행 자체를 건너뛰는 방식은 위 불변식을 충족하지 않는다.

**제 전제가 틀렸다면 고치지 말고 중단·보고하십시오.** 특히 “감사 실패 시 warehouse 도메인 쓰기를 살린다”가 기존 정책이 아니라면 트랜잭션 전파를 임의로 바꾸지 말고 PM에게 계약 결정을 요청해야 한다.

## 7. 이 라운드가 보지 않은 표면

- 공유 DB write와 실제 배포 환경의 warehouse 쓰기는 수행하지 않았다.
- design-system `AuditOverlay`를 간접 사용하는 desktop 7개 route를 각각 실제 업무 데이터와 backend로 클릭하지 않았다. component 좌표 1과 desktop 전체 회귀로만 확인했다.
- `arologis-desktop`, `mobile-public`, `mobile-staff`의 전체 화면/빌드는 다시 실행하지 않았다. 검색상 이번 helper 또는 design-system `AuditOverlay`의 직접 호출자는 아니다.
- 전체 저장소의 모든 actor/UUID 표시 좌표를 재감사하지 않았다. LUNA가 바꾼 7개 좌표와 warehouse 저장 경계만 검토했다.
- gateway 실서비스 decode 체인과 실제 인증 공급자의 header 조합은 재실측하지 않았다. 이번 변경이 해당 코드를 건드리지 않았고 `%20` RED-B는 service 경계에서 검증했다.
- 실제 recorder의 actor 이름 외 예외에 대한 기존 best-effort 트랜잭션 의미는 별도로 확정하지 않았다. 이번 재현은 actorName 필수 계약 충돌에 한정한다.
