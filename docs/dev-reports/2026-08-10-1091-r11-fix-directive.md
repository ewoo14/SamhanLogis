## 결함 1 — 거래처 DC의 버전이력 버튼은 실서버에서 항상 404다

### 재현 증거

1. `dev_master`로 로그인한다.
2. `/sales/partner-dc-config`에 진입한다.
3. 첫 거래처의 `보기` → `버전이력`을 누른다.
4. 실 요청 `GET /api/v1/dc-configs/{partnerCode}/audit-logs`가 **404**이고, 모달은 `버전 이력 조회 기능이 아직 제공되지 않습니다.`를 표시한다.

실행 원문:

```text
dc:done:404
beforeOpen = 수정 이력 미조회
httpStatus = 404
errorKind = not-supported
modalText = 버전 이력 조회 기능이 아직 제공되지 않습니다.
badgeAfter = 수정 이력 조회 실패
```

화면 증거: `docs/qa/2026-08-10-1091-r11-sol-reconvergence/03-live-dc-audit-404.png`

### 원인 좌표

- `clients/desktop/src/renderer/api/createAuditApi.ts:119-122`
  - FE는 `/api/v1/dc-configs/{partnerCode}/audit-logs`를 호출한다.
- `services/dc-config-service/src/main/java/com/samhanair/logis/dcconfig/web/PartnerDcConfigsController.java:40,48,67,77`
  - 실 컨트롤러는 `/api/v1/partner-dc-configs` 아래 목록·단건·PATCH만 제공하며 audit GET이 없다.
- `services/dc-config-service/src/main/java/com/samhanair/logis/dcconfig/service/DcConfigService.java:89`
  - PATCH는 `DcConfigAuditLogService`를 호출하지 않는다.
- `services/dc-config-service/src/main/java/com/samhanair/logis/dcconfig/audit/service/DcConfigAuditLogService.java:31`
  - recorder 구현은 존재하지만 저장 경로에 연결되지 않았다. 실 DB `dc_config_audit_logs`는 0행이었다.

R9의 `SalesPartnerDcConfigPage.tsx:121` 캐시 무효화 1줄과 정적 계약은 존재하고 통과한다. 그러나 실 audit 조회·기록 경로가 없으므로 **R9의 사용자 종단 불변식은 닫히지 않았다.**

### 불변식

DC 값을 실제로 변경해 PATCH가 200으로 끝나면 같은 거래처의 audit GET은 gateway를 통해 200이어야 한다. 저장 직후 재조회한 revision은 방금 저장한 변경 필드·이전 값·새 값·표시 가능한 변경자를 포함해야 하며, 성공한 빈 응답이나 404 기억 상태를 저장 전 결과로 재사용하면 안 된다.

### 양방향 RED

#### RED-A — 고칠 결함

실 renderer + 실 gateway에서 정리 가능한 QA 거래처를 사용한다.

1. DC 이력을 열어 최초 GET 200과 현재 revision 수를 기록한다.
2. `특이사항`을 고유 QA 문자열로 바꾸고 화면의 `저장`을 누른다.
3. PATCH 200 뒤 audit GET 호출 수가 1회 증가하고, 배지·모달에 새 revision과 `remark`의 이전/새 값이 보이는지 확인한다.
4. 원래 `특이사항`으로 복원 저장하고 재조회하여 복원 revision까지 확인한다. 종료 시 값은 원복한다.

아래 셋 중 하나라도 나오면 RED다.

```text
GET /api/v1/dc-configs/.../audit-logs = 404
PATCH 200 뒤 audit GET 호출 증가 0
PATCH 200 뒤 새 revision/remark 변경행 없음
```

#### RED-B — 지킬 구체적 표적

- `DcConfigServiceUpdateTest`: 일부 필드 PATCH가 요청하지 않은 `homeDiscountRate`·옵션 금액·`unitProcessingEnabled`를 바꾸지 않는다.
- `PartnerDcConfigsControllerSearchTest`: `%`, `_`, `\`가 검색 wildcard가 아니라 literal로 남는다.
- 동일 값 no-op PATCH는 audit row와 SSE를 새로 만들지 않는다.
- `sales.partner-dc-config` VIEW/UPDATE 권한 분리는 유지한다. VIEW 전용 사용자는 이력을 읽되 저장 버튼으로 PATCH하지 못해야 한다.

### 구현 방향

정본 외부 경로를 하나로 수렴시킨다. 현재 목록·PATCH와 같은 `/api/v1/partner-dc-configs/{partnerCode}/audit-logs`를 추가하고 FE 경로도 여기에 맞추는 안을 우선한다. PATCH 트랜잭션에서 변경 전/후를 비교해 실제 변경 필드만 `DcConfigAuditLogService`에 기록하고, 응답 전에 commit된 revision을 조회할 수 있어야 한다.

### 반대급부

- PATCH마다 audit INSERT와 SSE 비용이 추가된다.
- partnerCode를 `DcConfig` entity ID로 해소하는 조회가 필요하다.
- 기록을 응답 뒤 비동기로 미루면 R9의 저장 직후 invalidate가 기록보다 먼저 실행될 수 있으므로 순서 계약을 명시해야 한다.

## 결함 2 — 실 memo audit 3행을 받은 판매전표가 `변경 이력 없음`으로 보인다

### 재현 증거

1. `dev_master`로 로그인한다.
2. `/sales/slips`에서 `2026/08/10-14`를 연다.
3. 실 GET `/api/v1/slips/{id}/audit-logs`는 HTTP 200과 memo 3행을 반환한다.
4. 헤더 배지는 `수정 3회`인데 메모 Overlay는 `S33-open-collab-ok 변경 이력 없음`을 표시한다. 변경 전 값과 변경자도 화면에 없다.

실행 원문:

```text
initialStatus = 200
initialRows = 3
revision #3  fieldName=memo  oldValue=S33-open-overlay-ok  newValue=S33-open-collab-ok
revision #2  fieldName=memo  oldValue=S33-open-header-ok   newValue=S33-open-overlay-ok
revision #1  fieldName=memo  oldValue=S33-open-normal-path newValue=S33-open-header-ok
initialMemo = S33-open-collab-ok 변경 이력 없음
```

화면 증거: `docs/qa/2026-08-10-1091-r11-sol-reconvergence/04-live-slip-history-visible.png`

### 원인 좌표

- `services/slip-service/src/main/java/com/samhanair/logis/slip/audit/web/dto/SlipAuditLogResponse.java:25-35`
  - 실 DTO는 `fieldName`, `oldValue`, `newValue`다.
- `clients/desktop/src/renderer/api/slipAudit.ts:24-32,46-51`
  - FE 타입은 `field`, `beforeValue`, `afterValue`라고 선언하고 응답 정규화 없이 그대로 반환한다.
- `clients/desktop/src/renderer/routes/SlipDetailPage.tsx:2654-2666`
  - `log.field`로 그룹핑하므로 실 응답 세 행이 모두 `undefined` bucket에 들어간다.
- `clients/desktop/src/renderer/routes/SlipDetailPage.tsx:4205,4223`
  - `memo`·`shippingAddress` bucket은 빈 배열이 되어 실제 이력을 `없음`으로 렌더한다.

R10의 query 상태 6줄은 실 GUI에서 다음처럼 동작해 **상태 전달 자체는 닫혔다.**

```text
응답 지연  memo/배송지 = 변경 이력 불러오는 중
200 + []   memo/배송지 = 변경 이력 없음
네트워크   memo/배송지 = 변경 이력 조회 실패
```

그러나 200 + 실 이력의 정상 데이터 경로가 DTO 불일치로 은폐된다.

### 불변식

실 `SlipAuditLogResponse`의 `fieldName=memo` 행이 하나라도 있으면 메모 Overlay는 `변경 이력 없음`을 표시하면 안 된다. 최신 oldValue·변경자·시각을 보여야 하며, 배지의 distinct revision 수와 Overlay가 소비하는 행 집합은 같은 응답에서 나와야 한다.

### 양방향 RED

#### RED-A — 고칠 결함

실 DTO shape 그대로의 3행을 `listAuditLogs`에 입력한다.

```json
{"revisionNo":3,"fieldName":"memo","oldValue":"S33-open-overlay-ok","newValue":"S33-open-collab-ok"}
```

API 경계 정규화 뒤 다음을 모두 요구한다.

- `auditByField.memo.length === 3`
- 메모 Overlay에 `S33-open-overlay-ok`와 표시 가능한 변경자가 보인다.
- `변경 이력 없음`은 0개다.
- 배지는 계속 `수정 3회`다.

실 GUI `2026/08/10-14`에서도 같은 화면 결과를 캡처한다.

#### RED-B — 지킬 구체적 표적

- 실 200 + `[]` 전표 `2026/08/10-13`: 메모·배송지는 계속 `변경 이력 없음`이다.
- 첫 요청 지연: 두 Overlay 모두 `변경 이력 불러오는 중`이다.
- 첫 요청 네트워크 실패: 두 Overlay 모두 `변경 이력 조회 실패`다.
- `shippingAddress` 행이 없는 응답에서는 메모 이력만 보이고 배송지는 계속 `변경 이력 없음`이다.
- `redlineByField`에 `header.memo`가 있는 전표는 기존 `RedlineCell`이 우선되는 `renderRedlineCell` 계약을 유지한다.

### 구현 방향

`slipAudit.ts`의 API 경계에서 서버 DTO를 명시적으로 받아 UI 모델로 정규화한다.

```text
fieldName  -> field
oldValue   -> beforeValue
newValue   -> afterValue
```

소스 문자열 포함 여부를 검사하는 계약 테스트가 아니라, 실 DTO shape를 함수에 넣어 반환값과 Overlay 결과를 검증한다.

### 반대급부

- 정규화 뒤 지금까지 `undefined` bucket에 숨었던 과거 이력이 즉시 노출된다.
