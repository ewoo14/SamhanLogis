# PR #1137 / 이슈 #1136 — S11 재수렴 적대검증

## 결론

**결함 0이 아니다. 실 사용자가 밟는 경로에서 4건을 재현했다.** S9의 네 재현점은 S10에서 각각 닫혔지만, 실제 정상 Flyway 출력과 S10의 명시 대상 열거에서 새 fail-closed/fail-open 결함이 드러났다.

1. **S11-BLOCK-1** — checksum 불일치가 전혀 없는 정상 `validate` 성공행을 비-checksum 오류로 오인해 기본 전체 복구와 개별 서비스 복구가 exit 1이다.
2. **S11-BLOCK-2** — 적용된 migration 파일을 실행 불가능한 SQL로 완전히 손상해도 실제 Flyway 출력은 checksum mismatch뿐이며 repair preview가 exit 0으로 열린다.
3. **S11-MAJOR-3** — migration 디렉터리가 있는 신규 서비스는 기본 전체 실행에서 조용히 빠지고, 명시 실행은 `Unknown service target`으로 막힌다.
4. **S11-MAJOR-4** — 14개 매핑에 있는 기존 서비스도 migration 디렉터리가 없으면 기본 전체 실행에서 조용히 빠진다.

실제 `flyway_schema_history`는 읽기/`validate`만 했고 `repair`는 실행하지 않았다. Docker 재기동·재배포와 QA 잔재 DB 삭제도 하지 않았다. 작업트리의 production 코드·workflow는 수정하지 않았다.

### S11-BLOCK-2 — 손상된 적용 migration이 checksum-only repair로 통과한다

#### 재현 절차

실제 auth migration 96개를 임시 디렉터리에 복사하고 `V1__init_account.sql`의 전 내용을 `THIS IS NOT VALID SQL;`로 교체했다. 실제 `auth_db`에 대해 `validate`하되 `-WhatIf`로 repair 실행은 막았다.

#### 실측 원문

먼저 단순 주석 추가만 한 정상 checksum-only 복구 표본이다.

```text
Environment file: C:\dev\Samhan-Public\.claude\worktrees\t1123\infrastructure\.env.local
auth-service: checksum mismatch versions = 1
What if: Performing the operation "Flyway repair (checksum metadata only)" on target "auth-service".
REAL_CHECKSUM_ONLY_WHATIF_EXIT_CODE=0
```

같은 파일을 실행 불가능한 SQL로 완전히 교체한 표본이다.

```text
Environment file: C:\dev\Samhan-Public\.claude\worktrees\t1123\infrastructure\.env.local
auth-service: checksum mismatch versions = 1
What if: Performing the operation "Flyway repair (checksum metadata only)" on target "auth-service".
DAMAGED_APPLIED_MIGRATION_WHATIF_EXIT_CODE=0
```

두 실제 Flyway 판정은 동일하다. 분류기는 checksum mismatch 행의 존재와 허용 목록만 보므로 손상된 SQL도 141행의 `Flyway repair (checksum metadata only)`까지 도달한다.

#### 왜 실 경로인가

이 스크립트는 가드가 잡은 “이미 적용된 migration 수정”의 복구 명령으로 개발자에게 직접 출력된다. 개발자가 단순 주석/개행 변경이 아니라 SQL 본문을 잘못 덮어쓴 상태에서도 안내된 repair를 실행하면 history checksum을 그 손상본에 맞추는 경로가 열린다. fixture 전용 가짜 문구가 아니라 실제 `auth_db`와 Flyway 10.10.0의 `validate` 결과다.

### S11-MAJOR-4 — 매핑된 서비스의 migration 디렉터리 누락도 전체 실행에서 조용히 빠진다

### S9-BLOCK-2 — 실제 Flyway checksum-only 전문

가짜 4행이 아니라 실제 `auth_db`와 실제 Flyway 10.10.0에서 주석만 추가한 적용 V1을 validate했다.

실제 전문에는 `WARNING`, `Flyway OSS Edition`, `See release notes`, `Database:`, `ERROR: Validate failed`, `Migration checksum mismatch`, `-> Applied`, `-> Resolved`, revert 안내, flexibility 안내가 포함됐다. **S9의 checksum-only 전문 거부 재현점은 닫혔다.** 다만 정상 success 전문은 S11-BLOCK-1, 손상 파일은 S11-BLOCK-2다.

### S9-MAJOR-3 — PowerShell 5.1 inspect 따옴표 소실

위 S11-BLOCK-1 명령은 `powershell.exe` 5.1에서 `-EnvFile` 없이 실행했다. 전체 JSON parsing으로 실행 중 `samhan-auth-service` label이 가리키는 다른 worktree의 다음 파일을 찾았다.

```text

```

**S9의 자동 탐색 실패 재현점은 닫혔다.** 이후 exit 1은 inspect가 아니라 S11-BLOCK-1의 정상 Flyway success 행 때문이다.

### S9-MAJOR-4 — timeout 후 하위 프로세스 잔존

격리 저장소의 SSH helper를 60초 정지시키고 로컬에 없는 `BeforeRef`를 실제 guard에 주었다. helper가 시작됐음은 PID 파일로 확인하고, guard 반환 직후 같은 PID와 fixture 경로의 git fetch 프로세스를 조회했다.

```text
TIMEOUT_GUARD_EXIT_CODE=1
TIMEOUT_ELAPSED_SECONDS=21.0
HELPER_PID_FILE_PRESENT=True
HELPER_ALIVE_AFTER_RETURN=False
FETCH_PROCESS_COUNT_AFTER_RETURN=0
```

**S9의 반환 직후 하위 프로세스 2개 잔존 재현점은 닫혔다.**

## 이 라운드가 보지 않은 것

- 실제 `flyway repair`는 실행하지 않았다. 모든 repair 가능 판정은 `-WhatIf` 또는 fixture였다.
- 실제 PostgreSQL role 권한을 회수하지 않았다. 권한 없음은 잘못된 실제 자격으로 인증 거부 경로를 실행했으며, 연결 성공 뒤 schema/table 권한만 없는 문구 변형은 보지 않았다.
- 실제 신규 마이크로서비스를 배포하거나 DB를 만들지 않았다. 신규 서비스 도달성은 실제 스크립트와 격리 파일/Docker fixture로 판정했다.
- 실제 main push·force-push·외부 fork PR은 만들지 않았다. 정상 commit graph와 timeout 원격은 시스템 임시 디렉터리의 격리 fixture였다.
- Linux에서 Windows `taskkill /T /F`와 다른 프로세스 트리 모양은 보지 않았다.
- Docker 재기동·재배포, 실제 history 수정, QA 잔재 DB 삭제는 하지 않았다.
