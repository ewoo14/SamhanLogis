# 2026-08-01 #1020 기능 회귀 검토

## 1. 기존 담당자 등록·수정·삭제 경로 정적 추적

- 기존 API `POST /users/employees`, `PATCH /users/employees/{id}`, `POST /users/employees/{id}/terminate`는 모두 `EmployeeController`에서 `EmployeeProvisioningService`의 `create`, `update`, `terminate`로 이어진다.
- 관리자 API도 `AdminUserController`에서 같은 서비스의 `adminCreate`, `adminUpdate`, `adminDisable`로 이어진다.
- 신규 `EmployeeAccountLinkReconciliationController`와 `EmployeeAccountLinkReconciliationService`는 위 기존 경로에서 호출되지 않는다. 신규 repository도 기존 CRUD 서비스의 의존성에 추가되지 않았다.
- V12는 `employee_account_link_reconciliations` 테이블과 그 테이블의 인덱스 2개만 생성한다. `employees`에 컬럼·제약·trigger를 추가하거나 기존 행을 갱신하는 SQL은 없다.
- 신규 테이블의 `employee_id -> employees(id)` FK는 기존 삭제가 물리 DELETE가 아니라 `Employee.markDeleted(...)`를 쓰는 soft delete이므로 현재 등록·수정·퇴사 경로를 막는 접점이 없다.

정적 판정: 신규 기능이 기존 담당자 등록·수정·삭제 호출 경로에 개입하는 지점은 발견되지 않았다. 아래 실행 검증으로 보강한다.

## 2. V12 fresh PostgreSQL 적용과 기존 `employees` 불변 검증

기존 컨테이너와 포트를 공유하지 않는 일회성 `postgres:15-alpine` 컨테이너를 만들었다. V1~V11을 순서대로 적용한 뒤 `employees` 전체 행을 `to_jsonb`로 직렬화하여 행 수와 MD5를 측정하고, V12 적용 후 같은 SQL을 다시 실행했다. UUID 값 자체는 출력·기록하지 않았다.

## 3. 실 DB 읽기 전용 재현 — 미리보기 16건 여부

### 결함: 예상 16건이 아니라 0건

`auth_db.accounts`의 미삭제·활성 행을 후보 목록으로 읽고, UTF-8 바이트를 보존한 채 `user_db`의 읽기 전용 트랜잭션 CTE로 전달했다. CTE는 구현과 동일하게 다음을 적용했다.

1. 직원 `is_deleted=false`, `termination_date IS NULL`
2. 후보와 직원의 `full_name`·`login_id` 정확 일치
3. 같은 이름+로그인 후보가 정확히 1건
4. `employee.id == employee.account_id` 또는 기존 `account_id == 후보 account_id`이면 제외

실행 출력 원문:

```text
BEGIN
 active_employees | active_auth_candidates | duplicate_candidate_pairs | exact_unique_matches | preview_items | already_normal_skipped | already_normal_in_preview
------------------+------------------------+---------------------------+----------------------+---------------+------------------------+---------------------------
               24 |                     27 |                         0 |                   24 |             0 |                     24 |                         0
(1 row)

 employee_name | employee_code
---------------+---------------
(0 rows)

COMMIT
```

정찰 문서의 16건은 오래된 `employees.id`와 `employees.account_id`가 서로 같고, 그 값이 현재 `auth_db.accounts.id`에는 없는 행이다. 그러나 신규 구현은 참조 대상의 실재 여부를 검사하지 않고 `employee.id == employee.account_id`만으로 정상이라고 판정한다. 따라서 끊어진 16건도 정상 8건과 함께 모두 제외된다.

판정: **미리보기는 실제 16건을 집지 못하며 0건을 반환한다. 새 기능의 핵심 사용 흐름이 정상 동작을 시작하지 못하는 차단 결함이다.**

## 5. 미리보기 이후 데이터 변경과 오래된 `planKey`

적용 경로의 재검증 코드는 다음 세 직원 필드만 비교한다.

```java
if (!Objects.equals(employee.getAccountId(), plan.getOldAccountId())
        || !Objects.equals(employee.getFullName(), plan.getEmployeeName())
        || !Objects.equals(employee.getLoginId(), plan.getEmployeeLoginId())) {
    throw new IllegalStateException("미리보기 이후 직원 정보가 변경되어 연결을 중단합니다");
}
employee.linkToAccount(plan.getTargetAccountId());
plan.markApplied();
```

- 미리보기 이후 직원의 `account_id`, 이름, 로그인 ID 중 하나가 바뀌면 예외가 발생하고 `@Transactional` 적용 전체가 rollback된다.
- 반면 auth 후보 계정은 apply에서 다시 조회하지 않는다. 후보의 이름·로그인 ID가 바뀌거나 계정이 비활성화·삭제되어도 저장된 `target_account_id`를 그대로 적용한다.
- 계획에는 만료 시각이나 만료 조건이 없고 apply도 나이를 검사하지 않는다. 직원의 위 세 필드만 그대로라면 오래된 `PLANNED` 계획을 그대로 적용할 수 있다.

저장된 계획을 별도 apply에서 실제 적용하는 기존 테스트 단독 실행 원문:

```text
.\gradlew.bat :services:user-service:test --tests 'com.samhanair.logis.user.service.EmployeeAccountLinkReconciliationServiceTest.previewThenApply_linksOnlyAfterPreview_andStoresBothMatchReasons' --no-daemon --console=plain --rerun-tasks

> Task :services:user-service:test

BUILD SUCCESSFUL in 27s
13 actionable tasks: 13 executed
```

판정: 직원 측 세 값의 변경에는 fail-closed이지만, auth 후보 변화와 시간 경과에는 fail-open이다. **오래된 계획이 그대로 적용될 수 있다.**

## 최종 판정

| 확인 항목 | 실측 판정 |
|---|---|
| 기존 담당자 등록·수정·삭제 | 신규 경로와 분리되어 있으며 관련 29개 테스트 통과. 회귀 재현 안 됨 |
| V12의 기존 `employees` 변경 | fresh PostgreSQL에서 9행 전체 hash 전후 동일. 변경 없음 |
| 미리보기 16건 | **결함: 0건**. 끊어진 16건도 `id == account_id` guard가 제외 |
| 정상 8건 포함 여부 | 포함되지 않음(0건). 정상 보호는 동작 |
| 후보 2건 이상 | 계획하지 않고 건너뜀 |
| 미리보기 후 변경 | 직원 연결·이름·로그인 변경은 중단. auth 후보 변경·삭제·비활성 및 계획 노후화는 재검증하지 않아 오래된 계획 적용 가능 |

이번 변경으로 기존 담당자 CRUD나 V12 적용이 멈추는 회귀는 재현되지 않았다. 그러나 새 복구 기능은 현재 실 데이터에서 대상 16건을 하나도 계획하지 못하므로 핵심 흐름이 차단되어 있다. 또한 계획 생성 후 auth 후보가 달라져도 오래된 target을 적용할 수 있다.
