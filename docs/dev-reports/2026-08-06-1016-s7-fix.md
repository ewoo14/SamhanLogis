# #1016 S7 fix 보고서 — 이전 mutation 뒤 UPDATE 회수 안내 충돌 해소

작성일: 2026-08-06  
브랜치: `feat/1016-aligo-upload`  
기준 HEAD: `92f6fd64f`  
지시서: `docs/dev-reports/2026-08-06-1016-s6-fix-directive.md`

## 결론

S6 지시서의 전제는 코드와 테스트에서 참으로 확인되었다. 현재 권한이 `VIEW=true`, `UPDATE=false`가 되면 이전 mutation 상태가 idle·200·403·500·network·null 중 무엇이든 권한 부재 안내가 우선하고, sync 버튼과 handler가 잠긴다.

변경 범위는 FE 화면 1개, 해당 Vitest 1개, 실제 mock 라우트 Playwright 1개다. 서버 권한 정책·API·집계·`usePermissions`의 30초 stale 정책은 변경하지 않았다. 커밋·푸시·Docker·실 Aligo 호출·Drive 쓰기는 하지 않았다.

## 원인과 수정

원인은 `AligoAddressBookPage.tsx`가 버튼에는 현재 `canSync`를 적용하면서 안내에는 mutation의 마지막 상태를 우선 적용한 데 있었다.

- 500·network 오류는 `syncMutation.isError`의 일반 재시도 문구가 계속 보였다.
- 200 응답은 결과가 남아 일반 오류 블록이 없으므로 권한 안내 자체가 없었다.
- 200 + `data=null`은 `syncMutation.isSuccess && !result` 재시도 문구가 계속 보였다.
- 기존 idle 권한 안내는 mutation이 완전한 최초 idle일 때만 렌더되었다.

수정은 세 갈래다.

1. 현재 `!canSync`이고 이전 mutation이 success/error이면 별도의 권한 부재 alert를 렌더한다. 200 결과·chip·실패 목록은 보존하면서 현재 실행 권한의 원인을 함께 표시한다.
2. 일반 오류 alert는 `syncMutation.isError && canSync`일 때만 렌더한다. `canSync=true`일 때는 기존 403 전용 잠금과 5xx·network 재시도를 그대로 유지한다.
3. null 성공 재시도 안내는 `canSync=true`일 때만 렌더한다. 현재 권한이 없을 때는 재시도를 지시하지 않는다.

지시서의 두 갈래만으로는 200 정상 결과를 설명할 수 없었다. 이 상태에는 오류 alert가 존재하지 않는다는 셋째 가능성이 있었고, 이를 별도의 현재 권한 alert로 닫았다.

## ② 불변식 검증

| 불변식 | 참이 된 이유와 증거 |
|---|---|
| 1. `VIEW=true`, `UPDATE=false`이면 버튼 disabled, POST 없음 | `disabled={syncPending || !canSync || syncForbidden}`와 handler의 `!canSync` 조기 반환을 유지했다. idle·VIEW-only·500/403/200/network/null 뒤 회수 테스트에서 disabled와 호출 수 1을 확인했다. |
| 2. `UPDATE=false`이면 상태와 무관하게 재시도 지시 금지, 권한 원인 표시 | success/error 뒤 `!canSync` alert가 보인다. 일반 오류와 null 재시도 문구는 `canSync=false`면 숨겨진다. 6개 직전 상태 축에서 권한 문구 visible, 재시도 문구 absent를 확인했다. |
| 3. 과거 결과와 현재 권한 설명 충돌 금지 | 200 세 상태의 notice·chip·실패 목록은 보존하고 별도 권한 alert를 추가했다. 과거 결과를 실행 권한으로 오해할 재시도 문구는 숨겼다. |
| 4. `UPDATE=true` + 5xx/network/null 재시도 유지 | 500·network·null은 첫 실패 뒤 enabled/재시도를 확인하고 UPDATE 재부여 후 두 번째 POST와 200 결과를 확인했다. |
| 5. 서버 403 확정 시 FE cache가 UPDATE를 허용해도 잠금 | `syncForbidden` 계산과 기존 disabled/handler guard를 유지했다. 403 권한 원인·새로고침 안내·disabled·POST 1회를 확인했다. |
| 6. 403 뒤 권한 부여 + 새로고침 후 회복 | 403 상태를 cleanup/remount로 새로고침에 해당하게 해소했다. 버튼 enabled, 다음 정상 200 결과, POST 2회를 확인했다. |
| 7. 전달 상태 3종 보존 | 기존 3종 0건 테스트와 새 200 후 UPDATE 회수 행렬을 통과했다. `NOT_DELIVERED`는 신규·변경 0, 나머지는 실제 상태·건수를 유지했다. |
| 8. CSV 고지 상시 유지 | 기존 화면과 새 200 상태 3종의 권한 회수 후 모두 CSV 고지를 확인했다. |

## ① 새로 가능해진 상태 조합과 결과

| 현재 권한 | 직전 결과 | 재조회 시점 | 밟은 경로 | 결과 |
|---|---|---|---|---|
| VIEW-only | 없음 | 최초 idle | 기존 Vitest/Playwright gate | disabled, 권한 원인, POST 0 |
| UPDATE 보유 | 없음 | 최초 idle | 기존 Vitest/Playwright gate | enabled, 실행 안내 |
| UPDATE 회수 | 없음 | 같은 mount idle rerender | 신규 Vitest | disabled, 권한 원인, 실행 안내 없음 |
| UPDATE 회수 | 500 | 같은 mount 권한 재조회 | 신규 Vitest | 재시도 숨김, 권한 원인, POST 1 |
| UPDATE 회수 | network | 같은 mount 권한 재조회 | 신규 Vitest | 재시도 숨김, 권한 원인, POST 1 |
| UPDATE 회수 | null | 같은 mount 권한 재조회 | 신규 Vitest | null 재시도 숨김, 권한 원인, POST 1 |
| UPDATE 회수 | 200 `NOT_DELIVERED` | 같은 mount 권한 재조회 | 신규 Vitest | 상태·chip·CSV 보존, 권한 원인 |
| UPDATE 회수 | 200 `DELIVERED` | 같은 mount 권한 재조회 | 신규 Vitest | 상태·실제 건수·CSV 보존, 권한 원인 |
| UPDATE 회수 | 200 `PARTIALLY_DELIVERED` | 같은 mount 권한 재조회 | 신규 Vitest | 상태·실패 목록·CSV 보존, 권한 원인 |
| UPDATE 회수 | 403 | 같은 mount 권한 재조회 | 신규 Vitest | 현재 권한 원인, disabled |
| UPDATE 보유 | 500 | 30초 stale 후 focus | 신규 실제 라우트 Playwright | disabled, 권한 원인, 재시도 0건 |
| UPDATE 보유 | 403 | 화면 새로고침 | 신규 Vitest | 버튼 회복, 다음 200, POST 2 |

반대급부도 별도로 밟았다. UPDATE가 유지된 500·network·null은 재시도 가능했고, 403 뒤 새로고침 회복도 유지되었다. S1·S3·S5의 전달 상태·CSV 고지·403 전용 잠금은 되돌리지 않았다.

```text

```

