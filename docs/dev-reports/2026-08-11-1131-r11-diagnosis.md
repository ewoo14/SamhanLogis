2. `코멘트/협업 → 버전 이력 → 이 시점으로 복원 → 복원`을 누른다. 서버는 200을 반환하고 성공 toast를 띄운다.

### 4.4 PM 범위 결정을 위한 fix 지시서

이번 라운드에서는 구현하지 않는다. 다음 구현 라운드는 아래 불변식을 먼저 확정해야 한다.

```text
revision 복원이 HTTP 200을 반환했다면, 복원된 현재 문서는 저장 가능한 계보 상태여야 한다.
특히 (slip, parentSetModel) 안에 head가 2개 이상인 keyless 다중 인스턴스를 커밋하면 안 된다.
```

필수 범위:

1. `SlipRevisionService.restore → Slip.restoreFromSnapshot`뿐 아니라 같은 도메인 메서드를 부르는 `SlipDocumentCollaborationPort` 시스템 복원도 함께 검사한다.
2. 동형인 `EstimateRevisionService.restore → Estimate.restoreFromSnapshot`도 sweep한다. 견적 구 revision이 keyless를 되살리면 견적 편집 또는 전표 전환에서 같은 결함이 재발한다.
3. 역사 원본 revision snapshot은 수정하지 않는다. 복원해 만든 **현재 문서**를 정상화하고, 그 정상화된 상태가 새 `RESTORE` revision에 캡처되게 순서를 보장한다.
4. 경계가 확정 가능한 legacy snapshot에는 인스턴스별 key를 부여한다. 경계를 확정할 근거가 없는 snapshot은 현재 상태를 먼저 바꾼 뒤 실패시키지 말고, 복원 mutation 전체를 원자적으로 거부하며 사용자가 이해할 메시지를 반환한다.
5. PM 결정 필요: `head부터 다음 head 직전까지`라는 snapshot 행 순서를 canonical 경계로 인정할지, 아니면 V119처럼 명시적으로 확인된 revision만 이관하고 나머지는 복원을 거부할지 선택해야 한다. 현 정책은 “모호한 경계를 추정하지 않는다”이므로 암묵적으로 순서 추정을 추가하면 안 된다.
6. RED는 최소 네 층이어야 한다: Slip 사용자 복원→첫 편집 200, Estimate 복원→편집/전환 200, 이미 keyed revision key 보존, 경계 불명 legacy 복원의 원자적 거부와 현재 문서 불변.
7. 기존 probe는 API `updatedAt`을 왕복하고 direct PUT 권위 필드만 보내도록 고쳐야 한다. 그렇지 않으면 409/금액 계약 400이 계보 결함을 다시 가린다.

## 5. slip-it-core B — V119 사후 검증 테스트 오류

### 5.1 원인 확정

check annotation 원문:

```text
SlipSalesUpdateIT > R9 RED-A GREEN: 명시 이관 후 keyless 8행 두 인스턴스의
첫 head 수량 편집은 200이다
expected: 0 but was: 4
at SlipSalesUpdateIT.java:627
```

실패는 PUT에 도달하기 전 migration helper의 사후 SQL에서 났다.

```java
// services/slip-service/src/test/java/com/samhanair/logis/slip/it/SlipSalesUpdateIT.java:620-627
assertThat(jdbcTemplate.queryForObject(
        "WITH groups AS (SELECT s.id, l.parent_set_model, COUNT(*) AS heads "
        // ...
        + "SELECT COUNT(*) FROM groups WHERE heads > 1", Integer.class))
        .isZero();
```

`COUNT(*) AS heads`는 head 수가 아니라 그룹의 전체 라인 수다. 따라서 keyless **단일 인스턴스**라도 구성품이 2행 이상이면 위반으로 잘못 센다. CI의 `4`는 이 오탐 그룹 수다.

실제 V119 preflight는 올바르게 head만 센다.

```sql
-- services/slip-service/src/main/resources/db/migration/V119__materialize_r9_keyless_bundle_instances.sql:87-104
COUNT(*) AS line_count,
COUNT(*) FILTER (WHERE COALESCE(l.set_head, false)) AS head_count
-- ...
WHERE head_count > 1;
```

### 5.2 이 테스트가 원래 지키던 것

**② 테스트 기대값 오류 확정.** 제품 기대값 `0`이 틀린 것이 아니라, 기대값에 넣을 관측값을 만드는 테스트 SQL이 틀렸다.

이 테스트의 원래 보호 계약은 두 단계다.

1. V119 적용 후 활성 keyless 그룹 중 **head가 둘 이상인 모호한 다중 인스턴스 그룹이 0개**여야 한다.
2. 명시 이관된 8행/2인스턴스 전표를 상세 조회하고 첫 head 수량을 2로 바꾼 PUT이 HTTP 200이어야 한다.

현재는 1단계 SQL 오타로 중단되어 2단계 제품 동작을 시험하지 못했다. 테스트를 green으로 만들 때 `.isZero()`를 완화하거나 제품 코드를 바꾸면 안 되고, migration과 동일한 `COUNT(*) FILTER (WHERE set_head)` 관측으로 복원해야 한다.

### 6.2 이 테스트가 지키던 것과 사용자 경로

**① 제품 결함 확정.** 기존 테스트는 다음 두 불변식을 함께 지켰다.

1. 세트 head의 품목을 무관 단품으로 교체하면 **그 교체 행만** 세트 계보에서 빠지고 사용자 입력 단가가 해당 단품의 최근가격으로 기억된다.
2. 사용자가 건드리지 않은 진짜 구성품은 세트 계보를 유지하고, 구성품 배분 단가가 개별 품목 최근가격으로 오염되지 않는다.

사용자 재현 경로:

1. 판매전표 상세에서 BUNDLE 구성품이 있는 전표의 `직접 수정`을 연다.
2. 세트 head 행의 품목만 무관한 단품으로 바꾸고 단가를 입력한다.
3. 다른 구성품 행은 그대로 둔 채 저장한다.
4. 저장은 성공하지만 건드리지 않은 구성품의 `parentSetModel/instanceKey`까지 사라진다.
5. 가격기억 수집은 계보 평면화 후 실행되므로 그 구성품 배분 단가까지 일반 품목 최근가격 후보가 되어 후속 견적/전표 단가를 오염시킬 수 있다.
