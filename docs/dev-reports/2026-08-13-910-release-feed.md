# #910·#935 릴리스 feed 첫 구현 라운드

> 대상: `feat/910-release-feed` · Electron `clients/internal-chat-desktop` 1개
> 날짜: 2026-08-13

## 결론

`electron-updater 6.8.9`는 자체서명 인증서를 금지하지 않는다. 다만 Windows가 인증서를 신뢰하지 않으면 updater가 installer를 거부한다.

> **운영 선행조건: 자체서명 인증서의 신뢰 루트를 모든 사내 Windows PC에 배포해야 한다.**
> 신뢰 루트가 없으면 `Get-AuthenticodeSignature`가 `UnknownError`가 되고, `electron-updater`가 `ERR_UPDATER_INVALID_SIGNATURE`로 설치를 거부한다. 이 조건이 충족되지 않으면 자동 설치는 전부 막힌다.

이번 라운드는 그 조건을 코드와 사용자 표시까지 고정했지만, 현재 머신의 electron-builder 패키징 도구가 Windows 권한 문제로 중단되어 signed installer의 실제 `download → quitAndInstall → 재기동` 완주 증거는 남기지 못했다. 따라서 이 문서는 **첫 구현 라운드**이며, 해당 smoke는 다음 QA에서 재개해야 한다.

## 1. `electron-updater` 서명 검증 실측

확인 명령:

```powershell

```

원문:

```text

  "dist.tarball": "https://registry.npmjs.org/electron-updater/-/electron-updater-6.8.9.tgz",
  "version": "6.8.9"
}
```

패키지 소스에서 확인한 원문(라인):

```text
NsisUpdater.js:52  const signatureVerificationStatus = await this.verifySignature(destinationFile);
NsisUpdater.js:56  throw newError(..., "ERR_UPDATER_INVALID_SIGNATURE");
NsisUpdater.js:87  publisherName = (await this.configOnDisk.value).publisherName;
NsisUpdater.js:88  if (publisherName == null) return null;
NsisUpdater.js:99  return await this._verifyUpdateCodeSignature(...);

```

즉 `publisherName`이 feed 설정에 있으면 검증하고, 검증 결과가 유효하지 않으면 설치를 중단한다. `publisherName`이 없을 때 검증을 건너뛰는 우회는 이번 구현에서 사용하지 않는다.

자체서명 실측 명령은 unsigned 9101 installer를 임시 복사한 뒤 `signtool.exe`로 서명하고, 같은 인증서를 CurrentUser 신뢰 루트에 넣었다가 제거하는 방식이었다.

원문:

```text
Successfully signed: ...\codex-signtool-release-probe\internal-chat-release.exe
UntrustedStatus : UnknownError
TrustedStatus   : Valid
Signer          : CN=Samhan Internal Release
```

미신뢰 상태의 실제 updater 오류는 다음처럼 renderer에 전달된다.

```text
ERR_UPDATER_INVALID_SIGNATURE: UnknownError
renderer status = {
  kind: 'error',
  message: '업데이트에 실패했습니다. 인터넷 연결을 확인한 뒤 다시 실행해 주세요.'
}
```

상세 `UnknownError`는 사용자 메시지에 노출하지 않지만, 오류 상태와 `다시 확인` 버튼은 표시한다. 따라서 현재 동작은 조용한 정상 통과가 아니라 사용자에게 실패를 보이는 동작이다.

## 5. 판단 필요 / 못 한 것

1. **운영 판단 필요:** 자체서명 루트 인증서를 사내 PC의 `Trusted Root Certification Authorities`에 배포하고 갱신·폐기 절차를 운영해야 한다. 이 배포가 없으면 모든 자동 설치가 `UnknownError`로 막힌다.
2. **이번 라운드 미완료:** `npm run build:win`의 signed package. electron-builder 25.1.8이 `winCodeSign-2.6.0.7z`를 풀 때 macOS 심볼릭 링크 생성 권한을 요구해 실패했다.

원문:

```text
ERROR: Cannot create symbolic link : 클라이언트가 필요한 권한을 가지고 있지 않습니다.
...\darwin\10.12\lib\libcrypto.dylib
...\darwin\10.12\lib\libssl.dylib
ERR_ELECTRON_BUILDER_CANNOT_EXECUTE
```

이는 `electron-updater`의 자체서명 거부가 아니라 Windows 빌드 도구 캐시 압축 해제 권한 문제다. 따라서 이 라운드에서는 실제 사내 서버 업로드, signed `latest.yml` feed, packaged 앱의 `quitAndInstall`·재기동, 다운그레이드까지 완료했다고 주장하지 않는다. 다음 QA는 Developer Mode/심볼릭 링크 권한이 준비된 머신에서 signed 9101→9102 feed 왕복을 재개해야 한다.

3. 상용 인증서, stable/beta 채널, 다른 8개 앱, DB migration은 범위 밖으로 남겼다.

### 원인 및 고른 수단

직전 라운드의 원인은 `winCodeSign-2.6.0.7z` 캐시 압축 해제 중 Windows 심볼릭 링크 생성 권한 부족으로 확인되어 있다. 다만 라운드 2의 현재 실행은 그 원인을 재확인하기 전에 릴리스 필수 환경변수 누락으로 중단됐다. 인증서·feed 위치를 추측하거나 서명을 끄는 우회는 하지 않았다. 다음 실행에는 자체서명 PFX, 비밀번호, 사내 feed URL, 그리고 Developer Mode 또는 심볼릭 링크 생성 권한이 준비되어야 한다.

### `quitAndInstall → 재기동` 실측

실측하지 못했다. signed installer 생성 전제(`INTERNAL_CHAT_UPDATE_URL`, `CSC_LINK`, `CSC_KEY_PASSWORD`)가 현재 환경에 없어서 `download → quitAndInstall → 재기동` 구간에 도달하지 않았다. 따라서 성공했다고 주장하지 않는다.

### 전량 테스트

이번 라운드는 보고서에 실패 원문만 추가했으며 코드/실행 모듈을 변경하지 않았다. signed build가 필수 환경변수 누락으로 시작되지 않아 변경 모듈 전량 테스트 및 `quitAndInstall` smoke는 실행하지 못했다.

### 못 한 것

실패 명령과 원문은 위 RED 절의 `npm run build:win` 출력 전부다. 이 상태에서는 `winCodeSign` 권한 문제를 해결했다고 판정할 수 없고, signed installer 재기동도 검증할 수 없다. 필요한 것은 자체서명 `CSC_LINK`/`CSC_KEY_PASSWORD`, `INTERNAL_CHAT_UPDATE_URL`, 그리고 `winCodeSign` 캐시가 심볼릭 링크를 만들 수 있는 Developer Mode 또는 동등한 권한이다.
