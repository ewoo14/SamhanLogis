## 2. 테스트가 틀렸나, 구현이 틀렸나

판정은 **둘 다 일부 원인이 있었지만, 품목 분리 기대값을 바꾼 직전 테스트 변경은 옳고 구현에 실제 결함이 있었다**이다.

직전 `+16/−30` 변경의 핵심인 `hasSize(1)→hasSize(2)`, `imported 12→24`는 되돌리지 않았다. 이전 실측에서 같은 품목명이어도 규격·단가가 다른 33개 그룹의 59개 필드가 사라졌고, fingerprint 기준으로는 소실 품목 33→0, 소실 필드 59→0이 된다. 따라서 서로 다른 업무값을 별도 Product로 남기는 기대값은 실제 계약에 맞다.

실제 구현 결함은 재임포트 시 `fallbackSameNameCandidate()`가 같은 품목명의 첫 DB raw 행을 fingerprint 확인 없이 다른 fingerprint singleton 그룹에도 재사용한 것이다. 첫 그룹 처리 후 두 번째 그룹이 그 DB main을 선택하면서 기존 `SAR-00006` alias를 다른 main에 매핑하려 했고, CI의 alias 충돌 예외가 발생했다. `@DirtiesContext`가 공유 DB를 정리하지 않는다는 기존 실측과도 일치한다.

나머지 assertion은 구현 값의 오류가 아니라 테스트가 `BigDecimal.equals` 기반 collection exact 비교를 사용한 scale 차이였다. DB가 반환한 `200000.00`과 기대 `200000`은 수치상 동일하므로 테스트를 `compareTo` comparator로 보정했다.

## 3. Fix

`EcountProductImporter`:

- 기존 DB 후보를 사용할 때 현재 fingerprint와 일치하는 raw 후보만 허용한다.
- 불일치하면 현재 fingerprint 그룹의 코드 오름차순 canonical raw로 진행해 다른 품목 그룹을 재사용하지 않는다.
- fingerprint singleton에는 `MERGED_SAME_NAME` 사유를 기록하지 않는다. 실제 병합 그룹(`size > 1`)에만 병합 사유를 기록한다.

`EcountProductImporterIT`:

- inbound price collection assertion을 `BigDecimal::compareTo` 기반으로 바꿔 scale 차이를 수치 오류로 판정하지 않게 했다.
- 테스트 skip·삭제·완화는 하지 않았다.
