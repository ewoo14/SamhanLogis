## ②-A revision 복원 제품 결함

### CI/재현 원문

```text
SlipRevisionRestoreIT > r10Probe_restoreLegacyRevisionReintroducesKeylessMultiInstanceAndBlocksNextEdit()
R10-RESTORE-REINTRO|restore=HTTP200|rows=8|heads=2|instanceKeys=0
R10-RESTORE-BLOCK|HTTP=400|code=INVALID_INPUT
```

### 수정

- `BundleSetInstanceKeyPolicy`에 `materializeLegacyMultiInstanceKeys(...)`를 추가했다.
- 동일 `parentSetModel`에 keyless head가 둘 이상인 revision만 head부터 다음 같은 parent의 head 직전까지 한 `instanceKey`로 승격한다.
- `Slip.restoreFromSnapshot`와 `Estimate.restoreFromSnapshot`가 같은 정책을 호출한다. 정책을 두 도메인에 복사하지 않았다.
- head 전에 keyless 구성품이 나타나 스냅샷만으로 경계를 확정할 수 없으면 `INVALID_INPUT`으로 복원 전체를 원자적으로 거부한다. 정상적인 head-선행 legacy 복원 자체는 막지 않는다.
- `SlipRevisionRestoreIT`는 복원 직후 8행/2 head/2 keys와 다음 수량 편집 HTTP 200을 검증하도록 바꿨고, Estimate 대칭 회귀도 `EstimateRestoreTest`에 추가했다.

### RED → GREEN 근거

수정 전 새 Slip 회귀는 `SlipRevisionRestoreIT.java:303`에서 `keys=0`으로 실패했고, Estimate 회귀도 keyless 옵션으로 실패했다. 정책 적용 뒤 두 테스트가 함께 `BUILD SUCCESSFUL`로 통과했다.

## ②-B V119 검증 SQL 오류

### CI 원문

```text
SlipSalesUpdateIT: expected 0 but was 4 at line 627
```

### 수정 및 근거

- `SlipSalesUpdateIT`의 group SQL에서 `COUNT(*) AS heads`를
  `COUNT(*) FILTER (WHERE COALESCE(l.set_head, false)) AS heads`로 고쳤다.
- V119 preflight와 같은 관측값(head 수)을 사용한다. 8개 구성품 행 수를 다중 인스턴스 수로 잘못 세던 테스트 SQL만 수정했고, migration/제품 제약은 약화하지 않았다.

## ②-C 가격기억 제품 결함

### CI 원문

```text
PartnerProductPriceMemoryIT.bundleHeadProductSwappedToUnrelatedItem_dropsLineageAndRemembersUserPrice()
expected untouched component parentSetModel=SET-809
actual untouched component parentSetModel=null
```

### 수정 및 근거

- `BundleLineageResolver.flattenHeadProductReplacements`가 교체된 head가 속한 인스턴스 전체를 평면화하던 동작을, 실제 교체된 head 행만 평면화하도록 고쳤다.
- 남은 진짜 구성품은 계보와 분배 단가를 보존하므로 가격기억 오염을 막는다.
- 기존 PostgreSQL IT의 기대값을 새 동작에 맞춰 약화하지 않았고, 관련 단위 회귀는 같은 계약으로 갱신했다.
