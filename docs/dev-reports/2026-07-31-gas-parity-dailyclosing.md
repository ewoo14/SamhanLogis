## 원본이 하는 일

### 실행 안전성 판정

- **근거 종류: 코드 근거.** 실행 대상 `processDailyData(ecountData, isMultiApplied, isBeforeHike)`는 가격표 Google Sheet를 `getValues()`로 읽고, Notion 데이터베이스를 query로 읽는다.
- 이 함수의 호출 경로에는 `setValue(s)`, `appendRow`, 시트 생성·삭제, Notion page 생성·수정이 없다. 쓰기 함수 `saveHistoryToNotion`, `savePendingToNotion`, `autoSaveToNotion`은 별도 진입점이며 이번 조사에서 실행하지 않는다.
- 따라서 `processDailyData`만 호출하는 것은 원본 외부 데이터에 대한 읽기 전용 실행으로 판정했다.

### 검증 규칙

- 입력은 이카운트 판매전표 행 배열이다. `일자_번호`로 전표를 묶고 원본 행 순서를 유지한다.
- 각 행의 모델 토큰으로 상업멀티(`AM...X/N`), 홈멀티(`AJ...X/N`), 싱글 본체·구성품 영역을 전환한다.
- 가격표에서 `출고가`, `납품가`, `고정DC`를 읽고, 입력 `단가(VAT포함)`과 수량으로 다음 숫자를 계산한다.
  - `할인율 = 1 - 단가(VAT포함) / 출고가`
  - `총계 = 단가(VAT포함) × 수량`
- 상업·홈멀티는 반올림한 실제 할인율(%)이 거래처별 DC 또는 품목 고정DC와 같은지 `확인`으로 판정한다. 별도 약정이 없으면 기본 45%다.
- 싱글은 실내기·실외기·옵션 구성품을 세트 카탈로그로 조합한 뒤 `기대 단가 합계 - 거래처별 정액 할인`과 판매전표 단가 합계의 절댓값이 같은지 검사한다. 360·4way·1way·스탠드·디럭스·1등급 정액 할인과 할인제외 품목을 구분한다.
- 구형·유연호스·방진가대·AXJ 등은 입력 단가가 납품가와 같은지 검사한다. 구형 AM/NJ/NS/AVX 일부는 50% 할인율을 검사한다.
- 출력은 각 행에 `출고가`, `할인율`, `총계`, `확인`, 거래처 DC 설명을 붙인 뒤 회계반영일자 유무에 따라 `main`과 `pre`로 나눈 `{status, main, pre, sum}`이다.

### 원격 접근 확인

- **근거 종류: 실행 환경 확인.** `clasp 3.3.0`이 설치돼 있고 인증된 계정에서 27개 GAS 프로젝트가 조회됐다.
- 대상 `일마감 프로그램` 원격 프로젝트가 목록에 존재하며 script ID는 보안 비밀이 아닌 Google Apps Script 프로젝트 식별자로 확인했다.
- 이 단계에서는 원격 함수 실행·배포·push를 수행하지 않았다.
- 원격에는 HEAD 배포와 고정 버전 배포 2개가 있으며, 최신 고정 버전은 46번 `7월1일 단가인상 시점 설정`이다.
- 46개 버전 이력에는 `싱글 세트 할인액 규칙 재적용`, `멀티 할인율 계산 적용 미적용`, `부자재 납품가 비교`, `일부 싱글세트 계산로직 수정`이 명시돼 있어 해당 검증이 단순 표시가 아니라 원본의 지속 운영 대상이었음을 확인했다.

### 원격 실행 시도 결과

- **실행 불가 — 사유 1:** `clasp run processDailyData`를 빈 입력으로 smoke 실행했으나, 원격 프로젝트가 Apps Script Execution API 실행 파일로 배포되지 않아 `Script function not found. Please make sure script is deployed as API executable.`로 종료됐다. 원본 함수 본문은 실행되지 않았다.
- **실행 불가 — 사유 2:** 고정 버전 46 웹앱을 통한 UI 실행을 준비했으나 현재 세션에 제어 가능한 인앱 브라우저가 없어 연결 단계에서 `No browser is available`로 종료됐다.
- Execution API 배포를 새로 만들거나 원격 코드를 수정하면 쓰기가 되므로 수행하지 않았다. 원본의 Notion 저장 함수도 실행하지 않았다.

## 같은 입력에 대한 출력 대조

### 대조 A — 상업멀티 품목 고정DC 50% (일치)

- 기준일: `2026-07-13`.
- 모델: `AM160NXVHHH1`.
- 입력: 출고가 11,572,000원, VAT 포함 단가 5,786,000원, 수량 1, 품목 고정DC 50%.
- **원본 결과(코드 공식 적용, 원격 실행값 아님):** `1 - 5,786,000 / 11,572,000 = 0.50`, 따라서 할인율 50%, 기대율 50%, `확인=true`, 총계 5,786,000원.
- **현행 결과(2026-07-13 실 Docker 라이브 QA 기록):** `releasePrice=11,572,000`, `deliveryPrice=5,786,000`, `expectedRate=50`, `actualRate=50`, `verified=true`, `revalidationStatus=VERIFIED`.
- 숫자 차이: 출고가 0원, VAT 포함 단가 0원, 실제 할인율 0%p, 기대 할인율 0%p, 판정 차이 없음.
- 현행 실측 출처: `docs/qa/773-s2b-revalidation-engine/qa-report.md`. 원본 쪽은 이번 원격 실행에 실패했으므로 코드 공식 산출값이다.

### 거래처 약정 실데이터 확인

- **근거 종류: 공유 DB 읽기 전용 조회.** 모든 쿼리를 `BEGIN TRANSACTION READ ONLY ... COMMIT`으로 실행했다.
- `dc_config_db`에서 주식회사 중앙유통의 홈멀티DC 48%, 상업멀티DC 48%, 360·4way·스탠드 정액 DC 각 70,000원, 1way 50,000원, 디럭스·1등급 각 30,000원을 확인했다.
- 같은 DB에는 48% 홈 또는 상업 약정 거래처가 다수 존재한다. 반면 현행 `DiscountRevalidator`는 거래처 식별자를 입력받지 않고, 품목 고정DC가 없으면 항상 45%를 기대율로 사용한다.

### 대조 B — 거래처 상업멀티 약정 48% (불일치)

- 기준일·거래처: `2026-07-13`, 주식회사 중앙유통.
- 비교 입력: 상업멀티 모델 `AM023TNVDBH1`, 출고가 100,000원, VAT 포함 단가 52,000원, 수량 1, 품목 고정DC 없음, 거래처 상업멀티DC 48%.
- 실제 할인율은 `1 - 52,000 / 100,000 = 48%`다.
- **원본 결과(코드 공식 + 실제 약정 DB 값 적용, 원격 실행값 아님):** 기대율 48%, 실제율 48%, `확인=true`, 총계 52,000원.
- **현행 결과(현행 코드 경로):** 거래처와 약정을 입력받지 않으므로 기대율 45%, 실제율 48%, `verified=false`, `revalidationStatus=VERIFIED`.
- 숫자 차이: 기대 할인율 **3%p**(원본 48% - 현행 45%). 판매금액 자체는 52,000원으로 같지만 판정은 정상(`true`)과 불일치(`false`)로 반대다.
- 주의: 현재 `accounting_db`의 계산서 19건·라인 22건에는 중앙유통 행이 0건이어서 이 조합을 현행 라이브 API로 호출하지 못했다. 입력값은 실제 약정 DB와 양쪽 코드 계약을 결합한 결정론적 대조다.

### 대조 C — 싱글 1way 정액 DC 50,000원 (현행 출력 없음)

- 기준일·거래처: `2026-07-13`, 주식회사 중앙유통.
- 비교 입력: 1way 싱글 세트, 카탈로그 구성품 기대 합계 1,000,000원, 실제 판매전표 구성품 단가 합계 950,000원, 거래처 1way 정액 DC 50,000원.
- **원본 결과(코드 공식 + 실제 약정 DB 값 적용, 원격 실행값 아님):** `1,000,000 - 50,000 = 950,000원`; 실제 합계와 일치하므로 관련 수량 단위가 모두 `used=true`, 행별 `확인=true`.
- **현행 결과(현행 코드 경로):** `AC|AP|AR|AF|PC|AWR|ARR` 접두를 `OUT_OF_SCOPE`로 즉시 반환해 `expectedRate=null`, `verified=null`. 정액 DC 금액 필드와 세트 기대합계 출력도 없다.
- 숫자 차이: 원본은 정액 DC **50,000원**을 검증에 반영하지만 현행 반영액은 산출 자체가 없다. 판정은 정상(`true`) 대 판정불가(`null`)다.
- 주의: 카탈로그 기대 합계 1,000,000원은 차이를 드러내기 위한 고정 비교 입력이며 현재 운영 전표에서 뽑은 값이 아니다. 거래처의 1way 정액 DC 50,000원은 공유 DB 실값이다.

## 현행이 하는 일

- `DailyClosingService`는 기준일·거래처·종류·원천별 공급가액, 부가세, 합계, 전표 건수를 합산해 `daily_closings` snapshot을 만들고 잠근다.
- 상세 재검증은 판매전표 업로드 행이 아니라 세금계산서 또는 회계전표 라인을 일자·품명 단위로 합산한 평균 VAT 포함 단가를 사용한다.
- 품목 고정DC가 있는 멀티, 구형 50%, 일부 액세서리 납품가 일치 검사는 수행한다.
- 거래처별 홈·상업 약정DC를 조회하지 않으며, 멀티의 품목 고정DC가 없으면 45%로 고정한다.
- 싱글 세트 구성품 매칭, 수량별 `riUsage`, 옵션 정액 DC, 할인제외 품목 검사는 수행하지 않는다.
- 응답에는 `releasePrice`, `deliveryPrice`, `expectedRate`, `actualRate`, `verified`, `revalidationStatus`가 있으나, 원본의 DC 설명·정액 DC 금액·문서별 구성품 매칭 결과는 없다.

### 현행 실행 검증

- `DiscountRevalidatorTest`만 실제 실행했다. `BUILD SUCCESSFUL`, 테스트 13건, 실패 0, 오류 0, skip 0이다.
- 이 테스트 묶음은 멀티의 품목 고정DC·45% 폴백, 싱글 세트 접두의 `OUT_OF_SCOPE`, 액세서리 납품가 일치, 구형 50% 등을 검증한다.
- Docker 재빌드·재기동과 공유 DB write는 수행하지 않았다.

## 최종 판정

**부분계승**

원본의 업무 목적은 계산서 발행 전 판매전표의 단가·DC율·싱글 정액 DC를 검증하는 것이다. 현행은 그중 일부 단품·멀티 재검증을 수행하지만, 거래처 약정과 싱글 세트 정액 DC라는 핵심 분기를 수행하지 않는다. 따라서 전체 계승도 아니고 대응 기능 전무인 미계승도 아니다.

### 되는 것

- 출고가 대비 VAT 포함 실단가로 할인율을 계산한다.
- 품목 고정DC가 있는 멀티는 원본과 같은 결과를 낼 수 있다. 대조 A에서 금액·할인율·판정 차이가 모두 0이었다.
- 구형 50%, 일부 액세서리의 납품가 완전일치, 운임·절삭 예외를 판정한다.
- 공급가·VAT·합계·건수 snapshot과 잠금, 목록·상세 이력을 제공한다.

### 안 되는 것

- 거래처별 홈·상업 약정DC를 선택하지 않는다. 48% 약정의 정확한 판매를 45% 기준으로 오판할 수 있다(대조 B: 기대율 3%p 차이, 판정 반대).
- 싱글 세트의 실내기·실외기·보조실내기·옵션 구성품을 문서별·수량별로 매칭하지 않는다.
- 360·4way·1way·스탠드·디럭스·1등급 정액 DC와 할인제외 품목을 검증하지 않는다(대조 C: 50,000원 반영 대 출력 없음).
- 원본 판매전표의 문서·거래처·원본 라인 순서를 보존하지 않고 일자·품명 평균으로 합친다. 서로 다른 문서·거래처의 오류가 상쇄될 수 있다.
- 원본보다 뒤 단계인 세금계산서/회계전표를 기본 원천으로 삼아 계산서 발행 전 최종 검증이라는 업무 위치를 완전히 재현하지 못한다.

## 완전계승에 필요한 작업 목록

전체 규모는 **대형(L)**이다. 단일 계산식 수정이 아니라 적어도 4~6개 통합 슬라이스, `accounting-service`·`product-service`·`dc-config-service`·전표/세금계산서 원천 계약·desktop UI를 함께 다뤄야 한다.

1. **원천 경계 복구 — L**
   - 세금계산서·매출전표·매입전표 세 경로에서 거래처 코드, 문서번호, 원본 라인, 모델 토큰, 개별 수량·VAT 포함 단가, 판매 카테고리와 행 순서를 판정 시점까지 보존한다.
   - 일자·품명 평균 집계는 판정 후 표시용으로만 사용한다. 필요한 스키마·backfill 범위를 별도 확정한다.
2. **거래처 약정 계약 연결 — M**
   - `dc_config_db.dc_configs`를 partnerCode로 bulk 조회해 홈·상업율과 옵션 정액 6종을 일마감에 공급한다.
   - 원본의 할인제외 품목·단위처리·특이사항 중 판정에 필요한 값을 현행 모델·import에 보존한다. 현재 `dc_configs` 컬럼만으로 부족한 항목은 migration과 backfill이 필요하다.
3. **세트 역방향 카탈로그 계약 — M~L**
   - `product_db`의 BUNDLE/구성품과 기준일 `price_history.delivery_price`를 이용해 구성품 묶음에서 가능한 세트를 찾는 bulk/inverse 조회를 제공한다.
   - 현행 enum에 없는 `SUB_INDOOR` 8개 모델·67개 링크의 표현 또는 레거시 토큰 기반 보정 규칙을 확정한다.
4. **원본 검증 엔진 계승 — L**
   - 문서·거래처별 zone 전환, 수량 단위 pool, 필수 실외기, 선택 옵션, `riUsage` 완전소비, 정액 DC 1회 차감, 할인제외, 음수 수량·단가 절댓값 비교를 재현한다.
   - 우선순위는 `품목 고정DC → 거래처 카테고리율 → 45% 폴백`으로 유지하고, 원금 snapshot은 재가격하지 않는다.
5. **응답·화면 계약 — M**
   - 정상/불일치/판정불가와 사유를 문서·거래처 경계를 잃지 않게 노출한다. 정액 DC 적용액과 세트 기대합계를 사용자가 확인할 수 있어야 한다.
   - UUID는 노출하지 않고 전표번호·거래처명·모델명 같은 업무 식별자를 사용한다.
6. **파리티 검증 체계 — L**
   - 멀티 45/48/50%, 세트 수량 1·2+, 구성품 누락, 보조실내기, 옵션 정액 6종, 할인제외, 음수 수량, 가격 결측 fixture를 원본 oracle로 고정한다.
   - 세 sourceKind 통합 테스트, 서비스 장애 fail-closed, 원금 불변 검증, read-only 운영 canary, 실제 GAS 원격 출력 대조를 포함한다.

## 확인하지 못한 것

- 원본 `processDailyData`의 실제 반환 JSON. Execution API 미배포와 브라우저 부재로 원격 함수 본문을 실행하지 못했다.
- 같은 기준일·같은 거래처의 원본 원격 출력과 현행 라이브 API 출력의 1:1 캡처. 대조 A의 현행은 과거 실 라이브 QA, 원본은 코드 공식이며, 대조 B·C는 실제 약정 DB 값과 양쪽 코드 계약을 결합한 결정론적 계산이다.
- 현재 Google 가격표 Sheet와 Notion의 중앙유통 약정이 이번 조회 시점에도 현행 `dc_config_db` 값과 완전히 같은지. 외부 원본은 쓰지 않았지만 원격 함수 실행이 막혀 반환값으로 확인하지 못했다.
- 운영 판매전표에서 거래처 약정 48%·싱글 정액 DC 분기가 실제로 발생하는 건수와 금액 합계.
- 현재 `accounting_db`에는 계산서 19건·라인 22건이 있으나 중앙유통 행은 0건이고, 싱글/AM/AJ 실라인도 없어 해당 조합의 현행 라이브 출력을 만들 수 없었다.
- 원격 HEAD 코드와 저장소 사본의 바이트 단위 동일성. 원격 버전·배포 이력과 로컬 전문은 확인했지만 원격 pull/push는 수행하지 않았다.
