## 확인 1 — 선행 측정 보고서와 작업 제약

- `2026-08-01-1011-double-receipt.md`와 `2026-08-01-1011-provisional-receipt-recon.md`를 읽었다.
- 선행 측정은 `InboundInspectionService.completeInspection`과 `SlipService.complete`를 서로 다른 재고 반영 경로로 지목한다.
- 현재 운영 로컬 DB에서 검수 행 0건, `INBOUND` movement 0건, 두 경로의 교집합 0건이다. 이는 상호배제 가드의 증거가 아니라 실제 입고 데이터 부재의 결과다.
- 검수 경로는 검수 정상수량(`inspectedQty - defectQty`)을 반영하고, 전표 라이프사이클 경로는 비시리얼 전표 예정수량 전량을 반영한다.
- 전표 seed는 상태만 만들고 inventory API를 호출하지 않으므로 상태만으로 재고 반영을 판정할 수 없다.
- 이번 작업에서 git 명령, 공유 Docker 재빌드·재기동, 실 DB 쓰기를 수행하지 않는다.

## 확인 3 — 코드·주석·기존 테스트의 업무 의도

- `docs/dev-reports/2026-08-01-1011-provisional-receipt-recon.md:13,15,17-24`는 최신 업무 흐름을 `DPS 가입고 업로드 → 입고전표 → DPS 정상입고 대조 → 검수 정상수량 확정 → 재고 반영`으로 정리하고, 검수 정상수량 재고 반영을 단일 권위로 삼아야 한다고 명시한다.
- `InboundInspectionService.completeInspection` Javadoc은 검수 완료 시 정상수량을 `StockLot + StockBalance + INBOUND_INSPECTION movement`로 반영한다고 명시한다. `InboundInspectionController`도 endpoint summary를 “검수 완료 → 재고 반영”으로 공개한다.
- `SlipService.complete` Javadoc과 `docs/dev-reports/slip-first-slice.md:69,80,96`는 전표 `/complete`가 입고전표 라인별 `inbound`를 호출한다고 명시하고, `SlipServiceTest`의 `complete_inbound_*` 테스트가 이 계약을 검증한다.
- 따라서 현행 코드·기존 테스트는 두 경로 모두 재고 반영 정본처럼 취급하고 있어 상호배제 정책을 완전히 합의한 상태가 아니다. 그러나 선행 조사 보고서의 최신 업무 판정은 검수 정상수량 경로를 정본으로 한다.
- 이번 수정의 정본 판정: **검수 완료 경로를 정본으로 유지하고, 전표 라이프사이클 경로는 검수 경로가 이미 반영한 동일 입고를 no-op 처리하는 보조 경로로 정리한다.** 전표 `/complete`만 실행되는 경우에는 기존 전량 입고를 유지하여 불변식 C를 보장한다.

## 확인 4 — 현행 검수 완료의 전표 상태 영향(D)

- 검수 complete endpoint는 inventory-service 내부의 `InboundInspection.status`만 `PENDING → COMPLETED`로 바꾸고 `stockApplied=true`를 기록한다.
- 같은 메서드와 controller에는 slip-service 상태 변경 호출이 없으며, `SlipService.complete`의 상태 전이는 별도 전표 endpoint에서 수행된다.
- 따라서 **현행 검수 완료가 입고전표 상태를 바꾸지 않는 것은 현재 구현상 의도된 분리 계약**으로 확인된다. 이번 이슈는 재고 경로 정리만 다루므로 전표 상태 동기화는 변경하지 않는다.

## 확인 5 — 기존 멱등 가드의 범위

- `InboundInspection.stockApplied`는 동일 검수 행 재호출만 막는다.
- `StockService.inbound`에는 동일 입고전표/품목/창고의 기존 lot 또는 movement를 검사하는 가드가 없다.
- `StockMovementRepository`의 기존 멱등 조회와 V14 unique index는 `RESERVE`에만 적용되며 `INBOUND` 교집합을 막지 않는다.
- 따라서 현재 가드는 두 경로 간 상호배제를 제공하지 않는다.

## 확인 6 — 동시성 방어와 Flyway 버전

- inventory-service의 기존 migration 최고 버전은 `V21__create_inventory_audit_number_sequences.sql`이다.
- 적용 migration은 수정하지 않고 `V22__add_inbound_slip_lot_idempotency_index.sql`만 신규 추가했다.
- 인덱스 대상은 활성(`is_deleted=false`) 일반 입고 lot 중 전표번호 형식(`YYYY/MM/DD-N`)이며, 이동전표(`source_transfer_id` 존재)와 임의 외부 lot 번호는 제외한다.
- 애플리케이션 조회 가드는 순차 교차 실행을 no-op으로 만들고, 신규 unique index는 동시 교차 실행에서 동일 `(품목, 창고, 전표번호)` lot가 두 개 생기는 것을 DB 레벨에서 차단하는 방어선이다.
