## 각도 1 — 타입 분리가 의미를 지키는가

### 전제 정정: API 타입은 원래부터 둘이었다

R6 직전 원문(`58f02d5fd^`)에서 API는 이미 다음 두 계약으로 분리돼 있었다.

```text
TabSyncResult: inserted, updated, unchanged, softDeleted, skipped
ComponentSyncResult: preservedManual, linked, bundlesMarked, softDeleted, skipped
```

원래 하나였던 것은 API DTO가 아니라 화면 투영용 `SheetSyncResult`였다. 따라서 “하나의 API 타입을 둘로 나눴다”가 아니라, 기존 두 API 의미를 화면의 `kind: 'product' | 'component'` 경계까지 보존한 변경이다. 이것이 제시된 두 선택지 외의 셋째 가능성이다.

현재 명시 계약은 다음과 같다.

- FE Javadoc: `TabSyncResult`는 BE `ProductSheetSyncService.TabSyncResult`와 1:1이다.
- BE Javadoc: Product sync는 신규/변경/동일/시트에서 사라진 row의 4-way 분기다.
- BE `ComponentSyncResult`: `linkedOccurrences`, `bundlesMarkedProducts`, `softDeletedComponentRows`, `skippedOccurrences`를 별도 필드로 둔다.
- BE `SyncSummary` Javadoc: Product row occurrence, 구성품 row occurrence, link occurrence를 서로 다른 필드로 노출한다.
- 계약테스트: `softDeletedComponentRows=3`이 화면 투영 뒤 3이고, 실 PostgreSQL IT는 구성품 1행 제거 시 `softDeletedComponentRows=1`을 단정한다.

현재 화면 투영은 Product 행에 `insertedRows/updatedRows/softDeletedProductRows`, 구성품 행에 `linkedOccurrences/bundlesMarkedProducts/softDeletedComponentRows`를 선택한다. API 원문과 화면 합계가 일치해 이 여섯 의미에서 사라진 상태는 찾지 못했다.

`preservedManualComponentOccurrences`와 `blockedByRuleOccurrences`는 구성품 행의 비고 투영에는 들어가지 않는다. 그러나 R6 전 화면 투영에도 `preservedManual`은 없었고, 두 값을 개별 행에 표시해야 한다는 Javadoc·계약테스트는 찾지 못했다. 지시대로 업무 의미를 추론하지 않고 **확인 필요**로 남기며 결함으로 세지 않는다. 합계 중 수동 보존 구성품 occurrence는 별도 chip으로 실제 표시된다.

## 각도 2 — 옛 이름 저장소 전수 grep

파일 확장자를 제한하지 않고 tracked 저장소 전체에 `git grep -n -I -w`를 실행했다. 일반어인 `inserted/updated/skipped` 등은 다른 도메인 계약과 역사 문서 때문에 각각 193/781/1,487건이므로 0건 주장의 증거가 될 수 없다. 개명된 구체 식별자도 역사 보고서·QA 원문에 남아 있다.

중요한 반례는 역사 문서가 아니라 현재 runtime source/test의 `totalUnchanged` 4건이다. 원문:

## 각도 3 — 화면의 3건이 3인가

발화 조건을 먼저 셌다.

```json
{
  "lastSyncAt": "2026-08-09T06:28:13.103216630Z",
  "byTabCount": 9,
  "byComponentTabCount": 2,
  "totalComponentLinkOccurrences": 1601,
  "totalSoftDeletedComponentRows": 3,
  "componentRows": {
    "싱글 구성품_단가인상": {"linkedOccurrences": 1447, "softDeletedComponentRows": 3},
    "상업멀티 구성_단가인상": {"linkedOccurrences": 154, "softDeletedComponentRows": 0}
  }
}
```

표본은 0이 아니다. 화면에서 눈으로 확인한 값은 총 삭제 `3`, `구성품 · 싱글 구성품_단가인상` 삭제 `3`, `구성품 · 상업멀티 구성_단가인상` 삭제 `0`이다. 구성품 행 합 `3+0=3`은 API의 `totalSoftDeletedComponentRows=3`과 같다. 연결 occurrence도 화면 `1,447+154=1,601`과 API 총계 `1,601`이 같다.

Playwright 원문:

```text
Running 1 test using 1 worker
{"measuredAt":"2026-08-09T07:19:07.971Z","totalPreservedManualProductOccurrences":0,"totalPreservedManualComponentOccurrences":2,"totalSkippedOccurrences":130,"totalComponentLinkOccurrences":1601,"totalSoftDeletedComponentRows":3}
```

조회·조인 키는 일회용 실 PostgreSQL을 READ ONLY transaction으로 측정했다.

```text
product_active=3084
product.model_code filled=3084/3084 (100.00%)
component_active=1598
bundle_component.bundle_product_id filled=1598/1598 (100.00%)
bundle_component.component_product_code filled=1598/1598 (100.00%)
```

미해소 부모 14행은 모두 `QA797-SET-01` 또는 `S3-1111-GUARD-*`가 soft-delete된 뒤 남은 QA 행이고, 미해소 자식 2행도 `created_by=qa798`의 `QA797-PART-01/02`다. 사용자 지시대로 이 PR의 결함으로 세지 않았다. 이 14행을 제외한 비-QA 표본은 부모·자식 조인 모두 `1,584/1,584 (100.00%)`다. SQL은 `BEGIN TRANSACTION READ ONLY`와 `ROLLBACK`으로 끝냈고 INSERT는 하지 않았다.
