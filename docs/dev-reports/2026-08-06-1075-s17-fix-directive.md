# PR #1078 · 이슈 #1075 — S17 SOL fix 지시서

## 1. 좌표 · 판정 · 재현 난이도

**판정: 실 사용자 경로 재현 결함 2건 · BLOCK · 머지 권고하지 않는다.**

PM이 제시한 둘 외에 **셋째 방식**이 실제 구현이다. S16은 별도 API 필드를 추가하거나 카탈로그 문자열과 비교해 추론하지 않는다. `specification` 문자열 앞에 zero-width `U+2060`을 붙여 provenance를 기존 필드 안에 운반한다.

### F1 — 자동 규격 50자는 저장할 수 없다

- 좌표: `clients/desktop/src/renderer/utils/estimateSpecificationProvenance.ts:5-13` — 자동 규격 앞에 `U+2060` 한 글자를 추가한다.
- 좌표: `clients/desktop/src/renderer/routes/EstimateFormPage.tsx:1677` — 표시 규격을 encode한 값을 저장 요청에 넣는다.
- 좌표: `services/slip-service/src/main/java/com/samhanair/logis/slip/estimate/web/dto/CreateEstimateRequest.java:36`, `UpdateEstimateRequest.java:64` — 서버 계약은 `specification` 전체 문자열을 `@Size(max=50)`로 검사한다.

실 API `http://localhost:8080`에서 화면과 같은 encoded 문자열로 재현했다.

```text
U+2060 + 표시 49자  POST 201
GET 재조회          Java/JS 길이 50 · 첫 코드포인트 8288(U+2060) · 뒤 49자 동일
다른 계정 GET       동일 값 왕복

U+2060 + 표시 50자  POST 400
INVALID_INPUT: lines[0].specification: size must be between 0 and 50
```

즉 marker는 실제 백엔드·DB 저장→재조회와 다른 계정 경계에서 살아남는다. 그러나 기존 서버가 허용하는 표시 규격 50자의 마지막 한 글자를 provenance가 잠식한다. 품목 카탈로그의 `Product.specification`은 255자 컬럼이므로(`services/product-service/.../Product.java:268`), 50자 자동 규격은 생성 가능한 실제 사용자 입력이다.

**재현 난이도: 보통.** 규격이 정확히 50자인 품목을 견적에서 확정해 저장하면 매회 400이다. API에서는 위 payload로 매회 재현한다.

### F2 — 원격 자동 규격을 받은 coedit 소비자가 USER로 오분류한다

- 좌표: `clients/desktop/src/renderer/routes/EstimateFormPage.tsx:374-388` — 원격 규격 값이 이전 값과 다르면 provider의 `specificationSource=CATALOG`보다 값 변경 판정을 우선해 무조건 `USER`로 만든다.
- 좌표: `clients/desktop/src/renderer/routes/EstimateFormPage.tsx:1536-1561` — 품목 해제는 로컬 source가 `CATALOG`일 때만 규격과 provider source를 지운다.
- 좌표: `clients/desktop/src/renderer/realtime/createCoeditProvider.test.ts:456-485` — S16의 두 소비자 테스트는 Y.Doc 셀을 직접 비운다. 실제 `EstimateFormPage` 소비자의 수신 분류와 품목 해제 핸들러를 통과하지 않는다.

실 제품 컴포넌트에 원격 행 `specification=REMOTE-CATALOG-SPEC`, `specificationSource=CATALOG`를 수신시킨 뒤 수신 소비자에서 모델명을 지우고 blur하는 임시 RED를 실행했다.

```text
Expected: specification = ''
Received: specification = 'REMOTE-CATALOG-SPEC'
Test Files 1 failed
Tests      1 failed | 43 skipped
```

수신 소비자의 로컬 provenance만 `USER`로 갈라져 `hadAutoSpecification=false`가 되고, 제거한 품목의 자동 규격이 화면과 coedit 문서에 남는다.

**재현 난이도: 쉬움.** 두 소비자에서 한쪽이 빈 규격 행에 자동 규격 품목을 확정하고, 다른 쪽이 수신한 뒤 그 품목을 해제하면 매회 재현한다.

## 2. 불변식

- provenance 때문에 사용자가 입력·선택할 수 있는 기존 표시 규격 최대 길이가 줄어서는 안 된다.
- 자동 규격은 저장→브라우저 완전 종료→다른 계정/기기 재조회 뒤에도 자동값으로 판정되어야 한다.
- 사용자 직접 규격은 같은 경계 뒤에도 USER로 남고, 자동 원문으로 직접 되돌린 경우도 USER여야 한다.
- 두 coedit 소비자는 값과 provenance를 함께 같은 의미로 해석해야 한다. 원격 값 변경이라는 이유만으로 명시적인 `CATALOG`를 `USER`로 덮어쓰지 않는다.
- 어느 소비자에서 해제하든 자동 규격은 양쪽과 문서에서 제거되고, 사용자 규격·사용자 단가·다른 라인 값은 보존되어야 한다.
- 다른 품목 재확정, 라인 삭제 후 재입력, 후보 모달 취소, F1 모달 전환, 판매전표 공용 `ProductAutocomplete`, UUID 비노출 계약을 유지한다.
- provenance의 표현·저장 위치·API 구조는 구현 수단이므로 이 지시서가 정하지 않는다.

## 3. 양방향 RED · 동시 GREEN

### RED-A — 저장 길이 경계와 provenance 왕복

1. 표시 규격 49자와 50자인 자동 규격을 각각 실제 저장 요청으로 보낸다.
2. 둘 다 저장되고, 서버 응답과 완전 재접속 GET 뒤 화면에는 원문만 정확히 보여야 한다.
3. 품목 해제 뒤 둘의 자동 규격만 제거되어야 한다.
4. 같은 길이의 사용자 직접 규격은 저장·재조회 뒤 보존되어야 한다.
5. 자동 원문을 한 글자 수정했다 되돌린 USER 규격도 저장·재조회·해제 뒤 보존되어야 한다.

### RED-B — 두 실제 소비자 수렴과 반대급부

1. 소비자 A가 자동 규격을 반영하고 소비자 B가 원격으로 수신한다.
2. B에서 품목을 해제하면 A·B·coedit 문서 모두 자동 규격과 provenance가 공란으로 수렴해야 한다.
3. 같은 시나리오를 A에서 해제해도 동일해야 한다.
4. A 또는 B가 규격을 직접 고친 뒤 해제하면 두 화면과 문서에서 사용자 규격이 보존되어야 한다.
5. 새 품목에 규격이 있으면 새 자동값으로, 없으면 이전 자동값 없는 상태로 수렴해야 한다.
6. 사용자 단가·다른 라인 규격/단가·후보 취소·F1 전환·판매전표 단건/다건 후보 경로를 함께 단정한다.

## 4. 이번에 하지 말 것

- 표시 길이 제한을 조용히 49자로 낮추거나 서버 validation만 완화해 DB 제약에 떠넘기지 않는다.
- 모든 저장 규격을 USER 또는 CATALOG 한쪽으로 일괄 분류하지 않는다.
- 원격 규격 값 변경을 전부 USER로 보는 기존 우선순위를 다른 provenance 필드에도 복제하지 않는다.
- 사용자 규격 보존을 위해 자동 규격 회수를 포기하거나, 자동 규격 회수를 위해 사용자 규격·단가를 지우지 않는다.
- 판매전표의 독립 규격 정책, 가격기억, VAT 권위, 라인 구조, 저장 유효성 규칙을 함께 재설계하지 않는다.
- Docker 재빌드·재배포·중지, DB 직접 쓰기, vendor 발송, 다른 트랙 `#1057`·`#1066`·`#1069` 변경을 하지 않는다.
- 기존 단정을 삭제·완화하거나 timeout 증가로 통과시키지 않는다.
