# PR #1164 / Issue #1163 — SOL 5.6 머지 전 최종 적대검증

## 판정

**실 사용자 경로 도달 결함 1건. 머지 불가.**

원 결함인 창고 이력 UUID 8자 폴백과 inventory `callerId → actorName` 저장은 닫혔다. R2/R3의 정상 이름 소실과 이중 decode도 재발하지 않았다. 그러나 이번 표시 가드는 `trim()`이 제거하지 않는 Unicode format 문자(U+200B)를 “이름 있음”으로 취급한다. 그 결과 사용자 이름을 U+200B 하나로 만들면 변경자 자리가 빈칸이 되고, `U+200B + canonical UUID`이면 UUID 판별도 우회해 화면에는 canonical UUID가 그대로 보인다.

현재 HEAD는 `3a3db509aad1bf1fe09738c949b781c8c9a95ecf`다. R6의 미커밋 live-spec 수정(+50/-4)과 `docs/dev-reports/2026-08-11-1163-r6-fix-directive.md`가 있는 상태에서 검증했으며 git 상태를 바꾸는 명령은 사용하지 않았다.

## 결함 1 — HIGH: 보이지 않는 format 문자가 빈 변경자와 UUID 가드 우회를 만든다

### 실 사용자 경로

1. 사용자 관리 이름 입력은 `fullName.trim()`으로 저장·활성 여부를 판단한다 (`UsersPage.tsx:671-672,790,928-929,957`). JavaScript `trim()`은 U+200B를 제거하지 않는다.
2. 사용자 생성 계약은 `@NotBlank @Size(max=50)`이다 (`AdminUserCreateRequest.java:25`). 실제 Jakarta Validator로 `fullName="\u200B"`를 검증했으며 위반 0건으로 통과했다. auth 동기화도 `@NotBlank @Size(max=100)`뿐이다 (`CreateAccountInternalRequest.java:20`, `UpdateDisplayNameInternalRequest.java:8`).
3. gateway는 이름을 1회 URL encode하고 (`JwtAuthenticationGatewayFilterFactory.java:257-264`), `UserHeaderDecodingFilter`는 1회 decode한다. U+200B는 C0/C1 제어문자가 아니어서 유지된다. 기존 필터 테스트도 `Alice\u200BBob` 보존을 명시한다 (`UserHeaderDecodingFilterTest.java:63-72`).
4. `WarehouseController` 네 쓰기 경로는 값을 재decode하지 않고 그대로 서비스에 넘긴다.
5. `WarehouseService.resolveActorName`의 `isBlank()`와 `trim()`도 U+200B를 빈 값으로 보지 않는다. `UUID.fromString`은 U+200B가 붙은 canonical UUID를 UUID로 인식하지 못하므로 그대로 `recordBatch(... actorName ...)`에 저장한다 (`WarehouseService.java:387-403`). 임시 표적 테스트에서 U+200B가 네 경계와 저장 경계를 그대로 통과했고 inventory 테스트는 `BUILD SUCCESSFUL`이었다.
6. `displayWarehouseActor`는 `!actorName`도 false, `UUID_RE.test(actorName.trim())`도 false라 U+200B를 그대로 반환한다 (`EditWarehouseModal.tsx:333-337`).

### 사용자에게 보이는 결과

- `actorName="\u200B"` → `#1 ·  26...`처럼 변경자 자리가 빈칸이다.
- `actorName="\u200B123e4567-e89b-12d3-a456-426614174000"` → U+200B는 보이지 않고 canonical UUID 전체만 보인다.
- 현재 공유 DB의 활성 계정/감사행에는 U+200B 표본이 없어 DB write 재현은 하지 않았다. 하지만 사용자 생성 검증→gateway/filter→inventory 저장→renderer 각 경계를 실제 코드와 표적 테스트로 연결했다.

시각 증거: `docs/qa/2026-08-11-1164-final/warehouse-zero-width-actor-blank.png`. 실 로그인·실 gateway·현재 renderer를 사용하고, 공유 DB write 금지 때문에 감사 조회 응답의 `actorName` 한 필드만 U+200B로 결정론적으로 대체했다. 실행 원문은 `1 passed (2.1s)`이며 로그의 `panelText`는 `#1 · ​ 26...`이었다. 이 캡처를 실 DB 신규 쓰기 E2E로 과장하지 않는다.

## 첫 각도 — fix가 정상 경로를 막았는가

### 과잉 UUID 은닉

임시 RED-B로 다음 정상 식별자를 프런트와 `WarehouseService`에 통과시켰다.

```text
1-1-1-1-1
김%감사
김+감사
김%20감사
%EA%B9%80
```

프런트 5/5, 서비스 5/5가 원문 보존으로 통과했다. #1134 R13의 `1-1-1-1-1` 과잉 은닉은 재발하지 않았다. UUID 판별은 canonical 36자와 정확히 같은 경우만 숨긴다. 다만 U+200B처럼 보이지 않는 문자가 canonical UUID 앞에 붙으면 너무 좁아지는 반대 결함이 이번에 확인됐다.

### decode 횟수와 실 데이터

```text
gateway URLEncoder 1회
→ UserHeaderDecodingFilter URLDecoder 1회
→ WarehouseController 0회
→ WarehouseService 0회
```

`김%감사`, `김감사`, `김%20감사`, `%EA%B9%80`, `김+감사`가 실제 필터 체인을 거쳐 네 쓰기 서비스 경계에 원문 그대로 도달했다. 활성 계정 32개를 읽기 조회한 결과 UUID형/blank/%/+ 이름은 각각 0개, 한글 이름은 27개였다. 현재 실 로그인 이름 `[DEV-SEED] 개발마스터`는 이미 디코드된 한글 표본이며 라이브 화면 상단에서 그대로 보였다. 즉 `%`·`+` 실 DB 표본은 없다고 기록하고 synthetic 표적 테스트 결과를 실데이터로 과장하지 않는다.

### 이름 부재 표시

- `null`/빈 문자열/canonical UUID는 `변경자 미상`으로 표시된다.
- U+200B-only는 빈칸으로 표시된다 — 본 라운드 결함.
- SYSTEM actor는 계속 `시스템`이다.

## LUNA fix 지시서

### 불변식

모든 창고 이력 revision의 변경자 표시는 정확히 다음 셋 중 하나여야 한다.

1. system sentinel actorId → `시스템`
2. null/empty/Unicode space·format-only/canonical UUID(보이지 않는 space·format 문자로 감싼 경우 포함) → `변경자 미상`
3. 그 외 정상 이름 → 사용자가 식별 가능한 원문 표시

UUID 전체·앞 8자는 0회 노출이어야 한다. `1-1-1-1-1`, 한글, `%`, `+`, 이미 디코드된 문자열은 UUID로 오인해 숨기거나 다시 decode하지 않는다.

### 좌표 전수

```text
입력 UI       UsersPage.tsx:671-672,790,928-929,957
user 계약     AdminUserCreateRequest.java:25
              AdminUserUpdateRequest.java:19
auth 계약     CreateAccountInternalRequest.java:20
              UpdateDisplayNameInternalRequest.java:8
gateway       JwtAuthenticationGatewayFilterFactory.java:257-264
decode        UserHeaderDecodingFilter.java:45-58,113-124
네 쓰기       WarehouseController.java:149-156,205-212,225-231,261-268
저장          WarehouseService.java:371-403
표시          EditWarehouseModal.tsx:333-337,359-364
테스트        WarehouseControllerUserNameContractTest
              WarehouseServiceTest
              EditWarehouseModal.test.tsx
```

### 재현 데이터

```text
A  actorName = U+200B                       → 현재 변경자 빈칸
B  actorName = U+200B + canonical UUID      → 현재 visually UUID 전체 노출
C  actorName = canonical UUID + U+200B      → 동일 우회 가능
정상 대조 = 1-1-1-1-1, 김%감사, 김+감사, 김%20감사, %EA%B9%80
```

### RED-A — 구체적 표적

1. `AdminUserCreateRequest`와 수정/내부 동기화 경계에서 U+200B-only 등 “표시 가능한 문자가 0개”인 이름을 거절한다. desktop 버튼도 같은 입력을 활성화하지 않는다.
2. gateway encode + 공통 filter decode를 실제로 거친 U+200B-only 및 U+200B+UUID가 네 warehouse 쓰기 경계에 들어왔을 때 `recordBatch.actorName`은 null이어야 한다. decode 횟수는 계속 정확히 1회다.
3. `EditWarehouseModal`에 A/B/C를 직접 주입하면 모두 `변경자 미상`이며 canonical UUID 전체·앞 8자가 0회여야 한다.
4. 공백 판정과 UUID 판정은 같은 “표시용 정규화 결과”를 사용해야 한다. raw 문자열에는 UUID가 아니지만 보이는 결과는 UUID인 조합을 놓치면 실패다.

### RED-B — 구체적 정상 경로

1. `1-1-1-1-1`, `김%감사`, `김+감사`, `김%20감사`, `%EA%B9%80`는 네 쓰기와 화면에서 원문 그대로 남는다.
2. 일반 한글 `[DEV-SEED] 개발마스터`, SYSTEM→`시스템`, null→`변경자 미상`, canonical UUID→`변경자 미상`을 유지한다.
3. `fieldName && fieldName !== 'isDeleted'` 되돌리기 조건과 감사행 자체의 존재를 유지한다.
4. 혼합 이름 `김\u200B감사`는 빈 이름으로 오인하지 않는다. format 문자 제거/정규화 정책을 택한다면 사용자에게 보이는 결과가 `김감사`인지 원문인지 테스트에 명시한다.

### fix가 만드는 새 조합

- 보이지 않는 문자 + canonical UUID 앞/뒤
- 보이지 않는 문자만 있는 이름
- 보이는 한글/영문 사이의 U+200B
- NBSP/U+FEFF/U+00AD 등 Unicode space·format 변형
- SYSTEM actorId + 악성/정상 actorName
- null/blank actorName + 비system actorId
- `%`, `+`, `%20`가 format 문자와 함께 있는 이름

전역 `\W` 또는 하이픈 개수 같은 넓은 UUID 판별로 바꾸지 않는다. 그러면 #1134 R13의 정상 식별자 은닉이 재발한다.

**제 전제가 틀렸다면 고치지 말고 중단·보고하십시오.** 특히 실제 사용자 생성/수정 경계가 U+200B를 이미 거절하거나, gateway/filter가 U+200B를 저장 경계 전에 제거한다는 재현 증거가 나오면 본 지시대로 수정하지 말고 그 원문을 보고해야 한다.

LUNA fix 후 SOL이 위 RED-A/RED-B와 라이브 read-only UI를 다시 검증한다. 도달 결함 0이 되기 전에는 PM에 머지 가능으로 보고하지 않는다.

## 이 라운드가 보지 않은 표면

- 공유 DB write 금지 때문에 새 inventory backend의 수정·삭제·복원·되돌리기 실제 저장 E2E는 실행하지 않았다.
- 현재 배포 inventory는 PR backend가 아니므로 신규 `actorName` 저장 결과를 live DB에서 확인하지 않았다.
- slip live 컨테이너와 체크인 소스의 actorName 정제 차이는 원인을 확정하지 못했다.
- actor 표시 7개는 정적/데이터 흐름으로 전수했지만, warehouse 외 6개 화면을 모두 클릭 캡처하지는 않았다.
- actor 계열이 아닌 모든 업무 UUID 표시 화면 전체를 라이브 순회하지는 않았다. 정확한 8자 절단 client grep은 전수했다.

## QA 잔재 분리

창고 코드 `2`/`00003`, `QA-1039-*`, S18 전표 등은 `created_at/created_by`로 QA 산물임을 확인했으며 화면의 이름·메모 깨짐이나 데이터 값 자체를 결함으로 세지 않았다. 이번 결함은 QA 값이 아니라 사용자 이름 검증을 통과하는 U+200B 데이터 흐름이다.
