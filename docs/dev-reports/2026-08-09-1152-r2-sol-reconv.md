## 결함 1 — 견적 변환 GOODS/혼합 전표는 창고를 확정할 수 없어 수락 409

### 실 사용자 경로

1. 등록 상품 또는 상품+비상품 혼합 견적을 생성한다.
2. 견적을 출고전표로 전환한다.
3. 변환된 전표를 저장하고 전송한다.
4. 전표 수락을 누른다.
5. 재고 예약이 `00000000-0000-0000-0000-000000000001` 창고를 조회하고 404를 반환하며, slip-service가 이를 409로 변환한다.

### 실제 재현

- GOODS 전표: create 201 → convert 200 → save 200 → send 200 → accept **409**.
- 혼합 전표: create 201 → convert 200 → save 200 → send 200 → accept **409**.
- 혼합 전표 응답 원문:

```text
inventory-service 호출 실패(404 NOT_FOUND):
{"code":"NOT_FOUND","message":"창고를 찾을 수 없습니다"}
```

- 두 전표의 DB `source_warehouse_id`는 `00000000-0000-0000-0000-000000000001`이었다.
- 실패 전후 GOODS balance는 `available|reserved|total = 3|1|4`로 불변이었다.
- 대조군 NON_GOODS 전표는 같은 변환 임시 UUID여도 재고 게이트가 창고 조회 전에 no-op하므로 create/convert/save/send/accept가 모두 성공하고 `ACCEPTED`가 됐다.

### 원문 근거

- `EstimateToSlipConverter.java:78-81` — 변환 전표에 임시 UUID를 하드코딩하고 "SlipForm 수정 시 교체"한다고 적는다.
- `CreateSlipRequest`에는 `sourceWarehouseId`가 있지만 기존 전표 수정 DTO인 `EditHeaderRequest`, `UpdateSlipRequest`, `SlipUpdateRequest`에는 해당 필드가 없다.
- desktop `SlipFormPage.tsx:1864`는 `sourceWarehouseId`를 신규 `createSlip` payload에만 보낸다.
- `SlipService.accept():944-957`은 OUTBOUND 각 라인을 inventory 예약으로 보낸다.

즉 R2의 비상품 게이트는 R1 경로를 열었지만, 같은 사용자 경로에서 막아야 할 GOODS와 혼합 전표가 정상 예약 단계까지 도달하지 못한다.

## 결함 2 — 실사 완료 한 단계가 NON_GOODS 재고를 실제 조정한다

### 실 사용자 경로

1. GOODS 품목을 입고해 재고 2를 만든다.
2. 견적품목 메뉴에서 해당 품목을 `NON_GOODS`로 전환한다.
3. 해당 창고 재고 실사를 생성하고 시작한다.
4. 실물 수량을 1로 입력하고 실사를 완료한다.
5. 비상품인데도 balance가 2→1로 줄고 `ADJUST` movement가 1건 생긴다.

### 실제 재현

정확한 HEAD inventory API와 일회용 DB에서 "재고 생성 당시 `goods=true`, 이후 조회 `goods=false`" 경계를 고정해 실제 실사 API를 밟았다.

```text
입고                         2
실사 생성                    PLANNED, lines=1, expected=2
실사 시작                    IN_PROGRESS
실물 입력                    actual=1, diff=-1
실사 완료                    COMPLETED
완료 후 balance              1|0|1
생성된 ADJUST movement       1
```

### 원문 근거

- `InventoryAuditService.create():106-130` — 창고의 모든 active balance를 snapshot하며 조회한 `ProductSummary`의 `goods/productType`을 필터하지 않는다.
- `InventoryAuditService.complete():247-253` — 차이가 있는 모든 라인을 `adjustStockForLine()`에 전달한다.
- `InventoryAuditService.adjustStockForLine():361-379` — product 조회/`isInventoryExcluded` 게이트 없이 `balance.adjust()`와 `ADJUST` movement를 실행한다.

V25는 최초 후보 34건의 기존 행만 차단한다. 이후 UI에서 기존 GOODS를 NON_GOODS로 바꾸는 정상 기능에는 적용되지 않으므로 이 경로는 도달 가능하다.

## R1 경로와 양방향 결과

### 단일 NON_GOODS 정상 경로

실제 HTTP 사용자 체인:

```text
견적 생성 201 (QUOTE_DRAFT)
→ 전표 전환 200 (QUOTE_CONVERTED)
→ 전표 저장 200 (SAVED)
→ 전송 200 (SENT)
→ 수락 200 (ACCEPTED)
```

해당 product의 `stock_balances`는 0행이었다. 따라서 R1의 "NON_GOODS 수락 시 예약 409"는 R2에서 해소됐다.

### GOODS가 여전히 막히고 실제 예약되는가

일회용 DB 실제 HTTP 결과:

```text
GOODS 입고 5
reserve 2  → available=3, reserved=2, total=5
reserve 4  → HTTP 409
409 뒤     → available=3, reserved=2, total=5 (원자성 유지)
release 1  → available=4, reserved=1
deduct 1   → available=4, reserved=0, total=4
```

즉 inventory 경계에서는 부족 409와 실예약/해제/차감이 유지된다. 다만 결함 1 때문에 견적 변환 GOODS 전표는 이 정상 예약 경계까지 도달하지 못한다.

### 혼합 라인

- inventory 경계를 같은 `referenceId=SLIP`로 순서 호출하면 GOODS만 `available 4→3`, `reserved 0→1`이 되고 NON_GOODS는 0/no-op이며 비상품 balance 0행을 유지했다.
- 실제 견적→전표 사용자 체인은 결함 1의 임시 창고 때문에 accept 409가 되어 전표가 `SENT`에 남았다.
