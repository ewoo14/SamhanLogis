## 머지 차단 도달 결함

### R10-SOL-1 — 상대의 정상 저장을 전 행 삭제로 오인한다

R9가 추가한 `previousServerLineIds` 선삭제는 “이전 ID가 현재 REST에 없으면 그 행은 원격 삭제행”이라고 가정한다. 그러나 매출 수정 BE는 정상 PUT에서도 `Slip.replaceSalesLines`를 호출하여 **기존 활성 라인 전부를 soft-delete한 뒤 요청 라인을 새 엔티티로 전량 교체**한다. 따라서 상대가 수량·메모만 정상 수정해도 모든 line ID가 바뀐다. 이전 ID와 현재 ID의 차집합은 실제 삭제행 집합이 아니다.

사용자 조작 순서:

1. 사용자 A와 B가 같은 수정 가능 판매전표의 수정 모드에 진입한다.
2. B는 자기 화면의 수량 또는 메모를 편집해 아직 저장하지 않는다.
3. A는 품목·행 수를 바꾸지 않고 수량 또는 메모만 수정해 저장한다.
4. BE `SalesSlipUpdateService.update` → `slip.replaceSalesLines(...)`가 기존 라인을 전부 soft-delete하고 새 ID 라인으로 교체한다.
5. `slip:edit` SSE가 B의 `['slip', id]`를 invalidate한다. 갱신된 상세 응답은 새 ID, B의 `previousServerLineIds`와 Y.Doc은 이전 ID다.
6. `reseedCoeditLineIds(nextProvider, newIds, oldIds)`가 Y.Doc의 모든 확정행을 “삭제행”으로 판정해 먼저 제거한다.

잘못된 결과 원문(현재 함수를 실제 실행한 상태 전이):

```text
BEFORE=[{"lineId":"11111111-1111-1111-1111-111111111111","productId":"product-1","quantity":"7","note":"정상 편집 보존값"},{"lineId":"22222222-2222-2222-2222-222222222222","productId":"product-2","quantity":"9","note":"정상 편집 보존값2"},{"lineId":"<client-id>","productId":"","quantity":"0","note":""}]
STALE=true
AFTER=[{"lineId":"<client-id>","productId":"","quantity":"0","note":""}]
```

즉 B 화면에는 미확정 trailing 빈행 하나만 남고, 서버에 정상 존재하는 두 확정행과 B의 미저장 수량·메모가 모두 사라진다. `persistedDetailLines(...).length === 0`이므로 저장 버튼도 비활성화된다. “원격 수량·메모 편집 보존”이라는 재시드 목적과 정반대 결과다.

실 데이터 영향 건수:

- R9 자체가 산정한 수정 가능 OUTBOUND **2,174문서·기존 라인 2,407개** 전부가 이 경쟁 조건의 대상이다.
- 1라인 문서도 상대 정상 저장 후 그 1행이 사라지고, 다라인 문서는 전 행이 함께 사라진다. 특정 품목·세트 여부와 무관하다.

근거 연결:

- `SlipDetailPage.tsx`: SSE가 모든 전표 이벤트에서 `['slip', id]`를 invalidate한다.
- `SlipDetailPage.tsx`: 갱신된 `slipData.lines`와 이전 React state에서 각각 현재/이전 ID 집합을 만든 뒤 R9 재시드를 호출한다.
- `coeditLineIds.ts`: 현재 집합에 없고 이전 집합에 있는 ID의 행을 즉시 `provider.items.delete`한다.
- `SalesSlipUpdateService.java`와 `Slip.java`: 정상 매출 PUT이 `replaceSalesLines`로 기존 라인을 전량 soft-delete하고 신규 라인을 추가한다.

## 새 표면별 판정

### 1. 확정행의 품목 선택기 제거 후 되돌림 경로

별도 도달 결함은 확인하지 않았다.

- 확정행의 품목 셀은 읽기 전용 `<span>`이지만 같은 행 끝의 `N번 행 삭제` 버튼은 `disabled` 조건 없이 남아 있다.
- 마지막 확정행을 삭제해도 `removeLinePreservingMinimum(..., 1)`이 최소 한 행을 유지하고, 그 행은 `productId=''`인 미확정 빈행이다.
- 따라서 잘못 고른 확정행은 `×`로 삭제 → 빈행 자동완성에서 다시 선택할 수 있다.
- 기존 실 QA의 `03-edit-mode-before-input` → `04-after-last-line-delete`는 이 삭제 도달성을 보여 주지만 R9 HEAD 이전 캡처이므로, R10 새 렌더의 라이브 증거로 과장하지 않았다. R9 diff는 삭제 버튼·삭제 함수에는 손대지 않았다.

### 2. 빈행 확정 직후 선택기 소멸

별도 도달 결함은 확인하지 않았다. 품목 선택 직후 해당 행은 `<span>`으로 바뀌지만 같은 행의 `×`는 유지된다. 새 확정행은 `lineId=null`이어도 안정 `key`로 제거되고, 그 아래 trailing 빈행이 계속 남는다. 확정 해제는 인라인 재선택이 아니라 “행 삭제 후 새 빈행에서 재선택” 경로다.

### 3. 최초 진입·연속 삭제·동시 삭제의 이전 ID

- 빈 Y.Doc 최초 진입은 `isEmpty()` 분기에서 서버 상세 전체를 seed하므로 R9 선삭제를 타지 않는다.
- 실제 서버 행 삭제처럼 생존 행 ID가 유지되는 경우에는 R9의 단일·중간 삭제 상태 전이가 삭제행을 제거하고 생존행을 보존한다.
- 그러나 “이전 ID가 낡음”의 핵심 실경로는 위 R10-SOL-1이다. 정상 PUT이 전 ID를 갱신하므로 값이 단순히 조금 낡는 것이 아니라 모든 정상행을 삭제행처럼 만든다. 연속·동시 저장에서도 같은 오판이 반복된다.

### 4. 정상 편집의 삭제 오인

**도달 결함 확인. R10-SOL-1과 동일하다.** 수량·메모만 바꾼 정상 PUT도 BE 라인 ID 전량 교체 때문에 전 행 삭제로 오인된다.

### 5. 저장 payload의 확정 새 라인 포함·미확정 빈행 제외

두 조건은 코드상 동시에 성립한다.

- 품목을 선택한 새 행은 `productId`가 생기므로 `persistedDetailLines`에 포함되고 `lineId=null` 신규 라인 payload가 된다.
- trailing 빈행은 `productId`가 비어 있어 같은 필터에서 제외된다.
- 대상 계약 테스트 107건을 직접 실행해 이 필터·lineId 상태 전이가 통과함을 확인했다. 다만 이는 위 2세션 정상 저장 오판을 다루지 않는다.

## 증거 무결성

- R10 HEAD 새 UI를 라이브 브라우저로 조작했다는 주장은 하지 않는다. 이 세션에는 제어 가능한 인앱 브라우저가 없었다.
- 고정 실 데이터에 PUT/DELETE를 보내지 않았고 DB 직접 쓰기도 하지 않았다. 따라서 R10-SOL-1은 무변경 함수 실행으로 재현하고, 실제 BE의 전량 교체 원문 및 SSE 재조회 연결로 도달성을 확정했다.
- `renderer-real-qa*.log`는 읽거나 수정하지 않았다. 조사 중 이미 수정 상태였던 두 파일은 잔여 프로세스 소유 변경으로 보며 본 리뷰 산출물에 포함하지 않는다.
- 조사 중 `npm test -- --run ...`은 pretest의 로컬 파생물 신선도 가드에서 본 테스트 실행 전에 중단됐다. 검증 품질 결함으로 취급하지 않았고, 같은 대상은 `npx vitest run ...`으로 직접 실행했다.

## 이 라운드가 보지 않은 것

- 견적·이동·분개는 재측정하지 않았다.
- 컨테이너 재빌드·재시작, DB 직접 조회·쓰기, 실 전표 PUT/DELETE는 하지 않았다.
- R10 HEAD의 실제 Chromium 화면 캡처, 실제 2브라우저 동시 저장은 제어 가능한 브라우저 부재 때문에 수행하지 않았다.
- 품목 자동완성 모달의 판매전표 예외 `resultSelectionMode={null}`는 확정 사양으로 받아 재논쟁하지 않았다.
- 검증 품질·테스트 충분성은 찾거나 결함으로 보고하지 않았다.
