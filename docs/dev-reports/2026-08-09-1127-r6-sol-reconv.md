## 결함 1 — 구성품 soft-delete row가 화면에서 항상 0으로 소실된다

실 사용자 경로는 `MASTER → 설정 → 시트 동기화 → 구성품 결과 행 → 삭제(softDeletedProductRows) 열`이다.

백엔드 응답 계약은 `ComponentSyncResult.softDeletedComponentRows`다.

- `clients/desktop/src/renderer/api/sheetSyncApi.ts:44` — `softDeletedComponentRows?: number`
- `services/product-service/src/main/java/com/samhanair/logis/product/service/ProductSheetSyncService.java:462` — 실제 삭제마다 증가

그러나 화면 변환기는 존재하지 않는 구성품 필드 `result.softDeletedProductRows`를 읽는다.

- `clients/desktop/src/renderer/routes/admin/sheetSyncRows.ts:36` — `softDeletedProductRows: result.softDeletedProductRows`
- `clients/desktop/src/renderer/routes/admin/sheetSyncRows.ts:51` — `undefined ?? 0`

임시 적대 fixture 원문은 `byComponentTab: { 구성품: { softDeletedComponentRows: 3 } }`였다. `rows[0].result.softDeletedProductRows === 3`을 단정해 관련 Vitest를 실행한 결과:

```text
expected +0 to be 3
COMPONENT_SOFT_DELETE_RED_EXIT=1
```

임시 테스트는 즉시 제거했다. 원문 테스트 파일 SHA-256은 전후 모두 `292E8865622F33C26CA8A03FC426DD00C586A4BCA05A098B03686A55C0A1CE01`, `git diff --exit-code`는 0이고 원래 2 tests는 다시 GREEN이다.

최종 원문 변환 테스트도 `2 tests / 0 failures`, 종료 0이다. `typecheck:real-qa`의 cleanup 2건과 scope 49건은 통과했으나 공식 집합 단정 1건은 이 라운드의 신규 스펙이 commit 금지에 따라 미추적이라는 이유로만 실패했다. 원문 메시지는 `1127-r6-sol-reconv-real-qa.spec.ts`가 “디스크에는 있지만 Git 추적 목록에는 없는 스펙”이라는 것이며, 애플리케이션 타입/동작 실패로 사용하지 않았다.

## 결함 2 — 이름 변경 소비자 전수가 아니다

현재 실 화면 캡처에도 열 머리글이 `신규 (insertedRows)`, `변경 (updatedRows)`, `삭제 (softDeletedProductRows)`로 남는다. 특히 구성품 `linkedOccurrences`는 신규 link가 아니라 기존 link 재처리까지 포함하는 occurrence인데 `신규 (insertedRows)` 열로 표시된다. 이는 R6가 선언한 단위 계약과 정면으로 다르다.

같은 옛 이름이 현재 운영 로그/Javadoc/테스트에도 남아 있다.

- `ProductSheetSyncService.java:289` — `insertedRows/updatedRows/softDeletedProductRows/skippedOccurrences`
- `ProductSheetSyncService.java:1461` — `insertedRows/updatedRows/unchanged/softDeletedProductRows/skippedOccurrences/preservedManualProductOccurrences`
- `ProductSheetSyncScheduler.java:93,139` — Product sync 로그의 `insertedRows/updatedRows/softDeletedProductRows`
- `ProductSheetSyncService.java:2113-2114` — Javadoc의 `skippedOccurrences`, `preservedManualProductOccurrences`
- `clients/desktop/src/renderer/routes/admin/sheetSyncRows.test.ts:5-9,36,41` — `insertedRows/updatedRows/unchanged/softDeletedProductRows/skippedOccurrences/linkedOccurrences/bundlesMarked` 옛 fixture

기존 화면 테스트는 숫자를 단정하지 않아 이 계약 이탈을 놓친다. 실제로 원문 테스트 2건은 GREEN인데 결함 1의 `3 → 0` 적대 fixture만 RED였다. 따라서 “API·화면·로그·테스트 소비자 전수 갱신” 주장은 원문과 일치하지 않는다.

## ① R5 3건 독립 재측정

2026-08-09 12:52:39.321 KST, Google Sheets API v4 readonly 2개 구성품 탭과 공유 `product_db` readonly 결합 결과:

```text

component_valid_occurrences=1639
component_skipped_missing_occurrences=37
manual_component_preserved_occurrences=2

```

R5 3건 자체는 R6 구현과 일치한다.

- Product 수동 보존 `0`과 구성품 수동 보존 occurrence `2`는 `totalPreservedManualProductOccurrencesProductOccurrences` / `totalPreservedManualProductOccurrencesComponentOccurrences`로 분리된다.
- `syncAll()`은 Product skip과 구성품 `cr.skippedOccurrences`를 모두 `totalSkippedOccurrencesOccurrences`에 더하므로 현재 구성품 skip 37이 total에 포함된다.
- 연결은 고유 link 1,581이 아니라 처리 가능한 시트 row occurrence 1,600이며 이름도 `linkedOccurrences` / `totalComponentLinkOccurrences`로 occurrence를 선언한다.

## ② suffix 강제 테스트 GREEN → 임시 위반 RED → 복구 GREEN

## ③ 카운터 계열 독립 전수

`ProductSheetSyncService` 공개 정수 카운터를 reflection 가드와 소스 증가·합산 지점으로 다시 셌다.

| DTO | 정수 카운터 수 | 독립 확인 |
|---|---:|---|
| `TabSyncResult` | 11 | 모든 이름이 `Rows` 또는 `Occurrences`; 증가 지점 확인 |
| `ComponentSyncResult` | 6 | `Occurrences/Products/Rows`; 증가 지점 확인 |
| `SyncSummary` | 17 | `Rows/Occurrences/Products/Tabs`; 모든 존재하는 `total*`의 부분합 확인 |
| 합계 | 34 | suffix 위반 0 |

`durationMs`는 별도 `long` 시간 측정값이다. R6 표가 적은 34개 카운터의 산술 합계는 맞지만, 소비자 전수는 결함 1·2 때문에 맞지 않는다.

## ④ R1~R3 회귀

관련 묶음 4 classes를 `--rerun-tasks`로 실행했다.

```text
BUILD SUCCESSFUL
RELATED_GRADLE_EXIT=0
RELATED_XML files=4 tests=54 failures=0 errors=0 skippedOccurrences=0
```

- 롤백 후 재시도 단가: 실패 뒤 DB `1,000,000`, 재시도 뒤 `1,200,000`, `updatedRows=1`.
- `name` 비교 제외: DB authoritative name을 유지하면서 반복 실행 `updatedRows=0`, `unchangedRows=1`, `nameDriftOccurrences=1`.
- dirty detection 양방향: Hibernate `EntityPersister.findDirty(currentState, loadedState, ...)`를 사용하므로 수동 필드 목록 축소가 없다.
- 보조 entity 변경 카운터: 재정렬 실행 `2`, 반복 실행 `0`.
