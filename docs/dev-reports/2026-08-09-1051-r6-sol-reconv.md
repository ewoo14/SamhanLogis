## ⑤ “활성 0%”의 정확한 의미와 #1051 범위

결론: **활성 0%라는 숫자는 맞지만 “참조 품목 100개가 전부 비활성 행으로 존재한다”는 진술은 틀리다. 실제 참조는 전부 끊겨 있다.**

공유 DB 읽기 전용 교차 집계:

| 모집단 | 고유 참조 | product 행 존재 | 활성 | model_code 채움 |
|---|---:|---:|---:|---:|
| 기존 `created_by=system` 전표 라인의 실제 `product_id` | 100 | **0** | 0 | 0 |
| 기존 전표 라인의 실제 snapshot `model_name` (`TEST-MODEL-0001` 계열) | 100 | **0** | 0 | 0 |
| 현재 `HvacProductSeeder`의 `created_by=system` HVAC 행 | 100 | 100 | 0 | 0 |

즉 기존 시드 전표는 `TEST-MODEL-*` UUID/모델명을 참조하지만, product DB의 100개 system 행은 `AR05TX...` 등 현재 HVAC catalog다. 서로 다른 집합이다. R6 진단은 현재 코드가 계산하는 HVAC UUID 100개를 세어 “UUID 100% 존재”라고 했지만, 그것은 기존 시드 전표가 실제 저장한 참조 100개가 아니다.

현재 HVAC 100행은 soft-delete 상태이고 `Product` 엔티티의 `@SQLRestriction("is_deleted = false")` 때문에 `findAllByIdIn`에서도 제외된다. 2026-08-09 08:45:42 KST에 inactive UUID 1개를 실제 `POST /products/internal/lookup`으로 읽기 조회한 결과는 **HTTP 200 + `data: []`**였고, `ProductClient`는 부분/빈 응답을 `NOT_FOUND`로 승격한다.

이 현상이 `#1051`의 본체다. 이 PR은 기존 끊긴 line을 수정하지 않으며, 현재 시더를 재기동해도 선행 product 조회가 실패한다. HVAC 행을 별도로 활성화하더라도 `SlipSeeder`는 기존 유형+전표번호를 idempotent skip하므로 기존 `TEST-MODEL-*` line 참조를 교체하지 않는다. 따라서 **이 PR은 #1051의 기존 데이터 단절을 고치지 않는다.** 범위 판단은 PM 몫이며 수정 요구는 하지 않는다.
