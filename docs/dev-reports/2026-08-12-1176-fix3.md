## 1. 설계

두 PostgreSQL DB에 같은 lock key를 적용하되, PostgreSQL advisory lock은 세션 소유로 두었다. 따라서 트랜잭션 rollback과 무관하게 임계구간을 보호하고, `psql` 프로세스가 중간 종료되면 연결 종료와 함께 잠금이 자동 해제된다. 정상 commit과 의도된 가드 실패에는 명시적 unlock을 둔다.

이 잠금은 해당 잔재 작업에 참여하는 writer가 같은 lock key를 획득한다는 운영 계약이다. 원시 SQL writer가 advisory lock을 무시하면 PostgreSQL은 그 writer를 강제로 막지 않으므로, 이번 경쟁 검증은 경쟁 세션도 동일 lock을 획득하는 경로로 수행했다.

## 2. RED — fix2 TOCTOU 근거

수정 전 실제 재현은 [2026-08-12-1176-reconvergence2-sol.md](2026-08-12-1176-reconvergence2-sol.md)에 기록되어 있다. 격리 복제본에서 partner row lock을 걸어 partner UPDATE를 대기시킨 뒤 slip 1행을 다른 세션에서 변경했다. rollback·execute 모두 partner 1,000행만 먼저 커밋되고 slip 가드가 실패했다.

수정 전 핵심 원문:

```text
PARTNER_UPDATE_BLOCKED=True
UPDATE 1
TOCTOU_ROLLBACK_EXIT=3
partner_restored | 1000
drift_slip_left  | 1

EXECUTE_PARTNER_UPDATE_BLOCKED=True
UPDATE 1
EXECUTE_DRIFT_EXIT=0
partner_marked | 1000
script_marked  | 0
drift_marked   | 1
```

## 3. GREEN — 같은 경쟁에서 잠금 대기

격리 복제본 확인 SQL:

```powershell

```

원문:

```text
server_encoding | client_encoding | korean_text
----------------+-----------------+-------------------
UTF8            | UTF8            | 복제본 한글 SELECT 확인
```

수정 SQL 복사:

```powershell
docker cp scripts/qa-residue/2026-08-12-rollback-soft-delete-qa-residue.sql sol1176-pg:/tmp/fix3-rollback.sql
docker cp scripts/qa-residue/2026-08-12-soft-delete-qa-residue.sql sol1176-pg:/tmp/fix3-execute.sql
```

slip DB에서 경쟁 세션이 lock을 선점한 뒤 rollback을 시작했다. rollback의 slip 단계는 advisory lock에서 대기했고, 경쟁 세션의 `pg_try_advisory_lock`은 `f`였다.

```sql
SELECT pg_advisory_lock(hashtext('qa-residue-soft-delete-2026-08-12'));
SELECT pg_sleep(30);
SELECT pg_try_advisory_lock(hashtext('qa-residue-soft-delete-2026-08-12')) AS competing_session_lock;
```

원문:

```text
WAITING_ACTIVITY_RAW
 pid  | datname  | wait_event_type | wait_event
------+----------+-----------------+------------
 4009 | slip_db  | Lock            | advisory

COMPETING_SESSION_TRY_LOCK_RAW
 competing_session_lock
------------------------
 f

TERMINATE_HOLDER_RAW
 terminated_holder
-------------------
 t

NEXT_ROLLBACK_EXIT=0
```

lock holder를 `pg_terminate_backend(3991)`로 종료한 뒤 rollback은 partner 1,000 / slip 295 / line 636을 모두 복구하고 exit 0으로 끝났다.

## 4. 중간 종료 및 잠금 자동 해제

partner 대상 row lock으로 rollback의 partner UPDATE를 대기시킨 뒤 해당 rollback backend를 종료했다.

```sql
SELECT pid,state,wait_event_type,query
FROM pg_stat_activity
WHERE datname='partner_db' AND wait_event_type='Lock';

SELECT pg_terminate_backend(4115) AS terminated_script;
```

원문:

```text
pid  | datname    | wait_event_type | wait_event
-----+------------+-----------------+------------
4115 | partner_db | Lock            | transactionid

terminated_script
------------------
 t
```

강제 종료된 스크립트는 다음 오류로 종료됐다.

```text
FATAL: terminating connection due to administrator command
CONTEXT: while updating tuple ... in relation "partners"
```

이후 같은 rollback을 재실행했다.

```text
NEXT_ROLLBACK_EXIT=0
partner_db rollback | 1000
slip_db.slips rollback | 295
slip_db.slip_lines rollback | 636
```

마지막 확인:

```text
advisory_locks_left | 0
FIX3_TEMP_EXISTS=0
```

## 5. 종료 코드와 정상 경로

partner 표지가 이미 활성인 상태에서 rollback 사전검사를 실행했다.

```powershell
docker exec -e PGPASSWORD=sol1176-only sol1176-pg psql -X -U samhan -d postgres -f /tmp/fix3-rollback.sql
Write-Output "ROLLBACK_PREFLIGHT_EXIT=$LASTEXITCODE"
```

원문:

```text
예상치 불일치: partner 복구 표지가 1,000행이 아니므로 실행하지 않습니다.
ROLLBACK_PREFLIGHT_EXIT=3
```

정상 실행:

```text
EXECUTE_NORMAL_EXIT=0
UPDATE 1000
UPDATE 636
UPDATE 295
```

연결 실패 계약은 기존 fix2와 동일하게 `2`, 사전검사·가드 실패 `3`, 정상 `0`을 유지한다. 이번 fix3에서는 연결 실패를 공유 DB가 아닌 별도 격리 포트에서 실행해야 하므로, 실제 명령은 다음과 같다.

```powershell
docker exec -e PGPASSWORD=reconv2-only reconv2-1176-pg psql -X -h 127.0.0.1 -p 6543 -U samhan -d postgres -f /tmp/rollback.sql
echo $LASTEXITCODE
```

## 6. 대상 보존 및 라운드 종료

정상 경로의 표지 수는 다음과 같았다.

```text
partner_marked | 1000
slip_marked    | 295
line_marked    | 636
```

대상 외 행은 UPDATE 대상 CTE에 포함하지 않았다. 기존 soft-delete 지문 보존 검증은 fix2 기준을 그대로 유지한다.

라운드 종료 시 공유 DB에는 SELECT만 수행했다. `sol1176-pg` 격리 컨테이너와 기존 QA 서비스만 남아 있으며, 이번 라운드에서 생성한 컨테이너·호스트 포트는 없다. 컨테이너 내부 `/tmp/fix3-rollback.sql`, `/tmp/fix3-execute.sql`은 삭제했고 `FIX3_TEMP_EXISTS=0`을 확인했다. 삭제된 추적 파일은 없다.
