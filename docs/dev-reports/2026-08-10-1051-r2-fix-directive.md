# PR #1157 · 이슈 #1051 — R2 도달 결함 fix 지시서

판정: **BLOCK — 실 장애 복구 경로 결함 1건**

## 지금 고칠 것

- V31 오삭제 뒤 V33에서 기동이 차단된 DB가 `DB-MIGRATION-RUNBOOK.md`의 명령을 그대로 따라 V35 복구 SQL 전체를 끝까지 실행할 수 있어야 한다.

## 분리할 것

- V33 적용 뒤 V35 배포 전에 관리자가 34개 후보의 상품/비상품 값을 바꾼 경우 V35가 다시 덮을 수 있다. 2026-08-10 11:53:13 KST 회사PC DB에는 해당 변경 표본이 0건이므로 이번 결함으로 확정하거나 없는 데이터로 재현하지 않는다.

## 1. 좌표와 재현 증거

### 결함 1 — 런북의 기동 차단 복구 명령이 V35 두 번째 문장에서 실패한다

- 좌표
  - `docs/handoff/DB-MIGRATION-RUNBOOK.md:222-229` — V33 차단 DB에서 V35 파일을 `psql --file`로 직접 실행하도록 지시한다.
  - `services/product-service/src/main/resources/db/migration/V35__repair_issue_1096_product_cleanup.sql:9-10` — `ON COMMIT DROP` 임시표를 만든 다음 별도 문장으로 101개 UUID를 INSERT한다.
  - `services/product-service/src/test/java/com/samhanair/logis/product/it/Issue1096ProductCleanupMigrationIT.java:90-96` — 수동 재실행 검증은 `setAutoCommit(false)` 뒤 SQL을 실행하므로 런북의 기본 psql 호출과 실행 경계가 다르다.
- 도달 조건
  1. V31 오삭제로 V33 활성 후보가 1~33개가 되어 Flyway가 V35에 도달하지 못한다.
  2. 운영자가 런북의 명령을 그대로 실행한다.
  3. psql 기본 `AUTOCOMMIT=on`에서 첫 `CREATE TEMP TABLE ... ON COMMIT DROP` 문장이 끝나며 임시표가 사라진다.
  4. 다음 `INSERT INTO _issue_1096_test_product_ids`가 관계 없음 오류를 내고, `ON_ERROR_STOP=1` 때문에 제품 복구 UPDATE 전에 종료된다.
- 실제 근거
  - 2026-08-10 11:47:11~11:50:14 KST 회사PC 읽기 전용 실측: 활성 3,061 / 삭제 2, Flyway 최신 V34, V31 UUID 존재 0, cleanup actor 네 테이블 0.
  - 현재 활성 NON_GOODS 후보는 34개이며 `created_by='system'` 2개, UUID actor 32개다. 이 DB가 V31 미적용 상태였다면 V31 뒤 후보는 32개이므로 PM 시나리오 ③은 V33을 통과하지 않고 시나리오 ①로 귀결된다.
  - 시나리오 ②는 V31 뒤 활성 후보 수가 정확히 0 또는 34이면서 다른 비대상 품목이 오삭제된 환경에서만 가능하다.
  - psql 기본 `AUTOCOMMIT` 실측은 `on`; `psql --help`는 파일 전체 실행 경계를 별도 옵션으로 구분한다.
- 증거 무결성
  - 구현자 보고 IT 성공은 Flyway 실행과 `autoCommit=false` 재실행만 증명한다. 실제 런북의 기본 psql 호출은 증명하지 않으며 현재 명령은 그 경로에서 실패한다.

## 2. 불변식

- 기동 차단 DB에서 런북에 공개된 명령을 그대로 실행하면 V35 파일의 임시 대상 집합 생성부터 네 테이블 복구와 NON_GOODS 재적용까지 전부 완료되어야 한다.
- 파일 실행이 중간에 실패하면 제품·alias·bundle·estimate exposure 중 일부만 복구된 상태가 남아서는 안 된다.
- `deleted_by='issue-1096-test-seed-cleanup'`이면서 V31의 101개 UUID 밖인 행만 복구하고, 101개 UUID 안의 의도된 삭제와 다른 actor의 삭제는 유지해야 한다.
- 재실행 전후 논리 데이터가 이미 목표 상태라면 같은 런북 절차를 반복해도 활성/삭제 범위와 34개 후보의 업무 값이 달라지면 안 된다.

## 3. 양방향 RED

### RED-A — 실제 V33 차단 상태에서 런북 복구 도달

- 폐기 가능한 PostgreSQL fixture를 V30까지 준비하고 다음 표본을 둔다: V31 목록 안 제품 1개, 목록 밖 cleanup 대상 제품 1개, 그 양쪽의 자식 3테이블 행, V33 후보가 V31 뒤 1~33개가 되는 실제 차단 분포.
- V31 적용 뒤 V33이 후보 수 예외로 멈추고 V35 미적용임을 단정한다.
- 문서에 공개된 런북 명령과 같은 호출 경계로 V35 파일을 실행한다.
- 현재 문서는 임시표 INSERT에서 실패해야 RED다. 결함 해소 뒤에는 호출이 성공하고, 목록 밖 cleanup actor 행만 복구되며 목록 안 제품·자식은 계속 삭제 상태여야 한다.
- 34개 후보는 `goods_type='NON_GOODS'`, `inventory_qty_mgmt=false`여야 하고 Flyway 재개 뒤 V33→V34→V35가 통과해야 한다.

### RED-B — 이미 복구된 상태의 반복 실행과 비대상 보존

- 폐기 가능한 fixture에 이미 복구된 목록 밖 행, 계속 삭제돼야 하는 101개 목록 안 행, 다른 actor가 삭제한 대조 행을 함께 둔다.
- 문서와 같은 호출로 V35를 두 번 연속 실행한다.
- 현재 문서는 두 실행 모두 임시표 INSERT에서 실패해야 RED다. 결함 해소 뒤에는 두 번 모두 성공하고, 두 번째 실행 전후 활성/삭제 집합과 34개 후보의 논리 값이 같아야 한다.
- 101개 목록 안 행과 다른 actor 대조 행이 하나라도 활성화되거나, 목록 밖 cleanup actor 행이 삭제 상태로 남으면 실패해야 한다.

## 4. 범위 밖

- 체크섬이 고정된 V31·V33 수정 금지.
- product-service 밖의 서비스 migration 신설 또는 변경 금지.
- 운영 DB 쓰기, Docker 재배포, 서비스 재시작 금지.
- V31 101개 UUID와 V33 34개 model_code 목록 변경 금지. 두 목록은 현재 각각 V31/V35 및 V33/V35 사이에서 순서까지 바이트 동일하다.
- 표본이 없는 V33 이후 사용자 변경 덮어쓰기 위험을 이번 수정에 포함하지 않는다.
