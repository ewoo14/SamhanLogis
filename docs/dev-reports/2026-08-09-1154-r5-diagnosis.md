- 진단일: 2026-08-09 KST
- 대상: `feat/896-partner-master-load` / `759077f415fd6c9e6bf3864d8863c189efb0846e`

- 원칙: 코드 수정·공유 DB 쓰기·commit·push 없음

## 1. 결론

근본 원인은 `findByPartnerCodeIncludingDeleted()`가 삭제행을 못 읽는 것이 아니다. 삭제행을 **정상 반환**하지만, 적재 진입 메서드가 트랜잭션이 아니고 같은 빈 안에서 `upsertPartner()`를 직접 호출하므로 `upsertPartner()`의 `@Transactional`이 적용되지 않는다. 삭제행은 native 조회용 EntityManager가 끝난 뒤 detached가 된다.

이 detached 엔티티를 `partnerRepository.save()`에 넘기면 Spring Data JPA가 `merge`를 수행한다. Hibernate는 원 UUID로 다시 SELECT하지만 `Partner`의 `@SQLRestriction("is_deleted = false")`가 붙어 삭제행을 못 찾는다. 그 결과 merge 대상 사본을 신규 엔티티로 처리하고 `@UuidGenerator`로 새 UUID를 발급해 INSERT한다.

따라서 다음 두 결과가 동시에 성립한다.

- Java 집계: native 조회 결과가 present였으므로 `isNew=false` → `updated=1`
- DB 결과: merge 재조회가 삭제행을 못 보므로 새 UUID INSERT → 원 삭제행 보존

확정된 코드 연쇄:

1. 비트랜잭션 진입 및 self-invocation: `EcountPartnerImporter.java:123-200`(CSV), `:244-290`(XLSX)
2. 적용되지 않는 내부 메서드 선언의 `@Transactional`: `EcountPartnerImporter.java:547-549`
3. 삭제행 native 조회: `PartnerRepository.java:147-149`
4. detached 엔티티 `save()` 호출: `EcountPartnerImporter.java:565-575`, `:614`
5. merge 재조회에 붙는 restriction: `Partner.java:40`
6. 신규 UUID 생성기: `Partner.java:43-47`

즉 단일 파일 한 줄만의 문제가 아니라, **트랜잭션 프록시를 우회한 self-invocation + detached merge + 엔티티 restriction**의 결합이 근본 원인이다.

## 3. 후보 5개 판정

### 후보 1 — native query가 실제 삭제행을 반환하는가

**판정: 확인함. `@SQLRestriction` hydration 필터로 `Optional.empty()`가 되지 않는다.**

`PartnerRepository.java:147-149`의 native SQL은 실제로 다음과 같이 나갔다. restriction이 추가되지 않았다.

```sql
SELECT *
FROM partners
WHERE partner_code = ?
ORDER BY is_deleted DESC, deleted_at DESC NULLS LAST
LIMIT 1
```

```text
binding parameter (1:VARCHAR) <- [SOL1154R5]
```

그 직후 Java 결과가 `updated=1`이었고, 뒤의 merge SELECT가 native 조회로 고른 최신 삭제 UUID `d796f479-b461-4215-a0e1-28c69e8f0749`를 바인딩했다. 따라서 native 조회가 삭제행을 엔티티로 hydration해 반환한 사실이 확정된다.

반대로 restriction이 실제 적용된 곳은 일반 `findByPartnerCode`와 뒤의 merge SELECT다. 후보 1의 “native hydration 단계에서 걸러 empty” 가설은 **아님**이다.

### 후보 2 — `markRestored()`가 삭제 플래그와 감사열을 복원하는가

**판정: 확인함. 메서드 자체는 정상이다.**

### 후보 4 — 트랜잭션·영속성 컨텍스트 경계

**판정: 확인함. native 조회 결과는 `save()` 시점에 detached다.**

CSV 진입점 `importCsv()`에는 `@Transactional`이 없고(`EcountPartnerImporter.java:123`), 같은 객체의 `upsertPartner()`를 직접 호출한다(`:200`). XLSX도 `importXlsx()`에서 같은 직접 호출을 한다(`:244`, `:290`). 따라서 `upsertPartner()` 선언부의 `@Transactional`(`:547`)은 Spring 프록시를 통과하지 않아 적용되지 않는다.

실 트랜잭션 로그도 이를 고정한다.

```text
No need to create transaction for [...findByPartnerCode]: This method is not transactional.
Creating new EntityManager for shared EntityManager invocation

No need to create transaction for [...findByPartnerCodeIncludingDeleted]: This method is not transactional.
Creating new EntityManager for shared EntityManager invocation

Creating new transaction with name [...SimpleJpaRepository.save]
Opened new EntityManager [SessionImpl(1188386088<open>)] for JPA transaction
```

즉 native query가 반환한 객체는 조회 호출 동안만 그 조회 EntityManager에 속하고, `save()`는 별도 새 EntityManager에서 받는다. `save()` 입장에서는 detached 엔티티다. 이 경계가 없었다면 같은 persistence context의 managed 엔티티 dirty checking으로 원행 UPDATE가 가능했을 것이다.

### 후보 5 — 새 UUID 발급 위치

**판정: 확인함. `Partner.register()` 분기가 아니라 Hibernate UUID generator다.**

`Partner.java:43-47`:

```java
@Id
@GeneratedValue
@UuidGenerator
@Column(name = "id", updatable = false, nullable = false)
private UUID id;
```

이번 재현 응답이 `imported=0, updated=1`이므로 `Partner.register()`가 있는 신규 분기(`EcountPartnerImporter.java:599-612`)는 타지 않았다. merge SELECT에는 원 UUID `d796...`가 바인딩됐지만 INSERT id에는 새 UUID `df3a...`가 바인딩됐다. 따라서 merge가 DB에서 managed target을 못 찾은 뒤 만든 신규 사본에 Hibernate `@UuidGenerator`가 UUID를 발급한 것이다.

`Partner.register()` 생성자는 UUID를 직접 만들지 않는다(`Partner.java:223-257`). identity/sequence DB 컬럼도 아니다.

## 4. R2 단위테스트가 통과한 이유

R2 테스트는 `partnerRepository.save(any())`를 전달 객체 그대로 반환하도록 mock했다(`EcountPartnerImporterTest.java:92-94`). 삭제행 테스트도 repository native 조회와 save를 모두 mock했으므로 실제 EntityManager 분리, merge 재SELECT, `@SQLRestriction`, INSERT가 전혀 실행되지 않는다.

또 테스트의 `originalId`는 영속화 전 `Partner.register()` 객체에서 읽어 null이며, save mock도 같은 객체를 반환하므로 `null == null` 단정만 통과한다(R2 추가 테스트 현재 `EcountPartnerImporterTest.java:303-321`). 따라서 실제 UUID 동일성을 고정하지 못했다.

### 5.2 거래처 관리자 화면·복원 API

실 경로는 존재한다.

- FE: `POST /admin/partners/{partnerCode}/restore` — `adminApi.ts:454-458`
- 화면 복원 버튼 — `PartnersPage.tsx:285-305`
- BE: `PartnerAdminController.java:223-237`
- 서비스: `PartnerService.java:439-454`

그러나 현재 잔재에는 사용할 수 없다. 서비스가 삭제행을 고른 뒤 동일 코드 활성행이 있으면 명시적으로 409를 낸다(`PartnerService.java:445-449`). 격리 환경의 같은 dual-row 상태에서 실 API를 호출해 다음을 확인했다.

```text
POST /admin/partners/SOL1154R5/restore
HTTP 409
이미 사용 중인 거래처 코드로 활성 거래처가 존재하여 복원할 수 없습니다: SOL1154R5
```

활성행을 먼저 관리자 DELETE한 뒤 restore하는 순서도 원 UUID를 복원하지 못한다. native lookup은 `is_deleted DESC, deleted_at DESC LIMIT 1`(`PartnerRepository.java:147-148`)이므로 방금 삭제한 신규행을 다시 고른다. 삭제행이 둘 이상이면 FE도 오복원 방지를 위해 복원 버튼을 비활성화한다(`PartnersPage.tsx:169-178`, `:285-296`). UUID로 특정 삭제행을 복원하는 API는 없다.

**판정: 거래처 관리자 화면/API만으로 원 UUID `9592...` 복원 및 신규행 `5e4...` 정리는 불가하다.**

### 5.3 주문 2건의 사용자 편집 경로

두 주문은 모두 DRAFT라 주문 수정 화면과 `PUT /api/v1/partner-orders/{id}` 자체는 접근 가능하다(`PartnerOrderEditController.java:38-48`). 그러나 현재 코드/사업자번호를 그대로 저장하면 `partnerIdentityChanged=false`라 기존 `partnerId=9592...`를 유지한다(`PartnerOrderUpdateService.java:96-104`). 즉 단순 재저장은 재조회·재연결이 아니다.

화면은 partnerCode만 편집하고 bizCode는 기존값을 그대로 전송한다(`SalesPartnerOrderDetailPage.tsx:1429-1433`, `:1488-1496`). 따라서 화면 한 번의 수정으로 같은 코드의 현재 활성 UUID를 다시 해소할 방법이 없다.

인증된 PUT API를 원시 호출해 각 주문을 **다른 정상 거래처 code+bizCode로 바꾼 뒤**, fresh `updatedAt`으로 `1068689215`에 되돌리는 2단계 우회는 코드상 partner identity resolver를 두 번 발화시켜 최종적으로 현재 활성 UUID `5e4...`에 재연결할 수 있다. 다만 주문마다 비즈니스 거래처 변경 2회, audit/revision 2회가 생기고 중간 순간 잘못된 거래처가 되며, 원 partner 행 dual-row 잔재도 남는다. 전용 복구 API가 아니므로 안전한 전체 복구 경로로 판정하지 않는다.

**판정: 주문 참조 2건만 살리는 위험한 API 우회는 이론상 가능하지만, 공유 DB 잔재 전체를 원상복구하는 실 사용자 경로는 없다.**

### 5.4 PM 판단이 필요한 복구안

원상복구 목표가 “원 UUID 유지 + 기존 주문 참조 보존”이라면 전용 데이터 복구가 필요하다. 이번 라운드에서는 실행하지 않았다.

PM 승인 후 필요한 원자적 작업의 의미는 다음과 같다.

1. 잘못 생성된 활성행 `5e4...`를 soft-delete 상태로 전환한다.
2. 원행 `9592...`만 `is_deleted=false`, `deleted_at/deleted_by=null`로 복원한다.
3. `staging.ecount_partner_raw.target_partner_id`를 원 UUID로 되돌린다.
4. 활성 코드 1건, 삭제 코드 1건, 주문 참조 2건 모두 원 활성 UUID 일치 여부를 한 트랜잭션에서 검증한다.

hard delete는 금지한다. 현행 API는 1·2를 원하는 UUID 대상으로 원자 실행할 수 없으므로, PM이 (a) 일회성 승인 DB 복구 또는 (b) UUID 비공개 원칙을 유지한 전용 관리자 repair endpoint 중 하나를 결정해야 한다.
