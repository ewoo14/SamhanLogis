## 구조 질문에 대한 답

### ① 옵션 UI 표시를 결정하는 값

옵션 UI는 전개 결과의 첫 구성품 `productId`가 아니라, 사용자가 선택한 원래 BUNDLE 행에서 파생된 옵션 컨텍스트가 결정해야 한다.

기존 구현은 BUNDLE 행을 구성품으로 치환하면서 컨텍스트 키를 첫 구성품 `productId`로 옮겼다. 재전개 전후 첫 구성품이 같으면 새 구성품 키가 기존 키와 같아졌고, pending 응답 처리와 후속 사용자 입력이 서로 다른 세대의 컨텍스트를 참조했다. 따라서 F1은 단순 렌더 조건 문제가 아니라 컨텍스트 소유권 키가 전개 결과에 종속된 구조 문제였다.

수정 후 컨텍스트는 매 전개에서 새로 생성한 첫 구성품의 안정적인 행 ID에 연결한다. 첫 구성품이 이전 구성품과 같을 때만 컨텍스트를 다음 세대로 이월하고, 달라지면 옵션 UI를 종료한다. 초기 BUNDLE 전개도 같은 규칙으로 옵션 UI를 연결한다.

### ② 저장 payload의 진실원

저장 payload는 렌더 시점의 `lines` 클로저가 아니라 저장 함수 실행 시점의 최신 `linesRef.current`와 최신 옵션 컨텍스트에서 만들어야 한다.

또한 옵션 재전개가 pending이면 화면에는 옛 SINGLE 구성품이 남아 있을 수 있으므로 저장을 허용하면 안 된다. `bundleExpansionPending`을 `canSubmit`에 포함해 전개가 확정되기 전 저장을 차단했다. 응답 완료 후에는 최신 컨텍스트가 반영된 최신 `linesRef.current`만 payload로 사용한다.

## 구현 판단 및 단순해진 점

구조를 바꾸는 쪽을 선택했다. 여섯 라운드 동안 비동기 응답마다 stale guard를 덧대는 방식으로는 컨텍스트 키와 저장 시점의 진실원이 계속 갈라졌다.

- 옵션 컨텍스트의 키를 `productId`에서 새 구성품 행 ID로 변경해 같은 품목 ID 재사용과 세대 충돌을 제거했다.
- 컨텍스트를 새 결과 행에 붙이는 시점을 `replaceWithExpandedBundleLines` 한 곳으로 모았다.
- 저장은 `linesRef.current`에서 읽고, pending 동안은 버튼 자체를 막아 옛 결과를 payload로 만들 수 없게 했다.
- 결과가 같은 경우/다른 경우의 UI 수명 규칙이 첫 구성품 비교 하나로 명확해졌다.

따라서 별도의 응답별 예외 차단을 추가하는 대신, UI 컨텍스트 소유권과 저장 시점의 단일 진실원을 정리했다.

## 불변식 확인

- 옵션 입력 가능: 옵션 UI는 원래 BUNDLE 컨텍스트에 귀속되고, 같은 첫 구성품 재전개 후에도 유지된다.
- 최신 입력 반영: pending 중 저장을 막고, 완료 후 최신 옵션으로 전개된 SINGLE 행만 저장한다.
- 옵션 확정 후 BUNDLE 라인 없음: 전개 함수는 기존처럼 구성품 SINGLE 행으로 치환한다.
- 정상 SINGLE 저장 경로: `canSubmit`의 기존 조건을 유지하고, 새 조건은 BUNDLE 전개 pending일 때만 추가 차단한다.
- S2·S4·S6·S8·S10 및 #1063 빈행 규약: 해당 로직과 백엔드 계약은 변경하지 않았다.
