## 결론

**도달 결함 1건**이다. S17이 11개 상태 전이를 모두 중앙 가드에 연결했다고 보고했지만 `INSPECTING → COMPLETED`의 `SlipService.inspect()`만 `assertAllowed()`를 호출하지 않는다.

나머지 실측 결론은 다음과 같다.

- 활성 기준선 0건에서 복원·수정·상태 전이·revision 복원은 각 1/1 성공했다.
- 기준선 활성 중에도 열린 날짜에서 같은 네 경로가 각 1/1 성공했다.
- 기존 과거 활성 전표 367건의 상태 전이 시도는 367/367 마감 409로 차단됐고 상태 분포는 불변이었다.
- 같은 367건의 복원 시도는 마감 차단 0건이다. 활성 OUTBOUND 325건은 no-op 200, INBOUND 42건은 판매전표 전용 타입 경계 404였고 활성 건수는 367로 불변이었다.
- 원 결함의 soft-delete 복원은 비예외 사용자 1/1이 409로 차단됐다.
- 예외 권한자는 닫힌 날짜의 soft-delete 복원·revision 복원·상태 전이를 각 1/1 통과했다.
- 공개 DTO에는 `slipDate` 변경 필드가 없다. 닫힌 날짜를 추가한 PATCH는 200이지만 실제 날짜가 유지돼 날짜 이동 표본은 0, 판정 불가다.
- `SYSTEM_ACTOR_ID`는 예외 권한이 없다. 다만 `restoreSnapshot()` main 호출부와 HTTP 진입점도 0건이라 현재 실사용자 HTTP 전면 장애로 판정할 표본은 0이다. 포트가 호출되는 경우에는 닫힌 snapshot이 전부 차단된다.
- 현재 dev 시드 100건은 모두 이미 존재해 `find...IncludingDeleted()`에서 guard 전에 skip되는 상태다. 재기동 금지 때문에 runner 자체는 실행하지 않았다.

## 결함 1 — `inspect()`만 중앙 날짜 가드를 우회한다

### 재현·대조 절차

1. 활성 기준선 0건에서 실 관리자 JWT로 `S18-1123-closed-inspect-bypass-v5` OUTBOUND 전표를 만든다.
2. 실 API로 `DRAFT → SAVED → SENT → ACCEPTED → PROCESSING → INSPECTING`까지 진행한다.
3. 관리자 API로 `OUTBOUND / 2026-08-09` 기준선을 활성화한다. 전표일 `2026-08-08`은 닫힌 날짜다.
4. 비예외 `dev_warehouse` JWT로 `POST /api/v1/slips/{id}/inspect`를 호출한다.
5. 코드와 실 auth 결재선 모집단을 대조한다.

### 실측 원문

```text
PREP5 create=201 no=2026/08/08-36
PREP5 save=200 status=SAVED
PREP5 send=200 status=SENT
PREP5 accept=200 status=ACCEPTED
PREP5 process=200 status=PROCESSING
PREP5 complete=200 status=INSPECTING

CLOSED warehouse_inspect=403 code=FORBIDDEN before=INSPECTING after=INSPECTING
message=출고 검수 권한이 없습니다 — 검수자 결재자(그룹/개인)만 처리할 수 있습니다
```

이 JWT는 서비스 진입 전 결재선에서 차단됐으므로 마지막 mutation의 live 표본은 0이다. 그러나 main 코드 전수 대조는 누락을 확정한다.

```text
SlipService.java:965   process()  assertAllowed
SlipService.java:983   inspect()  assertAllowed 없음
SlipService.java:987              slip.inspect(inspectorUserId)
SlipService.java:1133  complete() assertAllowed
```

`closedDateGuard.(assertAllowed|assertCreatable)` main 전수 grep에서 상태 전이 호출은 save, send, accept, process, complete, ship, deliver, confirm, reject, cancel의 10개뿐이다. `inspect`는 없다. 관련 테스트 grep도 0건이었다.

```text
INSPECT_GUARD_TEST_RG_EXIT=1
```

실 auth DB에는 OUTBOUND_INSPECT의 실제 USER 결재자 2명이 있고 둘 다 `slip.closed-date-exception` 권한이 없다. 현재 DB에는 기존 INSPECTING 과거 전표도 5건이다. 두 결재자 계정의 QA 로그인 자격은 제공되지 않아 실 JWT 최종 mutation은 판정 불가지만, 이 사용자들이 정상 로그인해 검수 완료를 누르면 컨트롤러 결재선을 통과한 뒤 날짜 가드 없이 `slip.inspect()`에 도달한다.

### 왜 실 사용자가 밟는가

`POST /api/v1/slips/{id}/inspect`는 전표 화면의 정식 “검수 완료” 동작이다. 등록된 검수 결재자는 예외 권한자가 아니므로, 마감 뒤 INSPECTING 전표를 완료할 때 이 누락을 밟는다. 이는 S17이 열거한 11개 상태 전이 중 하나가 실제로 빠진 도달 구멍이다.

## 2차 각도 — 원 결함 수렴

### soft-delete 복원

```text
CLOSED normal_soft_restore=409 code=CONFLICT
message=마감된 날짜에는 신규 전표를 만들 수 없습니다.
```

비예외 사용자 1/1 차단. S15의 200 결함은 닫혔다.

### revision / full-snapshot 복원

비예외 revision 복원은 날짜 가드보다 앞선 endpoint 권한에서 막혔다.

```text
CLOSED normal_revision_restore=403 code=FORBIDDEN
message=[SP-PO-1] 동적 권한 deny — page=slip.audit-revert action=RESTORE ...
```

현재 auth DB에서 `slip.audit-revert RESTORE=true`인 계정은 3명이고 3명 모두 `slip.closed-date-exception CREATE=true`다. “revision 복원 권한은 있으나 날짜 예외는 없는” 실 JWT 모집단이 0이므로 비예외 날짜 차단은 판정 불가다.

full-snapshot은 main의 `.restoreSnapshot(` 호출부 0건, HTTP endpoint 0건이다. 따라서 실 JWT 표본 0, 판정 불가다.

### 전표일자를 닫힌 날짜로 변경

공개 header DTO에 `slipDate`가 없다. 열린 전표에 unknown 필드를 넣어 실제 호출한 결과:

```text
DATE_CHANGE request_closed=2026-08-08 http=200 actual_date=2026-08-10
```

memo만 바뀌고 전표일은 유지됐다. 날짜 이동 표본 0이므로 차단 여부는 판정 불가다. revision snapshot에는 날짜가 있지만 현재 공개 수정 경로로 서로 다른 날짜 revision을 만들 수 없다는 S17 근거와 일치한다.

### 예외 권한자

`dev_manager` 실 JWT로 닫힌 날짜에서 다음 셋을 통과했다.

```text
CLOSED exception_soft_restore=200 status=DRAFT
CLOSED exception_revision_restore=200 status=DRAFT date=2026-08-08
CLOSED exception_state_save=200 status=SAVED
```

soft 복원·revision 복원·상태 전이는 각 1/1 통과. 날짜 변경은 공개 경로가 없어 판정 불가다.

## SlipSeeder

`SlipSeeder.run()`은 각 spec에서 다음 순서다.

```text
findBySlipTypeAndSlipNoIncludingDeleted(...) 존재 → skip
없음 → assertAllowed(...) → buildAndTransition(...) → save
```

실 DB에는 `created_by=system`인 Stage 2 전표가 100건이며 시더의 기대 건수 100과 같다. 98건은 memo에 `Stage 2`가 남아 있고 2건은 REJECTED 전이로 memo 앞에 반려 사유가 붙은 동일 시드다. 따라서 현재 DB에서는 기준선이 활성화돼도 100건 모두 guard 전에 skip된다.

컨테이너 재기동 금지 때문에 runner 자체는 실행하지 않았다. 현재 DB 재기동의 실패 건수는 실 실행 표본 0이라 판정 불가다. 코드상 “기준선 활성 + 기대 slipNo가 물리적으로 없음” 조합에서는 첫 누락 건에서 fail-fast한다. 그러나 soft-delete도 including-deleted 조회에 걸려 skip되고, fresh DB에는 기준선 자체가 없으므로 현재 허용된 API로 그 조합을 만들 수 없었다.

## 3차 각도 — 중앙화의 대가

### 가드 누락 경로

- 생성: 운영 7경로와 dev `SlipSeeder`는 생성 직전에 `assertCreatable/assertAllowed`가 있다.
- soft-delete 활성화: `markRestoredWithNameCleared()`의 Slip 호출부는 `SlipRestoreService` 1곳이고 guard가 있다.
- snapshot 날짜 대입: `SlipRevisionService.restore()`와 협업 `restoreSnapshot()` 모두 target snapshot 날짜 guard가 있다.
- 상태 전이: 11개 중 `inspect()` 1개만 누락. 본 보고서의 결함 1이다.
- dispatch 서비스의 `slipRepo.save(slip)` 호출은 배차 연결 필드를 저장하며 `Slip.status`, `slipDate`, `isDeleted`를 활성화/변경하는 호출이 아니다.

### 같은 요청의 중복 판정

revision 복원은 두 번 호출한다.

```text
SlipService.restoreToRevision:692       현재 slip 날짜 assertAllowed
SlipRevisionService.restore:235        target snapshot 날짜 assertAllowed
```

서로 다른 날짜 revision을 방어하려는 두 경계다. 현재/target 날짜가 같으면 예외 권한자의 동일 permission check도 2회 발생한다. 실 예외 revision 복원은 200이어서 중복 예외는 관찰되지 않았다. 그 밖의 생성 경로는 `assertCreatable → assertAllowed` 위임 1회이고, soft 복원·상태 전이는 요청당 1회다.

## 4차 각도 — S17 증거 무결성

S17에 명시된 Gradle 명령을 그대로 재실행했다.

```text
BUILD SUCCESSFUL in 11s
18 actionable tasks: 18 up-to-date
exit 0
```

revision 대상 날짜 묶음도 별도로 재실행했다.

```text
BUILD SUCCESSFUL in 13s
18 actionable tasks: 1 executed, 17 up-to-date
exit 0
```

반면 S17 보고서에는 `RG_EXIT=0` 문자열도, 그 결과를 만든 rg 명령도 없다. “같은 명령” 재현의 원문이 존재하지 않으므로 해당 주장은 그대로 재현할 수 없다. S18 독립 전수 명령은 다음 결과를 냈다.

```text
rg -n "closedDateGuard\.(assertAllowed|assertCreatable)" services/slip-service/src/main/java
S18_RG_EXIT=0
```

이 exit 0은 단지 match 존재를 뜻하며 완전성을 뜻하지 않는다. 실제 출력에는 `process` 다음 `complete`가 나오고 `inspect`가 빠져 S17의 “상태 전이 11종 전부” 서술을 반증한다. S17의 명시 테스트 목록에도 `process_checksClosedDateGuardBeforeStatusMutation`만 있고 inspect 날짜 가드 테스트는 없다.

## 이 라운드가 보지 않은 것

- 실제 OUTBOUND_INSPECT 결재자 2명의 로그인 자격이 없어 `inspect()` 누락의 최종 200 mutation은 실 JWT로 재현하지 못했다.
- `slip.audit-revert RESTORE=true`이면서 예외 권한이 없는 계정이 0명이라 비예외 revision 차단을 live 판정하지 못했다.
