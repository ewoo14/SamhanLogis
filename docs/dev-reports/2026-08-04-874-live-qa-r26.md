## 결함 1 — SENT 취소 노출

일반 SENT 판정: PASS

- 실제 계정 `dev_manager`로 판매관리 신규 전표를 만들었다. 새 전표번호는 `2026/08/04-1`, 메모는 `QA-874-R26-GENERAL-SENT`이다. 저장 전 화면 캡처: `docs/qa/874-riusage-global-dc-real-qa/r26-41-outbound-form-filled.png`.
- 목록에 새 전표가 `임시저장`으로 표시됐다. 캡처: `r26-42-outbound-saved-list.png`.
- 상세에서 `완료 (저장)`을 클릭해 `/slips/{internal-id}/save` HTTP 200, 이어 `완료 (전송)`을 클릭해 `/slips/{internal-id}/send` HTTP 200을 확인했다. 전송 후 상태는 `창고 전송` 단계이며, 상세 하단에 `삭제`가 노출됐다. 캡처: `r26-43-general-draft-detail.png`, `r26-44-general-after-save.png`, `r26-45-general-sent-cancel.png`.
- 결론: 일반 SENT 전표에서 RED-A의 취소 UI(`삭제`)가 보이고 실제 전송 경로가 동작하므로 PASS. 취소 버튼 자체는 데이터 보존을 위해 클릭하지 않았다.

주문전환 SENT 판정: 미발화

- 주문서 관리 내부 화면은 실제로 로드됐고 초기 API 응답 이후 `573건`의 기존 주문 목록을 표시했지만 신규 주문 생성 버튼은 없었다. `웹 주문서 ↗`의 실제 목적지는 `http://localhost:5180`이었고 링크 클릭 시 별도 팝업으로 열렸다. 캡처: `docs/qa/874-riusage-global-dc-real-qa/r26-50-orders-list.png`, `r26-51-external-order-entry.png`, `r26-57-order-app-popup.png`.
- 같은 w1057 워크트리의 `clients/web/order-app`을 실제 Vite strictPort 5180으로 기동한 뒤, 실제 `/api/v1/partner-orders/bootstrap` HTTP 200을 확인했다. 외부 주문서 화면은 사업자등록번호 조회부터 시작했다. 캡처: `r26-52-order-app-login.png`, `r26-53-order-app-bizno-filled.png`.
- 실제 거래처 `강릉HVAC솔루션`의 사업자번호 `334-26-10558` 조회는 HTTP 200이지만 `미등록 사업자번호`로 차단됐다. 기존 주문 목록에 표시된 사업자번호 `106-86-89215`도 HTTP 200이나 `미승인 사업자번호`로 차단됐다. 주문서 작성/발송까지 도달할 승인 계정이 없어 주문전환 SENT를 만들 수 없었다. 캡처: `r26-55-order-app-bizno-status.png`, `r26-56-order-app-registered-status.png`.
- 결론: 주문전환 SENT의 RED-B(취소 미노출)는 미발화이며 PASS로 세지 않는다. 기존 주문을 전환해 기존 행을 변경하는 우회는 사용자 지시(기존 행 수정·삭제 금지)에 따라 하지 않았다.

## 이 라운드가 보지 않은 것

주문전환 SENT 전표의 RED-B(취소 미노출)는 사업자 미등록/미승인으로 주문 생성 자체가 막혀 보지 못했다. 따라서 결함 1은 일반 SENT만 PASS, 주문전환 SENT는 미발화다. 기존 행을 수정·삭제하지 않았고, 취소 버튼을 통한 실제 삭제/취소 동작 자체도 데이터 보존을 위해 누르지 않았다.
