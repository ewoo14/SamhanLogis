## 확인 로그

### 1. R24 주장 원문 확보

- R24는 상태별 대조표에서 `DRAFT`부터 `CANCELED`까지 모든 상태의 백엔드 허용 액션과 화면 노출 액션이 일치한다고 주장한다.
- 특히 `INSPECTING`은 INBOUND/OUTBOUND 구분 없이 `inspect, reject`, `COMPLETED`는 OUTBOUND `ship` / INBOUND `confirm`이라고 기록했다.
- R24가 원문/실측으로 제시한 수치는 계약 Vitest `5 passed`, ESLint exit 0, TypeScript exit 0, `SlipDomainTest`의 `BUILD SUCCESSFUL`이다. 아래에서 현재 파일과 재실행 결과로 각각 검산한다.

### 2. 화면의 액션 계산과 실제 렌더 분리 확인

- `actionsForStatus` 자체는 `DRAFT save/cancel`, `SAVED send/cancel`, `SENT accept/reject/cancel`, `ACCEPTED process/reject`, `PROCESSING complete`, `INSPECTING inspect/reject`, `COMPLETED OUTBOUND ship / INBOUND confirm`, `SHIPPING OUTBOUND deliver`, `DELIVERED OUTBOUND confirm`을 계산한다.
- 모바일은 이 목록에서 `reject/cancel`을 제외한 첫 액션을 `mobilePrimaryAction`으로 그대로 렌더한다.
- 데스크톱은 예외가 있다. `slip.status === 'COMPLETED' && canCollabEdit`이면 `nextPrimaryAction` 버튼 대신 `수정` 버튼만 렌더한다. `canCollabEdit`은 `slip.audit-overlay` UPDATE 권한이 있고 물리 종결 상태가 아니면 참이며, 권한 seed에는 MASTER/MANAGER/SALES/WAREHOUSE의 UPDATE가 존재한다.
- 따라서 `actionsForStatus` 배열의 포함 여부만으로는 COMPLETED 데스크톱의 실제 버튼 노출을 증명할 수 없다. 백엔드가 COMPLETED 전이를 허용하는지 확인한 뒤 도달 결함으로 확정한다.

### 3. OUTBOUND SENT `PARTNER_ORDER` 취소는 화면 노출 후 409

- 주문 전환 발행 경로는 `sourceType=PARTNER_ORDER`를 지정하고 전표를 즉시 `DRAFT → SAVED → SENT`로 만든다. 이 상태의 전표는 판매 목록/상세 `/sales/:id`에서 실사용자가 열 수 있다.
- 화면은 sourceType을 응답 타입에 보유하지 않고 SENT이면 무조건 `cancel`을 포함한다. 데스크톱 `삭제`와 모바일 더보기의 `전표 취소`는 취소 권한 보유자에게 활성화된다.
- `Slip.cancel()`은 상태 검사보다 먼저 `sourceType == PARTNER_ORDER`를 검사해 `ErrorCode.CONFLICT`와 `주문 전환 출고전표는 취소할 수 없습니다`를 던진다. 즉 상태표의 단순 `SENT → cancel`은 이 실사용 하위 유형에서 거짓이다.
- 재현 경로: **판매 주문서에서 판매전표 전환/발행 → 판매관리에서 생성된 SENT 전표 상세(`/sales/:id`) → 하단 `삭제`(모바일: 더보기 → `전표 취소`) → 확인 → 409와 오류 배너**.

### 4. COMPLETED 데스크톱에서 백엔드 허용 전이가 `수정`으로 대체됨

- 백엔드는 OUTBOUND `COMPLETED → ship → SHIPPING`, INBOUND `COMPLETED → confirm → CONFIRMED`를 허용한다.
- 그러나 데스크톱 footer는 `slip.status === 'COMPLETED' && canCollabEdit`일 때 전이 버튼을 렌더하지 않고 `수정` 버튼 하나로 교체한다. MASTER/MANAGER/WAREHOUSE는 `slip.audit-overlay` UPDATE seed가 있으므로 이 분기에 실제로 들어가며, 동시에 OUTBOUND의 `ship` 또는 INBOUND의 `confirm` 백엔드 권한도 보유한다.
- 재현 경로 A: **판매관리 → COMPLETED 출고전표 상세(`/sales/:id`) → 데스크톱 하단 액션 → `배송 시작`/`완료 (배송 시작)`이 없고 `수정`만 표시 → SHIPPING으로 진행 불가**.
- 재현 경로 B: **구매관리 → COMPLETED 입고전표 상세(`/purchases/:id`) → 데스크톱 하단 액션 → `확정`/`완료 (확정)`이 없고 `수정`만 표시 → CONFIRMED로 진행 불가**.
- 모바일은 `mobilePrimaryAction`을 별도로 렌더하므로 같은 결함이 재현되지 않는다.

### 8. 기존 백엔드 회귀 증거 교차확인

- `Phase26cSlipImmutableIT.s5_partnerOrderSlip_cancelBlocked`는 GUI가 만드는 것과 같은 `sourceType=PARTNER_ORDER`, `status=SENT` 전표를 발행한 뒤 `POST /slips/{id}/cancel`이 409 CONFLICT인지 명시적으로 검증한다. 결함 1은 도달 가능성뿐 아니라 기대 HTTP 결과도 기존 백엔드 테스트 소스로 고정되어 있다.
- `SlipDomainTest`의 OUTBOUND lifecycle은 `complete()` 후 `INSPECTING`, `inspect()` 후 `COMPLETED`, 이어서 `ship()`/`deliver()`/`confirm()`을 호출한다. INBOUND lifecycle은 `COMPLETED`에서 곧바로 `confirm()`한다. 결함 2-A/2-B의 누락 버튼이 가리켜야 할 백엔드 전이가 실제 허용 전이임을 확인했다.

## R24 증거 무결성 정정

1. R24 원문: **"`cancel`의 도메인 내부 `PARTNER_ORDER` 추가 가드는 기존 화면 액션 집합과 별도의 실행 시 검증"**
   - 정정: 이번 유일한 질문은 바로 "화면이 노출한 액션이 실행 시 409/422를 내는가"다. GUI에서 정상 생성되는 SENT 주문전환 전표에 cancel을 노출하고 백엔드가 항상 409를 내므로, 이를 별도 검증으로 제외한 R24의 SENT `일치` 판정은 틀렸다.
2. R24 원문: **`COMPLETED (OUTBOUND) | ship | ship | 일치`**, **`COMPLETED (INBOUND) | confirm | confirm | 일치`**
   - 정정: 이는 `actionsForStatus`의 중간 배열만 본 값이다. 실제 데스크톱 JSX는 `COMPLETED && canCollabEdit`에서 ship/confirm 버튼을 `수정`으로 교체한다. 실제 GUI 노출 기준으로 두 행 모두 불일치다.
3. R24 원문 제목: **`GREEN 원문`**
   - 정정: 핵심 수치 `Test Files 1 passed`, `Tests 5 passed`는 재현됐다. 다만 R24 블록은 실제 출력의 `(1)`, `(5)`, 파일 실행시간, 시작시각, 전체 Duration을 생략했으므로 원문이 아니라 축약문이다. R25 실측 원문은 확인 로그 5에 기록했다.
4. R24 원문 제목: **`RED 원문`**
   - 정정: 대상 HEAD는 이미 수정 후 상태라 `2 failed, 3 passed`는 재현되지 않는다. 사전 수정 소스를 복구하지 않는 이번 제약 안에서는 역사적 요약으로만 남기며, 현재 HEAD 증거로 사용하지 않았다.
5. R24가 적은 ESLint exit 0, TypeScript exit 0, `SlipDomainTest`의 `BUILD SUCCESSFUL`은 이번 라운드의 단일 관련 Vitest 제한 때문에 재실행하지 않았다. 반대 증거는 없지만 R25 재현 증거로도 세지 않았다.

## 결함

1. **(신뢰도 10/10) OUTBOUND SENT `PARTNER_ORDER`의 cancel 노출 후 409**
   - 재현: 판매 주문서 → 판매전표 전환/발행 → 생성된 SENT 전표 상세 → `삭제`/`전표 취소` → 확인 → 409.
   - 원인: FE는 sourceType 없이 SENT에 cancel을 항상 넣고, BE `Slip.cancel()`은 `PARTNER_ORDER` cancel을 항상 CONFLICT로 거부한다.
2. **(신뢰도 10/10) OUTBOUND COMPLETED 데스크톱의 ship 버튼 소실**
   - 재현: 판매관리 → COMPLETED 출고전표 상세 → 데스크톱 하단에 `배송 시작` 대신 `수정`만 표시 → SHIPPING 진행 불가.
   - 원인: `COMPLETED && canCollabEdit` 분기가 `nextPrimaryAction=ship` 렌더 전체를 대체한다.
3. **(신뢰도 10/10) INBOUND COMPLETED 데스크톱의 confirm 버튼 소실**
   - 재현: 구매관리 → COMPLETED 입고전표 상세 → 데스크톱 하단에 `확정` 대신 `수정`만 표시 → CONFIRMED 진행 불가.
   - 원인: 같은 분기가 `nextPrimaryAction=confirm` 렌더 전체를 대체한다.
