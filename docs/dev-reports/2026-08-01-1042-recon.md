# 재고 현황 조회 400 — 정찰

조기 PR 개설용 자리표시. Codex 정찰 결과를 이 파일에 누적한다.

## 1. 화면의 실제 요청과 400 원인 (2026-08-01)

- 화면: `clients/desktop/src/renderer/routes/warehouse/InventoryStockBalancePage.tsx`
  - 조회 버튼은 선택 창고를 `queryWarehouseId`에 반영한 뒤 `listStockBalances()`를 실행한다.
  - 화면에는 창고 선택만 있고 품목 선택은 없다.
- API 함수: `clients/desktop/src/renderer/api/inventory.ts`의 `listStockBalances()`
  - 실제 요청은 `GET /inventory/balances`이다.
  - 항상 `page`와 `size`를 보내고, 창고를 선택한 경우에만 `warehouseId`를 보낸다.
  - `productId`는 옵션 타입에도 없고 요청에 포함되지 않는다.
- 서버: `services/inventory-service/src/main/java/com/samhanair/logis/inventory/web/StockController.java`
  - `GET /inventory/balances`는 `@RequestParam UUID productId`를 필수로 요구한다.
  - `warehouseId` 파라미터는 선언되어 있지 않다.
  - 저장소 호출도 `findAllByProductIdAndIsDeletedFalse(productId, pageable)`로 품목 기준만 지원한다.

판정: 화면과 서버 계약이 양방향으로 불일치한다. 전체 창고 조회는 `page,size`만 보내므로 필수 `productId` 누락 400이고, 특정 창고 조회도 `warehouseId,page,size`만 보내므로 동일하게 400이다. 서버가 알 수 없는 `warehouseId`를 무시하는지 여부와 무관하게 필수 `productId` 누락에서 먼저 실패한다. UUID는 내부 요청 키로만 쓰이며 화면 표시는 품목코드/품목명/창고코드/창고명으로 구성되어 UUID 비공개 규약은 현재 UI에서 지켜진다.

## 2. `POST /balances/batch`의 용도와 목록 화면 적합성 (2026-08-01)

- 요청 계약: `{ productIds: UUID[] }`, 1~100건 필수. 빈 배열과 100건 초과는 400이다.
- 조회 계약: 요청한 품목 각각에 대해 모든 활성 창고 잔량을 묶어 반환하며, 요청 품목 순서를 보존한다. 서버 쿼리는 `productId IN (...)` 한 번이다.
- 본래 용도: Javadoc·설계 문서·서비스 테스트 모두 영업 견적/주문 라인의 “이미 선택된 여러 품목” 재고 동시 조회로 명시한다.
- 제약:
  - 전체 품목 목록을 발견하는 API가 아니므로 호출 전에 화면이 품목 UUID 목록을 별도로 확보해야 한다.
  - 최대 100품목이고 페이지네이션이 없다. 현재 시드 기준도 100품목 × 2창고라 상한에 걸리며 품목 증가 시 전체 현황을 담을 수 없다.
  - 요청 자체에 창고 필터가 없으므로 선택 창고 필터링은 응답 후 FE에서 해야 한다.
  - 권한은 `inventory.list:VIEW`이고 현재 GET은 `inventory.stock-balance:VIEW`라 단순 전환 시 권한 의미가 바뀐다.
  - 응답은 내부 `productId`와 창고 코드/이름/유형·수량을 주지만 품목 모델코드/품목명은 주지 않는다. 호출자가 이미 가진 품목 메타데이터와 합치는 전제다.

판정: 방향 ③은 현재 화면의 목적(전체 재고 현황 + 창고 필터 + 서버 페이지네이션)과 직접 맞지 않는다. 품목 카탈로그 선행 조회, 100건 초과 분할, 응답 병합, FE 창고 필터, 권한 정합을 함께 새로 설계해야 하므로 “기존 다중 경로 재사용”이라는 작은 수정이 아니다. 반대로 이미 품목을 선택한 모달에서는 `fetchProductBalancesMatrix()`가 batch 응답과 `listWarehouses()`를 병합해 올바르게 사용 중이다.

### 추가로 발견한 후속 응답 계약 결함

현재 목록 화면 타입 `StockBalanceListRow`는 `productCode`, `productName`, `warehouseType`을 필수로 기대한다. 그러나 서버 `StockBalanceResponse`는 `id`, `productId`, `warehouseId`, 창고 코드/이름, 수량, version만 반환한다. 따라서 필수 파라미터 400을 제거하는 것만으로는 화면의 품목 표시와 창고유형 분기가 정상화되지 않는다. UUID를 노출하지 않으려면 서버 또는 FE의 product-service 병합 경계에서 모델코드/품목명을 채워야 한다.

## 4. 같은 형태 전수 검색과 개수 (2026-08-01)

전수 범위는 이 트랙의 서버 경계인 inventory-service의 “필수 query parameter가 있는 GET endpoint” 전체와, `clients/desktop/src/renderer`의 production API/화면 호출 전체로 잡았다. mock·test는 별도 false-green 근거로 분리했다.

inventory-service에서 필수 query parameter를 갖는 GET은 다음 6개다.

1. `/inventory/balances` — `productId` 필수: **재고 현황 화면이 누락**.
2. `/warehouse/audit/dps-compare/by-product` — `fromDate`, `toDate` 필수: `getDpsByProduct()`가 둘 다 전송.
3. `/warehouse/audit/dps-history/latest` — `programType` 필수: `getLatestDpsHistory()`가 전송.
4. 내부 `/internal/inventory/warehouses/by-code` — `code` 필수: 사용자 화면용 endpoint가 아니며 호출 계약상 code 제공.
5. `/inventory/stock-instances/fifo` — `productCode` 필수: 현재 데스크톱 production 화면 호출 없음.
6. `/inventory/stock-instances/recall` — `partnerCode` 필수: 현재 데스크톱 production 화면 호출 없음.

**개수 판정: 필수 query parameter 없이 호출하는 production 화면은 총 1개**이며, `InventoryStockBalancePage`의 `listStockBalances()` 한 자리다. 같은 함수의 다른 production 호출자는 없다. 모바일/웹 production client에서도 `/inventory/balances` GET 호출자는 발견되지 않았다.

화면 외에는 `tools/operational-validation/run-smoke-tests.ps1`가 `GET /api/v1/inventory/balances?page=0&size=10`을 호출해 `productId`를 똑같이 누락한다. 따라서 별도 비화면 결함 후보는 1개다.

### false-green 원인

- desktop mock의 `GET /inventory/balances` handler는 서버의 필수 `productId`를 검증하지 않고 목록 fixture를 반환한다.
- Phase 2.6c Playwright는 이 mock 계약을 사용하므로 실 서버 400을 검출하지 못한다.
- 서버 permission/IT는 반대로 GET 호출 시 `productId`를 명시하므로 서버 자체 계약은 통과한다.

즉 FE mock은 “창고 필터 목록 API”, BE 테스트는 “품목별 조회 API”라는 서로 다른 계약을 각각 green으로 만들었고, 경계 계약 테스트가 없었다.

## 6. 세 방향 판단 및 제안 (2026-08-01)

### ① 화면에 품목 필터 추가

- 장점: 기존 GET의 필수 `productId` 계약을 보존해 조회 범위와 DB 부하가 가장 작다.
- 필요한 추가 작업: 품목 검색/선택 UX, 모델코드·품목명 병합, 선택 창고 필터의 BE 지원 또는 FE 병합, `warehouseType` 응답 정합.
- 문제: 화면의 현재 명칭·문서·그리드·서버 페이지네이션은 전체 재고 현황을 의도하고, DB도 101품목 전체 분포를 보여줄 필요가 있다. 품목을 필수로 만들면 화면의 제품 의미가 “현황”에서 “품목 단건 조회”로 바뀐다.
- **기획 결정 필요**: 이 메뉴가 전체 재고 장부인지, 사용자가 반드시 한 품목을 골라 보는 조회 도구인지 결정해야 한다.

### ② `productId` 선택화 + 전체/창고별 페이지 조회 — 권장

- 근거: 현 UI 계약(`전체 창고`/창고 선택, 50행 페이지), 화면 도입 주석, DB 201행 분포와 일치한다.
- 권한: endpoint의 `inventory.stock-balance:VIEW`는 MASTER/MANAGER/WAREHOUSE/INVENTORY로 제한되어 있다. 이 page code를 유지하면 역할 확대는 없지만, 해당 역할 안에서는 데이터 범위가 “한 품목”에서 “전체 품목”으로 넓어진다. 감사/보안 관점의 명시적 승인 대상이다.
- 성능:
  - 현재 201행에서는 50행 pagination으로 작다.
  - 현 인덱스는 `(product_id,is_deleted)`와 활성 `(product_id,warehouse_id)`뿐이며 warehouse 선두 인덱스가 없다. 전체/창고 필터가 커지면 table/count scan 위험이 있다.
  - 구현 시 page/size 상한, 안정 정렬, 활성 `(warehouse_id, …)` 인덱스 검토, warehouse `EntityGraph`가 필요하다. `open-in-view=false`이고 `Warehouse`가 LAZY라 서비스 transaction 또는 fetch graph 없이 DTO 매핑하면 후속 500 위험이 있다.
  - 품목 모델코드/품목명은 현재 Excel export처럼 페이지의 distinct 품목을 product-service bulk lookup으로 결합해야 하며 N+1 호출을 피해야 한다.
- 단순히 `required=false`만 붙이는 수정은 불충분하다. `productId/warehouseId` 조합별 repository 분기, 전체 활성행만 조회, 응답 DTO의 모델코드·품목명·창고유형, 권한/페이지 크기/인덱스까지 하나의 계약으로 다뤄야 한다.

### ③ 화면을 `/balances/batch`로 전환

- 비권장. batch는 이미 선택된 1~100품목의 매트릭스용이며 전체 목록 발견·pagination·서버 창고 필터가 없다.
- 101번째 품목부터 누락/분할 로직이 필요하고, 현재 DB가 이미 101품목이라 단일 batch 한도를 초과한다.
- `inventory.list:VIEW`는 SALES/ACCOUNTANT까지 포함해 현재 화면의 `inventory.stock-balance:VIEW`보다 넓다. endpoint를 그대로 쓰면 서버 권한 경계도 달라진다.
- 모델코드/품목명은 별도 카탈로그에서 미리 확보해야 하므로 결과적으로 전체 카탈로그 조회 + chunk batch + 병합이라는 더 비싼 FE 구현이 된다.

### 최종 제안

**②를 통합 계약으로 구현하는 것이 가장 타당하다.** 다만 이는 단순 버그 한 줄 수정이 아니라 “권한 있는 재고 담당자에게 전체 활성 재고 장부를 페이지 공개한다”는 데이터 범위 결정이다. 따라서 전체 조회 허용 자체는 **기획/보안 결정 필요**로 표시한다. 승인되지 않으면 차선은 ①이며, ③은 현 데이터 규모·권한·pagination 때문에 선택 근거가 약하다.
