## 0. 설계 및 범위 판정

R23 진단 보고서(`docs/dev-reports/2026-08-04-1001-r23-structural-diagnosis-2.md`)의 원인 판정을 기준으로 한다.

- 일괄 인쇄: Electron에서 차단되는 반복 `window.open`을 제거하고, 선택 거래처들을 하나의 HashRouter 일괄 인쇄 화면으로 전달한다. 단건 경로는 기존 `navigate()` 계약을 유지한다.
- 조회 side effect: legacy `/accounting/journals/ledger-data` GET에서 snapshot 저장을 제거한다. 저장이 필요한 기존 기능은 명시적 저장 호출 경로를 유지하거나 별도 POST 트리거로 보존한다. legacy endpoint 자체의 제거·adapter 수렴은 이번 범위 밖이다.

이번 수정은 상태 집합, `SALE_SUMMARY` 정책, 실 데이터·스냅샷, Docker, 전체 Playwright/Gradle suite를 변경하지 않는다.

## 1. 결함 1 — 일괄 인쇄

### 원인

R23 확인 원인: `clients/desktop/src/renderer/routes/PartnerLedgerPage.tsx:306-318`의 일괄 인쇄 경로가 확인 후 거래처마다 `window.open(..., '_blank')`를 호출한다. Electron renderer에서는 내부 popup이 차단되며, 단건 경로 `:299-304`처럼 HashRouter `navigate()`를 사용하지 않는다. 활성 batch 경로 회귀 테스트도 없었다.

### 수정 및 판정 근거

대상 테스트가 선택 건 모두를 하나의 내부 인쇄 경로로 전달하고, `window.open`을 호출하지 않음을 검증하도록 한다. 단건은 기존 `navigate(buildPrintPath(...))`를 유지한다.

선택된 `QA-GATE-A`, `QA-GATE-B`가 `/print/partner-ledger-batch`로 함께 전달되고, `window.open` 호출 횟수는 0건이었다. batch print view도 두 거래처 원장명을 실제 렌더링했다.

### 반대급부 확인

- 단건 인쇄: 기존 단건 `navigate()` 회귀 테스트 및 대상 테스트로 확인한다.
- 일괄 인쇄: 선택 거래처가 batch 인쇄 route/state에 모두 나타나는지 확인한다.

## 2. 결함 2 — GET 조회 side effect

### 원인

R23 확인 원인: `services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/LedgerImageService.java:126-132`의 legacy `GET /accounting/journals/ledger-data` 호출 내부가 조회 결과를 만든 뒤 `TaxInvoiceBatch` snapshot을 자동 저장한다. 진단 중 GET 3회로 `LED20260804021438728`, `LED20260804021438773`, `LED20260804021438793`이 생성됐다.

### RED

대상 테스트와 실패 원문:

```text
BE RED — `..\..\gradlew.bat :services:accounting-service:test --tests com.samhanair.logis.accounting.service.LedgerImageServiceTest`
10 tests completed, 3 failed
FAIL 원장 조회는 TaxInvoiceBatch 스냅샷을 저장하지 않는다
FAIL 조회는 actor가 있어도 snapshot을 저장하지 않는다
FAIL 조회는 batch 번호를 생성하거나 저장하지 않는다
org.mockito.exceptions.verification.NeverWantedButInvoked
```

### 수정 및 판정 근거

GET은 ledger image를 읽고 반환하는 역할만 맡긴다. 기존 snapshot 저장이 필요한 경로는 명시적 저장 서비스/호출을 유지하며, 자동 저장 호출만 GET에서 분리한다. 이번 범위에서는 legacy `/ledger-data` 제거 또는 공통 산출기 adapter 수렴을 하지 않는다.

### GREEN

수정 후 대상 테스트 fresh 실행 원문:

```text
BE GREEN — `..\..\gradlew.bat :services:accounting-service:test --tests com.samhanair.logis.accounting.service.LedgerImageServiceTest --tests com.samhanair.logis.accounting.service.LedgerSnapshotServiceTest`
BUILD SUCCESSFUL
13 tests completed, 0 failed
```

`LedgerImageService.getLedger()`는 `@Transactional(readOnly = true)` 조회만 수행한다. 저장은 명시적 `POST /accounting/journals/ledger-snapshots` → `LedgerSnapshotService.capture()`에서 수행하며, capture 테스트는 repository save 및 actor 보존을 확인한다.

### 반대급부 확인

- GET 반복 조회 후 snapshot 수가 증가하지 않는지 테스트한다.
- 사용자가 의도한 snapshot 저장 경로가 여전히 저장되는지 기존/신규 좁은 테스트로 확인한다.
- 진단 중 생성된 3건은 보존하며 삭제하지 않는다.

진단 중 생성된 `LED20260804021438728`, `LED20260804021438773`, `LED20260804021438793`은 건드리지 않았다.

## 3. 범위 밖 기록

legacy `/accounting/journals/ledger-data`는 이번 R24에서도 아직 살아 있다. 독립 `LedgerImageService` 제거 또는 공통 산출기 adapter 수렴은 다음 판단 대상으로 남긴다.

GET 호출부와 FE mock/API 계약도 legacy `/ledger-data`를 아직 사용한다. 이번에는 endpoint 제거·adapter 수렴을 하지 않았다.
