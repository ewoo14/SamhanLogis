## 2. 각도 2 — 조회 시점 변경이 만든 새 표면

### 2.1 도달 결함 1 — 미조회 상태가 다시 `수정 0회`와 `변경 이력 없음`으로 표시된다

endpoint가 없는 여섯 화면의 query는 모두 `auditHistoryOpen`이 `true`일 때만 활성화된다.

- 세금계산서 상세 `TaxInvoiceDetailPage.tsx:117-122`
- 세금계산서 작성·편집 `TaxInvoiceFormPage.tsx:223-228`
- 매출마감 `SalesClosingPage.tsx:181-186`
- 기간마감 `PeriodCloseListPage.tsx:142-147`
- 월말마감 `MonthEndClosingPage.tsx:183-188`
- DC 설정 `SalesPartnerDcConfigPage.tsx:69-75`

모달을 처음 열기 전에는 요청이 없으므로 `auditQuery.data === undefined`, `auditQuery.isError === false`다. 그러나 여섯 화면 모두 `undefined`를 `[]`로 바꾸어 Badge와 Overlay에 전달한다. Badge는 오류가 아니면 무조건 `ready`로 표시하고 distinct revision 수를 출력한다.

- `AuditOverlaySection.tsx:49` — 빈 logs의 revision 수는 0
- `AuditOverlaySection.tsx:58` — `data-audit-state="ready"`
- `AuditOverlaySection.tsx:68` — 사용자 표시 `수정 0회`
- `AuditOverlay.tsx:105-126` — 오류도 최신 이력도 없으면 `변경 이력 없음`

따라서 여섯 화면에서 사용자가 상세/행 panel만 열고 버전이력 모달은 열지 않는 정상 경로로 다음 상태가 발화한다.

| 시점 | 실제 상태 | Badge/외부 표시 |
|---|---|---|
| 모달 첫 개방 전 | 미조회 | `수정 0회`, Overlay `변경 이력 없음`; DC 요약도 `변경 이력이 없습니다` |
| 첫 요청 중 | 조회 중 | 모달만 loading, 바깥 Badge/Overlay는 계속 0/없음 |
| 404 완료 후 | 기능 미제공 | Badge/Overlay/Modal이 실패·미제공 상태로 전환 |

즉 R4 결함 1이 **오류 후의 0회 표시**에서는 닫혔지만, R5가 새로 만든 **미조회→성공 빈 목록 변환**으로 되살아났다. 조회하지 않은 값을 `0회`라는 사실로 표시하므로 실제 audit row 유무와 무관하게 상태 진술이 잘못됐다. 가상 row나 없는 표본을 만들지 않고 코드 경로만으로 확정할 수 있는 도달 결함이다.

재고감사는 `enabled: !!id`를 유지해 즉시 조회한다(`InventoryAuditDetailPage.tsx:125-130`). 따라서 R5 때문에 이력 표시가 모달 개방까지 사라지거나 늦어지지는 않는다. 성공 응답 뒤에는 실제 이력 또는 `200 + []`가 표시된다. 다만 최초 요청 중 Badge가 잠시 `수정 0회`를 보이는 공통 loading 미구분은 남아 있다.

### 2.2 도달 결함 2 — endpoint 부재 404는 모달을 다시 열 때마다 재요청된다

`retry: false`는 한 번의 query 실행 안에서 자동 재시도만 막는다. 오류 결과 자체를 성공 데이터로 캐시하지는 않는다.

이 프로젝트의 QueryClient는 `staleTime: 5분`이다(`clients/desktop/src/renderer/App.tsx:19-27`). 설치된 TanStack Query 구현은 다음 조건을 사용한다.

- 이전 `enabled=false`에서 `true`가 되면 optional fetch 후보가 된다: `clients/desktop/node_modules/@tanstack/query-core/src/queryObserver.ts:791-802`
- `data === undefined`인 query는 항상 stale이다: `clients/desktop/node_modules/@tanstack/query-core/src/query.ts:316-320`

200 성공은 빈 배열이어도 `data`가 있어 5분 동안 캐시되므로 그 안의 재개방은 재요청하지 않는다. 반면 endpoint가 없는 여섯 화면의 404는 `data`가 계속 `undefined`다. 모달을 닫아 `enabled=false`로 만들고 다시 열어 `true`로 만들면 stale 조건이 충족되어 **개방마다 404 한 번**이 다시 나간다.

무한 loop나 한 개방 안의 retry는 없다. 그러나 R4에서 확인했던 “재개방은 재요청하지 않음” 성질은 endpoint 부재 경로에서 유지되지 않았다.

### 2.3 목록 행 변경에서 이전 행 데이터는 섞이지 않지만 결함 1이 새 행마다 반복된다

마감 3개와 DC 설정의 audit query key에는 각각 `selectedClosingId` 또는 `selectedPartnerCode`가 포함된다. React Query가 A행 데이터를 B행 key에 넘기는 `placeholderData`도 없다. 따라서 이전 행의 성공·오류 데이터가 다른 행에 남는 경로는 확인되지 않았다.

다만 B행을 선택한 뒤 모달을 열기 전에는 B행 query도 disabled/undefined이므로 `수정 0회`와 `변경 이력 없음`이 새로 표시된다. 이는 이전 행 잔존 결함이 아니라 2.1의 미조회 상태 오표시가 행마다 반복되는 것이다.

## 3. 각도 3 — mock 격리와 상태 형상

### 3.1 실 HTTP 누출은 차단됐다

audit 전용 handler는 broad domain handler보다 먼저 실행되고(`mock.ts:2274-2305`), 세금계산서·마감·DC·재고감사 경로 모두 `null` 대신 성공 또는 HTTP 오류 mock을 반환한다. 다음 환경으로 실제 base URL을 고의로 죽인 좁은 게이트를 실행했다.

```text
VITE_MOCK_MODE=1
VITE_API_BASE_URL=http://127.0.0.1:1
src/renderer/api/mock.test.ts 145 passed (145)
측정 2026-08-10 16:21 KST
```

따라서 이 네 API adapter의 mock 요청이 실 HTTP로 fallthrough하는 결함은 재현되지 않았다.

### 3.2 증거 무결성 결함 1 — 재고감사 성공 fixture의 원시 row shape가 실 서버 DTO와 다르다

실 endpoint는 `ApiResponse<List<InventoryAuditLogResponse>>`를 반환한다.

- controller: `services/inventory-service/src/main/java/com/samhanair/logis/inventory/web/InventoryAuditController.java:211-215`
- 실제 row: `InventoryAuditLogResponse.java:12-22`
- 실제 키: `id`, `entityId`, `revisionNo`, `actorId`, `actorName`, `actorColor`, `fieldName`, `oldValue`, `newValue`, `changedAt`

현재 `MOCK_INVENTORY_AUDIT_LOGS`는 `mock.ts:17420-17439`에서 정규화된 클라이언트 키인 `field`, `beforeValue`, `afterValue`를 사용하고 `id`, `entityId`, `actorColor`를 생략한다. mock test도 원시 응답에 `field`가 있다고 고정한다(`mock.test.ts:3815-3832`).

`createAuditApi`가 양쪽 alias를 받아 정규화하므로(`createAuditApi.ts:54-75`) 현재 mock UI는 동작한다. 그러나 이 테스트는 **실 서버 row shape를 통과시킨 증거가 아니다**. R4에서 요구한 “실제 서버 응답 형태와 같은 상태별 handler”라는 증거 조건은 재고감사 성공 경로에서 아직 충족되지 않았다.

404·403·500 body는 공통 `ApiResponse`와 같은 `success/code/message/data/timestamp` envelope이고 HTTP status도 Axios error에 보존된다(`mock.ts:98-108`, `client.ts:67-84`). 세금계산서·마감·DC에는 비교할 실 audit endpoint가 없으므로 성공 row의 실 서버 shape는 **판정 불가**다.

### 3.3 제거 분기의 audit 잔여 참조는 0건이다

audit component/API/일곱 route를 exact grep한 결과:

- `treat404AsNotSupported`: 0건
- audit error kind의 `not-found`: 0건
- 현재 `AuditHistoryErrorKind`: `not-supported | forbidden | temporary`만 존재(`AuditVersionHistory.tsx:11`)

일반 `NotFoundPage`의 test id는 audit 분기와 무관하다.

## 5. 지금 고칠 것 / 분리할 것

### 지금 고칠 것

1. **미조회·조회 중·성공 빈 목록·오류를 모든 소비처에서 분리한다.**
   - 200 응답을 받기 전에는 Badge가 `수정 0회`/`ready`를 사실로 표시하지 않아야 한다.
   - Overlay와 DC 별도 요약도 미조회/조회 중을 `변경 이력 없음`으로 표시하지 않아야 한다.
   - 7 Badge, 6 Overlay, 7 Modal뿐 아니라 DC의 표 밖 요약 소비처까지 같은 상태 계약을 적용한다.
2. **동일 entity에서 확정된 endpoint 부재 404를 모달 재개방마다 다시 요청하지 않게 한다.**
   - `retry:false`와 별개로 close/open에 따른 새 fetch를 막는 상태 또는 capability 계약이 필요하다.
   - 성공 데이터는 기존 5분 cache 정책을 유지할 수 있으나, 부재 endpoint의 확정 상태도 재개방 동안 보존돼야 한다.
3. **재고감사 mock의 원시 성공 row를 실제 `InventoryAuditLogResponse` shape와 맞춘다.**
   - raw handler 계약과 `createAuditApi` 정규화 후 계약을 구분해 증거를 남겨야 한다.

**도달 결함 2건 · 증거 무결성 결함 1건 · 현재 상태 머지 비권고.**
