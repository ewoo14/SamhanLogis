## 1. 요약과 다른 사실

- “잠금 대상 5건”은 **fresh 표준 시드 직후에만** 맞다.
- 날짜는 `SlipSeeder.buildSpecs()`와 `computeSlipDate()`에서 파생되므로 날짜 상수를 다시 복제하지는 않았다. spec/날짜 계산이 바뀌면 따라간다.
- 하지만 `confirmedSeedDates()`의 5개 값 자체가 아니라 `min()`/`max()`만 사용한다. 따라서 비연속 날짜 사이의 모든 활성·미잠금 CONFIRMED 전표를 흡수한다.
- 공유 DB 2026-08-09 07:31:57 KST 기준 해당 기간 활성 CONFIRMED는 **7건**이다. 이미 잠긴 5건 외에 현재 R4 쿼리가 새로 잠글 행은 **2건**이다.
- PM의 `tsc -p tsconfig.json` 0건과 구현자의 기존 오류 2건은 서로 모순이 아니라 **검사 대상 차이**다. 루트 `tsconfig.json`은 `files: []`와 project references만 있고 `tsc -p`는 하위 project를 build하지 않아 exit 0이다. 실제 `tsconfig.web.json`은 기존 TS2322 2건으로 exit 1이다.

## 4. (c) 성능 — 쿼리 수

- FE는 line별 호출이 아니라 중복 제거 후 100개씩 chunk한다.
- 임시 Vitest 계측에서 서로 다른 productId 250개를 입력했을 때 `apiClient.post` 호출은 **3회**, chunk 크기는 **[100, 100, 50]**이었다. 250회가 아니다. 임시 계측 파일은 즉시 삭제했다.
- product-service의 각 요청은 `ProductRepository.findAllByIdIn(ids)` 한 번이므로 DB 조회도 chunk당 1회, 250 unique 기준 **3회**다.
- 공유 DB 2026-08-09 07:38:24 KST의 실제 최대 전표는 활성 라인 12개, unique product 7개이며, unique 최대는 8개다. 현재 모든 전표는 presence HTTP/DB 조회 **각 1회**다.
- 결론: `ceil(uniqueProductIds / 100)`으로 증가하며 N+1은 아니다.

## 5. (d) 삭제 허용 유지

R4 commit의 product-service 삭제 controller/service, `ProductFormPage`, `productCatalogApi.deleteProduct` diff는 **0줄**이다. 전체 #1051 branch에서도 해당 삭제 경로 diff는 0줄이다. 현재 삭제 흐름은 기존 그대로 `DELETE /api/products/{id}` → `ProductService.delete()` → soft-delete다.

기존부터 존재한 BUNDLE 구성품 집합 확인 및 활성 수량동기화 규칙 참조 차단은 그대로지만, 전표/견적 참조를 이유로 한 신규 차단은 추가되지 않았다. 개발책임자가 선택한 “전표 참조 중이어도 삭제 허용”은 유지된다.

## 8. 검증 한계

- Docker 서비스를 R4 HEAD로 재배포하거나 시더를 공유 DB에서 실제 실행하지 않았다. lock 도달성은 실제 현재 repository 조건과 DB 전수 SELECT, runner 조건/게이트를 결합해 판정했다.
- 네트워크 장애·승인선 예외 계정으로 실제 UI를 열어 경고 미탐을 계측하지 않았다.
- UUID mutation을 이번 라운드에 다시 주입하지 않았다. 기존 3 assertion site와 무변경 diff를 확인했다.
- 실제 최대 8 unique보다 큰 전표의 성능은 임시 mock 계측(250 unique)과 BE repository 코드로 검증했다.
