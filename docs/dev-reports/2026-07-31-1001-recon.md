# Issue #1001 정찰 보고서 — 거래처별 원장 표시 사양

- 조사일: 2026-07-31
- 조사 범위: 거래처별 원장 화면·라우트·API·DB 원천, 기존 결정 교차검증, 구현 슬라이스 제안
- 조사 원칙: 구현·소스 수정 없음, Docker 이미지 재빌드·서비스 재기동 없음, DB 쓰기 없음
- DB 조회 방식: 모든 `psql` 조사문을 `BEGIN READ ONLY` 또는 `default_transaction_read_only=on`으로 실행

## 1. 결론

현재 `/accounting/partner-ledger`는 요구된 **판매전표 + 입금보고서 문서 원장**이 아니라, 회계 분개를 거래처로 모아 **계정별 차변·대변 라인**으로 보여주는 화면이다. 판매전표 품목, 수량, 부가세 포함 단가, 배송주소는 현 원장 응답 계약에 없다. 입금보고서도 문서 1건 또는 배분 1행으로 표시되지 않고 원분개·역분개의 복식부기 라인으로 풀려 나온다.

원천 데이터는 다음처럼 엇갈린다.

| 요구 값 | 구조 존재 | 공유 DB 실데이터 | 현 원장 API 배선 |
|---|---:|---:|---:|
| 판매전표 품목별 부가세 포함 단가 | 있음 | 활성 판매전표 라인 2,659/2,659건 값 있음 | 없음 |
| 배송주소 `slips.delivery_address` | 있음 | 활성 판매전표 2,299건 중 값 있는 문서 0건 | 없음 |
| 입금보고서 | 있음 | 활성 25건, 그중 분개 연결 21건 | 분개 라인으로 간접 노출 |
| 판매전표 + 입금보고서 2종 문서 구성 | 없음 | 해당 통합 read model 없음 | 없음 |

따라서 단순 화면 열 추가로 끝나지 않는다. 판매전표 원천 read 계약, 배송주소 수집 경로, 회계 서비스의 2종 통합 응답, 데스크톱 본문, 실제 인쇄 화면을 순서대로 나눠야 한다.

## 3. 현재 상태 실측

### 3.1 실제 화면 진입과 호출 경로

라우트는 두 개 모두 실재한다.

| 표면 | 실제 상태 | 근거 |
|---|---|---|
| 조회 화면 | `/accounting/partner-ledger`, `accounting.partner-ledger` `VIEW` 가드 | `clients/desktop/src/renderer/routes/index.tsx:958-968` |
| 인쇄 화면 | `/print/partner-ledger`, 같은 `VIEW` 가드 | `clients/desktop/src/renderer/routes/index.tsx:970-977` |

조회 화면은 `LedgerController`의 `/accounting/ledgers`를 사용하지 않는다. 실제 호출은 아래 두 개다.

| 단계 | 호출 API | 화면 역할 | 근거 |
|---|---|---|---|
| 1 | `GET /accounting/sales/aggregate` | 거래처별 매출·수금·채권 집계 | `clients/desktop/src/renderer/api/partnerLedgerApi.ts:110-132`, `clients/desktop/src/renderer/routes/PartnerLedgerPage.tsx:230-239` |
| 2 | `GET /accounting/journals/ledger-data` | 선택 거래처의 분개 라인 상세 | `clients/desktop/src/renderer/api/partnerLedgerApi.ts:134-152`, `clients/desktop/src/renderer/routes/PartnerLedgerPage.tsx:241-245` |

별도 `LedgerController`의 `GET /accounting/ledgers`는 존재하지만 `accounting.general-ledger` 권한과 `LedgerResponse`를 쓰는 다른 경로다(`services/accounting-service/src/main/java/com/samhanair/logis/accounting/web/LedgerController.java:54-75`). Issue 원문의 파일 지목만 보고 이 컨트롤러가 현 화면의 직접 백엔드라고 단정하면 틀린다.

### 3.2 화면이 지금 표시하는 값

#### 1단계 집계

화면은 기간과 선택 거래처 코드를 입력받고 다음 열을 표시한다.

```text
선택 | 거래처코드 | 거래처명 | 매출 합계 | 수금 합계 | 채권 잔액 | 원장
```

근거는 `clients/desktop/src/renderer/routes/PartnerLedgerPage.tsx:309-379`, `:451-502`다. 다만 `거래처코드` 열의 실제 셀은 `row.partnerCode`가 아니라 숫자만 남긴 `row.bizNo`를 렌더한다(`:456`, `:490-493`). 필터 placeholder는 거래처 코드 형식이다(`:354-361`). 즉, 열 이름·필터 의미와 실제 셀 값이 서로 다르다.

집계 백엔드는 분개 계정코드 401과 110만 사용한다.

- 401 대변-차변 = 매출 합계
- 110 대변 = 수금 합계
- 110 차변-대변 = 채권 잔액

근거는 `services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/SalesAggregateService.java:78-103`, `:130-139`다. 실 실행 중 서비스에 2026-01-01~2026-07-31을 조회했을 때 HTTP 200과 집계 41행을 확인했다.

#### 2단계 상세

선택 거래처 상세 헤더는 거래처명, 사업자번호, 단톡방, 기간을 표시한다(`clients/desktop/src/renderer/routes/PartnerLedgerPage.tsx:585-621`). 본문은 다음 열뿐이다.

```text
일자 | 분개번호 | 계정 | 적요 | 차변 | 대변 | 잔액
```

근거는 `clients/desktop/src/renderer/routes/PartnerLedgerPage.tsx:636-675`다. 품목명, 모델명, 수량, 단가, 품목 금액, 배송주소, 문서종류는 없다.

CSV도 같은 분개 라인만 `일자, 분개번호, 계정코드, 적요, 차변, 대변, 잔액`으로 직렬화한다(`clients/desktop/src/renderer/routes/PartnerLedgerPage.tsx:103-172`).

금액 포맷은 0을 `—`로 바꾸지만 음수를 `△ 1,234`로 표시한다(`clients/desktop/src/renderer/routes/PartnerLedgerPage.tsx:72-80`). 음수 빨강 스타일도 이 함수와 상세 셀에 없다. 이는 기존 회계 보고서 표시 결정과 어긋난다.

#### 인쇄 화면

인쇄 라우트는 거래처 코드와 기간 query string을 받지만 실제 API를 호출하지 않는다.

- `clients/desktop/src/renderer/print/PartnerLedgerView.tsx:201-222`에서 `MOCK_DATA`를 복사한다.
- `partnerCode`는 mock 객체의 코드만 바꾸고, 거래처명·품목·금액·라인은 정적 데이터다.
- 인쇄 표도 `일자, 전표번호, 적요, 차변, 대변, 잔액`뿐이다(`clients/desktop/src/renderer/print/PartnerLedgerView.tsx:259-327`).

파일 상단의 “API 활성 후 연결” 설명과 달리 현재 코드에는 `useQuery`가 없고, `:213` 주석도 향후 교체 대상으로 남아 있다. 따라서 조회 화면에서 실제 거래처를 골라도 인쇄 미리보기는 실제 원장이 아니다.

### 3.3 실제 원장 API 응답

`GET /accounting/journals/ledger-data`의 응답 계약은 다음뿐이다.

- 헤더: `partnerCode`, `partnerName`, `partnerBusinessNo`, `chatRoomNames`, `periodFrom`, `periodTo`
- 라인: `date`, `journalNo`, `accountCode`, `accountName`, `description`, `debit`, `credit`, `balance`

근거는 `services/accounting-service/src/main/java/com/samhanair/logis/accounting/web/dto/LedgerImageResponse.java:22-52`와 `clients/desktop/src/renderer/api/partnerLedgerApi.ts:68-108`이다. 실 API에서 동일 필드 구성을 확인했다.

실 데이터 `P-2026-0001`, 2026-01-01~2026-07-31 조회는 HTTP 200, 상세 10라인이었다. 그중 4라인의 라인 반영 후 잔액이 0이었다. 이는 서비스가 거래처의 모든 계정을 한 목록에 넣고 각 라인마다 `차변-대변`을 누적하기 때문이다(`services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/LedgerImageService.java:68-108`). 복식부기 한 문서의 모든 계정을 함께 읽으면 한 문서가 끝날 때 합계가 다시 0으로 수렴하므로, 이 `balance`는 매출채권 잔액 전용 열이 아니다.

저장소 쿼리는 다음 조건만 쓴다.

- 거래처 일치
- 기간 일치
- 분개 상태 `POSTED` 또는 `REVERSED`

분개 `source_type`과 계정코드 필터는 없다(`services/accounting-service/src/main/java/com/samhanair/logis/accounting/repository/JournalLineRepository.java:93-108`). 그래서 판매전표·입금보고서 이외 문서도 들어온다.

### 3.4 현재 원장에 섞이는 문서 원천

공유 `accounting_db`의 활성 분개를 실측했다. 아래 `거래처 라인`은 `partner_id`가 있는 라인 수다.

| `source_type` | 상태 | 분개 수 | 거래처 라인 수 | 의미 |
|---|---:|---:|---:|---|
| `CASH_RECEIPT` | `POSTED` | 21 | 42 | 입금보고서 원분개 |
| `CASH_RECEIPT` | `REVERSED` | 18 | 36 | 취소·수정 대상 원분개 |
| `MANUAL` | `POSTED` | 33 | 28 | 수기 분개 |
| `MANUAL` | `REVERSED` | 6 | 2 | 수기 분개 역분개 대상 |
| `SLIP` | `POSTED` | 30 | 90 | 현재 구현상 세금계산서 발행 분개 |
| `SLIP` | `REVERSED` | 5 | 15 | 세금계산서 취소 관련 |

`SLIP`이라는 기술 enum 이름만 보고 판매전표라고 해석하면 안 된다. 실제 생성 코드는 세금계산서 발행 시 `JournalSourceType.SLIP`과 `TaxInvoice.id`를 넣는다(`services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/TaxInvoiceService.java:257-264`). 현 원장은 판매전표가 아니라 세금계산서 분개를 매출 쪽에 주로 보여준다.

실 API 표본에는 취소된 입금보고서 `2026/05/15-1`의 원분개 두 라인과 역분개 `2026/05/15-2` 두 라인이 모두 나타났다. 현재는 입금보고서 1건을 수금내역 1행으로 접지 않는다.

### 3.5 권한 계약도 화면과 API가 다름

- 화면 라우트: `accounting.partner-ledger` `VIEW` (`clients/desktop/src/renderer/routes/index.tsx:963-967`)
- 집계 API: `accounting.reports` `VIEW` (`services/accounting-service/src/main/java/com/samhanair/logis/accounting/web/AccountingReportController.java:102-117`)
- 상세 API: `accounting.partner-ledger` `PRINT` (`services/accounting-service/src/main/java/com/samhanair/logis/accounting/web/AccountingReportController.java:120-133`)

따라서 거래처 원장 `VIEW`만 가진 사용자가 화면에 들어와도 집계 또는 상세 권한이 따로 없으면 403이 날 수 있다. 새 통합 API는 화면의 `VIEW` 계약과 정렬해야 한다.

## 4. 요구와의 격차

| 요구 축 | 요구 상태 | 현재 상태 | 빠진 것·다른 것 |
|---|---|---|---|
| ① 부가세 포함 단가 | 판매전표 품목 전부에 수량, 부가세 포함 단가, `수량 × 단가` 금액 표시 | 원장 DTO와 화면에 품목·수량·단가 필드 자체가 없음. 차변·대변 총액만 표시 | 판매전표 원천 조회, 품목 라인 응답, `unitPriceWithVat`, 수량, 품목 금액, 전표번호별 그룹이 필요 |
| ② 배송주소 데이터 | 적요가 아닌 판매전표의 구조화된 배송주소 표시 | 원장 DTO·API·화면·CSV·인쇄에 주소 필드 없음 | `slips.delivery_address` 배선과 상류 저장 경로 보강이 필요. `memo` 파싱 또는 `shipping_address` 대체 사용은 결정 위반 |
| ③ 판매전표/입금보고서 2종 | 판매전표는 문서 헤더+품목 상세, 입금보고서는 수금내역으로 구성 | 모든 `POSTED`+`REVERSED` 분개 라인을 원천 구분 없이 표시. 수기 분개와 세금계산서 분개도 포함 | 문서종류가 있는 통합 read model, 판매전표 문서 그룹, 입금보고서 문서/배분행, 취소·수정 접기 규칙이 필요 |

부가 격차는 다음과 같다.

- 요구는 왼쪽 `전표번호`인데 조회 화면 본문은 `분개번호`다(`clients/desktop/src/renderer/routes/PartnerLedgerPage.tsx:644`).
- 현 인쇄는 실제 데이터가 아니라 mock이다.
- 현 음수 표시는 `△`이며 빨강이 아니다.
- 현 거래처코드 열은 사업자번호를 표시한다.
- 현 상세 `balance`는 채권 계정 전용 잔액이 아니라 전 계정 차변-대변 누계다.

## 5. 원천 데이터 존재 여부

### 5.1 부가세 포함 단가

구조와 API는 이미 있다.

- DB: `slip_lines.unit_price_with_vat` (`services/slip-service/src/main/resources/db/migration/V12__add_ecount_slipline_fields.sql:16`)
- 엔티티: `SlipLine.unitPriceWithVat` (`services/slip-service/src/main/java/com/samhanair/logis/slip/domain/SlipLine.java:85-105`)
- 판매전표 상세 DTO: `SlipLineResponse.unitPriceWithVat` (`services/slip-service/src/main/java/com/samhanair/logis/slip/web/dto/SlipLineResponse.java:21-45`, `:63-79`)
- 내부 회계 연동 DTO: `SlipLineSnapshot.unitPrice`가 `SlipLine.unitPriceWithVat` 의미다(`services/slip-service/src/main/java/com/samhanair/logis/slip/web/dto/SlipLineSnapshot.java:11-34`, `services/slip-service/src/main/java/com/samhanair/logis/slip/web/SlipInternalController.java:397-415`)

공유 `slip_db` 실측:

| 항목 | 결과 |
|---|---:|
| 활성 판매전표 라인 | 2,659 |
| `unit_price_with_vat` 값 있음 | 2,659 |
| `unit_price_domain='VAT_INCLUSIVE'` | 11 |
| `unit_price_domain IS NULL` | 2,648 |

값은 전부 존재한다. 다만 대부분은 V59 이전 데이터라 단가 권위 도메인이 미상이다. Issue #1001의 표시 원천으로는 `unit_price_with_vat`를 직접 쓸 수 있지만, 과거값의 생성 경위까지 모두 확정됐다고 말할 수는 없다.

`COMPLETED`, `DELIVERED`, `CONFIRMED`만 후보로 놓고 봐도 21문서 62라인 모두 부가세 포함 단가가 있다. 어느 상태를 “원장에 실리는 판매전표”로 볼지는 별도 미결이다.

### 5.2 배송주소

구조와 일반 판매전표 API는 있다.

- DB: `slips.delivery_address` (`services/slip-service/src/main/resources/db/migration/V20__slip_query_columns.sql:14-25`)
- 엔티티: 실제 인수 현장 주소로 정의 (`services/slip-service/src/main/java/com/samhanair/logis/slip/domain/Slip.java:524-530`)
- 생성 요청: `CreateSlipRequest.deliveryAddress` (`services/slip-service/src/main/java/com/samhanair/logis/slip/web/dto/CreateSlipRequest.java:39-47`, `:73-81`)
- 상세 응답: `SlipDetailResponse.deliveryAddress` (`services/slip-service/src/main/java/com/samhanair/logis/slip/web/dto/SlipDetailResponse.java:91-105`, `:226-244`)
- 데스크톱 직접 생성 폼: 배송주소 입력·요청 전송 (`clients/desktop/src/renderer/routes/SlipFormPage.tsx:1086-1095`, `:1374-1390`)

그러나 공유 DB에는 실제 값이 없다.

| 범위 | 문서 수 | 배송주소 값 있음 |
|---|---:|---:|
| 활성 판매전표 전체 | 2,299 | 0 |
| `COMPLETED` | 7 | 0 |
| `DELIVERED` | 10 | 0 |
| `CONFIRMED` | 4 | 0 |

`shipping_address` 값은 활성 판매전표 중 2건뿐이며, 정본 결정상 배송주소 대체값으로 사용하면 안 된다.

상류 배선도 불완전하다.

- 직접 생성 폼은 `deliveryAddress`를 전송하고 서비스가 `withProjectInfo`로 저장한다(`services/slip-service/src/main/java/com/samhanair/logis/slip/service/SlipService.java:317-327`).
- 반면 거래처 주문 발행 계약은 `shippingAddress`만 받고(`services/slip-service/src/main/java/com/samhanair/logis/slip/publish/PublishFromPartnerOrderRequest.java:27-41`), 발행 서비스도 `applyEcountSchema`의 `shippingAddress`에만 저장한다(`services/slip-service/src/main/java/com/samhanair/logis/slip/publish/SlipPublishService.java:217-238`).
- 견적 발행 계약도 `shippingAddress`와 `inspectionAddress`만 있고 `deliveryAddress`는 없다(`services/slip-service/src/main/java/com/samhanair/logis/slip/publish/PublishFromEstimateRequest.java:35-53`).
- 거래처 주문 상세 DTO의 `deliveryAddress` 필드는 현재 변환 시 항상 `null`이다(`services/partner-order-service/src/main/java/com/samhanair/logis/partnerorder/web/dto/PartnerOrderDetailResponse.java:72-97`). `partner_order_db.partner_orders`에도 해당 컬럼이 없음을 read-only 스키마 조회로 확인했다.

따라서 배송주소는 “원장 화면에서 가져오기만 하면 되는 값”이 아니다. 판매전표 직접 입력 또는 주문·견적 등 구조화된 원천에서 `slips.delivery_address`까지 보존하는 경로가 먼저 필요하다. 이 워크트리에는 backfill 가능한 시드파일이 없으므로 과거 문서 배송주소 복구 가능 여부는 **확인하지 못함**이다.

### 5.3 입금보고서

구조·API·분개 연결은 존재한다.

- 엔티티는 전표번호, 거래처, 금액, 거래일, 종류, 상태, 계정코드, 분개 링크를 가진다(`services/accounting-service/src/main/java/com/samhanair/logis/accounting/domain/CashReceipt.java:43-80`).
- 목록 API는 거래처·기간·상태·종류 필터를 제공한다(`services/accounting-service/src/main/java/com/samhanair/logis/accounting/web/CashReceiptController.java:89-113`).
- 응답은 `slipNo`, 거래처 표시값, 금액, 거래일, 종류, 상태, 연결 분개번호·역분개번호를 제공한다(`services/accounting-service/src/main/java/com/samhanair/logis/accounting/web/dto/CashReceiptResponse.java:11-28`).
- 확정 시 `JournalSourceType.CASH_RECEIPT`로 차변·대변 분개를 만들고 입금보고서 ID를 연결한다(`services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/CashReceiptService.java:296-310`).

공유 `accounting_db` 실측:

| 상태 | 건수 | 분개 연결 |
|---|---:|---:|
| `CONFIRMED` | 3 | 3 |
| `CANCELLED` | 21 | 18 |
| `DRAFT` | 1 | 0 |
| 합계 | 25 | 21 |

즉, 입금보고서 자체를 원장 수금내역으로 구성할 데이터는 있다. 현 원장 API가 `cash_receipts`를 읽지 않고 그 결과 분개만 읽는 것이 격차다.

다만 현재 `CashReceipt`는 `partner_id`와 `amount`가 각각 단일 필드다(`services/accounting-service/src/main/java/com/samhanair/logis/accounting/domain/CashReceipt.java:43-53`). 한 입금을 여러 거래처·계정 행으로 분할하는 child 구조는 없다. 이 기능은 별도 Issue #1002의 범위이며, #1001 응답 계약을 단일 금액 1행으로 고정하면 #1002 후 재작업이 생긴다.

### 5.4 판매전표와 별개인 매출전표 도메인

회계 서비스에는 `SalesAccountingSlip`이 있지만 이것은 판매전표와 다른 **매출전표**다(`services/accounting-service/src/main/java/com/samhanair/logis/accounting/domain/SalesAccountingSlip.java:19-23`). 판매전표를 원천으로 배분해 생성하며, 원천 판매전표가 `OUTBOUND`·`CONFIRMED`인지 검사한다(`services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/SalesAccountingSlipCreateAttemptService.java:114-139`).

공유 DB에는 활성 매출전표가 0건이고, soft-delete된 `POSTED` 1건과 라인·배분 각 1건만 있다. Issue #1001이 정한 원천은 판매전표이므로, 매출전표나 세금계산서로 바꾸어 구현해서는 안 된다.

### 6.1 충돌 또는 미결로 남겨야 하는 항목

다음은 기존 자료만으로 확정할 수 없어 임의로 정하면 안 된다.

1. **“출고된 판매전표”의 상태 경계**
   - 후보 상태로 `COMPLETED`, `DELIVERED`, `CONFIRMED`가 모두 존재한다.
   - 매출전표 생성 코드는 `CONFIRMED`만 허용하지만, #1001 정본 문구가 회계반영 완료를 뜻하는지는 명시하지 않았다.
   - 구현 전 개발책임자 결정이 필요하다.
2. **취소·수정된 입금보고서의 원장 표시 방식**
   - 기존 잔액 결정은 원분개 `REVERSED`와 역분개 `POSTED`를 함께 읽는다.
   - 문서형 원장에서 `CANCELLED` 문서를 한 행으로 남길지, 취소선·상태로 보일지, 순액 0으로만 반영할지는 정해져 있지 않다.
3. **#1002 선후관계**
   - 현재 입금보고서는 단일 거래처·단일 금액이다.
   - 분할 child 모델이 먼저 확정되지 않으면 #1001 수금내역 계약이 다시 바뀔 수 있다.
4. **과거 배송주소 보정 정책**
   - 공유 DB의 `delivery_address`는 전량 공란이고 시드파일도 이 워크트리에 없다.
   - `shipping_address`, 거래처 주소, 적요 중 어느 것도 정본 배송주소로 대체할 권한은 없다.

## 7. 슬라이스 제안

권장 분해는 5개다. 각 슬라이스는 기존 소비자를 깨지 않는 추가형 계약 또는 한 표면 완결로 독립 머지할 수 있게 잡았다.

### 슬라이스 1 — 판매전표 원장용 read 계약

**경계**

- slip-service에 기간+거래처 기준의 원장 전용 read projection을 추가한다.
- 응답은 전표번호, 일자, 거래처 비즈니스 식별자, 상태, `deliveryAddress`, 품목명/모델명/수량/`unitPriceWithVat`/품목 금액만 포함한다.
- UUID는 내부 호출에 필요하더라도 외부 원장 응답·화면 계약에 넣지 않는다.
- 현 `/internal/slips/outbound-lines`는 수량까지만 있고 주소·단가·상태가 없으므로 그대로 재사용할 수 없다(`services/slip-service/src/main/java/com/samhanair/logis/slip/web/dto/OutboundSlipLineResponse.java:13-30`, `services/slip-service/src/main/java/com/samhanair/logis/slip/web/SlipInternalController.java:307-326`).

**선행 결정**: 원장 포함 상태.

**독립 머지성**: 신규 read-only 내부 API와 테스트만 추가하며 기존 화면은 무변경.

### 슬라이스 2 — 배송주소 수집 경로 정합

**경계**

- 판매전표 직접 생성, 거래처 주문 발행, 견적 발행 등 생성 경로별로 구조화된 배송주소가 `slips.delivery_address`에 도달하는지 정합시킨다.
- 원천에 구조화된 값이 없는 경로는 빈 값 유지와 사용자 입력 요구를 명시한다.
- 적요 파싱·`shipping_address` 자동 대체는 하지 않는다.
- 과거 데이터 backfill은 출처가 증명되는 데이터만 별도 dry-run·검증 후 수행한다. 현재 워크트리에서는 원천 파일 부재로 backfill 범위를 확정할 수 없다.

**독립 머지성**: nullable 필드의 상류 배선 보강이며 기존 원장 소비자와 무관하게 머지 가능.

### 슬라이스 3 — 회계 서비스 2종 통합 원장 API

**경계**

- accounting-service가 슬라이스 1의 판매전표 projection과 자체 `CashReceipt`를 합쳐 날짜·전표번호 순의 typed union을 반환한다.
- 최상위 행 종류는 판매전표/입금보고서 두 가지로 제한한다.
- 판매전표 행은 품목 child 전체와 배송주소를 가진다.
- 입금보고서 행은 전표번호, 거래일, 상태, 수금 금액, 거래처, 향후 #1002 배분 child를 수용할 구조를 가진다.
- read enrichment 실패는 502 fail-closed로 처리한다.
- 권한은 `accounting.partner-ledger` `VIEW` 하나로 정렬한다.
- 기존 `/accounting/sales/aggregate`, `/accounting/journals/ledger-data`, `/accounting/ledgers`는 즉시 제거하지 않고 기존 소비자 호환을 유지한다.

**선행 조건**: 슬라이스 1, 취소·수정 표시 규칙, #1002 계약 방향.

**독립 머지성**: 신규 API+통합 테스트만 추가하고 데스크톱은 기존 API를 계속 사용한다.

### 슬라이스 4 — 데스크톱 조회 화면·CSV 전환

**경계**

- `/accounting/partner-ledger` 본문을 슬라이스 3 API로 전환한다.
- 판매전표/입금보고서 두 행 종류, 왼쪽 전표번호, 판매전표 품목 펼침, 배송주소, 수량, 부가세 포함 단가, 품목 금액을 표시한다.
- CSV도 화면과 같은 typed 구조로 맞춘다.
- 0 `—`, 음수 `-X` 빨강, 코드 prefix 금지 규약을 적용한다.
- 거래처코드 열에 사업자번호를 넣는 현 오류를 바로잡는다.

**선행 조건**: 슬라이스 3.

**독립 머지성**: 인쇄 라우트는 기존 상태로 남겨 본문 화면과 CSV만 한 PR에서 완결한다.

### 슬라이스 5 — 실제 인쇄·일괄 인쇄 전환

**경계**

- `PartnerLedgerView`의 `MOCK_DATA`를 제거하고 슬라이스 3 API를 사용한다.
- 본문 화면과 동일한 전표번호·두 문서종류·판매전표 품목·부가세 포함 단가·배송주소를 A4에 표시한다.
- 단건·일괄 인쇄가 동일 계약을 사용하도록 한다.
- UUID 미노출, 긴 주소·다품목 페이지 나눔, 0/음수 규약을 실제 렌더로 검증한다.

**선행 조건**: 슬라이스 3. 화면과 표현을 맞추려면 슬라이스 4 다음을 권장한다.

**독립 머지성**: 인쇄 표면만 교체한다.

### 권장 순서

```text
상태·취소 표시 결정
  → 슬라이스 1 판매전표 read 계약
  → 슬라이스 2 배송주소 수집 경로
  → #1002 분할 계약 확정 또는 호환 DTO 확정
  → 슬라이스 3 통합 원장 API
  → 슬라이스 4 조회 화면·CSV
  → 슬라이스 5 실제 인쇄
```

## 8. 구현 착수 전 결정 요청 목록
