# S10 — PartnerOrder 복원 row lock 재설계

## 결론

S9의 `@Lock(PESSIMISTIC_WRITE) + nativeQuery` 조합은 제거했다. Spring Data JPA가 네이티브 SQL에 `@Lock`을 붙여 주지 않으므로, 복원 대상 조회를 다음 PostgreSQL native SQL로 고정했다.

```sql
SELECT * FROM partner_orders WHERE id = :id FOR UPDATE NOWAIT
```

`partner_orders` 단일 테이블 조회이므로 PostgreSQL의 `FOR UPDATE` row lock 대상이 유효하다. `NOWAIT`는 이미 다른 복원 트랜잭션이 row를 점유한 경우 무한 대기하지 않고 즉시 락 획득 실패를 반환한다. 서비스는 이 실패를 기존 FE 계약과 같은 409 응답으로 변환한다.

## 트랜잭션·대기 판단

- `PartnerOrderRevisionService` 클래스의 `@Transactional`이 `restore()` 전체를 감싼다.
- native 조회 직후부터 주문 변경, `saveAndFlush`, RESTORE revision 캡처까지 같은 트랜잭션이다. 따라서 row lock은 복원 완료/rollback 때까지 유지된다.
- PostgreSQL 기본 `lock_timeout=0`은 무한 대기지만, 이번 경로는 `NOWAIT`를 사용하므로 기본값에 의존하지 않는다.
- 락 경합은 `PessimisticLockingFailureException`에서 업무 409로 변환한다. 락 대기 요청이 쌓여 connection pool을 마르게 하는 설계는 채택하지 않았다.
- 순차 호출은 첫 트랜잭션이 종료된 뒤 두 번째 트랜잭션이 시작하므로 락 경합이 아니다. 기존 `restoreStartedAt` 판별을 유지해 같은 target의 동시 요청만 409로 막고, 순차 복원은 허용한다.
- soft-delete 주문도 기존 native 조회로 로드하므로 `@SQLRestriction` 우회와 케이스7 동작을 보존한다.

### RED-A

동일 target에 대한 2개 restore 요청을 13회 반복했다. 매 반복에서 HTTP 결과는 `200 + 409`, RESTORE revision은 정확히 1건이었다. 409 사유는 기존 FE가 표시하는 동시 복원 메시지다.

### RED-B

동일 target에 대한 순차 restore 2회를 실행했다. 두 요청 모두 `200`, RESTORE revision은 2건이었다. 따라서 사용자가 실제로 두 번 누른 순차 복원은 허용된다.
