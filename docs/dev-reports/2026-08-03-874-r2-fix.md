## 1. 결함 확인과 레거시 원문

적대검증 보고서 `docs/dev-reports/2026-08-03-874-r1-sol-review.md` §2의 재현을 먼저 확인했다. `AR06A9170HNQ`는 product-service 응답에서 `ACCESSORY`지만, 레거시 토큰 분류는 `SUB_INDOOR`다. 기존 `RiUsageDecision`은 `ACCESSORY`를 main도 `PANEL/REMOTE/MATERIAL` 부속도 아닌 것으로 보고 `null`을 반환했다. 기존 단가 fallback이 `true`이면 실제 레거시의 미소비 `(0/1) -> false`가 `true`로 남았다.

레거시 분류 권위는 `tools/legacy-gas/일마감 프로그램/Code.js`의 토큰 함수다.

| 원문 | 의미 |
|---|---|
| `Code.js:191-196` | `AWR-`/`AR-`는 `REMOTE`, `AC`의 7번째 문자는 `N -> INDOOR`, `X -> OUTDOOR` |
| `Code.js:198-203` | `AR` + 하이픈 없는 모델의 12번째 문자 `N -> INDOOR`, `X -> OUTDOOR`, `Q -> SUB_INDOOR` |
| `Code.js:205-210` | `AF` 모델의 12번째 문자 `N -> INDOOR`, `X -> OUTDOOR` |
| `Code.js:211` | 위 조건에 해당하지 않으면 `MATERIAL` |
| `Code.js:707-708` | `SUB_INDOOR` 자신의 `riUsage.used === total`이 `확인` 입력 |

계열 sweep은 파일명이나 모델명 일부가 아니라 위 원문의 각 조건을 그대로 코드로 계산했다.

`[실데이터/로컬 read-only]` 활성 `bundle_component`의 distinct 모델을 sweep한 결과, 카탈로그와 레거시 분류 불일치는 다음과 같았다.

| 카탈로그 kind | 레거시 kind | 모델 수 |
|---|---|---:|
| `ACCESSORY` | `SUB_INDOOR` | 8 |
| `ACCESSORY` | `MATERIAL` | 2 |
| `INDOOR` | `MATERIAL` | 41 |
| `OUTDOOR` | `MATERIAL` | 55 |
| `PANEL` | `MATERIAL` | 16 |
| `REMOTE` | `MATERIAL` | 8 |

`[실데이터/로컬 read-only]` 그중 12번째 문자가 `Q`인 활성 구성품은 8개 모델 코드, 67개 active link이며 67개 link 모두 카탈로그 kind가 `ACCESSORY`다. `SUB_INDOOR` kind 자체는 활성 카탈로그에 0건이었다.

## 2. RED-first

실제 모델 코드를 사용한 fixture를 먼저 추가했다. fixture는 raw SQL로 죽은 컬럼을 채우지 않고, 실제 production `RiUsageDecision`이 받는 `Row(modelToken, kind, sourceKey)`와 matcher가 생성하는 `Usage(total, used)`를 사용한다.

추가한 실패 조건은 다음이다.

- `AR06A9170HNQ`의 카탈로그 kind `ACCESSORY`가 레거시 `SUB_INDOOR`로 보정되어야 한다.
- 그 row의 usage `(total=1, used=0)`은 `확인=false`가 되어야 한다.
- 명시적인 카탈로그 `PANEL`은 Q 토큰이라는 이유로 재분류하지 않아야 한다.
- `QA797-PART-01`처럼 카탈로그 `ACCESSORY`이고 레거시 main이 아닌 모델도 `ACCESSORY`로 남아야 한다.

## 3. 구현과 권위 결정

신규 `LegacyModelKindClassifier`를 추가했다.

- `Code.js:191-211`의 순서와 문자 위치를 그대로 구현했다.
- 카탈로그 kind가 `PANEL/REMOTE/MATERIAL/INDOOR/OUTDOOR` 등 구체 값이면 카탈로그를 권위로 유지한다.
- 카탈로그 kind가 generic `ACCESSORY`이고 레거시 토큰이 `INDOOR/OUTDOOR/SUB_INDOOR`이면 레거시를 권위로 사용한다. 이 좁은 예외가 카탈로그와 레거시가 어긋난 Q형 8종을 `riUsage` main 판정에 도달시킨다.
- generic `ACCESSORY`를 레거시 `MATERIAL`로 다시 분류하지 않는다. 따라서 sweep에서 확인한 `QA797-PART-01/02` 2종은 `ACCESSORY`로 유지된다.
- `MonthEndCloseService`의 세트 후보 component kind, pool line kind, `RiUsageDecision` kind map에 동일한 보정 함수를 적용했다. 판정 입력과 세트 소비 입력의 kind가 갈라지지 않는다.

이 선택은 “카탈로그가 구체적으로 분류한 행은 다시 뜯지 않는다”와 “레거시가 main으로 분류한 generic ACCESSORY는 `riUsage`에 도달해야 한다”를 동시에 만족시킨다.

## 5. 불변식 측정

### 5.1 불변식 1 — 레거시 분류 도달과 반대급부

`[DEV-SEED/단위 fixture]` `AR06A9170HNQ`, catalog `ACCESSORY`, usage `(0/1)` fixture에서 기존 최종값은 적대검증 원문대로 `true`였고, 보정 후 `SUB_INDOOR` 자기 `riUsage` 판정은 `false`다. 이 fixture의 fix 전후 `확인` 변경은 **1행: true -> false**이며, 수량 미소비이므로 바뀌어야 한다.

`[DEV-SEED/단위 fixture]` `PANEL` catalog kind와 `QA797-PART-01` generic accessory/material mismatch는 각각 catalog kind와 `ACCESSORY`를 유지한다. 이 반대급부 fixture의 `확인` 값 변경은 **0행**이다.

`[실데이터/로컬 read-only]` 활성 Q형은 8개 모델/67 links지만 현재 `accounting_db`의 모델 보유 원천은 tax invoice 0행/22행, sales slip 0행/0행이다. 따라서 영속 일마감 응답에서 fix 전후 `확인` 변경은 **0행 관측**이다. 0행은 규칙 정확성 증거가 아니라 현재 모델 보유 전표 데이터 부재를 뜻한다.

### 5.2 불변식 2 — 분류 권위와 비재분류

`[실데이터/로컬 read-only]` 현재 활성 sweep에서 `ACCESSORY -> SUB_INDOOR`는 8개, `ACCESSORY -> MATERIAL`은 2개였다. 구현은 전자의 8개만 레거시 main으로 보정하고, 후자의 2개는 `ACCESSORY`로 남긴다. 구체 catalog kind를 레거시 결과로 덮는 경로는 없다.

`[DEV-SEED/단위 fixture]` Q형 미소비 row는 보정 kind `SUB_INDOOR`로 `false`에 도달한다. `PANEL` 명시 kind fixture는 `PANEL`로 남고, `QA797-PART-01` fixture는 `ACCESSORY`로 남는다.

### 5.3 불변식 3 — 앞선 세 갈래

`[DEV-SEED/단위 fixture]` 기존 `RiUsageDecisionTest`의 세 갈래를 유지했다.

- 부속 자기 소비 완료: `true`.
- 같은 scope에 미완료 main 존재: `false`.
- main이 모두 완료됐지만 부속이 미완료: `null`, 기존 단가 판정 유지.

이번 수정은 kind 해석만 보정하며 `RiUsageDecision`의 `null` 반환과 `MonthEndCloseService`의 non-null 조건부 `withVerified`를 변경하지 않았다.

### 5.4 불변식 4 — #1058 무회귀

`[실데이터/로컬 read-only]` fresh query 결과는 전역DC active config 210곳, 옵션 6종 모두 null인 거래처 164곳이다. 기존 #1058 기준선은 다음을 유지한다.

- 확정 과차감: 0행 / 0원.
- 옵션 미보유 거래처: 164곳 / 0원 변화.
- 스냅샷 기준선: 0.

이번 수정은 `parentSetNames`, 전역DC 계산, 옵션 정액 선택 규칙을 변경하지 않고 kind 정규화만 추가했다. 타깃 `DailyClosingDetailServiceTest`도 GREEN이다. 전체 accounting 스위트와 별도 스냅샷 전수는 실행하지 않았으므로 위 수치를 이번 라운드의 신규 전수 통과로 과장하지 않는다.
