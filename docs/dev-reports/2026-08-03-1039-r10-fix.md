## 정상·장애·복구 결과표

| 상황 | 발행 | code 상태 | 복구 경로 |
|---|---|---|---|
| 정상 inventory 응답 | 201 경로 유지 | `WH-R9-NORMAL`이 PostgreSQL에 저장 | 저장 완료 후 pending 해제 |
| inventory 장애 | 201 경로 유지 | code는 null, pending 유지 | 예외를 발행에 전파하지 않음 |
| 장애 후 inventory 복구 | 이미 발행된 전표 유지 | `WH-R10-RECOVERED` 저장 | scheduler가 pending 신규 행만 재처리 |

비동기 작업은 `afterCommit` 이후에만 executor로 제출되므로 rollback 전표에는 실행되지
않는다. V102의 기존 행 기본값 FALSE로 인해 기존 2,303행 provenance는 변경하지 않는다.

재시도, (3) afterCommit 작업의 HTTP 응답 경로 분리다.

## 수정 1 및 확인 3 — 영속 pending 재시도 경로 GREEN

신규 전표만 `source_warehouse_code_pending=true`로 표시하고, V102에서 기존 행의
기본값은 FALSE로 유지했다. `afterCommit` 작업은 `applicationTaskExecutor`로 넘기며,
저장은 `REQUIRES_NEW`로 독립 commit한다. scheduler는 pending 행만 조회한다.

복구 IT에서 첫 timeout은 code를 비워 둔 채 pending을 유지하고, 두 번째 정상 응답
`WH-R10-RECOVERED`를 별도 transaction으로 저장했다.

```text
실행: .\gradlew.bat :services:slip-service:test --tests "com.samhanair.logis.slip.it.WarehouseCodeSnapshotServiceIT.retryPending_inventoryRecovery_persistsSourceWarehouseCode" --no-daemon

> Task :services:slip-service:test
BUILD SUCCESSFUL in 52s
```
