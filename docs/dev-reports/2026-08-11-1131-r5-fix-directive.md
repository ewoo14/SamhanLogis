# PR #1131 R5 fix directive — 기존 0-head 전표 영구 차단 · 동일 세트 다중 인스턴스 오거부

## 판정

**BLOCKING. 실 사용자 경로로 재현 가능한 결함이 2건 있다.**

R4의 두 원 결함 중 “기존 수량 0 행의 조용한 삭제”는 닫혔고, canonical head가 하나뿐인 기존
그룹에서 head만 삭제하는 경로도 거부된다. 그러나 새 저장 직전 검증이 현재 DB 상태와 세트
인스턴스 표현을 고려하지 않아 정상 저장을 새로 막는다.

1. 실 DB에 이미 존재하는 0-head OUTBOUND DRAFT 16전표는 수량·단가를 양수로만 고쳐도 저장할
   수 없다.
2. 같은 `parentSetModel`의 정상 세트 인스턴스가 2개인 전표는 head가 2개라는 이유로 저장할 수
   없다. 새 검증이 인스턴스가 아니라 모델 문자열 전체를 한 그룹으로 합치기 때문이다.

## 도달 결함 1 — 기존 0-head 전표의 모든 정상 수정 차단

### 실 DB 분모

활성 전표·활성 라인만 집계했다.

```text
OUTBOUND BUNDLE 계보 159그룹 / 346라인
head=0             16그룹 / 19라인 / 16전표 — 전부 DRAFT
head=1            142그룹
head>1              1그룹 / 8라인 / 1전표
```

0-head 16그룹의 구성은 `QA797-SET-01` 14그룹과 일반 모델 세트 2그룹이다.

```text
2026/08/07-17  AF17DX738WSS       2라인 / head 0
2026/08/07-7   AC072CS6PBH1SY    3라인 / head 0
```

이 행들이 실제 업무 전표라는 뜻은 아니다. 그러나 활성 DRAFT로 실 DB와 판매전표 목록에 존재하고,
현재 화면에서 직접 수정 가능한 서버 데이터라는 도달성은 확정이다.

### 재현

1. 위 0-head DRAFT를 연다.
2. `직접 수정`에서 기존 행 수량을 양수 `1→3`으로 바꾼다. 삭제 버튼은 누르지 않는다.
3. 저장한다.
4. 배포 후 워킹트리 BE는 `restoreSlipLines`로 원래 0-head 계보를 복원한 직후 저장 전 검증에서
   거부한다.

현재 diff를 컴파일한 일회성 probe 원문:

```text
R5-DB-ZERO-HEAD-TARGET|parent=AF17DX738WSS|quantity=3|heads=0
BusinessException: 세트 head 구성품은 삭제할 수 없습니다
repository 저장 도달 전 거부
```

Playwright 실로그인·실 DB 복사본에서 수량 `3`, 저장 버튼 enabled까지 도달했다. 낡은 BE에는 새
검증이 없으므로 실제 거부 PUT은 **배포 후 검증**으로 남긴다.

- `docs/qa/1131-r5-fix/screenshots/02-live-zero-head-positive-edit-before-save.png`

## 도달 결함 2 — 동일 세트 2인스턴스 정상 저장 차단

실 DB 전표 `2026/08/07-20`에는 `AC060CS6PBH1SY`가 4구성품씩 두 번 저장돼 있다.

```text
AC060CN6PBH1[H], AC060CXAPBH1[C], PC6NUNK1NW[C], AR-EH05[C],
AC060CN6PBH1[H], AC060CXAPBH1[C], PC6NUNK1NW[C], AR-EH05[C]
총 8라인 / head 2
```

이는 같은 세트 모델 2개 인스턴스의 정상 표현이다. 그러나
`requireSingleHeadPerRetainedBundleGroup`는 `parentSetModel`만 key로 사용해 두 인스턴스를 하나로
합친 뒤 `headCount != 1`로 거부한다.

### 재현

1. 동일 세트 2인스턴스 DRAFT를 연다.
2. 첫 행 수량을 양수 `1→2`로 바꾼다. 계보·행 수·head는 건드리지 않는다.
3. 저장한다.
4. 배포 후 워킹트리 BE는 head 2개를 head 삭제와 같은 문구로 거부한다.

현재 diff probe 원문:

```text
R5-TWO-INSTANCES|parent=AC060CS6PBH1SY|lines=8|heads=2|userEdit=positive-quantity
BusinessException: 세트 head 구성품은 삭제할 수 없습니다
```

Playwright 실로그인·실 DB 복사본에서 12개 구성품 행, 첫 수량 `2`, 저장 버튼 enabled까지 도달했다.

- `docs/qa/1131-r5-fix/screenshots/03-live-two-set-instances-positive-edit-before-save.png`

## 이번 거부 추가 각도

### 수량 0

**신규 결함 없음.** 화면은 `0`과 빈 값을 편집 중간 상태로 입력할 수 있지만, 행 삭제는 별도 `×`
버튼으로 제공된다. 실로그인 Chromium에서 기존 `lineId`가 payload에 유지된 채 `quantity=0`이
전송됐고, 낡은 배포 BE의 기존 공통 가드가 다음처럼 명시 거부했다.

```text
R5-QTY-ZERO|HTTP=422|payloadQuantity=0|lineIdPreserved=true
BE 원문: 수량은 1 이상이어야 합니다.
화면: 매출 라인 입력값이 올바르지 않습니다. 수량과 단가를 확인해 주세요.
```

- `docs/qa/1131-r5-fix/screenshots/01-live-quantity-zero-422.png`

화면 상단의 별도 `업데이트 실패` 배너는 선재 앱 업데이트 조회 문구이며 이 422의 증거가 아니다.

### head 조합

- 구성품 1개 세트/head 1개: 통과.
- head를 남기고 자식 전부 삭제: 통과.
- 세트 전체 삭제: 결과에 그룹이 없어 통과.
- 비-head만 삭제: 통과.
- 기존 head 0개: **결함 1로 차단.**
- 같은 모델의 정상 다중 인스턴스/head N개: **결함 2로 차단.**

## 불변식

1. 기존 활성 0-head 데이터가 존재하는 상태에서 새 검증을 켜 정상 편집을 영구 차단하면 안 된다.
   배포 전 backfill/격리 또는 런타임 복구 정책이 먼저 적용돼야 한다.
2. head 정확히 1개 불변식은 `parentSetModel` 전체가 아니라 **세트 인스턴스별**이어야 한다.
3. 같은 모델의 N개 정상 인스턴스는 N개의 canonical head를 보존한 채 수량·단가 편집과 비-head
   부분삭제가 가능해야 한다.
4. 한 인스턴스의 head만 삭제하고 그 인스턴스 자식을 남기는 저장은 계속 거부해야 한다.
5. 한 인스턴스 전체 삭제와 문서의 모든 세트 전체 삭제는 계속 허용해야 한다.
6. 기존 `lineId` 수량 0은 payload에서 누락하지 않고 명시 오류로 거부해야 한다.
7. 신규 익명 BUNDLE의 부모·membership·중복·canonical head 검증과 1행 head 정규화는 약화하면
   안 된다.

## 양방향 RED

### RED-A-1 — 실 DB 0-head 정상 편집

`AF17DX738WSS`의 기존 2라인이 모두 `setHead=false`인 DRAFT를 준비하고, 두 라인을 그대로 유지한
채 첫 수량만 `1→3`으로 보낸다.

기대:

```text
배포 전 데이터 복구가 끝난 상태에서 2xx
또는 동일 요청에서 결정된 canonical head를 안전하게 복구한 뒤 2xx
사용자 수량 3 보존
```

현재:

```text
INVALID_INPUT
세트 head 구성품은 삭제할 수 없습니다
DB write 0회
```

### RED-B-1 — 0-head 수정의 구체 반대 표적

1. 정상 H/C 그룹에서 H만 생략하고 C를 남긴다 → `INVALID_INPUT`, DB write 0회.
2. 같은 H/C를 전부 삭제하고 평면 SINGLE만 남긴다 → 2xx.
3. 정상 H/C를 유지하고 수량·단가만 바꾼다 → 2xx, head 1개, 사용자값 보존.

### RED-A-2 — 동일 모델 2인스턴스 정상 편집

위 `AC060CS6PBH1SY` 4행 인스턴스를 2개 준비한다. 두 head와 8행을 모두 유지하고 첫 head 수량만
`1→2`로 바꾼다.

기대:

```text
2xx
8라인 / 세트 인스턴스 2개 / head 2개 보존
```

현재:

```text
INVALID_INPUT
세트 head 구성품은 삭제할 수 없습니다
```

### RED-B-2 — 다중 인스턴스의 구체 반대 표적

1. 두 인스턴스 중 첫 인스턴스 head만 삭제하고 그 자식 3행은 남긴다 → 거부.
2. 첫 인스턴스 4행 전체를 삭제하고 둘째 인스턴스 4행은 유지한다 → 2xx, head 1개.
3. 두 인스턴스 8행 전체를 삭제하고 평면 SINGLE만 유지한다 → 2xx.
4. 신규 익명 행에 membership 밖 SINGLE을 붙인다 → `INVALID_INPUT`, DB write 0회.

## 수정 범위

1. 활성 0-head 16그룹을 배포 전에 명시적으로 처리하고, 새 guard 활성화 전 read-only preflight가
   `zero_head_groups=0`을 확인해야 한다. QA 산물 정리와 일반 모델 2그룹 backfill을 구분한다.
2. 저장 검증의 grouping key에 안정적인 세트 인스턴스 식별자를 둔다. 현재 스키마에는 instance key가
   없으므로 `parentSetModel`만으로 “인스턴스별 정확히 1 head”를 증명할 수 없다.
3. 단순히 조건을 `headCount >= 1`로 약화하는 것만으로 닫지 않는다. 동일 모델 2인스턴스 중 하나의
   head만 삭제해도 다른 head가 전체 그룹을 통과시켜 원 결함을 다시 연다.
4. 기존 R4 FE projection과 신규 익명 BUNDLE membership 검증은 유지한다.
