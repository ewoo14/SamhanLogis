# PR #1131 · SOL R14 수정 보고서

## 판정

R13 HIGH 결함을 수정했다. legacy BUNDLE 복원은 더 이상 행의 연속성을 인스턴스 경계로 사용하지 않는다. Slip과 Estimate가 같은 `BundleSetInstanceKeyPolicy`를 호출하며, 복원 전에 정책 결과를 계산한다.

실제 DB에서는 signature로 확정할 수 없는 legacy 다중 인스턴스가 5건 확인됐다. 따라서 불확정 조합을 `INVALID_INPUT`으로 거부하지 않았다. 잘못된 키를 만들지 않고 keyless 상태로 복원·정상 왕복 편집을 허용하며, 공통 정책에서 `WARN` 로그를 남긴다.

## 1. 발화 조건 실측 — read-only

대상은 로컬 Docker의 공유 개발 PostgreSQL `samhan-postgres`, DB `slip_db`였다. 실행한 것은 `slip_revisions`·`estimate_revisions`의 JSONB를 읽는 `SELECT`뿐이며, 공유 DB write는 하지 않았다.

### Slip revision

| 항목 | 건수 |
|---|---:|
| legacy keyless 다중-head revision | 5 |
| parent 그룹 | 5 |
| signature로 확정 | 0 |
| 증명 불가 | 5 |
| duplicate head signature 그룹 | 5 |
| unmatched child signature 그룹 | 0 |

확인된 업무 식별자는 다음 5개 revision이다.

```text
2026/08/07-20#1 / AC060CS6PBH1SY
2026/08/11-3#1  / AC060CS6PBH1SY
2026/08/11-5#1  / AC060CS6PBH1SY
2026/08/11-7#1  / AC060CS6PBH1SY
2026/08/11-9#1  / AC060CS6PBH1SY
```

### Estimate revision

```text
legacy keyless 다중-head revision = 0
signature 확정 = 0
증명 불가 = 0
```

Estimate에서 0건이라는 결과는 “결함 없음”이 아니라 현재 공유 DB 데이터에서 발화 조건을 관측하지 못했다는 뜻으로 기록한다.

## 2. signature 구성과 처리

parent별 signature는 `instanceKey`를 제외한 다음 5개 값으로 구성한다.

```text
(
  remoteOption,
  remoteExcluded,
  panelOption,
  panelShape360,
  materialIncluded
)
```

문자열은 blank를 null로 보고 trim하며, Boolean은 값 그대로 비교한다. `parentSetModel`은 signature가 아니라 그룹 축이고, 기존 `instanceKey`는 signature에 넣지 않는다.

- keyless head가 2개 이상이고 각 head signature가 유일하며 모든 keyless 행의 signature가 정확히 한 head signature와 일치하면, signature별 UUID key를 생성한다. 행 위치·정렬·연속성은 사용하지 않는다.
- 같은 signature의 head가 둘 이상이거나 child signature가 어느 head와도 맞지 않으면, 해당 parent의 keyless 옵션을 그대로 보존한다. 복원을 성공시키고 `BundleSetInstanceKeyPolicy`의 경고 로그로 관측한다.
- 이미 keyed인 행, 단일 keyless 인스턴스, head 없는 legacy child는 기존 값을 보존한다.
- ambiguous legacy를 후속 direct edit할 때도 `BundleLineageResolver`가 새 임의 key를 만들거나 head 수를 행 순서로 판정하지 않는다. 정상 왕복 편집은 keyless로 저장된다.

이 선택은 실 DB의 증명 불가 5건을 차단하지 않으면서, child를 다른 head의 key에 잘못 붙이는 데이터 변형도 피한다.

## 4. 조합표

| 조합 | 처리 | 테스트 |
|---|---|---|
| 연속 배치 | unique signature면 매칭, duplicate면 keyless 보존 | `BundleSetInstanceKeyPolicyTest`, `SlipRevisionRestoreIT` |
| 교차 배치 | 행 위치와 무관하게 signature 매칭 | `BundleSetInstanceKeyPolicyTest`, Slip/Estimate restore |
| head가 뒤에 옴 | child 선행이어도 signature 매칭 | `matchesHeadAfterChildrenWithoutUsingRowOrder` |
| 인스턴스 3개 이상 교차 | 각 signature에 별도 key, 구성품 수 달라도 매칭 | `matchesThreeInterleavedInstancesWithDifferentChildCounts` |
| child만 있고 head 없음 | key를 발명하지 않고 keyless 보존 | `preservesHeadlessChildrenWithoutInventingInstanceKeys` |
| 같은 모델·같은 옵션 2개 | duplicate signature로 판단, 복원 성공·keyless 보존 | duplicate policy + Slip/Estimate restore |
| signature 중복 | 잘못된 key 생성 없이 WARN, 복원 계속 | `preservesAmbiguousDuplicateSignaturesAsKeyless` |
| child signature unmatched | 전체 keyless 보존, 복원 계속 | `preservesAllKeylessRowsWhenChildSignatureIsUnmatched` |
| keyed + keyless 혼합 | 기존 key byte-for-byte 보존, keyless만 독립 매칭 | `preservesKeyedRowsAlongsideSignatureMaterializedKeylessRows` |
| 서로 다른 parent 교차 | parent별로 독립 매칭 | `matchesInterleavedParentsIndependently` |
| Slip restore | 공통 정책 호출 및 복원 후 direct edit 200 | `SlipRestoreTest`, `SlipRevisionRestoreIT` |
| Estimate restore | 공통 정책 호출 및 key/계보 보존 | `EstimateRestoreTest` |

## 5. RED-B 보존 확인

- 연속/ambiguous legacy 복원 후 후속 수량 direct PUT: HTTP 200.
- 복원 자체: duplicate/unmatched를 포함해 snapshot을 통째로 차단하지 않음.
- 정책 정의: `BundleSetInstanceKeyPolicy` 한 곳. Slip과 Estimate가 모두 `materializeLegacyMultiInstanceKeys`를 호출.
- `PartnerProductPriceMemoryIT`: 파일 수정 없음, `30 tests / 0 failures / 0 errors`.
- R10 생성 경로: 전체 테스트 통과. 정상 견적 화면의 keyless 다중 인스턴스 재생성 계약을 변경하지 않음.
- V119 대상 계약: 8행, head 2, 제품 4종, 공급가 4,729,797원, VAT 472,980원 관련 전체 IT 통과.
- 수량 0: 422 계약 통과.
- 비-head 삭제 및 인스턴스 전체삭제: 기존 전체 IT 계약 통과.
- 기존 QA 증거: `git diff --name-status -- docs/qa` 출력 없음. 삭제·이동·덮어쓰기 없음.
