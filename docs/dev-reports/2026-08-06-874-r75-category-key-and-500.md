# R75 · #874 categoryKey 파생·전역DC 단건 500 fix

## 결론

두 결함을 함께 수정했다.

1. `ProductSummaryResponse`가 `product_category`만 읽어 `categoryKey=null`을 반환하던 경로에 `category_id`가 가리키는 물리 카테고리 fallback을 추가했다.
2. 전역DC 단건 조회는 거래처를 `JOIN FETCH`로 함께 읽도록 고쳐, 서비스 트랜잭션 종료 후 외부 DTO 변환에서 지연 로딩 예외가 500으로 전환되는 경로를 제거했다.

## RED-first 원문

### RED-A — categoryKey 파생 단절

추가한 `ProductSummaryResponseTest`를 수정 전 실행한 결과:

```text
ProductSummaryResponseTest > from_derivesHomeMultiCategoryKeyFromPhysicalCategoryWhenProductCategoryIsNull() FAILED
org.opentest4j.AssertionFailedError at ProductSummaryResponseTest.java:38
expected: "homemulti"
but was: null
```

원인은 `ProductSummaryResponse.from()`이 `p.getProductCategory()`만 `categoryKey()`에 전달했기 때문이다. Hvac native INSERT 경로는 `category_id`는 기록하지만 `product_category`는 기록하지 않는다.

### RED-B — 단건 조회의 세션 안전 경로 부재

추가한 서비스 회귀 테스트를 수정 전 실행한 결과:

```text
DcConfigServiceGetByPartnerCodeTest.java:34: error: cannot find symbol
  method findWithPartnerByPartnerCode(String)
```

단건 API의 응답 DTO는 `DcConfig.partner`의 `partnerCode/companyName`을 읽는다. 서비스 조회가 끝난 뒤 DTO 변환이 일어나는 경계를 명시적으로 보장하는 fetch-query가 없었다.

## 라이브 재현 원문 (읽기/API 호출만)

개발 게이트웨이에 `dev_master`로 로그인한 뒤 DB 쓰기 없는 GET을 수행했다.

```text
GET /api/products?q=AR09TXEAAWKNEU-04&size=20
HTTP 200
categoryId=00000000-0000-0000-0000-000000001004
categoryKey=null

GET /api/v1/partner-dc-configs/4348703365
HTTP 500
{"success":false,"code":"INTERNAL_ERROR","message":"서버 내부 오류가 발생했습니다.","data":null,...}
```

HTTP 응답은 내부 stack trace를 노출하지 않아 런타임 stack 원문 자체는 응답에서 확인할 수 없다. 코드·세션 경계 분석상 500 원인은 단건 조회 결과의 `partner` 지연 로딩을 외부 DTO 변환 시점에 의존한 것이다. `InternalDcConfigControllerSessionBoundaryIT`도 같은 위험을 “controller 반환 뒤 DTO 변환 시점의 LazyInitializationException”으로 명시하고 있다.

## 변경 내용

### ① categoryKey 파생

- 명시적인 `product_category`가 있으면 기존 시트 분류를 우선한다.
- `product_category=null`이면 `Product.category.code`를 파생 소스로 사용한다.
  - `INDOOR_WALL` → `homemulti`
  - `OUTDOOR`, `INDOOR_CEILING` → `commercialMulti`
  - 그 외 → `null`
- 따라서 대상 품목은 화면에서 `HOMEMULTI`로 판정되고, `homeMultiDc="48%"`를 선택한다.

### ② 전역DC 단건 조회

- `DcConfigRepository.findWithPartnerByPartnerCode()`를 추가했다.
- `JOIN FETCH dc.partner`로 단건 응답에 필요한 거래처를 조회 단계에서 확정한다.
- `DcConfigService.getByPartnerCode()`가 새 fetch 경로를 사용한다.
- DB 저장, Docker 재빌드/재배포/중지는 수행하지 않았다.

## 불변식 영향

| 불변식 | 코드/테스트 판정 |
|---|---|
| 홈멀티 전역DC 48% → 561,600 | `categoryKey` 회귀 테스트 + 기존 `slipDiscount` 테스트 통과; `1,080,000 × (1 - 0.48)` 계산 경로 보존 |
| 고정DC 970,200 유지 | 기존 `slipDiscount`/`SlipFormPage` 67개 테스트 통과 |
| 전역DC 없는 거래처 정가 | 기존 `slipDiscount` 테스트 통과 |
| 저장 201·discountInfo·UUID 없음 | R72 단일 권위 저장 경로와 이번 변경 범위 불변; 관련 화면 테스트 통과 |
| 조회 실패 시 저장 가능·사용자 인지 | FE의 기존 `null → calculateSlipDiscount(..., DC 없음)` 및 `discountInfo` 경로 불변 |

실제 561,600 화면/저장 및 201은 PM의 R75 배포 후 QA에서 재측정해야 한다. 현재 워크트리에서는 Docker 재배포가 금지되어 있어 라이브 서버는 수정 전 이미지 상태다.
