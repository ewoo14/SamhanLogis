## 1. 결론

P1 원인은 확인됐고 fix1에서 수정했다. 기존 기본 런처는 `base + local-all`을
서비스 필터 없이 호출했으므로 overlay의 logging-service가 자동 포함됐다.

수정은 기존 서비스 대상 지정 방식을 유지하면서 `logging-service`에만 Compose
`logging` profile을 부여하는 최소 변경이다.

- 기본 `launch-local-stack.ps1/.sh`: 기존 무필터 `base + local-all up -d` 호출 유지
- 기본 합성: logging-service 제외
- 명시적 `... up -d --build --no-deps logging-service`: logging-service만 선택 기동
- 기존 서비스 집합: 기본 합성에서 탈락 0개
- prod compose: 변경 없음

## 3. RED-A 실측 원문

### 3-1. 기본 기동 — logging-service 없음, 기존 서비스 집합 유지

Docker Compose는 v5.3.1이다. 이 버전에서 아래 `--dry-run` 호출이 실제
reconcile을 수행해 Prometheus stale mount 오류까지 발생했으므로, 공유 스택을
다시 건드리는 기본 전체 `up`은 실행하지 않았다.

```text
docker compose --dry-run -f infrastructure/docker-compose.yml -f infrastructure/docker-compose.local-all.yml up -d --no-build
→ Container samhan-logging-service Creating
→ Container samhan-logging-service Created
→ dependency failed to start: container samhan-prometheus exited (127)
```

변경 후 기본 RED-A는 read-only `config --services`와 계약 테스트로 증명했다.
기본 집합은 24개, profile 활성 집합은 25개, 차이는 logging-service 하나이며
누락된 기존 서비스는 0개다.

### 3-2. opt-in 기동 및 API

## 6. 이전 보고서 증거 정정

`docs/dev-reports/2026-08-12-1161-s1-local-logging-service.md`의 줄 끝 공백을
제거하고 다음 내용을 정정했다.

- overlay만 명시하면 opt-in이라는 결론 → 기본 런처가 overlay를 항상 소비한다는 사실 반영
- `git diff --check PASS` → 당시 committed range의 실제 결과 `exit 2`, trailing whitespace 2건
- 기존 activity 문서 1건 → 빈 배열 증거가 아님을 명시

현재 워크트리의 `git diff --check`는 exit 0이다. 아직 commit하지 않았으므로
역사적 `72cab52e..7d5571ed6` committed range 자체는 이전 blob을 가리킨다. PM이
이 변경을 commit한 뒤 새 HEAD 범위로 최종 재실행해야 한다.
