## 0. 결론

1. **별도 채팅 도메인을 만들면 안 된다.** Issue #894의 2026-08-06 개발책임자 결정은 “1:1 쪽지와 채팅 통합 — 기존 `messages` 확장”이다. 기존 `/messenger`, 수신자 검색, 복수 수신, 수신함, 읽음 처리, `MESSENGER` 알림 상관관계가 승계 대상이다.
2. **실시간은 제3안이다.** `createRealtimeClient`와 `RealtimeBroker`라는 SSE 전송 공통층은 재사용할 수 있으나, `createCoeditProvider`의 Yjs 문서 동시편집 계약 위에 채팅을 얹을 수는 없다. 기존 공통 전송층을 재사용하면서 **방 ID 단위의 별도 채팅 event/endpoint 계약**을 추가해야 한다.
3. 기존 `ChatRoomsPage`는 채팅방이 아니다. 거래처 코드와 외부 단톡방 이름의 매핑을 관리하며 현재 30초 polling을 쓴다.
4. 참여자 선례는 #895 일정에만 구현돼 있다. 작성자를 실제 참여자 행에 자동 포함하고 제거를 막는다. **채팅방 작성자에게 같은 규칙을 적용하라는 명시 계약은 아직 찾지 못했으므로 질문 사항**이다.
5. 현재 노출 표면은 데스크톱 `/messenger`와 알림 벨/내역이다. 그러나 Issue #894의 명시 계약은 데스크톱·모바일 모두 전역 삼한이 런처 + 방 목록 팝오버 + 독립 채팅 라우트/창이다. 모바일에는 현재 메신저/채팅 메뉴·화면이 없다.

## ② 실시간 계약

### 구조

1. `createRealtimeClient`
   - 도메인이 `endpointPath(entityId)`만 공급하는 generic SSE client다 (`clients/desktop/src/renderer/realtime/createRealtimeClient.ts:30-43`, `55-63`).
   - 인증 헤더와 `Accept: text/event-stream`을 붙여 native `fetch`로 연결한다 (`createRealtimeClient.ts:104-124`).
   - SSE frame의 `event:`/`data:`를 직접 파싱하고 JSON payload를 callback으로 전달한다 (`createRealtimeClient.ts:134-183`).
   - heartbeat 무응답 60초 감지, 5초→60초 지수 backoff, abort cleanup을 제공한다 (`createRealtimeClient.ts:46-52`, `87-94`, `188-208`).
2. `createCoeditProvider`
   - Yjs `Doc/Text`와 awareness를 만들고 (`clients/desktop/src/renderer/realtime/createCoeditProvider.ts:219-230`), update는 150ms debounce POST, awareness는 120ms debounce POST한다 (`createCoeditProvider.ts:244-301`).
   - 기본 HTTP 계약은 `GET /collab/coedit`, `POST /collab/coedit/update`, `POST /collab/coedit/awareness`다 (`clients/desktop/src/renderer/realtime/coeditApi.ts:22-52`).
   - 기본 SSE는 `${basePath}/collab/stream`이며 (`createCoeditProvider.ts:145-150`), `coedit:update`/`coedit:awareness`만 해석하고 5초 snapshot 재동기화를 병행한다 (`createCoeditProvider.ts:307-361`).
3. 서버 broker/SSE endpoint
   - 공통 `RealtimeBroker`는 **UUID entityId 단위** subscribe/publish 모델이며 in-memory 또는 Redis cross-node 전파를 지원한다 (`shared/realtime-abstraction/src/main/java/com/samhanair/logis/shared/realtime/broker/RealtimeBroker.java:6-17`, `23-60`).
   - 기본 broker는 entityId별 `SseEmitter` 목록, `connected` event, named event publish, 30초 heartbeat를 제공한다 (`InMemoryRealtimeBroker.java:42-50`, `82-104`, `107-173`).
   - 실제 endpoint 예시는 결재의 `GET /admin/groupware/approvals/{approvalId}/collab/stream`; `groupware.approvals:VIEW` 후 같은 approvalId broker를 구독한다 (`GroupwareApprovalCollabController.java:231-237`).
   - notification-service에는 event 이름을 가진 broker facade는 있지만 공개 controller endpoint는 없다 (`services/notification-service/src/main/java/com/samhanair/logis/notification/realtime/NotificationRealtimeBroker.java:10-29`). 기존 `ChatRoomsPage`도 이 사실을 명시하고 30초 polling을 쓴다 (`ChatRoomsPage.tsx:23-28`, `128-130`).

### 판정

**“기존 coedit 위”도 “완전 별도 실시간 인프라”도 아니다.** 기존 `RealtimeBroker`와 `createRealtimeClient`를 재사용하고, 방 ID를 entityId로 쓰는 채팅 전용 SSE endpoint/event 계약을 추가하는 구조가 코드 경계와 맞는다. `createCoeditProvider`는 같은 문서의 Yjs update/awareness 계약이므로 저장된 순서형 메시지, 재조회 가능한 이력, 참여자별 읽음, 첨부를 제공하지 않는다.

### mock hard gate

- mock mode는 `VITE_MOCK_MODE=1`/`development_mock`이다 (`clients/desktop/src/renderer/api/mock.ts:728-732`).
- Axios interceptor는 `getMockResponse()`가 non-null일 때만 adapter를 끼운다. null이면 인증 헤더 처리 후 **실제 요청**으로 진행한다 (`clients/desktop/src/renderer/api/client.ts:61-99`). `getMockResponse` 자체도 “매칭 실패 시 null” 계약이며 마지막에 null을 반환한다 (`mock.ts:2236-2242`, `14023-14026`).
- 기존 메신저 mock handler는 수신자 검색, 수신함, 읽음, bulk 발송만 처리하고 마지막에 null을 반환한다 (`mock.ts:19608-19715`). 방/참여자/첨부/채팅 stream handler는 없다.
- 일부 `/collab/stream`용 Blob handler가 `mock.ts` 안에 있어도 `createRealtimeClient`는 Axios가 아니라 native `fetch`를 사용한다 (`createRealtimeClient.ts:117-124`). 따라서 app mock adapter가 direct SSE fetch를 가로채지 않는다. 브라우저/Playwright route mock이 별도로 없으면 실 endpoint로 나간다.
- 결론: 채팅 REST endpoint마다 `mock.ts` handler가 필요하고, 채팅 SSE는 별도의 fetch intercept/주입 가능한 subscribe mock이 필요하다. handler 누락을 성공으로 간주하면 안 된다.

## ③ 참여자·권한 축

### 기존 채팅방 참여자 규칙

- 내부 채팅방/참여자 entity 자체가 없으므로 기존 채팅 참여자 결정 규칙도 없다.
- 현재 메신저는 송신자가 재직자를 직접 고르고, 본인은 수신자에서 제외하며, 각 수신자당 메시지 1행을 만든다 (`MessageService.java:85-100`, `102-134`; `MessengerPage.tsx:200-205`). 이것은 “방 참여자 규칙”이 아니다.
- #895의 확정 선례는 작성자를 대상자에 실제 포함하고 제거할 수 없게 하는 규칙이다 (`ScheduleService.java:38-48`, `Schedule.java:139-147`, `V17:1-27`). `.claude/memory/feedback_author_is_auto_participant.md`도 조건절 우회가 아니라 실제 집합 편입이라고 명시한다.
- **채팅방 생성자를 자동 참여자로 넣는지는 판정 불가**다. 코드에는 방이 없고 Issue #894 코멘트에도 해당 문장이 없다. 질문 1로 올린다.

### 붙을 위치

- **현재 데스크톱:** 그룹웨어 카테고리 아래 `/messenger`; `/admin/chat-rooms`는 별도 매핑 관리다 (`AppLayout.tsx:1293-1365`, `routes/index.tsx:410-416`, `1638-1646`). 알림은 전역 상단 벨과 `/notifications` 내역이다 (`NotificationBellDropdown.tsx:23-42`, `AppLayout.tsx:689-694`).
- **현재 모바일:** `clients/mobile-staff`, `clients/mobile`, `clients/arologis-mobile`의 추적 파일에서 메신저/내부 채팅 화면·라우트·메뉴를 찾지 못했다. 모바일의 기존 “notification” 언급은 전표 SSE foreground 안내나 push/테마이지 내부 채팅 표면이 아니다.
- **명시된 최종 부착 위치:** 데스크톱·모바일 모두 어느 업무 화면에서도 보이는 우측 하단 삼한이 런처 → 마스코트 위 방 목록 → 방 선택 시 독립 채팅 라우트/별도 창이다. 기존 `/messenger` 전체 페이지는 이 구조로 승계·재배치한다. 출처는 Issue #894 정정 코멘트다.

## 업무 판단이 필요해 추론하지 않은 질문 목록

1. **채팅방 생성/참여자 권한:** 누가 방을 만들고, 참여자를 초대·제거하고, 방 이름을 바꿀 수 있는가? `messenger.send`를 확장할지 별도 pageCode를 만들지도 확정이 필요하다. 또한 #895와 같이 **방 생성자를 실제 참여자 행에 자동 포함하고 제거 불가**로 할지 확인이 필요하다.
2. **이력 보존 기간:** 텍스트·사진·동영상·파일 및 읽음/리액션/멘션 이력을 각각 얼마 동안 보존하는가?
3. **삭제 정책:** 사용자 메시지 삭제, 방 나가기, 방 보관/삭제가 soft-delete인지, 상대 화면에서 어떻게 보이는지, 첨부 실물까지 언제 삭제하는지 확정이 필요하다.
4. **알림 연동 범위:** `MESSENGER`만이 아니라 APPROVAL/SAFETY_STOCK/ECOUNT_IMPORT 및 향후 채널을 모두 채팅으로 표시하는가? 알림 벨/내역을 대체할지 병존할지도 확정이 필요하다.
5. **기존 `batch_id` 의미:** 한 번에 N명에게 보낸 기존 복수 쪽지를 N개의 1:1 방으로 전개할지 하나의 그룹방으로 승격할지 확정이 필요하다.
6. **‘삼한이’ 발신자:** 실제 account/user row인지 가상 시스템 actor인지 확정이 필요하다.
7. **데스크톱 독립 창 구현:** Electron 별도 `BrowserWindow`인지 같은 창의 독립 라우트인지 확정이 필요하다. 모바일은 전체화면 라우트라는 방향만 명시돼 있다.
8. **‘특정 메시지 태그’ 의미:** 인용/답장인지 북마크인지 명시 계약이 없다.

## “이미 있는 것 / 새로 만들 것” 경계선

### 이미 있는 것 — 승계·확장

- `groupware-service`의 `messages`와 `/messenger` 표면
- 재직자 검색·수신자 picker·최대 50명 bulk send·수신함·읽음 처리
- `MESSENGER` 알림의 `sourceRefId=messageId`, deeplink, acknowledge 연계
- `notification_center`와 내부 fail-soft publisher
- SSE 전송 공통층(`createRealtimeClient`, `RealtimeBroker`, Redis cross-node hook)
- groupware 결재의 MinIO storage/권한 패턴
- 디자인시스템 삼한이 자산
- #895의 “작성자는 실제 참여자 집합에 자동 포함” 구현 선례

### 새로 만들 것 — 기존 도메인 안에서

- `messages`를 방 기반으로 넓힐 room/participant/message/read 모델과 기존 598행 마이그레이션
- 방 목록·대화 이력·전송·참여자 편집·참여자별 `read_at` API
- 방 ID 단위 채팅 SSE endpoint와 chat event schema
- 사진·동영상·일반파일 첨부 entity/API/storage key/참여자 접근가드/미리보기
- 리액션, 메시지 참조/태그, `@` 멘션 및 방 목록 `@` 미읽음 색인
- 사람 알림→1:1 방, 시스템 알림→삼한이 방의 변환/동기화 경계
- 데스크톱·모바일 전역 런처, 방 목록 팝오버, 독립 채팅 라우트/창
- 모든 신규 REST/SSE 경로의 mock hard gate와 회귀 테스트

### 만들지 않을 것

- `messages`와 병존하는 별도 채팅 도메인
- `partner_chat_room_mappings`를 내부 채팅방으로 재해석하는 것

- handler가 없는 mock 경로를 실제 API로 흘려보내는 false-green

## 못 한 것

- 코드·스키마·mock·테스트는 수정하지 않았다.
- UI 캡처는 생성하지 않았다. 이번 라운드는 코드/계약/SQL 진단이며 시각 결과를 주장하지 않는다. 따라서 `docs/qa/2026-08-10-1125-s1/`도 만들지 않았다.
