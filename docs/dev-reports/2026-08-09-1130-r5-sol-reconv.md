# PR #1130 R5 SOL 적대 재수렴 — MASTER 정본 정정 머지 판정

## 판정

```text
도달 가능한 결함: 2건
머지 불가
```

R5의 현재 mock 값 `MASTER inbound.inspection=1111111` 자체는 실 런타임과 맞다.
그러나 새 계약 테스트는 실제 백엔드 MASTER 분기를 보호하지 않으며, 공유 라이브
환경은 V98 미적용 상태라 발화 가능한 MANAGER 전표 2건이 모두 차단된다.

검증 기준은 워크트리 `t1064b`, HEAD
`f36a76532d173e9931ee5cf05c728ed62768a925`이다. 커밋·push·V98 수정·공유 DB
쓰기는 하지 않았다.

## 결함 1 — R5 전권 테스트는 실제 `/permissions/my` 서비스 분기를 지키지 않는다

### 실 사용자 경로

`MASTER 로그인 → GET /auth/admin/permissions/my → inbound.inspection 액션 → 입고전표
검수 완료 버튼`이다. 실제 endpoint가 특정 page code에서 액션 하나를 빠뜨리면 화면
가드가 그 액션을 잃는다.

### 근본 원인

현재 실제 endpoint는 R5 주석이 가리키는
`DynamicPermissionService#getMyPermissions`가 아니다.

- `PermissionAdminController.java:253-270`: `X-Is-System-Master=true`이면
  `allPageActions()`를 직접 반환한다.
- `PermissionAdminController.java:322-327`: `PageCode.values()` 전부에
  `ALL_ACTION_NAMES`를 넣는다.
- `inbound-permission-contract.test.ts`는 백엔드 코드를 호출하지 않고
  `getMockResponse()`만 검사한다.

### 재현과 원문

기준 상태에서 다음 두 테스트는 각각 통과했다.

```text
./gradlew.bat :services:auth-service:test \
  --tests "com.samhanair.logis.auth.web.PermissionAdminControllerTest.getMyPermissions_withSystemMasterHeader_returnsAllPageActions" \
  --rerun-tasks
BUILD SUCCESSFUL

npx vitest run src/renderer/test-utils/inbound-permission-contract.test.ts
Test Files 1 passed (1)
Tests 1 passed (1)
```

그 뒤 실제 서비스의 `allPageActions()`에서 오직 `inbound.inspection`의 `PRINT`만
임시 제거해 `1111111 → 1111110`으로 깨고 두 테스트를 다시 실행했다. 둘 다 RED가
아니라 GREEN이었다.

```text
backend: Exit code 0
BUILD SUCCESSFUL in 15s
12 actionable tasks: 12 executed

R5 frontend contract: Exit code 0
Test Files 1 passed (1)
Tests 1 passed (1)
```

기존 백엔드 테스트는 전체 page 수와 `accounting.journals` 한 셀만 검사한다. 따라서
다른 page의 선택적 비트 손실을 놓친다. 새 R5 테스트는 mock 손실만 잡으므로 실제
서비스 분기 회귀에는 false-green이다.

대조로 mock의 `inbound.inspection` PRINT를 임시 제거하면 새 테스트는 정상 RED였다.

```text
MASTER inbound.inspection: expected '1111110' to be '1111111'
Test Files 1 failed (1)
Tests 1 failed (1)
Exit code: 1
```

즉 “mock 전권”은 지키지만 “런타임 전권”은 지키지 않는다. 모든 임시 변경은 제거했다.

## 결함 2 — 공유 라이브 런타임에서 MANAGER 산출물이 2건 모두 차단된다

### 발화 조건 선측정

공유 `slip_db`를 읽기 전용 트랜잭션으로 집계했다.

```text
측정 시각: 2026-08-09 10:08:51.477 KST
INBOUND + INSPECTING 활성 전표: 2건
2026/08/08-3 | S20 QA
2026/08/08-4 | S20 QA
```

0건이 아니므로 라이브 판정이 가능하다.

### 재현 절차와 원문

`clients/desktop`에서 Vite web renderer를 `127.0.0.1:5175`, 실 gateway
`127.0.0.1:8080`, mock OFF로 기동하고 Playwright Chromium 1217을
`headless: true`로 실행했다. 캡처 경로는 전부 `resolveQaShotsDir()` 결과인
`docs/qa/1130-r5-sol-reconv/_local`이다. 상태 변경 버튼은 누르지 않았다.

동일한 `2026/08/08-3` 전표에서의 관측:

```text
2026-08-09 10:14:55.231 KST
dev_master / MASTER
GET /auth/admin/permissions/my = 200
inbound.inspection = [VIEW,CREATE,UPDATE,DELETE,RESTORE,DOWNLOAD,PRINT]
완료 (처리 완료) disabled=false

2026-08-09 10:15:01.344 KST
dev_manager / MANAGER
GET /auth/admin/permissions/my = 200
inbound.inspection = [VIEW]
완료 (처리 완료) disabled=true

2026-08-09 10:15:07.277 KST
dev_sales / SALES
GET /auth/admin/permissions/my = 200
inbound.inspection = []
/purchases/{id} 진입 시 / 대시보드로 redirect, 상세 GET 0회
```

공유 `auth_db.flyway_schema_history`의 최신 버전은 V96이다. V98은 아직 적용되지
않았고, 2026-08-09 10:43:04.609 KST 읽기 전용 대조에서도 MANAGER 템플릿과
계정 캐시는 모두 `1000000`이었다. 따라서 현재 실 사용자 경로에서는
`INBOUND + INSPECTING` 2건 모두 MANAGER에게 차단된다.

이는 R5 소스의 V98 SQL이 틀렸다는 증거가 아니라 라이브 환경에 아직 배포되지 않았다는
증거다. 하지만 이번 라운드 요구사항인 “본래 산출물이 실 사용자 경로에서 살아 있음”은
충족하지 못한다. 공유 DB 쓰기 금지 때문에 V98을 강제 적용하거나 완료 mutation을
호출하지 않았다.

## ① MASTER 런타임 전권 실측

`dev_master`로 실제 로그인 후 `GET /auth/admin/permissions/my`를 호출했다.

```text
측정 시각: 2026-08-09 10:08:29.772 KST
HTTP 200
page code 수: 200
7-action 미만 page code 수: 0
inbound.inspection: VIEW,CREATE,UPDATE,DELETE,RESTORE,DOWNLOAD,PRINT
```

원문 전체는 `docs/qa/1130-r5-sol-reconv/_local/observations.json`의
`dev_master.permissionResponses[].raw`에 보존했다. 응답의 200개 page code 전부가
정확히 7개 action을 가졌다. 현재 런타임 전권 규칙 자체는 성립한다.

## ② 비MASTER 정본 축과 특별 처리 역할 전수

### 코드 전수

실 endpoint의 분기는 다음 세 가지뿐이다.

1. `X-Is-System-Master=true`: 모든 `PageCode × 7 action`.
2. `X-Is-Partner=true`: 빈 map으로 fail-closed.
3. 그 외: `X-User-Id`로 `account_page_permissions`를 `bulkLoad`.

따라서 MASTER 외 역할이 런타임에서 템플릿을 직접 읽는 것은 아니다. 비MASTER의
실효 정본은 materialized `account_page_permissions`이고, 역할 템플릿/그룹은 그
생성 원천이다. PARTNER는 MASTER 외 유일한 특별 처리 identity다.

### 실 DB와 실제 응답 대조

2026-08-09 10:43:04.609 KST, `inbound.inspection` 9개 로그인 가능 비MASTER 역할의
템플릿과 계정 캐시는 전부 일치했다.

```text
ACCOUNTANT 0000000 = 0000000
DEVELOPER  0000000 = 0000000
DISPATCH   0000000 = 0000000
DRIVER     0000000 = 0000000
INVENTORY  1111000 = 1111000
MANAGER    1000000 = 1000000  (V98 미적용 런타임)
SALES      0000000 = 0000000
STAFF      0000000 = 0000000
WAREHOUSE  1111000 = 1111000
```

각 실 로그인 `/permissions/my`의 `inbound.inspection`도 위 계정 캐시와 동일했다.
V98 소스 적용 후 기대값은 MANAGER만 `1010000`이지만, 그 상태는 공유 DB에서
실증하지 못했다.
