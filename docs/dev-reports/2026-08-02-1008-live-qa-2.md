## ① 주입한 downstream 목록

공유 Docker 컨테이너는 `docker ps`와 `docker inspect`로 읽기만 했다. 확인된 호스트 포트와 standalone에서 필요한 주소는 다음 3개다.

| downstream | Docker 내부 주소 | 호스트 포트 | 이번 주입 주소 |
|---|---|---:|---|
| `partner-service` | `efab4f23312d` / `172.19.0.18:8095` | 8095 | `127.0.0.1:8095` |
| `product-service` | `049eab6b2a67` / `172.19.0.16:8084` | 8084 | `127.0.0.1:8084` |
| `dc-config-service` | `04da01e5921a` / `172.19.0.21:8089` | 8089 | `127.0.0.1:8089` |

총 **3개**를 주입했다. Eureka 응답을 로컬 QA 프록시(`127.0.0.1:8762`)에서 받아 위 3개 인스턴스의 Docker hostname/IP만 호스트 주소로 변환했다. 공유 Eureka와 공유 컨테이너는 재기동하지 않았다.

호스트 hosts 파일 직접 주입 시도 원문은 다음과 같다.

```text
Add-Content : Access to the path 'C:\Windows\System32\drivers\etc\hosts' is denied.
```

따라서 시스템 hosts 파일은 변경하지 않고, 임시 Eureka 중계 방식으로 주입했다. QA 종료 시 standalone jar, renderer, Eureka 중계 프로세스는 종료했다.

## ② 502 원인 판정

### 1차 502

최초 standalone 실행 시 원문:

```text
PartnerLookupClient batch 호출 실패 — count=1, msg=No instances available for partner-service
```

Eureka에는 `partner-service`가 Docker 주소로 등록돼 있었다.

```text
<hostName>efab4f23312d</hostName>
<ipAddr>172.19.0.18</ipAddr>
<port enabled="true">8095</port>
```

**1차 502 자체의 직접 원인은 QA 실행 토폴로지 문제**다. 공유 Docker 안에서는 유효한 주소지만 호스트 standalone JVM에서는 접근할 수 없다.

### 설정 결함 여부

이번 재시도에서 확인한 제품 설정 gap도 기록한다.

- `PartnerLookupClient`: `http://partner-service` 하드코딩
- `ProductClient`: `http://product-service` 하드코딩
- `PartnerDcConfigClient`: `http://dc-config-service` 하드코딩
- `application.yml`에 `PRODUCT_SERVICE_BASE_URL`가 있으나 `ProductClient`는 이를 사용하지 않는다.

따라서 **Docker 내부 배포만 전제하면 QA 환경 문제지만, standalone 호스트 실행도 지원해야 하는 운영/QA 계약이라면 URL 주입 불가가 동일 계열의 설정 결함**이다. 이번 PR의 일마감 기능 결함으로 직접 판정하지는 않지만, standalone 검증 가능성을 막은 제품 설정 결함으로 별도 기록한다. 임시 Eureka 주소 주입 후에는 같은 jar에서 downstream 호출이 회복되어 502가 사라졌다.
