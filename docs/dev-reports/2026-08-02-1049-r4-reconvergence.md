# PR #1050 재수렴 4차 적대검증 — fix 3회 전체 표면

## 결론

**BLOCK.** fix 3회가 직접 고친 품목 옵트인 경로는 실 데이터·실 화면에서 수렴했다. 그러나 PR 제목과 이슈가 약속한 품목·수신자·거래처·담당자 4종 중 결과 개수별 새 계약이 실제로 적용된 곳은 품목 1곳뿐이다. 수신자·거래처·담당자는 1건이어도 즉시 확정되지 않고, 2건 이상이어도 결과 선택 모달이 뜨지 않는다. 기존 dropdown을 실제로 클릭하면 선택 자체는 반영되므로 “완전 조작 불가”는 아니지만, PR 계약 3/4가 미롤아웃이다.

첫 질문에 대한 답은 **“같은 넓은 부분검색어를 유지하면 차단되는 실 레코드가 있다”**이다. `AJ` 품목은 실 DB 45건 중 모달에 20건만 보여 **25건**, `010` 거래처는 5,607건 중 dropdown에 20건만 보여 **5,587건**이 그 검색어로는 선택 불가능했다. 합계 **5,612건**이다. 실제 숨은 값 `AJ016MB1PBC2`, `01024100228`이 넓은 검색 결과에 없는 것을 DOM에서 확인했다. 다만 두 값 모두 정확 코드를 다시 입력하면 1건으로 검색·선택되어 영구 접근 불능은 아니었다.

검증은 코드·DB·공유 Docker를 수정하지 않고 수행했다. 이 브랜치 소스의 renderer를 `VITE_APP_VERSION=2026/08/02-1050`, 실 게이트웨이 `:8080`, mock OFF로 띄웠다. 먼저 두 라우팅을 모두 열어 `/products/estimate-items`는 대시보드, `#/products/estimate-items`만 목표 화면임을 확인한 뒤 모든 GUI 검증에 HashRouter 경로를 사용했다. DB는 `SELECT`만 수행했다.

## 1. fix 3회가 건드린 표면

`git log --oneline -20`과 각 commit patch를 직접 확인했다.

### fix 1 — `42eee1321 [FIX] #1049 검색 상태 잔재 — 세 경로 공통 정리로 통합`

### fix 2 — `b57422ea7 [FIX] #1049 경로별 resetDraft 분기 · product-catalog 스펙 갱신`

- `handleFocus`, `handleBlur`, `handleChange`, 모달 open/close, `displayValue` 계산을 모두 변경했다.
- 특히 `displayValue = open || draft.length > 0 ? draft : selectedLabel`은 옵트인 품목뿐 아니라 공용 base를 쓰는 legacy 입력에도 닿는 표면이다.
- `product-catalog.spec.ts`의 옛 1건 dropdown 클릭 표현을 즉시 칩 확정 표현으로 갱신했다.

### fix 3 — `fa0d13e05 [FIX] #1049 draft 보존 토큰을 일회용으로 소비`

- 모달 취소 후 첫 focus에서 `preserveDraftOnNextFocusRef.current = false`로 토큰을 소비하도록 했다.
- `AsyncAutocomplete` 단위 테스트 46행과 실 경로 Playwright 18행을 추가했다.

## 3. 막히는 사례 — 실제 값·실제 조작

### B-01 — 넓은 품목 부분검색에서 실 25건이 모달 후보 밖으로 잘린다

1. 실 DB에서 `name/model_name`에 `AJ`가 매치되는 활성 품목은 **45건**이었다.
2. 실 API는 `totalElements=45`, `content=20`을 반환했다.
3. 실제 화면에 `AJ`를 입력하자 품목 검색 결과 모달 checkbox는 **20개**뿐이었다.
4. 실 품목 `AJ016MB1PBC2`는 그 모달 DOM에 **0건**이었다. 같은 검색어를 유지한 채로는 선택할 수 없다.
5. Escape 후 `AJ016MB1PBC2`를 정확히 입력하면 모달 없이 `1개 선택됨`으로 확정됐다.

판정: **같은 부분검색어 기준 25건 차단, 정확 코드 재검색으로 회복 가능.** 모달이 API total을 버리고 첫 20건만 보여 주며 총 건수·추가 페이지·추가 입력 안내가 없다.

### B-02 — 넓은 거래처 부분검색에서 실 5,587건이 후보 밖으로 잘린다

1. 실 DB에서 거래처 코드/상호/사업자번호/전화에 `010`이 매치되는 활성 거래처는 **5,607건**이었다.
2. 실 API는 `total=5607`, `items=20`을 반환했다.
3. 실제 거래처 입력에 `010`을 입력하자 dropdown 후보는 **20개**, 검색 결과 선택 모달은 **0개**였다.
4. 실 거래처 코드 `01024100228`은 해당 dropdown DOM에 **0건**이었다.
5. 입력을 `01024100228`로 교체하면 API/UI 1건이 되고, 실제 클릭 후 `경기퀵-이영진님`이 입력에 반영됐다.

판정: **같은 부분검색어 기준 5,587건 차단, 정확 코드 재검색으로 회복 가능.** 이는 새 모달 롤아웃 누락과 기존 20건 상한이 동시에 드러난 사례다.

### B-03 — PR 계약 3/4 미롤아웃

운영 렌더 지점에서 새 `resultSelectionMode`를 쓰는 곳은 `EstimateItemsCatalogPage`의 `ProductMultiSelectAutocomplete` 1곳뿐이다. 수신자·거래처·담당자 실 화면은 각각 결과 1건과 다건을 실제 조작했지만 모두 legacy dropdown이었다.

- 수신자: 1건 자동 확정 없음, 6건 결과 모달 없음. dropdown 클릭 후 칩은 반영됨.
- 거래처: 1건 자동 확정 없음, 20건 결과 모달 없음. dropdown 클릭 후 단수 입력은 반영됨.
- 담당자: 1건 자동 확정 없음, 7건 결과 모달 없음. dropdown 클릭 후 복수 칩은 반영됨.

선택 자체가 완전히 막힌 레코드는 이 세 실측 검색어에서 0건이지만, 이슈/PR의 결과 개수별 UX 계약은 세 대상 전체에서 도달 불가능하다.

## 4. 판정

**BLOCK — 머지 불가.**

1. PR 제목과 #1049 범위의 4종 중 새 계약 적용은 품목 1종뿐이다. 수신자·거래처·담당자 3종은 1건 즉시 확정과 2건 이상 결과 모달이 모두 없다.
2. 사용자 첫 질문 기준, 같은 부분검색어로 선택되어야 할 후보가 `AJ` 25건 + `010` 5,587건 = **5,612건** 잘린다. 실제 숨은 값 두 건으로 DOM 부재와 정확 코드 회복을 각각 재현했다.
3. fix 1~3이 해결하려던 품목 상태 전이는 실 화면에서 수렴했다. 즉시 확정·모달 확정·취소·필드 왕복·재타이핑·0건 후 다음 행동에서 새 차단은 발견하지 못했다.
4. fix 2가 공용 `displayValue`/focus/blur/change를 바꾼 legacy 표면도 수신자·거래처·담당자의 실제 입력과 실제 선택으로 확인했다. 테스트한 값에서는 겉보기만 편집 가능하고 선택이 반영되지 않는 controlled-value 결함은 재현되지 않았다.
5. 정확 식별자 경로는 품목·거래처에서 실제 코드로, 수신자·담당자에서 현재 실데이터가 가진 `login_id`로 성공했다. 직원 `ecount_code`는 활성 24명 전원 미부여라 그 값 자체의 GUI 검증은 불가능했다.

현재 head `fa0d13e05`에 대해 `gh pr checks 1050`을 새로 조회했고 표시된 49개 check는 모두 `pass`였다. CI green은 위 실 UX 범위 누락과 후보 잘림을 검출하지 않는다.

## 5. 이 라운드가 보지 않은 것

- 코드 수정, 테스트 수정, commit/push/checkout/브랜치 조작을 하지 않았다.
- Docker 이미지 rebuild/restart와 DB write를 하지 않았다.
- 선택 후 서버 저장, 쪽지 발송, 결재 생성, 거래처 매핑 저장은 mutation이므로 실행하지 않았다. 선택 직후 controlled value/칩 반영까지만 확인했다.
- warehouse는 이번 지시의 4종에 포함되지 않아 조사하지 않았다.
- 41개 전체 렌더 지점을 다시 GUI 순회하지 않았다. 공용 legacy 회귀는 수신자·거래처·담당자 대표 실 화면으로 확인했다.
- `AJ`, `010`, `개발` 이외 모든 부분검색어의 잘림 규모를 전수 계산하지 않았다. 따라서 5,612건은 전역 유일 레코드 수가 아니라 **이번에 실제 조작한 두 넓은 검색어에서 후보 UI 밖으로 잘린 건수의 합**이다.
- 품목 1,120개 코드 각각과 거래처 7,259개 코드 각각을 GUI로 전수 입력하지 않았다. 품목은 DB 조건식으로 exact-code 비검색 행 0건을 계산했고 대표 실제 값을 조작했다.
- 스크린샷은 만들지 않았다. 저장소 QA 자산 삭제도 수행하지 않았다.
- CI 49건은 상태만 새로 조회했으며 로컬에서 전체 suite를 재실행하지 않았다.
