## ② 불변식 — 무엇이 참이어야 하는가

1. 한 사용자의 협업 저장 후 부수효과가 느리거나 실패해도, 같은 전표의 다른 사용자가 서로 다른 필드를
   정상 저장할 수 있어야 한다.
2. 같은 필드의 stale 저장은 최신 값을 덮지 않고 사용자에게 최신 확인이 필요한 409로 알려야 한다.
3. 서로 다른 필드의 같은-baseline 저장은 요청 도착 순서와 무관하게 둘 다 보존되어야 한다.
4. 잠금 획득 실패나 timeout이 발생해도 사용자는 일반 서버 내부 오류가 아니라 재확인·재시도 가능한
   의미를 받아야 한다.
5. 성공 응답 시 전표 변경, 감사/리비전, ACCEPTED 이력의 정합성이 유지되어야 한다.
6. 알림 실패는 이미 성공한 전표 저장을 되돌리지 않아야 하며, 사용자 화면에 내부 UUID가 노출되지 않아야 한다.

## ③ 양방향 RED

### RED-A — 되돌리면 안 되는 것

- 같은 필드 stale 두 저장에서 패배자가 409를 받고, 승자의 최신 값·감사·리비전이 보존된다.
- 서로 다른 필드 두 저장은 둘 다 성공하고 두 값이 최종 전표에 함께 남는다.
- 어느 필드 하나라도 baseline이 다르면 mutation·ACCEPTED 이력·알림이 부분 발생하지 않는다.
- 프런트는 원격 갱신 뒤에도 편집 시작 baseline을 보내고, 409의 한국어 안내를 `role=alert`로 보인다.
- **반대급부:** 잠금 체류를 줄이는 fix가 알림 누락, 중복/phantom 알림, 성공 이력 누락,
  커밋되지 않은 변경의 알림, same-field lost update, different-field false 409를 만들면 안 된다.
- best-effort 알림 실패가 성공한 저장 전체를 rollback시키는 회귀가 없어야 한다.

### RED-B — 재발하면 안 되는 것

- auth 조회 또는 notification 전송이 3초 이상 지연되는 동안, 먼저 시작한 협업 저장 때문에 같은 전표의
  두 번째 different-field 저장이 일반 500으로 끝나면 RED다.
- 잠금 획득 실패·timeout이 `INTERNAL_ERROR`와 `서버 내부 오류가 발생했습니다.`로 내려가면 RED다.
- 첫 사용자의 `수정완료` 응답이 수신자 수에 비례한 순차 외부 호출 시간만큼 체감 정지하면 RED다.
- 같은 필드의 두 번째 저장이 잠금 대기 실패 때문에 baseline 409 의미를 잃으면 RED다.
- `expectedBefore` 없는 생산 호출부가 생기거나, 기존 화면 저장이 모든 요청에서 409/400이 되면 RED다.
