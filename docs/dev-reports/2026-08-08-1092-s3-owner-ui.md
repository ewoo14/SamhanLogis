# #1092 Slice 3 — 담당자 UI 연결

## 범위

S1에서 준비된 견적서 담당 변경 API를 데스크톱 견적서 상세 화면에 연결하고, 통합 목록의 표시 용어를 `작성자`에서 `담당`으로 정리했다. 커밋·push와 공유 Docker 재기동은 하지 않았다.

## 구현 판단

- 단일 담당자이므로 `MultiSelectAutocomplete`가 아닌 design-system의 `AsyncAutocomplete`를 사용했다. `MultiSelectAutocomplete`는 여러 선택값과 칩 제거 UI가 목적이고, 이번 계약은 한 명의 담당만 선택한다.
- 사원 lookup은 저장소 표준인 `searchApprovalLineUsers`를 재사용한다. 후보와 현재 선택값은 `displayName`만 렌더링하고 UUID는 endpoint payload의 `requesterId`로만 사용한다.
- 통합 목록 열은 `담당`으로 변경했다. 이 화면에서 의미 있는 업무 축은 `requester_id`이고, `created_by`는 담당 변경과 무관한 불변 작성 감사 기록이다. 따라서 `작성자`라는 라벨을 유지하면 변경 가능한 담당과 불변 작성 기록을 혼동할 가능성이 더 크다. 주문서 계열에는 담당자 계약이 없으므로 빈칸을 유지한다.
- 교차 계열 선택 UI는 제공하지 않는다. 서버가 거부하는 경우에는 API의 한국어 사유를 공통 오류 배너에 표시해 사용자가 왜 실패했는지 알 수 있게 했다.

## 변경 내용

- `EstimateDetailPage`: 담당자 이름 lookup, 표준 `AsyncAutocomplete`, `PATCH /slips/estimates/{id}/owner`, 성공 시 상세·목록 query invalidate, 실패 사유 표시.
- `estimateApi`: `requesterName`/`createdByName` 표시 필드를 optional로 수용. raw ID는 화면에 렌더링하지 않는다.
- `estimateUnifiedListModel` / `EstimateListPage`: `writer` 축을 `owner`로 변경하고 열 라벨/test id를 `담당` 기준으로 변경. 견적서는 `requesterName`, 주문서는 빈칸.
- 테스트: 상세 담당 변경·UUID 비노출·교차 변경 오류, 통합 목록 담당 표시/정렬/부분 실패 회귀.

## RED → GREEN 증거

- RED-A: 담당자 이름을 화면에 표시하고 선택 시 `requesterId`만 owner endpoint에 전달하는 상세 화면 테스트를 먼저 실패시킨 뒤 구현 후 통과.
- RED-B: owner mutation body에는 `requesterId`와 `documentType`만 포함하며 `created_by` 필드는 추가하지 않았다. S1 서비스 계약의 `created_by` 보존 테스트와 함께 검증 대상이다.
- RED-C: owner endpoint가 주문서 계열 거부 사유를 반환하면 화면 alert 배너에 한국어 사유가 표시되는 테스트 통과.
- RED-D: 통합 목록의 견적서/주문서 교차 정렬, 부분 실패 보존, `담당` 열 회귀 테스트 통과.

## 미완료/주의

- 실제 화면에서 사원 후보가 보이려면 auth-service의 기존 `approval-line-configs/users` 권한과 서비스가 정상이어야 한다. 권한/서비스가 unavailable이면 UUID fallback을 사용하지 않고 오류 상태를 표준 컴포넌트가 표시한다.
- 커밋·push는 수행하지 않았다. PM이 후속 통합 및 CI를 대행해야 한다.
