# D-G1 S1 조회 결함 수정 보고서

작성일: 2026-08-11  
대상: PR #1165 / `accounting-service`  
범위: S1 문서번호 조회 입력 경계와 회귀 검증만

## 1. 판정

`findByDocumentNo`의 null/blank 호출을 repository 앞에서
`BusinessException(ErrorCode.INVALID_INPUT)`으로 차단했다. 유효한 번호는 `trim()` 후 조회하므로
CONFIRMED 왕복 조회가 유지되고, DRAFT의 `document_no IS NULL` 저장·확정 시 채번은 변경하지 않았다.

S2~S4는 착수하지 않았으며 git 조작·공유 DB write·배포도 하지 않았다. 모든 DB write는
Testcontainers PostgreSQL에서만 수행했다.

## 2. 근본 원인과 선택한 수단

### 근본 원인

현행 서비스는 다음 derived query에 입력을 그대로 전달했다.

```java
repository.findByDocumentNoAndIsDeletedFalse(documentNo)
```

Spring Data JPA에서 `null` 인자는 `document_no IS NULL` 조건으로 해석된다. 따라서 번호 없는
DRAFT가 있으면 `findByDocumentNo(null)`이 정상 결과처럼 DRAFT를 반환했다. `document_no`가
nullable이고, migration의 active unique index도 `document_no IS NOT NULL` 행만 대상으로 하므로
번호 없는 DRAFT 여러 건은 설계상 정상이다.

### 선택한 수단

서비스 경계에서 다음 순서를 고정했다.

```text
null/blank 검사 → INVALID_INPUT 예외 → trim → repository 조회
```

선택 근거는 다음과 같다.

1. `findByDocumentNo`는 “문서번호로 활성 정산서를 되찾는다”는 업무 API이므로 호출 실수인
   null/blank를 호출자에게 드러내는 위치가 서비스 경계다.
2. repository의 null 의미를 `IS NULL`에서 빈 결과로 바꾸면 호출 실수를 조용히 숨기게 된다.
   따라서 repository predicate만 바꾸지 않았다.
3. DRAFT에 임시 번호를 넣지 않아 채번 규약과 `DRAFT.document_no IS NULL` 불변식을 보존했다.
4. 현재 main 코드 검색에서 이 repository의 업무별 조회 메서드는
   `findByDocumentNoAndIsDeletedFalse` 하나뿐이며, 서비스 외 controller/다른 production caller는
   발견되지 않았다. `confirm(UUID)`의 `repository.findById(UUID)`도 별도 조회 좌표로 확인했다.

## 3. 조회 메서드 전수표

| 좌표 | 실제 조회 | null 인자 | 빈 문자열 인자 | 유효하지만 없는 값 | 수정 후 판정 |
|---|---|---|---|---|---|
| `SalesCommissionSettlementService.findByDocumentNo(String)` | `findByDocumentNoAndIsDeletedFalse(String)` | 수정 전 DRAFT 반환 | 수정 전 repository 호출 후 `NOT_FOUND` | `NOT_FOUND` | null/blank는 `INVALID_INPUT`, 그 외 trim 후 조회 |
| `SalesCommissionSettlementService.confirm(UUID)` | inherited `JpaRepository.findById(UUID)` | Spring Data가 repository 호출 전 `IllegalArgumentException`을 냄 | UUID 경로라 해당 없음 | `BusinessException(NOT_FOUND)` | S1 fix 범위 변경 없음 |
| `SalesCommissionSettlementRepository.findByDocumentNoAndIsDeletedFalse(String)` | active 문서번호 단건 조회 | 서비스 경계를 우회해 직접 호출하면 JPA의 `IS NULL` 의미가 남음 | 빈 결과 | `Optional.empty()` | public 업무 경로는 서비스에서 항상 guard 후 진입 |
| `JpaRepository` inherited `findAll`/`findAllById`/`existsById` 등 | 이 엔티티의 production caller 없음 | 문서번호 조회 경로 아님 | 문서번호 인자 없음 | 해당 없음 | 추가 수정 없음 |

별도 `SalesCommissionSettlement` controller route나 다른 production caller는 검색 결과 없었다.
따라서 이번 결함의 실제 외부 진입점은 서비스 `findByDocumentNo`이며, 서비스에서 repository 호출
전 차단하는 계약을 고정했다.

## 5. 조합별 결과

| 조합 | 기대/확인 결과 |
|---|---|
| 번호 `null` + DRAFT 1건 | `INVALID_INPUT`; DRAFT UUID가 반환되지 않고 행은 DRAFT + `document_no IS NULL`로 유지 |
| 번호 `null` + DRAFT 2건 | `INVALID_INPUT`; query가 실행되지 않아 `IncorrectResultSizeDataAccessException`으로 내려가지 않음 |
| 번호 `""` 또는 `"   "` + DRAFT | `INVALID_INPUT`; repository interaction 0건 |
| 존재하는 정상 형식 번호 + CONFIRMED | 기존 번호로 같은 정산서 UUID를 회수 |
| 존재하는 정상 형식 번호 앞뒤 공백 + CONFIRMED | trim 후 같은 UUID를 회수 |
| 존재하지 않는 정상 형식 번호 | 기존 계약대로 `NOT_FOUND` |
| DRAFT를 정상 번호로 조회 시도 | 번호가 없으므로 `NOT_FOUND`; DRAFT에 임시 번호를 부여하지 않음 |
| 활성 동일 번호 2건 | migration의 `uq_sales_commission_settlements_document_no_active` partial unique index가 차단하여 `DataIntegrityViolationException`; 동일 번호 2건은 활성 상태로 존재할 수 없음 |

동일 번호 제약은 `is_deleted = FALSE AND document_no IS NOT NULL`에만 적용된다. 따라서 soft-deleted
이력의 번호 재사용 가능성은 기존 soft-delete 설계 영역이고, `@SQLRestriction` 및 active repository
조건 때문에 이 조회 경로에서 활성 중복으로 보이지 않는다.
