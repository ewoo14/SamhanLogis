# #1032 totalAmount 계약 판정 및 수정 보고서

## 1. 판단 — ② 구현이 틀렸음

전수 조사 결과 `totalAmount`는 표시 전용이 아니라 계약/집계 필드다. 현재 변경은 `SlipResponse.from`과 `SlipSearchResult.from`에서 `totalAmount`를 `SlipDisplayAmount.vatInclusiveTotal(...)`로 계산해 VAT 포함 표시값으로 바꿨다. 그러나 기존 DTO Javadoc과 테스트 계약은 `lineTotal` 합산이며, 같은 값이 전표 목록·복원 응답, 그룹웨어 결재 전표 선택, 공개 인수증, 전표 정리/CSV, 기간별 집계 경로에 전달된다.

### 소비처 개수

- 저장소 전체 소스 파일의 `totalAmount` 참조: 167개(문서/QA 제외, 테스트 fixture 포함).
- slip-service main의 직접 참조 파일: 11개.
- 그중 전표 계약/표시와 직접 연결된 경로: 9개.
- 사용자 화면/출력 소비: 7개 — 판매관리, 구매관리, 그룹웨어 결재 작성/상세, 공개 인수증, 전표 정리 화면, 전표 정리 CSV.
- 회계·세금계산서·정산 계열은 `supplyAmount`/`vatAmount`/`totalAmount`를 함께 계약으로 사용하고, 회계 전표·부가세 신고가 금액 자체에 의존한다. 따라서 화면 표시 통일을 위해 계약 필드를 변경할 수 없다.
- slip-service test에서 `totalAmount`를 직접 검증하는 파일은 7개이며, 실패한 `SlipListE2RealtimeRestoreIT` 3건도 라인 복원 회귀를 `data.totalAmount`로 판정한다.

결론: 테스트 기대값만 VAT 포함으로 갱신하면 #758의 삭제 라인 오복원 회귀를 금액 규약 변경 뒤에 숨기고, 회계/복원 계약을 깨뜨린다. `totalAmount`는 기존 `lineTotal` 합산으로 되돌리고, VAT 포함 화면값은 별도 표시 필드로 제공해야 한다.

## 2. TDD RED

기존 단위 테스트를 계약값(`lineTotal` 합산)과 별도 `displayTotalAmount`(VAT 포함) 검증으로 바꾼 뒤 실행했다.

```text

3 errors
BUILD FAILED
```

이는 아직 표시 필드가 구현되지 않은 상태에서 새 계약 테스트가 의도대로 실패한 RED다.

## 5. 전수 개수 보강

`services/**/src/main`만 대상으로 한 직접 문자열 참조는 63개 파일이다. 그중 accounting-service 39개 파일, slip-service 11개 파일, partner-order-service 9개 파일이며, 나머지는 기타 서비스/공통 응답이다. 이 숫자는 필드 선언·DTO·계산·화면 계약을 포함한 파일 수이고, 동일 파일의 여러 참조를 중복 파일로 세지 않았다. 특히 accounting-service의 세금계산서·일마감·매출/매입 전표·자금/채권 리포트 경로가 포함되므로 ①(화면 전용)으로 볼 수 없다.
