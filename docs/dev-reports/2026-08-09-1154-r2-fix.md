## 1. 원인 확인

R1 전제와 현재 소스는 일치했다.

- `EcountPartnerImporter.upsertPartner()`의 기존행 분기는 `createdAt`을 건드리지 않았다.
- 신규행의 `overrideCreatedAtForImport()`는 Spring Data auditing 저장 시 `@CreatedDate`에 의해 실제 INSERT에서 적재 시각으로 덮였다.
- 기존행 조회가 `findByPartnerCode()`뿐이라 `@SQLRestriction("is_deleted = false")`로 삭제행을 놓쳤다.
- 활성행 조회를 먼저 하지 않으면 삭제행과 활성행이 동시에 존재하는 코드 조합에서 정상 활성행의 동작을 바꿀 수 있다.

## 2. 수정 내용

`EcountPartnerImporter`만 수정했다.

1. 활성 `partner_code` 조회가 비어 있을 때만 `findByPartnerCodeIncludingDeleted()`를 조회한다.
2. 삭제행을 찾은 경우 `markRestored()`를 호출한다. `status`는 변경하지 않는다.
3. 기존행에 `registrationDate`가 있을 때만 `registrationDate.atStartOfDay()`로 `createdAt`을 교정한다.
4. 등록일자 없는 기존행은 `createdAt`을 호출하지 않아 재적재로 바뀌지 않는다.

이로써 활성행 우선 정책으로 정상행의 F 불변식과 `status` 보존을 유지한다.

SOL이 사용한 SQL:

```sql
SELECT COUNT(*) AS source_rows,
       COUNT(*) FILTER(WHERE p.registration_date IS NOT NULL) AS registration_present,
       COUNT(*) FILTER (WHERE p.registration_date IS NOT NULL
                        AND p.created_at=p.registration_date::timestamp)
           AS created_at_matches_registration,
       COUNT(*) FILTER (WHERE p.registration_date IS NULL) AS registration_absent
FROM staging.ecount_partner_raw s
JOIN partners p ON p.id=s.target_partner_id
WHERE s.source_file_hash=
 '064770396F5586EC7D49E8219DD19086EF48C072F4BA4FF7B1BABB0EC14D4619';
```

### RED-B — 등록일자 없는 행의 재적재 불변

R2 실 API 2회 연속 재적재는 R1 격리 서비스(28095)와 정본 XLSX가 현재 존재하지 않아 새로 수행하지 못했다. 대신 수정 전 단위 RED 테스트를 작성했으며, 등록일자 없는 기존행 보존 테스트는 수정 전에도 통과했다. 이는 이번 변경이 해당 경로를 건드리지 않았음을 확인하는 보호 테스트다.

### RED-C — 삭제행 재적재 UUID 고아

R1 실측 원문(선행 R1은 DB UUID 직접 변조로 상태를 만들었으므로 R2에서는 반복하지 않음):

```text
AFTER_UUID_MUTATION

reference_rows=3
orphan_reference_rows=3

AFTER_REIMPORT
partner_code=000011111111
old_server_key_rows=0
new_server_key_rows=1

```

R2는 사용자 지시에 따라 DB 직접 INSERT/UPDATE로 표본을 만들지 않았다. 관리자 삭제 API → 정본 재적재 → 복구 확인의 실 경로는 현재 R1 격리 서비스와 정본 XLSX 부재로 실행하지 못했다.

### RED-D — 파일 YES가 기존 SUSPENDED를 활성화하지 않아야 함

기존 회귀 테스트 `기존_status는_파일이_YES여도_되살리지_않고_credit_limit_빈칸은_null()`을 수정 전 실행했으며 통과했다. 이 테스트는 `status` 축과 `is_deleted` 축을 섞지 않는 보호 게이트다.

## 5. 새로 가능해진 상태/조합 점검

단위 테스트로 다음 조합을 밟았다.

| 상태 | 결과 |
|---|---|
| 활성행 + 등록일자 있음 | 등록일자 자정으로 `createdAt` 교정 |
| 활성행 + 등록일자 없음 | 기존 `createdAt` 유지 |
| 삭제행만 존재 | 같은 행 복원, UUID 유지 |
| 활성행과 삭제행 동시 존재 | 활성행 우선, 삭제행 복원하지 않음 |
| 삭제행 + 파일 YES | `is_deleted`만 복원, 기존 `status` 의미 보존 |

실 API의 RED-C 및 연속 적재 RED-B/GREEN은 운영 산출물 부재로 미수행이다. DB 직접 조작으로 대체하지 않았다.
