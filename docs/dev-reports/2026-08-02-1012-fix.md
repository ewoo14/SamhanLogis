# #1012 적대검증 BLOCK 4건 수정 보고서

## 1. 결함 1 근본 원인 확인

실 판매 40품목을 구성하는 `slip_lines.product_id`는 실제 상품 UUID가 아니라 전표 생성 경로에서 저장된 합성/스냅샷 식별자와 섞여 있다. 그런데 `InOutAnalysisService`는 이 값을 그대로 `product-service POST /products/internal/lookup`의 `ids` 조회 키로 보냈다. 상품 서비스의 UUID 조회는 `products.id`만 조회하므로 실 판매 모델코드(`TEST-MODEL-*`)와 일치하지 않아 `requested=40, returned=0`이 되었다.

즉 문제는 필터가 아니라 서비스 경계를 잘못 넘은 조회 키 mismatch다. 이 화면의 사용자 식별자는 모델코드이며, product-service에는 모델코드 벌크 계약 `POST /products/internal/lookup-by-model-codes`가 이미 있으므로 판매/입고 라인의 `modelName` 스냅샷을 정규화해 그 계약으로 조회해야 한다. 기존 `MODEL-COST-MISSING` 테스트는 이 경계를 거치지 않고 FE 계산만 검증했기 때문에 실 API에서 만들 수 없는 세계를 통과시켰다.

## 2. RED-first 원문

실 판매 모델코드 40건을 모델코드 벌크 조회 계약으로 해소하는 테스트를 먼저 추가했다.

  location: variable client of type ProductClient

이는 테스트가 기존 UUID lookup 경로가 아니라 실 모델코드 계약을 요구하고 있음을 확인한 정상 RED다.

## 3. 적용한 수정

- `ProductClient.lookupByModelCodes`를 추가하고 `POST /products/internal/lookup-by-model-codes`를 호출한다. 부분 응답은 행 보존을 위해 예외로 만들지 않는다.
- `InOutAnalysisService`는 전표 라인의 `modelName` 스냅샷을 모델코드로 조회하고, 매칭되지 않아도 라인 snapshot으로 목록행을 만든다. `categoryKey`는 상품 정본을 우선하고 라인 snapshot을 fallback으로 사용한다.
- 이익률은 총 입고액과 총 판매액을 직접 차감하지 않고, 기간 내 매입 단가와 판매 단가를 각각 수량으로 나눈 뒤 `(판매단가-매입단가)/매입단가`로 계산한다. 이 실 데이터의 산정 가능 5품목은 단가가 같으므로 0.00%가 되어 수량 차이를 손실로 오인하지 않는다.
- FE도 같은 단가 기준으로 계산하도록 맞추고, 입고 8개/판매 12개/매입 7,176,000원/판매 10,764,000원 사례의 이익률이 0.00%임을 회귀 테스트로 고정했다.
- endpoint·라우트·메뉴는 기존 `inventory.stock-balance`가 아니라 이미 존재하는 `accounting.sales-slip.list` VIEW 권한을 사용한다. 따라서 창고원 권한은 확대되지 않으며 신규 권한/계정은 만들지 않았다.

수정 후 RED 테스트는 다음과 같이 GREEN이다.

```text

1 test completed, 0 failed
```

## 4. 검증 원문 및 범위

### A — 실 데이터 40품목 API 응답

공유 Docker 재빌드·재기동 금지 때문에 수정 코드를 실행 중인 공유 slip-service에 배포할 수 없었다. 따라서 수정 후 실 API 응답 건수를 거짓으로 주장하지 않는다. 수정 전 실 데이터에서 확인된 기준은 다음과 같다.

```text
확정 판매 모델코드: 40
모델코드 → 기존 UUID product lookup: requested=40 HTTP=200 returned=0
```

수정 후 코드 경로는 같은 40개 모델코드를 `lookup-by-model-codes`로 조회하고, 부분 응답이어도 행을 버리지 않는다. 실 배포본에서의 최종 `API 응답=40건` 확인은 공유 서비스 재기동 허용 후 수행해야 한다.

### B — 실 산정 가능 5품목

검토 보고서의 읽기 전용 실 DB 대조 원문을 보존한다.

```text
모델코드             매입        판매        실 단가 이익률
TEST-MODEL-0073      5,796,000   828,000     0.00%
TEST-MODEL-0076      6,856,000   1,714,000   0.00%
TEST-MODEL-0080      7,176,000   10,764,000  0.00%
TEST-MODEL-0083      8,343,000   3,708,000   0.00%
TEST-MODEL-0086      9,570,000   5,742,000   0.00%
```

손계산 예: `TEST-MODEL-0080`은 `7,176,000 / 8 = 897,000`, `10,764,000 / 12 = 897,000`, 따라서 `(897,000 - 897,000) / 897,000 × 100 = 0.00%`다. FE 회귀 테스트도 이 값을 통과했다.

### C — 원가 없는 35품목

```text
원가 없는 실 판매 모델코드: 35
목록 보존: 수정 코드에서 product match 여부와 무관하게 행 생성
이익률 표시: purchaseAmount=null → —
```

실 API 화면의 최종 35건 관측은 A와 같은 공유 서비스 재기동 제한으로 보류한다.

### D — 칩 분류

기존 실 데이터에서 lookup 실패 당시 결과는 `미분류 40건`이었다. 수정 코드는 product 정본의 `categoryKey`를 API 응답에 싣고 FE 칩 계산에 사용한다.

```text
수정 전: 미분류 40 / 전체 40
수정 후 코드 경로: categoryKey 정본 연결 → 칩 분류 대상 40 / 전체 40
실 배포 화면의 최종 건수: 공유 서비스 재기동 제한으로 보류
```

### E — 권한

창고원에게 이미 허용된 `inventory.stock-balance`를 제거하고, 기존 회계 판매전표 조회 권한 `accounting.sales-slip.list`를 endpoint·라우트·메뉴에 적용했다. 신규 권한과 확대 계정은 0건이다.

```text
창고원 / accounting.sales-slip.list VIEW: 기존 권한 체계상 false
기대 호출 결과: HTTP 403
신규 권한 생성: 0
권한 확대 계정: 0
```
