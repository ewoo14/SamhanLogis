# #1069 S20 SOL fix 지시서 — 거래처 주문 전환의 BUNDLE 부모 영속 우회

## 판정과 재현 난이도

**실 사용자 경로에서 재현 가능한 결함 1건. 현 HEAD `8671a7d527aea8ade2bbe14a749929692d38d603`은 머지 비권고다.**

- **F1 — 거래처 주문 상세의 `판매전표 전환` 경로가 BUNDLE 부모를 구성품으로 전개하지 않고 `slip_lines.product_id`에 그대로 저장한다.**
- 재현 난이도: **낮음**. 경합이나 타이밍 조작이 필요 없다. BUNDLE 라인이 있는 거래처 주문을 열고, 본사 데스크톱의 전환 모달에서 수량과 출고 창고를 선택한 뒤 `판매전표로 전환`을 누르는 정상 조작이다.
- 사용자 도달 근거:
  - `partner-order-service`는 BUNDLE 주문을 정상 생성·조회한다. `PartnerOrderConfirmServiceTest`에도 `productType="BUNDLE"` 주문 표본이 있고, 지정 테스트 7/7이 통과했다.
  - `SalesPartnerOrderDetailPage`는 주문 라인의 `productType`을 재고조회에서만 제외한다. 전환 모달은 모든 잔여 라인에 전환수량 입력을 노출하고 BUNDLE을 거르지 않는다.
  - `PartnerOrderConvertService`는 선택 라인의 모델코드를 `productCode`로 `/api/v1/slips/from-partner-order`에 전달한다.
  - `SlipPublishService.resolveLines`는 `lookupByModel`로 얻은 `ProductSummary.productType()`을 검사하지 않고 BUNDLE의 `id`를 `ResolvedLines.Entry`에 넣으며, `toEntityLines`가 이를 `SlipLine.create*`로 직접 생성한다.

S19의 접근성 결함 자체는 닫혔다. pending 중 가시 문구·`aria-label="세트 구성품 반영 중"`·저장 차단이 유지되고, 종료·유휴에서는 가시 문구와 접근성 이름이 함께 제거된다. 프론트 지정 3파일은 100/100, slip-service 지정 5 suite는 80/80이 통과했다. 읽기 전용 DB 기준선도 `OUTBOUND DRAFT` 2,387행 / 2,171전표 / `line_total` 2,902,645,781원, 권위 BUNDLE 344개와 교차 0행으로 재현됐다. 이 통과들은 아래 별도 쓰기 경로를 포함하지 않아 F1을 닫지 않는다.

## 1. 좌표

### 사용자 조작 표면

- `clients/desktop/src/renderer/routes/SalesPartnerOrderDetailPage.tsx:1644-1805`
  - `판매전표 전환` 모달이 `(query.data?.lines ?? [])` 전부를 순회한다.
  - 비활성 조건은 잔여수량뿐이고 `line.productType === 'BUNDLE'` 제외가 없다.
  - 사용자가 전환수량·출고 창고를 입력하면 `convertMutation.mutate`가 BUNDLE 라인도 정상 제출한다.
- `services/partner-order-service/src/main/java/com/samhanair/logis/partnerorder/service/PartnerOrderConvertService.java:119-216`
  - 선택 라인의 `productId` 존재·잔여수량·재고만 검증한다.
  - `line.getModelName()`을 `productCode`로 payload에 넣으며 BUNDLE 판정 또는 구성품 전개가 없다.

### BUNDLE 부모 영속 좌표

- `services/slip-service/src/main/java/com/samhanair/logis/slip/publish/SlipPublishService.java:762-791`
  - `productClient.lookupByModel(l.productCode())` 결과의 `summary.productType()`을 버린다.
  - BUNDLE `summary.id()`가 `ResolvedLines.Entry.productId`로 그대로 들어간다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/publish/SlipPublishService.java:1072-1090`
  - `ResolvedLines.toEntityLines`가 위 BUNDLE ID를 `SlipLine.createFromVatInclusive` 또는 `SlipLine.create`로 직접 엔티티화한다.
- 같은 resolver를 공유하는 발행 표면:
  - `publishFromEstimate`: `SlipPublishService.java:121-155`
  - `publishFromPartnerOrder`: `SlipPublishService.java:205-238`
  - `publishFromOrdersMerge`: `SlipPublishService.java:305-335`

비교 기준은 이미 닫힌 네 경로다. 일반 생성·라인추가는 `SlipService.addSlipLinesExpanded`로 전개하고, 판매전표 전체수정과 모바일 판매전표 생성은 BUNDLE 부모를 명시적으로 거부한다.

## 2. 불변식

1. BUNDLE 품목은 판매전표 생성 방식과 출처에 관계없이 `slip_lines.product_id`로 영속될 수 없어야 한다.
2. 거래처 주문의 BUNDLE 라인을 `판매전표 전환`하면 사용자에게 명시적으로 거부되거나 구성품으로 전개되어야 하며, 부모 BUNDLE 자체 저장은 허용되지 않아야 한다.
3. 단건 주문 전환·다중 주문 병합 전환·견적 발행이 공유하는 라인 해석 경로에 동일 불변식이 적용되어야 한다.
4. 정상 SINGLE 주문 전환은 기존과 동일하게 재고 예약, 전표 발행, 전환수량 누적까지 완료되어야 한다. BUNDLE 방어가 정상 SINGLE을 오차단하면 안 된다.
5. BUNDLE 처리 실패 시 slip 저장과 주문의 converted 수량 누적이 모두 없어야 하고, 선행 재고 예약이 있었다면 기존 보상 계약이 유지되어야 한다.
6. 이번 S19 접근성 상태 계약, 화면 구성품과 저장 구성품 일치, `#1063` 빈행 규약, 정상 SINGLE 기준선은 회귀하면 안 된다.

구현 수단은 지정하지 않는다. 어느 계층에서 거부·전개할지보다 위 결과 불변식과 세 발행 표면의 일관성이 판정 기준이다.

## 3. 양방향 RED

### RED-B — 결함 재현

- BUNDLE 라인이 있는 거래처 주문 상세에서 `판매전표 전환`을 실행한 뒤 생성 전표의 활성 라인에 그 BUNDLE `productId`가 존재하면 RED.
- `/api/v1/slips/from-partner-order`에 BUNDLE 모델코드 라인을 보내 `SlipPublishService`가 BUNDLE ID의 `SlipLine`을 만들거나 `slipRepository.save*`까지 도달하면 RED.
- 다중 주문 병합 발행 또는 견적 발행이 같은 `resolveLines` 우회로 BUNDLE 부모를 저장하면 RED.
- BUNDLE 처리 실패 후 주문 라인의 `convertedQuantity`가 증가하거나 재고 예약이 남으면 RED.

### RED-A — 반대급부 보존

- 정상 SINGLE 거래처 주문의 단건 전환 또는 병합 전환이 새 방어에 걸리면 RED.
- 정상 SINGLE 발행에서 기존 VAT 포함 단가·수량·`sourceOrderLineId`·`categoryKey` snapshot이 바뀌면 RED.
- BUNDLE을 구성품으로 전개하는 방식을 택한 경우 화면/주문에서 선택한 수량과 기존 BundleExpander의 가격 배분 결과가 저장 구성품과 다르면 RED.
- BUNDLE을 명시 거부하는 방식을 택한 경우 사용자가 원인을 알 수 없거나 재고 예약 보상이 누락되면 RED.
- 판매전표 입력 화면 pending 중 접근성 이름 또는 저장 차단이 사라지거나, 종료·유휴에 접근성 이름이 다시 남으면 RED.
- `#1063` 초기 5행·마지막 행 1개 증식·trailing 빈행 저장 제외 규약이 깨지면 RED.

## 4. 범위 밖 / 안 본 범위

- 범위 밖: `#1057`, `#1066`, `#1075`, `#1080` 파일, 견적 가격 정책 재설계, 세트 마스터 데이터 변경, Docker 재빌드·재배포·중지, DB write, 전체 게이트.
- 안 본 범위: 실제 DB write를 동반한 거래처 주문 전환 실행, 실제 모바일 기기, Docker 배포본과 작업 트리 HEAD 동일성, INBOUND 전표, 분개·이동 화면.
- 읽기 전용으로만 확인한 범위: 코드 경로, 지정 단위 테스트, 실 DB 집계 및 BUNDLE 교차 여부.
- 수정 파일은 결함 좌표와 직접 회귀 테스트에만 한정한다. 범위 밖 트랙 파일을 함께 손대지 않는다.

## 5. 커밋 전 좁은 검증 명령

결함을 고정하는 테스트는 최소한 다음을 포함해야 한다.

1. BUNDLE 거래처 주문 단건 전환 → 부모 BUNDLE 영속 0, 실패 시 예약 보상·converted 미증가.
2. BUNDLE 포함 병합 전환 → 부모 BUNDLE 영속 0.
3. `SlipPublishService`의 세 발행 진입점 중 공유 resolver를 지나는 BUNDLE → 부모 영속 0.
4. 정상 SINGLE 단건·병합 전환 → 기존 성공 계약 유지.
5. S19 a11y pending/종료 상태와 판매전표 화면·저장·빈행 회귀 유지.
