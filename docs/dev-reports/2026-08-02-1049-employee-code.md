# #1049 담당자코드 원천 확인

- `docs/migration/ecount-data/`에는 안내 문서 2개, `.gitignore`, `raw/.gitkeep`만 있으며, 이 워크트리에는 직원 원본 데이터 파일이 없다.
- 이카운트 직원 임포터의 필수 원본 컬럼은 `사원(담당)코드`이며, 그 값을 staging의 `employee_code`와 대상 `employees.ecount_code`에 그대로 저장하도록 구현돼 있다.
- 주 저장소의 ignored raw 디렉터리에도 거래처·품목 CSV만 있고 직원 CSV는 없어, 원본 `사원(담당)코드` 실제값 표본은 파일에서 확보할 수 없다.
- 실행 중 `user_db`의 `staging.ecount_employee_raw`는 전체 0건이므로 DB staging에서도 `사원(담당)코드` 표본을 확보할 수 없다.
- `employees` 24개 컬럼을 전수 확인했으며 사번·사원번호 전용 컬럼은 없고, 별도 식별자 후보 컬럼은 `account_id`, `login_id`, `email`, `phone`, `ecount_code`다.
- `employees` 전체 25건에서 채워진 건수는 `account_id` 25건, `login_id` 25건, `email` 9건, `phone` 9건, `ecount_code` 0건이다.
- `employees`는 전체 25건, 활성 24건, soft-delete 1건이며, 전체 퇴사일 도래 행 1건은 soft-delete 행이고 활성 퇴사자는 0건이다.
- `employees.ecount_code`는 활성 여부와 무관한 전체 25건에서 채워진 행이 0건이다.
- 이카운트 인사카드·급여 임포터도 각각 원본 첫 컬럼 `사원번호`를 읽어 `employees.ecount_code`와 대조하므로, 저장소가 판정한 동일 원천은 직원 마스터의 `사원(담당)코드`/인사·급여의 `사원번호`다.
- #1020 조사 문서는 당시 활성 24건 중 담당자-계정 참조 파손 16건을 확인했고, 그 16건 모두 `employees.login_id = accounts.login_id`인 단일 활성 계정 후보가 있었다고 기록한다.
- 현재 DB 재확인에서는 활성 직원 24건 모두 `login_id`가 정확히 하나의 미삭제·활성 `accounts.login_id`와 일치한다.
- 현재 활성 직원 24건의 `account_id`도 모두 실재 계정과 연결되고 같은 `login_id`를 가지므로, #1020의 16건 참조 파손은 현재 DB에서는 해소돼 있다.
- 명시 예시인 `dev_master`도 직원 1건·계정 1건이 같은 `login_id`로 존재하며 현재 계정 연결도 일치한다.
- 실제 unique는 `ecount_code IS NOT NULL AND is_deleted=false`인 partial unique이므로 활성 24건은 제약 대상이고 soft-delete 1건은 제외된다.
- 이카운트 직원·인사카드·급여 staging 3종과 대상 `employee_cards`·`payroll_employees`는 모두 0건이어서 실제 코드 표본 5개는 어느 보조 경로에서도 확보되지 않는다.

## 결론

**부여 가능한 실제 원천은 없다:** 저장소가 정한 이카운트 원천 컬럼은 직원 마스터 `사원(담당)코드`와 인사·급여 `사원번호`지만 원본·staging·대상 값이 모두 없으며, 2·3에서 확인된 후보는 전 직원에 채워져 계정과 단일 일치하는 `employees.login_id`/`accounts.login_id`와 전 직원에 채워진 계정 연결 컬럼이다.

- 실제 이카운트 코드 표본: 0개(직원 원본 파일과 적재 행이 없어 요청된 5개를 제시할 수 없음).
- 개인정보 값과 내부 식별자 값은 기록하지 않았고, 모든 DB 확인은 읽기 전용 트랜잭션 또는 서버 읽기 전용 옵션으로 수행했다.
