# PR #1124 S32 — 출고 마감시각 게이트 Clock 날짜 판정 수정

## 결함 원인

`OutboundCutoffGuard`는 `Clock`을 주입받고도 당일 여부를 `LocalDate.now(clock.getZone())`으로 판정하고 있었습니다. 이 호출은 zone만 주입 시계에서 가져오고 날짜·시각은 실제 시스템 시계에서 읽습니다.

테스트는 `TODAY = 2026-08-08`과 `Clock.fixed(2026-08-08의 마감 초과 시각, KST)`를 사용합니다. 2026-08-08에는 우연히 실제 KST 날짜와 고정 날짜가 같아 green이었지만, 2026-08-09가 되면서 첫 날짜 관문이 조기 return하여 마감 초과 예외가 사라졌습니다. 초기 재현 원문은 다음과 같습니다.

```text
18 tests completed, 11 failed
```

동일 계열의 `passesCutoffFor`에도 같은 문제가 있었습니다.

PM 진단을 검증한 결과 셋째 원인은 확인되지 않았습니다. 마감 시각 비교 자체는 이미 `LocalTime.now(clock)`을 사용하고 있었고, 실패는 두 날짜 비교 호출에서 발생했습니다.

## 고친 내용

`OutboundCutoffGuard.java`의 두 호출을 다음과 같이 수정했습니다.

- `LocalDate.now(clock.getZone())` → `LocalDate.now(clock)` — 본 전표의 오늘 여부
- `LocalDate.now(clock.getZone())` → `LocalDate.now(clock)` — 대체 출고 후보의 컷오프 통과 여부

운영 `Clock`은 실제 KST 시스템 시계이므로 운영 동작은 유지됩니다. 테스트에서는 fixed `Clock`의 날짜가 오늘의 기준이 되어 실행 날짜에 의존하지 않습니다. `closedDateGuard == null`인 2-인자 경로도 기존처럼 컷오프 판정을 먼저 수행하므로 차단 능력을 유지합니다.

## 양방향 RED 결과

초기 결함 재현:

```text
./gradlew :services:slip-service:test --tests '*OutboundCutoffGuardTest*'
18 tests completed, 11 failed
```

수정 후:

```text
./gradlew :services:slip-service:test --tests '*OutboundCutoffGuardTest*'
BUILD SUCCESSFUL in 14s
```

해당 테스트는 다음을 동시에 검증합니다.

- RED-A: 2-인자·마감 초과 및 4-인자·마감 초과가 `BusinessException(CONFLICT)`를 던짐
- RED-B: 2-인자·마감 전 및 미래 날짜가 통과하고, 3-인자·마감 전도 통과함
- `closedDateGuard == null`: 2-인자 경로와 명시적 3-인자 null 경로 모두 마감 초과를 차단함
- `closedDateGuard != null`: 4-인자 대체 날짜 계산 경로가 익일/후속 날짜 계약을 유지함

## 4-(a) Clock 계열 sweep

`services/slip-service/src/main/java`에서 `Clock`을 보유한 클래스와 인자가 없는 `now()` 호출을 대조했습니다.

| 파일 | 호출 | 이번 라운드 | 근거 |
|---|---|---|---|
| `mobile/service/MobilePartnerOrderService.java` | `LocalTime.now()` | 보류 | 주문번호용 시각 문자열 생성이며 이번 출고 마감 게이트 판정과 무관. 운영 Clock 주입을 활용하는 별도 후속 범위 |
| `publish/SlipPublishService.java` | `LocalTime.now()` | 보류 | 발행 시각 문자열 생성이며 이번 게이트 판정과 무관. 운영 동작 변경을 피하기 위해 별도 범위로 남김 |
| `service/SlipService.java` | `LocalTime.now()` | 보류 | 전표 번호용 시각 문자열 생성이며 이번 게이트 판정과 무관. 별도 시간 일관성 sweep 대상 |

그 외 `Clock` 보유 클래스의 현재 시각 사용은 `LocalDate.now(clock)`, `LocalTime.now(clock)`, 또는 `LocalDateTime.now(clock)` 형태였습니다. `OutboundCutoffGuard`의 두 호출은 수정 후 이 목록에서 제외됩니다. 이번 라운드에서는 다른 기능의 시각 생성 semantics를 바꾸지 않았습니다.

## 4-(b) 조합별 결과

| 생성자/guard | 마감 전 | 마감 후 | 실행 결과 |
|---|---|---|---|
| 2-인자 (`closedDateGuard=null`) | 당일 통과 | 당일 `CONFLICT` | GREEN |
| 2-인자 (`closedDateGuard=null`) | 미래 날짜 통과 | 해당 조합은 미래 날짜 통과로 확인 | GREEN |
| 3-인자 (`closedDateGuard!=null`) | 당일 통과 | 당일 `CONFLICT`, 익일/후속 후보는 날짜 가드에 따라 안내 | GREEN |
| 3-인자 (`closedDateGuard=null`) | — | 당일 `CONFLICT` | GREEN |

추가한 테스트:

- `threeArgumentGuard_beforeCutoff_allowsToday`
- `threeArgumentGuard_nullClosedDateGuard_afterCutoff_stillBlocksToday`
