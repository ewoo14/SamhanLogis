# PR #1127 R3 SOL 재수렴 — Hibernate dirty 판정 전환 검증

검증 좌표는 `feat/978-fast-path-carryover` / `61935ce322b291b14f25edea20deccb53e96cfd6`이다. 코드·테스트는 수정하지 않았고, 실 DB·실 Google Sheets·운영 Docker에는 접근하지 않았다. 테스트는 격리된 Testcontainers PostgreSQL과 `@MockBean GoogleSheetsClient`만 사용했다.

## 판정

**도달 가능한 데이터 정합성 결함은 발견하지 않았다. 도달 가능한 집계 의미 결함 1건을 발견했다.**

- **[MED, 관측/계약] Product 밖 엔티티만 실제 변경된 행도 `unchanged`로 집계된다.** 쓰기는 정상 실행되고 같은 탭 트랜잭션으로 커밋/롤백되므로 데이터 유실이나 다음 실행 skip은 아니다. 그러나 공개 `SyncSummary.totalUpdated`와 scheduler 로그가 단순히 `updated`라고 노출되고, `unchanged` 역시 Product 한정이라고 명시하지 않아 “이 행에서 DB 변경이 없었다”는 의미로 읽으면 사실과 다르다.
- 커밋 설명의 **“쓰는 필드가 곧 보는 필드”, “양방향 차집합이 구조적으로 0”은 Product의 Hibernate dirty-checkable 영속 속성에 한정해야 사실**이다. 엔티티 밖 writer, `@Transient`, `@Formula`, 컬렉션에는 일반화할 수 없다. 이는 위 집계 결함의 구조적 원인이고, Product scalar/to-one writer의 누락 결함은 이번 라운드에서 찾지 못했다.

사용자 요약의 좌표·구현 방식·`-70/+86`은 사실과 일치한다. 실제 numstat는 서비스 `+46/-70`, 테스트 `+40/-0`, 합계 `+86/-70`이다. 다만 요약에 인용된 구조적 완전성 주장은 위 범위 한정 없이 사용하면 사실이 아니다.

## (a) 구조적 완전성의 실제 경계

### 1. Product 밖 writer 전수와 집계 관계

| 대상 | 실행 위치/조건 | Product dirty 밖에서만 바뀌는 도달 가능 시나리오 | 현재 집계 |
|---|---|---|---|
| `PriceHistory` 현재 단가 | row마다 `upsertPriceHistory(..., 2026-04-01, ...)` | Product 가격은 시트와 같고 같은 effective-date history만 잘못된 경우 | history는 수정되지만 `unchanged++` |
| `PriceHistory` 인상 전 단가 | 탭 후반 `syncBeforeIncreasePriceHistory(..., 2000-01-01, ...)` | Product/current history는 같고 인상 전 history만 잘못된 경우 | `updated/unchanged` 어느 쪽에도 반영되지 않음 |
| `ProductEstimateExposure` | row 판정 뒤 `upsertSheetExposure` | 동일 Product 두 행의 시트 순서만 바뀌어 `display_order`만 변경 | 각 Product는 `unchanged`; exposure 변경 전용 카운터 없음 |
| `ProductSpec` | row 판정 뒤 `loadSpecsForProduct` → `upsertSpec`/soft-delete | 가격·분류 등 Product 값은 같고 spec 값/순서/존재만 변경 | Product는 `unchanged`; `specsLinked`는 유효 spec 처리 수이지 실제 변경 수가 아님 |
| `Classification` master | Product 조회/스냅샷 전 `resolveClassifications` → `findOrCreateClassification` | `classificationManual=true`라 Product FK는 보존되지만 새 분류 master가 필요한 이름 | master는 생성되지만 Product는 `unchanged` |
| `BundleComponent` | 별도 `syncComponentTab` | 링크/수량/종류/soft-delete만 변경 | Product `updated`와 분리; `linked`, `softDeleted`, `bundlesMarked`로 별도 집계하므로 문제 없음 |
| `ProductEstimateExposure` soft-delete | Product soft-delete 뒤 `softDeleteExposures` | exposure도 함께 soft-delete | Product의 `softDeleted`가 대표하므로 별도 `updated` 누락으로 보지 않음 |

핵심 실행 순서는 다음과 같다.

```text
ProductSheetSyncService.java:1302  ProductMutationSnapshot.capture(entityManager, p)
ProductSheetSyncService.java:1364  upsertPriceHistory(...)
ProductSheetSyncService.java:1367  if (before.changed()) updated++ else unchanged++
ProductSheetSyncService.java:1374  upsertSheetExposure(...)
ProductSheetSyncService.java:1378  loadSpecsForProduct(...)
```

따라서 외부 엔티티 쓰기를 건너뛰는 결함은 아니다. 문제는 공개 결과의 `updated/unchanged`가 **Product 엔티티 변경 여부**인 데 비해 Javadoc은 “tab 별 inserted/updated/softDeleted/skipped 집계”라고만 하고, scheduler와 admin API도 이 값을 한정 없이 노출한다는 점이다.

#### 재현 절차 — 외부 엔티티만 변경

코드 수정 없이 정적으로 재현 가능한 최소 상태 전이는 다음과 같다.

1. 기존 Product의 `release_price`/`delivery_price`를 시트 값과 같게 둔다.
2. 같은 Product의 `price_history` 현재 effective-date 가격만 다른 값으로 둔다.
3. 같은 시트 row로 `syncAll()`을 실행한다.
4. `p.changePrices()`는 Product를 dirty로 만들지 않지만 `upsertPriceHistory().changePrices()`는 history를 변경한다. 그 뒤 `before.changed()`는 Product만 보므로 `updated=0, unchanged=1`이 된다.

동일하게 Product 값은 유지한 채 두 행의 순서만 바꾸면 exposure `display_order`만 저장되고 두 행은 `unchanged`가 된다. 사용자 금지사항에 따라 임시 테스트 코드나 실 DB 상태를 만들지 않았고, 아래 실행 원문으로 실제 분기 순서와 공개 계약을 확인했다.

### 2. JPA/Hibernate 속성 종류별 경계

- **현재 `Product`에는 `@Transient`, `@Formula`, `@OneToMany`, `@ManyToMany`, `@ElementCollection`가 없다.** 현재 sync writer가 변경하는 Product 값은 scalar/enum/`BigDecimal`/`@ManyToOne`이고 이들은 persister property 배열에 포함된다.
- **`@Transient`**는 Hibernate persister property 배열 자체에서 제외되므로 `getPropertyValues()`/`findDirty()`가 보지 않는다.
- **`@Formula`**는 persister에는 읽기 속성으로 나타날 수 있지만 updateable column이 없다. `findDirty()`는 `propertyColumnUpdateable`을 사용하므로 formula-only 변화는 이 판정의 변경으로 간주할 수 없다.
- **컬렉션**은 이 방식의 완전성 근거가 아니다. Hibernate는 collection wrapper/`CollectionEntry`의 dirty 상태를 별도 flush 단계에서 처리한다. `EntityPersister.findDirty(currentState, loadedState, ...)`만 호출해 컬렉션 원소 변화까지 Product property dirty로 환산한다고 볼 수 없다. 현재 Product에 컬렉션 매핑이 없어 현행 도달 결함은 아니다.
- **`@ManyToOne`**인 `category`, `catL/M/S`는 Product property 배열에 들어가고 Hibernate association type 비교를 받는다. 현재 2회 실행 회귀 테스트에서 가짜 dirty는 관측되지 않았다.

Hibernate 6.5.3 실제 구현도 `AbstractEntityPersister.findDirty()`가 `propertyColumnUpdateable`을 `DirtyHelper.findDirty()`에 전달하고, 각 dirty-checkable property의 `Type.isDirty()`를 호출함을 `javap`로 확인했다.

### 3. `getLoadedState() == null`

이 구현은 `entry == null || entry.getLoadedState() == null`이면 `unchanged`로 조용히 집계하지 않고 다음 예외를 던진다.

```text
IllegalStateException: Product must be a managed existing entity: <id>
```

- 신규 Product는 `existing.isEmpty()` insert 분기로 가므로 snapshot을 만들지 않는다.
- detached/비영속 기존 Product가 들어오면 해당 탭이 실패하고 per-tab 트랜잭션이 롤백된다. fail-fast라서 오집계보다 안전하다.
- 현재 운영 진입점은 `syncAll()` → 주입된 `self.syncTab(...)`이고 `syncTab`은 `@Transactional`이다. repository 조회 Product는 managed 상태다. scheduler/admin controller도 `syncAll()`만 호출한다.
- `syncTab`은 public이며 propagation 기본값이 `REQUIRED`이므로, 미래의 활성 트랜잭션 caller가 이미 dirty인 Product를 같은 영속성 컨텍스트에 둔 채 호출하면 sync writer와 무관한 기존 dirty까지 `updated`로 셀 수 있다. 현재 production call graph에는 그런 caller가 없어 잠재 경계로만 기록한다.

## (b) 과잉 감지

### BigDecimal scale

현재 Hibernate는 `org.hibernate.orm:hibernate-core:6.5.3.Final`이다. `BigDecimalJavaType.areEqual()` 바이트코드를 직접 확인한 결과 `BigDecimal.equals()`가 아니라 `compareTo() == 0`을 사용한다. 따라서 `606000`과 `606000.00`만의 scale 차이는 dirty가 아니다.

```text
> javap -classpath hibernate-core-6.5.3.Final.jar -c org.hibernate.type.descriptor.java.BigDecimalJavaType
public boolean areEqual(java.math.BigDecimal, java.math.BigDecimal);
  13: aload_1
  14: aload_2
  15: invokevirtual java/math/BigDecimal.compareTo
  18: ifne 25
  21: iconst_1
```

### audit timestamp

`Product`가 상속한 `BaseEntity.modifiedAt/modifiedBy`도 persister property에는 포함된다. 그러나 Spring Data auditing은 flush의 `@PreUpdate` 시점에 이 값을 바꾸며, 현재 `before.changed()`는 flush 전에 호출된다. 따라서 audit timestamp 자체가 매 row마다 선행 변경되어 항상 dirty가 되는 흐름은 아니다. 실제 동일 입력 연속 실행도 이를 부정한다.

## (c) Hibernate 내부 API와 트랜잭션

`SessionImplementor`, `EntityEntry`, `EntityPersister`는 Hibernate SPI/내부 계약이며 JPA 표준이 아니다. 현재 고정 조합 Spring Boot 3.3.5 + Hibernate 6.5.3.Final에서는 48개 sync 테스트와 전체 suite가 통과했지만, Hibernate minor/major 업그레이드에서 unwrap 대상, persistence-context entry 표현, `loadedState` 의미, `findDirty` signature/dirty 규칙이 바뀌면 컴파일 실패뿐 아니라 조용한 판정 변화도 가능하다. 따라서 현재 게이트 결함은 아니지만, 버전 업그레이드 시 이 클래스의 동일 입력·ECOUNT 승격·롤백 재시도 테스트를 필수 호환성 게이트로 두어야 하는 고결합 지점이다.

현재 production 진입에서 snapshot이 트랜잭션 밖에서 실행될 여지는 찾지 못했다. `syncAll()` 자체는 비트랜잭션이지만 반드시 `self.syncTab()` 프록시를 호출하고, `syncTab`은 `@Transactional`이다. scheduler와 controller도 `syncTab`을 직접 호출하지 않는다. 다만 public `syncTab`을 Spring 프록시가 아닌 직접 생성 객체/동일 클래스 self-invocation으로 호출하는 미래 경로는 `entry == null` fail-fast 대상이다.

## (d) R1 롤백 재시도와 인메모리 상태

운영/테스트 source grep 결과 D-1의 `lastKnownRowHash`와 관련 hash transaction state는 0건이다.

