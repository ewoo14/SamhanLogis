# R80 좁은 진단 — 최근단가와 DC/판매가 우선순위

- 대상: PR #1057 · 이슈 #874 · HEAD `09adade13`
- 역할: 2차 적대검증자(SOL)
- 성격: 진단 전용. 코드 수정, git 쓰기, DB 직접 쓰기·삭제, Docker 재빌드·재배포·중지를 하지 않았다.
- 결론: R79의 `561,600` 재현은 R78 코드 결함이 아니라 R76 F1 결함 시점에 저장된 최근단가 데이터가 설계된 우선순위로 다시 제안된 것이다. 사용자가 올바른 단가를 직접 입력해 정상 저장하면 같은 `(거래처, 품목)` 행이 새 값으로 교정된다.

## 1. 최근단가와 DC/판매가의 의도된 우선순위

### 코드로 확정한 순서

품목을 선택하거나 교체할 때의 최종 순서는 다음과 같다.

1. **사용자 직접입력(`USER`)**: `clients/desktop/src/renderer/utils/priceSourceRules.ts:20-25`는 `USER`만 자동채움 불가침으로 둔다. 단가 입력 시 `clients/desktop/src/renderer/routes/SlipFormPage.tsx:736-747`이 `priceSource='USER'`로 바꾸고 최근단가 표시 상태를 지운다.
2. **고정DC 또는 자격 있는 전역DC**: `clients/desktop/src/renderer/utils/slipDiscount.ts:26-41`에서 고정DC를 먼저 계산하고, 고정DC가 없을 때만 `hasVariableDiscount === true`인 홈/상업 멀티 품목에 전역DC를 계산한다. `clients/desktop/src/renderer/routes/SlipFormPage.tsx:873-881`은 그 결과의 `source`가 `FIXED` 또는 `GLOBAL`이면 `hasAuthoritativeDiscount=true`로 판정하여 최근단가 hit보다 할인 완료 단가를 선택한다.
3. **최근단가**: DC 결과가 `NONE`이고 최근단가 hit가 있을 때 `clients/desktop/src/renderer/routes/SlipFormPage.tsx:874-893`이 기억값을 선택하고 `priceSource='REMEMBERED'`로 표시한다.
4. **판매가 fallback**: DC 결과가 `NONE`이고 최근단가도 miss이면 같은 파일 `:876-880`에서 `resolvedDcResult.unitPrice`(NONE 결과는 판매가) 또는 `fallbackUnitPrice`를 선택한다. API의 `204 -> null` 계약은 `clients/desktop/src/renderer/api/slip.ts:520-536`이다.

즉 일반식은 **사용자 직접입력 > 유효한 고정/전역DC > 최근단가 > 판매가**다. 변동DC 비대상 품목은 전역DC가 아니라 `NONE`이므로 그 품목에 최근단가 행이 있으면 **최근단가가 판매가보다 이기는 것이 현재 설계**다.

### 설계 근거와 R78 영향

- 가격기억 기능의 원래 결정은 품목 선택 시 hit면 기억값, miss면 판매가를 채우고, `REMEMBERED/CATALOG/USER`로 사용자 override를 구분한다(`docs/dev-reports/2026-07-15-809-partner-product-price-memory.md:26-35`).
- 서버도 화면이 DC/최근단가/사용자 협의가를 반영해 확정한 값을 정본으로 삼고 재계산하지 않는다(`services/slip-service/src/main/java/com/samhanair/logis/slip/service/SlipService.java:270-280`).
- R78은 `hasVariableDiscount` 자격을 계산기에 추가했지만(`clients/desktop/src/renderer/utils/slipDiscount.ts:31-38`), `DC가 있으면 DC, 없으면 최근단가`라는 기존 분기 자체는 유지했다. R78 diff에서도 우선순위 식은 `dcResult`를 비동기 완료값 `resolvedDcResult`로 바꾼 것뿐이고, 기억값 선택 조건은 동일하다.

따라서 이번 현상은 **R78이 새 우선순위를 만든 것이 아니다.** 다만 R76에서는 F1 때문에 해당 품목이 잘못 `GLOBAL`로 분류되어 `561,600`을 저장했고, R78이 그 품목을 올바르게 `NONE`으로 분류한 뒤 기존 최근단가 우선 경로가 그 오염값을 드러냈다. 이 의미에서는 R78이 만든 **새 관찰 표면**이지만, R78의 새 가격 권위 규칙은 아니다.

### R77 RED-B와 이번 사안의 관계

R77 RED-B의 문장은 `docs/dev-reports/2026-08-06-874-r77-fix-directive.md:77-82`에 있다. 이는 **현재 한 라인의 품목 선택 비동기 흐름에서** 정상 DC GET으로 확정한 자격 있는 전역DC 단가를 뒤이어 도착한 최근단가 응답이 덮지 말라는 뜻이다. 현재 코드는 `SlipFormPage.tsx:877-881`의 `hasAuthoritativeDiscount`로 그대로 지킨다.

이번 품목은 R78 이후 `hasVariableDiscount=false`여서 자격 있는 전역DC 결과가 없고(`source='NONE'`), 최근단가는 이전 저장 세션에서 이미 만들어진 값이다. 따라서 **한 편집 안의 응답 순서 보호인 RED-B와, 세션을 건너 저장된 최근단가의 재사용은 다른 사안**이다.

## 2. 최근단가 행이 없는 조합에서 R78 F1 fix가 동작하는가

### 지목한 읽기 전용 표본

- 거래처: `4348703365` — 주식회사 엠엠시스템에어(고영현), 홈멀티 전역DC `48%`
- 품목: `AY047BA1SBA`
- 상품 API 실응답: 판매가 `939,400`, `categoryKey=homemulti`, `fixedDiscountRate=null`, `hasVariableDiscount=false`
- 최근단가 API 실응답: `GET /slips/price-memory?...` HTTP `204`(miss)
- DB 읽기 대조: 이 거래처의 활성 가격기억은 7행이며 `AY047BA1SBA` 조합은 없다.

이 입력은 물리 카테고리는 홈멀티지만 변동DC 비대상이므로 `slipDiscount.ts:31-38`에서 전역DC raw를 `null`, 결과를 `source='NONE'`, 단가 `939,400`으로 만든다. 최근단가도 miss이므로 `SlipFormPage.tsx:876-880`의 최종값 역시 `939,400`이다. 즉 **행이 없는 조합에서는 R78 F1 fix가 깨끗하게 동작한다.**

- 무기억·변동DC 비대상 물리 fallback 품목이 정가를 유지: `clients/desktop/src/renderer/routes/SlipFormPage.test.tsx:624-639`

## 3. 오염된 최근단가 행은 사용자 교정 가능한가

**교정 가능하다. 영구 재생 구조가 아니다.**

1. 사용자가 단가 입력칸에 올바른 값을 입력하면 `SlipFormPage.tsx:736-747`이 그 값을 유지하면서 출처를 `USER`로 바꾼다. 이후 늦은 최근단가 응답도 `SlipFormPage.tsx:865-871, 883-889`의 `USER` 가드 때문에 덮을 수 없다.
2. 저장 payload는 현재 화면 단가를 그대로 `unitPrice`에 넣고 `priceVatInclusive=true`로 보낸다(`SlipFormPage.tsx:1184-1195`). 서버는 이를 다시 DC 계산하지 않고 정본으로 사용한다(`SlipService.java:270-289`).
3. 서버는 그 입력 단가를 가격기억 command로 모으고(`SlipService.java:1563-1580`), 원 전표 커밋 뒤 batch 저장을 예약한다(`SlipService.java:337-351`; `PartnerProductPriceMemoryService.java:172-194`).
4. `(partner_id, product_id)` 충돌 시 SQL은 `unit_price = EXCLUDED.unit_price`로 갱신한다. 최신 `remembered_at`보다 오래된 저장만 막으며, 정상적인 새 저장은 행을 새 단가로 교체한다(`services/slip-service/src/main/java/com/samhanair/logis/slip/price/repository/PartnerProductPriceMemoryBatchRepository.java:46-76`).

실 DB 사실도 이 사슬과 일치한다. 문제 행은 `created_at=2026-08-06 00:25:46`인데 R79 저장 뒤 `modified_at=2026-08-06 03:06:58`, `remembered_at=2026-08-06 03:06:58`로 갱신됐다. 즉 R79가 읽은 값을 다시 저장했을 때도 기존 행은 실제 upsert되었다. 사용자가 그 자리에서 `1,080,000`을 직접 입력해 저장했다면 동일 upsert가 `1,080,000`을 기록한다.

오염 행을 실제로 교정 저장하지는 않았다. 진단 라운드에서 기존 실데이터를 보존하기 위해 코드 사슬, focused 사용자 override 테스트, R79가 남긴 실제 `modified_at` 갱신을 삼각 대조했다. 가격기억 flush는 비동기 fail-soft이므로 일시적 실패/짧은 반영 지연 가능성은 원 설계의 운영 한계지만(`PartnerProductPriceMemoryService.java:172-194`), 성공한 정상 저장이 구값에 영구히 막히는 구조는 아니다.

## PM 전제 대조

PM이 제시한 전제는 틀리지 않았다. 읽기 전용 DB 조회에서 문제 행은 `561,600 / LINE_SAVE / created_at 00:25:46 / modified_at 03:06:58`로 일치했고, 같은 거래처의 R79 신규 세 행도 각각 `1,355,640`, `1,089,000`, `204,000`으로 일치했다. 따라서 `561,600`은 R76 F1 생존 시점에 생성되고 R79가 재조회·재저장한 값이라는 시간 순서 해석이 가장 직접적인 설명이다.
