## 1. 환경별 UUID 차이와 하드코딩

### 확인 원문

```text
infrastructure\.env.example:96:WAREHOUSE_UUID_HQ=11111111-1111-1111-1111-000000000001
infrastructure\docker-compose.local-all.yml:249:      WAREHOUSE_UUID_HQ: 11111111-1111-1111-1111-000000000001
infrastructure\terraform\templates\user_data.sh:186:WAREHOUSE_UUID_HQ=11111111-1111-1111-1111-000000000001
services/slip-service\src\main\resources\application.yml:188:      "[00003]": ${WAREHOUSE_UUID_HQ:11111111-1111-1111-1111-000000000001}
.github\workflows\ci.yml:51:      WAREHOUSE_UUID_HQ: 11111111-1111-1111-1111-000000000001
```

나머지 세 값도 `…0002`, `…0003`, `…0004`로 같은 위치들에 동일하게 복제돼 있다. 그러나 이 값은 이번 로컬 DB에서 우연히 생긴 UUID는 아니다. inventory의 정규 Flyway V2가 네 행을 고정 UUID로 삽입한다.

```text

('11111111-1111-1111-1111-000000000001', 'HQ-001', '본사창고', ...)

('11111111-1111-1111-1111-000000000004', 'VR-001', '가상창고', ...)
```

### 판정

- **정규 V1→V2 Flyway로 만들어진 로컬·회사PC·신규 운영 DB라면 환경별 UUID는 다르지 않다.** 네 UUID는 deterministic seed 계약이다. 따라서 “지금 로컬 DB 값만 하드코딩해서 새 환경은 당연히 다르다”는 주장은 이 저장소의 정규 생성 경로에서는 재현되지 않는다.
- 반대로 이미 별도 방식으로 생성·baseline 처리된 inventory DB, V2 행이 삭제/soft-delete/재등록된 DB, 데이터 복원 시 다른 UUID로 치환된 DB는 값이 달라질 수 있다. 그 경우 현재 검증은 설정을 자동 조정하지 않고 해당 환경의 slip-service를 차단한다. 이 실패는 아래 일회성 DB 기동에서 별도로 재현한다.
- production compose는 UUID를 `.env.production`에서 받지만 `user_data.sh`가 다시 같은 상수를 생성한다. 즉 운영자가 환경별 실제 값을 명시적으로 관리하는 구조가 아니라 **inventory V2 seed가 영구 불변이라는 전제**를 배포 설정 여러 곳에 중복 고정한 구조다.

### UUID가 다른 DB 재현

일회성 DB의 조회 대상 테이블에 설정과 다른 `aaaaaaaa-...-aaa1`~`aaa4` 네 행만 두고 현재 JAR를 기동했다. 아래 원문은 Windows 콘솔의 Java 한글 인코딩이 깨진 그대로이며, code와 UUID 및 예외형은 보존됐다.

## 2. 기동 순서와 실제 DataSource 결속 — BLOCKER

### 실제 코드 결속

`SlipDataSourceConfig`의 메인 `dataSource`는 `@Primary`다. 새 설정은 별도 빈을 만들지만 이를 사용하는 메서드 인자에 `@Qualifier("warehouseValidationDataSource")`가 없다.

```java
@Primary
@Bean(destroyMethod = "close")
public HikariDataSource dataSource(DataSourceProperties properties) { ... }

@Bean(name = "warehouseValidationDataSource")
DataSource warehouseValidationDataSource() { ... }

@Bean
JdbcTemplate warehouseValidationJdbcTemplate(DataSource warehouseValidationDataSource) {
    return new JdbcTemplate(warehouseValidationDataSource);
}
```

실행 결과, 메서드 인자 이름으로 별도 빈이 선택되지 않고 `@Primary`인 **slip_db DataSource가 선택됐다.** 따라서 현재 구현은 inventory DB를 조회하지 않는다.

### 일회성 컨테이너 재현 A — inventory DB가 아예 없어도 slip_db를 조회함

일회성 `postgres:16-alpine` 컨테이너 `sol-1018-pg`를 임의 호스트 포트 `52306`에 띄웠다. `slip_db`만 정상 Flyway 적용되게 하고, 검증 URL은 존재하지 않는 `inventory_missing`으로 주입했다. 당시 `slip_db`에는 `warehouses`가 없었다.

```text

2026-08-01T08:53:31.087+09:00 ERROR ... Application run failed
Caused by: org.springframework.beans.factory.BeanCreationException: Error creating bean with name 'warehouseCodeMapper': Invocation of init method failed
Caused by: org.postgresql.util.PSQLException: ERROR: relation "public.warehouses" does not exist
```

존재하지 않는 `inventory_missing`을 실제로 사용했다면 `database "inventory_missing" does not exist`여야 한다. 실제 오류가 `relation "public.warehouses" does not exist`인 것은 이미 정상 연결된 slip_db에서 조회했다는 실측이다.

### 일회성 컨테이너 재현 B — slip_db에 테스트용 warehouses를 만들면 inventory DB 부재를 무시하고 기동

같은 일회성 `slip_db`에 최소 `warehouses(id, is_deleted)`와 설정 UUID 4행을 만든 뒤, 검증 URL은 계속 존재하지 않는 `inventory_missing`으로 유지했다.

### 현재 공유 DB 읽기 전용 실측


명령은 각 DB에서 `to_regclass('public.warehouses')`만 조회했다. 현재 정상 데이터 상태에서도 slip_db에는 해당 테이블이 없고 inventory_db에만 있다.

### 판정

- **현재 바이너리는 정상 로컬·회사PC·운영 환경 모두 기동을 막는다.** 실제 inventory DB 준비 순서 이전에, 잘못 결속된 slip_db에서 `warehouses`를 찾다가 실패한다.
- compose에도 별도 순서 보장이 없다. local의 `slip-service.depends_on`은 postgres/redis/rabbitmq/eureka/api-gateway뿐이고, production의 `app-depends`는 rabbitmq/elasticsearch/eureka뿐이다. 어느 쪽도 inventory-service의 Flyway 완료를 기다리지 않는다.
- 다만 현 코드에서는 inventory DB가 미준비이거나 V1 마이그레이션 전인 상황 자체가 검증 경로에 도달하지 않는다. **inventory 연결 설정이 무시되기 때문이다.** “inventory가 먼저 떠야 해서 실패한다”보다 앞선 실제 BLOCKER다.

## 3. inventory DB 접속 권한

### 설정 조사

저장소의 현재 로컬·운영 표준은 service별 DB 계정을 분리하지 않는다.

```text
infrastructure/docker-compose.local-all.yml:19:  DB_USER: samhan
infrastructure/postgres/init/01-create-databases.sql:CREATE DATABASE inventory_db OWNER samhan;
infrastructure/postgres/init/01-create-databases.sql:CREATE DATABASE slip_db      OWNER samhan;
infrastructure/docker-compose.prod.yml:42:  DB_USER: ${SAMHAN_DB_USERNAME}
infrastructure/terraform/templates/init-rds.sql:CREATE DATABASE inventory_db OWNER samhan;
infrastructure/terraform/templates/init-rds.sql:CREATE DATABASE slip_db      OWNER samhan;
```

`GRANT`, `REVOKE`, service별 `CREATE ROLE/USER`로 slip 읽기 권한을 따로 부여하는 운영 SQL은 검색되지 않았다. `WAREHOUSE_DB_USER`를 compose가 별도 공급하지도 않아 application.yml의 `${WAREHOUSE_DB_USER:${DB_USER:...}}`에 의해 메인 DB 사용자와 같다. 따라서 **현재 저장소가 정의한 로컬/운영 환경 중 “slip 계정은 slip_db만 접근”하는 환경은 확인되지 않았다.**

### 현재 코드의 권한 교차 재현

일회성 DB에 올바른 네 행이 있는 `inventory_restricted`를 만들고, 검증 계정은 존재조차 하지 않는 `no_such_role`/오류 암호로 주입했다. slip_db에는 앞선 최소 fixture를 유지했다.

```text
EXITED_WITHIN_35S=False
PROCESS_EXIT=-1
2026-08-01T08:57:29.915+09:00  INFO ... WarehouseCodeMapper : [Phase 6 M5] warehouse-code-map 로드: 4 entries
2026-08-01T08:57:38.689+09:00  INFO ... SlipServiceApplication : Started SlipServiceApplication in 30.319 seconds (process running for 31.571)
```

### 판정

- 현재 구현에서는 별도 inventory 자격증명도 사용되지 않는다. 잘못된 계정을 넣어도 slip_db의 테이블만 있으면 기동한다.
- DataSource 결속을 의도대로 고치면, 현재 공통 master 계정 환경은 읽을 수 있다. 그러나 service-per-DB를 실제 최소권한 계정으로 운영하는 환경은 명시적 `CONNECT`/schema `USAGE`/`warehouses SELECT`가 없으므로 기동 실패한다. 저장소에는 그 권한 provisioning이 없다.
- 즉 현재는 “권한이 없어 정상 환경을 막음”이 아니라 **권한 검증 자체가 우회됨**이고, 결속만 바로잡을 경우에는 최소권한 환경을 막는 두 번째 회귀가 대기한다.

## 5. service-per-DB 경계, migration·backup·schema 영향

현재 SQL 계약은 다음 한 줄에 고정돼 있다.

```text
SELECT id FROM public.warehouses WHERE is_deleted = false AND id IN (?, ?, ?, ?)
```

inventory의 `warehouses` 소유 migration은 inventory-service의 V1/V2이고, slip-service Flyway는 이를 관리하지 않는다. 그 결과 정상 결속으로 고치더라도 다음 결합이 생긴다.

- **migration 순서 결합:** inventory V1(테이블)과 V2(행)가 완료된 뒤에만 slip이 뜬다. compose에는 그 완료 barrier가 없다.
- **schema 결합:** `public`, `warehouses`, `id UUID`, `is_deleted BOOLEAN`은 inventory 내부 구현인데 slip 코드가 직접 컴파일되지 않는 런타임 계약으로 소비한다.
- **backup/restore 결합:** slip_db만 정상 시점으로 복원해도 inventory_db의 네 master 행이 다른 시점·다른 UUID·soft-delete 상태면 slip 재기동이 막힌다. 반대로 inventory 복원/재등록이 slip의 가용성을 바꾼다.
- **권한 결합:** inventory owner가 아닌 slip runtime 계정에 cross-DB 읽기 권한 lifecycle을 추가 관리해야 한다.

### schema 변경 일회성 재현 원문

조회 대상의 `is_deleted`를 `deleted_flag`로 이름만 바꾼 뒤 현재 JAR를 기동했다.

```text
ALTER TABLE
PROCESS_EXIT=1
2026-08-01T09:00:37.497+09:00 ERROR ... Application run failed
Caused by: org.springframework.beans.factory.BeanCreationException: Error creating bean with name 'warehouseCodeMapper': Invocation of init method failed
Caused by: org.postgresql.util.PSQLException: ERROR: column "is_deleted" does not exist
```

따라서 inventory schema가 해당 이름을 바꾸거나 테이블을 다른 schema로 옮기면 slip-service는 실제로 깨진다. 현재 결속 결함 때문에 재현 테이블은 slip_db에 있었지만, 실행된 SQL과 실패 조건은 코드의 동일 SQL이다.

## 6. 경계를 유지하면서 같은 목적을 달성할 수 있는가

**“inventory의 현재 실데이터와 매번 slip 프로세스 기동 시 동기 대조”를 그대로 유지하면서, inventory DB/API/복제본 어느 것에도 의존하지 않는 방법은 없다.** 현재성 확인에는 반드시 inventory 소유 상태의 어느 표현을 읽어야 하기 때문이다. 다만 목적을 “잘못된 정적 매핑의 배포 방지”로 정의하면 경계를 유지하는 더 안전한 방법이 있다.

### 권장: inventory migration 이후 deployment preflight

1. inventory-service Flyway를 먼저 완료한다.
2. 배포 파이프라인의 일회성 preflight가 운영자/배포용 읽기 자격증명으로 `code 또는 고정 UUID + is_deleted=false`를 확인한다.
3. 통과한 설정으로 slip-service를 배포한다. slip runtime에는 inventory DB 권한을 주지 않는다.

이 방식이 가능한 근거는 네 UUID가 inventory V2의 deterministic seed이고, 검증 대상이 요청마다 변하는 재고량이 아니라 정적 master 4행이기 때문이다. 서비스 디스커버리와 애플리케이션 기동 순서 결합도 만들지 않는다. 실패 시 새 slip 프로세스가 crash-loop하는 대신 배포 단계에서 중단된다.

### 대안: slip 소유 로컬 projection

inventory의 warehouse-created/updated/deleted 이벤트를 slip_db의 로컬 projection에 반영하고 기동 시 그 projection만 확인할 수 있다. 재기동은 inventory 가용성과 분리되지만, 최초 환경 bootstrap·이벤트 replay·지연 상태 정책이 추가로 필요하다. “현재 inventory DB와 즉시 동일”이라는 강한 보장은 event consistency로 완화된다.

### 비권장: 기동 시 inventory API 호출

DB 경계는 지키지만 inventory-service 발견·네트워크·migration 완료에 slip 기동을 결속하므로, 사용자가 지적한 또 다른 기동 순서 문제를 그대로 만든다. 이번 목적에는 deployment preflight보다 열등하다.

## 최종 판정

**BLOCKER — 현재 변경을 그대로 배포하면 정상 환경의 slip-service가 뜨지 않는다.** 핵심 원인은 inventory의 UUID가 환경마다 달라서가 아니라, 새 JdbcTemplate가 `@Primary` slip DataSource에 결속되어 slip_db의 존재하지 않는 `public.warehouses`를 조회하기 때문이다. CI는 같은 slip 테스트 DB에 V999 `warehouses` fixture를 만들어 이 결함을 가렸다.

결속을 정상화한 뒤에도 compose 기동 순서, cross-DB 최소권한, inventory schema/backup lifecycle 결합은 별도 회귀로 남는다. 목적상 가장 경계 친화적인 해법은 inventory migration 이후 deployment preflight이며, 애플리케이션 기동 시 직접 cross-DB 조회는 제거하는 것이다.
