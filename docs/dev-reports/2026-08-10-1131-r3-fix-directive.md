# PR #1131 R3 fix directive — 정상 BUNDLE과 사용자 편집을 거부하는 R2 검증

## 판정

**BLOCKING. 실 사용자 경로로 재현 가능한 결함이 있다.**

R2는 구성품이 2행 이상인 BUNDLE 신규행의 계보 소실 자체는 닫았다. 그러나 새 검증이 `부모 BUNDLE에서 나온
구성품인가`뿐 아니라 **행 수·수량·단가·setHead를 product-service 전개 원문과 완전 동일**하게
강제한다. 그 결과 다음 정상 요청이 저장 전에 `INVALID_INPUT`으로 거부된다.

1. product-service가 정상 반환한 **1행 BUNDLE** — 활성·비삭제 표본 16개.
2. 전개 후 사용자가 구성품 수량을 바꾼 요청.
3. 전개 후 사용자가 구성품 단가를 바꾼 요청.
4. 전개 후 사용자가 비-head 구성품 하나를 지운 요청.

수정 화면은 이 세 편집을 실제 사용자 동작으로 제공한다. 계보 위조 방지와 전개행 불변 강제는
같은 불변식이 아니다.

## 재현과 원문

### A. 정상 1행 BUNDLE이 거부된다

실 product-service 직접 응답 — 재배포 없이 현재 배포본에 read-only 호출:

```text
request  parentModelCode=AM240AXVHHR1SY, setQty=1, setUnitOverride=1000000
response HTTP 200
{"count":1,"modelCode":"AM120AXVHHR1","quantity":1.00,
 "unitPrice":5808000,"componentKind":"OUTDOOR","setHead":false}
```

이 응답을 FE가 그대로 신규 계보 요청으로 보내면 `validateExpandedLines`의
`expanded.stream().filter(ExpandedLineDto::setHead).count() != 1`에 도달한다.

```text
INVALID_INPUT
세트 계보 검증 실패: 서버 전개 결과의 구성품 수 또는 setHead가 올바르지 않습니다
```

실 DB 분모:

```sql
WITH counts AS (
  SELECT p.id, p.status, p.bundle_mode,
         COUNT(b.id) FILTER (WHERE b.is_deleted=false) AS component_count
  FROM products p
  LEFT JOIN bundle_component b ON b.bundle_product_id=p.id
  WHERE p.is_deleted=false AND p.product_type='BUNDLE'
  GROUP BY p.id, p.status, p.bundle_mode
)
SELECT COUNT(*)
FROM counts
WHERE status='ACTIVE'
  AND COALESCE(bundle_mode,'EXPAND')='EXPAND'
  AND component_count=1;
-- 16
```

### C. 부모 검증 조회 장애

첫 품목 lookup 성공 뒤 R2가 추가한 부모 lookup만 실패시킨 결과:

```text
R3-PARENT-LOOKUP-OUTAGE|INTERNAL_ERROR|product-service 호출 실패
repository.saveAndFlush 호출 0회
```

완전 장애 때는 R2 이전 좌표 `:91`에서 SINGLE을 포함한 모든 매출 수정이 먼저 막힌다. 따라서
"오늘 5시간 장애 동안 저장 가능"은 현행도 R2도 만족하지 않는다. R2는 그 기존 장애 의존을 만든
원인은 아니지만 신규 BUNDLE에 실패 가능한 동기 호출 구간을 더 늘린다.

## 직전 BLOCKING 폐쇄 여부

**구성품이 2행 이상인 신규 BUNDLE의 무편집 왕복에 한해서는 폐쇄됐다.**

- service 계보 round-trip: 신규 구성품 전부 `parentSetModel` 보존, head 정확히 1개 PASS.
- controller JSON → service → repository/GET/DB IT PASS.

다만 정상 1행 BUNDLE은 위 새 head 검증에 막히므로 전체 사용자 경로 기준 폐쇄 판정은 할 수 없다.

## 불변식

1. product-service가 반환한 비어 있지 않은 구성품 결과는 행이 1개라는 이유만으로 거부하면 안 된다.
   slip 저장 경계는 1행 계보도 일관된 head 규약으로 정규화해야 한다.
2. 신규 BUNDLE 계보의 보안 검증 대상은 **부모 정체성·허용 구성품 membership·그룹 정합**이다.
3. 사용자가 수정 화면에서 입력한 양수 수량과 0 이상 단가는 사용자 권위값이다. 서버 전개 원문과
   다르다는 이유만으로 거부하면 안 된다.
4. 사용자가 비-head 구성품을 명시 삭제하면 남은 행이 모두 부모의 허용 구성품인 한 저장돼야 한다.
5. 부모 구성품이 아닌 임의 SINGLE에 계보를 붙이는 요청은 계속 `INVALID_INPUT`이어야 한다.
6. 기존 `lineId` 기반 `BundleLineageResolver`와 구 규약 행 승계는 그대로 유지한다.

## 양방향 RED

### RED-A — 통과해야 할 사용자 요청

1. **1행 정상 BUNDLE:** `AM240AXVHHR1SY` 수량 1, 단가 1,000,000 선택 → product 응답
   `AM120AXVHHR1` 1행·`setHead=false` → PUT 2xx → DB `parent_set_model='AM240AXVHHR1SY'`.
2. **수량 편집:** `AC023CS1DBC1SY` 전개 후 첫 비-head 구성품 수량만 `기존+1` → PUT 2xx,
   사용자 수량과 계보 보존.
3. **단가 편집:** 같은 세트의 비-head 구성품 단가만 `기존+1원` → PUT 2xx, 사용자 단가와 계보 보존.
4. **부분 삭제:** 같은 세트에서 마지막 비-head 구성품 1행 삭제 → PUT 2xx, 남은 구성품과 정확히
   1개 head 보존.
5. 각 케이스는 HTTP 2xx 뒤 GET/DB까지 확인한다.

### RED-B — 구체 반대 표적

1. 기존 SINGLE `ACL-KORGHP07` 수량 `1→2` + 신규 SINGLE `ACM-A202DN`을 같은 저장에 추가한다.
   기존 lineId 고정, 신규 lineId null, 둘 다 `parent_set_model NULL/set_head=false`, PUT 2xx여야 한다.
2. 신규 `ACM-A202DN`에 `parentSetModel='AC023CS1DBC1SY'`와 부모 UUID를 위조해 붙인다.
   이 품목은 해당 부모 전개 membership이 아니므로 `INVALID_INPUT`, DB write 0회여야 한다.
3. 구 규약 lineId BUNDLE 두 행의 수량·단가를 각각 `3/333`, `4/444`로 바꿔 재저장한다.
   두 행의 기존 계보가 유지되고 product expand 추가 호출은 0회여야 한다.

## 수정 범위

- `SalesSlipUpdateService`의 신규 계보 검증을 **exact expansion equality**에서
  **부모·membership 검증**으로 좁힌다.
- 1행 BUNDLE head 규약은 slip 경계에서 정규화한다. `BundleExpander`는 건드리지 않는다.
- 사용자 수량·단가를 product 재전개값으로 덮어쓰지도 않는다.
- 비-head 부분 삭제를 허용하되, 남은 품목이 허용 membership 밖이면 계속 거부한다.
- 장애 독립성까지 이번 R4에 포함하려면 live 재조회 대신 `/slips/expand-line`이 발급한 서버 서명
  proof(부모·옵션·허용 구성품 ID 집합만 서명, 수량·단가는 서명 대상 제외)를 PUT에서 검증하는
  계약이 필요하다. proof 없이 단순 fail-open은 계보 위조를 재개방하므로 금지한다.

## 반대급부

- exact equality를 membership 검증으로 좁히면 사용자가 부모 전개 기본 수량·배분가에서 벗어날 수
  있다. 이는 화면이 이미 수량·단가 편집과 행 삭제를 제공한다는 사용자 계약의 대가다.
- 반대로 membership까지 없애면 임의 SINGLE 계보 위조가 다시 열린다. RED-B 2가 그 경계다.
- signed proof를 채택하면 저장 시 product-service 장애 창을 줄일 수 있지만 proof 발급·검증과 키
  회전 계약이 추가된다. proof를 채택하지 않으면 신규 BUNDLE 저장은 product-service 장애·timeout에
  계속 종속된다는 사실을 운영 문서에 남겨야 한다.

## 증거 무결성 — 343 vs 276

PM의 정의 `is_deleted=false AND product_type='BUNDLE'`에 따른 분모는 **343이 맞다**. LUNA의 276에는
`status='ACTIVE'` 필터가 추가됐다. 차이 67은 `DISCONTINUED 50 + NOT_FOR_SALE 14 + OUT_OF_STOCK 3`이다.

```sql
SELECT status, COUNT(*)
FROM products
WHERE is_deleted=false AND product_type='BUNDLE'
GROUP BY status
ORDER BY status;
-- ACTIVE 276 / DISCONTINUED 50 / NOT_FOR_SALE 14 / OUT_OF_STOCK 3

SELECT COUNT(*)
FROM products
WHERE is_deleted=false AND product_type='BUNDLE';
-- 343

SELECT COUNT(*)
FROM products
WHERE is_deleted=false AND product_type='BUNDLE' AND status='ACTIVE';
-- 276
```

72가 양쪽에서 같았던 이유도 같은 SQL로 설명된다. 비ACTIVE 67개는 전부 기본 구성품이 1개 이상이고,
기본 구성품 0개인 72개는 전부 `status='ACTIVE'`다.

```sql
SELECT p.status,
       COUNT(*) AS bundle_count,
       COUNT(*) FILTER (
         WHERE NOT EXISTS (
           SELECT 1
           FROM bundle_component bc
           WHERE bc.bundle_product_id=p.id
             AND bc.is_deleted=false
             AND bc.is_default=true
         )
       ) AS no_default_component
FROM products p
WHERE p.is_deleted=false AND p.product_type='BUNDLE'
GROUP BY p.status
ORDER BY p.status;
-- ACTIVE 276/72, DISCONTINUED 50/0, NOT_FOR_SALE 14/0, OUT_OF_STOCK 3/0
```
