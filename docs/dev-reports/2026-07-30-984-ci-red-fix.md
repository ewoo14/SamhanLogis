# PR #984 CI red fix — ECOUNT·시트 수렴 및 IT 격리

## 1. 판정 (A) — 테스트가 맞고, 순서 수렴 구현이 불완전했다

`EcountSheetOrderConvergenceIT`의 기대값은 관측값에 맞춘 것이 아니다. 수정 전 실 PostgreSQL 실행에서
`import_then_sync_converges_to_sheet_canonical_state()`가 다음처럼 실패했다.

```text
expected: "시트 정본명"
 but was: "이카운트 최초명"
at EcountSheetOrderConvergenceIT.assertSheetCanonicalState(EcountSheetOrderConvergenceIT.java:114)
```

원인은 `ProductSheetSyncService`의 기존 행 갱신 경로가 ECOUNT 계보를 SHEET로 승격하고
`productCategory`/`usageScope`/exposure를 갱신했지만, 승격 순간 `Product.name`을 시트 행의
정본명으로 바꾸지 않은 것이다. 따라서 `lineage=SHEET`가 되어도 이름만 ECOUNT 값으로 남았다.

수정 후 `ProductSheetSyncService.java:1289-1292`에서 `promotedFromEcount`일 때만
`p.rename(name)`을 수행한다. 이미 SHEET/MANUAL인 행에는 이름 변경을 적용하지 않는다.
그러므로 시트 정본명 보존, ECOUNT 재임포트 시 이름 덮어쓰기 방지, 기존 수동 계보 보호를 함께
유지한다.

## 2. 격리 실패 원인 (B)

`AbstractPostgresIT.java:26-44`는 product-service IT 전체가 싱글턴 Testcontainers PostgreSQL과
같은 DB를 공유한다. `@DirtiesContext`는 Spring ApplicationContext를 폐기할 뿐 DB 행을 지우지
않는다.

새 IT의 `sync_then_import_converges_to_sheet_canonical_state()`는
`EcountSheetOrderConvergenceIT.java:115-119`에서 다음 데이터를 만든다.

```text
model_code = ORDER_CONVERGENCE_SYNC_IMPORT
product_category = HOME_MULTI
usage_scope = BOTH
product_estimate_exposure(estimate_category=HOME_MULTI) = active
```

시트 sync가 먼저 제품을 생성하므로 이 행의 `created_by`는 ECOUNT importer의
`t984-order-test`가 아니다. 이후 importer가 갱신해도 생성자 값은 유지된다.

이 행이 남으면:

- `ProductCatalogControllerIT.java:492-516`의 `q=ORDER_` 조회에서 `ORDER_FIRST`보다
  `ORDER_CONVERGENCE_SYNC_IMPORT`가 먼저 반환된다.
- `ProductCatalogControllerIT.java:855-880` 및 `969-983`의 display-orders 요청은
  활성 HOME_MULTI exposure 전체를 요청 body와 대조하므로 누락된 새 행 때문에 204 대신 400이 된다.

`EcountSheetOrderConvergenceIT.java:74-98`에 `@AfterEach` fixture cleanup을 추가했다.
`ORDER_CONVERGENCE_%`라는 이 IT 전용 modelCode 범위의 alias, staging, exposure, price_history,
products를 FK 순서로 제거한다. actor 기준만 사용하지 않고 modelCode prefix를 함께 사용해
sync-first 데이터도 반드시 회수한다. 테스트용 disposable PostgreSQL fixture만 대상으로 하며
공유 실데이터에는 접근하지 않는다.
