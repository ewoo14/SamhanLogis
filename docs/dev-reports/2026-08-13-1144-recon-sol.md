### 1.4 전표 ↔ 회계전표 연결 축

연결 축은 이미 존재한다.

```text
slip_db.slips.id / slip_no
  └─ slip_lines.id / line_no
       ↕ accounting_db.{sales|purchase}_accounting_slip_allocations
          source_slip_id + source_slip_no + source_line_id + source_line_no
          allocated_qty + allocated_amount
       └─ {sales|purchase}_accounting_slip_lines.slip_id
            └─ {sales|purchase}_accounting_slips.id
```

- 저장 스키마에는 UUID와 사용자용 번호 snapshot이 함께 있다 (`V18:68-73`, `V19:68-73`).
- 생성 서비스의 실제 신뢰 앵커는 `sourceLineId`이다. slip-service `GET /internal/slips/lines/{lineId}`로 조회한 `slipId/slipNo`를 allocation에 다시 저장한다 (`SlipInternalController.java:488`, `:491`, `:522`; `SalesAccountingSlipCreateAttemptService.java:100`, `:105`).

## 2. 공유 DB 실측

모든 psql 실행은 `BEGIN TRANSACTION READ ONLY; ... ROLLBACK;`이었다. Docker 컨테이너는 중지·재시작하지 않았다.

### 2.1 매출/매입 대상 전표 수와 코드 채움 비율

“대상”을 코드 계약 그대로 두 층으로 센다.

- 원천 상태 기준: 활성 `CONFIRMED`는 **OUTBOUND 2건 / INBOUND 1건**.
- 현재 생성 서비스가 실제 수용할 조건(`CONFIRMED` + 거래처 UUID·코드·명 + 활성 라인): **매출 2건(5라인) / 매입 0건**.
- 현재 allocation은 `2026/07/27-64` 한 건뿐이고 현재 CONFIRMED 3건과 번호가 겹치지 않는다. 따라서 매출 후보 2건은 기존 allocation에 의해 제외되지 않는다.

쿼리 원문:

```sql
BEGIN TRANSACTION READ ONLY;
SELECT slip_type,
       COUNT(*) AS confirmed_rows,
       COUNT(*) FILTER (WHERE partner_id IS NOT NULL) AS uuid_filled,
       COUNT(*) FILTER (WHERE NULLIF(BTRIM(partner_code), '') IS NOT NULL) AS code_filled,
       COUNT(*) FILTER (WHERE partner_id IS NOT NULL AND NULLIF(BTRIM(partner_code), '') IS NULL) AS uuid_only,
       COUNT(*) FILTER (WHERE partner_id IS NOT NULL
                         AND NULLIF(BTRIM(partner_code), '') IS NOT NULL
                         AND NULLIF(BTRIM(partner_name), '') IS NOT NULL) AS partner_complete,
       ROUND(100.0 * COUNT(*) FILTER (WHERE NULLIF(BTRIM(partner_code), '') IS NOT NULL)
             / NULLIF(COUNT(*),0), 2) AS code_pct
FROM slips
WHERE is_deleted = false AND status = 'CONFIRMED'
GROUP BY slip_type ORDER BY slip_type;

SELECT s.slip_type, COUNT(DISTINCT s.id) AS candidate_slips, COUNT(l.id) AS candidate_lines
FROM slips s
JOIN slip_lines l ON l.slip_id=s.id AND l.is_deleted=false
WHERE s.is_deleted=false AND s.status='CONFIRMED'
  AND s.partner_id IS NOT NULL
  AND NULLIF(BTRIM(s.partner_code),'') IS NOT NULL
  AND NULLIF(BTRIM(s.partner_name),'') IS NOT NULL
GROUP BY s.slip_type ORDER BY s.slip_type;
ROLLBACK;
```

결과 원문:

```text
 slip_type | confirmed_rows | uuid_filled | code_filled | uuid_only | partner_complete | code_pct
-----------+----------------+-------------+-------------+-----------+------------------+---------
 INBOUND   |              1 |           1 |           0 |         1 |                0 |     0.00
 OUTBOUND  |              2 |           2 |           2 |         0 |                2 |   100.00

 slip_type | candidate_slips | candidate_lines
-----------+-----------------+----------------
 OUTBOUND  |               2 |               5
```

활성 전표 전체의 UUID/코드 채움 비율도 함께 셌다.

```sql
SELECT slip_type, COUNT(*) AS rows,
       COUNT(*) FILTER (WHERE partner_id IS NOT NULL) AS uuid_filled,
       COUNT(*) FILTER (WHERE NULLIF(BTRIM(partner_code),'') IS NOT NULL) AS code_filled,
       COUNT(*) FILTER (WHERE partner_id IS NOT NULL AND NULLIF(BTRIM(partner_code),'') IS NULL) AS uuid_only,
       ROUND(100.0*COUNT(*) FILTER (WHERE NULLIF(BTRIM(partner_code),'') IS NOT NULL)/COUNT(*),2) AS code_pct
FROM slips WHERE is_deleted=false GROUP BY slip_type ORDER BY slip_type;
```

```text

-----------+------+-------------+-------------+-----------+---------
 INBOUND   |   42 |          40 |          31 |         9 |    73.81
 OUTBOUND  |  146 |          65 |          65 |         0 |    44.52
```

OUTBOUND의 `code_pct=44.52%`는 UUID 없는 행까지 전체 분모에 넣은 값이다. 결함 패턴인 “UUID만 있고 코드 없음”은 OUTBOUND 0건, INBOUND 9건이다.

CONFIRMED 상세 원문은 다음과 같다. UUID 값 자체는 사용자 비공개 원칙에 따라 `SET/EMPTY`만 출력했다.

```text
 INBOUND  | 2026/08/09-6 | CONFIRMED | SET | <EMPTY>      | ?????              
 OUTBOUND | 2026/08/03-6 | CONFIRMED | SET | 2148720659   | (주)삼한공조시스템
 OUTBOUND | 2026/08/07-3 | CONFIRMED | SET | 000011111111 | 한울냉열시스템
```

`?????`는 psql 출력에서 실제로 그렇게 반환된 원문이며 업무명을 추정하지 않는다.

### 2.2 이미 회계 처리된 건수와 생성 경로

활성 회계 매출/매입전표는 **0건**이다. 따라서 현재 CONFIRMED 원전표 3건 중 활성 회계전표에 연결된 건도 **0건**이다. 현재 CONFIRMED 세 전표번호와 일치하거나 description에 포함하는 활성 journal도 0건이다.

과거 흔적은 하나 있다.

- soft-delete된 매출 회계전표 `2026/07/26-1027` 1건, 상태 `POSTED`.
- 회계 라인 1건도 soft-delete.
- allocation 1건은 **활성으로 남음**. 원천은 `2026/07/27-64`, 현재 slip_db에서 `REJECTED + is_deleted=true`.
- MIG-3 staging 매출/매입 row는 모두 0건이므로 이 1건은 MIG-3 import가 아니라 allocation 생성 경로다.
- allocation 합계 repository는 parent 헤더/라인의 삭제 상태를 join하지 않고 allocation의 `isDeleted=false`만 합산한다 (`SalesAccountingSlipAllocationRepository.java:16`, `:24`). 따라서 이 잔재는 해당 삭제 원천 라인의 잔여 계산에는 계속 들어간다. 현재 활성 CONFIRMED 후보와는 다른 원천이다.

쿼리 원문:

일반 `journals`에는 활성 `source_type=SLIP`이 POSTED 30건·REVERSED 5건 존재한다. 그러나 현재 CONFIRMED 세 원전표 번호와 exact/description match는 0건이다. 기존 SLIP journal 35건을 현재 세 원전표의 처리 건수로 합산하지 않았다.

## 3. 이미 확정된 규칙

다음은 새 제안이 아니라 기존 이슈·문서에 적힌 확정 규칙이다.

1. **#1072 정본:** 이카운트 계정과목 체계가 정본이다. 3코드만 먼저 바꾸지 않고 **전 목록을 먼저 확정**한다 (`docs/dev-reports/2026-08-12-1072-1144-recon.md:52`, `:88`; `docs/tracks/2026-08-12-1072-1144-accounting-canon.md:5`).
2. **#1072 현재 확정값:** 코드까지 확인된 매핑은 `110→1089`, `401→4019` 두 개뿐이다. 현재 S1은 표시만 바꾸고 DB·원장 행은 바꾸지 않는다 (`2026-08-13-1072-s1-mapping-luna.md:11`, `:28`).
3. **도메인 분리:** 매출/매입 회계전표는 세금계산서와 별도 도메인이며 accounting-service 소관이다 (`docs/superpowers/specs/2026-05-19-sales-purchase-accounting-slip-design.md:28`, D-SAS-01/02).
4. **수동 트리거:** 자동 생성하지 않고 관리자가 수동 생성한다 (같은 spec `:34`, D-SAS-03).
5. **연결 카디널리티:** 원전표↔회계전표는 라인·부분금액 기준 N:M, partial 허용, over-allocation 차단 (`:35-36`, D-SAS-04/05; 물리 모델 `:113`).
6. **세금계산서 묶음:** 매출 회계전표 N:1, 동일 거래처·동일월 (`:37`, `:152`).
7. **입고 측 별도 축:** PurchaseAccountingSlip과 수신 세금계산서 축이 있다 (`:38`, `:202`). 최신 #1144는 매입=채무, 출금으로 소멸하므로 입금 로직을 단순 반전하지 말라고 추가 명시했다.
8. **VAT:** 원 전표 단가는 VAT 포함이며 과세는 공급가와 VAT로 분리, 영세·면세는 VAT 0; 현재 매출/매입 회계전표 1장당 단일 `tax_type` (`:39`, `:265`, `:296`).
9. **#1144 핵심 11규칙:** 상세 단건·외부 복수·일마감 생성 경로, 매출=채권·매입=채무, 3금액 표시, 회계전표 전에도 문서원장 반영, 연결된 것만 세금계산서 발행, 금액 변경 시 삭제→재생성 (`docs/dev-reports/2026-08-12-1072-1144-recon.md:148`).
10. **원장/세금계산서 축 분리:** 원장은 원 판매/구매전표로 항상 반영하고 세금계산서는 회계전표 연결이 게이트다 (`:162`).
11. **추가 규칙 12~16:** 출금보고서, 출금→보고서 반영, 선택 거래처 반영, 계좌·카드·대출 3메뉴, 등록된 것 전체 조회 (`:169`).
12. **자기 회사 플래그 불요:** `is_self`를 만들지 않는다. `(주)삼한공조시스템 / 2148720659`를 일반 기초거래처로 선택한다 (`:177`).
13. **#922 경계:** 등록 메뉴 활성 체크와 10분 바로빌 수집은 #922이며, #1144의 3메뉴/전체조회와 분리한다 (`:181`).
14. **MIG-3 import:** 파일 hash+row 멱등키, transaction/advisory lock, 거래처 lookup miss reject, soft-delete row restore, UUID 비노출 (`migration/decisions/DECISIONS.md:2134`, `:2140`).

## 4. #1072 미정 9건이 #1144의 전제인가

### 판정: **예. #1144는 이 결정 없이는 못 나간다.**

근거는 업무 추론이 아니라 이미 기록된 의존성이다.

1. 트랙 정본이 `#1072 선행 / #1144 후행`으로 명시한다. “#1144가 만드는 분개는 #1072 계정과목 체계 위에서 만들어진다”고 적혀 있다 (`docs/tracks/2026-08-12-1072-1144-accounting-canon.md:5`, `:9`).
2. 기존 정찰은 `#1072-A` 완료 전 `#1072-B/C`나 `#1144` 쓰기 슬라이스 진입이 “전 목록 먼저 확정” 결정을 위반한다고 판정했다 (`docs/dev-reports/2026-08-12-1072-1144-recon.md:476`, `:488`).
3. #1144 구현 계획 Q10은 매출/매입 POST의 상대계정과 VAT 계정이 미확정이라고 명시한다 (`docs/dev-reports/2026-08-08-1144-implementation-plan.md:659`, 확정 못한 것 `:730`).
4. 실데이터에서 미정 코드가 이미 사용 중이다: `201` 3라인, `210` 1라인, `220` 34라인, `255` 7라인. 매입 채무/VAT/출금 분개를 어느 코드로 쓸지 정하지 않고 새 분개를 만들면 다시 이관해야 한다.

“9건”은 오기가 아니다. 문서가 **9개 불일치 건 / 실제 코드 10개**로 정의한다. `220·255`가 같은 부가세예수금 불일치 한 건이라 둘을 묶어 센다 (`docs/dev-reports/2026-08-13-1072-s1-mapping-luna.md:15`). 실제 코드 집합은 다음 10개다.

```text
103 · 104 · 105 · 201 · 919 · 142 · 210 · 220 · 255 · 900
```

단, 이 블로커가 #1144와 무관한 문서 정리나 read-only 화면 조사까지 막는 것은 아니다. **계정코드·분개·원장 금액을 쓰는 #1144 제품 슬라이스가 블로킹 대상**이다.

## 5. 개발책임자에게 물어야 할 것

### Q1. #1072 미정 9건(코드 10개)의 최종 처리

- (a) 각 코드의 이카운트 목표 코드와 유지/병합/분할을 확정
- (b) 해당 코드의 원증빙·계좌종류·만기·감모 기준을 먼저 보강한 뒤 확정
- (c) 현재 코드를 영구 유지할 예외 목록으로 확정

본인은 **(b)** 권장. `103/104/105/201/919`는 기존 문서가 원자료 부족을 명시했고, `142/210/220/255/900`도 현재 S1이 임의 매핑을 금지했다.  
**이걸 정하지 않으면:** #1072 물리 chart/원장 전환과 #1144 매출·매입·VAT·출금 POST 분개가 막힌다.

### Q2. 회계전표 POST가 만들 분개의 책임과 계정 조합

- (a) 회계전표 POST가 채권/채무·매출/매입·VAT 분개를 만들고 세금계산서는 연결/발행만 담당
- (b) 현행처럼 세금계산서 발행이 매출 분개를 만들고 회계전표 POST는 상태만 변경
- (c) 둘 다 만들되 동일 원천 dedup

기존 정찰은 **(a)**를 권고했지만 개발책임자 확정은 없다. 정확한 코드값은 Q1 후속이다.  
**이걸 정하지 않으면:** #1144 원장·분개 인과, 이중계상 방지, 세금계산서 게이트가 막힌다.

### Q3. 회계전표 삭제→재생성의 정확한 수명주기

- (a) `VOIDED` + 원분개 역분개 + 세금계산서 연결해제 후 재생성
- (b) DRAFT만 soft-delete, POSTED는 `VOIDED`+역분개
- (c) 연결 세금계산서를 먼저 취소한 경우에만 (a)/(b) 허용

본인은 **(b)+(연결 세금계산서 선처리 규칙 별도 확정)** 권장. hard delete는 기존 BaseEntity/감사 규칙과 충돌한다.  
**이걸 정하지 않으면:** 새 생성 경로를 열기 전에 필요한 정정·복구 경로와 기존 soft-delete allocation 잔재 처리가 막힌다.

### Q4. 외부 “복수 생성”의 결과 단위와 원자성

- (a) 원전표 N건 → 회계전표 N건, 전부 성공/전부 실패
- (b) 원전표 N건 → 회계전표 N건, 건별 성공
- (c) 원전표 N건 → 회계전표 1건 합산

본인은 기존 #1144 문구와 기존 계획의 권고를 따라 **(a)** 권장.  
**이걸 정하지 않으면:** bulk API 응답, transaction 경계, 재시도 멱등키와 화면 결과표가 막힌다.

### Q5. UUID만 채워진 CONFIRMED INBOUND 1건의 처리

- (a) #1155의 공식 backfill 경로로 거래처코드를 복구한 뒤 매입 후보로 포함
- (b) 원거래처를 개발책임자가 확인해 관리 경로로 보정
- (c) 복구 불가 자료로 분류해 회계전표 대상에서 제외

본인은 **(a), 실패 시 (b)** 권장. 현재 값은 `partner_name=?????`라 거래처를 추론하지 않는다.  
**이걸 정하지 않으면:** 현재 공유 DB에서 매입 회계전표 실 사용자 표본은 계속 0건이고 매입 경로 라이브 검증이 막힌다.

### Q6. soft-delete 헤더 아래 활성 allocation 1행의 정리 정책

- (a) parent 헤더/라인 삭제 시 allocation도 같은 시각 soft-delete
- (b) 합산 query가 활성 parent만 join하도록 변경하고 잔재는 감사 보존
- (c) 두 조치를 모두 수행

본인은 **(c)** 권장. 현재 repository는 allocation 자체의 삭제 플래그만 본다.  
**이걸 정하지 않으면:** 삭제된 회계전표의 배분이 원천 잔여를 계속 차감해 재생성/재연결 가능 수량·금액이 틀릴 수 있다.

## 7. 정찰 결론

1. 매출·매입 회계전표 엔티티/테이블/API/목록·작성 화면/N:M allocation은 이미 있다. “새 도메인 신설” 제안은 결함이다.
2. 현재 실데이터의 생성 가능 원전표는 매출 2건(5라인), 매입 0건이다. 매입 원천 1건은 UUID만 있고 코드가 비어 있다.
3. 활성 회계 매출·매입전표는 0건이다. 과거 allocation 생성 매출전표 1건은 soft-delete됐고 active allocation 1행만 남았다. MIG-3 실적은 0건이다.
