## A1. dev_dispatch 운송사 등록·수정·비활성화·삭제 차단

### 클릭 경로

1. `dev_dispatch` 로그인
2. 좌측 `배차` 카테고리 확장
3. `인사 > 운송사 목록` 메뉴 존재 여부 확인
4. 메뉴가 없는 상태에서 직접 `http://127.0.0.1:5175/#/admin/carriers` 진입

### 기대

운송사 마스터의 등록·수정·비활성화·삭제 컨트롤은 DISPATCH 계정에 제공되지 않고, 직접 URL로도 운송사 관리 화면에 들어갈 수 없어야 한다.

### 실제

- `dev_dispatch`의 `auth/me` 실 응답은 `role=DISPATCH`였다.
- `auth/admin/permissions/my` 실 응답에서 `dispatch.board`는 `VIEW/CREATE/UPDATE/DELETE/RESTORE`를 받았고 `hr.carriers` 권한은 반환되지 않았다.
- 직접 `GET http://localhost:8080/admin/carriers`는 `HTTP 403`을 반환했다.
- 응답 code는 `FORBIDDEN`이며, 화면은 운송사 관리 화면 대신 대시보드로 돌아갔다.
- 따라서 등록·수정·비활성화·삭제 버튼이 렌더링되지 않았다. 권한이 없는 상태에서 mutation 요청은 발행하지 않았다.

- MASTER 대조용 운송사 관리 화면: `docs/qa/1039-s12-real-qa/11-master-carrier-admin-baseline-real-qa.png`

### 브라우저 콘솔 원문

로그인 화면 부팅 직후 다음 오류가 재현됐다.

```text
[arologis-auth] 초기 토큰 조회 실패

  at bootstrap (.../stores/authStore.ts:7:46)
```

같은 세션의 runtime 확인 결과:

```text
window.api        === undefined
window.electronAPI === undefined
window.process    === undefined
```

### 로그인 직후 network

Samhan Public 로그인 API 자체는 성공했다.

```text
POST http://localhost:8080/auth/login                    200
GET  http://localhost:8080/auth/admin/permissions/my     401
GET  http://localhost:8080/auth/me                       401
```

`auth/login` 200 응답에는 `role=DISPATCH`가 있었지만 renderer 화면은 로그인 화면에 남았다. 이후 인증 관련 호출이 401로 이어졌다.

아로로지스 자체 관리자 로그인 경로도 별도로 확인했다.

```text
POST http://localhost:8097/auth/admin/login               401
응답: {"code":"UNAUTHORIZED","message":"invalid credentials"}
```

이는 Samhan Public의 200 로그인 응답과 다른 인증 경로다. read-only DB 확인에서도 `arologis_db.auth_admin_user`에는 `dev_dispatch` 계정 행이 없었다. 따라서 이 401은 별도 seed/인증 경로 관찰이며, S11의 “Samhan auth 200 후 GUI 진입 실패” 원인과 혼동하지 않았다.

### 원인 판정

**원인 확정: renderer-only Vite 세션에 main↔renderer 인증 IPC bridge가 없다.**

아로로지스 renderer는 초기 인증 bootstrap과 API interceptor 양쪽에서 `window.api.getToken()`을 호출한다. 현재 renderer에는 `window.api` 자체가 없으므로 `getToken` 호출이 공통으로 실패한다. 그 결과 200으로 받은 Samhan auth token이 renderer 인증 상태로 이어지지 않고 GUI 진입이 중단된다.

현재 확인은 사용자가 지정한 renderer-only launch config 기준이다. packaged Electron main process를 별도로 띄워 preload가 어떤 채널을 제공하는지는 이번 라운드 범위 밖이라 확인하지 않았다. 따라서 확인된 사실은 “현재 renderer에 `window.api.getToken` 채널이 없다”이며, 다른 IPC 채널명으로 대체되어야 한다고 추측하지 않는다.
