## ② 불변식 — 수단이 아니라 사용자에게 반드시 참이어야 하는 결과

1. `버전이력` 버튼이 노출된 모든 화면은 현재 선택/라우트 entity의 권위 있는 audit row를 조회할 수 있어야 한다.
2. 실제 조회 실패와 성공한 0건 응답은 서로 다른 상태다. 실패를 “아직 버전 이력이 없습니다.”라고 표시해서는 안 된다.
3. 세금계산서 수정, 마감·역마감, DC 설정 변경 뒤 해당 entity의 새 변경이력이 사용자에게 도달해야 한다. 기록되지 않은 변경을 이력 0건으로 단정해서는 안 된다.
4. audit 조회 실패는 본문·목록·저장·발행·마감·역마감·DC 변경·재고감사 전이의 기존 사용자 경로를 무너뜨리면 안 된다.
5. 기존 `AuditRevisionBadge`와 기존에 있던 `AuditOverlay`는 그대로 남아야 한다. 세금계산서 편집 화면은 원래 Overlay가 없었으므로 새로 있다고 가장해서는 안 된다.
6. 성공 응답의 표시는 현재 adapter 계약을 유지해야 한다: `revisionNo` 단위 묶음, 시간 내림차순, 변경항목 기본 접힘, field·변경 전·변경 후·변경자명·시각 보존.
7. `actorId` 및 값 내부의 사용자 비공개 UUID는 새 사용자 표면에 노출되면 안 된다.

## ③ 양방향 RED — RED-A 반대급부 필수

### RED-A — 정상 이력 도달과 기존 기능 반대급부

- 세금계산서 상세/편집, 매출·기간·월말 마감, DC 설정, 재고감사 각각에서 실제 mutation 후 같은 entity의 버전이력을 연다.
- 새 revision과 변경항목이 현재 entity에만 보이고 최신 카드가 위에 있으며 변경항목은 기본 접힘이어야 한다.
- **반대급부:** 이 경로를 닫는 변경 때문에 기존 `AuditRevisionBadge`/`AuditOverlay`가 사라지거나, 저장·발행·마감·역마감·DC 변경·재고감사 전이가 차단되거나, audit 조회 실패가 화면 전체 오류로 번지면 RED다.

### RED-B — 성공한 0건과 조회 실패의 양방향 구분

- 권위 있는 audit GET이 `200 + []`를 반환한 entity에서는 “아직 버전 이력이 없습니다.”가 보이고 실패 문구는 보이지 않아야 한다.
- 같은 사용자 화면에서 audit GET이 403·404·5xx 또는 네트워크 실패가 되면 “버전 이력을 불러오지 못했습니다.”가 보이고 “아직 버전 이력이 없습니다.”는 보이지 않아야 한다.
- **반대급부:** 실패를 구분하는 동안에도 화면 본문과 기존 핵심 CTA는 계속 도달 가능해야 하며, 실패 상태를 성공한 0건으로 캐시해 이후 정상 응답까지 가리면 RED다.

### RED-C — 목록 선택/라우트 entity 격리

- 마감 3화면과 DC에서 A를 열고 닫은 뒤 B를 선택하면 B의 이력만 보여야 한다.
- 모달이 열린 상태에서 실제 라우트 unmount 또는 선택 entity 소멸이 일어나면 A의 내용이 다음 entity 모달로 남지 않아야 한다.
- **반대급부:** entity 격리를 위해 모달을 닫더라도 B를 다시 열면 B의 최신 이력이 정상 조회되어야 하며, 정상 캐시까지 전역 삭제하면 RED다.

## ④ 범위 밖 — 지금 고칠 것과 분리할 것

### 지금 고칠 것

- 결함 A: 이번 슬라이스가 버튼을 노출한 6개 화면의 audit GET/기록 계약이 실 사용자 mutation까지 이어지지 않는 문제.
  - 도달성 근거: 상세/편집 진입 또는 목록 행 선택만으로 존재하지 않는 경로를 자동 호출한다.
- 결함 B: 7화면 전부 audit 조회 실패를 성공한 빈 이력으로 오표시하는 문제.
  - 도달성 근거: 여섯 화면은 현재 404로 상시 발화하고, 재고감사는 실제 권한·서비스·네트워크 실패에서 발화한다.

### 분리할 것

- audit 기록 기능이 없던 시기의 세금계산서·마감·DC 과거 변경을 추정해 backfill하는 작업.
  - 도달성 근거: 기존 entity를 연 사용자는 과거 이력이 없을 수 있으나, 원본 변경 사실을 복원할 권위 있는 표본이 없으면 가상 revision을 만들 수 없다. 이번 수정은 적어도 이후의 실제 mutation과 조회 성공/실패 진실성을 닫고, 과거 backfill은 별도 데이터 근거가 있을 때만 다룬다.
- 협업 changeSet 3개, `SlipDetailPage`, mobile-staff, 창고편집/입금자명매핑/아로로지스 역할이력, 아로로지스 저장 이력은 요청대로 제외한다.
- 모달 디자인 재설계, full-snapshot 복원 기능 추가, 운영 DB 직접 쓰기, Docker 재배포, 라이브 브라우저 QA는 제외한다.
