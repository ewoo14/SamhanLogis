## 3. P1-2 — 결합문자 U+0301로 정규화 판정을 우회한다

Java [`ActorDisplayName.java`](../../shared/common/src/main/java/com/samhanair/logis/common/security/ActorDisplayName.java)는 NFKC → `Cf` 제거 → dash/confusable folding을 사용한다(17~19행, 76~83행). TypeScript [`actorName.ts`](../../clients/web/design-system/src/utils/actorName.ts)도 같은 순서다(1~4행, 19~35행).

비교용 값 `c\u0301afebabecafebabecafebabecafebabe`는 U+0301을 제거하면 raw 32hex UUID가 되지만, 현재 구현에서는 UUID가 아니라고 판정된다.

임시 공격 테스트 원문:

```text
TypeScript:
expected 'ćafebabecafebabecafebabecafebabe' to be null

Java:
expected "변경자 미상"
but was "ćafebabecafebabecafebabecafebabe"
```

임시 테스트는 검증 후 제거했다.

### 변형 행렬

| 입력 변형 | Java | TypeScript |
|---|---:|---:|
| 대소문자 혼용 canonical UUID | 차단 | 차단 |
| 하이픈 없는 32hex | 차단 | 차단 |
| 앞뒤 ASCII 공백 | 차단 | 차단 |
| U+200B~U+200F, U+FEFF | 차단 | 차단 |
| 전각 문자·숫자·dash | 차단 | 차단 |
| RTL embedding U+202A/U+202C | 차단 | 차단 |
| **hex 사이 U+0301 결합문자** | **노출** | **노출** |

### 정상 이름 보존

비교용 정규화가 정상 표시 문자열을 망가뜨리는지 별도로 단정했다. 다음 이름은 Java/TypeScript 모두 원문 그대로 보존됐다.

- `김감사`
- `김 감사`
- `김감사/야간(대리) #1`
- `홍길동·품질_A팀`
- 자모 분해형 한글 `김감사`

따라서 현 결함의 수정은 **비교용 skeleton만** 강화하고 정상 이름의 반환 원문은 바꾸지 않아야 한다.

## 7. 수정 지시

### 지시 1 — 구조 검사를 AST/semantic 경계로 교체

- TS/TSX는 AST를 사용해 raw actor 표시 필드가 JSX, 템플릿 리터럴, 문자열 연결, formatter/helper, print/CSV/Excel/알림 payload로 흐르는 경로를 검사한다.
- Java는 getter 문자열 검색이 아니라 record component, field, constructor mapping, builder, Jackson DTO, 문자열 조립을 포함한 응답/출력 경계를 검사한다.
- client/service root는 하드코딩 목록이 아니라 repo의 실제 client/service 디렉터리에서 도출한다. 새 root를 추가하면 자동으로 모집단에 포함되어야 한다.
- 화면뿐 아니라 print, Excel/CSV, 알림, 이메일/SMS, 감사 API 등 사용자에게 나가는 모든 출구를 관할한다.
- 구조 검사를 일반 test/CI 필수 경로에 연결한다.

### 지시 2 — 비교용 Unicode skeleton을 닫는다

- 원문 표시값은 그대로 보존한다.
- 비교용 값만 NFKD/NFKC 기반으로 분해한 뒤 combining mark(`\p{M}`)와 format(`\p{Cf}`)을 제거하고 UUID skeleton을 판정한다.
- U+0300~U+036F만 열거하지 말고 Unicode mark category 전체를 다룬다.
- 보안 판정용 skeleton과 사용자 표시용 반환 문자열을 분리해 한글·공백·특수문자·정상 결합문자 이름을 변형하지 않는다.

### 지시 3 — 아래 mutation을 영구 RED 계약으로 추가

1. 직접 JSX
2. 별칭 변수 후 템플릿 리터럴
3. 문자열 연결
4. 신규 client/service root
5. Java record raw actorName response
6. 다른 service의 DTO
7. print/CSV/Excel
8. notification body
9. resolver-backed 정상 구성 GREEN

### 지시 4 — auth 양방향 계약 보존

- 이번에 복원된 actorId 저장·materialization·`findByActorId`를 삭제하거나 화면 차단과 결합하지 않는다.
- 수정 후에도 동일한 PUT → DB actor_id 역조회 → GET/화면 UUID 부재 계약을 반복한다.

### 지시 5 — 동일 격리 라이브 QA 재실행

- 공유 DB 로그인 없이 격리 PostgreSQL과 전용 서비스로 여섯 화면을 다시 밟는다.
- U+0301뿐 아니라 여러 Unicode mark category의 변형을 fixture로 넣는다.
- visible text, title, aria-label과 인쇄/다운로드 산출물까지 비교용 skeleton으로 스캔한다.
- 여섯 화면 모두 UUID/변형 UUID 0건이어야 한다.

위 미검토 표면은 현재 구조 검사가 자동으로 덮는다고 간주할 수 없다.

## 9. 최종 결론

구조 검사 주장은 공격 8형 중 7형을 놓쳐 거짓 GREEN이며, 정규화는 U+0301 변형에 뚫린다. 격리 실화면에서도 6개 중 4개가 실패했다. auth actorId 양방향 복원과 나머지 RED-B는 보존됐으므로 그 부분은 되돌리지 말고, 위 두 P1만 구조적으로 닫은 뒤 동일 mutation/라이브 QA로 재검토해야 한다.
