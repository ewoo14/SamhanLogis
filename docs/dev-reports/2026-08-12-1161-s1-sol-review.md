## 1. 판정 요약

핵심 계약인 “logging-service 로컬 opt-in”이 지켜지지 않았다. 저장소의 실제 기본 로컬 전체 스택 진입점인
`scripts/launch-local-stack.ps1`과 `.sh`는 `docker-compose.yml + docker-compose.local-all.yml`을 서비스
필터와 profile 없이 `up -d`한다. 변경된 `logging-service` 정의에도 profile이 없다. 따라서 사용자가 logging-service를
명시하지 않아도 기본 전체 스택 기동이 이를 생성·기동한다.

기본 인프라 파일 `docker-compose.yml`만 따로 보면 logging-service가 없는 것은 사실이지만, 이 좁은 확인은 실제 기본
로컬 런처의 동작을 증명하지 못한다. `docker compose --dry-run`에서 실제 기본 런처와 같은 합성 명령이
`samhan-logging-service Creating`과 `Created`를 계획하는 것을 재현했다.

핵심 전제가 무너졌으므로 지시서의 “전제가 틀렸으면 중단·보고”에 따라 logging-service 실기동, RabbitMQ 재선언,
POST/GET, ES 쓰기 검증은 수행하지 않았다. 공유 RabbitMQ/ES에 추가 쓰기를 만들지 않았다.

## 2. 발견 결함

### SOL-S1-01 — P1 차단: 기본 로컬 전체 스택이 logging-service를 자동 포함한다

**불변식**

- 평소 `launch-local-stack` 또는 동일한 `base + local-all up -d`는 logging-service를 생성·기동하지 않아야 한다.
- `logging-service`를 명시한 선택 기동만 이를 생성해야 한다.
- 기본 compose와 prod compose의 blob은 변경하지 않아야 한다.
- 기존 네트워크·볼륨·서비스 컨테이너를 재생성하거나 중지해서는 안 된다.

**좌표**

- `infrastructure/docker-compose.local-all.yml:159-190`: logging-service에 비활성 기본 profile 또는 동등한 opt-in gate가 없다.
- `scripts/launch-local-stack.ps1:46-48`: base와 local-all을 항상 합성한다.
- `scripts/launch-local-stack.sh:56-60`: 같은 합성 모델을 서비스 필터 없이 `up -d`한다.
- `docs/operational-validation/boot-and-smoke-validation.md:33-42`: base 파일만 “기본 기동”으로 취급해 실제 런처 경로를 누락했다.

**재현 데이터**

```text
docker compose -f infrastructure/docker-compose.yml config --services
→ logging-service 없음

docker compose -f infrastructure/docker-compose.yml \
  -f infrastructure/docker-compose.local-all.yml config --services
→ logging-service 있음

docker compose --dry-run -f infrastructure/docker-compose.yml \
  -f infrastructure/docker-compose.local-all.yml up -d --no-build
→ Container samhan-logging-service Creating
→ Container samhan-logging-service Created
```

base 단독으로 `up ... logging-service`를 시도하면 `no such service: logging-service`로 exit 1이었다. 이는 base 파일의
불변만 증명하며, 실제 기본 로컬 전체 스택이 local-all을 항상 합성한다는 위 재현을 반박하지 않는다.

**근본 원인**

local-all overlay 자체를 opt-in 수단으로 간주했지만, 이 저장소에서 local-all은 이미 기본 전체 로컬 런처가 항상 소비하는
파일이다. “파일을 명시해야 한다”는 전제가 실제 사용자 진입점과 다르다.

**구현자 지시 / RED 표적**

1. 먼저 자동 회귀 가드 또는 동등한 검증으로 다음 RED를 고정한다.
   - `logging-service` 정의에 명시적인 opt-in gate가 없으면 실패한다.
   - 기본 런처와 같은 합성 `up` dry-run에는 `samhan-logging-service` 생성 계획이 없어야 한다.
   - 명시적 `up ... logging-service`는 선택 기동 가능해야 한다.
2. 최소 수정 후보는 logging-service에 Compose profile을 부여하는 것이다. 명시적으로 서비스를 지정한 Compose 기동은
   해당 profiled service를 선택 실행할 수 있으므로 현재 문서의 단독 기동 UX를 유지할 수 있다. 구현자는 사용 중인
   Docker Compose 버전에서 이 동작을 RED/GREEN으로 직접 입증해야 한다.
3. `scripts/launch-local-stack.ps1/.sh`를 수정해 기본 서비스 목록을 좁히는 대안은 기존 22개 스택 계약 영향이 더 크므로,
   택한다면 전체 서비스 목록 회귀를 별도 증명한다.
4. 수정 후 plain base+local-all 기동, 명시적 logging 기동, 정리 후 plain 기동을 순서대로 확인한다. 전후 기존 컨테이너
   ID/health를 비교하고 다른 컨테이너를 재생성하지 않는다.
5. **profile/Compose 의미에 대한 전제가 틀렸으면 임의의 우회 구현을 계속하지 말고 중단·보고한다.**

### SOL-S1-02 — P2: 검증 보고서의 `git diff --check PASS`가 실제 결과와 다르다

**좌표**

**재현**

```text
git diff --check 72cab52e..b2d45df4
→ docs/dev-reports/2026-08-12-1161-s1-local-logging-service.md:3: trailing whitespace.
→ docs/dev-reports/2026-08-12-1161-s1-local-logging-service.md:4: trailing whitespace.
```

**지시**

줄 끝 공백을 제거하고 같은 base/HEAD 범위로 재실행해 exit 0을 확보한 뒤 보고서 기록을 갱신한다. 검증 명령의 대상 범위와
exit code를 원문에 함께 남긴다. 전제가 틀렸으면 PASS 문구를 유지하지 말고 중단·보고한다.

### SOL-S1-03 — P2: 요구된 `GET /logs/activity` 빈 결과 증거가 없다

PR 보고서 `docs/dev-reports/2026-08-12-1161-s1-local-logging-service.md:95-100`은 POST 직후 GET을 실행했고,
`items` 1건, `totalElements=1`을 기록했다. 검토 시작 시 기존 `samhan-audit-logs` index에도 동일한 프론트 QA 문서가
1건 남아 있었다. 이것은 POST가 저장됐다는 증거지만, S2 발행자가 없어 활동 로그가 비어 있다는 요구의 증거는 아니다.

**지시 / RED 표적**

- 재검토에서는 POST 전의 깨끗하거나 격리된 검색 조건으로 `GET /logs/activity 200`과 빈 `items`를 먼저 입증한다.
- 그 뒤 고유한 검증 event를 POST하고, 응답 200뿐 아니라 해당 고유 event를 ES에서 조회해 저장을 입증한다.
- 기존 공유 데이터 삭제로 빈 배열을 만들지 않는다. 격리 조건이 불가능하면 공유 index를 임의로 정리하지 말고
  전제가 틀렸음을 중단·보고한다.
