## 2. 판정

**도달 결함 2건. R11 재수렴 불통과.**

1. **분류 축 누락:** 실제 입력 데이터 실패가 `DataAccessException`이 아닌 `IllegalArgumentException`으로 발생한다. 기존 거래처의 음수 여신한도 행은 두 bucket 어디에도 들어가지 않고 HTTP 400으로 파일 전체 흐름을 중단한다. 앞 정상행은 이미 커밋되고 뒤 정상행은 처리되지 않는다.
2. **호출자 계약 소실:** 직접 partner 응답에는 `infrastructureFailure=true`가 보이지만, 실제 재import 호출자인 `EcountRemoteImportClient`가 그 필드를 파싱하지 않는다. 200 인프라 실패 응답을 `imported=0, rejected=0`으로 축약해 상위 관리자 경로에 전달한다.

R10이 직접 고친 원 결함은 해소됐다. 잠금 대기 JDBC PID만 종료한 표본은 `DB_INFRASTRUCTURE`, `infrastructureFailure=true`로 정확히 응답됐다. R8/R9가 얻은 201자 데이터 실패 격리, 삭제행 UUID, 정본 7,253건 분포, 수정 파일 재적재도 모두 유지됐다.

| 각도 | 판정 |
|---|---|
| 1. 축이 옳은가 | **FAIL** — 입력 데이터 실패의 제3축(`IllegalArgumentException`)이 실제 도달 |
| 2. 원 결함 해소 | PASS — 요청 JDBC PID 종료 → `DB_INFRASTRUCTURE`, boolean `true` |
| 3. 반대급부 | PASS — 201자 격리·UUID·7,253 분포·수정 재업로드 유지 |

## 3. 각도 1 — 저장 실패 전수와 분류 축

### 3.1 importer가 실제로 쓰는 입력·제약 열거

`upsertPartner()`가 이카운트 행에서 변경하는 컬럼과 현재 PostgreSQL/JPA 제약을 전수 대조했다. 같은 실패 성격은 한 행으로 묶되 실제 컬럼은 모두 적었다.

| 실제 발생 가능한 실패 | 대상 컬럼 / 조건 | 실제 Spring/Java 경로 | 현재 축 | 판정 |
|---|---|---|---|---|
| 문자열 길이 초과 | `partner_code`·`biz_no` 100, `name` 200, `address`·`address1` 500, `phone` 50, `sub_biz_no` 20, `representative` 50, `mobile` 50, `search_keyword` 500, `partner_group1` 50, `transfer_info` 20, `manager_name` 50 | Hibernate `DataException` → Spring `DataIntegrityViolationException` | `DB_CONSTRAINT` + held | 맞음. 201자 이름 실측 |
| 숫자 정밀도 초과 | `credit_limit NUMERIC(15,2)`의 정수부 초과 | `DataIntegrityViolationException` | `DB_CONSTRAINT` + held | 맞음 |
| 활성 유일키 충돌 | `ux_partners_partner_code_active`, `ux_partners_biz_no_active`; 특히 동시 신규/복원 race | `DataIntegrityViolationException` | `DB_CONSTRAINT` + held | 타입상 맞지만 입력 자체 중복과 동시성 race를 같은 이름으로 묶음 |
| 음수 여신한도 — 기존 행 | `replaceCreditLimitFromImport(-1)` | **`IllegalArgumentException`**, `DataAccessException` 아님 | 어느 축에도 없음; HTTP 400 | **오분류가 아니라 축 누락. 도달 결함** |
| 음수 여신한도 — 신규 행 | `Partner.register(..., -1)`에는 동일 가드 없음 | 예외 없이 저장 | 성공으로 계상 | 예비 실행에서 HTTP 200/imported=1 실측. 기존/신규 비대칭 |
| DB 연결 종료·rollback 실패 | row transaction의 JDBC 연결 단절 | `JpaSystemException` (`DataAccessException`) | `DB_INFRASTRUCTURE` | 맞음. 실측 |
| deadlock·lock timeout·연결 획득 실패 | row transaction query/commit | `CannotAcquireLockException`, `QueryTimeoutException`, `DataAccessResourceFailureException` 등 non-integrity `DataAccessException` | `DB_INFRASTRUCTURE` | 재시도 축으로 타당 |
| staging 선행 쓰기 실패 | `stagingUpsert()`의 DB 불능 또는 `imported_by VARCHAR(50)` 초과 | catch보다 **앞**에서 발생 | 응답 boolean 없이 요청 실패 | 유효 auth UUID는 36자라 길이 초과는 정상 사용자 경로 아님. DB 불능은 가능하나 R9에서 이미 구분한 지속 장애 형태 |
| 실패 후 staging 상태 갱신 실패 | row 실패 catch 뒤 `updateStagingStatus()` 시 DB가 계속 불능 | catch 밖 재실패 | 응답 boolean 없이 요청 실패 | R9의 지속 장애 경로와 동일, 이번 재진단 대상 아님 |

실패하지 않고 별도 정책으로 수렴하는 입력도 확인했다.

- 거래처명 빈값 → `REJECT_NAME_NULL`
- 거래처코드 빈값/CSV placeholder → `SKIPPED_PLACEHOLDER`
- 숫자가 아닌 여신한도 → `null`로 저장
- 잘못된 등록일 → `registration_date=null`, 배치 적재시각 사용
- `note`는 `TEXT`라 길이 제약 없음
- status는 입력 문자열을 직접 저장하지 않고 코드가 `ACTIVE/SUSPENDED`만 생성

## 6. 각도 4 — 응답 계약과 관리자 화면

### 6.1 직접 API 응답

각도 2 원문처럼 직접 partner 관리자 API 호출자는 응답 본문에서 `infrastructureFailure=true`와 `DB_INFRASTRUCTURE` 표본을 볼 수 있다. 이 좁은 계약은 PASS다.

### 6.2 실제 상위 호출자에서 필드 소실

실제 MIG-1 재import 경로는 `EcountReimportService`가 다음 endpoint를 `EcountRemoteImportClient`로 호출한다.

```text
partner-service /admin/partners/imports/ecount
```

그러나 `EcountRemoteImportClient.parse()`가 읽는 필드는 아래뿐이다.

```text
imported + updated + aliasImported + lineAdded
rejected + rejectedNullName
sourceFileHash
```

`heldParseFailureRows`, `infrastructureFailureRows`, `infrastructureFailure`는 전부 버린다. 따라서 각도 2의 HTTP 200 응답은 상위 관리자 재import 경로에서 `imported=0, rejected=0`으로 축약되고 실패 신호가 남지 않는다. desktop 소스의 `infrastructureFailure` 소비자는 0개였고, 직접 거래처 이카운트 업로드 화면/API client도 없었다. mock 알림의 deeplink `/admin/ecount/reimport`만 존재한다.

### 6.3 실 화면 확인 상태

인앱 브라우저와 연결된 외부 브라우저를 조회했으나 사용 가능한 브라우저가 0개라 실제 관리자 화면을 열어 캡처하지 못했다. 다른 브라우저 제어 수단으로 가장하지 않는다. 따라서 화면 자체의 육안 확인은 **미완료**다.

다만 화면 유무와 별개로, 실제 상위 호출자가 boolean을 폐기하는 계약 결함은 코드 원문으로 확정된다. 화면이 이 상위 결과를 표시하면 인프라 실패를 성공/0건으로 오해한다.
