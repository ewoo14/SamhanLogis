  (`scripts/app-build-version.cjs:42-62`).
- `VITE_APP_VERSION` 부재, `2026/7/30-2`, 실제로 존재하지 않는 날짜는 builder
  spawn 전에 종료한다 (`scripts/app-build-version.cjs:100-113`).
- 유효한 `2026/07/30-2`는 `1.20260730.2`가 되어 두 wrapper에서 통과한다. 따라서
  정상 release를 막는 fail-fast 오탐은 확인되지 않았다.
- AROLOGIS의 `AROLOGIS_UPDATE_URL` 필수 검사는 기존 정상 release 전제이며 이번
  semver 검사의 오탐이 아니다.

버전 계산 단계에서 두 앱의 실제 electron-builder 25.1.8 CLI parser는
`--config.extraMetadata.version=1.20260730.2`를
`config.extraMetadata.version`으로 읽었고, 실제 app-builder-lib transformer는
두 포장 대상 `package.json.version`을 모두 `1.20260730.2`로 만들었다.

인자 이름과 형식은 electron-builder 25.1.8의 tagged source가 예시하는
`--config.extraMetadata.foo=bar` 계약과 일치한다:
[electron-builder 25.1.8 builder.ts](https://github.com/electron-userland/electron-builder/blob/electron-builder%4025.1.8/packages/electron-builder/src/builder.ts#L294-L297).

단, Windows 숫자형 VERSIONINFO는 네 개의 16-bit 구성요소만 표현한다.
app-builder-lib는 `1.20260730.2`를 `1.20260730.2.0`으로 계산한다
(`clients/desktop/node_modules/app-builder-lib/out/appInfo.js:66-85`).
NSIS 쪽은 이 값을 거부하기보다 WORD로 절삭하는 경로여서 정상 release 중단
결함으로 집계하지 않았다. app executable의 실제 rcedit 결과와 Windows에 기록되는
최종 숫자형 값은 installer 생성 게이트에서 확인해야 한다.

   0건이라고 구분했다.
6. 열린 PR 충돌 판정은 조사 도중 바뀐 #994의 이전 head가 아니라 최종
   `82f922ee…` 기준이다.
7. 전체 Windows 포장을 금지한 조건을 지켰다. installer 산출을 가장한 mock이나
   실패한 외부 cache probe를 결함 증거로 사용하지 않았다.

## 6. 머지 가능 여부

**명시적 판정: 현재 HEAD `ede7b83d5`는 머지 불가다.**

결함 A는 로그인한 모든 Samhan Public DESKTOP 사용자에게 잘못된 semver를 보여주고,
결함 B는 두 제품의 표준 NSIS 설치·Windows 설치 앱 경로에서 업데이트 비교 전용
semver를 사용자에게 보여준다. 두 결함 모두 제품의 날짜 버전 표시 불변식을
실사용 경로에서 위반한다.

기존 설치본의 첫 업데이트 안내 문제는 개발책임자 확정대로 첫 롤아웃 수동 설치
계획에 남기며 이 라운드 결함으로 재보고하지 않는다.

## 7. 실제 배포 시점에 남는 게이트

머지 전 결함 A·B를 해소한 뒤에도 실제 배포 시 다음을 모두 통과해야 한다.

1. 두 앱의 코드서명된 NSIS installer와 필요한 portable 산출물을 실제 생성한다.
2. installer 파일명, 설치 창 branding, Windows 설치된 앱 `DisplayVersion`,
   실행 파일·installer VERSIONINFO가 사용자 날짜 버전과 일치하는지 확인한다.
   특히 `1.20260730.2.0`의 16-bit 구성요소 절삭 여부를 실제 산출물에서 확인한다.
3. clean Windows에서 두 installer를 설치하고 앱 기동·로그인·사이드바 표시를
   확인한다.
4. 이전 지원 설치본에서 실제 `latest.yml`과 blockmap을 사용하는 업데이트를
   감지·다운로드한다.
5. 두 앱에서 `quitAndInstall` 후 실제 종료·재기동·신 버전 기동을 확인한다.
6. 실제 HTTPS feed의 `latest.yml.version`이 내부 비교용 `1.YYYYMMDD.N`이고,
   URL이 날짜형 artifact를 정확히 가리키며 코드서명이 검증되는지 확인한다.
7. 첫 롤아웃은 확정된 배포 계획대로 기존 `0.1.0`/`1.0.0` 사용자에게 수동
   installer 설치를 안내한다.
8. 사내 비공개 feed나 실 PC에 `20260730.N.0` 설치본이 없음을 배포 자산
   inventory로 최종 확인한다.

## 이 라운드가 보지 않은 것

- 전체 `build:win`, 실제 installer·portable·`app.asar`·`latest.yml`·blockmap·코드서명
- clean Windows 설치, Windows 설정 앱과 파일 속성의 실제 캡처
- 실제 HTTPS 업데이트 feed, CDN 캐시, 운영 정책 DB와 업로드 이력
- `quitAndInstall`의 실제 종료·재기동
- 저장소 밖 사내 비공개 feed, 수동 반출 파일, 사용자 PC 설치 inventory
- Docker·Gradle과 다른 트랙이 사용하는 실행 환경
- 이미 확인된 exact SHA CI 49/49와 개발 모드 라이브 QA의 재검증
- 개발책임자가 배포 계획으로 이관한 기존 설치본 첫 롤아웃 문제의 재판정
