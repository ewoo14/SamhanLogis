## A. 기존 마감 구조

### A-1. `DailyClosing`

근거: `services/accounting-service/src/main/java/com/samhanair/logis/accounting/domain/DailyClosing.java:52-116,118-175,178-234`.

스키마/도메인 필드는 다음과 같다.

| 필드 | 의미 |
|---|---|
| `id` | 내부 UUID |
| `closingDate` | 마감 대상 날짜 (`closing_date`, NOT NULL) |
| `partnerId` | 거래처 UUID, NULL이면 전체 거래처 |
| `closingKind` | `SALES`/`PURCHASE` |

`DailyClosing`은 원래 특정 날짜의 매출/매입 집계 snapshot이며, `partnerId=NULL`이 전체 거래처 통합 마감이라는 기존 모델은 있다. 그러나 한 날짜에 `closingKind`와 `sourceKind` 조합이 붙고, 금액·전표건수 snapshot도 필수다. 따라서 이번의 “거래처 무관한 날짜 집합”을 그대로 표현하려면 최소한 거래처·집계종류·source·집계 snapshot의 의미를 무시하는 별도 행 규칙이 필요하다. 기존 unique 제약/조회/집계 경로가 조합에 의존하는지 확인 없이 재사용하면, 같은 날짜의 단일 마감과 여러 snapshot이 충돌하거나 UI에 집계 행이 여러 개 보일 위험이 있다.

판정: **그대로 재사용할 수 없다.** `partnerId=NULL`은 축 하나만 맞출 뿐이며, `DailyClosing.isLocked`도 전표 생성 차단의 전역 진실원이 아니다. 새 날짜 마감 저장 모델을 별도로 두거나, 기존 구조를 확장하되 “날짜 집합 마감”과 집계 snapshot을 명시적으로 분리해야 한다.

### A-2. `AccountingPeriod`와 `AccountingPeriodGuard`

`AccountingPeriod` (`.../AccountingPeriod.java:50-118`)는 `periodType`(`DAILY`/`MONTHLY`), `periodDate`, `status`(`OPEN`/`CLOSED`), `closedAt/By`, `reversedAt/By`, 매출·매입·판관비 합계, `lockedSlipCount`, `description`, `version`을 가진다. 월 단위에서는 `periodDate`를 월 1일로 normalize한다. `close()`는 OPEN→CLOSED, `reverse()`는 CLOSED→OPEN이며 이전 마감 audit stamp를 보존한다.

`AccountingPeriodGuard` (`.../AccountingPeriodGuard.java:27-113`)는 accounting-service의 interceptor다. POST `/accounting/journals`의 `journalDate`, POST/PUT `/accounting/tax-invoices`의 `supplyDate`를 읽고 `MonthEndCloseService.findClosedPeriodCovering(date)`가 기간을 반환하면 CONFLICT를 낸다. `/accounting/closings` 자체는 제외한다. 즉 월 CLOSED 기간의 “포함되는 모든 날짜”를 막는 연속 기간 guard이며, 이번 요구의 개별 날짜 집합 semantics와 다르다. 또한 slip-service 전표 생성 경로에는 연결되어 있지 않다.

### A-3. `slips.lock_flag`, `requireNotLocked()`, `lock-by-period`

`Slip`의 lock 도메인 경로는 `services/slip-service/src/main/java/com/samhanair/logis/slip/domain/Slip.java:1413-1441`이다.

- `lock()`은 `lockFlag=true`만 설정한다.
- `requireNotLocked()`는 `lockFlag=true`이면 CONFLICT를 낸다.
- 현재 확인된 호출은 매출 전표 삭제 validation (`:1390-1405`), `reject()` (`:1254-1263`), `cancel()` (`:1284-1297`), revision snapshot 복원 (`:2216-2224`) 등 기존 전표 mutation 일부다.
- 일반 신규 생성 시 `lock_flag`를 검사하지 않는다. 신규 전표는 아직 lock 대상 전표가 아니므로 이 구조만으로 신규 “마감 날짜”를 막을 수 없다.

`POST /internal/slips/lock-by-period`는 `SlipInternalController:260-283`에 있다. 내부 토큰 인증과 `@PreAuthorize("hasRole('MASTER')")`를 사용하고, `LockByPeriodRequest(startDate,endDate,status)`로 기간+상태를 받아 `SlipService.lockByPeriod()`가 일괄 lock한다. 기본 상태는 CONFIRMED다. 이는 **연속 날짜 범위의 기존 전표 lock** 계약이고, 개별 날짜 집합의 신규 생성 guard 계약과 다르다.

### A-4. 해제 경로와 칩 제거의 연결 가능성

`DailyClosing.unlock()` (`DailyClosing.java:197-213`)은 `isLocked=true`를 false로 되돌릴 뿐이며 `lockedAt`/`lockedBy`는 보존한다. `DailyClosingService.unlock()` (`.../DailyClosingService.java:272-318`)은 날짜·거래처·kind·source 조합으로 기존 행을 찾아 호출한다. Controller는 `PATCH /accounting/daily-closings/{closingDate}/lock` + `{"locked":false}`만 허용하고, `accounting.daily-closing.unlock` UPDATE 권한을 요구한다 (`DailyClosingController.java:121-170`).

따라서 기존 `unlock()`은 “해당 snapshot의 잠금 flag 해제”에는 얹을 수 있지만, 날짜 집합 칩 제거의 정본으로 바로 사용하기에는 거래처/kind/source 식별자가 필요하고 신규 날짜 모델의 행을 찾지 못한다. 더 중요한 점은 `unlock(actorUserId)`가 actor를 검증만 하고 별도 해제 audit 행/event를 만들지는 않는다는 것이다. `BaseEntity`의 수정 audit와 기존 stamp 보존은 있으나, 이슈가 확정한 “마감·해제 양쪽 감사 기록”을 만족하는지 별도 audit 설계 확인이 필요하다.

## C. 동적 권한

### C-1. PageCode 신설 흐름

`services/auth-service/src/main/java/com/samhanair/logis/auth/domain/PageCode.java:16-21`의 절차는 enum 상수 추가 후 Flyway V8+ seed row 추가다. 실제 권한 저장은 기존 `role_page_permissions`에서 V39 이후 `role_page_permission_templates`, `account_page_permissions`로 확장되었고, V42의 `permission_groups`, `group_page_permissions`, `account_permission_overrides`, V43/V44의 기본 그룹·계정 materialize 흐름을 거친다.

`products.admin` 전체 예시는 `services/auth-service/src/main/resources/db/migration/V10__sp_d4_remaining_domains_page_permissions.sql:247-256`이다. 역할별 VIEW/EDIT row를 모두 삽입한다. V39 이후 새 코드의 정본은 `role_page_permission_templates`에 역할별 template를 넣고, 필요 시 비-MASTER 계정에 materialize하는 방식이다. 기존 V39 설명은 MASTER가 bypass되어 계정 materialize 대상이 아님을 명시한다.

### C-2. 기본 MASTER·MANAGER만

이번 코드의 seed는 다음처럼 **두 역할 row만** 두고 둘 다 VIEW/EDIT를 true로 하는 형태가 맞다.

```sql
('MASTER',  '<new.page.code>', TRUE, TRUE, NOW(), 'system', NOW(), 'system', FALSE),
('MANAGER', '<new.page.code>', TRUE, TRUE, NOW(), 'system', NOW(), 'system', FALSE)
```

`products.admin`의 ACCOUNTANT/SALES/WAREHOUSE/DISPATCH/INVENTORY row처럼 false를 넣는 방식도 가능하지만, “기본값은 MASTER·MANAGER만”이라는 확정 요구에는 다른 역할 row를 만들지 않는 것이 명확하다. V39+ 권한그룹 흐름을 정본으로 택하면 동일한 두 역할만 template/group permission으로 seed하고, 기본 계정 materialize 정책과의 중복 여부를 확인해야 한다.

### C-3. 서버 확인 방식

`@RequirePermission`은 controller method 진입 시 고정 page/action을 검사하는 데 쓸 수 있다. 실제 전표 생성 controller는 현재 `SlipController.java:302-310`에서 slip type별 생성 권한을 별도로 확인한 뒤 service를 호출한다. 하지만 “마감 날짜면 차단, 권한자는 예외”는 요청의 `slipDate`와 계정 권한을 함께 판단해야 한다.

공통 `DynamicPermissionClient` (`shared/security/src/main/java/com/samhanair/logis/security/permission/DynamicPermissionClient.java`)는 `check(UUID accountId,pageCode,action)`와 역할 기반 `canView/canEdit`을 제공하고, `DefaultDynamicPermissionClient.java:68-80,147-164`가 auth-service의 internal permission check를 호출한다. 따라서 서비스 층에서 요청자 `X-User-Id`를 account UUID로 받아 새 PageCode의 예외 권한을 직접 `check(..., PermissionAction.CREATE/UPDATE)`하는 방식이 가능하다. `@RequirePermission`만 생성 endpoint에 붙이면 “생성 권한”과 “마감 예외 권한”을 분리해 표현하기 어렵고, 날짜 판정 전후의 예외 semantics도 서비스에서 보장해야 한다.

권한자 예외의 정확한 action은 판단 필요 사항이다. 기본 seed를 VIEW+EDIT로 할지, CREATE/UPDATE 중 어떤 action을 예외로 사용할지는 기존 PageCode action 계약과 맞춰 결정해야 한다.

## E. 칩 UI primitive

### E-1. 기존 계약

- `TagChip` (`clients/web/design-system/src/components/TagChip/TagChip.tsx:10-22,24-39,122-149`): `value` 필수, 선택 `label`, `onRemove`, `removeLabel`을 제공한다. `onRemove`가 있으면 X 버튼을 렌더하고, 제거 click은 stopPropagation한다. label 없이 value-only 표시가 가능하다.
- `FreeTextChipInput` (`.../FreeTextChipInput.tsx:15-30,106-180,194-220`): `string[]`을 단일 진실원으로 받고, Enter/쉼표/blur/`flush()`로 입력을 확정하며 각 항목은 TagChip으로 표시·제거한다. 문자열 날짜를 직접 입력해 칩 목록으로 관리하는 primitive다.
- `MultiSelectAutocomplete` (`.../MultiSelectAutocomplete.tsx:14-76,109-151,172-220`): 후보 검색 기반이다. `selected[]`, `onAdd`, `onRemove`, opaque key, 검색/표시 renderer를 요구하며 내부 칩은 TagChip이다. 날짜 후보를 검색/선택해야 할 때 적합하다.

날짜를 칩으로 관리하는 동일 업무 사례는 확인하지 못했다. `DailyClosingPage.tsx:902-941`은 거래처 범위의 TagChip을 쓰고, `GroupwareApprovalTemplateAdminPage.tsx:441-448`은 FreeTextChipInput으로 SELECT 옵션 문자열 목록을 관리한다. 즉 날짜 칩 전용 precedent는 없지만 primitive 자체의 계약은 충분히 재사용 가능하다.

### E-2. 제안

날짜를 자유 입력하고 `yyyy-MM-dd` 정규화·중복 제거·내림차순 정렬해야 한다면 `FreeTextChipInput` + `TagChip` 조합이 가장 직접적이다. 다만 현재 `FreeTextChipInput`은 문자열을 append하고 입력 순서를 보존하므로, 부모가 날짜 검증과 정렬을 담당해야 한다. 서버가 후보 날짜 목록을 제공하거나 date picker 선택이 정본이면 `MultiSelectAutocomplete`의 `selected[]/onAdd/onRemove`와 `renderChip`에 날짜 표시를 주입하는 편이 안전하다.

추가로 기존 컴포넌트는 날짜 parsing/최소·최대 날짜/선택 날짜의 내림차순 정렬을 책임지지 않는다. 신규 컴포넌트 hand-roll 없이 부모 상태 변환과 기존 `TagChip`을 사용해야 하며, UUID는 사용자 표시값에 포함하지 않아야 한다.

## 판단이 필요한 것

1. 새 저장 모델을 `DailyClosing` 확장으로 할지, 거래처·집계 snapshot과 분리된 날짜 집합 마감 테이블로 둘지 결정이 필요하다. 본 정찰 판단은 **별도 모델 또는 명시적 분리** 쪽이다.
2. “마감 날짜”의 대상 필드를 `Slip.slipDate`로 확정할지 확인이 필요하다. 코드상 생성 경로의 공통 날짜는 `slipDate`지만, 회계의 `journalDate`/`supplyDate`, 배송의 `unloadDate`, 확정 시점의 accounting date는 서로 다른 업무 의미다.
3. 마감 날짜 차단 대상을 수동 생성·복사·견적 발행·거래처 주문 발행·주문 병합·모바일 주문의 모든 OUTBOUND와 수동 INBOUND까지로 할지, 또는 특정 전표 종류만으로 제한할지 결정이 필요하다. 이슈 요구만으로는 “신규 전표” 전체가 자연스럽지만 기존 cutoff 주석은 출고 중심이다.
4. `editHeader`의 배송태그 확정은 RED-E(기존 수정 불변) 때문에 새 날짜 차단 대상에서 제외하는 것이 맞는지 확인이 필요하다. 현재 `editHeader`는 날짜를 바꾸지 않지만 기존 컷오프 guard는 두 지점에 있다.
5. 권한 예외의 PageCode action을 CREATE, UPDATE, 또는 별도 action 중 무엇으로 seed하고 검사할지 결정이 필요하다. 기본 seed 범위는 확정대로 MASTER·MANAGER만이다.
6. 권한자 예외를 “마감 날짜 신규 생성만” 허용할지, 마감/해제 칩 관리 API에도 동일 권한을 쓸지 결정이 필요하다. 현재 DailyClosing unlock은 별도 `accounting.daily-closing.unlock` UPDATE 권한을 사용한다.
7. 칩 제거의 감사 기록을 기존 BaseEntity 수정 audit만으로 인정할지, 마감/해제 각각 별도 audit row/event를 신설할지 결정이 필요하다. 기존 `DailyClosing.unlock()`은 flag만 false로 만들고 `lockedAt/By`를 보존한다.
8. RED-B 기준선의 검증 범위를 active 367건으로 할지, 삭제 포함 2,542건도 별도 보존 기준으로 기록할지 결정이 필요하다. 본 보고서는 active 367건을 사용자 행위 기준선으로 권장한다.
