### Throwaway 실 GUI 생성 및 차단

- `dev_manager`로 실제 renderer에 로그인했다. renderer는 `VITE_MOCK_MODE=0`, `VITE_APP_VERSION=2026/08/03-87400`, API는 `http://127.0.0.1:8080`을 사용했다.
- 판매전표 작성 화면에서 `QA-874-A`, `QA-874-B`를 저장했다. 두 건 모두 게이트웨이 `POST /slips`가 `201`을 반환했다. A/B는 패널-본체-패널 의도였으나 `PC1` 자동확장으로 6개 라인이 저장됐다.
- 같은 GUI 경로에서 자동확장 없는 단순 모델 조합으로 `QA-874-C`, `QA-874-D`도 저장했다. 각 건은 `AR-EH05` 3라인이며 `POST /slips` `201`이다.
- C에서 GUI의 `완료(저장)` → `완료(전송)`까지 진행했다. `POST /slips/{id}/save`와 `/send`는 각각 `200`이었다.
- GUI의 `완료(수락)`에서 `POST /slips/32174043-11a5-4967-b8ff-759e25934c9d/accept`가 `409`로 실패했다. 화면 원문:

  `inventory-service 호출 실패(400 BAD_REQUEST): {"success":false,"code":"INVALID_INPUT","message":"productCode: productCode 는 필수이며 공백만으로 구성될 수 없습니다"...}`

- A도 동일한 `accept` 단계에서 동일 원문으로 실패했다. 번들 자동확장 여부와 무관하게 재현됐다. 수락 실패로 출고 원천이 생성되지 않아 회계 매출전표 배분·전기까지 도달하지 못했다.
- 증거: `20-*` 작성 전 화면, `21-*` 저장 후 화면, `30-accept-409-productCode.png`.

## 결함

### BUG-874-LIVE-01 — 판매전표 수락이 `productCode` 누락으로 출고·회계 체인을 차단

재현 절차:

1. `dev_manager`로 로그인한다.
2. 판매 → 새 판매전표에서 `HQ-001`, 거래처 `P0-6-C002`, 표식 `QA-874-C`를 입력한다.
3. `AR-EH05` 3라인을 입력하고 저장한다(`POST /slips` 201).
4. 상세에서 `완료(저장)` → `완료(전송)` → `완료(수락)`을 누른다.
5. `POST /slips/{id}/accept`가 409가 되고 화면에 `productCode 는 필수이며 공백만으로 구성될 수 없습니다`가 표시된다.

영향: 실제 출고 원천 및 `POSTED` 회계 매출전표가 만들어지지 않아 PR #1057의 시나리오 2~5를 라이브 판정할 수 없다. 이번 라운드는 결함 없음이 아니라 **선행 체인 결함으로 미실시**다.
