## 1. R3 MASTER PRINT 제거 뮤테이션

R3에서 사용한 형태대로 MASTER의 전체 7액션에서 PRINT만 제거했다.

```ts
permissions[page] = page === 'inbound.inspection'
  ? allActions.filter((action) => action !== 'PRINT')
  : allActions
```

결과는 RED였다.

```text

```

R4 정본은 PRINT뿐 아니라 RESTORE와 DOWNLOAD도 제거한 `1111000`이므로, PRINT만 제거한
R3 뮤테이션 `1111110`을 정확히 구별한다.

복구 후 다음 blob hash가 HEAD와 일치했다.


### 3.3 실 백엔드 MASTER 계약

2026-08-09 09:35:44 KST, 로그인 없이 auth-service의 읽기 전용
`GET /auth/admin/permissions/my`를 실 계정 identity header로 호출했다.

```text
MASTER  CREATE,DELETE,DOWNLOAD,PRINT,RESTORE,UPDATE,VIEW = 1111111
MANAGER VIEW                                           = 1000000
```

원문도 같은 의미다.

- `PermissionAdminController.java:242,259-260`: `X-Is-System-Master=true`이면
  `allPageActions()` 반환
- `AccountPermissionService.java:62-63`: 시스템 MASTER 계정의 개별 권한 check는 항상
  `true`
- R4 mock 원문 `mock.ts:13928`: `inbound.inspection`만 `allActions.slice(0, 4)`

즉 실 DB의 MASTER template `1111000`은 런타임 MASTER 권한 정본이 아니다. MASTER는
계정 캐시를 materialize하지 않는 시스템 우회 계정이며 실 계정의 해당 캐시 행도 없다.
R4는 DB snapshot에는 맞지만 실제 `/permissions/my` 응답에는 맞지 않는다. 다만 현재 UI의
해당 액션 소비가 0개이므로 이 라운드의 도달 결함 수에는 포함하지 않았다.

### 4.2 실 데이터 차단 수

측정 시각 2026-08-09 09:32:28 KST.

```text
INBOUND + INSPECTING = 2건
2026/08/08-3
2026/08/08-4
```

현재 공유 DB 기준 MANAGER에게 잘못 차단되는 실 전표는 2건이다. 이는 PR 코드 결함이 아니라
미머지 V98이 공유 DB에 아직 적용되지 않은 환경 상태다. V98의 additive projection을 적용하면
세 MANAGER 계정 모두 두 권한을 만족해 이 차단은 0건이 된다.

허용되면 안 되는 역할의 `inbound.inspection:UPDATE` template grant는 0행이었다. 현재
허용 역할은 WAREHOUSE·INVENTORY이고, V98 후 MANAGER가 추가되며 MASTER는 시스템 우회다.
ACCOUNTANT·SALES·DISPATCH·DRIVER·STAFF·DEVELOPER·PARTNER는 모두 false다. 대상 전표
2건 기준 의도된 차단은 7역할 × 2건 = 14 role-slip 조합이다.

쓰기 금지 때문에 `/inspection/complete`는 호출하지 않았다.
