# #1069 S30 SOL fix 지시서 — mock E2E의 실 API 누출

## 판정

**개발책임자가 제시한 (가)/(나) 양자택일 전제가 틀렸다.** 세 SHA의 CI red는 옛 계약 단언이나 실외기 옵션 기능 단절을 아직 증명하지 않는다. `VITE_MOCK_MODE=1` 전용 spec이 새 `POST /slips/expand-line`을 mock하지 않아 실제 기본 API(`localhost:8080`)로 누출되고, CI에서는 연결 실패를 제품 전개 실패로 처리한 것이 직접 원인이다.

이 라운드의 단 하나의 질문에 대한 답은 **현재 증거로 재현 가능한 실 사용자 결함은 확정되지 않았다**이다. 다만 mock hard gate가 외부 서버 유무에 따라 red/green이 바뀌므로 **증거 무결성 결함 1건**이며, 게이트 ②가 닫히기 전에는 머지 비권고다. 지시의 “전제가 틀리면 중단”에 따라 ① S29 표면 검증은 수행하지 않았다.

재현 난이도: **하(100%, 약 18초)**. Docker·DB 없이 `VITE_API_BASE_URL=http://127.0.0.1:1`로 실행하면 문제의 두 시나리오가 모두 같은 DOM 원문으로 실패한다.

## 1. 좌표와 재현 증거

- `clients/desktop/src/renderer/api/slip.ts:310-318` — 화면이 `POST /slips/expand-line`을 호출한다.
- `clients/desktop/src/renderer/api/mock.ts` — 이 경로의 handler가 없다. 함수 말미의 `return null`로 빠진다.
- `clients/desktop/src/renderer/api/client.ts:63-68` — mock mode라도 `getMockResponse(config) === null`이면 adapter를 설치하지 않아 실제 Axios 요청으로 진행한다.
- `clients/desktop/src/renderer/routes/SlipFormPage.tsx:949-1002` — 요청 실패를 catch한 뒤 원래 BUNDLE 행을 오류가 든 빈 행으로 교체한다.
- `clients/desktop/playwright/bundle-set-options/bundle-set-options.spec.ts:15-20,94-129` — spec은 스스로 mock 전용이라 선언하지만 전개 endpoint 응답은 고정하지 않았다.
- `origin/main`과 HEAD의 해당 spec blob SHA는 둘 다 `278c437817071b9fc1f8e0962ac3da30ba2b1212`로 동일하다. 반면 `origin/main`의 `SlipFormPage`에는 `expandBundleLine` 호출이 없고 BUNDLE 부모에서 바로 `BundleOptionRow`를 렌더한다. 즉 첫 기능 SHA `00c8d1f88`부터 생긴 red는 변경되지 않은 spec 자체보다 새 외부 요청 경계에서 시작됐다.

격리 재현 DOM 원문:

```text
3 x <input id=":rl:"  value="SET" aria-label="라인 1 품목">
6 x <input id=":r1l:" value=""    aria-label="라인 1 품목">
Expected /SET-HM2WAY/, Received ""
```

이는 **동시에 같은 라벨의 input 두 개가 존재한 것이 아니다.** Playwright `toHaveValue`의 시간순 polling 중 원래 자동완성 행(`:rl:`)이 전개 실패 catch로 제거되고, `emptyLine()` 기반 새 행의 `ProductAutocomplete`가 재마운트(`:r1l:`)된 기록이다. 자동 trailing 빈행이 같은 라벨로 중복 렌더된 증거도 아니다.

같은 HEAD의 대조 실행:

```text
기본 API localhost:8080 사용  2 passed (6.8s)
API를 127.0.0.1:1로 격리      2 failed (18.4s), GitHub와 동일 DOM 전이
```

따라서 첫 통과는 로컬 기존 서버 응답에 의존한 false green이며, CI의 3-SHA red와 모순되지 않는다.

## 2. 불변식

1. `VITE_MOCK_MODE=1` hard gate는 로컬·CI의 API 서버/Docker 유무와 무관하게 동일한 결과를 내야 한다.
2. BUNDLE 선택 후 화면은 서버 `BundleExpander` 계약을 따라야 한다.
   - `KEEP`: 부모 BUNDLE 한 행이 남고 그 행에 세트 옵션 UI가 연결된다.
   - `EXPAND` 및 `bundle_mode IS NULL`: 부모는 저장 후보에서 사라지고 구성품 행으로 전개된다. 옵션 UI는 옵션 확정에 필요한 동안 구성품 계보에 연결된다.
3. 전개 실패는 빈 정상 행으로 조용히 보이면 안 되며, 사용자가 실패를 인지하고 재시도할 수 있어야 한다.
4. mock이 위 두 모드를 명시적으로 고정하지 않은 채 외부 서버 응답으로 모드를 결정해서는 안 된다.

## 3. 양방향 RED

### RED-A — 외부 서버 독립성 및 모드별 화면 계약

- 미사용 API 주소로 격리한 mock E2E에서도 BUNDLE 전개 요청이 네트워크로 나가지 않아야 한다.
- `KEEP` fixture에서는 부모 모델명, BUNDLE 타입, 세트 옵션 행, `실외기 제외 -> 실외기 교체 비활성화`가 함께 유지되어야 한다.
- `EXPAND` fixture와 `bundle_mode IS NULL` fixture에서는 부모가 아니라 구성품 행이 보이고, 수량·단가·규격·옵션 및 `parentSetModel`/`setHead` 계보가 저장 계약과 일치해야 한다.

### RED-B — 반대급부

- SINGLE 선택·자동 trailing 빈행·라인 번호/접근성 라벨은 종전대로 유지되어야 한다.
- 전개 실패를 검증하기 위해 정상 mock 응답까지 실패시키거나, 세트 옵션 기능을 삭제하거나, spec의 핵심 단언을 완화해서 통과시키면 안 된다.
- 로컬 `localhost:8080` 서버가 떠 있을 때만 통과하는 false green이 재발하지 않아야 한다.
- KEEP 허용을 위해 EXPAND/NULL 부모 저장 차단을 풀거나, EXPAND 차단을 위해 KEEP 부모 저장을 다시 막으면 안 된다.

## 4. 범위 밖

- `BundleMode` 정책 변경, 운영 DB 수정, Docker 재빌드·재배포·중지는 범위 밖이다.
- 기존 spec을 단순 삭제·skip·quarantine하거나 기대값만 구성품명으로 바꾸는 것은 범위 밖이다.
- 다른 트랙 `#874`, `#1066`, `#1075` 파일은 건드리지 않는다.
- S29의 전체 입구 `bundleMode` 전달, 지연 응답 스냅샷, 구성품 계보, SINGLE 2,107행/2,100전표/2,837,681,781원 오차단 검증은 이번 라운드에서 **안 봤다**. 전제 오류에 따른 중단 범위다.

## 5. 커밋 전 실행 명령

```powershell
cd clients/web/design-system
npm ci
npm run build

cd ../../desktop
$env:CI='1'
$env:VITE_API_BASE_URL='http://127.0.0.1:1'
npx playwright test playwright/bundle-set-options/bundle-set-options.spec.ts --project=chromium --workers=1 --retries=0 --reporter=line

npx vitest run src/renderer/routes/SlipFormPage.test.tsx src/renderer/api/slip.test.ts
```
