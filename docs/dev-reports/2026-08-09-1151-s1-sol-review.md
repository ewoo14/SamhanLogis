## 1. 트랜잭션 양방향 롤백

실 PostgreSQL에서 정방향 mutation과 journal을 함께 밟았다.

### 정방향 이후 강제 롤백

동일 `TransactionTemplate` 안에서 `StockService.inbound(...)`로 lot/balance/movement/journal을 만든 직후 `IllegalStateException("SOL forced forward rollback after journal")`을 던졌다.

```text
stock_lots(lot_no=probe) = 0
source_operation_journals(source_operation_id=probe) = 0
```

### journal 실패가 정방향을 롤백하는지

같은 `sourceOperationId` journal을 먼저 커밋한 뒤 신규 lot 입고에 동일 ID를 다시 사용해 journal unique 제약 실패를 직접 일으켰다.

```text
SQLState: 23505
ERROR: duplicate key value violates unique constraint
"source_operation_journals_source_operation_id_key"
Detail: Key (source_operation_id)=(0b204d53-c615-4f79-be94-45e2df3bd913) already exists.

stock_lots(probe lot_no) = 0
stock_balances(probe product_id) = 0
stock_movements(probe product_id) = 0
source_operation_journals(probe source_operation_id) = 1  # 사전 주입 행만 존재
BUILD SUCCESSFUL
```

양방향 local transaction 원자성은 정상이다. 변경 경로에는 트랜잭션 밖 mutation cache가 없어 #978 D-1과 같은 cache 이탈은 재현되지 않았다.

## 2. 네 API의 생성 집합

실 PostgreSQL + HTTP API로 확인했다.

| API | 재현 | journal 생성 집합 | 판정 |
|---|---|---|---|
| `lots/inbound` | 신규 lot | `createdLotIds` 1개, 실제 lot ID와 일치 | 정상 |
| `lots/inbound` | 같은 lotNo 재호출, 요청 qty 5→9 | 기존 qty 5 유지, 두 생성 배열 모두 빈 배열 | 정상 |
| `deduct` | 기존 lot FIFO 차감 | 두 생성 배열 모두 빈 배열 | 정상 |
| `instances/batch` | 기존 1개에서 목표 3개 | 두 신규 ID만 기록, 기존 instance ID 미포함 | 정상 |
| `ship-batch` | RESERVED 3개 출고 | 상태만 변경, 두 생성 배열 모두 빈 배열 | 정상 |
| `ship-batch` | 다시 호출 | `NO_OP_EXISTING`, 두 생성 배열 빈 배열 | 정상 |

기존 lot/instance가 생성 집합에 섞이는 재현은 없었다.

## 3. outcome 도달성

- `APPLIED`: lot 입고, deduct, instance deficit 생성, ship-batch에서 실제 발생.
- `NO_OP_EXISTING`: 동일 lot 입고와 ship 재호출에서 발생.
- `NO_OP_EXCLUDED`: 비상품 deduct에서 발생.
- 결함: 비상품 `ship-batch`만 `NO_OP_EXISTING`으로 잘못 기록.

## 4. 기존 동작·차단·성능·동시성

- 관련 단위/계약 묶음: `SourceOperationJournal*`, `StockServiceTest`, `StockInstanceServiceBatchTest`, `StockInstanceServiceOutboundTest` 재실행 종료코드 0.
- 실제 API 행렬에서 정상/NO_OP 9호출은 모두 기존 2xx 계약을 유지했다. journal 추가 때문에 정상 업무가 새로 차단된 건수는 `0/9`.
- 응답 body에는 journal 필드가 추가되지 않았고 기존 DTO shape을 유지했다.
- journal은 호출당 INSERT 1회다. line별 journal N행 증폭은 없었다.
- 동일 `sourceOperationId` 동시/중복 충돌은 unique 제약에서 한 트랜잭션 전체를 롤백하므로 한쪽 mutation만 남지 않았다.
- 별도 부하 벤치마크는 수행하지 않았으므로 latency 수치는 판정하지 않았다.
