## 수정 1 — inventory 검증 풀 격리 비용 제한 및 준비 실패 fail-loud

`AbstractPostgresIT`의 컨테이너 분리는 유지했다. `app.publish.warehouse-validation.hikari.maximum-pool-size=1`, `minimum-idle=0`을 DynamicPropertySource에 추가해 컨텍스트마다 inventory 검증 풀이 PostgreSQL 연결을 과점하지 않게 했다. 또한 컨테이너 start 실패를 무조건 무시하지 않고, Docker 데몬이 실제로 사용 가능한데 준비가 실패한 경우 `ExceptionInInitializerError`를 다시 던지도록 바꾸었다. Docker 데몬 자체를 확인할 수 없는 경우에만 기존 조건부 skip을 유지한다. V999와 적용된 Flyway migration은 수정하지 않았다.

## 조사 3 — 무자격 JdbcTemplate 회귀 원인 확정

물리 컨테이너를 하나로 되돌린 뒤 warehouse focused test는 통과했지만, `EstimateControllerIT` 단일 테스트는 다음 원문으로 실패했다.

```text
Caused by: org.postgresql.util.PSQLException:
ERROR: relation "estimates" does not exist
```

`WarehouseValidationDataSourceConfig`의 inventory용 무자격 `JdbcTemplate` 빈 때문에 Boot 기본 JdbcTemplate 자동구성이 back-off되고, 기존 통합테스트의 무자격 `@Autowired JdbcTemplate`이 inventory DB를 받은 것이 원인이었다.

## 수정 2 — 주 DB JdbcTemplate 명시 및 mapper qualifier

`SlipDataSourceConfig`에 `@Primary` 주 DB(`slip_db`) JdbcTemplate을 추가하고, `WarehouseCodeMapper` 생성자에 `@Qualifier("warehouseValidationJdbcTemplate")`를 지정했다. 최소 재현 결과:

```text

```

## 불변식 점검

- G: `slip-service/src/main` 및 Flyway migration에는 `warehouses` DDL/fixture가 없고, warehouse fixture는 test classpath의 `inventory_db` 초기화 SQL에만 있다.
- H: 컨테이너 준비 실패 시 Docker가 사용 가능한 경우 `ExceptionInInitializerError`를 재던져 Docker skip으로 조용히 통과하지 않는다. Docker 자체를 확인할 수 없는 경우만 기존 skip 대상이다.
- V999 및 적용된 Flyway migration은 수정하지 않았다.
