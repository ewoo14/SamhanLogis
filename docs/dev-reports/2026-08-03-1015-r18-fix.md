# R18 — 주문앱 접근권한 활동 키·출고 결손 fix

일자: 2026-08-03  
대상: PR #1060 / Issue #1015  
기준 커밋: `9818265d5`

## 결론

두 결함을 수정했다.

- 주문 → 출고 변환 payload가 주문의 `bizCode`를 전달하고, slip 저장 시 `business_number` snapshot으로 보존한다.
- 기존 `PARTNER_ORDER` 레거시 행에 대해서는 사업자번호를 추정하지 않고, 사업자번호 조회가 결과를 못 찾은 경우에만 동일 요청의 `legacyPartnerCode`를 사용해 exact `partner_code` fallback을 수행한다.
- 미리보기 API·실제 인증·만료 API는 모두 `bizNo` 우선 + `partnerCode` legacy fallback이라는 동일한 활동 조회 경로를 사용한다.
- UUID는 조회 API의 경로·응답에 추가하지 않았다. fallback은 사용자에게 노출되는 partner code만 전달한다.

## 구현

### 결함 A

`PartnerOrderConvertService`와 `PartnerOrderMergeConvertService`가 주문의 `bizCode`를 slip-service 요청에 추가한다. `PublishFromPartnerOrderRequest`와 `PublishFromOrdersMergeRequest`는 새 `bizCode` 필드를 받되, 기존 호출부를 위해 이전 생성자도 유지한다. `SlipPublishService`는 두 변환 경로 모두 해당 값을 `business_number`에 저장한다.

활동 조회는 다음 순서다.

1. 주문 서비스: `bizCode` 정규화 exact 조회
2. slip 서비스: `business_number` 정규화 exact 조회
3. primary 결과가 없을 때만 `legacyPartnerCode` exact fallback

fallback은 서로 다른 거래처의 행을 합치지 않는다. 사업자번호 primary 결과가 존재하면 fallback을 실행하지 않으며, partner code도 요청 auth 행의 값 하나만 사용한다.

### 기존 저장 데이터 결정

공유 DB에는 쓰기/DDL을 실행하지 않았다. `slip_db` Flyway 최고 적용 버전은 다음과 같이 100이었다.

```text
[실데이터/로컬 read-only]
version | description
100     | normalize quote snapshot json owner totals
```

따라서 migration은 추가하지 않았다. 이미 저장된 `PARTNER_ORDER` 20건은 모두 `business_number IS NULL`이지만 `partner_code`가 있고, 각 행에 사업자번호를 추정·기입하는 migration은 서로 다른 데이터베이스의 주문 원장에 의존하고 snapshot의 역사적 정확성을 보장하지 못한다. 이 행들은 exact legacy fallback으로만 읽는다. `MANUAL` NULL 행 2,033건은 partner code도 없는 행이어서 특정 거래처에 귀속하지 않고 계속 미식별/보류로 둔다. 주문에서 전환된 활동은 주문 원장의 `bizCode` 조회가 함께 보완한다.

새로 생성되는 출고는 사업자번호 snapshot을 가지므로 이 레거시 window가 누적되지 않는다.

### 결함 B

`PartnerAuthService.evaluateEffectiveStatus`, `PartnerApprovalService.previewLongUnusedReport`, `PartnerAuthService.getExpiration` 세 경로 모두 `readSafely(reader, auth.getBizNo(), auth.getPartnerCode())`를 호출한다. downstream 오류 또는 null은 기존 R16 보류 semantics를 유지한다.

HTTP 계약은 기존 `GET /internal/partner-activity/{businessNumber}`를 유지하고 선택 query parameter `legacyPartnerCode`만 추가했다. 응답 DTO는 변경하지 않았으므로 만료 API의 기존 소비자는 깨지지 않는다. 세 경로의 expiration 계산과 strict `isBefore(now)` 경계도 변경하지 않았다.

## 도달성 측정

아래는 모두 공유 DB에 변경을 가하지 않은 `docker exec ... psql -c SELECT` 결과다.

### 수정 전/현재 저장 데이터

```text
[실데이터/로컬 read-only]
source_type  | total | business_number_null | business_number_present
MANUAL       | 2325  | 2033                 | 292
PARTNER_ORDER| 20    | 20                   | 0

[실데이터/로컬 read-only]
partner_order_outbound | null_business_number | partner_codes
20                     | 20                   | 11

[실데이터/로컬 read-only]
partner_order_partners_with_outbound_activity | 11
business_numbers_with_outbound_activity       | 0

[실데이터/로컬 read-only]
confirmed_orders | partners_with_confirmed_orders | biz_code_null
30               | 30                             | 0

[실데이터/로컬 read-only]
auth_rows | access_candidates
2         | 2
```

수정 전에는 `PARTNER_ORDER` 출고의 사업자번호 활동 hit가 0개였다. 수정 후 새 출고는 `bizCode`를 보존하고, 기존 20건은 exact legacy fallback으로 읽을 수 있다. 현재 데이터베이스에는 새 출고를 생성하지 않았으므로 저장 행 자체의 NULL 수는 변하지 않는다.

2026-08-03 기준 auth 두 행을 주문 원장의 `bizCode` 활동과 생성시각에 대조하면, 활동이 잡히는 거래처는 1곳(`2118712345`, 마지막 주문확정 `2026-01-03 10:00:00`)이고 strict `<` 기준 차단 대상은 1곳이다. `1068689215`는 활동이 없지만 생성일이 `2026-07-30`이라 아직 30일 대상이 아니다. 즉 활동을 넓게 잡아 전원을 면제하지 않으며, 실제 무활동 거래처는 30일 경과 후 계속 대상이 된다.

출고 원장 자체의 legacy 활동 파트너 수는 11곳이다.

```text
[실데이터/로컬 read-only]
source_type='PARTNER_ORDER', slip_type='OUTBOUND' 기준
활동 partner_code 수: 11
business_number 기반 활동 수(수정 전 저장값): 0
```

### DEV fixture와 실데이터 구분

- `[DEV-SEED/단위 fixture]` RED A: 실제 slip publish MockMvc API 호출 후 저장 entity의 `businessNumber`를 단언.
- `[DEV-SEED/단위 fixture]` RED B: `bizNo`와 `partnerCode`가 다른 auth 및 사업자번호 키 활동 mock.
- `[DEV-SEED/단위 fixture]` legacy client: primary business-number 응답과 legacy query parameter를 분리한 HTTP server fixture.
- `[실데이터/로컬 read-only]` 위 SQL은 공유 로컬 PostgreSQL의 현재 행을 SELECT로만 측정.
