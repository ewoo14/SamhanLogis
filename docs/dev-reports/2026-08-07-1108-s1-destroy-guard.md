# 이슈 #1108 S1 — 구성품 전량 파기 무경고 가드

## 결론

`UpdateProductRequest.confirmBundleChildrenDeletion`을 추가했다. 기본값은 `false`(생략 시 차단)다. 활성 구성품이 있는 BUNDLE 품목을 단일 품목으로 바꾸거나 자재로 바꾸는 PATCH는 명시적 확인 없이는 `INVALID_INPUT`으로 중단된다. 확인된 경우에만 기존 soft-delete가 실행된다.

화면은 기존 카탈로그 목록의 `componentCount`를 사용해 저장 전 `구성품 N건이 삭제됩니다`를 표시한다. 구성품 편집 UI는 추가하지 않았다.

## 네 RED 실행 원문

### RED-A — 확인 후 의도적 전환

명령: `./gradlew :services:product-service:test --tests "*ProductServiceTest.update_setToGeneral_removesChildrenAfterExplicitConfirmation" --tests "*ProductServiceTest.update_materialTransition_removesChildrenAfterExplicitConfirmation"` 결과: `BUILD SUCCESSFUL`.

확인 플래그가 true이면 두 전환 모두 `removeBundleChildren(productId, "system")`가 호출되고, SET→GENERAL은 SINGLE이 된다.

### RED-B — 확인 없이는 삭제 금지

명령: `./gradlew :services:product-service:test --tests "*ProductServiceTest.update_setToGeneral_requiresExplicitConfirmationWhenChildrenExist" --tests "*ProductServiceTest.update_materialTransition_requiresExplicitConfirmationWhenBundleChildrenExist"` 결과: `BUILD SUCCESSFUL`. 화면 명령 `npx vitest run src/renderer/routes/ProductFormPage.test.tsx` 결과: `ProductFormPage.test.tsx — 6 tests passed`.

구성품 수가 3/2건일 때 확인 필드 생략은 예외를 발생시키고 `removeBundleChildren`를 호출하지 않는다. 화면에서 취소하면 `updateProduct` 호출도 없다.

### RED-C — 삭제 건수 표시

화면 테스트가 `window.confirm` 원문에 각각 4와 2를 포함하는지 검증했다. 구성품 목록은 표시하지 않고 요구된 최소 정보인 건수만 확인 문구에 넣었다.

### RED-D — API 직접 호출 보호

`ProductService.update` 진입 직후 `assertBundleChildrenDeletionConfirmed`를 실행한다. 화면을 거치지 않고 PATCH를 호출해도 확인 필드가 없거나 false이고 활성 구성품 수가 1 이상이면 차단된다. 확인 플래그는 서버의 명시적 의사표시 계약이다.

## ① 새로 가능해진 상태·조합과 결과

| 조합 | 확인 전 | 확인 후 | 검증 |
|---|---|---|---|
| BUNDLE → GENERAL/SINGLE | 구성품 있으면 차단 | 기존 soft-delete 후 SINGLE | ProductServiceTest, ProductFormPageTest |
| BUNDLE → SET_COMPONENT 등 non-SET | 구성품 있으면 차단 | 기존 전환/링크 처리 유지 | 공통 서버 guard, 기존 테스트 |
| BUNDLE + productCategory=MATERIAL | 구성품 있으면 차단 | 기존 `applyMaterialDefaults` 유지 | ProductServiceTest, ProductFormPageTest |
| BUNDLE → SET, 비자재 | 삭제 없음 | 기존 동작 | 기존 ProductService 테스트 |
| BUNDLE이지만 활성 구성품 0건 | 차단 없음 | 기존 전환 허용 | 서버 count=0 분기 |
| 이미 SINGLE인 품목 | guard 대상 아님 | 기존 수정 동작 | 서버 guard 조건 |

실 DB 재측정은 Docker 금지 및 `psql` 부재로 수행하지 못했다. PM 제시 344/1,588 수치를 새로 확정했다고 주장하지 않는다.

## ② `removeBundleChildren` 호출부 전수

실행: `rg -n "removeBundleChildren" services/product-service/src/main clients`

운영 호출부는 아래 2곳뿐이다.

| 파일 | 위치 | 조건 | 가드 |
|---|---:|---|---|
| `services/product-service/.../ProductService.java` | 1153 | `itemKind != SET` 전환 | update 진입 전 확인 검증 |
| `services/product-service/.../ProductService.java` | 1233 | MATERIAL의 `applyMaterialDefaults` | update 진입 전 확인 검증 |

테스트 verify/메서드 정의 외 추가 운영 호출부는 없다. `updateProduct(` 소비자는 `ProductFormPage.tsx` 1곳이며 해당 요청에만 확인 플래그를 붙인다. `new UpdateProductRequest(`는 product-service 테스트/통합 테스트에만 존재하고 시더·마이그레이션·타 서비스 운영 호출은 검색되지 않았다. 기존 16-인자 Java 생성자 호환은 유지하되 서버 생략은 차단한다.

## ③ 변경 파일 참조 테스트

`./gradlew :services:product-service:test --tests "*Bundle*" --tests "*ProductService*"` → `BUILD SUCCESSFUL`.

`npx vitest run src/renderer/routes/ProductFormPage.test.tsx src/renderer/routes/productFormModel.test.ts` → 2 files passed, 21 tests passed.

`npx tsc -p tsconfig.node.json --noEmit` 및 `npx tsc -p tsconfig.web.json --noEmit` → exit 0.

요청한 `npm run test`와 `npm run typecheck`는 stale design-system dist/Electron 산출물을 검사하는 precheck에서 실행 전 중단됐다. 다른 워크트리를 수정하지 않기 위해 기존 산출물을 임시 junction으로 읽기 연결했지만 산출물이 현재 소스보다 오래되어 precheck를 통과시키지는 못했다. 본체 Vitest와 `tsc`는 직접 실행해 통과시켰고 junction은 제거했다.

## 남은 차단

- 실 DB 활성 BUNDLE/`bundle_component` 수치는 Docker 금지 및 `psql` 부재로 재확정하지 못했다.
- npm wrapper 전체 precheck는 stale 로컬 산출물 갱신 없이는 판정할 수 없다. CI가 권위다.
- 커밋·푸시는 하지 않았다.
