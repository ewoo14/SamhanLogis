## 1. 현행 검색 입력 컴포넌트 전수

### 집계 기준

- 운영 소스의 `.tsx`만 세고 테스트·Storybook·Playwright·주석 예시는 제외했다.
- “사용처”는 정적 JSX 렌더 지점 수다. 같은 파일에 두 번 렌더되면 2곳으로 센다.
- `role="combobox"`/`aria-autocomplete="list"` 구현까지 역검색했다. 그 결과 자동완성 5종 외 독립 검색 입력 2종도 확인됐다.
- 사용자 화면의 정적 검색 입력 사용처는 **총 41곳, 컴포넌트 구현 7종**이다. `AsyncAutocomplete` 내부 조합 3곳은 이 41곳에 중복 가산하지 않았다.

- `PartnerAutocomplete`, `ProductAutocomplete`, `MultiSelectAutocomplete`는 내부에서 `AsyncAutocomplete`를 각각 1곳씩 렌더한다. `JournalFormPage`의 거래처 검색만 base를 직접 사용한다.

## 2. 모달/dialog 0건 주장 재확인

### 결론

- **저장소 전체의 모달/dialog 코드는 0건이 아니다.** 운영 `.tsx`에서 `<Modal` 접두사만 **86행·59파일**이 검색됐다(이 수에는 타입명/문서 예시 같은 접두사 오탐이 소수 포함되므로 UI 개수로 사용하지 않는다). 공용 구현도 `clients/web/design-system/src/components/Modal/Modal.tsx`에 존재한다.
- 반면 **다섯 대상의 부분검색 결과가 2건 이상일 때 별도 모달로 후보를 나열하는 구현은 0건**이다. 이것이 #825 실측 주장의 정확한 범위다.
- 대상 검색 컴포넌트 디렉터리(`AsyncAutocomplete`, `MultiSelectAutocomplete`, `PartnerAutocomplete`, `ProductAutocomplete`, `WarehouseAutocomplete`)와 직접 소비 화면(`JournalFormPage`, `MessengerPage`)에서 `Modal|Dialog` 참조를 다시 검색했으며 **0건**이었다.

### 혼동하기 쉬운 기존 코드

- `clients/desktop/src/renderer/routes/components/MergeConvertDialog.tsx`는 공용 `Modal` 안에서 거래처 단수 자동완성, 주문 복수 칩 선택, 창고 단수 자동완성을 함께 쓴다. 하지만 “검색 결과 2건+이면 새 후보 선택 모달”이 아니라 **업무 자체가 주문 병합·전표 전환인 기존 모달**이다.
- `InventoryLookupModal.tsx`, `LineLookupReferenceModal.tsx` 등 조회 모달과 각종 관리/확인 dialog도 다수 존재하지만, 다섯 대상의 부분검색 중복 선택 계약을 구현하지 않는다.
- 현행 후보 표시는 모두 input 아래 `listbox`/dropdown이다. `AsyncAutocomplete`는 빈 후보에 “검색 결과 없음”을 표시하고, `MultiSelectAutocomplete`는 같은 dropdown에서 선택 후 칩을 쌓는다.

## 3. 구조상 단수 강제 자리

### 판정 기준

- 단순히 현 UI가 단수 컴포넌트인지는 근거로 삼지 않았다. 상태·요청 DTO·도메인 관계가 한 코드/한 대상만 받는지를 확인했다.
- **필터**는 다중 조건으로 확장할 수 있으므로 별도 분리했다. 반면 문서 헤더, 문서 한 행, 매핑 한 건, 전환 작업 한 건은 현재 구조상 단수다.
- #853의 전표 거래처 불변식도 재확인했다. `SENT` 이상 커밋 상태는 거래처가 필수이며, `DRAFT`/`SAVED`/`CANCELED`의 null만 허용한다. 따라서 전표 헤더에 복수 거래처를 저장하는 변경은 이번 UI 범위가 아니라 전표 도메인 재설계가 된다.

### 단수 강제에서 제외할 자리

- `JournalStatusReportPage`, `NotesReceivablePage` 목록 필터, `CollectionPlanPage` 목록 필터의 거래처는 문서 소유 필드가 아니라 조회조건이다. 개발책임자 지시대로 거래처 복수선택 후보로 볼 수 있다.
- 쪽지 수신자는 이미 `MessengerPage`에서 복수 칩이다.
- 결재자 검색(`ApprovalLineConfigPage`, `GroupwareApprovalCreatePage`)도 이미 복수 칩이다.
- 현행 검색 컴포넌트 소비처 중 `employees.ecount_code` 기반 **단수 담당자 선택 필드**는 발견되지 않았다. 화면의 다른 “담당자” 표기는 문자열 필터·읽기 전용 주문 담당자·거래처 연락담당자 입력이며, 이번 직원 검색 대상과 같은 구현이 아니다.

### 확인 제안

- 위 표의 거래처/품목 자리는 **후보 모달에서는 여러 결과를 보여주되 최종 확정은 1개**로 유지하는 것이 현재 데이터 구조와 맞다.
- 복수선택을 허용하려면 조회 필터·쪽지 수신자·결재자, 그리고 여러 전표 행/설정 행을 만들 수 있는 명시적 “일괄 추가” 동작으로 한정해야 한다. 특히 전표 헤더 거래처 복수화는 #853 불변식과 충돌하므로 제외가 필요하다.

## 4. 사용자 노출 코드·unique·동명이름 실측

### 방법

- 실행 중인 공유 PostgreSQL에 `SELECT`만 수행했다. 컨테이너 재빌드·재기동과 DB 쓰기는 하지 않았다.
- `is_deleted=false` 활성 행 기준으로 코드 중복 그룹, 이름 exact-match 중복 그룹, 그 그룹에 속한 행 수를 집계했다. 코드/이름 원문과 내부 식별자는 출력·기록하지 않았다.
- unique 여부는 실제 `pg_indexes`와 migration을 함께 확인했다. 네 코드 모두 **활성 행 partial unique**다. 따라서 soft-delete 뒤 코드 재사용은 스키마상 허용되지만 활성 후보끼리는 중복될 수 없다.

### 결과

| 대상 | 사용자 노출 코드 컬럼 | 컬럼/unique | 활성 행 | 코드 없음 | 활성 코드 중복 | 같은 이름 그룹 | 같은 이름에 속한 행 | 중복 초과 행 |
|---|---|---|---:|---:|---:|---:|---:|---:|
| 품목 | `product_db.products.model_code` | nullable, `ux_products_model_code_active` | 1,220 | **100** | 0그룹/0행 | **187** | **700** | **513** |
| 창고 | `inventory_db.warehouses.code` | NOT NULL, `ux_warehouses_code_active` | 4 | 0 | 0그룹/0행 | 0 | 0 | 0 |
| 담당자 | `user_db.employees.ecount_code` | nullable, `ux_employees_ecount_code_active` | 24 | **24** | 0그룹/0행 | 0 | 0 | 0 |
| 거래처 | `partner_db.partners.partner_code` | NOT NULL, `ux_partners_partner_code_active` | 7,259 | 0 | 0그룹/0행 | **20** | **55** | **35** |

`중복 초과 행`은 각 동명이름 그룹에서 첫 행을 제외한 수(`sum(count-1)`)다. 예를 들어 품목은 187개 동명이름 그룹에 700행이 들어 있고, 이름만으로는 추가 513행을 구분할 수 없다.

### 해석

- **기능 필요성이 실데이터로 확인된다.** 품목 동명이름이 187그룹/700행, 거래처 동명이름이 20그룹/55행이다. 이름 부분검색 후 첫 행 자동확정은 잘못된 대상을 고를 위험이 크다.
- 품목 모델코드는 활성 1,220행 중 100행이 비어 있다. unique 자체는 보장되지만 “모델코드로 사람에게 구분”할 수 없는 활성 품목이 존재한다. 이 경우 모달에는 임의 내부 키를 노출하지 말고, 모델코드 미등록 상태와 품목명/규격 같은 승인된 비즈니스 정보가 필요하다.
- 담당자코드 컬럼과 unique index는 실제 존재하지만, 현재 활성 직원 24명 전원이 `ecount_code` 미부여다. 메신저 DTO도 이 컬럼을 `employeeCode`로 전달하고 미부여 시 null로 명시한다. 따라서 현재 DB에서는 동명이인이 생기면 화면이 `코드없음`으로만 구분되어 **담당자코드 병기 요구를 충족하지 못한다.** 코드 backfill은 이번 정찰/PR 범위 밖이지만 구현 게이트로 기록해야 한다.
- 창고는 현재 4행 모두 코드·이름이 유일하다. 그래도 창고 단수 계약과 unique index는 확인됐다.
- 전체 행(soft-delete 포함) 코드 중복도 네 대상 모두 현재 0그룹이었다. 다만 제약은 활성 행에만 걸린다는 구조적 사실은 변하지 않는다.

## 5. #866 / PR #892 쪽지 수신자 칩 재사용 판단

### 현행 구현

- `MessengerPage.tsx`가 `MultiSelectAutocomplete<RecipientOption, RecipientOption>`을 사용한다.
- 선택 배열이 단일 진실원이며 후보 추가/칩 제거, 이미 선택한 후보 제외, 최대 50명, 본인 제외, 0명 발송 차단을 구현한다.
- 후보/선택 dedupe 키는 내부에서만 쓰고 화면에는 이름·부서·담당자코드만 표시한다. 동명이름이 검색 응답에 2건 이상이면 담당자코드를 병기한다.
- 발송 payload는 선택된 수신자 배열을 `recipientIds` 배열로 변환해 bulk API에 보낸다. 따라서 **쪽지 도메인의 복수 저장·발송 계약은 이미 완성돼 있다.**

### 재사용 가능/불가능 경계

| 요소 | 판단 | 근거 |
|---|---|---|
| 선택 배열·중복 제외·최대 개수·칩 제거 | 재사용 가능 | `MultiSelectAutocomplete`의 generic 계약과 기존 테스트가 보장 |
| `TagChip` 표시·제거 접근성 | 재사용 가능 | 선택 순번/이름/부서 표시, 제거 버튼, 선택 개수 live 안내가 있음 |
| 쪽지 수신자 검색 API·bulk 발송 API | 그대로 재사용 가능 | 이미 다중 수신 계약 |
| “1건이면 즉시 확정” | **그대로는 불가** | 현 `AsyncAutocomplete`는 검색 1건이어도 dropdown 후보를 열고 사용자 pick을 기다림 |
| “2건+이면 모달에서 나열·복수 확정” | **그대로는 불가** | 현 구현은 input 아래 listbox에서 한 건씩 즉시 `onAdd`; 모달 draft 선택 후 일괄 확정 계약이 없음 |
| 거래처/품목에 동일 컴포넌트 직접 대입 | 제한적 | 저장 구조가 단수인 자리와 여러 행 일괄추가 자리를 먼저 구분해야 함 |

### 범위 산정

- 화면별 조합으로 해결하면 공용 `Modal`과 `TagChip`, 기존 selected/onAdd/onRemove 패턴은 재사용할 수 있다. 다만 후보 모달의 임시 선택→확정/취소 상태는 새 화면 로직이 필요하다.
- `AsyncAutocomplete` 또는 `MultiSelectAutocomplete` 자체에 결과 개수별 모달 전환을 넣으면 **design-system 변경**이다. 이 경우 단위 테스트뿐 아니라 기존 mock Playwright 회귀가 필수다.
- 최소 mock 회귀 범위: `clients/desktop/playwright/ac-825-s6-messenger-chip/`, `ac-2-product-autocomplete/`, `ac-3-partner-autocomplete/`, `ac-4-partner-standardize/`, 창고 자동완성 소비 시나리오(`phase-2-6a-order-convert/`)와 변경 대상 화면별 신규 1건/2건+/취소/복수확정 케이스.
- design-system 자체에서는 `AsyncAutocomplete.test.tsx`, `MultiSelectAutocomplete.test.tsx`, `ProductAutocomplete.test.tsx`, `WarehouseAutocomplete.test.tsx`, `PartnerAutocomplete/highlight.test.tsx` 회귀가 필요하다.

### 최종 판단

**쪽지의 데이터/API/칩 선택 모델은 재사용 가능하지만, 이번 핵심인 결과 개수별 모달 전환은 재사용 가능한 현행 코드가 없다.** 따라서 #892를 복사하는 작업이 아니라, 기존 칩 모델을 보존하면서 별도의 결과 판정·모달 확정 계층을 붙이는 범위로 산정해야 한다.
