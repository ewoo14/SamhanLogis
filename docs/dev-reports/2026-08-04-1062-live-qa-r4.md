## 2. PR 변경 표면과 기대 동작

- 견적: `EstimateFormPage`에 `ensureTrailingBlankRow`가 상세 hydration/co-edit seed에 연결되어 수정 진입 시 품목코드 확정 행 아래 trailing 빈행을 유지한다. 빈행 품목코드 확정 시 다음 빈행을 추가하고 저장 payload에서는 미확정 행을 제외해야 한다.
- 이동: `TransferFormPage`에 사용자 입력 변경 시 `appendBlankRowIfLastChanged`가 연결되어 마지막 행에 입력하면 다음 빈행을 추가한다. 저장 시 빈행이 전송되면 안 된다.
- 분개: `JournalFormPage`에 `ensureTrailingBlankRow`가 상세 hydration에 연결되어 수정 진입 시 계정코드 확정 행 아래 trailing 빈행을 유지한다. 저장 시 미확정 행은 제외되어야 한다.
- 자동완성 mode 표: 판매전표 SlipFormPage는 resultSelectionMode={null}(모달 기대 금지, R3 확정). R4 대상 견적·이동은 ProductAutocomplete가 직접 연결되지 않고 별도 mode prop도 없어 모델명 blur lookup 경로이며, 분개 거래처 AsyncAutocomplete도 mode 미지정으로 listbox 경로다. 따라서 대상 3개 화면에서는 2건 이상 모달을 기대하지 않고 코드/실측 표를 기준으로 판정한다.

## 4. 실행 결과

### 견적

- 실 로그인: dev_manager UI 로그인 성공. renderer 18502 → gateway 8080 실 호출.
- 수정 진입: SQL 대상 c6e00c99-c464-4255-9045-d045e7984651 (2026/07/17-20)에 대해 확정 3행 + 4번 trailing 빈행을 확인했다. 각 입력은 disabled=false, 모델명 input은 readonly=false였고 실제 fill 조작이 반영됐다.
- 빈행 입력/추가: 4번 모델명에 AC1000CNCDEH-85를 입력하고 blur했다. blur 전 모델 input 4개, blur 후 5개이며 값은 QA797-PART-01, QA797-PART-02, AC1000CNCDEH-85, AC1000CNCDEH-85, ''였다. 즉 확정 후 맨 아래 빈행 유지 동작은 PASS.
- 실 API 증거: GET /slips/estimates/c6e00c99-c464-4255-9045-d045e7984651 200; GET /slips/lookup-product?modelName=AC1000CNCDEH-85 200; 협업 stream/coedit 호출도 200.

- 후보 1건/2건 이상: 거래처 자동완성에서 P-2026-0002는 listbox 1건(한국공조시스템(주) · P-2026-0002 · 126-14-10062), 한국은 다수 후보 listbox를 표시했다. 두 경우 모두 role=dialog 모달은 열리지 않았다. 이 화면의 AsyncAutocomplete에는 resultSelectionMode prop이 전달되지 않아 코드상 모달 기대 대상이 아니다. 표시 텍스트는 잘리지 않았다.

- 위 저장 조작으로 실 API가 생성한 테스트 분개는 2026/07/05-13 (id `3e27cff8-fbe8-405c-80f9-023d014ecfc5`, DRAFT)이며, DB 직접 쓰기는 하지 않았다.
- 마지막 행 삭제: 생성 문서 수정 화면에서 라인 3 삭제로 trailing 빈행을 삭제하자 계정과목 input은 3개→2개가 됐다. 이어 라인 2 삭제를 눌러도 최소 2행 보장이 작동해 2개를 유지했다. PASS.

## 6. 결함 및 증거

- R4 측정 범위에서 trailing 빈행 생성과 저장 payload의 빈행 제외는 견적·분개에서 확인했다.
- 견적 저장은 UI가 빈행을 제외한 payload를 만들었지만 실 backend가 기존 문서의 누락 product ID를 이유로 404를 반환했다. 이는 저장 성공/재열기 판정의 blocker이며 위 실 응답 원문을 증거로 남긴다.
- 분개는 dev_accountant에서 실 POST 201 및 생성 문서 재열기를 확인했다.
- renderer 로그인 과정에서 GET/POST /app/notices/active, POST /logs/front 일부 503이 있었으나 대상 문서 GET/저장 API와 QA 동작에는 영향이 없었다.

## 이 라운드가 보지 않은 것

- 이동 화면: SQL상 수정 가능 기존 문서가 0건이어서 실 API 생성 없이 수정/저장/재열기 시나리오를 폐기했다.
- 견적: backend 404 blocker 때문에 성공한 PUT 후 재열기 영속성은 보지 못했다. 빈행 제외 payload까지만 확증했다.
- 공용 ProductAutocomplete가 직접 연결된 다른 화면의 후보 1건/2건 이상 모달은 이번 R4 대상에서 보지 않았다.
- 판매전표는 R3에서 확정·제외된 표면이므로 재측정하지 않았다.
