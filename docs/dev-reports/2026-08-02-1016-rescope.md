# #1016 알리고 자동 업로드 재범위 조사

- 레거시 원문은 `tools/legacy-gas/알리고 자동 업로드/`의 `Code.js`, `Index.html`, `appsscript.json` 3개 파일이다.
- 최신 GAS 전수대조 문서에서는 이 프로그램을 15번으로 식별하지만, 과거 Phase 10 문서의 9번 표기는 당시 부분 분류 번호다 (`docs/dev-reports/2026-07-31-977-gas-full-recheck.md:56`, `migration/decisions/DECISIONS.md:1069`).

## 1. 레거시 GAS 원문에서 확인한 동작

- 접근은 로그인 계정을 외부 권한 DB에서 조회해 등록 계정만 허용하고 작업자 표시명을 얻는다 (`Code.js:18-64`).
- 입력은 이카운트 거래처 엑셀과 KT 주소록 파일이며, 이카운트 파일은 첫 시트의 두 번째 행부터 읽고 마지막 행을 버린 뒤 `SF(밴더)` 그룹만 남긴다 (`Index.html:314-366`).
- 이카운트 입력에서 거래처코드·담당자 구분·거래처명·대표자명·주소·전화번호·비고를 추출해 서버 동기화용 행을 만든다 (`Index.html:333-341`).
- KT 주소록은 `SF벤더` 그룹이면서 숫자만 남긴 번호가 11자리 `010` 형식인 행만 수신자 후보에 넣는다 (`Index.html:342-358`).
- 이카운트 행은 50건씩 나누어 외부 거래처 DB에 추가·갱신·변경없음·실패 건수를 누적한다 (`Index.html:382-445`, `Code.js:426-510`).
- 외부 거래처 DB의 기존 행은 거래처코드로 찾고 담당 구분·거래처명·대표자명·주소·비고·전화번호 중 하나라도 다를 때만 갱신한다 (`Code.js:431-500`).
- 담당 구분은 거래처명에 폐업 표시가 있으면 폐업, 담당 정보가 없으면 미지정, 특정 채권·소송 상태 키워드는 별도 상태로 정규화한다 (`Code.js:286-295`).
- 외부 거래처 DB 저장 시 특정 채권·소송 상태의 거래처명은 취소선으로 표시한다 (`Code.js:474-483`).
- 번호 정규화는 여러 전화 유형을 분리·하이픈 형식화·접두사 우선순위 정렬하고, 한 필드의 복수 번호를 줄바꿈으로 보존한다 (`Code.js:299-383`).
- 수신자 자료는 외부 거래처 DB 전체 페이지와 별도 공유 시트 3개를 함께 읽으며, 거래처명·전화번호·주소를 공통 표현으로 만든다 (`Code.js:181-262`).
- 외부 거래처 DB에서는 담당 구분에 신용정보·전자소송·보류·폐업 표지가 있는 행을 수신자 자료에서 제외하고, 전화번호와 주소가 모두 있는 행만 포함한다 (`Code.js:208-219`).
- 공유 시트에서는 회사명·연락처·주소가 있고 연락처와 주소가 비어 있지 않은 행만 포함하며, 출처 구분을 이름 앞에 붙인다 (`Code.js:228-255`).
- 요일 발송 목록은 당일에 매핑된 지역만 고르고, 외부 거래처 DB를 우선 담은 뒤 같은 번호의 공유 시트 행을 제외한다 (`Index.html:472-490`, `616-653`).
- 기본 요일·지역 매핑은 월=전라, 화=경상, 수=서울·경기, 목=강원·제주이며 화면에서 선택을 바꿀 수 있다 (`Index.html:472-490`).
- 전체 거래처 목록은 이카운트 주소록과 KT 주소록을 번호 기준 병합한 뒤 외부 거래처 DB에만 있는 번호를 보태고, 하드코딩 차단 3건을 제외한다 (`Index.html:451-455`, `656-678`).
- 골프회 목록은 사용자가 하나 이상 고른 지역에 맞는 외부 거래처 DB와 공유 시트 수신자를 번호 중복 없이 합친다 (`Index.html:681-723`).
- 결과 표는 번호·이름·그룹을 표시하고 각 셀을 사용자가 직접 편집할 수 있으며, 번호·이름·그룹 문자열 필터를 적용할 수 있다 (`Index.html:535-575`).
- CSV는 UTF-8 BOM과 `전화번호,이름,그룹` 3열로 만들고 이름의 큰따옴표를 RFC 4180 방식으로 이스케이프한다 (`Index.html:578-601`).
- 파일명은 실행 종류·날짜·선택 지역을 조합하고 그룹 값은 확장자를 뺀 파일명과 같다 (`Index.html:540`, `648-652`, `670-677`, `718-722`).
- 생성 결과는 브라우저에 로컬 다운로드한 뒤 Google Drive에 같은 파일명이 있으면 덮어쓰고 없으면 새 CSV로 저장한다 (`Index.html:603-611`, `Code.js:266-282`).
- 작업 이력은 결과 목록 JSON을 gzip+Base64로 압축해 최대 2개 속성에 2,000자 조각으로 저장하고, 작업자·계정·프로그램유형·주제도 함께 남긴다 (`Code.js:68-116`).
- 거래처 동기화 완료 이력에는 입력 이카운트 전체 자료와 총 건수를, CSV 생성 이력에는 최종 필터 결과와 결과 건수를 저장한다 (`Index.html:393-413`, `603-614`).
- 이력 목록은 생성일 범위와 프로그램유형으로 최근순 최대 50건을 조회하고 작업자·시각·주제를 보여준다 (`Code.js:120-155`, `Index.html:759-779`).
- 이력 상세는 압축 본문을 복원해 결과 건수와 첫 행 미리보기를 보여주도록 작성돼 있으나, 상세 조회 URL에 `api`가 중복되어 정상 조회가 실패할 가능성이 있다 (`Code.js:159-177`, `Index.html:782-798`).
- 외부 거래처 DB 요청은 429의 `Retry-After`와 최대 20초 지수 backoff를 사용해 기본 5회 재시도하며, 소진하면 `null`을 반환한다 (`Code.js:387-423`).
- 거래처 동기화는 행별 성공 여부를 집계하고 성공한 외부 쓰기 뒤 100ms를 쉬지만, 실패 행 자체나 원인을 이력에 남기거나 실패 행만 재실행하는 기능은 없다 (`Code.js:461-510`).
- CSV의 Google Drive 저장 실패는 `false`로 바꾸어 화면에 실패 알림을 표시하지만 로컬 다운로드와 이력 저장 호출은 이미 별도로 실행된다 (`Code.js:266-282`, `Index.html:603-614`).
- 대상 3개 파일에는 알리고 API endpoint 또는 알리고 API 호출이 0건이며, 외부 HTTP 호출은 권한·거래처·이력용 Notion 통신이고 최종 업로드 목적지는 Google Drive다.

## 2. 알리고 연결과 무관한 계승 축

- 이 레거시는 SMS를 발송하거나 SMS 문구를 조립하지 않고, 발송 대상 주소록 CSV를 만드는 프로그램이므로 “문구 조립 규칙”과 “SMS 전달 이력”은 원문상 존재하지 않는다.
- 레거시의 이력은 SMS 전달 결과가 아니라 거래처 동기화 입력 또는 생성한 수신자 목록 snapshot의 작업 이력이다.
- 알리고 연결과 무관한 핵심은 원천 수집, 수신자 포함·제외·중복 규칙, 지역·요일별 세그먼트, 번호 정규화, 결과 편집·필터, CSV 계약, 산출물 보관, 작업 이력, 외부 원천 동기화 실패·재시도 정책이다.

## 3. 현행 구현 확인

- 현행 주소록 경로는 partner-service가 만든 CSV를 notification-service가 읽고 50건씩 `AligoAddressBookClient`에 넘기는 구조다 (`PartnerAligoExportService.java:83-126`, `RestClientAligoCsvSourceClient.java:62-120`, `AligoAddressBookSyncService.java:57-95`).
- 현행 수신자 원천은 자체 DB의 활성 거래처 단일 집합이며, 레거시의 이카운트·KT 주소록·외부 거래처 DB·공유 시트 다중 원천 및 세 종류 결과 목록을 그대로 재현하지 않는다 (`PartnerAligoExportService.java:83-100`).
- 현행은 차단 거래처와 유효 휴대전화가 없는 거래처를 제외하며, 휴대전화 우선·일반전화 fallback 뒤 한국 휴대전화 접두사와 길이를 검증한다 (`PartnerAligoExportService.java:100-109`, `129-184`).
- 현행의 신용정보·전자소송·폐업 문자열 제외는 의도적으로 미적용이고 활성 상태와 차단 목록만 권위로 삼으므로, 레거시의 문자열 제외 규칙과 다르다 (`PartnerAligoExportService.java:33-40`).
- 현행은 지역 분류, 요일별 지역 매핑, 사용자가 지역을 고르는 골프회 목록, 전체 목록의 다중 원천 병합을 갖고 있지 않다.
- 현행은 번호 기준 다중 원천 중복 제거 규칙을 갖고 있지 않고 활성 거래처를 행 단위로 그대로 내보내므로, 자체 DB 안의 번호 중복도 제거하지 않는다 (`PartnerAligoExportService.java:100-116`).
- 현행 번호 정규화는 한 필드에서 번호 하나만 선택하고 휴대전화만 허용하므로, 레거시의 복수 번호 보존과 일반전화·인터넷전화 표현 범위는 계승하지 않는다 (`PartnerAligoExportService.java:129-184`).
- 현행 CSV는 UTF-8 BOM과 RFC 4180 escaping을 갖지만 열은 `그룹명,이름,휴대폰,비고` 4개여서 레거시 `전화번호,이름,그룹` 3열과 계약이 다르다 (`PartnerAligoExportService.java:59-66`, `186-201`).
- 현행 그룹은 거래처 그룹값 또는 기본값이고, 비고에는 거래처 코드를 넣는다; 레거시 그룹은 실행별 파일명이며 비고 열은 없다 (`PartnerAligoExportService.java:110-146`, `Index.html:540`, `583-601`).
- 현행 데스크톱은 전체 CSV 다운로드와 전체 주소록 sync만 제공하며, 결과 행의 사전 편집·문자열 필터·세그먼트별 파일명 생성 UI는 없다 (`AligoAddressBookPage.tsx:55-215`).
- 현행 주소록 sync는 50건 chunk, 429에 200·400·800ms backoff 3회, 비429 오류의 chunk별 계속 진행과 실패 표시는 갖는다 (`AligoAddressBookSyncService.java:40-47`, `69-95`, `103-130`).
- 현행 주소록 sync는 5xx·예외를 재시도하지 않고 429만 재시도하며, chunk 멱등키와 실패 chunk 재실행 저장소가 없다 (`AligoAddressBookClient.java:30-41`, `AligoAddressBookSyncService.java:75-91`).
- 현행 주소록 sync의 added·updated·skipped·failed 결과는 응답과 로그에만 남고 별도 영속 작업 이력으로 저장되지 않는다 (`AligoAddressBookSyncService.java:57-95`).
- 현행 CSV 다운로드는 브라우저 로컬 저장만 수행하고 Google Drive의 동일 파일명 갱신·신규 생성 보관은 계승하지 않는다 (`AligoAddressBookPage.tsx:60-73`).
- 현행 `MockAligoAddressBookClient`는 외부 호출 없이 입력 chunk 전건을 `added`로 반환하고 HTTP 200으로 가장한다 (`MockAligoAddressBookClient.java:46-62`).
- 따라서 현행 화면은 mock 경고문을 표시하면서도 mock의 전건 수를 `신규` 성공 건수로 표시해, “전달되지 않았는데 성공처럼 보이는” 상태를 동시에 만든다 (`AligoAddressBookPage.tsx:143-155`, `225-259`).
- `AligoSmsAdapter`도 자격값이 비었거나 placeholder이면 외부 호출 없이 `NotificationGatewayResult.success(...)`를 반환한다 (`AligoSmsAdapter.java:53-60`, `122-131`).
- 이 SMS stub 결과는 공통 서비스에서 요청 상태를 `SENT`, attempt 로그를 `SUCCESS`, 성공 metric으로 기록한다 (`NotificationService.java:252-277`, `NotificationRequest.java:134-150`).
- SMS stub-success 요청은 이미 `SENT`이므로 관리자 재시도 허용 상태가 아니며, 실제 미전달 건을 실패·재시도 대상으로 다루지 못한다 (`NotificationService.java:168-201`, `NotificationRequest.java:152-162`).
- 통합 테스트도 외부 호출이 없음을 알면서 요청을 `SENT`, 로그를 `SUCCESS`, 배차 발송 감사를 sent 건수로 기록하도록 명시적으로 고정한다 (`AligoSmsAdapterPlaceholderRuntimeGuardIT.java:42-62`, `AligoSmsAdapterSendAuditIT.java:37-50`).
- 그러므로 저장소의 “알림 QA stub-success 트랩”은 주소록 sync와 SMS 발송 양쪽에 존재하며, dev의 `SUCCESS`·`SENT`·`신규`는 실제 전달 증거가 아니다.
- 저장소 메모리도 dev의 SMS `SUCCESS`는 자격값 미설정 시 외부 호출 없는 stub이며 실제 전달 증거가 아니라고 명시한다 (`.claude/memory/feedback_notification_stub_success_qa_trap.md`).
- #1013의 별도 브랜치 commit `294272367` 계보에는 `AligoSmsAdapter` placeholder 결과를 `NOT_SENT_CREDENTIALS_PLACEHOLDER` 실패로 바꾸는 선행 변경이 있으나, 현재 #1016/PR #1037 브랜치의 adapter는 아직 stub `SUCCESS`다 (`git diff HEAD..origin/feat/1013-dispatch-parity`).
- 따라서 “보내지 않았으면 성공이 아니다” 판단과 동일한 축이 #1016에도 직접 존재하며, 이 결론은 알리고 실연결을 요구하지 않고 상태의 정직성만 요구한다.

## 4. 결론 — 알리고 연결을 제외하고 남는 계승 대상

| 계승 대상 | 현행 유무 | 근거·판정 |
|---|---|---|
| 등록 사용자만 실행하는 접근 통제 | 있음(방식 변경) | 현행은 데스크톱 권한과 `aligo.address-book` UPDATE 권한으로 trigger를 제한한다 (`AligoAddressBookPage.tsx:55-59`, `AligoAddressBookController.java:46-49`). |
| 이카운트 `SF(밴더)` 입력 제한 | 없음 | 현행은 자체 DB의 모든 활성 거래처를 원천으로 삼아 해당 그룹 제한이 없다. |
| KT 주소록 `SF벤더` 그룹 포함 | 없음 | 현행 원천에 KT 주소록이 없다. |
| 외부 거래처 DB·공유 시트 3종 보완 수집 | 없음 | 현행 원천은 partner-service 단일 DB다. |
| 활성·차단·유효 휴대전화 필터 | 부분 있음 | 현행은 활성·DB 차단·휴대전화 유효성은 갖지만 레거시 상태 문자열 제외와 규칙이 다르다. |
| 신용정보·전자소송·보류·폐업 제외 | 없음(과거 의도적 차이 기록) | 현행 테스트와 주석은 문자열 필터 미적용을 고정한다 (`PartnerAligoExportService.java:33-40`). 완전계승 관점에서는 정책 대체 여부를 명시적으로 확정할 항목이다. |
| 복수 번호 분리·형식화·우선순위 정렬 | 부분 있음 | 현행은 단일 휴대전화 정규화만 있고 복수 번호와 비휴대전화 표현은 버린다. |
| 다중 원천 번호 중복 제거와 원천 우선순위 | 없음 | 현행은 원천 병합·번호 dedup을 하지 않는다. |
| 요일별 지역 수신자 목록 | 없음 | 레거시 기본 매핑과 화면 선택 기능이 현행에 없다. |
| 전체 거래처 수신자 목록 | 부분 있음 | 전체 활성 거래처 CSV는 있으나 레거시 다중 원천 병합·중복 제거·하드코딩 차단 3건과 결과 집합이 다르다. |
| 선택 지역 골프회 수신자 목록 | 없음 | 현행에 해당 세그먼트와 지역 선택 UI가 없다. |
| 생성 전 행 편집·번호/이름/그룹 필터 | 없음 | 현행은 CSV 즉시 다운로드 또는 sync만 제공한다. |
| UTF-8 BOM CSV와 안전한 문자열 escaping | 있음 | 현행은 BOM과 RFC 4180 escaping을 구현했다. |
| 레거시 3열 CSV·실행별 그룹/파일명 계약 | 부분 있음 | 현행은 4열 주소록 계약과 고정 다운로드 파일명을 사용해 레거시 실행별 계약과 다르다. |
| 브라우저 로컬 CSV 다운로드 | 있음 | 데스크톱에서 Blob을 파일로 저장한다. |
| 동일 이름 산출물 갱신·보관 | 없음 | 레거시 Google Drive 역할을 대체하는 서버측 산출물 보관소가 없다. |
| 거래처 동기화 결과 건수 집계 | 부분 있음 | 현행 sync는 added·updated·skipped·failed를 집계하지만 주소록 mock 결과이며, 레거시 원천→거래처 마스터 추가·갱신·변경없음·실패와 의미가 다르다. |
| 생성 목록 snapshot 작업 이력 저장 | 없음 | 현행 주소록 sync·CSV 다운로드에는 영속 작업 이력이 없다. 일반 SMS 로그와 배차 발송 감사는 다른 도메인이라 대체물이 아니다. |
| 날짜 범위 이력 목록·상세 복원 | 없음 | 현행 주소록 화면에는 이력 조회와 결과 snapshot 복원이 없다. |
| 429·일시 장애 재시도 | 부분 있음 | 현행 주소록 sync는 429만 3회 backoff하고, 레거시는 외부 거래처 DB 요청에서 429와 5xx·예외를 기본 5회 재시도한다. |
| 부분 실패 후 나머지 처리와 실패 식별 | 부분 있음 | 현행은 실패 chunk 뒤 다음 chunk를 계속하고 chunk 식별자를 반환하지만 행별 실패·원인·재실행 저장은 없다. |
| 비전송을 성공으로 세지 않는 상태 계약 | 없음(결함) | 주소록 mock은 전건 `added`, SMS placeholder는 `SUCCESS`·`SENT`·sent 감사로 기록한다. 알리고 미연결을 유지하더라도 `NOT_SENT` 또는 dry-run 결과로 분리할 계승 대상이다. |
| SMS 문구 조립 | 해당 없음 | 레거시 15 원문에 SMS 본문 생성이 없다. |
| SMS 전달 이력 | 해당 없음 | 레거시 이력은 목록 snapshot이며 실제 전달 이력이 아니다. |
| 알리고 API 호출 | 범위 제외·레거시에도 없음 | 실호출 0건은 의도된 상태이며 이번 계승 목표가 아니다. |

최종 범위는 **수신자 집합의 의미 보존 + CSV/검토 UX + 작업 이력 + 실패·재시도 + 비전송 상태의 정직성**이다. 알리고 API 연결은 이 목록에 포함하지 않는다.

## 5. 조사 제약 준수

- 정적 원문·현행 코드·테스트·브랜치 간 read-only diff만 확인했으며 코드·자격값·Docker·실 DB를 변경하지 않았고 stage·commit·push도 하지 않았다; 신규 파일은 이 보고서 1개뿐이다.
