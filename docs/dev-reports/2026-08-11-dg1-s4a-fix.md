## 1. 결론

- R-1은 **11개 역할 × 7비트 exact** 감시로 보강했고, 두 방향의 뮤테이션이 모두 RED임을 확인했다.
- PM 판단에 따라 `draftReference`는 만들지 않았다. 세금계산서·분개·입금보고서의 선례대로 UUID는 내부 route/wire key로만 사용한다.
- 정산서 DRAFT도 `/accounting/sales-commission-settlements/{id}`로 상세 진입한다.
- 목록 링크는 입금보고서의 native `Link` + `returnTo` + `returnEntryKey` + scroll anchor 규약을 그대로 준용했다.
- R-5는 공유 DB나 배포 JAR 없이 H2 in-memory, Spring Boot embedded server, RANDOM_PORT, `TestRestTemplate`의 실제 HTTP 요청으로 SALES 토큰 `403`을 증명했다.
- 사용자 화면의 UUID 문자열은 정산 목록·상세에 렌더되지 않는다. route path와 API wire의 `id`는 내부 키로 남긴다.

공유 DB write, 배포, git 조작, `samhan-*` 조작, S4b 연결 버튼, 확정 취소 변경은 수행하지 않았다.

## 4. R-3·R-4 구현 근거

`clients/desktop/src/renderer/routes/SalesCommissionSettlementListPage.tsx`에 다음을 적용했다.

- DRAFT와 CONFIRMED 모두 native `<Link>`를 렌더한다.
- href는 `/accounting/sales-commission-settlements/{row.id}`다.
- `state.returnTo = { pathname, search }`, `state.returnEntryKey = location.key`를 전달한다.
- 클릭 전 `saveScrollAnchor(location.key)`를 호출한다.
- 목록 재진입 시 `getScrollAnchor(location.key)`를 읽어 scroll을 복원한다.
- 화면 텍스트와 접근성 라벨에는 문서번호 또는 `임시저장 · 날짜`만 사용한다.

`clients/desktop/src/renderer/routes/SalesCommissionSettlementDetailPage.tsx`는 입금보고서의 `getReturnTo` 관례를 따라 history entry가 있으면 `navigate(-1)`, 없으면 `returnTo`로 replace 이동한다. 따라서 목록의 query 상태와 scroll anchor가 유지된다. 새 복귀 방식을 만들지 않았다.

추가 회귀 테스트:

- `SalesCommissionSettlementListPage.test.tsx`: DRAFT/CONFIRMED 링크, 내부 id href, DRAFT 링크 텍스트, UUID 미렌더, `returnTo` query 전달
- `SalesCommissionSettlementDetailPage.test.tsx`: DRAFT 내부 id 상세 진입 및 목록 query로 history 복귀

## 5. R-2 UUID 화면 노출 전수 확인

정산 API의 `id` wire 필드는 내부 route 조인에 필요하므로 유지했다. 대신 정산 목록·상세의 렌더 경로를 grep 및 컴포넌트 테스트로 확인했다.

| 위치 | UUID 처리 | 사용자 노출 |
|---|---|---|
| REST/API `id` | wire 내부 식별자 | 허용된 내부 사용 |
| 목록 href | `/.../{id}` | 주소의 내부 route key, 링크 라벨에는 없음 |
| 목록 라벨/컬럼 | `documentNo` 또는 `임시저장 · settlementDate` | UUID 없음 |
| 상세 제목/필드 | 문서번호 또는 상태/업무값 | UUID 없음 |
| 라이브 DOM body | UUID 정규식 점검 | `body_uuid_visible=false` |

즉, PM이 확정한 저장소 규칙에 따라 route/wire UUID는 허용하고 화면 문자열 노출만 차단했다. `draftReference` 같은 새 식별자 축은 추가하지 않았다.

## 6. R-5 실제 HTTP 403 증명

격리 조건:

- 테스트: `services/accounting-service/src/test/java/com/samhanair/logis/accounting/it/SalesCommissionSettlementHttpGuardIT.java`
- `@SpringBootTest(webEnvironment = RANDOM_PORT)` + embedded Tomcat
- `spring.profiles.active=local`, H2 in-memory
- Eureka 비활성화
- 외부 client 6종 `@MockBean` 격리
- `TestRestTemplate`로 실제 TCP HTTP GET
- `X-User-Role: SALES`, 동적 permission `VIEW=false`

요청:

```text
GET /accounting/sales-commission-settlements?page=0&size=20
X-User-Id: 00000000-0000-0000-0000-000000000901
X-User-Role: SALES
```

확보한 원문:

```text
status=403 body={"success":false,"code":"FORBIDDEN","message":"[SP-PO-1] 동적 권한 deny — page=accounting.sales-commission-settlement action=VIEW role=SALES reason=account permission missing","data":null,"timestamp":"2026-08-11T09:00:18.411604700Z"}
```

검증은 status 403, `success:false`, `code:FORBIDDEN`, `동적 권한 deny`, page code, `action=VIEW`를 모두 assert한다. 이는 낡은 배포 JAR이나 화면 메뉴 숨김이 아닌 격리된 실제 HTTP guard 증명이다.
