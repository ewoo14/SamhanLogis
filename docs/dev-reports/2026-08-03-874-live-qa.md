### 0-3. standalone 기동 2차 실패 및 안전한 우회

- 실행 결과: HTTP 연결 실패.
- 실패 원문(standalone jar 로그): `FlywayValidateException: Validate failed: Migrations have failed validation` / `Detected resolved migration not applied to database: 68.`

- 금지사항 준수: 공유 DB에 migration 적용·write·DDL을 하지 않았다.
- 조치: 공유 DB를 변경하지 않기 위해 `--spring.flyway.enabled=false`로 동일 jar를 재기동한다. DB 스키마는 기존 dev 시드를 읽기만 하며, 해당 옵션은 QA 기동 시점의 migration 실행을 막는다.

### 0-4. standalone 기동 3차 실패

- 실행 결과: HTTP 연결 실패.
- 실패 원문: `SchemaManagementException: Schema-validation: missing column [lines_json] in table [cash_receipts]`
- 원인: Flyway를 끈 상태에서도 Hibernate `validate`가 대상 HEAD 엔티티와 공유 dev DB의 이전 스키마 차이를 검증해 중단했다.

## 2. 라이브 장애/데이터 확인

- 공유 DB read-only SELECT 결과 `daily_closings`는 총 2건이며 모두 `[DEV-SEED]`의 `2020-01-02` `SALES/TAX_INVOICE` 행이었다. `2026-05-19` 및 `2026-07-27` 대상은 없었다.
- standalone jar의 대상 엔드포인트는 목록 요청 시 `PartnerLookupClient`가 Docker 내부 호스트명 `http://partner-service/internal/partners/lookup-by-ids`에 접근하다 실패했고, 상세 요청도 정상 표를 반환하지 못했다.
- standalone 기동 자체는 성공했지만, 공유 Docker 네트워크 밖의 host 프로세스가 Docker 내부 service name을 해석하지 못하는 환경 제약으로 실제 상세 표 검증까지 진행되지 않았다.
- 공유 Docker stack은 재빌드하지 않았고, 공유 DB write/DDL도 수행하지 않았다.
- Playwright 실행 결과: 로컬 격리 캡처 스펙 `1 passed` — 이는 캡처 절차 성공이며, 기능 판정 성공을 의미하지 않는다.
