## 2. 판정

**결함 1건 재현. R7 재수렴 불통과.**

원 결함인 삭제행 UUID 재발급은 해소됐다. 그러나 행 단위 트랜잭션은 “앞선 성공행을 전체 롤백하지 않는다”까지만 성립한다. 한 행이 실제 DB 제약에서 실패하면 HTTP 500으로 배치 루프가 중단되어 **뒤의 정상 행은 적재되지 않는다**. 이는 유효한 관리자 업로드 경로로 매번 재현된다.

| 각도 | 판정 |
|---|---|
| 1. 원 결함 해소 | PASS — 정본 거래처 UUID 동일, 활성 1/삭제 0, 사용자 참조 고아 0 |
| 2. 행 실패 격리 | FAIL — 앞 행만 커밋, 실패행 PENDING, 뒤 정상행 미처리 |
| 3. 정상 분포 | PASS — 7,253건 분포·null·created_at 교정 유지 |
| 4. 새 표면 | 기동/초기화 PASS, null fallback의 지원되는 프로덕션 발화 경로 없음 |

## 3. 각도 1 — 원 결함 해소

R4의 `1068689215`와 다른 정본 숫자 거래처 `00`을 사용했다. 순서는 정본 적재 → 배송지 API로 참조 생성 → 관리자 DELETE → 같은 7,253건 정본 XLSX 재적재였다.

응답 원문 핵심:

```text
DELETE /admin/partners/00 -> HTTP 200
POST /admin/partners/imports/ecount-xlsx -> HTTP 200
totalRows=7253 imported=0 updated=7253 activeCount=7253 suspendedCount=0
```

삭제 전 UUID와 재적재 직후 SQL 원문:

```sql
SELECT p.id::text AS active_uuid,
       '<before_uuid>' AS before_uuid,
       count(*) FILTER (WHERE p.is_deleted=false) AS active_rows,
       count(*) FILTER (WHERE p.is_deleted=true) AS deleted_rows,
       (SELECT count(*)
          FROM partner_shipping_addresses a
         WHERE a.id='<이번 API가 반환한 addressId>'
           AND a.partner_id <> p.id) AS orphan_rows
  FROM partners p
 WHERE p.partner_code='00'
 GROUP BY p.id;
```

```text
a2dbdb4c-2e80-4718-962c-8a5f4fa4babf|
a2dbdb4c-2e80-4718-962c-8a5f4fa4babf|1|0|0
```

즉 UUID 동일, 활성 1, 삭제 0, 이번 사용자 참조 고아 0이다. 검증 후 배송지는 실 DELETE API로 지웠고 정본 거래처는 정본 재적재로 원래 활성 상태를 유지했다.


## 6. 각도 4 — `@Lazy` 자기 참조 새 표면

### 6.1 기동·초기화

새 DB와 새 JAR 기동 로그 원문:

```text
Database: jdbc:postgresql://sol1154-r7-db:5432/partner_r7 (PostgreSQL 16.14)
Tomcat started on port 8095 (http) with context path '/'
Started PartnerServiceApplication in 9.924 seconds (process running for 10.529)
```

`APPLICATION FAILED`, `BeanCurrentlyInCreation`, circular-reference 문구는 0건이다. `@Lazy` 자기 참조 때문에 기동·초기화가 깨지는 결함은 재현되지 않았다.

### 6.2 `transactionalProxy == null` 프로덕션 도달성

```text
EcountPartnerImporter.java:118 @Lazy
EcountPartnerImporter.java:119 @Autowired
EcountPartnerImporter.java:120 private EcountPartnerImporter transactionalProxy;
EcountPartnerImporter.java:541 target = transactionalProxy == null ? this : transactionalProxy;
EcountPartnerImporter.java:549 target = transactionalProxy == null ? this : transactionalProxy;
```

지원되는 프로덕션 경로는 Spring bean이며 `@Autowired`는 기본 `required=true`다. bean 초기화 완료 뒤 importer controller가 호출되므로 null fallback에 도달하지 않는다. 실제 정본 삭제행 복원이 성공한 사실도 프록시 경로가 실행됐다는 행동 증거다. null이면 원 self-invocation 경로로 돌아가 R5의 새 UUID INSERT가 재현돼야 한다.

반면 Mockito 단위테스트는 `EcountPartnerImporterTest.java:69-70`의 `@InjectMocks` 직접 인스턴스여서 Spring field injection이 없고 null fallback을 사용한다. 프로덕션에서 이를 발화시키려면 Spring 밖에서 importer를 직접 생성하거나 reflection으로 필드를 null로 만드는 비지원 경로가 필요하다. **지원되는 실 사용자 프로덕션 경로에서는 관측 가능한 발화 경로가 없다.**
