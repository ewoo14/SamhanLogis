# #1069 S14 SOL fix 지시서 — 판매전표 세트 재전개 저장 잠금

## 판정

**실 사용자 경로에서 재현 가능한 결함 2건. 머지 차단.**

- **F1 — 재전개 대기 중 행 편집 후 저장이 영구 잠긴다.** 구성품 행의 옵션 컨텍스트는 행 ID로 조회하지만, 수량·단가·규격 편집 시 갱신본을 `productId` 키에 추가한다. 이때 기존 행 ID 컨텍스트와 `productId` 고아 컨텍스트가 함께 남는다. 재전개 응답이 성공하거나 실패해도 행 ID 컨텍스트만 정리되므로, 고아 컨텍스트의 `expansionPending=true`가 페이지 수명 동안 유지되어 일반 SINGLE 행까지 포함한 전표 전체의 저장 버튼을 계속 비활성화한다. 화면 행을 삭제하거나 다른 품목으로 교체해도 고아 키는 정리되지 않으며 페이지를 다시 열어야 회복된다.
- **F2 — 정상 재전개 대기 중 저장 차단 사유가 보이지 않는다.** 옵션 변경 직후 `bundleExpansionPending`이 저장을 차단하지만 화면 안내는 `priceResolutionBusy`일 때의 `최근단가 확인 중…`만 제공한다. 정상 네트워크에서도 응답 전까지 사용자는 저장 버튼이 왜 비활성화됐는지 알 수 없다.

HTTP 공통 클라이언트에는 10초 timeout이 있으므로 단순 무응답만으로 영구 대기가 되지는 않는다. F1은 정상 응답·실패·timeout 어느 쪽에서도 고아 pending이 남는 별도 영구 잠금 경로다.

재현 난이도:

- F1 **쉬움** — 옵션이 있는 EXPAND 세트 1개와 재전개 응답을 잠시 지연할 수 있는 네트워크만 필요하다. 빠르게 `옵션 변경 → 수량/단가/규격 편집`하면 된다.
- F2 **매우 쉬움** — 옵션이 있는 EXPAND 세트에서 옵션을 한 번 변경하면 응답 전 즉시 관찰된다.

## 1. 좌표

### F1 — 행 ID 컨텍스트가 `productId` 고아 컨텍스트로 복제됨

- `clients/desktop/src/renderer/routes/SlipFormPage.tsx:719-738`
  - `updateLineFromUser`는 컨텍스트를 `before.id`로 읽은 뒤 갱신본을 `[before.productId!]`에 쓴다.
  - 기존 `[before.id]`를 교체하지 않으므로 두 키가 동시에 남는다. 대기 중 편집이면 복제본도 `expansionPending=true`다.
- `clients/desktop/src/renderer/routes/SlipFormPage.tsx:828-838`
  - 재전개 완료 정리는 `delete next[source.id]`만 수행한다. 위에서 생성된 `productId` 고아 키는 성공·빈 결과·실패 모두에서 남는다.
- `clients/desktop/src/renderer/routes/SlipFormPage.tsx:941-945`
  - 품목 교체도 현재 화면 행 ID만 삭제한다. 고아 키는 회복 동작으로 정리되지 않는다.
- `clients/desktop/src/renderer/routes/SlipFormPage.tsx:756-763`
  - 행 삭제도 현재 화면 행 ID만 삭제한다. 고아 키는 회복 동작으로 정리되지 않는다.
- `clients/desktop/src/renderer/routes/SlipFormPage.tsx:1399-1407`
  - 화면 행과 무관하게 `expandedBundleOptions`의 모든 값을 검사하므로 고아 pending 하나가 전표 전체 저장을 영구 차단한다.

재현:

1. 판매전표 입력에서 옵션이 있는 `SINGLE_SET / EXPAND` 세트를 선택해 첫 구성품과 옵션 UI가 나타날 때까지 기다린다.
2. 옵션을 변경해 `/slips/expand-line` 재전개를 시작한다.
3. 응답 전에 같은 구성품 행의 수량, 단가 또는 규격 중 하나를 편집한다.
4. 재전개 후속 응답을 정상 성공시킨다. 실패나 10초 timeout이어도 결과는 같다.
5. 창고와 유효한 일반 SINGLE 행을 갖춘 상태에서도 저장 버튼이 계속 비활성임을 확인한다.
6. 문제 행을 삭제하거나 일반 품목으로 교체해도 저장이 회복되지 않고, 페이지를 다시 열어야만 회복됨을 확인한다.

### F2 — bundle pending 저장 차단 안내 부재

- `clients/desktop/src/renderer/routes/SlipFormPage.tsx:1398-1407`
  - `bundleExpansionPending`은 `canSubmit`에 포함되어 저장을 차단한다.
- `clients/desktop/src/renderer/routes/SlipFormPage.tsx:2059-2078`
  - 저장 영역의 상태 문구는 `priceResolutionBusy`만 설명하며 `bundleExpansionPending`에 대응하는 가시 문구나 live 안내가 없다.

재현:

1. 옵션이 있는 EXPAND 세트를 전개한 뒤 옵션을 변경한다.
2. 재전개 응답 전에 저장 영역을 본다.
3. 저장 버튼은 비활성이나 처리 중인 작업과 저장 불가 이유는 아무 곳에도 표시되지 않는다.

## 2. 불변식

1. 옵션 컨텍스트의 소유권은 구성품 행 ID 하나에만 귀속되어야 하며, `productId`가 같거나 행이 재생성·재정렬돼도 다른 행 또는 고아 키로 복제되면 안 된다.
2. 재전개 성공·실패·timeout·연속 변경·행 편집·품목 교체·행 삭제 뒤에는 현재 화면 행에 대응하지 않는 pending 컨텍스트가 남으면 안 된다.
3. 재전개가 실제 진행 중일 때만 옛 구성품 저장을 차단하고, 종료 뒤에는 최신 구성품과 정상 SINGLE 행을 저장할 수 있어야 한다.
4. 저장 차단 중에는 사용자가 기다려야 하는 작업과 저장 불가 이유를 화면에서 알 수 있어야 한다.
5. 옵션 미입력 기본 전개와 BUNDLE을 고르지 않은 일반 전표는 새 차단에 걸리면 안 된다. 정상 SINGLE 기준 **2,387행 / 2,171전표 / 2,902,645,781원**의 생성·수정·모바일 저장 계약을 바꾸면 안 된다.
6. S2·S4·S6·S8·S10·S12가 닫은 경합·실패·옵션 UI·최신 payload 계약과 `#1063` 초기 5행/마지막 행 1개 증식/trailing 빈행 제외 규약을 유지해야 한다.

구현 수단은 지정하지 않는다. 특히 저장 차단 자체를 제거하거나 임의 시간 후 옛 구성품을 저장 가능하게 만드는 방식은 금지한다.

## 3. 양방향 RED

### RED-B — 결함 폐쇄

- 재전개 pending 중 같은 행의 수량·단가·규격을 각각 편집하고 최종 응답을 성공시킨 뒤에도 저장이 비활성이면 RED.
- 같은 세 경로에서 최종 응답을 실패 또는 timeout 처리한 뒤, 오류 행을 삭제하거나 정상 품목으로 교체했는데 저장이 회복되지 않으면 RED.
- 위 경로 뒤 현재 화면 행 ID와 대응하지 않는 `expansionPending=true` 컨텍스트가 하나라도 남으면 RED.
- 재전개 pending 중 저장 버튼이 비활성인데 처리 중이라는 가시 안내와 접근성 상태 안내가 없으면 RED.
- 재전개 전후 첫 구성품이 같을 때 옵션 UI가 사라지거나, 후속 옵션 변경이 최신 옵션으로 다시 전개되지 않으면 RED.
- 재전개 응답 전 저장으로 옛 구성품이 payload에 들어가면 RED.
- 같은 첫 구성품을 공유하는 세트 두 건 또는 행 재정렬 뒤 옵션이 다른 행에 붙으면 RED.

### RED-A — 반대급부 보존

- 고아 pending을 없애기 위해 재전개 중 저장을 허용하여 옛 구성품이 payload로 나가면 RED.
- pending 안내를 추가한 뒤 재전개가 끝났는데도 안내 또는 저장 차단이 남으면 RED.
- BUNDLE을 선택하지 않은 일반 SINGLE 전표가 bundle pending 차단이나 안내에 걸리면 RED.
- 재전개 실패 뒤 사용자가 오류를 인지하거나 행을 교체·삭제해 회복할 수 없으면 RED.
- 연속 옵션 변경의 중간 응답이 적용되거나 구성품이 누적·중복되면 RED.
- 옵션 확정 후 BUNDLE 부모 행이 화면 또는 저장 payload에 남으면 RED.
- 초기 5행, 마지막 행 편집 시 빈행 1개 증식, trailing 빈행 저장 제외 중 하나라도 깨지면 RED.
