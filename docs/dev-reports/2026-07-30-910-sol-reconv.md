## 결함 1 — `extraMetadata.version` env 리터럴로 두 Windows 릴리스가 중단된다

### 실 사용자 경로

1. 사용자가 날짜 버전 A를 설치해 사용한다.
2. 운영자가 공통 release wrapper로 후속 날짜 버전 B를 만든다.
3. wrapper는 `SAMHAN_RELEASE_PACKAGE_VERSION=1.20260730.N`을 자식 프로세스에
   전달한다.
4. electron-builder가 `electron-builder.yml`을 읽지만 `extraMetadata.version`의
   `${env.SAMHAN_RELEASE_PACKAGE_VERSION}`을 환경값으로 치환하지 않는다.
5. 포장 대상 `package.json.version`과 `AppInfo.version`이 env 표현식 리터럴이 된다.

## 결함 2 — 기존 설치본의 첫 업데이트 안내에 내부 semver가 노출된다

이 결함은 결함 1 때문에 표준 릴리스 경로에서 현재 마스킹된다. 결함 1을 제거하거나
요구사항에 제시된 새 형식 feed를 제공하는 즉시 이미 배포된 구 설치본에서 도달한다.

### 실 사용자 경로

1. 사용자는 기존 DESKTOP `0.1.0` 또는 AROLOGIS `1.0.0` 설치본을 실행한다.
2. updater가 `version: 1.20260730.2`인 새 feed를 읽는다.
3. electron-updater는 이를 정상 업데이트로 판정하고 `update-available`을 발생시킨다.
4. 구 설치본의 main process는 `info.version`을 변환하지 않고 renderer IPC로 보낸다.
5. renderer는 그 값을 사용자 문장에 보간한다.

### 재현 절차

1. 저장소에 보존된 실제 설치 산출물에서 package version을 확인했다.

   - DESKTOP:
     `clients/desktop/release/2026-07-30-2/win-unpacked/resources/app.asar`
     → `0.1.0`
   - AROLOGIS:
     `clients/arologis-desktop/release/2026-07-30-3/win-unpacked/resources/app.asar`
     → `1.0.0`

2. 두 `app.asar`의 실제 `out/main/index.js`를 메모리로 추출해 event payload를
   확인했다.

   ```text
   broadcast({kind:"available",version:info.version})
   broadcast({kind:"downloaded",version:info.version})
   ```

3. 설치된 electron-updater 6.8.9의 실제 `AppUpdater.isUpdateAvailable()`에
   구 버전과 새 feed 버전을 넣었다.

   ```text
   0.1.0       -> 1.20260730.2 = true
   1.0.0       -> 1.20260730.2 = true
   ```

4. 보존된 renderer가 IPC의 `status.version`을 그대로 안내 문구에 보간하는 경로를
   대조했다.

### 4. `extraMetadata.version`과 패키징

**FAIL — 유효 semver 주입 전에 env 리터럴이 남아 패키징이 중단된다.**

공통 생성기가 반환한 `1.20260730.N` 자체는 Node `semver` 기준 유효하다. 문제는 그
값이 builder metadata에 들어가지 않는다는 것이다. 이 때문에 새 `app.asar`와 feed의
version 일치 여부는 실제 산출물 기준으로는 **판정불가**다. 양쪽 모두 같은
`AppInfo.version`을 정본으로 삼도록 설계돼 있지만 해당 `AppInfo.version`이 유효
값이 아니어서 산출이 완료되지 않는다.

지시에 따라 `build:win`은 시도하지 않았다. 패키징 없이 가능한 실제 loader/transformer/
`AppInfo` 실행까지만 수행했다.
