# PR #1060 R19 재수렴 — `partner_code` fallback 오연결 검증

## 조사 로그

### 1. R18 기준선 확인

- R18은 활동 조회를 `bizNo` primary exact 조회 후 결과가 없을 때 동일 auth의 `partnerCode`로 exact fallback하는 방식으로 설명한다.
- 공유 DB 측정 기준은 `PARTNER_ORDER` 출고 20건, 서로 다른 `partner_code` 11개, 해당 출고의 `business_number`는 모두 NULL, auth 행은 2개였다.
- R18 자체는 "fallback은 서로 다른 거래처의 행을 합치지 않는다"고 결론 냈지만, 이번 라운드는 키 공간 충돌 가능성을 SQL로 독립 검증한다.

- 실제 fallback 구현은 두 소유 서비스 모두 `businessNumber` 조회 결과가 null일 때만 `legacyPartnerCode` exact 조회를 수행한다.

### 13. 키 비교 규칙의 코드 위치 확인

재현 명령:

```powershell
rg -n -C 4 "findLastConfirmedAtByBizCode|findLastOutboundDateByBusinessNumber|findLastOutboundDateByPartnerOrderCode|findLastConfirmedAtByPartnerCode|legacyPartnerCode" <관련 5개 Java 파일>
```

확인된 위치와 규칙:

- `services/partner-auth-service/src/main/java/com/samhanair/logis/partnerauth/client/PartnerActivityClient.java:51`: `legacyPartnerCode != businessNumber`일 때만 fallback query parameter 전송.
- `services/partner-order-service/src/main/java/com/samhanair/logis/partnerorder/repository/PartnerOrderRepository.java:23`: primary는 `replace(bizCode, '-', '') = businessNumber`.
- 같은 파일 `:29`: fallback은 `partnerCode = legacyPartnerCode` exact.
- `services/partner-order-service/src/main/java/com/samhanair/logis/partnerorder/web/PartnerActivityController.java:26`: primary가 null일 때만 fallback.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/repository/SlipRepository.java:29`: primary는 `replace(businessNumber, '-', '') = businessNumber`, `OUTBOUND`, soft-delete 제외.
- 같은 파일 `:35`: fallback은 exact `partnerCode`, `PARTNER_ORDER`, `OUTBOUND`, soft-delete 제외.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/web/PartnerActivityController.java:27`: primary가 null일 때만 fallback.

따라서 `477-03-10899` 표본은 auth의 무하이픈 사업자번호 `4770310899`로 primary 조회되어 45행 중 OUTBOUND 최신일이 잡힌다. 같은 문자열이 code에도 있어도 primary 결과가 존재하므로 fallback은 실행되지 않는다.

### 14. auth 2행의 fix 전후 활동 hit 대조

재현 명령:

```powershell
docker exec samhan-postgres psql -U samhan -d partner_order_db -c "WITH auth(biz_no,partner_code) AS (VALUES ('1068689215','1068689215'),('2118712345','2118712345')) SELECT a.biz_no, a.partner_code, MAX(o.confirmed_at) FILTER (WHERE replace(coalesce(o.biz_code,''),'-','')=a.biz_no) AS primary_last_order, MAX(o.confirmed_at) FILTER (WHERE o.partner_code=a.partner_code) AS code_last_order, (a.partner_code<>a.biz_no) AS fallback_allowed FROM auth a LEFT JOIN partner_orders o ON o.confirmed_at IS NOT NULL GROUP BY a.biz_no,a.partner_code ORDER BY a.biz_no;"
docker exec samhan-postgres psql -U samhan -d slip_db -c "WITH auth(biz_no,partner_code) AS (VALUES ('1068689215','1068689215'),('2118712345','2118712345')) SELECT a.biz_no, a.partner_code, MAX(s.slip_date) FILTER (WHERE replace(coalesce(s.business_number,''),'-','')=a.biz_no AND s.slip_type='OUTBOUND' AND s.is_deleted=false) AS primary_last_outbound, MAX(s.slip_date) FILTER (WHERE s.partner_code=a.partner_code AND s.source_type='PARTNER_ORDER' AND s.slip_type='OUTBOUND' AND s.is_deleted=false) AS fallback_last_outbound, (a.partner_code<>a.biz_no) AS fallback_allowed FROM auth a LEFT JOIN slips s ON true GROUP BY a.biz_no,a.partner_code ORDER BY a.biz_no;"
```

```text
------------+--------------+---------------------+-----------------+------------------

(2 rows)
```

출력 원문(출고):


- auth 모집단에서 활동이 잡히는 거래처 수는 fallback 전 1곳, fallback 후 1곳이다. 증감은 0곳이다.

- `1068689215`는 주문·출고 활동이 모두 없어 fix 후에도 활동 누락 상태인 거래처 1곳이다. 그러나 이는 매핑된 실제 활동이 있는데 조회가 빠지는 누락으로 재현된 것이 아니라, 원장에 활동 자체가 없는 상태다.
- 현재 auth는 두 행 모두 fallback 불허(`partner_code = biz_no`)이므로 이 전후 동일성은 규칙이 일반적으로 안전해서가 아니라 auth 행이 2개뿐이고 둘 다 fallback에 진입하지 않기 때문이다.

## 최종 판정

### 질문별 답

1. **서로 다른 거래처가 같은 활동으로 이어질 수 있는가**
   - 현재 auth 사업자번호와 같은 `partner_code` 행 중 다른 거래처 소유로 확인된 행은 주문 0행, fallback 대상 출고 0행이다.
   - 거래처 원장 전체의 `partner_code = 다른 거래처 biz_no` 교차 충돌도 0쌍이다.
   - 그러나 레거시 `PARTNER_ORDER` 출고 source를 따라가면 현재 code 소유자와 다른 사업자번호 snapshot이 확인되는 출고가 13행이고, code별 최신 fallback이 다른 사업자 source인 code가 7개다. 즉 규칙 자체가 소유권을 증명하지는 않는다.

2. **한 auth가 남의 출고를 가져가 부당하게 차단을 면제받는가**
   - 현재 auth 2행에서는 0곳이다. 두 auth 모두 `partner_code = biz_no`라 fallback query parameter가 전송되지 않는다.
   - 위 7개 위험 code를 가진 auth는 현재 0행이다. 그 auth가 실제 생성 가능한지 확인하려면 전환 경로를 조사해야 하므로 이번 지시 범위에서는 미판정이며 결함으로 세지 않는다.

3. **활동이 여전히 누락되는 거래처와 fix 전후 수**
   - 현재 auth 모집단: 활동 hit 1곳 → 1곳, 증감 0곳. `1068689215` 1곳은 활동이 없지만 원장에도 해당 활동이 없어 조회 누락으로 재현되지 않았다.
   - 레거시 출고 소유자 11곳: primary hit 4곳 → fallback 포함 11곳, 7곳 복구, 활동 존재가 계속 누락되는 곳 0곳.
   - 최신 시각 기준으로는 `P-2026-0001`의 2026-05-31 fallback 출고가 primary 2026-05-20 때문에 읽히지 않아 11일이 누락된다. 현재 auth가 없어 접근 판정 영향은 재현되지 않았다.

4. **차단 판정 flip 수**
   - 0곳. 부당 면제 0곳, 신규 차단 0곳.
   - 이 0은 규칙이 맞아서가 아니라 **auth 행이 2개뿐이고 둘 다 fallback에 진입하지 않기 때문**이다.

### 결함 수

**이 각도에서 현재 데이터와 현재 auth 모집단으로 도달 가능한 결함 0.**

미판정 1건:

- 파일: `services/partner-order-service/src/main/java/com/samhanair/logis/partnerorder/repository/PartnerOrderRepository.java:29`, `services/slip-service/src/main/java/com/samhanair/logis/slip/repository/SlipRepository.java:35`
- 가능한 사용자 조작: 현재 거래처 원장 code가 `P-2026-0001`, `0002`, `0003`, `0005`, `0006`, `0007`, `0008`인 거래처에 auth가 생성되고 활동 조회/차단 판정을 실행.
- 가능한 잘못된 결과: code 아래 저장된 다른 사업자 snapshot의 주문·출고가 해당 auth 활동으로 귀속되어 차단 면제 또는 만료 연장.
- 실데이터 증거: §21에서 다른 사업자 source 출고 13행, 다른 사업자 source가 최신인 code 7개를 확인.
