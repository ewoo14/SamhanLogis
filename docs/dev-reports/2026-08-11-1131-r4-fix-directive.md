# PR #1131 R4 fix directive — 수량 0의 조용한 행삭제 · 기존 BUNDLE 0-head 계보 저장

## 판정

**BLOCKING. 실 사용자 경로로 재현 가능한 결함이 있다.**

결함은 2건이다.

1. 수정 화면에서 기존 행 수량에 `0` 또는 빈 값을 입력하면, 서버의 “수량 1 이상” 가드로 보내지
   않고 저장 payload에서 그 행 자체를 제외한다. 다른 유효 행이 하나라도 있으면 PUT이 성공하고
   사용자가 삭제 버튼을 누르지 않은 기존 행이 조용히 삭제된다.
2. R3 fix의 신규 익명 BUNDLE membership 검증은 head 삭제를 거부한다. 그러나 이미 저장된 BUNDLE
   구성품은 `lineId` 계보 승계 경로를 타며, 요청 그룹에 신규 익명 라인이 없으면 신규 membership
   검증을 통째로 건너뛴다. 사용자가 수정 화면에서 기존 BUNDLE의 첫 `setHead=true` 행만 삭제하면
   PUT이 성공하고, 남은 행은 `parentSetModel`을 계속 보유하지만 `setHead=true`가 0개인 상태로 저장된다.

## 사용자 재현

### A. 기존 행 수량 0

1. 라인이 2개 이상인 기존 DRAFT 매출전표를 연다.
2. `직접 수정`에서 한 기존 행의 수량을 `0`으로 바꾼다. 삭제 버튼은 누르지 않는다.
3. 저장한다.
4. 화면 projection이 수량 0인 기존 `lineId`를 payload에서 누락하고, 나머지 행만 PUT한다.
5. PUT이 성공하며 누락 행은 전체교체 저장에서 삭제된다.

### B. 기존 BUNDLE head 삭제

1. 구성품이 2행 이상이며 head가 정확히 1개인 기존 DRAFT 매출전표를 연다.
2. `직접 수정`에서 BUNDLE 첫 행(head)을 `×` 버튼으로 삭제한다. 또는 그 head 수량을 `0`으로
   바꿔 결함 A의 projection 누락을 유발한다.
3. 다른 신규 행을 추가하지 않고 저장한다.
4. PUT이 성공한다.
5. 저장 결과에는 같은 `parent_set_model`의 비-head 행만 남고 head 수는 0이다.

일회성 FE/service probe 원문:

```text
R4-QTY-ZERO|uiQuantity=0|payloadLines=1|omittedLineId=server-line-1|remainingLineId=server-line-2
R4-EXISTING-HEAD-DELETE|HTTP-EQUIVALENT=SUCCESS|saved=1|parent=R4-BUNDLE|heads=0|expand=0
BUILD SUCCESSFUL
```

probe 파일과 생성 산출물은 판정 직후 삭제했다. 제품 조회는 최초 공통 lookup 1회뿐이었고 `expand=0`,
`repository.saveAndFlush`가 실제 호출됐다.

## 불변식

1. 기존 non-null `lineId` 행의 수량이 1 미만이면 그 행을 payload에서 삭제로 투영하면 안 된다.
   명시적인 입력 오류로 저장을 거부해야 한다.
2. 저장된 BUNDLE 계보 그룹이 하나라도 남으면 `setHead=true`는 정확히 1개여야 한다.
3. 기존 그룹의 canonical head만 삭제하고 비-head를 남기는 부분삭제는 저장 전에
   `INVALID_INPUT`으로 거부해야 한다.
4. 비-head만 삭제하고 canonical head를 남기는 부분삭제는 계속 허용해야 한다.
5. 한 BUNDLE 그룹 전체를 삭제 버튼으로 명시 삭제하는 것은 계속 허용해야 한다.
6. 기존 구성품의 양수 수량·단가 편집은 사용자값을 보존하고 product expand 추가 호출 없이 저장돼야 한다.
7. 신규 익명 BUNDLE의 부모·membership·중복·canonical head 검증은 약화하면 안 된다.

## 양방향 RED

### RED-A-1 — 수량 0이 기존 행을 조용히 삭제

기존 `lineId=A/B`인 평면 행 두 건을 수정 화면에 로드하고 A의 수량만 `2→0`으로 바꾼 뒤
`buildSalesEditLinePayloads`를 실행한다.

기대:

```text
payload에 A(lineId=A, quantity=0)가 남아 서버 INVALID_INPUT에 도달
또는 FE가 명시 오류를 표시하고 PUT 자체를 호출하지 않음
```

현재:

```text
uiQuantity=0
payloadLines=1
omittedLineId=A
remainingLineId=B
```

같은 projection으로 실제 PUT하면 전체교체 저장이므로 A가 삭제된다.

### RED-A-2 — 기존 BUNDLE head 삭제가 0-head로 저장

기존 라인 두 건이 다음 계보를 가진 전표를 준비한다.

```text
line H: lineId=H, productId=P1, parentSetModel=SET-A, setHead=true
line C: lineId=C, productId=P2, parentSetModel=SET-A, setHead=false
```

최신 `lineIdContract=true` 요청으로 C만 보내고 H를 생략한다. 신규 익명 행은 없다.

기대:

```text
INVALID_INPUT
세트 head 구성품은 삭제할 수 없습니다
repository.saveAndFlush 0회
```

현재:

```text
SUCCESS
saved lines=1
parentSetModel=SET-A
setHead count=0
product expand=0
```

### RED-B — 구체 반대 표적

1. 같은 H/C에서 C만 삭제하고 H를 남긴다 → 2xx, 남은 H의 head 정확히 1개.
2. 같은 H/C와 별도 평면 SINGLE S가 있는 전표에서 H/C를 모두 삭제하고 S만 남긴다 → 2xx,
   BUNDLE 그룹 0개. “head 0개”를 문서 전체 기준으로 금지하면 안 된다.
3. 기존 행 A의 수량을 `2→3`으로 바꾸면 payload에 A의 동일 lineId와 수량 3이 남고 2xx다.
   신규 trailing 빈 행(`lineId=null`, productId 없음)은 계속 payload에서 제외한다.
4. H/C를 모두 유지한 채 수량·단가를 각각 `3/333`, `4/444`로 바꾼다 → 2xx,
   사용자값·계보 보존, product expand 0회.
5. 신규 익명 행에 `SET-A`를 붙이되 productId를 SET-A membership 밖의 SINGLE로 보낸다 →
   `INVALID_INPUT`, DB write 0회. 기존 그룹 보강이 신규 membership 검증을 약화하면 안 된다.
6. 신규 다행 BUNDLE에서 요청 head를 다른 구성품으로 옮기거나 같은 productId를 두 번 보낸다 →
   `INVALID_INPUT`, DB write 0회.

## 수정 범위

- `buildSalesEditLinePayloads`는 기존 non-null `lineId` 행을 양수 수량 여부로 삭제 투영하지 않는다.
  기존 행 수량 0은 FE에서 저장을 막거나 payload에 남겨 BE 공통 가드가 400으로 거부하게 한다.
- 명시 삭제는 계속 `removeSalesLine`/삭제 버튼으로만 표현한다. 신규 trailing draft 필터는 유지한다.
- `SalesSlipUpdateService`에서 기존 lineId 계보 복원 후, 저장 직전 그룹 단위 head 불변식을 검증한다.
- 전체 삭제된 그룹은 검증 대상에서 제외한다.
- 남아 있는 기존 그룹은 local lineage 정보만으로 정확히 1 head를 요구할 수 있으므로,
  이 결함을 고치기 위해 product-service expand 호출을 추가하지 않는다.
- 신규 익명 그룹의 현행 부모 lookup + membership 검증은 그대로 유지한다.

## 반대급부

- 수량 0을 “행 미완성이라 저장 제외”로 쓰던 생성 화면 규칙을 수정 화면의 기존 행에는 적용하지
  않게 된다. 수정 화면에서 기존 행을 없애려면 삭제 버튼을 사용해야 한다.
- 사용자는 기존 BUNDLE의 canonical head만 지우고 나머지를 같은 세트처럼 남길 수 없게 된다.
  필요한 동작은 비-head 부분삭제 또는 그룹 전체삭제로 표현해야 한다.
- local 그룹 검증으로 닫으면 저장 시 product-service 의존과 호출 수는 늘지 않는다.
- parentSetModel만 같고 실제로 서로 다른 세트 인스턴스가 여러 개 존재하는 표현은 현 스키마에
  instance key가 없다. 이번 지시는 그 구조를 확장하지 않고, 각 잔존 그룹에 head가 하나라는
  최소 불변식만 닫는다.
