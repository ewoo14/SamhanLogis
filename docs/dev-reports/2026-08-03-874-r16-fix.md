### 1. R15 선행 보고서·작업 상태 확인

- `docs/dev-reports/2026-08-03-874-r15-reconvergence.md`를 먼저 읽었다. R15가 고정한 재현은 `PANEL → INDOOR → PANEL`에서 첫 패널은 `UNKNOWN → DEFAULT → true`, 세 번째 패널은 `SINGLE → SINGLE_ACCESSORY → false`이며, 집계행은 첫 route를 선택해 `확인`을 표시하는 결함이다. 반대 순서 `INDOOR → PANEL → PANEL`에서는 `불일치`로 바뀐다.
- R15의 최종 판정은 도달 가능한 결함 1건이며 `LegacyVerificationChain`의 15개 leaf와 중첩 우선순위는 이미 레거시 원문과 일치한다고 확인했다. 이번 라운드에서는 해당 사슬을 재작성하지 않는다.
- 현재 HEAD는 `7e5537ca8`, 브랜치는 `feat/874-set-riusage-global-dc`다. 작업 시작 후 새 파일은 이 R16 보고서뿐이다.
- 핸드오프에 accounting-service 전체 테스트의 300초대 timeout 이력이 기록되어 있어 전체 suite 결과는 timeout이면 그대로 기록한다.

다음 단계: R15의 재현을 실패 테스트로 먼저 고정하고 캐시를 배제해 RED 원문을 확보한다.

### 2. RED 테스트 설계

- R15의 최소 재현을 `MonthEndCloseService.getDailyDetail()` 서비스 경로에 고정한다. 같은 거래처·품명·modelToken·카테고리·실제 VAT 포함 단가의 패널 2행과 target 본체 1행을 한 세금계산서 원천 행으로 만든다.
- 입력 순서는 두 가지를 함께 검사한다.
  - `패널 → 본체 → 패널`: 첫 패널은 `DEFAULT/true`, 뒤 패널은 `SINGLE_ACCESSORY/false`이므로 집계 결과는 `false`여야 한다.
  - `본체 → 패널 → 패널`: 두 패널 모두 `SINGLE_ACCESSORY/false`이므로 집계 결과는 역시 `false`여야 한다.
- 테스트는 제품 가격·라벨 매칭을 고정해 `MISSING_REFERENT`가 아니라 실제 `VERIFIED/false`를 관찰한다. 테스트 파일만 먼저 변경하고 production 파일은 아직 수정하지 않는다.

### 4. line_no 명시 후 재실행 결과

동일한 캐시 배제 명령을 line_no 명시 fixture에 재실행했지만 다시 `BUILD SUCCESSFUL`이었다. 따라서 현재 fixture가 여전히 첫 route를 `SINGLE_ACCESSORY/false`로 선택하는지, 또는 두 호출이 같은 fixture를 읽는지 출력으로 확인한다. 아직 RED로 인정하지 않으며 production 수정도 하지 않는다.

출력 원문:

```text
R16_PROBE panelFirst=... actualUnitPrice=77000.0000000000 ... discountAmount=23000.00 ... verified=false
R16_PROBE mainFirst=... actualUnitPrice=77000.0000000000 ... verified=false
```

판정: fixture의 패널 `unitPrice=70000`은 세금계산서 순액이어서 VAT 포함 실제 단가가 77,000원이었다. 따라서 첫 패널의 DEFAULT 경로도 `출고가-실제단가`와 납품가 기준액이 달라 현재 구현이 정당하게 `false`를 냈다. R15와 동일하게 “VAT 포함 실제 단가=납품가 70,000원”이 되도록 순액을 63,636.36원으로 조정한 뒤 RED를 다시 확인한다.

추가 확인: 공통 VAT 계산은 공급가액의 10%를 원 단위 `DOWN` 절사한다. 그러므로 `63,637 + floor(6,363.7) = 70,000`이 되도록 fixture 순액을 63,637원으로 고정해야 한다.

### 6. “여러 원천 행을 합쳐 대표 하나를 고르는 지점” 계열 sweep

대상 범위는 사용자 판정 경로인 `MonthEndCloseService`와 직접 호출되는 `LegacySetMatcher`·`LegacyVerificationChain`이다. accounting-service 전체의 다른 `findFirst()`·`get(0)`은 입금/이카운트/배치 등 다른 도메인의 대표 헤더·조회값이어서 이번 일마감 route 집계 계열에 포함되지 않는다.

| 단정 내용과 위치 | 원천 행을 대표 하나로 축약하는가 | 이번 결함과 같은가 | Linux(`ubuntu-latest`)에서도 참인가 |
|---|---:|---|---|
| `accumulateProduct`/`accumulateSalesLine`의 `byModel.computeIfAbsent(AxisKey)`가 같은 축의 수량·금액을 하나의 `ModelAccumulator`에 합산한다 | 예 | 직접적인 route 선택은 아니지만 원천 행별 금액·행 상태를 accumulator에 보존하지 않는 집계 경계다. `setPool`에는 원천 행이 남아 있어 이번 수정은 그 보존 자료를 사용한다 | 예. `LinkedHashMap`·`computeIfAbsent` Java 동작은 OS와 무관하다 |
| `revalidateProductLines`의 `findFocusRoute`가 거래처·품명·token만 필터링한 뒤 `.findFirst()`로 route 하나를 선택한다 | 예 | **예, 직접 원인. scope·sourceKey·그 행의 zone이 선택 조건에서 빠져 다른 원천 행의 branch/판정을 숨긴다** | 예. 동일 Java 17 stream 순서와 `setPool` 순서를 사용하면 Ubuntu에서도 첫 원천 route가 선택된다 |
| `LegacyVerificationChain.riUsageDecision`의 `focusRows`가 같은 partner·token·kind·branch 행들을 모은다 | 아니오. 모든 관련 row를 모은다 | 아니오. chain 내부는 row별 branch와 scope별 main 상태를 계산하며 사슬을 재작성할 대상이 아니다 | 예. 순차 stream·`sameScope` 필터 모두 OS 무관 |
| `LegacySetMatcher.findMatchesWithUsage`가 pool 순서로 indoor을 방문하고 `findUnusedByToken`이 같은 scope의 첫 미사용 component를 소비한다 | 예에 가까운 matching 선택 | 아니오. 이는 레거시 세트 매칭의 순서 의미이며 집계 표시 route 대표화가 아니다. `line_no` 순서를 보존해야 하므로 변경하지 않는다 | 예. 입력 list 순서와 Java loop semantics가 동일하다 |
| `resolveMatchedSetNames`의 `parentSetNames.putIfAbsent(PartnerModelKey, setName)`가 같은 token의 여러 matched parent 중 첫 set 이름을 보존한다 | 예 | 아니오. branch를 숨기는 지점이 아니라 옵션 정액 token을 고르는 catalog resolution이다. 이번 1건 범위를 넓히지 않는다 | 예. `LinkedHashMap.putIfAbsent`는 OS 무관 |
| `kindByToken`의 `toMap(..., (left, right) -> left)`가 중복 catalog component token의 첫 kind를 고른다 | 예 | 아니오. 원천 전표 행이 아니라 catalog metadata 중복 해소이며 `LegacyVerificationChain` 사슬과 다른 문제다 | 예. merge 함수가 명시돼 OS 무관 |
| `resolveProductSummaries`가 model token별 `lookupByModel` 한 건을 Map에 넣는다 | 예 | 아니오. product referent metadata 해소이며 source route branch를 고르지 않는다 | 예. token별 단일 조회와 Map 삽입은 OS 무관 |
| `firstSalesSourceSlipNo`/`firstPurchaseSourceSlipNo`가 allocation의 첫 원천 전표번호를 표시값으로 고른다 | 예 | 아니오. 사용자 판정이 아닌 전표 헤더의 표시용 source 번호이며 UUID를 화면에 내보내지 않는다 | 예. `findFirst`는 명시된 association 순서를 따른다 |
| 최종 `products`가 `byModel`의 AxisKey마다 `DailyProductLine` 하나를 만든다 | 예 | 증상을 화면에 만드는 집계 출력 경계다. 해결은 행을 무조건 펼치거나 순서를 바꾸지 않고, 이 한 행의 `verified`를 모든 matching route의 보수적 결합으로 산출하는 것이다 | 예. `LinkedHashMap` insertion order와 DTO 생성은 OS 무관 |

전수 결론: **직접 branch 대표 선택은 1곳(`findFocusRoute`)이고, 집계 경계 2곳(`byModel` 누적 및 AxisKey별 DTO 생성)이 같은 문제를 운반한다.** chain·세트 매칭의 나머지 선택은 레거시 의미 또는 catalog metadata 해소로 이번 결함과 다르다.

### 7. Root cause hypothesis

**`MonthEndCloseService`가 AxisKey별 집계행을 만들 때 `setPool`의 같은 축 원천 route 전부를 평가하지 않고 `findFocusRoute(...).findFirst()`의 첫 route를 branch·riUsage의 대표로 사용한다.** 따라서 `DEFAULT/true`와 `SINGLE_ACCESSORY/false`가 같은 축에 공존하면 첫 행에 따라 결과가 `true` 또는 `false`로 바뀌며, false 행이 화면에서 사라진다.

수정 가설 검증 기준은 명확하다: 각 matching source route에 기존 `LegacyVerificationChain.branch`와 `DiscountRevalidator.revalidateByLegacyBranch`를 그대로 적용하고, 결과에 `false`가 하나라도 있으면 `verified=false`, false가 없고 모두 true일 때만 true로 합친다. 이 결합은 입력 순서와 무관하고, false로 바뀌는 행에는 해당 source route의 `SINGLE_ACCESSORY` 또는 다른 legacy branch 결과라는 건별 근거가 있다.

### 8. 첫 fix 컴파일 확인

첫 production 수정은 `MonthEndCloseService`에 원천 route 전수 평가와 결과 결합을 추가했지만, stable comparator의 람다 추론이 `Object`로 잡혀 컴파일이 실패했다.

    .comparing(e -> String.valueOf(e.route().row().sourceKey()))

판정: 로직 실패가 아닌 Java generic lambda 타입 추론 오류다. comparator 첫 람다에 `RouteEvaluation` 타입을 명시해 재실행한다.

### 9. fix 후 순서 대조 GREEN

수정 내용:

- `findFocusRoute(...).findFirst()`를 제거하고 `setPool`·`routedRows` 동일 인덱스에서 AxisKey가 정확히 일치하는 모든 route를 수집한다.
- 각 route마다 기존 chain의 `branch`, `riUsageDecision`, `revalidateByLegacyBranch`를 독립 실행한다. `LegacyVerificationChain`의 분기 구조는 변경하지 않았다.
- 집계 결합은 `false` 우선, 그 다음 `null`, 모든 route가 `true`일 때만 `true`다. 대표 숫자 필드는 sourceKey 안정 순서의 대표 결과를 사용하며 DTO 행 순서는 `byModel` insertion order를 유지한다.

### 12. 수정 후 보수적 코드 점검

변경 직후 경로를 다시 대조해, matching source route가 없는 기존 synthetic fallback에는 R15의 `riUsageDecision`을 새로 적용하지 않도록 `applyRiUsage=false`를 명시했다. 기존 구현도 `focusRoute == null`이면 riUsage를 호출하지 않았으므로 이 fallback 행의 행위는 보존한다.

또한 출력 list를 정렬하거나 `byModel`의 insertion order를 바꾸지 않았다. stable comparator는 여러 route의 숫자 대표 필드를 고를 때만 사용한다.

#### 값이 바뀐 케이스와 건별 근거

| 케이스 | 수정 전 | 수정 후 | 근거 |
|---|---|---|---|
| 1전표 `패널 → 본체 → 패널`, 같은 패널 집계행 | `확인(true)` | `불일치(false)` | line 1 패널은 `UNKNOWN → DEFAULT → true`, line 3 패널은 본체 뒤 `SINGLE → SINGLE_ACCESSORY`, 미소비 riUsage로 `false`. 뒤 route의 false를 숨기지 않도록 바뀐 유일한 값 변경이다 |
| 같은 입력 `본체 → 패널 → 패널` | `불일치(false)` | `불일치(false)` | 두 패널 모두 본체 뒤 `SINGLE_ACCESSORY/false`; 값 변경 없음. 순서 대조가 1번과 같은 결과를 낸다 |
