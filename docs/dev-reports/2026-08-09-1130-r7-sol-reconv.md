## 1. R6 관측 유효성 — 결과는 같지만, 구경로의 HashRouter 도달 증명은 무효

R7의 해시 경로로 실제 HashRouter 렌더러를 기동해 두 스펙 5개를 다시 실행했다.

```text
Running 5 tests using 1 worker
5 passed (8.0s)
PLAYWRIGHT_LIVE_EXIT=0
```

R6에서 보고한 핵심 결과와 이번 재측정 결과는 같다.

| 관측 | R7 재측정 |
|---|---|
| MANAGER `inbound.inspection` | `VIEW, UPDATE` |
| MASTER 권한 page 수 | 200 |
| MASTER `system.permission-admin` | 7 actions |
| SALES inventory 목록 API | HTTP 403 |
| inventory 검수 목록 | 0건 |
| `INBOUND + INSPECTING` 전표 | 2건 |
| MANAGER 전표 상세 `완료 (처리 완료)` | visible + enabled |

다만 R6의 해시 없는 URL을 **HashRouter 화면 도달 증거**로 재사용할 수는 없다. 실제 HashRouter
하네스에서 같은 해시 없는 MASTER URL은 §2처럼 RED다. 따라서 R6가 `4/4`였다는 기록은
BrowserRouter 렌더러를 사용했거나 실행 하네스가 보고와 달랐다는 뜻이다.

R6 판정 중 무효였던 범위는 다음과 같다.

- 해시 없는 goto 자체로 HashRouter 목표 화면에 도달했다는 증명은 전부 무효다.
- R6의 SALES UI 차단은 당시 홈 고유 요소 단정이 없었으므로, 최초 홈 낙착과 권한 차단 redirect를
  구분하지 못했다. 이 **UI 차단의 인과 증명**은 무효였다. SALES 실 API 403 관측은 독립 단정이라
  유효하다.
- MANAGER 목록/table, MANAGER 상세 버튼, MASTER 권한표는 원래도 목표 화면 고유 요소를 단정했다.
  HashRouter 구경로였다면 통과할 수 없으므로 R6의 하네스 진술은 신뢰할 수 없지만, R7에서 같은
  결과를 다시 얻어 제품 관측값 자체는 회복됐다.

현재 원문은 5개 goto 모두 `${BASE_URL}/#/...`이다. 목표 화면 고유 단정은
`1130-r6-sol-reconv-real-qa.spec.ts:52,71-73,87,106-107`과
`1130-r6-backend-master-guard-real-qa.spec.ts:80`에 있다.

## 2. 고유 요소 단정 RED — 실제 HashRouter 하네스

검증 하네스는 `clients/desktop/vite.config.ts`로 `VITE_PLATFORM`을 정의하지 않아
`createHashRouter`를 선택한다. `vite.web.config.ts`는 BrowserRouter이므로 이 RED의 하네스로
사용하지 않았다.

단일 뮤테이션:

```diff
- await page.goto(`${BASE_URL}/#/admin/permission-matrix`)
+ await page.goto(`${BASE_URL}/admin/permission-matrix`)
```

실행 결과:

```text
Locator: getByRole('heading', { name: '권한설정', level: 3 })
Expected: visible
Timeout: 30000ms
Error: element(s) not found
PLAYWRIGHT_HASH_RED_EXIT=1
```

즉 `권한설정` h3는 홈에서도 만족되는 공통 요소가 아니다. 뒤의
`permission-matrix-table` 역시 해당 화면 전용 test id다. 뮤테이션을 원문으로 복구한 뒤 5/5
GREEN을 다시 얻었다.

참고로 BrowserRouter 렌더러에서는 동일 해시 제거 뮤테이션이 GREEN이었다. 이는 단정이 약해서가
아니라 그 라우터에서는 pathname이 정답이기 때문이다. 이번 판정에는 실제 HashRouter RED만 사용했다.

## 3. inventory 표본 0 — 실 관리자 생성 경로는 존재한다

공유 DB 측정 시각은 다음과 같다.

```text
slip_db      2026-08-09 14:08:04.619335 KST
inventory_db 2026-08-09 14:08:04.893170 KST
```

SQL 집계:

```text
INBOUND + INSPECTING                    2
INBOUND + (SAVED 또는 CONFIRMED)        5
active inbound_inspections header       0
soft-deleted header                      1
active header 아래 active line          0
deleted header 아래 active line         5
```

실 관리자 GUI로 새 검수 대상을 만들 수 있다. 절차는 다음과 같다.

1. MANAGER가 구매관리 또는 입고전표 목록으로 이동한다.
2. `SAVED`/`CONFIRMED` 행의 `검수` 버튼을 누른다. FE 허용 상태 원문은
   `PurchaseQueryPage.tsx:36,95-96,588`과 `SlipListPage.tsx:204,331-337`이다.
3. `InboundInspectionDialog`가 열리며
   `GET /api/v1/inventory/inbound-inspections/{slipId}`를 호출한다
   (`InboundInspectionDialog.tsx:158`).
4. 이 GET은 조회 전용이 아니다. `InboundInspectionService#getOrCreateInspection()`가 헤더가
   없으면 `createInspectionFromSlipDetail()`을 호출해 헤더와 라인을 INSERT한다
   (`InboundInspectionService.java:123-128,325`).

현재 후보는 `SAVED 4 + CONFIRMED 1 = 5건`이고, 최근 기본 날짜 범위에 들어오는 후보는
`2026/08/08-5(SAVED)`다. 따라서 실 관리자 경로가 없어서 표본이 0인 것은 아니다. 다만
**다이얼로그를 여는 GET 자체가 실 DB write**이므로 이번 라운드에서는 누르지 않았다.

## 6. PR #1145 상호작용 — 보고만

PR #1145 현재 head `1fba06036eebda26401e78e5cc5ed3178c37ae38`를 git object로 읽었다.

- `permission-mock-divergences.ts`: 총 239, MASTER 0, 비MASTER 239.
- MASTER projection은 200 page 전부 `1111111`이다. 이 PR의 MASTER
  `inbound.inspection=1111111`과 **일치하며 충돌하지 않는다**.
- 그러나 #1145의 MANAGER `inbound.inspection` 동결 셀은
  `snapshotBits=1000000`, `mockBits=1000011`이다.
- 이 PR은 V98과 mock override로 같은 셀을 `1010000`으로 만든다. 따라서 두 PR이 합류하면
  #1145의 해당 non-MASTER snapshot/divergence 한 셀은 stale해지고 freshness/exact 가드 갱신이
  필요해진다.
- WAREHOUSE/INVENTORY의 #1145 동결 셀은 각각 `1111000 → 1111011`이며 이 PR이 건드리지 않는다.

요청대로 이 상호작용은 보고만 하며, #1145 수정을 이 PR의 머지 조건으로 요구하지 않는다.
