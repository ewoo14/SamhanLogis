# 2026-08-01 1013 fix-2xx

## 1. 계열 sweep 목록 (수정 전)

`AligoSmsAdapter` 선언, `NotificationGatewayResult` 생성·소비, SMS 내부 endpoint 호출자와 HTTP 2xx 처리 지점을 notification/slip/arologis 및 형제 알림 호출 범위에서 전수 검색했다. 가배차 8개 모드와 무관한 SMS 계열만 대상으로 했다.

| 위치 | 역할 | HTTP 2xx만으로 성공 판정 여부 | 판정 |
|---|---|---:|---|
| `notification-service/.../adapter/sms/AligoSmsAdapter` | Aligo 응답 `result_code == 1`을 해석해 `NotificationGatewayResult` 생성 | 아니오 | 정상 기준 구현 |
| `notification-service/.../service/NotificationService` | adapter 결과 `success()`로 요청을 `SENT`/`FAILED` 전이 | 아니오 | 결과 계약 소비처 |
| `notification-service/.../service/DispatchBatchSendService` | `NotificationRequest.status == SENT`로 배차 SMS sent/failed 카운트·태그 판정 | 아니오 | 결과 계약 소비처 |
| `notification-service/.../controller/NotificationInternalController` | `FAILED`도 HTTP 201 envelope로 반환 | **경계 원인** | body status 보존 필요 |
| `arologis-service/.../client/NotificationClient` | 응답 envelope의 `data.status`가 `SENT`인지 판정 | 아니오 | `FAILED`를 fail outcome으로 매핑 |
| `slip-service/.../client/NotificationClient.sendExternalSmsWithResult` | 타배송사 SMS 응답을 `toBodilessEntity()`로 읽고 예외가 없으면 `true` 반환 | **예** | **수정 대상** |
| `slip-service/.../service/ExternalDispatchService` | 위 boolean `true/false`로 external dispatch 성공/실패 전이 | 간접 | 수정 대상의 downstream |
| `slip-service`의 `sendExternalSms` 및 accounting/partner-order/inventory 알림 client | void graceful 호출; 결과로 SENT/FAILED를 판정하지 않음 | 해당 없음 | 성공 판정 소비처 아님 |
| PUSH/EMAIL adapter 및 소비처 | 채널 분기상 Aligo SMS 결과를 사용하지 않음 | 해당 없음 | 불변식 D 보호 범위 |

### sweep 결론

HTTP 2xx만 보고 미전송을 성공으로 세는 호출자는 `slip-service`의 `NotificationClient.sendExternalSmsWithResult` 1곳으로 확인했다. 이 값은 `ExternalDispatchService`에서 타배송사 배차의 `SENT`/`FAILED` 전이에 직접 사용된다. 나머지 SMS 결과 소비처는 body의 상태 또는 gateway result를 판정하며, PUSH·EMAIL은 Aligo 계열 밖이다.

## 2. RED — slip-service HTTP 2xx + `FAILED` body

실패 테스트를 먼저 추가해 실행했다.

```text
NotificationDispatchSmsContractIT > sendExternalSmsWithResult_doesNotTreatFailedBodyAsSuccessOn2xx() FAILED
    org.opentest4j.AssertionFailedError at NotificationDispatchSmsContractIT.java:56

2 tests completed, 1 failed

FAILURE: Build failed with an exception.
> Task :services:slip-service:test FAILED
```

원인: 응답 body를 읽지 않고 `toBodilessEntity()` 성공만으로 `true`를 반환했다.

## 3. GREEN — 결과 body의 `SENT`만 성공

`NotificationClient`가 응답 envelope의 `data.status`를 읽고 정확히 `SENT`일 때만 `true`를 반환하도록 최소 수정했다. `FAILED`, 빈 body, 상태 누락, HTTP 예외는 모두 `false`다.

수정 후 호출자 계약·타배송사 상태 전이 테스트 원문:

```text
> Task :services:slip-service:test

BUILD SUCCESSFUL in 41s
18 actionable tasks: 2 executed, 16 up-to-date
```

실행 대상: `NotificationClientTest`, `NotificationDispatchSmsContractIT`, `ExternalDispatchServiceTest`.


## 5. slip-service 전체 테스트 1차 실행

```text
command timed out after 124030 milliseconds
Exit code: 124
```

1차 실행은 테스트 자체의 판정 원문 없이 실행 제한 시간에 도달했다. 결과를 성공으로 세지 않고 더 긴 제한 시간으로 재실행한다.

재실행 시 이전 timeout이 남긴 Gradle test worker가 결과 binary를 잠근 상태여서 다음 원문으로 중단됐다. 해당 워커는 이 워크트리의 Gradle 프로세스임을 확인한 뒤 종료했다.

```text
> Task :services:slip-service:test FAILED
java.io.IOException: Unable to delete directory '...services\\slip-service\\build\\test-results\\test\\binary'
Failed to delete ...\\output.bin
BUILD FAILED in 19s
```

워커 정리 후 `--rerun-tasks`로 전체 재실행했으나 300초 동안 추가 출력이나 종료 결과 없이 timeout됐다.

```text
command timed out after 304039 milliseconds
Exit code: 124
```

slip-service 전체 테스트는 성공으로 판정하지 않는다. 수정과 직접 관련된 전체 호출자 테스트는 앞 절의 GREEN 원문으로 확인했고, 전체 task는 환경/통합 테스트 정체로 미완료다.

## 8. 최종 상태

- 계열 sweep 목록을 수정 전에 기록했다.
- 유일한 HTTP 2xx-only 판정 지점인 slip-service client를 body `SENT` 판정으로 수정했다.
- RED 원문과 GREEN 원문을 기록했다.
- 정상 자격증명 Aligo, placeholder 비전송, PUSH·EMAIL 분리 테스트는 notification-service 전체 재실행에서 성공했다.
- arologis-service 전체 재실행은 성공했다.
- slip-service 전체 task는 통합 테스트 정체로 timeout되어 **전체 성공으로 판정하지 않는다**. 직접 관련 회귀 테스트는 성공했다.
- 실제 문자 발송, 공유 Docker 재빌드·재기동, 실 DB 쓰기, 가배차 8개 모드 수정은 하지 않았다.
