## 1. 결론

`bitsMap()`이 모든 역할을 `0` 비트로 먼저 채운 뒤, 이전 값이 `0`인지로 중복을 판정하고 있었다. 따라서 `MASTER 000` 다음 `MASTER 111`은 첫 row와 두 번째 row 모두 “이전 값이 0”으로 보였고, 최종 map만 기대값과 같아 GREEN이었다.

수정은 실제 비트 값과 방문 여부를 분리하는 방식이다.

```java
Map<String, String> actual = new LinkedHashMap<>();
Set<String> seenRoles = new HashSet<>();
...
assertThat(seenRoles.add(row.role()))
        .as("duplicate grant row for %s", row.role())
        .isTrue();
actual.put(row.role(), bits(row.bits(), outputWidth));
```

이제 `000 → 111`, `111 → 000`, 동일 비트 중복, 중복+초과 조합 모두 중복 row 자체에서 실패한다. 정상적인 0비트 역할은 `seenRoles`와 별개이므로 계속 GREEN이다.

## 2. 원천 대조 — 불변식 3

검사기와 런타임의 권한 원천을 분리해 확인했다.

| 권한 | 검사/시더 원천 | 실제 소비 원천 | 결과 |
|---|---|---|---|
| VIEW/EDIT 2비트 | V101의 `role_page_permissions` grant CTE | `DynamicPermissionService` → `RolePagePermissionRepository.findByRoleCodeAndPageCode()` | 일치 |
| 7-action | V101의 `role_page_permission_templates` grant CTE 및 desktop DB snapshot | `AccountPermissionService` → `RolePagePermissionTemplateRepository` | 일치 |
| account/group materialization | V101의 `group_page_permissions`, `account_page_permissions` | account permission 소비 경로 | V101 동일 7비트 seed |

`DynamicPermissionService`는 활성 `role_page_permissions` 단일 row를 읽고, `AccountPermissionService.getTemplates()`는 활성 `role_page_permission_templates`를 읽는다. 검사기는 두 CTE를 각각 읽어 확인하므로 시더만 보고 다른 런타임 원천을 놓치는 구조는 확인되지 않았다. MASTER의 VIEW/EDIT 런타임 전권 예외도 desktop contract checker의 정본 규칙과 일치한다.

## 3. 같은 형태의 구멍 전수 조사

다음 패턴을 auth 전체 테스트, desktop permission contract/snapshot/checker, 관련 Java/TypeScript 테스트에서 검색했다.

```text
bitsMap
0 sentinel 초기화 후 put() 반환값으로 duplicate 판정
Map/Set 합산·merge·computeIfAbsent·groupingBy·toMap·OR 비트 합성 후 exact 비교
```

결과:

- `0` sentinel을 “미방문” 표지로 사용해 duplicate를 판정하는 코드는 `SalesCommissionSettlementPermissionSeedTest.bitsMap()` 한 곳이었다.
- desktop `assertExactPermissionMatrix()`는 role/page 집합을 먼저 `toEqual`하고, 각 cell을 7비트 문자열로 만든 뒤 각 셀과 divergence 집합을 `toEqual`한다. 동일한 sentinel 기반 duplicate 판정은 없다.
- `permissionPageCatalog.parity.test.ts`는 catalog를 Set으로 만들지만 중복 검사는 별도 `toHaveLength`/집합 크기 계약으로 수행하며 권한 row를 OR/합산해 비교하지 않는다.
- 기타 발견된 `reduce`/`merge`는 금액 합계·목록 집계·UI 데이터 변환이며 권한 exact 검사기가 아니었다.

따라서 이번 fix2의 수정 대상은 `bitsMap()` 하나이며, 무관한 합산 로직은 변경하지 않았다.

## 9. 이번 세션에서 재실행하지 않은 항목

다음은 fix2 세션에서 다시 돌리지 않고 SOL R2 증거를 유지한 항목이다.

- 실제 TCP HTTP 403 독립 출력 재수집
- 기존 43개 route Playwright sweep 및 회계 anchor 44 캡처
- 입금보고서 native Link의 브라우저 scroll 실측
- activeTargets/menu/matrix 독립 재계수

보조 집계 명령 `vitest list --json`은 별도 실행했으나 worker unexpected exit 및 124초 timeout이 발생해 집계 근거로 사용하지 않았다. 대신 단일 worker full Vitest 자체는 exit 0으로 완주했고, 최종 수치는 실행 결과와 SOL R2 집계를 사용했다.
