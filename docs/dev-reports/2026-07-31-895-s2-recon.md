## 1. 결론

PR #994가 병합한 소스에는 일정 원장과 CRUD, 초대 대상자의 기간 목록 조회, 독립 권한
groupware.schedules, 등록자 전용 수정·삭제, 작성자 자동 대상자 포함 및 기존 데이터
backfill이 있다. 그러나 사용자가 접근할 일정 화면, 일정 API 클라이언트, 단건 상세 조회,
대시보드 오늘/이번 주 위젯, 부서·전사 공유, 일정 알림은 아직 없다.

가장 중요한 잔여 계약 결함은 두 가지다.

1. 목록 조회 저장소가 여전히 “작성자 또는 활성 대상자” 조건을 사용한다. 작성자를 실제
   대상자 행으로 넣는 규칙이 생겼는데도 작성자 조건으로 접근을 우회할 수 있어, 대상자
   행이 다시 누락돼도 목록은 정상처럼 보인다.
2. 병합된 소스와 현재 공유 실행 스택이 다르다. 2026-07-31 20:05 KST 읽기 전용
   실측에서 groupware_db는 V14, auth_db는 V89였다. 활성 일정 42건 모두 작성자 대상자
   행이 없었고 groupware.schedules 실효 계정 권한도 0건이었다. 즉 현재 실행 스택은
   PR #994의 V17/V18/V90을 아직 적용하지 않았다.

따라서 다음 구현은 신규 일정 도메인을 만들 일이 아니라, groupware-service를 일정
원장으로 유지하면서 “대상자 집합이 접근 권한의 정본”이라는 계약을 먼저 완결하고 그 위에
데스크톱 캘린더, 부서·전사 공유, 대시보드 위젯, 알림을 순서대로 올리는 일이다.

## 4. “조회·공유”의 현재 실제 경로

### 4.1 백엔드 라우트

일정 라우트는 services/groupware-service/src/main/java/com/samhanair/logis/groupware/controller/GroupwareAdminController.java:281-334에 모여 있다.

| 메서드·경로 | 권한 | 객체 범위 | 현재 결과 |
|---|---|---|---|
| POST /admin/groupware/schedules | groupware.schedules / CREATE | X-User-Id가 작성자 | 작성자와 요청 대상자를 저장하고 응답 |
| GET /admin/groupware/schedules?from&to | groupware.schedules / VIEW | 호출자 UUID를 기간 목록 조회에 사용 | 작성자 또는 활성 대상자인 일정 목록 |
| PUT /admin/groupware/schedules/{scheduleId} | groupware.schedules / UPDATE | 작성자 본인만 | 일정과 대상자 전체 교체 |
| DELETE /admin/groupware/schedules/{scheduleId} | groupware.schedules / DELETE | 작성자 본인만 | 일정 soft-delete |

GET의 ownerId query parameter는 호환성 때문에 받지만 무시하고, 실제 호출자 헤더만 사용한다
(GroupwareAdminController.java:304-311). 타인의 UUID를 query로 넘겨 조회 범위를 바꿀 수
없는 점은 맞다.

반면 GET /admin/groupware/schedules/{scheduleId}는 없다. 같은 경로에 PUT과 DELETE만 있어
GET을 호출하면 Spring의 메서드 미지원 예외가 발생한다. 현재 예외 처리기는 그 예외를
별도로 매핑하지 않고 최종 Exception 처리로 500을 만든다
(GroupwareExceptionHandler.java:121-125). 더 중요한 점은 현재
ScheduleService.findById(scheduleId)가 호출자나 대상자 검사를 받지 않는 내부 helper라는
사실이다(ScheduleService.java:57-63). 이를 그대로 공개 상세 endpoint에 연결하면 안 된다.

### 4.2 공유 대상 지정

현재 공유 입력은 ScheduleRequest.participantIds의 사용자 UUID 배열뿐이다
(ScheduleRequest.java:22-31). 서비스는 각 UUID가 user-service에 존재하는지 확인하고
ScheduleParticipant로 저장한다(ScheduleService.java:40-48). 작성자는 요청 배열과 무관하게
먼저 추가된다.

그러나 일정 전용 대상자 검색 라우트와 데스크톱 선택 UI는 없다. 실제로 사용할 수 있는
유사 원시는 메신저 수신자 검색이다.

- GET /admin/groupware/messages/recipient-search
- GroupwareAdminController.java:229-242
- messenger.send / VIEW 권한으로 보호됨
- 내부 user-service /internal/users/search를 호출하며 재직자만 검색
- 응답은 userId, name, department, employeeCode

이 경로는 메신저 권한에 묶여 있으므로 groupware.schedules만 가진 사용자용 일정 공유
선택기로 그대로 쓸 수 없다. 다음 슬라이스에서는 같은 UserClient 원시를 재사용하되 일정
권한으로 보호되는 일정 전용 검색 표면이 필요하다.

사용자 노출용 코드는 담당자코드 employeeCode이며 원천은 employees.ecount_code다
(RecipientSearchResponse.java:5-15,
InternalEmployeeSearchResponse.java:5-16). UUID는 요청 payload와 React key 등 내부 식별에만
사용하고 화면에는 이름·부서·담당자코드를 표시해야 한다. 현재 메신저 화면도 동명이인일
때만 “이름 (담당자코드)”를 표시하고 UUID·로그인ID·이메일을 표시하지 않는다
(MessengerPage.tsx:40-53).

ScheduleResponse는 scheduleId, ownerId, participantIds를 UUID로 반환한다
(ScheduleResponse.java:22-40). API 내부 계약으로는 사용할 수 있지만, 후속 화면이 이 값을
문자열로 렌더링하면 UUID 비공개 규율을 위반한다.

### 4.3 데스크톱과 다른 클라이언트의 도달성

데스크톱 실제 라우트 표는 clients/desktop/src/renderer/routes/index.tsx:349-414이다.
홈, 알림, 그룹웨어 결재, 양식, 메신저는 있으나 일정 라우트는 없다. API 디렉터리에도
일정 클라이언트가 없고, groupware.schedules는 권한 타입과 권한설정 화면에만 존재한다.

사이드바 그룹웨어 블록도 결재·양식·링크발송·주소록·메신저·단톡방만 나열한다
(AppLayout.tsx:1280-1350). showGroupware 계산에도 일정 권한은 포함되지 않는다
(AppLayout.tsx:653-656).

다른 클라이언트의 실제 진입 파일도 확인했다.

- clients/mobile/App.tsx:21-40은 주문 WebView 단일 진입이다.
- clients/mobile-staff/App.tsx:26-45와 AppRootNavigator.tsx:13-20은 견적 WebView 단일
  진입이다.
- clients/arologis-mobile/src/navigation/RootNavigator.tsx:22-54는 기사 로그인·GPS·배차
  진입이다.
- clients/arologis-desktop/src/renderer/routes/index.tsx:140-197은 배차와 아로로지스 관리

- clients/web는 주문·견적·공개 모바일 화면 묶음이며 일정 라우터를 확인하지 못했다.

따라서 이번 후속의 첫 사용자 표면은 Samhan Public 데스크톱이 맞다. 웹·모바일 일정 화면은
현재 이슈의 독립 구현 근거를 확인하지 못했다.

## 5. 작성자 자동 대상자 규칙의 소비 표면 전수 대조

### 5.1 생산 코드 참조 전수 결과

일정 대상자 집합을 생산 코드에서 직접 읽는 경로는 다음으로 수렴한다.

- ScheduleService.update의 기존 대상자 전체 교체
- ScheduleResponse.from의 응답 대상자 목록
- ScheduleRepository.findVisibleInRange의 대상자 존재 여부
- GroupwareSeeder의 시드 작성

그 밖에 일정 알림, 일정 통계, 대시보드, 데스크톱 목록·상세 소비자는 현재 없다.
단순 0매치로 부재를 판정한 것이 아니라, 일정 컨트롤러의 전체 매핑, 저장소의 전체 메서드,
데스크톱 실제 route table, dashboard-service의 전체 controller/repository 목록,
notification-service 발행 진입점을 각각 확인했다.

### 5.2 표면별 판정

| 표면 | 실제 경로 | 작성자 포함 여부 | ownerId 우회 여부 | 판정 |
|---|---|---|---|---|
| 신규 생성 집합 | ScheduleService.java:33-50 | 요청보다 먼저 실제 대상자 추가 | 없음 | 소스 준수 |
| 수정 집합 | ScheduleService.java:74-105 | 수정 시작 시 작성자 행 복구, 제거 요청은 domain에서 no-op | 없음 | 소스 준수 |
| 단건 추가 helper | ScheduleService.java:108-117 | 작성자를 먼저 복구 | 없음 | 소스 준수. 단, controller 호출자는 없음 |
| 응답 대상자 목록 | ScheduleResponse.java:33-40 | ownerId를 먼저 넣고 활성 대상자와 distinct 합집합 | 접근 우회는 아니지만 DB 누락을 가리는 fallback | 응답 계약 준수 |
| 기간 목록 접근 필터 | ScheduleRepository.java:31-39 | V17 적용 후 작성자가 대상자 EXISTS에도 해당 | s.ownerId = :userId OR EXISTS가 남음 | 구조적으로 미준수 |
| 기간 목록 응답 | GroupwareAdminController.java:300-312 → ScheduleResponse.from | 반환된 모든 일정의 participantIds에 작성자 포함 | 저장소의 OR를 상속 | 표시 집합은 준수, 접근 정본은 미준수 |

| 알림 자기 제외 | 현재 일정 알림 producer 없음 | 실행되는 규칙 없음 | 해당 없음 | 후속 필수 |

현재 소스에서 ownerId 접근 우회는 ScheduleRepository.findVisibleInRange의 한 곳이다. 이
조건은 작성자가 대상자 행에 실제 존재한다는 불변식을 검증하지 않고도 접근을 허용한다.
응답 DTO의 owner 합집합도 사용자 응답을 맞게 만들지만 같은 데이터 누락을 관측하기 어렵게
한다. 개발책임자 확정 사항을 끝까지 적용하려면 접근 판정은 활성 대상자 EXISTS 하나를
정본으로 삼아야 하고, 작성자 행 누락은 테스트·운영 점검에서 실패로 드러나야 한다.

수정·삭제 권한은 별도 축으로 이미 분리돼 있다. 대상자라고 수정할 수 없으며,
groupware.schedules의 UPDATE/DELETE가 있어도 ScheduleService가 작성자 UUID를 다시
검사한다(ScheduleService.java:74-80,120-127). 이 구조는 유지해야 한다.

### 5.3 알림 표면의 현재 상태

현재 ScheduleStatus 주석은 CONFIRMED를 “참여자 알림 / 캘린더 노출 대상”이라고 쓰지만
(ScheduleStatus.java:7-9), 실제 ScheduleService에는 알림 publisher가 없다. 또한 데스크톱
CHANNEL_LABEL에는 SAFETY_STOCK, MESSENGER, APPROVAL, ECOUNT_IMPORT만 있고 SCHEDULE이
없다(notificationApi.ts:88-94). 일정 알림 행이 외부에서 들어오면 “알 수 없는 채널”로
보인다.

알림 벨은 안전한 deeplink를 그대로 navigate한다(NotificationBellDropdown.tsx:75-76).
일정 라우트가 없는 상태에서 과거 제안처럼 /schedules를 넣으면 인앱 404로 간다. 따라서
알림은 캘린더와 권한 있는 상세 경로가 먼저 병합된 뒤에만 붙여야 한다.

후속 알림 대상은 활성 schedule_participants에서 읽되 ownerId와 같은 작성자는 제외해야
한다. 작성자를 대상자 집합에서 빼는 방식으로 자기 알림을 막으면 안 된다. 집합은 그대로
보존하고 발행 소비 단계에서만 작성자를 제외해야 한다.

## 6. 대시보드 통합 지점

### 6.1 데스크톱 홈

루트 경로 /는 DashboardPage다(routes/index.tsx:343-350). 현재 DashboardPage는
처리 중 판매전표 수 한 항목만 실제 조회하고, 저재고 알림·미확인 메시지·결재 대기는
“준비중”이다(DashboardPage.tsx:24-68). 일정 query, 오늘/이번 주 카드, 일정으로 가는
빠른 액션은 없다(DashboardPage.tsx:70-98).

따라서 가장 작은 통합 지점은 DashboardPage에 호출자 기준 오늘/이번 주 일정 요약을
추가하고, 전체 캘린더 라우트로 이동시키는 것이다. 이 위젯은 반드시
groupware.schedules / VIEW와 대상자 기준 목록 응답을 사용해야 한다.

### 6.2 dashboard-service

DashboardAdminController가 소유한 실제 표면은 KPI, 실시간 재고, 매출 집계,
materialized view refresh다(DashboardAdminController.java:31-39,49-128).
V1 스키마도 kpi_snapshots, realtime_stocks, sales_aggregates와 두 materialized view뿐이다
(V1__init_dashboard.sql:13-142). controller와 repository 전체 목록에도 일정 원장은 없다.

이는 누락된 일정 원장을 dashboard-service에 새로 만들라는 뜻이 아니다. 일정 원장은 이미
groupware-service에 있고, dashboard-service는 표시·집계 경계다. 첫 위젯은 데스크톱이
groupware 일정 목록을 읽는 것으로 충분하다. 여러 도메인 overlay를 서버에서 합칠 필요가
생기는 선택 슬라이스에서만 dashboard-service 집계를 검토한다.

### 6.3 권한과 메뉴의 현재 연결

groupware.schedules는 권한설정 카탈로그에만 있다(PermissionMatrixPage.tsx:238-246,419-423).
AppLayout에는 해당 권한을 읽는 변수, 그룹웨어 일정 링크, activeTarget이 없고,
routes/index.tsx에도 PermissionGuard를 가진 일정 경로가 없다. 권한 등록과 사용자
진입점은 아직 연결되지 않았다.

## 7. 후속 슬라이스 제안

핵심 5개와 선택 1개로 나누는 것을 권장한다. 각 슬라이스는 앞 단계가 main에 병합됐다는
전제에서 단독으로 배포해도 기존 기능을 깨뜨리지 않고, 자기 산출물이 사용자 또는 다음
계약에 완결된 상태여야 한다.

### 슬라이스 S2-A — 대상자 정본과 조회·공유 백엔드 계약 완결

경계:

- 기간 목록 접근을 활성 대상자 EXISTS로 일원화하고 ownerId OR 우회를 제거한다.
- V17 적용 뒤 모든 활성 일정에 작성자 활성 대상자 행이 있는지 migration·통합 테스트와
  운영 점검으로 검증한다.
- GET /admin/groupware/schedules/{scheduleId}를 추가하되 호출자가 활성 대상자인지 검사한다.
- 일정 전용 대상자 검색을 groupware.schedules 권한으로 제공한다. 응답의 사용자 라벨은
  이름·부서·담당자코드이고 UUID는 payload 전용이다.
- 종일 일정의 명시적 저장·응답 계약을 추가한다.
- 기존 등록·수정·삭제와 작성자 전용 편집 규칙은 재설계하지 않는다.

독립 머지 결과: 화면이 없어도 API 계약과 데이터 불변식이 스스로 검증되며, 기존 CRUD
호출자는 계속 동작한다.

### 슬라이스 S2-B — 데스크톱 전체 캘린더와 명시적 담당자 공유

경계:

- /groupware/schedules 라우트, PermissionGuard, 그룹웨어 사이드바 링크를 추가한다.
- 기간 목록·상세·등록·수정·삭제 API 클라이언트를 연결한다.
- 기간/종일 일정과 월·주 범위 이동을 제공한다.
- 대상자는 이름·부서·담당자코드로 검색·선택하고 UUID를 화면에 표시하지 않는다.
- 작성자는 자동으로 선택된 고정 대상자로 보이되 제거할 수 없게 한다.
- 대상자는 조회만 가능하고, 작성자만 수정·삭제 버튼을 사용할 수 있게 한다.
- 알림과 부서·전사 공유는 넣지 않는다.

독립 머지 결과: 담당자 단위 일정 등록·조회·공유·수정·삭제가 실제 사용자 화면에서
끝까지 동작한다.

### 슬라이스 S2-C — 부서·전사 공유의 대상자 물질화

경계:

- 부서·전사 선택을 page-code나 OR role/department 조건으로 접근 허용하지 않는다.
- 선택한 부서 또는 전사의 활성 내부 사용자를 해석해 schedule_participants에 실제 사용자
  행으로 넣는다. 작성자도 같은 집합에 남긴다.
- 화면에는 부서명과 전사 라벨만 표시하고 부서 UUID·사용자 UUID를 표시하지 않는다.
- 부서 인사 이동·신규 입사 시 동적 재계산인지 등록·수정 시점 snapshot인지 정책을 먼저
  고정한다. 본 정찰의 권장은 예측 가능한 snapshot이며, 재동기화는 명시적 수정 행위로 둔다.
- 수정·삭제는 공유 범위와 무관하게 계속 작성자만 가능하다.

독립 머지 결과: 이슈의 담당자·부서 공유가 대상자 집합이라는 한 정본으로 동작한다.

### 슬라이스 S2-D — 대시보드 오늘·이번 주 일정 위젯

경계:

- DashboardPage에서 오늘과 이번 주의 호출자 대상 일정만 조회한다.
- 건수와 가까운 일정 요약을 표시하고 전체 캘린더로 이동한다.
- groupware.schedules / VIEW가 없으면 요청·위젯을 모두 숨기거나 권한 안내로 일관되게 처리한다.
- dashboard-service에 일정 복제 테이블을 만들지 않는다.
- 기존 배차·결재·주문 마감 overlay는 넣지 않는다.

독립 머지 결과: 이슈 제목의 “대시보드 일정관리”가 실제 홈과 연결된다.

### 슬라이스 S2-E — 일정 알림

경계:

- 활성 대상자 집합을 수신자 정본으로 사용하고 작성자 자신만 발행 단계에서 제외한다.
- 일정 commit과 발행을 분리하는 durable outbox 또는 동등한 재시도 상태를 둔다.
- 일정·대상자·사건 기준 멱등 키와 저장소 unique 제약으로 동시 확정 중복을 막는다.
- 대상자 제거 후 재초대를 새 사건으로 볼지 정책과 키를 명시한다.
- 데스크톱에 SCHEDULE 라벨을 추가하고 /groupware/schedules의 권한 있는 상세로 이동한다.
- 일시 실패 재시도, 동시 확정, 제거·재초대, 작성자 미발행, 알림 클릭을 한 번의
  종단 검증으로 확인한다.

독립 머지 결과: 캘린더가 이미 존재하므로 알림이 404로 끝나지 않고, 실패·중복에도
일정 저장과 수신자 집합이 어긋나지 않는다.

### 선택 슬라이스 S2-F — 기존 업무 데이터 overlay

배차 일정, 결재 기한, 주문 마감은 일반 일정 원장으로 복사하지 않고 읽기 전용 overlay로
표시한다. 각 도메인의 사용자 노출 식별자와 원래 상세 경로를 유지한다. Issue #895 원문도
이를 별도 슬라이스 후보로 두었으므로 핵심 5개 완료 전에는 섞지 않는다.

## 8. 순서와 병합 게이트

권장 순서는 S2-A → S2-B → S2-C → S2-D → S2-E이며 S2-F는 별도 결정 뒤 진행한다.

1. 대상자 정본과 상세 권한이 먼저 있어야 화면이 잘못된 데이터를 정상처럼 가리지 않는다.
2. 실제 캘린더·상세 경로가 있어야 대시보드와 알림의 착지점이 생긴다.
3. 부서·전사를 실제 대상자로 확장한 뒤 대시보드와 알림이 같은 집합을 읽어야 한다.
4. 대시보드 위젯은 원장 복제 없이 목록 계약만 소비하므로 독립적으로 병합할 수 있다.
5. 알림은 수신자 정본과 정상 deeplink가 완성된 뒤 마지막에 붙여야 한다.

Issue #895 종료 게이트는 핵심 5개 완료로 보는 것이 맞다. S2-F는 별도 후보이므로 명시적으로
범위에 승격되지 않는 한 #895 종료를 막지 않는다.

## 9. 확인하지 못한 것과 주의점

- 현재 공유 스택을 재기동하지 않았으므로 PR #994 바이너리의 실제 기동·Flyway 적용 결과는
  확인하지 못했다.
- V17/V18/V90을 공유 DB에 적용한 뒤의 실제 행 수와 HTTP 결과는 확인하지 못했다.
- 브라우저·실 GUI에서 일정 화면은 존재하지 않아 실행 캡처를 할 수 없었다.
- 웹·모바일용 신규 일정 UX의 제품 요구는 확인하지 못했다.
- 부서·전사 구성원 snapshot과 동적 추종 중 어느 정책이 최종 결정인지 확인하지 못했다.
- 종일 일정의 저장 표현을 boolean으로 둘지 날짜 경계 규칙으로 둘지 확정하지 못했다.
- 일정 알림의 정확한 발행 사건이 “CONFIRMED 전환”, “대상자 추가”, “시각 리마인더” 중
  어디까지인지 확인하지 못했다. 다만 어떤 사건이든 작성자 자신은 제외해야 한다.
- Schedule.java:139의 알림 이력 보존 주석과 ScheduleStatus.java:7-9의 알림 주석은 현재
  구현이 이월된 상태와 어긋난다. 이번 라운드는 소스 수정 금지이므로 고치지 않았다.
- Docker 조회는 컨테이너 목록과 PostgreSQL SELECT만 사용했다. 이미지 빌드·서비스
  재기동·공유 DB write는 없었다.
