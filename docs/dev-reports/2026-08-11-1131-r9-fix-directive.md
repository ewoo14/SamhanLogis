# PR #1131 R9 fix directive — keyless 정상 다중 인스턴스 저장 차단

## 판정

**BLOCKING. 실 사용자 경로로 재현 가능한 결함이 1건 있다.**

R7은 세트 인스턴스 정본을 `bundleSetOptions.instanceKey + parentSetModel`로 명시했지만,
guard를 켜기 전에 기존 keyless 다중 인스턴스를 그 정본으로 이관하지 않았다. 실 DB의 정상
DRAFT `2026/08/07-20`은 같은 `AC060CS6PBH1SY` 인스턴스가 두 번 들어간 8행 전표이고,
모든 행의 옵션 JSON은 존재하지만 `instanceKey`가 없다. 사용자가 수량만 양수로 바꿔도 현재
diff는 두 head를 하나의 legacy 인스턴스로 합친 뒤 저장 전에 400으로 거부한다.

## 좌표

- `services/slip-service/src/main/java/com/samhanair/logis/slip/service/BundleLineageResolver.java:269-309`
  - keyless 행의 grouping key가 `legacy: + parentSetModel` 하나다. 같은 모델의 두 정상 인스턴스가
    한 `ExistingBundleInstance`로 합쳐져 `historicalHeadCount=2`가 된다.
- 같은 파일 `:202-210`
  - 합쳐진 인스턴스의 retained head도 2개라 `!= 1`에 걸려
    `세트 head 구성품은 삭제할 수 없습니다`를 던진다.
- 같은 파일 `:312-319`
  - 별도 “경계 불명확” 문구는 `bundleSetOptions == null`일 때만 도달한다. 실 표적은
    옵션 객체가 존재하고 `instanceKey`만 없으므로 이 분기를 지나 위 head-count 문구로 막힌다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/service/SalesSlipUpdateService.java:115-126`
  - head 평면화 뒤 검증이 materialize보다 먼저다. 따라서 이 전표는 key materialize에 도달하지 못한다.
- `clients/desktop/src/renderer/routes/SlipDetailPage.tsx:2108-2127`
  - 400을 모두 협업/최신화 충돌 문구로 표시한다. 사용자는 수량 입력을 고쳐도 복구할 수 없다.

## 실 DB 원문

활성 전표·활성 라인만 집계했다. `instanceKey`의 null·빈 문자열을 모두 keyless로 셌다.

```sql
WITH active_bundle AS (
  SELECT s.id AS slip_id, s.slip_no, s.slip_type,
         l.id AS line_id, btrim(l.parent_set_model) AS parent_set_model,
         COALESCE(l.set_head, false) AS set_head,
         NULLIF(btrim(l.bundle_set_options->>'instanceKey'), '') AS instance_key
  FROM slips s
  JOIN slip_lines l ON l.slip_id = s.id
  WHERE s.is_deleted = false
    AND l.is_deleted = false
    AND l.parent_set_model IS NOT NULL
    AND btrim(l.parent_set_model) <> ''
)
SELECT slip_type,
       COUNT(*) AS rows,
       COUNT(DISTINCT slip_id) AS slips,
       COUNT(*) FILTER (WHERE instance_key IS NULL) AS keyless_rows,
       COUNT(DISTINCT slip_id) FILTER (WHERE instance_key IS NULL) AS keyless_slips
FROM active_bundle
GROUP BY slip_type
ORDER BY slip_type;
```

```text
INBOUND  | 24행  | 8전표   | keyless 24행 / 8전표
OUTBOUND | 346행 | 156전표 | keyless 346행 / 156전표
합계     | 370행 | 164전표 | keyed 0행
```

동일 모델 keyless 다중 인스턴스의 확정 근거는 head 2개 이상으로 한정했다.

```sql
WITH g AS (
  SELECT s.id AS slip_id, s.slip_no, s.slip_date, s.seq_no, s.status, s.slip_type,
         btrim(l.parent_set_model) AS parent_set_model,
         COUNT(*) AS line_count,
         COUNT(*) FILTER (WHERE COALESCE(l.set_head, false)) AS head_count,
         COUNT(DISTINCT l.product_id) AS product_count,
         COUNT(*) FILTER (WHERE l.bundle_set_options IS NULL) AS options_null_count,
         COUNT(*) FILTER (WHERE l.bundle_set_options IS NOT NULL) AS options_object_count
  FROM slips s
  JOIN slip_lines l ON l.slip_id = s.id
  WHERE s.is_deleted = false
    AND l.is_deleted = false
    AND l.parent_set_model IS NOT NULL
    AND btrim(l.parent_set_model) <> ''
    AND NULLIF(btrim(l.bundle_set_options->>'instanceKey'), '') IS NULL
  GROUP BY s.id, s.slip_no, s.slip_date, s.seq_no, s.status, s.slip_type,
           btrim(l.parent_set_model)
)
SELECT *
FROM g
WHERE head_count > 1
ORDER BY slip_date, seq_no, parent_set_model;
```

```text
2026/08/07-20 | DRAFT | OUTBOUND | AC060CS6PBH1SY
8행 | head 2 | product 4종 | options null 0 | options object 8
```

**현재 활성 DB에서 확정 가능한 keyless 동일 모델 다중 인스턴스 전표는 1건이다.**
OUTBOUND keyless 구성의 현재 분모는 346행·156전표·159 `(전표, parentSetModel)` 그룹이다.

## 재현

1. 실 DRAFT `2026/08/07-20` 또는 그 동일 구조 복사본을 연다.
2. 두 인스턴스와 8행을 모두 유지한다.
3. 첫 인스턴스 head `AC060CN6PBH1`의 수량만 `1 → 2`로 바꾼다.

## 불변식

1. 명시적 `instanceKey`가 없는 기존 정상 다중 인스턴스가 실 DB에 있으면, 새 guard 활성 전에
   각 인스턴스의 정본 key를 명시적으로 부여해야 한다. guard를 먼저 켜 정상 편집을 막으면 안 된다.
2. 런타임은 경계가 진짜 모호한 임의 keyless 다중 인스턴스를 추정해 통과시키면 안 된다.
3. 같은 `parentSetModel`의 N개 정상 인스턴스는 N개의 서로 다른 key와 각 1개 head를 보존한 채
   양수 수량·단가·헤더 편집 및 비-head 삭제가 가능해야 한다.
4. 한 인스턴스의 head만 삭제하고 그 자식을 남기는 저장은 계속 거부해야 한다.
5. 기존 단일 keyless 인스턴스와 역사적 0-head 인스턴스는 첫 정상 저장에서 한 key로 materialize되고
   사용자의 양수 편집을 보존해야 한다.

## 양방향 RED

### RED-A — 실 DB 정상 keyless 다중 인스턴스

`2026/08/07-20`의 정확한 구조를 PostgreSQL fixture로 준비한다.

```text
instance A: AC060CN6PBH1[H], AC060CXAPBH1[C], PC6NUNK1NW[C], AR-EH05[C]
instance B: AC060CN6PBH1[H], AC060CXAPBH1[C], PC6NUNK1NW[C], AR-EH05[C]
공통 parentSetModel=AC060CS6PBH1SY
공통 bundleSetOptions={remoteExcluded:false, materialIncluded:false, instanceKey 없음}
```

첫 head 수량만 `1 → 2`로 저장한다.

기대:

```text
2xx
8행·head 2 보존
서로 다른 instanceKey 2개
각 key마다 4행·head 정확히 1개
사용자 수량 2 보존
```

현재:

```text
400 INVALID_INPUT
세트 head 구성품은 삭제할 수 없습니다
DB write 0회
```

### RED-B — 구체 반대 표적

1. **명시 이관 대상이 아닌** 경계 불명 keyless 다중 인스턴스 fixture는 계속 400,
   `saveAndFlush=0`. 런타임 순서·첫 head 추정으로 자동 통과시키지 않는다.
2. 서로 다른 key를 가진 같은 모델 2인스턴스에서 첫 인스턴스 head만 삭제하고 자식 3행을 남긴다
   → `INVALID_INPUT`, DB write 0회.
3. 2번의 첫 인스턴스 4행 전체를 삭제하고 둘째 4행을 유지한다
   → 2xx, 남은 key 1개·head 1개.
4. 단일 keyless H/C 인스턴스의 양수 수량·단가 편집
   → 2xx, 두 행에 같은 새 key materialize, head 1개.
5. 실 legacy 0-head 표적 `2026/08/07-17`·`2026/08/07-7`의 양수 편집
   → 2xx, 원래 0-head 상태와 사용자값 보존, 각 그룹에 key materialize.
6. 기존 수량 0 → 422, 신규 0-head 생성·membership 위조 → 계속 거부.

## 수정 범위

1. 현재 DB의 `2026/08/07-20` 8개 lineId를 두 인스턴스로 **명시 매핑**해 서로 다른 key를
   부여한다. 런타임의 행 순서 휴리스틱으로 일반화하지 않는다.
2. guard 활성 전 read-only preflight를 추가한다.

```text
active_keyless_multi_instance_groups = 0
```

   0이 아니면 배포/guard 활성화를 실패시키고 대상 전표·모델·head 수를 보고한다.
3. R7의 `instanceKey + parentSetModel` 정본, head 교체 인스턴스 전체 평면화,
   keyless 경계 거부를 유지한다. 조건을 `headCount >= 1`로 완화하지 않는다.
4. RED-A를 실제 PostgreSQL IT로 고정한다. 메모리 fixture만으로 끝내지 않는다.

## 반대급부

- lineId 8개를 명시한 이관은 일반화된 자동 backfill보다 유지 비용이 작고 추정을 피하지만,
  대상 행이 배포 전에 바뀌면 migration/preflight가 실패한다. 실패는 조용히 다른 경계를
  만들어내는 것보다 안전하며, 그때 새 DB 실측으로 매핑을 다시 승인해야 한다.
- preflight가 배포를 막을 수 있다. 정상 사용자가 배포 직후 저장 불가를 만나는 대신,
  배포 전에 미이관 데이터가 운영자에게 드러나는 반대급부다.
- runtime 거부는 계속 남으므로 미래 keyless 다중 인스턴스 유입을 막는 생성/복사 계약도
  `instanceKey` 필수로 유지해야 한다.

## 라운드 성격

R7의 “조건 추가보다 정본 명시”는 head 교체 전체 평면화, VAT 권위, 최종 version token의 세
암묵 상태를 실제 필드·최종 flush로 바꾸어 R4~R6의 원 결함 표면을 수렴시켰다. 이번 1건은 그
방향이 틀려서 생긴 것이 아니라 **새 정본으로 넘어가기 전 legacy 이관 경계가 빠져** 정상
데이터 하나가 guard 밖에 남은 배포 순서 결함이다. 따라서 R9는 정본을 약화하거나 새 조건을
덧대는 라운드가 아니라, 실 DB의 유일한 keyless 다중 인스턴스를 명시 이관하고 preflight로
경계를 닫는 bounded 마감 라운드여야 한다.
