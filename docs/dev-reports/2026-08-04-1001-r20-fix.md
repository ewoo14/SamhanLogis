## 결함 1 — 무필터 거래처 식별 수정

### ① 원인

`PartnerLedgerReadModelService`는 기존에 journal/cash 집합을 만든 뒤(`groups`), 그 UUID만
`findByPartnerIdsBatch`로 조회했습니다. 판매전표는 그 다음에 `resolveSale`로 처리되므로
판매전표에만 존재하는 partner UUID는 `groups`에 없었고, `unresolved`에 `partnerId=null` 및
`salesTotal=0`으로 동결됐습니다. 직접 검색은 `selectedSummary`를 먼저 확보해 같은 UUID를
`groups`에 넣을 수 있어 두 경로가 달랐습니다.

근거 코드: 수정 전 `PartnerLedgerReadModelService.java`의 sales 조회가 batch lookup 뒤에
있었고, `resolveSale`의 `groups.get(sale.partnerId())`가 miss 시 unresolved로 보냈습니다.

### ② RED 원문

```text
unfilteredSaleOnlyPartnersUseTheSameIdentityAsDirectSearch() FAILED
expected: 229900
 but was: 0
```

실 데이터 재현 원문:

```text
무필터 43행 = 정상 코드 29행 + code='-' 14행
'-' 14행 salesTotal 합계 = 0
정상 거래처 13곳 · 정본 전표 13건 · 35라인 · 87,562,200원
```

### ③ 고친 내용

판매전표 조회를 partner batch lookup보다 먼저 수행하고, 선택 조건을 통과한 판매전표의
`partnerId`를 `groups`에 선등록했습니다. 따라서 무필터·직접 검색 모두 동일한 UUID를
partner master에서 해소하고, 기존 canonical sale 상태 집합과 표시 정책은 건드리지 않습니다.

## 결함 2 — `SALE_SUMMARY` UUID 노출 수정

### ① 원인

`PartnerLedgerReadModelService`가 journal-only 문서번호를
`"journal-summary:" + group.partnerId`로 만들고 `PartnerLedgerResponse.Document` 및
desktop 상세·인쇄가 public `documentNo`를 그대로 렌더링했습니다. `partnerId` 자체가
JSON 필드가 아니어도 UUID 문자열이 documentNo에 포함되어 public으로 도달했습니다.

### ② RED 원문

```text
journalOnlySalesBecomePubliclyUsableSummaryDocumentsWithoutUuid() FAILED
actual: journal-summary:3d4ed817-fd5a-48d8-b87a-043002a6138d
not to contain: 3d4ed817-fd5a-48d8-b87a-043002a6138d
```

실 데이터 재현 원문:

```text
22거래처 · SALE_SUMMARY 22문서 · 351,000,000원
상세·인쇄 양쪽 동일: journal-summary:<partner UUID>
```

### ③ 고친 내용

`SALE_SUMMARY.documentNo`의 공개 식별자를 거래처 `partnerCode`로 결정했습니다. 거래처
코드가 없는 방어적 fallback은 거래처명 기반 `매출 요약`, 최종 fallback은 고정된 `매출 요약`이며
UUID를 조합하지 않습니다. 거래처 코드가 저장소의 사용자용 business identifier라는 기존
규약과 직접 검색/목록 식별자 계약에 부합합니다.

### ⑤ R8 수치 재확인

정본 cohort 불변 확인 기준은 결함 1과 동일하다: `21전표 / 62라인 / 197,476,400원`,
`P-0005 26,000,000원`, `P-0017 20,000,000원`, `P-0026 5,656,200원`, 집계·상세·인쇄
금액 동일. 이번 fix는 summary의 documentNo만 public code로 교체하므로 금액·라인을
변경하지 않는다. 실 DB/배포 응답의 최종 세 경로 재확인은 PM 재배포 후 수행 대상이다.

## ⑥ R18 보고서 정정 확인

R18의 원문 인용은 보존하고 다음처럼 정정한다. 실제 `SALE_SUMMARY.documentNo`에
`journal-summary:<partner UUID>`가 포함됐으므로 “public UUID 없음” 및 “문서번호는 public
UUID가 아님”은 오기다. 정확한 거래처 상태 수치는 “활성 거래처 50곳”이 아니라
**ACTIVE 45곳 + SUSPENDED 5곳**이다. R20은 이 정정을 반영하고 문서번호를 거래처 코드로
교체했다.
