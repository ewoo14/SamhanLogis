## 2. 판정

## 도달 가능한 결함: 1건 — BLOCK

등록일자 `created_at` 보정과 등록일자 없는 행의 연속 적재 멱등은 실 관리자 적재 API에서 통과했다.

그러나 실제 관리자 삭제 API로 거래처를 삭제한 뒤 정본을 재적재하면 삭제행을 같은 UUID로 복원하지 않고 새 활성행을 생성한다. 삭제 전 UUID를 참조하던 실제 활성 주문 2건은 그대로 고아다.

```text
삭제 전 UUID = 9592e23e-ed3a-4868-be40-2549030f688d
재적재 활성 UUID = 5e4b31aa-048f-4fcc-a627-7f0063a80dbb
uuid_same_as_before = False
orphan_reference_rows = 2
```

DB 직접 INSERT/UPDATE는 수행하지 않았다. 삭제는 `DELETE /admin/partners/1068689215`, 적재는 `POST /admin/partners/imports/ecount-xlsx`만 사용했다.

### 6.1 ⓐ SUSPENDED + 파일 YES: 판정 불가

발화조건 SQL:

```sql
SELECT COUNT(*) FILTER(WHERE status='SUSPENDED') AS global_suspended,
       COUNT(*) FILTER(WHERE status='SUSPENDED' AND id IN (
         SELECT target_partner_id FROM staging.ecount_partner_raw
         WHERE source_file_hash='064770396F5586EC7D49E8219DD19086EF48C072F4BA4FF7B1BABB0EC14D4619'
       )) AS source_suspended
FROM partners WHERE NOT is_deleted;
```

```text

```

정본 7,253건과 현재 SUSPENDED의 교집합 표본이 0이므로 이 축은 판정 불가다. 표본을 만들기 위한 DB 직접 변경은 하지 않았다.

### 6.3 ⓒ native UPDATE 감사열 비오염: 통과

SQL 원문:

```sql
SELECT COUNT(*) AS registration_present,
       COUNT(*) FILTER(WHERE p.created_at=p.registration_date::timestamp)
         AS created_at_matches_registration,
       COUNT(*) FILTER(WHERE p.created_by='a0000000-0000-0000-0000-000000000003')
         AS created_by_polluted,
       COUNT(*) FILTER(WHERE p.modified_by='a0000000-0000-0000-0000-000000000003')
         AS modified_by_polluted
FROM staging.ecount_partner_raw s
JOIN partners p ON p.id=s.target_partner_id
WHERE s.source_file_hash='064770396F5586EC7D49E8219DD19086EF48C072F4BA4FF7B1BABB0EC14D4619'
  AND p.registration_date IS NOT NULL;
```

```text
registration_present=2423
created_at_matches_registration=2423
created_by_polluted=0
modified_by_polluted=0
```

첫 적재 전후 `created_by` 분포도 같았다.

```text
00000000-0000-0000-0000-000000000001 = 7204
sol-pr1154-r1                         = 49
created_by NULL                       = 0
```

샘플 5건의 `modified_at`·`modified_by`도 R1 값 그대로였고 `created_at`만 등록일 자정으로 바뀌었다. native UPDATE의 감사열 오염은 실 경로에서 관측되지 않았다.

각도 3에서 새 활성행의 `created_by=a0000000-0000-0000-0000-000000000003`이 생긴 것은 native UPDATE가 아니라 삭제행 복원 실패로 INSERT된 결함 1의 결과다.
