## 실행 경계와 증거 무결성

- 현재 브랜치 소스로 `accounting-service` bootJar를 재생성하고 `127.0.0.1:18087`에 별도 기동했다.
- 공유 `accounting_db` 연결은 JDBC `default_transaction_read_only=on`, Hikari read-only, Flyway 비활성, JPA DDL `none`, seed·scheduler·Eureka 비활성으로 고정했다.
- DB 명령은 `BEGIN READ ONLY`, `SELECT`, `SHOW transaction_read_only`, `ROLLBACK`만 실행했다.
- 로그인 자체가 공유 DB의 `last_login_at`을 갱신하므로 실 로그인을 하지 않았다. Playwright 세션·읽기 권한만 정적으로 주입했고, target 회계 응답은 현재 브랜치 `:18087`과 공유 DB의 실제 조회 결과다.
- renderer가 자동 시도한 모든 비조회 요청은 브라우저에서 서버 도달 전에 차단했다. 저장·확정·취소·역분개·코멘트 등록 버튼은 누르지 않았다.
- SSE는 `:5317 → :18087` 교차 출처만 해소하는 읽기 전용 프록시를 통과시켰다. 프록시는 GET/HEAD/OPTIONS만 전달하고 응답 CORS 헤더만 추가했으며, 실제 `JournalCollabController`의 응답 상태는 200이었다.
- 캡처 상단의 `업데이트 실패` 배너는 로컬 renderer의 보조 app-version 경로 상태이며 target 회계 API 판정과 분리했다. 최종 target 회계 네트워크에는 400/403/404/500이 없었다.

실행 원문:

```text

  reversal journal    = 2026/07/27-2 / POSTED
  original lines      = 102 차변 13,579 / 110 대변 13,579
```

- 기존 데이터에서 원분개 `REVERSED`, 역분개 번호 존재, 역분개 `POSTED`, 차대 swap을 **1/1** 확인했다.
- 과거 취소 응답 body 자체는 보존되지 않으므로 “응답으로 역분개 번호가 반환됐는가”는 재실행 없이 확인할 수 없다.
- 실제 취소 동작과 응답 계약은 공유 DB 쓰기가 필요해 **미검증**이다.
