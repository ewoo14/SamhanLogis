# PR #984 이카운트 품목 임포트 — 모델코드 일치 품목 병합 구현 보고서

## 작업 로그

- 시작: 보고서 파일을 생성하고 제목을 저장했다.
- 작업 규칙: git 명령, 공유 Docker 재빌드·재기동, 실 DB 임포트를 수행하지 않는다. 검증은 product-service 범위로 제한한다.
- 설계(초안): PostgreSQL `ON CONFLICT` 하나에 두 유니크를 표현하지 않고, 동일 트랜잭션에서 `model_name` 활성 행을 먼저 선조회/갱신한 뒤 없을 때만 `product_code` 활성·soft-delete 행을 선조회/복원하고 최종 `product_code` UPSERT를 수행한다. `model_name` 일치 행의 기존 ID를 반환하므로 기존 이름·단가·구성품 연결을 보존하고, 두 경로 모두 실패할 때만 신규 INSERT가 실행된다.

실제 XLSX를 API로 임포트하지 않았으며, 공유 Docker도 재빌드·재기동하지 않았다.

실제 파일은 회사명 행 1개 + 헤더 행 + 데이터 157쌍 구조(총 160행, 9열)임을 읽기 전용으로 확인했다. `EcountXlsxSupport`의 회사명 행 건너뛰기와 strict 9열 헤더 경로가 이 구조를 처리한다.

실제 `docs/migration/ecount-data/raw/품목관계리스트-Excel다운로드.xlsx`가 확보되어 있으나 기존 `parseRelations`는 CSV parser만 사용했다. 따라서 동일 관계 데이터가 XLSX로 업로드되면 157쌍을 읽지 못해 불변식 D를 위반한다. CSV 경로는 유지하고 XLSX만 공통 `EcountXlsxSupport`로 분기한다.

## 최종 변경 요약

- `UPSERT_PRODUCT_SQL`은 신규 행/`product_code` 기준 재임포트에만 사용한다. 동일 `model_name`은 선행 UPDATE가 기존 ID를 반환하므로 INSERT에 도달하지 않는다.
- 동일명 UPDATE는 활성 `model_name` 전체를 대상으로 하며, 다른 활성 행의 `product_code` 또는 `model_code`와 충돌하면 기존 병합 대상 값을 보존한다. 따라서 두 partial unique index를 하나의 `ON CONFLICT`로 합치려 하지 않는다.
- 관계 파일은 CSV와 XLSX를 모두 지원한다. 실제 오늘 확보된 XLSX는 157쌍 구조이며, API 실 임포트는 하지 않았다.
- Flyway migration은 필요하지 않다.
