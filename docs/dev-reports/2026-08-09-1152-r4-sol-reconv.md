## 결함 2 — “fixture가 가렸다”는 원인이 테스트에서 제거되지 않았다

### 실 사용자 경로

`Product` 도메인의 `NON_GOODS` → `ProductSummaryResponse.from(Product)` → Jackson JSON → HTTP 검색 응답 → `searchProducts()` → `ProductOption` → 견적 라인 선택이라는 실제 경계다. 이 중 어느 한 단계에서 `goodsType`이 다시 끊기면 사용자는 비상품 납품가를 입력해도 수량 1 규칙에 도달하지 못한다.

### 재현 절차와 원문

- FE 신규 테스트 `productApi.search-modal.test.ts:34-51`은 mock 응답에 `goodsType: 'NON_GOODS'`를 직접 주입한다. 직전 결함과 동일하게 서버 JSON에서 키가 사라지는 경우를 볼 수 없다.
- BE `ProductSummaryResponseTest:30-39`는 `from(NON_GOODS)`의 Java 메서드 반환만 본다.
- 별도 직렬화 테스트 `:43-49`는 `from(NON_GOODS)` 결과가 아니라 legacy 생성자의 기본 `goods=true` fixture를 직렬화해 `GOODS`만 단언한다.

즉 `from(NON_GOODS)`와 Jackson 직렬화를 한 테스트에서 연결하지 않았고, HTTP/controller 또는 BE JSON을 FE mapper에 통과시키는 계약 테스트도 없다. `@JsonProperty`를 다시 빼면 BE의 `from_includesGoodsTypeForEstimateSearch`는 계속 green이고, FE 테스트도 직접 주입 때문에 계속 green일 수 있다. 직전 결함을 가린 구조가 그대로 남은 도달 가능한 회귀 검출 결함이다.

## `@JsonProperty` 전수 판정

`ProductSummaryResponse`의 record component 25개는 Jackson이 자동 직렬화한다. 추가 파생 accessor는 `goodsType()` 하나뿐이며 `ProductSummaryResponse.java:179`의 `@JsonProperty("goodsType")`가 필요하다. 재빌드한 실제 HTTP 응답의 NON_GOODS 표본은 26개 key(25 component + goodsType)를 모두 포함했고 `goods=false`, `goodsType=NON_GOODS`였다. GOODS 대조군은 `goods=true`, `goodsType=GOODS`였다.

product-service의 품목 응답 DTO 전수 결과:

- `ProductResponse`: `goodsType`가 record component로 존재해 자동 직렬화.
- `ProductCatalogResponse`: `goodsType`가 record component로 존재해 자동 직렬화.
- `ProductSummaryResponse`: 레거시 `goods`와 파생 `goodsType`를 모두 실제 HTTP로 확인.
- `ProductByCodeResponse`: id/modelCode/name만 제공하는 identity 전용 계약이며 견적·재고 판정 소비자가 아니다.
- `ExpandedLineResponse`: 세트 전개 결과 계약으로 수량은 구성 규칙이 결정하며 견적 자동수량 판정 소비자가 아니다.
- `BundleComponentResponse`/`ProductSpecResponse`: 구성/규격 전용 계약이다.

따라서 현재 실제 소비 경로에서 추가로 빠진 `goodsType` 응답 DTO는 찾지 못했다. 다른 필드도 `ProductSummaryResponse` 실제 JSON key 전수 대조에서 누락 0이었다.
