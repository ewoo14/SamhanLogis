### 0.6 신규 handler와 실제 백엔드 DTO 대조

presence/co-edit:

- 실제 `SlipCollabController`의 join/list/update/awareness는 모두 `ApiResponse<T>` envelope를 반환한다.
- 실제 wire `PresenceEntry`는 `sessionId`, `displayName`, `color`만 노출하고 `lastSeenAt`은 `@JsonIgnore`다.
- 실제 co-edit snapshot은 `{ updates: string[] }`, update/awareness는 `ApiResponse<Void>`다.
- mock도 각각 `envelope(entry)`, `envelope(entry[])`, `envelope({updates})`, `envelope(null)`이므로 성공 응답 형식은 일치한다.

판매전표 PUT 직접 실행 원문:

```text
RESPONSE={"success":true,"code":"OK","message":null,"data":{"id":"slip-005",...,"lineIdContract":true,"lines":[{"lineId":"line-001","productId":"product-001","productName":"테스트 품목","modelName":"MODEL-1","specification":"SPEC","quantity":2,"unitPrice":"1000","note":null}]},"timestamp":"2026-08-12T04:24:24.392Z"}
```

실제 백엔드는 `SalesSlipUpdateController.update()`가 `ApiResponse<SlipDetailResponse>`를 반환하고, `SlipDetailResponse.lines`는 `SlipLineResponse`다. 실제 라인 응답의 식별자는 `id`이며 `lineTotal`, `supplyAmount`, `vatAmount` 등 계산된 응답 필드를 포함한다. 반면 mock은 요청의 `SlipLineInput`을 그대로 응답해 `lineId`를 남기고 `id`와 금액 응답 필드를 만들지 않으며, 요청 전용 `lineIdContract`까지 detail 최상위에 누출한다.

#### 결함 SOL-1178-02 — 판매전표 저장 성공 후 mock 상세 캐시가 잘못된 응답 형식으로 오염됨

- 심각도: 높음
- 실 사용자 표면: `#/sales/slip-005` → 수정 → 저장
- 사용자 영향: `SlipDetailPage.tsx:2095-2105`가 mutation 응답을 `['slip', id]` 캐시에 즉시 넣는다. 이어지는 상세 라인 렌더는 `line.id`를 key/선택 식별자로 쓰고, `slipLineAmounts()`는 `lineTotal` 또는 `supplyAmount`를 숫자로 바꾼다. mock 응답에는 이 필드들이 없어 라인 식별이 사라지고 공급가액·부가세·합계가 `NaN`으로 표시된다.
