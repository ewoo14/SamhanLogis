## 단계별 진행 로그

### R15 정상 행 제거 지점 규명

- R15의 `SalesAggregateService.applyLedgerSalesTotal()`은
  `partnerLedgerSalesClient.find(from, to, null, partnerId)`를 호출한다.
- R15의 `PartnerLedgerReadService.read()`도 선택 거래처일 때
  `salesClient.find(from, to, null, partnerId)`를 호출한다.
- `slip-service` `SlipRepository.findPartnerLedgerSales()`의 기존 조건은
  `:partnerId IS NOT NULL AND s.partnerId = :partnerId` 분기로 들어가
  `partnerCode`를 보지 않는다.
- 실 데이터의 정상 출고 전표는 `partnerId`가 비어 있고 `partnerCode`만 보존된
  legacy 행이므로, 정상 행이 서비스 재검증 전에 DB 조회 단계에서 0건으로 제거됐다.
- R15 재검증 코드 인용: `saleBelongsToPartner()`는 `saleCode`가 공란일 때만
  사업자번호를 허용하고, 조회 자체는 위 `partnerId` 단독 쿼리에 의존했다.

가설: 선택 조회에 master의 `partnerCode`를 함께 전달하고, slip-service가
`partnerId` 또는 동일 `partnerCode`를 조회하도록 하면 정상 legacy 행에 도달한다.
그 뒤 accounting-service의 `saleBelongsToPartner()`를 유지해 다른 거래처 행은
최종 응답에서 제거한다.

### 고친 내용

- `SalesAggregateService.applyLedgerSalesTotal()`과 `PartnerLedgerReadService.read()`가
  선택 master의 `partnerCode`와 `partnerId`를 함께 slip-service에 전달한다.
- `SlipRepository.findPartnerLedgerSales()`는 선택 시
  `s.partnerId = :partnerId OR s.partnerCode = :partnerCode`로 조회한다.
  공란 partnerCode 전표는 이 조건으로 자동 귀속되지 않는다.
- accounting-service의 `saleBelongsToPartner()` 재검증은 유지했다.
  partnerCode가 있으면 code가 일치할 때만, code가 공란이면 사업자번호가 유일하게
  일치할 때만 대상에 귀속한다. 따라서 조회 범위를 넓혀도 다른 거래처 금액은 섞이지 않는다.
- `PartnerLookupClient.searchDirectoryResult()`는 숫자 10자리 입력을
  `165-35-10155`로 포맷해 directory의 저장 형식과 맞춘다.
