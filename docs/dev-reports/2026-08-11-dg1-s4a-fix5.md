## 1. 원인 확인

원인은 읽기 인코딩이 아니라 PowerShell generator의 출력 literal이었다.

- `scripts/refresh-accounting-permission-db-snapshot.ps1:91`이 `PERMISSION_ROLES 횞 PERMISSION_PAGE_CODES`를 직접 출력했다.
- snapshot은 `Get-Content -Raw -Encoding UTF8`로 읽고 있었으므로 읽기 경로가 문자를 깨뜨린 것이 아니다.
- 현재 HEAD에는 fix4가 generator와 snapshot 양쪽에 `횞`를 함께 커밋해 둔 상태였다. 따라서 실행 전후 SHA-256은 같고, 잘못된 출력만 멱등했다.

## 2. RED-A 원문

지시서의 정상 generator를 수정 전에 PowerShell 5.1로 실행했다.

```text
PS_VERSION=5.1.26100.8972
RED_A_BEFORE_SHA256=2AA426DCBFB6860B452A1913CB97A227E394BF5F3D0292D8CE40F82ABC98169C
RED_A_EXIT=0
RED_A_AFTER_SHA256=2AA426DCBFB6860B452A1913CB97A227E394BF5F3D0292D8CE40F82ABC98169C
RED_A_DIFF: (0 lines)
```

현재 커밋된 snapshot 자체가 이미 `횞`였기 때문에, 지시서에 적힌 “커밋 정본 `×`와의 diff”는 이 워크트리에서는 재현되지 않았다. 이는 정본 대조가 통과한 것이 아니라, fix4가 틀린 snapshot을 정본처럼 고정한 증거다.

이를 고정하지 않기 위해 먼저 계약 테스트를 추가했고, 수정 전 결과는 다음과 같았다.

```text
accounting-slip-permission-contract.test.ts
14 passed / 1 failed
실패: refreshScript에 `횞`가 없어야 한다는 단정
```

## 3. 구현 변경

1. generator 91행 literal을 `PERMISSION_ROLES × PERMISSION_PAGE_CODES`로 교정했다.
2. generator를 정상 DB 입력으로 실행해 snapshot 4행을 동일한 `×`로 재생성했다.
3. `accounting-slip-permission-contract.test.ts:89-95`에 generator와 snapshot 모두 `횞`를 포함하지 않고 canonical `×`를 포함하는 회귀 가드를 추가했다.
4. 기존 fix4의 LF 출력, UTF-8 no BOM, 예외 메시지/exit 1 계약은 변경하지 않았다.

### 4.2 비ASCII 전수 확인

- generator: UTF-8 유효 디코딩, 비ASCII 고유 코드포인트 89개. `U+00D7 ×`와 기존 한글 주석/메시지 및 BOM만 존재한다.
- snapshot: UTF-8 유효 디코딩, 비ASCII 고유 코드포인트는 `U+00D7 ×` 1개다.
- 두 파일 모두 `횞`와 `U+FFFD`가 없다.
- generator source 형식은 CRLF 115줄·UTF-8 BOM으로 복원했고, 생성 snapshot은 LF-only 413줄·UTF-8 no BOM이다.
