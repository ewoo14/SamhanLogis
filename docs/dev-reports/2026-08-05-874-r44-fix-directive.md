## ② 불변식 — 구현 수단 지시 금지

1. 각 성공한 협업 저장 사건과 수신자의 관계는 payload가 같더라도 독립적으로 보존되어야 한다.
2. 하나의 저장 사건·수신자 알림은 scheduler, 커밋 직후 worker, lease 복구, 응답 유실 재시도가
   어떤 순서로 겹쳐도 외부 사용자에게 최대 한 번만 전달되어야 한다.
3. 외부 발송의 성공 여부가 불확정인 상태를 단순 실패와 동일시해 중복 발송하면 안 된다.
4. 커밋된 알림은 전달 완료 또는 재처리 가능한 상태여야 하고, 롤백된 저장은 알림 상태를 남기면 안 된다.
5. 이 불변식을 지키기 위해 협업 저장 응답이 auth/notification 호출, drain 완료, lease 만료를 기다리거나
   알림 장애 때문에 이미 유효한 전표 변경·감사·리비전·ACCEPTED 저장이 실패하면 안 된다.
6. genuine lock timeout 409, non-lock query timeout 중립 500, UUID 비공개 계약은 유지되어야 한다.

## ③ 양방향 RED

### RED-A — 되돌리면 안 되는 것

- 느린 auth/notification, executor 제출 거부, 큰 outbox backlog 중에도 `수정완료` 응답과 후속
  different-field 저장이 외부 호출/drain 완료를 기다리지 않는다.
- rollback 저장에는 outbox와 외부 알림이 없고, 성공 저장에는 전표·감사·리비전·ACCEPTED가 모두 남는다.
- same-field stale은 409, different-field same-baseline은 양쪽 변경 보존, genuine lock timeout은
  내부 원문 없는 409, non-lock query timeout은 거짓 잠금 문구 없는 중립 오류를 유지한다.
- **반대급부:** 중복을 막는 변경이 claim 동안 외부 호출까지 DB transaction/row lock 안에 넣어 저장과
  다른 worker를 붙잡거나, executor 거부 시 요청 스레드 동기 발송을 되살리면 RED다.
- **반대급부:** 서로 다른 저장을 구분하는 변경이 rollback 저장의 알림을 남기거나 동일 저장의 재시도마다
  새 사용자 알림을 만들면 RED다.
- **반대급부:** 발송 결과 확인을 위해 사용자 HTTP 응답을 외부 notification 완료까지 지연하거나 내부
  outbox/사용자 UUID를 화면 응답에 노출하면 RED다.

### RED-B — 재발하면 안 되는 것

- 동일 ready row를 scheduler와 afterCommit worker가 동시에 보게 한 뒤 둘 다 외부 push에 도달하면 RED다.
- notification-service가 발송을 수락·커밋한 뒤 응답만 유실된 경계를 재시도했을 때 같은 수신자에게
  같은 저장 알림이 두 번 가면 RED다.
- 동일 사용자·수신자로 `A→B`, `B→A`, `A→B`를 순차 정상 저장했을 때 세 저장은 각각 별도 사건으로
  남고, 세 번째 알림이 첫 번째 fingerprint 때문에 생성되지 않으면 RED다.
- worker가 발송 전 종료되면 재처리 상태가 남아야 하며, 발송 후 상태 기록 전 종료된 경우에도 중복과
  영구 누락 어느 쪽도 허용하지 않는다.
- 롤백 저장 알림, 제출 거부 동기 fallback, non-lock timeout의 잠금 409 오안내가 다시 나타나면 RED다.
