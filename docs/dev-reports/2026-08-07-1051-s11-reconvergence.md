## 2. ① 전파하지 않는 재시드

### 판정: 도달 결함 1건

`applyServerSnapshot()`은 기존 line array를 삭제하고 새 Y.Map을 삽입하지만 해당 transaction을 POST queue에서 제외한다. 따라서 A만 새 CRDT 구조를 알고 B와 서버 update log는 옛 구조만 안다. 이후 A의 정상 편집 update는 A에만 존재하는 새 구조를 참조한다.

인메모리 Yjs로 공통 base를 가진 A/B를 만든 뒤 A만 복원 snapshot을 적용하고, A의 후속 일반 update 2개(26/49 byte)를 B에 실제 `Y.applyUpdate`했다. 결과는 다음처럼 갈렸다.

```text
A  memo = restored memo + A edit   line = L2 / A edited restored line
B  memo = old memo                 line = L1 / old line
```

B 편집을 다시 A에 적용하면 A memo에는 B 입력 일부가 섞였지만 두 세션의 line 집합은 계속 달랐다. 즉 지연 전파가 복원값을 전부 새게 하는 형태가 아니라, 의존 구조가 없는 update가 원격 visible state에 도달하지 못하는 **영구 분기**다. 5초 resync는 서버에 기록된 옛 update만 다시 적용하므로 빠진 로컬 snapshot 구조를 제공하지 않는다.

다른 세션이 복원 결과를 결국 보는 경로도 없다. revision 복원은 board collection `RESTORED`만 발행하고 상세 화면은 그 채널을 구독하지 않는다. per-order collab SSE에는 복원 사건이 없다.

## 3. ② revision 생성 이벤트만 무효화

### 판정: 도달 결함 2건

#### 중복 잔존

협업 수정완료 한 번은 `partner-order:edit`와 `suggestion.accepted`를 모두 발행한다. R10은 둘 다 revision event로 분류하지만 `localRevisionRefreshRef` boolean은 첫 SSE 하나만 건너뛴다.

- HTTP success가 먼저면 local invalidate 1 + 남은 SSE invalidate 1 = 최소 2회.
- 두 SSE가 먼저면 둘 다 invalidate한 뒤 local success가 추가될 수 있다.
- 원격 세션은 suppression flag가 없으므로 같은 commit의 두 SSE를 모두 invalidate한다.

따라서 R7/R9의 “저장 직후 즉시 갱신”은 유지되지만, S10의 사용자 사건당 1회 계약은 닫히지 않았다.

#### 원격 복원 누락

RESTORE revision 생산자는 per-order revision event를 내지 않는다. 로컬 복원자는 mutation callback으로 detail/list/revision을 무효화하지만, 다른 사용자의 활성 상세 화면은 collection board event를 구독하지 않아 새 RESTORE revision과 복원 상세를 즉시 보지 못한다. 조건을 좁힌 반대편 누락이다.

direct 수정은 audit의 `partner-order:edit`, 삭제는 delete audit의 같은 event, 협업 commit은 두 event가 존재한다. 요청에서 열거한 경로 중 원격 revision 복원이 누락됐다.
