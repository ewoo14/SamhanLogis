## A1. 상세 화면 네트워크 요청 전수

목록에서 `2026/08/10-9`를 실제 클릭한 흐름과 같은 deep-link 새로고침에서 발생한 gateway 요청을 합쳐 중복 제거했다. comments·presence는 화면 자동 요청, edits·coedit·revision·stream은 동일 브라우저 인증 컨텍스트에서 개별 확인했다. token 값은 보고서와 캡처에서 `{token}`으로 가렸다.

| 요청 | HTTP 상태 |
|---|---:|
| `GET /auth/me` | 200 |
| `GET /auth/admin/permissions/my` | 200 |
| `GET /api/notifications/my` | 200 |
| `GET /app/notices/active` | 200 |
| `GET /app/version?clientType=DESKTOP&currentVersion=2026%2F08%2F13-1092` | **404** |
| `GET /slips/estimates/{token}` | 200 |
| `GET /api/v1/slips/estimates/{token}/collab/comments?limit=20` | 200 |
| `GET /api/v1/slips/estimates/{token}/collab/presence` | 200 |
| `GET /api/v1/slips/estimates/{token}/collab/edits` | 200 |
| `GET /api/v1/slips/estimates/{token}/collab/coedit` | 200 |
| `GET /api/v1/slips/estimates/{token}/revisions` | 200 |
| `GET /api/v1/slips/estimates/{token}/collab/stream` | 200 |

견적 상세·협업 요청에서는 `400`·`403`·`404`·`500`이 0건이다. 그러나 전체 요청 중 `/app/version` 404가 1건 있으므로 “하나라도 있으면 결함” 기준은 통과하지 못했다.

## 12가지 실행 원문과 숫자

### 1. 상세 화면 네트워크 요청 전수

위 표 12개 고유 요청을 확인했다. 견적 본체와 협업 7종은 전부 200이다. 보조 앱 버전 조회는 404다.

### 2. comments · presence · edits · coedit · revision · stream

```text
comments  GET 200 | 98 bytes
presence  GET 200 | 98 bytes
edits     GET 200 | 98 bytes
coedit    GET 200 | 110 bytes
revision  GET 200 | 373 bytes
stream    GET 200 | SSE 연결 후 body cancel
```

화면의 종전 원문 `코멘트를 불러오지 못했습니다.`와 `버전 이력을 불러오지 못했습니다.`는 재현되지 않았다. presence join/leave는 DB/상태 write이므로 브라우저에서 차단했다.

### 3. 목록 → 상세 여러 건 · deep-link 새로고침

```text
목록 클릭 2026/08/10-9 → /sales/estimates/{token-1} → 상세 정상
목록 클릭 2026/08/10-8 → /sales/estimates/{token-2} → 상세 정상
목록 클릭 2026/08/10-7 → /sales/estimates/{token-3} → 상세 정상
deep-link /sales/estimates/{token-1} 새로고침 → 같은 URL · 같은 상세 정상
```

세 상세 화면 본문에는 각각 원본 문서번호가 보였고 token 문자열은 보이지 않았다.

### 4. 상세에서 「편집」 클릭

```text
/sales/estimates/{token-1}
→ 편집 실제 클릭
→ /sales/estimates/{token-1}/edit
→ 견적서 편집 폼과 기존 값 표시
→ SPA 404 없음
```

임시저장·발송 버튼은 누르지 않았다. 편집 화면의 coedit GET은 200이었다.

### 5. 「인쇄」 경로

```text
/sales/estimates/{token-1}
→ 인쇄 실제 클릭
→ 새 창 /sales/estimates/{token-1}/print
→ 견적서 인쇄 화면 정상
→ 견적번호 2026/08/10-9 표시
→ SPA 404 없음
```

브라우저 인쇄 대화상자를 여는 두 번째 `인쇄` 버튼은 누르지 않았다.

### 6. 같은 견적을 두 번 열 때 token 일관성

```text
첫 목록 응답 token:  CDKnRwP4Sp6-1anB6ig3wA
두 번째 목록 응답:   CDKnRwP4Sp6-1anB6ig3wA
상세 URL·새로고침:    동일
일치: true
```

### 7. token 화면 비노출

상세·편집·인쇄·deep-link 새로고침 화면 본문에서 해당 22자 token 문자열은 모두 `0건`이었다. 네트워크 증거 오버레이도 실제 값을 `{token}`으로 마스킹했다.

### 8. UUID URL·화면·API 응답 비노출

```text
관찰 URL UUID: 0
화면 본문 UUID: 0
견적 목록·상세·comments·presence·edits·coedit·revision 응답 UUID: 0
GET /api/notifications/my 응답 UUID: 2
```

따라서 “URL·화면·API 응답 어디에도 UUID 없음”은 **실패**다. UUID 값 자체는 보고서와 스크린샷에 전재하지 않았다.

### 9. 원본 문서번호 형식

목록·상세·인쇄에서 `2026/08/10-9`가 원본 슬래시 형식 그대로 보였다. URL/API 식별자만 opaque token이고 업무 문서번호 표시는 보존됐다.

### 10. 전체와 출처별 건수

출처 select를 실제로 각각 선택해 `통합 목록 N건` 원문을 읽었다.

```text
전체                         64
데스크톱 · 종합견적서         45
데스크톱 · 주문서              4
웹 · 종합견적서                4
웹 · 주문서                   11
합계 검산: 45 + 4 + 4 + 11 = 64
```

### 11. 웹 저장분 상세

```text
웹 · 종합견적서  S3-1135-%_\
→ /sales/estimates/web-snapshots/... → 웹 종합견적서 상세 정상

웹 · 주문서  주문서 확정 임시저장 / 1068689215
→ /sales/partner-orders/web-drafts/... → 주문서 상세 정상
```

두 경로 모두 404 없이 원본 문서번호/거래처 코드를 표시했다.

### 12. 데이터 자리 `?`

화면에서 알려진 한 행이 그대로 보였다.

```text
2026/08/08-2 | S26 ??? ???
```

공유 `slip_db`를 `BEGIN TRANSACTION READ ONLY`로 조회한 원본도 `2026/08/08-2|S26 ??? ???`였다. 원본과 동일한 알려진 1행으로 기록하고 계속했다. 이 항목을 신규 결함으로 세지 않았다.

## 도달 가능한 결함

1. **deep-link 새로고침에서 앱 버전 조회가 404다.** `GET /app/version?clientType=DESKTOP&currentVersion=2026%2F08%2F13-1092`가 404이며 화면은 계속 열리지만, 이번 지시의 “400·403·404·500 하나라도 있으면 결함” 기준에 해당한다.
2. **같은 실 사용자 흐름의 알림 API 응답에 UUID가 2건 노출된다.** URL과 화면, 견적 도메인 응답은 0건이지만 `GET /api/notifications/my` 응답 본문에서 UUID 정규식 2건을 검출했다. “API 응답 어디에도 UUID 없음”을 위반한다.

**도달 가능한 결함: 2건. 머지 불가.**

견적 opaque token 축 자체의 종전 결함(협업 `400/403`, 편집 SPA `404`)은 재현되지 않았다.

## 공유 DB 쓰기 없음

직접 실행한 DB SQL은 모두 `BEGIN TRANSACTION READ ONLY`였다. 로그인·저장·수정·삭제·DDL을 실행하지 않았다. 브라우저 비-GET 요청은 전부 route에서 차단했다. `slip-service` 교체 전 소스/DB migration이 모두 V119임을 확인했으므로 신규 Flyway 적용은 없었다.
