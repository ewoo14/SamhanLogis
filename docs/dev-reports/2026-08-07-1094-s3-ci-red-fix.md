# #1094 S3 — CI red 두 잡 복구 보고서

## 결론

두 CI 잡의 실패 원인을 각각 확인하고 최소 수정했다.

- Frontend Desktop: `@testing-library/jest-dom` matcher 등록 누락
- Desktop Playwright: S2 회귀 spec의 stale `returnTo`와 두 테스트 조작/selector 결함

입력값·href·접근성 이름·필터/page/scroll 복원 단정은 삭제하거나 약화하지 않았다.

## 1. Frontend Desktop 원인과 수정

### 원인

CI의 Vitest 로그에서 다음 두 테스트만 실패했다.

```text
CashReceiptListPage > URL query의 필터와 page를 목록 정본으로 복원한다
  Invalid Chai property: toHaveValue
CashReceiptListPage > 전표번호는 상세 링크로 렌더한다
  Invalid Chai property: toHaveAttribute
```

`toHaveValue`와 `toHaveAttribute`는 Chai 기본 matcher가 아니라 `@testing-library/jest-dom` matcher다. 저장소 전수 검색 결과 desktop에 공통 Vitest setup 파일이나 기존 `@testing-library/jest-dom` 등록/import는 없었다. 따라서 사용된 matcher가 이번 S2 테스트에서 처음 실행 환경에 들어왔고, CI의 `expect`에 확장되지 않은 것이 직접 원인이다.

### 고친 방법과 이유

`@testing-library/jest-dom`을 desktop devDependency와 lockfile에 추가하고, 해당 matcher를 사용하는 `CashReceiptListPage.test.tsx`에만 다음 Vitest용 import를 추가했다.

```ts
import '@testing-library/jest-dom/vitest'
```

새 전역 setup 파일이나 Vitest 전역 config를 만들지 않았다. 기존 등록 방식은 저장소에 없었고, 파일 범위 import가 다른 테스트 파일의 matcher 환경과 실행 순서를 바꾸지 않아 불변식 ④를 가장 작게 지킨다. `toHaveValue`와 `toHaveAttribute` 단정은 그대로 유지했다.

## 2. Desktop Playwright 원인과 수정

CI job 로그의 실패는 S2가 새로 추가한 `cash-receipt-list.spec.ts`의 RED-A/RED-B 두 건이었다. 기존 cash-receipt 목록 spec의 기존 링크 경로 자체가 죽은 것은 아니었다.

### RED-A — 실제 코드 원인: stale `returnTo`

CI에서 상세의 `[목록]` 복귀 뒤 다음 단정이 실패했다.

```text
Expected: "DEPOSIT_REPORT"
Received: ""
```

`CashReceiptListPage`의 table columns가 `useMemo(..., [])`로 만들어져 최초 query가 없는 `returnTo`를 링크 closure에 고정하고 있었다. 필터를 적용한 뒤에도 링크 state에는 이전 query가 들어가므로 상세 CTA가 canonical path로만 돌아왔다.

수정은 columns memo dependency를 `[returnTo.pathname, returnTo.search]`로 바꾼 것이다. 링크가 현재 목록의 path+query를 state로 전달하게 되어 필터/page 복원 경로가 살아난다.

### RED-B — spec selector 원인

CI에서 다음 단정이 strict-mode로 실패했다.

```text
getByText('전표번호') resolved to 2 elements
1) 필터 label
2) table column header
```

번호 링크의 aria-label과 새로고침·삭제 surface는 정상 존재했고, 사용자 경로도 유지됐다. 따라서 단정을 삭제하거나 완화하지 않고 `getByRole('columnheader', { name: '전표번호' })`로 table header를 정확히 선택하도록 spec만 고쳤다.

### RED-A — spec 조작 원인

stale query를 고친 뒤 로컬에서 추가로 드러난 실패는 제품 코드가 아니라 spec의 `.click()` 자동 스크롤이었다. Playwright가 링크를 클릭하기 전에 링크를 viewport로 가져오면서 `onClick` 시점의 `window.scrollY`가 0이 되어 900 대신 0을 sessionStorage에 저장했다.

스크롤 단정은 유지하고, 현재 scroll 위치에서 native link click handler를 실행하도록 다음처럼 spec 조작만 바꿨다.

```ts
await page.getByTestId('cash-receipt-slip-2026/05/19-3')
  .evaluate((link) => (link as HTMLAnchorElement).click())
```

이것은 링크 click 자체를 우회하는 것이 아니라 동일한 DOM click 이벤트를 발생시키며, `[목록]` CTA의 query 복귀와 session scroll anchor 단정을 그대로 검증한다. 사용자 경로가 살아 있으므로 spec을 올바른 조작으로 갱신했다.

## 3. 기존 방식 조사 결과

- `clients/desktop/src` 전수 검색: `@testing-library/jest-dom`, `jest-dom`, `setupFiles` 등록 없음
- 기존 desktop 테스트의 `toHaveValue`/`toHaveAttribute` 사용: 이번 `CashReceiptListPage.test.tsx`의 세 단정이 최초
- Playwright matcher는 이미 `@playwright/test`의 `expect`가 제공하므로 별도 jest-dom 등록 대상이 아니다.

따라서 기존 matcher setup을 재사용할 수 있는 저장소 내부 방식은 없었다. 새 전역 setup 대신 파일 범위 import를 선택했다.

## 4. 기존 테스트/spec 수정 목록과 이유

- `clients/desktop/src/renderer/routes/CashReceiptListPage.test.tsx`
  - 기존 S2 테스트의 matcher 단정을 바꾸지 않고 `@testing-library/jest-dom/vitest` import만 추가했다.
- `clients/desktop/playwright/cash-receipt-list/cash-receipt-list.spec.ts`
  - RED-B의 모호한 `getByText`를 `columnheader`로 교정했다.
  - RED-A 링크 click을 DOM click으로 바꿔 Playwright 자동 scroll이 저장 anchor를 오염시키지 않게 했다.
  - 기존 목록·링크·필터 단정과 새 필터/page/scroll 왕복 단정은 모두 유지했다.

기존 사용자 경로를 삭제하거나 `toBeVisible`/`toHaveValue`/`toHaveAttribute`를 약화한 수정은 없다.

### CI 원본 실패 로그

- Frontend Desktop: 212 files 중 2 test failures, 1954 passed — 두 matcher 오류

수정 후 로컬 reference Playwright는 3/3으로 통과했다. 전체 660건 CI 재실행은 이 워크트랙에서 다른 스택과 병렬로 돌아가는 CI를 중복 발주하지 않고, 변경 산출물 검증 범위인 reference spec으로 확인했다.
