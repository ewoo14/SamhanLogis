# PR #1145 R1 적대검증 — 도달성

검증일: 2026-08-09  
대상: PR #1145, 이슈 #1144 P0-B, head `794e45189b5b291fef911229744f757aa4c18639`  
판정 질문: **실 사용자가 밟을 수 있는 경로로 재현되는 결함이 있는가?**

## 결론

**있다. 도달 결함 2건을 확인했다.**

1. `V97`은 PageCode 별칭만 정렬하지 않는다. V37이 회계전표 권한을 주지 않은 `MANAGER`·`SALES`의 `.list` 권한을 `.accounting`으로 덮어써서, 매출·매입 회계전표 접근을 넓힌다.
2. `accounting.*` 전수 대조에서 매출·매입 두 쌍 외에 수신 세금계산서도 FE `.inbound` ↔ BE `.inbound.manage`로 어긋난다. 실 MANAGER 계정이 화면 가드는 통과할 권한을 갖지만 목록 GET은 403이다.

마이그레이션은 실제 DB에 적용하지 않았다. 기존 전표는 조회·변경하지 않았고, 미래일(`2099-01-01`) 빈 목록 GET만 호출했다. DB SQL은 모두 `BEGIN TRANSACTION READ ONLY`였다.

## 1. 권한 복제 전후 — 계정·그룹·역할 세 축

두 대상(`sales`, `purchase`)은 실측값이 완전히 같았다. 아래의 “유효”는 해당 저장소의 액션 중 하나 이상이 `TRUE`인 주체 수다. “복제 후”는 V97의 SELECT/ON CONFLICT 규칙을 현재 행에 읽기 전용으로 대입한 결과다.

| 축 | `.list` 복제 전 행 / 유효 주체 | `.accounting` 복제 전 행 / 유효 주체 | 겹치는 주체 | `.accounting` 복제 후 행 / 유효 주체 | 권한 확대 주체 | 활성 중복 행 복제 전 / 후 |
|---|---:|---:|---:|---:|---:|---:|
| 계정 | 26 / 20 | 29 / 7 | 26 | 29 / 20 | 13 | 0 / 0 |
| 그룹 | 6 / 3 | 9 / 1 | 6 | 9 / 3 | 2 | 0 / 0 |
| 역할 템플릿 | 8 / 4 | 11 / 2 | 8 | 11 / 4 | 2 | 0 / 0 |
| 레거시 역할 행 | 8 / 4 | 11 / 2 | 8 | 11 / 4 | 2 | 0 / 0 |

원문 요약:

```text
account:       list_rows=26 overlap=26 expands=13 narrows=0
group:        list_rows=6  overlap=6  expands=2  narrows=0
role_template:list_rows=8  overlap=8  expands=2  narrows=0
role_legacy:  list_rows=8  overlap=8  expands=2  narrows=0
```

확대되는 역할·그룹은 두 전표 모두 동일하다.

```text
role_template MANAGER  list=VIEW,CREATE,UPDATE,DELETE  accounting=(없음)
role_template SALES    list=VIEW                       accounting=(없음)
group         매니저   list=VIEW,CREATE,UPDATE,DELETE  accounting=(없음)
group         영업원   list=VIEW                       accounting=(없음)
```

현재 DB의 활성 계정 행 기준으로 매출·매입 각각 13명이 `VIEW`를 새로 얻고, 그중 3명(`dev_manager`, `janyeonggu`, `manager@samhan.test`)은 `CREATE/UPDATE/DELETE`도 새로 얻는다. 13명 중 `dev_locked`는 현재 잠금 상태이므로 즉시 로그인 가능한 계정은 12명이다.

### 중복과 멱등성

네 저장소에는 각각 활성 `(주체, page_code)` partial unique index가 있다. V97도 네 INSERT 모두 같은 키의 `ON CONFLICT ... DO UPDATE`를 사용한다. 따라서 두 번 실행해도 활성 행 수와 권한 비트는 첫 실행 결과와 같고 중복 행은 0이다.

다만 매 실행마다 `modified_at=NOW()`와 `modified_by`를 다시 기록하므로 감사 필드까지 동일한 강한 의미의 멱등은 아니다. 사용자가 질문한 “두 번 돌렸을 때 중복 행”은 **0건**이다.

### `.list`를 남기는 것이 맞는가

남기는 것이 맞다. `.list`는 단순 폐기 별칭이 아니다.

```text
AppLayout.tsx:565                         입출고 분석 메뉴 가드
routes/index.tsx:629                      입출고 분석 라우트 가드
SlipQueryController.java:58              원천 매출 조회 VIEW
SlipAllocationSourceController.java:37   매출 배분 source VIEW
SlipAllocationSourceController.java:50   매입 배분 source VIEW
```

따라서 두 코드의 공존은 필요하다. 문제는 원천 전표 조회·배분용 `.list`의 권한을 회계전표 전용 `.accounting` 권한과 동일시해 복제한 것이다.

## 2. 도달 결함 1 — V97이 회계전표 접근을 MANAGER·SALES로 넓힌다

### 재현 절차

1. 읽기 전용 SQL로 `manager@samhan.test`의 두 코드 권한을 대조한다.
2. 공개 로컬 QA 자격으로 이 계정에 실제 로그인한다.
3. `GET /auth/admin/permissions/my`를 호출한다.
4. `GET /admin/sales-slips?from=2099-01-01&to=2099-01-01`와 매입 동형 GET을 호출한다.
5. V97의 계정·그룹·역할 SELECT 및 `DO UPDATE`를 현재 행에 읽기 전용으로 대입한다.

### 실측 원문

```text
login                     : manager@samhan.test
loginStatus               : 200
myPermissionsStatus       : 200
salesListActions          : VIEW,CREATE,UPDATE,DELETE
salesAccountingActions    :
purchaseListActions       : VIEW,CREATE,UPDATE,DELETE
purchaseAccountingActions :

/admin/sales-slips?...    : 403
/admin/purchase-slips?... : 403
```

대조군 실 계정:

```text
accountant@samhan.test  accounting.sales-slip.accounting    VIEW,CREATE,UPDATE,DELETE  GET 200
accountant@samhan.test  accounting.purchase-slip.accounting VIEW,CREATE,UPDATE,DELETE  GET 200
staff@samhan.test       accounting.sales-slip.accounting    (없음)                     GET 403
staff@samhan.test       accounting.purchase-slip.accounting (없음)                     GET 403
```

정본 V37의 권한 부여 원문은 두 `.accounting` 코드 모두 `MASTER`, `ACCOUNTANT`만 `TRUE`다(`V37:79-82`). 반면 V97은 겹치는 기존 `.accounting=FALSE` 행을 보존하지 않고 `.list` 값으로 UPDATE한다(`V97:31-35`, `55-64`, `84-93`, `113-122`). 파일 주석의 “기존 `.accounting` 행이 있으면 기존 권한을 보존”과 실제 SQL이 반대다.

### 왜 실 사용자가 밟는가

`manager@samhan.test`는 로그인 200인 실제 MANAGER 계정이며 현재 두 GET에서 403 경계를 직접 확인했다. V97 적용 후 이 계정의 enforcement cache는 두 코드 모두 `VIEW/CREATE/UPDATE/DELETE`가 된다. 변경된 FE는 목록을 `.accounting VIEW`, 작성 화면을 `.accounting CREATE`로 가드하므로 이 계정은 메뉴·목록·작성 화면과 BE 호출까지 허용 대상이 된다.

V97 적용 금지 조건 때문에 “적용 후 200”을 실 DB에서 실행하지는 않았다. 그러나 신규 행 가정이 아니라 현재 존재하는 동일 계정의 충돌 행을 SQL이 TRUE로 UPDATE하는 경로이며, 계정·그룹·역할 세 공급원이 모두 같은 방향으로 바뀐다.

### 원 결함이 닫히는 수와 닫히지 않아야 할 경계

| 대상별 계정 수 | 복제 전 | V97 읽기 전용 시뮬레이션 후 |
|---|---:|---:|
| `.accounting VIEW` 허용 | 7 | 20 |
| `.accounting CREATE` 허용 | 7 | 10 |
| `.accounting UPDATE` 허용 | 7 | 10 |
| `.list VIEW`인데 `.accounting VIEW`가 없던 계정 | 13 | 0 |
| `.list UPDATE`인데 `.accounting UPDATE`가 없던 계정 | 3 | 0 |

따라서 보고된 13개 GET 403과 3개 저장 403은 권한 비트상 해소된다. 동시에 V37이 분리해 둔 MANAGER·SALES 경계도 함께 없어진다. “403을 닫았다”와 “권한이 넓어지지 않았다”는 둘 다 참일 수 없다.

## 3. 액션 축 변경의 대가

`normalizePermissionAction('edit')`는 `update`다(`permissionsApi.ts:409-410`). 변경 후 작성 라우트는 `create`이고, 두 작성 컴포넌트는 각각 `createSalesSlipDraft`, `createPurchaseSlipDraft`만 호출한다. BE 초안 생성도 `CREATE`, 전기는 별도 `UPDATE`다.

현재 계정 권한과 V97 후 시뮬레이션을 직접 센 결과:

| 상태 | 전표별 CREATE 계정 | 전표별 UPDATE 계정 | UPDATE만 | CREATE만 |
|---|---:|---:|---:|---:|
| 복제 전 `.accounting` | 7 | 7 | 0 | 0 |
| V97 후 `.accounting` | 10 | 10 | 0 | 0 |

따라서 현재 실데이터에서는 `edit→create` 때문에 UPDATE-only 계정이 작성 화면을 잃는 경우가 0명이고, CREATE-only 계정이 수정/전기까지 얻는 경우도 0명이다. 새로 허용되는 3명은 `.list`에서 CREATE와 UPDATE를 둘 다 가진다. 또한 전기 endpoint는 계속 `UPDATE`를 검사하므로 CREATE만으로 수정/전기를 수행하는 코드 경로는 확인되지 않았다.

## 4. 도달 결함 2 — `accounting.tax-invoice.inbound`도 FE/BE가 어긋난다

구현자의 차집합 표를 사용하지 않고 다음 두 패턴을 저장소 전체에서 다시 추출했다.

```text
FE: PermissionGuard pageCode=... / dynamicCanAccess(...)
BE: @RequirePermission(page=...) — 동일 파일 상수도 실제 문자열로 해석
```

추출 결과는 FE 22개, BE 33개, 공통 20개였다. `accounting.deposit-mapping`은 BE가 외부 상수 `DepositorMappingService.PAGE_CODE`를 사용하므로 직접 grep으로 정합을 확인했다. 남은 실제 화면 불일치는 다음이다.

```text
FE routes/index.tsx:1392
  accounting.tax-invoice.inbound VIEW
BE TaxInvoiceInboundController.java:40,53,63
  accounting.tax-invoice.inbound.manage VIEW/CREATE
```

### 재현 절차와 실측 원문

1. `manager@samhan.test`로 실제 로그인한다.
2. `/auth/admin/permissions/my`에서 FE/BE 두 코드를 각각 읽는다.
3. 화면이 mount되면 호출하는 목록 GET을 미래일 조건으로 직접 호출한다.

```text
Login          : manager@samhan.test
FeGuardActions : VIEW,CREATE,UPDATE,DELETE
BeActions      :
GetPath        : /admin/tax-invoices/inbound
GetStatus      : 403
```

DB 전수 계수도 `.inbound VIEW=10명`, `.inbound.manage VIEW=7명`이며, 차집합은 `dev_manager`, `janyeonggu`, `manager@samhan.test` 3명이다.

### 왜 실 사용자가 밟는가

사이드바와 라우트는 `.inbound VIEW`를 사용하므로 위 MANAGER 3명에게 수신 세금계산서 화면을 노출하고 진입을 허용한다. 페이지 mount 직후 BE 목록 GET은 `.inbound.manage VIEW`를 검사하여 403을 반환한다. 실제 로그인 가능한 MANAGER 계정으로 같은 GET 403을 재현했다. 따라서 회계 계열의 FE↔BE 불일치가 매출·매입 두 쌍뿐이라는 판정은 성립하지 않는다.

## 6. 증거 무결성 — `12/12`와 Vitest

### 독립 정적 재현

라우트 4개, 메뉴 2개, V97 파일, 네 저장소, 네 PageCode, 네 upsert, DELETE 부재, 구형 edit 가드 부재를 12개 이름 있는 assertion으로 다시 실행했다.

```text
sales-list-route-accounting-view=true
sales-new-route-accounting-create=true
purchase-list-route-accounting-view=true
purchase-new-route-accounting-create=true
sales-menu-accounting-view=true
purchase-menu-accounting-view=true
migration-v97-exists=true
four-permission-stores=true
four-page-codes=true
four-upserts=true
no-target-delete=true
no-legacy-edit-guards=true
passed=12/12
```

이 12/12는 문자열 존재 계약을 재현할 뿐, 권한 확대가 없다는 뜻은 아니다. 실제로 새 Vitest도 충돌 UPDATE가 기존 FALSE를 TRUE로 바꾸는지 검사하지 않는다.

### Vitest 실제 실행

초기 상태에는 `clients/desktop/node_modules`와 `vitest/config`가 모두 없었다. 따라서 의존성이 없어 실행할 수 없었다는 설명은 초기 상태 기준 사실이다. 소스와 lockfile을 바꾸지 않는 `npm ci --ignore-scripts` 후 다음을 실행했다.

정식 명령:

```text
npm test -- --run src/renderer/test-utils/accounting-slip-permission-contract.test.ts
exit 1
[로컬 파생물 신선도 확인 실패]
- design-system dist/index.d.ts 없음
- Electron out/main/index.js 없음
```

Vitest 직접 실행:

```text
npx vitest run src/renderer/test-utils/accounting-slip-permission-contract.test.ts
Test Files  1 passed (1)
Tests       2 passed (2)
exit 0
```

검증용 `node_modules`는 실행 후 제거했다.

PR 본문은 `passed=12/12`, 구현 보고서 본문은 `passed=11/11`이라고 서로 다르게 기록한다. 원 12개 항목과 실행 명령·로그 파일이 남아 있지 않아, 위 독립 12/12와 구현자가 말한 12/12가 동일한 검증이라는 점은 재현할 수 없다. 테스트 자체의 현재 실행 결과 2/2와 독립 정적 계약 12/12는 재현됐다.

## 7. 이번 라운드가 실제로 하지 않은 것

- V97 적용 또는 rollback transaction 실행
- 권한 DB 직접 INSERT/UPDATE/DELETE
- 관리자 화면/API를 통한 임시 권한 부여
- 기존 전표 상태 전이·수정·삭제 및 기존 전표 본문 조회
- Docker 재기동·재배포
- P0-A(VAT), P0-C(채무 원장), P0-D(분개) 판정

V97 적용 금지 때문에 새로 확대될 MANAGER의 “적용 후 GET 200”은 실행하지 않았다. 대신 적용 전 실 계정 403, 현재 충돌 행, V97의 정확한 UPDATE 값, FE/BE 가드를 한 경로로 연결해 판정했다.
