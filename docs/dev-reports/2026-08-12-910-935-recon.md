# #910 + #935 클라이언트 자동 업데이트 트랙 정찰 (2026-08-12)

> 범위: 조사만 수행. 구현·spec 작성·빌드·패키징·공유 Docker 쓰기·git 명령은 수행하지 않았다.

## 가. 이 트랙이 지금 굴러갈 수 있는가 — 아니오

**트랙 전체는 지금 자격 대기다.** 개발책임자가 2026-07-26 이슈 댓글에서 코드서명을 **자체 서명(비용 0)** 으로 하기로 결정한 것은 확인했다. 그러나 결정과 실제 자격물 확보는 다르다. 현재 저장소·GitHub Actions 설정에서 실제 인증서, 개인키, 인증서 secret 이름, 서명된 installer를 확인할 수 없다.

- 저장소의 인증서 확장자(`pfx/p12/pem/cer/crt/key`) 파일: **0개**.
- GitHub repository secret: `CLAUDE_CODE_OAUTH_TOKEN` 1개뿐. `CSC_LINK`, `CSC_KEY_PASSWORD` 등 코드서명 secret은 **0개**.
- GitHub repository variable: **0개**. `DESKTOP_UPDATE_URL`, `AROLOGIS_UPDATE_URL`도 없다.
- GitHub environment는 `github-pages` 1개뿐이고 environment secret은 **0개**.
- 두 Electron builder 모두 `forceCodeSigning: true`라 인증서 없이 실제 배포 installer를 만들 수 없도록 fail-closed다.

피드의 **정책 결정은 이미 있다**. 개발책임자 댓글의 정본은 다음이다.

1. 삼한 퍼블릭과 아로로지스는 **피드 호스팅을 공유**한다.
2. 최종 호스팅은 **S3(Phase 11 AWS 연계)** 다.
3. AWS 전에는 **로컬 정적 피드로 완전 검증**하고, 추후 URL만 S3로 바꾼다.
4. 같은 호스팅을 쓰더라도 두 제품이 서로의 `latest.yml`/installer를 읽지 않도록 **제품별 경로 또는 동등한 격리 축**이 필요하다.

그러나 현재 실제 피드는 없다.

- 저장소의 `latest*.yml`: **0개**.
- 삼한 Electron은 `${env.DESKTOP_UPDATE_URL}`, 아로로지스 Electron은 `${env.AROLOGIS_UPDATE_URL}`이라는 서로 다른 generic feed URL을 요구한다.
- 두 URL의 실제 값, 로컬 정적 서버 주소, S3 버킷/오브젝트 prefix, 게시 CI가 확인되지 않는다.

따라서 **정책·UI 코드 조사/보완만 떼어 하는 것은 가능해도, #935 제목이 요구하는 “코드서명·피드 선행”을 충족한 자동 업데이트 트랙은 지금 굴릴 수 없다.** 이번 라운드의 결론은 구현 착수가 아니라 자격 대기다.

## 나. 개발책임자 결정이 필요한 항목 — 새 정책 결정 없음

이슈 댓글을 읽으면 앞서 결정 요청으로 잘못 올릴 수 있는 항목은 모두 이미 답이 있다.

| 항목 | 기존 개발책임자 결정 | 상태 |
|---|---|---|
| 서명 방식 | 자체 서명, 비용 0 | 결정 완료. **실제 인증서/CI secret 확보는 미완료** |
| 피드 분리 여부 | 삼한·아로로지스 **공유** | 결정 완료 |
| 최종 피드 위치 | S3, Phase 11 AWS 연계 | 결정 완료. AWS는 아직 미이식 |
| 당장 검증 방법 | 로컬 정적 피드로 완전 검증 후 S3 이식 | 결정 완료. 실제 로컬 URL/게시물 없음 |
| 버전 표기 | 전 앱 `YYYY/MM/DD-{번호}` | 결정 완료 |
| 데스크톱 범위 | 코드서명 대상 데스크톱은 모두 사내 PC | 결정 완료 |

그러므로 개발책임자에게 같은 선택지를 다시 물으면 안 된다. 남은 것은 **결정 이행**이다.

- `CN=Samhan Air Systems Co., Ltd.` 자체 서명 인증서와 개인키를 실제 발급·보관하고 `CSC_LINK`/`CSC_KEY_PASSWORD` 경로로 CI 또는 서명 실행 환경에 연결할 것.
- 신뢰 루트를 사내 PC에 배포할 운영 주체·절차를 실행할 것.
- 제품별 격리 prefix를 가진 로컬 정적 feed의 실제 URL과 게시 위치를 준비할 것.
- 추후 Phase 11에서 같은 구조를 S3로 이식할 것.

이는 이번 정찰에서 새 결정을 요청할 문제가 아니라, 이미 정한 방침의 자격물·인프라가 아직 없다는 상태 보고다.

## 2. #928과 #935가 이미 한 것

### #928 — 웹 3앱은 완료

#928은 CLOSED다. 마지막 댓글은 웹 3앱이 PR #934로 이미 완료됐고, 유일한 잔여가 아로로지스 데스크톱이라 #935/PR #981로 재조준됐다고 명시한다.

- 주문 웹: `clients/web/order-app/src/version/versionCheck.ts`, `versionGate.ts`
- 종합견적 웹: `clients/web/estimate-app/lib/version-check.js`, `public/version-gate.js`
- 모바일 퍼블릭 웹: `clients/web/mobile-public/src/version/versionCheck.ts`, `WebVersionGate.tsx`

세 앱 모두 `/app/version` 조회, 강제 수준 안내, 사용자가 누르는 새로고침을 갖는다. 주문/견적 dirty form은 confirm을 거치고, 모바일 퍼블릭 웹은 `isDirty`가 true일 때 별도 확인 dialog를 띄운다. 자동 새로고침은 하지 않는다.

### #935 — 아로로지스 데스크톱 배선도 이미 머지

PR #981은 2026-07-28 머지됐다. 현재 코드에는 다음이 이미 있다.

- `clients/arologis-desktop/src/renderer/version/versionCheck.ts`: `AROLOGIS_DESKTOP` 정책 조회.
- `clients/arologis-desktop/src/renderer/components/common/AppVersionGate.tsx`: MINOR/MAJOR/CRITICAL 안내·차단.
- `clients/arologis-desktop/src/main/auto-update.ts`: `electron-updater` check/download/status/`quitAndInstall` IPC.
- `clients/arologis-desktop/src/preload/index.ts`: 최소 updater bridge.
- `scripts/build-arologis-desktop-release.cjs`: 날짜 버전 주입, `AROLOGIS_UPDATE_URL` 미지정 fail-fast.
- `clients/arologis-desktop/electron-builder.yml`: `forceCodeSigning: true`, generic feed.

PR #981 본문도 “코드는 준비됐고 인증서·피드가 확보되면 실 설치본 검증”이라고 한정한다. 즉 새 updater를 또 만드는 것이 아니라, **실 자격과 피드를 연결해 이미 있는 경로를 검증하는 것이 잔여**다.

### #910이 이미 한 공통 축

기존 dev-report들과 현재 코드를 대조하면 다음은 이미 있다.

- 8개 canonical client identity와 DB CHECK migration.
- 앱별 `/app/version` 판정과 릴리스 관리 계약.
- 삼한 Electron updater 경로.
- 모바일 3앱의 `expo-updates` check/fetch/reload 배선.
- 웹 3앱의 버전 안내와 dirty form 새로고침 보호.
- 사용자 표시용 날짜 버전과 updater 비교용 내부 semver 변환.

없는 것은 “업데이트 배선 전체”가 아니라 **사용 중 재감지**, **모바일 reload 전 작업 보호**, **실 서명·피드·설치 E2E**다.

## 3. 사용 중 알림·작업 보호 계약

#910 본문에 이미 계약이 있다.

- N1: 사용 중 릴리스가 배포되면 재시작을 기다리지 않고 알린다.
- N2: 설치/reload/새로고침이 저장되지 않은 입력을 조용히 잃게 하지 않는다.
- N3: MINOR 알림은 업무를 막지 않는다.
- N4: 모든 클라이언트가 동시에 서버를 때리지 않는다.
- CRITICAL 외 확인 실패·오프라인은 작업을 막지 않는다.

현재 구현의 상태는 다음과 같다.

| 형태 | 현재 감지 | 현재 작업 보호 | 판정 |
|---|---|---|---|
| 삼한 Electron | `AppVersionGate` mount/bootstrapped 시 updater check와 `/app/version` 1회. 주기·focus 복귀 재확인 없음 | 기동 중에만 자동 설치. 기동 이후 늦게 다운로드 완료되면 즉시 설치하지 않고 “다음 기동 때 자동 설치” | 기동 안전 선례는 있음. **사용 중 새 릴리스 감지 없음** |
| 아로로지스 Electron | mount 시 updater check와 정책 조회 1회. 주기·focus 복귀 재확인 없음 | 사용자가 설치 동작을 선택하는 기존 UI. 앱 전체 dirty 상태와 updater install의 공통 계약은 없음 | **사용 중 새 릴리스 감지 없음** |
| Expo 3앱 | `MobileVersionGate` 단일 `useEffect`에서 부팅 시 1회 | update가 있으면 `fetchUpdateAsync()` 직후 `reloadAsync()` 자동 실행. dirty/AppState 보호 없음 | 현재 EAS project가 placeholder라 비활성. 활성화 순간 N2 위험이 살아남 |
| 웹 3앱 | 페이지 mount/DOMContentLoaded 시 1회. interval/visibility/focus 재확인 없음 | 사용자가 새로고침을 눌러야 하며 dirty면 추가 확인 | 작업 보호 선례는 있음. **사용 중 새 릴리스 감지 없음** |

모바일 3앱의 `app.config.js`는 모두 `EAS_PROJECT_ID || 'PLACEHOLDER_EAS_PROJECT_ID'`이고, placeholder이면 `updates.enabled=false`다. 따라서 자동 reload 위험은 현재 운영에서 비활성이지만, EAS 연결과 동시에 반드시 처리해야 한다.

정리하면 **“사용 중 알림” 계약은 #910에 있고 dirty 보호 선례도 웹에 있지만, 8앱 공통의 재감지 메커니즘은 없다.** 코드 검색에서 버전 gate 관련 `setInterval`, `visibilitychange`, `focus`, React Native `AppState`가 나오지 않았다.

## 4. 아로로지스 독립 운영 단위와 피드

기존 결정은 **호스팅 공유**다. 그러나 “같은 `latest.yml` 하나를 두 앱이 읽는다”는 뜻은 아니다. #935 댓글은 같은 위치에 게시하되 산출물이 서로를 덮거나 다른 앱 installer를 받지 않도록 경로 prefix·채널 등 앱 구분 축을 요구한다.

현재 코드는 이 결정을 다음처럼 부분 반영한다.

- 삼한: `${env.DESKTOP_UPDATE_URL}`
- 아로로지스: `${env.AROLOGIS_UPDATE_URL}`

즉 같은 S3 bucket/origin을 쓰더라도 `.../desktop/`과 `.../arologis-desktop/`처럼 서로 다른 base URL을 주입할 수 있다. 현재 builder 주석의 “아로로지스 전용 피드”는 **운영 인프라 분리 결정**이 아니라, 공유 호스팅 안의 제품별 feed 격리를 뜻해야 기존 댓글과 정합한다.

실제 bucket, prefix, URL은 아직 없으므로 결정의 코드 계약만 있고 운영 실체는 없다.
