# PR #1066 / 이슈 #1065 — R5 재수렴 2차 적대검증(SOL) fix directive

## 1. 판정과 실행 기준

**판정: 실 사용자 경로로 재현 가능한 결함 2건. 머지 비권고.**

R4가 서버의 `POST /slips/{id}/inspect` 정적 RBAC를 조건부로 우회했지만, 데스크톱/모바일 화면은 같은 정적 권한으로 버튼과 클릭을 계속 선차단한다. 따라서 이슈의 실제 결재자 `kimgicheol`·`kimeunji`는 HEAD에서도 화면을 통해 새 서버 경로에 도달하지 못한다. 또한 공용 상세 화면의 `complete` 라벨을 전표 유형과 무관하게 `출고 완료`로 바꿔 INBOUND 처리 화면 5건에 잘못된 액션명이 노출된다.

실행 환경 기준을 먼저 고정한다.

```text
검증 HEAD       17ef31a5c99b19c983c7c7a68267d11073367bca
slip 컨테이너   /samhan-slip-service
Created         2026-08-05T17:08:04.170798592Z (KST 2026-08-06 02:08:04)
app.jar mtime    2026-08-06 02:07 KST
R4 commit 시각  2026-08-06 05:32:04 KST
main #1057 merge 2026-08-06 05:13:47 KST (d82fb265c)
```

컨테이너는 R4보다 약 3시간 24분 먼저 생성됐고, JAR의 `SlipController.class`/`SlipService.class` 문자열에도 R2에서 도입된 `isOutboundInspectApprovalMember` 메서드명이 없다. 따라서 라이브 API의 R4 성공 여부를 이 컨테이너로 판정하지 않는다. 재배포·재빌드·중지는 하지 않았다.

R4 보고서의 표본 전제도 현재 DB와 다르다. 검증 시작 시 활성 `OUTBOUND × INSPECTING`은 6전표, 활성 개인 검수자는 2명(`kimgicheol`, `kimeunji`)이었다. API 생성 후 `OUTBOUND × INSPECTING`은 7전표다.

## 2. 재현 가능한 결함과 재현 난이도

### 결함 1 — 결재선 개인은 HEAD 화면에서도 `/inspect`에 도달하지 못한다

재현 난이도: **하**. `OUTBOUND × INSPECTING` 전표와 활성 개인 결재자가 있으면 항상 재현된다.

실 DB/API 원문 요약:

```text
kimgicheol | role=SALES      | slip.transfer.process actions=[] | hasUpdate=false
kimeunji   | role=ACCOUNTANT | slip.transfer.process actions=[] | hasUpdate=false
```

HEAD의 실제 선차단 경로:

1. `SlipDetailPage.tsx:1880-1881`이 `INSPECTING`에서 `possibleActions=['inspect']`를 만든다.
2. `SlipDetailPage.tsx:1108-1114`가 `inspect`를 여전히 `slip.transfer.process`에 매핑한다.
3. 모바일 버튼은 `SlipDetailPage.tsx:2133-2140`에서 정적 UPDATE가 없으면 disabled다.
4. 모바일 클릭 경로도 `SlipDetailPage.tsx:1982-1991`에서 같은 정적 UPDATE가 없으면 alert 후 return한다.
5. 데스크톱 하단 버튼은 `SlipDetailPage.tsx:4346-4353`에서 같은 조건으로 disabled다.

즉 R4 서버의 `SlipController.java:523-537` 조건부 우회는 올바른 요청을 받을 수 있지만, 실제 화면이 요청을 보내지 않는다. R4에 추가된 `SlipDetailPage.transition.test.ts`는 `actionsForStatus()`의 액션 문자열만 검사하며 이 권한 선차단을 재현하지 않는다.

구버전 컨테이너의 동일 계정 원문은 배포 전 증상을 재확인한다.

```text
kimgicheol GET     200, slipNo=2026/08/07-3, status=INSPECTING
kimgicheol inspect 403, "동적 권한 deny — page=slip.transfer.process action=UPDATE ..."
kimeunji GET       403, "매출 전표 조회는 SALES / MANAGER / MASTER 권한만 허용합니다."
kimeunji inspect   403, "동적 권한 deny — page=slip.transfer.process action=UPDATE ..."
```

수정 지시:

- 역할 템플릿을 넓히지 말 것.
- 서버가 단건 전표에 대해 계산한 `inspect` capability(예: `availableTransitions` 또는 `canInspect`)를 상세 응답이나 전용 capability API로 내려줄 것.
- FE는 `inspect`에 한해서만 `static UPDATE || server canInspect`를 사용하고, `accept/process/complete/ship/deliver`는 기존 정적 권한을 유지할 것.
- 단순히 모든 `OUTBOUND × INSPECTING` 사용자의 버튼을 켜지 말 것. 비결재선 계정에는 capability=false여야 한다.
- 데스크톱 버튼, 모바일 버튼, `handleTransition`의 명령형 가드를 동일 판정 함수로 수렴시킬 것.
- 회귀 테스트는 최소한 `canAccess=false + canInspect=true → desktop/mobile enabled + transitionSlip(..., 'inspect') 호출`, `canAccess=false + canInspect=false → disabled/미호출`을 포함할 것.

### 결함 2 — INBOUND `PROCESSING` 화면에 `출고 완료`가 노출된다

재현 난이도: **하**. 활성 INBOUND PROCESSING 전표가 현재 5건이다.

`SlipDetailPage.tsx`는 OUTBOUND/INBOUND 공용이다. R4는 `actionsForStatus(PROCESSING, mode)`를 두 유형 모두 `complete`로 정합화했으나, `SlipDetailPage.tsx:311-318`의 `ACTION_LABEL.complete`를 무조건 `출고 완료`로 바꿨다. 따라서 INBOUND 사용자는 하단에서 `완료 (출고 완료)`를 보게 된다. 서버의 동일 액션은 INBOUND 재고 입고 처리이므로 다른 전표 유형에 대한 사용자 경로 회귀다.

수정 지시:

- 라벨을 `action + mode`로 계산할 것. 최소한 `complete`는 OUTBOUND와 INBOUND를 구분한다.
- OUTBOUND PROCESSING, INBOUND PROCESSING 각각의 렌더 테스트에서 실제 버튼 텍스트를 단정할 것.

## 3. 권한 누출 전수 결과

R4 우회를 탈 수 있는 코드 경로는 다음 두 곳뿐이다.

```text
GET  /slips/{id}         SlipController.getOne
POST /slips/{id}/inspect SlipController.inspect
```

`@RequirePermission` AOP 자체와 다른 컨트롤러는 변경되지 않았다. `slip.transfer.process`를 쓰는 다른 액션은 `/accept`, `/process`, `/complete`, `/ship`, `/deliver`이며 모두 기존 `@RequirePermission(... UPDATE)`를 유지한다. `/inspect`만 어노테이션을 제거하고 수동 검사로 바꿨다.

우회 조건은 서버 저장 전표의 `slipType=OUTBOUND`, 서버 저장 상태 `INSPECTING`, auth-service의 `SLIP_OUTBOUND + OUTBOUND_INSPECT` 결과 `configured=true && allowed=true`다. 전표 유형·상태는 요청 본문이 아니라 `slipService.getOne(id)`에서 읽는다. 다른 전표 ID를 넣으면 그 ID의 서버 저장값을 다시 판정한다. DRAFT/PROCESSING/COMPLETED/SHIPPING/DELIVERED 및 INBOUND는 우회를 타지 않는다. 빈 결재선은 `configured=false`, 삭제된 config/approver는 repository의 `isDeleted=false` 조건에서 제외된다.

식별자는 `X-User-Id` 요청 헤더에서 읽는다. slip-service 자체는 이 헤더를 인증 주체로 신뢰하지만, 정상 사용자 경로의 api-gateway는 서명된 JWT의 userId로 해당 헤더를 remove-then-set한다(`JwtAuthenticationGatewayFilterFactory.java:224-243`). 무토큰 위조 헤더 요청은 실제 게이트웨이에서 401이었다. 따라서 외부 정상 사용자 경로에서는 본문·쿼리로 위조할 수 없다. 단, slip-service 직접 포트는 게이트웨이 신뢰 경계 내부이므로 외부 사용자 경로로 간주하지 않았다.

“이미 완료·비활성·만료된 결재선”은 셋째 가능성이다. 이 모델에는 전표별 결재 인스턴스, 완료 상태, active flag, 유효기간이 없다. 결재선은 문서유형+액션의 전역 설정이고 soft-delete만 존재한다(`SlipService.java:953-956`). 따라서 완료/만료를 우회한다고 판정할 대상 자체가 없으며, 모든 INSPECTING OUTBOUND에 같은 전역 결재자가 적용된다. 이는 PR #1066 이전 결정(전표별 매칭 불가, 상태 경계 대체)과 일치한다.

기존 역할 경로는 유지된다. 실 권한 API에서 `MANAGER`·`MASTER`·`INVENTORY`·`WAREHOUSE` 모두 `slip.transfer.process:UPDATE=true`, `SALES`·`ACCOUNTANT` 개인 결재자는 false였다. HEAD 강제 재실행 결과 `SlipLifecycleControllerIT` 3/3, `SlipDynamicPermissionIT` 6/6, `SlipOutboundApprovalEnforcementIT` 9/9가 통과했다. 활성 전표 영향 수는 OUTBOUND DRAFT 2,194 / PROCESSING 8 / INSPECTING 7 / SHIPPING 5 / DELIVERED 10, INBOUND DRAFT 12 / PROCESSING 5 / INSPECTING 2다. R4의 FE 액션 변경이 직접 닿는 표본은 PROCESSING 13건과 INSPECTING 9건이다.

## 4. 표본 0 질문 — 관리자 화면·API만으로 만들 수 있는가

**만들 수 있다.** DB 직접 INSERT 없이 실제 로그인과 업무 API만 사용해 새 OUTBOUND 전표를 INSPECTING까지 만들었다.

성공 동선:

```text
2026/08/07-3
POST /slips                201 DRAFT
POST /slips/{id}/save      200 SAVED
POST /slips/{id}/send      200 SENT
POST /slips/{id}/accept    200 ACCEPTED
POST /slips/{id}/process   200 PROCESSING
POST /slips/{id}/complete  200 INSPECTING
```

생성·변경한 데이터 전체:

| 전표번호 | 최종 상태 | 결과 |
|---|---|---|
| `2026/08/07-1` | CANCELED | 당일 마감으로 익일 생성 후 serial 재고 인스턴스 부족으로 accept 실패; API cancel로 정리 |
| `2026/08/07-2` | PROCESSING | batch balance는 있었지만 active lot 0으로 complete 409; API 역전이/취소 경로가 없어 잔존 |
| `2026/08/07-3` | INSPECTING | serial AVAILABLE 인스턴스가 있는 품목으로 목표 상태 도달 |

당일(`2026-08-06`) 생성 시 원문은 `409 CONFLICT`, `당일 당일 마감(00:01) 초과 — 익일 출고로 생성하세요`였다. 익일 날짜를 사용해 정상 생성했다. 결재자 추가 API도 시도했으나 실행 중 auth-service 구버전에는 POST mapping이 없어 `500`과 서버 원인 `Request method 'POST' is not supported`로 막혔다. DB에는 새 결재자 행이 생기지 않았다. 기존 활성 개인 결재자 2명을 사용했다.

R4가 배포되지 않았으므로 새 표본에서 R4 HEAD의 실 화면 성공과 회계 배분은 **판정 불가**다. 그러나 “실 관리자/API로 OUTBOUND × INSPECTING을 만들 수 있는가”에는 성공으로 답한다. 실제 화면 클릭의 HEAD 판정은 결함 1의 FE 선차단 때문에 실패가 확정적이다.

## 5. 증거 무결성, 수정 완료 조건, 안 본 범위

R4 보고서의 `SlipInspectControllerIT 전체 통과`는 캐시를 배제해 재현했다.

```text
.\gradlew.bat :services:slip-service:test \
  --tests "com.samhanair.logis.slip.it.SlipInspectControllerIT" \
  --no-daemon --rerun-tasks

BUILD SUCCESSFUL in 1m 1s
18 actionable tasks: 18 executed
TEST XML: tests=9, failures=0, errors=0, skipped=0
```

프런트 신규 테스트는 이 워크트리에 `clients/desktop/node_modules/vitest`가 없어 실행하지 못했다. 다만 결함 1은 테스트 실행 여부가 아니라 현재 HEAD의 세 군데 명시적 `canAccess(...UPDATE)` 선차단과 실제 계정 권한 응답 false의 결합으로 확정했다.

R6 완료 조건:

1. 개인 결재자 capability가 FE 데스크톱·모바일·명령형 가드에 동일하게 반영된다.
2. 비결재선 계정, 다른 상태, INBOUND에는 `/inspect` 우회가 생기지 않는다.
3. `accept/process/complete/ship/deliver`의 정적 권한은 그대로다.
4. INBOUND PROCESSING 버튼에 출고 용어가 노출되지 않는다.
5. `SlipInspectControllerIT`와 관련 권한/수명주기 IT, 새 FE 렌더·클릭 테스트를 강제 재실행한다.

안 본 범위: R4 미배포로 HEAD 바이너리의 실 브라우저 클릭·실 POST 200·후속 회계 배분, vendor 발송, 다른 트랙 `#1069`·`#1075` 파일. Docker 재배포/재빌드/중지, DB 직접 쓰기, Git add/commit/push는 수행하지 않았다.
