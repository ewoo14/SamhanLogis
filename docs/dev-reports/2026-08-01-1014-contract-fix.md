## 확인 3 — ①/② 판단 및 원인

### 판정: ① 단언은 표현을 고정한 것이며, 불변식은 아니다

근거:

1. `AccountingReportController.ledger`는 `@RequestParam String partnerCode`를 받고, `LedgerImageResponse`는 `partnerCode`·`partnerName`·`journalNo`만 응답한다. 응답 DTO에는 UUID 타입이 없다.
2. 네 번째 `parseUuid(userId)`는 화면 응답에 실리는 거래처 식별자가 아니라 `TaxInvoiceBatch.processedBy`에 저장되는 내부 작업자 UUID다. 즉 B의 “거래처는 partnerCode로 다룬다”와 A의 “작성자는 snapshot에 남는다”를 동시에 만족한다.
3. `LedgerImageService`의 4인자 경로는 3인자 호환 호출을 거쳐 조회 결과를 만든 뒤 `createDocumentSnapshot(..., actor)`로 `processedBy`에 작성자를 저장한다. 3인자로 강제하면 A가 깨진다는 직전 왕복의 재현 사실과도 일치한다.
4. 따라서 `getLedger(partnerCode, from, to)`라는 문자열은 호출 인자 개수까지 보장해야 하는 API 불변식이 아니라, 당시 3인자 호출 형태를 정적으로 표현한 취약한 단언이다. 단언을 통째로 삭제하지 않고, `partnerCode` 입력·UUID 비공개 DTO·작성자 전달/저장이라는 실제 불변식을 각각 검증하도록 고친다.

②는 `parseUuid(userId)`가 UUID를 “응답 DTO”로 흘린다는 근거가 없으므로 채택하지 않는다. 내부 DB audit 값인 `processedBy`까지 제거하면 A를 되돌리는 결과가 된다.

## 확인 6 — A 실제 저장 SELECT

공유 Docker가 아닌 테스트 전용 Testcontainers PostgreSQL에서 `LedgerSnapshotPersistenceIT`를 실행했다. 테스트는 자동저장 commit 후 아래 SQL을 실제 실행했다.

```sql
SELECT batch_no, processed_by::text AS processed_by,
       data_snapshot_json IS NOT NULL AS has_snapshot
FROM tax_invoice_batches
WHERE document_type = 'PARTNER_LEDGER' AND document_key = ?
ORDER BY processed_at DESC
LIMIT 1
```

원문:

```text
SELECT batch_no, processed_by, has_snapshot FROM tax_invoice_batches:
{batch_no=LED20260801191704554, processed_by=53357b0a-592c-4e71-b503-6175d47563ef, has_snapshot=true}
```

```text
BUILD SUCCESSFUL in 1m 32s
LedgerSnapshotPersistenceIT: tests=1, skipped=0, failures=0, errors=0
```

`processed_by`가 actor UUID와 일치하고 `has_snapshot=true`이므로 A를 실제 저장 결과로 확인했다. 배치번호 길이 assertion도 같은 테스트에서 통과했다.
