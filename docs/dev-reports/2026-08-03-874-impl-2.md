## 1. #1058 matcher와의 공존 판단

### 결론

`SetRiUsageMatcher`를 별도 matcher로 유지하지 않고 삭제했다. `#1058`의 `LegacySetMatcher`를 세트 후보·pool 소비·옵션 정액·금액 일치의 단일 권위로 유지하고, 이번 변경은 그 matcher에 **거래처·전표 scope를 전달하는 경계 보강**만 추가했다.

### 근거

- `services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/LegacySetMatcher.java:16-96`이 이미 `Code.js:568-659`의 실내기 후보, 필수 실외기, 선택 구성품, 가격 합계, `discountForSet` 적용을 수행한다.
- `services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/MonthEndCloseService.java:561-584`가 product-service의 `SINGLE_SET`·`COMMERCIAL_MULTI` 구성품 카탈로그를 읽고 부모 세트별 후보를 만들어 `LegacySetMatcher`에 전달한다.
- `PartnerDcConfigClient.LookupResult`와 `DiscountRevalidator.GlobalDiscount`에는 #1058에서 전역DC 옵션 6종이 이미 배선되어 있으며, `LegacySetMatcher.java:90`은 세트명으로 정액을 선택한다.
- 제가 처음 추가했던 `SetRiUsageMatcher`는 동일한 pool 소비·금액 비교를 복제하므로 두 matcher를 공존시키면 결과 권위가 갈라진다. 따라서 삭제했다.

### 이번 배선의 경계

- `MonthEndCloseService`는 세금계산서의 전표번호, 매출전표의 slip 번호를 `SetPoolLine.scopeKey`로 보존한다.
- `LegacySetMatcher`는 구성품을 실내기와 같은 `scopeKey`에서만 찾는다.
- 기존 4-인자 `InvoiceLine` 생성자는 호환성을 유지하고 partner code를 scope로 사용한다.
- 매입전표는 세트 pool에 모델 snapshot이 없으므로 빈 set pool을 전달한다.

## 3. RED

새 테스트 `LegacySetMatcherTest.neverConsumesAnOutdoorFromAnotherPartnerScope`를 먼저 실행했다.

```text
LegacySetMatcherTest > neverConsumesAnOutdoorFromAnotherPartnerScope() FAILED
java.lang.AssertionError at LegacySetMatcherTest.java:91
1 test completed, 1 failed
```

당시 `findUnusedByToken`은 partner/doc 범위를 보지 않아 P1 실내기와 P2 실외기를 한 세트로 소비했다.

문서 경계 RED도 추가했다. 초기 실행에서는 5-인자 `InvoiceLine` 생성자가 없어 다음 컴파일 RED가 발생했다.

```text
error: no suitable constructor found for InvoiceLine(String,String,BigDecimal,String,String)
2 errors
```

이는 scope 정보를 기존 matcher 입력에 아직 표현할 수 없다는 사실을 고정한 것이다.

## 4. 구현

### `LegacySetMatcher`

- `InvoiceLine`에 `scopeKey`를 추가했다.
- 기존 3·4인자 생성자는 유지했다.
- 실외기·선택 구성품 조회에 `Objects.equals(indoor.scopeKey(), candidate.scopeKey())` 조건을 추가했다.

### `MonthEndCloseService`

- 세금계산서: `taxInvoiceNo`를 scope로 전달
- 매출전표: `slipNo`를 scope로 전달
- 모델 snapshot이 있는 원본 라인을 `SetPoolLine(modelToken, unitPrice, quantity, partnerCode, scopeKey)`로 보존
- 기존 `byModel` 응답 집계는 유지하고, 세트 matcher 입력만 원본 scope pool로 분리
- `LegacySetMatcher` 외의 두 번째 세트 matcher는 두지 않음

### 고정DC 우선 회귀

고정DC 30%와 전역DC 48%가 동시에 존재하는 fixture를 추가했다. 기대율과 실제율 모두 30%를 확인한다.

## 6. 불변식 실측

### 6.1 불변식 1 — 레거시와 같은 결과

`[DEV-SEED/단위 fixture]`에서 다음을 GREEN으로 확인했다.

- 완성 세트의 실내기·실외기·선택 구성품 금액 합계 일치
- 다른 거래처와 다른 전표 scope의 부품을 섞지 않음
- #1058 기존 `DailyClosingDetailServiceTest`의 완성 세트 token 회귀

`[실데이터/로컬 read-only]` accounting 전표 모집단은 #1058 정찰 기준 0행이었다. 따라서 이번 세션에서 실 원본 전표 행별 레거시 금액 동등 건수를 새로 산출하지 않았다.

### 6.2 불변식 2 — `fixedDc ?? globalRate`

`[DEV-SEED/단위 fixture]` 고정DC 30%, 전역DC 48% → 적용값 30%, 판정 true를 확인했다.

`[실데이터/로컬 read-only]` 이번 세션의 실제 전표 대상에서 두 값이 동시에 존재하는 행 수는 0행으로 산출 가능한 모집단이 없었다. `[실데이터/로컬 read-only]` 참고 기준은 활성 `products` 1,220건, 고정DC 비null 167건, 활성 `dc_configs` 210건이다. 이 세 숫자를 고정DC와 전역DC의 직접 조합 건수로 해석하지 않는다.

### 6.3 불변식 3 — 움직이면 안 되는 금액 1원 불변

이번 변경은 원천 금액 저장·합계 계산을 수정하지 않고 matcher 입력 scope만 바꾼다. `[실데이터/로컬 read-only]` accounting 전표 0행이므로 before/after 금액 비교 모집단은 0행, 변화액은 0원이다.

`[실데이터/로컬 read-only]` #1058 기준선의 옵션 미보유 거래처는 164곳이며, #1058 보고서 기준 0원 변화다. 이번 세션에서 그 164곳을 재조회하지 않았으므로 새 실측으로 주장하지 않고 기준선으로만 보존한다.

### 6.4 불변식 4 — 차단되면 안 되는 것의 비차단

`[DEV-SEED/단위 fixture]` partner scope 1건, document scope 1건의 교차 소비 방지 테스트가 GREEN이다.

`[실데이터/스냅샷 기준선]` #1058 R9 스냅샷 `single-components-A1-N1737.csv`의 실외기 271행은 active 구성 링크 불일치 0행으로 기록되어 있다. 이 수치는 #1058에서 생성한 snapshot 기준선이며 이번 세션의 재전수는 아니다.

### 6.5 불변식 5 — #1058 성과 회귀 없음

이번 변경 후 타깃 회귀는 GREEN이다. 그러나 아래 수치는 이번 세션의 fresh 실측이 아니라 병합된 #1058 보고서의 기준선이다.

| #1058 기준 | 기준선 |
|---|---:|
| 확정 과차감 | 0행 / 0원 |
| 옵션 미보유 거래처 | 164곳 / 0원 변화 |
| 스냅샷 실외기 구성 링크 불일치 | 0행 |

이번 변경은 #1058의 `LegacySetMatcher`, 옵션 선택, snapshot 파일을 삭제·수정하지 않았다. 다만 accounting 전체 suite timeout으로 전체 회귀를 권위 있게 재확정하지 못했다.
