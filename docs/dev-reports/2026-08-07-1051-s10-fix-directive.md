## 2. 불변식(수단 금지)

1. 복원은 서버 권위 사건이지만, 다른 사용자의 미저장 편집을 고지·충돌 처리 없이 삭제해서는 안 된다.
2. 복원 후 편집에 보이는 값은 복원 성공 뒤 실제로 재조회에 성공한 서버 상세여야 한다. 실패한 재조회가 가진 과거 cache를 복원 결과로 취급해서는 안 된다.
3. 복원 재수렴은 header-only 변경과 동일 라인 수 변경도 처리해야 한다.
4. 일반 동시 편집과 복원 무관 realtime update는 보존되어야 한다.
5. revision을 만드는 사용자 사건 1회는 활성 revision 목록을 한 번만 최신화해야 하며, revision을 만들지 않는 댓글·제안 사건은 revision 목록을 재조회해서는 안 된다.
6. 해결 수단은 특정 hook, flag, debounce, Yjs API 또는 query API로 지정하지 않는다. 위 관찰 가능한 계약만 만족시킨다.

## 3. 양방향 RED

### D1

- RED-A: B가 memo 또는 line cell을 미저장 편집 중일 때 A가 복원 후 편집 진입 — B의 값이 조용히 복원값으로 바뀌면 실패.
- RED-B: 동시 미저장 편집이 없을 때 A가 header-only 및 line 변경 revision을 각각 복원 — 다음 편집에 복원 서버값이 아닌 stale CRDT 값이 보이면 실패.

### D2

- RED-A: 복원 POST 성공 + 후속 상세 GET 실패 + query에 복원 전 cache 존재 — 복원 전 cache를 provider에 재시드하거나 강제 재수렴 상태를 해제하면 실패.
- RED-B: 복원 POST 성공 + 후속 상세 GET 성공 — 성공 응답의 header/line/authority가 provider와 폼에 수렴하지 않으면 실패.

### D3

- RED-A: 협업 수정완료 1회에서 local success, `partner-order:edit`, `suggestion.accepted`를 같은 순서/역순으로 전달 — `/revisions` 유효 재조회가 1회를 넘거나 최종 최신 revision이 빠지면 실패.
- RED-B: `comment.created/resolved/deleted`, `suggestion.proposed/rejected/withdrawn` — revision GET이 발생하면 실패. 반대로 원격 `partner-order:edit`만 발생했을 때 최신 revision이 즉시 보이지 않으면 실패.
