## 2. fix

- 공용 `AsyncAutocomplete`: 기본 동작은 결과 1건을 기존 dropdown에 남기고, 2건 이상만 기존 공용 `SearchResultSelectionModal`을 연다. 기존 `ProductMultiSelectAutocomplete`의 1건 즉시 칩 계약은 `autoSelectSingleResult` opt-in으로만 보존했다. 자체 모달은 추가하지 않았다.
- Messenger 테스트 2건은 새 모달의 실제 checkbox/`선택 확정` 흐름으로 갱신했다. 1건 exact 검색은 기존 `mouseDown` 경로를 유지했다.
- `partnerApi.searchPartners`에 선택적 `limit`을 추가하고 기본값을 20으로 복원했다. `DepositorMappingPage`의 모달 호출만 `{ activeOnly: true, limit: 10000 }`을 전달한다.
- `PartnerAdminController`, `GroupwareAdminController`의 기본값은 20으로 복원하고, 세 BE 컨트롤러의 상한은 각각 10000을 유지했다. 따라서 넓은 상한은 명시 호출에만 사용된다.
- TaxInvoice의 기존 정준 소스/UUID 분리 계약은 유지하면서 요청 단정은 20 기본값으로 확인했다.

## 4. 5,587건 응답·렌더 비용 실측

공용 `PartnerAutocomplete`를 실제 jsdom DOM에 렌더하고, 5,587개 후보를 실제 공용 `SearchResultSelectionModal`에 전달했다. 응답 envelope를 `JSON.stringify`한 뒤 `TextEncoder`로 UTF-8 byte 수를 계산했다.

| 항목 | 실측 |
|---|---:|
| 후보 수 | 5,587건 |
| 응답 JSON 크기 | 786,730 bytes (약 768.29 KiB) |
| dialog DOM 완성까지 | 3,142.41 ms |
| 렌더 input 수 | single 모드 radio 5,587개 |

이는 비용상 문제가 있다. 현재 방식은 5,587개 전체를 한 번에 DOM에 렌더하므로, 상한 10000을 무조건 모든 화면에 적용하지 않고 모달 대상 호출에만 명시했다. 후속 최적화 후보는 목록 virtualization 또는 서버 페이지형 모달이며 R6에서는 계약/도달성 회귀를 만들지 않기 위해 범위를 넓히지 않았다.

## 5. BE 상한 확대의 타 소비자 영향

정적 호출자 전수 검색(`rg`) 결과 `/admin/partners/search`의 애플리케이션 타 소비자는 8개 호출 표면이었다.

| 타 소비자 | 요청 상한 | 영향 |
|---|---:|---:|
| `adminApi.listAdminPartners` 관리자 목록 | 기본 20 | 10000 미전달 |
| `sales.searchPartners` → EstimateForm | 8 | 10000 미전달 |
| `sales.searchPartners` → SlipDetail | 8 | 10000 미전달 |
| `partnerApi.searchPartners` → TaxInvoice | 기본 20 | 10000 미전달 |
| `partnerApi.searchPartners` → NotesReceivable 2개 필드 | 기본 20 | 10000 미전달 |
| `partnerApi.searchPartners` → CollectionPlan 2개 필드 | 기본 20 | 10000 미전달 |
| `partnerApi.searchPartners` → DailyClosing | 기본 20 | 10000 미전달 |
| `partnerApi.searchPartners` → MergeConvert | 기본 20 | 10000 미전달 |

위 8개 타 소비자 중 10000을 받는 호출은 **0개**다. R6 대상 `DepositorMappingPage` 1개만 `limit=10000`을 명시한다. `/admin/groupware/messages/recipient-search`, `/admin/groupware/approvals/approver-search`와 `/internal/users/search`는 정적 검색에서 R6 대상 외 production 호출자 0개였다. 따라서 BE 기본값 확대가 타 소비자에 전달하는 건수 영향은 **0건**이다.

## 6. 불변식 1~6 실측

1. **전체 GREEN:** desktop `195/195 files`, `1728/1728 tests`, BE 3 module Gradle exit 0.
2. **R5 회귀 없음:** 4종 계약 테스트 `search-modal-four-target.contract.test.ts` 통과, 담당자 mock Playwright 모달/checkbox/확정 통과, typecheck exit 0.
3. **도달성:** R6 대상 5,587건은 요청 `limit=10000`으로 절단 0건. Messenger 담당자도 BE 상한 10000. 따라서 도달 불가 건수 0건이며 Playwright에서 2건 이상 모달 선택을 실제 확인했다.
4. **비용 측정:** 786,730 bytes / 3,142.41 ms를 기록했다. “괜찮다”로 처리하지 않고 비용 문제를 보고하며, 10000을 모달 호출로 한정했다.
5. **BE 타 소비자 영향:** 타 소비자 8개 호출 표면 중 `limit/size=10000` 전달 0개, 영향 건수 0.
6. **정확 코드 경로:** 기본 1건 결과는 공용 dropdown을 유지하고, 기존 품목 다중선택 wrapper만 opt-in 즉시 칩을 사용한다. 일반 거래처 소비처 기본 요청은 20으로 복원했다. 정확 입력/1건은 모달이 뜨지 않으며, 기존 exact/클릭 선택 경로를 막지 않는다.
