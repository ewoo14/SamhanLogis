## 불변식 1 — 확정 품목은 단순 포커스로 해제되지 않음

### 진단

`AsyncAutocomplete.handleFocus`가 선택값이 있는 상태에서도 `setCommitted(value === null)`을 실행했다. 그 결과 선택된 품목을 마우스로 재클릭하거나 역방향 Tab으로 다시 포커스할 때 `false`가 상위로 전달됐다. `SlipFormPage`의 `onInputCommitChange(false)`는 이를 실제 해제로 해석해 `productId`, 품목명, 유형을 지웠다.

### 조치

포커스는 검색 표면을 여는 동작으로만 처리하고 committed 출력은 건드리지 않도록 했다. 실제 입력 변경은 기존 `handleChange` 경로를 그대로 사용하므로 사용자가 입력을 비우면 `false`가 발생하고, 전표 상위 상태가 품목을 해제한다. 즉 포커스와 값 변경을 분리했다.

이 변경이 전역 자동완성에 미치는 영향도 닫았다. 일마감과 차단 거래처는 포커스 뒤 표시 draft가 확정 라벨과 다른지 추가 비교해, 확정 선택을 조용히 실행하는 기존 오범위 방지 가드를 유지했다.

## 불변식 2 — 판매·구매 신규 전표의 다건 후보는 모달

### 진단

`SlipFormPage.tsx`의 판매·구매 `ProductAutocomplete` 두 곳이 `resultSelectionMode={null}`로 명시되어 있었다. 공용 자동완성은 이 값이 없으면 후보가 2건 이상이어도 인라인 목록만 유지한다. R2/R7의 이전 보고서에는 당시 Playwright inline-list 회귀를 피하려고 모달을 끈 이력이 있었지만, 현재 개발책임자 결정인 “후보 2건 이상이면 모달”을 우회할 지속적인 도메인 이유는 없었다.

## 불변식 3 — 모달의 규격 열은 실제 값을 표시

### 진단

공용 `ProductAutocomplete`와 프런트 `ProductOption`에는 이미 `specification` 열과 필드가 있었지만, 상품 검색 API의 `ProductSummaryResponse` record에 해당 필드가 없었다. 따라서 실제 규격이 있는 품목도 JSON에 값이 오지 않아 열 렌더러가 항상 `—`로 폴백했다.

### 판단

열을 제거하지 않고 값을 공급하는 쪽을 선택했다. 이미 화면·모달·프런트 타입이 규격을 표현하도록 설계되어 있고 `Product` 엔티티에도 필드가 존재하므로, 규격 열을 유지하면서 백엔드 계약을 완성하는 것이 사용자에게 가장 유용하고 변경 폭도 작다.

### 조치

`ProductSummaryResponse` canonical record에 `String specification`을 추가하고, `from(Product)`에서 `p.getSpecification()`을 매핑했다. 기존 호환 생성자는 `null`을 전달하도록 유지했고, parent-set 변환도 `base.specification()`을 보존한다. 자동완성의 규격 열 설명도 “검색 API가 생략”에서 실제 DTO 값을 표시한다는 내용으로 정정했다. DB migration은 필요하지 않다.

## 불변식 4 — 견적 협업 중 미저장 행 보존

### 진단 — 먼저 뿌리를 확인함

이 결함은 `CollaborativeSlipInput` 자체가 입력을 버리는 문제가 아니었다.

1. 참가자 A가 마지막 행을 입력하면 `appendBlankRowIfLastChanged`가 새 빈 행을 만들고, 협업 입력은 `createCoeditProvider.setItemValue`를 통해 Y.Array 행을 확장한다.
2. 참가자 B 진입 또는 재연결 때 `EstimateFormPage`가 서버 라인과 trailing 빈행 하나의 개수(`serverLineCount`)를 계산한다.
3. 기존 조건은 `providerLineCount !== serverLineCount`이면 모두 구조 불일치로 판정하고 `seedEstimateCoeditProvider`를 호출했다.
4. seed는 `createCoeditProvider.replaceItems`로 Y.Array 전체를 서버 스냅샷+빈행 하나로 교체한다. 그래서 서버보다 앞선 Y.Doc에 있던 A의 미저장 입력 행이 사라졌다.

R12·R14·R15가 반복한 표면 증상에 행 추가/재연결 보정만 덧대지 않고, 덮어쓰기를 일으킨 `!==` 조건이 근본 원인임을 고정했다.

### 제약 확인

R20에서 분리한 편집 라우트를 되돌리지 않았다. `SlipDetailPage.tsx`와 `CollaborativeSlipInput.tsx`는 `origin/main`과 바이트 동일하다는 결정에 따라 수정하지 않았고, `/sales/:id/edit` 복원도 하지 않았다.

### 조치

다음 우선순위로 바꿨다.

- provider가 비어 있거나 서버보다 뒤처진 경우에만 서버 seed
- provider 행 수가 서버와 같고 lineId가 낡은 경우에만 lineId 계약 복구용 reseed
- provider가 서버보다 앞서면 현재 Y.Doc을 보존하고 full `replaceItems` 금지

## 불변식 5 — 자동 빈행 하나만으로 계속 입력

### 진단

네 화면 모두 이미 사용자 입력을 받은 마지막 행에 `appendBlankRowIfLastChanged`를 연결하고 있었다. 따라서 수동 버튼을 제거해도 다음 경로가 유지된다.

- 전표: 시작 빈행 5개 + 마지막 행 입력 시 자동 증식
- 견적: 시작 빈행 1개 + 마지막 행 입력 시 자동 증식
- 분개: 시작 최소 2행 + 마지막 행 입력 시 자동 증식
- 재고이동: 시작 최소 1행 + 마지막 행 입력 시 자동 증식

분개는 `removeLinePreservingMinimum(..., 2)`, 재고이동은 `lines.length === 1` 방어를 유지했다. 즉 버튼 제거가 최소 행 규칙을 훼손하지 않는다.

### 조치

네 화면의 `addLine` 함수와 “+ 라인 추가” 버튼을 제거했다. 기존 재고조회 버튼, 행 삭제 버튼, 최소 행 방어는 남겼다. 견적/전표 Playwright도 버튼을 페이지 로드 sentinel로 쓰거나 클릭해 행을 만들던 부분을 실제 입력 후 자동 빈행 경로로 바꿨다.
