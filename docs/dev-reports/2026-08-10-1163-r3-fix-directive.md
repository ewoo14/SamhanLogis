# PR #1164 / 이슈 #1163 R3 수정 지시서

## 판정

도달 결함 1건. 이번 fix가 `X-User-Name`을 `WarehouseController`에서 다시 URL decode해, 공통 servlet 필터가 이미 decode한 표시명을 이중 decode한다. `%`를 포함한 합법 표시명은 수정·삭제·복원·되돌리기 네 쓰기 모두에서 `null` 또는 다른 문자열로 바뀌고 신규 감사행 화면이 `변경자 미상`으로 회귀한다.

일반 한글 표시명 `김감사`는 보존되므로 직전 R2 결함의 대표 표본은 닫혔다. 그러나 같은 실 사용자 경계에서 `%` 표시명이 다시 소실되므로 R3 전체 판정은 RED다.

## 실 사용자 재현 경로

1. MASTER가 사용자 관리에서 계정 성명을 `김%감사`로 생성·수정한다. 현재 입력 계약은 `@NotBlank/@Size(max=50)`뿐이라 `%`를 금지하지 않는다 (`AdminUserCreateRequest.java:25`, `AdminUserUpdateRequest.java:19`). auth 동기화 계약도 `@NotBlank/@Size(max=100)`뿐이다 (`UpdateDisplayNameInternalRequest.java:8`).
2. 해당 사용자가 다시 로그인해 새 JWT를 받고 `/admin/warehouses`에서 창고를 수정·삭제·복원·되돌린다.
3. 게이트웨이는 JWT의 원문 `김%감사`를 `URLEncoder`로 한 번 인코딩해 `%EA%B9%80%25%EA%B0%90%EC%82%AC`를 보낸다 (`JwtAuthenticationGatewayFilterFactory.java:257-264`).
4. inventory-service에 자동등록된 `UserHeaderDecodingFilter`가 이를 `김%감사`로 정상 복원한다 (`UserHeaderDecodingFilter.java:43-58`; `UserHeaderDecodingAutoConfiguration.java:28-34`; `inventory-service/build.gradle:54`).
5. 이번 fix의 `WarehouseController.decodeCallerName`이 `김%감사`를 다시 `URLDecoder.decode`한다 (`WarehouseController.java:273-281`). `%감`은 유효한 percent escape가 아니므로 `IllegalArgumentException`을 잡아 `null`을 서비스에 전달한다.
6. `WarehouseService.resolveActorName`은 그 `null`을 그대로 감사 recorder에 전달한다 (`WarehouseService.java:370-403`). 변경 목록은 비어 있지 않아 감사행은 생성되지만, 화면은 `EditWarehouseModal.tsx:334-337`에 따라 `변경자 미상`을 표시한다.

같은 원인으로 원문 `김%20감사`는 `김 감사`, 원문 `%EA%B9%80`은 `김`, 원문 `김+감사`는 `김 감사`로 바뀐다. 즉 예외가 나지 않는 입력도 조용히 다른 사람 이름으로 저장된다.

## 양방향 RED

### RED-A — 단일 decode와 네 쓰기 표시명 보존

구체 표적: `UserHeaderDecodingFilter`를 실제 filter chain에 넣은 `WarehouseController` PATCH·DELETE·restore·audit revert 경계.

- JWT 표시명 원문 `김%감사`를 게이트웨이와 동일한 `URLEncoder(UTF-8)`로 인코딩해 `X-User-Name`에 넣는다.
- 공통 필터를 지난 뒤 네 컨트롤러가 서비스에 전달하는 이름은 모두 원문 `김%감사`와 byte-for-byte 같아야 한다.
- 추가 표본 `김감사`, `김%20감사`, `%EA%B9%80`, `김+감사`도 각각 원문 그대로여야 한다.
- 저장 후 네 신규 감사행의 `actorName`과 `GET /inventory/warehouses/{id}/audit-logs` 응답, 실 화면 표시가 모두 원문과 같아야 한다.

현재 임시 경계 probe 원문:

```text
5 tests completed, 4 failed

Wanted:
warehouseService.update(..., "김%감사");
Actual invocations have different arguments at position [3]:
warehouseService.update(..., null);
-> at WarehouseController.update(WarehouseController.java:157)
```

삭제·복원·되돌리기도 각각 `WarehouseController.java:233`, `:269`, `:213`에서 기대 `김%감사` 대비 실제 `null`로 동일 실패했다. 일반 한글 `김감사` 1건은 통과했다.

### RED-B — 반대급부 구체 표적

- 중앙 필터를 제거하거나 우회하지 않는다. servlet runtime에서 URL decode 소유자는 `UserHeaderDecodingFilter` 한 곳이어야 한다.
- `X-User-Id`와 `X-User-Name`이 모두 없으면 네 경로 감사행은 system sentinel + `actorName=system`, 화면은 `시스템`이어야 한다.
- 정상 `X-User-Id`만 있고 이름 헤더가 없거나 blank면 감사행은 생성하되 `actorName=null`, 화면은 `변경자 미상`이어야 한다. 이를 system으로 오분류하면 실패한다.
- blank/UUID 이름 때문에 recorder 호출을 생략하면 실패한다. 수정의 실제 변경 필드 수, 삭제 1행, 복원 1행, 되돌리기 대상 필드 수만큼 감사행 증가를 각각 확인한다.
- UUID 차단은 canonical 36자 UUID만 대상으로 유지한다. `33333333-3333-4333-8333-333333333333`은 저장/표시하지 않고, `12345678-1234-1234-1234-12345678901Z` 같은 비canonical 문자열은 정상 이름으로 보존·표시한다.
- 프런트 되돌리기 조건은 유지한다. 일반 필드 revision에는 버튼 1개, `isDeleted` 전용 revision에는 0개여야 한다.
- 네 프런트 mutation 계약은 PATCH / POST revert / DELETE / POST restore를 유지한다.

## 나머지 다섯 각도 판정

1. **URL decode** — 일반 한글은 PASS, `%`·`+`·percent-escape 모양 입력은 이중 decode로 RED. root cause는 컨트롤러의 두 번째 decode다.
2. **헤더 없는 호출** — user-id도 없으면 `system/시스템`, user-id만 있으면 `null/변경자 미상`으로 코드상 구분된다. 이 축의 별도 결함은 없다.
3. **네 경로** — 컨트롤러와 서비스 연결은 네 경로 모두 존재하지만 같은 두 번째 decoder를 공유해 `%` 표시명은 4/4 실패한다. stale backend 때문에 배포 후 E2E 확인이 필요하다.
4. **blank/UUID와 감사행** — `recordAuditSafe`는 `changes`만 검사하고 이름을 조건으로 삼지 않아 기록 자체는 유지된다. 이 축의 별도 결함은 없다.
5. **UUID 판별 폭** — BE는 `UUID.fromString` 후 canonical round-trip 일치, FE는 anchored canonical 정규식이다. 비canonical UUID 유사 문자열은 실 화면에 표시됐고, auth DB 33계정 중 canonical UUID 이름 0건이었다. #1134 R13과 같은 과잉 판별은 확인되지 않았다.

## 수정 범위

- 포함: `WarehouseController`의 중복 decoder 제거 또는 중앙 필터 계약에 맞춘 단일 decode, 네 controller/filter 통합 계약 테스트, `%`·`+`·percent-escape 모양 회귀 표본, 기존 service/UI 계약 테스트.
- 배포 후 확인: throwaway `%` 표시명 계정 + throwaway 창고로 수정→되돌리기→삭제→복원, 네 DB 감사행과 화면 표시 확인 후 모두 정리.

## 반대급부

컨트롤러 decoder를 제거하면 공통 filter를 거치지 않는 standalone 직접 호출은 encoded 문자열을 그대로 볼 수 있다. 그러나 실제 inventory servlet runtime은 `shared:security` 의존성과 `/*` 자동등록 filter가 계약 소유자다. 이를 보완한다며 두 번째 decoder를 유지하면 `%` 원문을 안전하게 구별할 방법이 없다. filter 포함 controller 통합 테스트로 runtime 계약을 고정하고, 직접 단위 테스트는 이미 decode된 헤더를 넣어야 한다.
