# PR #1129 슬라이스 C r2 — BLOCKING 해소 보고

검증 시각: 2026-08-09 KST  
작업 브랜치: `fix/1051-product-link-track`  
범위: 코드·테스트·Compose 정렬만 수행. commit/push, Docker 재배포, 실 DB 쓰기, 기존 행 수정·삭제 없음.

## 판정

결함 1~3을 수정했다. RED-B의 정상 차단 건수는 **0건**이다.

- product 100건 중 `ACTIVE 96 + DISCONTINUED 4`를 모두 product 존재로 인정한다.
- 미존재 product와 product-service 조회 실패를 분리한다.
- 조회 실패 또는 시딩 중 예외가 나도 SlipSeeder가 오류를 명확히 로그로 남기고 시딩만 건너뛴다.
- Compose의 slip-service는 product-service `service_healthy` 이후 시작한다.

## 결함별 원인·수정·근거

### 결함 1 — 정상 단종 품목까지 전체 차단

원인: `SlipSeeder.loadSeedProducts()`가 `summary.id != null`과 별개로 `status == ACTIVE`를 요구했다. 표준 product seed의 seq 25·50·75·100은 `DISCONTINUED`이므로 4개가 탈락하고 all-or-nothing 검증이 100건 전체를 차단했다.

수정: 검증 게이트를 “응답에 해당 product UUID가 존재하는가”로 좁혔다. 상태는 전표 참조 가능 여부의 조건으로 사용하지 않는다.

근거: `SlipSeederProductIntegrityTest.discontinuedSeedProductStillAllowsAllHundredSlips`에서 `DISCONTINUED` 4건을 포함한 100개 응답을 주고 `save()` 100회를 확인했다. **정상 차단 = 0건**.

### 결함 2 — 조회 실패를 품목 없음으로 오분류·무제한 timeout

원인: bulk lookup의 모든 4xx가 `INVALID_INPUT/존재하지 않는 제품 ID`로 매핑됐고, 기본 `RestClient` request factory에 connect/read 상한이 없었다.

수정:

- bulk 404만 `NOT_FOUND/제품이 존재하지 않습니다`로 매핑한다.
- 401/403/408/429는 `INTERNAL_ERROR/product-service 조회를 검증할 수 없습니다`로 매핑해 인증·권한·timeout·rate limit을 “없음”과 구분한다.
- 운영 DI 경로에 connect timeout 2,000ms/read timeout 3,000ms를 적용했다. `samhan.product-client.connect-timeout-ms`, `samhan.product-client.read-timeout-ms`로 조정 가능하다.

근거: `ProductClientTest`에 bulk 404 및 401/403/408/429 회귀 테스트를 추가했고 모두 통과했다. 네트워크 timeout의 실 연결 테스트는 외부 서비스 호출 없이 수행하지 않았다.

### 결함 3 — product 준비 순서·시딩 실패가 기동을 죽임

원인: Compose에 product-service health dependency가 없었고, `CommandLineRunner`에서 lookup/seed 예외를 그대로 전파했다.

수정:

- `docker-compose.local-all.yml`, `docker-compose.prod.yml`의 slip-service에 `product-service: condition: service_healthy`를 추가했다.
- `SlipSeeder.run()`이 예외를 잡아 `[SlipSeeder] 시딩을 건너뜁니다 — 서비스 기동은 계속합니다. 원인: ...`를 error stack log로 남긴다. 활성 트랜잭션이면 rollback-only로 표시해 부분 seed commit을 막는다.

근거: 누락 product 테스트가 예외를 호출자에게 전파하지 않고 `save()` 0회를 확인한다. Compose 두 파일은 `docker compose ... config --quiet`로 문법 검증했다(재배포하지 않음).

### 결함 4 — 복사·revision 복원 생성 사각지대

이번 라운드에서는 범위를 넓혀 수정하지 않고 정확한 목록을 남긴다. `SlipDuplicateService.duplicate`와 `SlipService.restoreToRevision`은 product 재검증 없는 기존 경로이며, `EstimateSeeder`도 자체 lookup 없이 `SlipSeeder` 순서에 간접 의존한다.

이유: 이번 BLOCKING의 직접 원인은 시딩 선행 검증과 bulk 조회 분류이며, 복사/복원은 기존 데이터와 트랜잭션 경계를 넓히는 별도 변경이다. 잘못된 product UUID 차단을 이미 담당하는 직접 생성·수정 경로와 달리, 해당 경로를 이번 라운드에서 변경하면 별도 회귀 범위와 데이터 보존 검증이 필요하다. 따라서 목록을 남기고 후속 슬라이스 대상으로 분리했다. 잔재 데이터는 삭제·수정하지 않았다.
