## 2. 판정

**도달 결함 1건. R9 재수렴 불통과.**

R8의 원 목표인 DB 제약 실패행 격리와 뒤 정상행 계속 처리는 살아 있다. 그러나 `DataAccessException` 상위 타입 catch가 실제 일시적 JDBC 연결 실패까지 `DB_CONSTRAINT`로 오분류하고, 해당 행을 저장하지 않은 채 HTTP 200을 반환하는 실 관리자 경로가 재현됐다.

사용자가 제시한 “DB 전체 장애 중 7,253행 전부 HELD + 2xx”는 그대로의 형태로는 일반화할 수 없다. DB가 계속 불능이면 catch 직후 `updateStagingStatus(...)`도 실패해 2xx까지 도달하지 못한다. 실제 도달한 제3 경로는 다음이다.

> 행 트랜잭션의 특정 JDBC 연결이 일시적으로 끊김 → `JpaSystemException`(`DataAccessException`) → 해당 행은 `PENDING + DB_CONSTRAINT` → 다음 staging 연결은 정상 → HTTP 200.

응답에 `heldParseFailureRows`와 `heldSample`은 있으므로 실패 정보 자체가 사라지지는 않는다. 결함은 인프라 장애를 데이터 제약으로 거짓 분류하고 성공 상태코드로 반환해 재시도 대상 판단을 깨뜨리는 것이다.

| 각도 | 판정 |
|---|---|
| 1. 예외 분류 범위 | **FAIL** — 일시적 JDBC 연결 실패가 `DB_CONSTRAINT` HELD + HTTP 200 |
| 2. 3행 원 동작 | PASS — 앞/뒤 정상 저장, 201자 실패행 미저장, HTTP 200과 held 목록 |
| 3. 앞 라운드 불변 | PASS — UUID 동일, 7,253 분포·NULL·등록일 교정 불변 |
| 4. 고친 파일 재업로드 | PASS — 새 파일 행 IMPORTED, partner 활성 1; 옛 source hash PENDING은 이력으로 존치 |

## 3. 각도 1 — `DataAccessException` 범위

### 3.1 실 관리자 발화

정본 거래처 `01`의 행을 `SELECT ... FOR UPDATE`로 잠그고, 실 관리자 CSV가 거래처명을 변경해 실제 UPDATE 잠금 대기에 들어간 것을 `pg_blocking_pids()`로 확인했다. 그 뒤 차단된 **요청 JDBC PID만** `pg_terminate_backend`로 종료했다. fixture 데이터는 관리자 API만 사용했고 SQL 데이터 INSERT/UPDATE는 없었다.

```sql
BEGIN;
SELECT id FROM partners WHERE partner_code='01' FOR UPDATE;
SELECT pg_sleep(300);

SELECT pid::text
  FROM pg_stat_activity
 WHERE datname='partner_r9'
   AND application_name='PostgreSQL JDBC Driver'
   AND cardinality(pg_blocking_pids(pid)) > 0
 ORDER BY pid LIMIT 1;

SELECT pg_terminate_backend(119::int)::text;
```

```text
blockedPid=119
terminated=true
```

## 5. 각도 3 — 앞 라운드 불변

금지 코드가 아닌 정본 거래처 `0004`를 사용했다. 실 API로 배송지 생성 → 관리자 DELETE → 같은 정본 XLSX 재적재 → 배송지 실 API 삭제 순서다.

```text

DELETE /admin/partners/0004 -> HTTP 200
정본 재적재 -> HTTP 200, updated=7253
```

```sql
SELECT p.id::text,
       '3442cf20-d5b6-4c7b-8d35-b8e4a591999d',
       count(*) FILTER (WHERE p.is_deleted=false),
       count(*) FILTER (WHERE p.is_deleted=true),
       (SELECT count(*)
          FROM partner_shipping_addresses a
         WHERE a.id='be7e9ffa-398d-4c41-b839-5ca25d5adceb'
           AND a.partner_id<>p.id)
  FROM partners p
 WHERE p.partner_code='0004'
 GROUP BY p.id;
```

## 6. 각도 4 — 실패행을 고친 파일 재업로드

`SOL1154R9BAD`의 201자 이름을 `R9 고친 실패행`으로 줄인 새 CSV를 같은 실 관리자 API로 업로드했다.

```json
{
  "totalRows": 1,
  "imported": 1,
  "updated": 0,
  "activeCount": 1,
  "heldParseFailureRows": 0,
  "heldSample": []
}
```

```sql
SELECT transform_status,coalesce(reject_reason,''),target_partner_id IS NOT NULL
  FROM staging.ecount_partner_raw
 WHERE raw_partner_code='SOL1154R9BAD'
 ORDER BY transform_status;

SELECT count(*)
  FROM partners
 WHERE partner_code='SOL1154R9BAD' AND is_deleted=false;
```

```text
IMPORTED||true
PENDING|DB_CONSTRAINT|false
active=1
```

고친 새 파일의 source hash 행은 `IMPORTED`이고 partner도 정상 생성된다. 이전 실패 파일의 별도 source hash 행은 감사 이력으로 `PENDING + DB_CONSTRAINT`에 남지만 사용자의 수정·재적재를 막지 않는다. “고칠 길이 없이 영원히 PENDING” 결함은 재현되지 않았다.
