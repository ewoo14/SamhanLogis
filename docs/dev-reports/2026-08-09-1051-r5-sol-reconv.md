## ① 실 업무 전표가 하나도 안 잠기는가

공유 DB 2026-08-09 08:04:53 KST 기준 활성 lock은 **5건 전수**다.

| 전표번호 | 유형 | created_by | 생성 시각(KST) | 현재 lock | 시더 근거 |
|---|---|---|---|---:|---|
| `2026/02/15-1` | OUTBOUND | system | 2026-05-09 16:59:33.553366 | true | idx 45, CONFIRMED |
| `2026/02/16-1` | OUTBOUND | system | 2026-05-09 16:59:33.558451 | true | idx 46, CONFIRMED |
| `2026/02/17-1` | OUTBOUND | system | 2026-05-09 16:59:33.563664 | true | idx 47, CONFIRMED |
| `2026/02/18-1` | OUTBOUND | system | 2026-05-09 16:59:33.569431 | true | idx 48, CONFIRMED |
| `2026/04/08-1` | INBOUND | system | 2026-05-09 16:59:33.881534 | true | idx 97, CONFIRMED |

현재 잠긴 실 업무 전표는 **0건**이다. 다섯 행의 생성 시각은 전체 Stage 2 시드 100건이 생성된 2026-05-09 16:59:33.195242~16:59:33.901047 KST의 0.706초 묶음 안에 있고, 전표번호·유형도 `SlipSeeder`의 100개 결정 키와 일치한다.

R4의 추가 후보였던 `2026/03/08-1`, `2026/03/09-1`은 둘 다 `created_by=system`, CONFIRMED지만 lock=false 그대로다. R5 번호 집합에는 없다.

단, 이번 R5 재기동에서 새로 잠긴 행은 0건이고 runner 자체도 완료하지 못했다. 위 5건은 R5 실행 결과가 아니라 기존 2026-07-05 lock 상태다.

## ② 잠겨야 할 5건이 여전히 잠기는가

공유 DB 현재 상태로는 **5/5가 여전히 잠겨 있다**. 전후 snapshot에서 다섯 행의 `lock_flag`, `modified_at` 모두 불변이다.

그러나 fresh 환경에서 R5가 5건을 새로 잠그는 라이브 실행은 R5-SOL-1/2 때문에 관측하지 못했다. 단위 테스트는 OUTBOUND 4 + INBOUND 1을 반환하도록 mock한 뒤 5회 `lock()`을 확인하지만, 실제 runner 완료 증거를 대신하지 않는다.

## ③ 재기동해도 늘지 않는가

실제 측정값은 다음과 같다.

| 시각(KST) | 조건 | 활성 lock | 미잠금 system CONFIRMED |
|---|---|---:|---:|
| 08:02:57.913336 | R5 재기동 전 | 5 | 2 |
| 08:04:19.731105 | 직접 속성 재기동 직전 | 5 | 2 |
| 08:04:53.417031 | 직접 속성 재기동 후 | 5 | 2 |

수치는 **5 → 5, 증가 0건**이다. 하지만 첫 재기동은 runner 미활성, 둘째는 선행 시더 실패로 `SlipLockSeeder`가 skip했으므로 “R5 repository의 `lock_flag=false` 멱등성이 실 재기동에서 작동했다”는 관측은 아니다. 그 항목은 **관측 불가**다.

## ④ `created_by=system`이 정말 시더를 가르는가

2026-08-09 08:05:17 KST read-only 전수:

- 활성 `created_by=system`: **100건**
- `SlipSeeder` 결정 키와 일치: **100건**
- 결정 키 밖 `created_by=system`: **0건**
- 생성 시각 범위: 2026-05-09 16:59:33.195242~16:59:33.901047 KST

따라서 현재 공유 DB에는 `created_by=system`인 실 업무 전표가 **0건**이다. 다만 `system` 자체는 감사 fallback 값이라 일반적인 영구 provenance 표식은 아니다. R5는 이를 단독으로 쓰지 않고 유형+정확한 번호+상태와 교집합한다.

## ⑤ 번호 집합은 하드코딩인가 파생인가

현재 구현은 **파생**이다. `confirmedSeedSlipNosByType()`는 `buildSpecs()`, `computeSlipDate()`, `formatSlipNo()`를 재사용하고 실제 삽입과 같은 유형·날짜별 sequence 계산을 수행한다. 따라서 spec, 날짜 계산, 공용 formatter가 바뀌면 대상도 따라간다.

다만 삽입 loop와 lock용 loop가 별도 복제되어 있어 구조적으로 완전한 단일 산출물은 아니다. 향후 실제 삽입부의 sequence 규칙만 변경하고 helper를 같이 바꾸지 않으면 조용히 0건이 될 수 있다. 현재 테스트도 기대 번호 5개를 하드코딩해 repository 호출만 검증하므로 “실제 삽입 결과와 helper 결과의 동일성”을 검증하지 않는다. 현재 코드의 실제 불일치는 발견하지 못했으며, 이 항목은 잠재 drift 표면으로만 목록화한다.

### 취소/반려 원문

실제 R5 slip-service에서 잠긴 `2026/02/15-1`에 호출했다.

```text
POST /slips/{id}/cancel
HTTP 409
{"success":false,"code":"CONFLICT","message":"취소 가능한 상태가 아닙니다: 확정",...}

POST /slips/{id}/reject
HTTP 409
{"success":false,"code":"CONFLICT","message":"반려 가능한 상태가 아닙니다: 확정",...}
```

둘 다 409지만 **lock 가드 원문이 아니라 CONFIRMED 상태 가드**다. `reject()`와 `cancel()`이 상태를 먼저 검사하고 `requireNotLocked()`를 나중에 호출하며, 다섯 fixture가 모두 CONFIRMED라 lock으로 인한 409를 이 데이터로 분리 관측할 수 없다. 요청은 상태 전이 전에 끝나 DB 쓰기가 없었다.
