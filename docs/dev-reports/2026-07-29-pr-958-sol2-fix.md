# PR #958 S2 재수렴 2차 fix 개발 보고서

## 결론

- M-1: 수량 규칙 CRUD와 모든 BUNDLE 구성품 graph mutation이 같은 PostgreSQL advisory lock을 사용한다.
- M-2: `syncTab`/`syncComponentTab`은 외부 Sheets 응답을 기다리는 동안 lock을 점유하지 않고, 짧은 generation 예약과 mutation 직전 최신성 확인으로 늦은 응답의 overwrite를 막는다.
- M-3: 구성품 tab은 규칙 충돌 확인을 통과한 뒤에만 부모 BUNDLE 표식·자식 부모 표식·link를 같은 transaction에서 저장한다.
- M-4: R6 fixture 25건은 product/rule 상태를 실 HTTP API로 생성하며 SQL은 검증 조회와 cleanup에만 사용한다.
- M-5: `HOME_MULTI` 외에 `SINGLE_SET`, `COMM_MULTI`, `COMMERCIAL_MULTI` alias를 실 API 경로로 검증한다.
- 공유 `product_db`에는 write하지 않았다. 모든 통합테스트는 Testcontainers의 throwaway PostgreSQL을 사용했고, 최종 실행 후 해당 container/Ryuk가 제거된 것을 확인했다.

## 2. 생산 코드 변경

### 2.1 공통 graph lock

`BundleComponentService`의 replace/add/patch/remove/child-removal/display-order mutation 시작부에
`QuantitySyncRuleService.lockGraphMutation()`을 추가했다. 규칙 create/replace/delete가 이미 사용하던 lock key를 그대로 공유한다.

### 2.2 응답 순서 token

V25 `product_sheet_sync_generation`을 추가하고, `reserveSheetSyncGeneration()`이 동일 `sheetId + scope`의 generation을 unique-key UPSERT으로 증가시키도록 했다. 예약은 `REQUIRES_NEW` 짧은 transaction으로 외부 HTTP 전에 commit한다. generation row 자체의 UPSERT가 같은 scope의 예약을 직렬화하므로 graph lock을 예약 transaction까지 확장하지 않았다.

Sheets read/formula read 뒤 실제 mutation 직전에 graph lock을 얻고 generation을 재확인한다. stale이면 아무 DB mutation도 하지 않고 반환한다. 따라서 외부 HTTP 대기 중 일반 편집은 graph lock을 기다리지 않는다.

### 2.3 component partial state

`syncComponentTab`에서 활성 규칙 충돌 검사를 부모/자식/link 저장보다 먼저 실행하도록 순서를 바꿨다. 충돌 row는 BUNDLE 표식과 `parentBundleSetModel`을 남기지 않는다.
