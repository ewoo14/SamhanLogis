### 확인 6 — 35품목의 `—` 표현은 소스 경로상 보존되나 실행 화면에서는 미검증

### 결함 A2 — 창고원에게 판매금액·이익률 권한이 확대됨 (BLOCK)

신규 FE 라우트와 메뉴, BE endpoint가 모두 기존 `inventory.stock-balance` VIEW를 재사용한다. 실 권한 DB에서 창고원 그룹은 재고 현황과 구매전표 조회는 허용되지만 판매전표 조회는 거부된다.

```text

창고원   true                     true                 false            1
```

### 결함 A4 — 실 판매 40품목이 product lookup에서 0건 반환되어 API가 전부 실패함 (BLOCK)

신규 서비스는 집계 전에 모든 전표 품목을 `product-service /products/internal/lookup`으로 조회한다. 이 클라이언트는 반환 개수가 요청보다 적으면 예외를 던지므로 fallback 행 생성까지 도달하지 않는다. 실행 중 product-service에 실 판매 40품목을 읽기 전용 batch lookup한 결과는 다음과 같다.

```text
requested=40 HTTP=200 returned=0
```

- ① 실 사용자 경로 재현 여부: 실행 중 실 product-service와 실 slip DB의 40개 판매 품목 연결 경로에서 재현. 신규 slip endpoint 배포 여부와 무관하게 현재 구현은 `lookupProducts()`에서 중단된다.
- ② 재현 명령·출력 원문: 실 slip DB에서 확정 판매 품목 식별자를 메모리로만 읽고, `POST /products/internal/lookup` 조회 API에 전달했다. 출력 원문은 `requested=40 HTTP=200 returned=0`이다. 식별자는 저장·보고하지 않았다.
- ③ 실 데이터 영향 건수: 확정 판매 **40/40품목 전부** 응답 불가. 원가 없는 35품목과 산정 가능 5품목 모두 화면에서 사라진다.
- 판정: **BLOCK**. 개발책임자 결정의 핵심인 “원가 없는 35품목을 남기고 `—` 표시” 경로가 실 데이터에서 아예 도달하지 않는다.

### 결함 A5 — 실 판매 40품목은 모든 칩에서 0건으로 분류됨

실 product lookup이 0건이어서 `categoryKey`를 얻지 못하고, 전표의 실 품목명에도 `실외기/실내기/판넬/패널` 문자열이 없다. FE의 실제 칩 판정식을 실 판매 40품목에 적용한 결과다.

```text
칩 분류 결과: 미분류 40건
실외기 0, 실내기 0, 홈멀티 0, 싱글중대형 0, 상업멀티 0, 판넬 0
```

- ① 실 사용자 경로 재현 여부: API는 A4에서 실패하므로 실행 화면의 칩 클릭까지는 도달 불가. 실 DB 응답 후보 내용에 FE 판정식을 적용하는 데이터 경로에서는 재현.
- ② 재현 명령·출력 원문: `slip_db` 확정 판매 40품목을 `BEGIN READ ONLY`로 집계하고, FE와 동일한 품목명 포함 규칙으로 분류 → `미분류 | 40` 한 행만 출력.
- ③ 실 데이터 영향 건수: 40/40품목. 어떤 칩 하나를 선택해도 결과 0건이며, 전부 해제하면 소스상 전체 40건으로 돌아오지만 실제 API 실패 때문에 실행 화면에서는 전체 복원도 확인 불가.
- 판정: 칩이 “실제로 결과를 거르는” 대신 실 데이터 전체를 미분류로 탈락시킨다. A4 해소 후에도 상품 정본 연결 또는 모델코드 기반 분류가 해결되지 않으면 칩 기능은 실사용 불가다.

### 확인 8 — 분석 모델 4/4 및 desktop typecheck 재현

```text
명령: npm run test -- --run src/renderer/routes/warehouse/inoutAnalysisModel.test.ts
Test Files  1 passed (1)
Tests       4 passed (4)
Exit code: 0

명령: npm run typecheck
typecheck:real-qa tests 2 pass 2 fail 0
real-QA scope tests 50 pass 50 fail 0
Exit code: 0
```

- 실 데이터 영향 건수: 0건. 4/4는 `MODEL-COST-MISSING`과 100/125 합성 사례이므로 실 DB 40품목에 대한 A1·A4·A5 판정을 뒤집지 않는다.
- 판정: 숫자 주장 중 “분석 모델 테스트 4/4”, “desktop typecheck exit 0”은 재현됨.

### 확인 9 — 전량 원가 충족 4/부분 충족 1 재현

```text
 overlap_products | full_cost_products | partial_cost_products
------------------+--------------------+-----------------------
                5 |                  4 |                     1
(1 row)
```

- 재현 명령: 확정 입고·판매를 품목별 수량 합계로 묶어 `입고수량 >= 판매수량`을 전량 원가 충족으로 판정한 `BEGIN READ ONLY` SQL.
- 실 데이터 영향 건수: 산정 가능 5품목 중 전량 원가 충족 4, 부분 충족 1.
- 판정: `확정 판매 40 · 입고 없음 35 · 산정 가능 5 (전량 원가 충족 4)` 수치 자체는 모두 재현됨.

## 최종 판정

**BLOCK**

1. A4: 실 판매 품목 40건을 product-service에서 0건 반환하여 신규 API가 실 데이터에서 전량 실패한다.
2. A1: 그 연결을 우회한다고 가정해도 산정 가능 5품목의 이익률이 5/5 모두 실 단가 이익률과 다르다.
3. A2: 현행 판매전표 권한이 없는 창고원 실계정 1명에게 판매금액·이익률이 확대된다.
4. A5: 실 판매 40품목이 모든 칩에서 미분류되어 칩 선택 결과가 전부 0건이다.

비차단 도달성 관측: 기존 재고·판매전표·구매전표 API는 각각 200으로 유지됐고, 신규 라우트 문자열 충돌은 없다. 다만 신규 경로가 창고 운영 메뉴 자동 펼침 대상에서 누락됐다.

## 이 라운드가 보지 않은 축

- 공유 Docker를 재빌드·재기동한 뒤의 신규 endpoint 및 실제 렌더러 화면: 금지사항 때문에 미확인.
- 0/음수 매입가, 실제 손실, 복수 입고가의 사용자 화면: 현재 실 DB 도달 건수가 모두 0이라 미확인.
- 모바일·웹 등 데스크톱 외 클라이언트: 이번 변경 표면과 요청 범위 밖이라 미확인.
- 구매예측 및 검증 품질 평가는 요청에 따라 보지 않음.
