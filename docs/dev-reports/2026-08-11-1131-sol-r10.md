# PR #1131 · SOL R10 검토 — 판매전표 세트 인스턴스 계보

## 판정

**최종 판정: 결함 0.** 1차 검토에서 BLOCKING 1건을 발견했고, 아래 지시서에 따라 LUNA가
TDD로 수정한 뒤 SOL이 코드·테스트·격리 DB·실 Desktop 화면을 독립 재검토했다. 발견 결함은
닫혔으며, 이 라운드가 실제로 본 표면에서 사용자가 밟을 수 있는 잔존 결함은 없다.

1차 결함은 다음과 같았다. V119 자체는 승인된 실 전표 한 건을 정확히 이관하지만,
정상 Desktop 견적 생성 경로가 같은 모델의 다중 세트를 다시 `instanceKey` 없이 저장한다.
따라서 이관만으로는 사용자 결함이 닫히지 않는다.

정상 화면에서 `AC060CS6PBH1SY`를 두 번 담아 견적을 저장하고 판매전표로 전환한 결과는
`8행 · head 2 · instanceKey 0`이었다. 변환 전표의 첫 head 수량을 `1 → 2`로 저장하면
HTTP 400, `세트 head 구성품은 삭제할 수 없습니다`로 실패했다.

LUNA 수정 후 같은 화면 흐름은 keyless 요청을 보내더라도 서버 영속 결과가 `key 2`가 되고,
변환 전표의 첫 head 수량 2 저장이 HTTP 200이어서 이 결함은 닫혔다.

## 1. 공유 DB 읽기 전용 실측

공유 `slip_db`에는 `SELECT`만 실행했다. QA797·QA-1039 표본은 수정하거나 결함으로 세지 않았다.

### V119 WHERE 대상

```text
v119_where_rows=8|heads=2|products=4
target_all_rows=8|heads=2|products=4|keys=0
active_keyless_multi_instance_groups=1
```

- 전표: `2026/08/07-20`, `DRAFT`, OUTBOUND
- slip id: `fe0a9968-0a0f-4fef-b0fd-f5671d261434`
- parent: `AC060CS6PBH1SY`
- 생성 시각/주체: `2026-08-07 17:30:35` 전후,
  `a0000000-0000-0000-0000-000000000003`
- V119에 명시된 8개 line id가 실제 8행과 전부 일치했다.
- 제품은 `AC060CN6PBH1`, `AC060CXAPBH1`, `PC6NUNK1NW`, `AR-EH05` 4종이며
  동일 4행 인스턴스가 두 번 있다.

현재 공유 DB에는 아직 V119가 배포되지 않았으므로 대상은 여전히 keyless다. 공유 DB를
`pg_dump`로 복제한 격리 PostgreSQL에 현재 branch jar를 기동했을 때 Flyway가 V119를
118→119로 적용했고, 대상은 `8행 · head 2 · instanceKey 2종`이 됐다.

### 금액 불변

이관 전 공유 DB와 이관 후 격리 DB의 대상 전표 금액은 동일했다.

```text
전표 전체: 12행 | 공급가 4,729,797 | VAT 472,980
대상 세트:  8행 | 공급가 3,018,182 | VAT 301,818
```

V119는 `bundle_set_options` JSONB의 `instanceKey`만 갱신하며 수량·단가·금액 열은
변경하지 않는다. 이관 후 실제 API 응답의 전표 공급가도 `4,729,797`이었다.

### 견적 잔존 데이터

공유 DB의 활성 견적 중 같은 `(estimate, parentSetModel)`에 head가 2개 이상이고 키가
0개인 그룹은 현재 **0건**이었다. 이번 재현 데이터는 격리 DB에만 작성했다.

### 이관 대상 편집 계약

격리 복사본을 각각 새 전표로 복제해 독립 검증했다.

| 표적 | 결과 |
|---|---|
| 첫 head 수량 `1 → 2` | HTTP 200, 8행·head 2·key 2, 수량 2 보존 |
| 비-head 구성품 1행 삭제 | HTTP 200, 대상 세트 7행·head 2 |
| 첫 인스턴스 4행 전체 삭제 | HTTP 200, 대상 세트 4행·head 1·key 1 |
| 기존 head 수량 `0` | HTTP 422 `SLIP_UPDATE_INVALID_LINE` — 명시 거부 계약 유지 |

수량 0의 422는 R5/R9가 고정한 정상 계약이다. 수량 0을 조용한 행 삭제로 바꾸지 않았고,
비-head 삭제와 인스턴스 전체 삭제는 실제 저장됐다.

### 미래 keyless 재생성 — 결함 재현

## 4. R9 인용 수치 재현 여부

- `active_keyless_multi_instance_groups 1 → 0`: 공유 DB 1, V119 적용 격리 DB 0으로 재현.
- 이관 후 `HTTP 200 · 8행 · head 2 · instanceKey 2종 · 첫 head 수량 2`: 전부 재현.
- 이관 전 원 대상의 `repository.saveAndFlush=0`: 공유 DB 읽기 전용 제약 때문에 원 대상을
  PUT하여 계측하지 않았다. 대신 정상 화면이 새로 만든 동형 전표에서 HTTP 400과 같은 도메인
  문구를 재현했다. R9의 save 호출 횟수 **0은 R10에서 독립 재계측하지 않은 수치**다.

## 6. LUNA 수정 지시서

### 불변식

1. 서버가 BUNDLE 부모 한 행을 N개 구성품으로 전개해 영속할 때, 그 N개는 비어 있지 않은
   **동일 `instanceKey` 1개**를 가져야 한다.
2. 같은 문서에서 동일 BUNDLE 부모를 두 번 전개하면 서로 다른 키 2개가 생겨야 한다.
3. 요청에 명시적 키가 있으면 공백이 아닌 한 그대로 보존한다.
4. 일반 품목과 이미 명시 키가 있는 현재 Desktop 직접 전표 생성·수정 계약은 바꾸지 않는다.
5. 키 보강은 금액·수량·구성품 선택·product-service expand 요청 옵션을 바꾸지 않는다.
6. revision 복원과 converter는 저장된 키를 그대로 보존한다.

### 설계

권장안은 서버의 **BUNDLE 전개 경계에서 한 번만** 키를 보강하는 공통 정책이다.
`BundleSetOptions`가 null 또는 `instanceKey` null/blank이면 기존 5개 옵션 값을 그대로 둔 채
새 키를 만든다. 그 보강 결과 하나를 해당 전개의 모든 구성품에 기록한다. product-service에
보내는 `ExpandedLineDto.Options`는 기존 요청 옵션에서 계속 계산하여 null/default 동작을 바꾸지 않는다.

- 적용 필수: `EstimateService` BUNDLE 전개, `SlipService` BUNDLE 전개,
  `MobileQuotationService` BUNDLE 전개.
- 적용 금지: `SlipService:190`의 이미 전개된 개별 구성품마다 서로 다른 키를 만드는 방식.
  평면 요청은 현재 Desktop이 동일 키를 이미 보내므로 그대로 보존한다.
- converter·snapshot restore는 생성기가 아니라 보존 경계이므로 임의 재키잉하지 않는다.
- FE 한 곳만 고치는 안은 모바일/API 유입을 남기므로 채택하지 않는다.
- 도메인 `assignBundleComponent` 안에서 매 호출마다 키를 만드는 안은 한 인스턴스의 구성품마다
  키가 달라지므로 채택하지 않는다.

이 설계는 사용자가 “결함이면 지시서 작성 뒤 LUNA 수정”을 명시해 사전 승인한 범위다.
별도 기능·스키마·이관을 추가하지 않는다.

### RED-A

정상 Desktop 견적 생성과 같은 서버 호출을 고정한다.

```text
동일 AC060CS6PBH1SY BUNDLE 부모 요청 2개
→ 견적 8행, head 2
→ instanceKey 2개
→ 각 key마다 4행·head 1
→ 전표 변환 후에도 같은 key 2개
→ 첫 head 수량 2 저장 HTTP 200, 8행 유지
```

현재 RED는 견적/변환 전표 모두 `keys=0`, 수정 HTTP 400이다. 테스트는 production 변경 전에
작성하고 이 이유로 실패하는 것을 확인한 뒤 최소 구현한다.

### RED-B — 구체 반대 표적

1. 명시 키 `client-key-1`로 BUNDLE 하나를 전개하면 모든 구성품이 정확히 그 키를 보존한다.
2. null 옵션 BUNDLE 하나를 전개해도 product-service expand 호출의 옵션 인자는 기존처럼 null이고,
   저장된 구성품만 같은 새 키 1개를 가진다.
3. 일반 SINGLE 한 행은 `parentSetModel=null`, `bundleSetOptions=null`을 유지한다.
4. 이미 명시 키가 있는 동일 세트 2인스턴스에서 비-head 1행 삭제는 200, 첫 인스턴스 전체 삭제는
   200, head만 삭제하고 자식을 남기면 400, 수량 0은 422를 유지한다.
5. V119 대상은 `8행·head 2·key 2·공급가 4,729,797`을 유지하고 첫 head 수량 2 저장은 200이다.

### 수정이 만드는 새 조합

- 진입: Desktop 견적 / 모바일 견적 / 직접 판매·구매전표 API.
- 요청 옵션: null / 옵션 객체+키 null / 키 blank / 명시 키.
- 인스턴스: 동일 부모 1개 / 동일 부모 2개 / 서로 다른 부모 2개.
- 구성: 1개 구성품 / 4개 구성품 / 일부 productId 누락으로 기존 rollback.
- 후속: 견적 update / 견적→전표 convert / 전표 양수 수정 / 비-head 삭제 / 인스턴스 전체 삭제 /
  head 고아화 거부 / 수량 0 거부 / revision restore.

**제 전제가 틀렸다면 고치지 말고 중단·보고하십시오.** 특히 현재 Desktop 견적 payload가
실제로 키를 보내거나, `EstimateService`가 영속 전에 다른 좌표에서 키를 만든다는 증거가 나오면
위 수정은 진행하지 말고 그 원문을 보고한다.

## 8. LUNA 수정과 SOL 독립 재검토

### 수정

- 신규 `BundleSetInstanceKeyPolicy`는 명시 non-blank 키를 원문 그대로 보존한다.
- null/blank 키만 기존 5개 옵션을 보존한 UUID 키로 보강한다.
- `EstimateService`, `SlipService`, `MobileQuotationService`의 BUNDLE 전개 루프 밖에서
  전개당 한 번 호출하므로 한 인스턴스의 모든 구성품이 같은 키를 가진다.
- 이미 전개된 평면 구성품, converter, revision restore production 경로는 재키잉하지 않았다.
- product-service expand 옵션은 보강 전 요청 옵션에서 계속 계산한다.

LUNA RED 원문은 `7 tests completed, 4 failed`였다. 기대 실패는 견적의 키 집합이
`{"null"=[...]}` 한 그룹뿐인 점, blank 키가 보존된 점, 직접 전표·모바일 전개의
`setOptions=null`이었다. production 수정 후 LUNA와 SOL이 각각 fresh 회귀를 실행했다.

## 9. 최종 이 라운드가 보지 않은 표면

- 배포 backend #1134에는 V119와 LUNA 수정이 없으므로 **실배포 후 동작은 보지 않았다**.
- 공유 DB에는 SELECT만 했으므로 **실 공유 DB에서 V119 적용 및 원 전표 PUT은 보지 않았다**.
- Vite+headless Chromium으로 Desktop renderer를 봤으며 **패키징된 Electron 설치본·자동 updater
  bridge는 보지 않았다**.
- MobileQuotationService의 실제 서버 경계와 회귀 테스트는 봤지만 **모바일 실기기 화면은 보지 않았다**.
- 현재 Desktop 직접 전표 화면은 명시 키 생성 source와 기존 편집 E2E를 봤지만, **구버전 Desktop
  클라이언트가 이미 전개된 평면 keyless 구성품을 POST하는 호환 실행은 보지 않았다**.
- 동시 다중 사용자 협업 편집, 구매전표 화면, revision 복원 화면은 이 R10의 실제 화면 표적이
  아니어서 별도 E2E로 실행하지 않았다. 관련 기존 단위 회귀만 통과했다.
