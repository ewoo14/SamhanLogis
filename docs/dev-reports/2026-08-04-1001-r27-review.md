## 도달 가능한 결함

### 결함 1 — `현재 원장 저장`이 화면의 현재 원장이 아니라 구형 분개 원장을 저장한다

- 재현 경로: `회계 → 거래처 원장` → 기간 `2026-01-01 ~ 2026-03-31` 조회 → `(주)서울에어컨` 원장 보기 → 현재 1행 원장을 확인 → `현재 원장 저장` 클릭 → 새 이력의 `행 수`가 3으로 표시됨 → `복원` 클릭 시 저장된 3행 분개 원장이 현재 1행 화면을 대체한다.
- R12 실 GUI 산출물 자체가 재현 증거다. `08-history-before-save.png`에는 현재 상세가 `P-2026-0001` 1행이고 이력이 비어 있다. `09-history-after-save.png`에는 같은 상세 1행이 그대로인데 새 batch `LED20260804074502997`의 `행 수`가 **3**으로 표시된다.
- 원인 호출 경로: 현재 화면은 `getLedgerData` → `GET /accounting/journals/partner-ledger` → `PartnerLedgerReadService`의 출고 판매전표+입금보고서 read model을 사용한다. 저장은 `captureLedger` → `POST /accounting/journals/ledger-snapshots` → `LedgerSnapshotService.capture` → **별도 `LedgerImageService`의 회계 분개 line 재계산**을 저장한다. 두 산출기는 같은 거래처·기간만 공유하고 내용은 공유하지 않는다.
- 사용자 영향: 버튼 이름과 배치 위치가 약속하는 “지금 화면에 보이는 원장 보존”이 성립하지 않는다. 저장 성공과 건수 `+1`은 맞아도 snapshot 내용이 다르며, 복원하면 사용자가 저장했다고 본 원장이 아닌 다른 원장이 나타난다.

## 증거 무결성 정정

### R26 보고서 정정

R26 원문은 다음과 같다.

> “`LedgerSnapshotService.capture`는 `ledgerImageService.getLedger(...)` 결과를 … 저장한다. 즉 저장 대상은 조회 당시의 원장 결과”

이 문장은 실제 GUI 조회 결과를 가리키는 것으로 읽히지만 코드상 사실과 다르다. GUI 조회 결과는 `PartnerLedgerReadService` 산출물이고, capture가 저장하는 것은 독립 `LedgerImageService` 산출물이다. R26이 제시한 `Tests 8 passed`와 `BUILD SUCCESSFUL`은 호출·repository save를 확인할 뿐 두 산출물의 동일성을 입증하지 않는다. 같은 보고서도 “이번 세션에 실제 POST/DB 쓰기는 수행하지 않았다”고 명시하므로, R26의 `조작 → 건수 +1` 표현은 그 세션의 실측이 아니라 호출 그래프에 대한 추론이었다.

### R12 라이브QA 보고서 정정

R12 원문은 다음과 같다.

> “저장 전: **12건** … 현재 원장 저장 1회 … 저장 후: **13건**”
>
> “R26 저장 경로 관련 새 결함: **없음**.”

`12→13` 자체는 저장 호출과 새 batch 생성을 입증하지만 저장 내용의 정합성을 입증하지 않는다. 오히려 R12의 `08-history-before-save.png`와 `09-history-after-save.png`를 직접 대조하면 현재 화면은 1행인데 새 snapshot 이력은 3행이다. 따라서 “새 결함 없음”과 이를 근거로 한 “머지 가능” 결론은 정정돼야 한다. 조회 3회 후 `13` 유지 및 write 호출 0건은 RED-B와 일치하며, 그 부분은 코드 호출 그래프와 모순되지 않는다.

R12 산출물 디렉터리를 다시 열어 확인한 결과 11개 PNG만 있고 SQL/네트워크 원문 로그는 남아 있지 않다. Docker·라이브 서버 금지 때문에 `12→13→13` SQL 수치는 이번 라운드에서 독립 재실행하지 않았다. 다만 서로 다른 SHA-256인 전/후 캡처(`08`: `C84F...5FA1`, `09`: `6712...DB24`)와 현 HEAD의 POST→repository save 호출 경로가 신규 batch 생성을 뒷받침하며, 같은 캡처가 내용 불일치까지 직접 드러낸다.

## 최종 판정

유일한 질문 “실 사용자가 GUI로 밟을 수 있는 경로에서 재현되는 결함이 있는가?”에 대한 답은 **예, 1건**이다.

- **RED-A: FAIL.** `현재 원장 저장`은 실제로 새 batch를 저장하지만, 사용자가 보고 있던 `PartnerLedgerReadService` 원장이 아니라 독립 `LedgerImageService` 분개 원장을 저장한다. R12 GUI 산출물에서 현재 1행 대 새 snapshot 3행으로 이미 재현된다.
- **RED-B: PASS.** 페이지 진입, 필터 적용, 재조회, 이력 조회·복원, 단건·일괄 인쇄 미리보기는 GET/read 경로만 사용한다. snapshot POST의 운영 호출자는 저장 버튼 handler 한 곳이고, 조회 경로에는 repository save가 없다.
- 따라서 `snapshot 12→13`과 `13→13` 카운트는 각각 “쓰기는 있었다”와 “조회 쓰기는 없었다”만 말한다. 저장된 것이 사용자가 본 원장인지까지 확인해야 하며, 그 내용 정합성에서 결함이 재현됐다.
