- 정찰일: 2026-07-31
- 작업 브랜치: `feat/903-template-authoring-s2`
- 기준 HEAD/main/origin-main: `c46a5ccddf56ec8a3c947a19d3bbd37cc3f4d7b5` (세 참조와 merge-base 동일)
- 정찰 범위: PR #998 이후 남은 요구, 두 저작 방식의 현재 실체, #845와의 경계, Excel 라이브러리 현황, 기존 결정 충돌, 후속 슬라이스
- 작업 성격: 읽기 전용 조사 후 본 보고서 1개만 작성

이번 정찰에서는 구현·리팩터링·테스트·의존성 설치를 하지 않았다. Docker 이미지 재빌드, 서비스 재기동, DB 조회·write도 하지 않았다. 따라서 운영 DB의 실제 양식 행 수와 ACTIVE 양식 수는 **확인하지 못함**이다. 기능 존재 여부는 grep 0건만으로 판정하지 않고 실제 타입·API·라우트·편집기·렌더러·마이그레이션 경로를 열어 확인했다.

## 0. 결론

1. PR #998이 넣은 것은 `WORD | EXCEL` 타입, 표시 라벨, `WORD` 기본값, normalize 함수와 테스트뿐이다. 현재 production import는 0건이며 API·DB·선택 UI·편집기 분기·렌더러 분기는 없다.
2. “워드 문서 방식”의 실제 동작에 해당하는 것은 #845가 만든 그룹웨어 결재 문서용 밴드/요소 편집기다. 다만 `WORD` 값으로 선택·저장·dispatch되는 것이 아니라 **모드 없이 암묵적으로 단일 경로**로 동작한다. Microsoft Word `.docx` 저작 경로는 아니다.
3. “엑셀 방식”은 타입과 라벨 외에는 없다. 기존 HTML 표, Excel 다운로드, Apache POI 사용은 모두 셀 그리드 양식 저작 엔진이 아니다.
4. #903은 #845의 대체 에픽이 아니다. 기존 JSONB 저장, DRAFT/ACTIVE lifecycle, append-only revision pin, `DocumentRenderer → PrintLayout`을 재사용하면서 **저작 adapter와 renderer dispatch를 한 축 더 추가**하는 후속이다.
5. 백엔드 Excel I/O 라이브러리는 Apache POI `poi-ooxml:5.4.0`으로 이미 정해져 실제 사용 중이다. 반면 데스크톱/Electron의 셀 그리드 저작 라이브러리는 설치·선정되지 않았다. 즉 “Excel 라이브러리 선정”은 서버 I/O에는 신규 선택이 아니고, 프론트 저작 UI에는 아직 신규 선택이다.
6. 후속 구현은 4개 슬라이스를 권고한다: **S2 mode round-trip → S3 Excel DRAFT 저작 → S4 Excel DRAFT preview → S5 ACTIVE/재인쇄 pin/실인쇄 검증**. 견적서·판매전표 등 문서유형 확장은 #845 R4의 별도 문서유형 슬라이스로 남긴다.

## 4. 기존 문서 양식 엔진 #845와의 관계

#845 원문은 문서 미리보기 대상의 코드 기반 인쇄 양식을 데이터 기반 WYSIWYG로 옮기는 에픽이다. `docs/specs/document-form-designer-epic-design.md:23-26`은 스키마/렌더러/편집기 3계층, `:45-67`은 현 출력 1:1·픽셀 회귀·단계적 문서유형 확장을 결정했다. #845 이슈 본문상 DS-1~DS-4 코드는 머지됐지만 R1~R4 잔여가 있다.

### 4.1 만나는 지점

| 공통 기반 | 현재 근거 | #903이 해야 할 관계 |
|---|---|---|
| 양식 aggregate/lifecycle | V10 `document_templates` JSONB+DRAFT/ACTIVE(`services/groupware-service/src/main/resources/db/migration/V10__add_document_templates.sql:2-29`) | 새 독립 테이블을 만들지 말고 mode를 기존 aggregate에 보존 |
| 승인 재인쇄 | V12 append-only revision+복합 pin(`services/groupware-service/src/main/resources/db/migration/V12__pin_document_template_revisions.sql:10-75`) | mode와 mode별 payload도 같은 revision에 함께 고정 |
| 편집 진입 | `/groupware/document-templates/:id/edit`(`routes/index.tsx:392-403`) | 기존 편집 shell에서 mode별 adapter 선택 |
| renderer compiler | `DocumentRenderer.tsx:601-720` | `PrintLayout` 전에 WORD/EXCEL compiler를 dispatch |
| 인쇄 shell | `PrintLayout.tsx:25-63,99-105,136-139` | paper/no-print/`window.print()` 책임 유지, 저작 방식 선택 책임을 넣지 않음 |
| 권한 | #845 DFD-07은 기본 MASTER/MANAGER, 기존 page-code 재사용(`document-form-designer-epic-design.md:20`) | 별도 #903 전용 권한 체계를 중복 생성하지 않음 |

### 4.2 갈라지는 지점

- #845가 만든 실제 저작 모델은 **밴드/요소**다. #903의 추가 책임은 밴드 엔진을 다시 만드는 것이 아니라 셀 그리드 adapter와 mode dispatch를 추가하는 것이다.
- #845 R3는 구 필드 빌더와 신 문서 편집기 통합이 남아 있다. #903이 별도 입력 필드 빌더를 만들면 R3를 중복 구현한다.
- #845 R4는 거래명세서·판매전표·매입전표·견적서의 문서유형별 데이터 binding adapter 이관이다. #903이 Excel mode를 이유로 이 출력물을 한꺼번에 이관하면 R4를 중복하거나 범위를 침범한다.
- 법정 고정 양식은 자유설계 제외다(`document-form-designer-epic-design.md:21`). 세금계산서 Excel 다운로드가 존재한다는 이유로 세금계산서를 Excel 자유 저작 대상으로 포함하면 기존 결정과 충돌한다.

### 4.3 중복 구현 위험

다음 접근은 중복 구현 위험이 높다.

1. Excel mode 전용 template 테이블과 별도 DRAFT/ACTIVE lifecycle 생성: V10 aggregate와 이중 진실원이 된다.
2. Excel mode 전용 revision/snapshot 생성: V12 승인 시점 pin과 분리되어 재인쇄 외형 불변을 깨뜨릴 수 있다.
3. Excel 전용 인쇄 shell 생성: `PrintLayout`의 no-print, paper, headless 인쇄 계약과 분기되어 레거시 100% 일치 검증이 이원화된다.
4. Excel grid 안에 별도 문서 데이터 조회/필드 정의 시스템 생성: #845 R3/R4의 field/binding adapter를 중복한다.
5. 견적서·판매전표 JSX 이관을 #903 첫 Excel vertical slice에 포함: 저작 방식 추가와 문서유형 확장을 한 PR에 섞어 독립 회귀 판정이 불가능해진다.

### 5.2 프론트/Electron: workbook·grid 라이브러리 미선정

- `clients/desktop/package.json:31-77` dependencies/devDependencies에 `exceljs`, `xlsx`, `@fortune-sheet/react`가 없다.
- 전체 프론트 package manifest/lock과 `clients/**` 제품 import를 다시 검색한 결과 `exceljs|fortune-sheet|sheetjs|"xlsx"` 및 해당 import는 0건이었다.
- 현재 데스크톱은 `excelExportApi.ts:123-213`에서 서버 Blob만 수신한다. 브라우저 workbook library가 필요하지 않은 경로다.
- PR #998 정찰이 ExcelJS, SheetJS CE, FortuneSheet를 후보로 비교했지만 설치·선택 결정은 아니며 `DECISIONS.md`에도 선정 기록이 없다.

판정:

- **백엔드 parse/export**: Apache POI 5.4.0으로 이미 정해진 문제.
- **프론트 셀 그리드 저작 UI**: 새로 골라야 하는 문제.
- **프론트 XLSX I/O**: XLSX round-trip이 #903 범위인지부터 확인해야 하므로 현재는 선정 문제인지도 확정되지 않음.
- 후보 선정 시 최소 실측 항목은 라이선스, production bundle 증가량, Electron 33/React 18 호환, 키보드/한글 IME/접근성, 병합·행열 크기, 데이터 binding adapter 가능성, A4 page break/print fidelity다. 기존 보고서의 후보 설명만으로 선택 완료라고 보면 안 된다.

### 6.2 충돌·gap — 임의 결정하지 않음

#### A. 판매전표 기준 view와 88mm 정책

- 2026-06-14 memory는 입고/출고 전표를 `OutboundView`로 통일하고 A4 기본+88mm 토글로 기록한다(`project_print_preview_standardization.md:8-14`).
- 2026-06-22의 더 늦은 memory는 판매전표 출력의 단일 양식을 `DispatchView`로 확정하고 `OutboundView`를 폐기했다고 기록한다(`project_sales_slip_naming.md:3-10`).
- 현재 실제 route는 `/sales/:id/print/dispatch`→`DispatchView`(`routes/index.tsx:83,556`)이고 `git ls-files '*OutboundView.tsx'`는 0건이다. 즉 view 선택은 현재 코드와 후자 memory가 일치한다.
- 그러나 `PrintLayout`의 `receipt-88mm`와 toggle props/CSS는 남아 있고(`PrintLayout.tsx:25-31,56-63,136-139`, `global.css:3139,5396`), 제품 호출자는 확인되지 않았다. 후자 memory는 88mm를 명시적으로 폐기했다고 적지 않는다.

**판정**: `DispatchView` 단일화는 현 코드로 확인되지만, 판매전표/입고전표의 88mm 요구가 의도 폐기인지 미완 이관인지 **확인하지 못함**이다. #903 mode와 paper 토글은 다른 축으로 유지하고, 88mm 정책은 개발책임자 결정 전 임의로 포함·제외하지 않는다.

#### B. #845 “DS-4 완료”와 실제 활성화 가능성

- #845 본문은 DS-1~DS-4를 머지 완료로 표기한다.
- 같은 본문 R1과 현재 `DocumentTemplateService.java:31,114-120`은 DETAIL/IMAGE 양식 활성화를 차단한다.

**판정**: 코드/편집/preview 구현 완료와 운영 ACTIVE 도달 가능은 같은 상태가 아니다. #903이 #845를 “완전 운영 완료”로 가정하면 안 되며, 반대로 #903에서 이 게이트를 임의 해제해서도 안 된다.

#### C. 견적서 data-first 결정과 현재 JSX 출력

- `project_print_preview_standardization.md:12,18`은 견적서를 GAS 종합견적서+snapshot/data model 중심의 별도 에픽으로 둔다.
- 현재 route는 `QuoteView`의 고정 JSX/A4 출력이다(`routes/index.tsx:534-536`, `QuoteView.tsx:69-221`).

**판정**: 저장 데이터 결정과 출력 JSX가 병존하는 gap이다. #903의 Excel pilot에 견적서 이관을 포함하면 기존 견적 범위와 충돌할 수 있으므로 #845 R4의 별도 adapter 슬라이스로 남긴다.

#### D. 법정 양식과 Excel 다운로드

- #845 DFD-08은 세금계산서·재무제표를 자유설계 대상에서 제외한다(`document-form-designer-epic-design.md:21`).
- `.claude/memory/project_external_integration_research.md:20`은 전자세금계산서 홈택스 업로드용 Excel 다운로드 방식을 유지한다.

**판정**: Excel 파일 출력 계약과 Excel 방식 자유 저작은 다른 개념이다. 기존 다운로드를 근거로 법정 양식을 #903 자유 저작 대상으로 편입하면 충돌한다.

## 7. 구현 전 결정 게이트

다음은 기존 결정에서 확인하지 못했으므로 구현자가 추정하면 안 된다.

1. **mode 저장 단일 권위**: 기존 `document JSONB` 안의 discriminant+mode별 payload인지, 별도 DB column인지. 정찰 권고는 revision이 `document`를 통째로 pin하고 D-DS2-11이 typed JSONB를 권위로 두므로 **JSONB 내부 단일 권위**다. 다만 이는 기존 확정 결정이 아니라 S2 착수 결정이다.
2. **mode 전환**: 기존 양식의 `WORD↔EXCEL` in-place 변환을 허용할지. 손실 변환과 승인 pin 위험 때문에 정찰 권고는 **생성 후 mode 불변, 다른 mode는 새 DRAFT 복제**지만 기존 확정 결정은 아니다.
3. **프론트 grid 라이브러리**: 후보명만 있고 실측 선택이 없다. S3에서 실제 bundle/Electron/print/accessibility probe와 함께 확정해야 한다.
4. **XLSX 파일 round-trip**: 셀 그리드 저작만 필요한지, `.xlsx` import/export까지 필요한지 Issue 원문만으로 **확인하지 못함**이다. 미확정이면 S3~S5에서 제외한다.
5. **88mm와 #903 관계**: 저작 mode와 paper는 다른 축이다. 판매전표/입고전표 88mm 정책이 별도 확정되기 전 #903에서 해석하지 않는다.

## 8. 후속 슬라이스 제안 — 남은 구현 4개

공통 원칙은 그룹웨어 결재 문서 한 종류를 파일럿으로 유지하고, 각 단계가 독립 머지·롤백 가능하도록 다음 단계 기능을 명시적으로 차단하는 것이다.

| 순서 | 슬라이스 | 경계 | 독립 머지 조건 |
|---:|---|---|---|
| 1 | **S2 mode 저장·revision round-trip** | #998 계약을 FE/BE parser/request/response/JSONB/revision에 연결. mode 누락 v1/v2는 `WORD`. 저장 위치와 mode 전환 정책을 같은 PR에서 결정 기록. UI·Excel 의존성·renderer 분기 없음. | 기존 양식 JSON/출력 100% 무변경, 신규 `WORD/EXCEL` mode가 create/update/get/revision에서 보존, 미지 값 fail-safe 계약 명확 |
| 2 | **S3 Excel DRAFT 저작 vertical slice** | 측정 근거로 FE grid 라이브러리 선정. 신규 양식 생성에서 mode 선택. 단일 sheet, 셀 값/field binding, 행·열 크기, 병합의 최소 모델을 DRAFT 저장·재진입. 수식·매크로·다중 sheet·XLSX round-trip·다른 문서유형 제외. | 3 | **S4 Excel DRAFT preview renderer** | 저장된 Excel payload를 공통 문서 데이터 binding으로 렌더하고 `PrintLayout`에 수렴. 편집 preview와 인쇄 DOM compiler가 같은 model 사용. ACTIVE/승인 재인쇄는 계속 차단. | Excel DRAFT preview가 저장 재진입 후 동일, WORD renderer 무변경, 한글 IME/폰트·병합·행열 크기·반복행·A4 page break의 제한을 테스트로 고정 |

### 슬라이스 전체 제외 범위

- 견적서·판매전표·거래명세서·매입전표의 #845 엔진 이관: 문서유형별 #845 R4 후속 슬라이스.
- #845 R1 DETAIL/IMAGE activation gate 해제, R2 품목 원천 연결, R3 구 필드 빌더 통합.
- 판매전표/입고전표 88mm 정책 변경.
- 법정 고정 양식의 자유설계.

이 순서는 S2가 저장·pin 불변식을 먼저 세우고, S3/S4가 사용자에게 도달하지 않는 DRAFT 범위에서 라이브러리와 모델을 검증한 뒤, S5가 마지막에 ACTIVE와 실인쇄를 연다. 따라서 각 PR은 다음 PR이 없어도 기존 production 출력을 바꾸지 않으며 독립 머지 가능하다.

## 9. 확인하지 못한 항목

- 운영/공유 DB의 실제 `document_templates`·`document_template_revisions` 행 수와 mode 데이터: DB를 조회하지 않아 확인하지 못함.
