## 0. 요약과 계수 정정

Wave 1 보고서의 14개 합계는 878개이고, 이미 닫힌 arologis 70개를 빼면 **남은 보호 표면은 808개**다. 트랙/PR 본문에 숫자가 적힌 12개 서비스의 합은 803개이며, 목록에서 수치가 빠진 **partner-auth 5개**를 더해야 “나머지 13개”와 808개가 맞는다 (`docs/dev-reports/2026-08-14-1209-recon.md:57-71`).

`#1206`의 코드를 그대로 복사할 수 있는 서비스는 0개라는 Wave 1 결론은 유효하다. 다만 Wave 1이 만든 **원칙과 공통 헤더 목록/게이트웨이 필터**는 재사용할 수 있다 (`docs/dev-reports/2026-08-14-1209-recon.md:84-125`, `shared/common/src/main/java/com/samhanair/logis/common/http/HttpHeaderConstants.java:81-102`).

고위험 수는 컨트롤러의 `@DeleteMapping` 전수와 mapping 문자열에 `issue|emit|publish|approve|send`가 명시된 항목을 센 **정적 하한**이다. `confirm`, 상태변경처럼 이름만으로 의미를 알 수 없는 endpoint는 제외했으므로 실제 업무 비가역 표면은 더 크다.

### 1.2 권장 wave 순서

**중요:** 아래 wave는 동시 배포 묶음이 아니다. 각 셀의 화살표 순서로 **한 서비스 배포 → 수락 기준 1~8 확인 → 실패 시 즉시 중단**한다.

| 순서 | 서비스(순차) | 선정 근거 | 이 wave가 실패하면 멈추는 것 |
|---|---|---|---|
| P0 표준 canary | `dashboard` | 보호 19개, 공개 `/app/version`과 보호 publish 경로가 함께 있어 표준형의 공개/보호 분리를 가장 작은 업무 반경에서 검증 가능 (`services/dashboard-service/src/main/java/com/samhanair/logis/dashboard/config/SecurityConfig.java:31-40`) | 대시보드 공지·앱 릴리스 publish/unpublish/version 조회. 로그인·전표·재고는 계속 가능 |
| P1 권한 뿌리 | `auth` 단독 | 공개 인증 7경로와 보호 admin/internal이 혼재하고 모든 서비스 권한의 뿌리 | 신규 로그인·logout·비밀번호 흐름, 동적 권한/그룹/결재선 내부 조회. 기존 JWT만으로 downstream이 전부 정상이라고 단정할 수 없음 |
| P2 파트너 인증 | `partner-auth` 단독 | 공개 7경로와 직원 승인 5표면이 혼재. P1과 동시에 실패시키지 않음 | 파트너 상태/가입/비밀번호/로그인/임시비밀번호/만료/튜토리얼, 직원의 파트너 승인·reset. 직원 Samhan 로그인은 유지 |

### 2.2 헤더 제거 위치

| 층 | 해야 할 일 | 이미 있는 근거 / 남은 판단 |
|---|---|---|
| gateway 공개 route | 신뢰할 JWT가 없으므로 `INBOUND_IDENTITY_HEADERS` 전체를 **strip-only** | 전용 `StripInboundIdentityHeadersGatewayFilterFactory`가 공통 목록을 제거한다 (`services/api-gateway/src/main/java/com/samhanair/logis/gateway/filter/StripInboundIdentityHeadersGatewayFilterFactory.java:8-28`). auth/partner-auth 공개 route에도 이미 배선됨 (`services/api-gateway/src/main/resources/application.yml:43-52`, `services/api-gateway/src/main/resources/application.yml:184-192`, `services/api-gateway/src/main/resources/application.yml:204-211`, `services/api-gateway/src/main/resources/application.yml:240-245`) |
| gateway 보호 route | 클라이언트 값을 remove한 뒤 검증된 JWT claim으로 identity를 재주입하고 attestation을 추가 | `services/api-gateway/src/main/java/com/samhanair/logis/gateway/filter/JwtAuthenticationGatewayFilterFactory.java:237-260` |
| auth/partner-auth 서비스 | 공개 matcher에서는 identity를 인증 입력으로 **읽지 않아야** 하고, 보호 일반 경로에서만 attestation 검증 후 읽어야 한다. internal RPC principal은 별도 유지 | Wave 1 아로로지스는 공개 로그인/refresh를 `shouldNotFilter`로 제외했다 (`services/arologis-service/src/main/java/com/samhanair/logis/arologis/config/HeaderAuthenticationFilter.java:43-49`). auth/partner-auth에는 이 분기가 현재 없음 |

**미결 A — “제거”의 강도.** gateway 경유 요청은 실제 header 제거가 이미 보장된다. 서비스 직결 공개 요청에 대해서 Wave 1 아로로지스 방식은 “필터가 읽지 않음”이지 servlet request의 header 자체를 삭제하는 것은 아니다. 수락 기준 6이 직결 요청에서도 controller/AOP에 header가 보이지 않는 **물리적 제거**를 뜻한다면 request wrapper 기반 초기 sanitizing filter가 필요하다. Wave 1과 동일한 의미(인증 입력으로 읽지 않음)면 public matcher `shouldNotFilter` + gateway strip으로 충분하다. 임의 확정하지 않는다.

## ④ Wave 1 형태를 그대로 복사할 수 있는가

### 결론

- **그대로 복사 가능한 서비스: 0개.** logging은 `/logs/**` 단일 prefix를 기존 `InternalTokenFilter`로 막을 수 있었지만, 나머지는 공개/내부/일반 경로가 섞여 있다 (`docs/dev-reports/2026-08-14-1209-recon.md:116-125`).
