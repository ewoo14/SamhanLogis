# #910 + #935 클라이언트 버전·자동 업데이트 정찰

- 정찰일: 2026-08-08 (KST)
- 작업 트리: `feat/910-client-version-policy`
- 조사 범위: 코드·설정·기존 dev-report·git 이력만. Docker 재기동·DB 변경·자격값 조회/기록 없음.

## 판정 요약

PR #993의 핵심 산출물은 “8개 canonical client identity와 공통 버전 정책” 및 기존 데스크톱 업데이트 골격의 보완이다. #928/#935에서 시작한 아로로지스 데스크톱의 버전 확인·업데이트 IPC 코드도 현재 저장소에 있다. 그러나 코드서명 자격과 운영 피드가 저장소/실행 환경에 연결됐다는 증거, 서명된 Windows installer, 실제 피드에서의 설치·재기동 검증은 없다.

따라서 **정책 코드 후속은 조사상 가능하지만, #935의 운영 자동 업데이트(서명·피드·실설치) 슬라이스는 선행조건 미충족으로 착수 불가**다. 이는 #928 S2 보고서의 결론(인증서·피드 부재로 installer/update E2E 미검증)과 일치한다.

주의: `c2a8de933`(PR #993)는 `origin/main`의 조상으로 확인됐다. 다만 이 worktree의 HEAD에는 PR #993 뒤의 #910 재수렴 커밋들이 있고, 현재 로컬 `origin/main...HEAD` 비교는 46개 파일 차이를 반환한다. 사용자 지시의 “PR #993 이미 머지”는 맞지만, “HEAD와 origin/main 내용 차이 없음”은 현재 ref 실측과 일치하지 않는다. 이 차이는 이번 정찰에서 수정하지 않았다.

## A. 이미 된 것과 남은 것

### PR #993이 전달한 것

`c2a8de933 [FEAT] #910 전 사용자 대면 클라이언트 버전 정책 확대 — 정찰·기획 (#993)`의 실제 변경은 다음 범위다.

- `services/dashboard-service`의 앱별 `AppClientType` 8개 canonical 값과 legacy `WEB`/`MOBILE` 호환, `app_release` 조회·등록 정책.
- 앱별 릴리스 관리 화면/mock/회귀 테스트.
- 모바일 3앱의 명시적 client type 전환: `SAMHAN_MOBILE`, `SAMHAN_MOBILE_STAFF`, `AROLOGIS_MOBILE`.
- 기존 삼한 데스크톱과 아로로지스 데스크톱의 `/app/version` 게이트, Electron `electron-updater` IPC, 상태 표시 및 강제 수준(`MINOR`/`MAJOR`/`CRITICAL`) 계약.
- 공통 `scripts/app-build-version.cjs`: 사용자 표기 `YYYY/MM/DD-N`, 릴리스 내부 비교용 semver, 개발 sentinel, 릴리스 무주입 차단.
- Electron/PWA/Capacitor 빌드 wrapper와 stale/sentinel 산출물 차단.
- PR 이후 HEAD의 추가 #910 재수렴에서 날짜 버전의 내부 semver 매핑, 개발 모드 timeout, 사용자 화면 내부 semver 누출 및 installer 표시 결함을 보완했다. 마지막 커밋 메시지는 `a0021c684 ... SOL 재수렴 3 — PASS`다.

### #928이 남겼고 #935가 닫은 범위

기존 `docs/dev-reports/2026-07-29-928-version-check-s2.md`의 앱 표는 웹 3앱이 PR #934로 이미 완료됐고, 당시 유일한 미착수 앱이 `clients/arologis-desktop`이었다고 기록한다. #935 구현(PR #981 계열, `de46f7e2e`)은 다음을 추가했다.

- `AROLOGIS_DESKTOP` 전용 `/app/version` 조회와 MINOR/MAJOR/CRITICAL 안내.
- `electron-updater`의 checking/available/downloading/downloaded/error IPC 및 `quitAndInstall` 경로.
- 공통 릴리스 버전 주입과 `build-arologis-desktop-release.cjs` wrapper.
- `forceCodeSigning: true`와 아로로지스 전용 generic HTTPS feed 환경변수 검사.

그 보고서의 미완료는 명확하다: 실제 Windows installer 설치·재시작, update-available→download→quitAndInstall E2E, 코드서명 인증서 연결, `AROLOGIS_UPDATE_URL` 운영 피드 연결. 현재 코드도 피드가 없으면 `build:win`을 시작 전에 실패시킨다.

### 남은 항목

1. 삼한/아로로지스 Electron용 코드서명 인증서와 CI secret/runner 권한 연결 및 signed installer 생성.
2. 두 제품의 실제 HTTPS feed 게시 위치·`latest.yml`/installer/blockmap 배포와 feed URL 주입.
3. 깨끗한 Windows 설치본에서 update check→다운로드→재기동→새 버전 확인 E2E.
4. 모바일 3앱의 실제 EAS project/credential/store 또는 OTA 운영 연결. 현재 저장소 기본값은 placeholder이며 이것은 Electron feed와 별개다.
5. 웹 3앱은 자동 설치 업데이트가 아니라 `/app/version` 런타임 안내/새 자산 배포 방식이므로, 각 배포 환경에서 릴리스 버전 주입과 배포 순서를 운영 절차로 확정해야 한다.

**선행조건 결론:** 코드서명 인증서/CI 자격과 실제 HTTPS feed 게시가 모두 확인되지 않았으므로 #935의 명시적 선행조건은 충족되지 않았다. #935 운영 자동 업데이트는 착수 불가다. 먼저 자격·feed를 개발책임자가 결정/확보해야 한다.

## C. 클라이언트별 현재 버전·산출물·배선

현재 `package.json`의 버전은 대체로 마켓/패키지 메타데이터이고, 정책 비교 버전은 릴리스에서 `YYYY/MM/DD-N`을 주입한다. 값이 없는 자격·인증서 내용은 기록하지 않았다.

| canonical identity / 앱 | 현재 package 버전 | 버전 확인·업데이트 | 산출물 위치/현재 배선 |
|---|---:|---|---|
| `DESKTOP` 삼한 데스크톱 | `0.1.0` | `/app/version?clientType=DESKTOP`; Electron packaged NSIS는 feed check/download/install, 개발은 `not-available`; PWA/Capacitor는 version gate와 reload | Electron `clients/desktop/release/<release-version>/`; PWA `clients/desktop/dist/web`; Capacitor `clients/desktop/dist/capacitor` |
| `SAMHAN_MOBILE` 삼한 모바일 | `0.5.0` | `/app/version?clientType=SAMHAN_MOBILE`; EAS Updates는 project ID가 있을 때만 활성 | Expo/EAS build 산출물 외부; app config에 `ios`/`android` build number와 OTA 배선만 있고 실제 project/credential 미확인 |
| `SAMHAN_MOBILE_STAFF` 직원 모바일 | `0.4.0` | `/app/version?clientType=SAMHAN_MOBILE_STAFF`; EAS 조건부 | Expo/EAS build 산출물 외부; 실제 EAS 연결 미확인 |
| `AROLOGIS_MOBILE` 아로로지스 모바일 | `1.0.0` | `/app/version?clientType=AROLOGIS_MOBILE`; EAS 조건부 | Expo/EAS build 산출물 외부; 실제 EAS 연결 미확인 |

## D. 개발책임자 판단 필요 사항

- 삼한/아로로지스 Windows 코드서명 인증서의 소유 주체, 발급자/유효기간 관리, CI secret 저장소와 서명 runner 권한.
- 두 Electron feed를 같은 HTTPS origin으로 둘지 제품별로 분리할지, 공개/사내망 접근·인증·TLS·보존·rollback 정책.
- NSIS만 자동 업데이트 대상으로 할지 portable도 별도 배포/수동 업데이트 대상으로 유지할지.
- `latest.yml` 및 installer/blockmap 게시를 어느 배포 시스템이 책임질지와 릴리스 승격/rollback trigger.
- `YYYY/MM/DD-N`의 번호 발급 권위와 같은 날 재빌드/재배포·긴급 rollback 규칙.
- 모바일 3앱별 EAS project ID, OTA channel/runtimeVersion, App Store/Google Play 계정과 build credential 운영 주체.
- 웹 3앱에서 “사용 중 알림”을 어디까지 강제할지, order/estimate/mobile-public의 배포 순서와 CRITICAL 차단 시 dirty form 보호 정책.
- 운영 피드와 자격이 준비되기 전에는 #935를 코드/QA 착수로 표시할지, 또는 선행조건 준비 슬라이스로 분리할지.

## 슬라이스 후보 (결정 전)
