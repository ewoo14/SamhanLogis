# D-1018 창고 UUID 검증 DB 주입 경계 수정

## 조사 기록

### 1. 검토 보고서 확인

`2026-08-01-1018-sol-review.md`의 실행 증거를 확인했다. 현재 검증용 `JdbcTemplate`이 별도 qualifier 없이 주입되어 `@Primary`인 `slip_db`를 선택하고, CI는 `slip_db`에 test-only V999 `warehouses` 테이블을 만들어 결함을 가리고 있다. 정상 프로덕션 형태는 `slip_db`에 해당 테이블이 없고 `inventory_db`에만 존재한다.

### 2. RED 테스트 작성

`WarehouseValidationDataSourceConfigTest`를 추가했다. `@Primary`인 slip DataSource와 별도 inventory DataSource를 함께 등록하고, 창고 검증 `JdbcTemplate`이 inventory DataSource와 동일 인스턴스인지 확인한다. 현재 구현에서는 qualifier가 없어 `@Primary`를 선택하므로 이 테스트가 실패해야 한다.

### 3. qualifier 수정 및 GREEN 확인

`warehouseValidationJdbcTemplate`의 DataSource 파라미터에 `@Qualifier("warehouseValidationDataSource")`를 추가했다. `AbstractPostgresIT`는 Testcontainer 안에 `inventory_db`를 별도로 만들고 `warehouses`를 그 DB에만 준비하도록 바꿨으며, `slip_db`용 V999 migration 파일은 삭제했다.

#### GREEN 원문

```text

```

집중 테스트 `WarehouseValidationDataSourceConfigTest`는 통과했다. V999 fixture 없이도 통과했으며, 해당 fixture는 삭제되어 더 이상 `slip_db`에 `warehouses`를 만들지 않는다.

### 4. 첫 통합 테스트 실패 기록

`SlipPublishWarehouseIdIT` 실행 시 실제 검증 URL은 분리된 inventory DB를 향했지만, 테스트 준비 코드가 inventory DB 생성 실패를 기존 Docker skip 예외 처리로 삼켜 `warehouses`가 준비되지 않았다.

### 5. 테스트 DB 경계 보정 및 통합 GREEN

한 컨테이너에서 `inventory_db`를 동적으로 만들던 방식은 준비 실패를 숨길 수 있어 제거했다. `AbstractPostgresIT`는 이제 `slip_db`용 PostgreSQL과 `inventory_db`용 PostgreSQL을 각각 사용하고, inventory 전용 init script에만 `warehouses` 스키마와 4개 seed를 둔다. 따라서 slip DB에는 V999나 warehouses가 없다.

### 7. service-per-DB 경계 판단

현재의 전용 `warehouseValidationDataSource`는 `inventory_db`를 정확히 읽어 A/C/D를 만족시키고, 배포 시 inventory 서비스의 HTTP 기동 순서 의존성을 만들지 않는다. REST 호출로 바꾸면 inventory-service가 먼저 기동하고 네트워크가 준비되어야 하므로 정상 기동 D가 새로 깨진다. slip DB에 warehouse projection을 두는 방식은 inventory 이벤트/replay와 별도 스키마가 필요하고 적용된 Flyway migration 수정 금지 범위를 넘는다. 따라서 이번 범위에서는 직접 읽기를 유지하되 qualifier로 실제 DB를 고정했으며, 경계 해소는 별도 projection 설계 과제로 남긴다.
