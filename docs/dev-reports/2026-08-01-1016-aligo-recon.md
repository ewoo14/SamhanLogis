# 2026-08-01 알리고 자동 업로드 레거시 대조 조사

## 조사 범위

- `tools/legacy-gas/` 직접 목록에서 대상 폴더 `tools/legacy-gas/알리고 자동 업로드/`를 확인했다.
- 대상 레거시 원본은 `Code.js`, `Index.html`, `appsscript.json` 3개 파일이다.

## 레거시 확인 기록

### 데이터 원천과 선행 동기화

- 사용자가 올리는 이카운트 엑셀은 첫 시트를 두 번째 행부터 읽고 마지막 행을 버린 뒤 `그룹 === 'SF(밴더)'`만 남긴다. 원문: `data = XLSX.utils.sheet_to_json(sheet, { range: 1 });`, `if (data.length > 0) data.pop();`, `data = data.filter(row => String(row['그룹'] || '').trim() === 'SF(밴더)');` (`tools/legacy-gas/알리고 자동 업로드/Index.html:329-332`). 이 단계의 표현 필드는 `거래처코드`, `담당자명`, `거래처명`, `대표자명`, `주소1 || 주소`, `전화번호`, `검색창내용 || 비고`다 (`Index.html:333-341`).
- 로컬 주소록 입력은 이카운트와 KT 엑셀이다. 원문: `['ecount', 'kt'].forEach(type => {` (`Index.html:288-300`). 주소록 후보 필드는 전화번호가 `휴대폰 전화번호 || 연락처 || 전화번호`, 이름이 `성명 || 회사명 || 이름 || 거래처명`, 그룹이 `그룹`이다 (`Index.html:347-350`). 숫자만 남긴 뒤 11자리 `010`만 수용하고, KT는 `그룹 === '/SF벤더'`만 수용한다 (`Index.html:352-357`).
- 서버 자료는 Notion 거래처 DB와 Google Sheets 3개 시트다. Notion에서 `거래처명`, `전화번호`, `주소`, `담당자명`을 읽는다 (`tools/legacy-gas/알리고 자동 업로드/Code.js:180-218`). Sheets에서는 원문 `var cNameIdx = head.indexOf('회사명');`, `var cPhoneIdx = head.indexOf('연락처');`, `var cAddrIdx = head.indexOf('주소');`로 세 필드를 읽는다 (`Code.js:228-255`).
- 발송용 목록 생성 전에 이카운트 원본이 없으면 중단한다. 원문: `if (rawEcountData.length === 0) { alert('이카운트 거래처리스트 엑셀 파일을 먼저 업로드해주세요.'); return; }` (`Index.html:369-373`). 동기화는 50행 단위다. 원문: `let batchSize = 50;` (`Index.html:382-387`).

### 업로드 산출물과 건수 단위

- 레거시의 최종 산출물은 알리고 API 폼 요청이 아니라 CSV 파일이다. 원문: `let csvContent = '\uFEFF전화번호,이름,그룹\n';` 및 ``csvContent += `${r.phone},"${r.name.replace(/"/g, '""')}","${groupName}"\n`;`` (`Index.html:582-601`). 즉 UTF-8 BOM CSV, 헤더 3개(`전화번호,이름,그룹`), 연락처 1개당 1행이다.
- 생성된 CSV는 먼저 브라우저 로컬 다운로드를 수행하고 (`downloadLocal(dt.filename, csvContent);`, `Index.html:603`), 이어 GAS 서버 함수로 Google Drive에 저장한다 (`uploadCsvToDrive(dt.filename, csvContent, dt.folderId);`, `Index.html:605-611`). 서버는 같은 파일명이 있으면 내용을 덮고, 없으면 MIME `text/csv` 파일을 만든다 (`tools/legacy-gas/알리고 자동 업로드/Code.js:266-278`). 저장소·수단인 Google Drive 자체는 완전계승 대상이 아니다.
- 표시·업로드 건수는 필터 통과 연락처 행 수다. 표는 통과 행마다 `count++` 후 ```${count}건```을 표시한다 (`Index.html:535-559`). 실제 CSV와 이력의 건수도 `filteredList` 기준이며 (`Index.html:587-600`), 이력 주제에 ```${filteredList.length}건```을 기록한다 (`Index.html:613`).

### 업로드 조건과 제외 규칙

- 공통 조건은 먼저 Notion 동기화 완료 상태여야 한다. 요일발송·전체발송·골프회 모두 원문 `if (!isDataSynced) return alert('업로드 페이지에서 노션 동기화를 먼저 진행하세요.');`로 중단한다 (`Index.html:616-617`, `656-657`, `681-682`).
- Notion 원천에서는 담당자명에 `신용정보`, `전자소송`, `보류`, `폐업` 중 하나가 포함되면 제외하고, 전화번호와 주소가 모두 있어야 포함한다 (`Code.js:208-219`).
- 요일발송은 오늘 요일에 체크된 지역만 대상으로 하며 대상이 없으면 `지정된 발송 요일이 휴무 상태입니다.`로 중단한다 (`Index.html:619-625`). Notion은 주소 지역 일치와 휴대전화 패턴 일치가 필요하고, Sheets는 주소 지역 일치 후 Notion에서 이미 본 번호를 제외한다 (`Index.html:627-646`).
- 전체발송은 로컬 주소록을 먼저 합치고 Notion 번호는 없는 경우에만 보태며, 하드코딩된 연락처 3개를 제외한다 (`Index.html:660-674`). 보고서에는 금지된 실제 번호 값을 기록하지 않았다.
- 골프회는 7개 권역 중 하나 이상을 사용자가 선택해야 하며 (`Index.html:684-693`), 요일발송과 동일하게 지역 일치·Notion 우선 중복 제거를 적용한다 (`Index.html:697-716`).
- 최종 다운로드 시 화면 필터(`phone`, `name`, `group`)를 다시 적용하며 0건이면 `다운로드할 데이터가 없습니다.`로 중단한다 (`Index.html:587-597`).

### 결과 확인과 실패 처리

- Drive 호출이 성공 콜백으로 돌아오면 화면은 `다운로드 및 저장이 완료되었습니다.`를 표시하고, failure callback이면 `서버 업로드에 실패했습니다.`를 표시한다 (`Index.html:605-611`).
- 그러나 서버 함수는 Drive 예외를 `catch`하여 `false`로 반환하고 예외를 다시 던지지 않는다. 원문: `} catch(e) { return false; }` (`Code.js:268-282`). 클라이언트 성공 핸들러는 반환값을 검사하지 않는 `withSuccessHandler(()=>{ ... })`다 (`Index.html:605-607`). 따라서 **Drive 저장 실패도 성공 알림으로 판정될 수 있는 레거시 결함**이 있다.
- 로컬 CSV 다운로드는 Drive 결과 전에 이미 실행된다 (`Index.html:603-611`). Drive 저장 결과와 독립적으로 Notion 작업이력 저장도 호출된다 (`Index.html:613`). 그러므로 로컬 파일 생성·이력 존재는 Drive 전달 성공 증거가 아니다.

## 현행 확인 기록

### FE 진입점과 mock 분기

- 현행 화면은 `syncMutation.mutate()`로 `syncAligoAddressBook`을 호출한다 (`clients/desktop/src/renderer/routes/admin/AligoAddressBookPage.tsx:75-80`, `128-138`). API wrapper는 `POST /admin/notification/aligo/address-book/sync`를 호출하고 응답 envelope의 `data`를 그대로 반환한다 (`clients/desktop/src/renderer/api/aligoAddressBookApi.ts:83-93`). FE 자체에서 성공 건수를 만드는 mock 분기는 없고, mock은 notification-service의 주입 구현체에서 갈린다.
- 화면 코드가 현 상태를 명시한다. 원문: `// TODO(PR-F2): 알리고 실 spec 후 dryRun=false 활성. 현 BE 는 MockAligoAddressBookClient` (`AligoAddressBookPage.tsx:75-77`) 및 `주소록 동기화는 현재 mock dryRun 모드입니다 (실 알리고 호출 없음).` (`AligoAddressBookPage.tsx:154-155`).
- 정확한 mock 분기는 `MockAligoAddressBookClient`의 `@Bean` + `@ConditionalOnMissingBean(AligoAddressBookClient.class)`이다 (`services/notification-service/src/main/java/com/samhanair/logis/notification/client/MockAligoAddressBookClient.java:46-50`). 저장소에서 실 `AligoAddressBookClient` 구현체가 등록되지 않으면 이 bean이 활성화된다.
- mock lambda는 외부 요청을 전혀 만들지 않고 원문 `return AligoAddressBookClient.UploadResult.success(contacts.size());`로 입력 연락처 수 전부를 신규 성공 건수로 반환한다 (`MockAligoAddressBookClient.java:51-62`). `UploadResult.success`는 이를 HTTP 200, 갱신 0, 제외 0으로 만든다 (`services/notification-service/src/main/java/com/samhanair/logis/notification/client/AligoAddressBookClient.java:63-67`). 따라서 **현행 주소록 동기화는 실제 알리고 외부 호출을 하지 않는다.**

### 현행 화면의 성공 판정

- 화면은 HTTP mutation이 정상 resolve되어 받은 `result`가 존재하면 바로 결과 chip을 렌더링한다 (`AligoAddressBookPage.tsx:82-85`, `192-196`). 신규 chip 값은 `result.added`, 변경은 `result.updated`, 제외는 `result.skipped`, 실패는 `result.failed.length`다 (`AligoAddressBookPage.tsx:225-259`).
- 따라서 mock이 반환한 `contacts.size()`가 그대로 화면의 `신규` 성공 건수다. 외부 전달 증거와의 대조·확인 단계가 없다. **실제 알리고 전달과 무관한 성공 계수 경로가 현행 결함**이다.

### 현행 내부 CSV 원천

- notification-service는 partner-service의 내부 CSV endpoint를 실제 HTTP로 호출할 수 있다. `RestClientAligoCsvSourceClient`는 내부 토큰이 있을 때 `GET /internal/partners/export/aligo-csv`를 호출한다 (`services/notification-service/src/main/java/com/samhanair/logis/notification/client/RestClientAligoCsvSourceClient.java:62-78`). 이것은 알리고 외부 호출이 아니라 저장소 내부 서비스 호출이다.
- 내부 토큰이 비었거나 요청·파싱이 실패하면 빈 목록을 반환하는 fail-soft다 (`RestClientAligoCsvSourceClient.java:64-67`, `79-82`, `115-118`). 실 CSV source bean이 없을 때 `NoopAligoCsvSourceClient`도 항상 빈 목록을 반환한다 (`services/notification-service/src/main/java/com/samhanair/logis/notification/client/NoopAligoCsvSourceClient.java:37-42`).
- 현행 파서는 CSV 4열을 위치 기준 `group`, `name`, `phone`, `memo`로 읽고 이름 또는 전화가 비면 제외한다 (`RestClientAligoCsvSourceClient.java:90-119`). 레거시 최종 CSV의 3열 순서 `전화번호,이름,그룹`과 다르다.

### 현행 서버 집계·실패 계약

- controller는 권한 검사 후 `syncService.sync()` 결과를 언제나 정상 envelope로 반환한다 (`services/notification-service/src/main/java/com/samhanair/logis/notification/controller/AligoAddressBookController.java:46-50`). 서비스는 내부 CSV 연락처를 50건씩 나눠 `aligoClient.uploadChunk(chunk)`를 호출한다 (`services/notification-service/src/main/java/com/samhanair/logis/notification/service/AligoAddressBookSyncService.java:40-50`, `69-75`, `103-108`).
- 429는 200/400/800ms 지수 backoff로 최대 3회 재시도하고, 소진하면 chunk 실패 문자열을 누적한다 (`AligoAddressBookSyncService.java:43-47`, `75-86`, `103-118`). 400 이상 비-429도 chunk 실패로 누적한다. 성공 응답의 `added/updated/skipped`는 그대로 합산한다 (`AligoAddressBookSyncService.java:82-95`). 이 실패 확인 구조는 인터페이스상 존재하지만, 현 mock은 항상 200 성공을 반환하므로 운영상 검증되지 않는다.
- 내부 CSV fetch가 빈 목록이면 예외가 아니라 `new AligoAddressBookSyncResponse(0, 0, 0, List.of())`를 반환한다 (`AligoAddressBookSyncService.java:57-62`). 화면에서는 이것도 정상 resolve된 결과로 취급되므로 통신·설정 실패를 성공 응답과 구분할 수 없다.

### 현행 표현 데이터와 제외 규칙

- 현행 CSV 원천은 자체 partner-service의 `ACTIVE` 거래처다. 차단 거래처를 제외하고, `mobile` 우선·`phone` fallback을 정규화한 결과가 없으면 제외한다 (`services/partner-service/src/main/java/com/samhanair/logis/partner/service/PartnerAligoExportService.java:83-116`, `129-139`).
- 현행 CSV는 UTF-8 BOM + CRLF이며 헤더/필드가 `그룹명,이름,휴대폰,비고`다 (`PartnerAligoExportService.java:59-66`, `93-126`). 그룹은 `partnerGroup1` 또는 `기본`, 이름은 거래처명, 비고는 노출 가능한 거래처 코드다 (`PartnerAligoExportService.java:110-114`, `141-147`). 연락처 1개당 1행이라는 건수 단위만 레거시와 같다.
- 레거시의 `신용정보 / 전자소송 / 보류 / 폐업` 문자열 제외와 달리 현행 코드 주석은 이 필터를 적용하지 않는다고 명시한다 (`PartnerAligoExportService.java:33-40`). 현행은 대신 상태가 `ACTIVE`가 아니거나 차단 목록에 있는 거래처를 제외한다. 어느 쪽이 최신인가: 저장소 코드상 현행 주석은 이 차이를 ‘사용자 명시’로 기록하므로 **현행 ACTIVE/차단 정책이 최신 결정으로 보인다**. 다만 개발책임자의 이번 결정이 완전계승이므로, 문자열 규칙을 폐기한 결정의 원문 근거가 별도로 없다면 재확인이 필요하다.
- 현행 휴대전화 허용 prefix는 6종이고 10~11자리만 허용한다 (`PartnerAligoExportService.java:68-70`, `157-183`). 레거시는 최종 목록 생성에서 주로 `010`을 추출하며 로컬 엑셀도 11자리 `010`만 수용한다 (`Index.html:347-357`, `631-645`). 따라서 수용 연락처 범위가 다르다.

### 별도 FE mock route 확인

- desktop 공용 mock에는 `POST /admin/aligo/address-book/sync`가 별도로 존재하며 `IN_PROGRESS` 작업 응답을 만든다 (`clients/desktop/src/renderer/api/mock.ts:8697-8702`). 그러나 현행 wrapper가 호출하는 경로는 `/admin/notification/aligo/address-book/sync` (`aligoAddressBookApi.ts:83-91`)여서 경로가 다르고, 이 공용 FE mock route는 현재 화면 호출과 직접 일치하지 않는다. 양수 성공 건수의 실제 원천은 notification-service의 `MockAligoAddressBookClient`다.

### 운영 자격증명 확인

- notification-service 설정은 알리고 SMS용 API URL/key/userid/sender 네 항목을 환경변수로 받지만, 저장소 기본값은 자격 항목이 placeholder다 (`services/notification-service/src/main/resources/application.yml:56-60`). 값 자체는 이 보고서에 기록하지 않았다.
- 운영 compose도 같은 자격 항목을 외부 환경변수에서 주입하며 미주입 기본은 빈 값이다 (`infrastructure/docker-compose.prod.yml:647-650`). 운영 env 템플릿의 세 자격 항목도 빈 값이고 ‘실 발송 전환 시 실값 설정’이라고 명시한다 (`infrastructure/env-templates/notification-service.env:45-57`). Terraform user-data 템플릿 역시 세 자격 항목이 빈 값이다 (`infrastructure/terraform/templates/user_data.sh:278-281`).
- 워크트리 안에는 실제 운영 `.env`가 없고 예제·템플릿만 있다. 따라서 **저장소 증거로는 실제 운영 자격증명이 존재한다고 확인할 수 없다**. 확인 가능한 사실은 ‘템플릿/기본값은 빈 값 또는 placeholder’이며, 런타임 외부 secret 주입 여부는 확인불가다.
- 더 중요하게, 위 자격증명은 `AligoSmsAdapter`의 SMS 발송 설정이다 (`services/notification-service/src/main/java/com/samhanair/logis/notification/config/AligoProperties.java:7-21`). 주소록용 `RestClientAligoAddressBookClient` 구현체와 주소록 endpoint/payload/auth 설정은 저장소에 없다. 그러므로 SMS 자격증명이 런타임에 있더라도 현행 주소록 자동 업로드가 실호출로 전환되지는 않는다.
- 관련 사실도 일치한다. `AligoSmsAdapter`는 key/userid/sender 중 하나라도 blank/placeholder면 외부 호출 전에 stub 성공을 반환한다 (`services/notification-service/src/main/java/com/samhanair/logis/notification/adapter/sms/AligoSmsAdapter.java:53-60`). 주소록 쪽은 자격 상태와 무관하게 실 구현체가 없어서 `MockAligoAddressBookClient`가 입력 수 전부를 성공 처리한다.

### 레거시 세 목록의 원천 차이 보강

- `전체발송`의 로컬 원천은 정확히 이카운트와 KT 주소록 병합이며, 같은 번호는 뒤 원소의 이름으로 덮어쓴다. 원문: `let merged = [...localData.ecount, ...localData.kt];` 및 `merged.forEach(x => { map[x.phone] = x.name; });` (`tools/legacy-gas/알리고 자동 업로드/Index.html:451-455`). 여기에 Notion에만 있는 번호를 보탠다 (`Index.html:660-668`).
- `요일발송`과 `골프회`는 Notion과 Google Sheets 3개 시트를 원천으로 하며, Notion 번호가 우선이고 Sheets 중복 번호는 제외한다 (`Index.html:627-646`, `697-716`). 현행은 이 세 가지 표현 목록을 하나의 partner-service ACTIVE 목록으로 축소했으므로, 레거시의 요일별 지역 목록·골프회 지역 목록·전체 목록 구분이 없다.

### 레거시의 실제 외부 목적지 확인

- 대상 3개 파일 전수 검색 결과 `aligo.in` 또는 알리고 API endpoint 호출은 0건이다. `UrlFetchApp.fetch`는 Notion 통신에만 쓰이고 (`tools/legacy-gas/알리고 자동 업로드/Code.js:41`, `115`, `142`, `166`, `193`, `398`), 최종 파일 저장은 `DriveApp.getFolderById`다 (`Code.js:266-277`). 따라서 정적 원문으로 입증되는 레거시의 ‘업로드’ 목적지는 Google Drive이며, 이후 알리고 콘솔/연계가 실제로 가져갔는지는 이 프로그램에서 확인하지 않는다.

## 판정

**완전계승 미달이다.** 현행은 partner-service에서 CSV를 실제 생성·다운로드할 수는 있지만, ‘주소록 동기화 실행’은 알리고 외부 호출 없이 mock이 입력 연락처 수 전부를 `added`로 반환한다. 화면은 이 숫자를 `신규` 성공으로 표시하므로, 실제 전달과 무관한 성공 판정 결함이 확정된다.

레거시에서 계승해야 할 기능·표현 데이터는 세 종류 목록(요일발송/전체발송/골프회), 각 원천 병합·지역 선택·중복/제외 규칙, 최종 3열 CSV 표현, 최종 건수와 이력이다. Google Drive라는 저장 수단은 계승 대상이 아니다. 다만 레거시도 알리고 최종 반영을 확인하지 않고 Drive 실패를 성공으로 오판할 수 있으므로, 완전계승 구현은 그 결함까지 복제하지 말고 **vendor가 확인한 반영 건수/실패 사유를 성공의 권위**로 삼아야 한다.
