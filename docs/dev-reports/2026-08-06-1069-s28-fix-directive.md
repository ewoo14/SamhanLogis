# #1069 S28 SOL fix 지시서 — BUNDLE KEEP 부모 영속 우회

## 판정과 재현 난이도

**실 사용자 경로에서 재현 가능한 결함 1건. HEAD `c2878e436`은 머지 비권고다.**

- F1 — 품목 관리에서 BUNDLE을 `세트 유지(KEEP)`로 저장한 뒤 판매전표 또는 견적에서 선택하면, 전개 API가 구성품이 아니라 부모 자신을 반환한다. 화면은 이 부모를 `SINGLE` 라인으로 바꾸며, 신규 전표·라인 추가·견적·모바일 견적 저장 경로는 반환 ID를 재검증하지 않고 `slip_lines.product_id` 또는 `estimate_lines.product_id`에 쓴다.
- 재현 난이도: **낮음**. 품목 관리 권한 사용자가 세트 품목의 `세트 처리`를 `세트 유지`로 저장하고 전표/견적 폼에서 그 품목을 선택해 저장하는 정상 조작이다. 경합·지연 조작·비공개 API가 필요 없다. 현재 실 DB의 KEEP BUNDLE은 0개이므로 기존 문서를 여는 것만으로는 발화하지 않지만, 공개 관리 화면이 이 상태를 정상 생성·수정할 수 있다.

### 기준선과 반대급부 실측

읽기 전용 실 DB에서 `created_at < 2026-08-06 00:00:00`, 활성 `OUTBOUND DRAFT`, 현재 활성 product 정본을 같은 조건으로 재계수했다.

```text
SINGLE   2,107행 / 2,100전표 / 2,837,681,781.00원
BUNDLE       0행 /     0전표 /                 0원
활성 전체 BUNDLE 교차: slip_lines 0 · estimate_lines 0
revision BUNDLE 교차: slip_revisions 0 · estimate_revisions 0
활성 BUNDLE 정본: 344개 = EXPAND 343 · bundle_mode NULL(실행 시 EXPAND) 1 · KEEP 0
```

따라서 현재 2,107행 중 공통 guard에 걸리는 행은 **0건**이다. 정상 SINGLE 전체수정, 부분 라인 계약, 단일 라인 삭제를 포함한 slip-service 지정 8 suite **87 tests**가 모두 통과했다. `SlipFormPage`·slip API·빈행 지정 **100 tests**, 품목 폼 모델 **15 tests**도 통과했다.

## ② 불변식 — 수단 지시 금지

1. `product_type=BUNDLE`인 부모 UUID는 `bundle_mode`와 무관하게 `slip_lines.product_id` 및 `estimate_lines.product_id`에 저장되면 안 된다.
2. BUNDLE 선택의 정상 사용자 결과는 부모 평면 1행 유지나 단순 차단이 아니라, 저장 가능한 구성품 라인 전개여야 한다. 전개할 수 없는 업무 유형이면 저장 전에 한국어로 원인과 조치를 알려야 한다.
3. 화면이 BUNDLE 부모 응답을 `SINGLE`로 재분류해 서버의 타입 검증을 우회하면 안 된다.
4. 신규·전체수정·부분수정·라인 추가·모바일·발행/임포트·견적→전표·복사·revision 복원 중 어느 경로도 부모를 만들거나 되살리면 안 된다.
5. 기존 활성 SINGLE 2,107행은 오차단 없이 열기·저장·부분수정·삭제가 가능해야 한다.
6. EXPAND 구성품의 수량·단가·규격·옵션·세트 계보와 S18~S24의 지연 응답 스냅샷 규칙은 유지되어야 한다.
7. 오류는 한국어 업무 문구여야 하며 UUID, 내부 HTTP 상태 문구, 서비스명, stacktrace를 사용자에게 노출하면 안 된다.

## ③ 양방향 RED — 동시에 GREEN이어야 함

### RED-A — 정상 경로가 막히지 않음

- 현재 활성 SINGLE 표본을 매출·매입 전체수정으로 무수정 저장하고, 단가/수량/규격 부분수정 및 단일 라인 삭제했을 때 성공하지 않으면 RED.
- 일반 EXPAND BUNDLE을 판매전표·견적·모바일 견적에서 선택했을 때 구성품 N행으로 전개되고 부모 UUID가 저장되지 않거나, 옵션·수량·단가·규격·`parentSetModel`/`setHead` 계보가 보존되지 않으면 RED.
- 전개 요청 후 사용자가 품목·수량·단가·규격·옵션 중 하나를 바꿨을 때, 요청 시점 snapshot과 현재가 완전히 같은 응답만 반영되지 않거나 최종 한 벌로 수렴하지 않으면 RED.
- 정상 SINGLE 발행/주문 전환·견적 전환·전표 복사·revision 복원이 새 검증 때문에 차단되면 RED.

### RED-B — 결함 재발 없음

- 품목 관리 화면에서 BUNDLE을 KEEP으로 신규 생성하거나 기존 BUNDLE을 KEEP으로 바꾼 뒤 판매전표 신규 생성 또는 라인 추가를 하면 부모 UUID가 `slip_lines.product_id`에 남는 경우 RED.
- 같은 KEEP 품목을 일반 견적 신규·전체수정 또는 모바일 견적에서 사용해 부모 UUID가 `estimate_lines.product_id`에 남는 경우 RED.
- KEEP 전개 응답의 부모 UUID를 화면이 `productType='SINGLE'`로 바꾸어 저장 payload에 싣는 경우 RED.
- 품목 sheet sync가 KEEP BUNDLE을 만든 뒤 동일 우회가 재현되면 RED.
- direct PUT만 막히고 신규 POST/라인 추가/견적 경로 중 하나라도 부모를 저장하면 RED.
- 오류 응답에 UUID·내부 HTTP 문구·stacktrace가 보이거나, 사용자는 구성품 전개를 기대했는데 단순 차단 안내만 받고 기능을 완료할 수 없으면 RED.

RED-A와 RED-B는 같은 변경 상태에서 동시에 GREEN이어야 한다.

## ④ 이번에 하지 말 것

- BUNDLE/KEEP의 전사 상품 정책, 레거시 `SEND_AS_SET_IDS` 의미, 재고·주문 도메인을 이 PR에서 재설계하지 않는다.
- 정상 SINGLE 2,107행을 migration/backfill하거나 product master를 일괄 변경하지 않는다.
- S18~S24 지연 응답 snapshot 비교 필드·세대 규칙·접근성 안내를 넓게 리팩터링하지 않는다.
- `#874`, `#1066`, `#1075` 파일과 회계·가배차·검수결재 트랙을 수정하지 않는다.
- Docker 재빌드·재배포·중지, 실제 vendor 발송, DB write, 전체 게이트를 수행하지 않는다.
- 전표/견적 생성 기능을 단순 BUNDLE 차단으로 축소해 이 PR의 본 주제인 구성품 전개를 없애지 않는다.

증거 무결성: S27 보고서의 GREEN과 DB 수치는 재현됐다. 다만 보고서의 RED 원문은 git에 존재하지 않는 중간 상태(`ProductClient` 의존성은 있으나 guard 호출만 제거된 상태)에서 얻었다고 적혀 있고 raw log artifact가 없다. `HEAD^`에는 신규 테스트와 `ProductClient` 의존성 자체가 모두 없어 동일 명령으로 해당 `AssertionError at SlipUpdateServiceTest.java:64`를 독립 재생할 수 없다. 이 원문을 재인용할 때는 재현 완료로 표시하지 않는다.
