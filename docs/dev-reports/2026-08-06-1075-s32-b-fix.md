# #1075 S32 B 결함 fix — 명시적 전체 삭제와 우발적 공백 저장 구분

## 판정

S31의 전제는 맞다. 백엔드는 `lines == null`을 보존, `lines == []`를 명시적 전체 삭제로 정의하고 있고, 기존 프런트의 `valid.length === 0` 가드가 편집 전체 삭제까지 막고 있었다. 제3의 원인은 확인되지 않았다.

이번 수정은 다음 두 경로를 분리했다.

- 편집: 서버에서 hydrate한 기존 `lineId`가 하나 이상 있고, 그 기존 라인 각각에 대해 현재 사용자가 품목 해제 또는 행 삭제를 직접 수행했을 때만 빈 `lines: []`를 허용한다.
- 신규: 기존 서버 라인이 없으므로 빈 `lines`를 허용하지 않는다. 기존의 최소 유효 라인 정책을 유지한다.

Docker 재빌드·재배포, 백엔드 계약/마이그레이션 변경, commit, push는 하지 않았다.

## 1. 의도한 전체 삭제와 실수로 빈 상태를 가른 기준 및 근거

### 구분 기준

`EstimateFormPage.tsx`에 편집 시점의 서버 소유 라인 집합과 로컬 명시적 해제 집합을 각각 추적했다.

의도한 전체 삭제로 인정하는 조건은 모두 충족해야 한다.

1. `isEdit === true`이다.
2. hydrate 당시 서버 소유 `lineId`가 1개 이상이다. 원래 0라인인 편집 견적은 전체 삭제의 대상이 될 기존 라인이 없으므로 허용하지 않는다.
3. hydrate 당시의 모든 `lineId`가 현재 로컬 사용자 동작으로 명시적 해제/삭제 표시되었다.
4. 명시적으로 해제된 기존 라인 외에, 모델명·품목명·규격·메모·수량·단가가 남은 미확정 신규 입력이 없다.

명시적 동작으로 인정하는 입력 경로는 다음과 같다.

- 기존 라인의 모델명을 지우고 blur하여 `handleProductSelection(index, null)`에 도달한 경우
- 기존 라인의 품목 선택을 해제한 경우
- 기존 라인을 삭제한 경우

반대로 다음은 삭제 의도로 승격하지 않는다.

- 신규 작성의 빈 행
- 서버에서 협업 상대가 원격으로 품목을 비운 상태
- 기존 라인의 수량만 `0`으로 바꾼 상태
- 모델명/규격/메모/단가 등 미확정 입력이 남은 상태
- 기존 품목을 일부만 해제하여 다른 유효 라인이 남은 상태는 기존 `valid` 저장 경로를 사용한다.

협업 provider가 원격 상태를 반영할 때는 빈 품목을 로컬 명시적 삭제로 표시하지 않는다. 반대로 현재 사용자가 협업 화면에서 직접 품목을 해제하면 같은 `lineId` 기준 표시가 생긴다. provider 연결/해제로 hydrate effect가 재실행되어도 같은 견적과 같은 서버 라인 집합이면 표시를 초기화하지 않도록 했다. 견적 ID 또는 서버 라인 집합이 바뀌면 새 삭제 문맥으로 초기화한다.

### 근거

- 백엔드 계약: `UpdateEstimateRequest.java`의 `null`/빈 목록/값 있는 목록 의미
- 백엔드 계약 테스트: `update_onBundleEstimate_withEmptyLines_isAcceptedAsExplicitFullDeletion`
- 프런트 재현: S31 RED에서 유일 라인 해제 후 `updateEstimate` 호출 횟수가 0이었다.

따라서 “기존 서버 라인 전체에 대한 로컬 명시적 삭제 행위”를 의도성의 증거로 삼았다. 단순히 현재 화면이 비어 있다는 사실만으로는 충분하지 않다.

## 2. 안내 문구 변경과 사용 가능성

기존 문구:

```text
라인 1개 이상 (모델명 lookup 성공 + 수량 > 0) 을 입력하세요.
```

변경 문구:

```text
편집 경로: 유효한 라인이 없습니다. 품목을 입력하거나, 전체 삭제하려면 기존 품목을 모두 해제한 뒤 저장하세요.
신규 경로: 신규 견적은 모델명 lookup 성공 + 수량 > 0인 품목 1개 이상을 입력하세요.
```

편집 문구의 지시대로 각 기존 모델명을 지우고 blur한 뒤 저장하면 실제로 `PUT`과 `lines: []`가 발생한다. 모델명 lookup과 수량을 요구하는 신규 문구도 신규 빈 견적에서 실제로 수행 가능한 동작이다. 신규 경로는 이 변경으로 느슨해지지 않는다.

### RED-B — 보호 회귀 방지

RED-B는 S32에서 새로 고정한 보호 단정이다.

```text
신규 빈 견적은 조용히 저장되지 않는다.
```
