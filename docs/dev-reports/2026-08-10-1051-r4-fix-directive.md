# PR #1157 · 이슈 #1051 — R4 도달 결함 fix 지시서

판정: **BLOCK — 회사PC 런북 실행 경로 결함 1건**

## 지금 고칠 것

- 회사PC의 기본 개발환경에서 `DB-MIGRATION-RUNBOOK.md`에 공개된 V35 복구 명령을 그대로 복사해 실행하면, 숨은 사전 준비 없이 실제 `product_db`의 복구 SQL까지 도달해야 한다.

## 분리할 것

- `ON COMMIT PRESERVE ROWS` 때문에 동일 PostgreSQL 세션에서 V35 파일을 연속 두 번 실행하면 두 번째 `CREATE TEMP TABLE`이 이름 충돌한다. 현재 런북은 매번 새 psql 프로세스를 열고 Flyway는 V35를 한 번만 적용하며 V36도 없으므로, 이 비문서 경로는 이번 도달 결함으로 세지 않는다.
- Flyway가 V35 뒤 같은 커넥션을 재사용하면 임시표는 세션 종료까지 남는다. 현재 후속 migration과 애플리케이션에서 같은 이름을 참조하는 곳이 0이므로 별도 수정하지 않는다.

## 1. 좌표와 재현 증거

### 결함 1 — 런북 명령이 회사PC에서 SQL 실행 전에 실패한다

- 좌표
  - `docs/handoff/DB-MIGRATION-RUNBOOK.md:222-229` — host `psql`과 `$env:PRODUCT_DB_URL`이 이미 준비돼 있다고 가정한다.
  - `infrastructure/docker-compose.yml:25,40,45` — 회사PC의 실제 PostgreSQL은 `samhan-postgres`, 사용자 `samhan`, host port `5432` 구성이다.
  - `scripts/cleanup-loadtest-data.ps1:18` — 이 저장소의 기존 회사PC DB 호출은 `docker exec samhan-postgres psql` 경로를 사용한다.
- 회사PC 실측
  - 2026-08-10 12:28:39 KST: `Get-Command psql` 결과 없음.
  - 같은 시각: `$env:PRODUCT_DB_URL` 미정의.
  - 같은 시각: `samhan-postgres`는 healthy, V35 상대 경로는 현재 워크트리에서 존재.
  - 따라서 런북 명령을 그대로 붙여 넣으면 V35 파일을 읽기 전에 명령을 찾지 못해 종료된다. V33 차단 DB의 유일한 복구 경로가 문서상 존재하지만 회사PC에서는 도달할 수 없다.
- PM 기준선
  - 2026-08-10 12:17:30 KST 운영 DB 읽기 전용 실측: 활성 3,061 / 삭제 2, Flyway 최신 V34.
  - 커밋 `2880302e2`에서 V31·V33 diff 없음.
- R3 변경 자체의 대조
  - 실제 임시 PostgreSQL과 실제 psql에서 새 세션 2회 실행은 모두 성공했다.
  - UTF-8 fixture에서 101 UUID 대상은 삭제 유지, 비대상 제품과 자식 3종은 각 1건 복구, `qa-757` 제품·자식은 삭제 유지, 34개는 `NON_GOODS/false`로 전환됐다.
  - 동일 세션 연속 실행만 두 번째 `CREATE TEMP TABLE`에서 `relation already exists`로 실패했으며, 두 임시 컨테이너는 모두 제거했다.
- 증거 무결성
  - `Issue1096ProductCleanupMigrationIT.java:190-195`는 JDBC `autoCommit=true`로 핵심 문장별 commit 경계를 재현하지만 실제 psql 바이너리나 런북의 PowerShell 명령은 실행하지 않는다.
  - 구현자가 제출한 실제 psql RED와 R4 임시 DB 실측은 SQL 파일의 자동커밋 동작을 증명한다. 그러나 둘 다 회사PC 런북 명령이 그대로 실행 가능하다는 증거는 아니다.

## 2. 불변식

- 런북은 회사PC의 문서화된 기본 개발환경만 준비된 상태에서 복사 실행 가능해야 하며, 별도로 설명되지 않은 host 프로그램·접속 변수·현재 디렉터리를 요구해서는 안 된다.
- 실행 대상은 `samhan-postgres`의 `product_db`여야 하며, 다른 DB나 다른 컨테이너로 조용히 연결되어서는 안 된다.
- 실행 실패 시 복구 SQL 일부만 적용된 상태를 성공으로 안내해서는 안 되며, 실패 위치와 대상 DB를 운영자가 식별할 수 있어야 한다.
- V35 복구 후 활성 품목 수, cleanup actor 잔여 범위, 101 UUID 삭제 유지, 자식 3종 복구, 다른 actor 유지, 34개 `NON_GOODS/false`가 확인 가능해야 한다.
- PM의 실제 순서인 cleanup actor 기준 복구 → product-service 재기동 → V33 통과 → V34/V35 적용과 문서 순서가 일치해야 한다.

## 3. 양방향 RED

### RED-A — 회사PC 기본환경에서 V33 차단 복구

- host `psql`과 `PRODUCT_DB_URL`이 없는 회사PC 기본환경을 전제로, 폐기 가능한 PostgreSQL fixture를 V33 후보 32개 차단 상태로 준비한다.
- 런북에 최종 공개된 명령을 저장소 루트에서 그대로 복사해 실행한다.
- 현재 런북은 SQL 전에 실패해야 RED다. 결함 해소 뒤에는 V35가 끝까지 실행되고, 목록 밖 cleanup actor 제품·자식만 복구되며 101 UUID와 다른 actor 행은 계속 삭제 상태여야 한다.
- 이어서 Flyway를 재개했을 때 V33→V34→V35가 통과해야 한다.

### RED-B — 반복 실행과 오접속 차단

- 같은 폐기 가능한 fixture를 이미 복구된 상태로 만든 뒤, 런북 명령을 새로운 호출로 두 번 실행한다.
- 현재 런북은 두 호출 모두 host 명령 부재로 실패해야 RED다. 결함 해소 뒤에는 두 호출 모두 성공하고 두 번째 호출의 네 복구 UPDATE는 0건이어야 한다.
- 실행 전후 접속 DB가 `product_db`임을 명시적으로 확인하고, 대상 컨테이너나 DB가 잘못됐을 때는 V35의 첫 UPDATE 전에 실패해야 한다.
- 두 번째 실행 뒤에도 101 UUID와 다른 actor 행은 삭제 유지, 34개 후보는 `NON_GOODS/false`여야 한다.

## 4. 범위 밖

- V31·V33 수정 금지. 체크섬 보호 대상이다.
- V35의 101 UUID, 네 복구 UPDATE, 34개 NON_GOODS 목록과 `ON COMMIT PRESERVE ROWS` 변경 금지.
- product-service 밖의 migration 신설 또는 변경 금지.
- 운영 DB 쓰기, Docker 스택 재배포, 서비스 재시작 금지.
- 동일 세션에서 V35 파일을 두 번 읽는 비문서 경로와 미래 V36의 가상 이름 충돌은 이번 수정에 포함하지 않는다.
