## 2. 원인 · 셋째 가능성 · 수정 지시

S22의 `previous != null && current != null` 판정은 “정규화가 왜 일어났는가”를 구분하지 않는다. null이 한쪽에 있다는 사실만으로 source 차이를 버리고, marker 표현 정규화는 specification 비교에 그대로 남긴다.

정답은 “모든 `null→USER/CATALOG`를 제외”와 “source 차이를 전부 센다”의 양자택일이 아니다. **셋째 가능성은 구 문자열에서 기대되는 source와 사용자에게 보이는 canonical specification을 함께 계산하는 것**이다.

- 구 평문 `X/null`의 무행위 hydrate 결과는 `X/USER`다. 이 조합만 정규화로 제외한다.
- 구 marker `U+2060X/null`의 무행위 hydrate 결과는 `X/CATALOG`다. marker를 제거한 표시값이 같을 때 이 조합만 정규화로 제외한다.
- 구 평문 `X/null → X/CATALOG`와 구 marker `U+2060X/null → X/USER`는 기대 source와 다르므로 실제 명시 전환으로 센다.
- 표시 specification이 달라지면 source 정규화 여부와 무관하게 센다.
- `USER/CATALOG→null`은 복원 경계에서 생길 수 있다. 현재 helper는 이를 제외한다. current source가 null인 역방향은 정규화로 보지 말고 source 변경으로 센다.
- 양쪽 source가 명시된 `CATALOG↔USER`는 지금처럼 센다.

최소 RED/GREEN 집합:

1. `U+2060X/null → X/CATALOG`, 헤더만 변경: `lineModified=0`.
2. `X/null → X/USER`, 헤더만 변경: `lineModified=0`.
3. `X/null → X/CATALOG`, 나머지 동일: `lineModified=1`.
4. `U+2060X/null → X/USER`, 나머지 동일: `lineModified=1`.
5. `CATALOG→USER`, `USER→CATALOG`, `CATALOG/USER→null`: 각각 `lineModified=1`.
6. source 정규화 조합이어도 표시 specification·단가·수량·금액·비고 중 하나가 바뀌면 `lineModified=1`.
7. 실제 `decodeEstimateSpecification → draft → update body → snapshot summary` 조합으로 marker 실경로를 한 번 통과시킨다.

schema 변경은 필요하지 않다. V113을 고치거나 V114를 만들지 않는다.
