## 상태별 허용 액션 전수 대조표

기준은 `Slip.save/send/accept/process/complete/inspect/ship/deliver/confirm/reject/cancel`의
`requireStatus` 및 분기이며, 화면은 `SlipDetailPage.actionsForStatus(status, mode)`이다.

| 상태 | 도메인 허용 액션 | 화면 노출 액션 | 판정 |
|---|---|---|---|
| DRAFT | save, cancel | save, cancel | 일치 |
| SAVED | send, cancel | send, cancel | 일치 |
| SENT | accept, reject, cancel | accept, reject, cancel | 일치 |
| ACCEPTED | process, reject | process, reject | 일치 |
| PROCESSING | complete | complete | 일치; `/complete` 매핑 유지 |
| INSPECTING | inspect, reject | inspect, reject | R24에서 reject 추가, 일치 |
| COMPLETED (OUTBOUND) | ship | ship | 일치 |
| COMPLETED (INBOUND) | confirm | confirm | 일치 |
| SHIPPING (OUTBOUND) | deliver | deliver | 일치 |
| DELIVERED (OUTBOUND) | confirm | confirm | 일치 |
| CONFIRMED | 없음 | 없음 | 일치 |
| REJECTED | 없음 | 없음 | 일치 |
| CANCELED | 없음 | 없음 | 일치 |

`cancel`의 도메인 내부 `PARTNER_ORDER` 추가 가드는 기존 화면 액션 집합과 별도의 실행 시 검증이며,
상태별 허용 집합 대조에는 상태 가드 기준을 기록했다. INBOUND의 `ship/deliver`는 도메인에서
전표 유형상 거부되고 화면도 노출하지 않는다.

## 수정 및 결함 2 판정 근거

- `INSPECTING`의 `possibleActions`를 `['inspect', 'reject']`로 바꿨다. 기존 반려 사유 입력·버튼은
  `possibleActions.includes('reject')`와 `slip.reject` 권한 가드를 이미 사용하므로 OUTBOUND/INBOUND
  양쪽 상세 화면에 노출된다.
- PROCESSING의 `/complete` 호출, `complete()` 전이, OUTBOUND `deduct(..., true)`/`shipInstances`,
  INBOUND `inventoryClient.inbound`는 변경하지 않았다.
- 데스크톱 하단 주 액션과 반응형 모바일 주 액션이 같은 `transitionActionLabel`을 사용하므로,
  라벨을 `검수 시작`에서 `재고 반영 후 검수 대기`로 바꿨다. 이는 클릭 시 재고 반영이 끝나고
  상태가 INSPECTING으로 바뀐 뒤 검수를 기다리는 실제 결과를 직접 설명한다. 별도 확인 모달은
  전이 의미를 바꾸지 않지만 중복 확인 UX를 추가하므로 이번 최소 수정에서는 채택하지 않았다.
