동기화 전에 먼저 PostgreSQL read-only transaction으로 표본을 셌다. 표본은 0이 아니다.

```text

odu_recommendation_lookup|32|0
```

동기화 뒤 같은 read-only SQL을 다시 실행해 `28/32/6`, 활성 합계 `66`, 삭제 `0/0/0`이 유지됨을 확인했다.

## 각도 2 — `totalUnchangedRows` 집계 경로와 로그 자리

R9 diff의 런타임 3곳을 다시 따라갔다.

```text
TabSyncResult.unchangedRows
  -> runTab(): summary.totalUnchangedRows += result.unchangedRows
  -> syncAll() 완료 로그의 세 번째 placeholder
```

공개 admin 응답은 private lookup total을 직접 노출하지 않고 `ProductAdminController.mergeLookupSummary()`가 탭별 `lookupTab.unchangedRows`를 기존 `TabSyncResult.unchangedRows`에 복사한다. 따라서 private total 개명과 화면의 탭별 값은 별도 경로다.

현재 HEAD 배포본에서 뽑은 실제 로그 원문:

```text
2026-08-09T17:06:53.410+09:00 INFO ... ProductLookupSheetSyncService : [ProductLookupSheetSync] sync 완료: insertedRows=0, updatedRows=0, unchangedRows=66, softDeletedLookupRows=0, skippedOccurrences=94, duration=2488ms
```

자리 대조:

```text
1 insertedRows=0
2 updatedRows=0
3 unchangedRows=66 (= DB 28+32+6)
4 softDeletedLookupRows=0
5 skippedOccurrences=94 (= 0+1+93)
6 duration=2488ms
```

포맷 인자 밀림은 없다. `git grep -w totalUnchanged -- services/ clients/`도 0건이었다. 표적 IT는 fresh `--rerun-tasks`로 `BUILD SUCCESSFUL`이었다.
