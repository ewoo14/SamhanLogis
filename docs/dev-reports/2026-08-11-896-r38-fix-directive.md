## 4. 양방향 RED

### RED-A — healthy 정방향

현재 배포처럼 products/rules가 모두 `200`이면 전체 스펙을 한 명령으로 실행해 **3/3 PASS**여야 한다.

```text
live products=200
live rules=200
active rule=UI_HOME_MULTI_AM052BN6PBH1 1건
PC6NUDK1NW eligible=true
AM052BN6PBH1 eligible=false
R35 역방향/picker 케이스 실행
D15 writes=POST,PUT,PUT,DELETE sources=1>2>1>0 케이스 실행
_local PNG 00~06 총 7장 생성
```

### RED-B — 장애 역방향

products 또는 rules가 `503`이면 healthy 검증은 명시적으로 RED여야 한다. 과거 장애 캡처를 살리려고
`200/503`을 모두 허용하거나, 첫 테스트를 삭제·skip하거나, 응답 오류를 route fixture로 무조건
정상화하면 안 된다. 장애 원문은 assertion message/attachment로 보존하되 **503을 PASS 조건으로
되돌리지 않는다**.

뮤테이션 확인:

```text
healthy 단언을 다시 503 고정으로 되돌리면 현재 배포에서 RED-A가 `Received 200`으로 실패해야 한다.
503를 허용하는 분기를 추가하면 RED-B가 거짓 green이 되므로 실패해야 한다.
resolveQaShotsDir를 제거하면 H-2 가드가 RED여야 한다.
```

- 503을 정상값에서 제거하더라도 서비스 장애 관측력을 잃지 않는다. 장애는 RED + 응답 원문으로 남긴다.

- `test.describe.serial`의 D15 순서 계약과 브라우저 메모리 fixture 쓰기 격리는 유지한다.
- `QA_SHOTS_DIR` 미지정 기본값은 계속 `_local`; `QA_ALLOW_OVERWRITE=1`을 검증 명령에 넣지 않는다.
- 커밋 증거 7장의 SHA-256과 Git blob이 현재 HEAD와 동일해야 한다.
- 다른 real-QA 스펙이나 공유 helper는 변경하지 않는다. 필요한 수정 범위는 이 R36 스펙 안으로 제한한다.
