## 1. 어느 엔드포인트가 실제로 동작하는가

### 1-1. 코드상 창고 마스터 조회 endpoint 전수

창고의 실재성·정체성을 읽는 endpoint는 아래 다섯 종류다. audit log·SSE는 창고 마스터 lookup이 아니므로 제외했다.

| 계약 | controller 경로 | 실효 입력/부재 표현 | 인증 |
|---|---|---|---|
| 활성 창고 목록 | `GET /inventory/warehouses` | 전체 목록, 없으면 `200 []` | gateway JWT + `inventory.warehouse:VIEW` |
| 활성 창고 검색 | `GET /inventory/warehouses/search?q=` | code/name/address 부분검색, 없으면 `200 items=[]` | gateway JWT + `inventory.warehouse:VIEW` |
| 공개 UUID 단건 | `GET /inventory/warehouses/{id}` | 존재 `200`, 부재 `404` | gateway JWT + `inventory.warehouse:VIEW` |
| internal 코드 exact | `GET /internal/inventory/warehouses/by-code?code=` | 존재 `200`, 부재 `404` | `X-Internal-Token` |
| internal UUID exact | `GET /internal/inventory/warehouses/{id}` | 존재 `200`, 부재 `404` | `X-Internal-Token` |

관리자 복구용 `GET /inventory/warehouses/deleted`도 존재하지만 soft-deleted 행 전용이며 활성 매핑 검증에는 사용하면 안 된다. 현재 응답은 `200 []`였다.

gateway는 같은 공개 controller에 도달하는 alias 세 개를 제공한다.

```text
/inventory/**          -> no strip
/api/inventory/**      -> StripPrefix=1
/api/v1/inventory/**   -> StripPrefix=2
```

세 목록 alias를 실제 JWT로 호출한 결과는 모두 HTTP 200이었다. 로그인 응답 원문은 남기지 않았고 token은 즉시 폐기했다.

### 1-3. #1035의 404 원인

| 시기/경로 | 원인 판정 |
|---|---|
| 라운드 2 최초 검증 | mapper key `00003/2/14/1`을 `warehouses.code` exact endpoint에 보냈다. 당시 DB code는 `HQ-001/VH-001/CS-001/VR-001`뿐이어서 4/4 데이터 미존재 404였다. 경로와 internal 인증은 맞았다. |
| 라운드 4 UUID 조회 | internal UUID endpoint는 실재했고 UUID 4/4가 200이었다. `FOUND`만 보고 key와 정체성 대응을 확인하지 않은 것이 문제였다. |
| 라운드 6 UUID 후 코드 역조회 | UUID 4/4 200 뒤 legacy 코드 4/4 404였다. 서비스 미기동도 UUID endpoint 부재도 아니었다. |
| 더 오래된 공개 UUID 호출 | 공개 `/inventory/warehouses/{id}`에 internal token만 보낸 인증 계약 파손이었다. commit `058a9019d`에서 internal UUID endpoint로 교정됐다. |
| 현재 | S18이 실 관리자 API로 만든 `00003`·`2` 때문에 legacy code는 2/4 200, `14`·`1`은 2/4 404다. 네 UUID는 4/4 200이다. |

결론: UUID 경로와 코드 경로는 각각 존재하고 현재 동작한다. #1035의 반복 404는 endpoint 철자 문제가 아니라 서로 다른 코드 네임스페이스를 exact 동일 키처럼 취급한 설계와 당시 데이터 부재가 원인이다.

## 2. 기동 시점 조회가 맞는가

아니다. 외부 조회를 bean `@PostConstruct`에서 동기 실행해 기동을 막는 방식은 다시 사용하면 안 된다.

### 2-1. 세 방식 비교

| 방식 | 장점 | 이번 트랙의 결정적 한계 | 판정 |
|---|---|---|---|
| health/readiness 요청 때 원격 조회 | 지속 재평가 가능 | probe thread가 외부 지연에 묶이고 inventory 배포 순서·일시 장애가 slip health를 흔든다. 현재 Docker는 `/actuator/health` 실패 시 unhealthy/restart하므로 기동 차단을 다른 이름으로 반복한다. | 부적합 |
| 기동 후 비동기 1회 | Spring context는 산다 | 최초 시점이 inventory 늦은 기동이면 `UNAVAILABLE`로 끝나고 drift를 영구 재검증하지 못한다. | 단독 사용 부적합 |
| timeout 있는 독립 주기 검증(첫 실행도 scheduler) | 기동 비차단, 일시 장애 회복, 런타임 drift 탐지, 상태 전이·heartbeat 계측 가능 | 상태 소비자·경보·요청별 차단을 함께 만들지 않으면 라운드 6의 ERROR-only를 반복한다. | 권장 |

health endpoint가 원격 HTTP를 직접 호출해서는 안 된다. health나 관리자 API가 필요하면 마지막 주기 검증의 **캐시된 상태만** 읽어야 한다.

### 2-2. 일곱 실패별 방어 범위

기호: `○` 방어 가능, `△` 별도 조건 필요, `×` 방어 못 함.

| 과거 실패 | 원격 health/readiness | 기동 후 비동기 1회 | 주기 검증 |
|---|---:|---:|---:|
| R2 legacy 코드 4/4 404 | × 잘못된 대응 계약이면 같은 오판 | × | △ canonical pair 계약이 있어야만 방어 |
| R2 일시 장애·늦은 기동·미실재 미구분 | △ 상태 구분은 가능하나 probe flap/배포 결속 | △ 구분해도 재시도 없음 | ○ `UNAVAILABLE/NOT_FOUND/MISMATCH/VALID` 상태 + 재시도 |
| R4 뒤바뀐 식별자도 FOUND | × UUID 존재만 보면 통과 | × | △ UUID와 canonical expected identity의 pair 비교 필수 |
| R4 UNAVAILABLE 영구 미검증 | ○ 매 probe마다 실행하지만 운영 위험 | × | ○ 계속 재검증 |
| R4 timeout 없이 기동 thread block | △ timeout이 있어도 probe thread block | △ timeout 별도 필요 | ○ connect/read/call 전체 timeout 필수 |
| R6 legacy 역조회 4/4 404 재발 | × 같은 잘못된 역조회면 재발 | × | △ alias/canonical 대응 계약이 있어야 방어 |
| R6 재검증 불일치가 ERROR log뿐 | △ health DOWN이면 보이지만 전체 restart 위험 | × | ○ 상태 gauge·경보·관리 API·요청별 차단이 상태를 소비해야 함 |

주기라는 시간 모델만으로는 네임스페이스 오류와 뒤바뀜을 못 막는다. **canonical pair 계약 + 상태 소비**가 같이 있어야 한다.

## 3. 발견하면 무엇을 하는가

### 3-1. 저장소의 실제 관례

검색 결과 `services`와 `shared` main source의 custom `HealthIndicator` 구현은 0건이다. 반면 다음 관례는 실제로 있다.

1. **Micrometer + Prometheus rule**
   - `PartnerProductPriceMemoryService`가 counter/timer를 생성 시 등록한다.
   - `infrastructure/prometheus/rules/slip-price-memory.yml`은 5분 실패 증가량에 warning을 낸다.
2. **CloudWatch alarm + SNS**
   - `infrastructure/terraform/monitoring.tf`의 slip price-memory와 partner-order outbox alarm은 `alarm_actions`와 `ok_actions`를 `aws_sns_topic.alerts`에 연결한다.
   - 단순 로그가 아니라 실제 알림 전달 체인을 가진 운영 관례다.
3. **관리자 읽기 API**
   - `SlipCollabNotificationAdminController`의 `GET /admin/slip-collab-notifications/terminal`은 최종 실패를 전표번호·사유·시도 횟수로 노출하고 UUID를 반환하지 않는다.
4. **best-effort 운영자 push**
   - `CompensationAlertNotifier`는 notification-service push를 보내되 실패가 본 흐름에 전파되지 않게 하고, 전송 성공/실패/skip도 metric으로 남긴다.
5. **기동 후 비동기 + 주기 재시도**
   - `WarehouseCodeSnapshotService`는 본 거래 커밋 후 executor에서 조회하고 30초 주기로 pending을 재시도한다. 외부 inventory 호출을 핵심 전표 트랜잭션과 분리하는 같은 저장소의 직접 사례다.

### 3-2. 권장 처리

**일반 liveness/readiness를 DOWN으로 만들지 않는다.** 현재 compose의 모든 서비스 healthcheck가 `/actuator/health`를 직접 사용한다. 매핑 한 건의 불일치를 여기에 합치면 컨테이너 restart와 배포 결속으로 다시 기동 실패를 만든다.

대신 다음을 하나의 운영 계약으로 묶는다.

1. `WarehouseMappingVerifier`가 Spring 기동 완료 후 독립 scheduler에서 즉시 1회, 이후 고정 주기로 검증한다. connect/read/call 전체 timeout을 둔다.
2. 상태를 코드별 `VALID / UNAVAILABLE / UUID_NOT_FOUND / EXPECTED_IDENTITY_NOT_FOUND / MISMATCH`로 캐시한다. UUID 원문은 상태 API·metric tag·로그에 넣지 않는다.
3. `WarehouseCodeMapper.resolve(legacyCode)`는 해당 코드가 `VALID`일 때만 UUID를 반환한다. `UNAVAILABLE` 또는 불일치인 **그 코드의 발행만** 503으로 차단하고, slip-service의 다른 업무와 기동은 유지한다.
4. cardinality가 고정된 gauge `warehouse_mapping_invalid_count`, `warehouse_mapping_unavailable_count`, `warehouse_mapping_last_success_age_seconds`를 eager 등록한다. 상태 전이 counter도 둔다.
5. Prometheus rule과 production CloudWatch alarm을 함께 추가해 invalid > 0, unavailable 지속, heartbeat/metric 소실을 SNS로 발송한다. `treat_missing_data=breaching` 또는 동등한 metric 소실 방어를 둔다.
6. 권한 보호된 `GET /admin/slip-warehouse-mappings/status`를 두어 legacy code, expected business label, actual business label, 상태, 마지막 성공/시도 시각, 오류 분류만 반환한다. 기존 terminal API처럼 UUID는 반환하지 않는다. 관리자 화면은 이 API를 읽어 배너/표로 노출할 수 있다.
7. notification-service 운영자 push는 보조 신호로만 사용할 수 있다. CloudWatch/SNS와 관리자 상태가 권위이고 push 실패가 검증 상태를 지우면 안 된다.

이 설계는 “health/readiness 반영 / 경보 / 관리 화면” 중 **경보 + 관리 상태 노출 + 영향 코드 요청별 차단**을 선택한다. 전체 readiness DOWN은 선택하지 않는다.

표본은 0이 아니다. 현재 활성 창고 8건, 설정 UUID 대상 4건, exact legacy code 행 2건이 있다. 이번 라운드에서는 새 표본을 만들지 않았다.

표본 생성 가능성도 이미 실제 경로로 확인돼 있다.

- controller: `POST /inventory/warehouses`
- 화면: 기존 창고 관리 화면과 admin 창고 화면
- 현재 `2`·`00003` 행은 `created_by=a000...0001`이며 S18 QA 보고가 `POST http://localhost:8080/inventory/warehouses`로 생성하고 DB 직접 INSERT를 쓰지 않았다고 기록한다.

즉 회사 PC나 다른 깨끗한 PC에서 표본이 0이면 DB INSERT 없이 실제 관리자 API/화면으로 만들 수 있다. 단, 이번 D1에서는 공유 데이터 추가 생성을 하지 않았다.

## 5. 권장 설계 한 가지와 그것이 일곱 실패를 각각 어떻게 막는지

**권장 설계: “기동 비차단 주기 pair 검증 + 코드별 요청 차단 + metric/CloudWatch-SNS 경보 + UUID 없는 관리자 상태 API” 한 가지다.**

선행 결정은 legacy code → canonical inventory identity 대응표를 확정하는 것이다. 현재처럼 map key와 `warehouses.code`가 같은 네임스페이스라고 가정하지 않는다. 가장 안전한 형태는 inventory 쪽에 legacy alias를 명시적으로 보유해 `legacyCode -> warehouse UUID`를 단일 endpoint로 반환하고, UUID 단건 응답의 business code/name과 pair로 확인하는 것이다.

| 일곱 실패 | 권장 설계의 방어 |
|---|---|
| R2 정상 4개인데 legacy 조회 4/4 404 | legacy alias를 명시한 단일 출처를 사용한다. inventory native `code`와 legacy code를 혼동하지 않는다. |
| R2 일시 장애·늦은 기동·미실재 미구분 | `UNAVAILABLE`(transport/timeout/5xx/401/403)과 `UUID_NOT_FOUND`/`EXPECTED_IDENTITY_NOT_FOUND`를 분리한다. 기동은 유지하고 scheduler가 재검증한다. |
| R4 식별자가 뒤바뀌어도 FOUND | UUID 존재만 보지 않고 `legacy alias -> expected UUID`와 `UUID -> actual identity`를 pair 비교한다. |
| R4 UNAVAILABLE 영구 미검증 | 첫 비동기 실행 뒤에도 고정 주기로 계속 검증하고 마지막 성공 시각/heartbeat를 저장한다. |
| R4 느린 서비스가 timeout 없이 기동 thread block | 외부 조회는 기동 thread 밖이며 connect/read/전체 call timeout을 가진다. scheduler 전용 executor로 다른 scheduler도 막지 않는다. |
| R6 legacy 역조회 4/4 404 재발 | 잘못된 역조회 자체를 제거하고 alias 계약 test + 실 HTTP contract test로 endpoint/응답을 고정한다. |
| R6 불일치를 ERROR log만 남김 | invalid/unavailable gauge와 heartbeat를 CloudWatch alarm→SNS에 연결하고, 관리자 status API/화면에 노출하며, 해당 legacy code의 `resolve` 요청을 503으로 차단한다. |

전체 slip-service liveness/readiness는 유지한다. 잘못된 한 코드가 다른 전표·조회·관리 기능까지 내리지 않게 하면서도, 검증되지 않은 UUID가 실제 발행에 쓰이지 않게 코드별로 fail-closed한다.
