## 15단계 독립 전수 — 누락 0, 명칭은 7+8로 교정

R3 표를 믿지 않고 production service의 저장/dirty mutation과 controller 도달점을 다시 셌다.

- 실제 `stock_balances` 또는 `stock_movements`를 쓰는 업무 진입점: **7개**.
  - `StockService`: inbound, reserve, release, deduct, adjust — 5개.
  - `InboundInspectionService.completeInspection` — 1개.
  - `InventoryAuditService.complete` — 1개.
- `stock_instances`만 변이하는 `StockInstanceService`: **8개**.
  - create, inboundBatch, reserveBatch, shipBatch, releaseBatch, recallBatch, unrecallBatch, resellBatch.
- 합계: **전체 재고 변이 15개 = balance/movement 계열 7 + serial instance 계열 8**.

따라서 “balance/movement 쓰기 15개”라는 표현은 부정확하지만, R3이 의도한 전체 재고 변이 모집단 15개에는 누락이 없다. movement save는 `StockService.java:212,266,313,365,401`, `InboundInspectionService.java:292`, `InventoryAuditService.java:386`의 7곳이다. serial 변이는 `StockInstanceService.java:80,130,179,205,231,276,360,401`의 8곳이다. 각 변이 전에 공통 게이트가 있다.

dev profile/property guard 아래의 `StockBalanceSeeder`와 `StockInstanceSeeder`는 운영 업무 진입점이 아니므로 제외했다. production caller가 0인 dead lot mutation과 문서 상태만 바꾸는 StockTransfer도 제외했다.

## InventoryProductGate 동등성

신설 게이트는 다음 한 식이다.

```java
return !product.goods() || "BUNDLE".equals(product.productType());
```

직전 구현과 diff를 대조하면 `StockService`, `StockInstanceService`, `InboundInspectionService`의 기존 로컬 식이 위 공통 호출로 치환됐을 뿐이다. 기존 상수 값도 모두 `"BUNDLE"`이었다.

| 입력 | 기존 판정 | 신설 판정 |
|---|---:|---:|
| `goods=false` | 제외 | 제외 |
| `goods=true, productType=BUNDLE` | 제외 | 제외 |
| `goods=true, productType=SINGLE` | 허용 | 허용 |
| `goods=true, productType=null/blank` | `ProductSummary`가 SINGLE 정규화 후 허용 | 동일 |

production inventory-service에 동일 판정을 독자 구현한 잔존 지점은 0개다. 공통 호출축은 StockService, StockInstanceService, InboundInspectionService, InventoryAuditService 하나로 수렴한다.

## 실 DB 쓰기 경계

- 사용자 지시의 배포본 정렬을 위해 product-service를 재기동했고, 그 결과 서비스가 공유 product DB에 V33을 자동 적용했다. 이는 위 배포 단계에 원문과 시각을 명시했다.
- 그 이후 공유 DB 수동 쿼리는 모두 read-only transaction이었다.
- 라이브 상품 PATCH는 공유 DB가 아니라 삭제 가능한 일회용 격리 DB에만 수행했다.
- inventory-service/V25는 공유 DB migration write를 피하기 위해 재배포하지 않았다.
