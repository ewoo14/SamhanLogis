# PR #1154 R22 fix — 패널 배선 재수렴

## 판정

①~④의 원인 수정과 자동 회귀 테스트는 통과했다. 실제 관리자 화면의 우회 없는 적재→보류 패널→페이지 넘김은 실행했으나, 현재 Vite 화면에서 적재 요청이 완료 결과 state에 도달하지 않아 증거 캡처를 만들지 못했다. 이 실패를 GREEN으로 포장하지 않았다.

성능 ⑤는 수정하지 않았다.

## RED 원문 — 수정 전

### RED-A① 응답 봉투

R21 실측 원문:

```text
partnerImportApi.ts 는 response.data.data 를 읽지만 partner controller
POST /admin/partners/imports/ecount
GET  /admin/partners/imports/ecount/rejections
가 raw DTO 를 반환한다.

작은 파일도 적재 결과가 undefined가 되고 페이지는 data.items에 도달하지 못한다.
production 코드 그대로는 적재 결과 → 보류 패널 진입 불가.
```

수정 전 `EcountPartnerImportController`의 세 메서드는 `EcountPartnerImportResult` / `EcountPartnerRejectionPage`를 직접 반환했다.

### RED-A② mock hard gate

수정 전 mock 회귀 원문:

```text
거래처 적재 mock handler 계약 > POST CSV endpoint
expected response not to be null, received null
거래처 적재 mock handler 계약 > POST XLSX endpoint
expected response not to be null, received null
거래처 적재 mock handler 계약 > GET 보류 페이지 endpoint
expected response not to be null, received null
```

이는 `client.ts`가 adapter를 설치하지 않고 실제 `http://localhost:8080` XHR로 빠지는 조건이다.

### RED-A③ / RED-B③ 행별 인코딩

수정 전 R21 JSON 원문:

```json
{
  "rowNumber": 4,
  "reason": "CSV_ENCODING",
  "rawPartnerCode": "읽을 수 없음",
  "rawName": "읽을 수 없음"
}
```

실제로 line 4는 UTF-8 정상 행이었다. 기존 `decodeCsv()`는 파일 전체 strict decode 실패를 `encodingHeldResult()`로 보내 모든 데이터 행을 보류했다. 행 번호 자체는 유지되어야 한다는 R20 회귀도 보존 대상으로 고정했다.

### RED-A④ 새 파일 page state

R21 실측 원문:

```text
200건 2 / 2 상태에서 201건 새 파일을 적재한 뒤
1 / 3이 아니라 2 / 3, 첫 visible row 103.
sourceFileHash 변경 때 PartnerImportRejectionPanel의 page state가 0으로 초기화되지 않음.
```

## 변경 API 전수 × mock handler

| API | 용도 | 수정 전 handler | R22 상태 |
|---|---|---:|---:|
| `POST /admin/partners/imports/ecount` | CSV 적재 결과 | 없음 | 있음, ApiResponse 봉투 |
| `POST /admin/partners/imports/ecount-xlsx` | XLSX 정본 적재 결과 | 없음 | 있음, ApiResponse 봉투 |
| `GET /admin/partners/imports/ecount/rejections` | hash 기준 보류 페이지 | 없음 | 있음, ApiResponse 봉투 |

기존 FE API 클라이언트는 저장소 표준을 따라 세 응답 모두 `response.data.data`를 읽도록 유지했다. BE controller를 `ApiResponse.ok(...)`로 표준화하여 실제 gateway 계약과 FE 계약을 일치시켰다.

## 수정 내용

- `EcountPartnerImportController`: CSV, XLSX, rejection page를 `ApiResponse`로 반환.
- `EcountPartnerImporter`: UTF-8 헤더가 정상인 파일은 UTF-8 replacement decode 후 행/셀의 `U+FFFD`만 보류. 읽힌 거래처 코드는 보존하고 훼손된 상호 셀만 `읽을 수 없음`으로 표시.
- `PartnerImportRejectionPanel`: `sourceFileHash` 변경 시 `page=0`, 결과 state 초기화.
- `mock.ts`: 변경 API 3종 handler와 envelope fixture 추가.
- API/패널/importer 회귀 테스트 추가.

## RED-D 정상 CSV 4종

R21 기준선: UTF-8 한글, UTF-8 ASCII, CP949 한글, UTF-8 구두점·역슬래시 4종 모두 보류 0건이며 입력 문자열을 완전 보존했다. R22 importer 변경은 UTF-8 헤더 정상 파일의 행별 보류 판정만 바꾸고 CP949 전체 파일 경로는 기존 strict MS949 경로를 유지한다. 자동 R17/R22 mixed encoding 테스트가 이를 보강한다.

## ⑤ 성능 측정 및 범위 제외

R21 live boundary 측정은 다음과 같다.

```text
desktop apiClient timeout: 10,000 ms
1,000행 upload: backend 동기 완료까지 약 4분
UI: 10초 시점에 먼저 실패 표시
partner log: 이후 MIG-1 import 완료 로그 관측
```

이번 R22에서는 timeout, 비동기 job, batch, parser 또는 DB write 구조를 변경하지 않았다. 현재 증거로 확정 가능한 병목 구간은 `gateway request → partner 동기 import 완료`이며, 그 안의 CSV parsing 대 DB row write 비율은 별도 계측 없이는 분리할 수 없다. 성능 축으로 개발책임자 판단을 남긴다.
