## 3. 양방향 — MANAGER 외 역할이 잃거나 얻은 권한

V98 적용 구간의 전수 audit 차집합은 MANAGER 대상 5행뿐이다. role template 전체의 적용 전후 차이는 다음 한 셀로 복원된다.

```text
MANAGER | inbound.inspection | UPDATE false → true
그 밖의 role × page × 7 action 변화 0
```

현재 `inbound.inspection` role template 전수:

```text
MASTER/WAREHOUSE/INVENTORY 1111000
MANAGER                    1010000
ACCOUNTANT/DEVELOPER/DISPATCH/DRIVER/PARTNER/SALES/STAFF 0000000
```

따라서 V98 자체에서는 MANAGER가 다른 권한을 잃지 않았고, 다른 역할도 얻거나 잃은 비트가 없다. SALES 실 API·UI 차단도 §6에서 다시 확인했다.

## 4. 표본 0의 원인 — 서로 다른 두 검수 축

### slip-service 축

`slips`의 `INBOUND + INSPECTING + active`는 2건이며 둘 다 입고창고와 라인 1개가 있다. 이 상태는 `SlipDetailPage`의 lifecycle action `inspect`가 발화하는 표본이다.

```text
2026/08/08-3 | INSPECTING
2026/08/08-4 | INSPECTING
```

FE는 이 버튼에 다음 두 권한을 동시에 요구한다.

```text
slip.transfer.process:UPDATE
inbound.inspection:UPDATE
```

### inventory-service 축

`inbound_inspections`는 slip 상태 전이로 자동 생성되지 않는다. 구매관리의 `SAVED/CONFIRMED` 행에서 “검수”를 열어 다음 GET을 호출할 때 지연 생성된다.

```text
GET /api/v1/inventory/inbound-inspections/{slipId}
→ getOrCreateInspection()
→ 헤더 + 라인 INSERT (없을 때)
```

따라서 이 GET은 이름과 달리 DB write가 발생해 이번 검증에서는 호출하지 않았다.

현재 inventory DB:

```text
활성 inbound_inspections 헤더 0
활성 헤더 기준 UI 목록 0
soft-deleted PENDING 헤더 1 (전표번호 2026/03/31-1)
그 삭제 헤더 아래 active line 5
```

이 과거 헤더는 현재 INSPECTING 2건과 전표번호도 다르다. 즉 “전표는 2건인데 inventory 표본은 0”은 누락 동기화가 아니라 **서로 다른 저장소·생성 조건·업무 단계의 수치를 비교한 것**이다.

### 실 관리자 생성 경로 가능 여부

가능하다. 현재 후보는 `SAVED 4 + CONFIRMED 1 = 5건`이고, 그중 `2026/08/08-5(SAVED)`는 구매관리 기본 날짜 범위에도 들어온다. MANAGER가 구매관리의 “검수”를 열면 상세 GET이 inventory 헤더를 만든다. 실 DB write 금지에 따라 버튼을 열지는 않았다.

한편 lifecycle INSPECTING 2건은 이미 읽기 전용으로 상세 화면을 열 수 있으므로 R6의 “버튼 판정 불가”는 잘못된 축을 선택한 결과다. 이번 라이브 QA에서 MANAGER의 `완료 (처리 완료)` 버튼이 **visible + enabled**임을 확인했다.

## 7. 도달 가능한 결함 1건

### 결함 1 — V98 선적용 DB에서 #1145 V97을 포함한 auth-service가 기동 불가

**실 사용자 경로**

1. PR #1130/V98이 적용된 환경에서 auth DB schema history는 v98이고 V97은 없다.
2. 아직 머지 전인 #1145가 이후 배포되어 migration tree에 V97과 V98이 함께 존재한다.
3. auth-service 시작 시 Flyway validation이 수행된다.
4. validation 실패로 auth-service가 기동하지 못해 로그인·권한 조회 경로가 가용하지 않다.

**재현 절차**

- 공유 DB는 읽기만 했다.
- 시스템 임시 폴더에 #1145 migration tree를 archive하고 현재 V98을 복사했다.
- 공유 `auth_db`를 대상으로 Flyway `validate`만 실행했다.
- 임시 폴더는 즉시 제거했다.

**원문 근거**

```text
Database: jdbc:postgresql://samhan-postgres:5432/auth_db (PostgreSQL 16.14)
ERROR: Validate failed: Migrations have failed validation
Detected resolved migration not applied to database: 97.
To ignore this migration, set -ignoreMigrationPatterns='*:ignored'.
To allow executing this migration, set -outOfOrder=true.
FLYWAY_VALIDATE_EXIT=1
TEMP_REMOVED=...
```

`application.yml`에는 `out-of-order` 설정이 없으므로 Flyway 기본값 false다. 현재 공유 DB가 이미 이 순서에 도달했고 #1145는 OPEN이므로 추상적 위험이 아니라 다음 auth-service 재배포에서 바로 도달한다.
