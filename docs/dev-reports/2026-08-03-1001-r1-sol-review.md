# PR #1061 R1 SOL 적대검증 — 실 사용자 도달성

## 결론

**도달 가능한 결함 5건**이다.

이번 라운드는 테스트 강도, mock 충실도, 문서 표현은 평가하지 않았다. 오직 PR 변경 표면에서 사용자가 정상 조작으로 도달하는 결과만 판정했다. 정적 의심만 있거나 선행 blocker 때문에 실제 출력 결과까지 도달하지 못한 항목은 결함 수에서 제외하고 `미판정`에 남겼다.

- 사용자 조작: 출고전표를 처리하여 재고 차감/출고 단계로 보낸 뒤 원장을 조회한다. `COMPLETED`에서 원장에 보이던 전표에 `[배송 시작]`을 실행하면 `SHIPPING`이 되어 사라지고, `[배송 완료]` 후 `DELIVERED`가 되면 다시 나타난다. 재고 차감 직후 `INSPECTING` 5건도 처음부터 빠진다.

도달 결함 0건이다. 정상 생성, 수기 PUT, 견적 변환, 주문 단일/병합, 모바일, 스냅샷 복원은 저장 도메인을 보존한다. 원장 DTO는 `supplyAmount + vatAmount`를 우선하고 FE는 `lineAmount`를 그대로 debit에 쓸 뿐 VAT를 재가산하지 않는다.

## 미판정 및 이번 라운드가 실제 출력까지 보지 못한 표면

1. **인쇄 배송주소**: `partnerLedgerApi.ts`가 `deliveryAddress`를 `LedgerLine`에 넣지만 `PartnerLedgerView.tsx:223-230`의 로컬 변환이 버리고, 인쇄 표 `289-328`에도 주소 열이 없다. 구조상 non-null 주소도 인쇄에서 소실되지만 D4 hook crash가 먼저 발생해 이번 라운드에서는 실제 인쇄 결과까지 관찰하지 못했다. 따라서 의심이 아니라 강한 코드 결함 후보이나, 사용자의 “실제 재현만 결함 집계” 규칙에 따라 결함 수에서 제외했다.
2. **인쇄 0 표시**: `PartnerLedgerView.tsx:197-200`의 `formatBalance(0)`은 `krw(0)`인 `0`을 반환하고 일부 0 셀은 공란이다. 신규 adapter는 opening/line/closing balance를 모두 0으로 만든다. 역시 D4 때문에 성공 인쇄 화면까지 도달하지 못해 집계 제외했다.
3. **V12 이전 all-null legacy 금액 fallback**: `PartnerLedgerSalesResponse.java:85-89` 최후 fallback은 VAT 누락 가능성이 있으나 대상 DB 행이 0건이고 현행 사용자 입력 factory로 만들 수 없어 미판정이다.
4. Docker 이미지는 공유 스택 보호 지시 때문에 재빌드하지 않았다. 따라서 PR head의 새 accounting/slip endpoint를 실 Docker HTTP로 호출한 결과, 실제 Electron 창 캡처, 인쇄/PDF 출력은 보지 않았다.
5. `accounting-service` 전체 suite, 전체 desktop Vitest/Playwright, 다른 PR 표면은 지시대로 보지 않았다.
6. 현재 DB의 출고 단계 31건은 `partner_id`는 있으나 `partner_code`가 비어 있다. dev seed 특성인지 운영 migration 결함인지 이 라운드의 read-only 증거만으로 가르지 못해 독립 결함으로 세지 않았다.

## 작업 무결성

- git 조회 명령만 사용했다. commit/push/checkout/branch/stash/reset을 실행하지 않았다.
- 공유 DB에는 `SELECT`만 실행했다. write/DDL은 실행하지 않았다.
- Docker 이미지 재빌드는 실행하지 않았다.
- `npm install` 후 tracked lockfile 변경은 없었다.
- 최종 `git status --short`에서 본 보고서 1개만 신규 파일이어야 한다.
