## 작업 개요

- 대상 PR: #1061
- 대상 HEAD: `ee84ed20a` (detached HEAD)
- 작업일: 2026-08-04
- 담당: Codex
- 목적: R28 이후 발생한 백엔드 `LedgerSnapshotPersistenceIT` 실패와 프런트 `mock.test.ts` 문서번호 계약 실패를 현재 계약에 맞게 수정

## 불변식 및 범위

- `LedgerSnapshotService.capture` 저장 내용은 화면 read model인 `PartnerLedgerReadService` 결과를 유지한다.
- 조회 경로는 snapshot을 사용하지 않는다.
- 신규 `documents` payload와 구형 `LedgerImageResponse` payload 복원을 모두 유지한다.
- 테스트 단언/문서번호 계약을 느슨하게 만들지 않는다.
- 사용자가 지정한 두 검증 명령만 실행한다. 전체 테스트, Docker 재빌드/재배포, DB 쓰기, Git 명령은 실행하지 않는다.
- 코드 조사 전에 이 보고서 파일을 생성했다.

### 단계 1 조사 결과: 실패 원인 확인

#### 백엔드

- `LedgerSnapshotPersistenceIT`는 `ledgerSnapshotService.capture(...)`를 직접 호출한다.
- 따라서 테스트가 확인하는 행위는 R24 이전의 GET 진입 자동저장이 아니라, 현재 계약의 명시적 snapshot 저장이다.
- 현재 테스트 이름/클래스 Javadoc/메서드명이 `자동저장`이라고 되어 있어 R24 계약과 어긋난다. 단언 자체는 `processed_by`, `data_snapshot_json IS NOT NULL`, `batch_no` 길이만 확인하며 GET 자동저장을 단언하지 않는다.
- R28 이후 `LedgerSnapshotService.capture`는 `PartnerLedgerReadService.read`를 호출한다. Spring 통합 컨텍스트의 실제 `PartnerLedgerReadModelService`는 `PartnerLedgerSalesClient.find`를 호출하므로, 기존 IT가 이 외부 client를 mock하지 않아 `capture` 내부 read model 구성에서 실패할 수 있다.
- `PartnerLookupClient`의 구형 Optional 메서드만 stub하는 기존 설정은 `PartnerLookupSupport`의 호환 fallback으로 동작할 수 있으나, 현재 계약을 명확히 하려면 `findByPartnerCodeResult`를 stub하는 편이 맞다.
- 수정 방향: `PartnerLedgerSalesClient`를 `@MockBean`으로 격리하고 빈 판매전표를 반환하게 하며, 테스트 설명을 “명시적 저장”으로 바꾼다. `PartnerLedgerImageService`/snapshot을 조회 경로로 되돌리지 않는다.

#### 프런트

- `clients/desktop/src/renderer/api/mock.test.ts`는 `DOCUMENT_NO_KEY_SET` 필드 값에 대해 표준 문서번호 정규식 또는 `ALLOWED_NON_DOCUMENT_MARKERS` 명시 marker만 허용한다.

## DEBUG REPORT

Symptom: R28 이후 `LedgerSnapshotPersistenceIT`가 `slip-service` 인스턴스 부재로 실패했고, `mock.test.ts` 문서번호 계약이 `J-001` fixture를 위반으로 보고했다.

Root cause: 저장 원천이 `PartnerLedgerReadService`로 바뀐 뒤 IT가 새 `PartnerLedgerSalesClient`를 mock하지 않아 snapshot 저장 전에 외부 load balancer를 호출했다. 프런트 legacy 복원 fixture의 `J-001`은 표준 `YYYY/MM/DD-N` 문서번호 형식이 아니었다. Vitest 원문에서 검출된 violation 배열은 1개이며, `[ { …(3) } ]`의 3은 단일 violation 객체의 속성 수다.
