외부 호출을 직접 수행하므로 R39가 금지한 `수정완료` 응답 정지가 되살아난다.

## ② 불변식 — 무엇이 참이어야 하는가

1. 저장 201이 확정된 알림은 실제 전달됐거나 재시도 가능한 상태로 남아야 하며, 프로세스의 정상 종료와
   executor 제출 거부만으로 조용히 사라지면 안 된다.
2. 알림 보존 때문에 auth/notification 외부 호출을 저장 잠금 구간이나 `afterCommit` 요청 스레드에서
   동기 실행해 사용자 응답을 다시 멈추게 하면 안 된다.
3. 한 저장당 동일 수신자·동일 변경 알림은 최대 1회여야 하며, 재시도·종료 복구가 중복/phantom 알림을
   만들면 안 된다.
4. 롤백된 mutation·감사·리비전·ACCEPTED 이력에는 알림이 없어야 한다.
5. genuine 잠금 획득 실패/timeout은 UUID·JDBC 원문 없는 409와 재확인 문구를 유지해야 한다.
6. 잠금과 무관한 query timeout은 `다른 사용자가 수정 중`이라는 거짓 409로 내려가면 안 된다.
7. same-field stale 409, different-field same-baseline 양쪽 보존, 성공 이력 원자성은 그대로 유지돼야 한다.
8. 알림 실패는 이미 성공한 저장을 rollback시키거나 사용자 화면에 내부 UUID를 노출하면 안 된다.

## ③ 양방향 RED

### RED-A — 되돌리면 안 되는 것

- 느린 auth 조회와 notification 전송 중에도 첫 `수정완료` 응답과 두 번째 different-field 저장이 외부
  호출 완료를 기다리지 않는다.
- 같은 필드 stale 저장은 409이고 승자의 전표값·감사·리비전·ACCEPTED 이력이 보존된다.
- 서로 다른 필드의 same-baseline 병렬 저장은 도착 순서와 무관하게 둘 다 최종 전표에 남는다.
- rollback된 트랜잭션은 알림을 만들지 않고, 성공 저장의 알림 본문과 409 응답은 UUID를 노출하지 않는다.
- genuine `LockTimeoutException`/비관적 잠금 실패는 재확인 가능한 409를 유지한다.
- **반대급부:** 알림 유실을 막는 fix가 외부 호출을 저장 트랜잭션·행 잠금 안으로 되돌리거나,
  `afterCommit` 요청 스레드 동기 발송·무제한 대기로 응답 정지와 다른 저장 기아를 다시 만들면 RED다.
- **반대급부:** query timeout 과대매핑을 줄이는 fix가 genuine 잠금 timeout을 다시 일반 500으로 만들거나
  내부 SQL·UUID 원문을 노출하면 RED다.

### RED-B — 재발하면 안 되는 것

- 알림 worker를 latch로 붙잡고 후속 알림을 큐에 둔 뒤 애플리케이션 컨텍스트를 정상 종료했을 때,
  이미 201로 커밋된 알림이 전달도 되지 않고 재처리 상태에도 남지 않으면 RED다.
- executor가 제출을 거부한 상태에서 auth/notification을 느리게 했을 때 `수정완료` HTTP 응답이 그
  외부 timeout만큼 멈추거나, 저장은 성공했는데 알림이 조용히 사라지면 RED다.
- 종료 복구나 재시도 뒤 동일 수신자에게 동일 저장 알림이 두 번 가거나, rollback 저장 알림이 가면 RED다.
- 잠금 cause가 없는 `QueryTimeoutException`이 409 `다른 사용자가 전표를 수정 중입니다`로 내려가면 RED다.
- genuine 잠금 timeout이 500 또는 내부 식별자 포함 응답으로 내려가면 RED다.
- 성공 응답인데 전표 변경·감사/리비전·ACCEPTED 중 일부만 빠지면 RED다.
