## 4. 전잔·후잔 영향과 #1172 충돌 여부

**충돌하지 않는다.** 이유는 직접수정 상태 경계가 R22 판매 상태 경계보다 앞에 있기 때문이다.

```text
직접 수정 허용     DRAFT, SAVED
R22 판매 반영      CONFIRMED, DELIVERED, COMPLETED, INSPECTING, SHIPPING
```

코드 원문:

```text
Slip.java:65-66
EDITABLE_STATUSES = EnumSet.of(SlipStatus.DRAFT, SlipStatus.SAVED)

SlipDetailPage.tsx:1459-1460
return status === 'DRAFT' || status === 'SAVED'

PartnerLedgerContract.java:16-17
CONFIRMED, DELIVERED, COMPLETED, INSPECTING, SHIPPING
```

따라서 품목 추가·수량/금액 수정 시점의 해당 전표는 원장 판매 projection에 들어가지 않는다. 직접수정은 회계 분개나 재고를 역수정하지 않고 전표 DRAFT/SAVED와 revision/audit, 가격기억만 갱신한다. 이후 lifecycle이 R22 상태에 도달할 때 **수정 완료된 현재 라인 금액**이 한 번 반영된다.

#1172 계약도 그대로 유지된다.

- `PartnerLedgerReadModelService.java:45,583` — 공유 `CANONICAL_SALE_STATUSES` 직접 사용.
- `:586-590` — `JournalSourceType.SLIP`이면서 `journalNo`가 canonical `slipNo`와 exact match일 때만 중복 제거.
- `:339-341,520-522` 및 `JournalLineRepository` — `POSTED + REVERSED`를 함께 읽어 보상쌍 상쇄.
- MANUAL/번호가 다른 역분개는 exact 조건에 걸리지 않아 보존.

수정 성공 시 FE가 `['slip', id]` 캐시를 응답으로 즉시 교체하고 목록을 invalidate한다. 전잔·후잔 query key는 `id + partnerCode + from`이다. 동일 거래처의 DRAFT/SAVED 금액 수정은 R22 계산 대상이 아니므로 ledger 재조회 불필요하고, 거래처를 바꾸면 `partnerCode`가 바뀌어 새 query가 실행된다. 이 수정 화면은 전표일자·전표번호를 바꾸지 않는다.

## 5. 계보(`instanceKey`) 관계

#1131은 단순히 계보만 추가한 PR이 아니라 **#1071 품목 추가를 같은 PR S2로 구현한 트랙**이다. 두 기능은 의도적으로 한 저장 경계에서 수렴했다.

### 기존 라인

- 상세 hydrate가 `line.setOptions`를 보존하고 `bundleInstanceKey = line.setOptions?.instanceKey`로 읽는다.
- Y.Doc projection이 `bundleInstanceKey`를 읽어 `setOptions.instanceKey`로 재구성한다.
- payload가 `setOptions`와 기존 `lineId`를 함께 보낸다.
- BE `BundleLineageResolver`가 `(parentSetModel, instanceKey)`를 인스턴스 정본으로 사용하고 기존 계보를 복원·검증한다.

### 신규 SINGLE

- 품목 확정 시 Y.Doc 행으로 승격하지만 영속 `lineId`는 `null`이다.
- SINGLE이므로 `instanceKey`는 없다. 정상이다.

### 신규 BUNDLE

- FE `expandSalesBundleProductSelection`이 한 번의 전개에 단일 `instanceKey`를 만들고 모든 구성품의 `setOptions.instanceKey`에 넣는다.
- payload는 BUNDLE 부모 원본이 아니라 전개된 구성품들과 부모 계보 메타데이터를 보낸다.
- BE가 부모 membership·canonical head를 재검증하고 키가 없으면 `ensureInstanceKey()`로 생성한다.
- 동일 BUNDLE을 두 번 추가하면 서로 다른 instance key가 생긴다.

머지 후 V119 실서버 확인 보고서 원문:

## 6. 수정 가능한 상태와 재고·회계

수정 가능 상태는 **DRAFT와 SAVED만**이다. FE와 BE가 이중으로 같은 경계를 강제한다.

- FE `canOpenDirectEdit()` → `isDirectEditStatus()` + `sales.slip.edit/update`.
- BE `Slip.updateSalesHeader()`와 `Slip.replaceSalesLines()` → `requireEditable()`.
- BE `EDITABLE_STATUSES` → `DRAFT`, `SAVED`만.
- 다른 상태는 `409 CONFLICT`, “라인 수정 가능한 상태가 아닙니다”로 거부.

따라서 발행/진행 후 상태(`SENT`, `ACCEPTED`, `PROCESSING`, `INSPECTING`, `COMPLETED`, `SHIPPING`, `DELIVERED`, `CONFIRMED` 등)는 direct PUT으로 수정할 수 없다.

재고·회계 영향:

1. DRAFT/SAVED 수정 서비스에는 inventory-service나 accounting-service 호출이 없다.
2. 기존 라인은 soft-delete하고 replacement line을 저장한다. revision `EDIT`와 audit `SLIP_EDIT`를 남긴다.
3. 가격기억은 전표 저장 성공 후 after-commit으로 갱신한다.
4. 아직 재고 전이·R22 원장 반영 전이므로 보상 재고/역분개가 필요하지 않다.
5. 발행 후 수정 자체가 막혀 있으므로 “발행 후 수정 시 재고·회계를 어떻게 되돌릴지”라는 미정 계약은 현재 도달하지 않는다.
