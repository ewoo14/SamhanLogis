## 확인 3 — V22 기존 데이터 적용 가능성 실 DB 읽기 전용 실측

V22와 동일한 partial-index 조건으로 `inventory_db`를 `BEGIN READ ONLY` 안에서 조회했다.

출력 원문:

```text
BEGIN
 duplicate_groups | duplicate_lot_rows
------------------+-------------------
                0 |                  0
(1 row)

COMMIT
```

보조 원문:

```text
 qualifying_active_lots
------------------------
                      0
(1 row)

 version | description | success
---------+-------------+--------
(0 rows)
```

- 기존 중복 그룹은 **0건**, 그 그룹에 속한 lot도 **0건**이다.
- 현재 공유 DB에는 V22가 아직 적용되지 않았고, V22 대상 형식의 활성 lot 자체가 0건이다.
- 따라서 **현재 측정한 DB에서는 기존 중복 때문에 V22 생성이 실패하지 않는다.** 다만 이는 빈 모수에서의 결과다.

## 확인 4 — BLOCKER: 정상 동일 품목 복수 라인의 두 번째 수량이 막힘

저장소 계약 확인:

- `SlipService.create`는 조회용 품목 ID 목록만 `distinct()`하고, 실제 전표 라인은 요청의 모든 라인을 순회해 각각 추가한다. `slip_lines`에도 전표별 품목 unique 제약이 없다.
- 기존 `complete_inbound_duplicateSerialProductLines_aggregatesQuantityForIdempotentBatch`는 같은 전표에 모델코드 `MODEL-SERIAL` 수량 2와 3의 두 라인이 공존하는 것을 정상 계약으로 박제한다.
- 이 테스트를 재실행한 원문:

```text
> Task :services:slip-service:test

BUILD SUCCESSFUL in 42s
18 actionable tasks: 18 executed
```

그러나 비시리얼은 전표 완료가 두 라인을 합치지 않고 라인별로 `inventoryClient.inbound`를 호출한다. 첫 호출 뒤 같은 `(전표번호·품목·창고)` lot가 생기므로 두 번째 호출은 새 애플리케이션 가드에서 no-op이다. 해당 no-op 테스트 재실행 원문:

```text
> Task :services:inventory-service:test

BUILD SUCCESSFUL in 31s
18 actionable tasks: 18 executed
```

V22와 같은 unique index를 일회성 PostgreSQL에 적용하고 전표번호 `2026/08/01-1041`, 모델코드 `SHA-W15K`, 창고 `HQ-001`의 정상 라인 수량 2와 3을 차례로 넣은 실측 원문:

```text
CREATE TABLE
CREATE INDEX
INSERT 0 1
DO
 model_code | warehouse_code |     lot_no      | stored_lot_rows | stored_quantity
------------+----------------+-----------------+-----------------+----------------
 SHA-W15K   | HQ-001         | 2026/08/01-1041 |               1 |               2
(1 row)

NOTICE:  second normal line blocked: unique_violation
```

일회성 PostgreSQL은 출력 직후 제거했다.

**재현 판정: 전표 경로 하나만 실행한 정상 흐름에서도 같은 비시리얼 품목이 두 라인(2+3)으로 있으면 재고는 5가 아니라 첫 라인 2만 증가한다.** V22는 동시 실행에서 두 번째 lot를 오류로 막고, 애플리케이션 조회 가드는 순차 실행에서 이를 조용한 no-op으로 바꾼다. 정상 입고를 막는 실제 회귀이므로 BLOCKER다.

분할·부분 입고에 대해서는 사용자 매뉴얼이 부족분을 “차후 추가 입고 전표”로 보정하도록 명시한다. 즉 같은 전표를 재사용하는 부분/추가입고 계약은 확인되지 않았고 새 전표번호라면 V22에 막히지 않는다. 하지만 **동일 전표 내 정상 복수 라인**은 이미 허용된 계약이므로 위 결함은 그대로 성립한다.

## 확인 5 — 검수 경로 단독도 동일 품목 복수 라인에서 누락

- 검수 생성은 전표의 모든 라인을 순회하여 검수 라인을 1:1로 만든다. 동일 품목 라인을 합치거나 거부하지 않는다.
- 검수 완료도 라인별로 같은 `(품목·창고·전표번호)` lot를 조회하고, 첫 라인이 만든 lot를 두 번째 라인에서 발견하면 `continue`한다.
- 확인 4의 일회성 DB 실측은 이 경로에도 동일하게 적용된다. 모델코드 `SHA-W15K` 정상수량 2와 3의 두 검수 라인이라면 저장 수량은 5가 아니라 첫 라인 2다.

**판정: 단일 라인에서는 검수 경로 단독이 정확히 한 번 늘지만, 허용된 동일 품목 복수 라인에서는 검수 경로 하나만 실행해도 두 번째 정상수량이 누락된다.** 따라서 “두 경로 각각 단독 정상 입고” 요구는 일반적으로 충족되지 않는다.

## 확인 6 — 역순(전표 먼저 → 검수 나중)

재실행 명령의 핵심 테스트는 전표 경로 lot가 먼저 있는 상태에서 검수 완료가 lot/balance/movement를 추가 생성하지 않는지 확인한다.

출력 원문:

```text
> Task :services:inventory-service:test

BUILD SUCCESSFUL in 33s
18 actionable tasks: 18 executed
```

- 단일 라인 역순에서는 전표 경로가 먼저 예정수량을 한 번 가산하고, 검수 경로는 no-op이다. 따라서 두 경로를 합쳐 재고가 0회 증가하는 반대 결함은 재현되지 않았다.
- 다만 검수 정상수량이 예정수량과 달라도 두 번째 단계는 전혀 보정하지 않는다. 예컨대 예정 10을 먼저 넣고 정상수량 8을 확정해도 재고는 10으로 남는다. 이는 “재고가 안 늘어남”은 아니지만 검수 경로를 정본이라고 한 설명과는 맞지 않는다.
- 동일 품목 복수 라인에서는 확인 4~5의 첫 라인만 반영되는 BLOCKER가 역순 여부와 무관하게 선행한다.

## 확인 7 — 취소·반품·수정 흐름

취소, 단일 batch 반품 입고, serial 반품 회수, DRAFT 수정 테스트를 분리 재실행했다.

출력 원문:

```text
> Task :services:slip-service:test

BUILD SUCCESSFUL in 43s
18 actionable tasks: 18 executed
```

- 취소는 재고 반영 전 상태에서만 허용되고 inventory 입고를 호출하지 않아 새 lot 가드에 걸리지 않는다.
- DRAFT/SAVED 수정은 재고 반영 전 라인 수정 계약이므로 가드에 걸리지 않는다. INSPECTING 이후에는 기존 잠금 정책이 수정 자체를 막는다.
- serial 반품 회수는 `stock_instances` 회수 경로라 V22 대상이 아니다.
- batch 반품은 기존 lot 입고 경로를 유지하며 단일 라인은 정상 통과했다. 다만 같은 batch 품목이 복수 라인이면 확인 4의 두 번째 수량 누락을 그대로 상속한다.

## 확인 8 — 검수 완료의 입고전표 상태 불변

- `InboundInspectionService.completeInspection`은 inventory-service의 검수 상태와 `stockApplied`만 변경한다.
- 이 서비스가 사용하는 `SlipClient`의 공개 메서드는 `GET /slips/{slipId}` 조회 하나뿐이며, 검수 완료 경로의 실제 호출도 `slipClient.getSlip`뿐이다.
- 확인 2와 확인 6의 검수 완료 테스트가 이 경로로 통과했다.

**판정: 검수 완료가 입고전표 상태를 바꾸지 않는 계약은 이번 가드 뒤에도 그대로다.**

## 최종 판정

**BLOCKER 1건.** `(전표번호·품목·창고)`를 입고 1회가 아니라 lot 1행과 동일시하여, 정상적으로 허용되는 동일 품목 복수 라인의 두 번째 이후 수량을 막는다. 전표 경로 단독과 검수 경로 단독 모두 영향받으며, batch 반품 입고도 같은 형태면 영향받는다.

- 단일 품목 단일 라인: 두 경로 각각 정확히 1회 증가.
- 동일 품목 복수 라인: 첫 라인만 증가하여 정상 합계보다 적게 반영.
- 같은 전표 재사용 분할/추가입고: 현 매뉴얼은 새 추가 입고전표 사용 계약이므로 재현하지 못함.
- V22 기존 데이터 중복: 실 DB 0그룹, 대상 lot 자체 0건, V22 미적용 상태.
- 역순: 선행 전표 경로가 1회 증가하므로 총 0회 증가는 아니나 검수 정상수량 보정은 없음.
- 취소·DRAFT/SAVED 수정·serial 반품: 새 가드 비대상. batch 반품 복수 라인은 BLOCKER 상속.
- 검수 완료의 입고전표 상태 불변: 유지.
