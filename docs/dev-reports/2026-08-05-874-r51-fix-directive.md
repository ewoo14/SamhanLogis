# R51 2차 SOL 적대검증 → fix 지시서 — PR #1057 · 이슈 #874

최종 판정: **실 사용자 경로로 재현 가능한 결함 3건이 있다. 머지 비권고.**

첫 고정 각도부터 보면, 이번 배선 때문에 slip `수정완료` 저장 자체가 외부 auth/notification을 기다리거나
실패하는 경로는 재현되지 않았다. outbox 삽입은 저장 transaction 안에 있지만 외부 호출은 after-commit
executor/scheduler가 수행한다. 다만 정상 알림 차단 1건, 동일 사건 중복 발송 1건, 종결 없는 무한 재시도
1건이 실제 사용자 경로에 남는다.

R47의 영구 미발송 결함은 **동일 키의 순차적인 `FAILED → 재시도 → SENT`** 구간에서는 닫혔다. 반면
R47의 lease 경합 중복은 notification의 로컬 claim이 없어 닫히지 않았다. FCM vendor 자체 exactly-once
한계는 새 결함으로 세지 않았고, 아래 중복 결함은 vendor 호출 전에 로컬에서 막기로 한 계약이 성립하지
않는 경우만 센다.

## ① 좌표 — 파일:줄 전수

### 결함 1 — 동일 PENDING 사건이 로컬 직렬화 없이 gateway에 동시에 두 번 진입한다

- `services/notification-service/src/main/java/com/samhanair/logis/notification/service/NotificationDispatchPersistence.java:19-30`
  — 멱등 키 행을 `PESSIMISTIC_WRITE`로 읽는 transaction은 `prepare()` 반환과 함께 끝난다.
- `services/notification-service/src/main/java/com/samhanair/logis/notification/service/NotificationService.java:126-137`
  — 위 lock이 해제된 뒤 `invokeGatewayWithResult(prepared)`를 실행한다. 기존 행이 `PENDING`이어도
  현재 다른 발송자가 gateway 안에 있는지 구분하지 않고 다시 진입한다.
- `services/notification-service/src/main/java/com/samhanair/logis/notification/service/NotificationService.java:174-190`
  — 30초 지난 PENDING 복구도 조건부 claim/lease 없이 조회 결과를 바로 gateway에 넣는다.
- `services/notification-service/src/main/java/com/samhanair/logis/notification/repository/NotificationRequestRepository.java:22-30`
  — 멱등 키 조회 lock과 PENDING 목록 조회만 있고, 발송권을 원자적으로 획득하는 연산은 없다.
- `services/notification-service/src/main/resources/db/migration/V8__add_notification_idempotency_key.sql:4-6`
  — unique index는 요청 행 하나만 보장하며 같은 행을 잡은 두 호출의 외부 부수효과를 직렬화하지 않는다.

DB/vendor 없이 임시 결정적 RED를 실행했다. 같은 idempotency key의 동일 PENDING 엔티티를 두 요청에
반환하고 첫 gateway를 latch로 정지한 뒤 두 번째 요청을 넣었다. 두 호출이 모두 gateway에 진입했고
`gatewayEntries=2`여서 “최대 1회” 단언이 실패했다.

```text
R51AdversarialTest > samePendingEventMustNotEnterGatewayTwiceConcurrently() FAILED
    org.opentest4j.AssertionFailedError at R51AdversarialTest.java:81
2 tests completed, 2 failed
```

실 경로에서는 첫 notification 요청이 FCM에서 3초 넘게 걸려 slip client가 timeout으로 재시도를 남기거나,
30초 PENDING 복구와 동일 키 재요청이 겹치거나, notification 인스턴스 둘이 같은 오래된 PENDING을 읽으면
같은 사건·수신자의 FCM 호출이 동시에 두 번 일어난다. 이는 R47의 lease 경합 중복 재발이다.

### 결함 2 — V9 적용 뒤 멱등 키 없는 정상 PUSH 요청이 DB 제약으로 차단된다

- `services/slip-service/src/main/java/com/samhanair/logis/slip/client/NotificationClient.java:140-158`
  — 기존 `sendUserPush(...)`는 idempotency key가 없을 때도 JSON에 `idempotencyKey: ""`를 넣는다.
- `services/notification-service/src/main/java/com/samhanair/logis/notification/service/NotificationDispatchPersistence.java:20-30`
  — blank는 중복 조회만 건너뛰고, 정규화하지 않은 `""`를 새 `NotificationRequest`에 그대로 저장한다.
- `services/notification-service/src/main/resources/db/migration/V9__normalize_blank_notification_idempotency_keys.sql:1-8`
  — 적용 시점의 기존 blank만 NULL로 바꾼 뒤, 이후 모든 blank INSERT를 거부하는 CHECK를 추가한다.
- 실 호출 좌표: `DispatchCollabEditService.java:112`, `EstimateCollabEditService.java:111`,
  `SlipEditRequestService.java:355,367`, `CompensationAlertNotifier.java:90`.

임시 RED에서 `NotificationDispatchPersistence.prepare()`에 빈 키 요청을 넣고 영속 엔티티의 키가 NULL이어야
한다고 단언했다. 실제 값은 빈 문자열이라 실패했다. V9가 적용된 PostgreSQL에서는 이 값이
`ck_notification_requests_idempotency_key_not_blank`를 위반한다.

```text
R51AdversarialTest > blankIdempotencyKeyMustNotReachPersistence() FAILED
    org.opentest4j.AssertionFailedError at R51AdversarialTest.java:38
```

호출 서비스들은 notification 실패를 graceful 처리하므로 전표/견적/배차 저장은 대체로 성공하지만,
사용자가 기대하는 정상 PUSH는 나가지 않는다. 특히 이 결함은 V9가 실제 기존 notification_db에 적용된
뒤부터 발생하므로 migration과 코드가 함께 들어가는 이번 PR의 실 사용자 회귀다.

### 결함 3 — 영구 실패·해석 불가 수신자가 명시적 종결 없이 영원히 재시도된다

- `services/slip-service/src/main/java/com/samhanair/logis/slip/collab/SlipCollabNotificationOutbox.java:24,72-74`
  — 상태 집합은 `PENDING/SENDING/SENT`뿐이고 terminal failure/skip이 없다. attempts는 증가하지만
  재시도 간격만 최대 60초로 제한한다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/collab/SlipCollabNotificationOutboxService.java:64-84`
  — UUID 해석 실패, 수정자 자신, notification의 비-SENT, HTTP 실패를 모두 동일하게 `markRetry()`한다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/client/UserIdResolver.java:59-88`
  — `system`, zero UUID, 존재하지 않는 loginId는 정상적으로 empty를 반환하지만 outbox는 이를 terminal
  skip으로 소비하지 않는다.

따라서 과거 `createdBy=system` 등이 수신자 스냅샷에 포함된 수정완료 사건이나 영구 FCM token/adapter
실패는 60초마다 무기한 다시 처리된다. transient 실패 후 성공 가능성은 R48에서 복원됐지만, 성공 또는
명시적 종결로 수렴해야 한다는 R47 불변식은 아직 성립하지 않는다.

### 키 설계·FCM payload·마이그레이션·R50 되돌리기 대조

| 항목 | R51 판정 | 근거 |

`gh pr diff --name-only`로 읽기 전용 대조했다.

## ② 불변식 — 구현 수단 지시 금지

1. 같은 저장 사건·수신자에 대해 한 발송자가 gateway 처리 중이면 다른 HTTP 요청, PENDING 복구,
   scheduler 또는 다른 인스턴스가 동시에 gateway에 진입하면 안 된다.
2. 첫 명시 실패 뒤에는 같은 사건·수신자가 성공까지 재처리될 수 있어야 하지만, 이미 성공했거나 처리 중인
   요청을 재발송하면 안 된다.
3. transient 실패는 복구하고, 영구 실패·수신자 해석 불가·발송 불필요는 유한 횟수 안에 명시적 종결 상태로
   수렴해야 한다. 어떤 row도 60초 간격으로 영원히 vendor 후보가 되면 안 된다.
4. 멱등 키가 없는 기존 notification 소비자는 NULL 의미를 유지해야 하며, V9 적용 뒤에도 정상 알림이
   DB 제약으로 차단되면 안 된다.
5. 같은 ACCEPTED 사건·최종 recipient UUID는 raw 식별자 표현과 재시도 횟수에 관계없이 같은 키를 쓰고,
   서로 다른 ACCEPTED 사건은 독립 키를 써야 한다.
6. slip 수정완료 저장 transaction, 감사, 리비전, ACCEPTED 이력과 HTTP 응답은 auth/notification/FCM,
   PENDING 회수 또는 재시도 종결을 기다리거나 그 실패 때문에 rollback되면 안 된다.
7. 롤백 저장 알림 0, FCM `data.eventId`, UUID 비공개, genuine lock timeout 409와 non-lock timeout 중립 오류를
   유지해야 한다.

## ③ 양방향 RED — 반대급부 필수

### RED-A — 되돌리면 안 되는 것

- 느린 auth/notification, executor 거부, backlog, PENDING 회복 중에도 협업 `수정완료` 응답은 외부 호출을
  기다리지 않는다.
- 롤백된 저장은 outbox/외부 알림 0이고, 성공 저장은 전표·감사·리비전·ACCEPTED를 보존한다.
- 동일 사건·수신자의 첫 명시 실패 뒤 재시도는 gateway에 다시 진입해 SENT로 수렴할 수 있다.
- 서로 다른 정상 저장 사건은 payload가 같아도 독립 알림 사건으로 남는다.
- **반대급부:** 중복 방지를 위해 gateway 호출 동안 slip 저장 transaction/row lock 또는 사용자 HTTP
  응답을 붙잡으면 RED다.
- **반대급부:** PENDING을 무조건 terminal 처리하여 gateway 호출 전 종료 사건을 영구 누락시키면 RED다.
- **반대급부:** 영구 실패 종결을 넣으면서 transient 실패의 자동 회복을 제거하거나, 실패를 SENT로
  가장하면 RED다.
- **반대급부:** blank 정규화 변경으로 호출자가 실제 보낸 nonblank 키를 제거하거나 서로 다른 사건을
  같은 NULL 요청으로 합치면 RED다.

### RED-B — 재발하면 안 되는 것

- 동일 PENDING key의 첫 gateway를 latch로 멈춘 상태에서 두 번째 send 또는 `recoverPending()`을 실행했을
  때 gateway 동시 진입 수가 2면 RED다.
- 두 notification 인스턴스가 같은 30초 지난 PENDING을 동시에 읽었을 때 외부 호출 승자가 둘이면 RED다.
- 첫 gateway 명시 실패 후 같은 키 재시도에서 gateway 호출 수가 그대로 1이거나 SENT로 수렴하지 못하면
  RED다.
- 이미 커밋된 SENT의 응답만 유실한 재시도에서 gateway가 다시 호출되면 RED다.
- idempotency key 없는 기존 PUSH 요청을 V9 스키마에 저장했을 때 CHECK 위반/HTTP 500/알림 누락이 나면
  RED다. 저장되는 값은 blank가 아니어야 한다.
- `system`, zero UUID, 존재하지 않는 loginId 또는 영구 gateway 실패 row가 유한 종결 없이 60초마다 계속
  ready가 되면 RED다.
- 서로 다른 ACCEPTED event가 같은 notification key를 받거나, 같은 event·recipient가 raw 별칭 때문에
  서로 다른 key를 받으면 RED다.
- 롤백 저장 알림, executor 동기 fallback, notification 장애에 의한 저장 rollback, 내부 UUID 화면 노출이
  나타나면 RED다.

## ④ 범위 밖

- FCM vendor 자체의 요청 dedupe, 단건 도달 조회, 기기별 실제 도달률 개선.
- 협업 수정 알림 외 모든 notification 소비자의 멱등 계약 전면 재설계. 단, 이번 V9가 기존 소비자를
  차단하는 결함 2의 호환성 복구는 범위 안이다.
- accounting-service 협업 outbox 재도입 또는 열린 PR #1061의 accounting V96 변경.
- 시나리오 2~5 회계 배분·전기, 다른 트랙 기능 검증.
- Docker 재빌드·재배포·중지, 공유 DB 쓰기/Flyway 실제 적용, 실제 vendor 발송.
- 전체 Gradle/Playwright 게이트와 `clients/desktop/playwright/874-riusage-real-qa.spec.ts` 변경.

안 본 범위: 실제 PostgreSQL migration 적용, 다중 운영 replica, 실제 FCM, 전체 service/desktop 회귀,
accounting 런타임·테스트(compileJava와 삭제 참조 검색만 확인).

## ⑤ 좁힌 명령

먼저 notification-service에 결정적 양방향 RED를 둔다.

```text
1. 동일 PENDING key의 동시 send: 첫 gateway latch 중 두 번째 호출은 gateway에 진입하지 않음
2. send ↔ recoverPending 및 recoverPending ↔ recoverPending 경합: gateway 승자 최대 1
3. 최초 명시 실패 ↔ 동일 key 재시도: 두 번째 gateway 성공 후 SENT
4. 이미 SENT ↔ 응답 유실 재시도: gateway 총 1회
5. key null/blank 요청: V9 계약상 NULL 저장, 정상 gateway 호출
6. transient failure는 회복하되 영구 failure/unresolvable recipient는 유한 terminal 수렴
7. 같은 event의 UUID/loginId raw 별칭은 동일 최종 key, 다른 event는 다른 key
```

```powershell
.\gradlew.bat :services:notification-service:test `
  --tests '*NotificationServiceTest*' `
  --tests '*NotificationIdempotency*' `
  --tests '*NotificationPendingRecovery*' `
  --tests '*NotificationCollabMigrationVersionTest*' `
  --console=plain

.\gradlew.bat :services:slip-service:test `
  --tests '*SlipCollab*' `
  --tests '*NotificationClientTest*' `
  --tests '*GlobalExceptionHandlerTest*' `
  --console=plain

.\gradlew.bat :services:accounting-service:compileJava --console=plain
```

R51에서 수행한 기존 좁은 게이트는 `67 tests, failures=0, errors=0, skipped=0` 및 accounting
`compileJava` 성공이었다. 별도의 임시 RED 2개는 위 결함 1·2대로 실패했고 판정 직후 제거했다.
