## 결함

### 결함 1 — 성공 전이가 저장 가능한 협업 입력까지 무경고 폐기한다

**재현 경로**

1. 협업 수정과 전이 권한이 있는 사용자로 일반 SENT 전표 상세를 연다.
2. `수정`을 눌러 메모 등 협업 필드에 아직 저장하지 않은 값을 입력한다.
3. 폼을 저장하지 않은 채 하단 `완료 (수락)`을 누른다.
4. `accept`는 성공해 ACCEPTED가 되지만 편집 폼은 즉시 사라지고 입력값은 서버에도 브라우저에도 남지 않는다.
5. 다시 `수정`을 열면 전이 전 서버값으로 초기화되어 방금 입력을 복구할 수 없다.

같은 소실은 `process`, `complete`, `inspect`, INBOUND `confirm`에서 재현되며, 이 다섯 도착 상태는 협업 저장이 정상 허용된다. `reject`, SENT `cancel`, OUTBOUND `ship`에서도 dirty 경고나 `저장/폐기/취소` 선택 없이 입력이 사라진다. 협업 저장 mutation이 진행 중이어도 전이 버튼은 그 pending 상태를 보지 않으므로, 사용자가 `수정완료` 직후 전이를 누르면 요청 도착 순서에 따라 저장 성공 또는 409가 갈리는 단일 사용자 경합도 같은 원인에 포함된다.

**필요 동작**: dirty 또는 협업 저장 pending이면 전이를 막거나, `저장 후 전이 / 폐기 후 전이 / 돌아가기`를 명시적으로 선택시켜야 한다. 전이 종류와 무관한 성공 callback에서 폼을 일괄 닫아서는 안 된다.

### 결함 2 — 직접수정·기사 폼은 전이 뒤 남아 새 상태에서 저장 409를 낸다

**재현 경로**

1. OUTBOUND SAVED 전표 상세에서 상단 `수정`을 눌러 직접수정 폼을 열고 값을 바꾼다. 또는 기사 정보 `편집`을 연다.
2. 저장하지 않은 채 하단 `완료 (전송)`을 누른다.
3. 전표는 SENT로 성공 전이하지만 열린 폼은 그대로 남는다.
4. 남은 폼의 `저장`을 누르면 DRAFT/SAVED 전용 PUT/PATCH가 SENT에 호출되어 409가 난다. 직접수정은 이를 실제 원인과 다른 “다른 사용자가 먼저 수정했습니다”로 표시한다.

DRAFT/SAVED에서 `삭제`로 CANCELED가 된 뒤에도 동일하다. 한 번 남은 폼은 status 기반으로 닫히지 않아 사용자가 계속 전이를 누르면 `accept/process/complete/inspect/ship/deliver/confirm`까지 화면에 남을 수 있다. R28은 `collabEditMode`만 닫았고 `salesEditOpen`, `purchaseEditOpen`, `editingDriver`는 처리하지 않았다.

**필요 동작**: 전이와 모든 편집 표면의 dirty/pending 상태를 하나의 조정 경로로 묶고, 성공한 상태 변경 후에는 이전 상태 전용 폼을 저장 가능하게 남기지 않아야 한다. 단순 강제 닫기는 결함 1의 입력 소실을 직접수정 폼에도 복제하므로 dirty 확인이 함께 필요하다.

### 결함 3 — 다른 사용자의 전이는 열린 협업 폼을 닫지 못해 R27의 409가 남는다

**재현 경로**

1. 사용자 A가 OUTBOUND COMPLETED 전표 상세에서 `수정`을 열고 값을 입력한다.
2. 사용자 B가 별도 GUI 세션에서 같은 전표를 열어 `완료 (배송 시작)`을 성공시킨다.
3. A의 브라우저에서는 B의 `transitionMutation.onSuccess`가 실행될 수 없으므로 `collabEditMode=true`가 유지된다. SSE로 새 SHIPPING 상태를 받아도 패널은 status가 아니라 권한과 `editMode`만 보고 폼을 계속 렌더한다.
4. A가 `수정완료`를 누르면 서버의 SHIPPING `COLLAB_LOCKED` 가드에 도달해 409가 난다.

A가 같은 시점에 전이 버튼을 눌러 상태 불일치 409를 먼저 받아도 로컬 `onSuccess`가 없으므로 폼은 남고, 이어진 `수정완료`가 다시 409를 낸다. 즉 R28은 전이를 실행한 한 브라우저의 단일 성공 경로만 닫았고 R27 결함의 동시 사용자 경로는 해소하지 못했다.

**필요 동작**: 상세 status가 편집 불가 상태로 바뀌는 것을 관찰해 폼을 안전하게 종료하되, dirty 입력을 복구·복사할 기회와 명확한 충돌 안내를 제공해야 한다.

## 최종 판정

**실 사용자가 GUI로 밟을 수 있는 결함이 있다: 3건. 현 HEAD 머지 차단.**

R28의 한 줄 callback은 OUTBOUND `ship` 직후 같은 브라우저에서 남은 협업 폼을 다시 제출하는 한 경로는 닫았다. 그러나 (1) 정상 저장 가능한 다섯 도착 상태의 입력까지 무경고 폐기하고, (2) 직접수정·기사 폼은 전혀 닫지 않아 상태 전용 저장 409를 남기며, (3) 다른 사용자 브라우저의 열린 폼에는 효력이 없어 원래 409가 재현된다. 남은 한 번의 fix에서는 세 현상을 각각 땜질하기보다 **전이와 모든 편집 표면의 dirty/pending/concurrent-status를 한 경로에서 조정**해야 한다.

필수 재수렴 표면은 다음과 같다.

- dirty: 전이 전 `저장/폐기/취소` 선택, 무경고 소실 금지
- pending: 편집 저장과 lifecycle 전이 동시 발화 금지
- direct/driver/collab: 세 편집 표면 모두 동일 정책 적용
- concurrent: SSE/refetch로 status 변경 시 stale 폼 저장 금지 + 입력 복구 가능 안내
- failure: 서버 상태 불변 실패는 입력 유지, 동시 상태 변경 409는 stale 폼으로 계속 제출되지 않게 처리
