같은 예외가 `2026/08/10-7`, `2026/08/10-8`, `2026/08/10-9` 모두에서 반복됐다.

## 원인 판정

1. 목록 행 클릭은 이미 `/sales/estimates/2026%2F08%2F10-9`로 이동한다.
2. 상세 화면의 `estimateApi.getEstimate`는 id를 인코딩하지 않고 `/slips/estimates/${id}`에 그대로 붙였다.
3. 따라서 실제 API 요청은 `/slips/estimates/2026/08/10-9`가 됐다.
4. gateway/서버 경계에서 `%2F`가 `/`로 해석됐고, Spring은 `/slips/estimates/{id}` 단일 변수 매핑을 선택하지 못했다.
5. 정적 리소스 핸들러의 `NoResourceFoundException`이 공통 예외 처리에서 HTTP 500으로 반환됐다. 컨트롤러 내부의 견적 조회/DB 예외가 아니다.

웹 저장분은 `snapshotKey`/`draftKey`를 각 전용 API 경로에 인코딩해 보내는 별도 경로라 정상이며, 데스크톱 견적만 `estimateApi.getEstimate`의 원문 path 보간을 사용한 차이가 원인이었다.

## 선택한 방식

쿼리 파라미터 방식 대신 기존 서버 계약의 하이픈 path id를 선택했다.

```text
2026/08/10-9
→ toOrderPathId
→ 2026-08-10-9
→ encodeURIComponent
→ /slips/estimates/2026-08-10-9
```

서버 `EstimateService.getOne(String)`는 이 조회 전용 하이픈 형식을 원래 지원하고 `2026-08-10-9`를 `2026/08/10-9`로 복원한다. 따라서 업무 문서번호 표시 형식은 바뀌지 않고, gateway/Spring의 인코딩 슬래시 경계도 피한다. UUID를 URL에 추가하지 않으며, 쿼리 파라미터 도입에 따른 backend/gateway 계약 변경도 필요하지 않다.
