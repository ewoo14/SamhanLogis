## 원인 실행 확증

소스 원문에서 `CashReceiptService.updateConfirmed`는 다음처럼 헤더 비교만 통과하면 즉시 반환한다.

```text
if (isUnchanged(receipt, request, partner.partnerId())) {
    // 무변경 저장 — 역분개+재게시를 생략해 원장 노이즈(분개 2건/저장)를 차단한다.
    return responseOf(receipt);
}
```

`isUnchanged`의 실제 비교 원문에는 거래처·총액·일자·적요·차변계정·대변계정만 있고 `request.lines()` 또는 `receipt.getLinesJson()` 비교가 없다.

## RED — 헤더 불변 분할 행만 수정

생성값과 동일한 헤더(거래처 P-CR-001, 총액 1,000, 거래일 2026-07-03, 적요 `수기 입금`, 기본 계정)를 유지하고 `600 + 400` 두 행만 PATCH하는 IT를 추가했다. 수정 전 실행 원문:

```text
CashReceiptControllerIT > CONFIRMED에서 헤더 불변 분할 행만 PATCH해도 저장·역분개·재게시한다 FAILED
    java.lang.AssertionError at CashReceiptControllerIT.java:426

1 test completed, 1 failed
BUILD FAILED
```

실패 지점은 `$.data.lines.length() == 2` 검증이다. 헤더만 비교해 무변경으로 판단했으므로 응답은 기존 legacy 1행이며, 테스트는 아직 생산 코드 수정 전 RED 상태다.

## 수정 후 GREEN 및 DB 확인

`linesUnchanged`를 추가해 기존 legacy NULL 행과 요청 분할 행을 의미 비교하도록 수정했다. 수정 후 동일 IT 실행 원문:

```text
CONFIRMED_LINES_ONLY_DB old_status=REVERSED new_status=POSTED new_journal_lines=4 response_lines=2
1 test completed, 0 failed
BUILD SUCCESSFUL in 42s
```

이는 테스트용 DB에서 기존 분개의 상태가 `REVERSED`, 새 분개의 상태가 `POSTED`, 새 분개 행이 4개(분할 2행 × 차변/대변), API 응답 행이 2개임을 직접 확인한 결과다. UUID와 사용자 식별자는 출력하지 않았다.
