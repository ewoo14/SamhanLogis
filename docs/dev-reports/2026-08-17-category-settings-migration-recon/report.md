# 카테고리별 설정을 기초품목에서 견적품목으로 옮기는 방법 정찰

> 조사일: 2026-08-17  
> 범위: 애플리케이션 코드·레거시 GAS·실 DB 읽기·공유 스택 화면 관찰. 애플리케이션 코드, 공유 DB, 컨테이너, Issue/PR은 변경하지 않았다.  
> 용어: 이 보고서의 **품목구분**은 기초품목 세트 구성품 행의 `종류(component_kind)`를 뜻한다. 이카운트식 `products.product_business_type`이나 견적 분류 `cat_l_id/cat_m_id/cat_s_id`와는 다른 필드다.

견적품목 화면은 이미 카테고리 탭과 수량동기화 편집기를 갖는다. `EstimateItemsCatalogPage.tsx:1102-1107`이 현재 탭을 `HOME_MULTI/SINGLE_SET/COMM_MULTI` 규칙 조회 조건으로 넘기고, `:1252-1295`가 규칙을 생성·교체·삭제한다. 요청 DTO에도 `estimateCategory`가 이미 있다(`quantitySyncApi.ts:16-50`). 즉 **수량 규칙의 카테고리 컬럼은 새로 만들 대상이 아니다.**

### 카테고리별 차이 실측

| 실측 | 수치 |
|---|---:|
| 레거시 제품 연동 수량 규칙 | **68계열** = 홈멀티 23 + 싱글 5 + 상업멀티 40 |
| 그중 옵션 조건을 타는 규칙 | **55/68** |
| 같은 옵션 대상 SKU가 별도 카테고리 계산을 타는 쌍(쌍별, 중복 합산 금지) | 홈↔상업 **26 SKU**, 홈↔싱글 **11 SKU**, 상업↔싱글 **19 SKU** |
| 판넬 옵션 목록 | 홈 **5값**, 상업 **6값**, 싱글 **5값** — 세 목록 모두 다름 |
| 리모컨 옵션 목록 | 홈 **4상태**, 상업 **4상태**, 싱글 **4유효상태** — 라벨뿐 아니라 전개 의미가 다름 |
| 서로 다른 카테고리×옵션 목록 정의 | **6개** = 3카테고리 × 판넬/리모컨 2축 |

따라서 “카테고리별로 수량동기화 옵션이 다를 수 있다”는 것은 가정이 아니라 현재 레거시의 실제 구조다. 같은 `AWR-WE13N`도 홈은 전 실내기 유선 선택 합계와 키트를 함께 계산하고, 상업은 덕트 강제 유선 또는 유선 선택만 계산하며, 싱글은 세트별 기본 리모컨 교체와 유선보드 수량을 따로 계산한다.

## ② 대상 3종 현재 위치와 저장 구조

### 2.1 기초품목 화면

세트 품목 편집에서만 `BundleComponentsEditor`가 열린다(`ProductFormPage.tsx:612-614`). 구성품 API는 `GET/PUT /api/v1/products/{modelCode}/components`이며 replace-all 저장이다(`productCatalogApi.ts:684-719`).

구성품 한 행의 현재 필드는 다음과 같다.

- 모델코드·기본 수량: `ProductFormPage.tsx:983-984`
- 품목구분인 `종류`: `:985-987`
- 옵션인 `특징`: `:988-991`
- 옵션 보조축인 `형상`: `:992-994`
- 구성품 수량동기화 방식: `:995-997`
- 금액 배분 비중·고정금액: `:998-1006`
- 구성품 추가·삭제: `:1018-1024`

저장 payload는 `:956-968`에서 `defaultQty`, `qtyMode`, `componentKind`, `componentVariant`, `componentShape`, 배분 필드를 한 번에 전송한다. 세 설정만 옮기더라도 현재의 단일 replace-all 계약을 분리하거나 서버에서 병합해야 한다.

`BundleComponent` 엔티티의 대응 컬럼은 다음과 같다.

- `default_qty`, `qty_mode`: `BundleComponent.java:82-87`
- `component_kind`: `:89-92`
- `component_variant`: `:94-96`
- `component_shape`: `:98-100`
- `is_default`: `:102-104`
- 가격 배분 필드: `:118-126`

`bundle_component` 자체에는 `estimate_category`가 없다. `bundle_product_id` 부모가 `product_estimate_exposure`에 어떤 카테고리로 노출됐는지를 조인해야 카테고리를 알 수 있다.

### 2.2 견적품목 화면

견적품목의 수량동기화 편집기는 이미 본체 행 안에 있다.

- 카테고리 탭별 규칙 조회: `EstimateItemsCatalogPage.tsx:1102-1107`
- 수량동기화 버튼·모달: `:887-970`
- 대상 품목의 배수·특징·형상: `:954-964`
- 규칙 request에 카테고리·source·target 구성: `:354-383`
- 규칙 CRUD: `:1252-1305`, API 함수 `quantitySyncApi.ts:53-81`

`quantity_sync_rule`은 이미 `estimate_category`를 필수로 저장한다(`QuantitySyncRule.java:40-45`). target은 `multiplier`, `rounding_mode`, `component_variant`, `component_shape`, `display_order`를 갖는다(`QuantitySyncTarget.java:33-53`). 그러나 target에는 `component_kind`가 없고, 활성 target 3건의 특징·형상은 모두 NULL이다.

견적품목의 `분류 설정`(`EstimateItemsCatalogPage.tsx:650-719`)은 대·중·소분류 `cat_l/m/s` 편집이다. 이번에 옮길 구성품 `component_kind`와 이름이 비슷하지만 저장 의미가 다르므로 합치면 안 된다.

### 2.3 `product_estimate_exposure`

이 테이블은 현재 정확히 `product_id`, `estimate_category`, `display_order`와 감사 7필드만 갖는다. 엔티티 근거는 `ProductEstimateExposure.java:42-53`, 마이그레이션은 `V18__add_product_estimate_exposure.sql:6-26`이다. 활성 행은 **867**개다.

|---|---:|
| HOME_MULTI | 123 |
| COMMERCIAL_MULTI | 416 |
| SINGLE_SET | 288 |

가격 컬럼도 설정 컬럼도 0개다. `(product_id, estimate_category)` 활성 유니크 인덱스가 있으므로 동일 품목·카테고리에 구성품 옵션 여러 행을 직접 추가할 수 없다.

## ④ 이전 선택지 A~D 비교

### 공통으로 기초품목에서 빠지는 UI 범위

세 설정만 옮긴다는 전제에서는 `ProductFormPage.tsx`의 다음 제어만 제거·조회전용화 대상이다.

- `종류` 1개(`:985-987`)
- `특징`과 `형상` 2개(`:988-994`)
- `수량 동기화` 1개(`:995-997`)

모델코드, 기본 수량, 구성품 추가·삭제, 배분 비중, 고정금액은 남는다. 현 payload가 한 번에 저장되므로 어느 선택지든 DTO/API에서 “기초품목이 저장하는 필드”와 “견적품목이 저장하는 필드”의 병합 규칙이 필요하다.

### A. `product_estimate_exposure`에 설정 컬럼 추가

가능한 저장 단위가 두 가지라 비용도 둘로 갈린다.

#### A-1 부모 노출행에 구성품 설정 JSON을 둔다

- 기존 활성 노출 **867행** 중 세트 부모 노출 **343행**에 설정을 넣는다.
- 그 343행이 현재 구성품 **1,584행**을 중첩 JSON으로 보존할 수 있다.
- 노출이 없는 부모 **3개/구성품 14행**은 카테고리가 없어 자동 이관할 수 없다.
- 현재 수량 규칙 **1 rule/1 source/3 target**까지 같은 JSON으로 옮기면 기존 규칙 API·검증·인덱스를 포기하거나 이중 기록하게 된다.

화면 변경은 기초품목 1화면의 4제어 제거와 견적품목 1화면의 카테고리별 설정 모달 추가다. 서버는 노출 조회/수정 DTO, 내부 카탈로그 응답, sync를 함께 바꿔야 한다.

깨질 수 있는 것:

- 노출 제거가 설정 삭제와 같은 생명주기가 된다.
- JSON 내부 구성품 FK·중복·soft-delete를 DB 유니크 인덱스로 강제하지 못한다.
- 구성품 1,584행의 검색·부분 수정이 343개 JSON 문서 교체가 된다.
- 전체 다중 노출 **71품목/155행**은 카테고리별 JSON을 따로 가져야 하므로 복사·초깃값 규칙이 필요하다.

#### A-2 구성품 SKU 자신의 노출행에 scalar/JSON 설정을 둔다

- 현재 데이터에서 필요한 `(estimate_category, component_product_code)`는 **401쌍**이다.
- 해당 구성품 SKU가 같은 카테고리로 이미 노출된 쌍은 **47**뿐이다.
- 나머지 **354쌍**을 만들면 “설정용 행”이 실제 판매 노출로도 해석된다.
- 401쌍 가운데 종류 충돌 0, 수량 방식 충돌 0, 복수 특징은 `SINGLE_SET/AWR-WE13N` **1쌍**이다. 특징까지 행으로 펴면 **403설정 튜플**이다.

깨질 수 있는 것:

- 신규 354행이 견적 카탈로그에 부자재를 새로 노출할 수 있다.
- `(product_id, estimate_category)` 유니크 때문에 같은 SKU의 복수 옵션을 scalar 한 행으로 표현할 수 없어 배열/JSON이 다시 필요하다.
- 어떤 부모 세트의 구성품인지가 사라져 세트별 후보 차이를 표현하지 못한다.

### B. 카테고리별 설정 테이블 신설

테이블 키를 어디까지 보존하느냐에 따라 두 규모가 나온다.

- 부모 세트·구성품 관계를 보존: 카테고리를 확정할 수 있는 **1,584행** backfill, 노출 없는 **14행** 보류.
- 카테고리·구성품 단위로 축약: 기본 쌍 **401**, 복수 특징을 펴면 **403행**. 부모 세트별 차이는 잃는다.

수량 규칙은 이미 별도 카테고리 테이블이 있으므로 B가 `component_kind/variant/qty_mode`만 맡을 수도 있고, 세 축을 모두 통합해 `quantity_sync_*`까지 대체할 수도 있다. 후자는 현재 **1+1+3행**뿐일 때는 작지만 PR #1268이 68계열을 채운 뒤에는 재이관 대상이 최대 **68 rule 계열**로 늘어난다.

화면 변경은 A와 같고, 서버에는 새 엔티티·repository·CRUD·migration·cascade·soft-delete·권한 테스트가 추가된다.

깨질 수 있는 것:

- 기존 `bundle_component` 1,598행과 새 설정 행 사이 이중 정본이 생긴다.
- `ProductSheetSyncService`, `BundleExpander`, 구성품 replace-all, `bundle_components_manual`이 어느 쪽을 우선하는지 새 규칙이 필요하다.
- 구성품 삭제/세트 해제 시 기존 cascade 외에 새 행 cascade가 필요하다.
- 새 테이블을 부모 없는 401쌍으로 만들면 현재 346개 세트별 후보 차이를 잃고, 부모 포함 1,584행으로 만들면 `bundle_component`의 설정 부분을 사실상 복제한다.

### C. `quantity_sync_rule`에 카테고리를 둔다

`estimate_category`는 이미 있다. 따라서 수량 규칙 자체의 스키마 이동은 **0행/0컬럼**이다.

현재:

- 활성 rule **1** (`HOME_MULTI`, 조건 `{}`)
- source **1**
- target **3**
- target 특징/형상 **0/3**

레거시를 채우면 제품 연동 **68계열**, 그중 현 구조 수용 **62**, 구조 불가 **6**, 옵션 조건 필요 **55**다. `quantity_sync_target`에는 특징·형상이 있지만 품목구분 `component_kind`가 없고, `(rule_id,target_product_id)`가 활성 유니크라 같은 규칙에서 동일 target을 특징별 여러 행으로 둘 수 없다.

화면은 견적품목 수량동기화 모달을 이미 갖기 때문에 네 선택지 중 수량 부분의 UI 추가가 가장 작다. 다만 종류 편집과 “선택 가능한 옵션 목록” 편집은 별도 UI/필드가 필요하다. 기초품목의 세 제어는 제거·조회전용화된다.

깨질 수 있는 것:

- 견적 홈 evaluator는 현재 `condition_json`, target 특징·형상을 읽지 않는다.
- 주문 evaluator는 비어 있지 않은 조건을 거부한다.
- 데이터만 68계열 채워도 옵션 실행이 되지 않으며, 6계열은 구조 자체가 부족하다.
- 구성품 1,598행 전체를 수량 규칙으로 옮기면 “세트 구성”과 “본체→부자재 수량 파생”을 같은 것으로 취급하게 된다. 실제로는 동기화 대상이 아닌 FIXED 2행과 세트별 가격 배분도 존재한다.

### D. `bundle_component`를 카테고리별로 둔다

현재 데이터는 부모 세트가 카테고리에 속하므로 이미 간접적으로 이 구조다.

- 데이터 이동 **0행**
- 구성품 **1,598행**, 부모 **346개**
- 단일 카테고리 부모 **343개**, 노출 없는 부모 **3개/14행**
- 다중 카테고리 세트 부모 **0개**
- SINGLE_SET **1,447행/271부모**, COMMERCIAL_MULTI **137행/72부모**, HOME/LEGACY **0행**

화면은 현재 `BundleComponentsEditor`를 견적품목의 세트 행/카테고리 탭에서 다시 열도록 옮기거나 재사용한다. 데이터 모델은 안 바뀌지만 기초품목에서 구성품 4제어만 떼려면 동일 엔티티의 부분 수정 API가 필요하다.

깨질 수 있는 것:

- 현재 0건일 뿐, 한 세트 부모가 둘 이상의 카테고리에 노출되면 같은 1,598행 집합을 공유하므로 카테고리별 차이를 표현하지 못한다.
- HOME_MULTI와 LEGACY에는 bundle component가 0행이라 현재 레거시 수량 규칙을 이 구조만으로 옮길 수 없다.
- 전체 구성품 편집기를 견적품목으로 옮기면 #1111과 정면 충돌하고, 금액 배분·고정금액까지 함께 이동하기 쉽다.
- 구성품 후보와 수량 규칙의 역할을 구분하지 않으면 `BundleExpander`, 시트 sync, 수량 evaluator 세 소비자가 서로 다른 의미로 같은 행을 읽는다.

### A~D 화면·마이그레이션·파손 비교표

| 항목 | A exposure 확장 | B 새 테이블 | C quantity rule | D bundle 간접축 |
|---|---|---|---|---|

## ⑤ 기초품목에 남는 것 · #1111과의 관계

개발책임자의 “그것만은”을 문자 그대로 적용하면 기초품목에는 다음이 남는다.

- 물리 SKU의 모델코드·품명·규격·단위·단일/세트 유형
- 이카운트식 물리 품목구분 `products.product_business_type`
- 구성품 **어떤 SKU가 들어가는지**, 구성품 추가·삭제
- 구성품 기본 수량 `default_qty`
- 구성품 납품가와 세트 금액 배분 비중·고정금액
- 재고·매입·회계·세금·바코드·안전재고
- 수기 편집 우선권 `bundle_components_manual`

견적품목으로 옮길 후보는 카테고리 문맥의 `component_kind`, `component_variant/component_shape/is_default`, `qty_mode` 및 이미 그곳에 있는 `quantity_sync_rule/source/target` 편집이다. 납품가 소관은 바꾸지 않는다.

#1111은 “구성품 추가·수정·삭제를 기초품목에서 모두 설정하고 견적품목은 세트 검색·납품가만”이라고 확정했다. 따라서 관계는 다음처럼 나뉜다.

- A/B/C처럼 **구성품 관계와 가격은 기초품목에 남기고 카테고리 메타데이터 3종만 분리**: #1111의 “수정 모두” 문구와 **부분 충돌**, 구성품 소속·가격 소관과는 충돌하지 않음.
- D에서 전체 `BundleComponentsEditor`를 견적품목으로 이동: #1111의 추가·수정·삭제 소관과 **정면 충돌**.
- D에서 동일 엔티티를 쓰되 3종 제어만 견적품목에 노출: 데이터 소관은 유지되지만 편집 소관은 **부분 충돌**.

어느 결정이 우선하는지는 이 보고서에서 선택하지 않는다.

## ⑥ 착수 순서 제안 — 순서별 비용만 제시

### 스키마/소관을 먼저 확정하고 규칙을 채우는 순서

```text
카테고리 설정 소관 A~D 확정
  → 저장 단위·API·호환 읽기 확정
  → 기존 1 rule/1 source/3 target 및 1,598 구성품 이관
  → PR #1268의 68계열 채움
  → estimate/order evaluator 연결
```

- A/B가 수량 규칙까지 대체한다면 현재 옮길 규칙은 **1계열**이지만, #1268 뒤에는 최대 **68계열**을 다시 옮겨야 한다.
- C는 이미 카테고리 축이 있으므로 이 순서의 이점은 `component_kind` 등 필드 보강을 68계열 입력 전에 끝내는 데 있다.
- D는 수량 규칙을 대체하지 않으므로 #1268 데이터와 직접 마이그레이션 관계는 없지만 같은 견적품목 UI를 수정한다.

### 규칙 68계열을 먼저 채우는 순서

```text
PR #1268에서 68계열과 조건 평가기 완성
  → A~D 확정
  → 유지(C/D) 또는 68계열 재이관(A/B)
```

- C를 유지하면 먼저 채운 데이터가 그대로 남는다.
- A/B가 rule 저장소까지 통합하면 **최대 68계열 재이관/재검증**이 생긴다.
- D는 규칙 저장소가 별도이므로 데이터 재이관은 없지만 옵션 목록의 정본이 `bundle_component`인지 rule target인지 다시 맞춰야 한다.

### 동시 트랙 충돌

| 트랙 | 겹치는 파일/계약 | 관찰된 충돌 성격 |
|---|---|---|
| PR #1268 | `estimate-app/views/index.ejs`, order-app, `EstimateCatalogInternalController`, 옵션 명칭/수량 evaluator | 이번 이전의 C 및 모든 선택지의 소비자와 직접 겹침. 규칙 수 **1→68** 여부가 migration 규모를 바꿈 |
| PR #1265 웹→전표 | `estimate-app/views/index.ejs`, `lib/code.js`, `bundle_set_options` 전달 | 선택 옵션을 전표에 그대로 보존하는 계약과 겹침. 설정 키/라벨 변경 시 호환 읽기 필요 |
| 6계열 해부 정찰 | 실행 경로·레거시 차이 조사 | 코드 변경 없이 근거를 공유할 수 있으나, 6/68 구조불가 계열의 표현 방식이 A~D 비용을 바꿈 |

PR #1268과 #1265는 둘 다 `clients/web/estimate-app/views/index.ejs`를 수정한다. 이번 이전도 실행 UI까지 포함하면 같은 파일이므로 단순 데이터 작업처럼 병렬 합치기 어렵다. 어느 순서를 택할지는 A~D 선택과 함께 결정할 항목이다.

## ⑦ 판단이 필요한 지점 — 선택하지 않음

1. **품목구분의 정확한 의미**: 이번 지시가 구성품 `component_kind`만 뜻하는지, 견적 분류 `cat_l/m/s` 또는 물리 `product_business_type`까지 포함하는지.
2. **설정 단위**: `(카테고리, 구성품 SKU)`인지, `(카테고리, 부모 세트, 구성품 SKU)`인지. 현재 401쌍으로 축약 가능하지만 1,598 세트 관계를 잃는다.
3. **A의 저장 형식**: exposure 부모행 JSON인지, 구성품 exposure행 scalar/JSON인지. 후자는 신규 노출 354쌍 문제가 있다.
4. **수량 규칙 정본**: 이미 카테고리 축을 가진 `quantity_sync_rule`을 유지할지, A/B로 통합할지.
5. **옵션 목록과 선택 조건의 분리**: 선택 가능한 옵션 목록, 실제 target 특징, `condition_json`을 한 모델로 합칠지 각각 둘지.
6. **#1111 변경 범위**: “구성품 수정 모두 기초품목”에서 카테고리 메타데이터 3종만 예외로 뺄지, 구성품 편집기 전체 소관을 다시 바꿀지.
7. **노출 없는 3부모/14구성품**: 카테고리를 부여한 뒤 이관할지, 설정 미이관 상태로 둘지.
8. **HOME/LEGACY의 bundle 0행**: D를 쓸 때 별도 수량 규칙만 사용할지, 구성품 데이터를 새로 만들지.
