# PR #1078 · 이슈 #1075 — S6 SOL 2차 적대검증 지시서

## 1. 판정

**BLOCK 1건.** coedit 연결 후 기존 품목의 값 교체 경로는 열렸지만, 함께 열리면 안 되는 trailing 빈행의 품목 선택까지 열려 라인 추가 구조 잠금이 깨졌다.

S4의 “모델명 combobox가 disabled로 고정” 결함은 기존 확정행의 값 변경 관점에서는 닫혔다. 그러나 S5가 모바일·데스크톱의 모든 `ProductAutocomplete`에서 `coeditActive`를 제거하면서 기존 확정행과 구조 추가용 빈행을 구분하지 않았다. 그 결과 “값 변경만 허용, 라인 추가·삭제 잠금” 계약을 만족하지 못한다. **머지 비권고.**

## 2. 실 사용자 재현

환경은 이 worktree의 design-system을 먼저 빌드하고 desktop mock Vite 서버를 사용했다. Docker·DB·다른 트랙은 건드리지 않았다.

1. `/sales/estimates/est-001/edit?mockRole=MASTER`에 진입한다.
2. 서버 확정행 2개와 trailing 빈행인 `라인 3`이 보이고 coedit 연결이 완료될 때까지 기다린다.
3. `라인 3 모델명` combobox가 활성화돼 있음을 확인한다. 같은 행의 삭제 버튼은 비활성이다.
4. `AJ`를 입력하고 두 번째 후보 `AJ052RXH5BC1`을 확정한다.
5. `라인 3`이 새 품목으로 확정되고 새로운 trailing 빈행 `라인 4`가 생성된다. 행 수가 3개에서 4개로 증가한다.
6. 임시저장·발송 버튼도 활성 상태가 된다.

이 경로는 현재 `1062-line-input-ux.spec.ts`의 “견적 편집 화면은 기존 행을 보존하고 coedit 중에도 품목을 교체한다” 시나리오가 그대로 실행하며, 신선한 실행에서 통과했다. 시나리오 이름과 달리 기존 확정행을 교체한 것이 아니라 **빈행을 채워 새 라인을 추가**했다. 따라서 사용자가 실제 UI에서 재현할 수 있는 구조 잠금 위반이다.

## 3. 원인

- `EstimateFormPage.tsx`의 모바일·데스크톱 `ProductAutocomplete`가 모두 `disabled={isReadOnly || estimateFormCoeditPending}`만 사용한다. `coeditActive`뿐 아니라 “이 행이 coedit 시작 시 존재하던 값 편집 대상인지, 구조 추가용 trailing 빈행인지”를 구분하는 조건도 없다.
- 빈행에서 품목을 고르면 `handleProductSelection()`이 `updateLine(index, ..., true)`를 호출한다.
- `updateLine(..., fromUser=true)`는 마지막 행 변경을 `appendBlankRowIfLastChanged()`에 전달한다. 그 결과 현재 빈행이 신규 유효행으로 바뀌고 다음 빈행이 추가된다.
- 삭제 버튼과 모바일 `lineStructureLocked`는 여전히 `isReadOnly || coeditActive`라서 삭제만 잠긴다. 즉 잠금이 통째로 사라진 것은 아니지만, **추가 축이 실제 사용자 경로로 열렸다.**

첫 각도인 “차단되면 안 되는 것이 차단되는가”에서는 기존 확정행의 모델명 combobox가 coedit 연결 후 활성이고 저장·발송 버튼까지 활성화되는 것을 확인했다. BLOCK의 원인은 필요한 값 변경 차단이 아니라 구조 추가의 과잉 허용이다.

## 4. 수정 지시

1. coedit 활성 시 모델명 변경 권한을 행 단위로 분리한다. coedit 연결 당시 이미 존재한 유효행의 값 교체만 허용하고, 구조 추가용 trailing 빈행의 `ProductAutocomplete`는 비활성화한다. 입력 도중 `productId`가 일시적으로 비워져도 기존행 자격이 사라지지 않도록 현재 `productId` 값만으로 판정하지 말고 안정적인 행 식별자/연결 시점 구조 스냅샷을 사용한다.
2. 렌더의 `disabled`만 믿지 말고 `handleProductSelection()` 또는 그 직전 경계에도 같은 구조 잠금 가드를 둔다. coedit 중 구조 추가 대상 행으로 들어온 프로그램적 선택은 무시해야 한다.
3. 데스크톱과 모바일을 함께 고친다. 삭제 버튼과 `lineStructureLocked`의 현 잠금은 유지한다.
4. Playwright 편집 시나리오는 두 계약을 분리한다.
   - coedit 연결: 기존 확정행(예: 라인 1)의 품목을 교체하고 전체 행 수가 그대로이며 원래 라인 식별자가 보존되는지 확인한다. 교체 완료 후 임시저장과 발송을 실제 클릭 경계까지 도달시켜 갱신 payload에 교체 품목이 들어가는지 단정한다.
   - 구조 잠금: trailing 빈행 모델명이 비활성이고 후보 모달이 열리지 않으며 행 수가 증가하지 않는지, 추가·삭제가 데스크톱/모바일 모두 막히는지 단정한다.
5. `origin/main`에서 계승한 “편집 시 trailing 빈행 존재·확정 후 다음 빈행 생성” 단정은 없애지 말고 coedit 비활성/폴백 편집 시나리오로 보존한다. coedit 활성 시나리오와 섞어 상반된 계약을 동시에 주장하지 않는다.

## 5. 회귀·증거 무결성 및 범위

- 증거 무결성: `git show origin/main:clients/desktop/playwright/1062-line-input-ux/1062-line-input-ux.spec.ts`와 현재 파일을 전수 대조했다. `origin/main`의 `expect(...)` 18줄 중 현재 파일에서 사라진 줄은 **0개**다. 현재는 34줄이다. 원 테스트 제목 1개는 바뀌었지만 단정 소실은 없다.
- 견적 기존 계약: Vitest `EstimateFormPage` 37건이 통과했다. 이 집합에서 `estimateRestoreFence` 재시드, 가격기억/품목교체, 부분검색 후보·규격·단가·UUID 비노출 계약을 실행했다. `참조 조회` 버튼과 기준정보 모달 배선은 코드에서 유지돼 있다.
- 판매전표 무회귀: 공용 `ProductAutocomplete`의 판매전표 Playwright `ac-2-product-autocomplete` 7건이 통과했다. 다건 모달, 단건 자동확정, 단가 반영, UUID 비노출, 멀티라인 독립 선택을 포함한다.
- 전체 지정 Playwright: `ac-2-product-autocomplete` + `1062-line-input-ux` 합계 10건 통과. 이 중 편집 시나리오의 통과 결과 자체가 위 구조 추가 결함의 재현 증거다.
- 부가 확인: design-system build와 desktop typecheck가 exit code 0이었다.
- 환경 분리: 인앱 Browser 플러그인은 설치본에 필수 `scripts/browser-client.mjs`가 없어 사용할 수 없었다. 저장소 Playwright Chromium 경로는 정상 실행됐으므로 이 환경 제한을 코드 결함으로 세지 않았다.
- 안 본 범위: 실서버·실 DB 저장 결과, Docker 배포본, 모바일 실기기, 분개·재고이동 화면, 다른 트랙(`#1057` `#1066` `#1069` `#1080`)은 보지 않았다.
- 이번 S6 신규 파일은 이 지시서 1개뿐이다.
