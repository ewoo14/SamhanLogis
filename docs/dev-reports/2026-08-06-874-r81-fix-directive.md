읽기 전용 실 데이터 재현 조합:

```text

  partnerId=0f5f7e16-6787-464d-8968-a0cd423c4be5
  GET partner-dc-configs/1012555999 → homeMultiDc=45%
  GET /slips/price-memory?partnerId=...&productId=6fd28b44-... → HTTP 204
```

실 사용자 순서:

1. 판매전표 신규 화면에서 거래처 `4348703365`와 `AJ060MXHNBC1`을 선택한다.
2. 48% 적용값 `1,355,640`을 확인한다.
3. 품목은 그대로 두고 거래처만 `1012555999`로 바꾼다.
4. 새 거래처의 45% 적용 기대값은 `1,433,850`이나, 현재 경로는 최근단가 204를 `CATALOG`로 해석해 `2,607,000`을 쓴다.
5. 이 상태로 저장하면 서버는 화면 단가를 정본으로 보존하므로 잘못된 정가가 그대로 저장된다.

재현 난이도: **쉬움**. 저장 없이 거래처 교체만으로 화면에서 관찰 가능하며, 위 조합은 현재 실 DB/API에서 모두 재현된다.

### F2 — 비동기 DC 적용 성공 뒤 스크린리더가 할인 대신 “판매가 적용”으로 잘못 고지한다

좌표:

- `clients/desktop/src/renderer/routes/SlipFormPage.tsx:791-845`
  - 선택 시 캐시가 없으면 초기 `dcResult`는 `null`이고, 뒤늦은 DC 응답은 `resolvedDcResult`에 들어가 할인 단가와 `discountInfo`를 적용한다.
- `clients/desktop/src/renderer/routes/SlipFormPage.tsx:874-906`
  - 최종 단가 권위 판정은 올바르게 `resolvedDcResult`를 쓰지만, 성공 안내는 초기 `dcResult?.info`를 다시 읽는다.
  - 따라서 같은 라인에서 화면/저장값은 전역DC인데 `aria-live` 문장은 “판매가 적용”이 된다.

실 사용자 순서:

1. 변동DC 거래처를 선택하고 DC 응답 완료 전 `AJ060MXHNBC1` 같은 자격 품목을 선택한다.
2. DC 응답은 품목 선택 뒤 정상 도착하고 최근단가는 204(miss)로 둔다.
3. 화면 단가와 `discountInfo`는 전역DC로 바뀌지만 스크린리더 안내는 “판매가 적용”이라고 낭독한다.

재현 난이도: **보통**. DC 응답을 품목 선택 뒤 도착시키는 지연 제어가 필요하지만, R79와 같은 단일 route 지연으로 결정적으로 재현 가능하다.

### 별도 증거 무결성 — R79의 `저장 활성화 3ms`는 그 의미로 재현되지 않는다

- `clients/desktop/r79-riusage-live-qa-driver.mjs:57-88`은 품목 선택 전후에 850ms+900ms를 대기하고 캡처까지 끝낸다.
- 같은 파일 `:99-103`의 `enabledMs` 타이머는 그 뒤 `save()`에 진입한 시점부터 시작한다.
- 따라서 `enabled=true`는 원문으로 재현되지만 `3ms`는 **품목 선택부터 저장 활성화까지의 지연**이 아니라 이미 활성화된 버튼을 첫 polling에서 확인한 비용이다. “DC 조회가 저장을 3ms만 막았다”는 수치 인용에는 사용할 수 없다.
- 이는 사용자 결함 2건에 더해 세지 않고, 허용된 예외인 증거 무결성으로만 기록한다.

## 2. 불변식

1. 거래처를 바꾸면 기존 자동단가 라인은 새 거래처 기준으로 **사용자입력 > 유효한 고정/전역DC > 최근단가 > 판매가** 순서에 다시 수렴해야 한다.
2. `hasVariableDiscount=false/null` 또는 전역DC 비대상 카테고리는 새 거래처 DC를 받으면 안 된다. 고정DC 우선과 사용자 직접입력 불침도 유지해야 한다.
3. 빠른 품목 교체·거래처 A→B→A·라인 삭제 뒤 늦은 응답은 현재 거래처·현재 품목·현재 라인에만 적용되어야 한다. 5초 제한시간 뒤 도착한 선택 요청은 라인을 다시 쓰면 안 된다.
4. 화면에 실제 적용된 가격 출처와 `discountInfo`·`aria-live` 안내는 같은 완료 결과를 말해야 한다.
5. 서버 `POST /slips`는 화면/직접 API가 보낸 단가를 한 번만 저장해야 한다. 거래처 변경 보완을 서버 재계산으로 해결해 R67의 `970,200 → 494,802` 이중 적용을 되살리면 안 된다.
6. UUID는 사용자 문구에 노출하지 않는다.

## 3. 양방향 RED

### RED-A — F1 거래처 변경 재가격

- `4348703365` + `AJ060MXHNBC1`에서 48% 값 `1,355,640`을 만든 뒤 `1012555999`로 바꾸고 최근단가를 miss시키면, 라인은 새 거래처 45% 값 `1,433,850`과 `거래처 전역DC 45% 적용`으로 수렴해야 한다.
- 반대급부: 새 거래처 최근단가가 존재해도 자격 있는 전역DC가 최근단가보다 우선해야 한다.
- 반대급부: `hasVariableDiscount=false` 품목은 같은 거래처 변경에서 전역DC를 받지 않고 최근단가 hit 또는 판매가 miss fallback을 유지해야 한다.
- 반대급부: 고정DC 품목은 새 거래처의 전역DC율과 무관하게 고정DC를 유지해야 한다.
- 반대급부: `USER` 단가는 거래처 변경 bulk/DC 응답 모두가 덮지 않아야 한다.
- 반대급부: A→B→A를 빠르게 수행한 뒤 B의 늦은 DC/최근단가 응답이 마지막 A 라인을 바꾸지 않아야 한다.

### RED-B — F2 완료 결과와 안내 일치

- 거래처 DC를 지연시키고 자격 품목을 먼저 확정한 뒤 DC 성공+최근단가 miss를 완료하면, 화면 단가·`discountInfo`·`aria-live`가 모두 같은 전역DC율을 말해야 한다.
- 반대급부: 비대상 품목+최근단가 miss는 정가와 “판매가 적용”을 말해야 한다.
- 반대급부: 전역DC가 없고 최근단가 hit이면 최근단가와 “거래처 최근단가 적용”을 말해야 한다.
- 반대급부: DC 요청이 5초 제한시간을 넘긴 뒤 도착해도 timeout으로 확정된 라인과 안내를 뒤늦게 바꾸지 않아야 한다.

### 분포 RED — R78 정상 대상 무회귀

현재 실측은 ACTIVE 3,179개 중 `hasVariableDiscount=true` 802개, false 2,377개, null 0개다.

- `GET /api/products?status=ACTIVE&size=5000`은 true 802/802를 반환해야 한다.
- 동일 802개를 `POST /api/products/lookup` 100개 chunk로 조회해도 true 802/802, null/false 0이어야 한다.
- 카테고리 분포는 `homemulti 107 + commercialMulti 314 + singleSets 190 + singleParts 191 = 802`다.
- R78 전후 계산식 대조에서 새로 차단된 true 품목은 0건이어야 한다. 전역DC 계산 카테고리 421개는 전후 동일하고, 나머지 381개는 R78 전부터 `OTHER` 분기였음을 별도로 유지한다.
