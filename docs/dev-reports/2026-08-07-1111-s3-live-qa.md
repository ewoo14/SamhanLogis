## 6. 결함 수와 도달 경로

**결함 1건.**

### F1 — 구성품 보유 세트 삭제가 관문 없이 204이며 활성 구성품을 고아로 남긴다

도달 경로:

```text
dev_master 로그인
→ 기초품목 관리 → S3-1111-GUARD 세트 등록
→ 상세에서 단일 구성품 12건 추가·저장
→ 수량 수정·1건 삭제·저장(활성 11건)
→ 실제 관리자 DELETE /api/products/{id}
→ 기대: 구성품 존재 확인 관문/차단
→ 실제: HTTP 204, 부모 목록에서 제거
→ DB: 부모 is_deleted=TRUE, bundle_component 활성 11행 잔존
```

현재 HEAD와 배포 JAR의 `ProductService.delete()`는 수량 동기화 규칙 참조만 확인하고 부모 및 노출 행을 soft-delete한다. `bundle_component` 존재 확인/동의 토큰/자식 soft-delete가 없다. #1109 가드는 `PATCH`의 SET→GENERAL·SET→MATERIAL 전환에만 적용되어 이 DELETE 경로를 덮지 않는다.

## 7. `components_manual` 검증

배포본이 이 PR 코드가 아니므로 아래는 모두 **판정 불가**다.

| 항목 | 판정 |
|---|---|
| 수기 편집 세트가 sync 후 유지 | 판정 불가 — V32/필드/분기 미배포 |
| 손대지 않은 세트가 sync로 정상 갱신 | 판정 불가 — 현 배포본에는 manual 분기 없음 |
| `preservedManual` 카운트 = 실제 수기 편집 세트 수 | 판정 불가 — 응답 필드/컬럼 없음 |

이번 CRUD의 화면·기존 API 동작은 PASS지만, 저장 후 `bundle_components_manual=TRUE` 영속과 sync 보호를 증명한 것으로 해석하면 안 된다. 이 3항목은 PM이 PR 백엔드를 배포한 뒤 다시 밟아야 한다.
