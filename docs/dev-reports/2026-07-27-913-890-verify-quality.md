### R1-1 — taskkill /T /F(트리 종료)에서도 공유 실 DB에 throwaway가 남지 않는다

**진단 확증(실측)** — Node `spawn(..., { detached: true })`가 Windows에서 `taskkill /T /F`에
살아남는지 먼저 독립 실험으로 확인했다. 3단 프로세스 트리(조부모→부모→자식)를 만들고 자식을
(a) Node detached spawn, (b) `wmic process call create` 두 방식으로 각각 띄운 뒤 조부모를
`taskkill /PID <조부모> /T /F`로 종료했다.

```text
taskkill 직후: detached-heartbeat.txt=1785158234007(멈춤) / wmic-heartbeat.txt=1785158242991
+2초 후:      detached-heartbeat.txt=1785158234007(그대로 — 사망) / wmic-heartbeat.txt=1785158245122(전진 — 생존)

tasklist /FI "PID eq 69724"(detached 자식) → 요청한 작업에 지정된 조건에 일치하는 작업이 없습니다.
tasklist /FI "PID eq 70812"(wmic 자식)     → node.exe  70812 Console  1  63,584 K
```

Node detached 자식은 트리 종료 즉시 죽고, `wmic`으로 띄운 자식은 살아남는다 — Windows가
`CreateProcess` 호출 시 기록한 PPID를 재부모화하지 않기 때문에(POSIX의 init 재부모화와 다르다)
자식 스스로 detach해서는 벗어날 수 없고, 제3자(WMI provider host, WmiPrvSE.exe)가 대신
`CreateProcess`를 호출해야 트리 밖으로 나간다.

**fix** — `clients/desktop/scripts/ds4-real-qa-spawn-worker.cjs`(신규)가 cleanup worker를
`wmic process call create`로 우선 기동하고, 실패 시에만 기존 Node detached spawn으로 강등하며
그 사실을 `console.warn`으로 남긴다(무음 강등 금지). `startDs4RunScope()`(`ds4-real-qa-cleanup.ts`)가
이 헬퍼를 쓰도록 바뀌어 `async` 함수가 됐고(두 실 real-qa 스펙의 호출부를 `await`로 갱신), 어느
spawn 방식이 실제로 쓰였는지(`spawnMethod`)를 반환해 로그에 남긴다.

wmic도 실패하는 예외적 경우를 위한 안전망으로 self-healing sweep과 독립 reap CLI를 추가했다 —
"R1-1/R1-2 fix 불변식 2·4" 참고:

- `clients/desktop/scripts/ds4-real-qa-stale.cjs`(신규) — I/O 없는 순수 판정. run 이름에서
  `label`/`ownerPid`/`startedAtMs`를 파싱하고, "이 하네스가 만든 이름 형태" + "유예기간(기본
  60초) 경과" + "owner 프로세스가 실제로 죽음" 셋을 모두 만족할 때만 stale로 판정한다(하나라도
  아니면 false — 특히 owner가 살아있으면 나이와 무관하게 항상 false).
- `clients/desktop/scripts/ds4-real-qa-reap-core.cjs`(신규) — 실제 fetch로 stale 문서양식을
  조회·삭제하고 fs로 `.stop` marker를 정리한다. 조회/삭제/정리 실패는 삼키지 않고
  `%TEMP%/samhan-ds4-real-qa-cleanup-notices.log`에 append한다(무음 실패 금지).
- `clients/desktop/scripts/ds4-real-qa-reap.cjs`(신규) — 사람이 즉시 실행하는 CLI. 실패 시
  exit code 1.
- `ds4-real-qa-cleanup.ts`의 `sweepStaleDs4Templates()`(신규 export)를 두 real-qa 스펙의
  `finally`가 자신의 exact-match 정리 다음에 호출한다 — "이전에 죽고 아무도 못 지운" 다른 run을
  이번 실행이 대신 회수하는 self-healing.

**GREEN(실측, 공유 실 DB)** — `scripts/verify-ds4-real-qa-cleanup.cjs`에 실제 3단 트리를
`spawnDs4CleanupWorker()`(운영 코드와 동일 헬퍼)로 재현하고 `taskkill /T /F`한 뒤 공유 실 DB로

### R2-1 — ACTIVE 양식의 누락 revision self-heal 승인

#### RED 원문

🚨 **R3 정정(2026-07-28, R3 라운드 — 증거 무결성)** — 위 인용 중 `PR951_MID_FLUSH_FAILURE_CLASS` /

현재 트리 그대로 실행해도 이 세 줄만은 재현되지 않는다(직전의 `AssertionError`·`SQLState: P0001`·
`JpaSystemException` 원문은 실제 실행 결과이며 그대로 재현된다 — 문제는 이 세 줄에 한정된다).
RED-first 워크플로우 특성상 RED 시점 계측이 최종 커밋본과 글자 그대로 같지 않은 것 자체는
정상이다(RED 원문은 "그 순간 결함이 실제로 재현됐다"는 증거이지, 최종 테스트 파일의 축자적
사본이라는 뜻이 아니다). **다만 위조는 아니다** — 재수렴 라운드가 격리된 Testcontainers
PostgreSQL에 V1~V15 전체를 순서대로 적용하고 R2 fix 이전 순서(승인 상태 flush가 revision INSERT
보다 먼저 일어나는 순서)를 직접 SQL로 재현해, 이 세 줄이 주장하는 값과 독립적으로 일치하는
`{status=PENDING, version=0, document_template_id=null, document_template_revision=null,
document_template_default_pinned=false}` 롤백 행과 `revision 0건`을 별도로 확인했다.

#### fix

승인 경로에만 `ensureCurrentRevisionForApproval()`을 추가해 revision INSERT를 `save()`로 예약하고,
`line.pinDocumentTemplate()` 또는 `line.pinDefaultDocumentTemplate()`가 끝난 뒤
`ApprovalLineRepository.flush()`를 호출한다. 따라서 revision INSERT와 `APPROVED + pin` UPDATE가
한 flush에서 처리되고, 일반 양식 CRUD의 `ensureCurrentRevision()` 및 동시 self-heal 경합 계약은
기존 `saveAndFlush()` 경로로 보존된다.

적용된 V15 SQL은 수정하지 않았고 V16도 추가하지 않았다.

## 환경상 확인 사항

- Desktop 초기 의존성이 없어 `clients/desktop`에서 `npm ci --ignore-scripts`를 수행했다.
- 첫 Playwright 실행은 `@samhan/design-system/tokens.css`가 없어 Vite가 `Failed to resolve entry for package "@samhan/design-system"`로 중단됐다. 실행 전 `clients/web/design-system`에서도 `npm ci --ignore-scripts`와 `npm run build`를 수행해 의존성/빌드 산출물을 준비했고, 이후 새 테스트가 GREEN이 됐다. 소스 파일 변경은 아니다.
- `npx tsc -p tsconfig.web.json --noEmit`은 기존 로컬 `@samhan/design-system` 미빌드 상태에서 시작해 해당 패키지 import 및 연쇄 implicit-any 오류로 실패했다. 이 보고서의 관련 Vitest/Playwright/Gradle 선택 검증은 모두 GREEN이며 전체 클라이언트 typecheck는 실행하지 않았다.
- 전체 로컬 스위트는 실행하지 않았다. CI 전체 스위트는 CI 권위로 남긴다.
- SQL heredoc을 `docker exec` stdin으로 전달하지 않았다. 공유 실 DB probe는 API 경계를 사용했고, 직접 SQL이 필요한 테스트는 Testcontainers `JdbcTemplate`로 격리된 PostgreSQL에서 수행했다.
- **(R1 라운드)** 이번 워크트리(`.claude/worktrees/913-890`)는 `clients/desktop/node_modules`가 이미 설치돼 있어 별도 `npm ci`가 필요 없었다. 공유 Docker 스택(`samhan-api-gateway:8080` 등, 다른 워크트리도 같이 쓰는 실 Postgres)이 이미 기동 중이어서 그대로 사용했다 — 5175/5181/5299 포트는 쓰지 않았다.
- **(R2 라운드)** `npm test`(전체 데스크톱 단위 스위트)를 현재 워크트리에서 다시 실행했고 `src/main/build-output-cjs-interop.test.ts` 1건이 실패한다 — 실제 원문은 `Electron failed to install correctly, please delete node_modules/electron and try installing again`인 로컬 Electron 설치 환경 문제다. `src/main/`은 이번 라운드에서 건드리지 않았고, 이 환경 문제 자체는 수정하지 않는다. 상세는 "R2 라운드 fix" 절의 R2-3 소절 참고.
