# PR #1066 / 이슈 #1065 — R6 fix 구현 보고

## 판정

R5 지시서의 두 결함을 코드와 테스트로 수정했다. 서버 재배포·Docker 조작·DB 직접 쓰기·커밋은 하지 않았다.

실행:


이는 테스트 assertion 실패가 아니라 워크트리에 `clients/desktop/node_modules`가 없어서 발생한 실행 준비 실패였다. 기존 지시서의 환경 제약과 일치한다. lockfile 기반 `npm ci` 후 같은 테스트를 재실행해 4/4 통과를 확인했다.

### 결함 재현을 보장하는 RED assertion

추가한 테스트는 액션 문자열만 보지 않는다.

```text
canAccess(slip.transfer.process, UPDATE)=false
canInspect=true  -> canTransitionSlipAction('inspect')=true
canAccess(...)=false
canInspect=false -> canTransitionSlipAction('inspect')=false
INBOUND complete -> '출고 완료' 아님
OUTBOUND complete -> '출고 완료'
```

## 변경 내용

### 결함 1 — 결재선 개인의 화면 선차단 제거

- `SlipDetailResponse.canInspect`를 추가했다. `SlipService.getOne(id, actorUserId)`가 저장된 전표가 `OUTBOUND × INSPECTING`인지 확인한 뒤 auth-service의 `SLIP_OUTBOUND / OUTBOUND_INSPECT` 결재선 응답 `configured=true && allowed=true`일 때만 true를 넣는다.
- FE `canTransitionSlipAction()`은 `inspect`에 한해서만 `정적 UPDATE || 서버 canInspect`를 사용한다. 나머지 `accept/process/complete/ship/deliver`는 기존 정적 UPDATE만 사용한다.
- 같은 판정 함수를 모바일 버튼 disabled, 모바일 클릭 경로(`handleTransition`), 데스크톱 버튼 disabled 및 데스크톱 명령형 경로에 적용했다.
- 결재선 밖 계정은 서버 `canInspect=false`이며 기존 정적 UPDATE도 없으므로 버튼 disabled 및 호출 미실행이다. 서버 `/inspect`의 최종 결재선 검사는 그대로 유지된다.

화면이 결재선 구성원임을 아는 근거는 클라이언트가 사용자명·역할·전표 유형을 추측하는 것이 아니다. 단건 GET에서 서버가 저장 전표의 유형/상태를 읽고 auth-service 결재선 인가 결과를 계산해 내려주는 `canInspect` boolean뿐이다. 외부 사용자 경로에서는 게이트웨이가 서명된 JWT의 userId로 `X-User-Id`를 재설정하므로 클라이언트가 capability를 위조해도 서버 POST의 최종 검사에서 거부된다.

### 결함 2 — 전표 유형별 complete 라벨

- `labelForAction('complete', mode)`를 추가했다.
- OUTBOUND는 `출고 완료`, INBOUND는 `입고 완료`다.
- 공용 상세의 모바일 라벨, 데스크톱 title/버튼 텍스트 모두 이 함수를 사용한다.

## 테스트 변경

- `SlipDetailPage.transition.test.ts`: 정적 UPDATE가 없는 결재선 개인의 허용, 결재선 밖 계정의 차단, OUTBOUND/INBOUND 라벨을 검증한다.
- `SlipOutboundApprovalEnforcementIT`: 결재선 개인의 단건 GET에 `$.data.canInspect=true`를 검증한다.
