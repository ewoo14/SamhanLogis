# PR #1131 R7 fix directive — R6 도달 결함 3건

## 판정

**BLOCKING. 실 사용자 경로로 재현 가능한 결함이 3건 있다.**

1. head 구성품의 품목을 교체하면 그 행만 평면이 되고, 같은 인스턴스의 나머지 구성품은
   `parentSetModel`을 가진 0-head BUNDLE로 남는다. R5 fix는 품목 교체가 하나라도 있으면 해당
   인스턴스 검증을 전부 건너뛰므로 이 orphan 계보를 200으로 저장한다.
2. 기존 BUNDLE 전표를 실제 화면에서 수량만 양수로 바꿔도 FE가 구성품의 S/V/T를 권위금액으로
   보내고, BE는 `세트 구성품의 공급가액·부가세는 개별 편집할 수 없습니다`로 400 거부한다.
   따라서 R5에서 저장 버튼 직전까지만 캡처한 양수 편집은 실제 저장 경로를 통과하지 못한다.
3. 성공 PUT 응답의 `updatedAt`은 같은 트랜잭션 커밋 뒤 DB 값보다 오래됐다. 클라이언트가 성공
   응답을 cache에 채택한 직후 같은 전표를 다시 저장하면 409가 난다. realtime 재조회가 먼저
   도착하면 가려지고, 도착하지 않으면 실제 화면에서 `다른 사용자가 먼저 수정했습니다`가 뜬다.

slip-service 배포본에는 이번 미커밋 guard가 없으므로 1번의 **guard skip 자체**와 legacy 반복
통과는 현재 diff를 컴파일한 테스트로 판정했다. 라이브는 지시대로 재배포하지 않고 FE/API/DB
도달성과 현재 공통 저장 계약만 밟았다.

## 도달 결함 1 — head 품목 교체가 인스턴스를 평면화하지 않고 orphan BUNDLE을 남긴다

### 좌표

- `services/slip-service/src/main/java/com/samhanair/logis/slip/service/BundleLineageResolver.java:186-193`
  - productId가 바뀐 **행**은 계보를 승계하지 않지만 `lineageChangedInstances`에는 **인스턴스 전체**를 표시한다.
- 같은 파일 `:202-204`
  - `lineageChangedInstances.contains(instance.ordinal)`이면 남은 구성품의 head 수를 검사하지 않는다.
- `services/slip-service/src/test/java/com/samhanair/logis/slip/it/PartnerProductPriceMemoryIT.java:1419-1447`
  - 현 테스트도 head 교체 후 `swapped flat + 남은 child parent=SET-809/setHead=false` 혼합 상태를 기대한다.

### 불변식

품목 교체로 세트 인스턴스를 평면 전환한다고 결정했다면 그 인스턴스의 **모든 잔존 행**이
`parentSetModel=null`, `setHead=false`여야 한다. 반대로 변경하지 않은 구성품 계보를 남길 것이라면
그 잔존 BUNDLE에는 canonical head가 정확히 1개 있어야 한다. 평면 행과 0-head BUNDLE child가 섞인
제3 상태는 허용하면 안 된다.

### 재현

1. 정상 head 1개 + child 2개인 실 DRAFT `2026/08/07-10`을 throwaway로 복사한다.
2. 기존 head의 `lineId`는 유지하고 품목만 실 단품 `AJ060MXHNBC1`로 교체한다.
3. 나머지 두 child는 품목·lineId·계보를 그대로 둔다.
4. 저장한다.

라이브 원문:

```text
R6-HEAD-SWAP|source=2026/08/07-10|copy=2026/08/11-98|PUT=200
|remainingBundle=2|heads=0|swapped=AJ060MXHNBC1
```

현재 diff 테스트 원문은 `PartnerProductPriceMemoryIT.bundleHeadProductSwappedToUnrelatedItem_dropsLineageAndRemembersUserPrice`
1/1 PASS다. 이 PASS가 교체 행의 계보 제거와 가격기억은 증명하지만, 동시에 남은 진짜 구성품이
0-head BUNDLE로 저장됨을 증명한다. 임시 R6 probe도 이 혼합 상태를 그대로 재현했고 probe 소스는 삭제했다.

스크린샷:

- `docs/qa/1131-r6-fix/screenshots/02-live-head-product-swap-orphan-lineage.png`

### 양방향 RED

#### RED-A — head 품목 교체

원본 `H/C/C`에서 H의 lineId를 유지한 채 productId만 SINGLE로 교체한다.

기대:

```text
2xx
교체된 행 + 잔존 두 행 모두 parentSetModel=null / setHead=false
또는 정책상 전체 평면 전환이 불가능하면 저장 전 명시 거부
0-head BUNDLE 행 0개
```

현재:

```text
2xx
교체 head 행만 flat
잔존 child 2행 parentSetModel 유지 / setHead=false
```

#### RED-B — 구체 반대 표적

1. `H/C/C`에서 non-head C만 다른 SINGLE로 교체한다 → H와 변경하지 않은 C는 head 1개 BUNDLE로
   남고, 교체 C만 flat, 2xx.
2. `H/C/C`에서 H만 생략하고 C/C를 남긴다 → `INVALID_INPUT`, DB write 0회.
3. `H/C/C` 전체를 삭제한다 → 2xx.
4. H를 SINGLE로 교체하면서 C/C도 모두 삭제한다 → SINGLE 1행만 2xx, 계보 0행.
5. 인스턴스 밖 평면 라인의 품목 교체는 BUNDLE 검증을 약화시키지 않고 2xx.

## 도달 결함 3 — 성공 PUT 응답의 stale `updatedAt` 때문에 즉시 두 번째 저장 409

### 좌표

- `services/slip-service/src/main/java/com/samhanair/logis/slip/service/SalesSlipUpdateService.java:137-147`
  - 1차 `saveAndFlush` 뒤 `auditLogService.recordBatch`가 같은 Slip의 `revisionCount`를 다시 변경하고,
    마지막 flush 전에 `SlipDetailResponse.from(saved)`를 만든다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/audit/service/SlipAuditLogService.java:117-122`
  - `recordBatch`가 관리 중인 Slip을 다시 읽고 `incrementRevision()` 한다.
- `clients/desktop/src/renderer/routes/SlipDetailPage.tsx:2064-2075`
  - FE는 성공 응답을 `['slip', id]` cache 정본으로 즉시 채택한다.

### 불변식

성공 mutation 응답의 version token(`updatedAt`)은 그 응답을 그대로 다음 요청에 사용해도 유효해야
한다. 별도 realtime 이벤트가 도착해야만 성공 응답이 쓸 수 있는 상태가 되는 계약은 허용하면 안 된다.

### 재현과 원문

평면 DRAFT `2026/08/10-16` 복사본에서 첫 PUT 응답을 그대로 사용해 두 번째 PUT을 보냈다.

```text
R6-SECOND-EDIT|first=200|second=409
|responseUpdatedAt=2026-08-11T06:19:11.460334
|dbUpdatedAt=2026-08-11T06:19:11.506364
```

실 화면 격리 실행에서도 첫 저장 200 → 즉시 다시 열기 → 두 번째 저장 409와 다음 문구를 재현했다.
realtime 재조회가 먼저 도착한 재시도에서는 200으로 가려졌으므로 사용자 결과는 타이밍 의존이다.

```text
다른 사용자가 먼저 수정했습니다. 최신 내용 불러오기 후 다시 저장해 주세요.
```

- `docs/qa/1131-r6-fix/screenshots/03-live-second-edit-409-stale-put-response.png`

### 양방향 RED

#### RED-A — 성공 응답 연속 사용

첫 PUT의 응답 `updatedAt`과 신규 lineId를 그대로 두 번째 정상 PUT에 사용한다.

기대: 두 번 모두 2xx, 두 번째 사용자값 보존.

현재: 첫 PUT 2xx, 두 번째 409. 첫 응답 timestamp와 즉시 re-GET timestamp가 다르다.

#### RED-B — 구체 반대 표적

1. 서로 다른 두 사용자가 같은 원본 `updatedAt`으로 실제 동시 PUT → 정확히 하나 2xx, 패자는 409.
2. 과거 응답을 의도적으로 재사용 → 409 유지.
3. 성공 응답의 최종 token을 사용한 순차 PUT 두 번 → 둘 다 2xx.
4. realtime 연결이 없거나 늦어도 3번은 동일하게 통과.

현재 diff의 공통 direct-PUT 미러인 INBOUND `SlipUpdateConcurrencyIT`는 1/1 PASS다. 정확한 SALES
동시 2-PUT은 이번에 별도 실행하지 않았으므로 R7에서 같은 반대 표적을 SALES endpoint에 추가한다.

## 요청한 다섯 각도

### 1. historical head 원본 판정

- **저장 순서:** `Slip.lines`는 `Slip.java:651-653`의 `@OneToMany List`지만 `@OrderBy`/`@OrderColumn`이
  없다. resolver는 그 목록 순서로 인스턴스를 자른다. 이번 실 DB에서는 실제 head 오분류를 추가로
  재현하지 못해 별도 도달 결함으로 세지 않았다. 안정 순서가 계약으로 고정되지 않은 상태는 R7에서
  제거해야 한다.
- **lineId 재부여:** 실 0-head 일반 모델 2건 모두 첫 저장 뒤 lineId 전량 재부여를 확인했다. re-GET한
  최신 lineId로 두 번째 저장은 200이었다. 현재 diff 임시 probe도 재부여된 lineId의 2회 legacy 통과를
  확인했다.
- **협업/동시 편집:** `SalesSlipUpdateService`는 resolver보다 앞에서 `verifyVersion`을 호출한다.
  공통 INBOUND direct-PUT 동시성 IT는 1승/1패였고, SALES의 정확한 동시 2-PUT은 별도 실행하지 않았다.
  head 오분류는 재현하지 않았다. 단 성공 응답 자체가 stale한 3번 결함 때문에 정상 순차 편집도
  동시 편집으로 오인될 수 있다.

### 2. legacy 전표 반복 수정

resolver 자체는 0-head를 첫 저장 뒤에도 historical 0-head로 다시 인식해 계속 통과한다. 일반 모델
실 DB 2건은 re-GET 사이클을 끼우면 각각 두 번 200이었다. 그러나 성공 응답을 그대로 사용하는 실제
클라이언트 계약은 3번 결함으로 두 번째 저장이 409이므로, 사용자 관점의 반복 수정은 닫히지 않았다.

### 3. 동일 모델 3개 이상 인스턴스

임시 current-diff probe에서 `H/C × 3` 정상 유지 2xx와 가운데 인스턴스 head만 삭제 시 거부를 함께
확인했다(3/3 PASS, probe 삭제). 실 DB에는 같은 모델 head 3개 이상인 활성 표본이 0건이라 live
판정은 없었다.

### 4. 품목 교체와 계보

**결함 1로 실패.** head 교체가 인스턴스 평면 전환을 완성하지 않고 0-head child를 남긴다.

### 5. 실 DB 0-head 16건

활성 16건은 유지된다. 각각 throwaway 복사 후 양수 저장을 실제 호출했다.

```text
2건 — guard 도달 가능한 일반 모델
2026/08/07-17  AF17DX738WSS      1차 200 / re-GET / 2차 200 / lineId 재부여
2026/08/07-7   AC072CS6PBH1SY   1차 200 / re-GET / 2차 200 / lineId 재부여

14건 — 선재 product lookup에서 404, 신규 guard 도달 전 차단
2026/07/16-115, 116, 57, 58, 79, 80, 92, 93
2026/07/17-22, 23, 3, 4, 61, 62
공통 parentSetModel=QA797-SET-01
원문=일부 제품을 찾을 수 없습니다 (요청 1, 응답 0)
```

따라서 R5의 “실 DB 0-head 16건이 새 guard 때문에 저장 불가”라는 증거는 그대로 유지할 수 없다.
실제 guard 회귀 표본은 일반 모델 2건이고, 14건은 범위 밖인 선재 product lookup에서 먼저 막힌다.
이는 검증 평가가 아니라 요청이 허용한 **증거 무결성 정정**이다.

## R7 수정 범위

1. 품목 교체로 인스턴스를 평면 전환한다면 잔존 인스턴스 전 행의 계보를 원자적으로 제거한다.
   단순히 `lineageChangedInstances`에서 guard만 생략하지 않는다.
2. 기존 BUNDLE hydrate 시 서버 S/V/T가 존재한다는 이유만으로 사용자 권위 편집으로 표시하지 않는다.
   BUNDLE의 수량·단가 정상 편집 payload와 실제 S/V/T 개별 편집 payload를 분리한다.
3. `recordBatch`의 revision 증가까지 flush한 최종 Slip으로 응답 token을 만든다. 성공 응답을 그대로
   사용한 순차 2회 PUT을 실제 PostgreSQL IT로 고정한다.
4. 인스턴스 판정의 입력 순서를 명시적으로 고정하거나, 순서 추정 대신 안정 인스턴스 식별자를 둔다.
5. R5의 16건 주장을 2건 guard 표본 + 14건 lookup 차단으로 정정하고, 배포 후에는 일반 모델 2건으로
   guard 라이브 검증한다.

## 반대급부

- 인스턴스 전체 평면화는 기존 child의 세트 표시·세트 가격기억 제외 의미를 함께 잃는다. 이것이 도메인
  결정과 다르면 head 품목 교체를 거부하거나 새 canonical head를 선택하는 별도 정책이 필요하다.
- BUNDLE에서 S/V/T를 payload에서 빼면 서버 재계산이 정본이 된다. 기존 사용자 권위 VAT 편집을 계속
  지원하려면 `vatDirty` 하나가 아니라 “사용자가 실제로 해당 셀을 편집했는지”를 별도 표시해야 한다.
- 최종 flush 뒤 응답을 만들면 flush가 한 번 늘 수 있다. 대신 success token의 자기일관성과 realtime
  비의존성을 얻는다.
- 안정 인스턴스 ID를 스키마에 추가하면 migration/DTO/backfill이 든다. 순서 컬럼만 추가하면 비용은
  작지만 잘못 저장된 과거 인스턴스 경계를 스스로 복구하지는 못한다.

## 라운드 성격

R6 결과는 “도메인이 원래 복잡해서 끝없이 새로운 예외가 나온다”만으로 설명되지 않는다. 1번은 R5가
새로 도입한 `lineageChangedInstances` 전면 skip이 직접 만든 새 표면이고, 2·3번은 R5가 버튼 직전 또는
단일 요청 테스트에 머물 때 가려졌던 기존 end-to-end 저장 계약의 결함이다. 공통 원인은 세트 인스턴스,
사용자 VAT 권위, mutation 최종 version이라는 서로 다른 상태를 boolean/목록 순서/중간 flush 값으로
추정하는 구조다. 즉 **fix가 새 표면을 만들었고, 동시에 이 도메인의 암묵 상태가 그 표면을 크게 만든
상태**다. 다음 라운드는 head 조건 하나를 더 붙이는 방식보다 위 세 상태의 정본을 명시하는 bounded
수정이어야 한다.
