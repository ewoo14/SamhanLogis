# PR #1127 R2 fix 표면 SOL 재수렴

검증 기준은 `feat/978-fast-path-carryover` HEAD `43973cd79ae1876c0389d90f39f49abd6f0db733`이다. 코드, 실 DB, 실 Google Sheet, Docker에는 쓰지 않았다. 요청된 이 보고서만 새로 만들었다.

## 판정

**도달 가능한 결함 3건 + 증거 무결성 불일치 1건**이다. 따라서 이 라운드는 결함 0이 아니며 PR #1127을 이 상태로 머지해도 된다는 판정을 내릴 수 없다.

먼저 사용자 요약에서 사실과 다른 부분은 다음 두 가지다.

1. `name`은 이 sync가 전혀 쓰지 않는 필드가 아니다. ECOUNT→SHEET 승격 update 분기에서 `p.rename(name)`을 호출한다(`ProductSheetSyncService.java:1280-1297`). 일반 SHEET/MANUAL steady-state에서만 쓰지 않는다.
2. R2 보고서의 `692 tests, 0 failures`는 같은 명령으로 재현되지 않았다. 캐시를 강제 배제한 재실행은 `692 tests completed, 1 failed`, `BUILD FAILED`였다.

## (a) 비교 대상 전수 ↔ 갱신 대상 전수

### 양방향 차집합 — 경로 조건까지 포함한 실제 결과

| 도달 경로 | 쓰는데 안 본다 | 보는데 안 쓴다 |
|---|---|---|
| 동일 category인 일반 SHEET/MANUAL, 모든 manual flag false, 보존 규칙 없음 | `∅` | `∅` |
| ECOUNT 기존 행이 비교 필드 전부 일치 | `{lineage, productCategory, name}` | `∅` |
| 기존 행 category가 현재 탭 mapping과 다르고 ECOUNT가 아님 | `∅` | `{panelType, remoteType, pyongSize(해당 시), usageScope, hasVariableDiscount, setMaterialKey, legacyDiscountFlag, discountFlags, fixedDiscountRate, catL, catM, catS}` 중 불일치 필드 |
| `variableDiscountManual=true`, `fixedDiscountManual=false` | `∅` | `{fixedDiscountRate}` |
| `usageScopeManual=false`, usage가 다르며 활성 수량규칙이 NONE 전환을 차단 | `∅` | `{usageScope}` |

즉, R2 보고서의 양방향 `∅/∅`는 **일반 동일-category steady-state라는 부분집합에서만** 맞다. 메서드 전체의 양방향 차집합은 둘 다 0이 아니다.

### 결함 1 [BLOCKING] — R2가 ECOUNT 승격 트리거를 없앨 수 있다

R2는 `name`을 판정에서 제거했지만 이름 쓰기 자체는 ECOUNT 승격 분기 안에 남겼다. 기존 ECOUNT 행의 나머지 비교 필드가 시트와 같으면 `isProductRowUnchanged()==true`가 되어 update 분기에 진입하지 않는다. 그러면 다음 세 mutation이 모두 영원히 skip된다.

```java
boolean promotedFromEcount = p.promoteEcountToSheet();
if (promotedFromEcount) {
    p.rename(name);
    p.changeProductCategory(mapping.productCategory);
}
```

재현 절차(격리 PostgreSQL fixture):

1. `lineage=ECOUNT`, `productCategory=null`, `usageScope=NONE`인 ECOUNT 품목을 만든다. 이 상태는 V28 trigger와 ECOUNT importer의 정상 생성 상태다.
2. `UsageScope.NONE`인 구성품 탭(`싱글 구성품` 또는 `상업멀티 구성`)에 같은 modelCode를 두고, 가격·파생 속성·할인·분류를 DB와 같게 맞추되 시트명만 다르게 둔다.
3. `syncAll()`을 두 번 실행한다.
4. 현재 코드 흐름상 두 번 모두 name drift만 세고 unchanged로 빠지며 `lineage=ECOUNT`, `productCategory=null`, 기존 name이 남는다.

실행 원문에 해당하는 현재 분기:

```text
1266-1270: name 불일치 -> nameDrift++ / INFO
1272-1274: existing.isPresent() && !isProductRowUnchanged(...) 일 때만 update
1280-1297: update 안에서만 promoteEcountToSheet / rename / changeProductCategory
1336-1349: 그 외 existing은 unchanged 분기
```

기존 `EcountSheetOrderConvergenceIT`는 ECOUNT 가격(100,000/70,000)과 시트 가격(150,000/100,000)을 다르게 두므로 가격 비교가 update 분기를 강제한다. 따라서 위 “나머지 비교 필드가 이미 같음” 경계를 덮지 않는다.

### 결함 2 [HIGH] — 판정 가드와 쓰기 가드가 달라 영구 `updated`가 가능하다

두 독립 도달 경로가 있다.

- 다른 productCategory 탭: 판정기는 category 일치 여부와 무관하게 속성·usage·할인·분류를 전부 비교하지만, writer는 `p.getProductCategory() == mapping.productCategory || promotedFromEcount` 안에서만 해당 필드를 쓴다. 같은 modelCode가 여러 탭에 나타나는 것은 실 데이터에서 실제 발생한다(보존된 실측: 3,057 row occurrence / 1,118 distinct model).
- manual flag 조합: `fixedDiscountRate` 비교 조건은 `!fixedDiscountManual`뿐인데, 쓰기는 바깥의 `!variableDiscountManual`도 만족해야 한다. `markVariableDiscountManual()`은 fixed manual flag를 세우지 않으므로 `variableDiscountManual=true && fixedDiscountManual=false`는 정상 도달 상태다.

재현 절차:

1. 동일 modelCode를 서로 다른 productCategory 탭에 놓고 category별 파생 속성 또는 할인/분류 중 하나를 다르게 둔다. 첫 탭이 productCategory를 소유하게 한다.
2. 또는 품목에 `markVariableDiscountManual(...)`만 적용하고 DB fixed rate와 시트 fixed rate를 다르게 둔다.
3. 동일 입력으로 sync를 두 번 실행한다.
4. 두 경우 모두 판정은 매번 false이나 해당 필드는 writer guard 때문에 바뀌지 않아 매번 `updated++`가 가능하다.

관련 실행 원문:

```text
1293: if (p.getProductCategory() == mapping.productCategory || promotedFromEcount)
1320: if (!p.isVariableDiscountManual())
1321: nextFixedRate = fixed manual ? 현재값 : 시트값
1455-1459: variable discount 필드 비교 가드
1462: fixedDiscountRate 비교는 !fixedDiscountManual만 확인
```

활성 수량규칙이 `usageScope -> NONE` 쓰기를 막는 경로도 같은 “보는데 안 쓴다” 구조다. 다만 이 경로는 `preservedByRule`로 의도적으로 보존하며 R2가 새로 만든 것은 아니다. 그럼에도 `result.updated++`는 올라가므로 반복 실행 판정은 수렴하지 않는다.

## (b) `nameDrift`가 판정을 오염시키는가

### 집계 오염

`nameDrift++`는 update 판정 호출 전에 독립 수행되고, 이후 행은 실제 판정 결과에 따라 `updated` 또는 `unchanged` 중 하나에도 들어간다. `nameDrift` 자체가 판정 boolean에 입력되지는 않는다. 따라서 동일-category SHEET/MANUAL 이름-only 테스트에서는 다음이 동시에 성립했고, updated/unchanged를 서로 바꾸지 않았다.

```text
[ProductSheetSync] tab '홈멀티' modelCode='NAME_DRIFT_MODEL' name drift observed (DB name retained)
[ProductSheetSync] tab '홈멀티': inserted=0, updated=0, unchanged=1, nameDrift=1, ...
```

다만 결함 1처럼 ECOUNT 승격 필요 상태까지 이름-only로 취급해 unchanged로 보내므로, “카운터가 boolean을 직접 오염하지 않는다”와 “판정 의미가 올바르다”는 별개다.

### 로그 폭주

로그는 drift model당 1회가 아니라 **탭의 row occurrence당 INFO 1회**다. 테스트에서도 같은 `NAME_DRIFT_MODEL`이 여러 탭 응답에 나타나자 한 sync에서 홈멀티·상업멀티·상업멀티 구성·구형 각각에 INFO가 찍혔다.

직전 실측 증거는 다음까지만 보존되어 있다.

```text
ALL=3057 DISTINCT_ORDINAL=1118 MISSING=2
NAME_DIFF=481 NAME_ONLY_MIN_CANDIDATES=481 ECOUNT_OVERLAP=0
```

따라서 현재 실 데이터 기준 **최소 481 INFO/전체 sync**이고, drift 모델이 여러 탭에 중복되면 481보다 많다. 실 시트 재접근 금지 때문에 정확한 occurrence 수는 이번 라운드에서 관측 불가다. 최소 481개의 row별 INFO는 정기/수동 sync 한 번의 진단 로그로는 폭주로 판정한다. 탭별 summary의 `nameDrift`만으로 관측 가능하므로 row별 INFO가 필수인 구조도 아니다.

### 결함 3 [MED] — `nameDrift`가 모델 수가 아니라 탭 occurrence 수다

`summary.totalNameDrift += tabResult.nameDrift`이므로 동일 modelCode가 여러 탭에서 drift이면 합계도 중복된다. 운영자가 “이름 불일치 품목 수”로 읽으면 과대 집계된다. 테스트 원문이 같은 modelCode의 다중 탭 INFO를 직접 보였다.

## (e) 라이브 관측

**관측 불가**다. 현재 배포 컨테이너가 이 worktree HEAD라는 보장이 없고, sync POST는 dry-run이 아니어서 실 DB를 쓴다. 실 Google Sheet 접근도 명시적으로 금지됐다. 따라서 라이브 sync, 정확한 drift occurrence 수, ECOUNT overlap 재측정은 수행하지 않았으며 결함 0으로 세지 않았다.
