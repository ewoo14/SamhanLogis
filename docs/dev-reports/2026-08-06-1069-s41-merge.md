# #1069 S41 — main 머지 충돌 해소

## 판정

`git merge origin/main`을 수행했고, 충돌 3개를 의미 단위로 해소했다. `git push`는 하지 않았다.

충돌 원문은 다음과 같았다.

- `ProductSummary.java`: HEAD는 `bundleMode`를 추가했고, `origin/main`은 `fixedDiscountRate`를 추가했다. 실제 `hasVariableDiscount`는 `ProductSummaryResponse` 및 desktop 상품 응답 타입에 이미 존재했다.
- `SlipFormPage.tsx`: HEAD는 최근단가 응답 후 최신 BUNDLE 행을 재전개했고, `origin/main`은 고정DC·전역DC 단가 우선 및 경합 가드를 추가했다.
- `SlipService.java`: HEAD는 세트 계보/옵션/부모단가 인자를 전달했고, `origin/main`은 화면에서 계산된 DC 단가를 서버 저장 정본으로 사용했다.

## 해소 내용과 의도 보존 근거

### ProductSummary

canonical record에 아래 두 필드를 모두 유지했다.

```text
String bundleMode
BigDecimal fixedDiscountRate
```

기존 호환 생성자는 유지하고, `bundleMode` 생성자는 새 canonical에 `fixedDiscountRate = null`로 위임했다. 따라서 BUNDLE 정책(`KEEP`/`EXPAND`/null)과 #874의 고정DC 계약이 각각 사라지지 않는다. `hasVariableDiscount`는 product-service `ProductSummaryResponse`의 기존 wire 필드와 desktop 상품 타입 경로에 이미 남아 있음을 확인했다.

### SlipFormPage

최근단가가 있더라도 authoritative DC 결과가 있으면 DC 단가를 유지하고, DC가 없을 때만 최근단가를 사용한다. 응답 후 `latestBundle`을 현재 행에서 다시 취득해 `expandSelectedBundle`에 넘기는 HEAD의 재전개 흐름도 유지했다.

추가 회귀 단정 `applies global DC to a BUNDLE base price before expanding its components`를 넣었다. mock BUNDLE 정가 10,000원에 전역DC 48%를 적용한 5,200원이 `expandBundleLine` 호출의 `unitPrice`로 전달되는지 검사한다.

### SlipService

`calculatedPrices.get(lineIndex)`를 `addSlipLinesExpanded`의 단가로 사용하되, HEAD의 `setOptions`, `parentSetModel`, `setHead`, `bundleParentProductId`, `bundleParentUnitPrice` 인자를 모두 보존했다. 따라서 FE/서버 양쪽에서 DC가 반영된 세트 base 단가가 구성품 재배분 엔진에 들어가고, 계보·옵션 문맥도 유지된다.

## BUNDLE + DC 공존 확인 근거

- 코드: `SlipFormPage.tsx`의 `hasAuthoritativeDiscount` → `resolvedUnitPrice` → `expandSelectedBundle` 경로.
- 코드: `SlipService.create()`의 `calculatedPrices` → `addSlipLinesExpanded()` → `productClient.expand(..., unitPrice)` 경로.
- 테스트: `SlipFormPage.test.tsx`의 신규 공존 테스트가 10,000 × (1 - 48%) = 5,200을 전개 호출 단가로 확인.
- 지정 Playwright bundle 옵션 스위트 9/9 통과.
