# 2026-08-01 #1017 기능 회귀 검토 R3

## 1. 세 번째 fix 정적 표면

V61 원문을 확인했다. 세 번째 fix는 target 적재 직후 `new_line_total = new_supply`로 정규화하며, NEW 매칭·감사 after JSON·실제 UPDATE도 모두 `line_total = new_supply`를 사용한다. OLD 매칭은 기존 실 DB 값인 `old_line_total`을 그대로 사용한다.

출력 원문:

```text
UPDATE vat_correction_targets SET new_line_total = new_supply;
CASE WHEN sl.unit_price=t.old_unit_price AND sl.unit_price_with_vat=t.old_unit_vat AND sl.supply_amount=t.old_supply AND sl.vat_amount=t.old_vat AND sl.line_total=t.old_line_total THEN 'OLD' ELSE 'NEW' END AS state
OR (sl.unit_price=t.new_unit_price AND sl.unit_price_with_vat=t.new_unit_vat AND sl.supply_amount=t.new_supply AND sl.vat_amount=t.new_vat AND sl.line_total=t.new_supply))
jsonb_build_object('unit_price',t.new_unit_price,'unit_price_with_vat',t.new_unit_vat,'supply_amount',t.new_supply,'vat_amount',t.new_vat,'line_total',t.new_supply)
UPDATE slip_lines sl SET unit_price=t.new_unit_price,unit_price_with_vat=t.new_unit_vat,supply_amount=t.new_supply,vat_amount=t.new_vat,line_total=t.new_supply,modified_at=NOW(),modified_by='v61-vat-correction'
```

정적 계약은 요청한 새 의미와 일치한다. 실행 시 실제 19행, 재실행 0행, 소비처 영향은 아래에서 독립적으로 검증한다.

## 5. 공유 실 DB 읽기 전용 19행 재확인

첫 연결은 존재하지 않는 기본 역할을 지정해 인증 단계에서 거부됐고 SQL은 실행되지 않았다.

```text
psql: error: connection to server on socket "/var/run/postgresql/.s.PGSQL.5432" failed: FATAL:  role "postgres" does not exist
```

컨테이너의 사용자 이름만 확인한 뒤, `PGOPTIONS=-c default_transaction_read_only=on`과 `BEGIN READ ONLY`를 함께 적용했다. V61의 19개 VALUES와 최종 품목명 CASE를 순수 CTE로 만들고 실제 OLD/NEW 조인 조건을 그대로 실행했다. UUID는 조회·출력하지 않았다.

출력 원문:

```text
BEGIN
SET
 exact_matches | distinct_targets | old_state_rows | new_state_rows | missing_targets | extra_matches 
---------------+------------------+----------------+----------------+-----------------+---------------
            19 |               19 |             19 |              0 |               0 |             0
(1 row)

ROLLBACK
```

판정: 실 DB 대상은 여전히 정확히 19행이며 전부 OLD다. 누락 0, 중복 매치 0, NEW 0이다. 공유 스택은 재빌드·재기동하지 않았고 공유 DB 쓰기는 없었다.

분류 결과:

- 거래처 원장: `PartnerLedgerSalesResponse`가 저장 공급가액+VAT를 사용한다. 정정 후 원래 사용자 총액으로 내려가며 새 회귀가 없다.
- 세금계산서/홈택스 리포트: `SlipSalesQueryResponse`가 공급가액과 VAT를 별도 합산한다. 새 계약과 맞다. 단 현재 대상은 모두 `SENT` 11전표 또는 `REJECTED` 1전표라 `CONFIRMED` 전용 세금 리포트에는 아직 들어가지 않는다.
- 회계 배분/마감: slip-service의 회계 snapshot은 raw `line_total`이 아니라 `unit_price_with_vat × quantity`를 VAT 포함 합계로 만들어 보낸다. 격리 target에서 이 합계와 `supply+vat`는 각각 원래 총액과 19/19 일치했다. 월마감의 `line.getLineTotal()`은 accounting-service 자체 매출전표 라인과 배분비율을 읽는 것으로, V61이 수정하는 `slip_db.slip_lines` 직접 소비가 아니다.
- 전표 상세·현행 인쇄 금액 helper: 공급가액+VAT를 표시한다. 정정 후 51,690,000원으로 수렴하는 의도된 변화다. `InvoiceView`도 `line_total`을 공급가액으로 읽어 VAT를 더하므로 새 계약과 맞는다.
- 잘못되는 경로: `SlipResponse`, `SlipSearchResult`, `SlipCleanupService`, `SlipSignatureService`는 `line_total`만 “합계”로 내린다. 이 중 판매조회 `금액`, 그룹웨어 전표 검색 금액, 전표 정리 리포트 금액은 정정 후 공급가액만 표시한다.

## 9. 최종 판정

**BLOCK — 세 번째 fix의 DB 정정 계약은 맞지만, 새 `line_total=공급가액` 상태를 총액으로 노출하는 도달 가능한 사용자 화면 회귀가 재현됐다.**

1. 두 등식은 각각 19/19 성립한다.
2. 두 번째 업무 핵심 실행은 OLD 0행, NEW 19행, 감사 INSERT 0행, UPDATE 0행이다.
3. 실 DB 매칭은 OLD 19행·누락 0·중복 0으로 유지된다.
4. 6개 환경은 정확 19, 부분 적용, 삭제, 금액 변경, 중복 롤백, 치환 격리 동작을 모두 재현했다.
5. 원장·세금 리포트·회계 snapshot·상세/인쇄는 공급가액+VAT 또는 VAT 포함 단가를 사용해 정정 후 사용자 총액을 유지한다.
6. 그러나 판매조회 목록, 그룹웨어 전표 검색, 전표 정리 리포트는 raw `line_total`만 합계로 쓴다. 12개 대상 전표에서 사용자가 보던 목록 금액 합계 51,690,000원이 46,990,908원으로 바뀌고, 같은 전표 상세의 51,690,000원과 불일치한다. 이 실제 표시 회귀 때문에 현 상태로 배포 승인할 수 없다.
