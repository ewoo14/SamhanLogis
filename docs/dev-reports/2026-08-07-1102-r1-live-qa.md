2. 루트 작업공간이 이미 대상 브랜치를 점유해 동일 브랜치를 새 worktree에 연결할 수 없었다. 루트 checkout은 바꾸지 않고 `.claude/worktrees/t1103`을 **detached HEAD `1c6aa6ea1`**로 만들었다. 렌더 소스는 PR head와 byte-identical이다.

## 1. 시나리오 ① — 결함 재현 시도

### 표본과 실행

- 거래처: 부산냉난방테크
- 품목: `AR09TXEAAWKNEU-04` (카탈로그 판매가 1,080,000원)
- 기존 최근단가: 60,000원
- 실제 GUI 경로: `/#/sales/new` → 거래처 선택 → 출고창고 선택 → 품목 정확일치 자동확정
- 네트워크: 품목 검색 GET 200, 단건 최근단가 GET 200, 최근단가 응답 **18ms**

실행 원문:

```text
chromium.launch({ headless: true })
GET /api/products?q=AR09TXEAAWKNEU-04&usageScope=PARTNER_ORDER → 200
GET /slips/price-memory?... → 200 (18ms)
mock 호출 → 0건
```

### 관측

실제 가격 요청이 pending인 시점의 제품 DOM 실측:

```text
priceRequestsPending=1
unitPrice="0"
price note="판매가"
```

응답 완료 후:

```text
unitPrice="60,000"
price note="거래처 최근단가"
```

고빈도 샘플 120개의 값 전이는 `0 → 60,000`이었다. 조회 중 카탈로그 값 1,080,000원이 확정값처럼 보이지는 않았지만, 요구 계약은 “빈 값 + note 숨김”이다. 실제 화면은 빈 값 대신 숫자 `0`, 숨겨야 할 가격 출처 note 대신 `판매가`를 노출했다. 따라서 **fix 미완료, 도달 결함 1건**으로 판정한다.

### 조회 중 캡처 관측 불가

18ms 응답보다 Playwright PNG 캡처가 느려 `01` 캡처 시점에는 이미 60,000원으로 수렴했다. 응답을 지연하거나 가로채지 않았으며, `01`과 `02`가 동일한 완료 화면인 이유다. 조회 중 `0`/`판매가` 상태는 실제 요청 pending 플래그와 브라우저 DOM 샘플로 포착했지만 **PNG로는 관측 불가**로 남긴다.

```sql
SELECT s.slip_no, s.status, l.model_name,
       l.unit_price_with_vat, l.supply_amount, l.vat_amount
FROM slips s
JOIN slip_lines l ON l.slip_id = s.id
WHERE s.slip_no = '2026/08/07-18'
  AND s.is_deleted = false
  AND l.is_deleted = false
```


- 조회 중 PNG: 가격 응답 18ms/12ms/10ms로 캡처 전에 완료. 실제 네트워크를 지연하지 않았다.
