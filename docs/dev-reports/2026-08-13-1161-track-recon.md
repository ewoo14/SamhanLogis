### 1.3 현행 코드에서 직접 다시 센 정적 표면

대상은 S2 spec이 producer로 정한 14개 업무 서비스다. `logging-service`, `api-gateway`, `eureka-server`는 제외했다. `src/main/java/**/*.java`에서 주석/Javadoc을 제외하려고 줄 시작의 실제 annotation만 세었다.

```powershell
# 서비스별 main source에서 줄 시작의 mapping annotation 계수
'^\s*@GetMapping\b'
'^\s*@PostMapping\b'
'^\s*@PutMapping\b'
'^\s*@PatchMapping\b'
'^\s*@DeleteMapping\b'
'^\s*@Scheduled\b'
'\bimplements\s+CommandLineRunner\b'
```

완전 수식 annotation도 별도로 검사했다. producer 14개에는 추가 hit가 없었다. 저장소 전체의 추가 hit는 producer 대상이 아닌 `logging-service`의 `@org.springframework.web.bind.annotation.PostMapping("/front")` 1개였다(`AuditLogController.java:90-100`). `@RequestMapping(method=...)` 형식도 main source에서 추가 hit가 없었다.

재현 가능한 현재 정적 HTTP 표면은 **1,017개(조회 449 + 변경 method 568)**다. scheduler와 runner class를 기계적으로 더하면 **1,057개**다. 2026-08-10의 변경 annotation 556은 현재 568로 12개 늘었다.

그러나 **1,017 또는 1,057을 곧바로 “발행해야 하는 지점”의 확정 분모로 쓰지 않는다.** 이유는 다음과 같다.

- annotation 수는 실제 Spring `HandlerMethod` 수와 다를 수 있고 composed mapping, profile, 중복 route를 판정하지 못한다.
- 성공·실패는 route 두 개가 아니라 요청 완료 결과 하나의 분기다. 둘을 곱해 분모를 부풀릴 근거가 없다.
- 조회 의미 POST, 상태 변경 GET, SSE 최초 연결과 heartbeat, internal route, no-op을 annotation만으로 분류할 수 없다.
- `CommandLineRunner` 20개와 `@Scheduled` 20개 모두가 업무 데이터를 바꾼다는 업무 의미를 이번 정찰에서 추론하지 않았다.
- Flyway DML과 운영 script는 과거 보고서가 누락 축으로 지적했으나 S2 판별식에 포함할지는 명시적으로 닫히지 않았다.

현행 정본 spec은 구현 시 실제 `HandlerMethod` 목록을 추출해 각 route를 `기본 capture / override / 기술 exclude` 중 하나로 분류한 manifest를 분모로 삼고, HTTP 밖 scheduler/import/consumer를 별도 목록화하라고 한다(`docs/superpowers/specs/2026-08-12-1161-s2-audit-publishers.md:587-592`). **그 manifest는 현재 저장소에 없다.** 따라서 현행 의도상 분모의 *정의*는 있으나, 현재의 확정 *숫자*는 판정 불가다.

## 2. `shared:audit-publisher`와 S2a가 제공하는 계약

### 2.1 와이어 계약

`AuditEventV2`는 다음 축을 한 이벤트에 담는다(`shared/audit-contract/.../AuditEventV2.java:12-21`).

- 식별/출처: schema version, event id, service name.
- 분류: retention A/B/C, event kind, outcome, action.
- 상관관계: requestId, traceId, parentService.
- HTTP: method, route template, status, duration.
- actor/resource: userId, 표시명, role, resource type, 표시 ID, internal ID.
- 진단: description, before/after, error code/class/root cause/summary/fingerprint.
- 환경/시각: IP, user-agent, occurredAt.

라우팅은 `audit.change.<service>`, `audit.failure.<service>`, `audit.read.<service>`다(`AuditTopology.java:5-17`). validator는 필수 필드와 action-retention A/B/C 일치를 검사한다(`AuditEventValidator.java:8-20`). UUID 표시 방어는 `AuditSanitizer`가 canonical/32hex/URN 형태를 placeholder로 치환한다(`AuditSanitizer.java:7-27`).

다만 현재 factory와 sink는 wire 필드 전체를 끝까지 살리지 않는다.

- 세 factory는 `requestId`, `traceId`, `parentService`를 전부 null로 만든다(`AuditEventV2.java:31-69`).
- consumer wire DTO에는 이 필드들이 있지만(`logging-service/.../AuditLogEvent.java:31-49`), ES entity와 consumer mapping은 retention/eventKind/outcome/requestId/traceId/route/duration/error class/fingerprint를 저장하지 않는다(`AuditLogConsumer.java:34-54`, `AuditLog.java:35-94`).
- 따라서 현재 개발자 로그에서 S2의 핵심 목적이던 요청 상관관계 검색은 불가능하다.
- C_READ enum/routing/lane은 있으나 production main source에 C_READ 이벤트를 만드는 호출자가 없다. 두 pilot의 GET은 아직 중앙 발행하지 않는다.

### 2.2 실패·동기성 계약

`publishAfterCommit`은 transaction synchronization이 활성화되어 있으면 commit 뒤 enqueue하고, 없으면 즉시 `publish`한다(`AuditPublisher.java:67-76`). enqueue는 용량 128의 A/B priority lane과 용량 128의 C read lane에 `offer` 한 번만 수행한다(`:24-45`, `:53-64`). Rabbit `convertAndSend`는 daemon worker 2개에서 실행되고 RuntimeException은 worker가 흡수한다(`:78-91`).

따라서 현재 계약은 다음과 같다.

- request thread에서 Rabbit network publish를 하지 않는다.
- 중앙 발행 실패가 업무 예외로 전파되지 않는다.
- transaction이 있으면 성공 event는 commit 이후에만 enqueue한다.
- C가 A/B의 in-memory lane을 잠식하지 않는다.
- in-memory lane이 가득 차면 drop counter를 올리고 즉시 반환한다.

주의할 점:

- lane 크기 128, worker 2는 설정값이 아니라 하드코딩이다.
- retry/backoff, publisher confirm/return, nack/unroutable/retry-exhausted metric이 없다.
- queue-full은 counter만 올리고 해당 유실을 structured WARN으로 남기지 않는다.
- process가 enqueue 뒤 publish 전에 종료되면 in-memory event는 사라질 수 있다.
- `AuditContextContributor`는 interface만 있고 production 구현/호출자가 없다(`AuditContextContributor.java:5-8`).
- spec이 채택한 공통 request outcome filter, `@AuditKind`, `@AuditIgnore`, `publishSummary` 및 HandlerMethod manifest는 현재 코드에 없다. 따라서 S2a는 **공통 publisher primitive + 수동 pilot wiring** 단계다.

### 2.3 S0 부하 결론 반영 여부: 부분 반영

| S0/후속 결정 | 현행 S2a | 판정 |
|---|---|---|
| 업무 transaction을 막지 않는 비동기·논블로킹 발행 | after-commit + bounded offer + daemon worker + 예외 흡수 | 반영 |
| A/B를 C보다 우선 보존 | producer in-memory lane 분리 | 부분 반영 — broker에는 단일 queue |
| 유실이 생기면 유실 사실이 남음 | queue-full counter, worker WARN | 부분 반영 — 사유별 metric/confirm/retry 소진 없음 |
| consumer ES 실패 재시도 후 DLQ | consumer는 save 예외를 재throw | 미완료 — bounded backoff 정책 확인 불가, DLQ consumer 없음 |
| queue max-length·TTL | `RabbitConfig`에는 DLX/DLQ argument만 존재(`RabbitConfig.java:46-59`) | 미반영 |
| DLQ 소비·임계 관측 | DLQ 선언만 있고 listener/alert 없음 | 미반영 |
| A=1년, B=1년, C=30일 + rollover | 고정 `samhan-audit-logs`; ILM은 “later” 주석(`AuditLog.java:21-25`) | 미반영 |
| requestId로 진단 상관관계 | wire 필드는 있으나 factory null, ES 미저장 | 미반영 |

이는 기존 spec이 이미 밝힌 상태와 일치한다. S1.5가 미완료면 S2a 격리 구현은 가능하지만 14개 전체 활성화 전에 S1.5를 gate로 두라고 명시돼 있다(`...s2-audit-publishers.md:488-492`). 이번 정찰은 S0 부하를 다시 발생시키거나 Rabbit/ES 런타임 상태를 재측정하지 않았다.

## 3. 나머지 12개 서비스 확장 시 걸리는 것

### 3.1 공통 시작점

나머지 12개에는 현재 다음 세 가지가 모두 없다.

1. `shared:audit-publisher`/AMQP Gradle 의존성.
2. `AuditPublisherAutoConfiguration` DI import.
3. `samhan.audit.publisher.enabled` 설정과 `AuditPublisher` 호출.

모든 producer 서비스에는 각자의 `SecurityConfig`가 있어 handler 이전 인증/인가 실패를 잡으려면 security chain과의 결합을 서비스별로 검증해야 한다. 단순 Gradle 의존성 추가만으로는 GET, validation/security 실패, scheduler/batch를 발행하지 않는다.

### 3.3 기존 감사 계열과 중앙 파이프의 관계

2026-08-12 최신 결정은 과거 “중앙 일원화/서비스별 제거”를 폐기하고 **서비스별 + 중앙을 모두 유지**한다(`...s2-audit-publishers.md:264-273`, `:631-639`). 따라서 다음은 중앙 파이프와 중복 구현 관계가 아니다.

- `accounting_audit_logs` 등 서비스별 `*_audit_logs`, revision/history: 도메인 상세 diff·복원·원자성의 정본.
- `createAuditApi`: desktop이 여러 서비스별 감사 조회 endpoint를 공통 UI 형태로 읽는 adapter(`clients/desktop/src/renderer/api/createAuditApi.ts:85-146`). publisher가 아니다.
- `BaseEntity` 7 audit column: 행의 생성/수정자·시각·soft-delete 상태. 요청 결과, 실패, 조회, service chain을 나타내지 않는다.
- 중앙 event: 서비스 횡단 요청 결과와 진단 상관관계를 위한 요약/fan-out. 상세 local audit를 대체하지 않는다.

즉 중앙 파이프는 local 상세 기록의 **보완 경로**다. 다만 현행 S2a는 requestId와 공통 request capture가 없어 이 보완 역할을 아직 완성하지 못했다.

## 4. 다음 슬라이스 후보

설계를 하나로 확정하지 않고, 서로 다른 증명 범위와 잔여를 분리한다.

### 후보 A — 기존 S1.5: 보존 정책 + 실패 경로를 먼저 닫기

**증명하는 것**

- broker queue 상한/TTL과 DLQ 소비·관측이 실제로 동작한다.
- ES rollover/ILM에 A/B/C 보존 초기값을 연결한다.
- consumer ES 실패가 재시도 후 DLQ로 가고 조용히 사라지지 않는다.
- 12개를 켜기 전 sink/backpressure gate를 만족한다.

**남는 것**

- publisher 분자는 여전히 2개 서비스/3호출문이다.
- GET 공통 capture, requestId persistence, HandlerMethod manifest는 남는다.
- S2b~S2e 서비스 확장은 모두 남는다.

**대가**

- 발행 커버리지 숫자는 당장 늘지 않는다.
- Rabbit queue argument 변경은 기존 durable queue와의 호환/재선언 절차를 별도로 검증해야 한다.

### 후보 B — S2a 계약 마감: 공통 request outcome + manifest + 진단 필드

**증명하는 것**

- 두 pilot의 모든 업무 HTTP route가 기본 capture/override/기술 exclude로 분류된다.
- GET 성공, mutation 성공, validation/security 실패가 요청당 1건으로 발행된다.
- requestId/trace/route/outcome/retention이 ES와 조회까지 살아 있다.
- 정적 annotation 수가 아닌 실제 HandlerMethod 기반 분모가 처음으로 산출된다.

**남는 것**

- S1.5 broker/ILM/DLQ gate가 남는다.
- 나머지 12개 dependency/enablement와 domain contributor는 남는다.
- scheduler/import/runner 대상의 업무 판정은 별도다.

**대가**

- 기존 S2a를 완료로 본 범위에 보완 슬라이스가 추가된다.
- S1.5 전에 event 양을 늘리면 안 되므로 두 pilot을 넘는 활성화는 여전히 금지해야 한다.

### 후보 C — 기존 S2b: auth·user·dashboard 확장

**증명하는 것**

- 로그인/권한/잠금/비밀번호와 handler 이전 실패를 내부 사용자 security chain에서도 잡을 수 있다.
- local audit가 없는 auth/dashboard에서도 중앙 요약이 작동한다.
- 사용자/역할 표시값과 secret redaction 계약을 검증한다.

**남는 것**

- S1.5와 S2c~S2e 9개 서비스가 남는다.
- 공통 request filter/manifest 없이 수동 호출을 늘리면 route 누락이 계속 남는다.
- requestId 미저장 상태라 진단 목적은 미완성이다.

**대가**

- 기존 spec의 “S1.5 선행 gate”를 넘어서므로, A 없이 C를 선택하면 sink/backpressure 위험을 수용하는 별도 결정이 필요하다.
- B 없이 C를 선택하면 pilot의 수동 wiring 패턴을 확장했다가 공통 capture로 다시 바꿀 재작업 위험이 있다.

## 5. 개발책임자 판단이 필요한 질문

1. **현행 분모의 비-HTTP 경계**: S2 spec의 `HandlerMethod manifest + 상태 변경 scheduler/import/consumer`를 정본으로 확정하고, `CommandLineRunner`/Flyway DML/운영 script는 (a) 포함 / (b) 별도 운영감사 트랙 / (c) 제외 중 어디에 둘 것인가? 본 정찰은 업무 의미를 정하지 않아 숫자로 합치지 않았다.
2. **다음 슬라이스**: (a) 기존 gate대로 S1.5 / (b) S2a 계약 마감 / (c) S1.5와 S2a 계약 마감을 한 통합 슬라이스로 진행 중 어느 경계를 택할 것인가? S2b는 두 gate 뒤가 기존 결정과 가장 일관되지만, 이것은 최종 설계 확정이 아니라 선택지 비교다.

## 6. 판정 불가로 남긴 것

1. **확정 분모 숫자**: 실제 `HandlerMethod` manifest가 없고 기술 exclude/override 분류도 구현되지 않아 1,017은 정적 raw surface일 뿐이다.
2. **3호출문의 runtime 발행 횟수/성공률**: DB 쓰기·실요청 발화 없이 코드 경로만 확인했다. S2a 당시 QA 증거는 존재하지만 현재 runtime을 재발화하지 않았다.
3. **partner-auth failure helper의 route cardinality**: 한 helper가 validation 가능한 여러 endpoint에 걸릴 수 있어 호출문 수를 route 커버리지로 환산하지 않았다.
4. **현 시점 Rabbit/ES 수동 운영 설정**: S0 부하를 다시 재지 말라는 지시를 따라 live topology/ILM을 재조회하지 않았다. 저장소 선언 기준으로는 S1.5 미구현이다.
5. **runner/scheduler/Flyway의 감사 업무성**: 코드 존재 수만 셌고 무엇을 감사 대상으로 볼지는 개발책임자 판단으로 남겼다.
6. **법적 보존 기간**: A/B 1년, C 30일은 잠정 운영값이며 법적 요구는 기존 이슈에서도 미확정이다.

## 7. 정찰 결론

S2a는 트랙 미착수가 아니라 **공통 wire/publisher primitive와 2개 pilot의 대표 경로 3호출문까지 진행된 상태**다. 그러나 두 pilot 전 route coverage, 공통 request outcome, requestId 저장, 정확한 HandlerMethod 분모, S1.5 보존·실패 경로는 아직 없다.

따라서 이슈 제목의 `580개 중 0개`는 현재 진행률 표기로 사용하면 안 된다. 다음 슬라이스의 실질 경계는 “sink를 먼저 안전하게 만드는 S1.5”, “S2a의 공통 capture/manifest/진단 계약을 마감”, “S2b 서비스 확대”의 세 선택지이며, 앞의 두 gate를 어떤 순서와 PR 경계로 닫을지 결정해야 한다.
