# #1075 S2 SOL fix 지시서 — 견적 품목 후보 확정 차단

## ① 좌표

### 결함 1 — 공용 후보를 고른 뒤 견적의 `productId`가 확정되지 않아 저장이 차단된다

- `clients/desktop/src/renderer/routes/EstimateFormPage.tsx:1335-1430`
  - 공용 `ProductOption`과 레거시 `ProductLookupResult`를 하나의 `result`로 합친 뒤 `result.productId`를 읽는다.
  - 공용 후보의 내부 키는 `id`이므로 후보 선택 경로에서는 `productId`가 비어 있다.
  - 같은 구간의 라인 갱신은 후보의 `specification`도 반영하지 않는다.
- `clients/desktop/src/renderer/routes/EstimateFormPage.tsx:1451-1465`
  - 후보 선택 시 `productId`를 먼저 비우고 공용 후보를 ref에 넣은 뒤 레거시 lookup 흐름으로 넘긴다.
- `clients/desktop/src/renderer/routes/EstimateFormPage.tsx:1914-1937`, `2001-2024`
  - 모바일·데스크톱 모두 같은 결함 경로를 사용한다.
- `clients/desktop/src/renderer/routes/EstimateFormPage.tsx:1541-1548`
  - 저장은 `productId`가 없는 라인을 무효로 판정하므로 사용자가 화면에서 품목을 확정해도 저장이 차단된다.
- `clients/web/design-system/src/components/ProductAutocomplete/ProductAutocomplete.tsx:18-39`
  - 공용 계약의 내부 식별자는 `ProductOption.id`, 규격은 `ProductOption.specification`이다.

재현(로컬 mock 번들, `/sales/estimates/new?mockRole=MASTER`):

1. 거래처에서 `삼`을 입력해 `삼한공조 A`를 선택한다.
2. 라인 1 모델명에 `AJ040`을 입력해 단일 후보를 자동 확정한다.
3. 모델명 `AJ040RXH4BC1`, 품목명 `시스템에어컨 4Way 4HP`, 단가 `1850000`이 보이는 상태에서 `임시저장`을 누른다.
4. 실제 결과: `라인 1개 이상 (모델명 lookup 성공 + 수량 > 0) 을 입력하세요.`가 표시되고 저장되지 않는다.

다건 `AJ` 후보에서 첫 후보를 선택 확정하면 가시 모델명 입력이 공백으로 되돌아가고, 숨은 coedit 동기화 입력에만 `AJ040RXH4BC1`이 남는 표면도 재현됐다. 모달 자체에는 UUID가 노출되지 않았다.

환경 분리 증거:

- `clients/web/design-system` 의존성 설치 후 `npm run build` 성공.
- desktop 의존성 재결선 뒤 `npm run typecheck`는 환경 오류 없이 위 결함 좌표에서만 4건 실패했다: `productId` 3건, `sellingPrice` 타입 1건.
- 판매전표 `ac-2-product-autocomplete` 7건과 공용 모달 1건은 같은 번들에서 통과했다. 따라서 공용 컴포넌트 전체 장애가 아니라 견적 어댑터 경로의 결함이다.

### 결함 2 — 기존 mock 하드 게이트가 사라진 입력 계약을 기다려 CI를 red로 만든다

- `clients/desktop/playwright/1062-line-input-ux/1062-line-input-ux.spec.ts:41-55`
  - `estimate-form-line-2-model`을 찾지만 현재 견적의 사용자 입력은 `ProductAutocomplete` combobox이고 해당 test id는 존재하지 않는다.
  - design-system 빌드와 desktop 의존성 재결선 후에도 동일 locator에서 본 실행·retry 모두 60초 timeout으로 실패했다.
  - 같은 실행의 나머지 8건은 통과했으므로 번들 미기동 실패가 아니다.

## ② 불변식 — 수단 지정 금지

1. 견적에서 공용 검색 후보를 단건 자동확정하거나 다건 모달에서 확정하면, 사용자가 본 모델명과 동일한 품목이 내부 식별자까지 확정되어 즉시 저장 가능해야 한다.
2. 후보의 실제 규격과 단가가 견적 라인에 반영되어야 한다. 규격이 존재하는 후보를 선택했는데 기존 공란이 남아서는 안 된다.
3. 후보 확정 후 가시 모델명 입력이 공백으로 되돌아가거나 숨은 coedit 입력과 갈라져서는 안 된다.
4. 판매전표의 공용 후보 모달·단건 자동확정·단가 반영을 회귀시키지 않는다.
5. 견적의 `autoBlankRow`, `estimateRestoreFence`, `lineStructureLocked`, 가격기억, `참조 조회` 계약을 보존한다.
6. UUID는 payload/state 내부에서만 사용하고 화면 텍스트·DOM 접근성 이름에 노출하지 않는다.
7. mock 하드 게이트는 제거·완화하지 말고 현재 사용자 입력 계약으로 갱신하여 자동 빈행까지 계속 단정한다.

구조·API·알고리즘·구체 패치 방식은 구현자가 결정한다. 자체 품목 컴포넌트 신설이나 백엔드 검색 API 변경은 허용하지 않는다.

## ③ 양방향 RED — 반대급부 필수

- **RED-A(새 계약):** 견적 신규 작성에서 규격이 있는 단일 후보와 다건 후보를 각각 확정한 뒤 모델명·품목명·규격·단가·내부 품목 확정 상태가 일치하고 저장 payload에 그 라인이 포함되어야 한다. UUID는 어느 사용자 표면에도 없어야 한다.
- **RED-A 반대급부:** 위 확정 문제를 닫는 변경이 판매전표 선택, 사용자 직접 단가(`USER`) 보존, 거래처 가격기억, 후보 0건의 기존 안내, 자동 빈행, 버전 복원, coedit 구조 잠금, `참조 조회` 중 하나라도 깨면 RED다.
- **RED-B(차단 회귀):** 사용자가 후보를 확정했는데 가시 모델명이 비거나 `productId` 부재로 저장이 차단·누락되면 RED다. 규격 실값이 있는데 공란으로 남거나 후보 1건에 모달이 뜨거나 UUID가 보이면 RED다.
- **RED-B 반대급부:** mock 스펙의 stale locator를 없애는 과정에서 자동 빈행 단정 자체를 삭제하거나, 단순히 기다림/timeout만 늘려 green으로 만들면 RED다. 새 combobox 계약을 통해 품목 확정 후 다음 trailing 빈행 생성까지 증명해야 한다.
