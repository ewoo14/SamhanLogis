# PR #1060 R22 재수렴 — `bizCode` 없는 주문의 생성 가능성과 차단 영향

## 조사 기준

- 작업트리 HEAD: `56b5b5387 [FIX] #1015 출고 생성 전 경로에 사업자번호 보존 + CI red 해소`
- 조사 시작 시 변경 상태: 본 보고서만 신규 파일(`?? docs/dev-reports/2026-08-03-1015-r22-reconvergence.md`).
- 범위: 주문 생성 전 경로의 `bizCode` 제약 3층, 병합 첫 주문 기준과 실데이터 일치성, 400 사용자 표시, 차단 해제 대안의 영향만 확인한다.

## 확인 1 — 공통 DB·엔티티 제약

`partner_orders.biz_code`는 최초 스키마부터 `VARCHAR(20) NOT NULL`이다(`services/partner-order-service/src/main/resources/db/migration/V1__init_partner_order.sql:15-19`). 엔티티도 `@Column(nullable = false, length = 20)`이다(`services/partner-order-service/src/main/java/com/samhanair/logis/partnerorder/domain/PartnerOrder.java:57-59`). 모든 정적 팩토리가 통과하는 private 생성자는 `null`과 blank를 모두 `IllegalArgumentException("bizCode 필수")`로 거부한다(동 파일 `134-151`; 특히 `139-140`).

따라서 JPA 정적 팩토리 경로는 DB 도달 전에 null/blank가 차단되고, 직접 SQL 경로는 null만 DB가 차단한다. `NOT NULL` 자체는 빈 문자열을 막지 않으므로 직접 SQL 경로별 blank 검증은 별도로 확인해야 한다.

## 확인 2 — 주문서 웹앱 확정 경로

- HTTP: `POST /api/v1/partner-orders/{draftId}/confirm` (`PartnerOrderConfirmController.java:44-45,77-90`).
- 사용자 조작: 주문서 웹앱에서 임시저장 주문을 확정한다.
- 요청 층: body `ConfirmRequest`에는 `bizCode` 필드가 없고(`ConfirmRequest.java:15-17`), `X-Biz-Code` 헤더는 `required=false`라 선언 제약은 비어 있다(`PartnerOrderConfirmController.java:82-85`).
- 서비스 층(추가 방어): `PartnerOrderConfirmService.confirm`이 null/blank를 `INVALID_INPUT`으로 거부하고(`105-112`), partner identity 대조 뒤(`128-130`) `PartnerOrder.createFromConfirm`에 전달한다(`217-239`).
- 엔티티·DB 층: 확인 1의 blank 생성자 가드와 `NOT NULL`이 모두 적용된다.

판정: 요청 선언 층만 보면 필수가 아니지만, 현 운영 구현에서는 서비스 가드와 엔티티 가드 때문에 `bizCode` 없는 주문 row는 생성되지 않는다. 헤더 누락 시 주문 생성 자체가 400 계열로 막히는 경로다.

## 확인 3 — 관리자 견적→주문 생성 경로

- HTTP: `POST /api/v1/partner-orders/from-estimate/{estimateId}` (`PartnerOrderFromEstimateController.java:23-43`).
- 사용자 조작: 본사 사용자가 견적을 주문으로 변환한다.
- 요청 DTO 층: body가 없고 path의 `estimateId`만 받으므로 `bizCode` 요청 제약은 없다. 내부 `EstimateClient.EstimateSnapshot.bizCode`에도 Bean Validation 선언은 없다(`EstimateClient.java:18-26`).
- 서비스 층(추가 방어): snapshot의 `partnerCode`/`bizCode`를 `requirePartnerId`로 대조한다(`PartnerOrderFromEstimateService.java:59-69`). resolver는 입력 `bizCode` null/blank를 400으로 거부하고, partner-service 정본 사업자번호가 null/blank이거나 서로 다르면 역시 거부한다(`PartnerOrderPartnerIdentityResolver.java:33-50`).
- 엔티티·DB 층: `createFromEstimate`도 공통 private 생성자를 통과한다(`PartnerOrder.java:241-255`); DB `NOT NULL`도 적용된다.

판정: 요청/외부 snapshot 선언 층에는 제약이 없지만 현 운영 구현은 서비스 정본 대조와 엔티티 가드 때문에 `bizCode` 없는 주문을 만들지 않는다. 값이 없는 견적은 주문 변환 단계에서 400으로 막힌다.

## 확인 4 — MIG-8 관리자 임포트/배치 경로

- HTTP: `POST /admin/partner-orders/mig8-import?batchSize=...` (`Mig8OrderImportController.java:15-28`).
- 사용자 조작: 권한 있는 관리자가 MIG-8 native 이식 배치를 실행한다. 서비스가 accounting export를 페이지 단위로 가져와 주문별로 처리한다(`Mig8OrderImportService.java:51-63`).
- 요청 DTO 층: 요청에는 `batchSize`만 있어 `bizCode` 선언 제약이 없다. 사업자번호는 요청자가 입력하지 않고 partner lookup 결과에서 온다.
- 서비스 층: partner lookup 결과의 `partnerCode`와 `bizCode`가 모두 nonblank일 때만 유효하다(`Mig8OrderImportService.java:237-239,260-262`). miss/invalid는 주문 단위 `rejected`로 끝난다(`77-93`).
- 엔티티 층: 이 경로는 JPA 엔티티를 우회하므로 엔티티 생성자 제약이 적용되지 않는다.
- DB 층: 직접 `INSERT INTO partner_orders(... biz_code ...)`에 검증된 `partner.bizCode()`를 전달한다(`110-133`). DB `NOT NULL`도 적용된다.

판정: 엔티티/요청 선언 층은 비어 있지만, 현 직접 SQL 구현 직전의 `hasText` 검증 때문에 null/blank 주문은 생성되지 않는다. 검증이 제거되면 DB는 null만 막고 blank는 허용하므로 이 경로가 잠재 우회점이다.

## 확인 6 — 병합 전환은 요청의 첫 주문 `bizCode`만 사용

`PartnerOrderMergeConvertService`는 요청 `orders` 순서대로 entity를 조회해 같은 `partnerId`인지까지만 검사한다(`112-134`). `bizCode` 상호 일치 검사는 없다. slip payload의 `partnerCode`와 `bizCode`는 모두 `orders.get(0)`에서만 가져온다(`204-215`). 따라서 다음 두 위험은 코드상 성립한다.

1. 첫 주문의 `bizCode`가 null/blank이면 나머지 주문 값과 무관하게 R21의 slip 요청 `@NotBlank`에서 병합 전체가 400으로 거부된다.
2. 같은 `partnerId` 주문들의 `bizCode`가 서로 다르면 첫 주문 값 하나가 병합 전표 전체의 `business_number`가 된다.

첫 주문은 DB 정렬이 아니라 사용자가 모달에서 선택한 순서다. FE는 주문 추가 때 배열 뒤에 append하고(`MergeConvertDialog.tsx:664`), 그 순서로 상세 조회(`286-297`) 및 request `orders`를 만든다(`462-485`). 즉 사용자가 무엇을 먼저 선택했는지가 전표 사업자번호를 결정한다.

현재 신규 생성 경로는 null/blank를 차단하므로 위험 1의 신규 도달성은 확인되지 않았다. 위험 2는 같은 `partnerId`의 역사적/변경 snapshot 불일치가 있는지 실데이터 집계로 판정한다.

## 확인 8 — 차단 시 사용자 표시

slip-service의 누락 차단은 타깃 IT로 재현했다. 테스트는 `bizCode` 키를 제거하고 실제 MockMvc endpoint에서 400을 단언한다(`SlipPublishControllerIT.java:158-169`).

```text
.\gradlew.bat :services:slip-service:test --tests "com.samhanair.logis.slip.publish.SlipPublishControllerIT.publishFromPartnerOrder_withoutBizCode_returns400InsteadOfCreatingUnidentifiedSlip" --console=plain

> Task :services:slip-service:test

BUILD SUCCESSFUL in 29s
18 actionable tasks: 1 executed, 17 up-to-date
```

서비스 경계에서 원인 정보가 소실된다. `SlipServiceClient`는 slip-service의 400 response body를 읽지 않고 모든 해당 4xx를 `BusinessException(INVALID_INPUT, "slip-service 4xx: 400 BAD_REQUEST")`로 바꾼다. 단일은 `SlipServiceClient.java:136-144`, 병합은 `218-226`이다.

- 단일 전환 사용자 조작: 주문 상세에서 라인/창고를 선택해 `판매전표로 전환` 클릭. 400은 409/403 전용 분기 밖으로 빠져 화면에 `전환에 실패했습니다. 잠시 후 다시 시도해 주세요.`만 표시된다(`SalesPartnerOrderDetailPage.tsx:317-368`, 렌더 `1705-1714`). 원인을 알 수 없다.
- 병합 전환 사용자 조작: 병합 모달에서 주문·라인·창고를 선택해 발행. 400은 BE message를 그대로 써서 `slip-service 4xx: 400 BAD_REQUEST`가 표시된다(`MergeConvertDialog.tsx:493-528`). 기술적 status만 보이며 `사업자번호 없음` 원인은 알 수 없다.

잘못된 결과: 누락 주문이 존재한다는 가정 아래 단일/병합 모두 전표는 생성되지 않고, 사용자는 자기 조작으로 고칠 수 없는 원인을 알 수 없다. 다만 확인 1~5 및 실데이터 0건 때문에 현 상태에서 이 화면까지 도달하는 운영 주문은 확인되지 않아 사용자 영향은 **미판정(현재 측정 0건)**이다.

## 확인 9 — 차단 해제 시 `business_number` 선택지와 영향 건수

slip의 `business_number`는 DB migration과 엔티티 모두 nullable이다(`V20__slip_query_columns.sql:15`, `Slip.java:520-521`). 따라서 DTO `@NotBlank`만 풀면 기술적으로 NULL 전표 생성은 다시 가능하다.

현재 영향 모수는 `bizCode` blank 활성 주문 0건, blank 병합 가능 주문 0건이다. 세 정책 모두 **현재 신규 전환 영향 0건**이다. 과거 `PARTNER_ORDER` 출고의 현재 상태는 다음과 같다.

```text
 active_partner_order_outbound | blank_business_number | blank_with_partner_id | blank_without_partner_id
-------------------------------+-----------------------+-----------------------+--------------------------
                            20 |                    20 |                    17 |                        3
(1 row)
```

두 DB를 각각 SELECT한 뒤 UUID를 출력하지 않고 집계한 정본 조회 가능성:

```text
blank_slips_total=20 canonical_resolvable=17 canonical_blank=0 partner_missing=0 no_partner_id=3
identified_active_orders=1 canonical_match=1 canonical_differs=0 canonical_blank=0 partner_missing=0
```

| 정책 | 현재 blank 주문 영향 | `business_number` 결과 | 관측 영향 |
|---|---:|---|---|
| 비워 두기 | 0건 | NULL/blank 출고 허용 | 현재 과거 NULL `PARTNER_ORDER` 출고 20건과 같은 상태를 계속 만들 수 있다. 그중 17건은 `partner_id`가 있는데도 비어 있다. |
| 정본 조회 | 0건 | `partner_id`로 활성 partner의 `biz_no`를 조회해 snapshot | 현재 `partner_id`가 있는 활성 주문 1/1건은 정본과 일치한다. 과거 blank 출고는 17/20건 정본 조회 가능, 3/20건은 `partner_id`가 없어 불가하다. 조회 실패/삭제 거래처 정책이 추가로 필요하다. |
| 거부 유지 | 0건 | 미식별 출고를 만들지 않음 | 현재 모든 활성 주문 2,021건의 `bizCode`가 채워져 있어 정상 주문 차단 0건. 미래에 경로 제약을 우회한 손상 주문만 차단한다. |

판정: 현재 생성 불변식과 데이터에서는 **거부 유지가 정상 경로를 막지 않는다**. 차단을 풀어야 할 실데이터 근거는 0건이다. 만약 향후 누락 주문을 복구해야 한다면 NULL 허용보다 `partner_id` 정본 조회 후 저장이 더 안전하지만, 정본 조회 불가 시에는 여전히 거부해야 한다. 과거 NULL 출고 20건의 backfill은 이번 단일 각도/쓰기 금지 범위 밖이며 수행하지 않았다.

## 확인 10 — 같은 `partnerId`에서 미래 `bizCode` 불일치가 정상 조작으로 생기는가

거래처의 `partnerCode`와 `bizNo`는 불변 식별자다. 관리자 profile 수정 도메인은 name/address/phone만 갱신하고 둘은 변경하지 않는다(`services/partner-service/src/main/java/com/samhanair/logis/partner/domain/Partner.java:260-271`). 서비스 수정 경로도 같은 계약을 명시하고 `updateProfile`만 호출한다(`PartnerService.java:335-362`).

주문 생성 두 운영 경로는 모두 입력 사업자번호를 현재 같은 거래처 UUID의 정본 사업자번호와 대조한 뒤 snapshot한다(확인 2~3). 따라서 정상 API 조작만으로 같은 `partnerId`에 서로 다른 정규화 `bizCode` 주문이 새로 쌓이는 경로도 확인되지 않았다. 현재 1건의 identified 주문 역시 정본과 일치한다(`canonical_match=1`, `canonical_differs=0`).

판정: `orders.get(0)` 단일 기준은 방어적으로 취약하지만, 현재 코드·데이터에서 서로 다른 값의 다건 병합까지 도달하는 정상 경로는 없다. DB 수기변조/구버전 데이터/미래 불변식 변경을 전제로 한 위험이므로 이번 판정은 **도달 가능한 결함 아님**이다.

## 최종 판정

**이 각도에서 도달 가능한 결함 0.**

- `bizCode` 없는 활성 주문: 0/2,021건.
- 앞으로의 정상 주문 생성 경로: 3개 운영 경로 모두 null/blank를 저장 전에 차단. 개발 seed도 차단.
- 실제 병합 가능 주문: 1건, 다건 병합 집합 0개. 값 불일치 영향 0건이며 다건 실데이터 검증은 모집단 부재로 미판정.
- 같은 거래처 UUID의 서로 다른 `bizCode`: 정상 경로에서는 거래처 사업자번호 불변 + 생성 시 정본 대조로 도달하지 않음.
- R21 `@NotBlank` 유지 시 현재 정상 주문 차단: 0건.
- 차단 시 사용자 메시지는 원인을 설명하지 못하지만, 그 상태에 도달하는 주문이 없어 이번 각도에서는 잠재 방어 품질 문제로만 분류한다.

코드, DB, git에는 쓰지 않았다. 전체 스위트·Docker rebuild·Flyway는 실행하지 않았다. 타깃 IT 1건과 공유 DB read-only SELECT만 실행했다.
