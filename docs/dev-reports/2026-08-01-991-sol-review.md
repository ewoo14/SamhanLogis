# 2026-08-01 991 기능 회귀 검토

## 확인 1 — 저장 스키마의 기존값 처리

- `services/slip-service/src/main/resources/db/migration/V60__preserve_sales_category_axis.sql`은 `slip_lines.category_key VARCHAR(40)`를 nullable 컬럼으로 추가할 뿐 기존 행 backfill을 하지 않는다. 따라서 V60 적용 전에 생성된 라인은 실제로 `category_key = null` 상태가 된다.
- `unit_price_with_vat`도 V12에서 nullable 컬럼으로 추가됐고 당시 backfill이 없다. 따라서 V12 이전 라인 또는 이후에도 해당 값을 채우지 않은 생성 경로가 있다면 null이 가능하다. 실제 건수와 재시도 영향은 아래에서 DB 실측 및 호출 경로로 별도 확인한다.

## 확인 3 — `categoryKey`를 채우는 실제 호출자

`slip-service` 발행 DTO의 `categoryKey`에 값을 보내는 운영 코드 호출자는 다음 두 경로뿐이다.

1. 본사 데스크톱 `판매 > 거래처 주문 상세`의 단건 “출고전표 전환” → `PartnerOrderConvertService`가 저장된 주문 라인의 `getCategoryKey()`를 `lines[].categoryKey`로 전달한다.
2. 같은 업무의 여러 주문 “병합 전환” → `PartnerOrderMergeConvertService`가 각 저장 라인의 `getCategoryKey()`를 그대로 전달한다.

값의 최초 입력 화면은 다음과 같다.

- 거래처용 웹 `order-app`: HOME/COMM/SINGLE/OLD 섹션을 각각 `homemulti`/`commercialMulti`/`singleSets`/`oldProducts`로 매핑한다. 매핑되지 않으면 주문 확정 자체를 오류로 중단하므로 정상 확정 요청에서는 항상 값이 있다.
- 본사 데스크톱 `SalesPartnerOrderDetailPage`: 기존 값이 없으면 `homemulti`를 기본값으로 채우며 수정 요청 타입과 서버 `PartnerOrderUpdateRequest.LineRequest`가 non-null/`@NotBlank`를 요구한다. 따라서 갱신된 화면에서 저장한 주문도 항상 값이 있다.
- 발행 시에는 별도 조건문 없이 주문 라인 값을 그대로 전달한다. 즉 과거 주문 DB 라인이 null이면 null, 현행 주문이면 값 있음이다. 현재 `partner_order_db` 활성 라인 실측은 **2,052건 중 null 0건, 값 있음 2,052건**이다.

견적 웹 앱 `clients/web/estimate-app/lib/slip-bridge.js`도 `/internal/slips/from-estimate`를 실제 호출하지만 `lines`에 `categoryKey`를 넣지 않는다. 따라서 견적 재시도는 저장 null/요청 null로 category 비교를 통과한다. 이번 `categoryKey` 값 있음 재시도 조합의 실제 호출자는 위 두 주문 전환 경로뿐이다.

## 확인 4 — 영향 후보를 멱등 발행 전표로 축소

- 따라서 현재 DB에서 “저장 전표 null + 현행 호출 값 있음” 조합이 확정된 범위는 **전표 12건(11개 주문, 19개 전표 라인)**이고, 상한은 멱등 PARTNER_ORDER 전표 **16건**이다.

## 확인 6 — `unitPriceWithVat` 변경의 실제 영향

실측 원문:

```text
 all_rows | vat_null | category_null
----------+----------+--------------
     3243 |        0 |          3243

 idem_partner_lines | vat_null | equal_price | different_price
--------------------+----------+-------------+----------------
                 23 |        0 |           0 |              23

 lines | exactly_plus_10_percent
-------+-------------------------
    23 |                      23
```

- `unit_price_with_vat IS NULL`은 활성 2,791건뿐 아니라 삭제 포함 전체 3,243건에서도 **0건**이다. null 때문에 거부되는 라인은 없다.
- 그러나 멱등 PARTNER_ORDER 전표 라인 23건 전부가 `unit_price_with_vat = unit_price × 1.1`인 구 저장 계약이다. 당시 실제 주문 전환 요청의 `unitPriceVat`는 현재 DB의 `unit_price`와 같았고, 변경 전 `linesMatch()`도 이를 비교해 200 replay했다.
- 수정 후에는 같은 요청값을 `unit_price_with_vat`와 비교하므로 23/23 라인에서 10% 차이로 불일치한다. 위 200→409 원문은 이 경로의 실제 재현이다.
- 따라서 이번 라운드의 정상 동작 차단 결함은 `unitPriceWithVat`의 **null 호환 문제가 아니라 기존 저장 의미와의 호환 문제**다.

## 확인 7 — `categoryKey` 비교를 빼면 생기는 실제 합침

변경 전 실행 컨테이너에 기존 키로 `categoryKey`를 생략한 요청과 값을 넣은 요청을 각각 보냈을 때 둘 다 같은 `2026/05/31-5`를 `idempotentReplay=true`로 200 반환했다(확인 5 원문).

- 즉 legacy fingerprint에는 `categoryKey`가 없고 저장 라인도 null이므로, 비교를 빼면 서로 다른 category 요청이 같은 기존 결과로 합쳐지는 경우가 **실제로 있다**.
- 현행 fingerprint로 새로 발급된 전표는 fingerprint 자체가 category를 구분하므로 이 문제는 legacy 키에만 한정된다.
- legacy 전표는 원래 요청 category를 저장하지 않아 “같은 재시도의 값”과 “나중에 바꾼 값”을 구별할 근거가 없다. 현재의 엄격 비교는 둘 다 막고, 비교 제거는 둘 다 같은 null-category 결과로 합친다.

## 최종 판단

**차단 회귀 있음.** 실제 주문 전환으로 발급된 기존 멱등 키가 변경 전에는 200 replay였으나 현재 수정에서는 409가 된다.

- 직접 원인: `unitPriceVat` 요청을 기존 저장 라인의 `unitPriceWithVat`와 비교하도록 바꾼 것. 현재 멱등 PARTNER_ORDER 전표 16건의 23개 라인 전부가 구 저장 의미(`unitPriceWithVat = unitPrice × 1.1`)라 정상 재시도가 불일치한다.
- `unitPriceWithVat=null` 영향: **0건**. null이 아니라 기존 값의 의미 차이가 원인이다.
- `categoryKey` 조합: 활성 전체 라인 2,791건이 null이고 현행 주문 라인 2,052건은 전부 값 있음이다. 멱등 전표 중 현재 원천과 대조 가능한 **12건(11개 주문, 전표 라인 19개)**에서 질문의 조합이 확인됐다.
- `categoryKey`의 독립 추가 차단: 현재 실데이터에서는 단가 조건이 먼저 실패하므로 **0건**. 단가 조건이 호환됐다고 가정하면 같은 legacy replay에서 category null/value 비교도 실패한다.
- 현재 대기 중 자동 재시도: outbox **0건**. 저장된 과거 멱등 전표 16건은 같은 키를 다시 보내면 영향받지만, 현재 큐에서 즉시 실패할 건은 없다.
- category 비교 제거의 반대 영향: legacy 요청에서 서로 다른 category 요청이 같은 기존 전표로 200 합쳐지는 동작이 실제 출력으로 확인됐다.
