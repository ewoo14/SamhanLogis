## 1. 결론

S-03만 설정 기반 evaluator로 전환했다. 로그인 후 `SINGLE_SET` 규칙 API를 읽고, 유효한
`SINGLE_S03_CEILING_DRAIN_PUMP` 규칙과 실제 싱글 catalog graph가 모두 확인될 때만 설정
evaluator를 사용한다. 조회 실패·규칙 오류·source/target catalog 누락 때는 기존 S-03
계산을 유지하면서 사용자에게 경고한다. 설정 오류를 수량 0으로 바꾸는 경로는 두지 않았다.

홈 8개, 싱글 S-01/S-02, 상업·분기보드 9개, estimate-app은 변경하지 않았다.

`GET /api/v1/partner-orders/bootstrap` HTTP 200 응답의 `data.payloads.singleSets`에서

legacy 계산으로 남는다. 이 PC에서는 Docker/Gradle 실행 금지 지시에 따라 migration을
실제 DB에 적용하지 않았다.

## 4. 구현 내용

- `src/quantitySync.ts`: S-03 전용 rule 선택·catalog graph 검증·`SUM × factor × multiplier`
  evaluator. `SUM`, 조건 없음, source 1개, target 1개, `inactiveBehavior=ZERO`만 허용한다.
- `src/samhanApi.ts`: JWT가 준비된 로그인 뒤 `GET /quantity-sync-rules?estimateCategory=SINGLE_SET`
  를 읽는 paging adapter를 추가했다.
- `QuantitySyncRuleController`: PARTNER order-app이 읽을 수 있도록 목록 GET만
  `partnerSelfService=true`로 열었다. 변경 API 권한은 그대로 별도 admin 권한이다.
- `src/main.ts`: legacy inline page에 API 상태와 evaluator를 연결하는
  `window.__SAMHAN_QUANTITY_SYNC__` bridge를 설치했다.
- `index.html`: S-03 target만 설정 evaluator 결과를 사용한다. API 응답 전에는 동일한
  legacy 계산을 표시하고, 수동 잠금은 기존 `setSingleDerivedQty_` 경로로 보존한다.
  실패·누락 시 경고문과 legacy fallback을 표시한다.
- `V27__seed_s03_quantity_sync_rule.sql`: 실제 catalog 두 행을 찾은 경우에만 S-03
  rule/source/target을 seed한다. 데이터 backfill은 없다.
- `quantity-sync-s03-shadow.mjs`: 같은 fixture와 같은 입력을 legacy evaluator와 설정
  evaluator에 각각 넣어 수량·소계·전송 line을 비교하는 실행 가능한 shadow 대조를 추가했다.
- `QuantitySyncRuleControllerPermissionTest`: 목록 GET의 self-service read-only 경계를
  reflection으로 고정했다.

1. **수량 동일** — shadow 원문에서 0/1/4/77 각각 `beforeQuantity === afterQuantity`.
2. **금액 동일** — shadow에서 각 입력의 `beforeSubtotal === afterSubtotal`; 77개는
   `8,958,400`, 전송 line은 양쪽 모두 `SINGLE / ADP-F075SP / 77`이다.
3. **수동 입력 보존** — `quantitySyncS03Integration.test.ts`에서 target 수동 입력 77을
   설정 evaluator 재계산 뒤에도 77로 유지하고 manual lock을 유지하는 2개 테스트가 통과했다.
4. **설정/품목 누락 비침묵 처리** — source 또는 target을 실제 fixture에서 제거한 테스트가
   `status=error`, `missingCatalogCodes=['ADP-F075SP']`, 빈 target map을 확인한다. UI에는
   설정 실패 경고를 표시하고 기존 계산을 유지한다. 실제 장애 서버 주입은 Docker/Gradle
   금지로 실행하지 않았지만 API 예외도 bridge의 `error` 상태와 같은 fallback으로 처리한다.
   목록 GET은 PARTNER self-service read-only로 명시해 정상 로그인 token에서 권한 때문에
   항상 fallback 되는 경로도 제거했다.
5. **S-03 외 19개 보존** — 설정 branch는 `recomputeSingleExtras`의 S-03 target만
   대체하고, 기존 golden 20계열 테스트 및 전체 234개 테스트가 통과했다. H-07/C-09와

### 9.4 `partnerSelfService = true`의 실제 허용 범위와 DTO 노출 판정

코드 근거:

- `shared/security/src/main/java/com/samhanair/logis/security/permission/PermissionAspect.java:173-180`
  에서 `X-Is-Partner=true`를 확인한 뒤 `annotation.partnerSelfService()`가 true면
  즉시 `joinPoint.proceed()`한다. 이 분기에서는 PARTNER deny뿐 아니라 뒤의
  `X-User-Id` UUID 파싱과 `DynamicPermissionClient`의 계정/페이지 권한 확인도 실행하지 않는다.
- `services/product-service/src/main/java/com/samhanair/logis/product/web/QuantitySyncRuleController.java:41-45`
  에서 플래그가 붙은 것은 `GET /api/v1/quantity-sync-rules` 목록뿐이다.
  `GET /{ruleKey}`(50행), POST(58행), PUT(66행), DELETE(76행)는 플래그가 없어
  PARTNER 전면 차단 정책을 그대로 따른다.
- `QuantitySyncRuleService.list`는 `services/product-service/src/main/java/com/samhanair/logis/product/service/QuantitySyncRuleService.java:101-105`
  에서 `is_deleted=false` 전체를 optional `estimateCategory`로만 필터링한다.
  `partnerCode` 인자나 거래처 소유 범위 대조는 없다. 따라서 실제 허용 범위는
  PARTNER 사용자가 목록 endpoint를 호출해 삭제되지 않은 규칙을 볼 수 있는 것이며,
  order-app의 호출(`estimateCategory=SINGLE_SET`)은 그중 SINGLE_SET만 요청한다.

목록 응답 DTO(`QuantitySyncRuleResponse.java:12-24`) 기준으로 새 API가 내려주는 값은
`ruleKey`, `estimateCategory`, `name`, `enabled`, `aggregation`, `when`(내부
`conditionJson`), `inactiveBehavior`, `conflictPolicy`, `priority`, `legacyRef`,
`sources`, `targets`다. child DTO(`QuantitySyncProductRef.java:5-8`)는 source/target의
`productCode`, `productName`과 source `factor`, target `multiplier`, `roundingMode`,
`displayOrder`를 반환하며 내부 UUID는 반환하지 않는다.

현재 S-03에서의 노출 판정은 다음과 같다.

- **이미 거래처가 보던 값**: `AC072BSCPBH2SY` / `싱글 실링`과 `ADP-F075SP` /
  `실링용 드레인펌프`는 기존 `partner-orders/bootstrap`의 `singleSets` catalog에 있었다.
  특히 target `ADP-F075SP`와 표시명은 order-app bundle의
  `index.html:2630,2871,5214,5800`에도 하드코딩되어 있었다. 기존 legacy 계산이
  실링 source 수량을 합산해 target에 넣는 동작과 주문 payload도 shadow에서 그대로 유지됐다.
- **이번 API로 새로 노출되는 값**: 기존 bundle/catalog에는 규칙의 서버 정본 graph가
  없었으므로 `ruleKey=SINGLE_S03_CEILING_DRAIN_PUMP`, `legacyRef=S-03`, `name`,
  `enabled`, `estimateCategory`, `aggregation=SUM`, `when={}`, `inactiveBehavior=ZERO`,
  `conflictPolicy=REPLACE`, `priority=100`, 그리고 source `factor=1` / target
  `multiplier=1, roundingMode=NONE, displayOrder=1`이라는 설정 metadata가 새로 응답된다.
  또한 이 목록 endpoint에 다른 non-deleted 규칙이 있으면 category 조건에 맞는 규칙 전체가

  계산 결과는 기존과 동일했다.
