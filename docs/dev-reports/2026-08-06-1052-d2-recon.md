## 2. `(a) dev 대체 / (b) 운영 오매핑 / (c) QA 중복` 구분 설계

### 2-1. 현재 주기 pair 검증만으로는 구분하지 못한다

현재 사용할 수 있는 두 endpoint는 “UUID가 존재하는가”와 “code가 존재하는가”만 답한다. 데이터에는 환경 의도, 외부 코드 별칭, 물리 창고 identity, QA provenance를 기계 판독할 필드가 없다. 따라서 이름이나 UUID 패턴을 휴리스틱으로 보고 경보를 억제하면 운영 오매핑도 함께 숨길 수 있다.

### 2-2. 권장 판별 모델 — 명시적 정책 + canonical 외부 별칭

다음 한 가지 설계를 권장한다. 이번 라운드에서는 구현하지 않는다.

1. inventory를 창고 identity 정본으로 유지하고 `warehouse_external_aliases`를 둔다.
   - 필수 키: `(source_system, external_code)` unique
   - 값: `warehouse_id`, `intent=CANONICAL|DEV_SUBSTITUTE`, `environment_scope`, audit
   - ECOUNT 코드 `00003/2/14/1`은 별도 warehouse 행이 아니라 canonical warehouse를 가리키는 alias가 된다.
2. slip 검증 정책을 `STRICT` 또는 `DEV_SUBSTITUTE`로 **명시 주입**한다.
   - `production`은 `STRICT`만 허용한다.
   - local/dev는 명시적으로 `DEV_SUBSTITUTE`를 선택할 수 있다.
   - 프로파일 이름, UUID 모양, 이름 문자열로 모드를 추론하지 않는다.
3. slip은 기동 후 비동기 + timeout + 주기로 alias와 설정 UUID를 pair 비교한다. 외부 장애 때문에 기동을 막지 않는다.
4. production 배포 정적 가드는 `DEV_SUBSTITUTE` 및 known deterministic UUID의 주입을 거부한다. 이는 외부 서비스 조회에 의한 애플리케이션 기동 차단이 아니라 IaC/config 자체의 정적 검증이다.
5. 결과는 health/readiness, alert, 관리자 화면에 같은 상태 모델로 노출한다.

| 상태 | 판정 조건 | readiness | 경보 | 관리자 화면 |
|---|---|---|---|---|
| `(a) DEV_SUBSTITUTE` | 명시적 dev 정책 + alias intent가 `DEV_SUBSTITUTE` | 유지 | pager 없음 | `대체 매핑, 운영 판정 대상 아님`, 4건과 마지막 검증시각 표시 |
| `(b) STRICT_MATCH` | legacy alias의 canonical `warehouse_id` = 설정 UUID | 유지 | 없음 | 정상/coverage 표시 |
| `(b) STRICT_MISMATCH` | 두 조회 모두 성공하나 UUID 불일치 | `OUT_OF_SERVICE` | 즉시 pager | code·expected business code/name·actual code/name 노출, UUID 화면 비노출 |
| `STRICT_ALIAS_MISSING` | strict 환경에서 alias 없음 | `OUT_OF_SERVICE` | 즉시 pager | 미등록 code와 영향 경로 표시 |
| `UNAVAILABLE` | timeout/5xx/connection failure | 기존 readiness 유지 | 연속 실패 또는 stale 임계 초과 시 가용성 경보 | 마지막 성공시각·재시도 표시 |
| `(c) DUPLICATE_SITE` | 서로 다른 canonical warehouse가 같은 `physical_site_key`를 사용 | 기본 readiness 유지 | 운영 데이터 경보 | 병합/별칭 전환 후보 표시 |

`DEV_SUBSTITUTE`는 조용히 숨기지 않는다. pager만 억제하고 admin/metric에는 `not_applicable`과 coverage를 남긴다. 그래야 상시 ERROR 노이즈도 없고 “검증 0건을 결함 0”으로 오해하지도 않는다.

### 2-3. 물리 중복까지 자동 판정하려면 추가 identity가 필요하다

external alias unique만으로 한 legacy code가 두 warehouse를 가리키는 문제는 막지만, 이름이 다른 두 행이 같은 실물 장소인지까지는 알 수 없다. `warehouses`에 안정적인 `physical_site_key` 또는 별도 canonical site entity가 필요하다.

- 같은 실물의 여러 외부 코드: warehouse 행을 늘리지 않고 alias 여러 개가 한 canonical warehouse를 가리킨다.
- 서로 다른 재고 위치: 이름이 비슷해도 `physical_site_key`가 다르다.
- QA 데이터: production scope alias/site로 등록할 수 없고 `QA` scope/provenance를 가진다.
- 이름·주소 fuzzy match는 후보 제시에만 쓰고 확정/경보 근거로 쓰지 않는다.

```text
---------------------------+------------------------------------------------------------------------------------------------------------------

 ux_warehouses_code_active | CREATE UNIQUE INDEX ux_warehouses_code_active ON public.warehouses USING btree (code) WHERE (is_deleted = false)
 warehouses_pkey           | CREATE UNIQUE INDEX warehouses_pkey ON public.warehouses USING btree (id)
(3 rows)
```

실 endpoint를 네 코드로 각각 호출한 원문이다. internal token은 출력·저장하지 않았다.

따라서 legacy code `2`는 S18 행, `00003`은 S18 행을 정확히 반환한다. `QA-1039-*` 행은 코드가 다르므로 후보에 들어오지 않는다. SQL 순서나 우연으로 둘 중 하나를 고르는 문제가 아니다.

### 3-2. 그래도 라운드 4와 같은 계열이다

**정체성 계층에서는 같은 계열**이다. 네 행 모두 개별 code와 UUID가 있어 existence-only 검증은 전부 `FOUND`로 통과한다. 그러나 `FOUND`는 다음을 증명하지 못한다.

- 해당 legacy code가 의도한 물리 창고인가
- 다른 code 행과 같은 실물 창고를 중복 표현하는가
- QA 행인가 운영 canonical 행인가

D1의 pair 비교는 “설정 UUID와 exact code 행이 같은가”는 잡지만, 두 행이 같은 실물인지 판정할 canonical site key가 없다. 그러므로 라운드 4의 `FOUND = 정상 대응` 오류를 완전히 닫으려면 alias/site identity가 필요하다.

### 3-3. “같은 실물 창고가 둘씩”의 확정 수준

확정 가능한 사실:

- 상일 명칭 행 2개, 초월 명칭 행 2개가 활성이다.
- 네 행 모두 관리자 API가 만든 QA provenance를 갖는다.
- 앞의 두 행은 `QA-1039-*`, 뒤의 두 행은 S18 목적의 legacy code 표본이다.
- S18 행은 실제 slip에서 사용됐고 QA-1039 행은 현재 참조 0이다.

읽기 전용 참조 계수 원문:

```text

 QA-1039-CHOWOL |            0 |                 0
```

그러나 **동일 실물 장소 확정은 현재 스키마로 판정 불가**다. S18 행은 주소가 null이고 QA-1039 주소는 테스트 문자열이며, physical identity 필드가 없다. 이름과 QA 문서로 보아 중복일 가능성이 매우 높은 **후보 2쌍**이지, 기계적으로 확정한 물리 중복 2건이라고 쓰면 과장이다.

따라서 D2 수치는 다음과 같다.

| 항목 | 수치 |
|---|---:|
| 명칭·QA 목적상 중복 후보 | 2쌍 (상일 1쌍, 초월 1쌍) |
| 현 스키마로 확정한 동일 physical site 중복 | 판정 불가 |
| active code 자체의 DB 중복 | 0 (unique index) |
| endpoint의 비결정적 다건 선택 | 0 |

중복 행은 지우거나 수정하지 않았다.

## 4. 회사 PC에서는 무엇을 보고해야 하는가

회사 PC에는 접근하지 않았으므로 회사 PC 실측 건수를 쓰지 않는다. 다음은 `2`·`00003` 행이 없다는 조건별 **설계상 기대 결과**다.

| 회사 PC 선언 모드 | `2`·`00003` 행 없음 | 보고/경보 |
|---|---|---|
| `DEV_SUBSTITUTE` | 의도된 대체 환경 | `substitute=4`, `strict pair coverage=0/4`, `NOT_APPLICABLE`; pager 없음, admin 경고 표시 |
| `STRICT` | 운영 정본 alias 누락 | `STRICT_ALIAS_MISSING`; readiness `OUT_OF_SERVICE` + pager |
| 모드 미설정 | 의도 판별 불가 | `CONFIG_POLICY_UNKNOWN`; 배포 정적 가드 실패. 애플리케이션 외부조회 기동 차단으로 처리하지 않음 |

중복 검증도 동일하다.

- 상일/초월 canonical site 표본 0이면 `duplicate=0`이 아니라 `NOT_EVALUABLE (sample=0)`.
- QA provenance 행 0이면 “QA 오염 없음”은 말할 수 있지만 물리 중복 부재는 말할 수 없다.
- endpoint 가용성은 seed UUID 조회 또는 health로 별도 측정하고, legacy 대응 coverage 0을 가용성 성공으로 대체하지 않는다.
- 환경 보고에는 최소한 `host/environment-id`, `policy`, `configured`, `strict-covered`, `substitute`, `missing`, `mismatch`, `duplicate-candidate`, `last-success-at`을 포함한다.

회사 PC dev에서 관리자 API로 `2`·`00003`을 다시 만드는 것은 pair 표본은 만들지만 공유 데이터 중복을 더 늘린다. 권장 설계에서는 이를 warehouse 신규 행으로 만들지 않고 dev-scope external alias/fixture로 다뤄야 한다. 이번 D2에서는 어느 PC에도 행을 만들지 않았다.

## 최종 권장 설계 한 가지

**inventory canonical warehouse + 외부 alias 정본 + 명시적 환경정책 + 기동 후 비동기 strict 검증**을 한 세트로 권장한다.

| 요구/과거 실패 | 방지 방식 |
|---|---|
| dev placeholder가 상시 경보 | `DEV_SUBSTITUTE`를 명시하고 pager를 억제하되 admin/metric에 `NOT_APPLICABLE`과 coverage 노출 |
| 운영에서 A UUID가 B 자리에 감 | `STRICT`에서 `(source_system, external_code)` alias의 canonical UUID와 설정 UUID를 pair 비교; 불일치 readiness·pager 반영 |
| QA가 같은 실물 창고를 다른 code로 생성 | 외부 code는 신규 warehouse가 아니라 alias로 등록; canonical `physical_site_key`로 중복 후보/제약 제공 |
| 라운드 2·6 legacy 404로 기동 실패 | 외부조회는 기동 후 비동기·timeout·재시도; 404/5xx가 Spring context를 종료하지 않음 |
| 일시 장애와 미실재 혼동 | `UNAVAILABLE`, `ALIAS_MISSING`, `MISMATCH`를 별도 상태와 임계로 분리 |
| 라운드 4 `FOUND` 오통과 | 존재가 아니라 alias→canonical identity의 pair equality를 검증 |
| 라운드 4 UNAVAILABLE 영구 미검증 | 주기 재검증 + last-success/stale metric |
| 느린 서비스가 기동 스레드 block | 비동기 전용 executor + connect/read timeout |
| 라운드 6 ERROR 로그만 | confirmed strict mismatch는 readiness `OUT_OF_SERVICE`, pager, 관리자 화면에 동시 반영 |
| production 템플릿에 dev UUID 유입 | IaC/config 정적 가드가 production의 `DEV_SUBSTITUTE`와 known deterministic UUID를 거부 |
| 회사 PC 표본 0을 결함 0으로 오해 | `NOT_EVALUABLE`, `strict pair coverage=0/4`를 명시적으로 보고 |

이 설계는 외부 inventory 조회로 애플리케이션 기동을 막지 않는다. 단, 운영 배포 구성에 dev 대체값을 넣는 것은 외부조회와 무관한 정적 설정 오류이므로 배포 단계에서 거부한다.
