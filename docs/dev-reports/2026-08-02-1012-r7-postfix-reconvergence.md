원천은 **82라인 → 61모델 행 → 79 모델·연·월 점 / 4개월**이다. 월별 전표 수량은

   레거시보다 넓은 모집단을 순위화한 결함이다.

## 3. 레거시 규칙 대조와 경계

### 3.1 월 차원

- 레거시 `입출고 내역/code.js:63`은 날짜에서 `YYYYMM` 키를 만들고, `:65-70`은 모델별
  `input[keyDate]`/`output[keyDate]`를 누적한다.
- 현행 BE는 `YearMonth` 키의 `monthly[]`를 모델 행 안에 보존한다. DB 재생 결과 배열 원소 합계는
  **79/79점**이다.
- 그러나 화면 소스가 실제로 렌더하는 월 차원 전용 값은 79개 점의 상세가 아니라
  `monthlyPointCount`라는 **점 개수 1개**다. 전년·당년 표도 모델별 79점을 월 전체 합계 12개로
  축약한다. 실제 화면은 브라우저 부재로 보지 못했으므로, “화면에 79라는 숫자가 보인다”와
  “79개 월 값을 모두 표현한다”를 모두 실화면 통과로 판정하지 않는다.

### 3.2 전년·당년 추이

- 레거시 `Index.html:345-353`은 2025/2026 각각 12칸 배열에 출고를 누적한다.
- 현행도 선택된 전년/당년의 12칸을 만들고 월 출고를 누적하므로 현재 시드에서는 12행,
  당년 비0 3행이 산출된다.
- 차이: 레거시는 연도를 2025/2026으로 고정하지만 현행은 월 점의 최댓값을 당년으로 잡는다.
  조회에 2025년 데이터만 있으면 현행은 `previousYear=2024`, `currentYear=2025`로 재해석한다.
  즉 2026 데이터가 전혀 없는 경계에서는 레거시의 “2025=전년, 2026=당년”과 갈린다.

### 3.3 수요예측

레거시 `Index.html:368-381`과 현행의 중심 식은 일치한다.

1. `monthlyThis[k] > 0`인 마지막 월을 `lastMonth`로 갱신한다.
2. 당년 출고가 있는 월들만 동월 전년·당년 합계에 더한다.
3. 전년 합계가 0보다 크면 `rate=totalThis/totalLast`, 아니면 1을 쓴다.
4. 마지막 당년 출고월 다음부터 12월까지 `Math.round(previous[month] * rate)`를 만든다.

경계 결과:

| 경계 | 현행 결과 | 레거시 대조 |
|---|---|---|
| 당년 출고 0, 2026 입고 점은 존재 | `lastMonth=-1`, 12개월을 전년 월량×1로 예측 | 일치 |
| 전년 데이터 없음 | `rate=1`; 마지막 당년 출고월 이후 전부 0 | 일치 |
| 2025 데이터만 있고 2026 월 점 자체가 없음 | 2025를 당년으로 재해석해 2024와 비교 | **불일치**(동적 연도 선택 차이) |
| 반올림 | `Math.round` 사용 | 일치 |

현재 추가 테스트는 예측 배열 4~12월이 전부 0인 사례만 단언한다. 따라서 실제로
`전년 향후 월량 × 1이 아닌 rate`가 비0 값으로 반올림되는 경로는 테스트가 직접 증명하지 않는다.

### 3.4 Top 3 / Bottom 3와 동률

- 레거시 `Index.html:388-393`은 `outCounts`의 키만 출고량 내림차순 정렬한 뒤
  `slice(0, 3)`, `slice(-3).reverse()`를 적용한다.
- 현행의 `slice(0, 3)`과 `slice(-3).reverse()` 호출 자체는 원문과 같다.
- 그러나 현행 `aggregate`는 입고·출고 통합 응답 61행을 모두 넣는다. 그 결과 출고가 한 건도
  없는 입고 전용 모델도 `outboundQuantity=0`으로 Bottom 후보가 된다.

시드 직접 대조:

| 규칙 | Bottom 3 수량 |
|---|---|
| 레거시 `outCounts`(출고 모델만) | **1, 1, 2** |
| 현행 통합 61행 | **0, 0, 0** |

동률에는 양쪽 모두 보조 정렬 키가 없다. JavaScript의 안정 정렬은 입력 순서를 보존하지만,
현행 BE는 입고 조회를 먼저 처리한 뒤 출고 조회를 처리하고 같은 전표 안의 line 컬렉션에는 명시적
정렬도 없다. 따라서 출고 18 동률의 Top 1 모델, 출고 12 동률의 Top 3 마지막 모델, 출고 2 동률의
레거시 Bottom 3 마지막 모델은 정확한 식별자/순서를 계약으로 볼 수 없다. 수량 집합은 안정적이어도
동률 모델 순서는 레거시와 일치한다고 단정할 수 없다.

### 3.5 추천·알림

- 레거시 `Index.html:395-403`의 Top 1 재고차, `rate > 1.1`, fallback 규칙은 현행에 그대로 있다.
- 현 시드에서는 출고 18 Top 동률 후보 두 모델 모두 `입고-출고 <= 0`이므로 추천 종류는
  `발주 권장` 1건이다. `rate=1`이라 수요 상승 알림은 추가되지 않는다.
- 경계 차이: 출고 모델이 전혀 없고 입고 모델만 있을 때 레거시는 Top이 없어 `특이사항 없음`으로
  끝나지만, 현행은 0출고 입고 모델도 Top에 넣어 그 모델의 `주력 상품` 또는 `발주 권장`을 만들 수 있다.

## 4. 함께 본 각도 3~5

### 4.1 각도 3 — 월 차원 화면 79점

**조사하지 않음(실화면).** 브랜치 Vite까지 별도 포트에 띄웠지만 브라우저 백엔드가 0개였다.
API JSON이나 터미널 출력을 화면 증거로 대체하지 않았다.

정적·계산 경로로만 확인한 사실은 다음 둘이다.

- BE `monthly[]` 합계는 시드 **79점**이다.
- 화면은 이 79개 상세 값을 행으로 그리지 않고 합계 카운트 `79` 하나를 표시하도록 작성돼 있다.

### 4.2 각도 4 — 칩 회귀

HEAD의 실제 `modelChips`/`filterInOutRows`를 읽기 전용 DB 값에 직접 적용했다.

| 모집단 | 무필터 | 실외기 | 실내기 | 홈멀티 | 싱글중대형 | 상업멀티 | 판넬 | 미분류 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 기본 화면 61행 | 61 | 0 | 0 | 0 | 0 | 0 | 0 | **61** |
| 분류 실데이터 4행 | 4 | 1 | 1 | 2 | 0 | 0 | 1 | **0** |

- 원천 집계는 **82라인 → 61행**, 무필터 반환도 **61행**이다.
- 분류 4행은 복수 membership 5개 전부 자기 칩에 남아 false-negative **0/5**다.
- `미분류`는 기본 모집단 61/61을 반환하고 분류 4행은 0/4를 반환한다.
- 대상 Vitest는 이번 라운드에 재실행해 **10/10 통과**했다.
- 실제 화면 클릭 회귀는 브라우저 부재로 **조사하지 않음**이다.

### 4.3 각도 5 — `MonthlyPoint.year/month` 추가의 다른 소비처

전체 저장소 검색에서 이 DTO/FE 계약의 직접 소비처는 다음뿐이었다.

1. BE 생성: `InOutAnalysisService`
2. BE 노출: `SlipQueryController`
3. FE 계약: `clients/desktop/src/renderer/api/inventory.ts`
4. FE 소비: `InOutAnalysisPage`와 `inoutAnalysisModel`

다른 Java 생성자, 다른 FE 페이지, 공유 DTO 소비처는 검색되지 않았다. 새 필드는 기존 응답 필드를
삭제하거나 이름을 바꾸지 않은 additive JSON 필드다. `:services:slip-service:compileJava`는 이번
라운드에 **BUILD SUCCESSFUL**이었다. 따라서 저장소 내부의 알려진 소비처 파손은 확인하지 못했다.

단, 저장소 밖에서 응답을 strict schema로 역직렬화하는 소비자는 확인할 수 없으므로 외부 소비처까지
무회귀라고 단정하지 않는다. 또한 mock의 포괄 조건 `url.includes('/slips/query')`가
`/slips/query/inout-analysis`도 먼저 잡아 페이지가 기대하는 배열이 아닌 일반 조회 Page 응답을
돌려줄 수 있다. R6 실화면 mock QA 경로는 별도 전용 handler가 없어 신뢰할 수 없다.
