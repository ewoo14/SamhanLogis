- 사용자 조작: 정상 출고 흐름에서 창고 코드 `00003` 또는 `2`를 선택해 전표를 발행한 뒤, 가배차 화면에서 기간과 모드를 선택해 조회한다.

- 현재 DB에서 확인된 사실: 최신 단일 SELECT 스냅샷은 활성 OUTBOUND 2,303건, inventory 이름 조회 가능 2,299건, 실제 이름 조회 불가 4건이다. 현재 네 표시명 어느 것도 `상일`/`초월`을 포함하지 않는다.
- 정상 제외 건수: 기존 행의 UUID만으로 발행 당시 warehouse code의 provenance를 전부 복원할 수는 없다. 따라서 아래 `mode*_should`는 **현재 local code-map 의미를 적용한 도달 가능 집합**이고, 기존 2,303행 모두의 provenance가 입증됐다는 뜻은 아니다. 별도 provenance 없이도 정상 누락이 확정되는 행은 R1-3의 STACK 11건이다.

## 4. `sourceWarehouseName` 소비자·UUID 판정

- repo 내 `GET /internal/slips/outbound`의 실제 HTTP 소비자는 `arologis-service`의 `SlipServiceClient.java:99` 한 곳이다. `JsonNode` 선택 파싱이므로 필드 추가로 다른 소비자가 깨지는 경로는 발견하지 못했다.
- `OutboundSlipResponse.java:24-34`에는 UUID 필드가 없다. inventory 응답의 id/code는 `WarehouseInternalClient.parseName()`에서 버리고 name 문자열만 전달한다.
- arologis summary 생성은 `new OutboundSlipSummary(null, ...)`이라 신규 UUID가 사용자 화면으로 전파되지 않는다.
- 저장소 밖 별도 소비자는 미판정이다.

실제 명령/출력:

```powershell
rg -n -F "/internal/slips/outbound" services --glob "**/src/main/**"
```

## 5. 미판정·이번 라운드에서 보지 않은 표면

- 공유 Docker의 slip/arologis 이미지는 PR 이전 빌드다. 이미지 rebuild 금지에 따라 PR 배포 후 실 브라우저 E2E는 실행하지 않았다.
- inventory-service를 실제로 중지하거나 timeout시키지 않았다. 공유 스택 변경 금지 때문에 404/empty와 생산 코드 경계를 표적 실행으로 재현했다.
- `docs/migration/ecount-data/raw/` 원본과 현재 2,303행의 개별 warehouse provenance는 연결되지 않아, UUID만으로 상일/초월을 확정할 수 없는 행은 정상 누락 건수에 억지로 합산하지 않았다.
- 저장소 밖 외부 소비자와 운영 DB의 실제 warehouse 환경변수 값은 보지 못했다.
- slip-service 전체 suite는 지시대로 재실행하지 않았다.
