# D-G1 S2 fix — versioned 요율 계약과 확정 snapshot 불변성

> 대상: PR #1165 / 기준 HEAD `06bb8bf6e`
>
> 범위: D-G1 S2 차단 결함만 수정. 공유 DB write, 배포, git 조작, S3/S4는 수행하지 않았다.

## 선택 수단과 근거

1. `SalesCommissionSettlementService.calculate`의 공개 경계를 계약 entity가 아닌
   `rateContractVersion`으로 고정하고, `SalesCommissionRateContractRepository`에서
   `findByVersionNoAndIsDeletedFalse(version)`로 활성 행을 다시 읽는다. 따라서 caller가
   transient/detached 계약의 임의 요율을 주입할 수 없다. 여러 버전 중 선택 기준은
   **호출자가 지정한 명시적 version 번호**이며, 기준일·생성일·최신 행을 암묵적으로 고르지 않는다.
2. `CONFIRMED`는 service 경계에서 먼저 `CONFLICT`로 거부하고, aggregate
   `recordCalculation`에도 `DRAFT` 가드를 둔다. 전자는 불필요한 계약 조회 없이 외부 요청을
   차단하고, 후자는 다른 호출 경계가 생겨도 FK와 모든 입력·금액 snapshot의 덮어쓰기를 막는다.
3. 과거 정산 조회는 settlement의 저장된 FK를 `@EntityGraph`로 함께 적재하며 계산기를 호출하지
   않는다. 계약 entity의 전역 `@SQLRestriction`은 제거했다. 그래야 계약이 soft-delete된 뒤에도
   과거 정산의 FK를 따라갈 수 있다. 반면 새 계산용 repository query는 `is_deleted=false`를
   명시하므로 삭제된 계약은 새 DRAFT에 사용할 수 없다.

## RED 원문

SOL이 HEAD 원본에 임시 재현을 추가해 실행한 원문은 다음과 같다.

```text
.\gradlew.bat :services:accounting-service:test \
  --tests '*SalesCommissionSettlementCalculationServiceTest' --no-daemon

2 tests completed, 1 failed
confirmed_settlement_cannot_be_recalculated_with_a_new_rate_contract FAILED
```

재현 순서는 `v1(8%) 계산 → CONFIRMED → 같은 settlement에 v2(7%) 재계산`이다. 첫 assertion에서
`rateContract`가 v2로 교체됐고, 다음 금액 assertion도 `expense=-700`이 되는 경로였다.

이번 수정에서는 추가 RED
`confirmed_recalculation_is_rejected_before_any_rate_contract_lookup`를 먼저 실행했다.

```text
1 test completed, 1 failed
SalesCommissionSettlementCalculationServiceTest >
confirmed_recalculation_is_rejected_before_any_rate_contract_lookup() FAILED
```

실패 원인은 CONFIRMED에서도 계약 repository를 먼저 조회해 존재하지 않는 version이면
`NOT_FOUND`가 반환되는 것이었다. service 상태 선검사 추가 뒤 같은 calculation service suite 6건이
통과했다.

저장소 의존성 뮤테이션도 수행했다. `rateContractRepository` 조회 결과를 임시로 `null`로 치환하면
PostgreSQL 왕복 test가 아래처럼 RED가 되었다. 즉 repository 선택을 제거하면 테스트가 녹색으로
남지 않는다. 뮤테이션은 즉시 원복했다.

```text
1 test completed, 1 failed
SalesCommissionSettlementRateVersionIT >
persisted_versions_keep_their_own_confirmed_settlement_snapshots_after_reload() FAILED
java.lang.NullPointerException at SalesCommissionSettlementRateVersionIT.java:61
```

## 조합 검증

| 조합 | 보호 경로 | 검증 결과 |
|---|---|---|
| DRAFT 재계산 | 지정 version을 repository에서 매번 재조회 후 snapshot 갱신 | v1 8% → v2 7%, FK v2·제경비 -700 (`draft_recalculation_uses_the_new_repository_contract_version`) |
| CONFIRMED 재계산 시도 | service 상태 선검사 + aggregate `DRAFT` 가드 | `CONFLICT`, 기존 FK v1·적용율 0.08·제경비 -800 및 모든 입력·결과 snapshot record 동등성 유지 |
| CONFIRMED + 존재하지 않는 version | 계약 조회 이전 상태 검사 | `CONFLICT`, repository interaction 0 |
| 계약 없는 상태에서 계산 | 활성 계약 version 조회 | `NOT_FOUND` (`calculate_returns_not_found_for_missing_active_contract_version`) |
| 버전 여러 개 | 명시 version 선택; 최신/기준일 추정 없음 | PostgreSQL/Flyway 재조회 후 과거 v1=-800, 신규 v2=-700 |
| 수기 제경비율 | 저장소 계약 FK·다른 요율 보존, 제경비율만 override | v2 계약 7%, 수기 6%, 적용율 6%, 제경비 -600 |
| 계약 soft-delete 뒤 과거 조회 | 전역 restriction 없는 FK entity graph 조회 | 과거 FK v1·0.08·-800 조회 성공 |
| 계약 soft-delete 뒤 새 DRAFT 계산 | 활성 계약 repository filter | `NOT_FOUND`; 삭제 계약 재사용 불가 |
| 과거 조회 | `findByDocumentNo`는 settlement snapshot만 반환 | 재계산·현재율 선택 없이 entity graph DB 왕복 |
