# PR #1152 R3 — 재고 실사 NON_GOODS 게이트 보완 및 선재 결함 진단

작성일: 2026-08-09

## 1. 결론

- 결함 A는 재현됐고 이번 라운드에서 수정했다. `InventoryAuditService`의 생성 snapshot과 완료 시 라인 조정 모두 `StockService`·`StockInstanceService`가 사용하던 동일 판정으로 통합했다.
- 판정은 `!product.goods() || "BUNDLE".equals(product.productType())` 하나다. 품목명 기반 판정은 추가하지 않았다.
- 결함 B는 수정하지 않았다. `EstimateToSlipConverter`의 임시 창고 UUID와 전표 수정 API 계약 불일치를 진단만 했다.
- 직접 SQL INSERT/UPDATE/DELETE는 실행하지 않았다. 실 DB 조회는 SELECT만 수행했다.

## 2. 사용한 게이트

공통 게이트는 [InventoryProductGate.java](../../services/inventory-service/src/main/java/com/samhanair/logis/inventory/service/InventoryProductGate.java:11)의 `isExcluded`다.

```java
return !product.goods() || "BUNDLE".equals(product.productType());
```

기존 호출자도 같은 공통 게이트를 사용하도록 `StockService:506`, `StockInstanceService:451`, `InboundInspectionService:383`을 위임 형태로 정리했다. 실사에는 다음 두 지점을 적용했다.

- 생성 snapshot: `InventoryAuditService:132-136` — NON_GOODS/BUNDLE balance를 실사 라인으로 만들지 않는다.
- 완료 조정: `InventoryAuditService:364-370` — 이미 존재하는 비상품 실사 라인이 들어와도 balance와 ADJUST movement를 만들지 않는다.

## 3. 재고 balance/movement 변이 15단계 전수

### 세는 방법

모집단은 “재고 변이”를 결과로 만드는 서비스 공개 mutation 진입점으로 정의했다. 다음을 코드 전체에서 먼저 검색했다.

```text
StockBalance / StockLot / StockMovement / StockInstance
addInbound / reserve / release / deduct / adjust / ship / recall / resell
stockBalanceRepository.save / stockLotRepository.save / stockMovementRepository.save
repo.save / repo.saveAll
```

그 결과를 `inventory-service/src/main/java/.../service` 아래의 공개 mutation 메서드와 대조했다. 조회 메서드(`fifoCandidates`, `recallCandidates`, `byProduct`), 시드/엑셀 조회, 실사 `create`의 audit row 저장은 balance/movement 변이가 아니므로 모집단에서 제외했다. 공개 mutation은 `StockService` 5개 + `InboundInspectionService` 1개 + `StockInstanceService` 8개 + 실사 완료 1개 = 15개로 닫힌다.

| 단계 | 호출 지점 | NON_GOODS 게이트 | 없으면 무엇이 일어나나 |
|---:|---|---|---|
| 1 | `StockService.inbound:183` | 있음 — `StockService:185`, 공통 게이트 `InventoryProductGate:11` | lot/balance 증가와 INBOUND movement 생성 |
| 2 | `StockService.reserve:233` | 있음 — `StockService:234` | balance 예약 수량과 RESERVE movement 증가 |
| 3 | `StockService.release:285` | 있음 — `StockService:286` | 예약 수량 복구와 RELEASE movement 생성 |
| 4 | `StockService.deduct:337` | 있음 — `StockService:338` | FIFO lot 차감, balance 차감, DEDUCT movement 생성 |
| 5 | `StockService.adjust:389` | 있음 — `StockService:390` | balance 신규 생성/조정과 ADJUST movement 생성 |
| 6 | `InboundInspectionService.complete:260-265` | 있음 — `InboundInspectionService:262`, 공통 위임 `:383` | 정상 입고 lot/balance와 INBOUND_INSPECTION movement 생성 |
| 7 | `StockInstanceService.create:69-74` | 있음 — `StockInstanceService:73` | AVAILABLE serial instance 저장 |
| 8 | `StockInstanceService.inboundBatch:104-109` | 있음 — `StockInstanceService:108` | serial instance N건 저장 |

따라서 R2의 14단계 게이트 표에서 빠진 것은 15번 실사 완료 조정이다.

## 4. 양방향 RED 원문

### RED-A — NON_GOODS

추가 테스트: `InventoryAuditServiceTest.complete_nonGoodsDiff_doesNotAdjustStockOrCreateMovement`.

수정 전 관측: NON_GOODS 실사 라인 expected 2, actual 1 완료 시 balance가 `2→1`로 줄고 ADJUST movement 1건이 생성됐다.

수정 후 원문 단언:

```text
assertThat(balance.getTotalQty()).isEqualTo(2);
verify(stockMovementRepository, never()).save(any());
```

생성 단계도 `create_excludesNonGoodsBalancesFromAuditSnapshot`으로 snapshot 라인 제외를 고정했다.

### RED-B — GOODS

기존 테스트 `complete_negativeDiff_triggersJournalAndAdjustsStock`와 `complete_positiveDiff_triggersJournalIncrease`가 유지됐다. GOODS 라인의 `100→95` 조정은 그대로 balance 95 및 ADJUST movement 1건을 만든다.

## 5. 결함 B 진단만 수행

### 임시 UUID 유입

- [EstimateToSlipConverter.java](../../services/slip-service/src/main/java/com/samhanair/logis/slip/estimate/service/EstimateToSlipConverter.java:72) 주석이 임시 placeholder 정책을 명시한다.
- 실제 값은 `EstimateToSlipConverter.java:75-80`의 `00000000-0000-0000-0000-000000000001`이며 `Slip.createOutbound`의 `sourceWarehouseId`로 저장된다.
- inventory DB SELECT 결과: `warehouses`에서 해당 UUID 0건, 활성 warehouse 전체 8건.

### 수정 API 계약

- [UpdateSlipRequest.java](../../services/slip-service/src/main/java/com/samhanair/logis/slip/web/dto/UpdateSlipRequest.java:39-61)는 `partnerId`, 배송/메모/기사/V20 프로젝트 필드만 받으며 `sourceWarehouseId`가 없다.
- [SlipService.updateSlip](../../services/slip-service/src/main/java/com/samhanair/logis/slip/service/SlipService.java:476-491)도 해당 DTO 필드만 `Slip.editHeader`에 전달한다.
- 따라서 converter 주석의 “SlipForm에서 정확한 창고로 교체” 전제가 현재 수정 API로는 실현되지 않는다.
- 의도/누락 판정: converter 쪽 주석은 placeholder를 임시로 두고 후속 화면에서 교체하려는 **의도**를 보여주지만, 그 교체 필드가 DTO/서비스에 없는 것은 현재 계약의 **누락(계약 공백)**이다. 이번 PR에서는 고치지 않았다.

### 실 DB 수락 현황

SELECT 결과 (`slip_db`, `is_deleted=false`):

```text
slips.status=ACCEPTED   12건, slip_lines 43건
slips.status=CONFIRMED   9건, slip_lines 23건
ACCEPTED source_type=MANUAL 12건 (INBOUND 6, OUTBOUND 6)
estimates.status=QUOTE_DRAFT 55건; QUOTE_ACCEPTED 0건
```

즉 GOODS 전표 전체가 막힌 것은 아니다. 현재 실 데이터의 ACCEPTED는 견적 변환이 아닌 수동 전표 12건이며, 견적 테이블에는 수락 상태가 0건이다. 이 결과로 SOL의 409 재현 조건은 “모든 전표 수락 불가”가 아니라 견적 변환 경로/임시 창고에 국한된 특수 조건으로 판정한다.
