# PR #1145 R2 수정 보고 — R1 도달 결함 2건

## 결론

- V97은 권한을 복제하지 않는 멱등 no-op으로 고쳤다. `.list` 권한으로 `.accounting`을 새로 만들거나 기존 행을 덮어쓰지 않는다.
- 수신 세금계산서 FE 가드를 BE 정본인 `accounting.tax-invoice.inbound.manage`로 통일했다.
- 권한을 넓히지 않는 선택에 따라 회계전표 화면에 접근하지 못하는 주체는 의도적으로 남는다. 아래 목록에 모두 기록했다.
- 커밋·푸시·실 DB 쓰기·Docker 재배포는 하지 않았다.

## 결함 1 — V97 권한 경계 확대

### 원인

V97의 네 `INSERT ... ON CONFLICT DO UPDATE`가 `accounting.*.list`의 비트를 `accounting.*.accounting`에 복제했다. 기존 `.accounting` 행이 있으면 보존한다는 주석과 달리 `can_view/can_create/can_update/can_delete`를 `EXCLUDED` 값으로 덮어썼다. V37의 정본 시드는 두 회계전표 `.accounting` 코드를 `MASTER`·`ACCOUNTANT`로만 허용한다.

### 수정

V97을 `SELECT 1;`만 실행하는 부작용 없는 예약 migration으로 바꿨다. FE/BE PageCode 정합성은 애플리케이션 코드에서 해결하고, 기존 권한 행은 어떤 저장소에서도 변경하지 않는다. 번호는 V97을 유지했다.

### 접근을 얻지 못한 주체 목록

이는 V97이 원래 복제했을 주체를 권한 확대 없이 그대로 둔 목록이다. 매출·매입 각각 같은 실측이다.

| 주체 축 | 주체 | 건수 | 상태 |
|---|---|---:|---|
| 역할 템플릿 | `MANAGER` | 1 | `.list`는 VIEW/CREATE/UPDATE/DELETE, `.accounting`은 없음 |
| 역할 템플릿 | `SALES` | 1 | `.list`는 VIEW, `.accounting`은 없음 |
| 레거시 역할 행 | `MANAGER`, `SALES` | 2행 | 동일 경계 보존 |
| 그룹 | `매니저`, `영업원` | 2 | 각각 `.accounting` 권한 없음 |
| 계정 | R1 실측 13명 | 13명/전표 | VIEW 신규 획득 없음 |
| 계정 중 저장 액션 대상 | `dev_manager`, `janyeonggu`, `manager@samhan.test` | 3명/전표 | CREATE/UPDATE/DELETE 신규 획득 없음 |

R1 실측상 13명 중 `dev_locked`는 잠금 상태라 즉시 로그인 가능 계정은 12명이다. 권한을 넓히지 않았으므로 MANAGER 실 계정의 기존 `/admin/sales-slips`·`/admin/purchase-slips` 403 경계도 유지된다.

## 결함 2 — 수신 세금계산서 PageCode 불일치

### 원인과 정본 판정

정본은 BE의 `accounting.tax-invoice.inbound.manage`다.

- ⓐ `V37__seed_sp_d6_7_accounting_page_codes.sql`이 이 코드를 시드하고 `MASTER`·`ACCOUNTANT` 권한만 부여한다.
- ⓑ `TaxInvoiceInboundController`의 목록·등록·첨부 등록 세 endpoint가 모두 `@RequirePermission(page = "accounting.tax-invoice.inbound.manage", ...)`를 사용한다.
- ⓒ `AccountingPermissionControllerIT`도 수신 세금계산서 목록 계약을 `.inbound.manage`로 검사한다.

따라서 FE의 `.inbound`를 BE의 `.inbound.manage`로 변경했다. MANAGER의 기존 `.inbound` 권한을 `.inbound.manage`로 이관하거나 승격하는 migration은 만들지 않았다.

### 수정 및 접근 상실 목록

`AppLayout`, `routes/index.tsx`, mock 권한 매트릭스의 활성 화면 가드를 정본 코드로 맞췄다. `.inbound`에서만 VIEW를 가진 실 계정은 `dev_manager`, `janyeonggu`, `manager@samhan.test` 3명이며, 정본 `.inbound.manage`에는 없어 화면 접근을 잃는다. 역할 축에서는 V14의 `MANAGER` 1개 역할 행이 `.inbound`를 가지지만 V37의 `.inbound.manage`에는 없으므로 그대로 접근하지 못한다. 그룹 차집합은 R1 실측 원문에 별도 식별된 항목이 없어 확인된 상실 그룹은 없음이다.

R1 실측 원문:

```text
FeGuardActions : VIEW,CREATE,UPDATE,DELETE
BeActions      :
GetPath        : /admin/tax-invoices/inbound
GetStatus      : 403
DB: .inbound VIEW=10명, .inbound.manage VIEW=7명
차집합: dev_manager, janyeonggu, manager@samhan.test
```

## (a) 계열 전수 sweep

대상은 PR #1145가 손댄 회계 화면 표면과 해당 BE controller/계약 테스트이며, FE 활성 소비자는 `PermissionGuard`·`dynamicCanAccess`, BE 소비자는 `@RequirePermission` 문자열로 추출했다.

수정 전 결과는 FE 22개, BE 33개, 공통 20개, 실제 불일치 1건(`inbound` ↔ `inbound.manage`)이었다. 수정 후 재검색 결과 회계전표·수신 세금계산서 활성 FE/BE 불일치는 0건이다. `accounting.deposit-mapping`은 BE 상수 `DepositorMappingService.PAGE_CODE`를 직접 확인해 정합 판정했다.

```text
FE active guards: 22
BE permission codes: 33
common codes: 20
active FE/BE mismatches after fix: 0
inbound active FE: accounting.tax-invoice.inbound.manage VIEW
inbound BE: accounting.tax-invoice.inbound.manage VIEW/CREATE
```

## (b) 식별자 grep 전수

변경한 활성 문자열 `accounting.tax-invoice.inbound.manage`를 FE·BE·migration·test에서 다시 검색했다. 활성 가드는 모두 정본 문자열이다. 기존 `accounting.tax-invoice.inbound`는 V14 seed, `PageCode` enum, PermissionMatrix의 legacy 관리 목록, 타입 선언, mock의 legacy 페이지 목록에만 남겼다. 이는 기존 권한 데이터와 관리 화면 식별자를 삭제하지 않기 위한 의도적 보존이며, 활성 화면 가드에는 사용하지 않는다.

```text
routes/index.tsx:1392  pageCode="accounting.tax-invoice.inbound.manage" action="view"
AppLayout.tsx:526       dynamicCanAccess('accounting.tax-invoice.inbound.manage', 'view')
TaxInvoiceInboundController.java:40,53,63  accounting.tax-invoice.inbound.manage
legacy active guard matches: 0
```

회계전표 `.list` 식별자도 삭제하지 않았다. R1이 확인한 입출고 분석·원천 조회·배분 source가 계속 `.list`를 사용하므로 V97에서 제거하면 별도 화면을 깨뜨린다.

## (d) mock 게이트 격리

이번 라운드에는 신규 endpoint를 만들지 않았다. 따라서 새 endpoint용 격리 mock 게이트 실행 대상은 없다. BE endpoint와 PageCode만 맞췄고, 관련 controller IT는 외부 API를 호출하지 않는 테스트로 통과했다.

## 셋째 가능성

R1에서 확인된 추가 결함은 V97의 감사 메타데이터가 `v95-accounting-slip-alignment`로 기록되는 문제였다. 이번에 해당 DML을 제거하고 V97 주석으로 정정해 함께 닫았다. V98 이상 migration은 만들지 않았다.
