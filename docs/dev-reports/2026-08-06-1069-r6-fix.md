## 1. 원인 — 성공 응답이 화면에 반영되지 않던 지점

서버와 API 함수 expandBundleLine는 정상이고, 프런트엔드의 성공 응답 적용 직전 가드가 문제였다.

clients/desktop/src/renderer/routes/SlipFormPage.tsx:1035-1052, 1062-1079의 currentSnapshot은 재전개 대상이 구성품 행일 때 구성품의 quantity·unitPrice를 그대로 사용했다. 그러나 요청 스냅샷은 세트 부모 컨텍스트의 값으로 만들어졌다.

~~~text
요청 스냅샷 unitPrice       세트 부모 2,752,200
현재 스냅샷 unitPrice       첫 구성품 1,053,775
결과                       areBundleExpansionSnapshotsEqual=false
동작                       성공 응답을 버리고 조용히 return
~~~

따라서 restorePreviousExpansion()에는 진입하지 않았다. 성공 응답이 빈 응답으로 오인된 것이 아니라, replaceWithExpandedBundleLines() 호출 전의 최신성 검사가 정상 응답을 차단한 것이다. 수정은 비-BUNDLE 구성품 행을 비교할 때 context.quantity, context.unitPrice, context.specification을 부모 스냅샷에 명시적으로 덮어쓰도록 했다.

두 번째 적용 결함은 clients/desktop/src/renderer/routes/SlipFormPage.tsx:842-958의 교체 범위였다. 재전개 시 source는 첫 구성품 한 행인데, 기존 구현은 그 행만 응답 행으로 바꾸고 기존 형제 구성품 행은 남겼다. 그래서 판넬제외 3행 응답에서도 기존 PANEL 행이 남을 수 있었다.

수정 후 옵션 컨텍스트에 componentLineIds를 보관하고, 재전개 시 해당 부모가 소유한 기존 구성품 행 전체를 제거한 뒤 응답 행 전체를 같은 위치에 삽입한다. 새 행의 parentSetModel, bundleParentProductId, bundleParentUnitPrice, setOptions는 부모 컨텍스트에서 채워 저장 계보도 유지한다.

## 2. 저장 차단이 풀리지 않던 지점

clients/desktop/src/renderer/routes/SlipFormPage.tsx:1697-1706의 저장 조건은 두 busy 상태에 의존한다.

~~~text
priceResolutionBusy     = partnerReprice.isPending || lines.some(lookupLoading)
bundleExpansionPending  = lines.some(expandedBundleOptions[id].expansionPending)
canSubmit                = ... && !priceResolutionBusy && !bundleExpansionPending
~~~

옵션 변경 직후 expansionPending=true가 되었는데, 성공 응답이 위 최신성 가드에서 반환되면서 replaceWithExpandedBundleLines()가 실행되지 않았다. 그 함수가 담당하던 구성품 행 교체와 lookupLoading=false, expansionPending=false 수렴이 모두 누락되어 저장 버튼이 계속 disabled였다.

성공 응답이 실제로 적용되면 새 구성품 행을 모두 lookupLoading=false로 만들고, 컨텍스트를 expansionPending=false로 갱신한다. 실패·빈 응답은 기존 restorePreviousExpansion() 보호를 유지해 이전 행을 보존하고 같은 두 busy 상태를 해제한다(:995-1020, :1062-1079).

## 4. 기존 테스트가 결함을 못 잡은 이유

- 기존 성공 테스트는 productName과 전개 호출 횟수 중심이었다. 서버 응답의 modelCode·구성품 단가·재전개 후 전체 행 집합을 화면에서 대조하지 않았다.
- 기존 옵션 성공 테스트의 mock 응답은 첫 구성품이 같은 경우가 많았고, 성공 응답이 최신성 가드에서 조용히 버려지는 부모 단가 대 구성품 단가 불일치를 단언하지 않았다.
- 저장 payload 테스트는 초기 전개 직후 저장을 검증했다. 옵션 변경 후 응답 적용과 저장 POST까지 이어지는 경로가 없었다.
- 실패·빈 응답 테스트는 보호 경로를 잘 고정했지만, 성공 응답이 같은 경로 전에 return하는 경우를 고정하지 않았다. 그래서 단위 테스트는 GREEN인데 라이브 화면만 이전 행을 보이는 상태가 가능했다.
- R4 Playwright 계약은 도메인 select와 controlled round-trip을 검증하지만, 실제 /slips/expand-line 응답의 행 교체 결과까지는 범위에 없었다.

이번에는 테스트용 LineRow 경계에 data-model-code를 노출하고, 응답 → lines 상태 → 화면 행·단가 → 저장 payload까지 통과시켰다.
