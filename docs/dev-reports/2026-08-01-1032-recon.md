# 전표 목록·상세 금액 불일치 — 정찰

조기 PR 개설용 자리표시. Codex 정찰 결과를 이 파일에 누적한다.

## 정찰 로그

- 2026-08-01: 정찰 시작. 코드 수정 없이 실 DB 읽기 조회와 실행 중 API의 GET 호출만 수행한다. git 명령, Docker 재빌드·재기동, 실 DB 쓰기는 수행하지 않는다. 사용자 공개 식별자는 전표번호와 거래처코드만 기록하며 UUID는 기록하지 않는다.
- 실행 환경 확인: 기존 `samhan-slip-service`는 `127.0.0.1:18086`에서 healthy, 기존 `samhan-postgres`는 `5432`에서 healthy 상태다. 컨테이너에는 변경을 가하지 않았으며 이후에도 실행 중 인스턴스에 GET/SELECT만 수행한다.
- 실 DB 확인: 대상 DB는 `slip_db`, 헤더/라인 테이블은 `slips`/`slip_lines`다. 라인에는 `unit_price`, `unit_price_with_vat`, `line_total`, `supply_amount`, `vat_amount`, `unit_price_domain`이 함께 존재한다. 이 확인은 `information_schema` SELECT로만 수행했다.
- 1차 금액 경로 확인: 목록 DTO `SlipResponse.from`은 각 라인의 `SlipLine.getLineTotal()`을 합산해 `totalAmount`를 만든다(`SlipResponse.java:134-137`). 실 DB에서 활성 라인은 `line_total = supply_amount`가 전부 성립한다(불일치 전표 0건). 반면 `sum(line_total) <> sum(coalesce(supply_amount,line_total)+coalesce(vat_amount,0))`인 활성 전표는 **2,344건**이다. 아직 화면/API 필터를 적용하지 않은 원시 집계이므로 이슈의 2,335건과 같은 모집단인지 추가 분해한다.
- 2,344건 분해: 활성 전표 2,345건 중 부가세 합계가 0이 아닌 전표가 정확히 **2,344건**, 부가세 합계 0인 전표가 1건이다. 유형별 불일치는 OUTBOUND 2,302건 + INBOUND 42건이다. 상태별로도 전 상태에 걸쳐 있으며, 따라서 현재 실 DB의 활성 전체 모집단에서는 이슈 제목의 **2,335건이 재현되지 않고 실제는 2,344건**이다. 삭제 전표는 별도이며 활성 집계에 넣지 않았다.
- API 접근 1차 확인: 실행 중 slip-service에 역할 헤더만 넣은 GET은 동적 권한 가드에서 403이므로, 실제 인증 컨텍스트를 확보해 목록·상세 GET을 다시 호출한다. 실패 호출은 데이터 변경을 일으키지 않았다.
- API 인증 방식: 로그인 API는 `auth_db.accounts.last_login_at`을 갱신하므로 실 DB 쓰기 금지에 따라 호출하지 않았다. 대신 실행 중 slip-service가 신뢰하는 기존 개발 사용자 헤더 컨텍스트(`dev_master`, `MASTER`, system-master)를 사용한 GET만 수행했고 목록 조회가 200임을 확인했다.
- **실전표 재현 — 전표번호 `2026/05/20-1`, 거래처코드 `P-2026-0001`**: 목록 GET `/slips?...`의 `totalAmount`는 **2,076,816원**. 같은 전표의 상세 GET `/slips/{내부키}`를 호출해 라인 5건을 합산하면 `lineTotal` **2,076,816원**, `supplyAmount` **2,076,816원**, `vatAmount` **207,684원**, `supplyAmount + vatAmount` **2,284,500원**이다. 즉 **목록 API와 상세 API의 raw `lineTotal`은 일치**하고, 207,684원 차이는 상세 화면이 `supplyAmount + vatAmount`를 표시할 때 발생한다. 이슈 제목의 “목록 API vs 상세 API 자체 불일치” 해석은 사실이 아니다. 호출에 쓴 내부키는 보고서에 기록하지 않았다.
- 코드상 표시 경로 특정: 목록 화면 `SalesQueryPage.tsx:755`는 API 행의 `row.totalAmount`를 그대로 표시하고, 그 값은 BE `SlipResponse.java:134-137`의 `sum(SlipLine.lineTotal)`이다. 상세 화면은 `SlipDetailPage.tsx:214-229`의 `slipLineAmounts`에서 `supply = supplyAmount ?? lineTotal`, `vat = vatAmount ?? vatFromSupply(supply)`, `totalIncl = supply + vat`로 만든 뒤 `:3945-3976`에서 합계로 표시한다. 따라서 불일치 발생 계층은 **상세 API가 아니라 목록 요약 DTO와 상세 FE의 표시 의미 차이**다.
- 저장 규약 이력: V59(`2026-07-27 07:42:29` 적용)는 `unit_price_domain`을 추가하고 **legacy backfill을 의도적으로 하지 않았다**. `VAT_INCLUSIVE`는 `unit_price_with_vat`가 사용자 입력, `SUPPLY`는 `unit_price`가 사용자 입력, `NULL`은 판별 불가능한 legacy다. V61(`#1017` 정정, `2026-08-01 11:45:52` 적용)은 과거 PARTNER_ORDER VAT 중복가산 19개 표적 라인을 정정하면서 `line_total = supply_amount` 별칭 규약을 명시했다. #991 조사 문서도 과거 주문전환 23개 라인이 `unit_price_with_vat = unit_price × 1.1`인 구 규약이고, 신규 요청은 VAT 포함 단가 직접 의미라서 호환 분기가 필요하다고 기록한다.
- **기존/신규 혼재 실측**(활성 전표·활성 라인): 총 2,776라인 중 `unit_price_domain=NULL` **2,758**, `VAT_INCLUSIVE` **17**, `SUPPLY` **1**이다. V59 적용 전 생성 2,757라인, 적용 후 생성 19라인이며 적용 후에도 legacy 복사 의미를 보존한 `2026/07/27-245` 1라인만 domain이 NULL이다. 전표 단위로는 legacy-only **2,334전표**, tagged-new-only **11전표**, 한 전표 안에서 legacy/new가 섞인 경우 **0전표**다. 즉 DB 전체에는 기존·신규가 명백히 공존한다.
- 단가 관계 분포: `unit_price_with_vat × 수량 = supply_amount + vat_amount`만 만족 **2,760라인**, VAT가 0이라 공급/총액 양쪽과 같은 1라인, `unit_price_with_vat × 수량 = supply_amount`만 만족하는 구 오염형 **12라인**, 어느 쪽도 exact가 아닌 수동/반올림형 **3라인**이다. `unit_price_with_vat IS NULL`은 0건이다. 따라서 과거 행 호환은 null 여부가 아니라 **같은 컬럼 값의 의미가 시기·경로별로 달랐다는 문제**다.
- **동일한 목록측 공급가액(`sum(line_total)`)을 사용자에게 금액/합계로 노출하는 화면 전수: 6개 구현 화면**이다. (1) 판매관리 `SalesQueryPage`, (2) 구매관리 `PurchaseQueryPage` — 둘 다 `SlipResponse.totalAmount`; (3) 결재 작성 `GroupwareApprovalCreatePage`, (4) 결재 상세 `GroupwareApprovalDetailPage` — 둘 다 `SlipSearchResult.totalAmount`를 쓰는 `DocumentReferencePicker`; (5) 공개 인수증 `MobileRecipientPage` — `SlipSignatureService`가 `sum(lineTotal)`로 만든 `PublicSignatureViewResponse.totalAmount`; (6) 전표 정리 `SlipCleanupPage` — `SlipCleanupService`의 `sum(lineTotal)`이며 이 화면의 CSV도 같은 값이다. 현재 판매관리 화면을 제외하면 **다른 화면 5개**가 같은 공급가액 의미에 묶여 있다. 같은 컴포넌트의 표/DataGrid 전환이나 같은 화면의 CSV 버튼은 별도 화면으로 중복 계수하지 않았다.
- 인접 산출물 sweep: 활성 전표 인쇄 화면은 **3개**(`SalesTransactionStatementPrintPage`, `SalesInvoicePrintPage`, `PurchaseSlipPrintPage`)이며 모두 `storedLineAmounts`의 `S + V` 합계를 사용해 상세와 같은 VAT 포함 의미다. 구 `InvoiceView`는 라우트에서 대체되어 비활성이다. 전표 목록 XLSX는 **1개**지만 `SlipExcelExportService.COLUMNS`에 금액 컬럼 자체가 없어 이 불일치 값을 내보내지 않는다. 영업 모바일 대시보드 **1개**(`SalesHomeScreen` ← `MobileSalesDashboardService`)도 `supplyAmount + vatAmount`를 집계한다. 회계 연계는 3개 projection 계열(`SlipSummary`, `SlipSalesQueryResponse`, `PartnerLedgerSalesResponse`) 모두 S/V를 분리하거나 VAT 포함 `lineTotal`로 정규화하므로 목록측 raw `sum(line_total)`을 “합계”로 재사용하지 않는다.
- DC 규약 교차 확인: 가격 계산 코드는 품목의 `products.fixed_discount_rate`가 있으면 이를 먼저 반환하고, 없을 때 `dc_configs`의 카테고리별 전역DC를 고른다(`PriceCalculationService.pickCategoryRate`), 즉 **고정DC 우선(`fixedDc ?? globalRate`)**이 코드로 확인된다. 거래처 기본 할인율의 물리 저장소는 partner-service의 거래처 하위 정책 테이블 `partner_price_discounts.basic_discount_rate`다. 다만 현재 `PriceCalculationService`에는 이 기본 할인율을 3차 fallback으로 읽는 경로가 없으므로, 이 정찰에서 구현되어 있다고 확대 해석하지 않는다. 존재하지 않는 “약정DC”는 용어로 쓰지 않는다. 이 할인율 선택은 저장 단가를 만드는 상류 규약이고, 이미 저장된 `line_total`과 S/V 중 무엇을 목록에 표시할지의 직접 원인은 아니다.
- 어느 표시가 맞는가 — 근거: 도메인 README와 V61은 `line_total`을 VAT 제외 공급가액 S의 별칭으로 명시한다. 반면 상세 화면은 실제 라벨도 `합계(VAT포함)`이고, 활성 인쇄 3개와 모바일 대시보드도 S+V를 합계로 사용한다. 회계 결정문도 공급가액과 VAT를 분리하고 총액은 S+V로 정의한다. 레거시 이관 감사 테이블에는 `SUPPLY_AMT`와 `VAT_AMT`가 별도 보존되어 있어 공급가액 자체도 유효한 회계 값이지만, 현재 목록 열의 라벨은 `공급가액`이 아니라 포괄적인 `금액`이다.
- **제안 및 기획 결정 필요**: 현재 라벨을 유지한다면 목록의 `금액`은 상세·인쇄와 같은 **VAT 포함 S+V**로 통일하는 안을 권장한다. 이 경우 위에서 센 공급가액 노출 6개 화면을 함께 검토해야 하며 판매관리 한 곳만 바꾸면 다른 5개가 다시 어긋난다. 반대로 업무 의도가 공급가액이라면 값을 유지하되 6개 화면의 라벨을 명시적으로 `공급가액`으로 바꾸고 VAT/총액을 별도 제공해야 한다. 레거시 목록 화면의 실제 라벨·사용자 업무 의도까지 확정할 직접 자료는 저장소에서 찾지 못했으므로, 두 안 중 선택은 **기획 결정**이다.
- 완료 전 재검증: 같은 실전표의 목록/상세 GET을 다시 호출해 **2,076,816원 대 2,284,500원**을 재확인했고, 동일 SQL을 다시 실행해 활성 전표 **2,345건 중 불일치 2,344건**(OUTBOUND 2,302 + INBOUND 42)을 재확인했다. domain 분포도 활성 헤더와 활성 라인을 모두 조인한 동일 모집단에서 NULL 2,758 + SUPPLY 1 + VAT_INCLUSIVE 17로 재확인했다. 참고로 헤더 삭제 여부를 무시하고 라인만 `is_deleted=false`로 세면 NULL이 2,780으로 22건 늘어나므로 그 다른 모집단은 본문 수치에 섞지 않았다. 보고서의 UUID 형식 문자열은 정규식 검사 결과 0건이다.
