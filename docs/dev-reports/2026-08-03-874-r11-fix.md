# PR #1057 / 이슈 #874 R11 — line_no 정렬 계약과 레거시 행 순서 의미 검증

## 1. `line_no` 중복 분포 확인 — [실데이터/로컬 read-only]

읽기 전용 명령:

```text
docker exec samhan-postgres psql -U samhan -d accounting_db -P pager=off -c "... GROUP BY source,parent_id,line_no HAVING COUNT(*) > 1 ..."
```

출력 원문:

```text
             source             | duplicate_groups | rows_in_duplicate_groups
--------------------------------+------------------+--------------------------
 purchase_accounting_slip_lines |                0 |                        0
 sales_accounting_slip_lines    |                0 |                        0
 tax_invoice_lines              |                0 |                        0
(3 rows)
```

앞선 `line_no` null/채움률 측정과 함께 현재 활성 데이터에서 null 0건, 중복 그룹 0건이다. 단, 데이터에 중복이 없다는 관측과 별개로 정렬 계약의 동률 규칙은 코드/스키마 계약으로 확인해야 한다.

## 2. 레거시가 보는 행 순서 — [실제 원문]

레거시 원문은 입력 배열의 순서를 별도 정렬값이 아니라 그대로 사용한다.

| 근거 | 원문 의미 |
|---|---|
| `tools/legacy-gas/일마감 프로그램/Code.js:458-460` | `ecountData.map(function(r, i)`에서 입력 배열 index를 `_ri`로 보존한다. |
| `tools/legacy-gas/일마감 프로그램/Code.js:473-477` | `ecountDataMapped.forEach` 중 `invoiceGroups[key].push(row)`로 입력 순서를 그룹 배열에 보존한다. |
| `tools/legacy-gas/일마감 프로그램/Code.js:486-498` | `items.forEach`가 그 배열 순서대로 `currentZone`을 갱신하고 각 행에 `_zone`을 기록한다. |

따라서 레거시의 판정 입력 순서는 시트에서 파싱되어 `ecountData`가 된 배열의 행 순서이며, `Code.js:480-481`의 그룹 범위 안에서만 적용된다.

현행 이관 경로는 CSV 순서를 명시적으로 읽는다.

| 근거 | 원문 의미 |
|---|---|
| `services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/EcountTaxInvoiceImporter.java:58-60` | `parsed.dataRows().get(i)`를 입력 순서대로 읽고 `rowNo=i+1`을 부여한다. |
| `EcountTaxInvoiceImporter.java:84-88` | 그룹 전표를 유지하면서 처리 순서대로 `nextTaxInvoiceLineNo`를 받아 라인을 저장한다. |

이 경로에 대해서는 CSV dataRows 순서와 `line_no` 생성의 연결은 코드로 확인된다. 다만 `MonthEndCloseService`가 읽는 세금계산서·매출전표·매입전표 전체의 원천이 같은 legacy `ecountData` 배열이라는 연결은 확인되지 않았다. `docs/migration/ecount-data/raw/`에는 `.gitkeep`만 있어 원본 시트와의 직접 대조 자료도 없다.

## 3. 현행 전체 전달 경로의 정렬 계약 확인

매출·매입 생성 경로는 요청 리스트 순번을 저장 순번으로 사용한다.

- `SalesAccountingSlipCreateAttemptService.java:86-94`: `req.lines()`를 순회하며 `lineNo++`을 저장한다.
- `PurchaseAccountingSlipCreateAttemptService.java:85-93`: 같은 방식으로 `req.lines()` 순번을 저장한다.
- `TaxInvoiceService.java:104-108`, `:158-163`: 세금계산서도 요청 리스트 순번을 `line_no`로 저장한다.

그러나 조회/전달에는 명시적 자식 정렬이 없다.

- `SalesAccountingSlip.java:73-74`, `PurchaseAccountingSlip.java:72-73`, `TaxInvoice.java:190-192`: `List` 연관관계에 `@OrderBy`가 없다.
- `TaxInvoiceRepository.java:104-113`: `ORDER BY`는 부모의 `supplyDate, taxInvoiceNo`뿐이며 자식 `line_no`는 포함하지 않는다.
- `MonthEndCloseService.java:238-243`: `for (TaxInvoiceLine line : ti.getLines())`로 연관 리스트를 그대로 소비한다.

따라서 `line_no`의 저장값은 요청 입력 순번이라는 근거가 있으나, JPA 연관 리스트가 그 순서를 항상 반환한다는 정렬 계약은 현재 코드에 없다. 같은 입력에 같은 행 순서를 보장하려면 `line_no ASC` 정렬 계약과 동률 정책을 별도로 추가해야 한다.

## 4. 동률 정책과 데이터 안전성 — [실데이터/로컬 read-only]

스키마 조회 결과:

```text
purchase_accounting_slip_lines | ..._slip_id_line_no_key | UNIQUE | slip_id,line_no
sales_accounting_slip_lines    | ..._slip_id_line_no_key | UNIQUE | slip_id,line_no
tax_invoice_lines              | ux_tax_invoice_lines_invoice_line_active | UNIQUE INDEX | tax_invoice_id,line_no WHERE is_deleted=false
```

`line_no`는 세 엔티티에서 `nullable=false`이며, 활성 부모별 `(parent_id,line_no)`가 유일하다. 앞 절의 실데이터 측정도 세 테이블 모두 null 0건·중복 그룹 0건이다. 그러므로 정렬 계약을 추가할 경우 동률 보조키는 정상 활성 데이터에서 필요하지 않고, 계약은 부모 scope 내부 `line_no ASC`로 정한다. 비정상 데이터가 제약을 우회해 들어온 경우에는 행을 버리거나 임의로 재정렬하지 않고 오류/운영 데이터 정합성 문제로 다뤄야 한다.

## 5. ② 레거시 시트 행 순서와 `line_no` 의미의 동일성 판정 — 중단

판정: **동일한 의미라는 근거 미확보**.

- 레거시의 직접 근거는 `Code.js:458-460`, `:473-477`의 `ecountData` 입력 배열 순서 보존이다.
- 현행 UI 생성은 `request.lines()` 순서(`TaxInvoiceService.java:104-108`, `SalesAccountingSlipCreateAttemptService.java:86-94`, `PurchaseAccountingSlipCreateAttemptService.java:85-93`)를 저장한다.
- 현행 CSV 이관은 `parsed.dataRows()` 순서(`EcountTaxInvoiceImporter.java:58-60`)와 해당 전표 처리 순서(`:84-88`)를 연결한다.
- 하지만 `MonthEndCloseService`가 소비하는 세금계산서·매출전표·매입전표 각각의 입력이 레거시 `ecountData`의 동일한 행 순서를 보존한다는 공통 매핑/계약은 발견되지 않았다.
- `docs/migration/ecount-data/raw/`에는 `.gitkeep`만 있어 원본 시트 행과 `line_no`를 직접 대조할 실데이터 원본도 없다.

따라서 PM이 결정한 `line_no ASC` 정렬 계약은 필요성이 확인됐지만, 이 라운드에서는 그 정렬을 `riUsage` 판정의 레거시 순서와 동일하다고 간주하여 배선할 수 없다. 근거 없이 순서를 만들어내지 않기 위해 ③을 진행하지 않는다. 다음 판단 항목은 전표 원천별로 legacy `ecountData` 행 순서를 `line_no`에 보존한다는 입력 계약/매핑을 확정하는 것이다.

## 8. ① 정렬 계약 적용

`line_no ASC`를 자식 라인 조회 계약으로 추가했다.

- `TaxInvoice.java:190-193`: `@OrderBy("lineNo ASC")`
- `SalesAccountingSlip.java:73-75`: `@OrderBy("lineNo ASC")`
- `PurchaseAccountingSlip.java:72-74`: `@OrderBy("lineNo ASC")`

이 변경은 자식 행의 집합·필터·금액을 변경하지 않고, 부모 scope 안에서 반환 순서만 고정한다. 활성 데이터의 null/중복은 앞서 측정한 0건이며, 스키마 유니크 제약으로 정상 데이터의 동률은 허용되지 않는다.

## 9. R11 중단 판정

① 정렬 계약은 완료했다. 그러나 ②의 핵심 의미 검증에서 `line_no`와 레거시 `ecountData` 행 순서가 전표 원천 전체에서 동일하다는 근거가 확보되지 않았다. 사용자 절차에 따라 ③의 `riUsage` 판정 반영은 중단한다.

따라서 이번 라운드에는 RED fixture, 판정 구현, GREEN, 순서 축 조합표 재대조를 수행하지 않았다. 해당 항목을 통과 또는 완료로 보고하지 않는다.
