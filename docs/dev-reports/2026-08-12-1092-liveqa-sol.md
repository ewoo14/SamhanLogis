## 실행 경계

인앱 Browser 런타임 목록이 실제로 `[]`였으므로 지시대로 Playwright Chromium을 사용했다. 브랜치의 조회 전용 API를 검증하기 위해 DB migration이 없는 `slip-service`와 `partner-order-service`만 현재 브랜치 JAR로 빌드·교체했다.

공유 DB에는 아래 집계만 `BEGIN TRANSACTION READ ONLY`로 실행했다. `INSERT`/`UPDATE`/`DELETE`/DDL은 실행하지 않았다. 로그인은 `last_login_at`을 갱신하므로 호출하지 않았고, 읽기 전용 로컬 QA JWT 쿠키로 `GET /auth/me`만 호출했다. Playwright 라우트에서 gateway 대상 비-GET 요청을 전부 차단했으며, 앱의 `POST /logs/front` 1건이 `ERR_BLOCKED_BY_CLIENT`로 차단됐다. 저장·편집·복원·발송·전환 버튼은 누르지 않았다.

```text
DB READ ONLY
estimates|45
partner_orders|4
quote_snapshots|4
partner_order_drafts|11

브라우저 gateway 요청: GET/HEAD/OPTIONS만 허용
차단 원문: POST http://localhost:8080/logs/front
```

## 1. 출처 표시

실행: 견적서 관리에서 `통합 목록 보기`를 선택하고 `구분` 열 원문을 확인했다.

```text
화면 원문
데스크톱 · 종합견적서
데스크톱 · 주문서
웹 · 주문서

웹 · 종합견적서: 행 0건이라 화면 원문 확인 불가
오류 배너: 웹 종합견적서 목록을 불러오지 못했습니다. 가능한 데이터만 표시합니다.
```

보이는 세 출처는 데스크톱/웹 저장 위치와 종합견적서/주문서 계열이 구분됐다. `웹 · 종합견적서`는 gateway 조회 실패로 행 자체가 나오지 않았다.

## 2. 출처 필터

각 select option을 실제로 선택한 결과다.

| 필터 화면 원문 | 화면 건수 |
|---|---:|
| 전체 | 60 |
| 데스크톱 · 종합견적서 | 45 |
| 데스크톱 · 주문서 | 4 |
| 웹 · 종합견적서 | 0 |
| 웹 · 주문서 | 11 |

필터 자체는 현재 화면에 들어온 행에 정확히 적용됐다. 다만 웹 종합견적 4건이 공급되지 않아 전체/해당 필터 건수가 틀리다.

## 3. 웹 저장분 15건 전부 표시

**실 사용자 화면 FAIL — 15건 중 11건만 표시됐다.**

```text
공유 DB READ ONLY: quote_snapshots 4 + partner_order_drafts 11 = 15
slip-service 직접 GET /api/v1/estimates/web-snapshots: 200, data 4건
gateway GET /api/v1/estimates/web-snapshots: 404, body 148 bytes
gateway GET /api/v1/partner-orders/web-drafts: 200, data 11건
화면: 웹 · 종합견적서 0 + 웹 · 주문서 11 = 11건
```

직접 서비스 응답은 4건이며 UUID와 payload가 없었다. 그러나 api-gateway에 `/api/v1/estimates/web-snapshots` 라우트가 없어 실제 데스크톱 경로에서는 404가 재현됐다.

## 4. 기존 목록 보존

**기존 데이터는 보존됐다.**

```text
기본 견적 목록 제목: 견적서 관리 전체 45건
기본 테이블 실제 row: 45
통합 필터 데스크톱 · 종합견적서: 45
통합 필터 데스크톱 · 주문서: 4
기존 합계: 49
필터 없는 통합 목록: 60건 (기대 64건)
```

기존 `45 + 4 = 49`는 모두 남았다. 전체가 64가 아닌 60인 원인은 기존 행 유실이 아니라 웹 종합견적 4건의 gateway 404다.

```text

클릭 후: 견적서 상세 [2026/08/10-9] 표시, GET 200

```

데스크톱 저장분은 상세로 진입했다. 웹 주문서 행은 실제 클릭해도 이동하지 않았고, 웹 종합견적은 누락돼 시도할 행이 없었다. 쓰기는 필요하지 않은 조회 시나리오였으며 저장 동작은 하지 않았다.

## 6. UUID 화면/API 비노출

**FAIL. 화면 본문에서는 UUID 0건이었지만, 실 사용자 흐름의 API 응답 본문에는 UUID가 노출됐다.** 범용 UUID 형식 정규식으로 캡처한 모든 fetch/XHR 응답 본문을 전수 검사했다.

주요 업무 응답의 발생 횟수:

| 응답 | UUID 발생 횟수 |
|---|---:|
| `GET /slips/estimates?page=0&size=50` | 123 |
| `GET /slips/estimates?page=0&size=10000` | 123 |
| `GET /slips/estimates/{id}` | 5 |
| `GET /api/v1/partner-orders?page=0&size=10000` | 0 |
| `GET /api/v1/partner-orders/web-drafts` | 0 |
| slip-service 직접 `GET /api/v1/estimates/web-snapshots` | 0 |

같은 사용자 흐름에서 호출된 보조 응답도 `GET /auth/me` 2회, `GET /api/notifications/my` 2회, `GET /auth/admin/approval-line-configs/users` 29회 발생했다. 값 자체는 보고서에 전재하지 않았다. 따라서 “화면·API 응답 어디에도 UUID 없음” 계약은 충족하지 못했다.

## 도달 가능한 결함

1. `GET /api/v1/estimates/web-snapshots`가 api-gateway에서 404다. 직접 slip-service는 200/4건이므로 gateway 라우트 누락으로 재현된다. 영향: 웹 15건 중 11건만 표시, 전체 64건 대신 60건.
2. 웹 저장 행은 상세 진입 경로가 없다. 실제 표시된 웹 주문서 행을 클릭해도 URL과 화면이 바뀌지 않는다. 웹 종합견적은 결함 1 때문에 행 자체가 없다.
3. 견적 목록/상세 API 응답에 UUID가 노출된다. 화면 텍스트에서는 0건이지만 확정 규칙인 API 비노출을 위반한다.
4. 공유 DB 실 사용자 목록에서 `S26 ??? ???`가 표시된다. 상세 진입 중 담당 후보 응답에도 `??` 표시명이 재현된다.

결함은 **4건**이다.
