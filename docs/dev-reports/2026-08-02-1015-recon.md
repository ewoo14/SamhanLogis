## 2026-08-02 PR #1060 제한 정찰

- #1028 정찰의 표시≠실제 결함 1: 주문서 앱 안내는 `최종 주문일로부터 30일`을 차단 기준으로 표시했지만, 실제 backend는 `lastLoginAt`, 값이 없으면 `passwordChangedAt`으로부터 30일을 판정했다(`docs/dev-reports/2026-08-01-1015-order-app-access-recon.md`, `2026-08-01-1015-slice1-implementation.md`).
- #1028 정찰의 표시≠실제 결함 2: 승인현황에서 장기미발주 행을 `APPROVED`로 선택하면 화면은 성공처럼 갱신됐지만, backend의 승인 분기가 `LONG_UNUSED`를 처리하지 않아 실제 저장 상태는 바뀌지 않는 no-op이었다(같은 선행 문서).
- 결함 1 현재 코드 판정: **해소됨**. 현행 주문서 앱 안내는 `마지막 로그인일(로그인 기록이 없으면 비밀번호 변경일)로부터 30일`이라고 표시하고(`clients/web/order-app/index.html:8303`), 실제 계산도 `lastLoginAt`, 없으면 `passwordChangedAt`을 기준으로 30일을 더한다(`PartnerAuth.java:243-260`). 현행 주문 앱에는 옛 `최종 주문일` 문구가 없다.
- 결함 2 현재 코드 판정: **해소됨**. `PartnerApprovalService.updateStatus()`의 `APPROVED` 분기가 `LONG_UNUSED`를 명시적으로 처리해 `restoreFromLongUnused()`를 호출하며(`PartnerApprovalService.java:83-91`), 도메인은 상태를 `NEED_PW_INPUT`으로 바꾸고 만료 기준시각을 복구 시각으로 갱신한다(`PartnerAuth.java:200-208`). 따라서 종전 no-op과 복구 직후 재차단 코드 경로가 모두 제거됐다.
- 실 DB 읽기 확인(`partner_auth_db`, `BEGIN READ ONLY`): 활성 인증행은 `NEED_PW_INPUT` 2건이고 `LONG_UNUSED` 저장행 0건, 현행 30일 계산 후보 0건이다. 따라서 현재 실 데이터에서 두 결함을 재현할 대상은 없고 영향 건수는 0건이다. 실 DB 쓰기·상태변경은 하지 않았다.
- 현행 기능 존재 판정: **두 기능 모두 한 화면에 존재한다.** 실제 route `/sales/order-approvals`가 `SalesOrderApprovalsPage`를 등록하고(`routes/index.tsx:505-512`), 화면은 `주문서 앱 접근권한 설정` 제목, 1~365일 기간 입력, 후보 수·거래처코드·거래처명 미리보기, 선택 대상 비밀번호 초기화를 제공한다(`SalesOrderApprovalsPage.tsx:61-136,246-319`). 기존 `주문서 승인` 메뉴와 새 메뉴가 모두 같은 route로 연결된다(`AppLayout.tsx:755-764`, `SalesSubNav.tsx:23-25`).
- 현행 backend 계약: VIEW 권한의 `GET /api/v1/partner-approvals/access-preview?unusedDays=N`이 후보를 읽고, UPDATE 권한의 `POST /api/v1/partner-approvals/{partnerCode}/reset-password`가 거래처코드 단건을 초기화한다(`PartnerApprovalsController.java:68-93`). 화면의 선택 실행은 전용 일괄 endpoint가 아니라 선택 거래처별 단건 요청을 `Promise.all`로 병렬 호출한다(`SalesOrderApprovalsPage.tsx:119-136`).
- 레거시 장기미발주 원본 판정: 실행 시각의 정확히 30일 전을 cutoff로 잡고, 최근 30일의 `주문 성공` 로그 또는 출고 페이지 생성일/`출고일` 중 하나라도 있는 거래처코드를 활동 집합으로 본다. 두 활동이 모두 없고 승인 DB 생성도 30일을 넘긴 `승인` 거래처를 월요일 실행 때 `장기미발주`로 바꾸며, 최근 활동이 생긴 기존 `장기미발주` 거래처는 매일 `승인`으로 복구한다(`tools/legacy-gas/거래처 발송 주문서/장기미발주 거래처 선별/Code.js:15-52,67-174`).
- 레거시 기간별 비밀번호 재설정 원본: 인증 DB 전체 페이지 중 현재값과 과거 1~4 이력이 모두 빈 페이지만 제외한다. 함수명 `rotatePasswordsMonthly`와 로그는 **월간 작업**이지만 코드·manifest에 날짜 판정·시간기반 trigger가 없어 정확한 실행일과 실제 주기는 저장 원본만으로 확인불가다. 실행 시 새 값을 만들지 않고 현재값을 과거1로, 과거1~4를 다음 이력으로 밀며 현재값을 비운다(`tools/legacy-gas/거래처 발송 주문서/기간별 비빌번호 재설정/Code.js:1-75`).
- 현행과 레거시의 범위 차이: 현행 후보는 주문·출고 활동이 아니라 마지막 로그인, 없으면 비밀번호 변경일을 기준으로 하고 상태도 `NEED_PW_INPUT`·`OK`·`LONG_UNUSED`만 포함한다(`PartnerApprovalService.java:64-76`). 따라서 화면·route·API 관점에서는 두 기능이 통합되어 있으나, 레거시 의미의 주문/출고 기반 장기미발주 선별과 인증 DB 전체 월간 로테이션을 그대로 구현한 것은 아니다.
- 실 DB 레거시 30일 장기미발주 대상: **0건**. `partner_auth_db` 읽기 전용 조회에서 승인/장기미발주 대응 활성 상태(`NEED_PW_INPUT`·`OK`·`LONG_UNUSED`)이면서 인증 레코드 생성 후 30일을 넘긴 필요조건 충족 거래처가 0건이었다. 주문 성공·출고 부재 조건을 더해도 집합은 늘 수 없으므로 최종 레거시 대상도 0건이다.
- 결함 2 fresh 실행: 복구 후 상태조회 유지와 복구 후 로그인·토큰 발급 두 기존 backend 회귀 테스트를 `--rerun-tasks`로 실행해 exit 0을 확인했다. 결함 2는 현재 재현되지 않는다.
- 결함 1 테스트 한계: 주문 앱 회귀 테스트는 현재 `node_modules` 부재로 `vitest is not recognized`에서 시작되지 않았다. 다만 테스트는 현행 HTML에 새 기준 문구가 있고 옛 `최종 주문일` 문구가 없음을 정확히 단언하며, 실제 HTML 원문이 이 두 조건과 일치한다. 정적 코드·실 DB 0영향 기준으로 결함 1도 현재 재현되지 않는다.
