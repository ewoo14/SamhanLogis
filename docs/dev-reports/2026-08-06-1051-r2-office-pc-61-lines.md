## 결론 먼저

R1과 같은 조건(line.is_deleted = false)으로 다시 세면 현재도 61행 / 7개 product UUID이다. 다만 전체 테이블을 product DB와 대조하면 soft-delete된 2행이 추가되어 63행 / 9개 UUID가 된다. R1의 7개 목록 자체는 비삭제 61행에서 그대로 재확인됐다.

61개 비삭제 행은 두 계열로 갈린다.

1. 계열 A — 6개 UUID, 60행: UUID v3 + created_by='system'이지만 테스트제품-% 및 2026-05-09가 아니다. 2026-06-20에 생성된 PartnerOrderSeeder의 6-SKU 결정적 개발 시드 주문이다. #1084가 아니라 새 갈래(파트너 주문 시더-카탈로그 세대 불일치)다.
2. 계열 B — 비삭제 1개 UUID, 1행: UUID v4 + created_by='qa-757' + QA-MODEL-A/QA 활성 품목 + 2026-07-07이다. 같은 QA-757 fixture의 soft-delete된 형제 2행까지 합치면 3 UUID/3행이다. QA797의 soft-deleted product row를 참조하는 #1085와는 표식과 DB 상태가 다르다. 새 갈래(QA-757 fixture 잔재, product row 자체 부재)로 분리한다.

#1086과 ③④에도 해당하지 않는다. 61행은 참조 UUID가 정상이라는 #1086의 유형이 아니며, 사무실 제품 DB에는 이 7개 snapshot model code가 단 하나도 없다. 계열 A의 model name은 후보 모델명이 아니라 10행씩 반복되는 고정 시드 품목이다.

### 재현 SQL

아래는 partner order DB의 전수 원문을 추출한 핵심 SQL이다. product DB 존재 여부는 별도 집합 대조로 확정했다.

~~~
SELECT
    pol.product_id::text,
    pol.id::text AS line_id,
    po.order_no,
    po.status AS order_status,
    po.is_deleted AS order_is_deleted,
    po.slip_publish_status,
    pol.is_deleted AS line_is_deleted,
    to_char(pol.created_at, 'YYYY-MM-DD HH24:MI:SS.US') AS line_created_at,
    pol.created_by AS line_created_by,
    pol.model_name,
    pol.product_name,
    pol.category_key,
    pol.quantity,
    pol.price_vat,
    pol.subtotal,
    pol.converted_quantity,
    pol.remark
FROM partner_order_lines pol
JOIN partner_orders po ON po.id = pol.partner_order_id
WHERE pol.product_id IS NOT NULL
  AND pol.product_id = ANY (ARRAY[
    '01949ab7-e922-35c6-b289-5337d867a0ee',
    '508ffc15-4ebe-363e-a395-389ba0d6b6a7',
    '51e16f88-98ce-359c-b4e5-c6641325c5bd',
    'a9d88f27-98af-3009-8e1f-3d9a390c41f4',
    'aa757c01-0000-4000-8000-000000009001',
    'aa757c02-0000-4000-8000-000000009002',
    'aa757c03-0000-4000-8000-000000009003',
    'ae339262-7ca9-3f7c-8418-4339e88b3466',
    'e35ae4a5-0505-36a1-bbf2-b2abea094b8a'
  ]::uuid[])
ORDER BY pol.product_id, po.order_no, pol.id;
~~~

### 5.2 그래도 되살리기가 더 위험한 경우

현재 product row가 없다는 이유만으로 6개 제품을 재생성하거나 61행을 현재 다른 제품 UUID에 relink하면 안 된다.

- 계열 A는 30개 주문/60라인이고 그중 30라인이 PUBLISHED, 21라인이 PENDING_RETRY다. 제품을 되살리면 과거 dev seed가 현재 catalog에 다시 나타나며 전표/재시도/품목 선택/재고조회 경로가 잘못 이어질 수 있다.
- AF20BX1NWAEAH-50은 snapshot에 (단종)이 명시돼 있다. 현행 제품으로 relink하면 snapshot 의미와 현재 catalog 의미가 섞인다.
- 계열 B의 QA 활성 품목을 복원하면 QA fixture가 실제 업무 품목처럼 보인다. 삭제된 QA-MODEL-B/C까지 복원하면 삭제 주문/완료삭제 fixture도 재노출된다.

판정: 현재 행을 그대로 두는 것보다 의미 확인 없이 UUID를 재생성하거나 임의의 활성 제품에 relink하는 것이 더 위험하다. 안전한 다음 행동은 별도 시더/fixture 정리 결정을 내리는 것이며, 이 라운드에서는 복원·삭제·수정하지 않는다.
