# PR #1097 / 이슈 #1096 — S3 fix

- 기준: `docs/dev-reports/2026-08-07-1096-sol-s2-reconvergence.md` 선행 검토
- 범위: D3′ 주문 인라인 복원 완전성 분모 수정
- 제약: git 명령 0회, DB SELECT/쓰기 0회, 컨테이너 재기동·재빌드 0회

## 결론

D3′를 수정했다. 주문 복원 분모는 모든 과거 삭제 라인이 아니라 헤더의 현재 삭제 작업과 동일한 `deletedBy + deletedAt`을 가진 삭제 라인으로 한정한다. 정상 수정 이력(`system-partner-order-update`)은 복원 대상에서 제외되며, 현재 삭제 작업의 라인을 하나도 식별하지 못하면 409를 유지한다.

S2 보고서의 실 데이터 표본에서 정상 복원이 잘못 차단되는 DRAFT 주문은 **3건**, 혼입된 과거 수정 삭제 라인은 **5개**였다. 이번 변경은 그 3건을 복원 가능 상태로 만들고, 과거 5개는 삭제 상태로 유지하는 계약을 고정한다.

D2′ 시더 플래그와 QA797 일반 복원 차단은 이번 라운드에 변경하지 않았다. 따라서 신규 full-seed 문서 170건의 명시적 재활성화와 QA797 3건의 일반 복원 차단은 후속 작업으로 남는다.

수정 전 구현은 과거 수정 라인까지 `deletedLineCount`에 넣어 409를 발생시켰다. 수정 후 같은 테스트와 RED-B fail-loud 테스트가 모두 통과했다.

## 2. 제거·이동·개명한 식별자 grep 전수

식별자를 제거·이동·개명한 항목은 **없다**. 기존 `findAllIncludingDeletedByPartnerOrderId` 조회 계약은 유지했고, 새 내부 식별자 `deletionBatchLines`만 추가했다.

변경 식별자 grep 결과:

```text
PartnerOrderDeleteService.java:90  deletedBy + deletedAt 작업 식별자 매칭
PartnerOrderDeleteService.java:114 findAllIncludingDeletedByPartnerOrderId
PartnerOrderDeleteService.java:121 deletedLineCount
PartnerOrderDeleteService.java:124 deletionBatchLines.isEmpty()
```

QA797/cleanup provenance 및 시더 플래그 grep도 확인했다. 이번 변경 파일에는 `QA797`, `PM-LIVE-QA`, `issue-1096-test-seed-cleanup` 식별자를 새로 도입하거나 삭제하지 않았다.
