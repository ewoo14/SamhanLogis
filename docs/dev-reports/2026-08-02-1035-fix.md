## 확인 2 — B-01 원인 확정 (수정 전)

- 실제 read-only 호출 원문은 리뷰 보고서의 확인 10에 기록된 결과를 재검증 근거로 삼았다.
- `/internal/inventory/warehouses/by-code?code=`는 inventory-service의 `WarehouseRepository.findByCode(code.trim())` exact 조회 경로다. 게이트웨이 비노출 문제가 아니며, internal token으로 inventory-service에 직접 도달했다.
- 운영 DB의 정상 창고 4개 코드는 inventory 코드 체계이고, slip-service 설정 map의 key 4개는 legacy 전표 코드 체계다. 두 체계는 일치하지 않는다.
- 실제 호출 결과: legacy 코드 4건은 모두 `404`, inventory 코드 4건은 모두 `200`이었다.
- 따라서 B-01 원인은 권한·포트·배포본이 아니라 **legacy 코드를 inventory 코드 조회 endpoint에 전달한 코드 체계/조회 축 오류**다. 설정 UUID가 정상이어도 PR 구현은 UUID를 사용하지 않고 legacy key로 조회한다.

## 확인 3 — 수정 전 데이터 흐름과 B-02 원인

- `WarehouseCodeMapper`의 `@PostConstruct`가 map 각 key에 대해 `findWarehouseByCode(legacyKey)`를 동기 호출한다.
- `WarehouseInternalClient`는 404뿐 아니라 5xx, 네트워크/타임아웃, token 누락, 파싱 오류를 모두 `Optional.empty()`로 축약한다.
- mapper는 이 `empty`를 실제 미실재와 동일한 `IllegalStateException`으로 변환해 Spring context 생성을 중단한다. retry나 지연 health check가 없어 창고 서비스가 늦게 떠도 이미 종료된 프로세스는 회복하지 못한다.

## 확인 7 — E·F·G 및 전체 suite 원문

### E. 오주입 방어

실행한 `WarehouseCodeMapperStartupValidationTest`에서 다음 두 테스트가 통과했다.

```text
치환되지_않은_placeholder도_UUID를_노출하지_않고_기동_실패한다
UUID가_명백히_미실재하면_기동을_막는다
```

placeholder는 inventory 조회 전에 `UUID.fromString`에서 거부되고, 미실재는 UUID endpoint의 `NOT_FOUND`로 거부된다. 예외 메시지에는 창고코드만 포함하고 UUID/placeholder 원문은 포함하지 않는다.

### F. DataSource / pool

- 이번 변경은 `dedicatedDataSourceTrio`와 DataSource/Hikari 설정을 수정하지 않았다.
- 전체 테스트 결과에 pool 고갈을 나타내는 `too many clients`, `connection is not available`, `SQLTransientConnectionException`, `Pool exhausted`가 없었고, 종료 시 Hikari pool shutdown 원문이 확인됐다.

### G. UUID 비공개

- 새 client의 UUID 조회 성공/실패 로그는 status와 일반화된 문구만 기록한다.
- mapper 기동 예외는 창고코드와 사람이 읽을 수 있는 원인만 기록한다.
- UUID/설정 UUID/응답 body를 로그나 예외에 전달하지 않는다.

## 확인 9 — A 실행 근거

- 수정 전 read-only 실 inventory endpoint 호출에서 운영 창고 4개가 모두 `200`으로 응답하는 원문은 확인 10의 `HQ-001`, `VH-001`, `CS-001`, `VR-001` 4건이다.
- 수정 후 `WarehouseValidationApplicationContextIT`는 production `app.publish.warehouse-code-map` 4개를 유지하고 validation을 true로 켠 실제 Spring context를 기동했다. 결과 원문은 확인 6의 `BUILD SUCCESSFUL in 51s`다.
- 이 검증은 warehouse row를 만들지 않았고, 실제 row의 UUID를 테스트에 복사해 seed하지 않았다. Spring lifecycle에서 UUID endpoint 결과를 외부 client mock으로 격리해 정상 `FOUND` 경로를 확인한 것이다.
- 실 DB 4개를 대상으로 한 HTTP read-only 도달성은 확인 10 원문으로, Spring context lifecycle 통과는 확인 6 원문으로 각각 분리해 기록했다.
