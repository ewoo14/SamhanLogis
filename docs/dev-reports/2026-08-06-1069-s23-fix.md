# #1069 S23 fix 보고서 — BUNDLE 전환 안내 전달

## 결론

S22 F1을 수정했다. slip-service가 만든 BUNDLE 업무 안내를 partner-order-service의 단건·병합 RPC 경계에서 보존하고, 단건 화면은 400 업무 오류를 일반 재시도 문구로 덮지 않도록 했다. 병합 화면은 허용된 BUNDLE 안내만 표시하며 임의의 400 본문은 투과하지 않는다.

재고 예약 보상, `convertedQuantity` 성공 후 누적, 경합 수렴, SINGLE 발행 계약은 변경하지 않았다. Docker·DB 쓰기·git 명령은 수행하지 않았다.

## RED-first 원문

수정 전 신규 서비스 계약 테스트 2건이 다음 상태로 실패했다.

```text
SlipServiceClientTest > publishFromPartnerOrder_400의_업무안내를_원문으로_보존한다() FAILED
SlipServiceClientTest > publishFromOrdersMerge_400의_업무안내를_원문으로_보존한다() FAILED
```

실패 원인은 두 경로 모두 예외 메시지가 `slip-service 4xx: 400 BAD_REQUEST`로 치환되어 BUNDLE 안내가 사라진 것이었다. 단건 화면 RED는 400을 일반 실패 문구로 덮어 `구성품으로 전개해 주세요.`가 표시되지 않는 것이었다.

## 수정 내용

- `SlipServiceClient`의 단건·병합 기타 4xx 분기가 응답 본문을 읽고, 정해진 BUNDLE 조치 문구만 보존한다.
- 허용 문구가 아닌 임의의 400 본문은 `slip-service 4xx 오류`로 제한해 내부 식별자·HTTP 상태 문자열·민감 본문을 사용자에게 노출하지 않는다.
- `SalesPartnerOrderDetailPage`는 400 응답의 허용된 BUNDLE 안내를 `role="alert"`에 표시한다.
- `MergeConvertDialog`는 허용된 BUNDLE 안내만 표시하고 그 외 400은 기존 일반 실패 안내를 유지한다.

| 전표 부분/라인 수정 | `SlipUpdateService` | 계보 라인만 교체, 부모 ID 직접 추가 거부 | 차단 |

| 전표 revision 복원 | `SlipRevisionService.restore()` → `Slip.restoreFromSnapshot()` | 스냅샷 구성품만 복원 | 부모 신규 저장 없음 |
| soft-delete 전표 복원 | `SlipRestoreService.restore()` | 삭제된 기존 라인만 복원 | 부모 신규 저장 없음 |

outbox와 견적 revision 복원 경로를 표에 보완했다. 두 경로 모두 `slip_lines.product_id`에 새 BUNDLE 부모를 저장하는 우회가 없다.

## 검증

- `:services:partner-order-service:test --tests '*SlipServiceClientTest*'`: **통과**
- `SalesPartnerOrderDetailPage.coedit.test.tsx` + `MergeConvertDialog.test.tsx`: **29 tests 통과**
- 단건 오류 배너: `role="alert"`에서 구성품 전개 안내 확인
- 병합 오류 처리: 기존 409/권한/일반 실패 분기 유지, BUNDLE 허용 문구 필터 적용

미실행: 사용자가 금지한 전체 게이트, Docker, DB 쓰기, git 명령. 실 DB SINGLE 기준선은 읽기/쓰기 검증을 수행하지 않아 새로 주장하지 않는다.
