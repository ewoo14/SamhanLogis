## 5. 불변식 (구현자에게 — 수단 미지시)

> **Q-1** 제품이 고르는 부속 모델과 산출 금액이 **현재 라이브 레거시 GAS 와 같다** — 차이 ①②에 대해.
> **Q-2** **두 앱이 같은 답을 낸다** — `order-app` 과 `estimate-app`.
> **Q-3** 품목 코드는 **카탈로그에 실재하는 것을 참조**하고, 빗나갔을 때 **조용히 사라지지 않는다**.
> **Q-4** 기준일은 **환경마다 사람이 기억해야 하는 값이 아니다.** 그리고 **사용자가 관리 화면에서 손댄 값을 자동 갱신이 덮지 않는다**.

🔑 **Q-3 가 핵심입니다.** GHP 건이 정확히 그 형태였습니다 — `find()` 가 `undefined` 를 돌려주고 `if(!row) return;` 으로 에러 없이 스킵돼 6,710,000원 품목이 사라졌습니다. `AR-EH05` 로 바꿀 때 **카탈로그에 실재하는지 먼저 확인**해야 하고, 빗나가면 드러나야 합니다.

### 8.3 구현 내용

- `clients/web/order-app/index.html`의 상업멀티 360 리모컨을 `AR-EH05`로 변경했다. estimate-app의 기존 `AR-EH05` 규칙은 수정하지 않았다.
- 두 앱의 `chooseBaseModel()`에서 `isCoolTop` 30HP를 `방진가대S2중` 목록으로 이동하고 `방진가대S2대` 목록에서는 제거했다. `isStd` 30HP 규칙은 변경하지 않았다.
- 두 앱에 `requireCommCatalogRow_()`를 추가했다. 이번 슬라이스에서 새로 참조하는 `AR-EH05`·`방진가대S2중`이 실제 산출 target인데 카탈로그에 없으면 모델 코드와 원인을 포함한 오류를 낸다. 기존 synthetic golden에 포함되지 않은 범위 밖 0/누락 target은 이번 슬라이스에서 동작을 확대하지 않았다.
- helper는 `recomputeCommDerived()` 내부 지역 함수로 두어 실제 브라우저 계산과 기존 VM harness의 함수 추출 경계를 동일하게 유지했다. 기존 quantity boundary 파일의 최종 diff는 없다.
- 라이브 거래처 발송 주문서 oracle의 `AR-EH05`를 기준으로 `C-01-CIRCLE-360`, `C-01-SQUARE-360` order golden을 갱신했다. 제품 출력 복사가 oracle이 아니다.
