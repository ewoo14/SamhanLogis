# PR #1131 R2 — BUNDLE 전개 계보가 PUT 경계에서 조용히 소실되는 결함

## 판정

**도달 결함 1건. 직전 HTTP 400 표면을 FE 전개로 피했지만 end-to-end 계약은 폐쇄되지 않았다.**

사용자가 판매전표 수정 화면의 정상 선택지에서 BUNDLE을 고르면 HEAD 화면은 구성품 여러 행을 만든다. FE PUT에도 `parentSetModel`, `setHead`, `bundleParentProductId`, `bundleParentUnitPrice`, `setOptions`가 보인다. 그러나 매출 수정 BE DTO에는 이 필드가 없고 서비스도 읽지 않는다. Jackson은 초과 JSON 필드를 버리고, `lineId:null`인 신규 구성품은 평면 `SlipLine`으로 저장된다.

따라서 예상되는 실사용 결과는 다음과 같다.

1. BUNDLE 부모 원본이 payload에서 빠져 종전 `HTTP 400 INVALID_INPUT`은 피한다.
2. 기존 행 수정과 신규 구성품 행 자체는 HTTP 200으로 저장될 수 있다.
3. 사용자가 선택한 “한 세트의 구성품”이라는 계보는 조용히 사라진다: 재조회 시 `parentSetModel=null`, `setHead=false`.
4. 이후 화면의 세트 그룹 표시·세트 단위 옵션 문맥·부모 가격기억 제외 규칙이 작동할 근거가 없다.

현재 라이브 stack은 `samhan-product-service`가 종료 상태라 실제 PUT까지 도달하지 못했다. 이 환경 실패를 결함 재현으로 둔갑시키지 않는다. 상세 원문은 아래 “라이브 QA”에 분리한다.

## 좌표와 데이터 흐름

### FE — 계보를 생성하고 PUT에 싣는다

- `clients/desktop/src/renderer/routes/SlipDetailPage.tsx:1275-1351`
  - `expandSalesBundleProductSelection`이 구성품마다 `parentSetModel`, `setHead`, `bundleParentProductId`, `bundleParentUnitPrice`를 만든다.
  - 신규 전개행은 `lineId:null`이다.
- `clients/desktop/src/renderer/routes/SlipDetailPage.tsx:1210-1236`
  - `buildDetailLinePayload`가 계보 필드를 JSON payload에 싣는다.
- `clients/desktop/src/renderer/routes/SlipDetailPage.tsx:5706-5721`
  - 실제 수정 화면 BUNDLE 선택이 위 전개 함수를 호출한다.

### BE — wire DTO에서 계보를 받지 않고 신규행을 평면화한다

- `services/slip-service/src/main/java/com/samhanair/logis/slip/web/dto/SlipUpdateRequest.java:60-103`
  - `LineRequest` 필드는 `productId/productName/modelName/specification/quantity/unitPrice/note/lineId`와 VAT 3필드뿐이다.
  - FE가 보내는 `parentSetModel/setHead/bundleParentProductId/bundleParentUnitPrice/setOptions`가 계약에 없다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/service/SalesSlipUpdateService.java:87-110`
  - product lookup 후 `toLine`으로 전체 교체 라인을 만들고 기존 계보 resolver를 적용한다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/service/SalesSlipUpdateService.java:233-260`
  - `toLine`은 `SlipLine.create*`만 호출하고 신규 요청 계보를 부여하지 않는다.
- `services/slip-service/src/main/java/com/samhanair/logis/slip/service/BundleLineageResolver.java:14-29,74-90,149-156`
  - resolver는 **기존 영속 lineId**로 캡처한 계보만 복원한다.
  - 신규 전개행의 `lineId:null`은 명시적으로 복원 대상이 아니다.

즉, FE 테스트가 “payload에 계보가 있다”고 단정해도 BE wire 계약과 영속 결과는 검증하지 못한다.

## 불변식

수정 화면에서 선택 가능한 BUNDLE을 구성품으로 전개해 저장하면 다음을 동시에 만족해야 한다.

- 부모 BUNDLE 원본은 PUT 라인에 남지 않는다.
- 구성품 수·productId·수량·단가는 동일한 `BundleExpander` 결과와 일치한다.
- 모든 구성품은 같은 `parentSetModel`을 영속하고 정확히 1행만 `setHead=true`이다.
- 신규 구성품은 `lineId:null`, 기존 행은 기존 서버 `lineId`를 보존한다.
- HTTP 2xx만으로 성공 판정하지 않는다. 저장 후 상세 API와 DB가 위 계보를 왕복해야 한다.
- SINGLE 신규행/품목 교체는 `parentSetModel=null`, `setHead=false`인 평면행이어야 한다.

## 양방향 RED

### RED-A — 수정 화면 신규 BUNDLE의 영속 계보

1. 기존 활성 SINGLE 1행이 있는 throwaway OUTBOUND DRAFT를 만든다.
2. 직접 수정의 trailing draft에서 활성 BUNDLE `AC023CS1DBC1SY`를 선택한다.
3. 전개 완료 전 저장 버튼이 disabled이고, 전개 완료 후 사용자의 한 번의 저장 클릭이 PUT 1회로 처리되는지 기록한다.
4. 두 피어에서 구성품 행 수·순서·수량이 수렴하는지 확인한다.
5. PUT에서 부모 BUNDLE 원본 부재, 기존행 기존 `lineId`, 신규 구성품 `lineId:null`을 단정한다.
6. HTTP 200 후 GET/DB에서 구성품 7행 모두 `parent_set_model='AC023CS1DBC1SY'`, 정확히 1행 `set_head=true`를 단정한다.
7. 수정 화면을 다시 열어 같은 세트 그룹으로 렌더되는지 확인한다.

**현재 코드 RED 표적:** 6번. DTO와 `toLine`이 신규 계보를 받지 않으므로 전개 구성품이 `parent_set_model NULL / set_head=false`로 평면화된다.

### RED-B — SINGLE 기존 계약 무회귀

구체 표적은 `ACL-KORGHP07` 기존행 + `ACM-A202DN` 신규행이다.

1. throwaway OUTBOUND DRAFT의 기존 `ACL-KORGHP07` 행 서버 `lineId`를 고정한다.
2. 기존행 수량을 `1→2`로 수정한다.
3. trailing draft에서 활성 SINGLE `ACM-A202DN`을 선택한다.
4. PUT에서 기존행은 고정 `lineId`, 신규 SINGLE은 `lineId:null`인지 단정한다.
5. HTTP 200 후 GET/DB가 두 행과 수량 2를 보존하는지 단정한다.
6. 신규 SINGLE은 `parent_set_model NULL`, `set_head=false`여야 한다.

이 RED-B는 BUNDLE 계보 wire 계약을 추가하면서 평면 SINGLE을 거짓 세트 구성품으로 만들지 않는 구체 방어선이다.

## 수정 지시

1. `SlipUpdateRequest.LineRequest`에 수정 화면이 실제 보내는 계보 필드를 명시적으로 추가한다.
2. `SalesSlipUpdateService`가 `lineId:null` 신규행의 계보를 영속할 수 있게 하되, 요청값을 무조건 신뢰하지 않는다.
3. `bundleParentProductId + parentSetModel + setOptions`로 product-service `BundleExpander` 결과를 재검증하거나 서버가 다시 전개해, 요청 구성품 집합·수량·`setHead` 1건을 검증한 뒤 계보를 부여한다.
4. 기존 `lineId` 행의 계보는 현재 `BundleLineageResolver`의 품목 동일성 게이트를 유지한다.
5. FE payload 테스트만으로 닫지 말고 controller JSON 역직렬화 → service → repository/GET 왕복 IT를 추가한다.

단순히 DTO 필드만 열고 `assignBundleComponent(request.parentSetModel, request.setHead)`를 호출하면 임의 SINGLE을 세트 구성품으로 위조할 수 있으므로 금지한다.

## #1132 충돌 가능성

별도 worktree `w1132`, 커밋 `9517a5ddf`는 `BundleExpander`에서 repository 결과를 먼저 `isDefault=true`로 필터한다.

- 대표 `AC023CS1DBC1SY`: 활성 구성품 7, 기본 구성품 4. #1132 병합 후 수정 화면 전개 결과도 7행→4행으로 바뀐다. 이 PR은 같은 `/slips/expand-line`을 호출하므로 별도 중복 전개는 없고, 결과 수 감소 자체는 공통 엔진 계약에 따라 수렴한다.
- 현재 활성 BUNDLE 276개 중 **72개는 활성 구성품은 있으나 `is_default=true`가 0개**다. #1132 병합 후 이들은 빈 배열을 반환하고, 이 PR의 `components.length === 0` 분기에서 `세트 구성품을 찾을 수 없습니다.`로 끝난다. 활성·선택 가능 BUNDLE 72개가 사용자 경로에서 전개 불가가 되는 구체 충돌이다.
- #1132는 비기본 패널/리모컨도 `pickedFilter` 전에 제거하므로 옵션 선택 확장성과도 충돌 여지가 있다. 본 PR은 현재 수정 화면에서 `setOptions`를 전개 호출에 전달하지 않아 기본 전개만 사용하지만, wire 계약을 고칠 때 이 비대칭을 함께 확대하지 말아야 한다.

## 반대급부

- 서버 재검증은 product-service 호출과 구성품 비교 비용을 추가한다. 그러나 클라이언트가 보낸 계보를 무검증 영속하면 임의 품목을 세트 구성품으로 위조하고 가격기억을 누락시킬 수 있다.
- 서버 재전개 결과가 #1132의 default-only 정책과 함께 바뀌므로, 배포 순서가 어긋나면 FE가 본 구성품 집합과 BE가 검증하는 집합이 달라질 수 있다. PR #1131과 #1132의 slip/product 배포 순서를 한 트랙에서 고정해야 한다.
- 기존 400을 없애는 것만 성공 기준으로 두면 이번처럼 “저장은 됐지만 사용자가 만든 세트 계보가 사라진” 더 조용한 손실을 허용한다. 성공 기준은 반드시 GET/DB 왕복이다.
