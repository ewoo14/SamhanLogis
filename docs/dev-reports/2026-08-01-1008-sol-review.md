# 2026-08-01 #1008 일마감 할인율 판정 기능 회귀 검토

## 확인 1 — 범위와 선행 문서

- 검토 범위는 **전역DC 반영 변경 때문에 기존 정상 판정이 불일치가 되거나 일마감 전체가 중단되는지**로 한정한다.
- 코드 수정, git 명령, 공유 Docker 재빌드·재기동, 실 DB 쓰기를 하지 않는다. 결과 파일은 이 보고서 하나만 남긴다.
- `2026-08-01-1008-daily-closing-recon.md`, `2026-08-01-1008-slice1-implementation.md`, `2026-08-01-1008-slice1-fix.md`를 읽었다.
- 선행 구현 보고서는 실 일마감 대상 13라인 중 멀티 판정 도달이 0라인이라 판정 변화가 양방향 0건이라고 기록한다. 선행 fix 보고서는 미격리 `dc-config-service` 호출 때문에 일마감 API가 `500 INTERNAL_ERROR`로 실패한 원문을 기록한다. 두 주장 모두 이번 검토에서 독립 재현 대상으로 둔다.

## 확인 2 — 새 의존의 실제 호출 범위

- `dc-config-service` 호출은 일마감 실행 `POST /accounting/daily-closings`에 들어가지 않는다. 실행 경로인 `DailyClosingService.close()`는 원천 집계 → snapshot 저장·재계산 → lock만 수행한다.
- 새 호출은 상세 미리보기 `GET /accounting/closings/daily`의 `MonthEndCloseService.revalidateProductLines()`에 있다.
- 상세 대상 품목 그룹이 하나라도 있으면, 멀티 여부·고정DC 존재 여부와 무관하게 서로 다른 모든 거래처코드에 대해 `PartnerDcConfigClient.findByPartnerCode()`를 먼저 호출한다. 따라서 전역DC가 필요 없는 정상 일반품목/고정DC 품목도 서비스 장애의 영향을 받는다.
- 거래처코드가 null/공백이어도 집계 key에 들어가며 client는 즉시 `NOT_FOUND`를 반환하므로 외부 HTTP는 하지 않는다.

## 확인 3 — `MISSING_GLOBAL_DISCOUNT` API·화면 계약

- API DTO는 `verified=null`, `expectedRate=null`, `revalidationStatus="MISSING_GLOBAL_DISCOUNT"`를 그대로 직렬화할 수 있다. 이는 불일치(`verified=false`)가 아니라 판정불가다.
- 화면의 `DailyProductRevalidationStatus` union과 `REVALIDATION_STATUS_LABEL`에는 `MISSING_GLOBAL_DISCOUNT`가 없다. 실제 응답이 오면 확인 열에는 중립 `판정불가` 배지가 보이지만 사유 열은 label lookup 결과가 `undefined`라 빈칸으로 렌더된다.
- 이 상세 표는 read-only 미리보기다. `verified`나 `revalidationStatus`를 검사해 일마감 실행 버튼을 막는 로직은 없고, 실행 POST도 재검증을 호출하지 않는다. 따라서 이 상태 자체는 마감을 막지 않지만 사용자는 전역DC 미조회라는 원인을 화면에서 알 수 없다.

## 확인 7 — 기동 순서·서킷브레이커·재시도·타임아웃

- 기동 순서: local/prod compose 모두 `accounting-service`의 공통 `depends_on`에 PostgreSQL/Redis/RabbitMQ/Eureka/API gateway(환경별 일부 차이)만 있고 `dc-config-service`는 없다. 두 서비스는 서로 독립 기동하고 Eureka 등록 이후에만 이름 해소가 가능하다. accounting이 먼저 healthy가 될 수 있다.
- 서킷브레이커: 없다.
- 재시도: 없다. `PartnerDcConfigClient`는 `RestClient.retrieve()`를 한 번 호출하며 retry annotation/template이 없다. runtimeClasspath에도 `resilience4j`, Spring Cloud circuit breaker, `spring-retry`가 없고 loadbalancer만 있다.
- 타임아웃: 이 client와 공용 `loadBalancedRestClientBuilder()`에 connect/read timeout 설정이 없다. 따라서 production client 자체의 명시적 상한은 없고 하부 HTTP/OS 또는 상위 요청 제한에 의존한다. 이번 timeout 재현은 일회성 하네스에서 read timeout 100ms를 강제로 주어 예외 전파 결과를 확인한 것이다.

runtimeClasspath 원문:

```text
|    \--- org.springframework.cloud:spring-cloud-starter-loadbalancer:4.1.4
|         +--- org.springframework.cloud:spring-cloud-loadbalancer:4.1.4
+--- org.springframework.cloud:spring-cloud-starter-loadbalancer -> 4.1.4 (*)
```

판정: 기동 직후 아직 dc-config가 등록되지 않았거나 실행 중 일시 장애가 나면 상세는 즉시 500으로 실패한다. retry/circuit breaker/fallback이 없고, 무응답에는 명시적 timeout조차 없어 상세 요청이 장시간 멈출 수 있다.

## 확인 8 — 판정 산식과 허용 오차

산식은 그대로다.

```text
VAT 포함 실단가 = (공급가액 + 세액) / 수량       [scale 10, HALF_UP]
실제 할인율 = round_HALF_UP((1 - VAT 포함 실단가 / 출고가) × 100)
기대 할인율 = round_HALF_UP(고정DC percent 또는 전역DC ratio × 100)
판정 = 실제 정수 % == 기대 정수 %
```

- `MonthEndCloseService.actualUnitPrice()`가 공급가액+세액을 수량으로 나눈다.
- `DiscountRevalidator.actualRate()`가 `1 - 실단가/출고가`에 100을 곱해 정수 `HALF_UP`한다.
- 비교는 `Integer.equals()`뿐이며 ±1%p 같은 별도 허용 오차가 없다. 즉 각각 정수 %로 반올림한 뒤 **0%p 완전일치**다.
- 이번 변경은 `expectedRate()`의 고정DC 다음 입력만 전역DC로 바꿨고 실제율 산식·비교 함수는 건드리지 않았다.

fresh 단위 테스트 원문:

```text
<testsuite name="com.samhanair.logis.accounting.service.DiscountRevalidatorTest" tests="20" skipped="0" failures="0" errors="0" ...>

BUILD SUCCESSFUL in 42s
21 actionable tasks: 21 executed
```

경계 재현도 `실단가 54,500 / 출고가 100,000` → 원시 45.5% → 정수 46%, 기대 46%로 통과하며, 실제 49% 대 기대 50%는 불일치로 통과하지 않는다.

## 최종 판정 — BLOCK

### 차단 결함 1건

**B-01 — dc-config-service 일시 장애가 정상 일마감 상세 전체를 500 또는 장기 대기로 만든다.**

- 5xx·서비스 다운·timeout을 각각 재현했고 세 경우 모두 `GET /accounting/closings/daily` 전체가 500이었다.
- 멀티/전역DC가 실제로 필요하지 않고 고정DC가 있는 정상 품목도 먼저 거래처별 client를 호출하므로 함께 실패한다.
- retry·서킷브레이커·fallback이 없고 production 명시 timeout도 없다.
- 일마감 실행 POST와 잠금은 별도 경로라 계속 동작하지만, 화면이 기본으로 자동 조회하는 정상 상세가 통째로 멈춘다. “정상이던 동작이 새 의존 때문에 멈추는가” 기준에서 차단한다.

### 비차단 표시 결손 1건

**N-01 — `MISSING_GLOBAL_DISCOUNT` 사유가 화면에서 빈칸이다.**

- API는 200 + `verified=null` + `MISSING_GLOBAL_DISCOUNT`로 정상 응답한다.
- 화면은 중립 `판정불가`를 표시해 불일치로 오인시키거나 마감 실행을 막지는 않는다.
- 다만 FE union/label 누락으로 사유가 비어 원인을 알 수 없다.

### 나머지 결론

- 실 데이터 판정 반전: 일치→불일치 0라인, 불일치→일치 0라인. 변경이 무해해서가 아니라 현재 멀티 대상 데이터가 0라인이기 때문이다.
- 거래처 미식별: 거래처코드 없음 11전표/12라인, 코드가 있으나 dc-config 미존재 1전표/1라인. 현재 데이터에서는 모두 멀티 분기 전 다른 판정으로 끝나 판정 반전은 없다.
- 산식과 허용 오차: VAT 포함 실단가 기반 정수 % HALF_UP, 0%p 완전일치가 유지된다.
- 임시 외부 테스트 소스와 임시 UI 테스트는 삭제했다. Node 컨테이너는 `--rm`으로 종료됐고 Testcontainers PostgreSQL도 JVM 종료와 함께 제거됐다. 공유 Docker 스택 재빌드·재기동과 실 DB 쓰기는 하지 않았다.
