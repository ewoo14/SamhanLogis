## 확인 3 — 재검증 예외·경보·스레드/커넥션 도달성

실행:

- 주기는 기본 initial 30초, 각 실행 완료 후 fixed delay 30초다. 별도 환경 override는 application 설정에 없다.
- 반복 스케줄 작업의 unchecked 예외는 Spring 기본 handler가 ERROR stack trace로 기록하고 suppress한다. 따라서 재검증 실패가 프로세스를 죽이지는 않으며 다음 fixed-delay 실행은 계속 예약된다.
- `NOT_FOUND`·대응 불일치를 발견해도 actuator health, readiness, metric, 별도 경보 상태에는 반영하지 않는다. 도달 가능한 외부 신호는 ERROR 로그뿐이다. 로그 수집·알림 규칙은 이 service 범위에서 연결된 것이 검색되지 않았다.
- 성공한 매핑은 보류 집합에서 제거된다. 모든 보류가 제거되면 이후 scheduler는 즉시 return한다. 중간 매핑에서 예외가 나면 그 뒤 매핑은 해당 회차에 도달하지 못하고, 보류 집합은 남아 다음 회차에 다시 시도한다.
- `SimpleClientHttpRequestFactory`는 별도 커넥션 풀을 사용하지 않는다. 재검증 메서드도 동기화된 단일 fixed-delay 작업이고 요청을 직렬 실행하므로 매 회차마다 worker/connection 수가 누적되는 코드 경로는 없다.
- 반면 별도 scheduler pool 설정이 없어 기본 scheduler 자원을 공유한다. 보류가 있는 동안 네 매핑 전체를 검사하며 정상 매핑당 두 HTTP 요청을 직렬 수행한다. 최악 read-timeout 기준 한 회차가 최대 약 24초를 점유할 수 있어 같은 scheduler의 다른 작업을 지연시킬 수 있지만, 새 스레드를 계속 생성하는 누수는 아니다.

## 확인 9 — timeout 실측과 느린 환경 도달성

실행 중 inventory-service에 대해 식별자 endpoint와 실제 inventory 창고코드 endpoint를 각각 80회 읽기 호출했다.

```text

endpoint=actualCode samples=80 status200=80 minMs=11 avgMs=12.8 p95Ms=15 maxMs=18
```

- 현재 warm 공유 환경에서는 connect 2초/read 3초보다 충분히 짧아 timeout 오분류가 재현되지 않았다.
- CI·cold start·의도적 지연 주입은 실행하지 않아 “2초/3초가 모든 느린 정상 환경에 충분하다”의 도달성은 0이다.
- production 분기는 식별자 조회 timeout은 `UNAVAILABLE`로 보류하지만, 뒤이은 코드 조회 timeout/5xx도 `Optional.empty`로 축약해 대응 불일치와 같은 기동 예외로 처리한다. 따라서 코드 조회만 3초를 넘는 정상 지연은 `UNAVAILABLE` 오분류가 아니라 더 강한 **기동 실패**로 수렴한다. 실제 지연 주입 실행 도달성은 0이지만 분기 자체는 B-06의 실제 404 기동 실패와 동일하다.

## 결함 B-07 — 재검증이 불일치를 발견해도 health·업무 사용 상태가 바뀌지 않음

① 실 사용자 경로 재현 여부: **production 제어 흐름 도달, scheduler의 NOT_FOUND/불일치 전환 실행은 0.** 실제 scheduler 재호출과 context 생존은 확인 8에서 실행했고, 실패 handler와 상태 소비자는 코드·사용 Spring bytecode로 확인했다.

② 재현 명령·출력 원문:

```text

```

production 상태 흐름:

③ 영향 범위:

- 성공 시에만 보류 집합에서 제거되지만, 이 집합 자체는 `resolve()` 또는 health가 소비하지 않으므로 성공 전후 사용자 요청 동작은 동일하다.

## 최종 판정 — BLOCK

- **B-06:** 실 DB 정상 4개와 환경변수 4개를 넣은 PR head Spring boot가 코드 `00003`에서 실제 실패했다. 네 legacy 코드 역조회가 모두 404이므로 정상 기동 불가는 전 매핑 공통이다.
- **B-07:** 장애 중 기동한 뒤 재검증이 불일치를 발견해도 ERROR 로그 외 운영 상태와 업무 사용 상태가 바뀌지 않는다.
- timeout은 현재 warm 환경 160회에서 최대 58ms라 2초/3초 초과가 재현되지는 않았다. 다만 코드 역조회 timeout/5xx는 보류가 아니라 기동 실패로 처리되는 별도 도달 경로가 남는다.
- 주기 재검증은 실제 scheduler에서 실행됐고, 계속 `UNAVAILABLE`인 경우 서비스를 죽이지 않았다. 전용 client는 별도 connection pool을 쓰지 않고 single scheduler에서 직렬 실행하므로 pool/스레드 누수는 재현되지 않았다.
- 숫자는 fresh 전체 suite 두 번 모두 `1,548/실패 0/오류 0/skip 0`으로 재현됐다. 직전 16건 보고는 이번에 재현되지 않았으며 현재 head suite 결론에서 철회한다.

- 공유 Docker image를 PR head로 재빌드·재기동하지 않았다. 대신 DB write를 끈 별도 로컬 head Spring process로 실 DB·실 inventory boot를 실행했다.
