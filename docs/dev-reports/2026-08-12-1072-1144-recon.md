## 가. 이미 구현된 것 / 남은 것

**이미 구현된 것부터 센 결과:** 회계 매출·매입전표의 목록·외부 작성 폼·DRAFT 생성·POSTED 상태 전이는 이미 있다. #1148에서 VAT 포함 금액 표시 중복가산을 고쳤고, #1145에서 회계전표 PageCode/CREATE 권한을 정렬했다. 매출·매입전표에는 공급가액·부가세액·총금액과 세금계산서 연결 컬럼이 있고, POSTED 매출·매입전표를 묶어 세금계산서로 만드는 경로도 있다. #1172는 판매전표의 R22 원장 기준 전잔·후잔, `journalNo == slipNo` exact dedup, POSTED+REVERSED 상쇄를 이미 구현했다. #1168·#1169·#1170은 각각 영업수수료 정산의 그룹웨어 참조, 확정 취소, REST+화면+권한을 구현했지만 **영업수수료 정산 도메인**이므로 #1144의 판매/구매 회계전표 생성·연결을 구현한 것으로 세지 않는다.

**남은 것:** #1072의 전 목록 확정, 이카운트 chart 적재/정본화, 앱 생성·조회 경로 전환, 현재 실 DB의 `110` 99라인 + `401` 42라인 = **확정 후보 141라인** 정규화, SYSTEM 시드 트리 정리가 전부 남아 있다. 8코드 후속 범위의 `201` 3라인·`210` 1라인과 그 밖의 사용 계정은 전 목록 매핑 결과에 따라 추가될 수 있다. #1144에서는 원 판매/구매전표 상세의 단건 생성·역방향 연결 표시, N건 선택→N개 회계전표 생성, 일마감 생성·연결, 회계전표 POST 분개, INBOUND 채무 문서원장, 연결되지 않은 세금계산서의 메뉴/발행 차단, VOID/재생성 공식 경로, 사용자용 출금보고서, 출금→보고서→거래처/채무 반영, 입출금내역 계좌·카드·대출 3개 메뉴가 남아 있다.

실 DB 표본은 활성 매출·매입 회계전표가 각각 **0건**, 세금계산서 19건(ISSUED 12·DRAFT 4·CANCELLED 3), 사용자용 출금보고서 원천인 `cash_disbursements` 0건, 입출금 거래 316건(그중 출금 151건)이다. 코드 존재와 실사용 완주를 구분해야 한다.

## 나. 개발책임자 결정이 필요한 항목 (있으면 선택지와 근거)

1. **결정 C 자체는 재결정 대상이 아니다.** 이카운트 체계가 정본이고, 3코드만 먼저 바꾸지 않으며 전 목록을 먼저 확정한다는 결정이 이미 #1072 본문·댓글에 있다. 현재 이 PC에는 원본 `계정상세내역-Excel다운로드.csv`가 없고 `staging.ecount_account_raw`·`ecount_account_map`도 0건이므로, 지금 새 선택을 요구할 단계가 아니라 원본 확보→전 목록 대조표 작성→개발책임자 확인 순서다. `(a) 전 목록 확인 후 진행`이 기존 확정안이며, `(b) 1089/4019/2519만 선전환`은 댓글에서 명시적으로 금지됐다.
2. **회계전표 POST와 세금계산서 분개의 책임:** `(a) 회계전표 POST가 채권/채무·VAT 분개를 만들고 세금계산서는 연결/발행만 담당` / `(b) 현행처럼 세금계산서 발행이 매출 분개 원인` / `(c) 둘 다 만들되 source dedup`. **(a) 권고.** 명세는 회계전표 연결의 이유를 세금계산서와 다른 회계메뉴 확인으로 분리했고, 현재 회계전표 POST는 상태만 바꾸는 반면 독립 세금계산서 발행은 110/255/401 분개를 만들어 인과가 뒤집혀 있다. (c)는 이중계상 위험이 가장 크다. 정확한 계정코드는 #1072 전 목록 확정 뒤 결정해야 한다.
3. **규칙 8의 원장 표면/시점:** `(a) 거래처 문서원장은 판매·구매전표 즉시, 채권채무 현황·총계정원장은 회계전표 POST 후` / `(b) 문서원장+채권채무 현황 즉시, 총계정원장 POST 후` / `(c) 셋 모두 즉시`. **(a) 권고.** 기존 코드 주석은 거래처 원장을 거래 사실 문서, 총계정원장을 POSTED/REVERSED journal 원장으로 정의한다. (c)는 분개 없는 provisional 행을 총계정원장에 넣어 대차/감사 계약을 바꾼다.
4. **외부 일괄의 “복수 생성”:** `(a) 원천 N건→회계전표 N건` / `(b) 원천 N건→회계전표 1건 합산`. **(a) 권고.** 원문은 “선택 후 복수 생성 가능”이고, 현재 폼은 여러 원천을 첫 품목 한 라인으로 합쳐 1개만 생성해 품목 구분을 잃는다.
5. **금액 변경 후 “삭제 후 재생성”:** `(a) POSTED 회계전표를 VOIDED+역분개 후 새 전표 생성·재연결` / `(b) soft-delete만 하고 재생성` / `(c) hard delete`. **(a) 권고.** BaseEntity/감사/회계 무결성 정책상 hard delete는 금지이며, 원 분개를 UPDATE/삭제하면 잔액과 감사 추적이 흔들린다. 도메인에는 VOIDED 전이가 있지만 호출 API가 없다.
6. **출금보고서 회계 처리:** 상대 계정은 `(a) 회계담당자가 선택하고 201/210 등 채무 계정일 때만 채무 소멸` / `(b) 모든 출금을 채무 지급으로 고정`; 생성 시점은 `(a) DRAFT 확인 후 확정` / `(b) 통장 선택 즉시 확정`. 각각 **상대 계정 선택 + DRAFT 확인 권고.** 카드비용·자산취득·대출상환을 전부 채무 지급으로 보면 원장이 틀어진다. 자기 회사 플래그는 이미 “필요 없음”으로 결정됐고 일반 거래처 `(주)삼한공조시스템(2148720659)`을 선택하면 된다.

## 다. 첫 슬라이스 한 문단

**첫 슬라이스는 #1072만 다룬다.** 이카운트 `계정상세내역` 원본을 확보해 현행 8코드 화이트리스트와 모든 앱 생성·조회 상수를 전수 대조하고, `code/name/category/parent/is_leaf` 전 목록을 개발책임자가 확인한 뒤에만 정본 전환을 시작한다. 확정된 한 매핑으로 chart 적재/정리, 모든 신규 분개 생성 경로, 보고서·원장 읽기 경로를 함께 바꾸고, 실 DB의 확정 후보 141라인과 전 목록 대조에서 추가 확정된 라인은 금액·journal/partner/source/status를 건드리지 않고 `account_code`만 감사 가능한 ID 집합으로 치환한다. 전후 전체 차변·대변 `597,211,068 / 597,211,068`, 대차 0, 거래처별 잔액, POSTED+REVERSED 상쇄가 완전히 같아야 하며, 역방향 매핑은 변경 ID 집합에만 적용할 수 있어야 한다. #1144의 새 분개 쓰기는 이 슬라이스가 끝나기 전에는 시작하지 않는다.

### 2.3 `docs/dev-reports/` 결정 근거 원문

`docs/dev-reports/2026-08-05-1001-r46-canonical-accounts-and-opening.md`:

> - 범위: 거래처별 원장이 이카운트 계정 정본, 상대 라인 effect, 기간 경계의 확정수금, 기초-only 거래처를 올바르게 읽도록 수정
> - 범위 밖: 앱 생성 경로 전환, 기존 `110`/`401` 68라인 정규화, `chart_of_accounts` 정리, 다른 회계 화면 전환 — 이슈 #1072

> 현재 `PartnerLedgerReadModelService`와 `PartnerLedgerCollectionContract`가 `110`을 채권, `401`을 매출로 고정한다. 이 때문에 회사 DB에 실재하는 이카운트 정본 `1089`·`4019`·`2519`가 원장 분류에서 빠진다. 전환기 레거시 `110`·`401`도 함께 읽어야 한다.

> ### 3.1 계정 정본과 전환기 alias
>
> `PartnerLedgerReadModelService`가 `ChartOfAccountRepository.findAllByOrderByCodeAsc()`로 활성 chart를 읽고, `category`·정확한 `name`·leaf 여부로 계정 코드를 구성한다.
>
> - `ASSET / 외상매출금` → `110`, `1089`
> - `REVENUE / 상품매출` → `401`, `4019`
> - `LIABILITY / 외상매입금` → `201`, `2519`
>
> 분류 contract에는 계정 코드를 전달하고, chart를 사용할 수 없는 구형 단위 adapter에서만 `110`·`401` 호환 fallback을 사용한다. 앱 생성 경로·chart master 데이터는 변경하지 않았다.

따라서 R46은 #1072를 끝낸 문서가 아니라 **원장 한 표면의 전환기 alias**만 구현했고, #1072의 전역 쓰기/읽기/chart/데이터 정규화는 범위 밖이라고 명시했다.

## 3. #1144 “명세 전수” — 본문 11개 + 댓글 5개

### 3.1 본문 원문에서 분해된 규칙 1~11

1. 판매전표→매출전표, 구매전표→매입전표라는 회계전표를 **회계담당자**가 생성·연결한다.
2. 생성 경로 ① **해당 전표 상세**, 그 전표 한 건에 한한다.
3. 생성 경로 ② **외부에서 일괄**, 선택 후 **복수 생성** 가능하다.
4. 생성 경로 ③ **일마감에서 바로** 회계전표 생성·연결이 가능하다.
5. 일마감에서 회계담당자가 적절한 금액, 즉 **할인율 또는 할인액**인지 판단한다.
6. **매출전표는 채권**, **매입전표는 채무**다.
7. 회계전표에는 **총금액·공급가액·부가세액 등**이 표시된다.
8. 거래처별 채권/채무 원장에 매출액·매입액이 반영되며, **회계전표 생성 전에도 반영**돼야 한다.
9. 회계전표 생성·연결의 이유는 **세금계산서 발행 + 다른 회계메뉴에서 확인**하기 위함이다.
10. **회계전표를 생성·연결하지 않으면 세금계산서 메뉴에 나오지 않아 발행 불가**다.
11. 연결 후 금액이 변경되면 해당 회계전표를 **삭제 후 재생성하여 다시 연결**할 수 있다.

본문의 설계 축 원문:

```text

세금계산서    회계전표 연결이 게이트다 (없으면 아예 안 나온다)
```

## 6. 기존 라인 정규화 영향과 되돌리기

### 6.1 현재 실측 — 확정 후보 141개, 최종 변경 건수는 전 목록 매핑 전 확정 불가

실행 SQL:

```sql
SELECT jl.account_code, COUNT(*) AS lines, COUNT(DISTINCT jl.journal_id) AS journals,
       COUNT(DISTINCT jl.partner_id) AS partners,
       SUM(jl.debit_amount) AS debit_sum, SUM(jl.credit_amount) AS credit_sum
FROM journal_lines jl
JOIN journals j ON j.id=jl.journal_id
WHERE jl.is_deleted=false AND j.is_deleted=false
  AND jl.account_code IN ('110','1089','401','4019','201','2519','111','114','120','202','210','212')
GROUP BY jl.account_code ORDER BY jl.account_code;
```

출력 원문:

```text
 account_code | lines | journals | partners |  debit_sum   |  credit_sum
 110          |    99 |       99 |       41 | 526330034.00 |  14259034.00
 201          |     3 |        3 |        2 |    800000.00 |   4070000.00
 210          |     1 |        1 |        0 |         0.00 |    700000.00
 401          |    42 |       42 |       33 |    572727.00 | 463304727.00
```

1089/4019/2519/111/114/120/202/212는 활성 라인 0이다. #1072 본문의 과거 68라인은 현재 DB에 적용할 수 없다. 현재 **확정 후보**는 `110→확정될 이카운트 외상매출금` 99개와 `401→확정될 이카운트 상품매출` 42개, 합계 **141개**다. 이 중 DRAFT는 110 9개+401 5개=14개, POSTED/REVERSED는 127개다.

그러나 “실제로 바뀌는 최종 행 수”를 지금 141로 닫으면 댓글의 전 목록 결정을 다시 위반한다. 현재 활성 `journal_lines`는 23개 SYSTEM 계정코드에 총 309개다. 8코드 후속 범위 중 `201` 3개와 `210` 1개가 있어 대응 코드가 달라지면 확정 후보는 **145개**가 된다. 나머지 164개도 전 목록 crosswalk에서 같은 코드 유지인지 이카운트 코드 치환인지 판정해야 한다. 따라서 현재 답은 다음처럼 나뉜다.

```text
확정 후보       141개 = 110 99 + 401 42
8코드 매핑 대기   4개 = 201 3 + 210 1
그 밖 매핑 대기 164개 = 나머지 19개 사용 코드
전체 활성 라인   309개 = 23개 계정코드
최종 변경 건수   전 목록 crosswalk 전에는 확정 불가
```

### 6.2 되돌릴 수 있는가

**조건부로 가능하다.** 단순 `1089→110`, `4019→401` 역UPDATE는 금지해야 한다. 이카운트 이관 원본 라인과 이번에 바꾼 앱 라인이 같은 정본 코드로 합쳐진 뒤에는 코드만 보고 출처를 구분할 수 없기 때문이다.

되돌릴 수 있으려면 정규화 직전에 변경 대상 `journal_lines.id`와 `old_account_code/new_account_code`를 감사 가능한 고정 집합으로 보존하고, rollback은 그 ID 집합에만 역매핑해야 한다. 마이그레이션 자체를 transaction으로 실패 롤백하는 것과, 배포 후 업무 rollback은 별개다. 후자는 별도 forward 보정 migration이 필요하다. 원 분개·금액·상태를 UPDATE/삭제하는 rollback은 허용하지 않는다.

현재 `journal_lines.account_code`는 chart FK가 아니므로 코드 변경 자체가 FK cascade를 일으키지는 않는다. 대신 모든 소비자가 같은 배포에서 새 코드를 인식하지 않으면 화면별 잔액이 조용히 사라질 수 있다.

### 7.2 표시 잔액

현재 코드를 그대로 둔 채 데이터만 먼저 바꾸면 **표시 잔액은 흔들린다.** `PartnerLedgerReadModelService`는 chart 기반 alias를 읽지만, `PartnerAgingService`, `ReceivablesPayablesService`, `SalesAggregateService`, `TaxInvoiceService`, `AccountStatementService` 등은 110/401/201을 직접 사용한다. 이 상태에서 141라인만 새 코드로 옮기면 해당 화면은 금액을 못 보고 잔액이 감소/소실한다. 이것은 결함이다.

따라서 배포 순서는 “전 목록 확정→모든 쓰기/읽기 경로 dual-read 또는 정본-read 준비→데이터 코드 치환→구코드 쓰기 차단→화면별 전후 불변식 확인”이어야 한다. #1144 새 분개를 먼저 만들면 다시 정규화할 라인만 늘어난다.
