## 0. 먼저 보고할 요약 반증

사용자 요약은 두 지점에서 그대로는 사실이 아니다.

1. **`qty × unitPrice`를 서버와 같은 scale 2로 preview한다**는 설명은 저장 컬럼 계약에는 맞지만, `VatCalculator` 자체의 계산과는 다르다. 서버는 `qty.multiply(unitPrice)` 뒤 `setScale(2)`를 호출하지 않는다(`VatCalculator.java:24-25`). 클라이언트는 `(quantity * price).toFixed(2)`로 먼저 반올림한다(`vatRounding.ts:38-46`). 실제 양측 실행에서 `qty=0.001, unitPrice=5`는 서버 총액 `0.005`, 클라이언트 총액 `0.01`이었다.
2. **`34,783.04`를 보존·표시한다**는 설명은 작성 폼에는 맞지만 저장 후 목록에는 틀리다. 작성 폼은 `34,783.04`를 표시하지만 매출·매입 목록의 `fmtKrw`는 `Math.round`로 `34,783`을 표시한다.

셋째 가능성도 있다. 위 1번의 일반 계산기 불일치는 현재 두 작성 폼의 실제 생성 값에는 도달하지 않는다. 배분 편집기가 수량을 소수 둘째 자리로 만들고(`SlipLineAllocationEditor.tsx:121-125`), 폼이 제출 단가를 정수 반올림하기 때문이다(`SalesAccountingSlipFormPage.tsx:45-55`, Purchase 동형). 따라서 이를 이번 라운드의 도달 결함으로 세지 않고 계산기 계약 차이로 기록한다.

### 2.3 BigInt 음수 나눗셈과 도달성

클라이언트 `-100n / 110n`은 0 방향 절사되어 공급가 `0`, VAT `-1`이 된다. 서버 `RoundingMode.DOWN`도 수학적으로 0 방향 절사지만, 과세 분리 전에 음수 자체를 거절하므로 결과를 내지 않는다. 다만 작성 폼은 `allocatedAmount > 0`만 선택하고(`SalesAccountingSlipFormPage.tsx:40-42`, Purchase 동형), 서버 allocation도 `@Positive` 및 service 검증을 거친다. 현재 사용자 화면에서 음수 lineTotal은 만들 수 없어 도달 결함은 아니다.

### 2.4 Number와 큰 금액

`0.1 + 0.2`는 클라이언트에서 `0.30000000000000004`가 되지만 `amount*100 = 30.000000000000004`를 `Math.round`하여 cents `30n`, 즉 `0.30`으로 정규화된다. 이는 scale 2 화면 입력에는 원하는 결과다.

저장 컬럼 정밀도 상한 `NUMERIC(15,2)` 부근에서 cents 손실을 별도로 스캔했다.

```text
SCAN cases=1000000 mismatches=0
Exit code: 0
```

스캔 범위는 cents `999999999000000`부터 연속 1,000,000개다. 이번 도메인의 scale 2 상한 안에서는 `Number → ×100 → Math.round → BigInt` 불일치를 재현하지 못했다. 상한 밖 Number 일반론으로 판정을 확대하지 않는다.

## 3. (b) 소수 원 표시와 누적

작성 폼:

- `formatVatAmount`는 `maximumFractionDigits: 2`이므로 `34,783.04`, `3,163.04`를 보존한다(`vatRounding.ts:49-51`).
- 두 작성 폼은 공급가·VAT·합계 모두 이 formatter를 쓴다(`SalesAccountingSlipFormPage.tsx:150-155`, Purchase 동형).

저장 후 목록:

- F-01과 같이 `fmtKrw`가 총액을 원 단위로 반올림한다.
- 목록에는 VAT 열 자체가 없고 공급가와 합계만 있다. 합계의 `.04`가 사라진다.

누적 probe:

- `34,783.04 × 3 = 104,349.12`.
- `(31,620 × 3) + (3,163.04 × 3) = 104,349.12`.
- formatter 출력도 양쪽 `104,349.12`, 내부 equality도 `true`였다.

따라서 확인한 3라인 누적에서는 작성 폼 표시 합 불일치가 없었다. 실제 두 작성 폼은 여러 원천을 하나의 제출 line으로 압축한 뒤 단 한 번 분리해 표시하므로 라인별 표시 반올림 누적 구조도 아니다. 단, mock API의 다중 line 합산은 `Number` reduce 후 `String` 변환하므로 이 표면은 아래 계열 표에 별도로 남긴다.
