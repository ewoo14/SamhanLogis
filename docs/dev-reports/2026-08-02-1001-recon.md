# #1001 거래처별 원장 표시 사양 정합 — 잔여 정찰

PR #1003 머지 이후 남은 범위를 특정한다.

## 확인 기록

- GitHub 읽기 API 확인: PR #1003은 `main` 대상으로 2026-07-31 머지되었고 merge commit은 `77774a1175743b69518d13cd0f6ab90b9d13b0ab`이다.

- PR #1003의 실 코드 범위는 원장용 판매전표 read 계약 신설과 주문→전표의 구조화된 배송주소 배선이며, 거래처별 원장 화면이나 입금보고서 조회 구현 파일은 변경 목록에 없다.

- GitHub compare 확인: PR #1003 merge commit은 현재 `main`보다 23커밋 뒤의 조상이고 `behind_by=0`이므로 #1003 산출물은 현재 main에 포함된다.

- 실 코드 확인: `PartnerLedgerSalesResponse.Line`은 `unitPriceWithVat`과 VAT 포함 `lineAmount`를 내보내며, 저장된 공급가액+부가세를 우선 사용한다.

- #1003 문서 확인: 배송주소 배선은 거래처 주문 단건·병합 발행에 적용됐지만 견적 원천은 계속 null이고, 과거 전표 backfill은 하지 않았다.

- #1003 문서 확인: 데스크톱 화면·CSV·인쇄·회계 통합 원장 API와 입금보고서 조회 결합은 #1003 범위에서 제외됐다.

- 실 DB READ ONLY 확인: 원장 대상 상태(CONFIRMED·DELIVERED·COMPLETED)의 활성 판매전표는 21건·62라인이고 `unit_price_with_vat` null 0, 공급가액/부가세 불완전 라인 0이다.

- 실 DB READ ONLY 확인: 같은 21건 중 구조화된 `delivery_address` 값이 있는 문서는 0건이다.

- 실 DB READ ONLY 확인: 같은 범위의 `delivery_tag`는 REGION 0건·STACK 3건이며, 태그를 배송주소로 파싱하거나 대체하지 않았다.

- 실 코드 확인: 현재 `PartnerLedgerPage`는 기존 매출집계와 분개원장 API만 호출하며 #1003의 `/internal/slips/partner-ledger-sales` 소비자는 accounting-service와 desktop에 없다.

- 실 코드 확인: 입금보고서는 입출금 내역에서 생성하고 별도 화면에서는 신규 작성 없이 조회·편집할 수 있으나, 거래처별 원장에는 아직 결합되지 않는다.

- 실 DB READ ONLY 확인: 활성 입금보고서는 25건(CANCELLED 21·CONFIRMED 3·DRAFT 1)이고 전표번호와 거래처 연결은 모두 25/25 존재한다.

- ① 판정: 별도 잔여가 아니다 — #1003 원장 판매전표 계약이 VAT 포함 단가·금액을 이미 제공하고 대상 62라인에 필요한 값이 모두 있으며, #1032의 표시 합계 통일과도 충돌하지 않는다.

- ② 판정: 남음 — 주문 발행 배선은 생겼지만 실 원장 대상 21건의 구조화된 배송주소가 0건이고 견적 경로·과거 데이터·원장 화면 소비가 비어 있다.

- ③ 판정: 남음 — 판매전표 read 계약과 입금보고서 조회·편집은 각각 존재하지만 이를 판매전표/입금보고서 2종 원장으로 결합하는 회계 API·데스크톱·CSV·인쇄 소비가 없다.

## #1001 잔여만

- ② 구조화된 배송주소 데이터의 미수집 구간과 기존 데이터 공백, 거래처별 원장 표시 연결.

- ③ 판매전표와 입금보고서를 2종 문서 원장으로 결합해 조회·CSV·인쇄에 표시하는 소비 계층.
