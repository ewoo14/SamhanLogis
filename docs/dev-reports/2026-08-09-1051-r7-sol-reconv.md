### R7-SOL-1 — 실제 마감 lock 5건이 GUI에서 lock 배지로 관측되지 않는다

- 실 사용자 경로: `dev` 시더 기동 후 사용자가 잠긴 `CONFIRMED` 판매·구매전표 상세를 연다.
- 재현 절차: (1) `SAMHAN_SLIP_SEED_TEST_DATA=true`로 시더를 기동한다. (2) SQL에서 `lock_flag=true`인 파생 픽스처 5건을 확인한다. (3) 해당 전표 상세의 배지 조건을 평가한다.
- 기대: 실제 `lock_flag=true`가 상세 GUI의 마감 lock 배지로 표시된다.
- 실제: API/desktop `SlipDetail` 계약에 `lockFlag`가 없고, `SlipDetailPage.tsx:2389-2399`의 `isLocked`는 `SHIPPING/DELIVERED/CANCELED/REJECTED` 상태만 본다. 다섯 lock 픽스처는 모두 `CONFIRMED`이므로 `SlipDetailPage.tsx:4125-4133`의 `slip-detail-locked-banner`가 렌더링되지 않는다.
- 원문 근거: `rg -ni 'lockFlag|lock_flag'` 결과 외부 상세 DTO와 `clients/desktop/src/renderer/api/slip.ts`에는 일치가 없고 internal lock endpoint만 존재했다. 격리 SQL의 lock 전수는 OUTBOUND `2026/02/15-1`~`2026/02/18-1`, INBOUND `2026/04/08-1`, 전부 `CONFIRMED/system`이었다.
- 라이브 관측 상태: renderer·gateway·auth·slip은 모두 HTTP 200이고 mock OFF였으나 Browser 선택이 `No browser is available`, 가용 목록 `[]`라 실제 DOM/PNG는 **관측 불가**다. 정적 경로를 실 캡처로 둔갑시키지 않았다.

이 결함은 R7의 provenance 수렴 자체를 깨뜨리지는 않지만, 개발책임자가 이번 라운드의 명시적 머지 관문으로 지정한 lock 배지 GUI를 구조적으로 만족하지 못한다.

## ① 연결 전표 provenance 전수

새로 만든 격리 PostgreSQL에서 exact HEAD product/slip bootJar를 실행했다. 첫 실행 SQL 집계:

```text
slips=100
linked_slips=19
non_system_linked=0
active_locks=5
system_locks=5
batches=30
active_batches=30
```

연결 19건 전수는 다음과 같다. 모두 `OUTBOUND`, `created_by=system`, 해당 첫 시드 실행의 `created_at`을 가졌다.

| 상태 | 전표번호 |
|---|---|
| SHIPPING | `2026/02/03-1`, `2026/02/04-1`, `2026/02/05-1`, `2026/02/06-1`, `2026/02/07-1` |
| DELIVERED | `2026/02/08-1`, `2026/02/09-1`, `2026/02/10-1`, `2026/02/11-1`, `2026/02/12-1`, `2026/02/13-1`, `2026/02/14-1`, `2026/02/27-1`, `2026/02/28-1`, `2026/03/10-1` |
| CONFIRMED | `2026/02/15-1`, `2026/02/16-1`, `2026/02/17-1`, `2026/02/18-1` |

`SlipSeeder`의 파생 기대 `(slip_no,status)` 19개를 SQL `VALUES`로 독립 대조한 양방향 차집합은 다음과 같다.

```text
expected_missing=0
unexpected_linked=0
```

따라서 `DeliveryBatchSeeder`가 연결한 실 업무 provenance 전표는 **0건**이다.
