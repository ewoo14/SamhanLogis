# PR #1172 fix1 조사 보고서 — 금액 3건 및 CI 3건

## 전잔 정의 판정 — 구현 차단

이 라운드에서는 전잔을 코드로 안전하게 확정할 수 없어 금액 수정을 중단한다. 현재 구현은 전잔을 `회계일자 + 전일`로 계산한다(`services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/PartnerLedgerReadModelService.java:106-109,404-425`). slip projection 내부에는 `slipDate + seqNo` 순서만 있고(`services/slip-service/src/main/java/com/samhanair/logis/slip/repository/SlipRepository.java:258-267`), accounting 분개에는 별도의 `journalDate + journalNo + lineNo` 순서가 있으며, 입금은 `transactionDate`만 원장에 들어온다. 따라서 같은 날 여러 slip·분개·입금·조정 사이에서 “이 전표 직전”을 결정하는 공통 순서가 없다. 원장 상태는 공통 계약상 `CONFIRMED/DELIVERED/COMPLETED/INSPECTING/SHIPPING`만 정본 후보로 정의되어 있지만(`shared/common/src/main/java/com/samhanair/logis/common/ledger/PartnerLedgerContract.java:15-20`), 대상 slip 전용 endpoint는 삭제되지 않은 OUTBOUND를 상태와 무관하게 반환한다(`services/slip-service/src/main/java/com/samhanair/logis/slip/web/SlipInternalController.java:424-442`, `services/slip-service/src/main/java/com/samhanair/logis/slip/repository/SlipRepository.java:189-191`). 또한 accounting read model은 slip projection과 journal을 모두 수집하고(`services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/PartnerLedgerReadModelService.java:149-150,190-200`), 중복 방지 key가 현재 `Set.of()`로 비어 있어 어느 하나를 정본으로 삼는 계약이 없다. 특히 journal의 `sourceRefId`는 SLIP 원천 UUID와 역분개 원분개 UUID라는 이중 의미를 갖는다(`services/accounting-service/src/main/java/com/samhanair/logis/accounting/domain/Journal.java:84-104`). 그러므로 전표번호 순서/발행시각/회계일자+채번 중 어느 기준인지, CANCELED와 회계 역분개를 어떻게 처리할지, accounting journal과 slip projection 중 어느 하나를 금액 정본으로 할지를 개발자가 추측해 확정할 수 없다.

## RED-A 원문 — 수정 전 제출

아래는 SOL 지시서 `docs/dev-reports/2026-08-12-1068-sol-review.md`에 기록된 격리 Testcontainers PostgreSQL 실 왕복 결과 원문이다. 이번 조사에서는 정의가 확정되지 않은 상태에서 같은 fixture를 임의의 기준으로 재작성하지 않았다.

```text
PASS target already canonical: 1,100,000 한 번
PASS target absent canonical: 1,100,000 한 번
PASS negative fold: -1,100,000
FAIL CANCELED target: expected 0, actual 1,100,000
FAIL same-day earlier 500,000: expected target opening 500,000, actual 0
FAIL posted SLIP journal 1,100,000 + same sale projection: expected 1,100,000, actual 2,200,000
```

이 원문은 다음 세 불변식의 RED를 직접 보여준다.

1. 같은 날 앞선 전표가 전잔에 반영되지 않는다.
2. CANCELED 전표가 후잔에 포함된다.
3. posted journal과 동일 거래의 slip projection이 각각 합산된다.

## 금액 결함의 코드 근거

### ① 같은 날 앞선 전표가 전잔에서 빠짐

전잔 sales 조회 상한이 `from.minusDays(1)`이다(`PartnerLedgerReadModelService.java:106-109`). 전일 마감 기준이라는 동작은 확인되지만, 대상 전표 직전이라는 정의는 코드에 없다. 현재 period sales는 `from..to`로 별도 수집되어(`PartnerLedgerReadModelService.java:149-150`) 대상 전표의 앞선 같은 날 순서를 전잔에 넣을 수 없다.

### ② CANCELED 대상이 후잔에 포함됨

일반 projection 조회는 canonical 상태 집합과 삭제 제외를 적용한다(`SlipRepository.java:258-267`). 그러나 target 보정은 `findBySlipNo` 결과에 대해 거래처·일자·중복 slipNo만 검사하고 상태를 검사하지 않는다(`PartnerLedgerReadModelService.java:487-515`). 따라서 CANCELED 대상이 `result.add(target)`로 들어간다.

### ③ journal과 projection의 이중 계상 가능

read model은 slip sales를 수집한 뒤 journal 문서도 추가한다(`PartnerLedgerReadModelService.java:149-150,190-200`). 이 경로의 `canonicalSlipKeys`가 빈 집합이고(`PartnerLedgerReadModelService.java:195-200`), journal evidence에서도 동일 key로 건너뛸 수 없으므로(`PartnerLedgerReadModelService.java:305-327,451-463`) 두 원천을 연결할 안전한 근거가 없다. `sourceRefId`만으로 연결하는 것도 현재 domain 주석상 안전하지 않다(`Journal.java:84-104`).

## 개발책임자 결정 요청

다음 두 계약이 문서/코드로 확정되어야 RED-A를 올바른 순서로 GREEN으로 만들 수 있다.

1. **동일일 전체 순서**: `회계일자 + 전역 채번`, `전표 발행시각`, 또는 `전표번호 순서` 중 하나를 선택하고, slip·journal·입금·조정 사이의 tie와 DRAFT/CONFIRMED/CANCELED/삭제의 시점 규칙을 정한다.
2. **금액 정본과 correlation**: posted accounting journal을 정본으로 할지 slip projection을 정본으로 할지 선택하고, 두 원천을 연결할 영속적인 공통 key를 정한다. 금액·일자·거래처 추정 매칭은 동일 금액 전표를 오인할 수 있어 사용할 수 없다.

결정 전에는 금액을 생성하거나 기존 테스트를 새 동작에 맞추지 않는다.
