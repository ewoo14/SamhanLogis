# PR #1176 적대검증 — 공유 개발 DB QA 잔재 soft-delete

- 검증일: 2026-08-12
- 역할: SOL 적대검증
- 원칙: 공유 DB에는 `SELECT`만 수행하며, 구현·스크립트는 변경하지 않는다. 롤백 SQL은 실행하지 않는다.
- 판정 질문: 실 사용자 경로로 재현 가능한 결함이 있는가?

## 1차 측정 — 실행·롤백 SQL 정적 검증

실행 스크립트의 partner 대상식 원문:

```sql
SELECT id
FROM partners
WHERE NOT is_deleted
  AND partner_code ~ '^SOL1154R20-BULK-[0-9]+$'
  AND biz_no = partner_code
  AND created_at >= TIMESTAMP '2026-08-10 01:24:06'
  AND created_at < TIMESTAMP '2026-08-10 01:24:14';
```

실행 스크립트 전체에서 `sol-pr1154-r1` 문자열은 0회다. 따라서 배제하기로 한 `created_by = 'sol-pr1154-r1'` 49행 및 `modified_by = 'sol-pr1154-r1'` 7,203행은 실행 판별식으로 사용되지 않았다.

실행 스크립트의 멱등성 관련 원문:

```sql
WHERE NOT is_deleted
...
SELECT COUNT(*) AS partner_before,
       COUNT(*) = 1000 AS partner_count_ok
FROM qa_partner_targets
\gset
...
WHERE NOT l.is_deleted
...
WHERE NOT s.is_deleted;
...
(SELECT COUNT(*) FROM qa_slip_targets) = 295
AND (SELECT COUNT(*) FROM qa_line_targets) = 636 AS counts_ok
```

현재 표지로 이미 soft-delete된 행은 재실행 대상 임시 테이블에 들어가지 않는다. 따라서 재실행 시 partner 대상은 0행이고 첫 1,000행 가드에서 `ROLLBACK; \quit 1`로 종료된다. slip 블록까지 도달하지 않는다. 재실행이 성공하는 의미의 멱등은 아니지만, 이미 삭제된 행을 다시 변경하지 않고 건수 가드로 중단하는 요구 동작과 일치한다.

롤백 스크립트의 첫 DB 블록 원문:

```sql
\connect partner_db

BEGIN;

UPDATE partners
SET is_deleted = FALSE, deleted_at = NULL, deleted_by = NULL, deleted_by_name = NULL
WHERE is_deleted AND deleted_by = 'qa-residue-softdelete-2026-08-12';

UPDATE slip_lines
SET is_deleted = FALSE, deleted_at = NULL, deleted_by = NULL
WHERE is_deleted AND deleted_by = 'qa-residue-softdelete-2026-08-12';

UPDATE slips
SET is_deleted = FALSE, deleted_at = NULL, deleted_by = NULL, deleted_by_name = NULL
WHERE is_deleted AND deleted_by = 'qa-residue-softdelete-2026-08-12';
```

`\set ON_ERROR_STOP on` 상태에서 `partner_db`에 `slip_lines` 또는 `slips`가 없다면 두 번째 UPDATE에서 실행이 중단되고, 앞선 partner UPDATE도 COMMIT되지 않는다. 뒤의 `\connect slip_db` 블록에도 도달하지 못한다. 다음 측정에서 실제 스키마 존재 여부를 SELECT로 확인한다.

## 2차 측정 — 공유 DB 표지·롤백 선행조건·금액 실측

실행 SQL:

```sql
SELECT current_database() AS db,
       to_regclass('public.partners') AS partners,
       to_regclass('public.slips') AS slips,
       to_regclass('public.slip_lines') AS slip_lines;
```

원문 출력:

```text
     db     | partners | slips | slip_lines 
------------+----------+-------+------------
 partner_db | partners |       | 
(1 row)
```

판정: `partner_db`에는 `slips`, `slip_lines`가 실제로 없다. 따라서 롤백 스크립트는 `UPDATE slip_lines`에서 `relation "slip_lines" does not exist`로 중단되며, 같은 트랜잭션의 partner 복원 1,000건도 COMMIT되지 않는다. 이 스크립트는 현재 상태를 실제로 되돌릴 수 없다. **재현 가능한 결함**이다. 금지 지시에 따라 롤백 스크립트 자체는 실행하지 않았다.

실행 SQL:

```sql
SELECT deleted_by, is_deleted, COUNT(*) AS rows
FROM partners
WHERE deleted_by='qa-residue-softdelete-2026-08-12'
GROUP BY deleted_by,is_deleted ORDER BY is_deleted;

SELECT 'slips' AS relation, deleted_by, is_deleted, COUNT(*) AS rows
FROM slips
WHERE deleted_by='qa-residue-softdelete-2026-08-12'
GROUP BY deleted_by,is_deleted
UNION ALL
SELECT 'slip_lines',deleted_by,is_deleted,COUNT(*)
FROM slip_lines
WHERE deleted_by='qa-residue-softdelete-2026-08-12'
GROUP BY deleted_by,is_deleted ORDER BY relation;

SELECT COALESCE(SUM(line_total),0) AS active_line_amount
FROM slip_lines WHERE NOT is_deleted;
```

```text
(1 row)
```

## 4차 측정 — 삭제 slip 295건 판별식 전수 분해

실행 SQL:

```sql
WITH ms AS (
  SELECT id FROM slips
  WHERE deleted_by='qa-residue-softdelete-2026-08-12'
), r AS (
  SELECT l.slip_id,
    bool_or(l.created_by='system' AND l.created_at BETWEEN
      TIMESTAMP '2026-05-09 16:59:33.210336' AND TIMESTAMP '2026-05-09 16:59:33.901047') AS sys_window,
    bool_or(l.created_by='system-internal' AND l.created_at BETWEEN
      TIMESTAMP '2026-05-30 13:37:02.475652' AND TIMESTAMP '2026-05-30 13:39:39.203575') AS internal_window,

      '57dc63e2-43da-43e6-b73e-3c81822cf9a7',
```

## 5차 측정 — 자식 및 서비스 간 논리 참조

먼저 전체 접속 가능 DB의 `partner_id`, `slip_id`, `slip_no`, `source_slip_id`, `source_ref_id` 및 유사 열을 `information_schema.columns`로 열거했다. 그 결과 실제 업무 경로 후보는 회계, 재고, 그룹웨어, 알림, 거래처 주문, slip 자식 테이블에 존재했다. 삭제 전표의 `id` 295개와 `slip_no` 집합은 다음 SELECT의 원문 결과를 메모리 배열로 전달했으며 공유 DB에 임시 테이블이나 DDL을 만들지 않았다.

```sql
SELECT quote_literal(id::text)
FROM slips
WHERE deleted_by='qa-residue-softdelete-2026-08-12'
ORDER BY id;

SELECT quote_literal(slip_no)
FROM slips
WHERE deleted_by='qa-residue-softdelete-2026-08-12'
ORDER BY slip_no;
```

각 대상 DB에서 실행한 SELECT의 형태:

```sql
WITH ids AS (SELECT unnest(ARRAY[<위 SELECT의 295개 id 원문>]::text[]) AS v),
     nos AS (SELECT unnest(ARRAY[<위 SELECT의 slip_no 원문>]::text[]) AS v)
SELECT '<테이블.열>' AS reference, COUNT(*)
FROM <테이블>
WHERE <uuid 열>::text IN (SELECT v FROM ids)
   OR <전표번호 열> IN (SELECT v FROM nos);
```

### [HIGH] 되돌림 스크립트가 현재 실행 결과를 되돌리지 못한다

- 재현 경로: `psql -f scripts/qa-residue/2026-08-12-rollback-soft-delete-qa-residue.sql`을 실행한다고 가정한 정적·스키마 검증. 실제 실행은 금지 지시에 따라 하지 않았다.
- 원인: `\connect partner_db` 후 partner UPDATE와 함께 존재하지 않는 `slip_lines`, `slips`를 같은 트랜잭션에서 UPDATE한다.
- 실측: `partner_db | partners | <NULL slips> | <NULL slip_lines>`.
- 결과: `ON_ERROR_STOP`에 의해 `UPDATE slip_lines`에서 중단되고 partner 복원도 COMMIT되지 않으며 `slip_db` 복원 블록에 도달하지 못한다.
- 영향: 이미 적용된 partner 1,000 / slip 295 / line 636 soft-delete를 제공된 되돌림 스크립트로 복구할 수 없다.

그 외에는 실 업무 거래처·전표 오탐, 거래처/전표/재고/회계 화면 깨짐, 사용자에게 노출되는 고아 자식, PM이 확인한 회계 2건의 실 데이터 혼입을 재현하지 못했다. 실행 스크립트 재실행은 partner active 대상 0건으로 첫 건수 가드에서 ROLLBACK·종료하므로 이미 삭제된 행을 다시 변경하지 않는다.
