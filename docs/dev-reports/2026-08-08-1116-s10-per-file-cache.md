# PR #1118 / 이슈 #1116 — S10 파일 단위 캐시

## 판정

walk+stat 선측정은 45.07초 기준을 크게 넘지 않아 per-file 캐시 설계를 채택하고 구현했다. 다만 현재 워크트리에 `clients/desktop/node_modules`가 없어 Vitest가 시작 단계에서 중단되었으므로, S10 GREEN 및 전체 하네스/CI 시간은 아직 주장할 수 없다.

## walk+stat 선측정

기존 discovery의 skip 디렉터리와 동일한 규칙으로 저장소 루트를 walk하고, 파일 내용은 읽지 않고 각 파일에 `fs.statSync`만 적용했다.

```text
root: C:\dev\Samhan-Public\.claude\worktrees\t1116
files: 16,607
directories: 2,688
1회 elapsed: 1,368.49 ms
정적 discoveredEvidenceWriters 직접 호출 지점: 7곳
7회 환산: 9,579.47 ms
기존 S6 기준: 45.07 s
```

따라서 walk+stat만으로 중단하는 조건에는 해당하지 않았다.

## 구현

`discoveredEvidenceWriters()`를 다음 방식으로 변경했다.

- 매 호출마다 기존 scan roots를 walk한다.
- 파일마다 `realpathSync.native()`로 canonical 경로를 만든 뒤 `statSync`한다.
- `Map<canonicalPath, { mtimeMs, size, isEvidenceWriter }>`에서 동일한 `(mtimeMs, size)`이면 판정을 재사용한다.
- 신규 파일 또는 metadata 변경 파일만 `readFileSync` 후 writer 판정을 다시 한다.
- 이번 walk에 없는 Map 항목은 새 Map으로 교체해 삭제를 반영한다.
- 반환 경로는 canonical 경로만 사용해 junction 별칭 중복을 제거한다.

기존 writer 판정 규칙과 G8a 모집단, k6 `__ENV`, `gradlew`, `Dockerfile`, `_headers`, `.d.cts` 관련 범위는 변경하지 않았다.

## RED-A ①~③

다음 세 테스트를 추가했다.

1. 호출자 invalidate 없이 파일 추가 후 발견되고, 삭제 후 사라지는지 확인한다.
2. 파일 내용만 non-writer에서 writer로 바꾼 뒤 재판정되는지 확인한다.
3. junction 별칭으로 발견된 canonical 파일이 원본 삭제 후 사라지는지 확인한다.

현재 실행 결과:

```text
npx vitest ...
실패: vitest.config.ts에서 vitest/config을 resolve하지 못함
원인: 지정 워크트리에 clients/desktop/node_modules가 없음
```

따라서 RED-A는 테스트 코드를 작성했지만 이 워크트리에서는 실행/판정하지 못했다. 의존성 설치나 다른 워크트리 사용은 하지 않았다.
