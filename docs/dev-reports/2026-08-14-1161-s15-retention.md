# #1161 S1.5 — 보존 정책 · ILM · DLQ 운영 소비

## 1. 현황 실측

정찰 보고서와 S0 부하 실측을 다시 수행하지 않고 기준으로 사용했다.

- 정적 HTTP 표면: 1,017개. 실제 중앙 발행: pilot 2개 서비스 3곳. 확정 분모는 판정 불가.
- 기존 ES 저장소는 `samhan-audit-logs` 단일 고정 인덱스였고 ILM/rollover/data stream이 없었다.
- 기존 Rabbit topology는 audit queue와 DLQ만 있었고 queue max-length·TTL·운영 DLQ consumer가 없었다.
- S2a의 publisher는 after-commit/non-blocking/fail-soft와 retry 3회를 이미 제공했다.
- `AuditLogEvent`에는 A/B/C, event kind, outcome 계약이 있었지만 ES 문서에는 보존 등급이 저장되지 않았다.

양방향 RED의 반대편은 기존 fail-soft 계약 회귀 확인이다. S2a publisher 모듈 전체 테스트를 실행해 Rabbit 장애가 업무 호출 예외로 재전파되지 않는 기존 계약을 확인했다.

## 3. 고른 수단과 이유

- A/B/C별 `samhan-audit-logs-a/b/c` 인덱스를 사용한다. 이벤트 등급이 이미 계약에 있으므로 별도 분모 확장 없이 저장 경계에서 분리할 수 있다.
- `AuditRetentionProperties`의 설정값만 변경 지점으로 두었다. 초기 운영값은 환경변수 기본값으로 A/B 8760시간, C 720시간을 제공하지만 정본 업무·법규 정책으로 고정하지 않았다.
- ES startup initializer가 ILM policy와 index template을 멱등적으로 등록한다. ES가 unavailable이어도 예외를 삼켜 업무 기동을 막지 않는다.
- Rabbit routing key의 `audit.change/failure/read` lane을 변경·실패·조회 queue로 분리하고 queue별 max-length/TTL을 적용했다. C(read) queue 상한을 더 낮춰 부하 시 먼저 제한되게 했다.
- consumer에는 retry interceptor 3회와 `RejectAndDontRequeueRecoverer`를 적용했다. 저장 실패는 업무 publisher 경로가 아니라 consumer의 DLQ 경로로 간다.
- DLQ는 자동 재처리하지 않는다. `/logs/dlq` 운영 명령으로 inspect/retry/discard를 수행하며, retry header `x-samhan-dlq-retry-count`를 사용해 3회 초과 재처리를 거부한다. 실패 메시지는 DLQ에 남고 무한 순환하지 않는다.

## 5. 불변식 보증 방법

1. A/B/C 문서를 등급별 ES index로 저장하고 각 index template에 서로 다른 ILM delete age를 적용했다. 기간은 설정값으로만 조정한다.
2. 업무 publisher는 변경하지 않았고 S2a의 non-blocking, after-commit, fail-soft, retry 3회 계약을 유지했다. 변경 모듈 전체 테스트와 audit-publisher 전체 테스트가 통과했다.
3. DLQ queue를 bounded하게 만들고 운영 조회/재처리/폐기 API를 추가했다. retry count와 원인 header를 inspect 결과에 포함한다.
4. S0 부하 측정은 재수행하지 않았다. queue lane 분리와 C queue의 더 낮은 상한으로 고부하 대비만 추가했다.
5. S2a의 requestId·traceId·request capture·ES correlation 필드는 event-to-document 매핑에서 그대로 복사하며, consumer 회귀 테스트가 requestId·traceId·route를 확인한다.

### 불변식 ①~⑤ 보증

1. **중앙 발행**: 두 신규 경로에서 controller 호출 → publisher → Rabbit `audit.#` 수신을 확인했다.
2. **fail-soft**: 두 단위 테스트에서 publisher가 `RuntimeException("rabbit down")`을 던져도 기존 service 호출과 성공 업무 응답이 유지됐다.
3. **S0 부하 결론**: S0 보고서는 실제 이벤트 처리량·consumer 중단 시 backlog 처리량을 측정하지 않았다. 2개에서 4개 경로로 늘어난 효과를 수치로 추정하지 않았으며 결론은 **판정 불가**로 유지한다.
4. **S1.5/S2a 보존**: 기존 `AuditEventV2.mutation`/`AuditPublisher` 계약, retention A, A_CHANGE, requestId/traceId capture, after-commit, retry 3회, DLQ·ILM 경로를 변경하지 않았다.
5. **기존 동작 보존**: 업무 service 호출과 기존 응답 DTO를 먼저 만들고 보조 발행만 수행한다. publisher 실패는 응답으로 전파되지 않으며 기존 controller 생성자도 호환 유지했다.

## 큐 재선언 fix

### RED 원문

기존 큐를 삭제하거나 purge하지 않고, TTL 없는 durable 큐를 먼저 만든 뒤 PR HEAD의
`RabbitConfig`를 재선언했다. 기존 live QA의 원문은 다음과 같다.

```text
PRECONDITION_FAILED - inequivalent arg 'x-message-ttl' for queue
'samhan.audit.queue' in vhost '/': received the value '86400000'
of type 'long' but current is none

Application run failed
```

격리 Testcontainers 회귀 테스트에서도 같은 조건에서 기존 선언을 재현했고,
기존 코드의 `admin.declareQueue(...)`가 실패했다. 원인은 durable queue의 선언 인자는
제자리에서 변경할 수 없는데 `auditQueue()`와 lane queue들이 `x-message-ttl`/`x-max-length`를
매번 선언한 것이다.

### 고른 수단과 이유

큐 이름을 바꾸거나 기존 큐를 삭제·purge·이관하지 않고 RabbitMQ policy로 보존 정책을
분리했다. `auditQueue()`와 failure/read queue 선언에는 기존 호환에 필요한 DLX 인자만
남기고, `samhan-audit-retention` policy가 다음을 적용한다.

```text
pattern   = ^samhan\.audit\.(queue|failure\.queue|read\.queue)$
message-ttl = 86400000
max-length = 10000
```

logging-service가 ApplicationReady 시 Rabbit Management API에 policy를 멱등 PUT한다.
Management API가 일시적으로 실패해도 logging-service 기동을 막지 않고 오류를 기록하여
감사 발행의 fail-soft 성질을 보존한다. 운영자는 로그의 `policy=samhan-audit-retention`
오류를 보고 policy 적용 상태를 재시도해야 한다.

### 기존 큐가 있는 상태의 GREEN 원문

공유 스택에는 브랜치 빌드를 올리지 않고 격리 RabbitMQ container에서 검증했다.
TTL 없는 기존 큐를 먼저 만든 뒤 fix 코드로 topology를 선언하고 policy를 적용했다.

```text
6 tests completed, 0 failed
BUILD SUCCESSFUL

Rabbit retention policy applied policy=samhan-audit-retention
pattern=^samhan\.audit\.(queue|failure\.queue|read\.queue)$
ttlMs=86400000 maxLength=10000
```

Management API의 policy 조회 원문에 `message-ttl`, `max-length`, `86400000`, `10000`이
모두 존재했으며, 기존 queue 선언은 406 없이 완료됐다.

### 기존 메시지 처리 방법

기존 `samhan.audit.queue`를 삭제하거나 purge하지 않는다. 기존 queue의 미소비 메시지는
같은 queue에 그대로 남고 기존 consumer가 계속 소비한다. policy는 queue를 갈아타지 않고
기존 queue에 적용되므로 별도 forwarding lane, 메시지 복사, 재처리 migration이 필요하지
않으며 메시지 유실 경로도 추가하지 않는다. TTL 정책 적용 이후의 만료·max-length 초과는
RabbitMQ가 정책에 따라 처리한다.

### 불변식 ①~⑤ 보증

1. **기존 queue 기동**: TTL 없는 기존 durable queue를 격리 container에서 먼저 선언하고
   fix topology를 재선언한 테스트가 통과했다. 기존 queue 인자를 변경하지 않아 Rabbit 406이
   발생하지 않는다.
2. **S1.5 정책 적용**: 실제 Management API PUT/조회에서 TTL 86400000ms와 max-length
   10000 policy를 확인했다. 새 queue와 기존 queue 모두 같은 policy pattern 대상이다.
3. **메시지 보존**: queue 삭제·purge·rename·forwarding을 하지 않는다. 기존 미소비
   메시지는 `samhan.audit.queue`에 남아 같은 consumer로 처리된다.
4. **fail-soft**: `AuditPublisher`의 after-commit/non-blocking/retry 3회 계약과
   실패 비전파 테스트를 변경하지 않았다. policy 적용 실패도 logging 기동 예외로
   전파하지 않고 로그로 남긴다.
5. **S2b/#1200 회귀 방지**: user/dashboard 모듈과 shared publisher 코드는 수정하지
   않았다. requestId/traceId/request capture, 역할 변경, release publish/unpublish의
   기존 테스트 계약을 건드리지 않으며 logging-service 변경은 Rabbit declaration/policy
   경계에 한정했다.

### 전량 테스트
