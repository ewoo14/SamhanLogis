# #1161 S1.5 — 보존 정책 · ILM · DLQ 운영 소비

## 1. 현황 실측

정찰 보고서와 S0 부하 실측을 다시 수행하지 않고 기준으로 사용했다.

- 정적 HTTP 표면: 1,017개. 실제 중앙 발행: pilot 2개 서비스 3곳. 확정 분모는 판정 불가.
- 기존 ES 저장소는 `samhan-audit-logs` 단일 고정 인덱스였고 ILM/rollover/data stream이 없었다.
- 기존 Rabbit topology는 audit queue와 DLQ만 있었고 queue max-length·TTL·운영 DLQ consumer가 없었다.
- S2a의 publisher는 after-commit/non-blocking/fail-soft와 retry 3회를 이미 제공했다.
- `AuditLogEvent`에는 A/B/C, event kind, outcome 계약이 있었지만 ES 문서에는 보존 등급이 저장되지 않았다.

## 2. RED 원문 (양방향)

추가한 `S15RetentionRedGateTest` 최초 실행 결과:

  NoSuchFieldException: retentionClass
S15RetentionRedGateTest > retentionPolicy_isConfigurationBacked_notHardCodedInDomain() FAILED
  ClassNotFoundException: AuditRetentionProperties

양방향 RED의 반대편은 기존 fail-soft 계약 회귀 확인이다. S2a publisher 모듈 전체 테스트를 실행해 Rabbit 장애가 업무 호출 예외로 재전파되지 않는 기존 계약을 확인했다.

## 3. 고른 수단과 이유

- A/B/C별 `samhan-audit-logs-a/b/c` 인덱스를 사용한다. 이벤트 등급이 이미 계약에 있으므로 별도 분모 확장 없이 저장 경계에서 분리할 수 있다.
- `AuditRetentionProperties`의 설정값만 변경 지점으로 두었다. 초기 운영값은 환경변수 기본값으로 A/B 8760시간, C 720시간을 제공하지만 정본 업무·법규 정책으로 고정하지 않았다.
- ES startup initializer가 ILM policy와 index template을 멱등적으로 등록한다. ES가 unavailable이어도 예외를 삼켜 업무 기동을 막지 않는다.
- Rabbit routing key의 `audit.change/failure/read` lane을 변경·실패·조회 queue로 분리하고 queue별 max-length/TTL을 적용했다. C(read) queue 상한을 더 낮춰 부하 시 먼저 제한되게 했다.
- consumer에는 retry interceptor 3회와 `RejectAndDontRequeueRecoverer`를 적용했다. 저장 실패는 업무 publisher 경로가 아니라 consumer의 DLQ 경로로 간다.
- DLQ는 자동 재처리하지 않는다. `/logs/dlq` 운영 명령으로 inspect/retry/discard를 수행하며, retry header `x-samhan-dlq-retry-count`를 사용해 3회 초과 재처리를 거부한다. 실패 메시지는 DLQ에 남고 무한 순환하지 않는다.

## 5. 불변식 보증 방법

1. A/B/C 문서를 등급별 ES index로 저장하고 각 index template에 서로 다른 ILM delete age를 적용했다. 기간은 설정값으로만 조정한다.
2. 업무 publisher는 변경하지 않았고 S2a의 non-blocking, after-commit, fail-soft, retry 3회 계약을 유지했다. 변경 모듈 전체 테스트와 audit-publisher 전체 테스트가 통과했다.
3. DLQ queue를 bounded하게 만들고 운영 조회/재처리/폐기 API를 추가했다. retry count와 원인 header를 inspect 결과에 포함한다.
4. S0 부하 측정은 재수행하지 않았다. queue lane 분리와 C queue의 더 낮은 상한으로 고부하 대비만 추가했다.
5. S2a의 requestId·traceId·request capture·ES correlation 필드는 event-to-document 매핑에서 그대로 복사하며, consumer 회귀 테스트가 requestId·traceId·route를 확인한다.

## 6. 개발책임자 판단이 필요한 질문

- A 변경 감사와 B 실패의 1년, C 조회의 30일을 법적·업무 보존기간으로 확정해도 되는가?
- 회계·세무·전자금융 등 별도 법정 보존기간이 있다면 A/B 각각 어떤 기간을 적용할 것인가?
- 현재 값은 환경변수 기본값일 뿐이며, 발행 시작 후 증가율을 다시 측정해 queue 상한·ES 용량·ILM 기간을 조정할 것인가?

## 7. 전량 테스트 결과 / 못 한 것

- 실행: `./gradlew :services:logging-service:test --no-daemon` — 20/20 PASS.
- 실행: `./gradlew :shared:audit-publisher:test --no-daemon` — PASS.
- Testcontainers는 병렬 실행하지 않았고, 위 전체 logging-service 실행에서 기존 IT도 포함해 단독 실행했다.
- 새 DB migration은 필요하지 않았다. 따라서 migration 번호 충돌 검사는 적용 대상이 아니며, `#1198 #1201 #1203 #1204 #1180 #1162 #1188`의 번호를 사용하지 않았다.
- S0 부하 재측정, S2b 서비스 확장, 분모 리팩터링은 수행하지 않았다.
- 실제 운영 ES/Rabbit에 대한 장시간 보존 만료·DLQ 재처리 라이브 QA는 수행하지 않았다. 운영 환경에서 정책 적용과 메시지 처리량을 확인해야 한다.
