# PR #1138 / 이슈 #1116 — S10 재수렴 적대검증

## 결론

도달 결함 1건을 확인했다. process resolver(`ps1`, `sh`, `py`)가 모두 탐지되지 않는
환경에서는 S7이 Node 3종만 비교하고 green으로 끝난다. 이때
`availableResolvers.length >= nodeResolvers.length`는 구성상 항상 참이어서 아무것도
차단하지 않는다. 따라서 실행되지 않은 세 구현이 서로 어긋나도 이 테스트는 잡지 못한다.

현재 PR head의 실제 GitHub Ubuntu CI에서는 여섯 resolver가 모두 실행됐다. 또한
`git ls-files`에서 찾은 커밋 증거 이미지 6,716개, 상위 증거 루트 8개를 여섯 resolver에
넣은 결과는 모두 `BLOCK`으로 일치했다. 이 라운드에서 실제 QA 증거 루트를 통과하는
resolver 불일치는 찾지 못했다.

증거 무결성에서는 S9 보고서의 RED 명령을 현재 커밋에서 재현할 수 없었다. 같은 명령은
이름이 바뀐 S9 테스트를 하나도 선택하지 않은 채 파일 단위 pass로 끝난다. GREEN 명령의
Windows 수치 `pass 55 / fail 0 / skipped 0`은 재현됐지만, 같은 명령의 실제 Linux CI
수치는 `pass 39 / fail 0 / skipped 16`이다.

## 결함 1 — process resolver 0종 환경에서 Node 3종만 검사하고 green

### 재현 절차

테스트 파일은 수정하지 않았다. Node가 원본을 메모리에서 읽은 뒤 세 실행기 탐지 결과만
`null`로 주입하여 원래 파일명과 `__dirname`으로 컴파일했다. 실행 대상은 S7 하나로
좁혔다.

```powershell
$testPath=(Resolve-Path 'clients/desktop/scripts/qa-output-path-guard.test.cjs').Path
$loader='const fs=require("node:fs"),Module=require("node:module"),path=require("node:path");const filename=process.argv[2];let source=fs.readFileSync(filename,"utf8");source=source.replace("const POWERSHELL_EXE = findPowerShellExecutable()","const POWERSHELL_EXE = null").replace("const PYTHON_EXE = findPythonExecutable()","const PYTHON_EXE = null").replace("const GITBASH_EXE = findGitBashExecutable()","const GITBASH_EXE = null");const m=new Module(filename);m.filename=filename;m.paths=Module._nodeModulePaths(path.dirname(filename));m._compile(source,filename);'
$encoded=[Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes($loader))
node --test-name-pattern='S7 RED-B' -e 'eval(Buffer.from(process.argv[1],String.fromCharCode(98,97,115,101,54,52)).toString())' $encoded $testPath
if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }
```

### 원인과 도달성

`availableResolvers`는 먼저 `nodeResolvers` 3개를 무조건 넣고, 탐지된 process
resolver만 뒤에 붙인다. 따라서 다음 단정은 process resolver가 0개여도 항상 참이다.

```js
assert.ok(availableResolvers.length >= nodeResolvers.length, '실행 가능한 resolver가 하나도 남지 않았습니다')
```

Node만 있고 `bash`·`pwsh/powershell`·`python/python3`가 없는 개발자/QA 실행 환경은
테스트가 지원한다고 명시한 탐지 결과 조합이며, 테스트 파일을 직접 실행하는 실 사용자
경로다. 이 경로에서는 `.ps1`·`.sh`·`.py`의 판정 불일치가 있어도 exit 0이다. 이는 이
PR이 막으려는 조용한 skip/false-green과 같은 계열이다.

단, 현재 PR head의 GitHub Ubuntu runner는 이 결함 조건에 해당하지 않았다. CI 로그에는
skip 행이 없고 여섯 이름이 모두 출력됐다.

## 1차 각도 나머지 판정

### Linux에서 실제 검증한 resolver 수

주입해 process/Node 순서를 바꿔도 다음과 같이 올바른 현재 case의 여섯 행을 비교했다.

## 3차 각도 — S9 보고서 증거 무결성

### RED 명령은 현재 커밋에서 재현되지 않음

보고서와 같은 명령:


나온다. 보고서의 `pass 0 / fail 1` RED 출력은 현재 저장소 상태와 같은 명령만으로
재현할 수 없다.

## 이 라운드가 보지 않은 것

- Desktop mock 전체 스위트는 실행하지 않았다.
- Docker를 재기동·재배포하거나 새 컨테이너를 실행하지 않았다.
- macOS runner는 확인하지 않았다.
- 6,716개 파일 각각을 출력 파일로 쓰지는 않았다. `git ls-files`에서 도출한 상위 증거
  루트 8개와 실제 수동 재생성 루트를 여섯 resolver에 넣어 판정했다.
- process resolver 0종은 탐지 결과 주입으로 재현했다. 현재 GitHub Ubuntu runner는
  여섯 resolver 전부가 가용했다.
