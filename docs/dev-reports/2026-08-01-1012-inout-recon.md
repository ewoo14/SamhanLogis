# 2026-08-01 입출고 내역·입출고 분석 레거시 대조 조사

## 조사 범위

- `tools/legacy-gas/` 직접 목록에서 대상 폴더 `입출고 내역`, `입출고 분석`을 확인했다. 이번 조사는 이 두 프로그램만 대상으로 한다.
- `입출고 내역` 원본은 `appsscript.json`, `code.js`, `index.html` 3개 파일이고, `입출고 분석` 원본은 `appsscript.json`, `Code.js`, `Index.html` 3개 파일이다.

## 레거시 원본 확인

### 1. 입출고 내역 — 서버 동작

- 데이터 원천은 실시간 이카운트 API나 기존 Google Sheet가 아니다. Google Drive에서 이름이 정확히 `이카운트입출고내역.xlsx`인 파일을 찾는다: `var fileName = '이카운트입출고내역.xlsx';` 및 `var files = DriveApp.getFilesByName(fileName);` (`tools/legacy-gas/입출고 내역/code.js:14`, `:17`).
- 찾은 Excel blob을 임시 Google Sheets 파일로 변환하고 첫 번째 시트를 연다: `var tempFile = Drive.Files.insert(config, blob);`, `var ss = SpreadsheetApp.openById(tempFile.id);`, `var sheet = ss.getSheets()[0];` (`code.js:26-28`). 조회 후 임시 파일은 휴지통으로 보낸다: `DriveApp.getFileById(tempFile.id).setTrashed(true);` (`code.js:77-78`).
- 원본의 2행을 헤더, 3행부터를 데이터로 사용한다: `sheet.getRange(2, 1, 1, sheet.getLastColumn())` 및 `sheet.getRange(3, 1, lastRow - 2, sheet.getLastColumn())` (`code.js:34`, `:42`).
- 읽는 열은 헤더명 기준 `품목명`, `일자`, `입고수량`, `출고수량`이다 (`code.js:36-39`). 단, 실행 조건은 `품목명`과 `일자` 열 존재만 확인하며 (`code.js:41`), 수량 열이 없으면 해당 수량을 0으로 간주한다: `var qtyIn = (colIn > -1) ? (Number(row[colIn]) || 0) : 0;`, `var qtyOut = (colOut > -1) ? (Number(row[colOut]) || 0) : 0;` (`code.js:47-48`).
- 기간 키는 일별이 아니라 월별 `YYYYMM`이다. 날짜 문자열이 `^\\d{4}/\\d{2}`를 만족하는 행만 받고 (`code.js:50`), `var keyDate = rawDate.replace('/', '').substring(0, 6);`로 월 키를 만든다 (`code.js:63`). 날짜 범위 제한은 이 서버 코드에 없으며 파일에 든 모든 유효 월을 집계한다.
- 품목명 전처리 원문은 `var cleanName = rawName.replace(/[\\(\\[\\{].*?[\\)\\]\\}]/g, '').trim();`이다 (`code.js:53`). 즉 첫 괄호·대괄호·중괄호 구간을 제거한 문자열을 품목 집계 키로 삼는다.
- 필터 원문은 `var hasUsage = cleanName.includes('사용');`, `var isKoreanOnly = /^[가-힣\\s]+$/.test(cleanName);`, `var startsWithL = upperName.indexOf('L-') === 0;` (`code.js:57-59`)이고, 통과 조건은 `if (cleanName && !hasUsage && !isKoreanOnly && !startsWithL)` (`code.js:61`)이다. 따라서 빈 이름, `사용` 포함, 한글·공백만으로 된 이름, 대소문자 무관 `L-` 시작 품목을 제외한다.
- 결과 구조는 품목명별 `{ input: {}, output: {} }`이며 (`code.js:65-67`), 월별 입고·출고수량을 각각 합산한다: `db[cleanName].input[keyDate] ... + qtyIn`, `db[cleanName].output[keyDate] ... + qtyOut` (`code.js:69-70`). 금액 열이나 이익 값은 읽거나 계산하지 않는다.

### 1. 입출고 내역 — 화면 동작

- 표현 항목은 모델명 검색, 시작월·종료월, 조회 버튼, 월별 입고수량·출고수량 막대차트다. 원문은 `<input type="text" id="modelInput" placeholder="모델명 검색" ...>`, `<input type="month" id="startDate">`/`endDate` (`tools/legacy-gas/입출고 내역/index.html:206`, `:211-216`)와 차트 dataset `label: '입고수량'`, `label: '출고수량'` (`index.html:441-449`)이다.
- 초기 기간은 고정된 `2025-01`~`2025-12`다 (`index.html:234-237`). 시작·종료 역전을 자동 보정하고 (`index.html:256-267`), 월 차이가 12 이상이면 11개월 차이로 잘라 포함 월수 최대 12개월을 보장한다 (`index.html:268-278`).
- 모델 검색 제안은 대소문자를 무시한 부분포함이다: `modelNames.filter(m => m.toUpperCase().includes(val))` (`index.html:304-315`). 키보드 위·아래·Enter 선택을 지원한다 (`index.html:334-351`).
- 실제 조회는 대소문자를 무시한 정확일치 모델만 허용한다: `modelNames.some(m => m.toUpperCase() === val)`로 버튼을 활성화하고 (`index.html:378-387`), 차트 갱신도 `modelNames.find(m => m.toUpperCase() === model.toUpperCase())`를 사용한다 (`index.html:390-392`). 즉 복수 모델 동시 선택·분류 칩은 없다.
- 선택한 시작월부터 종료월까지 한 달씩 `YYYYMM` label을 만들고 (`index.html:396-409`), 누락 월은 0으로 표시한다: `mData.input[m] || 0`, `mData.output[m] || 0` (`index.html:411-413`).
- 차트는 입고수량·출고수량의 나란한 막대이며 (`index.html:435-454`), 0보다 큰 값만 막대 위 숫자로 노출한다: `return value > 0 ? value : '';` (`index.html:465-473`). 표, 원시 거래 행, 일별 상세, 금액, 이익률, 다운로드 동작은 원본에 없다.

### 2. 입출고 분석 — 서버 동작

- 웹앱 제목은 코드상 `수요예측시스템`이다 (`tools/legacy-gas/입출고 분석/Code.js:5-10`).
- 데이터 원천은 이카운트 API/현행 DB가 아니라 Google Drive의 출고·입고 전용 폴더 두 곳이다. 원문은 `var OUT_FOLDER_ID = '…';`, `var IN_FOLDER_ID = '…';` (`Code.js:1-3`)와 `fetchCsvData(OUT_FOLDER_ID)`, `fetchCsvData(IN_FOLDER_ID)` (`Code.js:47-51`)이다. 보고서에는 식별자 값을 재기재하지 않는다.
- 각 폴더의 모든 파일을 돌되 파일명에 `.csv`가 있거나 MIME이 CSV인 파일만 읽는다 (`Code.js:86-99`). 먼저 UTF-8로 읽고, 내용에 `품목명`과 `수량`이 모두 없으면 EUC-KR로 다시 읽는다: `if (content.indexOf('품목명') === -1 && content.indexOf('수량') === -1) { content = blob.getDataAsString('euc-kr'); }` (`Code.js:104-112`). 여러 CSV의 행은 하나의 배열로 병합한다 (`Code.js:153-158`).
- 헤더 위치는 고정 행이 아니다. 모든 행·셀에서 공백을 제거한 뒤 `품목명` 포함 셀을 품목명 열, `수량` 포함 셀을 수량 열, `일자` 포함 셀을 날짜 열로 잡는다 (`Code.js:122-135`). `품목명`을 발견한 행만 헤더로 간주해 건너뛴다 (`Code.js:125-137`). 날짜 열을 못 찾으면 0번째 열을 날짜로 사용한다: `var cellDate = (dateIdx !== -1) ? row[dateIdx] : row[0];` (`Code.js:142-145`).
- CSV 행 제외 규칙 원문은 `if (!cellName || !cellQty) continue;`, `if (cellName.indexOf('회사명') !== -1) continue;`, `if (cellQty === '0') continue;`, `if (!/\\d/.test(dateVal)) continue;` (`Code.js:146-151`)이다. 즉 빈 품목/수량, 품목명에 `회사명` 포함, 문자열이 정확히 `0`인 수량, 숫자가 하나도 없는 날짜를 제외한다.
- 수량은 쉼표를 제거하고 정수로 파싱하며 (`Code.js:169-172`), 품목명·날짜가 없거나 `quantity <= 0`이면 제외한다 (`Code.js:174`). 따라서 음수·0 입출고는 분석에서 사라지고 소수 수량은 정수로 절삭된다.
- 날짜는 공백 앞부분만 취해 `/`로 나누고 연·월만 파싱한다 (`Code.js:169`, `:176-180`). 일자는 결과에 보존하지 않으므로 집계 가능 단위는 월뿐이다.
- 품목명 정제 원문은 `String(rawItemName).replace(/\\([^)]*\\)/g, '').replace(/\\[[^\\]]*\\]/g, '').replace(/\\{[^}]*\\}/g, '')` 및 `cleanName.replace(/[\\s\\u00A0]+/g, '')` (`Code.js:181-184`)이다. 모든 소괄호·대괄호·중괄호 내용과 모든 공백/NBSP를 제거한다.
- 허용 접두사는 정확히 `['AJ', 'AM', 'AC', 'AP', 'AR', 'AF']`이고 나머지는 제외한다 (`Code.js:185-187`).
- 모델 길이 규칙 원문: `AR`은 길이 14 이상이면 앞 14자, 아니고 12 이상이면 앞 12자, 그보다 짧으면 제외한다 (`Code.js:189-193`). 나머지 접두사는 길이 12 이상이면 앞 12자, 짧으면 제외한다 (`Code.js:194-197`).
- 분류 규칙 원문: `AJ` → `홈멀티`, 실내기 여부는 7번째 문자(`cleanName.charAt(6) === 'N'`) (`Code.js:202-205`); `AM` → `상업멀티`, 같은 7번째 문자 규칙 (`Code.js:206-208`); `AC`·`AP`·`AR`·`AF` → `싱글중대형` (`Code.js:209-210`)이다.
- `싱글중대형` 실내기 판별은 `AR`·`AF`이면 12번째 문자(`charAt(11)`), `AC`·`AP`이면 7번째 문자(`charAt(6)`)가 `N`인지로 정하고 (`Code.js:211-215`), `if (!isIndoor) continue;`로 실외기를 모두 제외한다 (`Code.js:217-219`). 반면 `홈멀티`·`상업멀티`는 `isIndoor`를 계산하지만 제외에는 사용하지 않아 실내기와 실외기가 모두 남는다.
- 정제 결과 한 건의 표현 데이터는 `model`, `category`, `year`, `month`, `quantity`뿐이다 (`Code.js:221-227`). 입고·출고는 별도 배열 `result = { out: outData, in: inData }`로 구분한다 (`Code.js:53-59`). 거래일, 거래처, 구매액, 판매액, 원가, 순이익, 영업이익은 없다.
- 결과는 최대 90,000자 단위로 나누어 Script Cache에 3,600초 저장한다 (`Code.js:61-75`). 강제 새로고침 인자가 거짓이면 캐시를 우선 반환한다 (`Code.js:20-45`).

### 2. 입출고 분석 — 화면·계산 동작

- 화면 표현은 최신화, 시작월~종료월, 분류, 모델명 검색, `출고 예측` 선차트, `추천 및 알림`, `상위 모델 Top 3`, `하위 모델 Bottom 3`다 (`tools/legacy-gas/입출고 분석/Index.html:135-218`). 최신화는 `loadData(true)`로 서버 캐시를 우회한다 (`Index.html:227-258`).
- 기간 선택은 연도 없는 1월~12월이며 기본 1~12월이다 (`Index.html:150-181`). 시작월이 종료월보다 큰 경우를 보정하거나 거부하는 로직은 없다.
- 분류 선택지는 `전체`, `홈멀티`, `상업멀티`, `싱글중대형`뿐이다 (`Index.html:184-191`). 실내기·실외기·판넬 등의 별도 필터나 복수 칩 선택은 없다.
- 모델 자동완성 후보는 입고·출고 양쪽의 모든 모델을 합친 정렬 목록이다 (`Index.html:293-305`). 실제 모델 필터는 입력을 대문자로 바꾼 뒤 `item.model.indexOf(modelQuery) === -1`로 부분포함 판정한다 (`Index.html:319-338`). 서버 정제 모델이 대문자라는 전제이며 item 쪽 대문자 변환은 없다.
- 기간 필터는 `item.month < startM || item.month > endM`만 검사하고 연도를 제한하지 않는다 (`Index.html:326-338`). 따라서 선택한 월 구간에 해당하는 모든 연도의 행이 순위·재고 계산에 함께 들어간다.
- 월별 출고 비교는 연도를 2025와 2026으로 하드코딩한다. 원문은 `if (item.year === 2025) monthlyLast[mIndex] += item.quantity; else if (item.year === 2026) monthlyThis[mIndex] += item.quantity;` (`Index.html:343-357`). 다른 연도의 출고는 월별 차트에서 버려지지만 아래 모델별 출고 합계에는 포함된다.
- 비교 대상 누적과 추이 배율 계산식은 다음과 같다. 2026 출고가 0보다 큰 월만 찾아 그 월의 2025 출고와 2026 출고를 각각 합산하고 마지막 관측 월을 갱신한다 (`Index.html:364-374`). 기본 배율은 1이며, 비교기간 2025 합계가 양수면 `rate = totalThis / totalLast`다 (`Index.html:376-377`). 즉 표시 문구상 `작년 동기 대비`이고, 증감률 퍼센트를 직접 표시하지 않으며 출고수량의 동기비 배수만 내부 계산한다.
- 예측식은 마지막 2026 관측 월 다음 달부터 12월까지 `predicted[m] = Math.round(monthlyLast[m] * rate)`다 (`Index.html:379-382`). 이는 모델·월별 추세 회귀가 아니라, 필터된 전체 출고의 전년 동월 수량에 올해/작년 동기 누적 배율을 곱한 단순 출고수요 예측이다. 입고수량은 예측식에 전혀 쓰지 않는다.
- 2026 월 출고가 0인 값은 차트에서 `null`로 바꾼다 (`Index.html:384-386`). 따라서 실제 0과 데이터 부재를 구분하지 못한다.
- 차트 표현 데이터는 월별 `작년 출고`, `올해 출고`, `수요 예측` 3개 선이다 (`Index.html:424-460`). 구매량·구매액·발주량의 예측선은 없다.
- 상·하위 모델은 필터 범위의 모델별 출고수량 합계를 내림차순 정렬해 앞 3개와 뒤 3개를 뽑는다 (`Index.html:347-357`, `:388-393`). 화면에는 순위와 모델명만 렌더링하고 실제 합계 수량은 표시하지 않는다 (`Index.html:485-503`).
- 추천은 출고 1위 모델 하나에 대해서만 `stock = (inCounts[top] || 0) - (outCounts[top] || 0)`를 계산한다 (`Index.html:395-400`). 이 값은 선택 월 구간의 모든 연도 누적 입고수량-출고수량이며 실제 현재고 테이블이 아니다. 0 이하면 `<모델> 발주 권장`/`출고량 대비 잔여 재고가 부족합니다.`, 양수면 `<모델> 주력 상품`/`현재 안정적인 재고를 보유 중입니다.`를 표시한다 (`Index.html:398-400`). 권장 발주수량은 계산하지 않는다.
- 추가 알림은 `rate > 1.1`일 때만 `전반적 수요 상승`/`작년 동기 대비 판매량이 증가하고 있습니다.`를 표시한다 (`Index.html:402`). 여기서 `판매량`의 실제 계산 원천은 판매액이나 주문이 아니라 출고수량이다. 10% 이하 증가, 감소율, 모델별 증감률은 표시하지 않는다.
- 추천이 하나도 없으면 `특이사항 없음`을 표시한다 (`Index.html:403`). 다만 출고 Top 1이 존재하면 항상 발주 권장 또는 주력 상품 추천이 생기므로 이 fallback은 사실상 출고 데이터가 없고 배율도 1.1 이하일 때만 도달한다.
- 두 앱 모두 Apps Script V8이고 Drive v2 고급 서비스를 켠 웹앱이다 (`tools/legacy-gas/입출고 내역/appsscript.json:4-16`, `tools/legacy-gas/입출고 분석/appsscript.json:3-21`). 이는 위 Drive 파일·폴더 원천 판정을 뒷받침한다.

## 현행 대조 근거

### 실제 라우트 존재 여부

- 현행 데스크톱의 실제 라우트 정본은 `routes` 배열이며 (`clients/desktop/src/renderer/routes/index.tsx:333-348`), 마지막에 인증 영역 전체 catch-all `path: '*'`가 `NotFoundPage`로 연결된다 (`routes/index.tsx:1715-1720`). 따라서 등록되지 않은 경로는 다른 숨은 페이지가 아니라 404로 수렴한다.
- 입출고에 인접한 실제 라우트는 판매조회 `/sales` → `SalesQueryPage`, 출고전표 `/sales/slips` → `SlipListPage mode="OUTBOUND"` (`routes/index.tsx:425-435`), 구매조회 `/purchases` → `PurchaseQueryPage`, 입고전표 `/purchases/slips` → `SlipListPage mode="INBOUND"` (`routes/index.tsx:558-569`), 재고현황 `/inventory/stock-balance` → `InventoryStockBalancePage` (`routes/index.tsx:583-591`)다.
- 회계에는 `/accounting/reports/income-statement`와 `/accounting/reports/income-statement/monthly`가 각각 `IncomeStatementPage`, `MonthlyIncomeStatementPage`로 등록돼 있다 (`routes/index.tsx:674-699`). 이는 회사 전체 회계 손익 화면 후보이지, 아직 품목별 이익률 계승 여부는 별도 데이터 계약으로 확인한다.
- 위 실제 라우트 목록에는 월별 모델 입고·출고수량을 한 화면에서 비교하는 `입출고 내역` 대응 페이지도, 출고 추이·수요예측·Top/Bottom·추천을 제공하는 `입출고 분석` 대응 페이지도 등록돼 있지 않다. 문자열 0건만이 아니라 catch-all까지 포함한 라우트 정본 확인 결과다 (`routes/index.tsx:333-1720`). 인접 화면이 표현 데이터를 대체하는지는 아래에서 계속 대조한다.

### 인접 현행 화면의 실제 범위

- `/sales`는 `slipType: 'OUTBOUND'` 출고=매출 전표의 날짜 범위 목록이다 (`clients/desktop/src/renderer/routes/sales-query/SalesQueryPage.tsx:1-6`). `querySlips`에 일자 범위와 전표번호·거래처명·사업자번호·배송주소·프로젝트명을 전달한다 (`SalesQueryPage.tsx:230-246`). 월별 품목 입출고 집계가 아니다.
- `/sales`의 목록 금액은 전표 단위 `totalAmount`이고 (`SalesQueryPage.tsx:292-315`), 품목은 `BE lineSummary 없음 → 임시 "—"`라고 명시돼 있다 (`SalesQueryPage.tsx:9-20`). 따라서 모델별 출고수량·모델 필터·월별 차트·입고수량 대조를 표현하지 못한다.
- `/purchases`도 `slipType: 'INBOUND'` 입고전표의 날짜 범위 목록이며, 검색 조건은 전표번호·거래처명·사업자번호다 (`clients/desktop/src/renderer/routes/purchase-query/PurchaseQueryPage.tsx:161-175`). 열은 전표 단위 `totalAmount`, `totalQuantity`, 입고창고, 일자 등이다 (`PurchaseQueryPage.tsx:184-203`). 이 화면 역시 품목 칼럼이 `BE lineSummary 없음 → 임시 "—"`다 (`PurchaseQueryPage.tsx:4-16`).
- `/sales`와 `/purchases`는 판매·구매 전표를 서로 다른 화면과 API 호출로 나누므로, 같은 모델의 같은 월 입고수량·출고수량을 한 그래프에서 나란히 제공하는 레거시 표현 데이터와 다르다. 두 화면 모두 월 합계, 모델별 수량 집계, 복수 모델/분류 칩, 추이·예측을 계산하지 않는다.
- `/inventory/stock-balance`의 행은 품목코드·품목명·창고와 현재 `가용재고`, `예약재고`, `실재고`다 (`clients/desktop/src/renderer/routes/warehouse/InventoryStockBalancePage.tsx:87-184`). 조회 조건도 창고 하나뿐이고 (`InventoryStockBalancePage.tsx:203-237`, `:281-308`), 거래기간이나 입고수량·출고수량 이력은 없다. 따라서 현재고 화면은 레거시 월별 입출고 내역을 대체하지 않는다.

### 구매액·판매액 및 품목별 이익률 실행 가능성

- **구매액·판매액의 거래 스냅샷은 현행 DB에 있다.** `slip_db.slips`는 출고/입고 공용 테이블로 `slip_type`, `slip_date`를 보존한다 (`services/slip-service/src/main/resources/db/migration/V1__init_slip_service.sql:13-27`). `slip_db.slip_lines`는 `product_id`, `product_name`, `model_name`, `quantity`, `unit_price`, `line_total`을 보존한다 (`V1__init_slip_service.sql:65-78`). 따라서 `slip_type=OUTBOUND` 라인 금액은 판매액, `INBOUND` 라인 금액은 구매액으로 기간·품목별 집계할 원천이 존재한다.
- 라인에는 이후 `unit_price_with_vat`, `supply_amount`, `vat_amount`도 추가됐다 (`services/slip-service/src/main/resources/db/migration/V12__add_ecount_slipline_fields.sql:1-18`). 최신 계약에서 `line_total`은 공급가액 별칭이고 VAT 포함 총액은 `supply_amount + vat_amount`라고 명시한다 (`services/slip-service/src/main/resources/db/migration/V61__correct_partner_order_vat_overcharge.sql:38`). 어떤 단가가 사용자 입력 권위인지도 신규 행은 `unit_price_domain`으로 구별하지만, 기존 행은 `NULL`이라 알 수 없고 backfill하지 않았다고 명시한다 (`services/slip-service/src/main/resources/db/migration/V59__add_slip_line_unit_price_domain.sql:12-33`). 즉 금액 집계는 가능하나 레거시 행의 단가 표시 기준에는 확인불가 구간이 있다.
- 회계 DB에도 확정용 매출·매입 금액이 별도로 있다. `accounting_db.sales_accounting_slips`와 `purchase_accounting_slips`는 각각 `total_supply_amount`, `total_vat_amount`, `total_amount`를 저장한다 (`services/accounting-service/src/main/resources/db/migration/V18__add_sales_accounting_slips.sql:4-15`, `V19__add_purchase_accounting_slips.sql:4-15`). 각 라인도 `product_code`, `product_name`, `qty`, `unit_price`, `supply_amount`, `vat_amount`, `line_total`을 저장한다 (`V18__add_sales_accounting_slips.sql:39-49`, `V19__add_purchase_accounting_slips.sql:39-49`).
- 재고 DB에는 원가 보조 원천도 있다. `inventory_db.stock_lots`는 입고 로트별 `initial_quantity`, `received_at`, `unit_cost`를 저장하고 (`services/inventory-service/src/main/resources/db/migration/V1__init_inventory_service.sql:40-53`), `stock_movements`는 `lot_id`, `product_id`, `movement_type`, `quantity_delta`, 참조 문서, 발생시각을 저장한다 (`V1__init_inventory_service.sql:103-125`). 개별시리얼 재고도 `stock_instances.unit_cost`, 입고·출고 전표번호와 시각을 가진다 (`services/inventory-service/src/main/resources/db/migration/V15__create_stock_instances.sql:3-22`). 따라서 FIFO/개별시리얼 기준 실제 출고원가 추적을 설계할 재료는 있다.
- 상품 마스터의 기준가격도 `product_db.products.selling_price`, `purchase_price`로 존재한다 (`services/product-service/src/main/resources/db/migration/V1__init_product_service.sql:32-40`). 다만 이는 거래 당시 금액 스냅샷이 아니므로 품목별 실현 이익 계산의 우선 원천은 전표 라인과 출고 로트 원가다.
- **그러나 현 상태 그대로 계산 가능한 것은 구매·판매 차액 또는 매출총이익 성격이지, 회계상 품목별 영업이익·순이익은 아니다.** 회계 `journal_lines`에는 계정·차변·대변·거래처만 있고 품목 식별자나 품목별 배부키가 없다 (`services/accounting-service/src/main/resources/db/migration/V1__init_accounting_service.sql:99-124`). 회사 전체 영업이익은 `grossProfit - totalSga`, 순이익은 영업외손익과 법인세까지 반영한다 (`services/accounting-service/src/main/java/com/samhanair/logis/accounting/report/IncomeStatementService.java:109-123`). 판관비·영업외손익·법인세를 품목에 배부하는 기준/저장 컬럼이 없으므로 **진짜 품목별 영업이익·순이익은 현행 DB만으로 확정 계산 불가**다.
- 실행 가능성 판정: (1) `판매액 - 같은 기간 구매액`과 그 비율은 즉시 집계 가능하지만 재고 증감을 무시해 매출총이익과도 다를 수 있다. (2) `판매액 - 실제 출고원가`는 lot/instance 연결을 검증·집계하는 신규 백엔드가 필요하다. (3) 품목별 영업이익·순이익은 판관비·영업외·세금 배부 정책과 배부 데이터가 추가로 필요하다. 개발책임자 결정의 명칭을 유지하려면 이 배부 정책이 선행되어야 하며, 구매액·판매액만으로 산출할 경우 화면 명칭은 `매입·매출 차액/차익률` 또는 `매출총이익률`이 더 정확하다.

### 모델별 복수 칩 데이터 기반

- 현행 상품 도메인에는 홈멀티·싱글중대형·상업멀티 축이 있다. 내부 `ProductCategory`는 `HOME_MULTI`, `SINGLE_SET`, `SINGLE_PART`, `COMMERCIAL_MULTI`, `COMMERCIAL_PART`, `OLD`, `MATERIAL`을 정의한다 (`services/product-service/src/main/java/com/samhanair/logis/product/domain/ProductCategory.java:8-15`). 상품 분류 테이블도 `HOME_MULTI`, `SINGLE_SET`, `COMMERCIAL_MULTI`, `LEGACY`, `OTHER`를 허용하고 상품에 대·중·소 분류 FK를 둔다 (`services/product-service/src/main/resources/db/migration/V20__add_product_classification.sql:6-20`, `:23-37`, `:52-57`).
- 실내기·실외기·판넬 등의 구성 종류도 현행 카탈로그 타입으로 존재한다: `INDOOR`, `OUTDOOR`, `PANEL`, `REMOTE`, `MATERIAL`, `ACCESSORY`, `FOOT` (`clients/desktop/src/renderer/routes/EstimateItemsCatalogPage.tsx:120-128`). 재고 카테고리에는 `INDOOR`, `OUTDOOR`가 있고 판넬은 기존 시드에 아직 미정의라고 명시돼 있다 (`services/product-service/src/main/resources/db/migration/V9__add_category_serial_managed.sql:6-12`).
- 출고/입고 공용 `slip_lines`에는 `product_id`가 있으므로 상품 서비스 분류와 연결할 수 있다 (`services/slip-service/src/main/resources/db/migration/V1__init_slip_service.sql:69-77`). 다만 라인 snapshot `category_key`는 주문에서 전환된 **판매전표**만 보존하도록 추가됐고 수동·레거시 행은 null이며 backfill하지 않는다 (`services/slip-service/src/main/resources/db/migration/V60__preserve_sales_category_axis.sql:1-4`). 따라서 복수 칩 필터는 데이터 기반이 전혀 없는 것은 아니지만, 판매·구매 전 기간을 안정적으로 거르려면 `product_id` 기반 분류 조회/스냅샷 정책과 판넬 카테고리 정합을 신규 설계해야 한다. 현행 입출고 화면에는 이 칩 UI와 필터 API가 없다.

### 판매추이 → 구매예측 현행 여부

- 현행 라우트에는 구매예측/수요예측 화면이 없다. 관련 의미로 가장 가까운 `/inventory/safety-stock-alerts`는 실제로 등록돼 있지만 (`clients/desktop/src/renderer/routes/index.tsx:1693-1703`), 이는 예측이 아니라 현재 가용재고가 수동 임계값 이하인지 비교하는 화면이다.
- 안전재고 도메인의 원문은 `현재 가용 재고(availableQty)가 이 값 이하이면 알림 발생` (`services/inventory-service/src/main/java/com/samhanair/logis/inventory/domain/SafetyStockConfig.java:50-54`)이고, 서비스 계산도 `if (currentQty <= config.getThreshold())`뿐이다 (`services/inventory-service/src/main/java/com/samhanair/logis/inventory/service/SafetyStockService.java:148-160`). 부족량 역시 `threshold - currentQty`다 (`SafetyStockService.java:281-306`). 판매 추이, 전년 동월, 성장률, lead time을 사용하지 않으므로 레거시 수요예측도 개발책임자 결정의 판매추이→구매예측도 계승하지 않는다.
- 전체 현행 소스의 예측 관련 실제 업무 endpoint는 수금계획 forecast 등 다른 회계 도메인뿐이며, 상품 판매추이/구매예측 API는 확인되지 않았다. 따라서 구매예측은 신규 분석 API·화면이 필요하다. 원천 판매수량·현재고·안전재고·상품 `lead_time_days`/`min_order_unit` 데이터는 존재하므로 (`services/product-service/src/main/resources/db/migration/V5__add_ecount_product_fields.sql:22-26`) 구현 기반은 있으나 예측식과 산출물은 아직 없다.

## 필수 질문 최종 답

1. **레거시 데이터 원천·열**
   - 입출고 내역: Drive의 `이카운트입출고내역.xlsx`를 임시 Google Sheet로 변환해 첫 시트 2행 헤더/3행 이후 데이터를 읽는다. 열은 `품목명`, `일자`, `입고수량`, `출고수량`이다 (`tools/legacy-gas/입출고 내역/code.js:14-42`).
   - 입출고 분석: Drive의 출고·입고 전용 폴더 안 모든 CSV를 합치며, 포함문자 기준 `품목명`, `수량`, `일자` 열을 찾는다. 날짜 열이 없으면 첫 열을 쓴다 (`tools/legacy-gas/입출고 분석/Code.js:47-51`, `:86-99`, `:118-145`).

2. **집계 단위·기간**
   - 둘 다 핵심 집계 단위는 **월별**이다. 일별 집계/표현은 없다.
   - 입출고 내역은 서버가 파일의 모든 유효 월을 집계하고 화면이 선택 월 범위를 최대 12개월로 자른다 (`code.js:50-70`, `index.html:256-279`, `:396-413`).
   - 입출고 분석은 1~12월 필터이며 2025/2026을 비교한다. 연도 하드코딩은 현재 기준 낡았다 (`Code.js:176-180`, `Index.html:319-354`).

3. **필터·분류 규칙**
   - 위 두 대조표에 원문과 실제 행번호로 전부 열거했다. 핵심은 내역의 괄호 제거/`사용`/한글 전용/`L-` 제외와, 분석의 CSV 행 제외/괄호·공백 제거/6개 접두사/모델 길이/접두사별 분류·실내기 판별이다.

4. **분석이 계산하는 정확한 값**
   - **추이**: 2025 월별 출고와 2026 월별 출고를 선차트로 비교한다.
   - **증감률**: 퍼센트를 표시하지 않는다. 2026에 관측값이 있는 월의 누적 출고 ÷ 같은 월들의 2025 누적 출고를 내부 배율 `rate`로만 계산한다 (`Index.html:364-377`).
   - **예측**: 마지막 2026 관측 월 이후 각 월에 `2025 해당 월 출고수량 × rate`를 반올림한다 (`Index.html:379-382`). 이는 출고수요 예측이지 구매예측이 아니다.
   - **부가 분석**: 전 기간 모델별 출고 Top/Bottom 3, Top 1의 누적 입고-출고 기반 발주 권장/주력 상품, `rate > 1.1` 수요 상승 알림이다 (`Index.html:388-403`).

5. **현행 대응 화면**
   - **입출고 내역: 없음. 입출고 분석: 없음.** 실제 라우트 정본과 최종 catch-all을 확인했다 (`clients/desktop/src/renderer/routes/index.tsx:333-348`, `:425-591`, `:1715-1720`).
   - `/sales`, `/purchases`, `/inventory/stock-balance`, `/inventory/safety-stock-alerts`는 각각 전표 목록·현재고·임계값 알림의 일부 원천만 제공하며 레거시 표현 데이터와 분석 동작을 충족하지 않는다.

6. **이익률용 구매액·판매액의 현행 DB 존재 여부**
   - **있다.** 1차 원천은 `slip_db.slips.slip_type/slip_date`와 `slip_db.slip_lines.product_id/product_name/model_name/quantity/unit_price/line_total/unit_price_with_vat/supply_amount/vat_amount`다 (`V1__init_slip_service.sql:16-27`, `:69-78`; `V12__add_ecount_slipline_fields.sql:16-18`). 회계 확정용 매출·매입 전표/라인에도 총액과 품목별 공급가·부가세·합계가 있다 (`V18__add_sales_accounting_slips.sql:4-15`, `:39-49`; `V19__add_purchase_accounting_slips.sql:4-15`, `:39-49`).
   - **단, 품목별 회계 영업이익·순이익을 완성할 데이터는 없다.** 판관비·영업외손익·법인세 분개에는 품목 축/배부키가 없다 (`V1__init_accounting_service.sql:99-124`). 구매·판매액만으로 만들 수 있는 것은 매입·매출 차액/차익률이며, 회계 명칭의 영업이익·순이익에는 별도 배부 정책과 데이터가 필요하다.

## 최종 판정

- **입출고 내역: 미계승.** 현행에 판매·구매·재고 원천은 있지만 단일 모델 월별 입고·출고 비교, 레거시 필터, 연속 월 0 채움, 막대차트가 없다. 결정된 복수 칩과 품목별 이익률은 원본보다 넓은 신규 범위다.
- **입출고 분석: 미계승.** 현행에는 레거시의 전년/당년 출고 추이, 단순 수요예측, Top/Bottom, 추천·알림이 없고 판매추이 기반 구매예측도 없다.
- 구현 전 결정이 필요한 유일한 데이터 정책은 **품목별 `영업이익`·`순이익`의 비용 배부 정의**다. 이 정의 없이 구매액·판매액만 빼서 두 회계 명칭을 붙이면 값의 의미가 틀린다.
