## 1. 결함 · 실 사용자 재현 · 재현 난이도

### F1 — 새 거래처 DC를 기다리는 동안 직전 거래처의 늦은 bulk 최근단가가 현재 거래처 라인에 적용되고 저장까지 열린다

R82는 거래처 변경 때 새 DC를 먼저 기다린 뒤 bulk 최근단가 조회를 시작하도록 바꿨다. 그러나 새 거래처 선택 순간에는 이미 진행 중인 직전 거래처의 공용 훅 세션을 무효화하지 않는다.

좌표:

- `clients/desktop/src/renderer/routes/SlipFormPage.tsx:1058-1064`
  - 거래처 세대(`dcRequestSeqRef`)와 현재 거래처 ref는 즉시 바꾸지만 `partnerReprice.invalidate()`는 `partner=null`일 때만 호출한다.
- `clients/desktop/src/renderer/routes/SlipFormPage.tsx:1088-1097`
  - non-null 거래처는 새 DC promise를 만든 뒤 `refreshAutoPricesForPartner`로 넘긴다.
- `clients/desktop/src/renderer/routes/SlipFormPage.tsx:968-973`
  - 새 DC가 끝나야 새 `partnerReprice.run()`이 시작된다. 그 전까지 훅의 `activePartnerRef/requestRef`는 직전 거래처 run을 여전히 current로 본다.
- `clients/desktop/src/renderer/routes/SlipFormPage.tsx:975-997`
  - bulk 완료 뒤 `isCurrent()`만 검사하고 현재 `dcRequestSeqRef`·`selectedPartnerIdRef`를 다시 검사하지 않는다. 품목과 `priceSource`가 같으면 직전 거래처 outcome을 현재 라인에 쓰고 `lookupLoading=false`로 내려 저장 차단도 푼다.
- 대조: `EstimateFormPage.tsx:1150-1158`, `SlipDetailPage.tsx:2761-2770`은 `partnerRepriceSessionIsCurrent()`로 훅 current뿐 아니라 소비자 세대와 현재 거래처까지 함께 검사한다. `SlipFormPage`만 이 공용 가드를 사용하지 않는다.

실 사용자 재현:

1. 판매전표 신규 화면에서 거래처 A와 자동단가 품목을 선택해 라인을 만든다.
2. 거래처 B를 선택한다. B의 DC 응답은 완료시키고 `POST /slips/price-memory/bulk` 응답만 지연시킨다.
3. bulk가 진행 중인 상태에서 거래처 A를 다시 선택하고, 이번 A의 `GET /api/v1/partner-dc-configs/{code}` 응답을 지연시킨다.
4. A DC가 끝나기 전에 B bulk를 반환한다. 같은 라인·품목은 B outcome 단가와 `discountInfo`로 바뀌고 `lookupLoading`이 false가 된다.
5. 현재 화면 거래처는 A인데 저장 버튼이 활성화된다. 이 창에서 저장하면 서버는 화면 단가를 권위값으로 한 번 보존하므로 B 단가가 A 전표에 저장된다.

`A→B→A`뿐 아니라 `A→B`에서도 B DC 대기 중 늦은 A bulk가 같은 방식으로 적용될 수 있다. DC 제한시간이 5초이므로 직전 bulk가 그 안에 끝나면 창이 실제로 열리며, DC timeout 뒤 새 bulk까지 이어지는 경우 전체 대기 구간은 더 길어진다.

재현 난이도: **보통**. 화면 동작은 거래처 선택과 저장뿐이며, 두 응답의 순서만 지연 제어하면 결정적으로 재현된다. 이 PC의 Browser 플러그인 설치본에는 필수 `scripts/browser-client.mjs`가 없어 실화면 자동 조작은 중단했고, 금지된 Playwright 드라이버나 별도 자동화로 우회하지 않았다.

## 2. 불변식 · fix 지시 · 양방향 RED

불변식:

1. 거래처를 선택하는 순간 직전 거래처의 모든 DC/최근단가 세션은 즉시 stale이어야 한다.
2. 비동기 outcome 적용 직전에는 훅 세대뿐 아니라 `requestSeq === dcRequestSeqRef.current`와 `partnerId === selectedPartnerIdRef.current`도 모두 참이어야 한다.
3. 현재 거래처의 DC+bulk가 끝나기 전에는 직전 응답이 `lookupLoading`을 내려 저장을 열 수 없어야 한다.
4. `USER` 단가는 거래처 bulk·DC 단건·최근단가 단건 어느 응답도 덮지 않아야 한다.

fix 지시:

- non-null 거래처 선택 직후에도 `partnerReprice.invalidate(partner.id)`로 진행 중 직전 run을 즉시 무효화한다.
- bulk 완료 적용 가드는 `partnerRepriceSessionIsCurrent(requestSeq, dcRequestSeqRef.current, partnerId, selectedPartnerIdRef.current, isCurrent())`와 동등한 세 조건으로 묶는다. 한 군데만 고치지 말고 즉시 무효화와 적용 직전 소비자 세대 검사를 함께 둔다.
- stale run은 라인 값·`discountInfo`·`lookupLoading`·`priceRefreshChanged`·aria-live 중 어느 것도 쓰지 않아야 한다.

RED:

- B bulk를 pending으로 둔 뒤 A를 다시 선택하고 A DC도 pending으로 둔다. B bulk를 먼저 resolve해도 A 화면 단가·`discountInfo`가 B 결과로 바뀌지 않고 저장은 계속 비활성화되어야 한다.
- 이어 A DC와 A bulk miss를 완료하면 A의 고정/전역DC 결과로만 수렴해야 한다.
- 같은 순서에서 라인을 USER로 편집하거나 품목 교체·라인 삭제를 한 뒤 B bulk를 resolve해도 현재 값/라인을 쓰지 않아야 한다.
- A DC가 5초를 넘겨 timeout된 뒤 원 DC가 늦게 도착해도 확정 결과와 안내를 다시 쓰지 않아야 한다.

### USER·경합·공용 컴포넌트 전수

- 단건 DC 응답은 `current.priceSource !== 'USER'`, 단건 최근단가 응답은 `current.priceSource === 'USER'` 차단, bulk 적용은 `isAutoPriceSource(candidate.priceSource)` 재검사로 USER를 보호한다.
- 빠른 품목 교체는 `candidate.productId !== outcome.productId`, 라인 삭제는 현재 배열에 key가 없으므로 차단된다. 이번 F1은 품목/라인은 같고 거래처만 달라 이 두 가드를 통과하는 별도 축이다.
- `LineRow.tsx` 변경은 optional `LineDraft.hasVariableDiscount` 타입 필드 1개뿐이다. production `<LineRow>` 직접 사용처는 `SlipFormPage` 1곳이며, 견적은 `EstimateLineRow`, 분개는 `JournalLineRow`, 주문/회계전표는 별도 컴포넌트를 쓴다. 판매전표 외 렌더 동작 변경은 없다.
- 저장된 기존 전표 열기·수정·revision 복원은 `SlipDetailPage`/서버 복원 경로, 전표 복사는 `POST /slips/{id}/duplicate`, 견적·주문 전환은 각 서버 publish/convert 경로다. 신규 `SlipFormPage`는 `emptyLine()`으로 시작하는 `/sales/new`·`/purchases/new` 전용이며 R82 재계산이 기존 확정 단가를 열기 순간 바꾸는 경로는 확인되지 않았다.
