# PR #1131 R1 — 수정 화면 BUNDLE 품목 저장 차단 fix directive

## 도달 결함

판매전표 DRAFT 상세에서 `직접 수정`을 열고 품목 자동완성에 노출된 활성 BUNDLE을 선택하면 화면은 정상 신규행으로 승격하지만, 저장은 HTTP 400으로 차단된다.

실측 표본:

- 전표: throwaway `2026/08/10-17`
- 선택 1: `AC023CS1DBC1SY` (`product_type=BUNDLE`, `usage_scope=BOTH`)
- 선택 2: `AC032CS1DBC1SY` (`product_type=BUNDLE`, `usage_scope=BOTH`)
- 화면/협업: 두 품목 모두 신규행으로 승격되고 상대 피어에도 같은 행으로 도착
- 저장 요청: 기존행은 기존 `lineId`, 두 신규행은 각각 `lineId:null`
- 서버 원문: HTTP 400 `{"code":"INVALID_INPUT","message":"세트 품목은 구성품으로 전개해 저장해 주세요."}`
- DB: 저장 전후 활성 라인 1건으로 동일 — 사용자가 선택한 두 품목과 기존행 편집값 모두 저장되지 않음

## 불변식

판매전표 수정 화면의 품목 자동완성에서 사용자가 선택할 수 있는 활성 품목은 저장 가능한 표현으로 승격되어야 한다.

- SINGLE: 신규 평면행 1건, payload `lineId:null`.
- BUNDLE: 생성 화면과 동일한 구성품 전개 결과로 승격하고, 전개 완료 전 저장은 명시적으로 대기시킨다.
- 기존행: 상세 응답의 서버 `lineId`를 payload에 그대로 되돌려 보내 계보를 보존한다.
- 어떤 경우에도 UI에서 정상 선택을 확정시킨 뒤 서버 400으로 뒤늦게 거부하거나 입력을 조용히 버리면 안 된다.

## 양방향 RED

### RED-A — BUNDLE 정상 선택·전개·저장

1. 활성 DRAFT OUTBOUND 전표에 기존 SINGLE 1행을 둔다.
2. 수정 화면 trailing draft에서 활성 BUNDLE `AC023CS1DBC1SY`를 선택한다.
3. 두 피어에서 전개된 구성품 행과 수량이 같은 정체성으로 수렴하는지 확인한다.
4. 전개 완료 직후 저장한다.
5. PUT payload에는 BUNDLE 부모 원본이 없어야 하고, 생성 화면과 동일한 구성품 집합·세트 계보 표현이 있어야 한다.
6. HTTP 2xx 및 DB 구성품 저장을 단정한다. 현재 HEAD는 HTTP 400으로 RED.

### RED-B — SINGLE 신규행·기존행 lineId 무회귀

1. 활성 DRAFT OUTBOUND 전표의 기존행 서버 `lineId`를 고정한다.
2. 두 피어에서 기존행 수량/단가를 교차 편집한다.
3. trailing draft에서 활성 SINGLE `ACL-KORGHP07`을 선택하고 상대 피어가 같은 신규행 수량을 변경한다.
4. 저장 payload가 기존행에 고정한 서버 `lineId`, 신규 SINGLE에 `lineId:null`을 각각 싣는지 단정한다.
5. HTTP 2xx 후 DB에 기존 품목 편집값과 신규 SINGLE이 함께 저장되는지 단정한다.
6. 현 HEAD 라이브 기준 이 경로는 200 및 DB 2행으로 GREEN이므로 BUNDLE 수정 과정에서 깨지면 안 된다.

## 반대급부

- 수정 화면에 생성 화면의 BUNDLE 전개를 연결하면 비동기 구성품 조회·가격/DC 계산 동안 저장 지연이 생긴다. 사용자가 저장 버튼이 고장 났다고 오해하지 않도록 `세트 구성품 반영 중… 저장할 수 없습니다.` 상태를 명시해야 한다.
- BUNDLE을 자동완성에서 단순 제외하면 즉시 400은 사라지지만 이슈 #1071의 “수정 화면 품목 추가” 기능을 유효 품목 일부에서 제거한다. 이는 fix가 아니다.
- 부모 BUNDLE을 서버 PUT에 그대로 허용하는 방향은 `SalesSlipUpdateService`의 명시 계약과 생성 화면 정본을 깨므로 금지한다. 클라이언트에서 생성 화면과 같은 전개 결과로 수렴시킨다.
