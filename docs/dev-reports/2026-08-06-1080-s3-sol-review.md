# #1080 S3 2차 적대검증(SOL) — PR #1081

## 결론

**BLOCK — 머지 권고하지 않는다.**

`#1073` 이후 `origin/main`이 UI 경로에 32건만 넣던 상태와 비교하면, HEAD는 5,587건 배열의 **개수와 양 끝값이 `SearchResultSelectionModal` mock 경계에 도착하는 것**까지는 되찾았다. 그러나 중간 5,585건의 동일성·순서·중복·누락은 관찰하지 않고, 제품 `SearchResultSelectionModal`은 통째로 mock되어 실제 선택 가능한 DOM은 여전히 32건뿐이다. 따라서 사후 적대검증이 요구한 **5,587건 전수 전달·렌더 완전성**은 복원되지 않았다.

비용 상한도 복원되지 않았다. 현재 `domElementCount`는 제품 모달이 아니라 32건 표본을 만드는 테스트 mock의 DOM을 세며, 실측 516개에 상한 100,000개를 적용한다. 제품 모달의 행 구조 회귀와 5,587건 규모에 따른 비용 증가는 이 값에 반영되지 않고, 관찰되는 표본 비용도 약 193.8배 증가해야 실패한다.

반면 제품 런타임 코드는 변경되지 않았고, 변경 테스트에는 `performance.now()`·`Date.now()`·시간 기반 단정·명시적 timeout이 없다. 지정된 전체 테스트는 26 files / 189 tests 전부 통과했다. 테스트 통과는 아래 불변식 미충족과 별개다.

## 1. `origin/main`과 HEAD 대조

### `origin/main` (`#1073` 이후)

- 5,587건 fixture와 786,730바이트를 테스트 내부에서 만든다.
- 실제 `searchPartners` 반환값은 `items.slice(0, 32)`다.
- 제품 `SearchResultSelectionModal`이 32개의 radio를 렌더하는지만 본다.
- 따라서 33~5,587번째 항목은 `PartnerAutocomplete`에 전달되지 않는다.

### HEAD S2

- `searchPartners`는 `items` 5,587건 배열을 반환한다 (`PartnerAutocomplete.cost.test.tsx:67`).
- `AsyncAutocomplete` 제품 코드는 검색 결과를 `setSelectionCandidates(results)`에 넣고 모달 `options`로 넘긴다 (`AsyncAutocomplete.tsx:360-365`, `783-791`).
- 그러나 테스트가 제품 모달을 mock으로 치환한다 (`PartnerAutocomplete.cost.test.tsx:14-45`).
- mock은 `options.length`, 첫 label, 마지막 label만 probe에 기록한다 (`:28-30`).
- 실제 `getLabel`·`renderOption` 호출 및 radio 생성은 `options.slice(0, 16).concat(options.slice(-16))`, 즉 32건에만 수행한다 (`:31-40`).

### 판정

`origin/main`보다 **개수 수준의 경계 전달**은 강화됐다. 실제 실행 로그의 `modal radios=32`는 UI가 전 건을 렌더했다는 뜻이 아니고 mock 표본 수다.

다음 전수 계약은 관찰되지 않는다.

- 중간 5,585건 각각이 입력 fixture와 동일한지
- 1~5,587번 전체의 순서가 보존됐는지
- 중간 항목에 누락·중복·치환이 없는지
- 전 건이 제품 모달에서 실제 선택 가능한 결과로 만들어지는지

동일 길이를 유지한 채 중간 항목을 누락·중복·치환하는 회귀와, 제품 모달이 33번째 이후 렌더를 절단하는 회귀는 현재 단정을 통과할 수 있다.

## 2. 비용 상한의 검출력

현재 단정은 다음 값을 센다.

```text
dialog.querySelectorAll('*').length
실측: 516
상한: 100,000
여유 배수: 100,000 / 516 = 약 193.8
```

이 `dialog`는 제품 `SearchResultSelectionModal`의 DOM이 아니라 테스트 mock이 만든 DOM이다. 따라서 다음 비용 회귀는 검출하지 못한다.

- 제품 모달의 label/row/container 구조가 항목당 비대해지는 회귀
- 제품 모달이 5,587건에 대해 수행하는 `options.map(...)` 비용의 회귀
- 결과 수 N에 따라 커지는 DOM·메모리 비용의 회귀
- 제품 모달에서 전수 렌더가 다시 5초를 넘는 회귀

표본 32건의 `PartnerAutocomplete.renderOption` 구조가 극단적으로 커지면 실패할 수 있으므로 완전히 상수인 단정은 아니다. 그러나 5,587건 사용자 경로의 비용 상한으로서는 대상과 규모가 다르고, 현재값 대비 상한도 지나치게 느슨해 실질 검출력이 없다.

## 3. 사실상 무력화되거나 중복된 단정

1. `responseBytes > 700,000`은 테스트가 자체 생성한 고정 fixture의 직렬화 결과다. 제품 응답이나 컴포넌트 처리 결과와 독립적이라 UI 회귀에는 무력하다. 이 문제는 `#1073` 사후검증 때부터 지적됐다.
2. `modalProbe.optionCount === items.length`와 mock 내부의 `modal-option-count` text 단정은 같은 `options.length` 값을 두 번 읽는다. 항목별 완전성을 추가로 보장하지 않는다.
3. `radios.length === 32`는 mock이 16+16 표본을 만들도록 테스트 자체에서 고정한 결과다. 제품 모달의 렌더 개수 계약을 검증하지 않는다.
4. 첫·마지막 label 단정은 경계 두 건에는 유효하지만 중간 5,585건의 누락·중복·순서 손실에는 무관하다.
5. `domElementCount <= 100,000`은 제품 모달을 제외한 516개 mock DOM에 적용되어 요구된 대규모 비용 경계를 지키지 못한다.

미도달 분기는 발견하지 못했다. 다만 제품 모달 구현 전체가 module mock 때문에 이 테스트에서 도달하지 않는다.

## 6. 미충족 불변식

구현 수단을 지정하지 않고 되찾아야 할 계약만 적는다.

- **I-1 전수 전달 동일성:** 서로 다른 5,587개 검색 결과가 반환되면 1번부터 5,587번까지 각 항목의 식별자·순서·개수가 중간 경계에서 누락·중복·치환 없이 보존돼야 하며, 검증은 개수와 양 끝값만으로 대체될 수 없다.
- **I-2 전수 선택 가능성:** 전달된 5,587개 결과는 모두 사용자가 선택 가능한 결과 집합에 존재해야 하며, 33번째 이후의 절단 또는 미렌더가 검증을 통과해서는 안 된다.
- **I-3 제품 경로 비용 경계:** 비용 상한은 제품 사용 경로가 실제로 만드는 계산·DOM·메모리 비용을 대상으로 해야 하며, 결과 수 증가 또는 제품 모달 구조의 회귀가 측정값에 반영돼야 한다.
- **I-4 유효한 상한:** 비용 상한은 정상 기준값과 분리 가능한 합리적 여유를 가지면서 의미 있는 회귀를 실패시켜야 하고, 정상값보다 수백 배 느슨해 사실상 무제한인 값이어서는 안 된다.
- **I-5 결정성:** I-1~I-4의 판정은 `performance.now()`·경과시간 비교·CI 러너 순간 부하·경계에 가까운 timeout에 의존하지 않아야 한다.
