# PR #1128 S1 — 기존 재고 데이터 상태 진단

> 진단일: 2026-08-10 (KST)  
> 대상: PR #1128 / Issue #999 / 공유 `samhan-postgres`  
> 범위: 읽기 전용 SQL·API·코드 경로 조사. 코드·DB 수정 없음.

## 0. 결론

- 최우선 결함은 해소되지 않았다. 현재 활성 `stock_balances`는 **202행**, 참조 product UUID는 **102개**다. 그중 product DB 활성 행과 연결되는 것은 **2개**, soft-delete 행과 연결되는 것은 **100개**, product DB 자체에 전혀 없는 것은 **0개**다. 따라서 **활성 카탈로그 누락은 여전히 100개**다.
- #1113 당시 `201행 / 101 UUID / 활성 1 / 삭제 100`에서 바뀐 것은 정상 연결 1건뿐이다. 추가 `stock_balances` 1행의 생성일은 `2026-08-01 19:45:21`, 연결 product 생성일은 `2026-07-28 20:33:34`이므로 오늘 머지된 #1133·#1154보다 먼저 존재했다. 문제의 삭제 참조 100개는 그대로다.
- 실제 `GET /inventory/balances?page=0&size=20`은 부분 행이나 공백을 반환하지 않고 **HTTP 404 전체 실패**로 끝난다: `일부 제품을 찾을 수 없습니다 (요청 100, 응답 2)`. 데스크톱은 이 실패를 오류 alert로 표시하고 grid에는 성공 행을 넣지 않는다. 즉 현재 확인된 동작은 **공백/개별 행 사라짐이 아니라 화면 전체 조회 오류**다.
- `stock_instances`는 존재하며 활성 **20행 / 9 product UUID / 9 product_code**다. 상태는 `AVAILABLE 6`, `SHIPPED 14`다. 이 9 UUID 중 활성 product 연결 8, 삭제 product 연결 1이다.
- 노출 코드 선례는 있지만 재고 인스턴스용으로 확정된 선례는 없다. 같은 inventory-service의 실사번호·재고이동번호와 전표번호는 `yyyy/MM/dd-N` 일별 일련번호다. 노출 코드에 체크섬을 붙이는 선례는 찾지 못했다. 이것은 형식 추천이 아니라 현재 코드 조사 결과다.
- `clients/mobile-staff`에는 QR/바코드 스캔 화면·라우트·scanner 의존성이 없다. 사진 촬영용 `expo-image-picker`만 있다. inventory-service에는 재고 실사 라인의 `scanned` 기록 계약은 있으나 QR 값을 읽어 입출고하는 진입점은 없다.

## 1. 최우선 — 기존 재고와 product 참조 정합성

### 1.1 SQL 원문과 결과

DB가 서비스별 database로 분리되어 있고 `dblink`/FDW가 설치되어 있지 않다. 따라서 아래 1차 SELECT로 inventory UUID 집합을 읽고, 그 결과 102개를 **DB write 없이** product DB의 `VALUES` CTE에 바인딩했다. 보고서에는 UUID 비노출 규칙 때문에 개별 UUID literal을 남기지 않고 개수만 표시한다. 실행 당시 생성 SQL에는 102개 literal이 들어갔다.

```sql
-- inventory_db
SELECT
  COUNT(*) AS stock_balance_rows,
  COUNT(DISTINCT product_id) AS referenced_product_uuids
FROM stock_balances
WHERE is_deleted = FALSE;
```

```text
 stock_balance_rows | referenced_product_uuids
--------------------+-------------------------
                202 |                     102
```

```sql
-- product_db
-- inventory_db의 DISTINCT product_id 102개를 VALUES에 바인딩
WITH inventory_product_ids(product_id) AS (
  VALUES /* 102 UUID literals; 문서에서는 UUID 비노출 규칙으로 생략 */
),
matched AS (
  SELECT i.product_id,
         p.id IS NOT NULL AS exists_any,
         COALESCE(p.is_deleted, FALSE) AS is_deleted
  FROM inventory_product_ids i
  LEFT JOIN products p ON p.id = i.product_id
)
SELECT
  COUNT(*) AS referenced_product_uuids,
  COUNT(*) FILTER (WHERE exists_any AND NOT is_deleted) AS active_catalog_matches,
  COUNT(*) FILTER (WHERE exists_any AND is_deleted) AS deleted_catalog_matches,
  COUNT(*) FILTER (WHERE NOT exists_any) AS absent_from_products,
  COUNT(*) FILTER (WHERE NOT (exists_any AND NOT is_deleted)) AS missing_from_active_catalog
FROM matched;
```

```text
 referenced_product_uuids | active_catalog_matches | deleted_catalog_matches | absent_from_products | missing_from_active_catalog
--------------------------+------------------------+-------------------------+----------------------+----------------------------
                      102 |                      2 |                     100 |                    0 |                         100
```

삭제 여부별 독립 재확인도 정확히 `false 2 / true 100`이었다.

```sql
WITH inventory_product_ids(product_id) AS (
  VALUES /* 같은 102 UUID literals */
)
SELECT is_deleted, COUNT(*) AS matched_products
FROM products
WHERE id IN (SELECT product_id FROM inventory_product_ids)
GROUP BY is_deleted
ORDER BY is_deleted;
```

```text
 is_deleted | matched_products
------------+-----------------
 false      | 2
 true       | 100
```

현재 product 전체 분포도 함께 측정했다.

```sql
SELECT COUNT(*) AS all_products,
       COUNT(*) FILTER (WHERE is_deleted=FALSE) AS active_products,
       COUNT(*) FILTER (WHERE is_deleted=TRUE) AS deleted_products
FROM products;
```

```text
 all_products | active_products | deleted_products
--------------+-----------------+-----------------
         3224 |            3084 |              140
```

1. 연도·날짜+일련 선례는 있다. 가장 가까운 같은 서비스 선례는 재고 실사·재고 이동의 `yyyy/MM/dd-N`이다.

## 4. ③ QR 스캔과 입출고 진입점

### 4.1 `clients/mobile-staff`

- QR/바코드 scanner 화면, route, API client, scanner dependency: **없음**.
- 카메라 권한/촬영 기능은 있지만 첨부사진용이다. 설치 의존성은 `expo-image-picker`뿐이다: `clients/mobile-staff/package.json:25`, `app.config.js:180`, `src/components/PhotoAttachmentCapture.tsx:94-120, 214-245`.
- inventory-service에는 재고 실사 라인의 `barcode_scanned`, `scanned_at` 필드가 있고 `scanned=true` 요청을 기록한다: `V3__add_inventory_audit.sql:55-68`, `InventoryAuditLine.java:112-127`, `InventoryAuditController.java:144-149`. 이것은 **스캔 장치/QR 해석 경로가 아니라 이미 해석된 수량 입력에 scanned flag를 붙이는 계약**이다.

### 4.2 현재 inventory-service 입고·출고 경로

비시리얼 수량/lot 경로:

- 입고: `POST /inventory/lots/inbound` → `StockService.inbound`: `StockController.java:213-218`, `StockService.java:185`.
- 출고 예약/해제/차감: `POST /inventory/reserve`, `/release`, `/deduct`: `StockController.java:228-266`, `StockService.java:235, 282, 329`.

개별 instance 경로:

- 입고 생성: `POST /inventory/instances/batch`: `StockInstanceController.java:96-105` → `StockInstanceService.inboundBatch` `:106`.
- 출고 예약: `POST /inventory/instances/reserve-batch`: controller `:127-136` → service `:153`.
- 출고 확정: `POST /inventory/instances/ship-batch`: controller `:150-159` → service `:193`.
- 예약 해제: `POST /inventory/instances/release-batch`: controller `:173-181` → service `:217`.
- 반품/회차: `POST /inventory/instances/recall-batch`: controller `:194-203` → service `:244`.

상위 lifecycle 호출:

- 출고전표 `accept()`가 serial-managed면 FIFO instance reserve, 아니면 balance reserve: `SlipService.java:905-935`.
- 출고전표 `complete()`가 serial-managed면 instance ship, 아니면 lot/balance deduct: `SlipService.java:1109-1127`.
- 입고전표 `complete()`가 serial-managed면 instance N개 생성, 아니면 lot inbound: `SlipService.java:1148-1182`.
- 반품/회차 `complete()`는 instance recall: `SlipService.java:1195-1209`.
- 이 계약의 요약도 `InventoryClient.java:31-34, 152-218`에 명시돼 있다.

현재 모든 진입점은 UUID/productCode/slipNo/수량 요청 기반이다. **노출 시리얼키 또는 QR payload로 단일 instance를 찾아 입고·출고하는 endpoint는 없다.**

## 5. 명시 계약으로 확정된 2축

Issue #999 원문은 다음을 명시한다.

> 현재 `status`는 재고상황(가용·예약·출고) 축입니다. 품질 축을 별도 컬럼으로 둡니다.

| 축 | 명시 값 |
|---|---|
| 재고상황 | `AVAILABLE`, `RESERVED`, `SHIPPED` (기존 유지) |
| 품질 | 정상, 중고, 파손, 재포장, 박스불량 |

따라서 “무엇을 가르는가”는 이슈의 명시 계약으로 확정 가능하다. 단, 기존 코드에는 `RECALLED` 상태도 존재한다(`V15__create_stock_instances.sql:8,30`). 이것을 새 2축 계약에서 어떻게 취급할지는 이슈 표와 현재 코드가 완전히 일치하지 않으므로 질문으로 남긴다.

## 6. 업무 판단이 필요해 추론하지 않은 질문 목록

1. **노출 시리얼키 발급 규칙**: 접두사, 날짜/연도 포함 여부, 일련번호 폭, 발급 범위(전역/품목별/창고별), 재발급, 동시성, 체크섬 필요 여부를 확정해야 한다. 기존 선례 중 어느 것도 자동 채택하지 않았다.
2. **품질 축의 저장 값·기본값**: 한글 저장인지 enum 영문값인지, `정상/중고/파손/재포장/박스불량` 외 값·전이 규칙, 기존 20행의 backfill 값, “기록하지 않고 넘어갈 수 없음”을 DB NOT NULL/화면 필수 중 어디서 보장할지 확인이 필요하다.
3. **기존 데이터 마이그레이션**: 기존 instance 20행의 시리얼키 발급 순서·기준일과, 삭제 product를 참조하는 balance 100 UUID 및 instance 1 UUID를 복구/이관/격리 중 무엇으로 처리할지 확인이 필요하다.
4. **`RECALLED`의 축 위치**: Issue 표는 재고상황을 3개로 적었으나 현재 enum/migration은 `RECALLED`를 가진다. 재고상황 네 번째 값인지, 다른 축/이력으로 옮길지 명시가 필요하다.
5. **QR 대상 판정**: 실외기·실내기·판넬과 부자재 제외는 명시됐지만 현재 `serial_managed`/`inventory_qty_mgmt` 중 어느 필드를 정본으로 쓸지는 확정되지 않았다.

## 7. 착수 시 밟을 지뢰

- `stock_balances` 조회가 이미 전체 404다. 이 상태에서 새 instance UI만 붙이면 기존 재고 화면 결함을 가릴 수 있다.
- balance 삭제 product 참조 100개와 instance 삭제 product 참조 1개를 한 종류의 문제로 단정하면 안 된다. 행 집합과 lifecycle이 다르다.
- 기존 `stock_instances.id`를 화면/QR에 재사용하면 UUID 비노출 불변식을 즉시 위반한다. migration 주석의 옛 “UUID=시리얼 키” 문구도 정정 대상이지만 이번 진단에서는 수정하지 않았다.
- `stock_instances.product_code`는 FIFO index와 product lookup 경계다. #984 품목코드 전환과 순서를 정하지 않고 바꾸면 기존 20행이 고아가 될 수 있다.
- 일별 `max+1` 선례(주문/재고이동)는 동시 발급 안전성이 row-lock sequence 선례보다 약하다. 형식과 동시성 구현을 별개 판단해야 한다.
- QR 스캔은 mobile route만 추가해서 끝나지 않는다. 현재 backend에 시리얼키 단건 조회/전이 계약이 없고, 기존 실사 `scanned` flag는 QR decoder가 아니다.
- #999 표의 3상태와 현재 `RECALLED` 4상태 불일치를 해소하지 않고 품질 컬럼부터 추가하면 상태 의미가 다시 섞일 수 있다.

## 8. 못 한 것

- 연결 가능한 브라우저가 없어 실제 화면 PNG 캡처를 만들지 못했다. 따라서 `docs/qa/2026-08-10-1128-s1/`에는 아무 파일도 쓰지 않았다. 실제 API 404와 FE 렌더 분기는 확인했다.
- 레거시 원문에서 시리얼 발급 규칙·품질 값·마이그레이션 규칙은 찾지 못했고, 명시 계약도 없으므로 추론하지 않았다.
- 코드 수정, DB write, `tools/legacy-gas/**` 변경, commit/push/checkout/main 병합은 수행하지 않았다.
