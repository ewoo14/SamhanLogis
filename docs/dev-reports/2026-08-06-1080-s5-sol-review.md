# #1080 S5 2차 적대검증(SOL) — PR #1081

## 결론

**결함 0 — 머지를 권고한다.**

`#1073`에서 잃은 두 계약은 모두 제품 경로에서 복원됐다.

1. 서로 다른 5,587건이 `PartnerAutocomplete → AsyncAutocomplete → SearchResultSelectionModal`로 전달되고, 비가상화 제품 모달이 5,587개 radio와 5,587개 label을 실제로 만든다. 이름 배열 전체와 `partnerCode`의 개수·순서를 전수 대조하므로 33번째 이후 절단, 중간 누락·중복·치환은 통과하지 못한다.
2. 실제 제품 dialog가 만드는 DOM 89,979개에 100,000개 상한이 적용된다. 정상값 대비 여유는 10,021개, 즉 약 11.14%다. 행마다 element 1개가 늘면 95,566개로 통과하지만 2개가 늘면 101,153개로 실패하므로, 정상적인 단일 wrapper 보강은 허용하면서 반복 행 구조가 두 겹 비대해지는 회귀는 차단한다. jsdom의 element 개수는 러너 속도와 무관한 결정적 값이므로 이 여유는 적절하다.

30,000ms timeout은 이번 HEAD의 실제 지연을 숨기고 있지 않다. S5에서 전체 명령을 세 번 순차 실행한 결과 대상 테스트는 3,011–3,417ms, 전체 Vitest는 9.24–9.98s였다. S4 기록(대상 2,364–2,966ms, 전체 7.47–8.59s)보다 이번 환경이 다소 느렸지만, S5 세 회차는 `3,417 → 3,375 → 3,011ms`로 단조 악화하지 않았고 모두 같은 DOM 관찰값을 냈다. S5 최악값을 3배로 잡은 10,251ms도 timeout보다 19,749ms 작다.

제품 런타임 변경은 없고, `performance.now()`·`Date.now()`·경과시간 합격 단정도 없다. 개별 timeout은 비정상 정지를 끝내는 실행 한계일 뿐 비용 합격 기준은 아니다.

## 1. 5,587건 전수 전달·렌더 완전성

### 데이터 전달

`PartnerAutocomplete.cost.test.tsx:9-15`는 이름과 `partnerCode`가 서로 다른 5,587건을 만들고, `:26`에서 `searchPartners`가 `items` 전체를 반환한다. 제품 `AsyncAutocomplete.tsx:342`가 그 결과를 받고, 다건 모달 경로에서 배열을 자르거나 재구성하지 않은 채 `setSelectionCandidates(results)`로 저장한다(`:360-365`). 이후 같은 배열을 제품 모달의 `options`로 넘긴다(`:783-791`).

S3 때 존재하던 `SearchResultSelectionModal` module mock과 양 끝 32건 `slice`는 현재 테스트에 없다.

### 비가상화 코드 확인

`SearchResultSelectionModal.tsx`에는 virtualizer, windowing, viewport 기반 범위 계산 또는 options 절단이 없다.

- table 분기: `options.map(...)` (`:86-103`)
- 현재 PartnerAutocomplete가 타는 list 분기: `options.map(...)` (`:109-124`)
- 각 list option은 실제 `<label>`과 `<input type="radio">`를 만든다(`:113-122`).

따라서 현재 제품 컴포넌트는 **비가상화**이며, 5,587건 전부를 한 번에 DOM으로 렌더한다.

### 단정의 검출 범위

`PartnerAutocomplete.cost.test.tsx:40-46`은 다음을 함께 확인한다.

- radio 수가 정확히 5,587개다.
- 5,587개 radio의 `aria-label` 배열이 fixture 이름 배열 전체와 순서까지 동일하다.
- label 수가 정확히 5,587개다.
- 각 순번 label에 같은 순번 fixture의 고유 `partnerCode`가 들어 있다.

개수만 유지한 중간 누락·중복·치환 또는 순서 변경도 이름 배열 전체 비교에서 RED가 된다. 실제 세 회차 모두 `modal radios=5587`이었다.

## 2. 비용 상한 89,979 / 100,000 판정

상한 대상은 mock이나 32건 표본이 아니라 제품 dialog subtree 전체다(`dialog.querySelectorAll('*')`).

```text
정상값                 89,979
상한                  100,000
절대 여유               10,021
정상값 대비 여유         11.14%
상한 중 미사용 여유       10.02%
항목당 평균 element       16.10
```

이 여유는 적절하다.

- 너무 빡빡하지 않음: 반복 행마다 element 1개가 추가돼도 `89,979 + 5,587 = 95,566`으로 통과한다. 고정 모달 control 몇 개의 정상 변경도 충분히 흡수한다.
- 너무 느슨하지 않음: 반복 행마다 element 2개가 추가되면 `101,153`으로 즉시 실패한다. 현재 행 구조 대비 약 12.42%의 선형 DOM 증가는 허용하지 않는다.
- 러너 독립적임: DOM element 개수는 CPU 부하나 벽시계 편차로 변하지 않는다. 정상 구조가 그대로인 S5 세 회차도 모두 89,979였다.
- 검출력 확인됨: S4가 제품 dialog를 100,001개로 만드는 mutation에서 `expected 100001 to be less than or equal to 100000` RED를 기록했다. 현재 assertion과 대상 경로를 코드에서 대조했으며, S5는 git 쓰기 금지 때문에 mutation을 재작성하지 않았다.

## 3. 사실상 무력화된 단정·미도달 분기

목적 계약을 무력화하는 단정이나 도달하지 않는 제품 분기는 발견하지 못했다.

- `labels.every(...)`는 앞의 `labels.length === items.length` 때문에 빈 배열의 vacuous truth가 될 수 없다.
- radio 이름 배열의 전수 동일성은 개수·순서·중간 항목을 모두 관찰한다.
- DOM 상한은 정상값 89,979와 mutation 100,001을 구분한다.
- 현재 `PartnerAutocomplete`는 columns를 주지 않으므로 모달의 table 분기는 도달하지 않지만, 이 트랙의 실제 제품 경로는 list 분기다. 범위 누락이 아니다.

다만 `responseBytes > 700,000`은 테스트가 자체 생성한 고정 fixture를 다시 직렬화한 값이므로 제품 UI 회귀 검출에는 사실상 기여하지 않는다. 항상 참인 상수식은 아니지만 fixture가 유지되는 동안 자기충족적이다. 이 단정은 전수 렌더·DOM 상한 판정의 근거로 사용되지 않으며, 남아 있어도 이번 두 불변식을 약화하지 않는다.

`partnerCode` 검증의 `includes`는 label에 기대 코드가 존재하는지를 보며 텍스트 전체의 정확 일치까지 요구하지는 않는다. 그러나 고유 코드 5,587개를 같은 순번에서 전수 확인하고 이름 배열도 별도로 정확 비교하므로, 이 트랙이 막아야 할 절단·누락·중복·치환에는 유효하다.

## 4. 30,000ms timeout과 전체 실행 시간 추이

기록 비교:

| 단계 | 회차 | 대상 테스트 | 전체 Vitest |
|---|---:|---:|---:|
| S3 mock 경로 | 1 | 126ms | 6.83s |
| S4 제품 전수 경로 | 1 | 2,966ms | 8.59s |
| S4 제품 전수 경로 | 2 | 2,364ms | 7.47s |
| S4 제품 전수 경로 | 3 | 2,917ms | 8.20s |
| S5 fresh | 1 | 3,417ms | 9.98s |
| S5 fresh | 2 | 3,375ms | 9.24s |
| S5 fresh | 3 | 3,011ms | 9.29s |

S3 대비 약 3초가 늘어난 것은 mock 32건이 아니라 제품 DOM 89,979개를 다시 만드는 데 따른 의도된 비용이다. S5는 S4보다 0.05–1.05초 느린 표본을 보였으나 동일 코드·동일 DOM 개수에서 회차별 편차가 있고 단조 상승하지 않았다. 현재 테스트가 timeout 때문에 10초대나 수십 초 동안 조용히 통과하는 상태는 아니다.

30초는 현재 최악 3,417ms의 약 8.78배다. 따라서 DOM 수를 늘리지 않는 순수 계산 회귀를 30초 직전까지 성능 실패로 판정하지 않는 한계는 있다. 그러나 이 트랙이 되찾기로 한 비용 계약은 러너 독립적인 제품 DOM 구조 상한이고, 실제 실행 시간은 원문에 계속 노출된다. 현재 관찰값과 추이에 근거할 때 timeout이 새 문제를 숨긴다는 증거는 없다.

## 6. 벽시계 의존 판정

- 변경 테스트에 `performance.now()` 없음
- `Date.now()` 없음
- render elapsed 값을 비교하는 단정 없음

- `30_000`은 Vitest 실행 timeout이며 측정된 시간값을 제품 계약과 비교하지 않는다.

따라서 러너 순간 부하가 DOM 비용 단정을 RED로 바꾸는 벽시계 의존은 남아 있지 않다. 모든 테스트에는 종료 한계가 필요하므로 timeout 자체는 존재하지만, 현재 실측은 그 경계에 가깝지 않다.
