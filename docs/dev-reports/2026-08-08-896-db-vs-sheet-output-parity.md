# #896 DB 모드 대 시트 모드 출력 동등성 QA

## 환경 확인

- 판정: **불합격 — DB만으로 레거시와 같은 출력이 나오지 않는다.** 차이 0이 아니다.
- `product-service`: `samhan-product-service`, `Up 11 hours (healthy)`, `127.0.0.1:8084->8084/tcp`를 수집 전에 확인했다. Docker 재기동·재배포는 하지 않았다.
- 앱 모드: QA 담당자가 띄운 `estimate-app`에 `CATALOG_SOURCE=db`, `PRODUCT_SERVICE_URL=http://127.0.0.1:8084`, `PORT=5183`을 명시했다. `/healthz`는 `ok: true`, 앱 `estimate-app`, 버전 `2.0.0`이었다.
- DB 도달 근거: 같은 하네스가 DB 모드에서 홈멀티 119, 싱글세트 288, 싱글구성품 1,448, 상업멀티 408, 상업구성품 137, 구형 40건을 받아 5개 시나리오를 모두 완료했다. 런타임 진단에 product-service HTTP 실패는 없었다. 진단의 404 두 건은 폰트와 앱 버전 경로뿐이다.
- 동일 입력 근거: 기존 `capture-baseline.mjs`를 수정하지 않고 출력 경로만 `docs/qa/896-db-mode-output`으로 바꿔 실행했다. `05-price-scenarios.json`의 다섯 `input` 객체는 JSON 기준 모두 동일하다: `single-item`, `single-set-default`, `single-set-options`, `single-set-discount`, `freight-and-cutoff`.
- 고정 입력: `AJ060MXHNBC1` 2대, `AC060CS6PBH1SY` 기본/옵션/2세트 할인, 블랙판넬·사각·유선리모컨, 세트당 50,000원 할인, 운임 120,000원, 1,000원 절삭이다. 파생 수량 입력도 홈 `AJ060MXHNBC1=1`, `AJ012BN1PBC2=2`, `AM052BN4DBH1=1`; 상업 `AM072TNCDBH1=2`, `AM052DNLDBH1=1`로 동일하다.
- 중요한 한계: 시트 기준선 앱 SHA는 `a8bffbbb...`, 이번 DB 캡처 앱 SHA는 `ea844779...`로 서로 다르다. 따라서 아래 차이는 실제 두 산출물의 차이이지만, 그 전부를 카탈로그 소스 차이만으로 분리해서 확정할 수는 없다.
- 하네스 메타데이터 한계: `capture-baseline.mjs`가 `purpose`와 `catalogSource: "sheet"`를 상수로 기록한다. 따라서 DB 출력의 `00-metadata.json`도 잘못 `sheet`라고 적혀 있다. 코드를 수정하지 말라는 지시 때문에 고치지 않았으며, 실제 모드는 위 실행 환경과 DB 고유 건수로 판별했다.

## 비교 방법과 건수 정의

- 01은 `source + setModel + model + feature`, 02는 `sector + setModel + partModel + feature`, 03 구성품은 `setModel + model + feature`를 문맥 키로 삼았다.
- `시트에만 있음`/`DB에만 있음`은 같은 문맥 키의 행 수가 한쪽에 더 많은 경우다.
- `양쪽 값 다름`은 같은 문맥 키로 짝지어진 레코드에서 하나 이상의 필드가 다른 경우다. `값 셀`은 서로 다른 개별 필드 수다.
- `kind`의 한국어 값과 DB 영문 enum도 실제 출력값 차이로 세었다. 업무적으로 동등하다고 추측해 제외하지 않았다.

- 예: `SINGLE_SET / AR-EH05`는 시트 `16,000` / DB `13,915`.

### 141/132 다중 문맥 그룹과 실제 출력

- 이번 시트 기준선의 인상 탭 출력에서 동일 `모델 + 가격필드`가 문맥별 여러 값을 가진 그룹은 `price` 129개, `list` 5개, 합계 **134개**였다. DB 출력은 `price` 1개, `list` 1개, 합계 **2개**였다.
- 구성품만 보면 시트는 `price` 124개 + `list` 3개 = **127개**, DB는 **0개**다.
- 대표적으로 `PC6NUNK1NW.price`는 시트에서 홈멀티 문맥 `104,060`, 싱글 구성품 문맥 `128,000`을 함께 가진다. DB의 싱글 구성품 출력은 `104,060`으로 수렴한다.
- `AC060CXAPBH1.price`는 시트 구성품 문맥에서 `910,000`, `820,000`, `900,000`의 세 값을 가진다. DB 구성품 출력에서는 이런 다중 문맥 그룹이 0개다.
- 따라서 선행 판정의 핵심인 **한 모델·한 필드의 문맥별 여러 값이 현재 DB 출력에서 보존되지 않고, 실제 출력 차이로 나타난다**는 점은 확인됐다. 다만 이번 캡처에서 다시 센 수치는 134개이며, 선행 수치 141/132와 숫자까지 동일하다고 확정하지는 않는다.

## 단가변동 토글

- DB 모드 실측 기본값: 홈 `ON`, 싱글 `OFF`, 상업 `OFF`.
- DB 모드에서 세 토글을 모두 `OFF`와 모두 `ON`으로 바꾸어 전체 카탈로그 계산을 비교했다. 변경 셀은 홈 납품가 0·출고가 0, 상업 납품가 0·출고가 0, 싱글 구성품 납품가 0·출고가 0건이었다.
- DB는 `PRICE_INC` 키를 홈 115, 상업 412, 싱글 288개 주입했지만, 실측 계산값은 OFF/ON이 같았다.
- `AC060CS6PBH1SY` 기본 세트도 DB OFF/ON 모두 총액 1,660,000원이었고 네 구성품 단가가 각각 616,975 / 925,050 / 104,060 / 13,915로 같았다.
- 시트 기준선에서 기본 토글은 세 축 모두 `OFF`였다. 기존 05 시나리오는 이 OFF 상태의 출력이다.
- 시트 서버를 별도로 띄워 ON/OFF 재실측을 시도했으나 90초 안에 카탈로그 배열이 채워지지 않아 중단했다. 따라서 시트 ON 출력과 주문서 납기일 자동 전환은 이번 라운드에서 확정하지 못했다.

## DB에 더 넣어야 할 것 — 이관 작업 목록

1. `COMMERCIAL_COMPONENT`의 시트 전용 380개 문맥을 비롯한 시트 전용 398행을 DB 카탈로그/구성 문맥에 넣고, DB 전용 103행은 레거시 출력 포함 여부를 근거로 정리한다.
2. 세트별 구성품 관계를 `세트 모델 + 구성품 모델 + 특징` 문맥으로 보존한다. 현재 빠진 싱글/상업 구성과 수량을 채워 02의 시트 전용 171행을 없앤다.
3. 구성품 종류의 레거시 표시값(`실내기`, `실외기`, `판넬`, `리모컨` 등) 또는 그와 1:1인 출력 매핑을 넣는다. 현재 영문 enum이 그대로 출력된다.
4. 단위(`대` 대 `EA`), 용량, 규격, 고정DC, 명칭을 문맥별 레거시 값으로 채운다. 한 모델의 전역 단일값으로 합치지 않는다.
5. 옵션 특징과 기본값을 세트별로 채운다. 시트 전용 특징 5행, DB 전용 특징 2행을 정리하고 `chkHomeInc` 기본값도 레거시 `false`와 맞춘다.
6. 가격은 최소한 `세트/카탈로그 구분 + 세트 모델 + 구성품 모델 + 종류/특징 + 가격필드(price/list) + 단가변동 상태`를 구분할 수 있게 보존한다. 현재 `(product_id, effective_date)`당 한 행으로는 관찰된 다중 문맥 값을 담지 못한다.
7. 기본 세트의 구성품 단가/출고가와 옵션 교체 차액을 레거시 셀 값으로 채운다. 특히 `AC060CS6PBH1SY`의 실내기·실외기·판넬·리모컨 및 블랙판넬/유선리모컨 문맥을 우선 회귀 대상으로 삼는다.
8. 단가변동 OFF/ON이 실제 서로 다른 값을 내도록 인상 전/인상 후 값을 별도로 넣고, 카테고리별 기본 토글 값을 함께 이관한다.
9. 파생 수량 자체는 유지하되 `실링 드레인펌프`, `무선리모컨(무풍)` 등 레거시 출력 명칭을 보존한다.

이 목록은 관찰된 출력 차이를 없애기 위한 데이터 요구사항이다. 각 값의 업무상 의미나 DB 전용 행을 삭제해야 하는지는 이 QA에서 추측하지 않는다.

## 확정하지 못한 것

1. 선행 수치 비인상 141개·인상 132개를 이번 라운드에서 숫자까지 재현하지 못했다. 현재 시트 기준선 인상 출력에서는 134개를 셌고, 비인상 시트 ON 재수집은 로드 타임아웃으로 실패했다.
2. 시트 모드의 단가변동 ON 결과는 확정하지 못했다. 기존 기준선은 OFF 결과만 제공한다.
3. 주문서의 납기일 자동 전환은 이 견적서 하네스의 범위 밖이어서 확정하지 못했다.
4. 기준선과 DB 캡처의 앱 커밋 SHA가 다르므로 차이 중 코드 변경분과 소스 변경분의 비율은 확정하지 못했다.
5. DB 전용 103행과 시트 전용 398행 각각의 업무상 정당성은 확정하지 못했다.
6. `00-metadata.json`의 `catalogSource: "sheet"`는 하네스 상수 때문에 DB 캡처에서도 잘못 기록됐다. 파일을 수정하지 않았으므로 메타데이터 필드 자체만으로 DB 모드를 증명할 수 없다.
