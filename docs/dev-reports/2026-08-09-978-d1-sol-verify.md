# PR #1127 D-1 fix SOL 적대 검증

검증 기준은 `feat/978-fast-path-carryover` HEAD `a4f139f2d8af37a74c653f41cc607c6aa2b92004`이다. 코드, 실 PostgreSQL, 실 Google Sheet, Docker 배포에는 쓰지 않았다. Google Sheet 공개 CSV와 PostgreSQL에는 읽기만 수행했다.

## 0. 먼저 바로잡을 증거

- 사용자 요약의 핵심 원인과 fix 방향은 사실이다. `ProductSheetSyncService`의 프로세스 로컬 hash가 트랜잭션보다 먼저 성공을 기억했던 결함을 DB 현재 상태 비교로 바꿨다.
- `ProductSheetSyncServiceIT` 결과는 직접 재현됐다. `--rerun-tasks` 실행 원문은 `XML_TESTS=36 FAILURES=0 ERRORS=0 SKIPPED=0`, Gradle exit `0`이다.
- “`grep -rn lastKnownRowHash` 0건”은 **코드 범위**라면 사실이다. `services/product-service/src/main`과 `src/test`에서 0건이다. 저장소 전체를 문자 그대로 grep하면 과거 dev-report와 handoff에 역사 기록이 남아 있으므로 0건이 아니다.
- fix 보고서의 “`ProductLookupSheetSyncService.lastKnownRowHash`가 남아 있다”는 문장은 최종 HEAD에서는 낡았다. 뒤의 `origin/main` 병합으로 lookup 계층도 DB 직접 비교가 됐고, 운영 코드의 해당 필드는 없다.
- 브리프의 “빈칸=0이면 `680,000 ↔ 0` 충돌”은 **2026-08-09 현재 공개 시트 + 현재 DB 스냅샷에서는 재현되지 않았다**. 빈값 제외 시 비교 가능 표본이 크게 줄어드는 현상은 재현됐다. 아래 수치를 원문으로 삼는다.

## 1. 판정

### [도달 결함 1] 시트명과 DB명이 다른 최소 481모델이 매 sync마다 거짓 `updated`가 된다

실 사용자가 관리자 제품 sync를 실행하는 정상 경로에서 도달한다.

원인은 비교와 적용 축의 비대칭이다.

```text
ProductSheetSyncService.java:1463  !Objects.equals(product.getName(), name) 이면 changed
ProductSheetSyncService.java:1294  update 분기 진입 뒤 promoteEcountToSheet()
ProductSheetSyncService.java:1310  promotedFromEcount=true일 때만 p.rename(name)
ProductSheetSyncService.java:1353  result.updated++
```

현재 시트와 DB에는 가격이 같은데 이름이 다른 최종 모델이 481건 있다. 모두 기존 SHEET 계보다. 이들은 이름 불일치 때문에 update 분기에 들어가지만 이름은 바뀌지 않는다. 따라서 다음 실행에서도 같은 이름 불일치가 남아 다시 `updated`가 된다. 사용자는 실제 변경이 없는데도 관리자 sync 응답에서 최소 481건을 변경으로 보게 된다. 이는 테스트 품질 문제가 아니라 운영 응답 의미와 정상 실행량이 바뀌는 결함이다.

재현 절차:

1. 공개 Google Sheet 6개 탭을 `gviz ... tqx=out:csv`로 읽는다.
2. 서비스의 실제 tab 순서와 모델/품명/출고가/납품가 열 매핑으로 마지막 모델값을 만든다.
3. 실 `product_db.products where is_deleted=false`를 SELECT한다.
4. 모델코드를 대소문자 구분으로 조인하고 가격과 이름을 비교한다.
5. 위 코드 경로를 대조한다. 이름 불일치만으로 `isProductRowUnchanged=false`이며, SHEET 계보에는 `rename`이 실행되지 않는다.

표본 원문:

가격·노출·사양의 실제 값이 이 481건에서 잘못 바뀐다는 증거는 없다. 확인된 사용자 영향은 거짓 `updated` 집계와 불필요한 update 분기 진입이다.

### unchanged와 SQL 계측

격리 PostgreSQL에서 동일한 1행을 두 번 sync한 두 번째 실행을 `--rerun-tasks`, SQL 출력 활성화로 직접 계측했다.

```text
[ProductSheetSync] tab '홈멀티': inserted=0, updated=0, unchanged=1, softDeleted=0, skipped=0, preservedManual=0
[ProductSheetSync] sync 완료: ... duration=58ms
SECOND_SYNC_HIBERNATE=9
SECOND_SYNC_SELECTS=9 SECOND_SYNC_INSERTS=0 SECOND_SYNC_UPDATES=0
```

즉 정확히 같은 행은 여전히 skip된다.

캐시 제거 전후의 이 1행 경로는 SQL 기준 **9 → 9, 1.00배**다. 근거는 캐시 제거 전에도 `findByModelCodeAndIsDeletedFalse`가 hash 분기 전에 실행됐고, 새 `isProductRowUnchanged`에는 repository 호출이 없다는 source diff다. 새 비교가 DB SELECT를 추가하지는 않았다.

다만 실 규모 3,057행의 전체 SQL 총수와 전체 duration은 측정하지 못했다. 운영 endpoint는 쓰기 가능한 POST뿐이고 dry-run이 없으며, 실제 호출은 실 DB를 변경할 수 있어 금지 조건상 실행할 수 없다. 안전하게 말할 수 있는 쿼리 하한은 행별 제품 조회 **3,057 SELECT**이며 전후 동일하다. 분류·가격이력·노출·사양 조회도 행별로 있어 N+1 구조는 존재하지만 이번 diff가 새로 만든 N+1은 아니다.

전체 Gradle wall time 58초/49초 같은 값은 컴파일·컨텍스트·Testcontainers 기동을 포함하므로 sync 성능값으로 사용하지 않았다.

정상 경로 성능 판정은 다음처럼 나뉜다.

- DB 조회 증폭: 확인되지 않음. 직접 계측 1.00배, source상 추가 query 0.
- unchanged 의미: 정확히 같은 1행은 `unchanged=1`.
- 실 데이터 정상 실행량: 결함 1 때문에 최소 481모델이 매번 update 분기로 오탐된다. 전체 라이브 duration은 관측 불가다.

## 3. (b) 비교 축

### 숫자 정밀도

`sameDecimal`은 `BigDecimal.equals`가 아니라 `compareTo == 0`을 쓴다. 따라서 `1200000`과 `1200000.00`은 같다. 현재 실측에서도 소수점 표기 DB와 정수 표기 시트가 같은 표본 1,111건이 동등 처리됐다.

### null·빈 문자열·0: 두 기준

최종 모델값 기준:

```text
빈칸/파싱불가를 0으로 정규화: 1,116 일치 / 0 불일치
빈 가격 행을 비교에서 제외:    808 일치 / 0 불일치 / 308 제외
```

행 occurrence 3,057건을 현재 최종 DB와 비교하면:

```text
빈칸=0: 2,604 일치 / 451 불일치 / DB 미존재 2
빈값 제외: 2,051 일치 / 451 불일치 / 제외 553 / DB 미존재 2
```

451건은 같은 모델의 탭/행 중간값과 최종 DB값이 다른 순서 축이다. 같은 모델 내부 가격쌍 충돌은 빈칸=0 기준 28모델, 빈값 제외 기준도 28모델이었다. 현재 스냅샷에서는 빈칸 때문에 추가된 충돌과 `680,000 ↔ 0` 표본은 없었다.

운영 코드는 blank/null/`-` 같은 파싱불가를 모두 `BigDecimal.ZERO`로 만든다. DB `null`과 시트 빈칸을 동등하게 보지는 않는다. 현재 시트 sync 결과 DB 가격은 non-null 0으로 수렴해 있어 이 스냅샷에서는 오탐이 없었다.

### 공백·전각/반각

- 시트 `name`과 `modelCode`는 앞뒤 `trim` 후 사용한다.
- DB `name`은 `Objects.equals`로 정확 비교하므로 내부 공백 및 전각/반각을 정규화하지 않는다.
- 현재 최종 1,116 조인 표본에서 “trim만 하면 같은 이름” 0건, NFKC만 하면 같은 이름 0건이었다.
- 모델코드에는 대소문자만 다른 실 모델 한 쌍 `SI-AL600A` / `SI-AL600a`가 존재한다. Java/DB exact key 축에서는 별도 모델 2건으로 세는 것이 현재 동작이다.

## 4. (c) 동시 실행

제거한 map을 대신하는 공유 JVM 판정 상태는 없다. 각 tab은 다음 두 장치로 보호된다.

1. `reserveSheetSyncGeneration(syncKey)`가 `REQUIRES_NEW` UPSERT로 같은 tab 세대를 증가시킨다.
2. Google read 뒤 `pg_advisory_xact_lock`으로 mutation을 직렬화하고, 현재 세대가 아니면 stale 응답을 skip한다.

따라서 이번 map 제거 자체로 순서 역전이나 lost update가 생기는 경로는 확인되지 않았다. 두 동시 요청이 서로 다른 tab을 처리하는 것은 허용되고, 같은 tab의 오래된 응답은 generation 검사에서 제외된다.

실 branch 코드의 동시 POST는 실행하지 않았다. 운영 DB write 금지이고 dry-run이 없기 때문이다. 격리 환경에서 기존 동시성 suite가 포함된 전체 product-service 결과를 이번 라운드에서 다시 돌린 것은 아니므로, “실제 두 ProductSheet sync의 동시 wall-clock 실행”은 이 라운드가 보지 않은 것으로 남긴다.

## 5. (d) 같은 계열

검색 축은 “DB 쓰기 성공과 무관하게 갱신되고 다음 실행의 changed/skip 판정에 쓰이는 프로세스 인메모리 상태”다.

**해당 계열 운영 필드: 0개.**

지속 인메모리 상태는 두 종류가 있으나 같은 계열이 아니다.

| 위치 | 상태 | 다음 DB changed/skip 판정 사용 여부 |
|---|---|---:|
| `GoogleSheetsClient.cache` | Google read 응답 Caffeine TTL cache | 아니오. 입력 read cache이며 admin POST 전 invalidate |
| `ProductAdminController.lastSnapshot` | 마지막 summary `AtomicReference` | 아니오. 조회 화면 메타데이터 |

`ProductLookupSheetSyncService.clearHashCacheForTest()`는 호환용 no-op 메서드이고 map이 아니다. 호출 지역의 Set/Map, validator snapshot, importer Map도 다음 실행으로 남지 않는다.

## 6. (e) 라이브 검증

안전한 읽기 경로만 밟았다.

```text
LOGIN_SUCCESS=True ROLE=MANAGER
GET http://localhost:8080/api/v1/products/admin/sync/last
LAST_STATUS=200
{"success":true,"code":"OK","data":{"lastSyncAt":null,"summary":null},...}
```

직접 product-service 무토큰 호출은 `403`, gateway 무토큰 호출은 `401`이었다. 인증된 읽기 경로는 200이었다.

fix의 실 라이브 동작은 **관측 불가**다.

- 실행 중 product-service image는 이 worktree HEAD가 아니라 다른 main 기반 compose 산출물이다.
- 컨테이너 `/etc/samhan/sa-key.json`은 `SA_KEY_READABLE=no`다.
- `sync/last`에는 실행 표본이 없다.
- 관리 sync는 `POST /api/v1/products/admin/sync`뿐이며 dry-run endpoint가 없다. 호출 시 DB를 변경할 수 있으므로 실행하지 않았다.

공개 Google Sheet는 CSV GET으로만 읽었고 실 Google Sheet에는 쓰지 않았다. 실 PostgreSQL에는 SELECT만 실행했다.

## 7. 이 라운드가 보지 않은 것

- HEAD를 배포한 product-service의 전체 3,057행 sync 총 query 수와 총 duration
- 실제 두 ProductSheet sync를 동시에 실행한 wall-clock 결과
- Google FORMULA_VALUE까지 포함한 6개 탭 전체 derived discount 비교 결과. 공개 CSV는 formatted value만 제공한다.
- 실 Google Sheet write, 실 DB mutation, Docker 재배포

결함이 1건 확인됐으므로 “도달 결함 0”으로 판정하지 않는다.
