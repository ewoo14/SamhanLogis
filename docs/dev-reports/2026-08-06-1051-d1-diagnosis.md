## 조사 방법 — DB 간 join을 하지 않았다

`slip_db`와 `product_db`는 별도 DB라 SQL cross-database join을 쓰지 않았다.

1. `slip_db`에서 `slip_lines.product_id`, `estimate_lines.product_id`의 distinct 집합을 표준출력으로 추출했다.
2. 별도 접속으로 `product_db.products(id, is_deleted)`를 추출했다.
3. PowerShell hash set으로 `absent = referenced_ids - all_product_ids`, `soft = referenced_ids ∩ deleted_product_ids`를 계산했다.
4. 계산된 UUID 집합을 read-only `ANY(ARRAY[...]::uuid[])` 조건으로 다시 `slip_db`에 주입해 종류/상태/생성 분포/금액을 SQL 집계했다. 임시 테이블도 만들지 않았다.
5. 모델명·이름 후보도 두 DB의 read-only CSV 출력을 메모리에서 exact/trim 비교했다. 저장소나 DB에 중간 파일을 만들지 않았다.

### 2-4. 서비스 경계 판정

API 판정 전 컨테이너 생성 시각을 확인했다.

둘 다 이 진단 HEAD의 컨테이너가 아니다. 따라서 API는 현재 공용 DB와 배포된 계약의 보조 증거로만 사용했다. 로그인하지 않았고 토큰 원문을 출력/저장하지 않았다.

`ProductService.lookup(ids)`는 `findAllByIdIn(ids)` 결과만 반환하며, Product 엔티티의 `@SQLRestriction("is_deleted = false")` 때문에 soft-delete도 제외한다. 미존재/soft-delete만 요청하면 `200 data=[]`가 계약대로 나온다. 이 PC에서 “DB에는 활성 row가 있는데 API만 못 찾는” 서비스 경계 결함은 확인되지 않았다. 다만 `200 + 부분 목록` 계약은 호출자가 개수 비교를 하지 않으면 미존재와 soft-delete를 구분하지 못한다. slip `ProductClient.lookup()`은 응답 수가 요청 수보다 작으면 NOT_FOUND로 막는다.

- **삭제 row 자체로 원 신원을 유일하게 알 수 있음:** slip 549건 + estimate 63건/soft-delete product 3개. 활성 대체품은 0개다. 기술적으로 row 복원은 가능하지만 QA 품목을 카탈로그에 재활성화하는 것이므로 업무 복구로 권고하지 않는다.
- **동명 품목 때문에 broken line의 target이 유일하지 않음:** 0건. 이것은 표본 0이 아니라 broken line 915건(852 slip + 63 estimate) 전수 exact 비교 결과다. 전체 product DB에는 동명 200그룹/726품목/1,569쌍이 있으므로 일반 이름 기반 배치는 여전히 위험하다.
- **단서 자체가 없음:** 0건. 모든 broken line에 `product_name`과 `model_name` snapshot이 있다.
- **제3의 분류 — 단서는 있으나 현 catalog target이 없음:** legacy seed 300건/100 UUID. 모델명·이름이 모두 있으나 활성/삭제 product 어느 쪽에도 후보가 없다. 임의 연결은 복구가 아니라 새 신원 창작이다.

## 4. 복구 방안 — 실행하지 않음

### 방안 A. 화면에서 수동 재선택

편집 가능 범위 SQL은 전표 `DRAFT/SAVED`, 견적 `QUOTE_DRAFT/QUOTE_SENT`, header/line 모두 미삭제 기준이다.

```text
slip_lines
 reference_state |   correction_scope   | line_count
 HARD_ABSENT     | SCREEN_EDITABLE      |         64
 HARD_ABSENT     | VISIBLE_NOT_EDITABLE |        239
 SOFT_DELETED    | DELETED_SCOPE        |        216
 SOFT_DELETED    | SCREEN_EDITABLE      |        268
 SOFT_DELETED    | VISIBLE_NOT_EDITABLE |         65

estimate_lines
 reference_state | correction_scope | line_count
 SOFT_DELETED    | DELETED_SCOPE    |          4
 SOFT_DELETED    | SCREEN_EDITABLE  |         59
```

- 사용자가 현재 화면에서 고칠 수 있는 최대 범위는 slip 332건 + estimate 59건이다. 그러나 활성 후보가 실제로 있는 것은 그중 hard-absent 3건뿐이다.
- 3건은 모델명이 유일하지만 snapshot 이름이 다르므로 사용자가 실제 품목명을 확인한 뒤 재선택하는 방식이 안전하다.
- 나머지는 먼저 올바른 품목 master가 있어야 화면 재선택이 가능하다.
- 위험: 라인 교체 과정에서 수량·단가·공급가·VAT·할인·세트 계보가 재계산되면 원 금액이 달라질 수 있다. 화면 저장은 product ID만 바꾸는 전용 기능이 아니라 라인 전체 교체일 수 있으므로 자동 저장 전 diff가 필요하다.

### 방안 B. 검증된 매핑표 기반 배치

- 대상 후보: 화면에서 수정할 수 없는 visible slip 304건(239 hard + 65 soft) 및 대량 편집을 피할 editable 범위. 삭제 scope 220건은 별도 보존 정책 없이는 만지지 않는다.
- 필수 입력: `old_product_id → verified_new_product_id` 1:1 매핑표, 각 매핑의 근거(모델코드/원본 import/사용자 승인), dry-run 건수·금액 diff.
- 현재 자동 승인 가능한 매핑은 모델명 유일 1개뿐이다(3 line). legacy seed 100개와 QA797 3개는 활성 target이 없어 배치 조건을 충족하지 않는다.
- 위험: 잘못 연결하면 출고/입고 재고가 다른 SKU에 귀속되고, 매출원가·품목별 매출·할인·세트 구성·회계 보조부가 잘못된다. 이미 완료/확정/배송 상태인 239건은 화면 수정이 불가능하며 감사 trail을 보존하는 별도 정정 절차가 필요하다.

### 방안 C. soft-delete 품목 3개 복원

- 기술 대상: product 3 row, 참조 slip 549건 + estimate 63건.
- 장점: UUID를 바꾸지 않아 참조가 즉시 다시 해소된다.
- 이 PC에서는 **권고하지 않는다.** 이름/생성자/삭제자가 QA fixture임을 명시하고 있고, 복원하면 QA797 품목이 업무 카탈로그에 재노출된다. 관련 문서도 QA가 만든 극단값을 포함한다.
- 위험: QA 품목이 견적/주문/재고 선택지에 나타나고, 가짜 금액/재고/회계 분석이 정상 업무처럼 집계될 수 있다.

### 방안 D. legacy seed 100품목 재생성 또는 dev DB 일괄 재시드

- 대상: 300 slip line/100 누락 UUID.
- 운영 데이터 복구가 아니라 집PC dev 환경 정합 복구다. 보존이 필요하면 과거 `TEST-MODEL-*` 100개를 동일 결정 UUID로 별도 재생성해야 한다. 그렇지 않으면 slip/product/inventory/partner-order DB를 같은 seeder 세대에서 함께 재시드해야 한다.
- 위험: 구형 테스트 품목을 현 카탈로그에 되살리면 100개 쓰레기 품목이 노출된다. 반대로 DB 재시드는 현재 QA/개발 데이터를 잃는다. 어느 쪽도 이 읽기 전용 PR에서 실행하면 안 된다.
- 회사PC 실데이터에는 이 방안을 그대로 적용하면 안 된다. 회사PC에서 동일 ID 집합·생성 분포를 다시 측정한 뒤 원본 이카운트 import와 대조해야 한다.

## 이 넷이 정말 한 뿌리인가

아니다. 이 집PC 전수 결과에서 #1051이 묶은 현상은 최소 세 뿌리다. 구형 `TEST-MODEL-*` 시드와 신형 실 모델명 시드 사이의 데이터 이행 누락(300건), QA797 품목의 정상 soft-delete 후 과거 QA 문서가 남은 참조(612건), 그리고 존재하지 않는 임의 UUID에 유효한 모델 snapshot을 저장한 3건이 각각 다르다. `200 · data=[]`는 이 셋 중 행 부재와 soft-delete를 구분하지 못하는 API 표현일 뿐, 이 PC에서는 “DB에 활성 row가 있는데 서비스 경계가 잃어버린” 증거가 아니다. 회사PC의 46품목/4,196건이 같은 뿌리인지 여부는 회사PC에서 같은 집합 추출·생성 분포·soft/hard 구분을 다시 실행하기 전에는 판정할 수 없다.
