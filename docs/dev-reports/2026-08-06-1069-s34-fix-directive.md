# #1069 S34 SOL fix 지시서 — 이월분 재수렴

대상: PR #1077 · 이슈 #1069 · HEAD `06a730cb1`

## 판정과 재현 난이도

**실 사용자 경로로 재현 가능한 결함 2건이다. 현 HEAD는 머지 비권고다.**

- F1 재현 난이도: **중간**. 품목 관리 권한으로 BUNDLE을 `KEEP`으로 신규 생성하거나 변경한 뒤 전표·견적·모바일 주문·발행 경로를 사용한다. DB 직접 조작은 필요 없다. 현재 실 DB에는 KEEP이 0개라 기존 행을 여는 것만으로는 발화하지 않지만, 제품 등록 화면이 KEEP을 정상 선택지로 제공하므로 실 사용자 도달 경로다.
- F2 재현 난이도: **하**. 현재 활성 EXPAND 343개 또는 `bundle_mode IS NULL` 1개 중 하나를 새 판매전표 화면에서 선택해 구성품 전개 후 저장한다. 화면에는 구성품이 보이지만 저장 요청에는 부모 세트 계보가 없다. DB 직접 조작이나 개발자 도구가 필요 없다.

## 1. 좌표와 재현 사슬

### F1 — `bundleMode` 전송은 됐지만 소비자가 mode를 무시한다

S29는 wire 필드 자체는 연결했다.

- `ProductSummaryResponse.java:137-162`는 실제 `Product.bundleMode`를 응답한다.
- `ProductSummary.java:13-25, 99-115`는 slip-service에서 그 값을 역직렬화한다.
- `BundleProductGuard.java:29-36`와 매출·매입 전체수정 PUT은 KEEP 허용, EXPAND/NULL 차단으로 맞다.

그러나 다음 사용자 입구는 전달된 값을 사용하지 않아 KEEP을 EXPAND와 같은 것으로 취급한다.

1. `MobilePartnerOrderService.java:104-112` — `productType == BUNDLE`만 보고 모든 BUNDLE을 거부한다. KEEP도 `구성품으로 전개해 주세요`로 차단된다.
2. `SlipPublishService.java:765-778` — 견적 발행·거래처 주문 단건 발행·주문 병합 발행의 공통 resolver가 모든 BUNDLE을 거부한다. KEEP 3경로가 모두 막힌다.
3. `EstimateToSlipConverter.java:137-145` — KEEP 부모가 정상 저장된 견적도 전표 전환 시 `구성품으로 전개된 견적만` 허용한다며 거부한다.
4. `EstimateService.java:510-526` — 견적 revision 복원 후 모든 BUNDLE을 거부해 KEEP revision도 복원할 수 없다.

또한 전개 엔진을 호출하는 입구도 KEEP의 반환 의미를 끝까지 보존하지 않는다.

- `BundleExpander.java:84-89, 481-486`의 KEEP 결과는 `componentKind=null`, `setHead=false`인 부모 1행이다.
- `SlipService.java:193-215`, `EstimateService.java:128-150`, `MobileQuotationService.java:157-180`은 `componentKind`를 보지 않고 모든 BUNDLE 응답에 `assignBundleComponent(parentModel, setHead)`를 호출한다.
- 그 결과 KEEP 부모가 `parentSetModel=자기 모델`, `setHead=false`인 “자기 자신의 구성품”으로 저장된다. `BundleLineageResolver.isBundleComponent()`는 `parentSetModel` 비공백만으로 구성품을 판정하므로 상세 표시·후속 가격기억·수정 계약이 부모가 아니라 구성품 의미로 바뀐다.

즉 “모든 입구에 `bundleMode`가 전달되는가”의 답은 **wire 전달은 예, 행위 전달은 아니오**다. mode를 실제로 소비하는 곳은 평면 PUT guard와 product-service expander뿐이며, 그 뒤의 mode-blind guard/계보 부여가 다시 계약을 뒤집는다.

### F2 — EXPAND 화면 저장이 `parentSetModel`/`setHead`를 버린다

재현 사슬은 다음과 같다.

1. 새 판매전표에서 활성 EXPAND 또는 NULL BUNDLE을 선택한다.
2. `POST /slips/expand-line`은 구성품마다 `componentKind`와 `setHead`를 반환한다(`SlipLookupController.java:68-75`, `ExpandedSlipLineResponse.java`).
3. `SlipFormPage.tsx:838-871`은 `component.setHead`를 읽지 않고 구성품을 `productType='SINGLE'`인 `LineDraft`로 바꾼다.
4. `SlipFormPage.tsx:1453-1478` 저장 payload와 `SlipLineInput`에는 `setHead`/`parentSetModel` 필드가 없다. 구성품은 각 SINGLE productId로 전송되고, `toApiBundleSetOptions()`도 SINGLE이므로 부모 옵션 문맥을 payload에 싣지 않는다.
5. 서버 `SlipService.java:159-184`는 각 구성품 summary를 SINGLE로 보고 평면 `SlipLine`을 만들며 `assignBundleComponent()`를 호출하지 않는다. 부모 `SOURCE_BUNDLE_SET` 기억 대신 구성품별 `SOURCE_LINE_SAVE` 기억도 수집한다.

기존 테스트 `SlipFormPage.test.tsx:906-947`은 “부모 ID가 payload에 없다”까지만 단언하고 `setHead`/`parentSetModel`을 단언하지 않는다. S31/S33의 Playwright 9개 중 저장 payload 시나리오는 기본 KEEP fixture라 EXPAND 저장 계약을 통과시키지 않는다. 따라서 9/9와 F2는 모순되지 않는다.

## 2. 기준선·NULL·화면·지연응답 불변식

읽기 전용 실 DB를 S28과 같은 cutoff(`created_at < 2026-08-06 00:00:00`)로 재계수했다.

```text
활성 OUTBOUND DRAFT + 현재 활성 SINGLE
  2,107행 / 2,100전표 / 2,837,681,781.00원

현재 BundleProductGuard 적중
  0행

활성 BUNDLE 정본
  344개 = EXPAND 343 · bundle_mode NULL 1 · KEEP 0

활성 BUNDLE 교차
  slip_lines 0 · estimate_lines 0
  slip_revisions 0 · estimate_revisions 0
```

따라서 기존 전표를 여는 즉시 발생하는 SINGLE 오차단은 0건이다. NULL BUNDLE은 `BundleExpander.java:86`에서 EXPAND로 정규화되고, direct PUT에서는 `BundleProductGuard`가 KEEP이 아니므로 차단된다. 화면 선택에서는 EXPAND와 같이 구성품으로 보이지만 F2 때문에 저장 계보는 소실된다.

화면의 `productType` 무조건 SINGLE 덮어쓰기는 제거됐다. `componentKind=null`인 KEEP은 BUNDLE 부모 한 행과 세트 옵션 UI를 유지하고, EXPAND/NULL은 구성품 행으로 표시된다. 수량·단가·규격과 옵션에 따른 구성품 선택도 화면 계산에는 반영된다. 어긋나는 지점은 **저장 경계의 계보와 가격기억 의미**다.

S18~S24 지연 응답 규칙은 유지된다. `BundleExpansionSnapshot`은 productId/modelCode/modelName/productType/수량/단가/규격/5개 옵션을 전부 비교하고, 행별 generation까지 같을 때만 반영한다(`SlipFormPage.tsx:494-542, 922-1005`). S33 변경은 `modelCode`의 undefined→null 정규화, 배열 첫 원소 안전 접근, `LineDraft` 반환 타입 명시뿐이며 비교 축이나 세대 규칙을 줄이지 않았다. 관련 지연 응답 Vitest도 fresh suite 224/224 안에서 통과했다.

## 3. 가배차 병합 충돌과 양방향 RED

### #1039 가드 순서

같은 신규 출고전표 진입점에서 `SlipService.create()`는 가배차 cutoff를 `createOutbound` 직후(`:263-265`), BUNDLE 전개보다 먼저(`:273-281`) 실행한다. 따라서 cutoff와 전개 오류가 동시에 있으면 cutoff 문구가 먼저다. 이는 save 전 원자 차단이며, BUNDLE mode를 잘못 판정해서 생긴 순서 충돌은 아니다.

모바일 주문은 BUNDLE 거부가 `MobilePartnerOrderService.java:109-112`, cutoff가 `:132-135`로 BUNDLE 문구가 먼저다. 다만 모바일 cutoff는 deliveryTag가 null이라 현재 즉시 통과한다. 가배차 분류·배차그룹 가드는 저장된 전표의 조회/그룹 변경·삭제 경로에 있고 BUNDLE 저장 guard와 같은 요청에서 경쟁하지 않는다. #1039 자체와의 별도 도달 결함은 찾지 못했다.

### RED-A — 반대급부

- 기존 SINGLE 2,107행은 전체수정·부분수정·삭제·복원·발행 경로에서 새 guard에 걸리지 않아야 한다.
- EXPAND/NULL은 부모가 저장되지 않고 구성품 수량·단가·규격·옵션과 `parentSetModel`/`setHead`가 함께 보존돼야 한다.
- 지연 응답은 요청 snapshot과 현재 snapshot 및 generation이 모두 같을 때만 반영돼야 한다.
- cutoff와 BUNDLE 실패가 함께 있어도 저장·가격기억·revision이 일부 남아서는 안 된다.

### RED-B — 재발 금지

- KEEP을 “BUNDLE이므로 전개 필요”라고 거부하거나, KEEP 부모를 자기 자신의 구성품으로 표시하면 RED.
- KEEP 허용을 위해 EXPAND/NULL 평면 부모를 허용하면 RED.
- 화면 EXPAND 구성품을 평면 SINGLE들로 저장해 계보를 버리거나 구성품 가격기억을 `LINE_SAVE`로 각인하면 RED.
- 기존 9/9의 KEEP 저장만으로 EXPAND/NULL 저장 계약을 대신하면 RED.

## 4. fix 수렴 조건과 안 본 범위

수렴 조건은 구현 수단이 아니라 결과로 고정한다.

1. mode-aware 판정을 공통화해 모바일 주문, 발행 3경로, 견적→전표, 견적 revision이 KEEP을 정상 부모 1행으로 처리하고 EXPAND/NULL은 전개 또는 안전 차단해야 한다.
2. KEEP 반환(`componentKind=null`)에는 `parentSetModel`/`setHead` 구성품 계보를 부여하지 않아야 한다.
3. 화면 EXPAND 저장은 서버가 부모+옵션을 다시 전개하게 하거나 동등한 검증된 계약으로 `parentSetModel`/`setHead`를 보존해야 한다. 화면과 서버 결과의 수량·단가·규격·옵션이 같아야 한다.
4. EXPAND 화면 저장 후 부모만 `SOURCE_BUNDLE_SET` 가격기억 대상이고 구성품 배분가는 `LINE_SAVE`로 각인되지 않아야 한다.
5. KEEP/EXPAND/NULL 각각에 대해 화면 선택→저장 payload→서버 상세 응답을 한 묶음으로 단언하고, 기존 SINGLE·cutoff·지연응답 반대급부를 함께 둔다.

안 본 범위: 실제 DB write가 필요한 최종 저장 클릭과 KEEP 제품 생성, 실제 모바일 기기 GUI, vendor 발송, Docker 재빌드·재배포·중지, 전체 CI/전체 Gradle/전체 Playwright, 회계·재고 전체 기능, 다른 트랙(`#874`, `#1066`, `#1075`) 구현 파일, 배포 컨테이너와 HEAD 바이너리 동일성. DB는 SELECT만 사용했다.

## 5. 증거 무결성·검증 결과·신규 파일

S31~S33 수치는 fresh 실행으로 재현됐다.

```text
typecheck                         exit 0
Vitest 지정 3파일                224/224
격리 Playwright                  9/9 (자체 5175, API 127.0.0.1:1)
slip-service 지정 8 suite        BUILD SUCCESSFUL in 25s
```

Playwright 첫 재시도는 `npx vite src/renderer`에 `--config vite.config.ts`를 빠뜨려 `virtual:pwa-register` import 오류 뒤 timeout이 났다. S33 명령과 같은 config를 사용한 재시도는 9/9였다. 첫 timeout은 제품 결함이나 S33 수치 불일치로 계산하지 않았다. 5173과 타 워크트리 프로세스는 건드리지 않았고, 5175의 자체 listener PID만 종료했다. 임시 stdout/stderr는 `os.tmpdir()` 아래에만 두었으며 저장소 QA 디렉토리를 만들거나 덮어쓰지 않았다.

증거 무결성상 주의할 점은 9/9의 시나리오 6이 기본 KEEP fixture의 payload만 검증한다는 것이다. 보고된 9/9 숫자는 진실이지만 EXPAND/NULL 계보 저장을 증명하지 않는다. 이는 테스트 품질 평이 아니라 F2와 기존 green이 양립하는 이유를 밝히는 증거 경계다.
