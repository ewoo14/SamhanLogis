## 2. RED-first

실 DB 모양을 반영하도록 계약 테스트를 먼저 강화했다. 품목명까지 매칭하고, 첫 대상의 기존 `line_total`을 실제 값인 6,000,000원으로 사용하며, 부분 적용에서 구금액/신금액 상태를 구분하는 SQL 계약을 요구했다. 수정 전 V61에는 이 계약이 없었으므로 의도한 RED가 발생했다.

## 3. 고친 매칭 조건의 실 DB 읽기 전용 재현

고친 V61과 동일한 전표번호·모델·수량·실 DB 금액 조건을 조회하고, 품목명은 UTF-8로 비교했다. 공유 DB에는 쓰지 않았다.

출력 원문:

```text
BEGIN
SET
 matches | distinct_targets
---------+------------------
      19 |               19
(1 row)

ROLLBACK
```

품목명까지 실제 값과 비교한 별도 읽기 전용 확인:

```text
BEGIN

 product_condition_matches
---------------------------
                        19
(1 row)

ROLLBACK
```

## 4. V61 수정 내용과 6개 시나리오 판정

V61은 새 버전을 만들지 않고 기존 파일만 수정했다. `line_total`은 구금액과 신금액에 동일한 사용자 총액으로 두고, 품목명·모델·수량·5개 금액을 모두 비교한다. 매칭된 행은 `OLD`/`NEW` 상태로 분류하며 `OLD`만 감사 INSERT와 UPDATE를 수행한다. `NEW`는 이미 정정된 행으로 보고 건너뛴다. 동일 target 번호가 두 행 이상 매칭되면 오정정을 막기 위해 예외 처리한다.

이 정책은 일부만 정정된 환경에서도 배포를 막지 않는 E 불변식의 근거다. 삭제·금액 변경처럼 더 이상 확정된 구금액과 일치하지 않는 행도 건드리지 않고 통과시킨다. 품목명만 다른 중복·치환 행은 품목명 조건에서 제외되므로 대상 행을 대체하지 않는다.

SOL 검토 보고서의 6개 fixture를 수정 SQL의 상태 분류에 다시 대입한 결과:

| 시나리오 | OLD | NEW | 정정/감사 | 판정 |
|---|---:|---:|---:|---|
| 정확 19행 | 19 | 0 | 19 | 성공, 19행 정정 |
| 부분 적용(10행 기정정) | 9 | 10 | 9 | 성공, 10행은 재정정하지 않음 |
| 삭제 | 18 | 0 | 18 | 성공, 삭제 행 제외 |
| 금액 변경 | 18 | 0 | 18 | 성공, 변경 행 제외 |
| 품목명만 다른 중복 | 19 | 0 | 19 | 성공, 비대상 중복은 제외 |
| 품목명만 다른 치환 | 18 | 1 | 18 | 성공, 이미 신금액인 원 대상과 비대상 치환 모두 보존 |

모든 경우에 `supply_amount + vat_amount = line_total`은 정정된 행에서 성립하며, 정상 7행·확인불가 3행은 대상 금액·품목명 조건을 만족하지 않아 정정되지 않는다. 중복 행이 같은 품목명까지 완전히 같은 확정 조건으로 들어오는 경우에는 모호성 예외로 롤백한다.

## 6. 불변식 최종 판정

- A: 실 DB 읽기 전용 매칭 19행/고유 대상 19행 확인.
- B: 품목명까지 포함한 실 DB 조건 19행 확인. 품목명만 다른 행은 매칭하지 않는다.
- C: 정상 7행·확인불가 3행은 대상 집합에서 제외된다.
- D: `line_total`을 원래 사용자 총액으로 보존하고 새 공급가액·부가세 합계가 그 금액과 같도록 정정한다.
- E: 부분 적용은 `NEW`를 skip하고 `OLD`만 정정하므로 재배포가 막히지 않는다.

공유 Docker 스택은 재빌드·재기동하지 않았고 실 DB에는 읽기 전용 조회만 수행했다. 별도 검증 컨테이너는 검증 후 제거했다.
