## 6. 첫 각도 나머지 판정

### `2519 외상매입금`의 자격

수수료 4개 journal은 거래처별 view가 8개다. 고객 view 4개는 `1089` 대변을 귀속 금액으로, 다른 거래처 소유 `2519` 차변을 effect로만 사용해 PAYMENT **4건·412,500원**이 됐다. `2519` 소유 거래처인 새한신용정보(주) view 4개는 귀속 채권 금액 0원이라 `NONE/0`이며 필터에서 사라진다. 따라서 412,500원이 새한신용정보의 채권 원장 금액으로 섞인 건수는 **0건**이다.

다만 이 결과는 `LIABILITY/외상매입금` 의미군을 실제 분류기가 사용해서 나온 것이 아니다. §9와 같이 `2519`는 단지 “채권·매출이 아닌 차변”이라 effect에 들어간다.

### 확정수금 기초·기간 이중 계상

기초 query는 `transactionDate < from`, 기간 query는 `from <= transactionDate <= to`라 경계가 겹치지 않는다. `2026-05-10` 시작 전후를 805곳 전수 비교한 결과 같은 기말 불일치는 **0곳·0원**이다. 전체기간 화면 기말과 `110+1089` 직접 잔액도 **805곳 전부 일치**, 합계는 양쪽 모두 735,329,017원이다.

### 목록 row·기말 0

- R45 전체기간 row 805 → R46 805.
- R45 코드 재산출 기말 0 row 475 → R46 58.
- `2026-06-01~08-03` R46 row 747 중 기초-only 746, 기말 0은 0.

기초-only 보존이 기말 0 거래처를 대량 생성한 실데이터 사례는 없다.

## 9. 계정명 결합과 증거 무결성

### 화면 도달성

현재 활성 chart의 exact leaf는 PM 기록과 동일하게 6개다.

```text
ASSET/외상매출금       1089, 110
REVENUE/상품매출       401, 4019
LIABILITY/외상매입금   201, 2519
```

사용자 화면 `/accounting/accounts`의 `AccountTreePage`는 read-only이며 API도 `GET /accounting/accounts` 하나뿐이다. 계정명을 바꾸거나 같은 이름의 leaf를 추가하는 데스크톱 화면은 없다. 따라서 “화면에서 이름 변경 → 원장에서 조용히 소실”의 현재 도달 건수는 **0건**이다.

저장소에는 `POST /admin/accounts/imports/ecount`와 서버-side reimport API가 있지만 이를 호출하는 데스크톱 라우트는 없다. 화면 도달 질문의 결함으로 세지 않았다.

외부 import 등으로 exact-name leaf가 추가되면:

- `ASSET/외상매출금`: 그 코드의 대상 거래처 차변은 상대 계정과 무관하게 SALE, 대변은 임의의 다른 차변이 있으면 PAYMENT로 섞인다.
- `REVENUE/상품매출`: 대상 거래처에 귀속된 해당 코드의 순액이 SALE 후보로 섞인다.
- `LIABILITY/외상매입금`: 현재 분류 결과에는 변화가 없다. `payableCodes`가 사용되지 않기 때문이다.

### 증거 무결성 예외 판정

R46 보고서의 “exact leaf 6개”, 수수료 4건·412,500원, 지정 테스트 `21/4/9` 통과는 재현됐다. 그러나 **“외상매입금 201·2519를 chart 의미군으로 동적 해석해 effect에 사용한다”는 인과 설명은 코드와 다르다.**

`LedgerAccountCodes.from()`은 `payableCodes`를 만들지만 production reader가 없다. `classify()`에 전달되는 것은 `receivableCodes`와 `revenueCodes`뿐이다. `2519`가 effect에 들어가는 실제 이유는 `PartnerLedgerCollectionContract:132-133`이 모든 비채권·비매출 차변을 `otherDebit`으로 합치기 때문이다. 이 차이가 바로 `9549 잡손실`까지 PAYMENT로 들어간 원인이다.
