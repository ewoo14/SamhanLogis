## 2026-08-02 후속 정찰

- 기존 `1013` 정찰의 최종 판정은 도달 가능 결함 2건을 (1) notification-service가 `FAILED` 상태를 담아 HTTP 2xx로 응답해도 slip-service 타배송사 문자 client가 body를 읽지 않고 성공으로 처리하는 거짓 성공, (2) 가배차 8모드가 실행 서비스에서 모두 빈 결과이고 화면 진입점과 창고 판정 계약도 없는 결함으로 기록했다(`docs/dev-reports/2026-08-01-1013-sol-review-final.md`).
- 결함 1은 현재 소스에서 살아 있지 않다: `NotificationClient.sendInternalWithResult`가 HTTP 성공 여부만 보지 않고 응답 envelope의 `data.status`가 정확히 `SENT`일 때만 `true`를 반환하며, `FAILED` 2xx를 `false`로 고정한 계약 테스트도 존재한다(`services/slip-service/src/main/java/com/samhanair/logis/slip/client/NotificationClient.java:150-187`, `services/slip-service/src/test/java/com/samhanair/logis/slip/it/external/NotificationDispatchSmsContractIT.java:37-58`).
- 결함 2는 현재도 소스상 살아 있다: 양 데스크톱 API에는 선택적 `mode` 인자가 있으나 두 실제 화면은 이를 전달하지 않고, slip-service `OutboundSlipResponse`에도 창고 필드가 없어 상일/초월 모드를 판정할 계약이 없다(`clients/desktop/src/renderer/api/arologisDispatchApi.ts:111-116`, `clients/arologis-desktop/src/renderer/api/arologisDispatch.ts:122-127`, 두 `PreClassifyPage`의 조회 호출, `services/slip-service/src/main/java/com/samhanair/logis/slip/web/dto/OutboundSlipResponse.java:28-37`). 이 결함은 분리 트랙 `#1039` 범위이므로 추가 정찰·수정하지 않았다.

### 레거시 GAS 배차안내문자(13)

- 수신자 판정: 거래처명을 정규화해 단톡방 매핑을 먼저 찾되 이름에 `회계`가 들어간 방은 제외하고, 단톡방이 없을 때만 이카운트 `인수자 번호`에서 `010` 시작 11자리 휴대번호를 추출해 사용한다; 발송금지 거래처와 전표 매칭 오류·기사 연락처 누락 행은 정상 안내 묶음에서 제외한다(`tools/legacy-gas/배차안내문자/Code.js:195-201,208-310,379,431-456`, `Index.html:1147-1168`).
- 문구 조립: 같은 단톡방(없으면 같은 인수자 번호)의 행을 묶고 하차일 숫자 오름차순으로 정렬한 뒤, 고정 인사말 → `N일 하차 건 배송기사님 연락처를 안내드립니다.` → 각 행의 `배송기사 연락처 / 배송주소 앞 3개 공백 구획`을 붙이며, 인수자 번호 수신 묶음에는 끝에 출하창고 지연 양해 문구를 추가한다(`tools/legacy-gas/배차안내문자/Code.js:376-379`, `Index.html:1154-1188`).
- 전송 시점: GAS 자체에는 SMS·알리고·카카오 발송 호출이 없고 결과 표의 선택 셀을 TSV로 클립보드에 복사하는 기능만 있으므로, 프로그램이 자동 전송하는 시점은 없으며 사용자가 결과 생성·검토 후 외부 채널에 붙여넣을 때 비로소 전달된다(`tools/legacy-gas/배차안내문자/Index.html:880-914,1489-1528`).

### 현행 계승 여부

- 수신자 판정은 부분 계승이다: 거래처코드 우선·거래처명 snapshot 보조로 단톡방을 찾고 매핑 건은 클립보드 수동 전달 대상으로 두며, 매핑이 없는 건만 전표의 인수자 전화번호를 SMS fallback으로 만든다; 발송금지 재검사는 있으나 `회계` 단톡방 제외 규칙은 없다(`DispatchBatchPreviewService.java:73-103`, `clients/desktop/src/renderer/routes/DispatchSmsPage.tsx:70-85,319-344`, `DispatchBatchSendService.java:94-109`).
- 제보된 ``recipientPhone = `room:${chatRoomName}``` 경로는 현재 소스에는 없다: `buildSendEntries`는 `preview.unmapped`의 실제 `recipientPhone`만 사용하고, 서버도 방어적으로 `room:` 값을 `FAILED` 처리한다(`clients/desktop/src/renderer/routes/DispatchSmsPage.tsx:70-85`, `services/notification-service/src/main/java/com/samhanair/logis/notification/service/DispatchBatchSendService.java:82-93`).
- 문구 조립은 계승하지 않았다: 현행은 출고전표마다 `[배차안내] / 거래처 / 시간 / 주소 / 품목`을 만들 뿐, 같은 수신자 묶음·하차일 정렬·배송기사 연락처·주소 앞 3구획·고정 인사말·지연 양해 문구가 없다(`services/notification-service/src/main/java/com/samhanair/logis/notification/service/MessageTemplateService.java:47-58`, `DispatchBatchPreviewService.java:73-103`).
- 전송 시점은 “미리보기 후 발송 확인 체크 → 2회 확인 대화상자 → 발송 API 호출”로 구현되어 있으나, 단톡방 매핑 건은 복사 후 수동 전달이고 실제 SMS entry는 미매핑 건의 인수자 전화번호만 생성된다(`clients/desktop/src/renderer/routes/DispatchSmsPage.tsx:283-292,351-361,552-608,667-697`).
- 현행 화면의 발송 대상 수와 실제 entry 모집단은 서로 다르다: `sendableCount`와 버튼 활성화는 단톡방 매핑·비차단 건을 세지만 `buildSendEntries`는 미매핑·인수자 전화번호 보유 건만 만든다(`DispatchSmsPage.tsx:70-85,307-325`). 따라서 화면에 표시한 “SMS 발송 N건”이 실제 API 요청 건수를 뜻하지 않는다.
- 알리고 미연결 상태는 성공으로 세지 않는다: key/userid/sender가 비었거나 placeholder이면 adapter가 `NOT_SENT_CREDENTIALS_PLACEHOLDER` 실패를 반환하고, batch 집계는 최종 상태가 `SENT`인 경우에만 성공을 증가시킨다(`services/notification-service/src/main/java/com/samhanair/logis/notification/adapter/sms/AligoSmsAdapter.java:53-61`, `DispatchBatchSendService.java:120-137`). 따라서 이 환경에서 실제 발송 성공은 0건이어야 한다.
