# 창고 UUID 검증 회귀 수정 보고서

## 확인 1 — 현재 구현과 원인 가설

- `WarehouseCodeMapper`가 `@PostConstruct`에서 `public.warehouses`를 조회한다.
- 이를 위해 `WarehouseValidationDataSourceConfig`가 `warehouseValidationDataSource`와 `warehouseValidationJdbcTemplate`를 별도 생성한다.
- `SlipDataSourceConfig`는 이미 주 `dataSource`와 가격기억 전용 `priceMemoryDataSource`를 제공하며, 전용 JDBC 3종은 `PriceMemoryJdbcAccess` 한 객체로 묶어 `dedicatedDataSourceTrio` 계약을 보존한다.
- 따라서 현재 창고 검증은 컨텍스트마다 Hikari pool을 추가하고, `slip-service`의 기존 주 DB/가격기억 DB 계약에 세 번째 DataSource를 더하는 구조다. 이 구조가 CI에서 보고된 커넥션 고갈 및 `dedicatedDataSourceTrio` 회귀의 직접 가설이다.
- 기존 검증 테스트는 별도 DataSource 존재를 전제로 하므로, 먼저 실제 RED 원문으로 계약 위반을 고정한 뒤 검증 방식을 바꿔야 한다.

## 확인 2 — 첫 RED 실행 경로 오류

실행 명령:

```text
.\gradlew.bat :slip-service:test --tests "com.samhanair.logis.slip.price.config.PartnerProductPriceMemoryAsyncConfigTest" --tests "com.samhanair.logis.slip.publish.WarehouseValidationDataSourceConfigTest" --no-daemon
```

결과 원문:

```text
Cannot locate tasks that match ':slip-service:test' as project 'slip-service' not found in root project 'samhan-public'.
BUILD FAILED
```

루트 Gradle은 서비스별 독립 빌드를 포함하지 않으므로, 서비스 모듈의 Gradle wrapper/빌드 경로로 재실행한다.

## 확인 3 — RED 원문 확보

재실행 명령:

```text
.\gradlew.bat :services:slip-service:test --tests "com.samhanair.logis.slip.price.config.PartnerProductPriceMemoryAsyncConfigTest" --tests "com.samhanair.logis.slip.publish.WarehouseValidationDataSourceConfigTest" --no-daemon
```

결과 원문:

```text
PartnerProductPriceMemoryAsyncConfigTest > dedicatedDataSourceTrio_coexistsWithPrimaryMainDataSource() FAILED
  AssertionError: [전용 JdbcTemplate 이 JdbcOperations 빈으로 새면 자동구성 jdbcTemplate 이 back-off]
  Expecting empty but was: ["jdbcTemplate"]

8 tests completed, 1 failed
BUILD FAILED
```

`WarehouseValidationDataSourceConfigTest`는 통과했지만, 그 테스트 자체가 검증 전용 DataSource를 기대하므로 현재 구조의 회귀를 가리는 상태다. 현재 코드에는 `dataSource`, `priceMemoryDataSource`, `warehouseValidationDataSource` 세 DataSource가 존재하며, 후자는 컨텍스트마다 추가 pool을 만든다.

## 확인 4 — 새 계약 테스트 RED

검증용 DataSource를 제거하고 연결 설정만 남기는 계약 테스트를 먼저 작성한 뒤 실행했다.

결과 원문:

```text
Task :services:slip-service:compileTestJava FAILED
error: cannot find symbol
  class WarehouseValidationProperties
2 errors
BUILD FAILED
```

생산 코드에 아직 새 설정 타입을 추가하지 않았기 때문에 발생한 의도적인 RED다.

## 확인 5 — 첫 구현 컴파일 확인

새 설정 타입을 추가한 뒤 테스트 accessor를 JavaBean getter에 맞추기 전 실행 결과:

```text
Task :services:slip-service:compileTestJava FAILED
error: cannot find symbol
  method jdbcUrl()
  method username()
2 errors
BUILD FAILED
```

이는 구현 실패가 아니라 테스트가 Lombok JavaBean getter를 record accessor처럼 호출한 오류였으며, 테스트 호출을 `getJdbcUrl()`/`getUsername()`으로 바로잡았다.

## 확인 6 — 구현 후 첫 GREEN 전 단계

직접 JDBC 설정 타입을 추가한 뒤 실행 결과:

```text
PartnerProductPriceMemoryAsyncConfigTest > dedicatedDataSourceTrio_coexistsWithPrimaryMainDataSource() FAILED
  Expecting empty but was: ["jdbcTemplate"]

WarehouseValidationDataSourceConfigTest > warehouseValidation_keepsOnlyConnectionProperties_withoutAdditionalDataSourceBean() FAILED
  expected: "jdbc:h2:mem:inventory-db" but was: null
```

첫 결과는 현재 `SlipDataSourceConfig`가 의도적으로 주 `jdbcTemplate`을 노출하는데 테스트가 이를 금지하던 기존 단언의 불일치다. 두 번째는 bean method binding 대신 `@EnableConfigurationProperties` 방식으로 명시 등록해야 한다는 설정 바인딩 문제다. 둘을 각각 계약에 맞게 수정했다.

## 확인 8 — 실제 Spring 기동 실패 검증의 첫 컴파일 RED

존재하지 않는 UUID를 설정한 `ApplicationContextRunner` 기동 검증을 추가하고 실행했다.

결과 원문:

```text
Task :services:slip-service:compileTestJava FAILED
error: cannot find symbol
  method hasRootCauseMessageContaining(String)
1 error
BUILD FAILED
```

AssertJ 버전에 없는 chained assertion을 원인 예외 순회 단언으로 교체했다. 검증 대상 로직의 실패가 아니라 테스트 표현식 호환성 문제였다.

## 확인 9 — 불변식 A 실행 검증 GREEN

실행 명령:

```text
.\gradlew.bat :services:slip-service:test --tests "com.samhanair.logis.slip.publish.WarehouseCodeMapperValidationTest" --no-daemon
```

결과 원문:

```text
BUILD SUCCESSFUL in 15s
18 actionable tasks: 2 executed, 16 up-to-date
```

테스트는 실제 H2 `warehouses` 테이블(행 없음)을 준비하고 Spring `ApplicationContextRunner`를 기동했다. 설정된 UUID가 없으므로 `WarehouseCodeMapper`의 `@PostConstruct`가 `IllegalStateException`으로 컨텍스트를 실패시켰다. 즉 A를 직접 실행으로 재확인했다.

## 확인 10 — `slip-service` 전체 테스트 실행 결과

실행 명령:

```text
.\gradlew.bat :services:slip-service:test --no-daemon
```

결과 원문:

```text
command timed out after 904030 milliseconds
```

Gradle은 약 15분 동안 종료되지 않았고, 최종 `BUILD SUCCESSFUL` 또는 실패 통계를 출력하지 못했다. 따라서 `slip-service` 전체 0실패를 이 환경에서 주장할 수 없다. 공유 Docker는 건드리지 않았으며 실행 중 새 컨테이너도 확인되지 않았다. targeted 검증은 GREEN이지만 전체 모듈 검증은 timeout으로 미완료다.

## 확인 11 — timeout 후 재검증 시도

timeout으로 남은 해당 워크트리 Gradle test worker가 `build/test-results/test/binary/output.bin`을 잠근 상태여서 재실행 첫 시도는 아래처럼 끝났다.

```text
java.io.IOException: Unable to delete directory
'...services\\slip-service\\build\\test-results\\test\\binary'
Failed to delete ... output.bin
BUILD FAILED
```

공유 서비스나 Docker가 아닌 해당 테스트의 잔류 Java worker만 종료한 뒤 재실행한다.

실행 명령:

```text

```


창고 UUID 기동 실패·추가 DataSource 부재·가격기억 전용 DataSource 계약을 함께 재확인했다.

## 결론

- 검증용 Spring `DataSource`/`JdbcTemplate`를 제거했다. `WarehouseValidationProperties`만 바인딩하고, `@PostConstruct`에서 `DriverManager` 연결을 한 번 열어 `public.warehouses`를 조회한 뒤 try-with-resources로 닫는다.
- 따라서 inventory DB 연결 실패도 `IllegalStateException`으로 기동 실패하며, 실재하지 않는 UUID도 조용히 통과하지 않는다.
- `slip_db`에는 warehouse fixture를 추가하지 않았다. 통합 테스트의 기존 별도 `inventory_db` fixture 계약은 그대로 사용한다.
- `dedicatedDataSourceTrio` 테스트는 주 `jdbcTemplate` 1개와 가격기억 `PriceMemoryJdbcAccess` 결속을 검증하도록 정정했고 통과했다.
- 최종 targeted GREEN은 3개 테스트 클래스이며, `slip-service` 전체 테스트는 904030ms timeout으로 0실패를 확인하지 못했다. 이 사실은 미완료로 남긴다.
