## 1. 결론

R15 HIGH의 **결함 자체는 실재했다.** 다만 결함의 정확한 증상과 R15의 처방을 다음처럼 정정한다.

- 새 `lineId`를 반영한 부모 동작은 head 삭제 저장 **200**, 이어지는 수량 편집도 **200**이다. “삭제 뒤 다음 편집이 현행 400”은 성립하지 않는다.
- 실제 결함은 첫 200 저장 뒤 삭제된 head와 경계를 증명할 수 없는 행에 `parentSetModel`이 남아, 일부가 **깨진 BUNDLE 계보**로 저장되는 것이었다.
- 따라서 R15에서 요구한 “일부 head 삭제 400 + 전체 삭제 후 재생성 안내” 처방은 불변식이 너무 넓었다. 기존 정본인 lineage-drop과 충돌하므로 철회한다.
- R16은 경계를 증명할 수 없는 keyless duplicate 그룹에서 원본 head 하나라도 삭제되면 남은 모호 행 전체에 기존 `SlipLine.clearBundleComponent()`를 적용한다. 행·수량·단가·공급가·VAT는 건드리지 않고 깨진 계보만 제거한다.

R10 정상 견적, R13 교차 배치 복원, R14 duplicate-signature 복원/편집, keyed head 삭제 차단, 비-head 삭제, 인스턴스 전체 삭제, 수량 0 거부, 가격기억, V119 수치는 모두 보존됐다.

## 2. R15 증상 서술 재검증

### 2.1 R16을 제외한 부모 동작 직접 probe

제품 코드에는 남기지 않은 단일 테스트에서 R16 호출만 잠시 제외하고 다음 순서로 재현했다.

1. 원본 `[head-A, child-A, head-B, child-B]`를 같은 parent/signature의 keyless duplicate로 구성
2. `head-A`만 뺀 3행 저장
3. 저장 mock이 실제 전체교체처럼 세 행에 **새 lineId** 부여
4. 조회된 새 lineId로 첫 잔존 행 수량을 다시 편집

실측 원문:

```text
R17_PARENT_PROBE|headDelete=200|freshLineIds=true|followupEdit=200|rows=3|heads=1|parentSetModel=retained
```

즉 후속 400은 재현되지 않았다. 전체에 head가 하나 보이는 이유는 둘째 head가 남았기 때문이며, 첫째 child의 소속 경계를 증명할 수 없는 상태에서 같은 keyless parent가 유지된 것이 진짜 손상이다. probe와 임시 R16 제외는 즉시 제거했고, 제거 뒤 제품 diff 0을 확인했다.

### 2.2 R15 판정 중 유지·철회 항목

| R15 항목 | R17 판정 |
|---|---|
| ambiguous legacy 조기 `continue`가 기존 단일-head 검사를 우회 | 유지 — 당시 200 저장 원인 분석은 맞음 |
| 행 삭제 버튼으로 head 한 행만 삭제 가능 | 유지 |
| 200 저장 뒤 parent 계보가 남음 | 유지 — HIGH의 실질 |
| 삭제 뒤 새 lineId 후속 편집이 400 | **정정 — 200** |
| 일부 head 삭제는 반드시 400이어야 함 | **철회 — 기존 lineage-drop 정본과 충돌** |
| 사용자는 그룹 전체를 삭제하고 재생성해야 함 | **철회 — R16 평면화가 데이터 보존 복구 경로** |

따라서 R15의 HIGH는 “깨진 계보를 조용히 저장한다”는 이유로 유효했지만, 400 차단 처방은 유효하지 않다.

### 3.2 무엇이 사라지는가

`SlipLine.clearBundleComponent()`가 지우는 값은 세 가지뿐이다.

1. `parentSetModel = null`
2. `setHead = false`
3. `bundleSetOptions = null`

즉 **세트 소속이라는 의미 데이터는 의도적으로 사라진다.** 수량·단가·공급가·VAT·합계·품목·행은 사라지지 않는다. 이후 세 행은 일반 단품 행으로 취급되며 공급가/VAT 입력도 일반 행처럼 편집 가능하다.

현재 판매전표 상세/편집 UI는 `parentSetModel`을 별도 세트 배지·그룹 경계로 표시하지 않는다. 삭제 전 스크린샷에도 별도 묶음 표시가 없고, 삭제 후 상세와 재진입 화면에도 잔존 3행이 모두 실제로 보였다. 따라서 사용자가 보는 추가적인 “세트 표시 소실”은 없지만, 서버 의미론상 세트 관계가 해제된다는 사실은 분명하다.

### 3.3 가격기억

평면화는 `collectPriceMemory()`보다 먼저 수행된다. 평면 행은 기존 일반 행 규칙대로 후보가 되고, 현재 R16 테스트는 다음 값을 정확히 단언한다.

```text
child-A = 220.00
head-B  = 110.00
child-B = 220.00
```

`SalesSlipUpdateR5FixTest` 13/13과 `PartnerProductPriceMemoryIT` 30/30이 새 JVM 강제 실행에서 통과했다. `PartnerProductPriceMemoryIT.java`는 R16 커밋 및 `origin/main...HEAD`에서 수정되지 않았다.

## 4. 기존 lineage-drop과 같은 의미론인가

두 사건의 **검출 함수는 서로 다르지만**, 같은 저장 파이프라인과 같은 단일 mutation primitive를 사용한다.

```text
SalesSlipUpdateService
  → flattenHeadProductReplacements(...)
      → retainedLine.clearBundleComponent()
  → flattenAmbiguousLegacyLineageAfterHeadDeletion(...)
      → retainedLine.clearBundleComponent()
  → requireSingleHeadPerRetainedBundleInstance(...)
  → materializeLegacyInstanceKeys(...)
  → collectPriceMemory(...)
  → replaceSalesLines(...)
```

- head 품목 교체 검출: `BundleLineageResolver.java:221-245`
- ambiguous keyless head 삭제 검출: 같은 파일 `:257-283`
- 공통 mutation: `SlipLine.java:409-413`
- 공통 호출 위치: `SalesSlipUpdateService.java:115-126`

두 경로가 복제된 필드 대입을 각각 갖는 것은 아니다. 둘 다 정확히 같은 `clearBundleComponent()`를 호출하므로 “계보를 떼되 금액은 건드리지 않는다”는 규칙은 하나다.

차이는 의도된 대상 범위다.

- 품목 교체: 교체한 head 행만 평면화; 기존 자식 계보는 정본대로 보존
- keyless duplicate head 삭제: 어느 자식이 삭제된 head 소속인지 증명할 수 없으므로 그 ambiguous 그룹의 잔존 행 전체를 평면화

따라서 같은 detector 분기를 지나지는 않지만, lineage-drop의 상태 변경 의미론은 실제 코드 수준에서 공유된다.

6. **실사용자 의미 인지 조사**: 현재 UI에 세트 배지/경계가 없다는 코드·픽셀 사실은 확인했지만, 평면화 뒤 사용자가 품목명 자체를 보고 느끼는 업무 의미까지 사용자 조사로 검증하지 않았다.
