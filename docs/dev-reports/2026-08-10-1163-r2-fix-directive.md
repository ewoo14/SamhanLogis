# PR #1164 / 이슈 #1163 R2 수정 지시서

## 판정

도달 결함 1건. 인증된 사용자가 창고를 수정·삭제·복원·되돌린 뒤 변경 이력을 열면, 게이트웨이에 정상 표시명이 있어도 신규 감사행의 변경자가 `변경자 미상`으로 표시된다.

## 재현 경로와 원문

1. 로그인 사용자가 `/admin/warehouses`에서 창고 행의 편집 버튼을 누른다 (`WarehousesPage.tsx:194-196`).
2. 저장하면 게이트웨이는 JWT의 표시명을 읽어 `X-User-Name`으로 내려보낸다 (`JwtAuthenticationGatewayFilterFactory.java:167,261-263`).
3. 그러나 창고 PATCH 컨트롤러는 `X-User-Id`만 받고 `X-User-Name`을 받지 않는다 (`WarehouseController.java:148-154`). 삭제·복원·되돌리기도 같은 구조다 (`:201-207`, `:221-226`, `:256-261`).
4. 서비스는 정상 사용자 호출이면 아래 원문처럼 `actorName=null`을 기록한다.

```java
// WarehouseService.java:351
String actorName = (callerId == null || callerId.isBlank()) ? "system" : null;
```

5. 변경 이력을 펼치면 화면은 그 `null`을 아래 원문대로 표시한다.

```ts
// EditWarehouseModal.tsx:334-337
if (actorId === SYSTEM_ACTOR_ID) return '시스템'
if (!actorName || UUID_RE.test(actorName.trim())) return '변경자 미상'
return actorName
```

따라서 UUID 노출은 막혔지만, 게이트웨이가 이미 가진 실제 변경자 표시명까지 저장 경계에서 버려진다.

## 실 데이터와 라이브 화면

- 관측 당시 `inventory_db.inventory_audit_logs JOIN warehouses`는 2행이었다.
- 분류: 정상 표시명 0행 / UUID 형태 `actorName` 2행 / null·blank 0행 / system 이름 0행.
- `auth_db.accounts` 실 데이터 33계정(활성 32, 비활성 1) 중 UUID 정규식과 일치하는 `display_name`은 0건, null·blank도 0건이었다. 따라서 이번 실 데이터에서는 UUID 판별식이 실제 이름을 과잉 차단한 행이 없다.
- 즉 과거 정상 표시명이 화면 가드에 의해 가려진 실 행은 0건이다. 결함은 HEAD 배포 후 신규 창고 감사행이 정상 표시명을 받을 통로가 없다는 쓰기 경계 회귀다.
- 실제 `EditWarehouseModal`을 Playwright headless로 렌더하고 API 응답을 고정해 확인했다. 정상 이름은 `김감사`, system sentinel은 `시스템`, HEAD 신규 쓰기 계약인 `actorName=null`은 `변경자 미상`, 과거 UUID형 `actorName`도 `변경자 미상`이었다. `isDeleted` 행만 되돌리기 버튼이 없었고 나머지 3행에는 버튼이 있었다.
- 캡처: `docs/qa/2026-08-10-1163-r2/screenshots/warehouse-actor-name-lost.png`
- SHA-256: `3C400BD26C5F868FB9460B55542629BBCC47AEDDC3AD0788AD6DCC7D0CA12641`

라이브 캡처는 새 백엔드 배포본이 아니라 HEAD 프런트 컴포넌트 + 고정 API 응답이다. 실행 중 inventory 컨테이너가 HEAD 이전 이미지라 재배포하지 않았고, 따라서 새 쓰기의 end-to-end 캡처라고 과장하지 않는다.

## 불변식

1. 인증 경계에 정상 `X-User-Name`이 있으면 창고 감사행은 그 표시명을 보존하고 화면은 그대로 보여야 한다.
2. 표시명이 없거나 UUID 형태로 오염됐으면 UUID 전체·앞 8자 모두 화면에 노출하지 않고 `변경자 미상`으로 표시해야 한다.
3. `actorId=00000000-0000-0000-0000-000000000000`은 계속 `시스템`이어야 한다.
4. 변경이 실제로 있으면 감사행은 계속 생성되어야 한다. 이름을 싣지 않는 것과 기록을 생략하는 것을 혼동하지 않는다.
5. 되돌리기 버튼 조건 `fieldName && fieldName !== 'isDeleted'`는 바꾸지 않는다.

## 양방향 RED

### RED-A — 정상 고지 보존

구체 표적: `WarehouseController`의 PATCH·DELETE·restore·audit revert 네 쓰기와 `WarehouseService.recordAuditSafe`.

- `X-User-Id=<정상 UUID>`, `X-User-Name=<UTF-8 URL 인코딩된 김감사>` 요청을 넣는다.
- 저장된 `InventoryAuditLog.actorId`는 요청 UUID, `actorName`은 디코딩된 `김감사`여야 한다.
- 이후 `GET /inventory/warehouses/{id}/audit-logs`와 `EditWarehouseModal`에서 `김감사`가 보여야 하고 `변경자 미상`으로 덮이면 실패한다.
- 현재 HEAD는 컨트롤러가 이름 헤더를 받지 않고 서비스가 null을 기록하므로 이 RED가 실패해야 한다.

### RED-B — UUID 비공개·system·기록·액션 무회귀

구체 표적:

- 이름 헤더 누락 + 사용자 UUID: 감사행은 생성되되 `actorName`에 UUID를 복사하지 않고 화면은 `변경자 미상`; UUID 전체와 앞 8자 모두 0회 노출.
- 과거 `actorName=<UUID>` 응답: 화면은 `변경자 미상`.
- system sentinel: 화면은 정확히 `시스템`.
- 정상 `actorName=김감사`: 화면은 정확히 `김감사`.
- 변경 필드 1건 저장 전후 감사행 수는 +1. 감사 기록 호출을 제거하거나 예외로 삼으면 실패.
- `name` 행에는 되돌리기 버튼 1개, `isDeleted` 전용 행에는 0개.

이 RED-B는 정상 이름 복구 과정에서 `callerId` 폴백이나 화면 UUID 가드를 되돌리는 반대급부를 차단한다.

## 수정 범위

- 포함: `WarehouseController` 네 쓰기 경로의 `X-User-Name` 수신, 안전한 UTF-8 URL 디코딩, `WarehouseService`로 표시명 전달, UUID형/blank 표시명 저장 방어, 해당 controller/service/UI 계약 테스트.
- 제외: slip-service #1134 R12, partner-order·accounting 기존 가드, `deletedBy/createdBy/markDeleted` 내부 감사 컬럼, 전 서비스 resolve 패턴 일괄 정리.

## 범위 밖 계열 도달 근거

- `InventoryAuditController`: audit 응답은 `InventoryAuditDetailPage`에 연결되지만 현재 화면 소비자는 `AuditRevisionBadge`의 revision 수/복원 후보뿐이며 actor 텍스트를 렌더하지 않는다. edit-request의 `requesterName/approverName` 응답은 현재 desktop 화면 소비자가 없다.
- `ArologisAdminController`: audit API factory는 선언돼 있으나 `arologisDispatchAuditApi`를 import해 렌더하는 desktop 화면이 없다. edit-request 이름 응답도 현재 화면 소비자가 없다.
- `PartnerVersionHistoryPanel`과 `PartnerOrderVersionHistoryPanel`: 각각 UUID 정규식 + `displayActor`를 거쳐 UUID형 actorName을 null 처리한 뒤에만 렌더한다 (`PartnerVersionHistoryPanel.tsx:55-66,282-284`; `PartnerOrderVersionHistoryPanel.tsx:116-127,363`).
- 나머지 `resolveName(callerId, callerName)` 13개 파일 중 사용자 화면 소비가 확인된 slip·partner-order·accounting 계열은 이번 명시 범위 밖이다. product·partner edit-request 계열은 현재 desktop 화면 소비자가 없다.

따라서 위 범위 밖 목록에서 이번 범위에 추가할 UUID 화면 도달 경로는 확인되지 않았다.

## 반대급부 금지

- `actorName=callerId` 복원 금지.
- 프런트 UUID 정규식 가드 제거 금지.
- 정상 사용자의 `actorId`를 system sentinel로 바꿔 숨기기 금지.
- 감사 recorder 호출 생략·조건 확대 금지.
- 되돌리기 버튼 조건 변경 금지.
