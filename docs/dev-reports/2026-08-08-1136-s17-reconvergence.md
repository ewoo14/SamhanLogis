# PR #1137 / 이슈 #1136 — S17 SOL 재수렴

## 결론

**BLOCK 1건.** S16의 정상 출력 허용, fixture 실행 입력 배선, git baseline, 누락 진단, 적용 migration 가드는 재현됐다. 그러나 S16에서 추가한 성공 정규식은 숫자와 실행 시간 형식을 제한하지 않아, 정상 Flyway 출력이 아닌 문장을 실제 repair 스크립트 경로에서 성공으로 통과시킨다.

검증 대상은 도달성 4개 각도로 한정했다. 실제 `repair`와 `flyway_schema_history` 변경은 실행하지 않았다.

## 1. 1차 각도 — 정상 경로와 반대쪽

### 1.1 실제 정상 경로 — accounting-service / auth-service

다음 명령을 현재 HEAD `e79b720ab04a668e1e80688c57fe0a6651fe30a9`에서 각각 실행했다.

```powershell
powershell.exe -NoProfile -File scripts/repair-flyway-checksums.ps1 -Service accounting-service -WhatIf
powershell.exe -NoProfile -File scripts/repair-flyway-checksums.ps1 -Service auth-service -WhatIf
```

실측 원문:

```text
===ACCOUNTING===
Environment file: C:\dev\Samhan-Public\.claude\worktrees\t1123\infrastructure\.env.local
accounting-service: checksum mismatch versions = (none)
ACCOUNTING_EXIT=0

===AUTH===
Environment file: C:\dev\Samhan-Public\.claude\worktrees\t1123\infrastructure\.env.local
auth-service: checksum mismatch versions = (none)
AUTH_EXIT=0
```

동일 이미지·네트워크·migration read-only mount로 Flyway 원문도 직접 대조했다.

```text
Database: jdbc:postgresql://postgres:5432/accounting_db (PostgreSQL 16.14)
Successfully validated 70 migrations (execution time 00:00.172s)
accounting-service_RAW_EXIT=0

Database: jdbc:postgresql://postgres:5432/auth_db (PostgreSQL 16.14)
Successfully validated 96 migrations (execution time 00:00.215s)
auth-service_RAW_EXIT=0
```

**판정: 정상 양방향 도달.** S16 보고서의 “실제 accounting-service · auth-service WhatIf exit 0” 주장을 재현했다.

### 1.2 S17-BLOCK-1 — 새 성공 정규식이 비정상 문장을 성공으로 통과시킨다

대상 정규식:

```regex
^\s*Successfully validated\s+[0-9,]+\s+migrations\s+\(execution time\s+[^)]+\)\s*$
```

`[0-9,]+`는 쉼표만 있는 값도 허용하고, `[^)]+`는 시간 형식이 아닌 임의 문자열도 허용한다. 다음 fake Docker는 스크립트가 공식 지원하는 `-DockerCommand` 경계에 연결했고, validate 호출에 비정상 한 줄을 그대로 반환한 뒤 exit 0을 반환했다.

```text
FAKE_DOCKER_RAW:
Successfully validated ,,, migrations (execution time permission denied)
FAKE_DOCKER_EXIT=0
```

실제 스크립트 실행 결과:

```text
Environment file: C:\Users\user\AppData\Local\Temp\s17-output-cases-...\test.env
auth-service: checksum mismatch versions = (none)
overbroad-success-regex_EXIT=0
```

재현 절차:

1. 위 한 줄을 stdout으로 내고 exit 0인 임시 `.cmd`를 만든다.
2. dummy credential fixture와 함께 `repair-flyway-checksums.ps1 -Service auth-service -DockerCommand <cmd> -WhatIf`를 실행한다.
3. 스크립트가 비정상 원문을 `$unexpectedLines`에서 제거하고 `(none)`, exit 0으로 끝내는 것을 확인한다.

왜 실 경로인가: 정규식만 단독 호출한 것이 아니다. 공개 매개변수 `-DockerCommand` → `Invoke-Docker` → `$validate.Output` → `$unexpectedLines` → 215행 판정 → 서비스 성공 출력까지 전체 실행 경로를 통과했다. S16이 추가한 바로 그 허용 분기가 비정상 문장을 제거했다.

**영향:** “성공 출력 형식만 허용한다”는 경계가 도달하지 않는다. Flyway가 아닌 wrapper/대체 Docker command가 exit 0과 이 문장을 반환하면 검증 실패 근거가 없어도 정상으로 판정된다.

### 1.3 비-checksum 실패 거부

각 케이스는 `-WhatIf` 또는 임시 입력만 사용했다.

#### DB 접속 불가 — 실제 Flyway

`-Network none`으로 실제 Flyway 10.10.0 컨테이너의 DB 접속을 끊었다.

```text
ERROR: Unable to obtain connection from database (jdbc:postgresql://postgres:5432/auth_db) for user 'samhan': The connection attempt failed.
SQL State  : 08001
Caused by: java.net.UnknownHostException: postgres
DB_CONNECTION_EXIT=1
```

#### schema history 없음 — 실제 Flyway 원문 + wrapper 재입력

읽기 조회로 `postgres` DB에 history table이 없음을 확인한 뒤 validate만 실행했다. 실행 전후 모두 table은 없었다.

```text
POSTGRES_DB_HISTORY=MISSING
Schema history table "public"."flyway_schema_history" does not exist yet
ERROR: Validate failed: Migrations have failed validation
Detected resolved migration not applied to database: 1.
SCHEMA_HISTORY_MISSING_RAW_EXIT=1
POSTGRES_DB_HISTORY_AFTER=MISSING
```

이 실제 형식의 핵심 행들을 fake Docker 실행 입력으로 repair 스크립트에 넣은 결과:

```text
auth-service validate failed for a reason other than a checksum mismatch:
ERROR: Validate failed: Migrations have failed validation
Schema history table "public"."flyway_schema_history" does not exist yet
Detected resolved migration not applied to database: 1.
SCHEMA_REAL_SHAPE_WRAPPER_EXIT=1
```

#### 권한 없음

DB 권한 거부 형식의 실행 입력을 실제 repair 스크립트 경계에 넣었다.

```text
auth-service validate failed for a reason other than a checksum mismatch:
ERROR: permission denied for table flyway_schema_history
permission-denied_EXIT=1
```

별도로 실제 PostgreSQL 인증 거부도 exit 1이었다.

```text
ERROR: Unable to obtain connection ... FATAL: password authentication failed for user "samhan"
SQL State  : 28P01
PERMISSION_EXIT=1
```

#### migration 파일 손상 — 실제 DB validate + git baseline

auth migration 94개를 임시 migration root에 복사하고 `V1__init_account.sql`에 미커밋 주석을 추가했다. 실제 auth DB validate가 checksum mismatch version 1을 냈고, repair 전에 git baseline이 차단했다.

```text
auth-service: checksum mismatch versions = 1
auth-service: repair 거부 — git baseline 검증 실패
services/auth-service/src/main/resources/db/migration/V1__init_account.sql:
HEAD=d964aeec4a6d29c50e5dcafa7688b0046b109b47
working-tree=ee262f82cacace781af90a1d3a6bcf9656fb9e50
MIGRATION_DAMAGE_EXIT=1
DAMAGE_TEMP_REMOVED=True
```

#### 예상 밖 출력

```text
S17_UNEXPECTED_FLYWAY_OUTPUT
auth-service validate failed for a reason other than a checksum mismatch:
unexpected-output_EXIT=1
```

#### checksum mismatch + 다른 오류 혼합

```text
Migration checksum mismatch for migration version 1
Detected failed migration version 2
auth-service validate failed for a reason other than a checksum mismatch:
mixed-checksum-other_EXIT=1
```

**판정:** 요청된 비-checksum 실패 5종과 혼합 오류는 거부됐다. 다만 1.2의 새 정규식에 맞춘 비정상 성공 문장은 반대쪽을 통과한다.

## 2. 2차 각도 — fixture 배선

### 2.1 실행 입력 사용 여부

`repair-flyway-checksums.test.ps1`의 `$fixtureDocker`는 다음처럼 fixture 파일을 직접 `type`하고 exit 1을 반환한다. 테스트는 이 command를 `-DockerCommand $fixtureDocker`로 실제 repair 스크립트에 전달한다.

```text
type "scripts/fixtures/flyway-validate-checksum-mismatch.txt"
exit /b 1
```

원본 테스트 실행 결과:

```text
auth-service: checksum mismatch versions = 1
What if: Performing the operation "Flyway repair (checksum metadata only)" on target "auth-service".
Flyway repair credential scenarios: PASS
REPAIR_TEST_EXIT=0
```

### 2.2 실제 Flyway 출력과 대조

fixture의 구조:

```text
Flyway OSS Edition 10.10.0 by Redgate
Database: jdbc:postgresql://127.0.0.1:5432/auth_db (PostgreSQL 16.13)
ERROR: Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 1
-> Applied to database : 123
-> Resolved locally    : 906221903
Either revert the changes to the migration, or run repair to update the schema history.
```

실제 auth migration 임시 손상으로 캡처한 Flyway 10.10.0 원문:

```text
Flyway OSS Edition 10.10.0 by Redgate
Database: jdbc:postgresql://postgres:5432/auth_db (PostgreSQL 16.14)
ERROR: Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 1
-> Applied to database : -670111044
-> Resolved locally    : 1418916544
Either revert the changes to the migration, or run repair to update the schema history.
REAL_MISMATCH_EXIT=1
```

호스트·PostgreSQL patch version·checksum 숫자만 환경에 따라 다르고 문장 구조는 일치한다.

### 2.3 fixture 변이 생존성

저장소 파일은 바꾸지 않고 fixture와 테스트의 임시 복제본을 만들었다. fixture 마지막 허용 행을 다음 sentinel로 교체했으며, fixture 완전성 사전검사는 그대로 통과하도록 checksum 핵심 행은 유지했다.

```text
S17_UNEXPECTED_SENTINEL_FROM_MUTATED_FIXTURE
```

결과:

```text
fixture-backed checksum mismatch preview failed:
auth-service validate failed for a reason other than a checksum mismatch:
...
S17_UNEXPECTED_SENTINEL_FROM_MUTATED_FIXTURE
MUTATED_FIXTURE_TEST_EXIT=1
TEMP_REMOVED=True
```

**판정:** fixture는 정규식 사전검사에만 쓰이는 것이 아니라 실제 실행 입력이다. fixture 변경이 실행 결과를 바꾸고 테스트를 실패시켰다.

## 3. 3차 각도 — 회귀 울타리

### 3.1 git baseline

현재 HEAD migration 전수를 `git rev-parse HEAD:<path>`와 `git hash-object -- <path>`로 대조했다.

```text
HEAD_MIGRATIONS=407
GIT_BASELINE_MATCH=407
GIT_BASELINE_MISMATCH=0
```

정상 복사본은 repair preview에 도달했고, 위 1.3의 미커밋 손상은 blob 불일치로 거부됐다.

### 3.2 조용한 누락 없음

회귀 테스트의 실제 실행 원문:

```text
Service discovery failed; resolve the omitted service(s) before running Flyway repair.
dashboard-service (migration directory not found): ...\services\dashboard-service\src\main\resources\db\migration
new-service (no database mapping): ...\services\new-service\src\main\resources\db\migration
```

명시 서비스 호출도 각각 `no database mapping`, `migration directory not found`로 거부됐다.

### 3.3 가드 본체 — 실 데이터 차단 수

`origin/main` tree의 실제 경로를 가드의 `Is-AppliedMigration` 정규식과 `M`/`D`/`R*` 분기에 대입해 셌다.

```text
ORIGIN_MAIN_MIGRATIONS=407
AS_MODIFIED_BLOCK=407
AS_DELETED_BLOCK=407
AS_RENAMED_OLDPATH_BLOCK=407
```

서비스별 실측 합계:

```text
accounting-service 70   arologis-service 25   auth-service 94
dashboard-service 7    dc-config-service 5   groupware-service 18
inventory-service 23   notification-service 10   partner-auth-service 3
partner-order-service 17   partner-service 13   product-service 32
slip-service 78   user-service 12
TOTAL 407
```

현재 branch는 migration diff가 없고 실제 guard가 정상 개발 상태를 막지 않았다.

```text
PASS: origin/main 대비 적용된 마이그레이션 변경 없음 (신규 migration 추가는 허용).
CURRENT_GUARD_EXIT=0
```

회귀 테스트는 신규 migration 추가와 unrelated 변경을 허용하고, 수정·삭제·rename을 거부한 뒤 다음으로 끝났다.

```text
Flyway applied-migration guard scenarios: PASS
GUARD_TEST_EXIT=0
```

**판정:** 적용 migration 수정·삭제·rename은 각 407/407 BLOCK, 현재 정상 개발 작업의 오차단은 0건이다.

## 4. 4차 각도 — S16 증거 무결성

재현된 주장:

- 실제 `accounting-service -WhatIf`: exit 0.
- 실제 `auth-service -WhatIf`: exit 0.
- 실제 Flyway 정상 원문: 각각 `Successfully validated 70/96 migrations`.
- fixture checksum-only 입력: version 1 및 repair WhatIf 도달.
- 미커밋 migration 손상: 실제 DB validate 뒤 git baseline 거부.
- 비-checksum 혼합 실패: exit 1.
- repair 테스트와 가드 테스트: 모두 exit 0.
- S14 잔존 식별자 grep: `STALE_IDENTIFIERS=0`.

S16 보고서의 위 핵심 주장은 재현됐다. 단, S16의 “비-checksum 실패 거부를 그대로 유지했다”는 포괄 결론은 S17-BLOCK-1의 비정상 성공 문장까지 포함하면 성립하지 않는다.
