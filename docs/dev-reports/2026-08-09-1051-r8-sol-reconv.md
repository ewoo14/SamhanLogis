## 3. 잠금 독립축·취소 409

- exact HEAD 실 API에 잠긴 `CONFIRMED` 전표 취소를 요청하자 `HTTP 409`, `code=CONFLICT`, `message=취소 가능한 상태가 아닙니다: 확정`이었다.
- 직후 재조회는 `status=CONFIRMED`, `lockFlag=true`; 상태·잠금 모두 불변이었다.
- 현재 실 잠금 5건은 전부 `CONFIRMED`라 UI에 취소 버튼 자체가 없다. 사용자는 화면의 “회계 마감으로 잠긴 전표입니다. 취소·반려를 포함한 변경은 409로 차단됩니다.” 안내를 먼저 본다. 409 원문도 현재 상태에서 취소 불가임을 설명하므로 이해 가능하다.
- 잠금은 DTO에서 `slip.getLockFlag()`로, 상태는 `slip.getStatus()`로 각각 매핑된다. FE도 `slip.lockFlag === true` 배지와 별도 상태 배지를 동시에 렌더한다.
- `SlipLockTest`는 잠긴 DRAFT의 cancel, 잠긴 SENT의 reject가 상태와 별개로 CONFLICT이고 `unlock()`을 명시 호출해야 가변성이 돌아오는 계약을 고정한다.

## 4. mock ↔ 실 API parity

- mock fixture: `lockFlag=true`와 `lockFlag=false`가 모두 있고 상세 handler가 해당 객체를 반환한다.
- 실 API: 잠금 2건 `lockFlag=true`, 미잠금 1건 `lockFlag=false`를 실제 DOM까지 왕복했다.
- mock과 실 서버 모두 잠금 취소를 409로 거부한다. 문구는 mock이 회계 마감 사유를 직접 말하고, 실 데이터는 이미 `CONFIRMED`라 상태 가드 문구를 먼저 반환하지만 HTTP 의미와 `lockFlag` 계약은 같다. UI에는 회계 마감 사유가 별도 안내된다.

따라서 “mock만 `lockFlag`를 내고 실 서버는 누락”하는 false green은 재현되지 않았다.
