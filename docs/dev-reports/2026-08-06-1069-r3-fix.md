## 1. 0단계 C-1 판별

판정은 **(다)**이다.

단품 경로에서는 거래처 전역DC가 적용된다. `SlipFormPage`에 `product_type=SINGLE`, `categoryKey=commercialMulti`, 판매가 `20,680,000`, 거래처 commercial DC `46%`를 넣은 판별 테스트에서 단가 `11,167,200`과 `거래처 전역DC 46% 적용`이 확인됐다. 따라서 `#874`처럼 판매전표 입력 전체에서 전역DC가 빠진 상태인 (나)는 아니다.

세트 경로도 세트 부모의 전개 기준 단가에는 전역DC가 먼저 적용된다. 기존 전역DC 전개 테스트와 C-1 판별 테스트가 이 경로를 고정한다. 다만 `BundleExpander`는 구성품 중 `PANEL`·`REMOTE` 같은 고정 구성품을 각 구성품의 `delivery_price`로 `fixedSum`에 먼저 넣고, 남은 금액만 실내기/실외기 6:4로 재분배한다(`BundleExpander.java:318-357`). 그러므로 R2에서 본 세트 판매가 `2,752,200`의 배분과 PANEL·REMOTE 단가 불변은 구성품마다 DC를 다시 곱하지 않는 현재 설계의 결과다.

즉, “단품에도 전역DC가 안 붙는다”는 결함은 재현되지 않았고, “세트의 고정 구성품에도 전역DC를 개별 적용해야 한다”는 해석은 현재 `BundleExpander` 설계와 다르다. C-1 생산 코드는 변경하지 않았다.

실행 환경에서 인증 없이 다시 확인한 API 결과는 다음과 같다. R2의 인증된 실측에서 partner DC endpoint가 `200`이었다는 기존 증거와 달리, 현재 세션의 직접 호출은 인증이 없어 `401`이다.

```text
401 http://localhost:8080/api/v1/partner-dc-configs/1012555999
401 http://localhost:8080/api/v1/slips/lookup-product?modelName=AM340AXVGHH1
```

## 2. C-2 결정 및 수정

### 선택한 도메인

서버 도메인에 화면을 맞췄다.

```text
'' | 판넬제외 | 블랙판넬 | 승강판넬 | 공청판넬
```

근거는 `BundleExpander.pickPanel`과 Javadoc(`BundleExpander.java:166-225, 496-503`)가 이미 이 문자열을 계약으로 사용하고 있고, 기존 견적 화면의 `SINGLE_PANEL_OPTIONS`도 동일한 목록이기 때문이다. 서버에 모델코드 매칭을 새로 추가하지 않았다.

변경 내용:

- `BundleOptionRow.tsx`의 판넬 자유 입력을 서버 도메인만 제공하는 `<select>`로 변경했다. 안내 문구와 실제 입력값이 일치한다.
- 기존 견적 화면과 판매전표 화면이 공유하도록 `utils/bundleOptionDomain.ts`에 목록과 정규화 판별 함수를 두었다.
- `toApiBundleSetOptions`에서 서버 도메인 밖의 값은 `null`로 정규화한다. 모델코드 `PC6NUCK1NW`가 API에 그대로 전송되지 않는다.
- 개발용 `api/mock.ts`도 같은 키워드 도메인으로 판넬 variant를 선택하거나 `판넬제외` 시 판넬 행을 제외하도록 맞췄다. 이 후속 표면은 RED를 별도로 재현했다.
- 무효 옵션으로 재전개 요청이 실패하거나 빈 전개 응답이 오면, 최초 전개가 아니라 기존 구성품이 있는 재전개라면 기존 구성품을 유지하고 `lookupLoading`/`expansionPending`을 해제한다. 안내만 오류 상태로 남기고 저장 버튼을 영구 비활성화하지 않는다(`SlipFormPage.tsx:972-1050`).
- `REMOTE` 교체 컨트롤은 추가하지 않았다.

### REMOTE 컨트롤 확인 결과

현재 브랜치 소스 기준으로는 “컨트롤이 전혀 없음”이 아니다. `BundleOptionRow.tsx:91-115`에 `실외기 제외` checkbox와 `실외기 교체` modelCode 입력이 이미 있고, `slip.ts:256-259, 298-299`, `SlipLookupController.java:64-67`, `ProductClient.java:329-330`을 통해 `remoteOption`·`remoteExcluded`가 전달된다. 따라서 R2 화면에서 보이지 않았다는 관측은 현재 소스와 불일치하며, 배포된 renderer artifact 또는 해당 QA 화면 조합 차이로 별도 확인할 사안이다. 이번 변경에서는 컨트롤을 신설하지 않았다.

## 4. 새로 가능해진 조합 점검

| 조합 | 점검 결과 |
|---|---|
| 세트 + 옵션 미입력 + 전개 전/후 | 서버 기본 판넬을 포함한 4행 유지. `BundleExpanderIT` GREEN |
| 세트 + `블랙판넬`/`승강판넬`/`공청판넬` | select가 키워드를 보내고 서버가 해당 panel variant를 선택. mock도 같은 계약으로 GREEN |
| 세트 + `판넬제외` | PANEL 행 제거, IN/OUT/REMOTE 유지. `BundleExpanderIT`에서 3행 GREEN |
| 세트 + 예전 모델코드/임의 문자열 | API에서 `null`로 정규화되어 서버 기본 경로. 재전개 실패 시 기존 행과 저장 가능 상태 유지 |
| 세트 + 유효 옵션 변경 + 저장 전/후 | 옵션 pending이 성공 시 해제되고, 전체 `SlipFormPage` 테스트에서 기존 저장/전개 계약 회귀 없음 |
| 비세트 SINGLE + commercialMulti + 전역DC | `20,680,000 × 54% = 11,167,200`, 46% 전역DC 표시 확인. BUNDLE 전개 경로를 거치지 않음 |
| 세트 + REMOTE 제외/교체 | 기존 컨트롤·API 전달 경로를 확인했으며 이번 라운드에서 UI를 추가하지 않음 |

실제 저장 API를 인증된 라이브 환경에 쓰는 검증은 현재 세션 인증이 없어 수행하지 않았다. 대신 무효 재전개 테스트에서 저장 버튼이 다시 활성화되는 상태를 검증했고, 전체 저장 payload 회귀 테스트를 포함해 실행했다.

## 5. 식별자 grep 전수 결과

실행한 survey 결과:

- 기존 placeholder `판넬 모델코드`는 현재 production renderer source에 남아 있지 않다.
- `SINGLE_PANEL_OPTIONS`의 단일 정의는 `utils/bundleOptionDomain.ts`이며, `EstimatePricingConfigPage.tsx`와 `BundleOptionRow.tsx`가 이를 참조한다.

- `remoteOption`·`remoteExcluded`는 화면 → API → `SlipLookupController` → `ProductClient` → `BundleExpander` 전 경로에 존재한다.
- `PC6NUCK1NW`는 서버 도메인 밖 값의 정규화 RED 테스트에만 남아 있다.
