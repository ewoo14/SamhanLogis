## 원인 가설 확정 및 경로 전수

**Root cause hypothesis:** `PartnerLedgerReadService.read()`가 `partnerCode`를 받으면 partner master `FOUND`를 `requireFound()`로 강제한 뒤에야 slip-service를 호출한다. R11 목록의 code-only 행은 master UUID가 없어도 slip-service의 `partnerCode` 조건으로 읽을 수 있으므로, 이 선행 검증이 목록과 상세의 식별자 계약을 갈라 422를 만든다.

| 사용자 경로 | 현재 내부 경로 | R13 처리 여부 |
|---|---|---|
| 무필터 목록 조회 | `SalesAggregateService` → `PartnerLedgerSalesClient.find(from,to,null,null)` | 유지. code-only 행을 목록에서 빼지 않음 |
| 정상 master 행 클릭 | `PartnerLedgerReadService` → partner `FOUND` → `find(..., null, partnerId)` | 유지. UUID 내부 조인 및 기존 상세 보존 |
| code-only 행 클릭 | `PartnerLedgerReadService` → partner `NOT_FOUND`에서 422 → slip 조회 미도달 | 수정 대상. `find(..., partnerCode, null)` fallback |
| 상세의 자동 저장 이력 | `LedgerSnapshotService.history()` → partnerCode 문자열 조건 | 기존 경로 유지·별도 422 선행 검증 없음 |
| 상세의 인쇄 미리보기 | `PartnerLedgerPage.handlePrint()` → `/print/partner-ledger?partnerCode=...` → `getLedgerData()` → 위 상세 경로 | 상세 fix 후 데이터 있는 상태에서 재현·검증 |
| 일괄 인쇄 | 각 선택 code에 대해 동일 print route 반복 | 상세 fix와 함께 확인 |

**Linux 판정:** 이 경로 단정은 OS API/경로 구분자가 아니라 Java 서비스의 문자열·HTTP 계약과 React 라우트 계약에 대한 것이므로 `ubuntu-latest`에서도 동일하다. RED 회귀 테스트는 UUID·전표번호를 응답 표시 식별자로 단정하지 않고, code-only business key와 문서/라인 존재만 검증한다.

### RED 실행 보정

- 첫 실행은 `BUILD FAILED`였지만 제품 422가 아니라 Mockito `UnnecessaryStubbingException`이었다. 수정 전 서비스가 partner master `NOT_FOUND`에서 조기 종료하여, 테스트에 미리 둔 slip/receipt stub이 사용되지 않았기 때문이다.
- 이 테스트 하네스 문제만 `lenient` stub으로 보정한다. 이 시점에는 제품 코드를 수정하지 않았다.

일괄 인쇄를 단건 fix의 처리 완료로 세지 않았다. 새 UUID/전표번호를 목록·상세 화면 식별자로 추가하지 않았고, code-only fallback의 `partnerCode`는 내부 API 조회 키로만 사용한다.

## accounting-service 전체 변경 표면 테스트

요청한 캐시 배제 조건으로 모듈 전체 테스트도 시도했다.

```powershell
.\gradlew.bat :services:accounting-service:test --no-daemon --no-build-cache --rerun-tasks
```

- 결과: **304초 timeout**. `UP-TO-DATE`/`FROM-CACHE`를 사용하지 않았으나 전체 모듈 완료/실패 원문을 받기 전에 runner timeout이 났다.
- 관련 Gradle launcher/test worker PID는 확인 후 종료했다. 이 정리는 Docker 서비스나 실 DB에 영향을 주지 않는다.
- 권위 있는 변경 표면 테스트 결과는 앞서 수행한 동일 조건의 `PartnerLedgerReadServiceTest` 2건 **2 passed**, `21 actionable tasks: 21 executed`이다. 전체 모듈 GREEN은 주장하지 않는다.
- **Linux 판정:** Gradle 명령·캐시 배제 플래그와 변경 표면 테스트 계약은 Linux에서도 동일하지만, 전체 모듈은 이번 Windows runner에서 timeout되어 ubuntu-latest 결과를 대신 주장하지 않는다.

## 새로 만든 표면 진술

- BE: partner master `NOT_FOUND`인 기존 판매전표 code-only 행에도 `partnerCode` 기반 상세 문서/라인 조회 경로를 새로 열었다. master `FOUND`는 UUID 내부 조인을 그대로 사용한다.
- FE: 단건 인쇄 버튼이 Electron의 차단된 내부 `window.open()` 대신 현재 BrowserWindow의 기존 `/print/partner-ledger` route로 진입하도록 새 navigation 표면을 만들었다.
- 테스트: code-only/master 상세 계약 2건과 실제 데이터 상세→인쇄 route 이동 회귀 테스트를 새로 만들었다.
- 새 화면 식별자나 UUID/전표번호 노출 표면은 만들지 않았다. 일괄 인쇄 다중창은 기존 표면으로 유지했다.
