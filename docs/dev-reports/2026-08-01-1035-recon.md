- `2026-08-01-1018-fix.md`와 `2026-08-01-1018-fix2.md`는 컨테이너 분리 뒤 전체 1,532건 중 441건이 실패했으며, 공유 스키마 teardown 경합과 병렬 fork의 PostgreSQL 연결 초과가 원인이었음을 기록한다.
- `2026-08-01-1018-fix3.md`는 검증용 세 번째 DataSource/Hikari pool 추가가 커넥션 고갈과 `dedicatedDataSourceTrio` 계약 실패를 일으킨 사실을 기록한다.

## 확인 1 — `warehouse-code-map` 현재 형태

- `services/slip-service/src/main/resources/application.yml:184-191`에 legacy 창고코드 → 내부 창고 식별자 매핑으로 선언돼 있다.
- `application.yml:187`의 `warehouse-code-map` 아래에 창고코드 `[00003]`, `[2]`, `[14]`, `[1]` 네 항목이 있고, 각각 `WAREHOUSE_UUID_HQ`, `WAREHOUSE_UUID_HUBAL`, `WAREHOUSE_UUID_ANSEONG`, `WAREHOUSE_UUID_CHANGWON` 환경변수 placeholder를 사용한다(`:188-191`).
- 환경변수는 총 **4개**다. 각 placeholder에는 기본값이 함께 있어 환경변수가 없더라도 문자열 치환 자체는 성공한다.
- UUID 값은 규약에 따라 기록하지 않았다.

## 확인 2 — 실 DB `warehouses` 실재성

- 실행 중인 `samhan-slip-service` 컨테이너에 주입된 네 환경변수 값을 내부적으로만 읽어, 실행 중인 `samhan-postgres`의 `inventory_db.public.warehouses`에 읽기 전용 `SELECT`로 대조했다. Docker 재빌드·재기동과 DB 쓰기는 수행하지 않았다.
- soft-delete되지 않은 실재 행 기준 결과: **4개 중 4개 실재**.
- 창고코드 대조: `[00003]` → `HQ-001`, `[2]` → `VH-001`, `[14]` → `CS-001`, `[1]` → `VR-001`; 모두 `EXISTS`였다.
- UUID 값은 조회 출력과 보고서에 기록하지 않았다.

## 확인 3 — 미치환/오주입 시 실행 경로

- Spring 바인딩 대상은 `Map<String, String>`이다(`WarehouseCodeMapper.java:39-45`). `@PostConstruct`는 맵이 비었는지만 경고하고, 비어 있지 않으면 항목 수만 INFO로 남긴다(`:47-57`). 값 형식이나 `inventory_db.warehouses` 실재성·창고코드 일치 여부는 기동 때 검사하지 않는다.
- `application.yml:188-191`은 `${환경변수:기본값}` 형태다. 따라서 환경변수가 없으면 placeholder 문자열이 그대로 남는 것이 아니라 기본 UUID 문자열이 선택되고, 서비스는 예외 없이 기동한다. 현재 실행 환경에서는 그 기본/주입 식별자 네 개가 확인 2와 같이 모두 올바른 실재 행을 가리킨다.
- 발행 요청 때에야 `WarehouseCodeMapper.resolve()`가 매핑 존재와 UUID **문법**만 확인한다(`WarehouseCodeMapper.java:66-81`). 문법상 유효하지만 미실재이거나 다른 창고를 가리키는 UUID는 그대로 반환한다.
- 반환값은 견적 발행에서 `Slip.createOutbound(...)`로 들어가고(`SlipPublishService.java:135-149`), `saveAndFlush`로 저장된다(`:173-178`). 주문/병합 폴백도 같은 mapper를 사용한다(`:215`, `:316`, `:446-455`).
- 전표 엔티티는 `source_warehouse_id`를 단순 UUID 컬럼으로 가진다(`Slip.java:164-168`); V1 스키마에도 inventory `warehouses`를 향한 외래키가 없다(`V1__init_slip_service.sql:25-26`). 도메인 생성 검증도 null만 거부한다(`Slip.java:656-665`).
- 판정: **기동 예외가 아니라 조용한 통과**다. 더 정확히는 현재 로컬 네 값은 정상이나, 코드상 임의의 “문법상 유효한” 오주입도 기동·매핑·전표 저장까지 통과할 수 있다. 이것이 결함의 크기이며, 실재성뿐 아니라 창고코드 정체성도 보장하지 않는다. 반대로 빈 문자열이나 UUID 문법 오류도 기동 때는 통과하고 최초 해당 발행 요청에서만 `INTERNAL_ERROR`가 난다.

## 확인 4 — 맵 사용처 전수 조사

- production Java 전체 검색 결과, 맵을 소유하고 직접 읽는 클래스는 `WarehouseCodeMapper` **1개**뿐이다. 직접 데이터 접근은 기동 로그용 `isEmpty()`/`size()`(`WarehouseCodeMapper.java:50,56`)와 해석용 `get()`(`:70`)이다.
- 이 mapper를 주입받는 production 소비 클래스도 `SlipPublishService` **1개**뿐이다(`SlipPublishService.java:101`).
- `warehouseCodeMapper.resolve(...)` 직접 호출 지점은 **2곳**이다: 견적 발행(`:135`)과 공통 폴백 helper(`:455`).
- 공통 폴백 helper 호출 지점은 주문 발행(`:215`)과 주문 병합 발행(`:316`) **2곳**이다. 따라서 맵이 실제 업무에서 사용되는 논리 경로는 견적·주문·주문 병합의 **3개**다.
- 다른 서비스에서 발견된 `WarehouseCodeMapper` 문자열은 복제 금지를 설명하는 Javadoc 참조뿐이며, 실제 소비가 아니다.

## 확인 5 — `dedicatedDataSourceTrio` 강제 계약

- 계약 테스트는 `services/slip-service/src/test/java/com/samhanair/logis/slip/price/config/PartnerProductPriceMemoryAsyncConfigTest.java:133-164`의 `dedicatedDataSourceTrio_coexistsWithPrimaryMainDataSource()`다.
- `dataSource`와 `priceMemoryDataSource` 두 bean이 모두 존재해야 한다(`:138-140`). 무자격 `DataSource` 조회는 `@Primary` 메인 `dataSource`와 동일해야 하고, 가격기억 전용 DataSource와는 다른 인스턴스여야 한다(`:141-145`).
- `PriceMemoryJdbcAccess`가 감싼 **세 요소**—전용 DataSource, `JdbcTemplate`, `DataSourceTransactionManager`—는 모두 동일한 `priceMemoryDataSource` 인스턴스에 결속돼야 한다(`:146-153`). 즉 이름의 “Trio”는 전용 DataSource가 3개라는 뜻이 아니라, **전용 DataSource + JdbcTemplate + 트랜잭션 매니저 3종**의 동일 인스턴스 결속이다.
- 전용 `JdbcTemplate`과 트랜잭션 매니저는 각각 `JdbcOperations`/`TransactionManager` 타입 bean으로 노출되면 안 된다. `JdbcOperations` bean 이름은 정확히 `jdbcTemplate` 하나여야 하고, `TransactionManager` 타입 bean 목록은 비어 있어야 한다(`:155-163`). 그래야 Boot 기본 `jdbcTemplate`과 `JpaTransactionManager` 자동구성이 back-off하지 않는다.
- production 구성의 대응 구현은 `SlipDataSourceConfig.java:90-95`(메인 `@Primary` pool), `:122-125`(가격기억 전용 pool), `:136-145`(전용 3종 묶음), `:160-163`(record)이다.
- 판정: 현재 강제 계약은 **DataSource 2개(메인 1 + 가격기억 전용 1)**와 전용 접근 3종 결속이다. 창고 검증용 세 번째 DataSource/pool 또는 독립 `JdbcOperations`/`TransactionManager` bean을 추가하면 이 계약을 침범한다.
