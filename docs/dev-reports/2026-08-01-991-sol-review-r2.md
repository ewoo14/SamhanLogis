## 확인 1 — 실행 환경과 기준 legacy 전표

현재 완화가 반영된 `samhan-slip-service`가 `127.0.0.1:18086`에서 healthy 상태임을 확인했다. 기준 실 DB 전표의 읽기 전용 조회 원문은 다음과 같다.

```text
   slip_no    |  source_type  | has_idem | lines | min_unit_price | min_vat_price 
--------------+---------------+----------+-------+----------------+---------------
 2026/05/31-5 | PARTNER_ORDER | t        |     1 |     2400000.00 |    2640000.00
(1 row)
```

이 전표 라인은 `unit_price_with_vat = unit_price × 1.1`인 구 저장 규약이다.

## 확인 2 — 신 규약 저장 라인에 저장값의 1/1.1 요청

실 DB의 신 규약 라인(`2026/08/01-7`)을 사용했다. 대상 라인의 저장값은 `unit_price=1,200,000`, `unit_price_with_vat=1,320,000`이고 최초 요청도 `unitPriceVat=1,320,000`이었다. 먼저 최초 요청을 그대로 replay해 기준을 확인한 뒤, 같은 멱등 키에서 해당 라인의 요청만 정확히 `1,320,000 / 1.1 = 1,200,000`으로 바꿨다. 질문의 `110,000 → 100,000`과 같은 비율·저장 규약이다.

실행 출력 원문:

```text

HTTP_STATUS:200
{"success":true,"code":"OK","message":"ì±ê³µ","data":{"slipId":"25298823-2c5e-4494-9f66-1df522650334","slipNo":"2026/08/01-7","status":"SENT","sourceType":"PARTNER_ORDER","sourceId":"6c1a168e-3687-4cfe-a64b-74ddfc5b9409","idempotencyKey":"qa-991-live-3dbab0ac-8b92-4120-b465-d799e86ee076","idempotentReplay":true},"timestamp":"2026-07-31T20:48:07.511006557Z"}
```

판정: **409**다. `unitPriceMatchesLegacyOrCurrent()`만 떼어 보면 `1,320,000 = 1,200,000 × 1.1`을 허용하지만, 실제 replay 전체 경로에서는 그 전에 저장된 `request_fingerprint`와 변경 요청의 현행/legacy fingerprint가 모두 불일치한다. 따라서 이 신 규약 실전표에서는 완화가 다른 금액 요청을 200으로 통과시키지 못했다.

## 확인 3 — 두 가격 컬럼만으로 규약을 구별할 수 있는가

두 규약 모두 `unit_price_with_vat = ROUND(unit_price × 1.1, 2)` 형태를 만들 수 있으므로 두 가격 컬럼만으로는 규약을 구별할 수 없다. 활성 라인 전체와 실제 멱등 PARTNER_ORDER 라인을 각각 읽기 전용 집계했다.

## 확인 4 — 실 사용자가 신 규약의 1/1.1 요청을 같은 키로 만들 수 있는가

호출자를 끝까지 추적한 결과, **화면 조작으로 같은 키·다른 단가 요청을 만들 수 없다.** 관련 화면은 본사 Desktop의 `판매 > 거래처 주문 상세`이다.

1. 주문 상세 편집에서 라인의 `deliveryPrice`를 수정할 수 있다(`SalesPartnerOrderDetailPage.tsx`의 `items.{index}.deliveryPrice` 입력).
2. 같은 화면의 `판매전표 전환` 모달은 사용자가 라인과 수량·창고만 고른다. 단가는 입력받지 않는다.
3. `PartnerOrderConvertService`가 DB의 `PartnerOrderLine.priceVat`를 `unitPriceVat`로 복사한다.
4. 멱등 키는 `orderId + lineId + convertedBefore + quantity`로만 만들며 단가를 포함하지 않는다.
5. 그러나 주문 편집은 기존 라인을 제자리 수정하지 않는다. `PartnerOrderUpdateService.update()`가 `order.replaceLines(...)`를 호출해 기존 active 라인을 soft-delete하고 새 UUID 라인으로 재생성한다. 따라서 단가를 바꾼 뒤 같은 수량으로 전환해도 `lineId`가 달라져 멱등 키가 바뀐다.

응답 유실 뒤 사용자가 편집하지 않고 같은 라인·수량을 다시 전환하면 같은 키이지만 단가도 동일하다. 단가를 예컨대 1,320,000에서 1,200,000으로 편집하면 새 라인 UUID 때문에 새 키가 발급된다. 따라서 확인 2의 같은 키·1/1.1 요청은 직접 API를 변조하지 않는 한 실 사용자 조작으로 만들 수 없다. 직접 API로 보낸 경우에도 실제 결과는 **409**였다.

일반 사용자가 slip-service 요청 본문에 임의 단가를 직접 넣는 화면은 없다. 단일·병합 전환 모두 주문 DB의 `priceVat`를 그대로 전송한다.

## 확인 5 — 구 규약 실 DB 전표 정상 replay 재확인

실 DB 전표 `2026/05/31-5`의 기존 멱등 키와 원 요청을 사용했다. 원 요청의 JSON 숫자 scale까지 동일하게 `unitPriceVat=2400000.00`으로 전송했다.

실행 출력 원문:

```text
LEGACY_2026_05_31_5
HTTP_STATUS:200
{"success":true,"code":"OK","message":"ì±ê³µ","data":{"slipId":"cbe784ee-ede8-4a46-aa09-1f0dfe269724","slipNo":"2026/05/31-5","status":"SENT","sourceType":"PARTNER_ORDER","sourceId":"8c976ad1-8370-47e2-87ef-14467d55b6ee","idempotencyKey":"PO-CONV-8c976ad1-8370-47e2-87ef-14467d55b6ee-61f046c62f0f9576","idempotentReplay":true},"timestamp":"2026-07-31T20:50:55.361360466Z"}
```

판정: **200 replay 유지**다. 앞 라운드의 실측과 일치한다. 참고로 PowerShell 숫자 객체를 거쳐 `2400000.0` scale로 보낸 1차 캘리브레이션은 fingerprint가 달라 409였고, 원 요청 원문 scale인 `2400000.00`으로 보내자 위와 같이 200이 재현됐다. 이는 보고된 200과 수치 불일치가 아니라 요청 바이트/BigDecimal scale 차이를 제거한 재현 결과다.

## 확인 6 — legacy 키에서 category만 다른 요청

동일한 legacy 멱등 키·동일 원 요청에 `categoryKey`만 각각 `homemulti`, `commercialMulti`로 바꿔 실제 호출했다.

실행 출력 원문:

```text
CATEGORY_ONLY_COMMERCIAL_MULTI
HTTP_STATUS:200
{"success":true,"code":"OK","message":"ì±ê³µ","data":{"slipId":"cbe784ee-ede8-4a46-aa09-1f0dfe269724","slipNo":"2026/05/31-5","status":"SENT","sourceType":"PARTNER_ORDER","sourceId":"8c976ad1-8370-47e2-87ef-14467d55b6ee","idempotencyKey":"PO-CONV-8c976ad1-8370-47e2-87ef-14467d55b6ee-61f046c62f0f9576","idempotentReplay":true},"timestamp":"2026-07-31T20:51:30.155235490Z"}
```

## 확인 7 — 최종 재검증과 판단

최종 상태를 새 요청으로 다시 검증한 원문:

```text
VERIFY_CURRENT_CHANGED_STATUS=409
VERIFY_LEGACY_STATUS=200
VERIFY_CATEGORY_HOME_STATUS=200
VERIFY_CATEGORY_COMMERCIAL_STATUS=200
29|25
REPORT_CHECKS=6
REPORT_HAS_RAW=True
```

`29|25`는 실제 멱등 PARTNER_ORDER 라인 29건 중 두 가격 컬럼이 1.1 관계라 가격쌍만으로 규약을 구별할 수 없는 행이 25건이라는 뜻이다.

### 최종 판단

이번 검토 각도인 **“완화가 실제로 다른 금액 요청을 같은 전표로 통과시키는가”는 실 사용자 흐름 기준 재현되지 않았다.** 신 규약 실전표에서 저장 VAT 포함 단가의 1/1.1 값을 같은 키로 직접 보냈을 때도 HTTP 409였다. 저장 fingerprint가 가격 완화보다 먼저 다른 본문을 차단하며, 화면에서 단가를 바꾸면 라인이 새 UUID로 재생성되어 멱등 키도 바뀐다.

구 규약 정상 재시도는 실 DB `2026/05/31-5`에서 HTTP 200을 유지했다.

`categoryKey` 제거는 직접 API 수준에서 서로 다른 category 요청을 같은 legacy 전표로 HTTP 200 합친다. 그러나 category 화면 편집 역시 새 라인 UUID와 새 멱등 키를 만들므로 현재 실 사용자 흐름에서는 같은 키 조합을 만들 수 없다.

비율 허용 없이 가격 컬럼 두 개만 보고 구/신 규약을 안전하게 판별할 수는 없다. 실제 모호 가격쌍은 활성 전체 2,670건, 멱등 PARTNER_ORDER 25건이다. `unit_price_domain`까지 보면 신규 `VAT_INCLUSIVE`와 과거 `NULL`을 운영 데이터에서 나눌 수 있으나, 현재 완화 함수는 이 메타데이터를 사용하지 않는다.
