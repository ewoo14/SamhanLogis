# D-G1 S3 fix3 — 스크롤 첫 paint 분리 해소

> 대상: PR #1168, HEAD `da31f87ed` 기준 작업 트리  
> 검증일: 2026-08-11  
> 범위: `DocumentReferencePicker` portal dropdown · S3 회귀 테스트  
> 공유 DB write / 배포 / git 조작: 0건

## 1. 결론

실제 스크롤 owner를 대상으로 첫 `requestAnimationFrame`을 계측했다. 수정 후 window·overflow 조상 스크롤 모두 첫 paint에서 dropdown이 닫혔고, 두 번째 paint에도 낡은 fixed 좌표가 남지 않았다.

선택한 수단은 **스크롤 중 dropdown 즉시 숨김 + React 상태 닫힘**이다. fixed 좌표를 scroll event 후 state로 재계산하는 경로는 첫 paint 경쟁을 피할 수 없으므로, scroll listener에서 portal DOM에 `visibility:hidden`을 먼저 적용하고 `flushSync`로 `dropdownPosition`·`open`을 닫는다. 다음 render에서는 portal이 제거되고, 스크롤 후 입력값을 다시 검색하면 정상 재열린다.

좌표 재배치를 선택하지 않은 이유는 React state commit이 scroll event와 같은 frame에 보장되지 않는 환경에서 다시 한 frame 분리를 만들 수 있기 때문이다. 닫힘은 사용자가 스크롤 중 목록을 선택하는 모호한 상태도 제거한다.

## 2. 진짜 스크롤 컨테이너 확정 근거

### Window / document

- `document.scrollingElement`를 런타임에서 읽어 `HTML`임을 확인했다.
- `main.app-main`의 `scrollTop`을 건드리지 않았다.
- body 끝에 160px sentinel을 두어 실제 document scroll range를 만들고 `window.scrollBy(0, 80)`을 실행했다.
- 계측값: `scrollTop 0 → 80`, `maxScrollTop=160`, `main.scrollHeight=main.clientHeight=1000`.
- 따라서 이 케이스의 실제 owner는 `window/document.scrollingElement(HTML)`이다.

### Overflow 조상

- `.app-main`은 computed `overflow:auto`인 overflow 조상이다.
- 테스트에서 `main`을 실제 viewport 높이(`height:100vh; min-height:0`)로 제한하고 sentinel을 자식으로 넣어 `scrollHeight=1086`, `clientHeight=480`을 만들었다.
- `main.scrollBy(0, 80)` 후 실제 `main.scrollTop=80`을 단언했다. synthetic `scroll` dispatch만으로 통과시키지 않는다.
