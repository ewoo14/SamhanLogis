## 결함 1 — NON_GOODS 출고 전표 수락이 재고 예약 409로 막힌다

### 실 사용자 경로

1. 견적에 `NON_GOODS` 품목을 넣는다.
2. 출고 전표로 전환한다.
3. 출고 전표를 수락한다.
4. 전표 수락 로직은 비시리얼 라인에 `inventoryClient.reserve(...)`를 무조건 호출한다.
5. 비상품은 입고 이력이 없어 balance가 없으므로 inventory가 HTTP 409 `가용 재고가 없습니다: 해당 제품의 입고 이력이 없습니다`를 반환한다.
6. 따라서 출고 완료까지 갈 수 없다.

### 실제 재현

정확한 HEAD의 inventory-service를 일회용 PostgreSQL에 기동하고 `goods=false`, `serialManaged=false`인 동일 품목으로 실제 HTTP를 호출했다.

| 호출 | HTTP | 호출 후 `stock_balances/lots/stock_instances/stock_movements` |
|---|---:|---:|
| `/inventory/lots/inbound` | 201 | `0/0/0/0` |
| `/inventory/deduct` | 200 (`deductedQuantity=0`) | `0/0/0/0` |
| `/inventory/instances/batch` | 201 (`[]`) | `0/0/0/0` |
| `/inventory/reserve` | **409** | `0/0/0/0` |

즉 “비상품이 재고 행을 만들지 않는다”는 세 게이트에서는 참이지만, 출고 전표의 선행 예약 경로가 no-op이 아니어서 정상 업무가 먼저 실패한다. 행 생성 0은 성공 증거가 아니라 **출고 도달 실패의 결과**다.

## ⑥ goods-type PATCH 권한

실 product API에서 존재하지 않는 모델코드로 호출해, 허용 역할은 서비스 내부 404까지 도달하고 거부 역할은 DB 접근 전 403이 되는 양방향을 측정했다. 따라서 공유 DB 쓰기는 발생하지 않았다.

| 결과 | 역할 |
|---|---|
| 허용(404 도달) | `MASTER`, `MANAGER`, `SALES`, `INVENTORY`, `DEVELOPER` |
| 거부(403) | `ACCOUNTANT`, `DISPATCH`, `DRIVER`, `STAFF`, `WAREHOUSE`, `PARTNER` |

원문 annotation은 `ProductCatalogController.java:292-293`의 `products.admin / UPDATE`이며 desktop mock의 허용 집합과 실측이 일치한다. 초과·누락 결함은 발견하지 못했다.
