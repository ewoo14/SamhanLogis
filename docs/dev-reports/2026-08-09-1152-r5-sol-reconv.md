### 결함 1 — 실 견적 작성 경로에서 비상품 수량이 1로 바뀌지 않고 잘못된 저장 payload가 발화한다

실 사용자 경로:

```text
견적서 작성 → 실 API 비상품 "운임" 선택 → 수량 7 → 납품가 12345 입력
→ 수량 7 유지 → 임시저장 버튼 활성 → POST payload quantity=7
```

재현 절차와 원문:

1. renderer를 `:5175`, mock OFF, `headless: true`로 기동했다.
2. `${BASE_URL}/#/sales/estimates/new`로 이동하고 이 화면 고유 요소인
   `data-testid="estimate-form-save-button"`의 가시성을 단언했다.
3. 실 gateway `:8080`의 `/api/products`를 먼저 계수했다.
4. 실 거래처를 선택하고 비상품과 상품을 서로 다른 두 라인에 선택했다.
5. 저장 POST는 Playwright route 경계에서 body만 읽고 `blockedbyclient`로 차단했다.

```text
CATALOG_ROWS=3083
TRIGGER_EXPOSED_NON_GOODS=2
TRIGGER_GOODS=772
CATALOG_GOODS_TYPE_VALUES=undefined
WIRE_NON_GOODS_GOODS_TYPE=0
WIRE_GOODS_GOODS_TYPE=0

LIVE_GOODS_QTY=3
SAVE_PAYLOAD_LINES=2
SAVE_PAYLOAD_NON_GOODS_QTY=7
SAVE_PAYLOAD_GOODS_QTY=3
```

Playwright RED 원문:

```text
Error: 비상품 납품가 입력 후 수량
Expected: "1"
Received: "7"

Error: payload에 비상품 라인 없음

```

상품 대조 라인은 실 카탈로그에서 `goods=true`임을 다시 결박했고 수량 3과 payload 3을
유지했다. 따라서 양방향 중 GOODS는 유지되지만 NON_GOODS 방향은 실 사용자 경로에서 실패한다.

직접 원인은 실제 검색 응답 3,083행 전부에 `goodsType` key가 없는 것이다. FE는
`productApi.toProductOption()`에서 `p.goodsType ?? undefined`를 그대로 사용하고,
`EstimateFormPage`는 그 값을 라인 상태에 저장한다. 결과적으로
`quantityAfterDeliveryPriceInput(null, "7", "12345")`가 7을 반환한다.

주의: 실행 중인 `samhan-product-service`의 Docker compose label은 이 워크트리가 아닌
다른 작업 디렉터리에서 만든 image를 가리켰다. 그 디렉터리 파일은 열거나 변경하지 않았다.
따라서 위 결과는 **현재 실제 QA 배포 경로의 사용자 결함**을 확정하지만,
HEAD 소스의 `@JsonProperty("goodsType")`가 깨졌다는 증거로 과장하지 않는다. 요구된 라이브
머지 게이트가 대상 HEAD artifact로 재수렴하지 않았고 실제 사용자 경로가 RED이므로 머지 불가다.

## ③ 공식 하네스 1건의 실제 범위

공식 명령 원문:

```text
npx playwright test --config=playwright.real-qa.config.ts \
  --list --reporter=line playwright/1152-r3-non-goods-real-qa

[renderer] › 1152-r3-non-goods-real-qa\1152-r3-non-goods-live-real-qa.spec.ts:38:1
Total: 1 test in 1 file
```

디렉터리와 파일명은 모두 `-real-qa`이고 공식 하네스가 정확히 1건 선택한다. 그러나 그 한 건은
요구 시나리오를 실제로 끝까지 덮지 않는다.

- 품목 확정 화면에서 변경하는 `modelCode`는 첫 편집 가능 임의 행이다.
- 견적에서 사용하는 `nonGoodsModelCode`는 변경 전에 이미 노출된 다른 행이다. 확정→견적 연결이 없다.
- 같은 라인 1을 비상품에서 상품으로 교체한 뒤 저장한다. 성공하더라도 저장 payload에 비상품이 없다.
- 거래처를 선택하지 않는다. `buildBody()`는 `거래처를 선택하세요.`에서 null을 반환하므로 POST가 발화하지 않는다.
- 저장 상세 도달이 선행 조건이라 뒤의 인쇄도 도달하지 않는다.
- 원문은 품목 PATCH와 견적 POST를 실제 서버로 보내므로 중간 실패 시 원복도 실행되지 않는다.

비쓰기 차단을 임시 삽입해 원문 스펙 자체를 실행했을 때는 첫 품목 PATCH가 차단되자 다음에서
즉시 RED였다. 임시 변경은 실행 후 원복했다.

```text
Expected select value: NON_GOODS
Received: GOODS
1 failed
```

즉 `Total: 1`은 선택 수만 맞고 품목 확정·비상품 포함 저장·인쇄의 도달 증거는 아니다.
