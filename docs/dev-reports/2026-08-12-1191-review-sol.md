# PR #1191 적대검증 — 격리 DB UTF-8 복제 하네스

검증일: 2026-08-12  
검증자: CODEX SOL  
대상: `scripts/qa/clone-db-utf8.sh`, `docs/qa/clone-db-utf8-README.md`  
판정 질문: **실제로 이 하네스를 쓰는 경로에서 한글이 깨진 복제본이 통과할 수 있는가?**

## 결론

**그렇다. 도달 가능한 결함 2건을 재현했다.**

1. 원본과 복제본에서 “한글을 하나라도 포함한 행 수”와 “`?`를 하나라도 포함한 행 수”만 같으면, 같은 행 안의 한글 일부가 `?`로 바뀌어도 `EXIT=0`으로 통과한다.
2. 검사 형식(`text`/`varchar`/`char`)에 한글 행이 하나도 없으면 fail-open 한다. 실제로 JSONB 안의 `한글이름`을 `????`로 훼손한 복제본이 warning 뒤 `EXIT=0`으로 통과했다.

전부 `?`로 훼손한 경우, 한 테이블만 전부 `?`로 훼손한 일반적인 부분 손상, 소스 dump 실패는 모두 `EXIT=1`로 차단됐다. PowerShell에서 **명시적으로 Git Bash를 호출한 경로**에서도 보호와 위 두 fail-open 결과가 동일했다.

공유 `samhan-postgres`에는 `pg_dump`와 `SELECT`만 실행했다. 장애 주입용 쓰기는 격리 대상 컨테이너와 별도 소스 fixture 컨테이너에만 실행했다.

## 도달 가능한 결함

### SOL-1 — 기존 `?`가 있는 행의 부분 한글 손상은 행 단위 카운트에 가려져 PASS

하네스는 각 컬럼에서 아래 두 수치만 비교한다.

- 한글을 하나 이상 포함하는 **행 수**
- 물음표를 하나 이상 포함하는 **행 수**

따라서 원본 `정상?한글`을 복제한 뒤 격리본만 `정상???`으로 훼손하면 두 값이 모두 `1|1`로 유지된다. 실제 문자열은 손상됐지만 비교 조건 `target_korean < source_korean || target_question > source_question`은 거짓이어서 PASS한다.

재현 단계:

1. 별도 PostgreSQL 소스 DB `sol_partial_masked`에 `z_target(name text)` 한 행 `정상?한글`을 넣었다.
2. PowerShell에서 `C:\Program Files\Git\bin\bash.exe scripts/qa/clone-db-utf8.sh sol_partial_masked`를 시작했다.
3. dump/restore가 끝나 `z_target`이 격리본에 나타난 즉시 **격리본만** `UPDATE z_target SET name='정상???'`으로 바꿨다.
4. 소스/대상 값과 하네스가 비교하는 두 카운트를 각각 조회하고 하네스 종료코드를 기다렸다.

실행 원문:

```text
UPDATE 1
SOURCE_VALUE:
정상?한글
TARGET_VALUE:
정상???
SOURCE_COUNTS:
1|1
TARGET_COUNTS:
1|1
[clone] isolated container: qa-clone-utf8-20260812213202-480
[clone] dumping sol_partial_masked from host.docker.internal:55591
[clone] verifying UTF-8 content in sol_partial_masked
[clone] PASS sol_partial_masked
[clone] PASS all databases; isolated container and dump files will be removed
EXIT=0
LEFTOVERS:
```

### SOL-2 — 검사 형식에 한글 행 0개면 JSONB 한글이 깨져도 warning 후 PASS

`information_schema.columns` 조회가 `text`, `character varying`, `character`만 고른다. 그 컬럼들에 한글 행이 없으면 `found=0`인 채 warning만 출력하고 PASS한다. 실제 프로젝트 데이터가 JSON/JSONB에도 한글을 담을 수 있는 경로에서 깨진 복제본이 통과 가능하다.

재현 단계:

1. 별도 소스 DB `sol_no_checked_korean`에 `meta(note text, payload jsonb)`를 만들었다. `note='ASCII only'`, `payload={"name":"한글이름"}`이었다.
2. 검사 대상 text 컬럼은 모두 ASCII만 갖도록 했다.
3. PowerShell에서 명시적 Git Bash로 하네스를 시작하고, restore 직후 격리본만 `payload={"name":"????"}`로 바꿨다.
4. 소스/대상 JSON과 종료코드를 확인했다.

실행 원문:

```text
UPDATE 1
SOURCE_JSON:
{"name": "한글이름"}
TARGET_JSON:
{"name": "????"}
[clone] isolated container: qa-clone-utf8-20260812213245-1003
[clone] dumping sol_no_checked_korean from host.docker.internal:55591
[clone] verifying UTF-8 content in sol_no_checked_korean
[clone] PASS sol_no_checked_korean
[clone] PASS all databases; isolated container and dump files will be removed
EXIT=0
LEFTOVERS:
[clone] warning: source 한글 컬럼 없음: sol_no_checked_korean
```

PowerShell background-job 오류 스트림 직렬화에서는 마지막 warning의 한글이 mojibake로 표시됐지만, UTF-8로 직접 실행한 메시지는 위 스크립트 원문과 같은 `source 한글 컬럼 없음`이다. 종료코드와 PASS 여부에는 영향이 없었다.

## 요구된 다섯 가지 시도 — 실행 원문

모든 fixture는 별도 컨테이너 `qa-sol1191-source-0812`에 만들었고, 하네스가 실제 사용하는 dump → 파일 → `docker cp` → `pg_restore` 경로를 그대로 실행했다. 장애 주입은 restore 완료 후 동적 이름의 격리 대상 컨테이너에만 수행했다.

### 1. 한글이 전부 깨진 복제본

격리본의 검사 대상 한글을 모두 `?`로 바꿨다.

```text
UPDATE 1
UPDATE 2
FAULT_TARGET=qa-clone-utf8-20260812213103-1010
1|?? ?? ??
2|??????
[clone] isolated container: qa-clone-utf8-20260812213103-1010
[clone] dumping sol_fullbroken from host.docker.internal:55591
[clone] verifying UTF-8 content in sol_fullbroken
UTF-8 검증 실패: db=sol_fullbroken table=public.a_delay column=c01 source_korean_rows=1 target_korean_rows=0 source_question_mark_rows=0 target_question_mark_rows=1
  target sample: ????1
EXIT=1
LEFTOVERS:
```

판정: **차단됨.** exit 1이며 정리 후 격리 컨테이너가 남지 않았다.

### 2. 검사 대상 한글 행 0개

SOL-2 원문과 같다. 검사 대상 text 컬럼에는 ASCII만 있었고, JSONB의 한글은 실제로 `????`로 손상됐다.

```text
SOURCE_JSON:
{"name": "한글이름"}
TARGET_JSON:
{"name": "????"}
[clone] PASS sol_no_checked_korean
[clone] PASS all databases; isolated container and dump files will be removed
EXIT=0
[clone] warning: source 한글 컬럼 없음: sol_no_checked_korean
```

판정: **통과 결함.** warning은 차단하지 않는다.

### 3. 일부 테이블만 깨짐

`m_keep`은 그대로 두고 `z_broken`만 `????`로 바꿨다.

```text
UPDATE 1
FAULT_TARGET=qa-clone-utf8-20260812213126-2017
keep|멀쩡한 테이블
broken|????
[clone] isolated container: qa-clone-utf8-20260812213126-2017
[clone] dumping sol_partial_detect from host.docker.internal:55591
[clone] verifying UTF-8 content in sol_partial_detect
UTF-8 검증 실패: db=sol_partial_detect table=public.z_broken column=name source_korean_rows=1 target_korean_rows=0 source_question_mark_rows=0 target_question_mark_rows=1
  target sample: ????
EXIT=1
LEFTOVERS:
```

판정: **일반적인 부분 손상은 차단됨.** 다만 같은 행에 원래 `?`와 남은 한글이 함께 있는 부분 손상은 SOL-1처럼 통과한다.

### 4. 복제 자체 실패

존재하지 않는 소스 DB를 지정해 `pg_dump`를 실패시켰다.

```text
[clone] isolated container: qa-clone-utf8-20260812213307-1495
[clone] dumping sol_missing_db from host.docker.internal:55591
pg_dump: error: connection to server at "host.docker.internal" (192.168.65.254), port 55591 failed: FATAL:
database "sol_missing_db" does not exist
EXIT=1
LEFTOVERS:
```

판정: **차단됨.** 검증/PASS 문구로 진행하지 않았고 격리 컨테이너도 정리됐다. dump 성공 후 `pg_restore` 자체만 강제로 실패시키는 별도 장애 주입은 하지 못했다.

### 5. PowerShell 호출

PowerShell에서 README의 실제 의도대로 Git Bash 실행 파일을 명시해 정상 fixture를 실행했다.

```text
[clone] isolated container: qa-clone-utf8-20260812213020-1283
[clone] dumping sol_baseline from host.docker.internal:55591
[clone] verifying UTF-8 content in sol_baseline
[clone] PASS sol_baseline
[clone] PASS all databases; isolated container and dump files will be removed
EXIT=0
```

같은 PowerShell → 명시적 Git Bash 경로에서 전부 손상과 일반 부분 손상은 exit 1, SOL-1과 SOL-2는 exit 0이었다. 즉 PowerShell 호출이 보호를 없애지는 않지만, 하네스 자체의 두 fail-open도 그대로 유지된다.

추가로 PowerShell에서 README 코드 블록처럼 **bare `bash`**를 실행하면 이 PC에서는 Git Bash가 아니라 다음 경로가 선택됐다.

```text
powershell_bash_resolution=C:\WINDOWS\system32\bash.exe
POWERSHELL_BARE_BASH=TIMEOUT_TERMINATED
STDOUT:
STDERR:
LEFTOVERS:
```

10초 동안 출력/종료가 없어 해당 검증 프로세스만 종료했다. 이 경로는 깨진 복제본을 PASS시키지 않았으므로 도달 결함으로 세지 않았다. `C:\Program Files\Git\bin\bash.exe`를 명시한 실제 하네스 실행은 완료했다.

## 증거 무결성 대조

PR #1191 본문과 기존 보고서 `docs/dev-reports/2026-08-12-qa-clone-utf8-harness.md`의 다음 실측을 공유 DB 읽기 전용으로 다시 대조했다.

### 실제 `partner_db` 정상 복제 PASS

```text
[clone] isolated container: qa-clone-utf8-20260812213436-217
[clone] dumping partner_db from 127.0.0.1:5432
[clone] verifying UTF-8 content in partner_db
[clone] PASS partner_db
[clone] PASS all databases; isolated container and dump files will be removed
EXIT=0
LEFTOVERS:
```

재현됨.

### 실제 `partner_db` 한 행 훼손 수치와 exit 1

공유 원본 조회:

```text
8314|0
EXIT=0
```

격리본 한 행만 `????`로 바꾼 직후:

```text
UPDATE 1
8313|1
UTF-8 검증 실패: db=partner_db table=public.partners column=name source_korean_rows=8314 target_korean_rows=8313 source_question_mark_rows=0 target_question_mark_rows=1
EXIT=1
LEFTOVERS:
```

PR/기존 보고서의 `8314 → 8313`, `0 → 1`, exit 1이 모두 재현됨.

### PR/README에 적힌 원본 거래처명

공유 원본 읽기 전용 조회:

```text
(주)서울택배
(주)한국냉동물류
대한화물서비스(주)
EXIT=0
```

재현됨. `실서버 QA — 6월 택배비 지출결의` 문구가 현재 어느 DB/테이블에 남아 있는지는 별도로 찾지 못했다. 따라서 그 한 문구의 현재 DB 재현 여부는 확인하지 못했다. 이미 삭제됐거나 다른 QA 데이터일 가능성을 추정으로 판정하지 않았다.

증거 무결성 결론: **직접 대조한 수치와 출력에는 불일치가 없다.** 확인하지 못한 지출결의 문구 1건은 확인 불가로 남긴다.

## 못 한 것

- dump가 성공한 뒤 `pg_restore` 프로세스만 강제로 실패시키는 장애 주입은 하지 못했다. 소스 dump 실패 경로는 exit 1과 cleanup을 확인했다.
- README의 `실서버 QA — 6월 택배비 지출결의` 문구가 현재 저장된 물리 테이블은 찾지 못해 현재 DB 값과 직접 대조하지 못했다.
