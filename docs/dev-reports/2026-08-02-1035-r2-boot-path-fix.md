## 1. 원인

두 결함은 같은 가드를 약화해야 생기는 문제가 아니라, 입력 공급과 형식 판정이 각각 잘못 연결된 문제였다.

1. `application.yml`의 base 프로파일은 `WAREHOUSE_UUID_*` 4개를 fallback 없이 요구한다. 그런데 README의 기본 `slip-service bootRun` 명령은 `local` 프로파일을 켜지 않았고, `infrastructure/env-templates/.env.dev-seed`도 4개 변수를 공급하지 않았다. 따라서 저장소가 안내한 정상 개발 경로 2건이 `WarehouseCodeMapper`에서 차단됐다.
2. `WarehouseCodeMapper`는 `UUID.fromString`의 성공만 확인했다. Java 파서는 `1-1-1-1-1`을 `00000001-0001-0001-0001-000000000001`로 받아들이므로 canonical textual UUID가 아닌 축약형이 기동까지 통과했다.

새 테스트의 Linux 이식성 점검:

- `WarehouseBootPathConfigurationTest`는 `Path`/`Files` API만 사용하고 Windows 구분자, 대소문자, 개행을 단정하지 않는다.
- 저장소 루트는 `user.dir`에서 `settings.gradle`을 부모 방향으로 찾으므로 Linux Gradle 실행 위치에서도 동일하게 동작한다.
- 가드 테스트는 문자열 값과 mapper 실제 동작만 단정하며 운영체제 경로에 의존하지 않는다.

## 3. fix와 긴장을 푼 방식

가드를 삭제하거나 빈 값을 허용하지 않았다. 정상 경로가 가드의 요구 계약을 충족하도록 연결을 고쳤다.

- README의 기본 `slip-service` 명령에 `--args='--spring.profiles.active=local'`을 추가했다. 이 경로는 local H2와 local 전용 4개 대체 UUID를 사용하므로 외부 DB 없이 개발 기동이 가능하다.
- `.env.dev-seed`에 `WAREHOUSE_UUID_HQ`, `WAREHOUSE_UUID_HUBAL`, `WAREHOUSE_UUID_ANSEONG`, `WAREHOUSE_UUID_CHANGWON`의 정규 36자 값을 추가했다. 따라서 `start-local-full.ps1`이 이 파일을 export한 뒤 사용하는 `dev` 프로파일도 가드 입력을 빠짐없이 가진다.
- `WarehouseCodeMapper`에 `8-4-4-4-12` hexadecimal canonical 문자열 검사를 먼저 적용하고, 그 다음 `UUID.fromString`을 호출한다. 대소문자는 허용하지만 trim, padding, 중괄호, 하이픈 생략은 허용하지 않는다.
- `resolve`에도 동일 검사를 적용해 기동 검증과 런타임 변환의 판정 차이를 없앴다.

따라서 결과는 “값이 없을 때 통과”가 아니라 `정상 경로는 값을 공급 → 엄격한 가드는 계속 오주입 차단`이다.

## 6. 비정규 값 통과/차단 표

새 검사는 정규 textual UUID 패턴을 먼저 적용한다.

| 입력 | 결과 | 근거 |
|---|---|---|
| `11111111-1111-1111-1111-000000000001` | 통과 | canonical 36자 `8-4-4-4-12` |
| `AAAAAAAA-AAAA-AAAA-AAAA-AAAAAAAAAAAA` | 통과 | hex 대소문자 비구분(`(?i)`) |
| `1-1-1-1-1` | **차단** | 축약 그룹, 실제 standalone exit 1 |
| 앞뒤 공백 포함 UUID | **차단** | 패턴이 전체 문자열에 일치해야 함 |
| 개행 포함 UUID | **차단** | 패턴 전체 불일치 |
| `{11111111-1111-1111-1111-000000000001}` | **차단** | 중괄호는 canonical textual 형식 밖 |
| 하이픈 없는 32 hex | **차단** | 그룹/하이픈 형식 불일치 |
| `not-a-uuid`, 빈 문자열, 공백만 | **차단** | 패턴 불일치 또는 blank 검사 |
| 형식은 정규지만 DB에 실재하지 않는 UUID | 통과 | 이번 가드는 형식 전용이며 실재성 조회를 하지 않음 |

즉 이번 라운드의 오주입 차단 불변식은 충족하지만, UUID의 DB 실재성/창고 정체성 검증은 범위 밖 기존 계약으로 남아 있다.
