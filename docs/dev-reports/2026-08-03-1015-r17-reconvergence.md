```powershell
docker exec samhan-postgres psql -U samhan -d partner_auth_db -c "WITH activity(biz_no,old_order,new_order,old_slip,new_slip) AS (VALUES ('1068689215',NULL::timestamp,NULL::timestamp,NULL::date,NULL::date),('2118712345',NULL::timestamp,TIMESTAMP '2026-01-03 10:00:00',NULL::date,NULL::date)), evaluated AS (SELECT pa.biz_no, GREATEST(pa.created_at,pa.access_restored_at,a.old_order,a.old_slip::timestamp) AS old_base,GREATEST(pa.created_at,pa.access_restored_at,a.new_order,a.new_slip::timestamp) AS new_base FROM partner_auth pa JOIN activity a USING(biz_no) WHERE pa.is_deleted=false), verdict AS (SELECT *,old_base+INTERVAL '30 days'<LOCALTIMESTAMP AS old_blocked,new_base+INTERVAL '30 days'<LOCALTIMESTAMP AS new_blocked FROM evaluated) SELECT COUNT(*) AS total_auth,COUNT(*) FILTER (WHERE old_blocked<>new_blocked) AS flipped_partners,COUNT(*) FILTER (WHERE NOT old_blocked AND new_blocked) AS newly_blocked,COUNT(*) FILTER (WHERE old_blocked AND NOT new_blocked) AS newly_unblocked FROM verdict;"
```

```text

------------+------------------+---------------+-----------------
          2 |                0 |             0 |               0
```

**현재 DB에서 실제 차단 판정이 뒤집힌 거래처: 0곳.**

## 하이픈 제거 매칭 부작용

### 실조회 테이블 저장 형태

| 표면 | 총 행 | 정상/숫자 | 공백·전각·기타 구분자 | 비고 |
|---|---:|---:|---:|---|
| active auth `biz_no` | 2 | 숫자 10자리 2 | 0 | collision 0 |
| active 주문 `biz_code` | 2,021 | 표준 하이픈 2,018 + 숫자 1 | 기타 문자 2 | `BIZ-0002` 2행, 모두 `confirmed_at=null` |
| confirmed 주문 | 30 | 전부 표준 하이픈 | 0 | 활동 가능한 행에는 비정상 형태 없음 |
| active OUTBOUND `business_number` | 2,303 | 표준 하이픈 280 | 공백·전각·기타 0 | NULL 2,023 |

- 앞뒤 공백: 0
- 내부 공백: 0
- 전각 공백/전각 숫자: 0
- 하이픈 외 구분자: 활동 가능한 주문·출고에서 0
- `GROUP BY replace(value,'-','') HAVING COUNT(DISTINCT value)>1` collision:
  - auth: 0
  - partner_orders: 0
  - slips: 0

따라서 **현재 실제 활동 테이블에서는 하이픈 제거가 서로 다른 raw 값을 하나로 합친 경우가 0건**이다. partner master에는 normalized 사업자번호가 같은 중복 코드가 4그룹 있지만, 이들은 활동 테이블 raw collision이 아니며 현재 auth와도 교집합이 없다. 출고에는 normalized `3342610558`이 두 partner_code에 걸친 128행이 있으나 이름과 master 사업자번호가 같은 한 거래처의 코드 표현 차이이며 서로 다른 사업자를 합친 증거는 아니다.

## 두 경로·경계·보류 무회귀

### 두 경로 키

- 관리자 미리보기: `bizNo` — 일치
- 실제 checkStatus/tryLogin: `bizNo` — 일치
- 주문앱 만료 API: `partnerCode` — **결함 2로 불일치**

### strict `<` 30일 경계

`services/partner-auth-service/src/main/java/com/samhanair/logis/partnerauth/service/PartnerAccessPolicy.java:22-42,58-65`에서 공통 `expiresAt.isBefore(now)`를 사용한다.

- 정확히 30일: 활성
- 30일을 초과한 순간: 만료
- 관리자 미리보기, checkStatus/tryLogin, 만료 판정의 비교 연산 자체는 일치
- 단 만료 API는 결함 2 때문에 비교에 넣는 활동 집합이 다를 수 있음

### downstream 실패 시 보류

- `PartnerActivityClient.java:31-52`: ORDER/SHIPMENT 성공 여부를 독립 플래그로 보존
- `PartnerApprovalService.java:96-110`: incomplete 거래처는 후보에서 제외하고 deferred 수/원천에 포함
- `PartnerAccessPreviewResponse.java:7-10`: deferred 정보 응답
- `SalesOrderApprovalsPage.tsx:294-313`: 관리자 화면에서 보류 수/원천 경고, 선택 후보로 사용하지 않음
- `PartnerAccessPolicy.java:38-39`: incomplete면 만료시각 null
- 실제 checkStatus/tryLogin: incomplete lookup으로 LONG_UNUSED를 만들지 않음

따라서 downstream 실패 보류는 **응답 DTO·관리자 화면·실제 인증 세 군데에서 존중된다.**

## 이번 라운드가 보지 않은 표면

1. 지시상 공유 DB write를 하지 않아 신규 주문 전환 HTTP를 직접 호출하지 않았다. 결함 1은 사용자 API 호출 사슬, 무조건 `null` 저장 코드, 기존 `PARTNER_ORDER` 20행을 결합해 확정했다.
2. 로컬 auth는 2행뿐이고 PARTNER_ORDER old-only 11 partner_code와 교집합이 없다. 따라서 현재 계정 단위 end-to-end 차단 flip은 0이며 운영 전체 분포로 일반화할 수 없다.
3. 운영/production DB는 조회하지 않았다. 수량은 로컬 공유 DB snapshot 기준이다.
4. `business_number`가 빈 OUTBOUND 2,023행 중 2,003행은 `partner_code`도 비어 있어 어느 거래처 활동인지 현재 컬럼만으로 판정하지 못했다.
5. 견적 publish도 `businessNumber=null` 생성 코드가 있고, 모바일 partner-order API도 사업자번호를 저장하지 않는다. 다만 견적 UI의 현재 실제 도달성과 mobile-staff의 `/api/v1/slips/mobile-order` 경로가 gateway에서 별도 rewrite되는지는 미판정이다.
6. partner-service 장애 중 수동 전표 생성 후 confirm하는 런타임 HTTP 재현은 하지 않았다. 코드상 NULL 저장 및 confirm 미보강은 확정했다.
7. 로컬 데이터에는 이미 저장 상태가 `LONG_UNUSED`인 auth가 없어, 저장된 LONG_UNUSED 복구 이전 상태와의 실데이터 비교는 하지 못했다.
8. 서비스 런타임 로그·브라우저 렌더·운영 시간대 변환은 이번 범위에서 직접 관찰하지 않았다.
