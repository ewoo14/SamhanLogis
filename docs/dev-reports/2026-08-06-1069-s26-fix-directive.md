# #1069 S26 SOL fix 지시서 — 매입전표 전체수정의 BUNDLE 부모 영속 우회

## 판정과 재현 난이도

**실 사용자 API 경로에서 재현 가능한 결함 1건. 현 HEAD `c6bc83e09c5c0a032335a5b648b520cfe405b290`은 머지 비권고다.**

- **입구가 또 하나 나왔다.** S2가 판매전표 범위 밖으로 명시 제외했던 매입전표 전체수정 `PUT /slips/{id}`가 현 S25 전수표에서는 BUNDLE 부모 거부로 기재됐지만 실제 코드에는 그 거부가 없다.
- 재현 난이도: **중간**. `purchases.slip.edit UPDATE` 권한과 DRAFT/SAVED 매입전표가 필요하고, 현 데스크톱 수정 화면은 품목 ID 선택기가 아니라 기존 `productId`를 유지한 채 이름·모델명 등을 편집하므로 브라우저 개발자 도구나 API 클라이언트로 정상 PUT 요청의 신규 라인 `productId`를 활성 BUNDLE ID로 바꿔야 한다. 내부 토큰이나 DB 조작은 필요 없다.
- 읽기 전용 실측 표본: 활성 BUNDLE **344개**(EXPAND 343, `bundle_mode=null` 1 — 도메인 기본값 EXPAND, KEEP 0), 수정 가능한 INBOUND DRAFT/SAVED 전표 다수. 사용자 식별 예시는 모델코드 `AC023CS1DBC1SY`다. UUID는 보고서에 싣지 않는다.
- 예상/실제: BUNDLE 부모는 구성품 전개 또는 명시 거부되어야 하나, 요청의 BUNDLE `productId`가 평면 `SlipLine`으로 생성되어 `slip_lines.product_id`에 저장된다.

### S25 전수표 대조와 증거 무결성

- S25 표의 `전표 전체·부분 수정 | SlipUpdateService, SalesSlipUpdateService | BUNDLE 부모 거부`는 절반만 맞다.
  - `SalesSlipUpdateService.update()`는 `rejectBundleProducts()`로 판매전표 부모를 거부한다.
  - `SlipUpdateService.update()`는 위 좌표처럼 매입전표 부모를 거부하지 않는다.
- 그 밖의 생산 코드 라인 생성 호출을 재대조했다.
  - 직접 생성/라인 추가는 `SlipService.addSlipLinesExpanded()`에서 전개한다.
  - 판매 전체수정, 모바일 전표, 주문 단건·병합·outbox 발행은 기존 거부 경계를 유지한다.
  - 일반/모바일 견적은 `EstimateService`/`MobileQuotationService`에서 전개하고, 견적→전표와 견적 revision 복원은 부모를 재검증한다.
  - 전표 복사, 전표 revision/협업/soft-delete 복원은 기존 스냅샷만 복사·복원한다. 현재 실 DB의 활성·삭제 포함 `slip_lines`/`estimate_lines` BUNDLE 부모 교차가 모두 0행이므로 이 경로들은 현 데이터에서 부모를 새로 만드는 별도 재현 경로가 아니다.
  - seed는 비사용자 개발 경로이며, 현 생산 코드에서 import/template/외부연동이 별도 `SlipLine`/`EstimateLine`을 생성하는 호출은 찾지 못했다.
- 모바일 견적 BUNDLE은 일반 서버 견적 저장과 동일하게 `ProductClient.expand(parentModelCode, setQty, 기본옵션, setUnitOverride)`를 호출하고, 응답 `quantity`를 정수 반올림·최소 1로 저장하며 응답 `unitPrice`를 공급단가로 `EstimateLine.create()`에 전달한다. 구성품 수량·단가 매핑은 일반 `EstimateService.addEstimateLines()`와 같다.
- S24 고정 기준을 같은 SQL 조건으로 재측정한 정상 SINGLE은 정확히 **2,107행 / 2,100전표 / 2,837,681,781원**이다. S25 보고서는 이 실측을 새로 주장하지 않았고, 이번 읽기 조회가 수치를 재확인했다.

## 2. 불변식

1. 활성 BUNDLE product는 OUTBOUND/INBOUND 구분 없이 어떤 사용자 쓰기 경로에서도 부모 자체가 `slip_lines.product_id` 또는 `estimate_lines.product_id`로 새로 저장되면 안 된다.
2. 매입전표 전체수정은 BUNDLE 부모를 구성품으로 전개하거나 저장 전에 한국어 업무 오류로 원자 거부해야 한다. 어느 정책을 택할지는 구현 수단으로 지정하지 않는다.
3. 정상 SINGLE 신규/기존 매입 라인, 기존 BUNDLE 구성품 계보, 권위 금액, lineId 계약, 낙관적 잠금, 가격기억은 기존 의미를 유지해야 한다.
4. 판매전표 생성·수정, 일반/모바일 견적, 견적→전표, 주문 단건·병합·outbox의 기존 전개/거부와 사용자 안내는 유지해야 한다.
5. 모바일 견적의 구성품 수량·단가·규격·순서 및 부모 계보는 일반 견적 저장 전개와 같아야 한다.
6. S17 경합 수렴, S19 a11y, S23 주문 전환 안내, 세트 옵션 입력/안내, `#1063` trailing 빈행 1개·무의미 빈행 저장 제외 규약은 유지해야 한다.

## 3. 양방향 RED

### RED-B — 결함 재현

- DRAFT/SAVED INBOUND 전표의 `PUT /slips/{id}`에 `lineIdContract=true`, 유효한 `updatedAt`, 신규 익명 라인(`lineId=null`), 활성 BUNDLE `productId`를 보내 BUNDLE 부모가 `slip_lines`에 저장되면 RED.
- BUNDLE 요청이 거부되는 정책인데 저장/감사 revision/가격기억 중 일부만 남으면 RED.
- 거부 사유가 사용자에게 읽을 수 있는 한국어 원인·조치를 제공하지 않으면 RED.
- 동일 부모를 권위 금액 3종 포함/미포함 두 조합 중 하나만 우회 저장할 수 있으면 RED.

### RED-A — 반대급부 보존

- 활성 SINGLE 신규 익명 라인과 기존 SINGLE lineId 왕복 수정이 차단되면 RED.
- 기존 전개 구성품의 lineId 계보·`setHead`·`parentSetModel`이 무수정 왕복 또는 정상 수정에서 소실되면 RED.
- 권위 금액 3종을 가진 일반 SINGLE 매입 라인, 기존 구성품 권위 금액 거부, 낙관적 잠금 409, lineId 계약 400의 기존 판정이 바뀌면 RED.
- 모바일 BUNDLE 견적의 구성품 수량 또는 단가가 같은 입력의 일반 견적 저장 전개와 달라지면 RED.
- 정상 SINGLE 견적/견적 전환/주문 전환/일반 저장이 BUNDLE 차단으로 오차단되면 RED.
- 경합 수렴, a11y 이름, 옵션 입력, 주문 전환 안내, `#1063` 빈행 규약 중 하나라도 깨지면 RED.

## 4. 범위 밖 / 안 본 범위

- 범위 밖: `#1057`, `#1066`, `#1075` 파일, product master·bundle_component 데이터 변경, 가격 배분 정책 재설계, Docker 재빌드·재배포·중지, DB 쓰기, 전체 게이트.
- 안 본 범위: DB 쓰기가 필요한 실제 PUT 영속 실행, 실제 모바일 기기, 배포 컨테이너가 현 HEAD와 동일한지 여부, 회계·재고 전체 기능, 타 트랙 화면.
- 읽기 전용 확인: product DB의 활성 BUNDLE 344개/KEEP 0개, slip DB의 활성·삭제 포함 BUNDLE 부모 교차 `slip_lines=0`, `estimate_lines=0`, 수정 가능한 INBOUND DRAFT/SAVED 표본 존재, 고정 cutoff SINGLE 2,107행.
- 코드로 본 범위: slip-service 생산 코드의 `SlipLine.create*`/`copyOf`, `EstimateLine.create*`, `restoreFromSnapshot`, slip/estimate repository 저장 호출, scheduler/import/batch/template/external 키워드, desktop 매입 수정 호출부. 타 서비스의 회계용 별도 slip 테이블은 이번 `slip_lines`/`estimate_lines` 축이 아니므로 제외했다.
