실행 순서:

1. 새 renderer에서 주문 상세를 열고 기존 버전 이력의 복원 버튼 6개를 확인했다.

3. 저장 1회: `PUT .../2026-06-08-1983 -> 200`.
4. 새로고침 없이 최신 EDIT가 이력 맨 위에 나타났고 복원 버튼 수가 `6 -> 7`로 증가했다.
5. 직전 revision 7을 선택해 복원했다: `POST .../revisions/7/restore -> 200`; 토스트 `버전 7 시점으로 주문을 복원했습니다.` 표시.

따라서 R7의 즉시 갱신은 실효가 있지만, 개발책임자 기준인 “저장 1회에 revisions GET 1회”는 충족하지 못했다. 경계 증거상 첫 호출은 direct `updateMutation.onSuccess`의 invalidation, 두 번째 호출은 같은 저장 뒤 도착한 collaboration realtime invalidation과 겹친다. 화면 깜빡임은 없었으나 상세 GET도 2회였다.

### 제시된 갈래 밖의 셋째 상태 — 복원 후 편집 초안 stale

복원 직후 동일 페이지에서 두 값이 갈렸다.

```text
읽기 화면 요청사항    R8 표식 없음 (복원값)
정식 편집 요청사항    R8 표식 있음 (복원 전 값)
```

편집 모달에서는 저장하지 않고 닫았다. 페이지를 다시 진입한 뒤에는 편집값도 복원값으로 수렴했다. 즉 DB/상세 query 복원 실패가 아니라 **같은 페이지의 coedit provider가 보유한 복원 전 header 초안을 잠시 다시 적용하는 프런트 stale**다.

코드 경계도 관측과 일치한다. `openEditDialog()`가 최신 `query.data`로 폼을 먼저 동기화하지만, 이어서 `applyProviderState()`가 CRDT header 값을 덮는다. provider 재시드는 `empty` 또는 `라인 수 불일치`일 때만 수행되어, 복원으로 header `memo`만 바뀐 경우는 server-wins 재시드 조건에 들지 않는다. 이 라운드에서는 수정하지 않았다.

## 2. SUPPLY 권위 — 견적 → 주문 전환

### 판정: 주문 전환 이후는 **판정 불가**

견적 GUI에서 SUPPLY 기준 라인은 만들 수 있었다. 그러나 그 견적을 **거래처 주문서**로 전환하는 GUI 경로가 없었다. 우회하지 않고 중단했다.

도달한 단계:

1. 견적 신규 작성에서 거래처 `주식회사 제이앤피공조`와 모델 `AR13TXEAAWKNEU-06`을 선택했다.
2. 공급가액 입력을 `1,000,000`으로 바꿨다.
3. 화면이 단가(VAT 포함) `1,100,000`, 부가세 `100,000`, 합계 `1,100,000`으로 계산했다.
4. GUI 임시저장 후 견적 `2026/08/07-3` 상세를 재조회했고 같은 금액을 확인했다.
5. 상세의 유일한 변환 control은 `전표 변환`이다. 이 control은 `convertEstimate()`를 호출해 **판매전표(OUTBOUND slip)** 를 만드는 경로이며 거래처 주문서 생성 경로가 아니다. 확인 dialog는 취소했고 판매전표를 생성하지 않았다.

막힌 원문:

```text
GUI: 견적 상세의 변환 control = "전표 변환"
코드 계약: "이 견적을 판매전표로 변환하시겠습니까?"
성공 계약: 신규 판매전표가 임시저장 상태로 생성
프런트 검색: /api/v1/partner-orders/from-estimate 호출자 0건
실행 BE: FixtureEstimateClient.findById(...) -> Optional.empty()
```

즉 `PartnerOrderFromEstimateService`의 네 권위 분기는 존재하지만, 현재 실행 BE의 `EstimateClient`는 “호출 가능한 estimate-service endpoint가 없다”는 fixture이고, 해당 endpoint를 밟는 실 GUI도 없다. 이것이 “견적 화면에서 SUPPLY를 만들 수 없어서”가 아니라 **SUPPLY 견적은 만들 수 있으나 partner-order 전환 wiring이 없는 셋째 가능성**이다.

DB/API 직접 쓰기를 하지 않았으므로 다음은 판정할 수 없다.

- `partner_order_lines.amount_authority=SUPPLY` 생성
- 주문 저장 → 재조회 → 수정·저장 후 SUPPLY 유지
- 주문서 쪽 SUPPLY 금액 재계산
