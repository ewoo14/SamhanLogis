## 2. ① R9 재시드 결과

### 결함 D1 — 다른 세션의 미저장 초안이 조용히 삭제된다

`seedPartnerOrderCoeditProvider`는 header 세 필드를 쓰고 line을 전량 `replaceItems`한다(`SalesPartnerOrderDetailPage.tsx:123-128`). R9는 복원 직후 provider가 열려 있으면 이를 즉시 호출하고, 닫혀 있으면 `forceServerReseedRef`로 다음 편집 진입 때 호출한다(`:509-523`, `:464-467`).

이 provider의 `doc.on('update')`는 `REMOTE_ORIGIN`이 아닌 update를 모두 POST queue에 넣는다(`createCoeditProvider.ts:578-583`). seed가 사용하는 `setHeaderValue`와 `replaceItems`는 별도 remote/system origin 없이 일반 local Yjs transaction을 만든다(`:691-697`, `:733-753`). 따라서 재시드는 A 화면에만 적용되는 초기화가 아니라 서버에 누적되고 `coedit:update` SSE로 B 화면에도 적용되는 공유 문서 변경이다.

실 사용자 경로는 다음과 같다.

1. B가 정식 편집에서 memo/line을 입력하고 아직 PUT 저장하지 않는다.
2. A가 같은 주문의 과거 revision을 복원한다.
3. A가 정식 편집을 연다. 복원 시 모달이 닫혀 provider가 없었더라도 이 단계에서 강제 재시드된다.
4. A의 server-wins 전량 update가 B provider에 전달되어 B의 미저장 초안을 조용히 덮는다.

복원이 서버 권위 사건이라는 사실은 서버 저장 내용의 권위를 뜻하지만, 다른 세션의 미저장 입력을 무통보 삭제해도 된다는 뜻은 아니다. 현재는 conflict/고지/보존 경계가 없다. **도달 결함이다.**

### 결함 D2 — 후속 상세 GET 실패 시 복원 전 cache로 재시드한다

`handleOrderRestored`는 `await refetch()` 후 `result.data` 존재만 확인한다(`SalesPartnerOrderDetailPage.tsx:509-523`). 상세 query에는 복원 전 data가 이미 있다(`:219-228`). React Query v5의 refetch 오류 결과는 기존 성공 data를 query state에 보존할 수 있으므로, 복원 POST 성공 뒤 GET만 실패하면 `result.data`가 복원 전 cache인 조합이 성립한다.

그 경우 코드는 stale data를 provider에 쓰고 `forceServerReseedRef.current = false`로 지운다. 성공 토스트는 이미 표시된다(`PartnerOrderVersionHistoryPanel.tsx:176-197`). 즉 네트워크 일시 실패라는 실 사용자 경로에서 R8 stale이 재발하고 오히려 공유 문서로 전파될 수 있다. **도달 결함이다.**

반대로 상세 GET이 실제 성공한 경우 header-only, 동일 line 수, line 수 변경 모두 R9의 명시적 seed를 타므로 “재시드가 너무 좁아 stale이 남는” 추가 조합은 찾지 못했다.

증거 무결성: R9 보고서의 “복원 완료 후 권위 있는 상세를 다시 조회”는 성공 응답 분기에서는 맞지만, 현재 코드는 재조회 성공 여부를 검증하지 않는다. 따라서 무조건적인 표현으로는 성립하지 않는다.

## 3. ② R7 네 경로 무효화 결과

### direct 저장 2 GET에 대한 PM 판정

R8이 관측한 direct 저장 1회당 `/revisions` 2회만으로 잘못된 목록이나 깜빡임이 발생한다는 근거는 찾지 못했다. PUT commit 뒤 local invalidation과 같은 commit의 `partner-order:edit` event가 겹치므로 두 응답은 같은 서버 revision 집합으로 수렴한다. **그 좁은 표본에 대한 “데이터 오류 0·깜빡임 0” 판정은 반박하지 않는다.**

### 결함 D3 — 협업 수정완료는 최대 3회, 비 revision 사건도 재조회

다만 R7의 realtime 분기는 `partner-order:edit`만 걸러내지 않는다. `comment.*`, 모든 `suggestion.*`, `message`도 revision query를 무효화한다(`PartnerOrderCollaborationPanel.tsx:102-108`, `:170-178`).

협업 수정완료 1회에는 세 생산자가 겹친다.

1. mutation success가 revision query를 invalidate (`:244-251`).
2. overlay audit가 `partner-order:edit` 발행 (`PartnerOrderAuditLogService.java:146-149`).
3. 같은 commit service가 `suggestion.accepted` 발행 (`PartnerOrderCollabEditService.java:76-84`).

따라서 event/HTTP 완료 순서에 따라 revision GET은 최대 3회다. 또한 댓글 생성·해결·삭제와 revision을 만들지 않는 `suggestion.proposed/rejected/withdrawn`도 revision GET을 만든다. 요청 증폭은 사용자 댓글/수정완료 경로로 재현 가능하며 R7이 새로 추가한 표면이다. **도달 결함이다.**

잘못된 revision 목록이 최종 표시되는 race의 정적 근거는 찾지 못했다. 결함 판정은 잘못된 event→query 매핑과 실제 요청 증폭에 한정한다.

### 누락 경로

- direct PUT, 협업 overlay commit, 원격 `partner-order:edit`, 삭제, revision 복원에는 revision 목록 갱신 경로가 있다.
- 보류/해제와 부분 판매전표 전환은 현재 revision을 생성하지 않으므로 누락으로 판정하지 않았다.
- R7이 열거한 실제 revision 생성 경로 중 “갱신 자체가 빠진” 추가 경로는 찾지 못했다.

## 4. ③ V17 `amount_authority` 결과

### 왕복

- 생성: `PartnerOrderLine.createFromAuthoritativeAmounts`가 네 authority별 S/V/T/price를 계산한 뒤 `amountAuthority`를 반드시 설정한다(`PartnerOrderLine.java:173-233`). PRICE 일반 생성도 같은 함수로 수렴한다(`:159-164`).
- 영속/backfill: V17은 컬럼 추가, 기존 행 PRICE backfill, NOT NULL을 적용한다(`V17__persist_partner_order_line_amount_authority.sql:1-12`).
- 조회: 상세 응답은 추측 없이 entity enum을 반환한다(`PartnerOrderDetailResponse.java:175-190`). `ProductClient`는 조회 시 productType만 enrich하므로 authority를 바꾸지 않는다(`PartnerOrderQueryService.java:124-169`).
- 수정: direct PUT은 기존 matched line의 authority를 기본값으로 사용하고 명시적 authority 변경을 거부한다(`PartnerOrderUpdateService.java:333-359`, `:471-482`).
- snapshot: capture가 entity authority를 `LineSnapshot`에 저장한다(`PartnerOrderSnapshot.java:109-149`, `:161-180`).
- 복원: authority가 있는 snapshot은 같은 authority로 factory를 호출하고, authority 없는 legacy snapshot만 PRICE로 복원한다(`PartnerOrderRevisionService.java:297-306`). RESTORE revision도 복원 결과를 다시 capture한다(`:275-289`).

신규 V17 snapshot의 `snapshot → restore → RESTORE snapshot → detail GET` 왕복에서 authority가 유실·오변경되는 경로는 찾지 못했다. 기존 snapshot의 authority null → PRICE fallback은 V17 이전 권위를 DB/JSON만으로 판별할 수 없고, R6이 기존 live 행 PRICE 파생값을 실측한 정책과 일치한다.

### SUPPLY 방침

견적 원천에는 authority가 없고 견적→거래처 주문서 전환은 실제 업무 흐름이 아니라는 개발책임자 확정에 반하는 코드/호출자 증거를 찾지 못했다. 따라서 **PRICE 근거로 닫고 SUPPLY는 판정 불가로 기록한다는 PM 방침을 반박하지 않는다.** SUPPLY가 이월된다고 PASS 처리하지도 않는다.
