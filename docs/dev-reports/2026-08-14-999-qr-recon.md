# #999 축 ③ — QR 스캔 입출고 정찰

> 일자: 2026-08-14  
> 역할: 정찰자(SOL)  
> 범위: 읽기 전용 코드·마이그레이션·화면·권한 정찰. 구현·DB 쓰기·배포·컨테이너 조작·git 작업 없음.  
> 정본: `gh issue view 999`의 이슈 본문과 개발책임자 댓글.

## 0. 결론

이슈 #999의 축 ③에 필요한 토대 중 **노출 시리얼키, QR 렌더링, 시리얼키 조회, 품질 축, 전표 기반 수량 입출고와 수불행**은 이미 있다. 그러나 **스캔된 특정 `SI-......` 개체를 입고 또는 출고시키는 mutation은 없다.** 현재 시리얼 입출고는 전표 수량을 기준으로 인스턴스를 일괄 생성하거나 FIFO 예약·출고한다. 스캔 결과를 받는 요청 계약, 특정 개체 검증, 스캔 세션/멱등성, 기기 화면이 모두 없다.

따라서 과거 기록인 *“mutation 경로 자체가 없음”*은 **“QR/시리얼키 기반 입출고 mutation”이라는 뜻으로는 지금도 맞다.** 다만 재고 mutation 전체가 없다는 뜻으로 읽으면 틀리다. 일반 lot mutation과 전표 연동 시리얼 배치 mutation은 이미 존재한다.

또한 대상 판정 정본은 이슈 본문에 적힌 `products.inventory_qty_mgmt`가 아니다. 현행 코드는 `categories.serial_managed`를 `ProductSummary.serialManaged`로 전달해 `stock_instances`와 `stock_lots`를 가른다. `inventory_qty_mgmt`는 단순 수량관리 여부이며, 판넬 카테고리는 현재 시드에 없다는 주석이 남아 있다.

## 2. 축 A~E 현행 상태

### 축 A — QR에 무엇이 담기는가

**확정 상태다.** 이슈 #999 정본은 QR payload를 UUID·품목코드·전표번호가 아닌 **노출 시리얼키 `SI-......` 문자열**로 지정한다. 현행 `SerialQr`도 `QRCode.toCanvas(..., value)`에 `row.serialKey`를 그대로 넣는다. 이 결정은 다시 열 필요가 없다.

주의할 점은 조회 응답이다. QR 자체에는 UUID가 없지만 `GET /inventory/instances/serial`의 `StockInstanceResponse`가 raw `id`와 `productId`를 반환한다. 스캔용 공개 계약은 `StockInstanceListResponse`처럼 UUID 없는 별도 DTO여야 한다.

### 축 B — 스캔 주체

현행 확정 주체는 없다.

- **데스크톱 연결 스캐너:** 가장 가까운 선례는 재고실사 `BarcodeInput`이다. autofocus 텍스트 input과 Enter/form submit 구조라 키보드 웨지 장치를 수용할 수 있지만, 시리얼 입출고 화면은 없다.
- **`clients/mobile-staff`:** 카메라 모듈은 사진용으로 있고 Samhan JWT를 쓰는 API 코드 선례도 있다. 그러나 실제 App 진입은 견적 WebView 하나뿐이라 창고 스캔 화면을 넣으려면 앱의 역할을 다시 넓혀야 한다.
- **`clients/arologis-mobile`:** 카메라 사진 코드는 있으나 아로로지스 기사 전용 인증·배차 앱이다. inventory-service와 `inventory.stock-balance` 권한 체계에 직접 연결돼 있지 않다. 창고 스캔 주체로 쓰면 arologis-service 브리지와 권한 경계 재설계가 필요하다.
- **`clients/mobile`:** 거래처 주문 WebView wrapper이며 대상이 아니다.

### 축 C — 스캔 후 무엇이 일어나는가

현행은 **조회까지만 가능**하다.

1. QR에서 `SI-......`을 얻는다.
2. `GET /inventory/instances/serial`로 개체를 찾을 수 있다.
3. `PATCH /inventory/instances/quality`로 출고 전 품질을 바꿀 수 있다.
4. 그러나 그 `serialKey`를 입고/출고시키는 API는 없다.

기존 입출고 API를 그대로 호출하는 것도 충분하지 않다. `/batch`, `/reserve-batch`, `/ship-batch`는 수량·품목코드·전표번호 기준이며 특정 스캔 개체 목록을 받지 않는다. 따라서 **새로운 serial-key 기반 명령 계약은 필요**하고, 내부에서는 기존 상태 전이와 movement 기록 규칙을 재사용해야 한다. 전표와 무관한 직접 입출고를 별도로 허용할지는 개발책임자 결정 사항이다.

### 축 D — 기존 재고 흐름과의 접점

#1203 이후 수불 정본은 `stock_movements`이며 물리 착지 다섯 계열은 다음과 같다.

| 업무 | movement | 전표번호 연결 |
|---|---|---|
| 입고전표/시리얼 입고 | `INBOUND +` | `reference_type=INBOUND`, slip UUID는 내부에서만 해석, 화면은 slipNo |
| 출고전표/시리얼 출고 | `DEDUCT -` | `reference_type=SLIP`, 화면은 slipNo |
| 재고이동 출발 | `TRANSFER_OUT -` | `reference_type=STOCK_TRANSFER`, note의 transferNo |
| 재고이동 도착 | `TRANSFER_IN +` | 동일 |
| 재고실사 | `ADJUST +/-` | `reference_type=AUDIT`, auditNo |

QR 스캔 mutation도 별도 “QR 전용 수불부”를 만들면 안 되고 이 정본에 합류해야 한다. 권장 접점은 다음과 같다.

- 전표 귀속 스캔: 기존 `INBOUND`/`SLIP` reference와 내부 slip id를 보존해 전표번호 열·클릭 이동이 그대로 동작하게 한다.
- 이동전표 스캔: `STOCK_TRANSFER` reference와 `TRANSFER_OUT/IN` 두 행을 같은 트랜잭션으로 기록한다.
- 스캔 자체의 감사 정보는 movement note에만 밀어 넣기보다 별도 scan session/event가 필요하다. 단 새 엔티티라면 BaseEntity 7 + soft delete를 적용한다.
- 상태 전이와 movement 저장은 #1199와 동일하게 한 트랜잭션이어야 한다.
- 현재 이동 확정은 lot 경로만 다뤄 시리얼 개체 `warehouse_id`를 옮기지 않는다. QR 이동까지 범위에 포함하면 이 분기가 선행 보완 대상이다.

### 축 E — 권한

현행 시리얼 조회·변경 권한은 모두 동적 page-code `inventory.stock-balance`에 매달려 있다.

| 동작 | action |
|---|---|
| 시리얼 조회·목록 | `VIEW` |
| 수동/배치 입고 인스턴스 생성 | `CREATE` |
| 예약·출고·회수·품질 변경 | `UPDATE` |

역할 템플릿상 `MASTER`, `MANAGER`, `WAREHOUSE`, `INVENTORY`가 이 page-code의 view/edit 권한을 갖는다(`auth-service` V35/V39). 다만 V39 이후 실제 enforcement는 계정별 `account_page_permissions`가 정본이므로 개인/그룹 override가 가능하고, 역할명만으로 최종 허용을 단정하면 안 된다.

추가 문제는 두 가지다.

1. 데스크톱 `/inventory/stock-balance` route guard가 다른 page-code(`accounting.sales-slip.list`)를 사용한다. 스캔 화면을 이 라우트에 붙이기 전에 정합을 확인해야 한다.
2. `arologis-mobile`의 DRIVER 인증은 arologis 전용 경계다. 현행 그대로는 `inventory.stock-balance` 계정 권한을 소비하는 창고 작업자가 아니다.

## 3. “mutation 경로가 없다” 재판정

### 판정

**QR 스캔 입출고에 한정하면 지금도 맞다.**

### 근거

- `serialKey` 입력 endpoint는 `GET /inventory/instances/serial`과 `PATCH /inventory/instances/quality`뿐이다.
- 입고 mutation `/inventory/instances/batch`는 `productId/productCode/warehouseId/quantity/inboundSlipNo`로 새 개체를 생성한다.
- 출고 mutation `/reserve-batch`, `/ship-batch`는 `productCode/warehouseId/quantity/outboundSlipNo`로 FIFO 집합을 처리한다.
- 저장소 전역에서 QR decode/scan 결과를 시리얼 상태 전이에 전달하는 controller, request DTO, service, 모바일/데스크톱 화면이 발견되지 않았다.
- 모바일 의존성에는 QR/바코드 인식기가 없고 카메라 코드는 사진 촬영용이다.

### 문구 정정

향후 핸드오프에는 다음처럼 써야 오해가 없다.

> 일반 재고와 전표 기반 시리얼 배치 mutation은 존재한다. **없는 것은 `serialKey`로 특정 개체를 스캔 검증하여 입고/출고하고 movement까지 원자적으로 남기는 mutation 경로다.**

## 4. 착수 순서 제안

### 1순위 — 스캔 업무 계약을 먼저 잠근다

기기 구현보다 먼저 다음 한 요청의 의미를 고정해야 나머지가 쉬워진다.

```text
작업 방향(INBOUND/OUTBOUND/TRANSFER_OUT/TRANSFER_IN)
업무번호(slipNo/transferNo — UUID 비노출)
창고코드
serialKey 목록
각 serialKey의 품질(또는 명시 확인값)
작업자
멱등키/scan session 번호
예상수량과 완료 조건
```

특히 “전표에 귀속된 스캔”과 “전표 없는 직접 입출고”를 같은 의미로 섞으면 수불부 링크·회계·보상 처리까지 갈라진다.

### 2순위 — 라벨 생명주기와 대상 판정을 고친다

1. 입고 전에 `SI-`를 선발급할지, 어떤 전표 상태에서 라벨을 출력할지 정한다.
2. 대상 판정은 `categories.serial_managed`를 정본으로 사용한다.
3. 판넬 카테고리/데이터를 식별하고 `serial_managed=true`가 실제로 적용되게 한다.
4. `inventory_qty_mgmt`를 개별/묶음 판정으로 사용하지 않는다.

### 3순위 — inventory-service에 시리얼 단건/세션 mutation을 만든다

- UUID 없는 스캔 조회 DTO.
- 상태·현재 창고·품목·전표 예약 대조.
- 명시 품질 검증.
- 상태 전이 + `stock_movements` 저장 원자성.
- 중복 스캔·재시도 멱등성.
- 이동 범위 포함 시 `stock_instances.warehouse_id` 이동.

기존 `StockInstance.ship/reserve/changeQuality`와 #1199 movement 규칙은 재사용하되, 기존 수량 배치 endpoint를 클라이언트가 연쇄 호출하는 방식은 피한다. 중간 실패로 상태·수불이 갈릴 수 있다.

### 4순위 — slip-service/이동전표와 결합한다

- 스캔 완료 집합을 전표 라인 예상수량과 대조한다.
- 기존 complete가 다시 `/ship-batch` 또는 `/batch`를 호출해 중복 처리하지 않도록 단일 소유자를 정한다.
- reject/cancel/되돌림의 시리얼 보상 경로를 정의한다.
- 전표번호 열이 유지되도록 기존 reference 규칙을 그대로 사용한다.

### 5순위 — 선택된 기기 UI를 붙인다

- 데스크톱이면 autofocus + Enter + 연속 스캔 큐를 재고실사 선례에서 가져온다.
- 모바일이면 실시간 카메라 decoder, 진동/음, torch, 권한 거부, 중복 표시, 네트워크 재시도까지 필요하다.
- 어떤 기기든 품질 미확인 상태로 완료할 수 없게 한다.

### 6순위 — 권한·QA

- 기존 `inventory.stock-balance` 재사용 또는 전용 `inventory.qr-scan`을 결정한다.
- FE route guard와 BE page-code를 일치시킨다.
- 실외기·실내기·판넬 성공, 부자재 거부, UUID 0, 중복/오프라인/부분수량/잘못된 창고/잘못된 전표/이미 SHIPPED를 검증한다.
- 수불부 다섯 계열·전표번호 클릭·캐시 무효화까지 종단 확인한다.

## 5. 개발책임자 결정이 필요한 미결 항목

### A. QR payload

**결정 불필요 — 이슈 정본으로 확정:** `(a) SI- 노출 시리얼키 원문`.

- 금지: UUID, 품목코드만, 전표번호만.
- 권장 구현도 URI/JSON wrapper가 아니라 현재와 동일한 `SI-......` 원문이다. 장치 종류와 무관하고 키보드 웨지에도 바로 들어간다.

### B. 어느 기기로 스캔할 것인가

선택지:

- **(a) 데스크톱 + USB/Bluetooth 키보드 웨지 스캐너부터** — 기존 Samhan JWT·동적 권한·gateway·재고 화면을 그대로 쓸 수 있어 가장 짧다. 본인은 1차로 권장한다.
- (b) 별도 창고 모바일 앱/모드 — 현장성은 가장 좋지만 인증·배포·카메라 decoder·오프라인 정책까지 새로 필요하다.
- (c) `mobile-staff`에 창고 모드 재도입 — 사진/JWT 선례는 있으나 현재 “견적 WebView 단일 앱” 결정과 충돌한다.
- (d) `arologis-mobile` 사용 — 배송기사 경계라 비권장. 창고 권한과 arologis 브리지를 새로 만들 이유가 있어 범위가 가장 커진다.

권장 단계는 `(a)로 업무 계약과 서버를 검증 → 필요 시 (b)`다.

### C. 스캔은 어느 업무문서에 귀속되는가

- **(a) 반드시 기존 입고/출고전표를 먼저 선택하고 스캔** — 수불부 전표번호, 회계, 취소/보상과 자연스럽게 결합. 본인 권장.
- (b) 전표 없는 즉시 입출고도 허용 — 별도 업무번호 채번·사유·승인·회계 정책 필요.
- (c) 둘 다 — 전표 귀속을 기본, 직접 입출고는 `inventory.adjust`급 별도 권한/감사로 제한.

### D. 출고 스캔과 FIFO의 관계

- **(a) 전표 accept 때 예약된 FIFO 시리얼만 스캔 허용** — 실물과 시스템 예약 불일치 즉시 차단. 본인 권장.
- (b) 스캔된 AVAILABLE 시리얼이면 FIFO 밖 개체도 출고 허용 — 현장 유연성은 높지만 기존 FIFO 불변식 변경.
- (c) 기본은 (a), MANAGER 승인으로 교체.

### E. 입고 전 QR 라벨은 언제 생기는가

- **(a) 입고전표 라인 기준으로 시리얼 선발급·라벨 출력 후 현장에서 스캔 확정** — “QR을 붙여 입고”와 순서가 맞다. 본인 권장.
- (b) 입고 완료 시 시리얼 생성 후 QR 출력 — 최초 입고는 스캔으로 처리할 수 없고 이후 출고부터만 QR 사용.
- (c) 외부 제조사 QR을 읽어 내부 `SI-`와 매핑 — 별도 외부키 컬럼/중복 정책 필요.

### F. 품질 입력 강제 방식

- **(a) 각 스캔 또는 동일 배치에 품질을 명시 선택하고 확인해야 완료** — 이슈 불변식 5에 가장 직접적. 본인 권장.
- (b) `NORMAL`을 미리 선택하되 사용자가 완료 버튼으로 명시 확인.
- (c) DB 기본 `NORMAL`로 자동 통과 — 현행이지만 “분류를 건너뛸 수 없음”과 충돌하므로 비권장.

### G. 재고이동도 이번 QR 범위인가

- **(a) 구매 입고 + 판매 출고 먼저, 같은 트랙 다음 단계에서 이동 출발/도착까지 포함** — 위험을 나누면서 #1203 접점을 닫는다. 본인 권장.
- (b) 구매/판매 입출고만 #999 범위, 이동은 별도 이슈.
- (c) 처음부터 입고·출고·이동 4동작을 한 번에.

### H. 권한 page-code

- (a) 기존 `inventory.stock-balance`의 VIEW/CREATE/UPDATE 재사용 — 빠르지만 재고 전체 수정권과 스캔권을 분리할 수 없다.
- **(b) `inventory.qr-scan` 전용 page-code 신설** — 최소권한·기기별 통제에 유리. 본인은 운영 기능으로는 (b)를 권장한다.

## 6. 착수 시 수정 가능성이 높은 위치

| 영역 | 후보 |
|---|---|
| inventory API/서비스 | `StockInstanceController`, `StockInstanceService`, 신규 UUID-free request/response DTO |
| 상태/위치 전이 | `StockInstance`에 스캔 입고·출고·이동 규칙 또는 전용 도메인 서비스 |
| 조회/락/멱등 | `StockInstanceRepository`, 필요 시 scan session/event 엔티티·Flyway |
| 수불 | `StockMovement`, `StockLedgerService`의 기존 유형/reference 규칙 재사용 |
| 전표 결합 | `slip-service`의 `SlipService`, `InventoryClient`, 보상 실패 처리 |
| 이동 결합 | `StockTransferService`, `StockService.transfer`의 serial-managed 분기 |
| 대상 판정 | `product-service` `Category.serialManaged`, 판넬 카테고리 마이그레이션/데이터 |
| 데스크톱 | `InventoryStockBalancePage`, 신규 scan 화면/모달, `api/inventory.ts`, route/page-code 정합 |
| 모바일 선택 시 | 신규 창고 앱/모드가 우선 후보. `arologis-mobile` 직접 재사용은 비권장 |
| 권한/gateway | auth-service page-code seed, account permission materialization, gateway inventory route는 기존 경로 재사용 가능 |

## 7. 최종 요약

- **이미 있는 것:** `SI-` 시리얼키, 품질 축, QR 렌더, 시리얼 조회/품질 변경, 전표 기반 배치 입출고, `stock_movements` 수불부와 전표번호 연결.
- **다른 것:** 현행 입출고는 수량/FIFO 배치이지 스캔된 특정 개체 처리가 아니다. 재고실사 바코드 입력과 모바일 카메라는 각각 품목수량 수동입력·사진촬영용이다.
- **없는 것:** serial-key 입출고 mutation, 스캔 기기 화면, scan session/멱등/부분완료, 전표 대조, 입고 전 라벨 발급, 시리얼 재고이동.
- **가장 먼저 할 일:** 축 B·C·D/E의 업무 결정을 잠근 뒤, UUID 없는 스캔 명령 계약과 입고 전 라벨 생명주기를 먼저 설계한다.
