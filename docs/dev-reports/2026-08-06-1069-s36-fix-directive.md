## 판정과 재현 난이도

**실 사용자 경로로 재현 가능한 결함 2건과 명시 수렴조건 위반 1건이다. 현 HEAD는 머지 비권고다.**

- F1 재현 난이도: **중간**. 품목 관리 화면에서 BUNDLE을 `KEEP`으로 생성/변경한 뒤 새 판매전표에서 선택해 전개 응답을 받은 후 저장한다. 현재 실 DB의 KEEP은 0개라 기존 표본만으로는 발화하지 않지만, 제품 등록 화면이 KEEP을 정상 선택지로 제공한다.
- F2 재현 난이도: **하**. 활성 EXPAND 343개 또는 `bundle_mode IS NULL` 1개 중 하나를 새 판매전표에서 옵션과 함께 전개해 저장한 뒤 상세를 재조회한다. `parentSetModel`/`setHead`는 남지만 선택한 옵션 문맥은 응답에 없다.
- F3 재현 난이도: **하(코드 경계 확인)**. 매출 또는 매입 전표 전체수정 PUT을 호출한다. 두 입구는 `BundleModePolicy`가 아니라 `BundleProductGuard` 안의 복제 조건을 지난다. 현재 두 식의 결과는 우연히 같아 즉시 오차단은 없지만, 이번 라운드의 명시 조건인 “모든 판정 지점의 공통 정책 지배”를 위반한다.

## 1. 결함 좌표와 재현 사슬

### F1 — KEEP 화면 반환에도 구성품 계보를 무조건 부여한다

1. product-service는 KEEP을 부모 1행으로 반환한다. `BundleExpander.java:86-88`에서 KEEP을 `ExpandedLine.single()`로 보내고, `:481-489`의 반환은 `componentKind=null`이다.
2. 화면은 `SlipFormPage.tsx:843-845`에서 `componentKind === null`인 반환을 BUNDLE 부모로 정확히 구분한다.
3. 그러나 같은 변환이 반환 mode와 무관하게 `parentSetModel=source.modelCode`, `setHead`, 부모 productId/단가를 모든 행에 채운다(`SlipFormPage.tsx:859-863, 874-878`). KEEP 분기가 없다.
4. 저장 payload는 `parentSetModel` 비공백이면 이 필드를 그대로 전송한다(`SlipFormPage.tsx:1470-1484`).
5. 서버는 대상 product가 KEEP이라 `BundleModePolicy.shouldExpand()`가 false인 평면 분기로 들어간 뒤, 요청 `parentSetModel`을 그대로 `assignBundleComponent()`한다(`SlipService.java:161, 172-196`).
6. 재조회 후 `BundleLineageResolver.isBundleComponent()`는 `parentSetModel` 비공백만으로 true가 된다(`BundleLineageResolver.java:134-143`).

따라서 S34 F1의 “KEEP 부모가 자기 자신의 구성품이 된다”는 화면 경유 경로에서 그대로 남았다. 서버 직접 생성·견적·모바일 견적의 KEEP 계보 부여는 S35에서 닫혔지만, 데스크톱 판매전표의 실제 사용자 경로는 닫히지 않았다.

### F2 — EXPAND 옵션 문맥은 payload까지만 가고 저장·재조회에서 사라진다

1. 화면은 전개 구성품마다 `setOptions`를 유지하고 저장 payload에 싣는다(`SlipFormPage.tsx:863, 878, 1470-1484`).
2. `CreateSlipRequest.SlipLineRequest`도 `setOptions`를 받는다(`CreateSlipRequest.java:96-108`).
3. 그러나 화면이 보낸 구성품 product는 SINGLE이므로 `SlipService.addSlipLinesExpanded()`의 평면 분기(`SlipService.java:161, 172-196`)로 들어간다. 이 분기는 `parentSetModel`/`setHead`와 부모 가격기억만 소비하고 `setOptions`는 읽거나 영속하지 않는다.
4. `SlipLine`에는 `setHead`와 `parentSetModel`만 있고 옵션 필드가 없으며(`SlipLine.java:140-144, 387-390`), 상세 DTO도 이 둘까지만 반환한다(`SlipLineResponse.java:21-55, 63-79`).

따라서 EXPAND의 구성품 결과·계보와 부모 `SOURCE_BUNDLE_SET` 가격기억은 남지만, 사용자가 선택한 `remoteOption`·`remoteExcluded`·`panelOption`·`panelShape360`·`materialIncluded` 원문 문맥은 저장 후 재조회할 수 없다. S34 수렴조건의 “화면 전개 → 저장 → 재조회까지 옵션 문맥 보존”은 충족되지 않았다.

### F3 — 전체수정 2입구가 공통 정책을 지나지 않는다

- 매출 전체수정: `SalesSlipUpdateService.java:75-85` → `BundleProductGuard.rejectParents()`.
- 매입 전체수정: `SlipUpdateService.java:69-81` → 같은 guard.
- 실제 판정은 `BundleProductGuard.java:29-35`에 `productType == BUNDLE && bundleMode != KEEP`로 다시 적혀 있고 `BundleModePolicy.shouldExpand()`를 호출하지 않는다.
- 공통 정책의 정본은 `BundleModePolicy.java:12-15`다.

현재 두 조건은 동치여서 SINGLE 기준선의 오차단은 0행이다. 다만 S27→S28 전례를 막기 위해 이번 라운드가 요구한 단일 정책 경계는 성립하지 않으며, 향후 mode 해석 변경 시 두 전체수정 입구만 다시 갈라진다.

## 3. 직접 POST 호환성·공용 LineRow·#874 충돌

### `POST /slips` 구 호출자

신규 네 필드는 `CreateSlipRequest.java:105-108`의 nullable 필드이며 `@NotNull`이 없다. JSON에서 생략하면 null로 역직렬화되고 `SlipService.java:184-195`는 기존 평면 SINGLE/KEEP 분기로 처리한다. Java 내부 호출자도 7/8/9/12-arg 호환 생성자가 새 필드를 null로 위임한다(`CreateSlipRequest.java:122-153`). 따라서 구 클라이언트·모바일·임포트가 필드를 생략해도 필수화로 깨지지 않는다.

### `LineRow.tsx`

S35 변경은 `LineDraft` optional 필드 4개 추가뿐이다(`LineRow.tsx:114-125`). production `<LineRow>` 직접 렌더는 `SlipFormPage.tsx:596` 한 곳이다. 견적은 `EstimateLineRow`, 분개는 `JournalLineRow`, 주문/회계 화면은 별도 컴포넌트를 사용한다. `LineRow` 지정 Vitest 36/36도 통과했다.

`feat/874-set-riusage-global-dc`도 같은 `LineDraft` 선언부에 할인 optional 필드를 추가한다. 현재 merge-base `35afbb1d7` 기준 3-way `git merge-tree`에서 `LineRow.tsx` 자체는 양쪽 optional 필드를 자동 병합하며 conflict marker가 없었다. 다만 같은 병합에서 `SlipFormPage.tsx`, `slip.ts`, `ProductSummary.java`, `SlipService.java` 등에는 실제 conflict marker가 발생하므로 #874 통합 시 이 트랙의 계보 필드를 누락하지 않는 수동 해소가 필요하다. 다른 트랙 파일은 읽기 조회만 했고 수정하지 않았다.

## 4. fix 수렴 조건과 안 본 범위

1. `replaceWithExpandedBundleLines()`는 `componentKind == null`인 KEEP 부모에 `parentSetModel`/`setHead`/`bundleParentProductId`를 부여하지 않아야 한다. 저장 후 `BundleLineageResolver.isBundleComponent()`가 false여야 한다.
2. EXPAND/NULL 구성품만 계보와 부모 가격기억 문맥을 전송해야 하며, 저장 후 상세 재조회에서도 `parentSetModel`/`setHead`와 선택 옵션 문맥을 복원할 수 있어야 한다.
3. `BundleProductGuard`의 복제 조건을 제거하고 `BundleModePolicy.shouldExpand()`를 호출해 매출·매입 전체수정도 같은 정책 경계를 지나야 한다.
4. KEEP/EXPAND/NULL 각각에 대해 화면 선택 → 저장 payload → 서버 저장 → 상세 재조회 단언을 둔다. KEEP은 계보 없음, EXPAND/NULL은 계보+옵션 보존, 구성품별 `SOURCE_LINE_SAVE` 없음, 부모 `SOURCE_BUNDLE_SET` 1건이어야 한다.
5. 기존 SINGLE 2,107행과 모바일 주문·발행 3경로·견적 전환·revision·가배차 문구 순서를 반대급부로 유지한다.

안 본 범위: 실 DB에 KEEP 품목을 새로 생성하는 write, 실제 HEAD 서버를 별도 기동해 공유 DB에 전표를 저장하는 라이브 QA, 실제 모바일 기기 GUI, vendor 발송, Docker 재빌드·재배포·중지, 전체 CI, 회계·재고 전체 기능. DB는 SELECT만 사용했다. #874는 충돌 판정을 위한 git object 읽기만 했고 #1066/#1075 구현은 보지 않았다.
