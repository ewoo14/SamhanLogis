# #896 시트 두 가격 벌 ↔ DB 차집합 실측 v2

- 실측일: 2026-08-08 (KST)
- DB 최종 조회 시각: `2026-08-08 20:48:40.505945+09`
- 입력: 내려받아 둔 CSV와 현재 `product_db`
- 준수사항: Google 접근 없음, DB 쓰기 없음, Docker 재기동·재배포 없음, 코드·Git 조작 없음, 이관 미수행

## 1. 결론

접미사 없는 탭과 `_단가인상` 탭은 **둘 다 이관 대상**이다. 코드상 접미사 없는 탭은 화면의 `인상 전 단가` 선택값이고, `_단가인상` 탭은 기본 카탈로그 값이다.

기존 DB는 제품 단위의 두 시점 가격을 담을 뼈대는 이미 갖고 있다. `price_history`에는 `2000-01-01` 1,082행과 `2026-04-01` 1,119행이 있고, `price_change_schedule`에는 네 카테고리의 전환일과 견적서 체크박스 기본값이 있다. 그러나 **현재 데이터와 현재 키 구조만으로 CSV 두 벌 전체를 손실 없이 표현하지는 못한다.**

근거는 다음과 같다.

1. 비인상 벌과 현재 DB의 단가 충돌은 1,458셀, 인상 벌과 현재 DB의 충돌은 1,432셀이다.
2. 빈칸·0을 모두 제외해도 각각 917셀, 891셀이 충돌한다. 두 벌 모두 `시트 양수 ↔ DB 0` 541셀을 갖는다.
3. `price_history`의 `2000-01-01` 값과 비인상 CSV를 직접 대조해도 1,456셀이 다르고, 비인상 CSV 모델 39개에는 해당 날짜 이력이 없다.
4. `price_history`는 `(product_id, effective_date)`당 한 행, 가격 필드도 `release_price`와 `delivery_price` 각 하나뿐이다. 반면 같은 날짜 벌 안에서도 같은 모델·같은 필드가 문맥에 따라 여러 값을 갖는 그룹이 비인상 141개, 인상 132개다.
5. 두 벌 사이에서 실제로 다른 가격 30셀의 방향은 `_단가인상` 쪽이 큰 8셀, 작은 22셀이다. “인상 후는 항상 크거나 같다”는 규칙은 성립하지 않는다.

따라서 기존 구조는 **제품 전역 단가 두 시점**은 표현할 수 있지만, **시트의 행 문맥·중복 납품가 열까지 포함한 두 벌 전체**는 표현하지 못한다. 새 구조를 먼저 제안하지는 않는다. 이관 전에 적어도 `(세트, 구성품, 특징, 원본 가격열)` 문맥을 보존할 수 있는 능력과, 각 원본 셀을 어느 DB 값으로 대응할지에 대한 명시 규칙이 더 필요하다.

| **합계** | - | - | **49,900** | **2,582** |

`싱글 세트`의 2,556셀은 실질 변경 수가 아니다. 비인상 65행부터 세 모델이 인상 탭에 없어서 뒤 행 좌표가 당겨진 효과가 대부분이다.

### 4.2 모델/문맥 정렬 후의 실질 차이

`싱글 세트`는 모델명으로 정렬하고, 행 수가 같은 나머지 탭은 원래 문맥·행 순서를 보존했다.

| 항목 | 건수 |
|---|---:|
| 양쪽 공통 데이터행 | 3,017 |
| 모든 셀이 같은 행 | 2,991 |
| 한 셀 이상 다른 행 | 26 |
| 비인상에만 있는 행 | 3 |
| 인상에만 있는 행 | 0 |
| 같은 가격 셀 | 7,975 |
| 값이 다른 가격 셀 | 30 |
| 비인상에만 있는 가격 셀 | 9 |
| 인상에만 있는 가격 셀 | 0 |

비인상에만 있는 세 모델은 `AC072BSCPBH2SY`, `AC090BSCPBH2SY`, `AC130BSCPHH2SY`다. 각 행에 출고가와 납품가 두 열, 총 3가격셀이 있어 9셀이다. 이 모델들은 구성품 탭에도 남아 있으므로 여섯 탭 전체 모델 세계에서는 사라지지 않는다.

### 4.3 가격 방향

| 방향 | 셀 수 | 판정 |
|---|---:|---|
| `_단가인상` > 비인상 | 8 | 인상 방향 |
| `_단가인상` < 비인상 | 22 | 역방향 |
| 합계 | 30 | 방향 불일치 |

인상 방향 예시:

- `AC060CXAPBH1` 출고가 1,254,000→1,331,000
- `AC072CXAPBH1` 출고가 1,276,000→1,540,000
- `AC110CXAPBH1` 출고가 1,342,000→2,156,000
- `AC130CXAPBH1` 출고가 1,644,500→2,354,000
- `AC145CXAPHH1` 출고가 1,771,000→2,387,000

역방향 예시:

- `AP145BAPPHH2S` 납품가 두 열 1,980,000→1,890,000
- `AR06D1150HZS` 납품가 두 열 370,000→360,000
- `AR-EH05` 출고가 10개 행 각각 33,000→25,300
- `AP145BNPPHH1` 납품가 792,000→756,000
- `AR06D1150HAX` 납품가 222,000→216,000

따라서 탭 이름의 “인상”은 코드가 구분하는 버전명이지, 모든 셀의 산술적 증가를 보장하지 않는다.

## 5. 기존 DB가 두 벌을 표현할 수 있는가

### 5.1 `products`

`products.release_price`와 `products.delivery_price`는 활성 제품당 단일 현재값이다. 활성 3,083행의 `model_name`은 모두 채워져 있고 중복이 없다. 이 단일 행만으로는 두 벌을 동시에 담을 수 없다.

### 5.2 `price_history`

스키마와 제약:

| 열 | 의미 |
|---|---|
| `product_id` | 제품 FK |
| `effective_date` | 적용 시작일 |
| `release_price` | 시점별 출고가 |
| `delivery_price` | 시점별 납품가 |
| `set_material_key` | 시점별 자재 키, nullable |

`uq_ph_product_date`가 `(product_id, effective_date)`를 유일하게 만든다. 즉 제품·날짜당 출고가 1개, 납품가 1개다.

실제 분포:

| 적용일 | 행/제품 | 출고가 양수 | 납품가 양수 |
|---|---:|---:|---:|
| `2000-01-01` | 1,082 | 1,078 | 771 |
| `2026-04-01` | 1,119 | 1,115 | 808 |

- 두 날짜를 모두 가진 제품: 1,082
- `2026-04-01`만 있고 과거행이 없는 제품: 37
- 두 날짜 값이 모두 같은 제품: 1,072
- 어느 한 가격이 바뀐 제품: 10
- `2026-04-01` 1,119행은 현재 `products` 가격과 1,119/1,119 모두 정확히 같다.
- `set_material_key`는 2,201행 전부 null이다.

두 날짜가 모두 있는 1,082제품의 방향은 출고가 증가 7제품, 출고가 감소 0제품, 납품가 증가 0제품, 납품가 감소 3제품이다.

### 5.3 CSV와 `price_history`의 실제 일치도

코드가 baseline으로 고정 조회하는 날짜는 `2000-01-01`이다. 인상 후는 `2026-04-01` 이력과 현재 `products`가 같다.

| 비교 | 모델 이력 보유 | 일치 가격셀 | 충돌 가격셀 | 시트 빈칸 | 해당 이력 없음 |
|---|---:|---:|---:|---:|---:|
| 비인상 CSV ↔ `2000-01-01` | 1,079/1,118 | 5,964 | 1,456 | 595 | 79셀/39모델 |
| 인상 CSV ↔ `2026-04-01` | 1,116/1,118 | 6,053 | 1,432 | 595 | 5셀/2모델 |

비인상 이력이 없는 39모델은 DB 자체에 없는 2모델과 과거 이력이 없는 37모델이다. 따라서 `price_history`가 두 날짜를 갖는다는 사실만으로 두 CSV가 이미 이관됐다고 볼 수 없다.

두 벌 사이에서 실제로 바뀐 15개 고유 `(모델, 가격필드, 전값, 후값)` 전환을 현재 이력과 비교하면 다음과 같다.

| 이력 표현 상태 | 고유 전환 |
|---|---:|
| 전·후 모두 정확 | 9 |
| 후만 정확 | 2 |
| 둘 다 정확하지 않음 | 4 |

후만 정확한 것은 `AR-EH05`·`AC145BXADHH1` 출고가다. 둘 다 정확하지 않은 것은 `AP145BNPPHH1`, `AC145BXAPHH5`, `AR06D1150HZN`, `AR06D1150HAX` 납품가다.

### 5.4 구조적으로 표현하지 못하는 문맥 가격

같은 벌 안에서 `(model_name, release/delivery)`로 묶었을 때 서로 다른 양수 값이 둘 이상인 그룹은 다음과 같다.

| 벌 | 모델-가격필드 그룹 전체 | 복수 값 그룹 | 해당 셀 발생 수 |
|---|---:|---:|---:|
| 비인상 | 2,226 | 141 | 1,385 |
| 인상 | 2,226 | 132 | 1,308 |

예를 들어 비인상 `AC060CXAPBH1`은 납품가 820,000·900,000·910,000을 서로 다른 싱글 구성 문맥에서 갖고, 출고가도 1,254,000·1,331,000 두 값이다. 제품·날짜당 한 가격만 허용하는 현재 `price_history`로는 이 원문을 모두 담을 수 없다.

시트 fallback의 `getPriceIncData_()`도 같은 모델을 순회하며 마지막 양수 값을 덮어쓰는 map이다(`code.js:1775-1791`). 이것은 현재 화면용 축약 동작이지, 원본 두 벌 전체를 보존한다는 증거가 아니다.

### 5.5 `price_change_schedule`

스키마는 카테고리별 `effective_date`와 `default_pre_change`를 담으며, 활성 카테고리당 한 행만 허용한다.

| 카테고리 | 전환일 | 견적 기본 `인상 전` |
|---|---|---|
| `commercialMulti` | 2026-07-01 | false |
| `homemulti` | 2026-07-01 | true |
| `oldProducts` | 2026-07-01 | false |
| `singleSets` | 2026-07-01 | false |

이 테이블은 **어느 버전을 선택할지**는 표현하지만 가격 자체는 담지 않는다. 구성품은 별도 카테고리가 아니라 `singleSets` 또는 `commercialMulti` 전환일을 상속한다. 또한 실제 이력의 인상행 날짜 `2026-04-01`과 화면 전환일 `2026-07-01`은 다르다. 어느 날짜가 업무상 진짜 인상일인지 이번 자료만으로 확정하지 않는다.

### 5.6 판정

| 질문 | 판정 |
|---|---|
| 제품 전역 출고가·납품가 두 시점을 저장할 수 있는가 | 가능. `price_history`의 날짜별 행 사용 |
| 견적서의 기본 토글 상태를 저장할 수 있는가 | 가능. `price_change_schedule.default_pre_change` |
| 주문서의 납기일 기준 버전 선택을 저장할 수 있는가 | 가능. `price_change_schedule.effective_date` |
| 현재 DB에 두 CSV 값이 이미 모두 들어 있는가 | 아니오. 대량 충돌·과거행 누락 존재 |
| 두 CSV의 모든 행·중복 가격열·세트 문맥을 손실 없이 저장할 수 있는가 | 아니오. 제품·날짜당 단일 가격만 존재 |

## 6. 두 앱이 가격 벌을 가르는 방법

### 6.1 견적서 `estimate-app` — 수동 토글

시트 모드에서 기본 카탈로그는 `_단가인상` 5종이다.

- `clients/web/estimate-app/lib/code.js:129-133` — 다섯 상수가 `_단가인상` 탭을 지정
- `clients/web/estimate-app/lib/code.js:749-750, 832, 924, 1012-1013, 1102` — 기본 카탈로그 loader가 그 상수를 read
- `clients/web/estimate-app/lib/code.js:1742-1745, 1795-1799` — `getPriceIncData_`는 반대로 접미사 없는 5종을 `인상 전 단가` map으로 read

화면은 날짜가 아니라 체크박스로 선택한다.

- `clients/web/estimate-app/views/index.ejs:2261-2278` — `chkHomeInc`/`chkCommInc`/`chkSingleInc`가 켜지면 `PRICE_INC`의 접미사 없는 값을 사용, 아니면 기본값 반환
- `clients/web/estimate-app/views/index.ejs:4390-4412, 5134-5145` — 싱글 구성품·세트 가격도 `chkSingleInc`가 켜지면 `PRICE_INC.single` 사용
- `clients/web/estimate-app/views/index.ejs:6645-6666, 7813-7824, 7852-7859` — 세 카테고리 모두 화면 라벨은 `인상 전 단가`, 변경 시 재렌더

기본 실행은 DB 모드다(`code.js:1843-1847`). 이때 기본 카탈로그는 현재 `products`, 인상 전 map은 `/price-baseline`의 `2000-01-01` 이력이다(`code.js:1882-1892`, `db-catalog.js:183-206`, `EstimateCatalogInternalController.java:377-413`). 체크박스 기본값만 `price_change_schedule.default_pre_change`에서 받는다.

`code.js:340`의 정규식은 수식에서 `'싱글 세트'`와 `'싱글 세트_단가인상'` 참조 행 번호를 모두 추출할 뿐이다. 두 탭 중 하나를 선택하는 조건은 없다.

### 6.2 주문서 `order-app` — 납기일 자동 전환

- `clients/web/order-app/index.html:1446-1451` — `due < effectiveDate`이면 인상 전 map 활성, 전환일 이상이면 기본 인상 후 값
- `clients/web/order-app/index.html:2722-2726` — 홈멀티
- `clients/web/order-app/index.html:2750-2753, 2780-2784, 3283-3287` — 싱글 구성품·싱글 세트
- `clients/web/order-app/index.html:2760-2767, 2846-2850` — 상업멀티 구성품·본품
- `services/partner-order-service/src/main/java/com/samhanair/logis/partnerorder/service/BootstrapService.java:359-377` — 현재 카탈로그와 baseline map, schedule을 함께 payload로 구성

따라서 두 앱은 정말 다르다.

- 견적서: 사용자가 `인상 전 단가` 체크박스로 직접 고른다. schedule의 `default_pre_change`는 초기 상태만 정한다.
- 주문서: 납기일과 `price_change_schedule.effective_date`를 비교해 자동으로 고른다.

## 7. 이관 전에 필요한 것

새 테이블 설계를 제안하는 절이 아니라, 현재 구조로 부족한 표현 능력을 적는다.

1. DB에 없는 모델 2개의 식별 결정을 해야 한다.
2. 비인상 과거행이 없는 DB 제품 37개를 어떻게 채울지 정해야 한다.
3. 비인상 1,456셀·인상 1,432셀의 값 우선순위를 정해야 한다.
4. 같은 모델·같은 날짜의 복수 가격을 구분할 원본 문맥이 필요하다. 최소 구분 후보는 세트, 구성품, 특징, 가격열 위치다.
5. 중복 `납품가` 두 열의 업무 의미와 전역 단가/문맥 단가 여부를 확정해야 한다.
6. `0`을 실제 0원으로 볼지 미등록으로 볼지 열별 규칙을 정해야 한다.
7. 비인상에만 있는 싱글 세트 3행을 의도적 제외로 볼지 별도 보존할지 정해야 한다.
8. 이력 인상일 `2026-04-01`과 앱 전환일 `2026-07-01`의 역할 차이를 승인해야 한다.

## 8. 확정하지 못한 것

- `_단가인상`이 모든 품목에서 시간상 더 최신이거나 금액상 더 높다는 것은 확정할 수 없다. 실제 30개 차이 중 22개가 더 작다.
- 두 `납품가` 열이 각각 어떤 계약·거래처·세트 문맥을 뜻하는지 CSV와 코드만으로 확정할 수 없다.
- 같은 모델의 여러 문맥 가격 중 어느 값을 제품 전역 가격으로 승격해야 하는지 모른다.
- 비인상에만 있는 세 모델이 단종으로 의도적으로 빠진 것인지, 누락인지 모른다.
- JHJ 14세트와 그룹명 4개가 현재 실제 업무에서 쓰이는지 모른다.
- `AP110RNPPHH1↔AP110RNPPBH1`, `PC6NUNK1N↔PC6NUNK1NW`가 오타 매핑인지 별도 모델인지 모른다.
- `2000-01-01`, `2026-04-01`, `2026-07-01` 중 어느 날짜가 회계·견적·주문 각각의 정식 효력일인지 이번 자료만으로 확정할 수 없다.
- CSV 파일 시각이 Google 서버 export 완료 시각과 정확히 같은지는 모른다.

## 9. 재현 방법

Google에는 접근하지 않고 CSV와 DB를 읽기만 한다.

```powershell
# DB 스키마·분포
docker exec samhan-postgres psql -U samhan -d product_db -P pager=off -c "SELECT effective_date,count(*),count(DISTINCT product_id) FROM price_history WHERE NOT coalesce(is_deleted,false) GROUP BY effective_date ORDER BY effective_date;"
docker exec samhan-postgres psql -U samhan -d product_db -P pager=off -c "SELECT category,effective_date,default_pre_change FROM price_change_schedule WHERE NOT coalesce(is_deleted,false) ORDER BY category;"

# 코드 근거
rg -n "HOME_NAME|SINGLE_NAME|SINGLE_PARTS_NAME|COMM_NAME|COMM_PARTS_NAME|getPriceIncData_|chkSingleInc" clients/web/estimate-app/lib/code.js clients/web/estimate-app/views/index.ejs
rg -n "function incActive|incActive\(" clients/web/order-app/index.html
```

CSV 재계산 입력 루트:

```text
C:/Users/user/AppData/Local/Temp/claude/C--dev-Samhan-Public/cdbb83c4-61fe-4c24-ba6f-7688e70e25fa/scratchpad/
```

재계산 시 여섯 탭의 모델명 열을 `products.model_name`에 조인하고, 각 행의 출고가 및 모든 납품가 셀을 각각 `products.release_price`/`delivery_price`와 대조한다. 한 번은 빈칸을 0으로 치환하고, 한 번은 어느 한쪽이 빈칸 또는 0인 셀을 제외한다. 두 벌 사이의 가격 diff는 `싱글 세트`만 모델명으로 정렬하고 나머지는 같은 문맥 행 순서를 유지한다.
