## 1. 결론

S4 지시서의 결함 2건을 수정했다.

- `VIEW=true`, `UPDATE=false` 사용자는 기존처럼 페이지와 CSV를 사용할 수 있지만, 실행 버튼은 계속 disabled이고 화면에는 실행 버튼을 누르라는 문구 대신 동기화 권한 부재 원인이 표시된다.
- sync가 HTTP 403으로 끝나면 권한 원인을 표시하고 버튼을 disabled로 잠근다. “잠시 후 다시 시도” 안내와 초기 실행 안내는 같은 화면에 남지 않는다.
- HTTP 500·네트워크 오류·결과 data null은 권한 오류로 오표시하지 않는다. 일시 오류/결과 불명 상태는 재시도 가능한 경로로 유지한다.
- S1·S3의 전달 상태 3종, 건수 0/양수, mock 미전달 문구, CSV 고지는 변경하지 않았다.

실제 Aligo 호출, 서버 코드 변경, Docker, migration, commit, push는 수행하지 않았다.

## 2. 원인과 수정

### 결함 1

`AligoAddressBookPage.tsx`의 빈 상태 문구가 `canSync`와 무관하게 렌더링됐다. 같은 파일 앞부분에서는 이미 `!canSync`일 때 버튼과 클릭 핸들러를 차단하고 있었지만, 빈 상태의 실행 안내가 권한 경계를 읽지 않았다.

수정:

- `canSync=false` 초기 상태에는 `주소록 동기화 실행 권한이 없어 실행할 수 없습니다. 관리자에게 동기화 권한을 요청하세요.`를 표시한다.
- `canSync=true` 초기 상태에만 기존 실행 안내를 표시한다.
- VIEW 전용 테스트에서 클릭과 Enter/Space 키보드 조작 후 sync wrapper 호출 횟수가 0인지 고정했다.

### 결함 2

`syncMutation.isError`가 HTTP 상태를 구분하지 않고 모든 오류를 같은 문구로 표시했다. 버튼도 `syncPending || !canSync`만 보므로, FE 권한 캐시가 UPDATE를 허용한 뒤 서버가 403을 확정해도 활성 상태로 남았다.

수정:

- `getHttpStatus(error)`가 Axios 오류 또는 mock 오류의 `response.status`만 읽도록 추가했다.
- `syncForbidden = getHttpStatus(syncMutation.error) === 403`을 두었다.
- 403에서는 권한 원인과 “권한 요청 후 화면 새로고침” 다음 행동을 표시하고, 버튼을 disabled로 유지한다.
- 403이 아닌 오류는 기존 `동기화 중 오류가 발생했습니다. 잠시 후 다시 시도해 주세요.` 경로를 유지한다.
- 성공했지만 `data=null`인 경우에는 초기 실행 안내를 다시 표시하지 않고 `동기화 결과를 확인할 수 없습니다. 잠시 후 다시 시도해 주세요.`를 표시한다.

## 3. 지시서 ② 불변식 판정

1. **VIEW=true, UPDATE=false는 페이지·CSV 사용 가능, sync 실행 불가**  
   `canSync`는 기존 `aligo.address-book/update` 판정을 유지한다. sync 버튼은 disabled이고 CSV 버튼은 enabled다. VIEW 전용 단위 테스트와 실제 Playwright 라우트 테스트가 모두 이 DOM을 확인했다. 서버 권한 정책과 route guard는 변경하지 않았다.

2. **실행 불가능 사용자에게 실행·재시도 지시 금지**  
   초기 VIEW 전용 화면은 권한 원인을 표시하고 실행 안내를 숨긴다. 403 화면은 권한 원인과 새로고침 다음 행동만 표시하며 일반 재시도 문구와 실행 안내를 모두 숨긴다. 클릭·Enter·Space 조작도 sync wrapper를 호출하지 않는다.

3. **UPDATE 보유 최초 정상 경로 유지**  
   UPDATE 보유 초기 화면은 버튼 enabled와 기존 실행 안내를 함께 표시한다. UPDATE 보유 클릭은 기존 `syncAligoAddressBook` wrapper를 1회 호출한다. 실제 라우트에서도 enabled와 실행 안내를 확인했다.

4. **403 확정 후 권한 원인과 다음 행동 즉시 표시**  
   `response.status=403`을 일반 오류와 분리해 `주소록 동기화 권한이 없습니다. 관리자에게 권한을 요청한 뒤 화면을 새로고침해 주세요.`를 표시한다. 버튼은 disabled이고 같은 mutation을 즉시 다시 보낼 수 없다.

5. **5xx·네트워크 오류는 재시도 가능 오류 유지**  
   HTTP 500과 response 없는 네트워크 오류는 모두 기존 일반 오류 문구를 표시하고 버튼을 enabled로 유지한다. 권한 오류 문구는 표시하지 않는다.

6. **전달 상태·건수 회귀 금지**  
   `deliveryStatus`, `ResultChips`, `DeliveryStatusNotice`, `FailedList`와 서버 계약은 변경하지 않았다. `NOT_DELIVERED`, `DELIVERED`, `PARTIALLY_DELIVERED`의 양수/0건 테스트 6개가 계속 통과했다.

7. **CSV 고지 전 상태 유지**  
   정적 고지 문단을 오류·권한 상태에서도 제거하지 않았다. 실제 전달 상태에서는 CSV 고지만, 그 밖의 결과 없음/미전달/오류 상태에서는 기존 mock 미전달 문구와 CSV 고지를 함께 표시한다. VIEW 전용, 403, 500, 네트워크 오류, data null, 전달 상태 3종에서 CSV 고지를 확인했다.

8. **클릭·키보드 mutation 경계 유지**  
   VIEW 전용 버튼의 click/Enter/Space 조작은 sync wrapper 0회다. UPDATE 보유 클릭은 기존 sync wrapper 1회다. 서버 POST endpoint와 `@RequirePermission(UPDATE)`는 변경하지 않았다.

## 4. 새로 가능해진 상태·화면 조합과 밟은 결과

지시서의 교차곱에서 `deliveryStatus` 3종은 HTTP 200 응답에만 존재한다. 403·500·네트워크 오류·data null에는 전달 상태가 없으므로, 오류를 전달 상태 3종에 억지로 끼워 넣지 않고 별도 화면 상태로 닫았다. 이것이 API 계약상 세 번째 경계다.

| 권한 상태 | 응답 | 전달 상태 | 실제로 밟은 결과 |
|---|---|---|---|
| VIEW 전용 (`VIEW=true`, `UPDATE=false`) | 초기 `null` | 없음 | 버튼 disabled, CSV enabled, 권한 원인 표시, 실행 안내 없음, click/Enter/Space sync 0회 |
| 실행 가능 (`VIEW=true`, `UPDATE=true`) | 초기 `null` | 없음 | 버튼 enabled, 기존 실행 안내 표시 |
| 실행 가능 | HTTP 200 | `NOT_DELIVERED` | 실제 전달 0건, 신규/변경 0 유지, mock+CSV 고지 유지 |
| 실행 가능 | HTTP 200 | `DELIVERED` | 실제 전달 문구, 신규·변경 양수/0건 표시, mock 미전달 단정 없음, CSV 고지 유지 |
| 실행 가능 | HTTP 200 | `PARTIALLY_DELIVERED` | 일부 전달 문구, 전달 건수와 실패 목록 동시 표시, 전체 미전달 단정 없음 |
| 실행 가능, 서버 권한 회수 | HTTP 403 | 없음 | 권한 원인 표시, 일반 재시도 문구 없음, 버튼 disabled, CSV 고지 유지 |
| 실행 가능 | HTTP 500 | 없음 | 기존 일반 오류·재시도 문구, 버튼 enabled, 권한 오류 문구 없음 |
| 실행 가능 | 네트워크 오류(response 없음) | 없음 | 기존 일반 오류·재시도 문구, 버튼 enabled, 권한 오류 문구 없음 |
| 실행 가능 | HTTP 200 + `data=null` | 없음 | 결과 확인 불가 문구, 초기 실행 안내 없음, 버튼 enabled, CSV 고지 유지 |
| VIEW=false 경로 | 어떤 sync 응답이든 | 없음 | 페이지 자체가 기존 VIEW route guard 경계 밖이다. 이번 페이지 변경으로 우회시키지 않았다. |

응답 200의 전달 상태 3종은 기존 양수/0건 행렬 테스트로 각각 다시 밟았다. 403/500/null은 `deliveryStatus`가 없는 오류·결과 불명 상태로 직접 주입했다. VIEW 전용은 버튼과 키보드가 POST를 만들 수 없으므로 서버 응답을 기다리는 조합 자체가 사용자 도달 불가임을 테스트로 고정했다.
