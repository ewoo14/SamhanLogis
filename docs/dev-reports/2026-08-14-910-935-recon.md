# #910 + #935 클라이언트 자동 업데이트 확대 정찰

> 작성일: 2026-08-14 KST  
> 역할: SOL(정찰)

## 0. 결론

`#1204`는 9개 앱 자동 업데이트를 끝낸 PR이 아니다. **`clients/internal-chat-desktop` 한 앱에서만** 자체서명 installer, generic feed, `electron-updater`, 오류 안내 3계열, 실제 `quitAndInstall` 재기동과 cleanup 하네스를 완주한 선행 실증이다.

현재 사용자 대면 배포 앱은 기존 8개에 사내 메신저 데스크톱을 더한 **9개**다. 서버에는 9개 모두 고유 식별자가 있다. 9개 모두 `/app/version` 버전 확인 코드도 있다. 그러나 형태별 실운영 상태는 다르다.

- Electron 3앱: updater 소스 배선은 모두 있다. 실제 자체서명 feed 왕복까지 검증된 것은 사내 메신저 1앱뿐이다.
- Expo 3앱: `expo-updates` OTA 코드는 모두 있다. 저장소·`infrastructure/.env.local`에 실제 `EAS_PROJECT_ID` 주입이 없어 현재 OTA는 비활성이다.
- 웹 3앱: 버전 정책 안내와 사용자가 선택하는 새로고침은 있다. binary/OTA 자동 업데이트 대상은 아니다.
- **사용 중 재감지·알림은 0/9**다. 모든 게이트가 기동 또는 최초 mount 1회만 확인하며 폴링, 브라우저 focus/visibility 복귀, React Native `AppState` 복귀 재확인이 없다.

`#935`의 2026-07-26 표는 현재는 낡았다. 아로로지스 데스크톱의 버전 확인·updater·publish·릴리스 wrapper는 이후 PR들, 특히 PR `#981`에서 이미 들어왔고 PR `#1181`이 오류 관측·다운그레이드·설치 실패 전달을 보강했다. 다만 실제 아로로지스 signed installer와 feed 왕복은 여전히 증명되지 않았다.

## 3. 형태별 차이

### 3.1 Electron 설치본

업데이트 단위는 서명된 NSIS installer다. generic feed의 `latest.yml`, installer, blockmap이 필요하다. 다운로드 후 `quitAndInstall(true, true)`로 프로세스를 종료하고 설치·재기동한다. portable 산출물은 자동 업데이트 설치 대상이 아니다.

공통 선행조건:

1. 앱별 feed URL 또는 channel/prefix 격리
2. installer 코드서명과 `publisherName` 일치
3. 설치 PC 신뢰 루트 배포
4. installer·feed·재기동을 실제 packaged 앱으로 검증

### 3.2 Expo 모바일

현재 구현은 native binary 교체가 아니라 EAS Update의 JS/assets OTA다. `runtimeVersion: { policy: 'appVersion' }`라 native 변경은 새 store/internal build가 필요하다. 현재 코드는 업데이트가 있으면 `fetchUpdateAsync()` 뒤 곧바로 `reloadAsync()` 한다.

중요한 현재 결함 경계:

- `MobileVersionGate`는 mount 1회다.
- OTA 확인은 background로 실행되고 사용자가 업무 화면에 진입한 뒤 reload가 발생할 수 있다.
- 저장되지 않은 입력을 검사하거나 reload 동의를 받는 공통 장치가 없다.
- 지금은 `updates.enabled=false`라 잠복해 있지만 EAS project를 연결하는 순간 경로가 활성화된다.

### 3.3 웹

새 배포는 다음 document reload로 받는다. 세 앱 모두 자동 reload를 하지 않고 사용자가 버튼을 눌러 새로고침한다. 주문·견적은 dirty DOM을 검사하고 모바일 퍼블릭은 서명 stroke 존재 여부를 검사한다. 이 입력 보호는 유지해야 한다.

다만 최초 load 후 새 릴리스가 올라와도 다시 조회하지 않으므로 장시간 열린 탭에는 알림이 오지 않는다.

## 4. `#1204`가 정확히 만든 것

PR 제목과 달리 제품 코드는 `clients/internal-chat-desktop`만 변경했다. 다른 Electron·Expo·웹 앱 제품 코드는 건드리지 않았다.

### 4.1 실제 산출물

- 사내 메신저 builder를 `forceCodeSigning: true`로 전환하고 `INTERNAL_CHAT_UPDATE_URL`, `CSC_LINK`, `CSC_KEY_PASSWORD`를 필수화
- `latest` generic feed용 signed NSIS 산출물 생성
- `electron-updater` 오류를 세 계열로 구분
  - 미신뢰 인증서
  - 손상/검증 실패
  - 네트워크/서버 연결 실패
- 임시 자체서명 인증서 생성 또는 기존 인증서 재사용, `CurrentUser\Root` 신뢰 확인, 로컬 HTTP feed 기동
- 9101 설치 → 9102 감지·다운로드·`quitAndInstall`·재기동·DisplayVersion과 `app.asar` 교체 확인
- downgrade, 같은 버전, 사용자 localStorage 보존, 미신뢰 installer 설치 차단 검증
- feed process, 앱 process, 임시 폴더, uninstall registry, updater cache를 정리하고 진짜 cleanup 실패는 exit 1로 만드는 하네스

### 4.2 공통 자산 / 앱 전용 구분

| 자산 | 판정 | 재사용 범위와 제약 |
|---|---|---|
| `scripts/app-build-version.cjs`의 날짜형 버전→Electron semver/DisplayVersion 변환 | **공통 자산** | 이미 세 Electron wrapper와 웹·모바일 version resolver가 공유한다 |
| generic feed 계약(`latest.yml` + installer + blockmap) | **공통 패턴** | Electron 3앱에 동일 적용 가능. 단 제품별 URL/prefix/channel 격리가 필요 |
| `forceCodeSigning` + `CSC_LINK`/암호 fail-closed | **공통 패턴** | 삼한·아로로지스 wrapper에도 명시 필수화를 이식할 수 있음 |
| 오류 안내 3계열과 내부 오류 비공개 | **공통화 후보** | 현재 구현은 사내 메신저 전용. 삼한·아로로지스는 아직 모든 오류를 한 문구로 처리 |
| cleanup helper의 process 종료 확인·directory retry·실패 fatal | **부분 공통** | 함수는 일반화 가능하지만 현재 runner의 제품명·레지스트리·cache·feed port는 사내 메신저 고정 |
| `run-internal-chat-release-feed.ps1` | **앱 전용 하네스** | 앱 경로, 제품명, 환경변수, installer 이름, updater cache가 모두 hard-code. template로는 유용하지만 그대로 재사용 불가 |
| `build-internal-chat-desktop-release.cjs` | **앱 전용 wrapper** | 공통 helper를 사용하지만 app dir와 env가 고정 |
| `clients/internal-chat-desktop/src/main/auto-update.ts`와 renderer UI | **앱 전용 구현** | IPC window namespace와 UI DOM이 앱 전용. 공통 모듈 추출 후보일 뿐 현재 공통 자산 아님 |
| `CN=Samhan Internal Release` 인증서 2개 | **현재는 사내 메신저 전용 운영 자산** | 다른 두 앱의 `publisherName: Samhan Air Systems Co., Ltd.`와 불일치. 그대로 서명하면 검증 계약이 어긋남 |

따라서 `#1204`는 재사용 가능한 **검증 레시피**를 만들었지만, 세 Electron 앱이 곧바로 같은 인증서·스크립트를 쓰게 만든 것은 아니다.

## 6. `#1181` 이름과 실제의 차이

PR `#1181` 제목은 “클라이언트 자동 업데이트 — 8앱 + 아로로지스 데스크톱”이지만, 아로로지스 데스크톱은 원래 8앱 안에 포함된다. 사내 메신저가 추가돼 실제 제품 수가 9개가 된 것이다.

실제로 한 일:

1. `INTERNAL_CHAT_DESKTOP`을 서버 enum·Flyway CHECK에 추가해 **9번째 식별자**를 등록
2. 사내 메신저에 version API, renderer 안내, `electron-updater` IPC와 builder publish 골격을 신설
3. 기존 8앱의 정책 조회 실패를 조용히 삼키지 않고 사용자 배너로 보이게 보강
4. Electron의 downgrade/설치 실패 전달을 보강
5. 모바일 OTA 실패를 배너로 관측 가능하게 보강
6. 웹 3앱의 실제 reload와 Electron UI/IPC 호출을 라이브 QA로 확인

하지 않은 일:

- 9개 앱의 운영 feed/자격 배포
- 삼한·아로로지스 signed installer 실제 왕복
- Expo EAS project 연결과 OTA publish
- 사용 중 재감지·알림
- stable/beta channel 분리
- 사내 PC 전체 인증서 배포

따라서 정확한 이름은 **“9앱 버전 정책·오류 관측 계약 + 사내 메신저 updater 골격”**에 가깝다. `#1204`가 그 골격 중 사내 메신저 1앱의 실제 feed·자체서명 왕복만 닫았다.

## 7. “사용 중 알림” 현재 상태

판정: **0/9**.

| 형태 | 현재 트리거 | 빠진 사용 중 트리거 |
|---|---|---|
| 삼한 데스크톱 | bootstrapped 후 updater·정책 각 1회 | 주기 확인, window focus/restore 시 확인 |
| 아로로지스 데스크톱 | bootstrapped 후 각 1회 | 위와 같음 |
| 사내 메신저 | renderer 시작 직후 각 1회 | 위와 같음 |
| Expo 3앱 | `MobileVersionGate` mount 1회 | `AppState` active 복귀, jitter 포함 주기 확인 |
| 웹 3앱 | 최초 main/DOM ready/mount 1회 | `visibilitychange`/focus 복귀, jitter 포함 주기 확인 |

단순 고정 간격 폴링을 9앱에 동시에 넣으면 N4(동시 요청 방지)를 위반할 수 있다. 공통 정책은 “긴 기본 주기 + 앱/설치별 jitter + background에서는 중지 + foreground 복귀 시 최소 간격을 지킨 재확인”이 적합하다.

알림 후 행동도 형태별로 달라야 한다.

- Electron: 사용 중에는 다운로드까지만 하고 재시작/설치는 사용자 선택 또는 안전한 유휴 시점으로 미뤄야 한다.
- Expo: `reloadAsync()` 전 dirty 판단 또는 명시 동의가 필수다.
- 웹: 현재 사용자 선택 reload와 dirty confirm을 유지한다.

## 8. 인증서 배포 확대 영향

현재 `CurrentUser\Root`에는 `CN=Samhan Internal Release` 인증서 2개가 있고 `#1204`는 이 store에서 정상 동작했다. CurrentUser store이므로 이 PC 실측상 관리자 권한 없이 배포 가능하다.

그러나 앱 수 확대에는 다음 문제가 있다.

1. **publisher 불일치**: 삼한·아로로지스는 `Samhan Air Systems Co., Ltd.`, 사내 메신저는 `Samhan Internal Release`다.
2. **중복 루트**: 같은 subject 인증서가 현재 2개다. 실제 운영은 어떤 지문이 정본인지 정해야 한다.
3. **만료·교체**: 2027-08 만료다. 새 인증서 roll-over 때 구버전 앱이 새 signer를 신뢰할 수 있도록 겹침 기간이 필요하다.
4. **PC 전수 배포 증명**: 앱별 배포를 늘리기 전에 대상 사내 PC inventory와 설치 성공/실패를 확인할 수단이 필요하다.
5. **서명키 보관**: 신뢰 루트 `.cer`는 배포 가능하지만 private key/PFX는 빌드 주체에만 보관해야 한다.

한 회사-wide 코드서명 인증서와 동일 publisher로 통일하면 Electron 앱이 늘어도 PC당 루트 설치는 1회다. 앱별 인증서를 유지하면 격리는 강해지지만 PC마다 여러 루트와 갱신 절차를 관리해야 한다.

## 9. 착수 순서 제안

### 1순위 — Electron 공통 운영 계약 확정

사내 메신저에서 검증한 흐름을 기준으로 다음을 먼저 고정한다.

- 정본 인증서 subject/publisher와 지문
- 공통 서명키 주입 방식
- 제품별 feed prefix/channel 규칙
- 세 오류 계열 공통 판별
- 공통 E2E runner의 제품 파라미터 계약

이 순서를 먼저 밟으면 삼한·아로로지스가 같은 오류·서명·cleanup 문제를 각자 반복하지 않는다.

### 2순위 — 아로로지스 데스크톱

`#935` 코드 골격이 이미 가장 완성돼 있어 사내 메신저 하네스를 제품 파라미터화하는 두 번째 실증에 적합하다. `AROLOGIS_UPDATE_URL` feed, 정본 인증서, 1→2 왕복, downgrade, 오류 3계열을 실제로 닫는다.

### 3순위 — 삼한 데스크톱

동일 공통 자산을 적용하되 삼한 데스크톱은 Electron 외 Web/Capacitor 변형이 있어 회귀 표면이 더 넓다. 두 번째 제품에서 공통화가 검증된 뒤 적용하는 편이 안전하다.

### 4순위 — 웹 3앱 사용 중 감지

배포 인프라가 필요 없고 현재 dirty 보호가 이미 있다. 공통한 foreground/jitter 정책을 먼저 검증하기 좋다. 웹에서 재감지 정책을 확정하면 모바일 foreground 정책의 참고가 된다.

### 5순위 — Expo 3앱

EAS project·채널 결정과 N2 안전장치를 같은 슬라이스에서 처리한다. OTA를 먼저 켜고 reload 안전장치를 뒤로 미루면 잠복 결함을 활성화한다.

### 6순위 — 전 앱 통합 사용 중 알림 QA

9개 앱 각각에서 릴리스 게시 후 기동 없이 감지, jitter, background 복귀, 입력 보존, 오류 안내를 실측한다.

## 10. 개발책임자 결정이 필요한 미결 항목

### 결정 1 — Electron stable/beta 격리 방식

- **A. 제품별 URL prefix + 동일 `latest` channel (권장)**: 현재 세 builder 구조와 가장 가깝다. 예: `/desktop/latest.yml`, `/arologis/latest.yml`, `/internal-chat/latest.yml`. beta는 별도 prefix로 추가한다.
- B. 공유 URL + 제품별 channel 이름: manifest 이름과 updater channel 설정을 더 많이 바꿔야 하며 운영자가 잘못 publish할 위험이 있다.
- C. stable만 운영하고 beta는 보류: 초기 단순성은 높지만 사내 선행 검증군을 자동 배포로 운용하기 어렵다.

별도 질문: beta 대상자를 앱 별도 설치본으로 둘지, 동일 앱 설정으로 채널 전환할지도 함께 정해야 한다.

### 결정 2 — 모바일 업데이트 방식

- **A. EAS Update OTA + 사용자 동의 reload + native 변경은 store/internal build (권장)**: 현재 코드와 `runtimeVersion: appVersion`을 살린다. EAS project/소유 계정·비용 정책을 확정해야 한다.
- B. OTA를 사용하지 않고 store/internal build만 배포: 운영은 단순하지만 긴급 JS 수정 반영이 느리다.
- C. 자체 OTA 서버: 외부 의존은 줄지만 Expo 업데이트 서버 운영·서명·롤백을 새로 책임져야 해 현재 범위를 크게 늘린다.

어느 안이든 현재의 즉시 `reloadAsync()`는 유지하면 안 되며 dirty 보호와 명시 동의를 OTA 활성화와 같은 슬라이스에서 넣어야 한다.

### 결정 3 — 자체서명 인증서 배포 범위

- **A. Electron 3앱 공통 회사-wide 인증서 1개 + 동일 publisher + CurrentUser Root 전 사내 PC 배포 (권장)**: PC당 1회 설치, 앱 추가 비용이 가장 낮다.
- B. 앱별 인증서 3개: 제품 격리는 강하지만 루트·만료·교체 관리가 3배가 된다.
- C. 현재 사내 메신저 인증서만 유지하고 다른 두 앱은 별도 결정: `#935`와 삼한 데스크톱 실제 자동 설치가 계속 미완료로 남는다.

선택 후 정해야 할 운영 세부: 정본 thumbprint, 발급/보관 책임자, `.cer` 배포 스크립트 또는 관리도구, inventory, 만료 전 roll-over 기간, 폐기 인증서 제거 기준.

### 결정 4 — 사용 중 확인 정책

- **A. 공통 기본 30분 + 설치별 jitter ±20% + foreground 복귀 시 최소 10분 경과한 경우 확인 (권장)**: 서버 동시 부하와 알림 지연의 균형이 좋다.
- B. 5~10분 단주기: 감지는 빠르지만 9앱 동시 요청과 장시간 탭 부하가 커진다.
- C. 서버 push: 즉시는 가능하지만 새 인프라를 만들어야 하며 이 이슈 범위를 크게 늘린다.

### 결정 5 — 웹 release wrapper 표준화

- **A. 웹 3앱 모두 명시 버전 release wrapper를 신설 (권장)**: Electron과 같은 fail-closed 운영 계약을 갖는다.
- B. 현 resolver만 유지: production env를 정확히 주입하면 동작하지만 일반 `npm run build`와 릴리스 산출물 구분이 약하다.

## 11. 착수 시 보존할 불변식

1. 한 앱의 릴리스가 다른 앱의 정책이나 feed를 오염시키지 않는다.
2. 사용 중 자동 install/reload/새로고침이 저장되지 않은 입력을 조용히 잃게 하지 않는다.
3. 버전 정책·feed 실패가 앱 사용을 무조건 차단하지는 않되 사용자에게는 드러난다. `CRITICAL` 정책만 차단한다.
4. 내부 오류 코드·경로·UUID를 사용자 화면에 노출하지 않는다.
5. 모든 Electron 릴리스는 서명 없이는 빌드 실패하고, signer와 배포된 신뢰 루트가 일치한다.
6. 하네스 성공은 실제 updater 경로, 실제 installer, 실제 재기동과 cleanup 성공을 포함해야 한다.
7. 9개 앱은 각각의 실행 환경에서 별도로 검증한다.
