### 확인 3 — 버튼이 요구하는 실제 page/action 값

`SlipDetailPage.tsx:1102-1115`에서 `inspect`와 `complete`는 모두 `pageCode='slip.transfer.process'`로 매핑된다. `usePermissions.ts:80-87`의 `canAccess`는 `GET /auth/admin/permissions/my` 결과에서 동일 `pageCode` 행을 찾고, 그 행의 `actions` 배열에 정규화된 `'update'`가 있어야 `true`를 반환한다. 데이터가 아직 로드되지 않았거나 pageCode 행이 없거나 UPDATE가 없으면 모두 `false`다.

즉 `kimgicheol` 버튼의 비동기 pending 상태가 아니라 안정 상태 권한 판정값을 확정하려면 다음 실측값이 필요하다.


## 2. `kimeunji` 상세 조회 실패

### 확인 2 — 화면 문구가 응답 코드를 구분하지 않는 위치

`clients/desktop/src/renderer/routes/SlipDetailPage.tsx:1281-1285`가 `getSlip(id)`를 호출하고, `clients/desktop/src/renderer/api/slip.ts:498-500`의 실제 요청은 `GET /slips/{id}`이다. `SlipDetailPage.tsx:1873-1877`은 `detailQuery.isError || !detailQuery.data`인 모든 경우에 응답 코드와 무관하게 정확히 `전표를 불러오지 못했습니다.`만 표시한다. 따라서 화면 문구만으로 403/404/500/200+빈값을 판정할 수 없으며, HTTP를 별도로 측정해야 한다.

### 확인 4 — 상세 조회의 서버 측 권한 경로

`services/slip-service/.../SlipController.java:270-279`의 `GET /slips/{id}`는 먼저 `SlipService.getOne(id)`로 전표를 찾고, 그 응답의 전표 유형에 대해 `SlipSalesAccessGuard.guardOutboundSalesRead(...)`를 실행한다. OUTBOUND이면 `SlipSalesAccessGuard.java:69-78,143-161`의 OR 조건 중 하나를 만족해야 한다.

```text
role ∈ {SALES, MANAGER, MASTER}
또는 X-User-Groups에 built-in MASTER(…100), MANAGER(…101), SALES(…102) 포함
또는 X-Is-System-Master=true
```

WAREHOUSE/INVENTORY 역할 및 WAREHOUSE built-in 그룹(…103)만으로는 OUTBOUND 상세를 허용하지 않고 `BusinessException(FORBIDDEN, "매출 전표 조회는 SALES / MANAGER / MASTER 권한만 허용합니다.")`를 던진다. 이 코드가 `kimeunji`에게 실제 발화했는지는 계정 행·JWT 헤더·HTTP 응답을 이어서 측정한다.

### 확인 12 — ACCOUNTANT 동일 권한 문맥의 상세 GET HTTP 실측

이슈 당시 `kimeunji` 요청 자체의 네트워크 캡처는 선행 QA 보고서에 남아 있지 않고, 현재 DB에는 계정과 대상 전표가 없다. 따라서 아래 결과를 “당시 kimeunji 세션 원문”이라고 쓰지 않는다. 현재 서비스에 존재하는 `dev_accountant`(ACCOUNTANT built-in 그룹 `…104`, system master=false)와 현재 존재하는 OUTBOUND 전표로 같은 서버 권한 분기를 읽기 전용 GET 재현했다.

### 확인 14 — 프런트가 실제 소비하는 SALES `/permissions/my` 값

현재 DB의 SALES seed 계정으로 프런트와 동일한 읽기 전용 endpoint를 호출했다.

```text
GET http://127.0.0.1:8081/auth/admin/permissions/my
X-User-Id: a0000000-0000-0000-0000-000000000004
X-User-Groups: 00000000-0000-0000-0000-000000000102
X-Is-System-Master: false
```

응답 status와 목표 키 원문(전체 응답 중 목표 항목은 마지막에 존재):

```text
HTTP/1.1 200
Content-Type: application/json

...
"slip.transfer.process":[]
...
```

DB의 `account_page_permissions.can_update=false`가 API에서는 빈 actions 배열 `[]`로 직렬화된다. `usePermissions.ts:80-87`은 이 배열에 `UPDATE`가 없으므로 `canAccess('slip.transfer.process','update') = false`를 반환한다. 결과적으로 `SlipDetailPage.tsx:4383-4387`의 두 번째 disabled 항이 true다.

```text
nextPrimaryAction                                      = inspect
slipActionPageCode(nextPrimaryAction).pageCode         = slip.transfer.process
```

선행 실 QA 캡처는 `kimgicheol`을 `SALES`로 기록한다. 당시 `kimgicheol` 본인 endpoint 응답 원문은 저장되어 있지 않고 현재 계정 행도 없으므로, 위 API 원문을 그 계정의 당시 캡처라고 가장하지 않는다. 다만 현재 실 DB의 SALES role template, 영업원 group permission, materialized account permission이 모두 같은 page의 UPDATE=false이고, 현재 API도 `[]`를 반환하므로 버튼 차단의 판정식과 정책값은 확정된다.

### 확인 15 — 당시 auth 계정 키와 employee 키가 달랐던 선행 실측

`docs/dev-reports/2026-08-01-1020-employee-account-link-recon.md:237-243`에 남은 당시 auth DB 읽기 전용 SQL 결과는 UUID 전체가 아닌 앞 8자리만 기록했지만, 계정 행 존재 자체와 로그인 ID를 확인할 수 있다.

```text
display_name | login_id   | account_id_prefix | ver | created_at                 | created_by      | deleted | enabled
-------------+------------+-------------------+-----+----------------------------+-----------------+---------+--------
김기철       | kimgicheol | 8c613bed          | 4   | 2026-05-09 15:53:17.535422 | system-internal | f       | t
김은지       | kimeunji   | c5af1500          | 4   | 2026-05-09 15:53:18.160509 | system-internal | f       | t
```

같은 보고서의 employee recon은 김기철 employee 쪽 깨진 `account_id` prefix를 `67b844f5…`, 김은지를 `86a56215…`로 기록하며 auth DB에 그 값이 존재하지 않는다고 판정했다. 즉 당시 시스템에 auth account UUID와 employee 측 UUID drift가 실제 있었던 것은 맞다. 그러나 결재선 USER picker/저장/표시/authorize는 모두 auth-service 내부의 `accounts.id`만 사용한다. 특히 이슈 당시 default-approvers API가 두 결재자를 삭제 사용자 표기가 아닌 `김기철`·`김은지`로 풀어냈으므로, 이 drift가 이번 결재선 게이트의 조용한 빈 조인을 만들었다는 증거는 없다.

## 4. 두 원인의 동일성 판정

**판정: 원인은 둘이다. 결재선 UUID 조인 실패 하나로 두 증상을 설명할 수 없다.**

### `kimgicheol` — 프런트 동적 RBAC에서 선차단

1. 이슈 당시 `INSPECTING`의 `nextPrimaryAction`은 `inspect`이고, 표시 라벨은 `완료 (처리 완료)`다.
2. 버튼은 `canAccess('slip.transfer.process', 'update')`가 false이면 disabled다.
3. SALES의 현재 실 DB 세 층(role template, 영업원 group permission, materialized account permission)에서 `can_update=false`이고, 프런트가 소비하는 실제 `/permissions/my` 값은 `"slip.transfer.process":[]`다.
4. 따라서 클릭 이벤트와 `POST /slips/{id}/inspect`가 발생하기 전에 브라우저에서 차단된다. `approvalGateForInspect`까지 도달하지 않는다.

이슈 당시 `kimgicheol` 계정의 권한 응답 원문은 선행 QA가 저장하지 않았고 현재 DB에도 계정이 없어 본인 행을 재측정하지 못했다. 그러나 선행 캡처의 역할은 SALES이며, 현재 실 DB와 endpoint가 보여 준 SALES 정책값 및 disabled 코드가 증상을 완전히 설명한다.

### `kimeunji` — 상세 GET의 OUTBOUND 열람 가드에서 선차단

1. 상세 화면은 먼저 `GET /slips/{id}`를 호출한다.
2. OUTBOUND 응답이면 컨트롤러가 `SlipSalesAccessGuard.guardOutboundSalesRead`를 실행한다.
3. 선행 실 QA가 기록한 역할은 ACCOUNTANT이고, ACCOUNTANT/회계원 그룹/system-master=false는 허용 OR 조건을 하나도 충족하지 않는다.
4. 동일 권한 문맥의 현재 서비스 GET 실측은 `HTTP/1.1 403`, body code `FORBIDDEN`, message `매출 전표 조회는 SALES / MANAGER / MASTER 권한만 허용합니다.`다.
5. 프런트는 403을 구분해 표시하지 않고 모든 detail query 실패를 `전표를 불러오지 못했습니다.`로 축약한다.

따라서 `kimeunji`는 전환 버튼 렌더링/판정 전에 상세 GET에서 막히며, 역시 `approvalGateForInspect`까지 도달하지 않는다.

### 결재선 키 판정

- 저장: `auth_db.approval_line_approver.config_role_id -> approval_line_config.id`; USER는 `approver_type='USER'`, `approver_ref_id=auth_db.accounts.id(UUID)`; GROUP은 `approver_type='GROUP'`, `approver_ref_id=permission_groups.id(UUID)`.
- 게이트 조회: gateway JWT sub가 전달한 `X-User-Id`를 UUID로 파싱하여 USER `approver_ref_id`와 직접 equals; 그룹은 같은 account UUID의 `account_groups.group_id`와 GROUP `approver_ref_id` 교집합.
- 이슈 당시 선행 읽기 전용 API 결과: 목표 결재선은 USER 2명(`kimgicheol`, `kimeunji`), GROUP 0명.
- 현재 실 DB 결과: 목표 결재선 USER 0행, GROUP 0행이며 두 계정과 대상 전표도 없다. 현재 DB는 이슈 당시 DB가 아니다.

정상 UI 저장·표시·authorize 모두 auth account UUID를 사용하고, 당시 API가 두 USER UUID를 실제 이름으로 역해석했다. 따라서 이번 두 증상의 원인은 UUID/login ID mismatch가 아니라 각각 **전환 RBAC 부재**와 **상세 열람 역할 가드**다.

## 5. 수정 방향(제안만, 미구현)

- 결재선의 OUTBOUND 검사자에게 `slip.transfer.process:UPDATE`를 어떤 방식으로 부여할지 정해야 한다. 현재 정적 SALES/ACCOUNTANT 역할 정책만으로는 개인 결재선 지정이 실행 권한을 만들어 주지 않는다.
- ACCOUNTANT인 개인 검사자가 OUTBOUND 상세를 읽어야 한다면 `SlipSalesAccessGuard`의 역할 고정 allowlist와 결재선 기반 접근의 우선순위를 설계해야 한다. 상세를 읽지 못하면 결재선에 올라도 실행 UI까지 도달할 수 없다.
- 결재 게이트 자체의 auth UUID 비교는 현재 코드상 정합하므로, 위 두 선행 가드를 해결하지 않고 결재선 조인만 바꾸는 수정은 증상을 해결하지 못한다.
