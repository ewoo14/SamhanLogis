확정 모델(전개=is_default / 동기화=종속1←기준N·factor·multiplier·SUM / 옵션=component_variant·is_default·'제외' 자동포함 / 할인=고정DC 우선·전역DC·반올림)에 안 맞는 것들.

[1] 정액 할인 6종은 '율' 축이 아니라 '금액 차감' 축이다 — dc_configs 의 rate 계열과 단위가 다르다. 게다가 order-app:2812 · 거래처 발송 주문서:2542 는 같은 값을 1 미만이면 율, 1 이상이면 정액으로 해석한다(이중 단위). 견적 계열(estimate-app:4442 · 종합견적서:4026)은 정액 전용. 모델을 '할인=율' 로만 잡으면 이 6종이 안 들어간다.

[2] 정액 6종은 순차 누적 차감이다 — adjustSingleSetBasePrice(estimate-app:3306-3311)에서 6개 조건이 모두 참이면 6번 다 뺀다. Math.max(0, ...) 하한이 매 단계에 걸려 있어 중간에 0 이 되면 나머지는 무효. '가장 유리한 하나' 나 '합산 후 1회 차감' 이 아니다.

[3] '고정DC 우선' 이 상업멀티에서는 소스마다 다르다 — 견적 계열은 **변동DC(useK2) 가 켜진 행에서만** 고정DC 가 전역율을 대체한다(estimate-app:4488). 주문 계열은 변동DC 가 꺼져 있어도 고정DC 단독으로 출고가 할인을 건다(order-app:2858). 게다가 홈멀티에는 주문 계열에도 이 단독 분기가 없다(order-app:2731). 즉 '고정DC 우선' 은 (앱 × 섹션) 4칸 중 1칸에서만 무조건 참이다.

[4] 변동DC 는 값이 아니라 **스프레드시트 수식 참조**로 결정된다 — Code.js:419/841 `useK2 = /\$L\$2/i.test(priceFormula)`. 구형 할인 여부도 마찬가지로 F열 수식의 `$I$1` 참조(Code.js:1742). DB 로 옮기면 이 두 플래그의 출처가 사라지므로 별도 컬럼(예: uses_global_dc, is_discountable)이 필요하다. 변수명 useK2 와 실제 검사 $L$2 가 불일치하는 점도 주의.

[5] 반올림은 견적/주문의 적용 축이 다르다 — 견적앱 roundByConfig(n, prefix) 는 홈/상업/구형 **섹션별 DOM 셀렉트**를 읽고 prefix 가 없으면 아무것도 안 한다(estimate-app:3326). 주문앱 roundByConfig(n) 은 prefix 가 없고 **CONFIG 전역 1쌍**만 쓴다(order-app:1752). unit_round_to/mode 를 거래처당 1쌍으로 잡으면 견적앱의 섹션별 설정이 표현 불가.

[6] 동일 이름 함수의 동작이 앱마다 반대 — applyHomeMultiPriceVat 는 견적앱에서 prefix 없는 roundByConfig 호출이라 **no-op**(estimate-app:4252), 주문앱에서는 실제 단위처리가 걸린다(order-app:2606).

[7] 구형 50% 는 '설정' 이 아니라 코드 리터럴이 지배한다 — 주문 계열은 0.5 를 5곳(order-app:4831/4872/4900/6198/6638)에 하드코딩하고 서버가 보내는 oldDiscount 를 아예 안 읽는다. 견적 계열은 old_rate 입력칸을 두었지만 sumOld(estimate-app:7577)만 0.5 로 남아 합계가 어긋난다. 적요는 또 별개로 '(50% DC)'(종합견적서:9305) 또는 CONFIG 기반(estimate-app:9609).

[14] 적요 배치는 '금액 계산' 이 아니라 '빈 칸 찾기' 알고리즘이다 — 전역DC는 섹션 내 remarks 가 빈 첫 행, 없으면 섹션 첫 행에 ' / ' 로 병합(estimate-app:15752-15770). 주소가 들어간 행에는 절대 안 붙인다. 고정DC 는 직전 행과 같은 값이면 생략(15846). 주문 GAS 는 아예 다른 규칙 — 전역DC 를 **무조건 index 1 행**에 넣고 행이 1개면 생략(Code.js:2084). 같은 데이터로 만든 전표의 적요가 견적/주문에서 다르다.

[15] 서버가 적요를 만드는 쪽과 안 만드는 쪽이 갈린다 — 주문 GAS 는 sendOrderFromUi 안에서 전역DC/고정DC/세트DC 를 조립한다(거래처 발송 주문서 Code.js:2152-2182). 견적 GAS/BE 는 프런트가 만든 dcInfo·REMARKS 를 그대로 통과시킨다(종합견적서 Code.js:1889/1901, lib/code.js:2396). DC 로직의 소재지가 다르다.

[16] 세트 구성품에 부모의 DC 가 복사된다 — buildSendRows 에서 SET 행 전개 시 모든 구성품에 세트 본행의 fixedDc 를 그대로 붙이고(estimate-app:9496/9509), 싱글은 정액 플래그 6개를 구성품 전부에 붙인 뒤 적요는 head 행만 사용한다(9593-9594). 즉 플래그의 '보유' 와 '표시' 가 분리돼 있다.

[17] 전송행 병합에서 할인 필드의 누산 방식이 서로 다르다 — 플래그 6종은 OR, 고정DC 는 **MAX**(estimate-app:9211-9213). 확정 모델의 SUM 누산과도, REPLACE 와도 다르다.

[18] 고정DC 파서가 두 벌이다 — parseFixedDc(estimate-app:3126)는 음수 클램프 + 0.99 상한 + % 인식, getActiveFixedDc(9419)는 `[^0-9.]` 제거 후 `v>1?v/100:v` 로 상한도 음수 처리도 없다. 전자는 단가 계산용, 후자는 적요용이라 **같은 셀 값이 계산과 표시에서 다른 비율이 될 수 있다**(예: '150%' → 계산 0.99, 적요 1.5 → '150%').

[19] 0 을 '설정 안 함' 으로 취급하는 자리가 있다 — initDcConfigFromNotion 은 homeDiscount/commDiscount 가 0 이면 무시하고 기본 45% 를 남긴다(종합견적서 Code.js:2179-2183, lib/code.js:2179-2180). 정액 6종은 0 도 반영. 즉 '0% 할인' 을 저장할 수 없다.

[20] 노션 '단위처리' select 파싱은 문자열 순서에 의존한다 — `/반올림/` 를 `/올림/` 보다 먼저 검사해야만 정상(종합견적서 Code.js:2130-2132). '반올림' 에 '올림' 이 포함되기 때문. 옵션 문자열이 바뀌면 조용히 CEIL 이 된다.

[21] 선금할인은 견적앱에만 있는 신규 할인이다 — legacy 종합견적서·주문 계열 어디에도 applyEstimateTotalAdjustments 가 없다. 그리고 '행 1개를 추가하는' 방식이라 단가에 녹는 다른 할인과 표면이 다르다(음수 단가 행 · qty 1 · 이름 '선금할인').

[22] 정액 입력칸은 값을 조용히 바꾼다 — numInp(step===1000) change 핸들러가 1~999 를 ×1000 하고 천 단위가 아니면 반올림한다(estimate-app:3083-3089). 사용자가 '5' 를 넣으면 5,000 이 되고, dc_configs 에서 온 5,500 은 6,000 으로 바뀐다(setField 가 change 이벤트를 dispatch 하므로 **거래처 DC 적용 시점에도 발동**한다 — applyCustomerDiscounts:2617).

[23] 인상 전 단가는 '할인 기준액' 을 바꾼다 — DC 를 적용하기 전에 출고가/납품가를 PRICE_INC 또는 *_INC 로 치환한다(estimate-app:2267 getBaseListPrice, order-app:2723). 게이트 방향이 소스마다 반대: 현행 order-app incActive 는 `due < 변동일 → 인상 전`, legacy 주문서는 `due >= PRICE_INC_DATE('2026-07-01') → 인상 단가`. 견적앱은 날짜가 아니라 체크박스(#chkHomeInc).

[24] 카드수수료는 할인의 반대 방향인데 같은 자리에서 처리된다 — Math.floor(total × cardFeeRate)를 수량 1 인 행 하나에 **더한다**(estimate-app:16662-16672). legacy 는 0.03 리터럴(종합견적서:16183). 절삭 대상 행 선택 로직도 거의 같아 두 조정이 같은 행에 겹칠 수 있다.

[25] 세트 단가에서 정액 할인은 기준가에만 걸린다 — `setPrice = adjustSingleSetBasePrice(s, baseL) + unitExtras`(estimate-app:5183-5185). 판넬/리모컨/자재 델타는 할인 대상이 아니다. 델타가 음수(판넬 제외 등)면 할인 후 기준가에 음수가 더해지고 최종 0 하한만 걸린다.
