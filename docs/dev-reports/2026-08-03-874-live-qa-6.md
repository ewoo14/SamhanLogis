## 1. 계정 선택 근거

게이트웨이 `http://127.0.0.1:8080`에서 동일 비밀번호 `dev_p05_pass!`로 기존 후보를 로그인한 뒤, 각 토큰으로 `GET /auth/admin/permissions/my`를 실제 호출했다. 확인 원문에서 회계 권한 항목은 다음과 같다.

```text
dev_manager:    "accounting.sales-slip.accounting": []
dev_master:     "accounting.sales-slip.accounting": ["VIEW","CREATE","UPDATE","DELETE","RESTORE","DOWNLOAD","PRINT"]
dev_accountant: "accounting.sales-slip.accounting": ["VIEW","CREATE","UPDATE","DELETE"]
dev_staff:      "accounting.sales-slip.accounting": []
dev_sales:      "accounting.sales-slip.accounting": []
dev_warehouse:  "accounting.sales-slip.accounting": []
```

원문 응답 형식(실응답 발췌):

```json
{"success":true,"code":"OK","message":"성공","data":{"accounting.sales-slip.accounting":["VIEW","CREATE","UPDATE","DELETE"]},"timestamp":"2026-08-03T13:05:21.572019782Z"}
```

`dev_accountant`를 선택했다. 이유는 기존 계정 중 해당 페이지에 `CREATE`와 `UPDATE`를 실제 보유한 회계 전담 계정이며, 전표 생성이 아니라 이미 준비된 전표의 회계 배분·전기만 수행하기 때문이다. 권한 DB/API를 변경하지 않았다.

## 2. 배분·전기 및 POSTED 모델축 실측

`dev_accountant`로 실 GUI에서 `2026/08/03-6` 기본 구성품 4행을 각각 100%로 배분하고 거래처 `P0-6-C002` / `(주)삼한공조시스템`, 메모 `QA-874-R6-POST-AC060`을 입력했다. 화면 계산은 공급가 `1,739,100`, 부가세 `173,910`, 합계 `1,913,010`으로 5차 준비값과 일치했다.

저장 버튼을 클릭했을 때 게이트웨이 `POST /admin/sales-slips`가 다음 원문으로 거부했다.

```text
HTTP 422
{"success":false,"code":"SAS_SOURCE_SLIP_NOT_CONFIRMED","message":"원천 전표가 확정 상태가 아닙니다 (전표=2026/08/03-6, 상태=수락)","data":null,"timestamp":"2026-08-03T13:13:45.370197294Z"}
```

준비된 출고 전표의 화면/업무 상태는 `수락(ACCEPTED)`인데 회계 배분 API는 원천 상태 `CONFIRMED`를 요구한다. 기존 전표 상태 변경, DB 직접 수정, 우회 옵션은 하지 않았다.

저장 시도 후 read-only로 `GET /admin/sales-slips?from=2026-08-03&to=2026-08-03&status=POSTED`를 호출한 결과는 다음과 같다.

```text
HTTP 200
[]
```

따라서 이번 라운드에서 생성된 `POSTED` 모델축 행 수는 **0건**이다. 배분·전기 단계가 이 계약 불일치로 차단되어 시나리오 2~5는 실행하지 않았다.

## 4. 결함

### 결함 후보 1 — 수락 출고 전표가 회계 배분 API에서 확정 원천으로 인정되지 않음

- 재현 계정: `dev_accountant` (실제 `accounting.sales-slip.accounting: [VIEW, CREATE, UPDATE, DELETE]` 확인)
- 재현 절차: 로그인 → `/accounting/sales-slips/new` → 거래처 `P0-6-C002` / `(주)삼한공조시스템` → 출고전표 `2026/08/03-6` 기본 4행을 100% 배분 → 임시저장
- 기대: 준비된 `수락 완료` 출고 전표의 회계 매출전표가 저장되고 이어서 전기 가능
- 실제: HTTP 422 `SAS_SOURCE_SLIP_NOT_CONFIRMED`, 원문은 2절에 기록
- 영향: `POSTED` 모델축 행 생성 및 시나리오 2~5 전체 진입 불가
- 비고: 이번 QA에서는 기존 데이터/권한/DB/코드를 변경하지 않았다. 화면의 `수락`과 회계 API의 `CONFIRMED` 상태 계약 불일치가 결함 후보이다.
