# #1069 S18 SOL fix 지시서 — 유휴 상태에 남는 세트 재전개 접근성 상태

## 판정

**실 사용자 경로에서 재현 가능한 결함 1건. 머지 차단.**

- **F1 — 재전개이 끝나거나 한 번도 시작되지 않은 유휴 화면에도 접근성 트리에는 `세트 구성품 반영 중` 상태가 계속 남는다.** 재현 난이도 **매우 쉬움**. 정상 SINGLE 판매전표 입력 화면을 열기만 하거나, 세트 옵션 재전개가 끝난 뒤 접근성 트리에서 `status`를 확인하면 된다. 가시 문구와 저장 차단은 해제되지만 S17이 추가한 정적 `aria-label`은 해제되지 않아 실제 상태와 반대인 처리 중 이름이 남는다.

S17 F1의 스냅샷 계열은 이번 범위에서 새 도달 결함을 찾지 못했다. 비교 필드는 `BundleExpansionSnapshot`과 `areBundleExpansionSnapshotsEqual`에 한 번만 정의되어 있고, 품목 식별자·모델 식별자/명·품목 유형·수량·단가·규격·5개 옵션을 성공·실패·재요청 판단이 공통 사용한다. 불일치 후 최신 상태가 BUNDLE이면 최신 스냅샷으로 재요청하고, 자동완성 재입력·일반 품목 교체·행 삭제처럼 BUNDLE이 해제됐으면 폐기한다. 입력이 멈춘 뒤 새 요청은 같은 세대·스냅샷에서 종료하므로 자동 무한 재요청 경로도 재현되지 않았다.

증거 무결성:

- 검증 HEAD는 `58b94c0c43f3be7480c503cb365719d7ce03287c`이다.
- S17 지정 프론트 검증은 3파일 **100 tests passed**, 지정 백엔드 검증은 `BUILD SUCCESSFUL`이었다.
- 실제 S17 유휴 마크업과 같은 `role="status"`, 빈 `textContent`, 정적 `aria-label`을 `dom-accessibility-api.computeAccessibleName`으로 계산한 결과 `textLength=0`, `accessibleNameLength=11`, `remainsNamed=true`였다.
- 읽기 전용 실 DB에서 2026-08-06 00:00 이전 정상 `OUTBOUND DRAFT`는 **2,387행 / 2,171전표 / 2,902,645,781원**으로 재계수됐고, 현재 권위 BUNDLE 344개와 교차하는 기준 라인은 **0행**이었다. 현재 총계 **2,393행 / 2,176전표 / 2,906,079,417원**과 섞지 않았다.

## 1. 좌표

### F1 — 처리 종료 뒤에도 처리 중 접근성 이름이 상시 유지됨

- `clients/desktop/src/renderer/routes/SlipFormPage.tsx:2169-2180`
  - `role="status"` 요소는 페이지 수명 동안 상시 마운트되고 `aria-label="세트 구성품 반영 중"`도 조건 없이 항상 존재한다.
  - 가시 텍스트만 `bundleExpansionPending` 조건으로 표시되므로 재전개 종료 뒤 `textContent`는 비지만 접근성 이름은 그대로다.
- `clients/desktop/src/renderer/routes/SlipFormPage.test.tsx:1227-1250`
  - 재전개 중 접근성 이름과 종료 뒤 빈 가시 텍스트라는 현재 상태 전이를 그대로 보여 준다. 종료 뒤에도 정적 이름은 제거되지 않는다.

재현:

1. 판매전표 입력 화면을 열고 정상 SINGLE 품목을 입력하거나, 옵션이 있는 세트를 전개한 뒤 옵션을 변경한다.
2. 세트 재전개가 끝나 `세트 구성품 반영 중… 저장할 수 없습니다.` 문구가 사라지고 저장 버튼이 정상 상태로 돌아온 것을 확인한다.
3. 브라우저 접근성 트리 또는 스크린리더의 상태 요소 탐색에서 해당 `status`의 이름을 확인한다.
4. 진행 중 작업이 없는데도 `세트 구성품 반영 중`이라는 접근성 이름이 남아 실제 처리 상태와 반대로 안내되는 것을 확인한다.

## 2. 불변식

1. 세트 재전개가 실제 진행 중일 때는 저장 차단 사유가 가시 문구와 식별 가능한 접근성 상태로 함께 제공되어야 한다.
2. 재전개가 끝나거나 한 번도 시작되지 않은 상태에서는 처리 중이라는 가시·접근성 상태가 남으면 안 된다.
3. 접근성 상태 해제가 저장 차단 자체를 약화하면 안 되며, pending 중에는 옛 구성품 payload 저장이 계속 차단되어야 한다.
4. 품목 교체·자동완성 재입력·선택 해제·행 삭제 뒤에도 유휴 상태로 복귀하면 처리 중 상태와 저장 차단이 함께 해제되어야 한다.
5. 스냅샷 불일치 시 최신 BUNDLE 재요청, BUNDLE 해제 시 폐기, 연속 변경 최종 한 벌 수렴과 성공·실패 종료 계약을 유지해야 한다.
6. S2·S4·S6·S8·S10·S12·S14·S16의 폐쇄 계약, BUNDLE 부모 영속 차단, 최신 payload, 규격 승계와 `#1063` 초기 5행·마지막 행 1개 증식·trailing 빈행 저장 제외를 유지해야 한다.
7. 정상 SINGLE **2,387행 / 2,171전표 / 2,902,645,781원**의 생성·전체수정·모바일 저장 경로를 새 상태 배선이 차단하면 안 된다.

구현 수단은 지정하지 않는다. 처리 중 접근성 이름을 없애기 위해 live 안내 자체를 제거하거나, 재전개 중 저장을 허용하는 방식은 금지한다.

## 3. 양방향 RED

### RED-B — 결함 폐쇄

- 페이지 최초 진입 또는 정상 SINGLE 입력 상태에서 접근성 트리에 `세트 구성품 반영 중` 상태가 존재하면 RED.
- 옵션 재전개 중에는 접근성 이름으로 상태를 식별할 수 없거나 가시 저장 차단 문구가 없으면 RED.
- 재전개 성공·실패·timeout 뒤 가시 문구는 사라졌지만 접근성 트리에 처리 중 이름이 남으면 RED.
- pending 중 자동완성 재입력·일반 품목 교체·선택 해제·행 삭제 뒤에도 처리 중 접근성 상태가 남으면 RED.

### RED-A — 반대급부 보존

- 접근성 상태를 종료시키는 동안 재전개가 아직 진행 중인데 저장 버튼이 활성화되거나 옛 구성품 payload가 전송되면 RED.
- 처리 중 상태의 접근성 이름을 조건화한 뒤 실제 pending 시작 시 이름 또는 live 전달이 누락되면 RED.
- 스냅샷 불일치인데 최신 BUNDLE 재요청이 없거나, BUNDLE 해제 상태인데 옛 요청이 다시 구성품을 넣으면 RED.
- 연속 수량·단가·규격·옵션 변경에서 중간 응답이 적용되거나 자동 재요청이 사용자 입력 없이 계속 발행되면 RED.
- 한 행의 종료 처리가 다른 행의 유효한 pending 상태를 지우면 RED.
- 일반 SINGLE 저장, BUNDLE 부모 차단, 최신 구성품 저장 또는 `#1063` 빈행 규약이 깨지면 RED.

## 4. 범위 밖·안 본 범위

- 범위 밖: 견적·분개·이동·INBOUND 화면, 세트 마스터와 가격 배분 정책, 다른 트랙 `#1057`·`#1066`·`#1075`·`#1080`, Docker 재빌드·재배포·중지, DB 쓰기, 전체 게이트, 로컬 design-system 미빌드 `tsc`.
- 안 본 범위: DB write를 동반한 실제 전표 생성·수정, 모바일 실제 기기, Docker 배포본과 작업 트리 HEAD 동일성, 견적·분개·이동·INBOUND, 범위 밖 타 트랙 파일.
- 읽기 전용 DB 조회, 작업 트리 소스 상태 전이, 접근성 이름 계산, 지정 FE/BE 테스트만 수행했다.
