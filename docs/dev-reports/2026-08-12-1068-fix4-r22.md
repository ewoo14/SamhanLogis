# #1068 fix4 — R22 원장 정본 복원 및 exact dedup 보고

## 결론

fix3의 `POSTED 분개만 금액 정본` 경로를 되돌리고, 거래처원장 read model을 R22 전표 상태 계약에 합류시켰다. 판매 projection은 `PartnerLedgerContract.CANONICAL_SALE_STATUSES`를 직접 참조해 `Effect.SALE`로 fold에 들어간다. 분개와 projection의 중복은 금액·일자·거래처 추정 없이 `JournalSourceType.SLIP`인 분개의 `journalNo`와 projection의 `slipNo`가 완전히 같을 때만 제거한다.

따라서 분개번호와 전표번호의 채번 규칙 동일 전제는 코드상 성립한다. 수작업·역분개·개시·마감 분개는 “빈 journalNo”로 저장되는 것이 아니라 별도 journalNo와 `MANUAL/CLOSING` 등의 source type을 가진다. 전표번호가 없는 거래 문서와 exact match가 없으므로 그대로 계상해야 하며, `JournalSourceType.SLIP` guard로 같은 문자열을 쓰는 MANUAL 분개도 오인 제거하지 않는다.

## 구현

- [`PartnerLedgerReadModelService.java:168-171`](../../services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/PartnerLedgerReadModelService.java:168): 기간 판매를 공통 R22 상태 집합으로 먼저 필터링하고 canonical slip key set을 만든다.
- [`PartnerLedgerReadModelService.java:433-500`](../../services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/PartnerLedgerReadModelService.java:433): 전잔에도 동일 projection을 넣고, 전잔 journal evidence와 같은 contract로 fold한다.
- [`PartnerLedgerReadModelService.java:578-586`](../../services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/PartnerLedgerReadModelService.java:578): dedup은 `sourceRefId`가 아닌 `sourceType == SLIP && journalNo == canonical slipNo` exact match만 사용한다.
- [`PartnerLedgerReadModelService.java:647-669`](../../services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/PartnerLedgerReadModelService.java:647): `yyyy/MM/dd-N`만 전표 sequence로 해석하고, 해석되지 않는 번호는 같은 날 뒤로 보낸다.
- [`PartnerLedgerReadModelService.java:269-288`](../../services/accounting-service/src/main/java/com/samhanair/logis/accounting/service/PartnerLedgerReadModelService.java:269): canonical projection은 공통 방향성(`debit/credit`)을 부여해 화면 표시 금액과 contract fold 금액을 일치시킨다.

`Journal.sourceRefId`는 사용하지 않았다. 코드상 tax invoice UUID와 역분개 원분개 UUID가 함께 들어가는 dual-use 필드이므로 동일 금액·일자·거래처 추정 매칭도 추가하지 않았다.

## RED-A 및 화면 숫자 대조

화면이 소비하는 동일 `PartnerLedgerReadModel`을 대상으로 다음 값이 확인됐다.

| 시나리오 | 기대/실측 |
|---|---:|
| canonical projection만 존재 | sales `100`, receivable `100` |
| exact SLIP journal + projection | 해당 거래 `100` 한 번 |
| exact SLIP journal + projection + manual journal | `100 + 300 = 400` |
| CANCELED target projection | `Effect.NONE`, sales `0`, receivable `0` |
| 같은 날 sequence 1/3, target 2 | opening `100`, later `200` 및 no-slip `300` 미반영 |
| 같은 text의 MANUAL journal + projection | `100 + 100 = 200` — 오인 dedup 없음 |

① canonical projection 금액과 ④ exact dedup 후 금액은 거래처원장 read model의 `salesTotal/receivableBalance`와 동일한 값으로 검증됐다. ### fix3의 1,870 → 1,676 건수 차이

확인 결과 현재 accounting Gradle 설정에는 `includeTestsMatching`·`excludeTestsMatching` 필터가 없고 JUnit Platform만 사용한다([`services/accounting-service/build.gradle:79`](../../services/accounting-service/build.gradle:79), 루트 `build.gradle:95`). 현재 소스에는 229개 test Java 파일이 있다. fix3 보고서의 1,676은 전체 테스트 결과로 기록돼 있지만, fix2 보고서의 1,870은 “이번 fix2에서 재실행하지 않은 수치”라고 명시돼 있다. 따라서 현재 워크트리에서 설정 필터나 fix4의 테스트 삭제 원인은 확인되지 않았고, 확인 가능한 원인은 1,870이 stale baseline이었고 fix3에서 실제 전체 실행 결과 1,676이 기록된 수치라는 점이다. git 조작 금지 조건 때문에 과거 커밋 간 삭제 목록을 추적해 단정하지 않았다. 이번 `*Test` 1,075 건수는 IT를 제외한 명시적 진단 필터이므로 1,676과 직접 비교하지 않았다.
