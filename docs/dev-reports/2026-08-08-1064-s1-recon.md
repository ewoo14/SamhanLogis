# #1064 정찰 보고서 S1 — 입고 전표 lifecycle 버튼/API 전이

- 조사일: 2026-08-08
- 대상: PR #1130 / Issue #1064
- 조사 범위: 도메인 전이, 데스크톱 화면 액션, 권한 계약, 공유 `slip_db` 실데이터
- 조사 원칙: 코드·DB 모두 읽기만 수행. DB `INSERT/UPDATE/DELETE` 및 Docker 재기동 없음.

## 결론 요약

도메인 전이 그래프와 화면의 액션 코드 집합은 대체로 일치한다. 다만 `complete`의 실제 API 전이는 `PROCESSING → INSPECTING`인데 화면 라벨은 입고에서 `입고 완료`로 표시되고, 다음 `inspect`가 `INSPECTING → COMPLETED`를 수행한다. 즉 현재 핵심은 전이 코드 자체의 역전보다는 **사용자 라벨과 실제 도착 상태의 의미 불일치**, 그리고 `inspect`에만 추가로 필요한 `inbound.inspection:UPDATE` 권한이다.

실데이터에는 `INSPECTING` 1건과 `COMPLETED` 10건이 있어 표본 0이 아니다. 상태 그래프만 기준으로는 활성 입고 전표 35건 모두 `CONFIRMED`까지의 경로가 있다. 그러나 `MANAGER` 역할은 `inbound.inspection` 편집 권한이 없어 `INSPECTING → COMPLETED` 버튼/API를 실행할 수 없다. `WAREHOUSE`/`INVENTORY`/`MASTER`는 해당 권한을 가진다.


출고 전표는 `COMPLETED --ship--> SHIPPING --deliver--> DELIVERED --confirm--> CONFIRMED`를 추가로 거친다.

### A-3. 차집합

| 비교 | 도메인에만 있음 | 화면에만 있음 | 판정 |
|---|---|---|---|
| `INBOUND` 수명주기 액션 | 없음 | 없음 | 액션 코드 집합은 일치 |
| `OUTBOUND` 수명주기 액션 | 없음 | 없음 | `ship`/`deliver`는 도메인도 출고 한정 |
| `SENT`의 `PARTNER_ORDER` | 도메인 메서드에는 `cancel` 이름이 있으나 호출 시 `CONFLICT` | 화면도 `cancel` 미노출 | 화면이 도메인 가드를 선반영 |

차집합은 0이다. 다만 의미상 불일치는 있다. 화면은 `PROCESSING`의 `complete`를 입고에서 `입고 완료`로 라벨링한다(`SlipDetailPage.tsx:346-348`). 실제 API는 `POST /{id}/complete`로 `PROCESSING → INSPECTING`이다(`SlipController.java:542-552`). 다음 `inspect`가 `INSPECTING → COMPLETED`이고 화면 라벨은 `처리 완료`다(`SlipController.java:513-540`, `SlipDetailPage.tsx:332-338`).

```sql
SELECT slip_type, status, COUNT(*) AS count FROM slips WHERE is_deleted = false GROUP BY slip_type, status ORDER BY slip_type, status;
```

### B-3. 활성 입고 및 막힘 판정

```sql
SELECT status, COUNT(*) AS count FROM slips WHERE is_deleted = false AND slip_type = 'INBOUND' AND status NOT IN ('CONFIRMED','REJECTED','CANCELED') GROUP BY status ORDER BY status;
```

```text
   status   | count
------------+-------
 ACCEPTED   |     6
 COMPLETED  |    10
 DRAFT      |     8
 INSPECTING |     1
 PROCESSING |     5
 SAVED      |     3
 SENT       |     2
```

활성 입고 전표는 35건이다. 상태 그래프만으로 `CONFIRMED` 경로가 없는 활성 상태는 없으므로 **도메인 dead-end 건수는 0건**이다. `INSPECTING` 표본 1건이 있어 판정 불가가 아니다. 이 1건은 `inspect` 권한을 가진 사용자에게는 실제 검수 완료 후보이며, `MANAGER`처럼 `inbound.inspection:UPDATE`가 없는 사용자에게는 GUI/API 모두 막힌다.

보조 확인:

```sql
SELECT status, COUNT(*) AS partnerless_count FROM slips WHERE is_deleted = false AND slip_type = 'INBOUND' AND partner_id IS NULL GROUP BY status ORDER BY status;
```

결과 행 없음. 따라서 현재 실데이터에서는 거래처 필수 불변식 때문에 전이가 막힌 표본도 확인되지 않았다.

## C. 출고 대조

출고와 입고 모두 `PROCESSING → INSPECTING → COMPLETED`까지는 같은 도메인/화면 액션 구조다. 갈림은 `COMPLETED` 이후다.

| 유형 | `COMPLETED` 이후 도메인 | 화면 버튼 | 필요한 후속 조작 |
|---|---|---|---|
| 입고 | `confirm` → `CONFIRMED` | `확정` | 1회 |
| 출고 | `ship` → `SHIPPING` → `deliver` → `DELIVERED` → `confirm` | `배송 시작` → `배송 완료` → `확정` | 3회 |

근거: 도메인 `Slip.java:1198-1242`, API `SlipController.java:554-590`, 화면 `SlipDetailPage.tsx:306-311`.

따라서 출고가 GUI로 끝까지 가는 구조인지 여부와 입고의 `INSPECTING` 진입 후 완료 여부는 같은 층위가 아니다. 출고/입고 모두 상태 코드 집합은 맞지만, 입고는 `inspect` 한 단계에 추가 권한이 있어 역할에 따라 GUI 완료 가능 여부가 갈린다. 출고는 `inspect`부터 후속 `ship/deliver/confirm`까지 별도 출고 검수 capability 예외가 있다(`SlipDetailPage.tsx:1294-1304`, `SlipController.java:531-535`, `:561-573`).

## D. 권한 축

### D-1. 전이별 서버 권한

| 액션 | 입고 서버 권한 | 서버 근거 |
|---|---|---|
| `save`, `send` | `purchases.slip.edit:UPDATE` | `SlipController.java:465-488`의 동적 `checkSlipMutationPermission` |
| `accept`, `process`, `complete` | `slip.transfer.process:UPDATE` | `SlipController.java:497-510`, `:548-551` |
| `inspect` | `slip.transfer.process:UPDATE` + `inbound.inspection:UPDATE` | `SlipController.java:525-539` |
| `confirm` | `purchases.slip.edit:UPDATE` | `SlipController.java:576-589`의 INBOUND 분기 |
| `reject` | `slip.reject:UPDATE` | `SlipController.java:599-607` |
| `cancel` | `purchases.slip.edit:UPDATE` | `SlipController.java:615-623`의 동적 분기 |

화면도 동일한 요구사항 표를 사용한다(`SlipDetailPage.tsx:1245-1281`). 특히 입고 `inspect`는 두 권한을 모두 요구하고(`:1272-1275`), `canAccessSlipAction`이 이를 AND로 판정한다(`:1287-1305`). 따라서 버튼이 비활성화된 경우 `inspect`는 전이 정의 누락이 아니라 권한 부족일 수 있다.

### D-2. 역할별 차이

권한 seed 근거:

- `inbound.inspection`: `MASTER` 편집 허용 `V7__add_role_page_permissions.sql:75`, `MANAGER`는 조회만 `:89`, `WAREHOUSE` 편집 허용 `:131`, `INVENTORY` 편집 허용 `:159`.
- `slip.transfer.process`: `MASTER`, `MANAGER`, `WAREHOUSE`, `INVENTORY` 편집 허용 `V36__seed_sp_d6_6_slip_page_codes.sql:83-87`.
- `purchases.slip.edit`: `MASTER`, `MANAGER`, `WAREHOUSE` 편집 허용 `V36...sql:54-57`.

그러므로 `MANAGER`는 입고 전표를 `PROCESSING`까지 진행하고 `COMPLETED`를 확인할 수 있어도, `INSPECTING → COMPLETED`인 `inspect`는 `inbound.inspection:UPDATE` 부재로 실행할 수 없다. `WAREHOUSE`/`INVENTORY`/`MASTER`는 해당 권한 조합을 만족한다. 이 차이는 API 전이 정의가 아니라 권한 설계/역할 배정 문제다.

## 선택지 — 판단 요청

아래 중 선택해 주십시오. 정찰 단계에서는 선택하지 않는다.

1. **A안: 전이 의미를 유지하고 화면 라벨/안내만 정합화**
   - `complete`를 “검수 대기”로, `inspect`를 “입고 완료(검수 완료)”로 명확히 표기.
   - `MANAGER`가 입고를 끝내야 하는 역할이면 `inbound.inspection:UPDATE`를 권한 정책으로 추가.
   - 장점: 현재 도메인 전이와 API 계약을 보존.

2. **B안: 입고 전용 완료 전이를 단축**
   - 입고 `complete`가 `PROCESSING → COMPLETED`가 되도록 도메인/API/화면 계약을 재설계.
   - 장점: 기존 “입고 완료” 버튼 의미와 일치.
   - 주의: `INSPECTING` 검수 단계 및 `inbound.inspection` 권한을 입고에서 어떻게 보존할지 별도 결정 필요.

3. **C안: 권한만 먼저 정리하고 실 화면 회귀 확인**
   - 도메인/버튼은 유지하고, 실제 입고 담당 역할에 `slip.transfer.process:UPDATE`와 `inbound.inspection:UPDATE`가 모두 있는지 운영 권한을 확인.
   - 장점: 코드 변경 없이 현재 1건 `INSPECTING` 표본으로 GUI 완료 가능 여부를 가를 수 있음.
   - 주의: 라벨의 의미 불일치는 남는다.
