## 1. 결론

SOL이 제기한 S3 차단 결함 R-1/R-2를 수정했다.

- R-1: Axios `config.params`를 읽지 않던 정산서 및 같은 계열 6개 검색 mock을 보완했다.
- R-2: 표시·링크 결정 기준을 `attachmentType`에서 `refDocType` 우선 맵으로 옮겼다.
- 기존 6종의 인쇄 라벨, 상세 라벨, 상세 링크는 조사 결과를 그대로 맵에 고정했다.
- 정산서는 `영업수수료 정산서`로 표시하며, S4 화면이 아직 없으므로 번호를 `href="#"`로 만들지 않고 텍스트로 렌더한다.
- 격리된 Vite mock 서버에서 실제 Chromium-1217 Playwright가 검색·선택·상세·인쇄를 모두 통과했다.

## 2. R-1 RED 원문과 원인

### 최초 재현

실패한 targeted test:

```text
npx vitest run src/renderer/api/mock.test.ts -t "그룹웨어 문서 참조 검색 mock transport params 계약" --reporter=verbose
```

결과: URL query 케이스 1건만 통과하고 `config.params` 케이스 6건이 실패했다.

```text
6 failed, 1 passed
각 config.params 호출의 반환 data = []
정산서 기대값: settlementNo === "2026/08/11-1"
```

원인은 `getMockResponse()`가 URL 문자열만 handler에 전달하고 Axios의 `config.params`를 query로 해석하지 않았기 때문이다. 실제 `searchByType()`는 다음 형태로 호출하므로 URL에 query가 없는 mock 호출은 항상 빈 검색어로 처리됐다.

```ts
getMockResponse({
  method: 'GET',
  url: '/admin/accounting/sales-commission-settlements/search',
  params: { q: '2026/08/11', limit: 10 },
})
```

### 수정 방식

`clients/desktop/src/renderer/api/mock.ts:224`에 `mockQueryParams(config)`를 추가했다. URL query를 보존하면서 `config.params`를 읽고, 같은 키는 Axios params를 우선한다. `URLSearchParams`, 일반 object, 배열 반복 query, null/undefined 제외를 처리한다.

중요하게도 요청 URL 자체를 전역으로 변형하지 않았다. 이 mock에는 query suffix에 의존하는 legacy 상세 route와 POST import route가 있어 전역 URL 변형을 먼저 시도했을 때 해당 회귀가 발생했다.

## 4. 기존 6종 라벨·링크 전수 조사표

다음 값은 수정 전 화면·인쇄 소비자와 기존 테스트/fixture를 대조해 기록한 값이다. 맵에도 동일한 문자열과 href 계약을 넣었으며, 기존 6종의 값은 변경하지 않았다.

| `refDocType` | 기존 인쇄 라벨 | 기존 상세 라벨 | 기존 상세 링크 |
|---|---|---|---|
| `OUTBOUND_SLIP` | `전표 참조` | `출고전표` | `#/sales?slipNo={refDocNo 또는 refSlipNo}` |
| `INBOUND_SLIP` | `전표 참조` | `입고전표` | `#/purchases?slipNo={refDocNo 또는 refSlipNo}` |
| `JOURNAL` | `전표 참조` | `분개장` | `#/accounting/journals?journalNo={refDocNo}` |
| `TAX_INVOICE` | `전표 참조` | `세금계산서` | `#/accounting/tax-invoices?taxInvoiceNo={refDocNo}` |
| `STATEMENT` | `전표 참조` | `거래명세서` | `#/accounting/statement-batch?statementNo={refDocNo}` |
| `PARTNER_LEDGER` | `거래처원장 참조` | `거래처원장` | `#/accounting/ledgers?partnerCode={refPartnerCode}&period={refPeriod}` |

구현 위치: `clients/desktop/src/renderer/api/approvalAttachmentPresentation.ts`.

`refDocType`이 존재하면 위 맵을 우선 사용한다. `refDocType=null`인 legacy 첨부만 기존 `attachmentType`/`refSlipType` fallback을 사용한다. 따라서 기존 `SLIP_REF`, `PARTNER_LEDGER_REF`, `FILE` 저장 분류와 기존 직접 생성 경로는 유지된다.

## 5. R-2 RED 원문과 수정 결과

### 최초 실패

정산서 fixture를 소비자에 넣은 RED에서 다음 계약이 깨졌다.

```text
approvalRenderModel: expected "영업수수료 정산서", received "전표 참조"
FrozenApprovalDocLegacy: settlement label was not rendered as "영업수수료 정산서"
GroupwareApprovalDetailPage: settlement number rendered as <a href="#">2026/08/11-1</a>
```

원인은 `SLIP_REF`의 거친 transport 분류만 보고 인쇄 라벨을 정하고, 상세 링크 함수에 `SALES_COMMISSION_SETTLEMENT` 분기가 없었기 때문이다.

### 수정 결과

- 신규 인쇄 모델과 frozen 인쇄 fallback이 `approvalAttachmentPrintLabel()`을 사용한다.
- 상세가 `resolveApprovalAttachmentDocType()` → `approvalAttachmentDetailLabel()`을 사용한다.
- `SALES_COMMISSION_SETTLEMENT`은 인쇄·상세 모두 `영업수수료 정산서`로 표시한다.
- S4 정산서 화면/연결 route는 이번 범위에 만들지 않는다. 따라서 정산서 번호는 `<span>` 텍스트이며 `href="#"`가 없다.
- FILE 첨부는 기존 파일 표시를 유지한다.

## 6. 새 조합 검토표

| 축 | 확인한 조합 | 결과 |
|---|---|---|
| transport | Axios `config.params` / URL query string | 둘 다 검색 가능 |
| 검색 유형 | outbound, inbound, journal, tax invoice, statement, partner ledger, settlement | 6개 기존 handler와 정산서 handler 모두 params 사용 |
| 검색어 | 빈 값 / 일반 문자열 / `2026/08/11` slash 값 | 빈 값은 0건, 정산서 slash 검색은 1건 |
| limit | mock 공통 clamp: 0 이하→1, 1, 10, 20, 21 이상→20 | 기존 계약 유지 |
| 렌더 | 7개 `refDocType` × detail/current print/frozen print | 기존 6종 값 불변, 정산서 신규 라벨 |
| compatibility | `refDocType` 있음 / legacy null / `refDocNo` / partner ledger 식별자 / FILE | refDocType 우선, null만 legacy fallback |
| S4 경계 | 정산서 상세 route 없음 | dead link 대신 plain text |
| mock isolation | `VITE_API_BASE_URL=http://127.0.0.1:1` | 실 API 누출 0건 |

`%`, `_`, `\` query는 query parser가 URLSearchParams 값으로 읽어들이며 mock 문자열 contains 검색 계약을 유지한다. 이번 변경의 회귀 핵심인 slash 값은 실제 fixture와 Playwright로 검증했다.
