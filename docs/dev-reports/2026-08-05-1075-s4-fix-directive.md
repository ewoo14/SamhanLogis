## 1. 좌표와 재현 증거

### 결함 1 — 협업 연결된 편집 견적에서 품목 확정 경로가 영구 차단된다

- 코드 좌표

  - `clients/desktop/src/renderer/routes/EstimateFormPage.tsx:1927-1948` — 모바일 품목 `ProductAutocomplete`가 `coeditActive`에서 비활성.
  - `clients/desktop/src/renderer/routes/EstimateFormPage.tsx:2014-2035` — 데스크톱 품목 `ProductAutocomplete`도 같은 조건에서 비활성.
  - 대조 계약: 같은 파일 `1709-1731`은 협업 중 거래처 재선택을 막으면 저장 데드락이 된다는 기존 결함을 명시하고, 연결 중에만 잠근다.
- 실 사용자 재현
  1. mock 사용자 `MASTER`로 `/sales/estimates/est-001/edit` 진입.
  2. 편집 가능한 견적과 협업 provider 연결 완료를 기다림.
  3. 라인 1 모델명 combobox를 클릭하고 부분검색어 `AJ` 입력 시도.
  4. 실제 측정값: `modelDisabled=true`, `fill('AJ')` timeout. 같은 시점 `saveDisabled=false`, 확정행 2개와 trailing 빈행 1개는 보인다.
  5. 따라서 기존 라인을 그대로 임시저장하는 버튼은 열려 있어도, 품목 교체 또는 trailing 빈행의 품목 확정은 시작조차 못 한다. 선택 후 임시저장과 발송(정식 저장) 경로 모두 도달 불가다.
- 범위 대조
  - 신규 견적에서는 후보의 `id → productId`, 모델명·품목명·규격·단가가 create payload까지 보존됨을 확인했다. S2 결함 1은 **신규 임시저장 경로에 한해서** 닫혔다.
  - 판매전표의 공용 `ProductAutocomplete` 사용자 경로는 부분검색·복수 후보 모달·단일 후보 자동확정·단가·멀티라인·UUID 비노출이 유지된다. 이번 결함은 공용 컴포넌트가 아니라 견적 편집 호출부의 차단 조건에서 발생한다.

### 증거 무결성 — `#1063` 편집 회귀 울타리가 사라졌다

- `clients/desktop/playwright/1062-line-input-ux/1062-line-input-ux.spec.ts:41-68`은 S3에서 기존 `/sales/estimates/est-001/edit` 시나리오를 `/sales/estimates/new`로 교체했다.
- 교체 과정에서 다음 단정이 사라졌다: 편집 진입 직후 0·1·2번 라인 존재, 기존 trailing 빈행에 품목 확정, 다음 3번 빈행 생성, `data-price-source` 행 4개 유지.
- `clients/desktop/src/renderer/routes/EstimateFormPage.coedit.test.tsx:96-151`의 `ProductAutocomplete` mock은 호출부의 `disabled`를 입력에 전달하지 않는다. 그래서 provider가 성공한 편집 렌더에서도 실제 combobox 잠금을 관측하지 못한다.
- 신규 후보 모달 시나리오는 유지하되, 위 편집 계약을 대체물로 취급하면 안 된다.

## 2. 불변식

- `QUOTE_DRAFT` 또는 `QUOTE_SENT`이고 `estimates.list UPDATE` 권한이 있는 사용자는 협업 provider 연결 완료 후에도 기존 라인의 품목 교체와 trailing 빈행의 품목 확정을 수행할 수 있어야 한다.
- 협업 중 구조 잠금은 라인 추가·삭제·순서 같은 **라인 구조**에 한정한다. 품목 확정은 모델명·품목명·규격·단가·`productId`를 같은 라인 identity에 동기화하는 **라인 내용 편집**이다.
- 후보 확정 후 모델명·품목명·규격·단가가 UI와 coedit 문서에 남고, 임시저장은 update payload까지, 발송은 선행 update payload와 send 호출까지 동일 값을 보존해야 한다.
- provider 연결 중(`coeditPending`)의 이중 입력 차단, 읽기 전용 status 차단, 가격 조회 중 저장·발송 차단, coedit 라인 구조 잠금, 자동 빈행, 버전 복원 fence, 가격기억, `참조 조회`, UUID 비노출 계약은 유지한다.
- 수단 금지: 협업 기능을 끄거나 provider 실패 폴백으로 우회하지 말 것. 부분검색을 정확 모델명 lookup으로 되돌리지 말 것. 품목 입력을 숨기거나 테스트 단정을 약화해 통과시키지 말 것. 판매전표 공용 컴포넌트의 기존 계약을 변경하지 말 것.

## 3. 양방향 RED

### RED-A — 편집 견적 후보 확정과 임시저장

- provider 생성이 성공한 편집 가능한 견적을 렌더한다.
- 협업 연결 완료 뒤 모델명 combobox가 활성인지 단정한다.
- trailing 빈행에서 부분검색으로 2개 이상 후보 모달을 열고 두 번째 후보를 확정한다.
- 선택 후보의 `id`, 모델명, 품목명, 규격, 단가가 각각 `productId`, 라인 표시값, coedit item에 남는지 단정한다.
- 다음 trailing 빈행이 정확히 하나 생기고, 임시저장 시 `updateEstimate` payload에 선택값이 남는지 단정한다.
- **반대급부:** provider가 아직 pending인 동안에는 combobox와 저장이 계속 차단되어야 하며 검색 API도 호출되면 안 된다. provider 연결 완료 후에도 라인 삭제는 구조 잠금 상태를 유지해야 한다.

### RED-B — 편집 견적 후보 확정과 발송

- provider가 연결된 `QUOTE_DRAFT` 편집 견적에서 기존 품목을 다른 후보로 교체한 뒤 발송한다.
- confirm 승인 후 `updateEstimate`가 새 `productId`·모델명·품목명·규격·단가를 먼저 받고, 성공 뒤 `sendEstimate`가 호출되는지 단정한다.
- **반대급부:** 후보 확정 뒤 가격기억/카탈로그 조회가 아직 진행 중이거나 단가가 미해결이면 임시저장과 발송 모두 계속 차단되어야 하고, 옛 품목의 `productId` 또는 단가로 update/send가 진행되면 안 된다.

### 회귀 울타리 복구

- `1062-line-input-ux.spec.ts`에 신규 견적 후보 모달 시나리오를 유지한다.
- 별도 편집 시나리오로 기존 `#1063` 계약을 복구한다: 편집 진입 시 확정행+trailing 빈행, 협업 연결 후 combobox 활성, 후보 확정 후 다음 빈행 정확히 1개, 전체 행 수와 가격 source 유지.
- coedit 단위 테스트의 `ProductAutocomplete` mock이 실제 `disabled` 계약을 반영하도록 하여 편집 잠금을 관측 가능하게 한다.
