# 🚨 **QA 라운드가 공유 데이터에 잔재를 남긴다** — 하룻밤에 네 건

라이브QA 는 실 화면·실 API 로 데이터를 만든다(그게 규칙이다). 그런데 그 데이터가 **공유 DB 에 남아** 다음 라운드·다른 트랙에서 다른 의미로 읽힌다.

## 2026-08-06 하룻밤에 확인된 네 건

| 잔재 | 어떻게 오해됐나 |
|---|---|
| `partner_product_price_memory` 에 `561,600` | fix 후 QA 가 그 값을 읽고 **BLOCK** 을 냈다 → [[feedback_defective_round_poisons_db_for_next_round]] |
| 창고 `QA-1039-SANGIL`·`QA-1039-CHOWOL`(08-04) | 같은 실물 창고가 **중복 2쌍**으로 존재 |
| 창고 코드 `2`·`00003`(08-05 S18) | `#1052` 가 **"UUID 대응 불일치 2건"** 으로 측정 → 실은 placeholder 설정 ↔ QA 행 충돌 |
| `QA797` 품목 3개 + 최근단가 8행 + `9,999,999,999,999원` 경계값 | `#1051` 이 **복구 대상 549전표+63견적**으로 집계 → 되살리면 QA 산물이 실 데이터가 된다 |

## 🔑 가르는 법 — 행의 **생성 시각·생성자·이름**

```sql
SELECT created_at, created_by, <식별 컬럼> FROM <테이블> ORDER BY created_at DESC;
```

- **우리 라운드 시각과 일치하면 우리가 만든 것**이다.
- 이름에 `QA`·라운드 번호(`S18`·`QA-1039`·`QA797`)가 박혀 있으면 결정적이다. **QA 데이터에 라운드 식별자를 넣게 하는 것이 그래서 값지다.**
- `created_by` 가 QA 계정 하나로 몰려 있으면 신호다.

## 🔑 판정 — 잔재인가 결함인가

1. **의도된 동작을 코드로 확정**한다(`파일:줄`).
2. **잔재가 없는 조합**으로 재검증한다 — 기억 없는 partner+product, 코드 행이 없는 창고 등.
3. **사용자가 정상 경로로 교정 가능한가.**

셋 다 정상이면 **게이트 ①에 세지 않는다.** 다만 *"잔재이니 무시"* 가 아니라 **그 사실을 PR 에 근거와 함께 남긴다** — 다음 라운드가 같은 것을 또 발견한다.

## 🔑 병렬 트랙의 측정 위생

`#1051` D2 도중 **다른 트랙이 견적을 추가해 `estimate_lines` 가 2,058→2,060 으로 변했다.** 진단자가 그 사실과 최종 측정 시각을 보고서에 적었고, 그게 옳다.

- 병렬 트랙이 같은 DB 를 쓰는 동안 낸 수치는 **측정 시각과 함께** 읽는다.
- 진단 브리핑에 *"측정 중 값이 변하면 그 사실과 최종 측정 시각을 적으라"* 를 넣는다.

## 🚫 하지 말 것

- **잔재를 지워서 "해결"** 하지 말 것. 증거가 사라지고, 같은 QA 가 또 만든다.
- 잔재를 **복구 대상으로 세지** 말 것. `#1051` 의 `QA797` 은 되살리면 QA 산물이 실 데이터처럼 살아나고 경계값까지 딸려 온다.
