🚨 **fix 가 무언가를 "차단하지 않고 남기기로" 결정하면, 그 남은 상태가 다음 라운드의 결함 표면이 된다.**

## 실측 — `#1131` R10 → R17 (여덟 라운드)

```text
R10  정상 견적 화면이 keyless 다중 인스턴스를 **재생성**      → 생성 경로를 정책으로 차단
R11  CI 5실패 — **복원 경로**가 그 정책을 안 지난다            ← R10 이 생성만 막았다
R13  복원이 인스턴스 경계를 **행 순서로 추정**                 ← R12 공통 정책이 연속 배치를 가정
R14  duplicate signature 는 **차단하지 않고 keyless + WARN**   ← PM 지시: 복원을 막으면 안 되므로
R15  🚨 그 **keyless 로 남은 상태**에서 head 삭제가 보호를 우회 ← R14 가 남긴 상태 표면
R17  결함 0
```

🔑 **결함을 못 찾아서 라운드가 는 게 아니다.** 결함은 매 라운드 첫 시도에 나왔다.
**직전 fix 가 만든 표면**을 다음 라운드가 발견한 것이다.

## 그래서 무엇을 할 것인가

```text
✅ fix 가 "막지 않고 남기는 상태" 를 만들면, **그 상태에서 가능한 조작을 그 라운드에 열거**하라
   R14 에서 "keyless 로 남긴다" 를 정했을 때
   "그럼 keyless 상태에서 삭제·수량0·교체를 하면?" 을 같은 라운드에 물었어야 했다
✅ fix 지시에 **"이 fix 가 새로 가능하게 만드는 상태·조작"** 절을 넣는다
✅ 계열 전수표(O/X)를 요구한다 — 경로별로 "이 보호가 걸리는가"
   (실측: #1166 ECOUNT 복원 · #1168 mock 6개 · #1131 0-head 경로가 전수표로 추가 발견됐다)
```

## 🚩 함께 나온 두 가지

### ① PM 불변식이 너무 넓으면 기존 정본 테스트와 충돌한다

```text
PM 1차  "0-head 계보는 **어떤 경로로도** 저장되지 않는다"
실측    head 품목 교체 시 **계보를 떼는 것은 의도된 동작**이었다 (정본 테스트가 단정)
PM 2차  "**깨진 계보를 남기지 않는다**" 로 좁히고
        기존 lineage-drop 경로와 **같은 의미론**을 재사용하게 했다
⟹ 새 방어를 만드는 것보다 **이미 있는 동작에 합류시키는 것**이 낫다.
   기존 IT 와 싸우지 않는다
```

### ② 증상 서술이 틀려도 결함은 실재할 수 있다

```text
PM/SOL  "삭제 후 다음 편집이 HTTP 400"
실측     새 lineId 기준 재현에서는 **삭제 200 → 편집 200**
실제     **200 저장 후 깨진 계보가 남는 것**이 결함이었다
⟹ 구현자가 정정했고 검증자가 확인했다.
   🚨 서술이 틀렸다고 결함을 기각하지 말고, **무엇이 진짜인지 다시 확정**하라.
      그리고 그 라운드의 다른 단정도 재확인하라
```
