# 🚨 fix 브리핑에 **반대급부**를 안 걸면 그것을 잃는다 (2026-08-09 · 하루 세 번)

라운드가 길어진 트랙들을 보니 **결함이 계속 나온 게 아니라 PM 지시가 새 표면을 만든 것**이었다.

| 트랙 | PM 이 건 것 | 구현자가 만든 새 결함 |
|---|---|---|
| `#1152` R6 | *"1만 호출을 없애라"* | `size: 50` 이 되어 **찾던 품목을 못 찾게** 됨 (`A` 검색 2,686건 중 50건만, `AP110BAPPBH2S` 밖) |
| `#1127` R6 | *"카운터 계열을 한 규칙으로 닫아라"* | 개명이 **화면·로그·Javadoc** 을 깨뜨림 (실제 3건이 화면에 0건) |
| `#1130` R5 | *"전권 규칙을 단정하는 테스트를 만들어라"* | **mock 만** 지키고 백엔드는 안 지킴 (컨트롤러에서 PRINT 빼도 GREEN) |

**셋 다 구현자는 지시를 정확히 따랐다.** 지시에 반대급부가 없었다.

## 🚨 2026-08-15 증보 — **fix 브리핑에만 걸어 두면 재구성에서 그대로 당한다**

`#1219` 일마감. 개발책임자가 *"레거시처럼 표시"* · *"3개로 나뉜 걸 하나로 통일"* 이라고 했고, PM 이 그대로 옮겼다. 결과:

⟹ 사용자가 **일마감을 실행할 수 없게** 됐고, 일마감이 없으면 **매출전표도 못 만든다**(`requireLockedClosing` 게이트).

```text
🔑 이건 fix 가 아니라 "화면을 이렇게 바꿔라" 였다
   그래서 PM 이 이 규칙을 적용할 생각을 안 했다
🔑 개발책임자가 "3개를 하나로" 라고 한 것은 매출/매입/통합 3분할이었지

```

**화면·모듈을 다시 만드는 지시에서 표적은 "그 화면이 지금 하는 일 전수" 다.**
```text
✅ 브리핑 전에 PM 이 먼저 센다
     기존 파일 줄 수 · 버튼/액션 목록 · 그 화면을 거는 테스트 목록
   그리고 "이건 남는다" 를 명시한다
🚩 줄 수가 크게 줄면(1,217 → 285) 그것 자체가 신호다. 커밋 전에 세라
```

## 🔑 왜 이 저장소의 기존 규칙만으로 부족했나

[[feedback_bidirectional_red_for_fix]] 가 이미 *"RED-A/RED-B 를 각각 고정하고 동시 GREEN"* 을 말한다. 그런데 **RED-B 를 무엇으로 쓸지**가 매번 빠졌다.

```
❌  RED-B "기존 동작 불변"          ← 너무 넓어서 아무것도 안 지킨다
✅  RED-B "AP110BAPPBH2S 를 선택 모달에서 골라낼 수 있다"   ← 구체적 표적
```

🔑 **반대급부는 "무엇이 깨질 수 있나" 를 PM 이 먼저 상상해서 표적으로 적어야 한다.** 구현자는 자기가 만든 fix 의 반대편을 보지 않는다 — 그건 PM 의 일이다.

## How to apply

fix 브리핑에 이 절을 **항상** 넣는다.

```
## 🚨 이걸 고치면서 잃으면 안 되는 것
- <구체적 표적 1> — 예: "A 로 검색해 AP110BAPPBH2S 를 실제로 선택할 수 있다"
- <구체적 표적 2> — 예: "화면 라벨이 '연결 occurrence' 로 뜬다"
- 위를 각각 RED 로 고정하고 **동시 GREEN** 을 원문으로 보일 것
```

표적을 고르는 질문 셋:
```
① 이 fix 가 좁히는 것은 무엇인가        → 좁혀서 빠지는 쪽이 표적
② 이 fix 가 이름·구조를 바꾸는가         → 그 이름을 쓰던 소비자가 표적
③ 이 fix 가 어느 층에 들어가는가         → 다른 층(백엔드/화면/로그)이 표적
```

🚨 **"기존 동작 불변" 같은 문장은 표적이 아니다.** 그건 검증되지 않고, 검증 안 되면 안 지켜진다.

**Why:** 이 패턴은 라운드를 배로 늘린다. `#1152` 는 R6→R7, `#1127` 은 R6→R7, `#1130` 은 R5→R6 이 전부 **직전 라운드가 만든 표면을 닫는 라운드**였다. 표적을 처음부터 걸었으면 각각 한 라운드에 끝났다.
