# 🚨🚨 **라이브QA 는 마지막이 아니라 첫 라운드다** (2026-08-03 개발책임자 결정 · 25라운드 머지 0건 실측)

## 무슨 일이 있었나

하루에 **25라운드를 돌리고 머지 0건**이었다. 5트랙 전부 게이트 ①(도달 결함 0)·②(CI green)를 통과했는데 **전부 ③ 라이브QA 에서 되돌아왔다.**

QA 를 돌린 **4트랙에서 4번 다** 결함이 나왔다.

```text
#1061  재수렴 결함0  → QA 가 422 + 인쇄 미개방  → fix → QA 가 집계 공란 + 번호 변형
#1059  R13 이 V92 권한 "회수됨" 판정 → QA 에서 그 계정이 화면에 실제 접근
#1045  재수렴 결함0  → QA 가 적요 미저장
#1057  재수렴 결함0  → QA 가 main 선재 결함(mock 이 덮고 있던 것)
```

## 🔑 코드 재수렴이 부실한 게 아니다 — 안 보이는 층이 실재한다

가장 선명한 증거가 `#1059` 다. R13 은 DB 행을 정확히 세어 *"V92 대상 41행만 회수, 다른 화면 6,186행 영향 0"* 을 확인했고 **그건 사실이었다.** 행은 정확히 지워졌다. **화면이 그 행을 안 볼 뿐이었다** — 메뉴 노출·라우트 가드가 다른 경로로 판정하고 있었다.

`#1061` R12 SOL 은 결함 0 을 내면서 판정문에 *"브라우저 GUI 클릭은 실행하지 않았다"* 를 **스스로 명시**했다. 그 한 줄이 정확히 그 다음 QA 가 잡은 422 결함이었다.

**DB·코드로는 증명할 수 없는 것이 있다.** *"권한이 회수됐다"* 는 DB 행으로 증명되지 않고, *"목록에 뜬다"* 는 클릭해 봐야 안다.

## 왜 순서가 문제인가

코드 라운드를 5~7번 돌린 뒤 QA 를 하면, **QA 가 잡은 결함이 그 라운드들을 통째로 무효화**한다. fix → 재수렴 → 재배포 → 재QA 로 사이클이 다시 돈다. `#1061` 은 7라운드를 돌고도 QA 를 못 넘겼다.

## 📌 개발책임자 결정 (2026-08-03)

> **전부 완주 — 다만 QA 를 앞으로.**

**새 순서** — 구현 → **라이브QA 1회** → 적대검증(QA 결과 포함) → fix → 재수렴 → 머지 전 QA 재실시.

**단축하는 것은 검증 깊이가 아니라 순서다.** 라이브QA·RED-first·두 검증 스테이지는 그대로 둔다.

## 함께 지킬 것 — 오늘 QA 를 낭비시킨 3가지

1. 🚨 **QA 전에 발화 조건을 세라.** 오늘 **3번**(`#1061` 기간에 라인 55건 · `#1045` 8모드 표본 0건 · `#1057` `model_rows=0`) 데이터가 없어 미실시로 끝났다. SQL 한 줄이면 막는다. **없으면 실 API 경로로 throwaway 를 만들게 하고, DB 직접 INSERT 는 금지.**
2. 🚨 **PM 브리핑 오류가 QA 한 사이클을 통째로 버린다.** `#1061` 한 PR 에서만 3건 — ①화면 표시 코드를 API 코드로 줌 ②라인 없는 기간 지정 ③*"전표번호 미노출"* 이라는 없는 기준. **기준은 실 DB·기존 결정에서 먼저 확인하고 근거를 브리핑에 인용할 것.**
3. 🚨 **mock 이 덮는 표면을 목록화하라.** `#1057` 을 막은 선재 결함이 그것이었다 — 클라이언트가 게이트웨이 비노출 경로(`/internal/**`)를 부르는데 `isMockMode()` 분기가 `MOCK_SOURCE_SLIPS` 를 돌려줘 mock 스위트는 **항상 통과**했다.
