# 🚨🚨 검증이 **사용자 경로가 아닌 것**을 잰 경우

## 실측 — `#1090` 단가·할인 축

같은 품목 `AC023BN1DBC1` 인데 두 축이 달랐다.

```
재수렴2 (API·DB 축)   266,800원   "전수 대조 불일치 0건 · 머지 가능"
라이브QA (화면 축)     316,800원   "머지 불가"
```

규명해 보니 —

> **재수렴2 의 `266,800원` 은 API 응답값이 아니라 `calculateSlipDiscount()` 에 정액 DC 50,000원을 직접 넣은 계산 결과였다.**
> 견적 화면은 **거래처 DC API 를 호출하지 않고** `sellingPrice` 와 고정 할인율만 쓴다.

즉 재수렴은 **존재하는 함수가 올바르게 계산하는지**를 쟀고, 화면은 **그 함수를 부르지도 않았다.**

## 🔑 왜 위험한가

재수렴2 는 이렇게 보고했다.

```
V42 직후        분류 218행 + 미분류 113행  불일치 0
분류 저장 후     98품목 · 2,781조합         불일치 0
분류 되돌림 후   이중 적용 0
전체 Java 1,400건 · Desktop 35/35
```

**숫자가 많고 전수이고 전부 0 이라 통과처럼 보인다.** 그런데 그 전수가 **사용자가 안 밟는 경로 위의 전수**였다. 화면을 안 봤으면 그대로 머지됐을 것이다.

## How to apply

**금액·수량처럼 사용자가 보는 값을 바꾸는 트랙은 반드시 화면으로도 잰다**
> 🔑 DB·API 계산 대조만으로 끝내지 마십시오. **사용자가 화면에서 보는 숫자**로 전/후를 대조하십시오.

**검증 브리핑에 "무엇을 통해 쟀는지" 를 요구한다**
> 값을 어떤 경로로 얻었는지 적으십시오 — 화면이 부르는 API 인지, 계산 함수를 직접 부른 것인지. **화면이 실제로 부르는 요청을 네트워크로 전수 관찰**해 대조하십시오.

**두 축이 다른 값을 내면 그 자체가 발견이다**
`#1090` 의 경우 규명 결과 **"견적 화면이 거래처 DC API 를 아예 호출하지 않는다"** 는 **기존 결함**이 드러났다. 축이 어긋난 것을 "어느 쪽이 맞나" 로만 보지 말고 **왜 다른지** 를 물어야 한다.
