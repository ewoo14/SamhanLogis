# fix 는 결함을 막는 게 아니라 **정상 경로를 막는다** (2026-07-30 · 하루에 4트랙)

결함을 고치면 그 fix 가 **막는 방향**으로 작동하고, 그 차단이 **정상 사용자 경로까지** 덮는다. 하루에 네 트랙에서 같은 형태로 나왔다.

| 트랙 | 원 결함 | fix 가 만든 것 |
|---|---|---|
| **#984** | 삭제 UUID 가 주문 160건에 박힘 | guard 가 **정상 주문 3,489건 전부 거부**(`PENDING 26,055행/3,489주문 → 3,489/3,489`). 원인=주문의 `품목명[규격]` 라벨 vs exact 품목코드 alias 계약 불일치 |
| **#996** | target catalog 부재 시 경고만 하고 전송 허용 | reset 뒤 누락 Map 이 **S-03 무관 25,000원 정상주문 차단** · 합법 십진 계수를 브라우저가 오판해 **4,527,600원 주문 전체 거부** |
| **#994** | 대상자 알림 미발행 | PM 불변식 *"이미 알림 받은 사람에게 중복 발행되지 않는다"* 가 **제거 → 재초대** 케이스를 막아 알림 누락 |
| **#993** | 날짜 버전이 감지되지 않아 영구 차단 | fix 가 **실제로는 동작 안 함**(`${env...}` 리터럴이 치환되지 않아 패키징 중단). 그 fix 의 테스트도 **로컬에서만 통과**(`app-builder-lib` 실물 require) |

## 규칙

🚨 **재수렴 브리핑의 첫 각도는 항상 "fix 가 정상 동작을 막는가" 로 시작한다.**

구체적으로 물을 것:
- 이 fix 가 **차단하는 방향**이면, **차단되면 안 되는 입력**이 무엇인가
- 그 입력을 **실 데이터에서 세어라** — "몇 건이 이제 막히는가"
- 기존에 통과하던 경로 중 **이 변경으로 통과하지 못하게 된 것**이 있는가

이 각도를 넣은 라운드에서 **네 건 모두 잡혔다.** 넣지 않았으면 전부 머지됐을 것이다.

## 함께 나온 것 — 증상과 원인의 구분

**#996** 에서 PM 이 `V29` seed 를 제거해 결함 3건이 *"동시에 소멸했다"* 고 판정했으나 반증됐다. seed 제거는 규칙이 **자동 생성**되는 경로만 막았고, **관리자 `POST` 로 같은 규칙을 만들면 결함이 그대로 재현**된다.

⟹ *"이 결함을 만드는 데이터를 없앴다"* 와 *"그 데이터가 있을 때 생기는 결함을 고쳤다"* 는 다른 주장이다. **데이터를 만드는 경로가 하나뿐인지** 먼저 확인할 것.

## 함께 나온 것 — "고쳤다" 와 "동작한다"

**#993** 은 fix 가 **패키징 단계에서 중단**돼 실제로 동작하지 않았고, 그 fix 의 테스트는 **CI 에 없는 의존을 require** 해 로컬에서만 통과했다.

⟹ **검증 환경이 실제와 다르면 "고쳤다" 만 확인되고 "동작한다" 는 확인되지 않는다.** 실행 원문을 요구하되 **어디까지 실행했고 어디부터 못 했는지**를 함께 적게 할 것.

**Why:** 적대검증이 결함을 내면 fix 하고, fix 가 새 결함을 만들어 라운드가 늘어난다. 그런데 그 새 결함의 **대부분이 같은 형태**(과차단)라서 **미리 물으면 한 라운드에서 잡힌다.** 실제로 오늘 네 트랙 모두 첫 각도에서 잡혔다.

**How to apply:** 재수렴 브리핑 각도 1번을 *"fix 가 정상 경로를 막는가 — 거부되면 안 되는 것이 거부되는가. 실 데이터에서 몇 건이 막히는지 세어라"* 로 고정한다. 관련 [[feedback_harness_defect_zero_design]] · [[feedback_reconvergence_before_merge]] · [[feedback_pm_means_instruction_creates_defect]] · [[feedback_pm_adjusts_workflow_weight_per_track]]
