개발책임자 지적(2026-07-16 #809 R8): 한 슬라이스(R8)를 **아침~저녁 하루 종일** iterate — 리뷰→fix→QA(신규)→fix→QA(잔여)→fix→QA(또 잔여) 로 **"fix 가 새 결함을 낳음" 패턴을 여러 라운드 반복**. 원문: **"아침부터 저녁까지 R8만 진행하는데 이게 맞냐?? 이런 건 PM 이 조절을 해야지."**

**무엇이 잘못이었나**: [[feedback_canonical_workflow]] 의 0수렴 반복을 **기계적으로** 적용하며, PM-QA 로 **한 코너씩 순차 발견→fix→재QA**(VAT 드리프트 → miss → 세트 구성품 …)를 돌렸다. "속도<충실도"는 지켰으나 **"언제 멈추고 바운드/에스컬레이션할지"의 PM 판단을 안 했다**. 결과: 좁은 엣지에 diminishing returns, 다른 대기 슬라이스 지연.

**How to apply**:
1. **매 라운드 후 자문**: 이 슬라이스가 시간/라운드를 과도 소모하나? 남은 게 핵심인가 좁은 엣지인가?
2. **3라운드+ 연속 "fix 가 새 결함"** 이면 묻지 않고 계속 갈지 말고 **개발책임자께 바운드 옵션 제시**(현 견고 상태 게시+엣지 후속분리 / 스코프·우선순위 재논의 / 계속).
3. **한 코너씩 PM-QA 순차 발견 지양** → 코드를 견고 상태로 만든 뒤 **적대 라운드(OPUS/CODEX)가 종합 발견**하게 하고 findings 를 **BATCH disposition + 재수렴 1회**. 개별 재QA 스파이럴 금지.
4. 엣지케이스는 [[feedback_fix_in_current_pr_no_split]] 대로 **후속 이슈로 바운드** 가능(개발책임자 판단).

**선례 처분(2026-07-16 #809)**: 개발책임자 결정 = "구성품 fix(소규모·진행중) 마치고 **R9 1회 종합** 후 오늘 머지" — R9 findings 를 한 코너씩 재QA 하지 말고 **일괄 처리·재수렴 1회**. 0수렴 원칙은 유지하되 R9 를 **종합검증 1회로 바운드**. → [[feedback_autonomous_loop_schedulewakeup]] 의 "매 단계 재자각"에 "슬라이스 총량 자각"을 더한다.

## 🚨 2026-07-22 개발책임자 지시 — **"fix 후 자꾸 새 결함이 생기는 것 같으면 PM 이 중재해라"**

기존 조항은 **라운드를 세고 에스컬레이션**하는 데까지다. 이 지시는 한 층 앞이다 — **fix 가 새 결함을 만들기 전에 PM 이 개입**하라는 것. 사후 적발(리뷰 라운드가 잡아냄)은 이미 라운드를 하나 태운 뒤다.

**실측 근거(2026-07-22 #865 R3)**: R2 fix 커밋 `0dc88b3a4`(17파일) 대비 R3 발견 ~29건의 위치를 대조하면 **~22건이 그 fix 가 만진 파일 안**, **~5건은 fix 가 도입한 필드를 전파하지 않아 생긴 것**(mock·CI 게이트), 진짜 무관은 ~2건. ⟹ **R3 발견의 대부분이 R2 fix 에 귀속**된다. 같은 날 #864 는 fix 가 도입한 V65 CHECK 를 **자기 기존 IT 데이터가 위반**해 CI RED.

### 중재 3단 (PM 이 실제로 하는 행위)

**1단 · 착수 전 — 파급 선언(blast-radius)을 받고 시작한다.** fix 를 쓰기 **전에** 구현자가 답해야 한다:
- ① **새 상태/필드/제약을 도입하는가?** → 그것을 알아야 하는 곳 **전수 목록**(mock·시드·스펙·DECISIONS·CI 게이트·타 서비스 DTO·FE 계약)
- ② **기존에 허용되던 조합을 금지하는가?** → 그 조합을 쓰는 **기존 테스트·시드·문서 전수**
- ③ **타이밍/순서/latch 를 바꾸는가?** → 새로 생기는 **창(window)**

🔴 2026-07-22 하루에 이 셋이 **전부** 터졌다: ①신규 필드 `documentTemplateDefaultPinned` → mock·CI 게이트 미갱신(**2개 차원이 독립 포착**) ②신규 제약 V65 `ALL`+refs 금지 → 기존 IT 가 그 조합 사용(**CI RED**) ③E-P2 가 `await` 로 성공 배너를 refetch 뒤로 미룸 → **"저장은 됐는데 고지가 없는" 창**(PM 이 커밋 전 반려).

**2단 · 커밋 전 — PM 선제 적대 질문 1개를 반드시 통과시킨다.**
> **"이 fix 가 새로 *가능하게* 하거나, 새로 *금지*하거나, 새로 *지연*시키는 것은 무엇인가?"**

세 동사에 하나라도 걸리면 그 대상의 **기존 사용처를 전수 확인**하기 전에는 커밋하지 않는다. E-P2 를 잡은 것이 정확히 이 질문이며, 실제로 새 결함 1건이 PR 에 실리기 전에 차단됐다. 🚫 **"리뷰 라운드가 잡아주겠지" 는 중재가 아니다** — 그건 라운드를 한 번 더 태우는 선택이다.

**3단 · 라운드 후 — fix-유발률을 측정해 게시한다.**
`직전 fix diff 안에 있거나 그 fix 의 누락 때문인 [NEW] 발견 / 전체 [NEW] 발견`. 방법 = `git show <fix-sha> --name-only` 와 발견 표의 `파일:라인` 대조.
- **50% 초과면 "한 라운드 더" 가 답이 아니다** — fix 방식 자체를 바꿔야 한다는 신호다(범위 최소화·전파 목록 선행·RED-first 강화).
- 수치를 **PR 에 게시**한다. 체감으로 말하면 근거 없는 감상이 되고, 수치로 말해야 개발책임자가 바운드를 판단할 수 있다.

**적용 순서**: 1단·2단은 **PM 이 매 fix 마다 무조건** 수행(에스컬레이션 불요·PM 자율). 3단 수치가 임계를 넘으면 기존 조항대로 **개발책임자께 바운드 옵션 제시**.

### 🚨 4단 · 무한루프 차단기 — **"RED 불가 = 고치지 않는다" 를 기본값으로 엄격 적용**

개발책임자 추가 지시(2026-07-22): *"가급적 자꾸 결함이 발생해 무한루프되지 않도록 주의."*

**무엇이 루프를 만들었나**: PM 도 구현자도 **"전 심각도 0" 을 "목록의 전건을 fix 한다" 로 읽었다.** 그런데 적대 라운드가 내는 LOW 에는 **도달 불가(defense-in-depth) · 이미 다른 fix 로 해소됨 · 문서 위치 문제 · pre-existing 공용 스크립트** 가 대량 섞인다. 이것들을 fix 하면 **표면만 늘고 그 표면에서 다음 라운드 결함이 나온다.**

**차단기는 캐논에 이미 있다** — *"RED 를 못 만들면 고치지 말고 보고하십시오."* 이건 예외 조항이 아니라 **기본 규칙**이며, 🔑 **도달 불가능한 결함은 정의상 RED 를 만들 수 없다.** 따라서 **전 심각도 0 을 완화하지 않고도** fix 부피가 구조적으로 캡된다.

**3단계 분류를 fix 착수 전에 강제한다**:
1. **도달 가능한가?** 실 사용자 경로(또는 위협모델에 포함된 직접 write)로 **재현되는가?** → 재현 안 되면 🚫 **fix 금지**. *"도달 불가 + 근거"* 로 disposition 하고 주석·보고에만 남긴다.
2. **이미 해소됐는가?** 같은 라운드의 다른 fix 가 없앴을 수 있다 → **재확인 후 보고만**, 추가 변경 금지.
3. **남은 것만 RED-first 로 fix.**

**함께 금지**: "혹시 몰라서" 하는 방어적 변경 · 결함 fix 가 아닌 리팩터링/정리/개선 · 도달 불가 항목에 "심층방어" 명목의 코드 추가 · 범위 밖(pre-existing 공용 스크립트·타 슬라이스) 손대기.

**실측(2026-07-22 #865 R3)**: LOW ~20건 중 **도달 불가 4 · 이미 해소 가능성 2 · 문서 위치 3 · 범위 밖 3** 이었고 **실제 fix 대상은 4건**이었다. 전건 fix 했다면 부피가 5배가 되고 그만큼 새 표면이 생겼을 것이다.

**PM 이 구현자에게 줄 기본값**: *"판단이 애매하면 고치지 말고 물어보십시오. **안 고치는 쪽이 기본값**입니다."* — 지금 필요한 것은 완결성이 아니라 **수렴**이다.

⚠️ **PM 자신의 실패도 루프 원인**: #865 R3 종합 게시 때 PM 이 차원별 보고의 **LOW 개별 항목(위치·재현·근거)을 압축해 집계 매트릭스만** 남겨, 구현자가 처분 불가 상태가 됐다(구현자가 §0 으로 지적). **종합 게시는 요약이 아니라 처분 가능한 원문이어야 한다** — [[feedback_canonical_workflow]] 의 "실행=게시 1:1" 은 건수가 아니라 **행동 가능성** 기준이다.
