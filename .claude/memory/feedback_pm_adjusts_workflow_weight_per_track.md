# 🚨 무거운 워크플로우는 **PM 이 트랙별로 조정**한다 — 상시 위임

> 개발책임자 원문(2026-07-28): *"워크플로우가 너무 무거워서 자꾸 무한 루프를 돌 것 같으면, 개선방향을 자꾸 마련해야해. PM이 자율진행으로 해당 트랙에 대한 방향을 조정하고 **결함없이 머지가 되면 돼**."*

직전 발화: *"너무 오래걸리잖아. 서비스를 이제 곧 개시해야하는데 아직도 이슈가 21개나 남았어."*

## 무엇이 바뀌었나

[[feedback_canonical_workflow]] 의 *"두 검증 스테이지를 도달가능 0 까지 반복"* 은 **품질에서는 옳지만 처리량에서 병목**이다. 실측: PR 당 **6~8라운드**. 2026-07-28 하루에 5트랙을 돌려 머지 0건.

⟹ **절차의 무게를 PM 이 트랙별로 정한다.** 물어보고 기다리지 않는다. [[feedback_pm_autonomous_recommended_direction]] 의 자율 범위에 **"워크플로우 무게 조정"** 이 추가된 것이다.

🔑 **유일한 판정 기준 = "결함 없이 머지"**. 절차를 다 밟았는지가 아니라 **결함이 없는지**가 기준이다.

## 경로 배분 (PM 이 트랙마다 정한다)

| 경로 | 대상 | 절차 |
|---|---|---|
| **정밀** | 금액 · 회계 · 권한 · 데이터 무결성 · 실사용자 데이터 삭제 가능성 | 현행 캐논 유지 — 2검증 스테이지 · 라이브QA · 0수렴 |
| **신속** | UI · 문서 · 하네스 · CI · 관측 · 개발자 도구 | **1라운드 + CI green + 라이브QA 1회**로 바운드. 잔여 엣지는 후속 |

애매하면 **금액에 닿는가**로 가른다. 닿으면 정밀.

## 🚨 무한 루프 신호 — 이게 보이면 즉시 조정한다

1. **fix 가 3회 연속 새 표면을 만든다** → [[feedback_pm_regulate_slice_effort]] 발동. 동결하고 바운드
2. **같은 계열 결함이 3회 이상 재발** → 값 열거식 fix 를 멈추고 **판정 축 자체를 바꾼다**(#958 이 그렇게 6번째까지 흡수)
3. **라운드 번호는 오르는데 도달가능 결함 수가 안 준다** → 수렴비 c 를 재고 c≥0.45 2연속이면 분할 동결
4. **리뷰가 "범위 밖" 을 반복 언급** → 범위를 좁혀 닫고 나머지를 후속으로

## 🔑 "개선방향을 자꾸 마련해야 한다"

개발책임자가 요구한 것은 **절차를 줄이는 것이 아니라 계속 개선안을 내놓는 것**이다. 같은 병목을 두 번 겪으면 그 자리에서 구조를 바꾼다:
- 라운드가 오래 걸리면 → **브리핑 범위를 좁혀 완주시킨다**(2026-07-28 SOL 7200초 타임아웃으로 산출물 0 → 범위 3개로 축소해 재투입)
- 같은 계열이 반복되면 → **열거 대신 결과 상태로 판정**
- 게이트가 못 잡는 표면이 나오면 → **게이트를 넓힌다**(#974 가 `tools/legacy-gas` 편입)

## 여전히 멈추는 것

PM 이 조정할 수 없는 것은 그대로다 — **새 이슈 등록** · 무결성 도메인 정책 · 모델 대체 · 가짜 데이터. 그리고 **"결함 없이" 는 타협 대상이 아니다** — 절차를 줄이는 것이지 결함을 눈감는 것이 아니다.
발견했으나 이번에 안 고치는 것은 **PR 에 정직하게 남긴다**([[feedback_unverified_scope_is_not_zero_defects]] — "범위 밖" 을 "결함 0" 으로 세지 않는다).
