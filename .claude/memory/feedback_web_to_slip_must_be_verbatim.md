# 🚨🚨 웹 → 전표는 **그대로**다

> 2026-08-17 개발책임자: *"견적 및 주문 웹에서 주는 **품목 등의 전표 그대로 생성**되어야해"* · *"그래 **가격 정보 등도 그대로** 말야"*

## 확정

```text
견적서웹 · 주문서웹이 넘긴 것이 전표에 변형·누락 없이 들어간다

  품목   모델코드 · 품목명 · 규격
  수량   기본 수량 · 세트 전개 후 수량
  가격   단가 · 공급가 · 부가세 · 합계
  옵션   판넬 · 리모컨 등 선택값
```

🚫 **서버가 다시 계산해 다른 값을 넣으면 안 된다.** 웹 화면에서 본 것과 전표가 달라지면 그것이 결함이다.

## 이것이 정하는 것

```text
slip-service 가 클라이언트 단가를 정본으로 저장하는 현재 구조는
  결함이 아니라 요구사항이다 (P1-02 실증이 "서버 DC 재검증 없음" 으로 올렸던 것)

⟹ P1-02 의 "slip 저장 시 서버 DC 재검증" 항목은 이 확정과 충돌한다
   개발책임자가 범위에서 뺀 것이 일관된다 (2026-08-17 "estimate-app 404 폴백만 차단")
```

🔑 서버 재검증이 필요한 것은 **웹이 잘못된 값을 만들지 않게** 하는 쪽이지, 전표 저장 단계에서 값을 바꾸는 것이 아니다. 그래서 P1-02 의 조치가 *"조회 실패 시 임의 기본값으로 금액을 만들지 않는다"* 로 잡힌 것이다.

## 🚨 웹은 이미 **구성품 단위**로 보낸다

> 2026-08-17 개발책임자 정정: *"아니지 **웹에서는 이미 구성품으로 보내잖아**"*

```text
세트 전개는 웹에서 끝난다
  견적서웹·주문서웹이 세트를 구성품으로 펼쳐서 행 단위로 넘긴다
⟹ 서버는 전개할 일이 없다. 받은 행을 그대로 저장하면 된다

🚫 서버가 다시 전개하거나 · 합치거나 · 재계산하면 그것이 결함이다
```

PM 이 처음에 *"세트 전개가 변형을 만드는가"* 를 핵심 의심 지점으로 잡았는데 **틀렸다.** 전개 자체가 서버에 없다.

## 확인해야 할 의심 지점

```text
행 보존      웹이 보낸 행 수와 전표의 행 수가 같은가
             합쳐지거나 빠지는 행이 없는가

값 보존      단가 · 공급가 · 부가세 · 합계가 그대로인가
             서버가 반올림·재계산을 끼워 넣지 않는가

옵션 전달    slip_lines.bundle_set_options
             PM 실측 (2026-08-17): 72행 전부 panelOption·remoteOption 이 null
             ⟹ 웹에서 고른 옵션이 전표에 안 실리고 있을 가능성

경로         /api/v1/slips/from-estimate
             /api/v1/slips/from-partner-order
             /api/v1/slips/from-orders-merge
             (api-gateway application.yml:443-450)
```

**Why:** 견적서와 주문서는 거래처에게 이미 제시된 문서다. 그것으로 만든 전표가 다른 금액을 담으면 고객에게 약속한 값과 청구가 달라진다.

**How to apply:** 전표 생성 경로에 계산 로직을 넣지 마라. 값을 옮기기만 한다. 검증이 필요하면 **막되 바꾸지 마라** — 어긋나면 저장을 거부하고 사용자에게 알리는 쪽이지, 조용히 다른 값을 넣는 것이 아니다. 관련 [[feedback_amount_must_be_single_source_across_steps]] · [[feedback_daily_closing_uses_estimate_items]]
