# 🚨 **결함이 살아 있는 동안 돌린 라이브QA 가 다음 라운드를 오염시킨다**

**2026-08-06 `#874`(PR #1057)** 에서 한 사이클을 통째로 쓸 뻔했다.

## 무슨 일이 있었나

```
R76 라이브QA   전역DC 오적용 결함이 살아 있는 상태에서 실행 → 561,600 으로 "PASS" 판정
                그 저장이 slip_db.partner_product_price_memory 에 561,600 을 써 넣음
R77 SOL        오적용을 결함으로 확정 (변동DC 비대상 92개까지 전역DC 적용)
R78 fix        적용 자격 검증 추가 — 코드는 고쳐짐
R79 라이브QA   같은 품목이 여전히 561,600 → BLOCK
R80 진단       결함 아님. 최근단가 우선순위는 기존 설계이고, R76 이 남긴 오염 행이 재생된 것
```

**R79 는 정직했고 실측도 정확했다.** 561,600 은 실제로 화면·POST·재조회에 전부 나왔다. 틀린 것은 그 값의 **출처에 대한 해석**이었다.

## 🔑 왜 알아채기 어려운가

- 오염 값은 **실 DB 에 실제로 있다.** fixture 도 mock 도 아니다.
- 오염 값은 **재현된다.** 매번 같은 값이 나오므로 결함의 모든 겉모습을 갖춘다.
- 코드는 이미 고쳐져 있어서 **"fix 가 동작 안 한다" 는 결론**으로 곧장 간다. 실제로는 fix 는 동작했고 다른 층이 앞에 있었다.

## 🔑 가르는 법 — 행의 **생성 시각과 생성자**를 보라

```sql
SELECT created_at, modified_at, created_by, <값> FROM <기억 테이블>
 WHERE <키> = ... ;
```

```
partner 77d0513c… / product d7f488a5…   561,600
  created_at  2026-08-06 00:25:46   ← R76 라이브QA 시각
  modified_at 2026-08-06 03:06:58   ← R79 라이브QA 시각
```

**우리 라운드 시각과 일치하면 우리가 만든 것이다.** 값을 재계산하면 "다른 값이 나온다" 로만 끝나지만, 시각 분포를 보면 "애초에 우리가 넣었다" 가 드러난다 → [[feedback_real_data_label_points_elsewhere]]

같은 라운드가 새로 쓴 **다른 행들이 전부 옳은지**도 함께 본다. R79 가 새로 만든 세 행(1,355,640 / 1,089,000 / 204,000)은 전부 정확했다 — 오직 미리 존재하던 행 하나만 틀렸다는 것이 결정적 신호였다.

## 🔑 결함이냐 잔재냐를 가르는 질문 세 개

1. **의도된 우선순위가 무엇인가** — 코드에서 `파일:줄` 로 확정한다. 이번 건은 `사용자 직접입력 > 유효한 고정/전역DC > 최근단가 > 판매가` 가 이미 설계돼 있었고 fix 가 만든 것이 아니었다.
2. **기억이 없는 조합**으로 같은 검증을 하면 깨끗하게 동작하는가. 무기억 조합은 정가로 정상 수렴했다.
3. **사용자가 교정할 수 있는가** — 올바른 값을 저장하면 그 행이 갱신되는가. upsert 로 교정 가능하면 잔재이고, 영구 고착이면 결함이다.

세 답이 다 "정상" 이면 **게이트 ①에 세지 않는다.**

## 🚫 하지 말 것

- **DB 행을 지워서 "해결"** 하지 말 것. 지워도 같은 결함이 다시 만들면 재현되고, 지운 사실이 증거를 없앤다 → [[feedback_fix_blocks_normal_path]] 의 증상/원인 구분
- QA 결과를 받자마자 fix 라운드를 열지 말 것. **한 번은 "이 값이 어디서 왔나" 를 묻는 진단 라운드**가 싸다. 이번엔 진단 한 라운드가 fix 라운드 하나 이상을 아꼈다.

## 🔑 예방

결함이 확정된 뒤에는 **그 결함이 쓰기를 하는 경로인지** 먼저 본다. 쓰기를 한다면 그 라운드의 라이브QA 산출물은 **DB 에도 남는다**는 것을 PR 에 기록해 둔다. 다음 라운드가 같은 데이터를 다시 밟기 때문이다.
