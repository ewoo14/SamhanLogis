# 🚨 불변식처럼 보이는 **수단 지시** — 2026-07-28 #958 실측

[[feedback_canonical_workflow]] 에 *"PM 은 fix 지시에서 **불변식만** 말하고 **구현 수단을 지시하지 않는다** — 수단 지시 시 그 결함까지 PM 이 떠안는다"* 가 이미 있었다. **그런데 규칙을 알면서도 어겼다.**

## 무슨 일이 있었나

SOL 이 *"`syncTab` 이 전역 잠금을 쥔 채 외부 시트 왕복 → 일반 품목 편집 **566배 지연**"* 을 잡았다. PM 이 이렇게 걸었다:

> **I-4** 무결성 잠금이 **외부 시스템 응답을 기다리는 구간을 덮지 않는다.**

지연은 해소됐다. 그런데 잠금이 외부 HTTP **뒤로** 가면서 **lost update** 가 생겼다 — 다음 라운드 SOL 실측:

```text
동시 syncTab 에서 응답 순서 역전 시
  새 값 3,000,000 저장 → 구 값 2,000,000 이 최종 저장
```

## 🔑 왜 이게 수단 지시인가

- **불변식** = *"무엇이 성립해야 하는가"* → *"정상 편집이 외부 응답을 기다리며 막히지 않는다"*
- **수단** = *"어디에 무엇을 놓아라"* → *"**잠금이** 그 구간을 **덮지 마라**"*

I-4 는 **잠금이라는 구현 수단의 위치를 지정**했다. 구현자에게 남은 선택지는 *"잠금을 뒤로 옮긴다"* 뿐이었고, 그 결과 생긴 순서 문제는 **PM 이 만든 것**이다.

## 어떻게 고쳐 걸었나

다음 라운드에서 **두 요구를 동시에** 거는 형태로 바꿨다:

> **M-2** 먼저 읽은 값이 나중에 읽은 값을 덮지 않는다 — **동시에**, 정상 편집이 외부 응답을 기다리며 막히지도 않는다.
> 🚫 잠금 구간을 다시 넓히는 되돌리기 금지.

구현자는 **순서 토큰**(V25 `product_sheet_sync_generation` — 외부 HTTP 전에 generation 을 올리고 잠금을 쥔 상태에서 확인)을 골랐다. PM 이 생각하지 못한 수단이고, 두 요구를 다 만족한다(응답 역전 시 최종 `3,000,000` · 편집 지연 `13ms`).

## 판별법 — 브리핑을 쓰고 나서 자문한다

> **"이 문장이 구현자의 선택지를 하나로 좁히는가?"**

좁힌다면 수단 지시다. 다시 써라.

🔑 **특히 위험한 형태** — 결함이 "X 때문에 생겼다" 고 진단한 뒤 *"X 를 하지 마라"* 로 적는 것. 진단은 옳아도 **X 를 제거하는 방법이 여러 개**이고, 그중 하나만 남기면 그게 수단 지시다. *"X 가 만들던 문제가 없어야 한다"* 로 쓰고, **그 반대급부도 함께 걸어야** 한다(우리 사례에서는 "지연이 없을 것" 만 걸고 "순서가 보존될 것" 을 안 걸었다).
