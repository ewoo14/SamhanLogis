# 🚨 변경 줄 수 보고는 **개별 파일 numstat 으로 대조**한다 (2026-07-28 · 5 PR 연속 실측)

구현자·fix 담당이 보고하는 "변경 줄 수" 표가 **다섯 PR 연속** 실제와 달랐다. 전부 대조 각도(SONNET5)가 잡았다.

| PR | 주장 | 실제 |
|---|---|---|
| #969(#964) 구현 | `총 +455/−3` | **`+549/−3`** (개별 항목도 전부 상이) |
| #958(#896 슬2) R4 fix | test 수정 `+91/−6` | **`+78/−6`** (13줄 과다) |
| #967(#963) 구현 | `index.ejs +4/−`, `index.html +116` | **`+2/−2`**, **`+75/−41`** |
| #967(#963) R1 fix | dev-report `+86/−2`, spec `+17/−7`, plan `+6/−3` | **`+84/−2`**, **`+10/−7`**, **`+3/−3`** |
| #968(#965) 구현 | validator `+23/−`, 테스트 `+101` | **`+13/−10`**, **`+83/−18`** |

## 🔑 단일 패턴 — **삭제분을 추가분 칸에 더해 넣는다**

`86 = 84+2` · `17 = 10+7` · `6 = 3+3` · `23 = 13+10` · `101 = 83+18` · `116 = 75+41`.
`git diff --stat` 이 보여주는 **(추가+삭제) 합산 막대 수치**를 `+N / −M` 형식에 그대로 옮겨 적어서 생긴다. 우연이 아니라 **표기 규약 혼용**이다.

🔑 **총계는 대체로 정확하다** — `+441/−18`·`+519/−51`·`+549/−3` 은 numstat 과 일치했다. 그래서 **총계만 확인하면 못 잡는다.**
🔑 **정확한 값이 이미 저장소 안에 있는 경우가 많다** — #967 은 dev-report §8.6 표가 6개 파일 전부 numstat 과 100% 일치했는데, **PR 코멘트로 옮기는 과정에서만** 3행이 깨졌다.

## 규칙

- **대조 각도(SONNET5)의 상시 항목**이다. `git show --numstat <sha>` 로 **개별 파일 단위** 대조한다. 총계 일치로 갈음하지 않는다.
- 보고하는 쪽은 **`--numstat` 출력을 그대로 옮긴다.** `--stat` 의 막대 옆 숫자(합산)를 `+N/−M` 로 적지 않는다.
- PM 이 PR 코멘트에 표를 옮길 때도 같은 함정에 빠진다(2026-07-28 PM 본인 2회). **dev-report 에 이미 정확한 표가 있으면 그것을 복사**한다.

## 왜 중요한가

변경 줄 수는 **최소 변경 원칙의 계량 지표**다([[feedback_canonical_workflow]] — *"fix 부피가 곧 다음 라운드의 감사면"*). 부풀려 보고되면 fix 가 실제보다 커 보여 판단이 흐려지고, 반대로 축소 보고되면 감사면을 과소평가한다. 무엇보다 **"실측" 으로 제시된 수치가 틀린 것 자체가 증거 무결성 문제**다 → [[feedback_quoted_output_splice_forgery]] · [[feedback_pm_verify_what_measurement_proves]]
