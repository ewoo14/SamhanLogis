# 🚨 수량 동기화 = **본체 → 부자재** · 부자재 쪽에서 **칩으로 복수 지정** (2026-08-10 개발책임자)

## 개발책임자 정의 (원문)

> *"**부자재 쪽에 수량동기화를 품목지정**해 놓으면 해당 품목들에 수량이 들어갔을 때
> **그 합산 수량이 부자재에 설정**되는 시스템.
> **반대로 지정해 놓더라도 마찬가지로 동작은 가능해야 함.**"*

> *"갈래 2로. **수량 동기화는 본체 → 부자재 용도**야."*

> *"잊지마. **부자재 수량동기화 설정에 실내기 또는 실외기 품목들을 지정**(복수 가능, **칩 형태로 추가 삭제 가능**)."*

---

## 계약

```text
의미     source 품목들의 **수량 합** → target 부자재의 수량으로 설정
source   **본체** — 실내기 또는 실외기. **복수**
target   **부자재** — 호스 · 판넬 · 리모컨 · 발통 · 분기관 등
작성 위치 🆕 **본체 설정 화면** (2026-08-10 개발책임자 전환 — 아래 참조)
작성 방향 반대(부자재에서 본체 지정)도 **동작해야** 한다. 의미는 하나다
```

## 🆕 2026-08-10 — 작성 진입점을 **본체 쪽으로 전환** (개발책임자 확정)

> *"차라리 **본체에 수량 동기화를 걸도록** 할까? 내가 원래 발주한 것은 부자재에 걸도록 했는데,
> 생각해보니 **본체에 거는 게 더 깔끔**할 것 같아."* → *"**본체 전환은 결정으로 기록**"*

### 🔑 가르는 것은 **누락의 비대칭**이다

```text
부자재 쪽   새 실외기 모델이 나오면 10개 규칙을 다 찾아가 추가해야 한다
            하나 빠뜨리면 견적이 받침 없이 나간다 — **조용하다**
본체 쪽     새 실외기를 등록하는 그 자리에서 부자재를 지정한다
            일괄 편집이 불편해진다 — **시끄럽다**
⟹ 잦은 일은 '새 모델이 나왔다' 이지 '111개 받침을 한꺼번에 바꾼다' 가 아니다
```

### 🚨 스키마도 규칙 개수도 바뀌지 않는다

```text
저장 구조   그대로 (sources[] / targets[]) — 10규칙 509행
바뀌는 것   **작성·편집 진입점**뿐
양방향 표시 본체 화면: '이 본체가 부르는 부자재' / 부자재 화면: '나를 부르는 본체들'
```

🚫 **본체마다 규칙 하나로 쪼개 500규칙을 만들지 마라.**
   `방진가대S2중` 을 쓰는 111개 본체가 흩어지면 "이 받침이 언제 들어가나" 를 볼 수 없고
   규칙 하나 고칠 일이 111번이 된다. 원 발주의 *"반대로 지정해도 동작 가능"* 이 이미 이걸 담고 있다.

### 🚨 순서 제약 — 분류를 먼저 고친다

매핑표(`docs/dev-reports/2026-08-10-896-product-role-mapping-table.md`)가 **catL 불일치 46건**을 찾았다.
본체 쪽에서 작성하려면 **"이게 본체냐 부자재냐" 가 먼저 정확해야** 한다.

```text
GHP 9건        DB '부자재' ↔ 레거시 '실외기'   → 본체인데 부자재로 잡혀 있다
판넬 14건      DB '실내기' ↔ 레거시 '판넬'
운임·절삭 6건  DB '부자재' → validator 가 **운임을 target 으로 허용**한다
⚠️ 순서를 바꾸면 본체 목록에 운임이 뜬다
```

🔑 **역할축은 (품목 × 견적카테고리) 단위**여야 한다 — `AIM-H04N`·`ACR-SMA`·`ACR-SKE` 는
   상업에서 부자재이고 홈에서 미언급이라, 품목당 역할 하나로 두면 즉시 모순이 난다.

현행 구현이 이 모양과 이미 맞다 (2026-08-10 PM 실측):

```text
칩 UI    ProductMultiSelectAutocomplete   EstimateItemsCatalogPage.tsx:1320
스키마   List<QuantitySyncProductRef> sources · targets   QuantitySyncRuleResponse.java:23-24
```

## 🚨 이 정의가 열 라운드를 끝냈다

`#896` PR `#1126` 은 **R11 부터 열 번 부분해**였다. 매번 legacy 계산기를 조정했다.

```text
R11 계열 5 중 3만  → R15 반대 의미론 → R17 옵션 2갈래 → R19 옵션 16상태
→ R21 target 단위 병합 → R23 순서 무관성 → R25 반복 무관성 → R27 비활성 규칙
```

R26 이 낸 마지막 결함(**규칙 target 이 주품목이면 그 주품목이 다시 파생의 source 가 돼 순환**)은
계산기 문제가 아니었다 — **"target 이 무엇이 될 수 있는가" 가 정해져 있지 않았던 것**이다.

```text
관리자 UI   target 검색에 제품 역할 제한 없음   EstimateItemsCatalogPage.tsx:1153
서버        같은 HOME_MULTI 노출이면 허용        QuantitySyncRuleValidator.java:293
```

⟹ **용도를 확정하니(본체→부자재) 계산기를 더 고칠 필요가 없어졌다.**
   서버 validator 가 target 을 부자재로 제한하면 그 순환은 애초에 만들어지지 않는다.

🔑 **열 번 미끄러진 뒤에 나온 교훈** — 계산기가 계속 틀리면 계산기를 의심하기 전에
   **입력의 정의가 열려 있는지**를 보라. 정의를 좁히는 것이 계산을 고치는 것보다 싸다.
