# 🚨 조인 키로 쓰는 **코드 컬럼이 비어 있다** — UUID 만 채워져 있다

2026-08-03 하루에 **세 번** 같은 모양이 나왔다. 셋 다 CI green 상태에서 숨어 있었고, 셋 다 **실 사용자 경로에서 데이터가 통째로 사라지는** 결함이었다.

| PR | 조회하는 쪽 | 조회당하는 쪽 | 실측 |
|---|---|---|---|
| #1060 | `partner_auth.biz_no` = `2118712345` | `partner_orders.partner_code` = `P-2026-0001` (사업자번호는 `biz_code` 에) | 주문 2,024건 중 조회되는 것 **1건**, 그마저 `confirmed_at` 없음 |
| #1060 | 같은 auth 키 | `slips.business_number` | OUTBOUND 2,303건 중 보유 **280건**. 주문 전환 출고는 **20건 전부 NULL** |
| #1061 | 화면이 넘긴 `P-2026-0017` | `slips.partner_code` | 원장 후보 **31건 전부 비어 있음**. `partner_id` 는 채워져 있음. 12,276,000원이 화면에서 사라짐 |

## 왜 안 잡히나

- **컴파일도 되고 테스트도 통과한다.** 타입이 같은 `String` 이라 잘못된 조인이 문법적으로 정상이다.
- **CI 는 fixture 로 돌아서 양쪽을 다 채운다.** 실 데이터의 결손 분포를 재현하지 않는다.
- **조회 결과가 `null`/0건이지 오류가 아니다.** 그래서 "해당 없음" 으로 표시되고 장애처럼 보이지 않는다. #1060 이 애써 만든 `deferred`(보류) 장치도 못 잡았다 — 조회가 **실패**한 게 아니라 **200 OK 로 빈 결과**를 줬기 때문이다.
- **증상이 시간차로 온다.** #1060 은 auth 행이 30일을 넘겨야 드러나는 것이었다(생성 07-09 → 08-08 도달).

## 규칙

**조회 키를 정하거나 바꿀 때, 실 데이터에서 그 컬럼이 몇 % 채워져 있는지 먼저 센다.**

```sql
SELECT count(*) AS 총,
       count(*) FILTER (WHERE <키컬럼> IS NOT NULL AND <키컬럼> <> '') AS 키있음,
       count(DISTINCT <키컬럼>) AS 구별값
FROM <테이블> WHERE <실제 조회 조건>;
```

- **양쪽 키 공간이 같은지 표본을 눈으로 본다.** `P-2026-0001` 과 `2118712345` 는 둘 다 문자열이지만 **다른 세계**다.
- **UUID 가 채워져 있는데 코드가 비어 있으면, 코드로 조인하는 설계 자체를 의심한다.** UUID 는 사용자에게 노출하지 않되 내부 조인 키로는 쓸 수 있다([[feedback_uuid_no_user_visibility]] — 금지는 **화면 노출**이지 내부 조인이 아니다).
- **적대검증 브리핑에 넣을 각도**: *"이 조회의 키가 실 데이터에서 몇 건이나 매칭되는가. 0이면 0이라고 써라."*
- 조회가 빈 결과를 줄 때 **"데이터가 없다"와 "키가 안 맞는다"를 구분**할 수 있어야 한다. 둘이 같은 화면으로 보이면 영원히 안 잡힌다.
