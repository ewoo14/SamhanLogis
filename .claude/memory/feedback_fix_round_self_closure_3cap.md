# 🚨🚨 fix 라운드 상한 3 — fix 는 **자기가 만든 표면을 자기 라운드에서** 닫는다 (2026-08-04 개발책임자 결정)

## 개발책임자 지시

> *"라운드가 이렇게 무한정으로 늘어나버리면 답이 없어. 초반에는 라운드 상한을 걸었잖아."*
> *"상한은 3라운드가 적절한 것 같아."*

**fix 라운드 상한 = 트랙당 3.** 상한에 닿으면 fix 를 멈추고 ①현 견고 상태 게시 ②개발책임자께 바운드 옵션 제시(현 상태 머지 / 엣지 후속분리 / 스코프 재논의)로 전환한다.

🚫 **줄이는 것은 절차이지 결함 허용이 아니다.** 상한에 닿았다고 도달 가능한 결함을 눈감지 않는다. 그 시점에 **"현 상태 + 남은 엣지 목록"** 을 올리고 판단을 받는다.

---

## 🔑 핵심 진단 — 라운드를 늘린 것은 "결함을 못 찾아서" 가 아니다

결함은 **매번 첫 라운드에 나왔다.** 늘어난 이유는 **fix 가 만든 새 표면을 다음 라운드에서 발견**했기 때문이다.

```text
#1057  R26 fix 가 전이 버튼과 `수정` 을 공존시킴 (그 전엔 둘 중 하나만 렌더)
       → R27 이 그 조합(편집 중 전이 → 409)을 발견 → R28 fix
       ⟹ R26 이 자기가 만든 조합을 셌으면 거기서 끝났다

#1061  R28 fix 가 생성자 의존을 바꿈      → R29 (mock 배선 누락 · compileTestJava 단계)
       R28 fix 가 엔드포인트 경로를 옮김  → R30 (옛 경로를 단언하는 계약 스펙 + mock 핸들러 구멍)
       ⟹ 둘 다 R28 안에서 닫을 수 있었다
```

세 건 모두 **fix 라운드가 끝나기 전에 잡을 수 있었다.**

역산: 이 조항들이 있었으면 `#1057` 5라운드 → **3**, `#1061` 4라운드 → **2**.

## fix 브리핑 필수 절 3종 — 종료 조건

### 1. 새 조합 열거

> *"이 변경으로 **새로 가능해진** 상태·화면 조합을 나열하고 각각 밟아라."*

R26 이 이걸 했으면 `편집 중 + 전이 가능` 을 스스로 적었을 것이다. **fix 는 대개 "없던 조합" 을 만든다** — 버튼 두 개가 처음 공존하고, 상태 두 개가 처음 겹친다.

### 2. 참조 전수

> *"제거·이동·개명한 식별자(경로·필드·함수명)를 grep 으로 전수 조사하고 남은 참조를 전부 처리하라."*

R28 이 `ledger-data` 를 grep 했으면 계약 스펙 1줄과 mock 핸들러 구멍이 그 자리에 나왔다. → [[feedback_defect_family_sweep_fix]]

### 3. 영향 테스트 실행

> *"바꾼 클래스·파일을 **참조하는** 테스트를 전부 실행하라."*

⚠️ **PM 이 "지정 파일만" 으로 좁힌 것이 R29 를 만들었다.** 토큰·시간을 아끼려 테스트 범위를 좁히면 그 절약분이 다음 라운드 하나로 되돌아온다. **좁혀야 할 것은 전체 스위트이지 영향 범위가 아니다.**

#### 🚨 3-1. 생성자·빈 배선을 바꿨으면 **IT 를 최소 1개** (2026-08-04 실증)

`#1061` R33 이 `영향 Java 9개 테스트 클래스 BUILD SUCCESSFUL` 로 보고했는데 **CI 에서 accounting 10잡이 죽었다.**

```text
Caused by: BeanCreationException → BeanInstantiationException → NoSuchMethodException
```

생성자 시그니처를 바꿨는데 옛 시그니처로 인스턴스화하는 곳이 남아 **Spring 컨텍스트가 통째로 안 떴다.** 무관한 IT 까지 전부 죽었다(wildcard 검색·audit log·dynamic permission·계정명세서…).

🔑 **그 9개는 유닛 테스트였고 컨텍스트를 로드하지 않는다.** 유닛 GREEN 은 배선을 아무것도 보장하지 않는다. **생성자·`@Bean`·의존 주입을 건드린 라운드는 컨텍스트를 로드하는 IT 를 최소 1개 돌릴 것.**

## PM 브리핑 정확성 3종

### 4. 수치는 SQL 원문 그대로

**요약·라벨 금지.** 같은 날 두 번 틀렸다.

```text
PM "slip_db 미삭제 127건"   → 실제 전체 127 / 미삭제 118 (COUNT(*) 를 미삭제로 라벨링)
PM "dev_master 로 로그인해"  → 실제 캡처 계정은 dev_manager(MANAGER)
```

둘 다 **하위 분해는 맞았고 요약 라벨만 틀렸다.** 쿼리와 출력을 그대로 붙이면 이 오류는 발생할 수 없다. → [[feedback_real_data_label_points_elsewhere]]

### 5. QA 시나리오마다 발화 조건 카운트

0 이면 **"만들 수 있는가"** 부터 확인하고 발주한다. 0 인 채로 발주하면 라운드가 통째로 버려진다.

```text
#1045  delivery_tag 가 활성 120건 전부 NULL → 8모드 전부 총 0건 (지난 회차 통째 낭비)
#1057  주문전환 SENT — 사업자번호 미등록/미승인이라 주문 생성 자체가 불가 (미발화)
```

### 6. 환경 변경 전 호출 관계를 코드로 확인

**PM 이 메모리 확보를 위해 `arologis-service` 를 "현재 트랙과 무관" 으로 중지시켰는데, 가배차가 그 서비스를 쓴다.** QA 가 503 을 받고 `exit=137` 로 원인을 짚어 재기동했다. 컨테이너를 내릴 때는 **어느 트랙이 그 서비스를 호출하는지 코드로 확인한 목록**만 만든다.

## 남는 한계 — 정직하게

**원인이 다른 층에 있는 경우는 진단 라운드가 반드시 필요하다.**

```text
#1045  게이트웨이가 C5-4 에서 X-User-Role 을 떼는데
       arologis 는 여전히 enforcement-mode: role 로 인가한다
       → 생산자·소비자 계약 불일치. fix 로는 못 찾고 진단이 찾았다
```

이런 건 `발견 → 진단 → fix` 로 **3라운드가 최소값**이고 줄일 방법이 없다. 대신 **진단을 fix 뒤가 아니라 앞에 둔다** — `#1045` 가 그 순서였고 한 번에 원인이 나왔다. → [[feedback_reconvergence_before_merge]]
