# 🚨🚨 라운드마다 **PM 이 검증하고 다음 fix 를 구체적으로 지시**한다 (2026-08-04 개발책임자 지시)

## 개발책임자 지시

> *"fix가 새로운 결함을 내지 않도록 라운드가 끝날때마다 PM이 검증하고 다음 fix에 대한 지시를 구체적으로 정할 것. 전체적으로 결함이 없는 방향으로 진행 요청."*

**3라운드 이내 결함 없는 머지**가 목표다. → [[feedback_fix_round_self_closure_3cap]]

## 🔑 왜 — PM 이 전제를 실측하지 않고 지시하면 **그 결함은 PM 이 만든 것이다**

2026-08-04 `#1063` 실측. PM 이 *"수정 모드에 trailing 빈행을 유지하라"* 고 지시해 R5 fix 가 들어갔고, 그 fix 가 **도달 결함 2건**을 만들었다.

```text
결함 1  수정 화면 빈행에 입력한 모델명·규격·수량·단가·적요가
        경고 없이 저장 payload 에서 사라진다      실 데이터 2,174건 전부 도달
결함 2  빈행이 협업 문서에서 클라이언트 임시 lineId 를 받아
        coeditLineIdsAreStale 를 항상 true 로 만들고
        reseedCoeditLineIds 가 서버 lineId 를 다른 행에 재부착   동일 2,174건
```

**근본 원인은 PM 이 확인하지 않은 전제 하나였다.**

```text
그 화면(SlipDetailPage 인라인 수정)에는 productId 를 확정할 품목 선택기가 없다
⟹ 빈행은 영원히 미확정 → filterMeaningfulRows 가 통째로 버린다
⟹ 확정할 수단이 없는 화면에 빈행만 넣은 것이 함정이 됐다
```

지시 자체가 *"빈행을 유지하라"* 라는 **수단**이었고, *"그 행이 쓸모 있으려면 무엇이 필요한가"* 를 묻지 않았다. → [[feedback_pm_means_instruction_creates_defect]]

## 라운드 종료 시 PM 이 하는 것 (릴레이 금지)

구현자·리뷰어 보고를 그대로 옮기지 않는다. **매 라운드 다음 넷을 직접 한다.**

1. **산출물 실물 확인** — `git status --porcelain` + `git diff --stat` 로 무엇이 바뀌었는지 눈으로 본다. 보고와 파일이 다른 경우가 실제로 있었다.
2. **핵심 주장 1개 이상을 재확인** — 코드·SQL·실행 중 하나로. 릴레이하면 틀린 판정이 그대로 게이트를 통과한다.
   - 실측 예: SOL 이 *"증거 무결성 결함"* 으로 올린 수치 불일치가 **회사PC/집PC 시드 차이**였다(창고 30 vs 6). PM 이 커밋 출처를 확인해 정정했다.
   - 실측 예: SOL 이 *"`SALE_SUMMARY` 가 계약에 없다"* 고 했고 PM 이 `grep` 으로 확인해 사실이었다(핸드오프의 *"현재 구현 유지"* 가 틀렸다).
   - 🆕 **보고서가 *"~도 함께 갱신했다"* 로 나열한 항목은 각각 `grep` 으로 대조한다.** 나열 자체는 검증되지 않은 주장이다. 2026-08-09 실측: R2 가 *"mock 권한 매트릭스와 계약 테스트 갱신"* 이라 적었는데 `mock.ts` 에는 새 page code 가 **하나도 없었고**, 적대검증(R3)도 못 잡았다 — R3 는 실 계정 로그인·DB 대조는 했지만 **Playwright mock 게이트를 돌리지 않았다.** CI 가 `6 failed` 로 잡았다. 🔑 **실서버 검증과 mock 게이트는 서로를 대체하지 못한다.**
   - 🆕 **작업 브랜치가 main 에서 얼마나 뒤처졌는지 센다** (`git rev-list --count HEAD..origin/main`). 같은 날 실측: 트랙 브랜치가 **42커밋 뒤처져** 이미 삭제된 코드를 보고 있었고, 구현자가 그것을 "범위 밖 잔존 결함" 으로 보고했다. fix 는 낡은 base 위에서 만들어졌으므로 **병합 후 반드시 재검증**한다.
3. **다음 fix 지시를 구체적으로 쓴다** (아래 5절 구성).
4. **커밋 → 즉시 게시**를 한 묶음으로. → [[feedback_review_post_one_to_one_enforcement]]

## 다음 fix 브리핑 5절 — 이 형태로 쓴다

```text
① 결함           사용자 조작 순서 · 기대 · 실제(원문) · 실 데이터 영향 건수
② 근본 원인      PM 이 코드/SQL 로 역추적한 것. 파일·줄 인용
③ 전제 실측      "이 화면에 그 수단이 있는가" 를 PM 이 먼저 확인해 브리핑에 넣는다
                 (라우트·컴포넌트·권한·데이터 분포 — 구현자가 추측하지 않게)
④ 불변식         지켜야 할 결과. 🚫 수단 지시 금지
⑤ 깨뜨리면 안 되는 것  이전 라운드가 세운 것들을 RED-B 로 명시
```

여기에 **종료 조건 3종**(새 조합 열거 · 참조 전수 · 영향 테스트 + 컨텍스트 IT)을 붙인다. → [[feedback_fix_round_self_closure_3cap]]

## 판단 기준 — 이 fix 가 새 표면을 만드는가

지시를 쓰기 전에 스스로 묻는다.

```text
· 이 지시가 구현자의 선택지를 하나로 좁히는가          → 좁히면 그 결함까지 PM 몫
· 그 화면·경로에 이 동작이 성립할 전제가 실재하는가     → PM 이 실측해서 브리핑에 넣는다
· 이전 라운드가 세운 것 중 무엇이 깨질 수 있는가        → RED-B 로 명시
· 같은 계열의 다른 경로가 있는가                       → 전수 sweep 를 종료조건에 넣는다
```

**fix 3연속으로 새 표면이 나오면 fix 를 멈추고 구조 진단으로 전환한다.** → [[feedback_harness_defect_zero_design]]
