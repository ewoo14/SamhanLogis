🚨 **무엇이든 "새로 만들자" 로 올리기 전에 3축을 대조한다.**

> *"GAS 전수조사 시 **기존 이슈 또는 구현된 기능인지, 그것도 확인**하라해줘."* (2026-08-11 개발책임자)

## 3축

```text
① 코드   git ls-files <추정경로>  ·  git grep -ril <기능어> -- services/ clients/
② 이슈   gh issue list --state all --limit 400   ← 🚨 CLOSED 포함. 닫힌 이슈가 곧 구현이다
③ 기존결정  .claude/memory/ · docs/handoff/CURRENT-WORK.md · 해당 PR 코멘트
```

**Why:** 이 세션에만 **네 번** 이미 있는 것을 개발책임자께 물었다 —
거래처 DC 설정 화면(`SalesPartnerDcConfigPage.tsx`) · 배차 지역 설정 화면(`DispatchGroupPage`) ·
세트 구성품 비율(`#1093 CLOSED` / `#1143 OPEN`) · 단가변동 이력(`price_history` 테이블 + `#1140 OPEN`).
매번 개발책임자가 *"이미 정한 결정이 있을텐데?"* 로 정정해야 했다.
그리고 조사 산출물도 같은 병을 앓았다 — Critic 이 원문 결정 50건 중 **상당수가 이미 저장소에 있다**고 걸러냈다.

🔑 **가장 자주 놓치는 축은 ②의 CLOSED 다.** 이 저장소는 기능을 이슈로 완결하고 닫는다.
`--state open` 만 보면 구현된 기능이 통째로 안 보인다.

🔑 **"기능이 없다" 와 "이름이 다르다" 를 구분하라.** 레거시 이름으로 grep 해서 안 나오는 것은
없는 것이 아니라 **우리 이름으로 있는 것**일 수 있다. 도메인 개념으로도 찾아라.
(실측: 원본 전용 이름 257개 중 **109개가 '대체'** — 이름만 다르고 기능은 있었다.)

## How to apply

**조사·제안 산출물의 모든 항목에 네 열을 의무화한다:**

| 열 | 내용 |
|---|---|
| `existing_file` | 대응 코드가 있으면 `파일:줄`, 없으면 **검색어와 함께** `없음(grep: …)` |
| `existing_issue` | 이슈 번호 + OPEN/CLOSED, 없으면 `없음` |
| `prior_decision` | 관련 기존 결정, 없으면 `없음` |
| `semantic_delta` | 있는데도 올리는 경우 **무엇이 다른지** |

🚨 **하나라도 걸리면 질문이 바뀐다** — *"만들까요?"* 가 아니라
*"이미 있는 것과 이렇게 다른데 맞출까요?"* 이고, 재현 fixture 로 그 차이를 보여야 한다.

🚨 **거르는 것도 보고하라.** 몇 건을 왜 걸렀는지 남기지 않으면 다음 라운드가 또 올린다.

관련: [[feedback-always-present-options-for-decisions]] — 올릴 것이 남았을 때 비로소 선택지를 만든다.
[[feedback-conflict-is-mostly-one-sided-blank]] — 올리기 전에 "고를 게 있긴 한가" 를 먼저 센다.

## 🚨 2026-08-14 새 구멍 — **산출물이 아니라 "브리핑" 에서 샜다**

위 규칙은 **조사·제안 산출물**에 네 열을 요구한다. 그런데 이번에 샌 곳은 그 앞이다 —
**PM 이 정찰 브리핑을 쓸 때 기존 결정을 안 훑었다.**

```text
#999 축③ QR 스캔 입출고 정찰을 발주하며 PM 이 축 A 를 "QR 에 무엇을 담는가" 로 열어 두었다
정찰자도 그대로 미결로 올렸고, PM 이 개발책임자에게 선택지로 물었다

개발책임자: "다만 QR은 실내기, 실외기, 판넬에 한함. 이미 예전에 결정한 사안"

실측 — 저장소에 이미 있었다
  .claude/memory/project_serial_inventory_model.md:42
    QR 스캔 입출고 — 대상 실외기·실내기·판넬(부자재 제외)
    QR 에 담는 값은 시리얼키(UUID 아님)
```

🔑 **정찰자는 브리핑에 없는 것을 스스로 찾지 않는다.** PM 이 "이건 열린 질문" 이라고 적으면 정찰자는 그렇게 다룬다. 이미 닫힌 것을 PM 이 다시 열면 **개발책임자가 같은 결정을 두 번 한다.**

### How to apply — 정찰·기획 브리핑을 쓰기 전에

```text
1  .claude/memory/ 에서 그 도메인 파일을 먼저 읽는다
   (project_*.md 가 도메인 정본이다 — 이번 것은 project_serial_inventory_model.md 였다)
2  docs/decisions/ 에서 그 이슈·인접 이슈를 grep 한다
3  브리핑에 "이미 결정된 것" 절을 만들어 근거 경로와 함께 적는다
   ⟹ 정찰자가 그것을 미결로 다시 올리지 않는다
4  그래도 미결이면 그때 축으로 연다
```

🚩 **`gh issue view` 만으로는 부족하다.** 이 저장소의 도메인 결정은 이슈 본문이 아니라 **메모리와 `docs/decisions/`** 에 쌓인다.

🔑 판단 기준 — *"이 질문을 개발책임자가 전에 답한 적이 있는가?"* 를 **묻기 전에 검색**한다.
같은 결정을 두 번 묻는 것은 라운드를 태우는 것보다 나쁘다 — 신뢰를 깎는다.

## 🚨 2026-08-16 세 번째 구멍 — **선택지의 "전제" 가 틀렸다**

> 개발책임자: *"질문하기 전에 다시 제대로 정찰해."*

앞의 두 절은 *"이미 결정된 것을 다시 묻지 마라"* 다. 이번에 샌 곳은 다르다 —
**질문 자체는 새것이었는데 그 질문이 깔고 있는 사실이 틀렸다.**

```text
PM 질문   "레거시는 GAS 시트/Notion 을 기준으로 쓰고 현행은 product_db 를 쓴다.
           어느 쪽이 가격·상품의 정본인가?"
사실      시트/Notion 데이터는 이미 우리 DB 로 이관이 끝났다.
          "두 정본이 경합" 하는 상태가 아니었다
개발책임자  "GAS 시트와 노션을 우리 DB로 데이터를 옮겼잖아."

PM 질문   "배차·DPS 는 레거시가 외부 파일을 기준으로 대조한다. 외부 파일 업로드를 만들까?"
사실      배차 원천은 이미 우리 출고전표 DB 다. 외부 파일이 필요한 것은 DPS 쪽뿐이다
개발책임자  "배차는 우리 출고전표 DB를 가져오는거고 DPS관련 자료만 엑셀로 받기로 했잖아."
```

🔑 **정찰 요약본만 읽고 선택지를 만들면 이렇게 된다.** 대조 보고서는 *"레거시는 A, 현행은 B"*
라고 적어 주지만, **그 둘이 지금도 경합하는지**는 말해 주지 않는다.

### How to apply — 선택지를 쓰기 전에

```text
🚨 각 선택지의 전제를 한 줄로 적어 보고, 그 한 줄이 사실인지 실측하라
   "지금 두 원천이 경합한다" 는 전제인가?  → 정말 둘 다 살아 있는지 확인
   "그 기능이 현행에 없다" 는 전제인가?     → 이름이 다를 뿐인지 확인
   "외부 파일이 필요하다" 는 전제인가?      → 우리 DB 에 이미 있는지 확인
🚨 전제가 흔들리면 선택지를 만들지 말고 정찰을 한 번 더 돌려라
   틀린 전제로 만든 선택지는 개발책임자가 고쳐 줘야 한다 — 그게 두 번 일하게 만든다
```

🚩 **분류·요약 산출물은 전제를 보증하지 않는다.** Ⓐ/Ⓑ/Ⓒ 로 나눈 표는 "판단이 필요하다"
까지만 말한다. **무엇을 판단해야 하는지는 PM 이 실측으로 세워야 한다.**
