# 🚨 TODO 는 **트랙별로 하나**, **단계마다 갱신**

**2026-08-05 개발책임자 지시.**

> *"TODO 리스트는 트랙별로 다시 재갱신."*
> *"TODO리스트는 계속 단계가 끝날때마다 갱신 요망."*

## 규칙

1. **한 트랙 = 한 항목.** `[#1045 가배차]` 처럼 **PR·이슈 번호를 제목 앞에** 붙인다. 라운드마다 새 항목을 만들지 않는다.
2. **항목 제목에 게이트 상태를 적는다** — `①0 ✅(S24) — S25 라이브QA 통과하면 머지` 처럼 **지금 어디에 있고 다음 한 수가 무엇인지**가 제목만 보고 읽혀야 한다.
3. **단계가 끝날 때마다 갱신한다.** 라운드 완료·게이트 충족·머지·차단 — 상태가 바뀌면 바로 `TaskUpdate`. 나중에 몰아서 하지 않는다.
4. **머지되면 머지 커밋 SHA 와 close 한 이슈 번호**를 제목에 남기고 completed 로 바꾼다.
5. **대기 중인 트랙도 항목으로 둔다** — 무엇을 기다리는지(`#1057 머지 대기`)를 적어야 잊히지 않는다.
6. 백로그는 하나로 묶되, **해제 조건**을 적는다(`#1063 머지 후`).

## 🚨 7. 사용자 보고 문장은 **TODO 와 일치해야 한다** (2026-08-06 개발책임자 지적)

> *"트랙 전부 진행 중이 맞아?"* · *"TODO는 왜 갱신안해?"* · *"사실이 아닌 상태를 보고하면 안되지."*

**실측된 위반 (2026-08-06 회사PC)**

```text
PM 이 쓴 것    "일곱 트랙 전부가 진행 상태로 들어갔습니다"
실제           codex 실행 2개 · CI 감시 1개 · 나머지 4개 대기
PM 이 쓴 것    "#1037 SOL 이 낸 결함 2건의 fix 를 이어서 발주하겠습니다"
실제           발주하지 않은 채 다음 트랙으로 넘어가 그대로 잊혔다
               (개발책임자가 물어서야 드러남)
```

🔑 **원인은 두 가지가 겹친 것이다.** ①TODO 를 상태 변화 시점이 아니라 몰아서 갱신했고 ②보고 문장을 TODO 가 아니라 **기억**으로 썼다. 기억은 "하겠다" 와 "했다" 를 구분하지 못한다.

**규칙**

```text
· 보고에 쓰는 트랙 상태는 TODO 에서 읽어 쓴다. 기억으로 쓰지 않는다
· 🚨 발주하지 않은 것은 "진행 중" 이 아니다 — "다음 한 수" 로만 적는다
· "이어서 …하겠습니다" 라고 썼으면 그 턴 안에 실제로 도구를 호출하거나,
  못 했으면 TODO 에 미실행으로 남긴다
· 트랙 수를 셀 때 **무엇이 실제로 돌고 있는지**(codex/모니터/대기)를 구분해 적는다
```

⚠️ 이 저장소에는 이미 *"도구 호출을 텍스트로 적으면 미실행"* 규칙이 있다([[feedback_emit_real_tool_calls]]). 이번 건은 그 변형 — **선언은 했는데 호출을 안 했고, 다음 보고에서 한 것으로 셌다.**

## Why

트랙이 5~6개 병렬로 돌면 **어느 트랙이 어느 게이트에서 막혀 있는지**가 PM 머릿속에만 남는다. 그러면 같은 것을 두 번 시키거나(오늘 `#1064` 중복 트랙 실측), 끝난 트랙의 다음 한 수를 놓친다. TODO 가 **트랙 상태판** 역할을 해야 한다.

## How to apply

```
[#1045 가배차] ①0 ✅(S24) — S25 권역 라이브QA 통과하면 머지 (#1057 보다 먼저)
[#1057 riUsage] main 병합 완료(d61093969) · ②CI green · 남은 것은 라이브QA
[#1069 세트 전개] S1→S3→S5 fix · SOL 이 매 라운드 새 결함 — S7 이 fix 상한 3번째
[백로그] #1075 · #1068 — #1063 머지 후
```

- description 에는 **HEAD SHA · 실측 수치 · 다음 라운드 근거**를 적는다.
- 🚨 **트랙 상태를 볼 때 `SOL 실행 횟수`를 함께 센다** → [[feedback_sol_stage_starvation]]
