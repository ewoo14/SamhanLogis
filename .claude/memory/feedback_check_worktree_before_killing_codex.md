개발책임자 지적: *"아니 다 끝낸 뒤였다니 그걸 왜 자꾸 뒤늦게 확인하는거야"*

**실측 (2026-08-02).** 개발책임자 PC 자원 확보를 위해 codex 3개(#1046 #1048 #1060)를 즉시 중단하고
개발책임자께 *"진행분이 전부 날아갔다"* 고 보고했다. **틀렸다.** 이후 `git status` 로 보니
#1046 · #1048 은 **코드·테스트·보고서가 완성돼 있었다**(RED/GREEN 원문 · 모듈 전체 테스트
`626 tests` / `542 tests` · 불변식 실측 · 11경로 재집계표까지). 두 세션은 일을 끝내고
마무리 중이었다. #1060 만 실제로 0건이었다.

**왜 틀렸나.** 메모리의 *"실행 중 codex 강제 종료 금지 — 산출물 0"*
([[feedback_parallel_backend_tracks_share_docker_stack]]) 을 **확인 대신 가정으로 썼다.**
그 규칙은 *작업 중*인 세션 얘기지 **끝낸 세션에는 해당하지 않는다.**
같은 세션 초반 유령 프로세스를 정리할 때는 워크트리를 먼저 확인하고 죽였는데,
급해지자 그 절차를 건너뛰었다.

**How to apply:**
- 🔑 **`TaskStop` 전에 해당 워크트리 `git status --porcelain` 을 먼저 본다.** 명령 하나다.
- 🔑 죽인 뒤 **"날아갔다"고 보고하기 전에도** 반드시 확인한다 — 개발책임자가 잘못된
  손실 보고를 근거로 재발주를 결정할 수 있다.
- 🔑 파일이 남아 있으면 **재발주가 아니라 검증→커밋**이 다음 수다. 완성도 판단은
  보고서에 `RED`/`GREEN`/`BUILD`/`미완` 이 있는지로 빠르게 가른다.
- 규칙을 근거로 **관찰을 생략하지 말 것**. 규칙은 관찰의 우선순위를 정할 뿐이다.

**Why:** 잘못된 손실 보고는 실재하는 산출물을 버리게 만들고, 같은 작업을 두 번 시켜
처리량 병목([[feedback_codex_parallel_throughput_collapse]])을 스스로 키운다.
