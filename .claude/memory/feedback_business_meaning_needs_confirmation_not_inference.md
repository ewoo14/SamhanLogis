# 🚨 **업무 의미는 추론하지 말고 확인받는다**

> 개발책임자 (2026-08-06)
> *"전제가 여러 번 틀렸다면 나한테 확인을 받아야 하는 것 아닌가? 함부로 추측한 것은 추후 설계를 다시 변경해야할 수 있어."*

## 한 세션에 다섯 번 틀렸고, 전부 같은 성격이었다

| PM 이 브리핑에 넣은 전제 | 실제 | 어떻게 틀렸나 |
|---|---|---|
| 세트 `bundle_component` 13행 = **13행 전개** | 계열별 **선택지** · `is_default` 로 4행이 정답 | 행이 있으면 다 쓰는 줄 알았다 |
| 전역DC `500` = **제품 결함** | **8일 낡은 배포본** (소스엔 매핑 존재) | 증상을 원인으로 단정 |
| `has_variable_discount = true` → **할인된다** | **원칙적 자격**일 뿐 · `categoryKey=singleSets` 엔 적용 율이 없다 | 불리언 이름에서 업무 규칙을 읽었다 |
| UUID `v3` = **구형 dev 시드** 표식 | `UUID.nameUUIDFromBytes`(MD5) 결과 — **시드 세대와 무관** | 기술 표식으로 정체를 단정 |
| `RegionalService` 의 **17개 시도 방식이 틀렸다** | 선별은 이미 `deliveryTag=REGION` · 시도는 **표시 그룹 키** | 메모리 규칙을 코드 확인 없이 적용 |

🔑 **전부 "데이터·코드에서 업무 의미를 추론" 한 것이다.** 다섯 번 다 검증자가 반려해 살았지만, **반려되지 않았으면 그대로 설계에 박혔다.**

## 규칙 — 두 종류를 섞지 않는다

```text
측정 가능한 사실        PM 이 직접 잰다. 확인받지 않는다.
  행 수 · 채움률 · 배포 생성 시각 · CI 결과 · git diff · 파일 존재 · 참조 grep

업무 의미               추론하지 않는다. 셋 중 하나로만 확정한다.
  ① 레거시 원문을 **PM 이 직접 읽는다**
  ② 코드의 명시적 계약(Javadoc·계약 테스트·enum 정의)을 **직접 읽는다**
  ③ 개발책임자께 **확인받는다**
  예: 이 컬럼이 무엇을 뜻하나 · 이게 결함인가 · 무엇이 정본인가 ·
      어느 것이 권위 원본인가 · 이 동작이 의도된 것인가
```

## 특히 위험한 형태

- **후보를 권위로 승격**하는 것. 조사 보고서가 *"후보 A~E, 확정하지 않음"* 으로 올린 것을 PM 이 하나 골라 브리핑에 *"권위 원본은 X 다"* 로 쓰면, 그 선택이 설계에 박힌다. **고르는 것은 개발책임자 몫이다.**
- **"이 방향이 맞는지도 당신이 판단하십시오"** 로 헤지하는 것. 구현자는 대개 주어진 방향으로 간다. 헤지는 확인이 아니다.
- 메모리 규칙을 **해당 코드를 안 읽고** 적용하는 것. 규칙은 다른 맥락에서 만들어졌을 수 있다.

## How to apply

브리핑에 문장을 쓰기 전에 자문한다 — **"이 문장은 내가 잰 것인가, 내가 해석한 것인가?"**

```text
잰 것    그대로 쓴다. SQL·명령 원문을 함께 넣는다
해석한 것 ①레거시 원문 ②명시적 계약 ③개발책임자 확인 — 셋 중 하나를 붙이거나,
          붙일 수 없으면 **브리핑에 넣지 말고 질문으로 올린다**
```

그리고 **이미 설계에 박힌 추측은 소급해서 올린다.** 되돌리는 비용이 라운드 하나보다 크다.
