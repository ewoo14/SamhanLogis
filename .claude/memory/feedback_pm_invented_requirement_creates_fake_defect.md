# 🚨 PM 이 지어낸 요구값 = 가짜 결함

## 실측 — `#1187` 리모컨 「특징」 드롭박스

라이브QA9 가 **도달 가능한 결함 1건**을 올렸다.

```text
요구값     기본 · 유선리모컨 · 컬러유선리모컨
실제 화면  기본 · 유선 · 컬러          ← "결함"
```

fix 라운드를 발주했는데 개발책임자가 잘랐다.

> *"1187은 **짧게 특징 값을 하기로 했잖아.** 그러면 요구값을 변경해줘야지."*

**구현이 맞았고 PM 이 넣은 요구값이 틀렸다.** fix 를 중단하니 작업 트리 변경 0건이었고,
그 PR 은 결함 0 으로 바로 머지됐다.

## 🔑 왜 이런 요구값을 지어냈나 — 두 축을 섞었다

PM 은 앞선 라운드에서 개발책임자의 정정을 이렇게 기억하고 있었다.

> *"유선리모컨 모델명도 모두 틀렸어. AWR로 시작해야하는데 왜 MWR로 들어가 있는거야?"*

그래서 실 DB 실측 정본 `기본(188) · 유선리모컨(62) · 컬러유선리모컨(65)` 을
**화면 드롭박스 라벨로 그대로 밀어 넣었다.** 그런데 그 둘은 다른 축이다.

```text
데이터 정본     실 DB 의 변형 명칭 · 모델코드 (AWR-, MWR 은 0건)
화면 표시 라벨  드롭박스에 보이는 글자 — 짧게 쓰기로 결정돼 있었다
```

**데이터 정본을 바로잡은 것이 화면 라벨까지 바꾸라는 뜻은 아니었다.**

## How to apply

**적대검증 브리핑에 요구값을 적을 때는 출처를 함께 적는다**
> 요구값 옆에 *"이 값의 출처 = 개발책임자 발언 원문 / 실 DB 실측 / spec 문서 N줄"* 을 적으십시오.
> 출처를 못 적겠으면 **그 요구값은 PM 이 지어낸 것**입니다.

**실 데이터 정본과 화면 표시는 따로 확인한다**
> DB 값을 고쳤다고 라벨까지 같이 고치지 마십시오. 라벨은 **별도 결정**입니다.

**"결함" 이 요구값 불일치 하나뿐이면 fix 전에 요구값부터 되묻는다**
> 도달성 결함이 *"값이 A 여야 하는데 B 다"* 형태 하나뿐이면, 고치기 전에
> **A 가 어디서 온 값인지** 확인하십시오. 오늘 실측 1건이 여기서 갈렸다.

**fix 를 중단할 수 있으면 즉시 중단한다**
> 요구값 오류가 확인되면 `TaskStop` 으로 바로 끊고 작업 트리를 확인하십시오.
> 이번엔 변경 0건이라 되돌릴 것이 없었다. 늦게 알수록 지워야 할 fix 가 쌓인다.
