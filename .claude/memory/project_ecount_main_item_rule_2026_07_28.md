# 이카운트 대표품목 판정 규칙 (2026-07-28 개발책임자 결정)

> 개발책임자 원문: *"품목코드와 품목명이 일치하는 품목이 대표품목이며, 사실 추후에 추가된 품목인데, 해당 품목으로 모두 변경할 예정."*

[[ecount-product-identity-rule]](2026-05-19) 의 **대표 선정 기준을 구체화**한 결정이다. 그때는 *"품목관계 매핑으로 같은 품목 판정"* 까지만 정해져 있었고 **어느 쪽이 대표인지**가 비어 있었다.

## 실측 — 규칙이 어디까지 성립하는가 (2026-07-28 · `기초품목.xlsx` 2,854행)

이름 충돌 그룹 **164개 / 328행**(고유 품목명 2,689).

| 분류 | 그룹 | 내용 | 예시 |
|---|---:|---|---|
| **A** 코드 == 명 | **116** | 규칙 그대로 성립 | `절삭` → 코드 `절삭` vs `00013` |
| **B** 공백만 다름 | **6** | 코드가 명에서 공백 제거 형태 | `방진가대 S2 소` → `방진가대S2소` vs `00196` |
| **C** 코드 == 괄호 앞부분 | **13** | 코드가 명의 괄호 이전 토큰 | `PC2NWSK1N (신형 2WAY 판넬)` → `PC2NWSK1N` vs `00219` |
| **E** 결정 불가 | **29** | 양쪽 코드가 명과 무관 | `바람막이` → `AAAA-00008` vs `ZENG-00009` |

A+B+C = **135/164 (82%)**.

🔑 **교차검증** — C 분류의 `AXJ-TA3419M (T형 분기관)` 이 고르는 대표코드 `AXJ-TA3419M` 은 **구글 시트 마스터가 쓰는 `model_code` 와 동일**하다. 규칙이 시트 정본과 같은 답을 낸다.

## 🔑 그런데 코드 변경이 필요 없을 수 있다

`EcountProductImporter.resolveMainCandidate` 의 판정 순서는 이미 이렇다:

```
① 품목관계 CSV 의 alias→대표 매핑(explicitMainCode)
② 품목관계에 대표로 등재된 코드(relationMainCodes)
③ DB 에 같은 품목명으로 존재하는 활성 품목(findActiveProductCodeByName)
④ 품목명이 유일하면 자기 자신이 대표
⑤ 그 외 → MIG2_NO_MAIN_CANDIDATE 로 fail-closed
```

**품목관계 테이블이 대표를 정한다는 규칙이 이미 구현돼 있다.** 2026-07-28 의 422(`name=절삭, sourceRowNo=15`)는 그 파일이 없어서 ①②를 건너뛰고 ⑤로 떨어진 것이다.

⟹ **순서**: 품목관계 export 를 받아 먼저 임포트하고, **그래도 남는 그룹에만** B·C 확장을 코드로 넣는다. 불필요한 코드 변경은 그 자체가 다음 라운드의 감사면이 된다([[feedback_canonical_workflow]] — fix 부피가 곧 감사면).

## ⚠️ 관찰 — ③이 임포트 결과를 DB 상태에 의존시킨다

`findActiveProductCodeByName` 은 **현재 DB 에 무엇이 들어 있는지**에 따라 대표를 다르게 고른다. 2026-07-28 에는 구글 시트 sync(품목 1,220)를 **먼저** 돌린 뒤 임포트를 시도했으므로, 같은 CSV 라도 sync 전/후 결과가 달라질 수 있다. 재현성이 필요한 검증에서는 **DB 상태를 함께 기록**할 것.
