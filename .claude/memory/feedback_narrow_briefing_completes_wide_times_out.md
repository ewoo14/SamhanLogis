# 🚨 브리핑을 **좁혀야 완주**한다 — 넓은 브리핑은 산출물이 0이다

2026-07-28 PR #957 의 CODEX SOL 라운드 실측:

| 시도 | 브리핑 범위 | 결과 |
|---|---|---|
| 1차 | 10사본 × 경로 표기 판정표 + 무력화 sweep + 플랫폼×에디션 격자(Docker Linux/pwsh7) + 이월 4건 | **7200초 타임아웃 · 산출물 0** |
| 2차 | 위에서 3개로 축소(판정표 + sweep + 증거 대조) | **7200초 타임아웃 · 산출물 0** |
| **3차** | **단일 항목** — *"판정 실패가 통과 쪽으로 새는 지점"* 만. 테스트·Docker·판정표 전부 제외, 코드 읽기 중심 | **완주 · 도달가능 6건** |

**4시간을 태우고 0건**이던 것이 **한 항목으로 좁히자 6건**이 나왔다. 그 6건은 `fs.existsSync()` 가 접근 오류에서도 `false` 를 돌려주는 것을 Node 계열 6벌이 *"경로 없음"* 으로 단정해 **물리 식별을 잃은 채 통과**시키던 실제 결함이었다.

## 왜 그런가

MCP codex 는 **7200초에 강제 종료**되고, 그 시점까지의 산출물이 **하나도 남지 않는다**. 즉 범위가 크면 "덜 찾는" 게 아니라 **아무것도 못 받는다**. 반면 좁은 브리핑은 완주하고, 완주한 한 각도가 넓은 미완주보다 훨씬 낫다.

## 규칙

- **브리핑에 "이번에 하지 마십시오" 절을 명시**한다. 무엇을 빼는지가 무엇을 넣는지만큼 중요하다.
- **비싼 항목을 먼저 뺀다** — 다른 OS 컨테이너 기동 · 대규모 스위트 실행 · 버전 매트릭스 재설치. 이것들이 시간을 먹는다.
- **"시간이 부족하면 ①만 완성하고 나머지는 미수행으로 적은 뒤 반드시 저장·보고하라"** 를 브리핑에 넣는다. 부분 산출물이 0보다 낫다.
- 빠진 항목은 **PR 에 "이 라운드가 보지 않은 것" 으로 남기고 다음 라운드로 이월**한다([[feedback_unverified_scope_is_not_zero_defects]] — 안 본 것을 0 으로 세지 않는다).
- **한 라운드에 각도 하나**. 여러 각도를 한 브리핑에 묶지 말고 나눠서 여러 번 돌린다.

## 🚨 2026-07-31 재발 — **"부족하면 ①만 하라" 지시로는 못 막는다**

PR #984 SOL 라운드에 각도 **5개**를 주면서 *"시간이 부족하면 첫 번째 각도만 완주하고 저장·보고하십시오"* 를 명시했다. 결과는 **7200초 타임아웃 · 산출물 0건**. 2시간을 태웠다.

🔑 **그 지시는 작동하지 않는다.** 리뷰어는 "부족하다" 를 스스로 판정하지 못하고 계속 조사하다 잘린다. 잘리면 메모리에 있던 것이 전부 사라진다.

### 그래서 두 가지를 **동시에** 건다

1. **각도를 애초에 1~2개만 준다.** 5개를 주고 "①만 해도 된다" 고 쓰는 것은 5개를 주는 것이다.
2. 🆕 **중간 저장을 강제한다** — 브리핑 맨 앞에 이렇게 넣는다:
   > *"조사를 시작하기 **전에 먼저** 보고서 파일을 만들고 제목만 적어 저장하십시오. **하나를 확인할 때마다 즉시 append 하고 저장**하십시오. 마지막에 몰아 쓰지 마십시오. 시간이 다 되어도 그때까지 확인한 것이 파일에 남아 있어야 합니다."*

   타임아웃이 산출물을 0으로 만드는 이유는 **결과를 마지막에 한 번에 쓰기 때문**이다. append 를 강제하면 잘려도 부분 산출물이 남는다.
