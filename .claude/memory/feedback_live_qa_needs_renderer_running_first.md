# 🚨 "로그인 화면에서 막혔다" = 결함이 아니라 **renderer 미기동**

2026-08-15 밤, 두 트랙이 같은 문장으로 캡처 0 을 보고했다.

```text
#1214  "실제 앱은 로그인 화면에서 인증이 필요해 목록 화면 관측 불가"
#1218  "기존 5175 renderer 가 로그인 후 /login 에 남아 캡처 생성 못 함"
```

🔑 **둘 다 결함처럼 읽힌다.** "로그인이 안 된다" 로 들리기 때문이다.
실제 원인은 **renderer `:5175` 가 안 떠 있었던 것**이었다. API Gateway 는 정상 응답하고 있었다.
띄우고 나니 MANAGER 로그인은 `#/` 홈으로 정상 이동했다.

## 대가

```text
#1214 S1  구현은 됐는데 캡처 0 으로 라운드 종료 → 다음 라운드로 이월
#1218 S1  같은 이유로 캡처 0 → 별도 캡처 라운드를 따로 발주
⟹ 라운드 2개가 "환경이 안 떠 있었다" 하나로 날아갔다
```

🚩 그리고 더 나쁜 것 — **한 트랙이 이것을 진단하기 전까지 아무도 몰랐다.**
두 트랙 다 "관측 불가" 로 정직하게 적었지만, 정직한 보고가 원인 규명은 아니다.

## How to apply — 라이브QA 브리핑에 기동 절차를 먼저 넣어라

캡처를 요구하는 **모든** 브리핑 맨 앞에:

```text
🚩 캡처 전에 renderer 가 떠 있는지 먼저 확인하라 (안 떠 있으면 띄워라)
   안 띄우고 로그인하면 /login 에 머문다 — 이건 결함이 아니라 미기동이다
🚩 "로그인 화면에서 막혔다" 로 라운드를 끝내지 마라
   그 문장이 나오려 하면 ① renderer 기동 여부 ② Gateway 응답 여부를 먼저 갈라라
```

🔑 **관측 불가로 적는 것과 원인을 안 파는 것은 다르다.**
"관측 불가" 는 통과로 세지 않기 위한 정직성이고, 그 다음에 **왜 못 봤는지**는 여전히 답해야 한다.

🚩 반대 방향도 조심하라 — 진짜 로그인 결함일 수도 있다.
`#1218` 은 renderer 를 띄운 뒤 **정상 이동을 실제로 확인하고** "결함 아님" 으로 판정했다.
띄우지도 않고 "환경 탓" 으로 넘기면 진짜 결함을 놓친다.
